# 知识库_编译框架

## Sparse Abstract Machine (SAM)

术语是什么？

Sparse Abstract Machine (SAM) 是 Hsu et al. (ASPLOS 2023) 提出的面向**稀疏张量代数的数据流抽象机器模型**。SAM 将稀疏张量代数计算表达为**流式数据流图**（streaming dataflow graph），其中张量被表示为流经数据流原语（dataflow primitives）的 token 序列（streams），而非传统的内存驻留多维数组。

SAM 的核心抽象包括：
1. **Streams**：三种类型的 token 序列——坐标流（crd，crd）、内部引用流（ref）、值流（val）。一个 n 阶张量由 n 个坐标流 + 1 个值流表示（共 n+1 条 stream）。
2. **Dataflow Primitives**（数据流原语）：9 种可组合的功能块：
   - **Level Scanner (LS)**：遍历张量层级，按 fibertree 格式产生坐标和引用流。嵌套 LS 产生等价于多维张量的流。
   - **Intersect/Union (Stream Joiner)**：合并或跳过跨张量坐标。Intersect 只输出所有输入共有的坐标（交集），Union 输出所有坐标（并集）。
   - **Repeater (Rep)**：广播操作数，按 repeat signal 复制值。
   - **ALU / Reducer (Red)**：执行逐元素计算和归约。
   - **Level Writer (LW) / Coordinate Dropper (CD)**：写回结果坐标和值，丢弃零坐标。
3. **SAM Graph 结构**：由三个区域组成——Input Iteration（蓝色，遍历所有输入张量坐标并 join 稀疏坐标）、Computation（黄色，获取数据值并计算结果值）、Tensor Construction（红色，将结果写回内存并丢弃零坐标）。如图 2 所示，以稀疏矩阵-向量乘法（SpMV）$T_i = B_{ij}C_j$（dataflow $j \to i$）为例。

SAM 将张量表示为 **fibertree** 形式——一种以层级（level）组织的坐标嵌套表示，每个层级包含：pos（指向下一层级起始位置的指针数组）、crd（坐标值数组）、可选的 val（值数组）。这种表示天然支持压缩稀疏格式（如 CSR、DCSR、COO 等）。

从编译框架角度拆解术语：

SAM 在编译流程中充当 **编译器中间表示（IR）**，将高层稀疏张量代数（Einsum 表达式）与底层数据流硬件解耦：

```
高层输入: Einsum 表达式 (如 T_i = B_{ij} C_j，指定 dataflow j → i)
    ↓ Custard / FuseFlow 编译
SAM Graph: LS(C_j) → LS(B_{ij}) → Intersect(j) → Rep(C across i)
            → ALU(B×C) → Red(j) → LW(T_i) → CD(T_i)
    ↓ SAM→Hardware lowering
物理硬件: CGRA PE 阵列 (如 Onyx [42], Opal [10]) 或 FPGA
   每个 SAM primitive 对应一个硬件模块，streams 对应物理连线
```

具体流程（以 SpMV $T_i = B_{ij} C_j$，CSR 格式的 B，$j \to i$ dataflow 为例）：
1. **Level Scanners**：LS(C_j) 遍历稠密向量 C 的 j 坐标，产生 crd stream `{j_0, j_1, ..., j_{J-1}}` 和 val stream `{C[j_0], C[j_1], ...}`。LS(B_i) 遍历 CSR 矩阵 B 的 i 层级，产生 crd stream `{i_0, i_1, ...}` 和 ref stream 指向 j 层级。LS(B_j) 通过 ref stream 定位 B 的具体 j 坐标。
2. **Intersect(j)**：比较 LS(B_j) 和 LS(C_j) 的 crd streams，仅输出两者都有的坐标（匹配的非零位置），跳过 C 中的零值对应坐标和 B 中的空行。
3. **Rep(C across i)**：对每个 i，重复 C 的 val stream（因为 B 的每行都需要与整个 C 做内积）。
4. **ALU(B×C)**：逐元素乘法，输入 B_val 和 C_val streams，输出乘积 stream。
5. **Red(j)**：对乘积 stream 按 j 维度归约（累加），输出 T_i 的 val stream。
6. **LW(T_i) + CD(T_i)**：写入 T 的坐标和值，丢弃零坐标（若某个 i 的累加结果为 0）。

术语一般如何实现？如何使用？

SAM 最初由 Custard 编译器 [Hsu et al., ASPLOS 2023] 实现，从高层 Einsum 表达式编译到 SAM graph。FuseFlow 将 SAM 重新实现为 **MLIR dialect**，并扩展为 **SAMML**（增加非线性函数、masking、dense blocks 支持）。SAM graph 可通过以下方式执行：
- **Comal 模拟器**（基于 DAM framework [81]，Rust 编写）：cycle-accurate 仿真 SAM graph 的执行
- **Onyx CGRA [42]**：物理芯片（12nm，756 GOPS/W），将 SAM primitive 映射到 CGRA PE
- **Opal CGRA [10]**：后续芯片（16nm），增加稀疏 ML 支持
- **FPGA 综合**（Vitis HLS → Xilinx VU9P）：将 SAM graph 综合为硬件比特流

涉及论文标题：
- FuseFlow

## Cross-Expression Kernel Fusion (EKF / 跨表达式核融合)

术语是什么？

Cross-Expression Kernel Fusion (EKF) 是一种**跨多个独立张量代数表达式（kernel）进行融合的编译技术**。不同于传统的单一表达式内融合（IIF），EKF 跨越 kernel 边界，将多个 producer-consumer 表达式合并为一个融合计算图，消除中间张量的内存物化。

在稀疏计算中，EKF 面临稠密计算中不存在的独特挑战：每个表达式有自己所需的张量遍历顺序（mode order），跨表达式融合时必须保证所有张量的遍历是 **concordant**（与存储格式一致），否则会导致渐进复杂度退化。FuseFlow 是首个支持通用 EKF 的稀疏编译器。

EKF 与另外两种融合形式的关系：
- **Pattern-based Operator Fusion (POF)**：基于识别已知算子模式进行替换（如 XLA、TensorRT），限于预定义模板，是 intra-layer 技术。
- **Intra-Expression Iteration Fusion (IIF)**：在单个表达式内融合迭代空间（co-iteration），TACO、Custard、Stardust 等稀疏编译器支持。
- **EKF**：跨表达式/kernel 边界融合，FuseFlow 首创于稀疏数据流编译器领域。

从编译框架角度拆解术语：

FuseFlow 的 EKF 算法流程（Section 5）：

```
输入: Fuse{} region 内的 Einsum 表达式 E = {E1, E2, ..., En}
      每个张量的 mode order（存储格式要求的遍历顺序）
      用户可选的局部 dataflow order
输出: Fused Einsum subgraphs + Partial Order Graph (POG)

Step 1: Rename Local Indices
  for each E_i:
    for each reduction index r (不在 LHS 上):
      r' = fresh_index()  // 避免跨表达式命名冲突
      替换为 r'

Step 2: Build Fused Einsum via Index Substitution
  for each tensor T that is a producer result:
    consumer = find_expression_using(T)
    // 将 T 在 producer 中的输出索引替换为 consumer 中的输入索引
    // 例如: producer T_{ij} = A_{ik} B_{kj}
    //       consumer O_{il} = T_{ij} C_{jl}
    //       → O_{il} = A_{ik} B_{kj} C_{jl} (substitute T_{ij} away)

Step 3: Propagate Order Constraints in POG
  for each producer→consumer index mapping:
    POG.add_edge(outer_index, inner_index)  // 保持 outer-to-inner 顺序
  // POG 节点 = 索引变量，有向边 = 顺序约束
  // 约束来源: (i) 张量存储 mode order, (ii) 用户 dataflow order

Step 4: Handle Multiple Tensor Uses
  for each tensor used in multiple expressions:
    views = create_distinct_views(tensor)  // 每个 use 有独立 view
    if conflicting_mode_orders(views):
      if detect_cycle(POG):
        materialize_permuted_copy(tensor, conflicting_view)  // 打破循环

Step 5: Topological Sort
  if POG.has_cycle():
    error: "No concordant fusion exists"
  else:
    return all topological_sorts(POG)  // 所有合法 global dataflow order
```

**关键设计决策**：EKF 通过 POG 将 ordering constraints 作为一等公民处理，而非事后检查。当多个 view 产生冲突约束时，FuseFlow 通过物化一个 permuted copy（高阶转置）来打破 POG 中的循环，而非放弃融合。这保证了 EKF 的通用性——任何存在合法遍历顺序的融合都可以被找到。

术语一般如何实现？如何使用？

EKF 在 FuseFlow 中通过用户的 `Fuse{}` region 标注触发。用户显式指定哪些表达式需要融合：
```
Fuse{
  %0 = linalg.einsum "ij, jk -> ik" (%A, %W)
  %1 = linalg.einsum "ik, kj -> ij" (%B, %0)
  %2 = linalg.relu(%1)
}
```
FuseFlow 自动处理 `Fuse{}` 内的所有 EKF，无需用户手动重写表达式。融合粒度由 `Fuse{}` 边界控制：partial fusion（层内融合）vs full fusion（跨层融合）。EKF 与 IIF（factored iteration）组合：EKF 决定哪些表达式融合，IIF 决定融合后如何遍历迭代空间。

涉及论文标题：
- FuseFlow

## Intra-Expression Iteration Fusion (IIF / 表达式内迭代融合)

术语是什么？

Intra-Expression Iteration Fusion (IIF) 是在**单个张量代数表达式内部**融合迭代空间的编译技术。对于稀疏张量，IIF 体现为 **co-iteration**（联合迭代）——同时遍历多个稀疏输入张量的坐标空间，在匹配的坐标处执行计算，跳过不匹配的坐标（即零值位置）。对于稠密张量，IIF 体现为传统的 loop fusion。

在数据流编译器中，IIF 决定了输入迭代子图的结构：是构建一个 n 维 global iteration space（单一大输入迭代子图）还是多个 smaller pairwise 子空间（factored iteration）。Custard/Stardust 默认产生 global iteration 的 IIF，FuseFlow 通过 fusion table IR 产生 factored iteration 的 IIF。

从编译框架角度拆解术语：

IIF 在 SAM 图中体现为 input iteration region 的结构。以 $D_{il} = A_{ik} B_{kj} C_{jl}$ 为例：

**Global Iteration IIF** (Custard/Stardust 默认)：
```
SAM Graph 拓扑（单个大 input iteration 子图 → 计算子图）:
Input Iteration: LS(A_i) → LS(A_k) → LS(B_k) → Intersect(k) → LS(B_j) → LS(C_j) → Intersect(j) → LS(C_l)
                  └──────────────── 4 维联合坐标空间 (i×k×j×l) ────────────────┘
Computation:     Val(A) → Val(B) → ALU(A×B) → Val(C) → ALU(×C) → Red(k,j) → Output
```
问题：4 维坐标空间的 intersect/union 操作数量随维度增长，对高维稀疏 ML 模型产生 coordinate explosion。

**Factored Iteration IIF** (FuseFlow 默认)：
```
SAMML Graph 拓扑（多个交错的小 input iteration → 计算子图对）:
Subgraph 1 (i→k→j): LS(A_i)→LS(A_k)→LS(B_k)→Intersect(k)→LS(B_j)→Val(A)→Val(B)→ALU(A×B)→Red(k)→E_j
                      └──── 3 维坐标空间 ────┘         └── 计算 ──┘
Subgraph 2 (i→j→l): E_j (streaming from Subgraph 1) → LS(C_j)→Intersect(j)→LS(C_l)→Val(E)→Val(C)→ALU(E×C)→Red(j)→D_il
                      └── 3 维坐标空间 ──┘                  └── 计算 ──┘
```
优势：坐标处理限于二元操作（3 维 max），通过流式传递中间结果避免物化。

术语一般如何实现？如何使用？

IIF 在 FuseFlow 中通过 **Fusion Table IR** 实现。Fusion table 的行编码融合迭代顺序，列编码张量视图，单元格为数据流原语或指针。编译器按 top-down 遍历 fusion table，自动生成 factored iteration 的 SAMML 图。Factored iteration 的 IIF 将输入迭代子图与计算子图交错排列（interleaved），而非先完整构建输入迭代再连接计算。

涉及论文标题：
- FuseFlow

## Pattern-based Operator Fusion (POF / 模式匹配算子融合)

术语是什么？

Pattern-based Operator Fusion (POF) 是**基于识别已知算子模式进行融合替换**的编译技术。编译器维护一个预定义的融合模式库（如 Conv+BN+ReLU → fused ConvBNReLU kernel），当在计算图中检测到匹配的模式时，自动替换为对应的融合 kernel。

POF 常见于稠密编译器（TensorRT、XLA、TVM、DNNFusion），因为稠密算子的计算模式有限且可枚举。POF 的局限在于：(1) 仅支持预定义模板，无法处理未见过的融合模式；(2) 是 intra-layer 技术，融合限于局部算子序列；(3) 难以扩展到稀疏计算——稀疏张量的存储格式和迭代策略多样，模式空间爆炸。

从编译框架角度拆解术语：

POF 在编译流程中的位置：
```
计算图: Conv → BatchNorm → ReLU → MatMul → Softmax
         ↓ POF pattern match
融合图: FusedConvBNReLU → MatMul → Softmax
         (单个 hand-crafted kernel 替代 3 个独立 kernel)
```

与 IIF 和 EKF 的对比（Table 1）：
| 融合类型 | 跨表达式 | 稀疏支持 | 实现方式 |
|---------|---------|---------|---------|
| POF | ✓（仅预定义模式） | ✗ | Pattern match → hand-crafted kernel |
| IIF | ✗（单表达式内） | ✓ | Co-iteration / loop fusion |
| EKF | ✓（通用） | ✓（FuseFlow） | Index substitution + POG |

FuseFlow 不依赖 POF——其 EKF 算法是通用的，不需要预定义模式库。但 POF 可与 EKF/IIF 结合使用（如先 POF 识别激活函数模式，再 EKF 融合跨表达式计算）。

术语一般如何实现？如何使用？

POF 在 TensorRT 中通过 layer fusion 实现（Conv+BN+ReLU、Conv+Add+ReLU 等）；在 XLA 中通过 HLO fusion pass 实现（instruction fusion）。FuseFlow 不实现 POF，但框架兼容 POF——如果前端（Torch-MLIR）已做 POF，FuseFlow 的 EKF 可以在此基础上进一步融合。

涉及论文标题：
- FuseFlow

## Partial Order Graph (POG / 偏序图)

术语是什么？

Partial Order Graph (POG) 是 FuseFlow 中用于**表示和求解跨表达式融合中的索引顺序约束**的有向图数据结构。POG 的节点是融合表达式中的索引变量（如 `i`, `j`, `k`, `l`），有向边表示 outer-to-inner 的"必须先于"（precedes）关系。

POG 中的约束来源有两类：
1. **Mode Order 约束**：每个稀疏张量的存储格式要求的遍历顺序。例如 CSR 矩阵要求 `i → j`（先遍历行再遍历列，即 `[0,1]`），DCSR 要求 `i → j → k`。违反 mode order 导致 **discordant traversal**（与存储格式不一致的遍历），通常渐进复杂度更差。
2. **Dataflow Order 约束**：用户或编译器选择的局部 dataflow order。例如对 SpMV $T_i = B_{ij} C_j$，用户可选择 `j → i`（Gustavson's algorithm）或 `i → j`（inner product）。

POG 的作用是在保留所有约束的前提下，通过 **topological sort** 找出所有合法的全局 dataflow order。如果 POG 中存在 cycle，说明约束冲突——没有 concordant 的遍历顺序能同时满足所有约束。

从编译框架角度拆解术语：

POG 在 EKF 算法中的使用（以两个表达式的融合为例）：

```
输入:
  E1: A_{ij} = B_{ik} C_{kj}    dataflow = i → j → k (inner product)
  E2: D_{il} = A_{ij} F_{jl}    dataflow = i → l → j
  Mode orders: B CSR [i,k]=[0,1] → i→k, C dense [k,j], F dense [j,l], D dense [i,l]

POG 构建过程:
  1. E1 mode order: B 要求 i→k → POG.add_edge(i, k)
  2. E2 uses A: A 在 E1 中是输出 [i,j]，在 E2 中是输入，mode order [0,1] → i→j
     → POG.add_edge(i, j)
  3. E2 mode order: F dense [j,l] → POG.add_edge(j, l)（如果要求）
  4. 传递约束: i→k 且 i→j → POG 中 i 是 outer-most

  最终 POG:
    i → k
    ↓
    j → l
  
  Topological sorts (所有合法 global dataflow order):
    i → k → j → l
    i → j → k → l
    i → j → l → k
    （共 3 种）

Cycle 检测与处理:
  如果 E2 要求 dataflow = k → i → j（冲突：k 必须在 i 之前，但 mode order 要求 i→k）:
    POG: i → k 且 k → i → 形成 cycle
    处理: 物化 A 的转置副本 A' = A^T（行主序改为列主序）
         重新分析 mode order for A'，消除 cycle
```

术语一般如何实现？如何使用？

POG 在 FuseFlow 中作为 EKF pass 的核心数据结构，以邻接表形式维护。每次添加新的表达式到融合区域时，增量更新 POG 并检测 cycle。当检测到 cycle 时，POG 分析 cycle 中的张量 views，选择物化 transposed copy 成本最低的 view。POG 的 topological sort 输出直接作为 fusion table 的行顺序（融合迭代顺序）。

涉及论文标题：
- FuseFlow

## Fusion Table (融合表 IR)

术语是什么？

Fusion Table 是 FuseFlow 引入的 **表格形式的 lowering 中间表示（IR）**，用于在生成最终 SAMML 数据流图之前，以可操作的方式规划融合迭代和计算的空间拓扑。Fusion table 本质上是一个 **二维网格**：
- **行（Rows）**：编码融合迭代顺序（控制流），每行对应一个索引变量或值计算，按 POG topological sort 的结果排序。
- **列（Columns）**：编码张量视图（数据流），每个操作数或中间结果各占一列。
- **单元格（Cells）**：位于行列交点，有两种类型：
  1. **Primitive Cell**：创建一个新的数据流节点（LS、Intersect/Union、Rep、ALU、Red 等）。
  2. **Reference Cell**：指向另一个 cell 的指针（如 `⟨T_i^0⟩`），表示复用已有节点，或当某索引变量对当前操作不需要时作为 pass-through。

Fusion table 的两个关键设计优势：
1. **Deferred Graph Construction**（延迟图构建）：编译器可以在数据流节点实际创建之前，通过 named pointers 引用未来的节点。这允许在 finalize 之前自由重连节点连接，无需复杂的图变换。
2. **Explicit Grid Layout**：行=控制、列=数据的网格布局使依赖关系和复用机会显式可见，简化融合图生成并自然映射到稀疏数据流硬件。

从编译框架角度拆解术语：

Fusion table 构建过程（以 SpMM $T_{ij}^0 = \sum_k A_{ik} \times X_{kj}$，dataflow $i \to k \to j$ 为例）：

```
Step 1: 创建空 fusion table
         Col A       Col X       Col T^0
  Row i  [ ]        [ ]         [ ]
  Row k  [ ]        [ ]         [ ]
  Row j  [ ]        [ ]         [ ]
  Row val[ ]        [ ]         [ ]

Step 2: 插入 Level Scanner cells 和 Value cells
         Col A         Col X         Col T^0
  Row i  LS(Â_i)      [ ]           [ ]
  Row k  LS(Â_k)      LS(X̂_k)       [ ]
  Row j  [ ]           LS(X̂_j)       [ ]
  Row val Val(A)       Val(X)        [ ]

Step 3: 插入 Repeat cells、Compute cells 和 Higher-Order Reduction
         Col A         Col X         Col T^0
  Row i  LS(Â_i)      [ ]           [ ]
  Row k  LS(Â_k)      LS(X̂_k)       [ ]
  Row j  [ ]           LS(X̂_j)       ⟨T_j^0⟩ (reducer output coord)
  Row val Val(A)       Val(X)        ALU(A×X) → Red(k) → T^0_val

Step 4: Stream Merging (合并共享索引的坐标流)
         将 LS(Â_k) 移入 Intersect cell（与 LS(X̂_k) 合并）:
         Col A         Col X         Col T^0
  Row i  LS(Â_i)      [ ]           [ ]
  Row k  Intersect(Â_k, X̂_k)        [ ]
  Row j  [ ]           LS(X̂_j)       ⟨T_j^0⟩
  Row val Val(A)       Val(X)        ALU→Red→T^0_val

Step 5: Codegen（遍历 fusion table 生成 SAMML graph）
  for each row from top to bottom:
    for each cell in row:
      if primitive cell: instantiate node
      if reference cell: wire pointer to existing node
  add tensor construction nodes (LW, CD)
```

为什么需要 fusion table？传统编译器表示（依赖图、value numbering）在节点实例化后难以动态重排和重连——需要繁琐的图变换。Fusion table 作为 malleable blueprint，编译器可以在 finalize 之前通过简单的 cell 移动来重连数据流连接。

术语一般如何实现？如何使用？

Fusion table 在 FuseFlow 中作为 EKF pass（产生 fused Einsum + POG）与 Codegen pass（产生 SAMML graph）之间的桥梁。FuseFlow 按 POG topological sort 的输出确定行顺序，按 fused Einsum 中的张量操作确定列结构，然后按 Section 6.1 的算法逐步填充 cells。Fusion table 的结构天然产生 **factored iteration** 的 SAMML 图（而非 global iteration）——因为每行独立处理一个索引变量的坐标流，行间可交错计算。

- FuseFlow

## Fused Einsum Representation (融合爱因斯坦求和表示)

术语是什么？

Fused Einsum Representation 是 FuseFlow 在 EKF 阶段产生的一种中间表示，用于**追踪跨融合表达式的索引（坐标）数据和值数据的流向**。它是标准 Einstein Summation (Einsum) 记号的扩展，通过 index substitution 实现 producer-consumer 连接：将 producer 输出张量的索引变量替换为 consumer 输入张量的对应索引变量，从而消除中间张量的显式表示。

融合 Einsum 表示的核心组件：
1. **Renamed Local Indices**：每个原始表达式的局部归约索引被替换为 fresh indices（u-indices），避免跨表达式命名冲突。
2. **Producer-Consumer Edges**：通过 index substitution 连接的融合链。例如：producer $H_{ij} = A_{ik} X_{kj}$ 和 consumer $O_{il} = H_{ij} W_{jl}$ 融合为 $O_{il} = (A_{ik} X_{kj}) W_{jl}$（无需显式命名 H）。
3. **Partial Order Graph (POG)**：伴随融合 Einsum 表示的约束图，记录所有索引变量的顺序关系。
4. **Tensor Views**：同一张量的每次使用作为独立 view，各自标注 mode order 要求。

从编译框架角度拆解术语：

以 GCN 的 partial fusion 为例（两个 matmul + 一个 ReLU）：

```
原始 Einsum 表达式:
  E1: H'_{ij} = A_{il} X_{lj}       (稀疏-稠密 matmul, A CSR, X dense)
  E2: H_{ik}  = H'_{ij} W_{jk}      (稠密-稠密 matmul)
  E3: O_{ik}  = ReLU(H_{ik})        (逐元素非线性)

Fused Einsum Representation (after EKF):
  Fusion region containing {E1, E2, E3}
  
  Index substitution:
    E1 输出 H'_{ij} → E2 输入 H'_{ij}  (相同索引，直接连接)
    E2 输出 H_{ik}  → E3 输入 H_{ik}   (相同索引，直接连接)
  
  融合后: O_{ik} = ReLU((A_{il} X_{lj}) W_{jk})
         其中 A 的 mode order [i,l]=[0,1] → i→l
         X 的 mode order [l,j] 可为任意
         W 的 mode order [j,k] 可为任意
         O 的 mode order [i,k]=[0,1] → i→k
  
  POG: i → l, l → j, i → j (transitive), i → k, j → k
  合法 global order: i → l → j → k, i → j → l → k
```

术语一般如何实现？如何使用？

融合 Einsum 表示在 FuseFlow 中由 EKF pass（Section 5）产生，作为 MLIR IR 的一部分。它与 POG 一起输入到 fusion table 构建阶段。融合 Einsum 表示的思想类似于 ReACT [82] 中的 factored iteration 表示，但 FuseFlow 将其扩展到数据流编译场景，并与 POG 结合实现约束感知的融合。

涉及论文标题：
- FuseFlow

## SAMML (SAM with ML Primitives)

术语是什么？

SAMML（SAM with ML Primitives）是 FuseFlow 对原始 SAM（Sparse Abstract Machine）的扩展，**增加了支持现代 ML 模型所需的非稀疏操作原语**。原始 SAM [Hsu et al., ASPLOS 2023] 仅支持稀疏张量代数操作（Einsum），无法表示 ML 模型中普遍存在的非线性激活函数、masking（如 causal attention mask、padding mask）、和 block-sparse 计算（如 BigBird attention）。

SAMML 在 SAM 基础上扩展了：
1. **Nonlinear Function Nodes**：ReLU、GELU、softmax、sigmoid 等激活函数的 dataflow 原语。这些节点的输入是 value stream，输出是变换后的 value stream，不涉及坐标处理。
2. **Masking Nodes**：支持 attention mask、dropout mask 等。Masking node 接收 mask stream（bool/int）和 value stream，按 mask 条件过滤或修改 values。
3. **Dense Block Nodes**：支持 block-sparse 张量的内层 dense block 处理。外层稀疏迭代决定哪些 block 参与计算，内层 dense block 作为连续数据块流式送入 vectorized ALU。
4. **Vectorized ALU**：支持 SIMD 风格的向量计算，用于高效处理 dense blocks。

从编译框架角度拆解术语：

SAMML 在编译流程中的位置：
```
PyTorch (含 ReLU, softmax, mask, block_sparse)
    ↓ Torch-MLIR / MPACT
MLIR Linalg + SparseTensor (含 sparse encoding)
    ↓ FuseFlow EKF pass
Fused Einsum + POG
    ↓ Fusion Table construction
SAMML Graph (SAM primitives + ML primitives)
    ↓ Codegen
Comal Simulator / FPGA / CGRA (Onyx/Opal)
```

SAMML 的关键意义：使 FuseFlow 能够编译完整的稀疏 ML pipeline（如 GPT-3 BigBird attention 的 17+ 个操作，包含 mask、softmax、reshape），而无需 CPU fallback。Custard 编译的原始 SAM graph 在遇到非线性操作时必须将中间结果传回 CPU 执行，再传回加速器——这严重限制了端到端性能。

术语一般如何实现？如何使用？

SAMML 在 FuseFlow 中作为 MLIR dialect 实现。每个 SAMML node 有对应的 cycle-accurate 模拟模型（在 Comal 中）、HLS 综合模板（在 Vitis HLS for FPGA 中）、和 VLSI 硬件模块（在 Onyx/Opal CGRA 中）。SAMML 的 ML primitive nodes 与 SAM 的 tensor algebra primitives 共享相同的 streaming 接口（crd/ref/val tokens），因此可以无缝连接在同一个 dataflow graph 中。

涉及论文标题：
- FuseFlow

## Custard Compiler

术语是什么？

Custard 是 Hsu et al. (ASPLOS 2023) 开发的**首个稀疏张量代数到 SAM (Sparse Abstract Machine) 数据流图的编译器**。Custard 将单个 Einsum 表达式编译为 SAM graph，支持 Intra-Expression Iteration Fusion (IIF) 和 dataflow order 选择。

Custard 的核心能力与局限：
- **支持 IIF**：在单个 Einsum 表达式内自动 co-iterate 输入张量的坐标空间，融合迭代。
- **支持 dataflow order 选择**：用户可指定 dataflow order（如 `j → i` 的 Gustavson 或 `i → j` 的 inner product）。
- **不支持的**：跨表达式融合（EKF）、partial fusion、非线性操作、masking、block sparsity。因此 Custard 不能编译完整的 ML 模型。

从编译框架角度拆解术语：

Custard 编译流程：
```
高层输入: Einsum 表达式 (e.g., T_i = B_{ij} C_j, dataflow j → i)
    ↓ Custard
SAM Graph: LS region → Computation region → Tensor Construction region
    ↓ SAM → Hardware
Onyx CGRA / Comal Simulator
```

Custard 生成的 SAM graph 默认采用 **global iteration**（先构建 n 维联合坐标迭代子图，再连接计算子图）。这是 Custard 与 FuseFlow 的 IIF 策略的本质区别——FuseFlow 的 fusion table lowering 产生 factored iteration。

Custard 的 EKF 限制：用户可以手动将多个表达式重写为一个超表达式（如将 `T = A×B; O = T×C` 重写为 `O = A×B×C`），Custard 可对此重写后的单表达式做 IIF 融合。但这在复杂模型（含非线性、masking、多输出）中不可行。

术语一般如何实现？如何使用？

Custard 最初作为 Stanford PPL 的研究编译器实现，与 SAM abstract machine 论文 [Hsu et al., ASPLOS 2023] 共同发布。FuseFlow 在评估中将 Custard+Stardust (C+S) 作为 baseline 对比，在 GCN OGB-Collab 上 C+S 手动重写可获得 1.97× speedup，而 FuseFlow 自动 EKF 获得额外 1.33×（总计 2.63×）。

涉及论文标题：
- FuseFlow

## Fusion Heuristic (融合启发式分析)

术语是什么？

Fusion Heuristic 是 FuseFlow 提供的**快速分析模型**，用于在完整仿真之前估算不同融合配置的 FLOPs（浮点操作数）和 Bytes Transferred（内存传输字节数），从而 prune suboptimal 配置、缩减搜索空间。

Heuristic 的输入和输出：
- **输入**：tensor dimensions（每个张量在各维度的尺寸）、sparsity percentages（每个张量的稀疏比例）、intersection rates（坐标流 intersect 操作的匹配率，反映稀疏结构的 overlap 程度）。
- **输出**：estimated FLOPs（融合后所有 ALU/Red 节点的操作数总和）、estimated Bytes（所有 stream edges 的 token 数量 × token width 总和）、operational intensity（FLOPs / Bytes）。
- **决策**：如果 operational intensity 低于阈值，或 FLOPs 因 recomputation 显著增加，标记配置为 suboptimal 并 prune。

从编译框架角度拆解术语：

Heuristic 在 FuseFlow 编译流程中的位置：
```
用户配置: Fuse{} regions, dataflow orders, parallelization factors
    ↓
Fusion Heuristic (快速估计，seconds 完成)
    ├─ prune suboptimal → 大幅缩减 search space
    └─ keep candidate → 进入完整编译+仿真 pipeline
         ↓
FuseFlow Compilation + Comal Simulation (minutes-hours 完成)
    ↓
精确性能结果: cycles, FLOPs, bytes, speedup
```

Heuristic 的准确性（Table 3，OGB-Collab 上评估）：
| 模型 | FLOPs avg error | Bytes avg error |
|------|----------------|----------------|
| GPT-3 (block=16) | 1.8% | 5.7% |
| GCN | 2.8% | 9.6% |
| GraphSAGE | 2.6% | 11.5% |

Heuristic 正确预测了各模型的最优融合配置（partial vs full fusion），证明了其作为 pruning 工具的有效性。

术语一般如何实现？如何使用？

Heuristic 在 FuseFlow 中作为独立的快速分析 pass 实现，不依赖 Comal 仿真。用户通过命令行参数触发，输出为各配置的估计 FLOPs 和 bytes。论文计划将 heuristic 集成到 autotuning 框架中 [Lacouture et al., NeurIPS 2025 Workshop]，用于 LLM-guided autoscheduling。

涉及论文标题：
- FuseFlow

## Concordant / Discordant Traversal (一致/不一致遍历)

术语是什么？

在稀疏张量编译中，**Concordant Traversal（一致遍历）**指按照张量存储格式的自然顺序（mode order）访问其非零元素；**Discordant Traversal（不一致遍历）**指以与存储格式不同的顺序访问。

例如，对于 CSR 格式的矩阵（行优先存储，mode order = `[0,1]` 即 `i → j`）：
- **Concordant**：先遍历行 `i`，再对每行遍历列 `j` → 顺序访问内存中的连续非零元素，O(nnz) 复杂度。
- **Discordant**：先遍历列 `j`，再对每列遍历行 `i` → 随机访问内存中的非零元素，需要间接查找或构建转置索引，复杂度可能退化到 O(nnz × log(nnz)) 或更差。

Concordant traversal 的要求是稀疏编译的核心挑战之一——EKF 必须确保融合后所有张量 view 的遍历都是 concordant，否则性能可能比不融合更差。

从编译框架角度拆解术语：

在 FuseFlow 的 POG 中，mode order 约束被显式编码为有向边。当一个张量的两个不同 view 产生冲突的遍历要求时：
```
例如: 张量 A 在 E1 中作为 CSR 矩阵被消费（要求 i → j）
            在 E2 中作为列优先被消费（要求 j → i）
      POG: i → j 且 j → i → CYCLE
      解决: 物化 A 的转置副本 A^T (CSC 格式，mode order = j → i)
           用于 E2，消除 cycle
```

这种物化转置副本的成本（额外内存和传输）必须与 discordant traversal 的渐进复杂度退化进行权衡。FuseFlow 选择物化 permuted copy 而非接受 discordant traversal，因为后者在稀疏 ML 的大规模数据下通常不可接受。

术语一般如何实现？如何使用？

Concordant traversal 的概念源于 TACO [Kjolstad et al., OOPSLA 2017] 的 sparse iteration space theory。TACO 在生成稀疏循环代码时自动确保 concordant traversal，否则报编译错误。FuseFlow 将这一概念扩展到数据流编译：POG 的 cycle detection 等价于 TACO 的 concordance check，permuted copy materialization 等价于 TACO 的 workspace transformation [Senanayake et al., OOPSLA 2020]。

涉及论文标题：
- FuseFlow

## CuTe-DSL (CUDA Templates DSL Embedded in Python)

术语是什么？

CuTe-DSL 是 NVIDIA CUTLASS 项目的一部分，是一种嵌入在 Python 中的 GPU kernel 编程 DSL（Domain-Specific Language），其编程模型与 CUTLASS C++ 模板库同构（isomorphic）。CuTe-DSL 允许开发者用 Python 语法编写 GPU kernel 的 tile 迭代、数据布局、MMA 指令调度等逻辑，编译器将其 JIT（Just-In-Time）编译为 PTX，再经 ptxas 生成 SASS 机器码。关键特性：(1) 与 CUTLASS C++ 同构——保留底层 GPU 编程的完整表达能力（包括通过 PTX escape hatch 直接访问硬件指令）；(2) Python 元编程——用 Python 而非 C++ 模板做编译期参数化和代码生成；(3) JIT 编译——大幅缩短编译时间（FA4 forward 2.5s vs FA3 C++ 55s，22× 加速）；(4) 模块化原语——block-sparse、masking、varlen、work scheduling 等 attention 功能作为正交原语提供。

从编译框架角度拆解术语：

```
CuTe-DSL 编译流程:

  Python Source Code (CuTe-DSL API)
    │ 例: @cute_dsl.kernel
    │     def flash_attn_fwd(q, k, v, ...):
    │         tile_q = tma_load(q_tensor, ...)
    │         tile_k = tma_load(k_tensor, ...)
    │         acc = mma(tile_q, tile_k, ...)
    │         ...
    ↓ CuTe-DSL Compiler (Python JIT)
  PTX (Parallel Thread Execution, intermediate ISA)
    │ 例: tcgen05.mma.sync.aligned ...  (Blackwell MMA)
    │     cp.async.bulk.tensor ...       (TMA load)
    │     shfl.sync ...                  (warp shuffle)
    ↓ ptxas (NVIDIA PTX Assembler)
  SASS (Shader Assembly, native GPU machine code)
    │ 例: 具体 Blackwell SM 微码指令
    ↓ GPU Execution (B200/GB200)

编译时间对比 (Table 4, FA4):
| Kernel           | FA3 (C++ Templates) | FA4 (CuTe-DSL) | Speedup |
|-----------------|--------------------|-----------------|---------|
| Forward pass    | 55s                | 2.5s            | 22×     |
| Backward pass   | 45s                | 1.4s            | 32×     |

注: FA2/FA3 的 C++ 模板方法需预编译数百个 kernel 变体 (不同 head dim/因果/数据类型组合)
    CuTe-DSL 的 JIT 只在需要时编译所需变体
```

CuTe-DSL 在 FA4 中的角色：

FA4 全部用 CuTe-DSL 编写（无任何 CUDA C++ 组件），这一选择的关键影响：

1. **开发效率**：FA3 修改一行 C++ 模板 → 重新编译需 ~50s；FA4 修改一行 Python → 重新 JIT 需 ~2s。迭代速度提升 20-30×
2. **可及性**：具备几个月 GPU 编程经验的研究者即可贡献 attention 变体，无需 C++ 模板元编程的深度专业知识
3. **模块化**：FA4 将 block-sparse、masking、varlen、work scheduling 等功能拆解为独立、可组合的原语。例如 FlexAttention 和 block-sparse attention 已在 FA4 基础上实现，无需修改核心框架
4. **PTX escape hatch**：对于 CuTe-DSL API 尚未完整覆盖的硬件功能，开发者可直接嵌入 PTX 汇编代码（如软件指数模拟的位操作），未来 API 更新后再切换回纯 Python

术语一般如何实现？如何使用？

- **安装**：CuTe-DSL 随 CUTLASS 发布（NVIDIA/cutlass GitHub），需 CUDA toolkit ≥ 13.0（Blackwell 支持）
- **基本用法**：
  ```python
  from cutlass import cute_dsl as cd
  
  @cd.kernel
  def my_kernel(input, output, ...):
      # 定义 tile shape
      tile_m, tile_n, tile_k = 128, 128, 128
      
      # TMA 异步加载
      tile_a = cd.tma_load(input, coord=(m_idx, 0), shape=(tile_m, tile_k))
      tile_b = cd.tma_load(weight, coord=(0, n_idx), shape=(tile_k, tile_n))
      
      # MMA 指令 (Blackwell 128×128 tile, TMEM accumulator)
      acc = cd.mma(tile_a, tile_b, acc_type=cd.TMEM)
      
      # 写回 HBM
      cd.tma_store(output, acc, coord=(m_idx, n_idx))
  ```
- **与 Triton 的关系**：Triton 是更高层的 DSL（自动 tile、自动 SMEM 管理、block-level 编程），CuTe-DSL 是更低层的 DSL（与 CUTLASS C++ 同构，显式 tile 管理、warp/warpgroup 级别控制、直接 PTX 访问）。FA4 比 Triton 快 2.1-2.7× 正是因为 CuTe-DSL 允许更精细的底层控制
- **限制**：(1) 需要理解 GPU 硬件细节（线程层次、内存层次、async 语义）；(2) 调试工具链不如 C++ 成熟；(3) API 仍在快速演进中（部分新硬件特性需通过 PTX escape hatch 访问）
- **愿景**：FA4 的 CuTe-DSL 实现旨在成为构建各种 attention 变体的通用框架，通过组合原语而非从零实现每个变体

涉及论文标题：
- FlashAttention-4

## TorchInductor

术语是什么？

TorchInductor 是 PyTorch 2.0 引入的后端编译器，是 `torch.compile` 编译栈的核心组件。它接收 AOTAutograd 分解后的 Aten 算子图（`fx.Graph`），将算子图映射到 Triton（GPU）或 C++/OpenMP（CPU）代码生成后端，最终产生可在目标硬件上执行的高效 kernel。TorchInductor 的核心能力包括：(1) 算子融合（将多个 element-wise 和 reduction 算子合并为单个 kernel）；(2) 自动分块（tiling）以利用 GPU 的共享内存层次；(3) 内存规划（分配和复用中间缓冲区以减少显存占用）。然而，TorchInductor 对矩阵乘法（`torch.bmm`/`torch.matmul`）有特殊处理：直接映射到 CUBLAS（cuBLAS）库调用，这形成了一个**融合边界**（fusion boundary），隔离了 GEMM 与周围的 softmax、mask 等运算。这是 Flashlight 论文所要解决的核心问题。

从编译框架角度拆解术语：

```
TorchInductor 在 PyTorch 编译栈中的位置:

  PyTorch Python 代码
    │
    ↓ TorchDynamo (FX Graph Capture)
  fx.Graph (计算图，包含高层算子如 torch.bmm, torch.softmax)
    │
    ↓ AOTAutograd (算子分解 + 反向图生成)
  Aten IR (分解为低层 Aten 算子，如 aten::bmm, aten::max, aten::exp)
    │
    ↓ TorchInductor (核心后端编译器)
    │  ├─ 算子匹配与调度: 将每个 Aten 算子映射到实现
    │  │   - torch.bmm → CUBLAS (GEMM 融合边界!)
    │  │   - torch.max → Triton reduction kernel
    │  │   - torch.exp → Triton element-wise kernel
    │  ├─ 融合 pass: 将相邻非-GEMM 算子合并
    │  ├─ 分块 (tiling): 按 tile 分解大矩阵操作
    │  ├─ 内存规划: 分配/复用 buffer
    │  └─ 代码生成: Triton (GPU) 或 C++/OpenMP (CPU)
    │
    ↓ Triton 编译器
  PTX (GPU 中间表示)
    │
    ↓ ptxas
  GPU 可执行 kernel
```

**Flashlight 对 TorchInductor 的扩展**：
Flashlight 通过在 TorchInductor 的 IR 层面引入**统一归约 IR**，将 matmul 从特殊的 CUBLAS 映射降级为与 max、sum 等算子同级的"广义归约"操作，使 matmul 能与周围算子跨 GEMM 边界融合。这本质上是消解了 TorchInductor 原有的 GEMM 融合边界。

**GEMM 融合边界的代价**（以 standard attention 为例）：
- TorchInductor 默认将 `Q@K^T` 和 `P@V` 映射到 CUBLAS（两个独立 kernel），softmax 映射到另一个 Triton kernel
- 中间张量 S（`Q@K^T` 结果）和 P（`softmax(S)` 结果）分别在 kernel 间通过 HBM 传递
- 内存流量：`O(N²)` 量级（S 和 P 的大小）；FlashAttention 手写融合 kernel 将其降至 `O(N)`
- Flashlight 通过在编译器层面生成融合 kernel 达到与手写 kernel 相同的 O(N) 内存流量

术语一般如何实现？如何使用？

- **API**：用户通过 `torch.compile(fn, backend="inductor")` 调用（这是默认 backend），或使用环境变量 `TORCHINDUCTOR_*` 控制其行为
- **扩展点**：TorchInductor 的 fusion pass 支持自定义 fusion pattern；Flashlight 利用这一扩展点注入新的融合规则
- **Triton 依赖**：GPU 代码生成依赖 Triton 库；CPU fallback 使用 C++/OpenMP
- **调试**：可通过 `TORCH_COMPILE_DEBUG=1` 查看生成的 Triton/C++ 代码；通过 `torch._inductor.config` 控制融合策略
- **Flashlight 使用**：`torch.compile(fn, enable_flashlight=True)` 启用 Flashlight 扩展

- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## PyTorch Compilation Stack (torch.compile)

术语是什么？

`torch.compile` 是 PyTorch 2.0 引入的 JIT 编译系统，通过多阶段编译将 Python 编写的 PyTorch 模型转换为优化的机器代码。编译栈包含三个阶段：(1) **TorchDynamo**：在 Python 字节码层面捕获 PyTorch 程序的计算图，生成 `fx.Graph`（FX 中间表示），处理 Python 控制流；(2) **AOTAutograd**：将前向计算图分解为低层 Aten 算子，并自动生成对应的反向计算图；(3) **TorchInductor**：后端编译器，将 Aten 算子图映射到 Triton（GPU）或 C++/OpenMP（CPU）代码生成后端。整个流程对用户透明——只需 `torch.compile(model)` 即可获得加速。

从编译框架角度拆解术语：

```
torch.compile 完整编译流程:

  # 用户代码
  @torch.compile
  def attention(Q, K, V):
      S = Q @ K.transpose(-2, -1) * scale
      P = F.softmax(S, dim=-1)
      return P @ V

  Step 1: TorchDynamo (FX Graph Capture)
    ├─ 拦截 Python 字节码执行
    ├─ 记录张量操作到 fx.Graph
    ├─ 处理控制流 (if/for/while)
    └─ 输出: fx.Graph
        %S = call_function(torch.bmm, %Q, %K_T)
        %S_scaled = call_function(torch.mul, %S, %scale)
        %P = call_function(torch.softmax, %S_scaled)
        %O = call_function(torch.bmm, %P, %V)

  Step 2: AOTAutograd
    ├─ 将 fx.Graph 分解为 Aten 算子
    ├─ 生成反向图 (对每个前向算子求导)
    └─ 输出: Aten IR (前向 + 反向)

  Step 3: TorchInductor
    ├─ 算子匹配: Aten 算子 → 实现
    │   ├─ aten::bmm → CUBLAS (GEMM, 融合边界)
    │   ├─ aten::softmax → Triton reduction
    │   └─ aten::mul → Triton element-wise
    ├─ 融合: 将相邻 element-wise/reduction 合并
    ├─ 分块: 按 GPU 共享内存分层
    └─ 代码生成: Triton kernel(s)

  Step 4: Triton → PTX → GPU

  # Flashlight 的修改
  # 在 Step 3 的 IR 层面:
  #   - 将 aten::bmm 映射从 CUBLAS 改为 Unified Reduction
  #   - 使 matmul 能参与跨算子融合
  #   - 应用 Structural Fusion + Semantic Fusion + Twin Matmul
```

**torch.compile 与 Flashlight**：
- `torch.compile` 默认配置下，attention 计算被拆分为 3+ 个 kernel（QK^T CUBLAS kernel, softmax Triton kernel, PV CUBLAS kernel）
- 启用 Flashlight (`enable_flashlight=True`) 后，Flashlight 扩展 TorchInductor 的 IR 和融合 pass，自动将整个 attention 融合为一个 FlashAttention 风格 kernel
- 用户代码无需任何修改——标准 PyTorch 代码即可享受融合 kernel 的性能

术语一般如何实现？如何使用？

- **基本用法**：`compiled_model = torch.compile(model)`；可选 `mode="reduce-overhead"` 或 `mode="max-autotune"` 控制优化激进程度
- **后端选择**：`backend="inductor"`（默认，Triton/C++）；`backend="openxla"` 等
- **动态 shape**：`dynamic=True` 支持可变输入尺寸（略微增加编译开销）
- **调试**：`TORCH_LOGS="+dynamo,+inductor"` 查看编译日志；`torch.compile(fn, options={"trace.enabled": True})` 查看 FX graph
- **限制**：图捕获阶段可能因 Python 动态特性而"图断裂"（graph break）；需要 warmup（首次调用触发 JIT 编译）
- **Flashlight 集成**：通过 `torch.compile(fn, enable_flashlight=True)` 透明启用，不需要额外的 API

- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## FlexAttention

术语是什么？

FlexAttention 是 PyTorch 提供的一种模板化的融合 attention kernel 系统，允许用户通过定义 `score_mod` 和 `mask_mod` 回调函数来描述 attention 变体的计算模式。FlexAttention 的编译器后端（TorchInductor）将用户定义的模板映射到预编译的融合 kernel（等价于 FlashAttention 风格的分块+online softmax+kernel fusion）。支持的变体通过 score_mod（修改 attention score）和 mask_mod（定义 mask 模式）的组合来表达，如 ALiBi、Softcap、Causal Mask、Sliding Window、PrefixLM、Document Mask 等。

从编译框架角度拆解术语：

```
FlexAttention 使用方式:

  # 用户定义 score_mod 模板函数
  def alibi_score(score, b, h, q_idx, kv_idx):
      # score: QK^T 结果 (query_len × kv_len)
      # 返回修改后的 attention score
      bias = alibi_slopes[b, h] * (q_idx - kv_idx)
      return score + bias

  def causal_mask(b, h, q_idx, kv_idx):
      return q_idx >= kv_idx  # mask: True = keep, False = mask out

  # 创建 block_mask (性能关键步骤)
  block_mask = create_block_mask(causal_mask, B, H, Q_LEN, KV_LEN)

  # 调用 FlexAttention
  output = flex_attention(query, key, value, score_mod=alibi_score, block_mask=block_mask)
```

**FlexAttention 编译流程**：
1. TorchDynamo 捕获 `flex_attention` 调用和用户定义的 `score_mod`/`mask_mod`
2. TorchInductor 的 FlexAttention pass 将 score_mod 和 mask_mod 内联到预定义的 attention kernel 模板中
3. 编译器生成一个融合的 Triton kernel，包含：tiled QK^T → score_mod → mask → online softmax → PV，全部在一个 kernel 内完成
4. Block mask 通过 `create_block_mask` 预计算哪些 Q-KV tile pair 完全被 mask（可跳过），减少无效计算

**FlexAttention 的局限性（Flashlight 所解决的）**：
1. **模板表达能力有限**：只能表达 `score_mod` + `mask_mod` 模式的变体。无法表达 data-dependent attention（如 differential attention 的 `λ*(Q1@K1^T - Q2@K2^T)`，其中 λ 是运行时标量）、multi-branch attention（Evoformer 的 gated self-attention，需要在 softmax 前后插入 gating）、invariant point attention（IPA，需要 3D 坐标变换）。
2. **Block-mask 开销**：`create_block_mask` 需要额外计算和内存（paper 中显示某些配置下 block-mask 创建时间超过 kernel 执行时间），且需要用户显式管理缓存。
3. **模板与代码分离**：用户必须将 attention 逻辑表达为模板函数而非直接 PyTorch 代码，增加使用门槛。

术语一般如何实现？如何使用？

- **API**：`torch.nn.attention.flex_attention.flex_attention(query, key, value, score_mod=None, block_mask=None)`
- **Block mask 缓存**：`block_mask = create_block_mask(mask_mod, ...)` 返回可缓存对象；在多次调用中复用可避免重复计算
- **与 torch.compile 集成**：FlexAttention 内部使用 `torch.compile` 的 TorchInductor 后端生成融合 kernel
- **Flashlight 对比**：Flashlight 不需要 score_mod/mask_mod 模板——用户直接写标准 PyTorch 代码（如 `A1 - λ*A2`），编译器自动推断并生成融合 kernel

涉及论文标题：
- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## Fusion Boundary (GEMM Fusion Boundary in TorchInductor)

术语是什么？

Fusion Boundary（融合边界）是指在编译器优化中，某些算子或算子类型因特殊映射而无法与周围算子参与融合的隔离现象。在 PyTorch 的 TorchInductor 中，最关键的融合边界是**GEMM 融合边界**：TorchInductor 将矩阵乘法（`torch.bmm`/`torch.matmul`）直接委托给 CUBLAS 库调用，而非在 IR 中表示为可融合的计算模式。由于 CUBLAS 是一个外部库，其内部实现对 TorchInductor 不可见且不可修改，编译器无法将 CUBLAS kernel 前后的 softmax、mask、element-wise 等操作融合到同一个 kernel 中。这使得 attention 计算被强制拆分为多个独立 kernel：每个 matmul 是一个 CUBLAS kernel，softmax 和 element-wise ops 是独立的 Triton kernel，中间张量必须在 kernel 间通过 HBM 传递。

从编译框架角度拆解术语：

```
GEMM 融合边界的示意:

  # 标准 attention: S = Q@K^T → P = softmax(S) → O = P@V

  TorchInductor 默认处理:
    ┌─────────────────────┐
    │ aten::bmm (Q, K^T)  │ → CUBLAS sgemm kernel → HBM (张量 S, 大小 N²)
    │ 【融合边界】          │
    └─────────────────────┘
              │ HBM read S
    ┌─────────────────────┐
    │ aten::softmax(S)    │ → Triton kernel → HBM (张量 P, 大小 N²)
    │ + element-wise ops  │   (max reduction + exp + sum + div)
    └─────────────────────┘
              │ HBM read P
    ┌─────────────────────┐
    │ aten::bmm (P, V)    │ → CUBLAS sgemm kernel → HBM (张量 O, 大小 N×d)
    │ 【融合边界】          │
    └─────────────────────┘

  Flashlight 消解融合边界后:
    ┌─────────────────────────────────────────────┐
    │ Unified Reduction IR (单一融合 kernel)       │
    │                                             │
    │ for each KV tile:                           │
    │   S_tile = Q_tile @ K_tile^T (MMA, on-chip) │
    │   P_tile = online_softmax(S_tile, m, ℓ)     │
    │   O = O + P_tile @ V_tile (MMA, on-chip)    │
    │                                             │
    │ S 和 P 从不离开片上内存 (SRAM)               │
    │ 仅最终 O 写回 HBM                            │
    └─────────────────────────────────────────────┘

内存流量对比:
  TorchInductor (3 kernels): HBM read Q,K + write/read S + write/read P + read V + write O
                             ≈ O(N²d) 中间张量流量
  Flashlight (1 kernel):     HBM read Q,K,V + write O
                             ≈ O(Nd) 输入输出流量
```

**融合边界的性能影响**：
- Attention 特有的 O(N²) 中间张量（S 和 P）使 GEMM 融合边界的代价远大于一般场景
- 对于长序列（N ≥ 4096），S 的大小 (N²) 可能超过 GPU 显存带宽，融合边界导致的延迟增加可达 5-10×
- 在 FlashAttention 出现之前，手写 CUDA kernel 是唯一绕过此限制的方法
- Flashlight 通过编译器方法自动绕过 GEMM 融合边界，使任意 attention 变体都能享受融合 kernel 的好处

术语一般如何实现？如何使用？

- **在不同编译器中**：TVM 通过调度原语（`compute` + `schedule`）允许用户手动将 matmul 改为 tiled 形式以跨算子融合；XLA 通过 HLO fusion pass 自动决定融合边界；Mirage 通过等价图变换寻找最优融合策略
- **Flashlight 的方法**：在 IR 层面将 matmul 从特殊的 CUBLAS 映射降级为与 max/sum 同级的广义归约操作，使 matmul 自然参与 TorchInductor 现有的融合 pass，无需手动标注
- **权衡**：放弃 CUBLAS 的专用 GEMM kernel（高度优化的 tiling + register blocking）换取融合自由度。对于计算密集的 matmul（大 M,N,K），CUBLAS 单 kernel 可能更快；对于内存密集的 attention（tiled matmul + softmax），融合收益远大于 GEMM kernel 性能损失

涉及论文标题：
- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## Unified Reduction IR

术语是什么？

统一归约 IR（Unified Reduction IR）是 Flashlight 在 TorchInductor 中引入的 IR 扩展，将矩阵乘法（GEMM）建模为一种广义的归约操作（reduction），使 matmul 在 IR 层面与 `torch.max`（max reduction）、`torch.sum`（sum reduction）等算子处于同等地位。在 TorchInductor 的默认 IR 中，matmul 被视为特殊的外部库调用（CUBLAS），不参与算子融合；在 Flashlight 的统一归约 IR 中，所有归约操作（包括 matmul、max、sum）共享同一种 IR 表示，编译器可以跨所有归约边界进行融合、分块和代数变换。

从编译框架角度拆解术语：

```
统一归约 IR 的语义:

  # 传统: 不同归约操作有不同 IR 表示
  torch.max(x, dim=j)    → ReductionOp(kind=MAX, input=x, axis=j)
  torch.sum(x, dim=j)    → ReductionOp(kind=SUM, input=x, axis=j)
  torch.bmm(A, B)        → ExternalCall(kind=CUBLAS_GEMM, ...)  ← 不可融合!

  # Flashlight 统一归约 IR:
  torch.max(x, dim=j)    → Reduction(kind=MAX, axes=[j], body=...)
  torch.sum(x, dim=j)    → Reduction(kind=SUM, axes=[j], body=...)
  torch.bmm(A, B)        → Reduction(kind=MMA, axes=[k], body=mul_add)  ← 可融合!

  # 在统一归约 IR 下, softmax + matmul 的融合:
  # 原始:
  #   S = Reduction(MMA, axes=[k])  (Q@K^T)
  #   P = softmax(S, dim=j)  (max reduction + exp + sum reduction + div)
  #   O = Reduction(MMA, axes=[j])  (P@V)
  #
  # Flashlight 融合后 (一个 kernel, 三个归约循环):
  for i in I:  # parallel (Q 的序列维度)
      m = -inf, ℓ = 0, O[i,:] = 0
      for j in J:  # reduction (KV 的序列维度, 融合了 softmax 的归约和 P@V 的归约)
          # QK^T: 隐式 matmul 归约 (k 维度在上层 tile 循环中)
          S_row = Q[i,:] @ K[j,:]^T  # 点积, tile 内的 k 维度已展开
          # online softmax
          m_new = max(m, S_row)
          ℓ = ℓ * exp(m - m_new) + exp(S_row - m_new)
          m = m_new
          # PV: 即时累加
          O[i,:] += exp(S_row - m) * V[j,:]
  # 关键: 在统一归约 IR 下, matmul 的归约轴 k 和 softmax 的归约轴 j
  #        与 PV matmul 的归约轴 j 都是 "归约", 编译器可以将它们自由组合和融合
```

**统一归约 IR 的设计原理**：
- Matmul `C[i,k] = Σⱼ A[i,j] × B[j,k]` 可以视为沿 j 轴的归约，归约操作的 body 是乘法+累加（mul_add）
- Max `m[i] = maxⱼ x[i,j]` 是沿 j 轴的归约，body 是 max
- Sum `s[i] = Σⱼ x[i,j]` 是沿 j 轴的归约，body 是 add
- 当所有归约共享统一的 IR 表示时，编译器可以：
  1. 将不同归约的循环嵌套融合（如 softmax 的 max 和 sum 归约与 matmul 的 MMA 归约）
  2. 在归约操作间应用代数变换（如 stable softmax → online softmax）
  3. 对融合后的归约循环进行统一的分块（tiling）调度

术语一般如何实现？如何使用？

- **IR 设计**：在 TorchInductor 的中间表示中，Reduction IR 节点包含 `kind`（MAX, SUM, MMA）、`axes`（归约轴）、`body`（归约体，如 mul_add, max, add）和 `init`（初始值，如 -inf, 0）
- **代码生成**：统一的 Reduction IR 在 Triton 代码生成阶段映射为对应的 `tl.reduce`、`tl.dot` 或手写 MMA 循环
- **与 TorchInductor 的集成**：Flashlight 在 TorchInductor 的算子调度（scheduling）阶段将 CUBLAS 映射替换为 Unified Reduction IR 映射，其余编译流程不变
- **适用条件**：适用于需要跨 matmul 边界融合的场景，如 attention（matmul + softmax + matmul）、MLP with activation（matmul + GELU + matmul）
- **局限性**：单次 matmul 的性能可能低于 CUBLAS（因为放弃了 CUBLAS 的手工优化），仅当融合收益超过时才有净收益

- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## Structural Fusion (Dimension Demotion)

术语是什么？

结构融合（Structural Fusion）结合维度降级（Dimension Demotion）是 Flashlight 引入的一种编译器融合 pass，用于解决 producer 和 consumer 的 kernel sketch（循环嵌套模式）不兼容的问题。当 producer 的并行循环维度在 consumer 中需要作为归约维度时，直接将两者的循环嵌套拼接会导致语义错误（并行维度不能包含有依赖关系的操作）。Flashlight 的维度降级将 producer 的并行维度**降级为融合后的归约循环维度**，使 producer-consumer 可以在同一个 kernel 中正确执行。核心原理是并行度↔内存局部性的权衡：牺牲部分并行度换取 tile 内数据局部性。

从编译框架角度拆解术语：

```
维度降级的具体过程 (以 attention 的 QK^T + softmax 为例):

原始 (两个独立 kernel):
  # Producer kernel (Q @ K^T)
  for i in I:        # parallel (Q 行)
      for j in J:    # reduction (K 列, 沿 d 维度归约)
          S[i,j] = Σ_k Q[i,k] × K[j,k]
  
  # Consumer kernel (softmax over j)
  for i in I:        # parallel
      m = -inf
      for j in J:    # reduction (沿 j 归一化)
          m = max(m, S[i,j])

  # 问题: Producer 的 j 是并行维度 (写入 S[i,j], 不同 j 无依赖)
  #        Consumer 的 j 是归约维度 (max 沿 j 需要所有 j 值)
  #        → 不能简单拼接: 无法在 producer 还没完成所有 j 时就开始 consumer 的 max!

Flashlight 维度降级融合:
  for i in I:        # parallel (保留)
      m = -inf
      for j in J:    # reduction (j 从 producer 的并行降级为归约)
          # Producer (原本是并行的 j 现在在归约循环中)
          S_row = Σ_k Q[i,k] × K[j,k]   # 每次迭代只计算一个 S[i,j]
          # Consumer (immediate consumption)
          m = max(m, S_row)             # 即时消费, S[i,j] 不需要写回 HBM!
      # m 是 row-wise max, 用于后续 online softmax

  # 维度降级的代价: j 维度不再并行 (原本可以多个 SM 同时处理不同 j)
  #                 所有 j 必须在同一个 block/thread 中串行归约
  # 维度降级的收益: S[i,j] 在片上即时消费, 不需要 HBM 写回 → O(N²d) → O(Nd) 内存流量
```

**维度降级的正确性条件**：
- Producer 的 j 维度操作间无依赖（各 j 独立计算 S[i,j]）→ 降级到归约循环后语义正确
- Consumer 的归约沿 j 维度需要所有 j 的值 → 归约循环自然满足
- 代价分析：`T_fused = T_prod × |J|`（原先并行 J 个 tile 现在串行），但省去 `|J| × d` 的 HBM 写入和读取。当 HBM 带宽是瓶颈时净收益为正

术语一般如何实现？如何使用？

- **在 Flashlight 中**：维度降级作为 TorchInductor 的一个 fusion pass，在分析 producer-consumer 的循环嵌套兼容性后自动决定是否降级
- **触发条件**：producer 的输出维度在 consumer 中是归约维度；producer 的该维度操作无跨迭代依赖
- **Tile 粒度**：降级发生在 tile 级别。原始并行维度 |J| 被分割为 tile（如 J_tile = 128），降级后的归约循环在 tile 内执行，不同 tile 仍可并行分配到不同 SM
- **通用性**：该技术不限于 attention。任何 producer 的并行维度恰好是 consumer 的归约维度的场景都可应用（如 matmul + layer norm, convolution + batch norm）

## Semantic Fusion (Algebraic Transformation)

术语是什么？

语义融合（Semantic Fusion）结合代数变换（Algebraic Transformation）是 Flashlight 引入的一种编译器 pass，利用数学恒等式在 IR 层面自动将多轮归约模式转换为单轮融合归约。典型应用是将 stable softmax（需要两轮归约：先 max 归约 → 再 exp + sum 归约）自动转换为 online softmax（单轮融合归约，同时维护 running max、running normalizer 和 running output）。核心数学基础是指数函数的同态性质（homomorphism）：$e^{a-b} = e^a / e^b$，允许在不知道全局最大值的情况下增量计算 softmax。

从编译框架角度拆解术语：

```
语义融合的代数变换过程:

IR 输入 (stable softmax, 两次归约):
  # Step 1: Max reduction
  m = -inf
  for j in J:
      m = max(m, x[j])
  
  # Step 2: Exp + Sum reduction
  s = 0
  for j in J:
      s = s + exp(x[j] - m)
  
  # Step 3: Normalize
  P[j] = exp(x[j] - m) / s

Flashlight 识别的模式:
  - 两个连续的 reduction (max → sum)
  - sum reduction 的 body 中包含 "x[j] - m" (x 是输入, m 是前一个 reduction 的结果)
  - exp 是同态: exp(x[j] - m) = exp(x[j]) / exp(m)

Flashlight 代数变换 → Online Softmax:
  m = -inf, ℓ = 0
  for j in J:                    # 单次归约循环
      m_new = max(m, x[j])       # running max
      ℓ = ℓ * exp(m - m_new)    # rescale old normalizer (利用同态!)
      ℓ = ℓ + exp(x[j] - m_new) # add new term
      m = m_new
  
  # 输出: ℓ = Σⱼ exp(x[j] - m_final)
  # 正确性由同态保证: ℓ_{k+1} = ℓ_k * exp(m_k - m_{k+1}) + exp(x_{k+1} - m_{k+1})

完整的 attention 融合 (matmul + online softmax + matmul):
  for i in I:                    # parallel (Q tile)
      m = -inf, ℓ = 0, O[i,:] = 0
      for j in J:                # reduction (KV tile, 融合三个操作)
          # Matmul 1: QK^T (implicit k-axis reduction in tiling)
          S_row = Σ_k Q[i,k] × K[j,k]
          
          # Online softmax (semantic fusion 的结果)
          m_new = max(m, S_row)
          ℓ = ℓ * exp(m - m_new) + exp(S_row - m_new)
          m = m_new
          
          # Matmul 2: PV (即时消费 P, 不物化)
          O[i,:] += exp(S_row - m) * V[j,:]
      
      # Final normalization
      O[i,:] = O[i,:] / ℓ
```

**代数变换的正确性证明（环论）**：
Flashlight 论文使用环论框架证明 online softmax 的等价性：
- 令 `(R, ⊕, ⊗)` 为半环，其中 `⊕ = +`（加法），`⊗ = ×`（乘法）
- `exp(x)` 是从加法群到乘法群的同态：`exp(a - b) = exp(a) ⊗ exp(b)⁻¹ = exp(a) / exp(b)`
- online softmax 的递推式 `ℓ_{new} = ℓ_{old} × exp(m_old - m_new) + exp(x_new - m_new)` 在此半环下保持归约的正确性
- 该框架是通用的：任何满足同态性质的归约对（如 `log` 对 `sum` 的同态 `log(ab) = log(a) + log(b)`）都可应用类似的代数变换

术语一般如何实现？如何使用？

- **模式匹配**：Flashlight 在 TorchInductor 的 IR 上执行 pattern matching，识别 "max reduction 的结果被后续的 exp + sum reduction 消费" 的模式
- **代数变换规则**：维护一个代数规则库（如 `exp(a-b) = exp(a)/exp(b)`、`log(ab) = log(a)+log(b)` 等），每个规则有对应的 IR 重写模板
- **验证**：编译器在应用变换前验证前置条件（如同态性质在给定数值精度下是否满足）
- **通用性**：该技术不限于 softmax。任何具有代数律（结合律、交换律、分配律、同态）的归约组合都可利用语义融合优化
- **局限**：需要编译器能够在 IR 中表达代数语义（如标记某函数为同态），这要求扩展 IR 的语义标注能力

## Tiling-Aware Dimension Elimination (Twin Matmul)

术语是什么？

分块感知维度消除（Tiling-Aware Dimension Elimination），也称 Twin Matmul（双矩阵乘法融合），是 Flashlight 引入的一种编译器 pass，用于融合连续的矩阵乘法操作。当计算图中出现 `(A · B) · D`（两个连续 matmul）时，标准编译流程会先执行 `A · B`（生成中间张量 C，大小为 `M × K₁`），再将 C 与 D 相乘。Twin Matmul 通过分块调度，使 B 的列维度 tile 在片上被即时消费，**不物化完整的中间张量 C**。两个 matmul 在同一个 kernel 中以 tile pipeline 方式执行。

从编译框架角度拆解术语：

```
Twin Matmul 的融合过程:

原始计算 (两个独立 kernel):
  # Kernel 1: C = A @ B (M×K₁ = M×K × K×K₁)
  for i in I:                  # parallel
      for k1 in K1:            # parallel
          C[i,k1] = 0
          for k in K:          # reduction
              C[i,k1] += A[i,k] × B[k,k1]
  # HBM: write C (M×K₁)

  # Kernel 2: O = C @ D (M×N = M×K₁ × K₁×N)
  for i in I:                  # parallel
      for j in N:              # parallel
          O[i,j] = 0
          for k1 in K1:        # reduction
              O[i,j] += C[i,k1] × D[k1,j]

Flashlight Twin Matmul (单一 kernel):
  for i in I:                  # parallel (Q 的序列维度)
      O[i,:] = 0
      for k1_tile in tiles of K1:   # tiling the intermediate dimension
          # Step 1: Compute C tile on the fly
          for k in K:               # reduction (inner product)
              C_tile[...] += A[i,k] × B[k, k1_tile]
          
          # Step 2: Immediately consume C tile
          for j in N:               # 并行或向量化
              O[i,j] += Σ_{k1∈tile} C_tile[...] × D[k1_tile, j]
      
      # C 的完整张量从未写出到 HBM!
      # 仅最终 O 写回 HBM

  # 或者等效的 tile 流水线:
  for i in I:
      O[i,:] = 0
      for k in K_tile:              # 外层分块 (沿归约轴 K)
          # Load A tile, B tile
          # Compute partial C tile: C_partial = A_tile @ B_tile
          # Consume partial C tile: O += C_partial @ D_tile
          # (C_partial 存于 SRAM, 被 D_tile 即时消费)
```

**Twin Matmul 在 Flashlight 中的应用**：
- **Evoformer gated attention**：`gating(x) · softmax(QK^T) · V`，中间有 gating → matmul → softmax → matmul 四个操作。Twin Matmul 将 gating、QK^T、softmax、PV 全部融合
- **Differential attention**：`(Q1@K1^T - λ·Q2@K2^T) · V`，涉及两个 QK^T 和一个 PV matmul，全部融合

**分块调度策略**：
- 沿 K₁ 维度分块（中间维度）。当 `K₁ / tile_size` 较大时，需要多轮 tile 迭代
- 沿 K 维度分块（最内层归约轴）。允许 partial C tile 在 K 维度上增量累积
- 两种策略可组合（3D tiling），在 SRAM 容量和并行度之间权衡

术语一般如何实现？如何使用？

- **触发条件**：IR 中出现连续两个 matmul，且第一个 matmul 的输出仅被第二个 matmul 消费（没有其他消费者）
- **Tile 大小选择**：受 SRAM/共享内存容量限制，需要容纳 A_tile、B_tile、C_partial、D_tile 和 O_tile
- **与 Structural Fusion 的组合**：如果两个 matmul 之间有其他操作（如 ReLU、GELU），需要 Structural Fusion 先将这些操作融合进来
- **与 Semantic Fusion 的组合**：如果中间有 softmax，需要 Semantic Fusion 先将其转换为 online softmax
- **性能收益**：消除了大小 `M × K₁` 的中间张量 HBM 写入和读取。当 K₁ 较大时收益显著

- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## HomoPhase Group and HomoSize Group (时空分组规划抽象)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
HomoPhase Group 和 HomoSize Group 是 STAlloc 在生成 GPU 内存分配计划时使用的两种分组抽象，用于将 NP-hard 的 Dynamic Storage Allocation 问题通过时空解耦降至 O(N log N) 可计算复杂度。

- **HomoPhase Group（同阶段组）**：将具有相同 computation phase pair (p_s, p_e) 的 allocation requests 归为一组。例如，同一 microbatch 的 forward pass 中产生的所有 activation tensors 归入同一个 HomoPhase Group（它们在 forward 分配、backward 释放，lifespan 高度重叠）。同一组内，所有 requests 的 lifespan 相似（overlapping），因此将它们 contiguously packed 到一个内存块中即可达到局部最优。相邻 HomoPhase Groups 的 fusion 通过 TMP（Time-Memory Product）指标决策——若 fusion 后 TMP 提升则合并，否则保持独立。

- **HomoSize Group（同尺寸组）**：将相同 allocation size 的 requests（来自 HomoPhase Group planning 后的输出）归为一组。例如，所有大小为 4096×128×2 bytes 的 activation tensors。组内 requests 的差异仅在 lifespan（起始/结束时间不同），lifespan 不重叠的 requests 可以复用同一块 GPU 内存（memory-layer 堆叠）。

两个分组的组合效果：HomoPhase Group 在时间维度上聚类（lifespan-aligned packing）→ HomoSize Group 在空间维度上聚类（same-size memory-layer stacking）→ 全局规划按 size 降序处理（大 size 优先占据地址空间，小 size 填入空闲 intervals）。

从编译框架角度拆解术语，比如术语如何在编译框架中发挥作用，给出术语在编译框架中运转流程的具体例子。通过联网搜索让回答具体和精准。

```
STAlloc Plan Synthesis 中 HomoPhase/HomoSize Group 的流程:

Step 1: HomoPhase Grouping
  M_s = {m | m.p_s == P_s AND m.p_e == P_e}  // 同 phase 的 requests
  例: 所有 "forward_3 → backward_3" phase 的 scoped tensors
  
  Group Fusion:
    for each adjacent pair (D_gi, D_gj):
      // 将较小的 group 插入较大的 group 的空闲位置
      insert D_gj into D_gi by sorting by t_e descending, placing at lowest available addr
      if TMP_new > weighted_avg(TMP_i, TMP_j):
        accept fusion
      else:
        reject fusion
  
  输出: Fused HomoPhase Groups → Local Plans D_g (relative addresses)

Step 2: HomoSize Grouping
  M_s = {m_g | m_g.s == S}  // 同 size 的 HomoPhase Group plans
  // Algorithm 1: Memory-Layer Construction
  sort M_s by t_s ascending
  for each m in M_s:
    find memory-layer L where L.last.t_e < m.t_s (lifespan 不冲突)
    if found: append m to L
    else: create new memory-layer L, append m to L
  
  输出: Memory-Layers per HomoSize Group (最小化 layer 数量)

Step 3: Global Planning
  for S_i in sorted_sizes_descending:
    // 已处理的所有 > S_i 的 memory-layers 构成 current plan
    for each request in HomoSize Group of size S_i:
      try_place_in_existing_plan_gaps(request)  // 填入大 size groups 的空闲间隔
    for remaining requests (无法填入 gaps):
      construct_new_memory_layers(remaining)  // 新建 layer
    insert new layers into global plan
```

**复杂度**：N 个 total requests。HomoPhase grouping: O(N log m) (m = max group size)。HomoSize sorting: O(N log N)。Memory-layer construction per group: O(|M_s|)（线性）。Global planning: O(N log N)。总 complexity O(N log N)，相比之下 brute-force Dynamic Storage Allocation 是 NP-hard。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **实现**：Plan Synthesizer 为 Python standalone 工具（STAlloc 代码库的一部分），读取 Allocation Profiler 输出的 JSON trace 文件，输出 JSON allocation plan 文件。
- **分组粒度**：HomoPhase Group 以 computation phase（forward/backward of each microbatch）为粒度；HomoSize Group 的 size 为精确字节匹配（非范围匹配），因为 spatial regularity 保证 ~10^5 requests 仅有 ~32 distinct sizes。
- **适用条件**：仅当训练 iteration 内的 allocation pattern 重复稳定时有效（LLM 训练天然满足）。不适用于 allocation 模式剧烈变化的场景（如 dynamic architecture search）。
- **与 compiler register allocation 的类比**：HomoPhase Group ≈ live range analysis（lifespan clustering），HomoSize Group ≈ graph coloring（same-size reuse），Global Planning ≈ spill cost minimization。但 STAlloc 在 10^5 量级的 requests 上操作，远超过传统 compiler 的变量数量。

## Memory-Layer (内存层 — GPU 分配规划)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Memory-Layer 是 STAlloc 在 HomoSize Group 规划中提出的抽象概念：将**相同 size 但 lifespan 不重叠**的多个 allocation requests 在时间轴上堆叠，复用同一块 GPU 内存地址空间。每个 memory-layer 对应一个固定的内存地址区间 = 单一 request size，其时间轴上挂载了多个 non-overlapping 的 allocation requests。Memory-Layer 的构建算法（Algorithm 1）是最小化 layer 数量的贪心算法：按 allocation time 排序 requests → 对每个 request 找到空闲时间最早的 memory-layer → 追加到该 layer 的尾部。该算法等价于 interval graph coloring 问题，贪心策略给出的是最优解（最少层数 = 最大 concurrent requests 数）。

从编译框架角度拆解术语，比如术语如何在编译框架中发挥作用，给出术语在编译框架中运转流程的具体例子。

```
Memory-Layer 示例:
  Request size S = 4MB
  Requests: R1([t0, t5]), R2([t2, t8]), R3([t6, t10]), R4([t1, t4])

  Algorithm 1 构建过程:
    sort by t_s: R1, R4, R2, R3
    
    R1([0,5]): 创建 Layer 1, L1 = [R1], L1.end = 5
    R4([1,4]): L1.end(5) > R4.t_s(1) → 冲突! 创建 Layer 2, L2 = [R4], L2.end = 4
    R2([2,8]): L1.end(5) > R2.t_s(2) → 冲突! L2.end(4) ≤ R2.t_s(2)? NO (4>2) → 创建 Layer 3, L3 = [R2], L3.end = 8
    R3([6,10]): L1.end(5) ≤ R3.t_s(6)? YES → 追加到 L1, L1 = [R1, R3], L1.end = 10

  结果: 3 个 memory-layers:
    L1: [4MB reserved] — R1(0-5), R3(6-10)
    L2: [4MB reserved] — R4(1-4)
    L3: [4MB reserved] — R2(2-8)
  
  总预留: 3 × 4MB = 12MB（vs naive 每个 request 独立地址需 16MB）
  Memory efficiency within this size group: 16/12 = 75%

时间-空间可视化:
  addr ↑
  12MB | L3: [        R2         ]
   8MB | L2: [   R4   ]
   4MB | L1: [  R1   ][  R3  ]
   0MB +----+----+----+----+----+----→ time
         t0  t2   t4   t6   t8  t10
```

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **实现**：Algorithm 1 在 Plan Synthesizer 中以 Python 实现。每个 HomoSize Group（特定 size S）独立执行 memory-layer 构建。内存用量 = num_layers × S。
- **优化目标**：最小化 memory-layer 数量 = 最小化该 size group 的 GPU 内存占用。Algorithm 1 的贪心策略（选择 end time 最接近但 < t_s 的 layer）在 interval graph coloring 中是最优的。
- **与 Global Planning 的关系**：Memory-Layer 构造后，每个 layer 被视为一个"超级 request"（size = S, lifespan = layer 的整个时间跨度），参与全局规划（按 size 降序放置）。大 size layers 先放置 → 小 size layers 填入 gaps。
- **限制**：同一 memory-layer 内的 requests 必须 non-overlapping（lifespan 不冲突），且 size 严格相等。如果 requests 的 size 略有不同但相近，需要先按 size 分组（HomoSize Group），不能跨 size 共享 memory-layer。

## Time-Memory Product (TMP — 时-存乘积, 分配规划度量)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Time-Memory Product (TMP) 是 STAlloc 用于评估内存分配计划质量的度量指标，定义为：

$$TMP = \frac{\sum_{d \in D_g} d.s \cdot (d.t_e - d.t_s)}{D_g.s \cdot (D_g.t_e - D_g.t_s)}$$

其中分子度量实际的内存-时间使用量（每个 allocated chunk 的大小 × 其 lifespan），分母反映预留内存-时间总量（总预留大小 × 总时间段）。TMP ∈ (0, 1]，越高表示内存时间利用率越好、spatio-temporal bubbles（空闲时间-空间间隙）越少。TMP 借鉴自操作系统中经典的外部碎片度量 Shore (1975) [40]。

在 STAlloc 中，TMP 用于两个关键决策：(1) HomoPhase Group Fusion——计算两个 groups 独立时的 weighted average TMP 和融合后的 TMP，仅当融合后 TMP 更高（合并减少了总 bubbles）时才执行 fusion；(2) 最终分配计划的质量评估——TMP 接近 1.0 表示接近无碎片的理想分配。

从编译框架角度拆解术语，比如术语如何在编译框架中发挥作用，给出术语在编译框架中运转流程的具体例子。

```
TMP 在 HomoPhase Group Fusion 中的应用:

两个相邻 HomoPhase Groups:
  Group A: D_gA, TMP_A = 0.85, size_A = 100MB, duration_A = 500ms
  Group B: D_gB, TMP_B = 0.90, size_B = 50MB, duration_B = 300ms

Weighted Average TMP（独立不融合）:
  TMP_separate = (0.85 × 100 × 500 + 0.90 × 50 × 300) / (100 × 500 + 50 × 300)
               = (42500 + 13500) / (50000 + 15000) = 56000/65000 = 0.862

Fusion（将 Group B 的 requests 插入 Group A 的空闲位置）:
  TMP_fused = computed_after_insertion = 0.88

决策: TMP_fused (0.88) > TMP_separate (0.862) → Accept Fusion
     （融合后 bubbles 更少）

若 Fusion 导致更多 bubbles（TMP_fused < TMP_separate）:
  决策: Reject Fusion → 两组保持独立

直观理解（Figure 7 左右例）:
  Left (Fusion accepted): Group A 和 B 的 timelines 恰好互补——Group B 的 requests 
    可填入 Group A 的 bubbles，融合后内存 block 更紧凑
  Right (Fusion rejected): Group A 和 B 的 timelines 高度重叠——将 B 插入 A 
    反而产生更多碎片，不如两组各自独立
```

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **实现**：TMP 在 Plan Synthesizer 中以 Python 实现，为每个 HomoPhase Group 计算并缓存。Fusion 尝试（尝试将较小的 group 插入较大的 group）时的临时 TMP 通过模拟插入后的 placement 计算。
- **理论基础**：Shore (1975) "On the external storage fragmentation produced by first-fit and best-fit allocation strategies" 中首次提出 time-memory product 概念用于分析分配器碎片。
- **Fusion 决策的保守性**：仅当 TMP 严格提升（而非持平）时才接受 fusion，避免引入不必要的 group 膨胀。这保证 Plan Synthesizer 的输出是单调改善的。
- **限制**：TMP 仅评估 memory-time utilization，不直接反映峰值内存（peak memory）——两个 groups 的 TMP 都很高但峰值叠加时，可能仍需要更大的总预留。STAlloc 的全局规划（按 size 降序放置）通过优先放置大 size 来间接控制峰值。

- Reducing GPU Memory Fragmentation via Spatio-Temporal Allocation Planning (STAlloc)

## Static Allocation Plan (GPU 内存静态分配计划)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Static Allocation Plan 是 STAlloc 的 Plan Synthesizer 输出的核心产物——一个预先计算的、包含每个 static allocation request 具体 GPU 内存地址的分配方案。每个 entry d ∈ D_s 包含完整的 allocation 信息：`d = (s, t_s, t_e, p_s, p_e, dyn=False, a)`，其中 a 是 Plan Synthesizer 通过 HomoPhase/HomoSize Group 规划后为 request 分配的起始地址。Plan 保证对于任意两个 allocation decisions d_i 和 d_j，它们不同时具有冲突的 lifespan 和冲突的地址范围（即无内存踩踏）。该 Plan 是训练前一次性生成的（~2-6 分钟），训练过程中不变。

Static Allocation Plan 的关键特性：(1) 地址是绝对的（相对于预分配的 static memory pool 基址的偏移）；(2) 大小覆盖所有 static requests 的峰值内存（约 73%-99% 的总分配）；(3) Dynamic requests 不在 plan 中有固定地址，而是在 plan 的空闲区间（Dynamic Reusable Space）中在线分配。

从编译框架角度拆解术语，比如术语如何在编译框架中发挥作用，给出术语在编译框架中运转流程的具体例子。

```
Static Allocation Plan 的生成和使用:

生成（Plan Synthesizer, offline, once）:
  输入: Profiler trace M_s (static requests only)
  处理:
    1. HomoPhase Grouping → Local Plans per phase group
    2. HomoSize Grouping → Memory-Layers per size group
    3. Global Planning → Address assignment per request
  输出: D_s = {(s, t_s, t_e, p_s, p_e, dyn=False, a) for each static request}

内存布局示例（简化）:
  addr ↑
  60GB | WWWWWWWWWWWWWWWWWWWWWWWWWWWWWWWW  | (Persistent: weights, grads, optimizer)
  50GB | AAAA  BBBB    CCCC  DDDD  EEEE    | (Scoped activations, HomoPhase-packed)
  40GB |     AABB  BBCC    DDEE            | (Memory-Layer reused same-size tensors)
  30GB |   AA    BB  CC  DD    EE          |
  20GB | [     Dynamic Reusable Space     ] | (Idle spaces for dynamic requests)
  10GB | AA__BB__CC__DD__EE__FF__GG__HH   | (Transient tensors, short lifespan)
   0GB +----------------------------------→ time
        t0   t1   t2   t3   t4   t5   t6

使用（Runtime Allocator, training time）:
  Static requests: hash(module_name, tensor_id) → lookup in D_s → return a
    O(1) per request, no search, no GPU API calls
  Dynamic requests: 
    1. 识别 HomoLayer Group G(l_s, l_e)
    2. 获取该组的 Dynamic Reusable Space A_i
    3. A_c = A_a ∩ A_i (当前空闲 ∩ pre-identified reusable)
    4. best-fit in A_c → allocate
    5. 若无法满足 → fallback Caching Allocator
```

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **存储格式**：D_s 以 hash map（key = request identifier from profiler）存储，每个 entry 包含 size + lifespan + address。运行时以 (module_name, tensor_shape, phase) 元组作为 lookup key。
- **大小**：对于 Llama2-7B-R（~86,721 static requests），D_s 约为数 MB（每个 entry ~64 bytes）。
- **预分配**：训练初始化时，STAlloc 根据 D_s 的峰值预留一块 contiguous GPU memory（通过单次 cudaMalloc），之后所有 static/dynamic allocations 在此 pool 内操作，不再调用 cudaMalloc/cudaFree。
- **错误处理**：若 runtime 出现不在 D_s 中的 request（plan mismatch），fallback 到 Caching Allocator（PyTorch 兼容模式），保证 robustness。
- **与 compiler 产物类比**：Static Allocation Plan 类似于 compiler 在 register allocation 后的 spill decision——它预先决定了每个"变量"（tensor）的"寄存器/栈位置"（GPU memory address），runtime 仅需查表。区别在于 scale（10^5 vs 10^2 量级）和维度（增加了时间维度的 lifespan 管理）。

## Logical Grid Dimensions

术语是什么？

逻辑网格维度（Logical Grid Dimensions）是 Flashlight 引入的一种分块策略，将编译器为 kernel 生成的分块网格（tiling grid）与 GPU 物理线程块数量限制解耦。在 GPU 编程中，kernel 的启动网格受硬件限制（如 `gridDim ≤ 65535` 每个维度），当问题规模较大时（如长序列 attention），逻辑分块可能超出物理 grid 限制。Flashlight 的逻辑网格维度允许编译器在 IR 层面使用任意 tile 维度组合，由代码生成阶段自动映射到物理 grid（通过 tile 合并或 grid-stride loop），使优化搜索空间不再受物理 grid 限制约束。

从编译框架角度拆解术语：

```
逻辑网格 vs 物理网格:

问题: attention with seq_len=131072, tile_size=128
  → 逻辑 m_blocks = 131072/128 = 1024
  → 如果 head dim=128, n_blocks = 131072/128 = 1024
  → 如果 num_heads=32, batch_size=8
  → 总 CTA 数 = 1024 × 1024 × 32 × 8 = 268,435,456
  → 远超物理限制 (单维度 ≤ 65535, 一维 grid ≤ 约 2³¹)

传统解决 (没有逻辑网格):
  方案 A: 增大 tile size (256, 512, ...) → 减少 block 数, 但可能降低 occupancy
  方案 B: 多维度 grid (2D/3D grid) → 需要手动映射 blockIdx 到逻辑坐标
  方案 C: grid-stride loop → 每个 block 处理多个 tile, 增加代码复杂度
  所有方案都限制了优化空间

Flashlight 逻辑网格:
  # IR 层面使用逻辑网格 (任意维度组合):
  logical_grid = (m_blocks=1024, n_blocks=1024, heads=32, batches=8)
  tile_shape = (M_tile=128, N_tile=128)
  
  # 代码生成时自动映射到物理网格:
  option 1: 平坦化 + 2D grid (充分利用 2D grid 的 65535²)
    gridDim.x = min(logical_total, MAX_GRID_X)
    gridDim.y = ceil(logical_total / gridDim.x)
  option 2: grid-stride loop (grid 大小 = SM 数 × 目标 occupancy)
    for logical_idx = blockIdx.x; logical_idx < logical_total; logical_idx += gridDim.x:
        (m, n, h, b) = unravel(logical_idx, logical_shape)
        process_tile(m, n, h, b)
  option 3: 混合 (某些维度用 grid-stride, 其他用 grid 直接映射)
```

**逻辑网格维度的意义**：
- 使编译器的 tile 大小选择不再受物理 grid 限制约束，扩大了优化搜索空间
- 代码生成阶段自动选择最优的物理映射策略，对上层 pass 透明
- 允许不同 tile 维度有独立的大小（如 M_tile=128, N_tile=64），提供更细粒度的分块控制

术语一般如何实现？如何使用？

- **IR 表示**：在 Flashlight 的扩展 TorchInductor IR 中，每个循环维度标注为 `#parallel` 或 `#reduction`，逻辑网格通过 `logical_grid_dims` 属性指定
- **代码生成**：Triton 的 `tl.program_id` 和 `tl.num_programs` 支持 grid-stride loop；Flashlight 在生成 Triton 代码时插入映射逻辑
- **与 Triton 的关系**：Triton 本身支持 1D/2D/3D grid（`grid` 参数），Flashlight 的逻辑网格在 Triton 的 grid 之上增加了一层抽象
- **适用场景**：大模型 + 长序列场景（如 128k context），逻辑 tile 数量远超 GPU grid 限制

涉及论文标题：
- Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

## Symbolic Shape Semantics (符号化形状语义)

术语是什么？

Symbolic Shape Semantics 是 STeP 编程抽象中用于**在编译时以符号表达式形式推导和验证 stream shape 的代数系统**。其核心思想是：在异步数据流编程中，每个 stream 不仅有数据类型，还有形状（shape），形状的维度可以是 static-regular（编译时常量）、dynamic-regular（运行时数据依赖常量）或 ragged（运行时可变化）。Shape semantics 定义了每种 STeP operator 对输入 stream shape 的变换规则，使编译器可以在编译时验证 stream shape 对齐（producer-consumer）、计算符号化的性能指标（off-chip traffic, on-chip memory requirement），并暴露 dynamic dimension 对 performance 的影响。

STeP 的 shape semantics 形式化为：
- 每个 rank-N stream（data type T）的形状为 $[D_{N-1}, \cdots, D_1, D_0]$，其中每个 $D_i$ 是 static-regular（常量）、dynamic-regular（符号常量）或 ragged（可变值集合）之一。
- Ragged dimensions 具有 **absorbing property**：如果某维度的 shape equation 包含 ragged dimension，该维度被当作新的 ragged dimension。例如 flatten 最内两个维度时，$[2, 2 \times D_0]$ → $[2, D'_0]$（而非 $[2, 2 \times D_0]$），其中 $D'_0$ 是新引入的 ragged dimension 符号。
- 维度类型按约束性强弱排序：regular > ragged, static > dynamic。若 operator 接受某种维度类型，它也接受更约束的类型。

从编译框架角度拆解术语：

Symbolic Shape Semantics 在 STeP symbolic Python frontend 中的编译时分析流程：
```
STeP Program (Python frontend):
  inp = LinearOffChipLoad(ref=..., ...)
  routed = Partition(inp, selector, num_consumers=2)
  ...

          ↓ Frontend Shape Inference

Shape Derivation for each operator:
  LinearOffChipLoad:
    Input ref shape: [D_1, D_0]                  (D_1 dynamic-regular)
    tiled_in_shape: [64, 256]                     (tiles of [64,256])
    Output shape: [D_1, 64//64, 256//256] = [D_1, 1, 1]  
  
  Partition(rank=b=0):
    Input shape: [D_1, 1, 1]                     (data stream)
    Selector shape: [D_1]                         (selector stream)
    Output shapes: [D_i, 1, 1] per branch i       (D_i dynamic-regular)
    Constraint: sum(D_i for all i) = D_1            (verified symbolically)

          ↓ Symbolic Metric Computation (SymPy)

For each operator, compute symbolic expressions:
  OffChipLoad:
    Off-chip traffic = ||[D_1, 1, 1]|| × |tile[64,256]|
                     = D_1 × 1 × 1 × (64×256 × 2 bytes)  (BF16)
                     = D_1 × 32768 bytes
  
  Bufferize(rank=1):
    On-chip memory = |input_dtype| + ||buffer|| × |input_dtype| × 2
    Where ||buffer|| = D_0_buffer (dynamic-ragged symbol)

          ↓ Symbol Substitution & Aggregation

Total off-chip traffic = sum of all off-chip operator expressions
Total on-chip memory = sum of all on-chip operator expressions

To analyze specific workload:
  Substitute D_1 = 64 (batch size), D_0_buffer = avg_tokens_per_expert
  → Get concrete numeric estimates
```

Shape semantics 的静态验证能力：
1. **Producer-Consumer Shape Alignment**：Frontend 内部验证 producer stream 的 output shape 与 consumer 的 expected input shape 一致（line 27 of Listing 1: `print_routed.get_shape()`）。
2. **已知属性的利用**：例如 Reassemble 引入的新动态维度可用输入 stream shape 替代（line 26 of Listing 1）。
3. **维度类型检查**：确保 operator 仅接受其支持的维度类型（如 Reshape 拆分最内维时无 static 限制，拆分更高维时需要 static 且可被 chunk_size 整除）。

术语一般如何实现？如何使用？

Symbolic shape semantics 的实现基于：
- **SymPy [Meurer et al., PeerJ 2017]**：Python 符号计算库，用于表达式推导、简化和替换。
- **Per-operator equations**：STeP frontend 为每个 operator 类型预定义了 shape transformation rules 和 metric equations。

在 STeP workflow 中的使用：
1. **Design Space Exploration (DSE)**：程序员写 STeP 程序后，frontend 自动推导符号化的 off-chip traffic 和 on-chip memory。通过代入不同的 tile sizes、parallelization factors，快速比较设计点（无需运行 simulator）。
2. **性能瓶颈诊断**：符号表达式直接暴露 memory traffic 和 on-chip memory 对 dynamic dimension 的依赖关系，帮助识别 memory-bound 或 compute-bound 的根源。
3. **与 Simulator 协同**：符号表达式提供 bound 估计，simulator 提供精确 cycle count。对于包含 runtime data 依赖的 operator（dynamic-regular/ragged dimensions），simulator 测量实际值并聚合到符号表达式中。

与 synchronous dataflow 的 shape semantics 的区别：
- Synchronous dataflow（如 StreamIt）：data rate 固定，shape 推导简单。
- Asynchronous dataflow（STeP）：data rate 可以是动态的，shape semantics 必须处理 dynamic-regular 和 ragged dimensions，并为未知维度引入符号变量。

涉及论文标题：
- Streaming Tensor Programs (STeP)

## Streaming Tensor Programs (STeP / 流式张量程序)

术语是什么？

Streaming Tensor Programs (STeP) 是 Stanford PPL 提出的**面向空间数据流加速器（SDA）的异步数据流编程抽象**，目标是为动态张量应用（如 LLM 推理中的 MoE 和 attention）提供高效的 SDA 编程模型。STeP 是 ASPLOS 2026 论文 "Streaming Tensor Programs: A Streaming Abstraction for Dynamic Parallelism" 的核心贡献。

STeP 的三个核心属性：
1. **Explicit Memory Hierarchy（显式内存层次）**：通过 Off-chip memory operators（LinearOffChipLoad/Store, RandomOffChipLoad/Store）和 On-chip memory operators（Bufferize, Streamify）显式控制数据在不同存储层级间的移动，使内存访问模式对程序员/编译器可见。
2. **Symbolic Data Consumption and Production Rate（符号化数据速率）**：每个 STeP stream 具有 shape semantics，维度可以是 static-regular、dynamic-regular 或 ragged。Shape 在抽象层面即已知（即使包含动态维度），使编译器无需"lift imperative code"即可分析性能。
3. **Data-dependent Control Flow Operators（数据依赖控制流算子）**：Partition、Reassemble、EagerMerge 支持在 tile 粒度（非 scalar 粒度）进行动态路由和合并，保持 tiled computation 的数据复用效率。

STeP 的工具链包括：
- **Symbolic Python Frontend**：类似 PyTorch 的编程接口，使用 SymPy 做符号化性能分析。
- **Rust Cycle-Approximate Simulator**：基于 Dataflow Abstract Machine (DAM) framework [Zhang et al., ISCA 2024]，集成 Ramulator 2.0 HBM 模拟。

从编译框架角度拆解术语：

STeP 作为编译框架的全流程：
```
High-Level Framework (PyTorch)
  │ torch.compile
  ▼
FX Graph (tensor-level operators)
  │ Compiler: traverse FX nodes, lower to STeP subgraphs
  │ Optimization schedules specified via index variables
  ▼
STeP Graph (stream-level operators)
  │
  ├─→ Symbolic Frontend (Python/SymPy):
  │     • Shape inference & verification
  │     • Symbolic metric computation (off-chip traffic, on-chip memory)
  │     • DSE: compare design points without simulation
  │
  └─→ Rust Simulator (DAM framework):
        • Cycle-approximate execution
        • HBM timing (Ramulator 2.0)
        • Roofline model for higher-order operators
        • Output: cycles, traffic, memory, utilization
              │
              ▼
        Performance Metrics & Design Points
```

STeP 的程序由五类算子组成（20+ 个算子）：
- **Off-chip Memory**: LinearOffChipLoad/Store, RandomOffChipLoad/Store
- **On-chip Memory**: Bufferize, Streamify
- **Dynamic Routing & Merging**: Partition, Reassemble, EagerMerge
- **Higher-order**: Map, Accum, Scan, FlatMap
- **Shape**: Flatten, Reshape, Promote, Expand, Zip

STeP 相比 prior SDA abstractions 的独特能力（Table 1）：
| 能力 | Spatial | Revet | StreamIt | SAM | Ripple | STeP |
|------|---------|-------|----------|-----|--------|------|
| Dataflow | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| Explicit Data Rate | ✗ | ✗ | ✓ | ✗ | ✗ | ✓ |
| Explicit Memory Hierarchy | ✓ | ✓ | ✗ | ✗ | ✗ | ✓ |
| Dynamic Routing & Merging | ✗ | ✓(limited) | ✗ | ✓(limited) | ✓ | ✓ |
| Dynamic On-chip Tiling | ✗ | ✗ | ✗ | ✓(limited) | ✗ | ✓ |

术语一般如何实现？如何使用？

STeP 的使用方式：
1. **直接编程**：程序员使用 STeP symbolic Python frontend 编写 SDA 程序，同时指定 schedule（parallelization, tiling, memory placement）。写 STeP 程序类似写 PyTorch，但使用 STeP operators，每个 instruction 有自己的异步执行 loop。
2. **编译器 target**：STeP 可作为 torch.compile 的 lowering target——PyTorch model → FX graph → STeP subgraphs。优化 schedules 通过 index variables 指定。
3. **DSE 工具**：Frontend 的符号分析 + simulator 的精确模拟结合，用于探索 tiling schemes、parallelization strategies、configuration time-multiplexing degrees。

## Algebraic Layout System (代数布局系统)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Algebraic Layout System 是 Tilus DSL/编译器提出的**寄存器张量布局的代数化表示和操作框架**，用于精确描述 GPU 线程块内 tile 元素如何分布到各线程的寄存器中。核心构成：

1. **参数化原语布局（Primitive Layouts）**：两种基本布局类型——`local(n₁, n₂)` 将所有 tile 元素存储在单个线程中（每个线程持有 n₁×n₂ 个元素，按 row-major 排列）；`spatial(n₁, n₂)` 将元素分布在 n₁×n₂ 个线程中（每个线程持有 1 个元素）。布局定义为函数 f(t, i)，映射线程索引 t 和局部元素索引 i 到逻辑元素坐标。例如 `local(2,3)` 给出 f(t,i) = (i/3, i%3)，`spatial(2,3)` 给出 f(t,i) = (t/3, t%3)。

2. **Kronecker Product (⊗, 布局组合)**：两个布局 f 和 g 的 Kronecker product h = f ⊗ g 定义为 h(t,i) = f(t/T_g, i/N_g) ⊙ S_g + g(t%T_g, i%N_g)，其中 T_g(N_g) 是 g 的线程数（局部元素数），S_g 是 g 的 shape。该操作是**结合但不交换**的。通过 ⊗ 可以从基本原语组合出任意复杂布局，如 Tensor Core mma.m16n8k16 的 A 操作数布局可表示为 `local(2,1) ⊗ spatial(8,4) ⊗ local(1,2)`。

3. **布局除法（Layout Division, /）**：若 h = f ⊗ g，则 f = h / g 为布局除法的结果。这允许从复合布局中提取子结构，是实现寄存器张量 reinterpretation 的数学基础。

4. **统一布局表示（Unified Layout Representation）**：每个布局用 4 个属性表示——shape（张量形状）、mode_shape（维度分解后的子维度列表）、spatial_modes（分配给线程的子维度）、local_modes（分配给线程局部存储的子维度）。通过 split→distribute→merge 三步将逻辑索引映射到 (thread_index, local_index) 对。

从编译框架角度拆解术语：

Tilus 编译器中，代数布局系统在以下编译阶段发挥作用：
- **DSL 编程阶段**：程序员通过 `local(a,b).spatial(c,d).local(e,f)` 等语法显式指定寄存器张量的分布式布局，编译器将其解析为统一布局表示（mode_shape, spatial_modes, local_modes）。
- **IR lowering 阶段**：布局的代数性质使编译器可以自动验证两个布局之间的 reinterpretation 是否合法——检查两者是否具有相同的 (T, N)（线程数和每线程元素数）和相同的 per-thread bit 数。例如 i6 的 `local(2,1).column_spatial(4,8).local(2,1)` 和 u8 的 `local(3).spatial(32)` 都是 32 线程 × 24 bits/thread，因此可以无代价互相 reinterpret。
- **指令选择阶段**：编译器检查布局是否兼容硬件优化指令。例如，若寄存器张量布局可被 `spatial(8,4).repeat(1,4)` 整除（通过布局除法检查），则可以选择 ldmatrix PTX 指令替代 lds。
- **代码生成阶段**：布局信息驱动自动向量化——根据 spatial_modes 和 local_modes 确定哪些维度适合向量化内存访问（如 ldg128, cp.async.v4）。

Tilus 的实现（开源在 https://github.com/NVIDIA/tilus）：布局通过 Python DSL 中的链式语法定义，例如 `column(2,2).spatial(8,4).local(1,2)` 等价于 Kronecker product 表达式。编译器将布局解析为 mode_shape + spatial_modes + local_modes 的统一表示，在优化 passes 中进行布局兼容性检查和变换。最终 CUDA 代码生成时，布局信息被展开为 per-thread 的数组索引计算，将逻辑张量访问转化为具体的寄存器访问。

## Thread-Block-Level Programming Model / SIMB Paradigm (线程块级编程模型)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Thread-Block-Level Programming Model（Tilus 中称为 Single-Instruction-Multiple-Block, SIMB）是一种 GPU 编程抽象，将操作定义在 **thread block 粒度**而非传统 CUDA/PTX 的 thread 粒度（SIMT 范式）。在 SIMB 模型中，一条指令操作整个 thread block 中的所有线程——所有线程协作完成同一操作的不同部分，程序员不需要关心单个线程的行为。

Tilus 的 VM 指令集完全基于此模型设计，分类包括：
- **Indexing**：`BlockIndices()` 获取当前 thread block 在 grid 中的索引
- **Tensor Creation**：`AllocateGlobal/Shared/Register(dtype, shape, [layout])` 分配不同内存空间中的张量；`ViewGlobal(ptr, dtype, shape, [layout])` 创建全局内存视图
- **Tensor Transferring**：`LoadGlobal/Shared(tensor, layout, offset)` 从全局/共享内存加载到寄存器；`StoreGlobal/Shared(tensor, mem, offset)` 存储回内存；`CopyAsync(shared, global)` 发起异步拷贝
- **Register Tensor Computation**：`Dot(a, b, c)` 执行矩阵乘法累加 d=a×b+c；`Cast(a, dtype)` 类型转换；`View(a, [dtype], [layout])` 无代价 reinterpretation
- **Control**：`Synchronize()` 同步线程块执行；`Exit()` 退出
- **Debug**：`Print(tensor)`

从编译框架角度拆解术语：

在 Tilus 编译器中，SIMB 模型的工作流程：
1. **DSL 输入**：程序员用 Python 编写 Tilus program，逻辑上每个操作都作用于整个 thread block。例如 `a_tile = LoadGlobal(A_global, layout=..., offset=[bi*BM:, k:])` 表示整个 thread block 协作从 A_global 中加载一个 BM×BK tile。
2. **IR 生成**：每条 SIMB 指令被翻译为 Tilus VM IR 中的一条 thread-block-level 指令。
3. **Code Emitting (→Hidet IR)**：每条 block-level 指令被展开为低层 per-thread CUDA 代码。例如 `LoadGlobal` 根据寄存器的 layout 和 global memory offset 计算出每个线程应访问的内存地址和应该使用的向量化加载指令（如 ldg128），然后生成对应的 per-thread load 代码。
4. **自动向量化**：编译器利用 layout 信息自动选择最宽的向量化内存访问指令——spatial 分布越宽的维度，越容易合并为向量化访问。
5. **同步管理**：`Synchronize` 指令在 code emitting 时翻译为 `__syncthreads()`。编译器还需确保 `CopyAsync` 和 `CopyAsyncWaitGroup` 之间正确插入同步点。

SIMB 模型的关键优势是它保留了高层结构信息（如张量 shape、layout、内存空间）直到 code generation 阶段，使编译器可以做更多优化。相比 Triton（也使用 block-level 编程但隐藏了 layout 和 memory hierarchy），Tilus 的 SIMB 显式暴露这些信息给编译器和程序员，使手工 kernel 级别的优化（如精确的寄存器分配、software pipelining、指令选择）可以在编译器框架内自动完成。Tilus 开源在 https://github.com/NVIDIA/tilus，约 35K 行 Python + C++ 代码。
