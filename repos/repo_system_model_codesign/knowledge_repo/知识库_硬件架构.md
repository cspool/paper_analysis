# 知识库_硬件架构

## Reconfigurable Dataflow Architecture (RDA / 可重构数据流架构)

术语是什么？

Reconfigurable Dataflow Architecture (RDA) 是一类**以粗粒度可重构计算单元（CGRA PE）为基本模块、通过可编程的 streaming interconnect 直接连接功能单元形成数据流图的硬件架构**。与传统的冯·诺依曼架构依赖指令驱动的控制流和缓存层次不同，RDA 的核心思想是：计算在空间上映射为功能单元的连接拓扑，数据通过 streaming connections 在单元间直接流动，减少对昂贵缓存和本地存储的依赖。

RDA 的关键特征：
1. **Spatial Computing**：计算在空间上分布式执行，而非时序上串行执行。每个功能单元独立处理流经它的数据流。
2. **Streaming Dataflow**：数据以 token 序列（streams）的形式在功能单元间流动，通过 ready-valid handshake 实现反压（back-pressure）。
3. **Reconfigurability**：功能单元间的连接关系和每个单元的功能可重配置，支持不同的算法映射。
4. **Coarse-Grained**：与 FPGA 的细粒度 LUT 级可重构不同，RDA 的 PE 是粗粒度的（如 ALU、乘法器、归约器等），面积效率更高。

从硬件架构角度拆解术语：

RDA 在 FuseFlow/SAM 生态系统中的硬件实现层次：
```
SAMML Graph (软件的 dataflow graph)
    ↓ 编译映射
RDA Hardware:
  ┌─────────────────────────────────────────┐
  │ PE Array (e.g., 384 PEs in Onyx)        │
  │  ┌──────┐  ┌──────┐  ┌──────┐          │
  │  │ LS   │→│Inters│→│ ALU  │→ ...      │
  │  │ (PE) │  │ (PE) │  │ (PE) │          │
  │  └──────┘  └──────┘  └──────┘          │
  │    ↕ streaming interconnect             │
  │  ┌──────┐  ┌──────┐  ┌──────┐          │
  │  │ Rep  │  │ Red  │  │ LW   │          │
  │  │ (PE) │  │ (PE) │  │ (PE) │          │
  │  └──────┘  └──────┘  └──────┘          │
  ├─────────────────────────────────────────┤
  │ Memory Tiles (e.g., 128 in Onyx)        │
  │  Level Buffers, Load/Store Engines      │
  ├─────────────────────────────────────────┤
  │ Global Buffer (e.g., 4MB in Onyx)       │
  │  └→ HBM2 / DRAM off-chip memory         │
  └─────────────────────────────────────────┘
```

RDA 特别适合稀疏计算的原因：稀疏数据的不规则访存模式使传统缓存层次效率低下（GPU SM 利用率平均仅 16.7%，如图 1），而 RDA 通过显式的 streaming connections 协调数据移动，绕过缓存层次，直接处理不规则访存。

术语一般如何实现？如何使用？

RDA 的物理实现包括：
- **Onyx [42]**：Stanford 的 12nm CGRA，384 PE tiles + 128 Memory tiles，756 GOPS/W，首个支持通用稀疏张量代数的可编程加速器。
- **Opal [10]**：Onyx 的后续芯片（16nm），增加稀疏 ML 支持（非线性、masking），是 FuseFlow SAMML graph 的直接编译目标。
- **Capstan [60]**：Stanford 的向量 RDA，支持稀疏计算的 vector 风格数据流。
- **Plasticine [57]**：早期 RDA 设计，支持 parallel patterns 到数据流硬件的编译。

FuseFlow 生成的 SAMML graph 可映射到上述任何 RDA 硬件——SAMML 的每个 primitive node（LS, Intersect, Rep, ALU, Red, LW, CD）对应一个 RDA PE 配置，streams 对应物理互联。

- FuseFlow

## Coarse-Grained Reconfigurable Array (CGRA / 粗粒度可重构阵列)

术语是什么？

Coarse-Grained Reconfigurable Array (CGRA) 是一种**由粗粒度处理单元（PE）组成的可重构计算架构**。与 FPGA 的细粒度 LUT 级可重构不同，CGRA 的 PE 是字级（word-level）的算术/逻辑功能单元（如 ALU、乘法器、归约器），通过可编程的片上网络（NoC）互联。

CGRA 的典型特征：
- **PE 粒度**：每个 PE 可执行整数/浮点算术、逻辑操作、数据路由等，而非单个门或 LUT。
- **可重构互联**：PE 间的连接拓扑可通过配置位流（bitstream）重编程，在运行时或编译时确定。
- **能效优势**：与 FPGA 相比，CGRA 的重配置开销更小（配置字少于 LUT 配置位流），面积效率更高（PE 面积不到 FPGA 等效逻辑的 1/10）；与 GPU 相比，CGRA 避免了指令 fetch/decode 开销。
- **空间架构**：类似于脉动阵列（systolic array），但 PE 功能和互联更灵活。

从硬件架构角度拆解术语：

CGRA PE 在 SAM/SAMML 执行中的角色映射：
```
SAM Primitive     → CGRA PE Configuration
────────────────     ─────────────────────
Level Scanner     → PE + Address Generator (遍历 fibertree 数据结构)
Intersect/Union   → PE + Comparator (比较多个坐标流)
Repeater          → PE + FIFO (按 repeat signal 复制值)
ALU               → PE (Arithmetic/Logic Unit)
Reducer           → PE + Accumulator (累加 partial sums)
Level Writer      → PE + Store Engine (写回结果)
Coordinate Dropper→ PE + Zero Detector (过滤零坐标)
Stream Par/Ser    → PE + Fork/Join FIFO (并行化/串行化)
```

Onyx CGRA 的具体参数（Koul et al., VLSI 2024/JSSC 2025）：
| 参数 | 数值 |
|------|------|
| 工艺 | GF 12nm |
| PE 数量 | 384 tiles |
| Memory tiles | 128 tiles |
| Global Buffer | 4 MB (16 tiles) |
| 能效 | 756 GOPS/W (INT16) |
| 主机处理器 | Arm M3 |
| 稀疏核 EDP | 最高 565× vs CPU+MKL/TACO |

术语一般如何实现？如何使用？

CGRA 的设计流程（以 Stanford AHA 流程 [Koul et al., TECS 2023] 为例）：高层 DSL（如 Peak/Ocean for PE 功能，Canal for 互联）→ RTL 生成 + 编译器 collateral 生成 → ASIC 流片。FuseFlow 编译的 SAMML graph 可通过 Cascade [Melchert et al., TCAD 2024] 应用流水线工具包映射到 CGRA 的物理 PE 阵列。

- FuseFlow

## Streaming Dataflow Model (流式数据流模型)

术语是什么？

Streaming Dataflow Model 是一种**以数据流 tokens 在功能单元间流动为基本执行范式的计算模型**。与传统的控制流模型（程序计数器驱动指令序列）不同，数据流模型中，操作的执行由**输入数据的到达（availability）**触发，而非由指令指针的顺序推进。

在 FuseFlow/SAM 的上下文中，Streaming Dataflow Model 的具体形式是：
- **Data = Streams of Tokens**：数据表示为流经数据流图的 token 序列。每个 token 携带一个数据值（坐标、引用或值）和隐式的控制信息（token 存在/不存在表示坐标空间中的位置）。
- **Control = Token-Driven**：每个数据流原语（node）在接收到所有必要输入 tokens 时执行（fire），产生输出 tokens 发送到下游。
- **Back-pressure**：Stream edges 有 FIFO 缓冲。当下游 node 的输入 FIFO 满时，上游 node 被反压（stall），实现自然的流水线同步。
- **Pipelining**：数据流图天然是流水线的——不同 tokens 可以在不同 nodes 中同时处理（spatial parallelism），无需显式的流水线寄存器插入。

从硬件架构角度拆解术语：

Streaming Dataflow 在 RDA 硬件中的物理实现：
```
Token format (在 streaming interconnect 上):
  ┌────────────┬──────────┬──────────┐
  │ valid bit  │ data[W]  │ ready bit│
  └────────────┴──────────┴──────────┘
  valid=1 表示当前 cycle 有有效数据
  ready=1 表示下游可以接收
  
Handshake protocol (ready-valid):
  Cycle t:   upstream puts data, sets valid=1
             downstream can receive, sets ready=1
  Cycle t+1: if valid && ready: data transferred
             else: stall (data held until ready=1)

Stream types in SAM/SAMML:
  - crd (coordinate stream): 坐标值流，如 {i0, i1, i2, ...}
  - ref (reference stream): 指向内部层级的引用，如 {ptr_to_row0, ptr_to_row1, ...}
  - val (value stream): 数值流，如 {B[i0,j0], B[i1,j1], ...}

在 Onyx CGRA 中的实现:
  - SplitFIFO [Koul et al.]: 将 ready/valid 和 data 路径分离的 FIFO 设计
  - 节省 13% 互联面积
  - 每个 PE→PE 连接为一个 SplitFIFO channel
```

术语一般如何实现？如何使用？

Streaming Dataflow 模型在以下系统中实现：
- **SAM (Sparse Abstract Machine)**：将 streaming dataflow 形式化为 tensor algebra 的抽象机器。
- **Comal Simulator**：基于 DAM framework 的 CSP-with-time 模型，用 token-passing 模拟 streaming dataflow 的 cycle-accurate 行为。
- **Onyx/Opal CGRA**：物理硬件中的 ready-valid streaming interconnect。
- **Spatial [Koeplinger et al., PLDI 2018]**：将 parallel patterns 编译到 streaming dataflow 硬件的高级语言。

涉及论文标题：
- FuseFlow

## Comal Simulator

术语是什么？

Comal 是 FuseFlow 使用的 **cycle-accurate 数据流模拟器**，基于 DAM (Dataflow Abstract Machine) 仿真框架 [Zhang et al., ISCA 2024]。Comal 对 SAMML 数据流图中的每个 IR node 的行为进行建模，追踪 fully pipelined dataflow 执行中的 cycles，并集成 HBM2 内存模拟（通过 Ramulator 2.0 [Luo et al., 2023]）。

Comal 的模拟原理：
1. **Token-Passing Simulation**：模拟器以 tokens 为单位追踪 dataflow graph 中的状态。每个 node 维护输入/输出 FIFO 队列，按 pipeline depth 处理 tokens。
2. **Cycle-Accurate Timing**：每个 node 的处理延迟（cycles）根据 pipeline depth 建模。Stream edges 在 FIFO 满时产生 back-pressure stall。
3. **Memory Simulation**：HBM2 内存访问的延迟和带宽通过 Ramulator 2.0 模拟，集成到 Level Scanner（读取内存）和 Level Writer（写入内存）的时序中。

从硬件架构角度拆解术语：

Comal 在 FuseFlow 工具链中的位置：
```
FuseFlow Compiler → SAMML Graph (JSON/Dialect)
                         ↓
Comal Simulator:
  ├─ Graph Parser: 解析 SAMML nodes & edges
  ├─ Token Engine: token-passing simulation
  │   ├─ Node Models: LS, Intersect, Rep, ALU, Red, LW, CD 的时序模型
  │   ├─ Stream Models: FIFO depth, bandwidth, back-pressure
  │   └─ Parallelization Models: Stream Par/Ser fork-join 同步
  ├─ Memory Model: Ramulator 2.0 (HBM2 timing)
  └─ Instrumentation: cycle count, FLOPs counter, bytes transferred counter
                         ↓
Output: latency (cycles), FLOPs, bytes, operational intensity
```

FPGA 验证：论文通过将 SAMML graph 综合到 Xilinx VU9P FPGA（Vitis HLS），比较 FPGA 实测 cycle count 与 Comal 模拟 cycle count，验证模拟器保真度。在 GCN、GraphSAGE、BigBird attention 多个 kernel 上，$R^2 = 0.991$（图 13），表明 Comal 与 RTL 仿真的趋势高度一致。

术语一般如何实现？如何使用？

Comal 在 FuseFlow artifact 中通过 Docker 容器提供。用户运行 `python3 scripts/figure_12.py --workers=N` 即可在 Comal 上执行所有 fusion 配置的仿真。模拟器基于 DAM framework（Rust 编写，开源 GitHub: `stanford-ppl/DAM-RS`），DAM 的 CSP-with-time 接口允许同时描述功能行为和时序行为。

涉及论文标题：
- FuseFlow

## DAM Simulation Framework (数据流抽象机器仿真框架)

术语是什么？

DAM (Dataflow Abstract Machine) Simulation Framework 是 Zhang et al. (ISCA 2024) 提出的**通用数据流系统仿真框架**，用 Rust 编写，开源在 `github.com/stanford-ppl/DAM-RS`。DAM 的核心理念是将数据流系统的仿真建模为 **Communicating Sequential Processes with Time (CSP-with-Time)**——允许用户同时描述功能行为（数据如何变换）和时序行为（变换需要多少 cycles）。

DAM 的三个关键技术：
1. **CSP-with-Time Interface**：每个仿真模块（process）用相同的接口描述功能（接收 tokens → 变换 → 发送 tokens）和时序（延迟 cycles、pipeline depth、吞吐量）。
2. **Scalable Point-to-Point Synchronization**：通过 token-level 的本地同步（而非全局 barrier）实现并行仿真，消除全局同步瓶颈。
3. **Slack-Aware Parallelism**：利用仿真系统中的 FIFO 缓冲（slack）增加仿真并行度——当一个 process 的输入 FIFO 有足够 tokens 时，可以在不等待全局同步的情况下提前执行。

从硬件架构角度拆解术语：

DAM 框架的层次结构：
```
DAM Framework
  ├─ Process Trait: 定义仿真模块接口
  │   fn functional(&self, inputs: &[Token]) → Vec<Token>
  │   fn timing(&self) → Cycles
  │   fn pipeline_depth(&self) → u32
  ├─ Channel: Process 间的 token 通道 (FIFO)
  │   capacity, current_occupancy, back_pressure_threshold
  ├─ Scheduler: Point-to-point synchronization
  │   当 process 的 input channel 有 token 时调度执行
  │   利用 slack (FIFO 剩余空间) 提前执行
  └─ Instrumentation: cycle_count, token_count, flops_counter
```

性能数据（ISCA 2024）：
- 比现有仿真框架快 2-15×
- 比 ad-hoc 研究模拟器快 5 个数量级
- 用 57% 更少的代码重新实现稀疏张量代数加速器模拟器

术语一般如何实现？如何使用？

DAM 是 Rust library，通过 `cargo` 管理依赖。用户实现 `Process` trait（定义功能+时序行为），用 `Channel` 连接 processes，调度器自动处理同步。Comal 模拟器是 DAM framework 的一个应用实例——每个 SAMML node 实现为一个 DAM process，node 间的 streaming edges 实现为 DAM channels。

涉及论文标题：
- FuseFlow

## Tensor Memory (TMEM)

术语是什么？

Tensor Memory (TMEM) 是 NVIDIA Blackwell GPU 架构（B200/GB200）引入的新型 on-chip 存储器，位于每个 SM 内部，容量 256KB，专门用于存储 tensor core MMA（矩阵乘累加）操作的中间结果（accumulator）。TMEM 是 warp-synchronous 的存储器（与 SMEM 的 CTA 级共享不同），与 tensor core 紧密耦合——MMA 指令的输出直接写入 TMEM，无需占用寄存器（register file）。这解决了 Hopper 架构上 accumulator 占用大量寄存器导致极端寄存器压力的痛点。TMEM 以 32 列（16KB）为粒度进行分配、释放和数据移动，需程序员显式管理。在 FlashAttention-4 中，TMEM 是前向 ping-pong 流水线和后向 5-MMA 重排的关键推动者。

从硬件架构角度拆解术语：

```
TMEM 在 GPU 内存层次中的位置:

Global Memory (HBM/GMEM)  ← 最大容量 (180GB), 最低带宽
  ↕ L2 Cache              ← on-chip, 所有 SM 共享
    ↕ Shared Memory (SMEM) ← per-SM, CTA-scope, 程序员管理
      ↕ TMEM              ← per-SM, warp-sync, tensor-core-coupled [Blackwell 新增]
        ↕ Register File   ← per-thread, 最快, 256 registers/thread

TMEM vs SMEM vs Register:
| 属性          | TMEM                    | SMEM                 | Register File     |
|--------------|-------------------------|----------------------|-------------------|
| 容量/SM       | 256 KB                  | 最大 ~228 KB         | 256×32-bit/thread |
| Scope        | Warp-synchronous        | CTA (thread block)   | Per-thread        |
| 访问延迟      | ~tensor core output      | ~20-30 cycles        | ~0 (immediate)    |
| 主要用途      | MMA accumulator 存储     | 通用数据共享/缓存     | 线程私有变量       |
| 管理方式      | 显式 alloc/dealloc (16KB granule) | 显式 (动态/静态) | 编译器分配         |
| MMA 集成      | 直接写入 (异步)          | 需显式 load/store     | Hopper MMA 目标   |

TMEM 在 FA4 Forward 中的使用:
  FA4 tile 配置: M=N=d=128 (BF16)
  
  TMEM 分配方案:
    2× Output accumulator: 128×128×2 bytes × 2 tiles = 64 KB
    剩余: 256 - 64 = 192 KB
    
    192 KB 可用于 S (M×N=128×128×2 bytes=32 KB per tile) 和 P (同尺寸)
    → FA4 选择: 两个 S tile (64 KB) + 重叠 P (复用 S 的 TMEM 空间)
    → 允许立即计算两个 S tile 启动流水线
    
    部分 TMEM 用于 correction warpgroup 传递 rescale statistics
```

TMEM 的关键硬件特性：
- **异步 MMA 写入**：Blackwell MMA 输出直接异步写入 TMEM，不阻塞 CUDA core（Hopper MMA 写入寄存器，阻塞直到写完成）
- **Warp-synchronous scope**：TMEM 的数据一致性在 warp 级别保证，跨 warp 访问需要显式同步
- **Granular allocation**：TMEM 以 32 列（16KB）为最小分配单元，程序员需显式 alloc/dealloc
- **与 2-CTA 的交互**：2-CTA MMA 模式下，两个 CTA 的 TMEM 可跨 CTA 访问（通过 hardware 合并 accumulator）

术语一般如何实现？如何使用？

- **CUDA 编程**：通过 PTX 指令或 CuTe/CUTLASS 抽象管理 TMEM 分配和数据移动。Blackwell 新增了 `tcgen05` 系列 PTX 指令直接操作 TMEM
- **CuTe-DSL 中的使用**：FA4 的 CuTe-DSL 实现通过高层抽象管理 TMEM lifetime：分配 MMA accumulator → MMA 写入 → softmax 读取 P → correction warpgroup 读取 rescale statistics → dealloc
- **对 kernel 设计的改变**：TMEM 解耦了 accumulator 存储和 register file，使大的 MMA tile (128×128) 成为可能（无需 4× interleaved thread-per-row）；使后向 5-MMA 重排成为可能（4 个 accumulator tile + 1 个共享 tile 可同时驻留 TMEM）
- **限制**：(1) 256KB/SM 容量有限——FA4 后向的 5 个 accumulator tile（5×128×128×2 = 160KB）配合 S/P 共享可容纳，但更复杂的 kernel 可能不够；(2) TMEM-SMEM 数据移动需显式 copy 指令

涉及论文标题：
- FlashAttention-4

## Blackwell Tensor Cores (5th-Generation)

术语是什么？

Blackwell Tensor Cores 是 NVIDIA Blackwell GPU 架构（B200/GB200）中第五代 tensor core，专门用于加速矩阵乘累加（MMA）操作。相比 Hopper（第四代），Blackwell tensor core 的关键变化包括：(1) MMA tile size 从 64×N 扩展到 128×N（典型 N=128 或 256），tile 面积翻倍；(2) BF16/FP16 吞吐从 4096 ops/clock/SM 翻倍至 8192 ops/clock/SM（对应 2.25 PFLOPS/GPU vs Hopper 1 PFLOPS）；(3) MMA 输出直接写入 TMEM 而非寄存器，且为完全异步操作（Hopper MMA 写入寄存器时阻塞）；(4) 支持 2-CTA 协作 MMA 模式（CTA pair 共享 B 操作数）；(5) 新增 FP4/FP6 数据类型支持。

从硬件架构角度拆解术语：

```
Blackwell vs Hopper Tensor Core 对比:

| 属性                | Hopper (H100, 4th-gen)     | Blackwell (B200, 5th-gen)      |
|--------------------|---------------------------|--------------------------------|
| MMA tile (M×N×K)   | 64×128×16 (or smaller)    | 128×128×16 (or 128×256×16)    |
| BF16 TFLOPS/GPU    | 1 PFLOPS (989.5 actual)   | 2.25 PFLOPS                    |
| BF16 ops/clock/SM  | 4096                      | 8192                            |
| Accumulator 存储    | 寄存器 (register file)     | TMEM (tensor memory)            |
| MMA 异步性          | 部分异步 (TMA 异步, MMA 同步) | 完全异步 (MMA 输出到 TMEM 不阻塞) |
| 多 CTA MMA         | 不支持                     | 2-CTA MMA mode                 |
| FP8 支持            | 是 (E4M3/E5M2)            | 是                              |
| FP4/FP6 支持        | 否                        | 是                              |

Blackwell Tensor Core 的 MMA 指令执行流程:

  1. 操作数加载:
     A[M,K] 来自 SMEM 或 TMEM (MMA 操作数)
     B[K,N] 来自 SMEM (MMA 操作数)
     
  2. MMA 执行:
     128×128 乘加 tile: C[i,j] += Σ_k A[i,k] × B[k,j]
     内部以 warp-level matrix fragment 分布到 128 threads
     
  3. Accumulator 输出:
     异步写入 TMEM (不阻塞 CUDA core)
     TMEM address 由程序员指定
     写入完成后通过 sync 原语确认

  4. 2-CTA 变体:
     A: 沿 M 分片 (CTA_0: rows 0-127, CTA_1: rows 128-255)
     B: 沿 N 分片 (各自加载一半 B 操作数)
     硬件合并 B tile 的完整视图进行乘法
     Accumulator: 沿 M 分片, 各自写入自己的 TMEM
```

非对称硬件扩展对 kernel 设计的冲击：

Blackwell 的 tensor core 翻倍 + MUFU/SMEM 不变 创造了新的瓶颈分布：

| 资源             | Hopper (H100)    | Blackwell (B200)  | 变化   |
|-----------------|------------------|-------------------|--------|
| Tensor Core     | 4096 ops/ck/SM   | 8192 ops/ck/SM    | **2×** |
| MUFU (exp)      | 16 ops/ck/SM     | 16 ops/ck/SM      | 1×     |
| SMEM bandwidth  | 128 B/ck/SM      | 128 B/ck/SM       | 1×     |
| Register/SM     | 65536 (256KB)    | 65536 (256KB)     | 1×     |
| TMEM            | N/A              | 256 KB/SM         | 新增   |

→ 瓶颈从 MMA 计算 转移到 non-MMA 操作（指数、SMEM 流量）→ FA4 的设计动机

术语一般如何实现？如何使用？

- **编程接口**：通过 CUDA PTX `tcgen05` 指令或 CuTe/CUTLASS 高层抽象使用。CuTe-DSL 提供 `mma` 原语封装 MMA 指令
- **数据精度**：BF16/FP16（accumulator 可为 FP32）、FP8（E4M3/E5M2）、FP4/FP6（Blackwell 新增）
- **tile 选择**：M=128 或 256（2-CTA），N=128 或 256，K=16（BF16）或 32（FP8）。tile 尺寸直接影响 SMEM 流量、TMEM 占用和寄存器使用
- **异步编程模式**：Blackwell 的完全异步 MMA 允许 producer warps 持续 issue MMA 指令而不等待完成，consumer warps 通过 TMEM ready 信号同步——这与 Hopper 的 "issue MMA → block until register writeback" 根本不同
- **在 FA4 中的体现**：所有 5 个技术支柱（软件指数模拟、条件 rescaling、乒乓流水线、2-CTA backward、LPT 调度）都直接回应 Blackwell tensor core 翻倍带来的非对称瓶颈

- FlashAttention-4

## NVIDIA B200 GPU (Blackwell Data Center GPU)

术语是什么？

NVIDIA B200 是 Blackwell 架构的数据中心 GPU，是 Hopper H100 的继任者。B200 代表了一次"非对称硬件扩展"：tensor core BF16 吞吐翻倍至 2.25 PFLOPS（8192 ops/clock/SM vs Hopper 4096），但 MUFU 指数单元（16 ops/clock/SM）、SMEM 带宽（128 bytes/clock/SM）和寄存器文件容量保持不变。同时引入了 TMEM（256KB/SM）、2-CTA MMA 模式、DSMEM 等新架构特性。FlashAttention-4 专门为 B200 上 attention 计算的瓶颈转移（从 MMA 计算转向指数吞吐和 SMEM 流量）而设计。

## Processing-in-Memory (PIM / 存内计算) 与 HBM-PIM

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Processing-in-Memory（PIM，存内计算/近存计算）是一种在 DRAM 芯片内部或紧邻 DRAM bank 放置轻量级处理单元（Processing Unit, PU）的架构技术，核心思想是将计算推到数据所在位置，利用 DRAM bank 内部极高带宽（可达外部接口带宽的 10× 以上）加速 memory-bound 操作。HBM-PIM 是将 PIM PU 集成到 HBM die 中的具体产品形态——三星 HBM-PIM（Aquabolt-XL, HBM3E-PIM）在标准 HBM die 的每个 bank 旁增加 PU（adder tree），牺牲约 50% 存储容量换取计算能力（compute density ≈ 1 op/byte）。每个 HBM-PIM stack 含 32 pseudo-channels（HBM3E），每 channel 含 24 banks，每 bank 有独立 PU。PIM 操作通过 DRAM 命令接口控制——GPU host 发出 PIM_GWRITE（broadcast 向量到所有 bank）和 PIM_GEMV（触发 bank 内 dot product）。Sieve 明确声明无需硬件修改：no new PIM commands, no changes to existing PIM architecture or command interface。

从硬件架构角度拆解术语，比如术语如何在硬件架构中发挥作用，给出术语在硬件架构中运转流程的具体例子。通过联网搜索让回答具体和精准。
PIM 在 multi-GPU + HBM-PIM 系统中的硬件架构和数据流：
```
每个 B200 GPU
  ├── 8 HBM-PIM stacks (96 GB, 50% capacity sacrificed for PU)
  │   └── 每个 stack: 32 pseudo-channels
  │       └── 每个 pseudo-channel: 24 banks, 每 bank PU (adder tree)
  └── NVLink (900 GB/s bidirectional) → 连接其他 GPU

PIM GEMV 流程:
1. GPU kernel 发 PIM_GWRITE: broadcast token vector 到所有 channel 的 global buffer
2. GPU kernel 发 PIM_GEMV: 各 bank PU 做 dot product (token[i] * weight[i,j] + acc)
3. 结果经 DRAM I/O 回传 GPU on-chip memory
```

硬件约束：(1) 每个 channel 内所有 PU 共享同一 vector operand（broadcast），因此 expert parallelism 跨 banks 会导致不均衡；(2) commercial PIM 不支持跨 channel/bank 直接数据传输；(3) DRAM 时序开销（tRCD/tRP/tRFC/bank contention/row buffer conflict）使 GEMV 时间非线性——2-token GEMV ≠ 2× 1-token GEMV 时间。Sieve 论文量化：roofline 估计可能高估 PIM 上 GEMV 性能 1.8–4.2×。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **产品实现**：三星 HBM-PIM (Aquabolt-XL, HBM3E-PIM) 是唯一 commercialized PIM 产品；SK hynix GDDR6-AiM 为另一产品线。学术界使用 Ramulator 2.0 做 cycle-accurate PIM 仿真（DRAM 时序+状态机+PIM 命令调度）。
- **LLM serving 使用**：(1) attention decode offload——GEMV 操作（QK^T, PV）offload 到 PIM，~2× speedup；(2) MoE expert offload——unpopular expert GEMV 计算到 PIM（Sieve）；(3) KV cache 存储+就地计算——避免 KV 传输开销。
- **性能特征**：PIM 内部带宽 ~8 TB/s per stack（远高于 HBM-GPU 外部接口），但 PU 计算能力有限（~1 TFLOPS per stack），ridge point ~10-20 FLOPs/byte，仅适合 memory-bound 操作。
- **编程模型**：GPU kernel 发 PIM 命令（内存映射 I/O 模式），参数（矩阵地址、尺寸、结果地址）运行时计算。接口规范遵循 NeuPIMs 的 PIM_GWRITE/PIM_GEMV。

## Spatial Dataflow Accelerator (SDA / 空间数据流加速器)

术语是什么？

Spatial Dataflow Accelerator (SDA) 是 Reconfigurable Dataflow Architecture (RDA) 的同义术语，指代一类**由空间分布的可重构计算单元和存储单元组成的可编程架构**，这些单元通过硬件 FIFO 和片上网络 (NoC) 进行通信。SDA 不执行冯·诺依曼模型中顺序的指令流，而是将程序表示为数据流图（dataflow graph），其中节点表示操作，边表示显式的数据依赖。数据流程序图中的节点被映射到分布式的计算和存储单元，边被映射到硬件 FIFO 和 NoC 上。

SDA 的存储组织为多个层级（tier），如本地 PE 存储、片上存储单元和片外存储。大多数 SDA 依赖编译器或运行时来显式编排和调度数据在不同存储层级之间的移动。

SDA 的关键架构特征使其能够避免通用处理器和 GPU 的指令解码、缓存层次和控制流分支开销。其数据流执行模型进一步支持激进的算子融合（operator fusion）、流水线（pipelining）和细粒度并行（fine-grained parallelism），从而减少片外内存流量和同步开销。例如，在 Llama-3.1-8B 和 70B 上，GPU 仅利用了不到一半的峰值 HBM 带宽，而 SN40L（一款商用 SDA）在 token 生成阶段实现了更高比例的峰值 HBM 带宽利用率，在仅一半峰值带宽下达到 2× 加速，在可比带宽下达到 3.7× 加速。

从硬件架构角度拆解术语：

SDA 的典型硬件组织结构：
```
SDA Hardware Fabric:
  ┌─────────────────────────────────────────────────┐
  │ Compute Array (e.g., 16×16 BFloat16 tiles/unit) │
  │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐       │
  │  │ PE0  │→│ PE1  │→│ PE2  │→│ PE3  │→ ...   │
  │  │(Map) │  │(Map) │  │(Accum)│ │(Scan) │       │
  │  └──────┘  └──────┘  └──────┘  └──────┘       │
  │    ↕ Hardware FIFOs (ready-valid handshake)     │
  │  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐       │
  │  │ MEM0 │  │ MEM1 │  │ MEM2 │  │ MEM3 │       │
  │  │(Buf) │  │(Buf) │  │(Buf) │  │(Buf) │       │
  │  └──────┘  └──────┘  └──────┘  └──────┘       │
  │    ↕ Network-on-Chip (NoC)                       │
  ├─────────────────────────────────────────────────┤
  │ On-Chip Scratchpad Memory (software-managed)     │
  │  └→ e.g., 512KB local memory per unit (SN40L)   │
  ├─────────────────────────────────────────────────┤
  │ Off-Chip HBM (e.g., HBM2 8 stacks)              │
  └─────────────────────────────────────────────────┘
```

SDA 执行动态 tensor workload 时的关键硬件机制（STeP Section 6.2 讨论）：
1. **Stop Token 处理**：Datapath 中使用少量 bit 标识 stop token 及其级别。先前 SDA 已通过复用现有硬件单元 [Revet, HPCA 2024] 或设计新的专用状态机 [Onyx, VLSI 2024] 来处理 stop-token 嵌入的数据流。
2. **Control Flow 实现**：SDA 在空间上布局所有 branch，在运行时根据数据动态激活适当的分支。路由可以通过计算单元中的预测（predication）[SARA, ISCA 2021] 或片上网络互联中的路由 [RipTide, MICRO 2022] 来实现。
3. **动态 Tensor Size 支持**：内存系统必须支持虚拟化——以独立于 stream 长度的固定粒度分配空间，并维护 stream 引用与其内存地址之间的映射。非连续分配（noncontiguous allocation）避免碎片化。可通过硬件管理的映射缓存（如链表）实现，在 512KB 本地内存下映射缓存开销 < 30KB（约 6%），与传统缓存中的 tag 开销相当。任意无上界的 tensor size 可通过 spill 机制支持 [Ripple, PLDI 2025]。

术语一般如何实现？如何使用？

商用和学术 SDA 实现包括：
- **SambaNova SN40L RDU [Prabhakar, Hot Chips 2024]**：商用可重构数据流加速器，用于 Gen AI 计算。在 Llama-3.1 推理中相比 GPU 实现 2-3.7× 加速和 3.8-4.6× 能效提升。
- **Plasticine [Prabhakar et al., ISCA 2017]**：早期 SDA 设计，支持 parallel patterns 到数据流硬件的编译。由 Pattern Compute Units (PCU) 和 Pattern Memory Units (PMU) 组成。
- **Onyx [Koul et al., VLSI 2024]**：12nm CGRA，384 PE tiles + 128 Memory tiles，756 GOPS/W。首个支持通用稀疏和稠密张量代数的可编程 CGRA。
- **RipTide [Gobieski et al., MICRO 2022]**：可编程、高能效的数据流编译器和架构，支持 coarse-grained reconfigurable array。
- **Aurochs [Vilim et al., ISCA 2021]**：面向 dataflow threads 的架构。
- **Gorgon [Vilim et al., ISCA 2020]**：面向关系数据 ML 加速的数据流架构。

STeP 作为 SDA 的编程抽象，其 symbolic frontend 和 simulator 可适配不同 SDA 硬件特性：frontend 中的方程可自定义以捕获 hardware-specific operator details（如 hardware tile sizes, matmul implementation），simulator 中 operator initiation intervals 和 latencies 可调整以匹配硬件特征。

## Stop Tokens (停止令牌 / 流终止信号)

术语是什么？

Stop Tokens 是异步数据流抽象中嵌入数据流的一种**特殊控制信号**，用于标注流中逻辑张量各维度的结束边界。Stop Token 机制最初由 SAM (Sparse Abstract Machine) [Hsu et al., ASPLOS 2023] 提出，专门为异步数据流抽象设计，支持维度是动态的（即在编译时未知）。STeP 沿用了 SAM 的 stop token 设计。

具体机制：
- 每个 stop token 表示为 $S_N (N \ge 1)$，其中 N 表示该维度的秩（如 N=1 表示一个向量的结束）。
- 在多个维度同时结束时，STeP 仅发射最高级别的 stop token。
- **Done token (D)** 在流的末尾发出，表示流的终止。
- 例如，流 `(1, 2, S_1, 3, S_2, 4, S_1, 5, 6, 7, S_2, D)` 的逻辑张量形状为 `[2, 2, D_0]`（最内维是 ragged）。

Stop tokens 使得 STeP 流在逻辑上等价于零个或多个张量——流的 rank 由对应张量的维数确定，每个维度的形状可以是 static-regular、dynamic-regular 或 ragged。

从硬件架构角度拆解术语：

Stop Token 在 SDA 硬件中的处理流程：
```
Data Stream on Hardware Interconnect:
  ┌──────┬──────────┬──────────┐
  │ data │ stop_bit │ stop_lvl │  (附加在 datapath 上的控制位)
  └──────┴──────────┴──────────┘
  
Stream: [W, X, S1, Y, Z, S2, D]
          ↓
  Hardware State Machine:
    State IDLE:
      on data → accumulate to buffer, State=ACCUM
    State ACCUM:
      on S1 → flush buffer as 1-D vector, State=WAIT_S2
      on S2 → flush buffer, emit Done, State=IDLE
      on D  → terminate stream
    State WAIT_S2:
      on S2 → flush buffer, State=IDLE
      on D  → terminate stream (premature end)

Bufferize Operator 使用 Stop Tokens 确定何时分配新的 on-chip buffer:
  Bufferize(rank=b):
    while stream not Done:
      accumulate tiles until stop token >= S_b
      enqueue buffer reference to output stream
      allocate new on-chip memory region
```

Stop tokens 的硬件实现方式（论文 Section 6.2）：
1. **Revet [Rucker et al., HPCA 2024]**：复用现有硬件单元处理 stop tokens。
2. **Onyx [Koul et al., VLSI 2024]**：设计新的专用状态机处理 stop tokens。
3. 两种方式均在 datapath 中使用少量 bit 标识 stop token 及其级别。

术语一般如何实现？如何使用？

Stop tokens 是异步数据流抽象的核心机制，用于支持动态维度的流处理：
- **Bufferize 算子**：根据 stop token 级别确定何时将累积的数据作为一个 buffer 输出。例如 Bufferize(rank=2) 在遇到 $S_2$ 或更高级别的 stop token 时将累积的 tile 打包为 buffer。
- **Accum 算子**：利用 stop tokens 确定归约边界——在遇到对应级别的 stop token 时完成当前归约并输出结果。
- **Shape Operators**（Flatten, Reshape 等）：仅修改 stop tokens 而不改变数据内容，从而改变流的逻辑张量结构。

STeP 的 stop tokens 与 SAM 的设计保持一致（均为异步数据流设计），但 STeP 在以下方面做了扩展：支持更多种类的维度类型（static-regular, dynamic-regular, ragged），并在 shape semantics 中引入了 ragged dimension 的 absorbing property（包含 ragged dimension 的 shape equation 产生新的 ragged dimension）。

涉及论文标题：
- Streaming Tensor Programs (STeP)
