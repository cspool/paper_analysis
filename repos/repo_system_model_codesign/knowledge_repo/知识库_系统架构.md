## Paged KV Cache (分页键值缓存)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Paged KV Cache（分页键值缓存）是 vLLM 系统（OSDI 2024）提出的 KV cache 内存管理机制。受操作系统虚拟内存的页表启发，它将 LLM 的 KV cache 划分为固定大小的 page（如 16 或 32 个 token 为一页），通过页表将逻辑 token 位置映射到物理 GPU 内存中的 page。这解决了传统 contiguous KV cache 的三个核心问题：(1) 内存碎片——由于每个请求的序列长度不同且动态增长，预分配连续内存导致大量内部和外部碎片；(2) 无法共享——不同请求可能有共同的 prompt prefix（如 system prompt），contiguous 分配无法按 prefix 共享 KV cache；(3) 动态扩展困难——当序列超出预分配空间时需要整体搬迁。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。
Paged KV Cache 在 LLM serving 系统中的运转流程：
```
请求到达 → Scheduler 分配逻辑 token 槽位

prefill 阶段:
  每个新 token → 分配到 page 中的下一个空闲 slot
  若当前 page 已满 → 分配新 page，更新页表
  KV 值写入物理 page 对应位置

decode 阶段:
  生成新 token → 追加到最后一个 page（或新 page）
  Attention kernel 通过页表 gather 所需 token 的 KV:
    for each query position:
      for each required context token (logical_idx):
        page_id = logical_idx // page_size
        offset  = logical_idx % page_size
        phys_addr = page_table[page_id].base + offset * kv_entry_size
        K, V = load(phys_addr)

Prefix 共享:
  请求 B 与请求 A 共享 prompt prefix
  → 页表中共享 prefix 部分的 page 指向同一物理 page
  → 引用计数管理，最后一个引用释放物理 page
```

在 "Inference Time Context Sparsity" 论文中，稀疏 decode kernel 正是构建在 FlashInfer 的 paged KV-cache 后端之上。稀疏索引选出的是逻辑 token 位置，kernel 通过页表将其转换为物理地址后才 gather K/V 值。page size 设为 16。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
主流实现：(1) vLLM 的 PagedAttention——最早的 paged KV cache 实现，使用虚拟内存风格管理，支持 prefix sharing 和 memory swapping；(2) FlashInfer 的 paged KV-cache 后端——提供高效的 page table 查询和 gather/scatter kernel，是 "Inference Time Context Sparsity" 论文中稀疏 decode kernel 的底层依赖。典型 page size 为 16 或 32 token。page size 越小 → 内存利用率越高但页表查找开销越大；page size 越大 → 反之。

涉及论文标题：
- Inference Time Context Sparsity
- Using Span Queries to Optimize Cache and Attention Locality

**Span Query 中的 Paged KV Cache 扩展**：Span Query 论文在 vLLM PagedAttention 基础上引入两个关键修改：(1) **RoPE on read**——将 RoPE 从 KV cache 写入时移到读取时，使同一物理 page 可被不同 span context 以不同 position offset 复用；(2) **Prefix hash chaining selective disable**——在 span 边界 block（以特殊 token `(` 开头）暂停 hash accumulation，以 `)n`（子表达式结束 + 位置指针）开头的 block 恢复 accumulation。这使得 prefix caching 从"token 级 exact match"升级为"span 级 commutative reuse"——同一组 document pages 即使在不同 query 上下文中也可被复用，因为它们的 hash 不再依赖前序 token 的位置。

## Span Query（生成式 AI 的树状查询接口 / 推理服务 API 泛化）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Span Query 是 IBM Research 提出的一种泛化 LLM inference API 接口——将 Chat Completion API 的线性 token 序列泛化为带 commutativity constraints 的 expression tree。核心思想类比 SQL query planner：SQL 利用 join commutativity 重排执行计划以最小化 I/O，Span Query 利用 token segment 的 commutativity 重排 KV cache 布局以最大化复用。Span Query 引入 `++`（commutative join）操作符：`++(A, B)` 表示 A 和 B 可任意顺序排列。Chat input 不 commute（消息顺序有语义），但 RAG documents、multi-agent generator outputs、system prompt 与 user prompt 等在很多场景下 commute。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。
Span Query 在 serving 系统中的全流程（以 RAG 场景为例）：
```
Client Side:
  构造 Expression Tree: R(query, ++(doc1, doc2, ..., docN))
  含义: query 与每个 doc 配对，docs 之间相互独立（commute）
  → 发送 Span Query（expression tree）给 vLLM server

Server Side (vLLM + Span Query extension, 492 行修改):
  1. Parser/Planner: 解析 expression tree
     → 识别 commutative sub-trees（++ 节点）
     → 识别 sequential sub-trees（依赖关系）
  
  2. High-level Optimizer (固定点树重写):
     Rule 1: Desugar Chat    C→G+⨝         (chat→generator+join)
     Rule 2: Desugar RAG     R→++F         (RAG→concat+fold)
     Rule 3: Simplification  ++(++(a,b),c)→++(a,b,c)
     Rule 4: Plus Distribution G+⨝(r1,r2)→⨝(G+r1, G+r2)
  
  3. Query Tokenization:
     expression tree → 带特殊 token 的线性序列:
     <bos> doc1_tokens <sibling_sep> doc2_tokens ... <subtree_end>n
     特殊 token:
       □   padding (对齐 block 边界)
       (   subtree start (暂停 hash chaining)
       )(  sibling boundary
       )n  subtree end + position pointer (n 指向子树起始位置，恢复 hash chaining)
  
  4. KV Cache 写入:
     - RoPE 不在写入时施加（与传统 vLLM 不同）
     - ( 开头 block: 暂停 prefix hash accumulation
     - )n 开头 block: 恢复 prefix hash accumulation
     - 同一物理 page 可属于多个 span 的 virtual mapping

  5. Attention 计算:
     - token 仅 attend 同 span 内的 token（sparser attention）
     - RoPE 在 attention 计算时动态注入（RoPE on read）
     - 通过 Span Table 查询 position offset

  6. KV Cache 复用（第二次请求，不同 query 相同 docs）:
     - doc pages 的 hash 不依赖 query（hash chaining 在 span 边界暂停）
     → doc pages 100% 复用（vs baseline 因 query 不同导致 prefix mismatch）
     - CIDRA 处理并发 block repositioning（多请求将同一 page 移到不同 virtual position）
```

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
实现：SPNL library（https://github.com/IBM/spnl），Rust 编写（93.8%），提供 Rust crate（crates.io）、Python package（PyPI）、CLI 工具（Homebrew/Docker）。vLLM 端仅 492 行修改（7 个文件：block_pool.py 68 行、kv_cache_manager.py 89 行、kv_cache_utils.py 73 行、output.py 4 行、scheduler.py 19 行、single_type_kv_cache_manager.py 4 行、gpu_model_runner.py 232 行）。核心修改仅为：(a) RoPE 从 write-time 移到 read-time；(b) prefix scan hash chaining 在 span 边界选择性暂停/恢复。使用方式：Client 用 SPNL library 构造 span query → 发送到 vLLM server（支持 span query 的修改版）→ server 自动优化执行。效果：RAG 场景 TTFT 加速 10-20×，Judge-Generator (fan-out 24) TTFT 加速 12-13×，attention-optimized span query on 2B model 在 needle-in-haystack accuracy 上超过 stock 8B model。

涉及论文标题：
- Using Span Queries to Optimize Cache and Attention Locality

## Span Table（Span 页表：物理 Page 到虚拟 Span 位置的映射）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Span Table 是 Span Query 系统中管理物理 KV cache pages 与虚拟 span positions 之间映射的数据结构。类似于操作系统页表将虚拟地址映射到物理页框，Span Table 将"某个 span 中的第 k 个 token 位置"映射到"物理 GPU 内存中的 page P"。由于同一物理 page 可被不同 span 以不同 offset 引用（commutativity 使 page 与位置解耦），Span Table 支持多对多映射（一个 physical page → 多个 virtual positions，不同 spans 中）。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。
Span Table 在 serving 流程中的作用：
```
请求: R(query, ++(doc1, doc2))  // 两个 doc commute

Physical KV Cache pages (已分配):
  Page_P1: [system_msg tokens...]     (hash=H1)
  Page_P2: [system_msg tokens cont.]  (hash=H2, chain=H1+H2_content)
  Page_P3: [doc1 tokens...]           (hash=H3_standalone, span 边界暂停 chaining)
  Page_P4: [doc1 tokens cont.]        (hash=H4, chain=H3+H4_content)
  Page_P5: [doc2 tokens...]           (hash=H5_standalone, span 边界暂停 chaining)
  Page_P6: [query tokens...]          (hash=H6, chain=H6_content)

Span Table (per request):
  Virtual Seq Position  | Physical Page | Intra-page offset
  ----------------------|---------------|-------------------
  [0, 16)               | Page_P1       | 0
  [16, 32)              | Page_P2       | 0
  [32, 48)              | Page_P3       | 0    ← doc1 span
  [48, 64)              | Page_P4       | 0
  [64, 80)              | Page_P5       | 0    ← doc2 span (可与 doc1 互换)
  [80, 96)              | Page_P6       | 0    ← query span

第二次请求: R(query2, ++(doc1, doc2))  // 不同 query，相同 docs
  → Span Table 中 doc1/doc2 指向同一物理 Page (P3,P4,P5)
  → 仅需新分配 query 的 pages
  → KV cache 复用率: doc pages 100%
```

Span Table 与 vLLM 原生 page table 的关键区别：vLLM page table 是 1:1 映射（每个 logical position → 一个 physical page），Span Table 支持多对多映射（同一 physical page 可出现在多个 span context 的不同 virtual position）。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
Span Table 在 vLLM block_pool.py（修改 68 行）和 kv_cache_manager.py（修改 89 行）中实现。其与 CIDRA 算法协同：当多个并发请求将同一 physical page 映射到不同 virtual position 时，CIDRA 处理 in-place repositioning（page 无需复制，仅更新 Span Table 映射）或 duplicate（出度 >1 时复制 page）。Span Table 通过 `)n` token 中的 n（指向子表达式序列化起始位置）快速定位 span 边界，避免维护解析栈。

涉及论文标题：
- Using Span Queries to Optimize Cache and Attention Locality

## FlashInfer

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
FlashInfer 是一个高性能 LLM 推理 kernel 库（flashinfer.ai），由 UC Berkeley 等机构开发。它提供一系列针对 GPU 优化的 attention 计算 kernel，包括：prefill attention（处理批量 prompt 输入）、decode attention（单 token 生成时的 KV cache 访问）、append attention（增量式 KV cache 更新）。FlashInfer 的核心设计特点是支持 paged KV cache 后端、NHD（num_heads, head_dim）layout、GQA/MQA 等现代 attention 变体，以及高效的页表查询和 gather/scatter 操作。在 "Inference Time Context Sparsity" 论文中，FlashInfer 既作为性能 baseline（dense decode kernel），也作为稀疏 decode kernel 的底层实现基础。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。
FlashInfer 在 LLM serving 系统中的位置和调用流程：
```
vLLM / SGLang / 自建 Serving 系统
  │
  ├── Scheduler: 管理请求队列、batching、prefix sharing
  │
  ├── Model Runner: 执行模型 forward pass
  │      │
  │      ├── FlashInfer Prefill Kernel: 对批量 prompt 做 attention
  │      │   输入: Q(K,V) tensors, paged KV cache (写入模式)
  │      │   输出: attention output, 更新后的 paged KV cache
  │      │
  │      ├── FlashInfer Decode Kernel (dense): 单 token 生成
  │      │   输入: Q vector, paged KV cache (只读模式)
  │      │   输出: attention output
  │      │   过程: 通过页表 gather 所有历史 token 的 K,V → 计算 softmax(QK^T/√d)V
  │      │
  │      └── Sparse Decode Kernel (本文): 替代 dense decode
  │          输入: Q vector, 稀疏索引, paged KV cache
  │          过程: 仅 gather 索引选中的 token 的 K,V → 计算 attention
  │
  └── GPU (H100/B200 等): HBM 带宽 ~3.35 TB/s (H100)
```
FlashInfer 的性能基准（Table 1 baseline）：H100 上 128K context、GQA Hq=32/Hkv=8/D=128/page_size=16，单 batch decode 延迟 0.19ms，batch=16 时 3.08ms。这些延迟几乎完全受 HBM 带宽限制（memory-bandwidth bound），因为每次 decode 需读取完整 KV cache（128K × 8 × 128 × 2 bytes ≈ 256 MB per step）。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
FlashInfer 通过 PyPI 安装（`pip install flashinfer`），与 PyTorch 深度集成。其核心 kernel 使用 CUDA/Triton 实现，针对不同 GPU 架构（Ampere/Hopper/Blackwell）和不同 attention 变体（MHA/GQA/MQA）有专门的优化路径。在 "Inference Time Context Sparsity" 论文中：(1) FlashInfer 的 dense decode kernel 作为 baseline；(2) 论文的稀疏 decode kernel 通过复用 FlashInfer 的 paged KV-cache 后端和页表查询基础设施实现，仅替换了 attention 计算部分——从"读取全部 token"改为"根据稀疏索引 gather 部分 token"。开源地址：https://flashinfer.ai, https://github.com/flashinfer-ai/flashinfer。

涉及论文标题：
- Inference Time Context Sparsity
- MAC-Attention Match-Amend-Complete Attention for Efficient Long-Context Inference

**MAC-Attention 中的 FlashInfer 使用**：MAC-Attention 以 FlashInfer 作为主要性能 baseline。在 120K context 下，FlashInfer dense decode 延迟 234.2 μs/token，MAC-Attention 降至 62.9 μs/token（3.7× 加速）。MAC-Attention 的 fused persistent kernel 替代了 FlashInfer decode kernel path，但仍通过 FlashInfer 的 paged KV-cache 后端访问 KV 数据。

## SGLang Runtime Hook Integration (SGLang运行时Hook集成, Zero-Source-Modification Serving Plugin)

术语是什么？

SGLang Runtime Hook Integration 是 MAC-Attention 采用的一种零源码修改的 serving 框架集成方式。通过在 SGLang 的 Python runtime 中注入 hook 函数（monkey-patching 风格），在 decode 阶段拦截 attention 计算调用并替换为自定义 kernel，而无需修改 SGLang 的 C++/CUDA 源码或重新编译。这种集成方式的关键优势：SGLang 保持对模型执行、请求调度、paged KV 分配和 FlashInfer 后端的完整控制；MAC-Attention 仅替换 decode attention 的计算路径。当 MAC 禁用或请求超出支持配置时，自动回退到标准 SGLang/FlashInfer 路径。

从系统架构角度拆解术语：

```
SGLang + MAC-Attention Runtime Hook 集成架构:

SGLang Server (未经修改的官方版本)
│
├── HTTP API Layer: 接收请求, tokenize, detokenize
│
├── Scheduler: 请求队列管理, continuous batching, prefix caching
│
├── Model Runner: 执行模型 forward pass
│   │
│   ├── Prefill 阶段: 标准 SGLang + FlashInfer prefill kernel
│   │   └── MAC Hook: on_prefill_done()
│   │       保存 prefill 产生的 initial Q/A → ring cache 初始化
│   │
│   └── Decode 阶段: ← MAC Hook 在此生效
│       │
│       ├── Hook: on_before_decode_attention()
│       │   1. 保存 pre-RoPE Q_n
│       │   2. 检查 MAC 启用条件:
│       │      - MAC_ATTENTION_ENABLE=1
│       │      - n >= MAC_GEN_MIN_LIMIT (默认 2048)
│       │      - model dtype == BF16
│       │   3. 若启用:
│       │        launch mac_persistent_decode_bf16(Q_n, K_cache, V_cache,
│       │                   Q_ring, A_ring, write_ptr, τ=0.45, r=256)
│       │        return A_n (MAC attention output)
│       │   4. 若禁用: return None (走原 FlashInfer decode path)
│       │
│       └── Hook: on_after_decode_attention()
│           更新 ring cache (Q_ring, A_ring write)
│
└── GPU (H100): Tensor Core + HBM + L2 cache
```

**Hook 的实现位置**：`mac_attention.integrations.sglang` Python 模块，通过 Python 的运行时反射（`setattr`/`__call__` override）注入到 SGLang 的 ModelRunner 对象中。

术语一般如何实现？如何使用？

- **安装方式**：`pip install -e <MAC-Attention repo>` 将 hook 模块安装为可编辑包。SGLang 保持官方版本，无需 patch 或 fork。
- **启动方式**：通过 MAC-Attention 提供的包装脚本 `run_sglang_mac_server.sh` 启动，内部设置环境变量后调用 `mac_attention.integrations.sglang.launch_server`。
- **环境变量控制**：`MAC_ATTENTION_ENABLE`（全局开关，1=启用）、`MAC_THRESHOLD`（匹配阈值，默认 0.45）、`MAC_LOOKBACK_TOKENS_LEFT`（ring cache 窗口，默认 512）、`MAC_GEN_MIN_LIMIT`（最小 token 数才激活，默认 2048）、`MAC_DISABLE_CUDA_GRAPH`（CUDA graph 禁用，benchmark 配置）、`MAC_PERSISTENT_PARTIAL_FP32`（FP32 partial workspace）。
- **fallback 路径**：当 MAC 禁用、request 不在支持配置内、或 matching 未命中时，hook 返回 None → ModelRunner 执行原始 SGLang/FlashInfer decode 路径。
- **适用性**：这种 hook 模式理论上可推广到任何 Python-based serving 框架（vLLM、TGI 等），前提是框架暴露了 attention 计算的替换点。关键在于找到合适的注入点——足够底层以拦截实际计算，但又足够高层以避免与框架内部实现细节耦合。

涉及论文标题：
- MAC-Attention Match-Amend-Complete Attention for Efficient Long-Context Inference

## CUDA Graph for Multi-Precision Kernel Dispatch（CUDA Graph 多精度Kernel调度）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

CUDA Graph 是 NVIDIA CUDA 提供的 kernel launch 批处理机制：将一系列 kernel launch 和 memory copy 操作预录制为图（graph），后续用单次 `cudaGraphLaunch` 替代多次独立 kernel launch，消除 CPU→GPU launch overhead。MixLLM 利用 CUDA Graph 解决混合精度 GEMM 中 INT4 和 INT8 两路 kernel 的并行调度问题——将 INT4 path kernel（two-step dequant + MMA + I2F + scale）和 INT8 path kernel（直接 MMA + scale）录制为同一 graph 的并行节点，加上 fused epilogue scatter kernel，在一个 graph launch 中完成全部操作。

```
   │                   ▼                                  │
   │  ┌────────────────────────────────────┐             │
   │  │ Fused Epilogue Scatter             │             │
   │  │ (根据 P_map 合并两路输出到 C_final) │             │
   │  └────────────────────────────────────┘             │
   └────────────────────────────────────────────────────┘

3. 继续下一 Linear 层（下一个 CUDA Graph 节点）
```

**为什么需要 CUDA Graph**：混合精度 GEMM 将原本的单次 kernel launch 变为至少 3 次（INT4 kernel + INT8 kernel + scatter epilogue）。若无 CUDA Graph，3 次独立 CPU→GPU launch 的 overhead 在 small-batch decode 场景下会显著降低吞吐。CUDA Graph 将其压缩为 1 次 launch，且 INT4/INT8 路径在 graph 内并行执行。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。

- **Graph 捕获**：CUDA Graph 通过 `cudaStreamBeginCapture`/`cudaStreamEndCapture` 在运行时捕获一组 kernel launch 为 graph node。MixLLM 在模型加载时预录制所有 linear 层的 graph，推理时 `cudaGraphLaunch` 重放。
- **Graph 实例化**：`cudaGraphInstantiate` 将 graph 模板绑定到具体 GPU 和设备上下文，生成可执行 graph。MixLLM 对不同 batch size 和精度配置预实例化不同的 graph 实例。
- **Fused Epilogue Scatter 开销**："basically costless"——scatter 操作映射 INT4/INT8 输出到最终 output channel 位置，dense 矩阵写回，利用 L2 cache 的 write-combining 特性几乎不增加延迟。
- **与标准 vLLM CUDA Graph 的关系**：vLLM 已使用 CUDA Graph 优化 decode 阶段的 kernel launch overhead。MixLLM 在此基础上增加 mixed-precision dispatch 的 graph 节点，与 vLLM 现有 graph 框架兼容。
- **限制**：(1) 所有 graph input 须在录制时确定（包括 batch size、precision map），运行时不可动态变化——因此 MixLLM 对不同 batch size 和配置预录制多个 graph；(2) graph 内的 kernel 不能包含 CPU-GPU 同步点（如 `cudaDeviceSynchronize`）。

- MixLLM: LLM Quantization with Global Mixed-Precision between Output and Embeddings

## GPU Memory Fragmentation in Deep Learning Training（深度学习训练中的GPU内存碎片）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
GPU Memory Fragmentation 指深度学习训练中由于 tensor 的 allocation 和 deallocation 交替发生，空闲 GPU 内存被分割为多个不连续小片段，虽总空闲足够但无法满足一个大连续 allocation request 的现象。STAlloc 论文测量 PyTorch caching allocator 在 VPP + recomputation 配置下 fragmentation ratio 可达 43%（wasting 14.4 GB on A800-80GB）。Memory efficiency E = M_a / M_r（已分配大小 / 总预留大小），fragmentation ratio = 1 - E。碎片主要源于 online best-fit allocator 在不知道 tensor lifespan 的情况下做局部最优分配决策。

从系统架构角度拆解术语，给出训练中碎片形成的流程例子：
```
初始: [               free 100MB            ]
分配 A(30MB): [A:30MB][       free 70MB     ]
分配 B(20MB): [A:30MB][B:20MB][  free 50MB  ]
释放 A:      [free 30MB][B:20MB][  free 50MB ]
分配 C(40MB): → OK: [free 30MB][B:20MB][C:40MB][free 10MB]
释放 B:      [free 30MB][free 20MB][C:40MB][free 10MB]
分配 D(45MB): → 总 free = 60MB, 最大连续 = 30MB → OOM!
```
VPP 和 recomputation 加剧碎片：VPP 的 virtual stages 交错执行使 alloc/free 更加 interleaved；recomputation 产生大量 transient tensors（快速 alloc-free），留下微小空洞。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **测量**：`torch.cuda.max_memory_allocated()` / `torch.cuda.max_memory_reserved()`。
- **现有缓解方案**：PyTorch expandable_segments（virtual memory 动态扩段）、GMLake（virtual memory stitching）、STAlloc（offline planning 主动避免碎片）。

涉及论文标题：
- Reducing GPU Memory Fragmentation via Spatio-Temporal Allocation Planning (STAlloc)

## Virtual Pipeline Parallelism (VPP, 虚拟流水线并行)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Virtual Pipeline Parallelism (VPP) 是 Megatron-LM (Narayanan et al., SC 2021) 提出的流水线并行调度优化。将每个物理 pipeline stage 划分为多个 virtual stages（通常 2-4 个），在同一 GPU 上独立调度，使 microbatch 交错粒度更细，pipeline bubble 更小。代价：(1) activation memory 增长 ~v×（每个 virtual stage 独立维护状态）；(2) allocation 模式由 1F1B 的 LIFO 变为 virtual stages 间的 interleaved alloc/free，加剧碎片。STAlloc 论文显示 VPP 下 PyTorch 的 memory efficiency 从 1F1B 的 90% 降至 80%。

从系统架构角度拆解术语：
```
1F1B: GPU0: F0 F1 F2 F3 B0 B1 B2 B3  (warmup + steady state)
VPP (v=2): GPU0 同时有 virtual_stage_0 和 virtual_stage_1:
  F0_v0 F0_v1 F1_v0 B0_v0 F1_v1 F2_v0 B0_v1 F2_v1 ...
  更细粒度交错 → bubble 缩小，但 alloc/free 交错加剧
```
STAlloc 在 VPP 配置下仍保持 >99% memory efficiency，因为 spatio-temporal regularity 不被 VPP 破坏。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **实现**：Megatron-LM 中 `virtual_pipeline_model_parallel_size` 参数控制 virtual stage 数（通常 v=2）。
- **与 recomputation 组合**：VPP + recomputation 常用——VPP 提升吞吐，recomputation 降低内存，但两者叠加加剧碎片。STAlloc 可在此组合下释放足够内存使原 OOM 配置可运行。

涉及论文标题：
- Reducing GPU Memory Fragmentation via Spatio-Temporal Allocation Planning (STAlloc)

## CUDA Caching Allocator (PyTorch)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
CUDA Caching Allocator 是 PyTorch 的默认 GPU 内存分配器。核心设计：(1) Caching——通过 cudaMalloc 获取大块内存缓存在进程内，application 的 malloc/free 在缓存块内切分/回收，避免频繁 cudaMalloc/cudaFree（每次 ~10-20 μs）；(2) Best-Fit——在缓存块中选择大小最匹配的空闲 chunk；(3) Block Merging——free 时与相邻空闲块合并。在 `c10/cuda/CUDACachingAllocator.cpp` 中实现。STAlloc 论文测量其在 VPP + recomputation 下 fragmentation ratio 可达 43%。

从系统架构角度拆解术语：
```
PyTorch Caching Allocator 运作:
  malloc(s): 在 free_blocks 中 best-fit 查找 ≥ s 的 block → 切分 → return
             无可用 → cudaMalloc(max(s, 2MB)) 获取新块
  free(addr): 标记为 free → 与相邻 free blocks 合并
```
环境变量 `PYTORCH_CUDA_ALLOC_CONF` 可配置 `max_split_size_mb`、`expandable_segments:True`（CUDA virtual memory 动态扩段）。PyTorch 2.0+ 引入 `PluggableAllocator` 接口允许替换默认分配器（STAlloc 即通过此接口集成）。

- Reducing GPU Memory Fragmentation via Spatio-Temporal Allocation Planning (STAlloc)

## Sieve Scheduler (Sieve 调度器 / 动态专家分区调度)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。
Sieve Scheduler 是 Sieve 论文提出的运行时调度器，用于在配备 HBM-PIM 的多 GPU 系统上动态决定 MoE 模型中每个 expert 的计算位置（GPU 还是 PIM）。其核心目标函数为：

$$S^* = \arg\min_{S \subseteq E} \max \left( T_{\text{Comm}}, T_{\text{GPU}}(G), T_{\text{PIM}}(S) \right)$$

其中 E 是激活的 expert 集合，S 分配到 PIM，G=E−S 分配到 GPU。T_Comm 是 inter-GPU all-to-all 通信时间（expert parallelism dispatch/combine），T_GPU(G)=max(T_offchip, T_comp) 是 GPU 侧时间（off-chip 访存和 grouped GEMM 计算取瓶颈），T_PIM(S) 是 PIM 侧时间（attention + unpopular expert GEMV）。Sieve Scheduler 使用贪心算法求解——按 token count 降序排序 expert → 从全部 assign 到 PIM 开始 → 依次将最 popular expert 移到 GPU → 直到 max(T_Comm, T_GPU, T_PIM) 不再下降。Overhead 约 20 μs（B200 GPU 未做 kernel 优化），对 critical path 影响可忽略。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。
Sieve Scheduler 在 multi-GPU + HBM-PIM 系统架构中的运行时调度流程：
```
每个 decode iteration (per MoE layer):

# Step 1: Router (per GPU)
for each GPU g in parallel:
    routing_map_g = gating(hidden_states_g)  # [{token_id: [top-k experts]}]

# Step 2: AllGather → 全局 routing map
global_routing = all_gather(routing_map_g)

# Step 3: Sieve Scheduler (per GPU, 本地贪心)
for each GPU g in parallel:
    E_g = activated experts assigned to GPU g
    sorted_experts = sort_by_token_count_desc(E_g)
    S = E_g  # 初始: 全部在 PIM
    T_best = inf
    for expert e in sorted_experts:
        S_temp = S - {e}   # 尝试移到 GPU
        T_new = max(T_Comm, T_GPU(E_g - S_temp), T_PIM(S_temp))
        if T_new < T_best:
            S = S_temp; T_best = T_new
        else:
            break  # 贪心停止

# Step 4: 并行执行
GPU_execute(G = E_g - S) || PIM_execute(S) || inter_GPU_dispatch/combine
```

计时模型细节：(1) T_Comm 由 expert parallelism 配置和 gating 结果决定，与 S 无关；(2) T_GPU 中 T_comp 假设 grouped GEMM with variable group sizes；(3) T_PIM 使用运行时 cost table（实测 GEMV 时间 exponential moving average per token count），因 roofline 模型忽略 DRAM 时序开销（bank contention/row buffer conflicts/refresh），可能高估 PIM GEMV 时间 1.8–4.2×。

术语一般如何实现？如何使用？通过联网搜索让回答具体和精准。
- **核心创新 vs Prior Work**：PIMoE [51] 使用静态 threshold 分配 expert，忽略 (a) attention 在 PIM 上的时间开销 和 (b) inter-GPU 通信开销（假设 global interconnect）。Sieve 将 T_Comm + T_PIM(含 attention) + T_GPU 联合优化，适应 bimodal expert distribution 的动态变化。
- **为什么不用 expert-level static threshold**：PIMoE 的静态 threshold 在 attention 时间增长（长序列/大 batch）或通信成为瓶颈时失效——PIM 端实际成为 bottleneck 但 scheduler 不知。Sieve 的 max(T_Comm, T_GPU, T_PIM) 保证三维联合瓶颈最小化。
- **PIM cost table 机制**：key=token count, value=EMA of observed GEMV time。首次遇到某 token count 时 fallback 到 roofline 估计，之后用实测值。由于 bimodal distribution 在连续 batch 间覆盖所有常见 token counts，cost table 在首次 few iterations 内收敛。
- **PIM 侧 Tensor Parallelism**：Sieve 在 PIM 侧采用 tensor parallelism（expert 参数均匀 shard 到所有 32 PIM channels）而非 expert parallelism。确保即使 S 中仅 1 个 expert 且 N=1，所有 32 channels 也被 100% 利用（每个 channel 算 d_ff/32 的部分 dot product）。PIMoE 的 expert parallelism 在 bimodal distribution 下导致某些 channel 满载、某些空闲（Figure 10）。
- **与其他系统组件的关系**：Sieve Scheduler 是 Sieve System（Section 6, DAG 协调层）的决策核心——Scheduler 输出 S/G 分区后，Sieve System 构建 MoE layer 的 dependency graph，overlap GPU grouped GEMM、PIM GEMV、inter-GPU dispatch/combine 和 HBM↔GPU 数据传输。Scheduler 和 System 的关系类似"决策器+执行器"。

- Sieve
