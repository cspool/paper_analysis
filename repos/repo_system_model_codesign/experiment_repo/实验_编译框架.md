# 实验_编译框架

## FuseFlow

- 属于编译框架的实现是什么？实验比较什么？
  - **实现**：FuseFlow 是首个面向可重构数据流架构（RDA）的**端到端稀疏 ML 编译器**，将 PyTorch 稀疏模型编译为 SAMML 融合数据流图。核心编译创新包括：
    1. **交叉表达式核融合（EKF/Inter-Expression Kernel Fusion）**：通过融合 Einsum 表示和偏序图（Partial Order Graph, POG），自动跨多个独立的稀疏 Einsum 表达式进行融合。POG 追踪索引顺序约束（张量存储格式的 mode order + 用户调度的 dataflow order），当多个 view 产生冲突时通过物化 permuted copy 打破循环。支持 partial fusion 和 full fusion 两种粒度。
    2. **融合表 IR（Fusion Table IR）**：二维表格形式的 lowering IR，行编码融合迭代顺序（控制流），列编码张量视图（数据流），单元格为数据流原语或对其他单元格的引用指针。允许在最终代码生成前 defer graph materialization，支持 memoized intermediate streams 的前向引用。基于融合表生成的 SAMML 图采用 **factored iteration**（分解迭代）而非 global iteration，将迭代子图和计算 pipeline 交错排列。
    3. **调度语言**：通过 `Fuse{}` region 标记、Linalg affine maps 修改和命令行参数，暴露 fusion granularity、dataflow ordering、parallelization 和 performance heuristic 给用户显式控制。
    4. **编译优化**：parallelization（stream parallelizer/serializer 原语，支持 nested parallelism）、sparsity blocking（将 dense block 映射到最内层坐标，外层保持稀疏迭代）、dataflow ordering（枚举所有有效 order）、fusion heuristic（基于 tensor 维度、稀疏度、intersection rates 快速估计 FLOPs/bytes）。
    5. **编译路径**：PyTorch → Torch-MLIR/MPACT → MLIR Linalg + SparseTensor → Fused Einsum + POG → Fusion Table → SAMML dataflow graph → Comal simulator / FPGA (Vitis HLS)。
  - **实验比较**：
    - **Fusion 粒度**：unfused vs partially fused vs fully fused，在 4 类模型（SAE, GCN, GraphSAGE, GPT-3 w/ BigBird）上评估。
    - **与现有编译器对比**：FuseFlow vs Custard+Stardust (C+S)，在 GCN (OGB-Collab) 上比较。
    - **Sparsity 消融**：50%-95% 稀疏度 × 3 种图结构（uniform random, power-law, block diagonal）。
    - **Parallelization**：parallelization factor 1-64 sweep，nested parallelism 效果。
    - **Block Sparse**：block size 对 BigBird attention 性能的影响。
    - **Dataflow Ordering**：nested matmul 的不同 dataflow order 对性能的影响（best vs worst ~29× 差异）。

- 硬件平台是什么，配置是什么。
  - **模拟器**：Comal（cycle-accurate dataflow simulator），基于 DAM simulation framework，Rust 1.87.0 编写。集成 HBM2 内存模拟（Ramulator 2.0）。
  - **FPGA**：Xilinx VU9P (AWS F1)，通过 Vitis HLS 综合。用于验证模拟器保真度（$R^2=0.991$）。
  - **模拟器建模**：对每个 IR node 的行为建模，基于 fully pipelined dataflow graph 追踪 cycles。所有模拟功能结果通过 dense PyTorch 实现验证。
  - **编译环境**：MLIR (LLVM 19.1.0)、Protobuf 28.1、OR-Tools 9.10、GCC 14.2.0。编译时间 < 750ms（所有 benchmark 模型）。

- 开源编译框架是什么。修改了什么。
  - **开源编译框架**：FuseFlow 在 MLIR 编译器框架内**全新实现**（非修改已有编译器），将 SAM 重新实现为 MLIR dialect。前端复用 Torch-MLIR（dense 组件）和 MPACT（sparse 组件）。
  - **新增内容**（非修改已有框架）：
    - **Fused Einsum + POG IR**：全新的跨表达式融合 IR，扩展 index substitution 算法并引入 POG 约束图。
    - **Fusion Table IR**：全新的 lowering IR，支持 deferred graph construction 和 factored iteration。
    - **SAMML MLIR dialect**：扩展原始 SAM 图以支持 ML 原语（nonlinear functions, masking, dense blocks）。
    - **编译 pass pipeline**：cross-expression fusion pass → fusion table construction pass → codegen pass → parallelization/sparsity blocking/dataflow ordering passes。
    - **Comal 模拟器**：基于 DAM 框架 [81] 实现的 cycle-accurate 数据流模拟器。
    - **Heuristic model**：FLOPs/bytes 快速估计模型用于 pruning suboptimal configurations。

  - **开源**：论文提供 artifact（GitHub: fuseflow-artifact 仓库 + Figshare DOI 存档），MIT License。Docker 镜像包含全部依赖（MLIR/LLVM、Python、Rust、protobuf 等），支持 x86-64 机器（≥64 GB RAM, ≥200 GB 磁盘）。
  - **编译框架输入到输出的全过程**：
    1. **输入**：用户用 PyTorch 编写稀疏 ML 模型，通过 sparse annotations（Scorch [75] 或 MLIR SparseTensor dialect）指定稀疏格式。例如 GCN 前向传播：
       ```python
       # PyTorch with sparse annotations
       # A: sparse adjacency matrix (CSR format)
       # X: dense feature matrix
       # W: dense weight matrix
       H1 = A @ X @ W    # sparse-dense matmul, then dense-dense matmul
       H1 = relu(H1)
       H2 = A @ H1 @ W2
       output = softmax(H2)
       ```
    2. **Frontend Lowering (Torch-MLIR/MPACT → MLIR Linalg + SparseTensor)**：PyTorch 模型被 lowering 到 MLIR Linalg + SparseTensor dialects。每个操作（如 `torch.mm`, `F.relu`, `F.softmax`）被表示为 Einsum 表达式或非线性 op。稀疏张量的格式信息（CSR、DCSR、COO 等）编码在 SparseTensor dialect 的 `sparse_tensor.encoding` 属性中。例如 `A @ X` 被表示为 `∀_{ikj} H_{ij} = A_{ik} X_{kj}`。
    3. **Fusion Schedule**：用户在 MLIR 中用 `Fuse{}` region 标注融合边界，用 Linalg affine maps 指定 dataflow order（如 `i → k → j`），通过命令行指定 parallelization factor、sparsity block size 等。例如：
       ```
       Fuse {
         %0 = linalg.einsum "ij, jk -> ik" (%A, %W)  // 第一个 matmul
         %1 = linalg.einsum "ik, kj -> ij" (%B, %0)  // 第二个 matmul
       }
       ```
    4. **Cross-Expression Fusion (Section 5)**：FuseFlow 的 fusion pass 处理每个 `Fuse{}` region：
       - a) **Rename local indices**：为每个表达式的局部归约索引分配 fresh indices（如 u-indices），避免跨表达式命名冲突。
       - b) **Build fused Einsum producer-consumer edges**：通过 index substitution 连接 producer 和 consumer。例如 producer `H1_{ik} = A_{il} X_{lk}` 的 `ik` 替换 consumer `H2_{im} = H1_{ik} W_{km}` 的 `ik`，将两者通过 `H1` 连接。
       - c) **Propagate order constraints**：在 POG 中插入表示 outer-to-inner 顺序关系的 directed edges。约束来源：（i）稀疏张量的 mode order（如 CSR A 要求 i→j，即 [0,1]），（ii）用户指定的 dataflow order。
       - d) **Handle multiple tensor uses**：同一张量被多次使用时，为每个 use 创建独立 view。若多个 view 产生冲突的 ordering 约束（POG 中出现 cycle），物化一个 permuted copy 来打破 cycle。
       - e) **Topological sort**：对无环 POG 进行 topological sort，输出所有 valid global dataflow order。输出为 fused Einsum 表示 + POG。
    5. **Fusion Table Construction (Section 6)**：对每个 fused Einsum：
       - a) **插入 Level Scanner (LS) 和 Value cells**：按 dataflow order 从上到下为每个输入张量 view 创建 LS cells（坐标流）和 value cells（值流）。
       - b) **插入 Repeat 和 Compute cells**：识别缺失的索引变量，插入 Rep nodes 进行广播。插入 ALU 和 Red nodes 进行计算。
       - c) **处理高阶归约 (Higher-Order Reduction)**：对归约操作（如 sum over k），创建 reducer cell，产生 reduced value stream 和 reduced output coordinate。
       - d) **插入 Stream Merging cells**：识别跨多个张量 view 共享的索引变量，创建 Intersect/Union cells 合并坐标流。通过移动已有 cells 到新 merged cells 来重连数据流连接。
       - 结果：一个完整的 fusion table，行 = 融合迭代顺序（i→k→j），列 = 每个操作数/中间结果，单元格 = 数据流节点或指针引用。
    6. **Code Generation (Section 6.2)**：从输出张量的 value cell 开始递归展开依赖链，按 fusion table 的 top-down 顺序实例化数据流节点：
       - 生成 Input Iteration region（蓝色）：Level Scanners → Intersect/Union coord merging
       - 生成 Computation region（黄色）：Value fetchers → ALU/MUL → Reducers
       - 生成 Tensor Construction region（红色）：Level Writers → Coordinate Droppers
       - 生成的 SAMML 图采用 **factored iteration**：迭代子图（input iteration）和计算子图（computation）在空间上交错排列（如图 11 所示），而非 global iteration 的单一大迭代子图。
       - 对于 parallelization：编译器通过 stream parallelizer 复制计算子图，通过 stream serializer 合并并行结果流。
    7. **Backend Execution**：
       - **Comal Simulator**：加载 SAMML 图，用 Rust 编写的 DAM simulation framework [81] 进行 cycle-accurate 仿真。模拟器对每个 IR node（LS, Intersect, Rep, ALU, Red, LW, CD 等）按 fully pipelined 方式建模。HBM2 内存访问通过 Ramulator 2.0 [48] 模拟。输出：cycle count, FLOPs count, bytes transferred。
       - **FPGA (Vitis HLS)**：SAMML 图被 lowering 到 HLS C++ 代码，通过 Vitis HLS 综合为 Xilinx VU9P (AWS F1) 比特流。用于验证模拟器 cycle count 与 RTL 仿真之间的一致性。
    8. **Heuristic Pruning**（可选的快速评估路径）：跳过完整模拟，用户输入 tensor dimensions、sparsity percentages、intersection rates，heuristic 快速估计 FLOPs 和 memory transfers。用于在 exhaustive search 前 prune 明显 suboptimal 的配置。

    **关键差异说明**：FuseFlow 的 factored iteration 与 Custard/Stardust 的 global iteration 本质不同——global iteration 先构建完整的 n 维输入迭代子图再连接计算子图（类似图 11 左侧），而 factored iteration 将输入迭代和计算交错为多个较小的子图对（类似图 11 右侧），在多稀疏张量场景下显著减少 coordinate processing overhead。

## Flashlight: PyTorch Compiler Extensions to Accelerate Attention Variants

- 属于编译框架的实现是什么？实验比较什么？
  - **实现**：Flashlight 是 PyTorch 生态系统内的编译器原生框架，通过扩展 `torch.compile` 的 TorchInductor 后端，**自动生成融合的 FlashAttention 风格 Triton kernel**，无需静态模板或预定义 kernel 特化。核心编译器扩展包括：
    1. **统一归约 IR (Unified Reduction IR)**：将矩阵乘法（GEMM）建模为广义归约操作，解除 TorchInductor 中原有 GEMM→CUBLAS 的融合边界，使 matmul 能够与周围的 softmax、element-wise 等操作在 IR 层面融合。
    2. **结构融合 + 维度降级 (Structural Fusion with Dimension Demotion)**：当 producer 和 consumer 的 kernel sketch 不兼容时（如 producer 的并行维度与 consumer 的归约维度冲突），通过将 producer 的并行维度降级为融合后的归约循环来使两者兼容。原理是用并行度换取内存局部性。
    3. **语义融合 + 代数变换 (Semantic Fusion with Algebraic Transformation)**：利用指数函数的同态性质（$e^{a-b} = e^a / e^b$），在编译器 IR 层面自动将 stable softmax（两轮归约：max 后 exp + sum）转换为 online softmax（单轮融合归约：同时维护 running max、running sum 和 running output），消除中间张量的物化。
    4. **分块感知维度消除 / Twin Matmul (Tiling-Aware Dimension Elimination)**：对连续矩阵乘法 $(A \cdot B) \cdot D$，通过分块使隐藏维度在 tile 级别被即时消费，避免物化完整中间张量。两个 matmul 在同一个融合 kernel 中以 tile pipeline 方式执行。
    5. **逻辑网格维度 (Logical Grid Dimensions)**：将逻辑分块网格与物理硬件限制解耦，允许独立选择 tile size，不受 GPU thread block 数量限制。
  - **实验比较**：Flashlight vs FlexAttention vs `torch.compile`（默认）。评估维度包括 kernel 执行时间、端到端延迟、block-mask 创建开销。覆盖 FlexAttention 兼容的 7 种标准 attention 变体和 FlexAttention 不支持的 2 种复杂变体（Differential Attention、AlphaFold Evoformer），以及 AlphaFold2 端到端推理。

- 硬件平台是什么，配置是什么。
  - **GPU**：NVIDIA A100 80GB 和 NVIDIA H100 80GB。SM 频率限制在 1290 MHz 以保持运行方差在 1% 标准差以内。
  - **软件栈**：Python 3.12, PyTorch 2.5.0, Triton 3.1.0, CUDA 12.9。
  - **Benchmark 设置**：每次测量 20 次运行取平均，10 次 warmup。

- 开源编译框架是什么。修改了什么。
  - **开源编译框架**：PyTorch 2.0 编译栈（TorchDynamo → AOTAutograd → TorchInductor）。Flashlight **不是独立的编译器**，而是对 TorchInductor 的扩展。用户通过 `torch.compile(enable_flashlight=True)` 启用。
  - **修改内容**：
    - **TorchInductor IR 扩展**：引入统一归约 IR，将 `torch.bmm`/`torch.matmul` 从直接映射到 CUBLAS 改为表示为归约操作，使其参与后续的融合和分块 pass。
    - **融合 pass 扩展**：增加结构融合（维度降级）、语义融合（代数变换）和分块感知维度消除三个新的编译器 pass。
    - **代码生成扩展**：生成的融合 kernel 输出为 OpenAI Triton 语言，再由 Triton 编译器编译为 NVIDIA PTX。与现有 TorchInductor pass 完全兼容。

  - **开源**：论文投稿时为匿名（MLSys 2026 已接收），代码尚未公开发布。论文未提供 GitHub 链接。
  - **编译框架输入到输出的全过程**：
    1. **输入**：用户编写的标准 PyTorch 代码（无需特殊 API、block mask 或模板）。例如 differential attention：
       ```python
       import torch
       def diff_attn(Q1, Q2, K1, K2, V):
           A1 = Q1 @ K1.transpose(-2, -1) * (1/d**0.5)
           A2 = Q2 @ K2.transpose(-2, -1) * (1/d**0.5)
           A = A1 - λ * A2                    # differential score
           return F.softmax(A, dim=-1) @ V
       
       # 用户只需一行启用
       compiled_fn = torch.compile(diff_attn, enable_flashlight=True)
       output = compiled_fn(Q1, Q2, K1, K2, V)
       ```
    2. **TorchDynamo (FX Graph Capture)**：捕获 Python 函数为 `fx.Graph` IR。图中的操作包括 `torch.bmm`（矩阵乘法）、`torch.softmax`、逐元素运算（减法、乘法、除法）。
    3. **AOTAutograd**：将前向图分解为 Aten 算子序列，生成对应的反向图。
    4. **TorchInductor + Flashlight 扩展**（核心阶段）：
       - **统一归约 IR**：将图中的 `torch.bmm`（通常直接映射到 CUBLAS）转换为归约操作节点，消除 GEMM 融合边界。
       - **结构融合 + 维度降级**：分析 producer（如 `Q1 @ K1^T`）和 consumer（如 softmax）的循环嵌套。若 matmul 的输出维度在 softmax 中是归约维度，通过维度降级将 matmul 的并行维度转为归约维度，使两者可融合为一个 kernel。
       - **语义融合 + 代数变换**：识别 softmax 的计算模式（max → exp → sum → div），利用指数同态性质自动将 stable softmax 的三轮循环（先 max、再 exp+sum、最后 div）转换为 online softmax 的单轮融合循环（同时维护 running max `m`、running normalizer `ℓ` 和 running output `O`），消除中间张量 `S` 和 `P` 的全局内存写入。
       - **Twin Matmul 分块融合**：对 `(A @ B) @ D` 模式，选择分块策略使 B 的列维度 tile 被即时消费，不物化 `(A @ B)` 的完整结果。
       - **逻辑网格维度**：根据 tile size 和计算量分配逻辑线程块，解耦物理 GPU grid 限制。
       - **Triton 代码生成**：将融合后的 IR 降级为 Triton 语言代码。生成的 kernel 包含分块循环、online softmax 的状态维护、以及 MMA（矩阵乘累加）指令。
    5. **Triton 编译器**：将 Triton 代码编译为 NVIDIA PTX。
    6. **输出**：可在 GPU 上执行的 PTX kernel。kernel 执行时对 Q/K/V tile 进行分块迭代，在共享内存/SRAM 中完成 matmul + online softmax + output accumulation，仅将最终 O 写回全局内存。
  - **对比 FlexAttention 的使用差异**：
    - FlexAttention 要求用户定义 `score_mod` 和 `mask_mod` 函数，并手动管理 `block_mask` 缓存（`block_mask = create_block_mask(mask_mod, ...)`），block-mask 创建本身有显著开销（paper 中显示在某些配置下 block-mask 创建时间超过 kernel 执行时间）。
    - Flashlight 不需要任何模板 API、block mask 或缓存管理。用户编写标准 PyTorch 代码，编译器自动分析并生成融合 kernel。对于 FlexAttention 支持的变体，Flashlight kernel 执行时间略慢于 FlexAttention 的 hand-tuned kernel，但总时间（含 block-mask 创建）Flashlight 更快。
  - **关键设计取舍**：统一归约 IR 将 matmul 表示为归约操作后，**放弃了专用 GEMM kernel（CUBLAS）的极致性能**，换取与周围操作融合的机会。当融合带来的内存带宽节省超过 GEMM kernel 的性能损失时，净收益为正。对于短序列或内存密集型 attention 变体，融合收益更大。

## Streaming Tensor Programs (STeP)

- 属于编译框架的实现是什么？实验比较什么？
  - **实现**：STeP 是一种面向空间数据流加速器（SDA）的异步数据流编程抽象，可作为编译器 IR。其编译框架包括：
    1. **Symbolic Python Frontend**：提供类似 PyTorch 的 Python 编程接口，使用 SymPy 实现符号表达式系统，自动计算 off-chip memory traffic、on-chip memory requirement 和 operational intensity 等性能关键指标。支持 stream shape 验证（producer-consumer shape alignment）和符号变量替换（用于分析不同 input shape/control-flow 下的指标）。
    2. **Stream-centric IR**：以 stream 为核心表示，stream 具有编译时确定的 rank 和 data type。每个 stream 支持三种维度类型：static-regular、dynamic-regular、ragged。Stream 通过 stop tokens（$S_N$, $D$）嵌入逻辑 tensor 结构。
    3. **五类 STeP 算子**：(a) Off-chip memory operators（LinearOffChipLoad/Store, RandomOffChipLoad/Store）表达片下-片上数据传输；(b) On-chip memory operators（Bufferize, Streamify）显式管理片上 scratchpad；(c) Dynamic routing and merging operators（Partition, Reassemble, EagerMerge）支持 data-dependent control flow；(d) Higher-order operators（Map, Accum, Scan, FlatMap）应用硬件支持的计算函数；(e) Shape operators（Flatten, Reshape, Promote, Expand, Zip）仅修改 stop tokens 不改数据。
    4. **Rust Simulator Backend**：基于 Dataflow Abstract Machine (DAM) simulation framework [55]，集成 Ramulator 2.0 HBM 节点模拟片外内存时序，使用 Roofline 模型计算 higher-order operator 延迟：max(size_of_inputs/on_chip_mem_BW, total_FLOPs/compute_BW, size_of_outputs/on_chip_mem_BW)。
    5. **编译路径设想**（Section 6.1）：PyTorch → torch.compile → FX Graph → STeP subgraphs（遍历 FX graph node 并 lowering，优化 schedule 通过 index variables 指定 parallelization、tiling、configuration time-multiplexing）。
  - **实验比较**：
    - **Dynamic Tiling vs Static Tiling**：MoE layer (Qwen3-30B-A3B, Mixtral-8x7B)，比较 cycle count 和 on-chip memory。Static tiling 扫描 tile sizes（2-1024），dynamic tiling 使用 Promote 替代 Reshape 使 Accum 自适应 batch dimension。PID（Pareto Improvement Distance）为 1.33×~2.11×。
    - **Configuration Time-multiplexing vs 每 expert 独立配置**：Sweep 共享同一 configured region 的 expert 数量，比较 compute utilization（static tiling 提升 2.64×，dynamic tiling 提升 2.51×）和 resource usage（释放 62% compute + 46% memory）。
    - **Dynamic Parallelization vs Static Coarse-grained/Interleaved Parallelization**：Attention layer 上比较不同 batch size 和 KV cache length 分布。Dynamic parallelization 通过 Partition + EagerMerge 实现异步 work dispatch。
    - **End-to-end Model**：Qwen3-30B-A3B 和 Mixtral-8x7B 完整模型，比较 optimized vs baseline 的 speedup（Mixtral 1.27×, Qwen3 1.15×）和 resource savings（Qwen3: 69% less on-chip memory, 54% fewer compute）。
    - **Simulator Validation vs HDL**：SwiGLU layer 在 STeP cycle-approximate simulator 与 Bluespec SystemVerilog cycle-accurate HDL simulator 之间比较，Pearson correlation = 0.99，不同 tile sizes 下 cycle count 高度一致。

- 硬件平台是什么，配置是什么。
  - **目标硬件**：Spatial Dataflow Accelerators (SDAs)，参考架构为 reconfigurable dataflow accelerators（SambaNova SN40L [33], Plasticine [35], Onyx [20]）。Compute units 操作于 16×16 BFloat16 tiles，initiation interval = 1。
  - **模拟器配置**：on-chip memory bandwidth = 64 bytes/cycle，off-chip memory bandwidth = 1024 bytes/cycle（匹配 SambaNova SN40L RDU 配置 [33]）。
  - **HDL 验证环境**：Bluespec SystemVerilog HDL model，cycle-accurate BlueSim simulator。HBM2 subsystem（8 stacks）通过 Ramulator 2.0 library calls 集成。on-chip memory bandwidth = 256 bytes/cycle。采用 hierarchical tiling（将 STeP-level logical tiles 分解为 16×16 physical tiles 匹配 fabric compute tile size）。
  - **运行环境**：x86-64 机器（≥32GB RAM），Docker 容器。完整实验约需 24.5 小时（Google Cloud C4-standard-8: 8 Intel Emerald Rapids vCPUs, 30GB memory）。

- 开源编译框架是什么。修改了什么。
  - **开源编译框架**：STeP **全新实现**（非修改已有编译器），包括 symbolic Python frontend 和 Rust simulator backend。
  - **开源仓库**：
    - https://github.com/stanford-ppl/step_artifact（Python frontend + Rust simulator + 实验脚本）
    - https://github.com/stanford-ppl/step-artifact-hdl（Bluespec SystemVerilog HDL 验证模型）
  - **License**：MIT License
  - **DOI**：https://doi.org/10.6084/m9.figshare.31095274
  - **核心组件**：
    - **Symbolic Frontend**：Python 实现，SymPy 符号表达式计算。提供每个 operator 的 off-chip traffic（output_stream_cardinality × |output_stream_dtype|）和 on-chip memory requirement 方程。Bufferize/Accum/Scan/Expand 算子考虑 double buffering。支持 hierarchical tiling 将 STeP-level tiles 分解为 hardware-aligned 16×16 tiles。

  - **工具链定制**：Frontend 方程可自定义以捕获 hardware-specific operator details（如 hardware tile sizes, matmul implementation）；Simulator 中 scratchpad simulator 可替换 Roofline model 以捕获 on-chip memory contention；内存技术可通过重新配置 HBM node 适配。

  - **编译框架输入到输出全流程**：

## Tilus

- 属于编译框架的实现是什么？实验比较什么？
  - **实现**：Tilus 是一个面向 GPGPU 低精度计算的 **tile-level 领域特定语言（DSL）和编译器**，支持 1-8 bit 任意位宽的整数和浮点低精度数据类型。核心编译组件包括：
    1. **代数布局系统（Algebraic Layout System）**：通过 primitive layouts（`local(n₁,n₂)` 和 `spatial(n₁,n₂)`）和 Kronecker product（⊗）组合成复杂寄存器张量布局，统一表示 tile 元素在线程间的分布。支持布局除法（h / g 逆运算），实现无代价的寄存器张量 reinterpretation。
    2. **Thread-Block-Level 编程模型（SIMB 范式）**：定义操作在 thread block 粒度而非 thread 粒度。指令集包括 Tensor Creation（AllocateGlobal/Shared/Register, ViewGlobal）、Tensor Transferring（LoadGlobal/Shared, StoreGlobal/Shared, CopyAsync）、Register Tensor Computation（Dot/Cast/View/Arithmetic）、Control（Synchronize/Exit）等。
    3. **低精度数据支持与 lowering**：通过全局内存中权重布局变换（例如 i6[BK,BN] → u8[BK×BN×6/8]），使低精度张量可用硬件友好的 LoadGlobal 加载；通过 PRMT/LOP3/bitwise 指令实现高效向量化类型转换（vectorized casting），所有操作在寄存器内完成，无需线程间通信。
    4. **编译路径**：Python DSL → Tilus IR → 优化 passes（冗余消除、算术简化）→ Hidet IR（CUDA C-like IR）→ 低精度 lowering（将低精度操作转换为标准类型的等价操作）→ CUDA C → nvcc → GPU 二进制 → Runtime 动态加载。
    5. **编译优化**：自动向量化（cp.async.v4, lds128, ldg128）、指令选择（ldmatrix 替代 lds，当布局兼容时）、Global/Shared Memory Planning（共享内存分配规划 + 全局内存 workspace 管理）、软件流水线（software pipelining）支持。
    6. **约 35K 行 Python + C++ 代码**实现。
  - **实验比较**：
    - **与编译器的比较**：Tilus vs Triton（编译器）、Tilus vs Ladder（编译器），在多种低精度数据类型的 matmul kernel 上比较 speedup（相对于 cuBLAS FP16）。
    - **与手工 kernel 的比较**：Tilus vs QuantLLM（手工）、Tilus vs Marlin（手工）。
    - **数据类型覆盖**：uint1-uint8, int2-int8, float3-float8（e4m3, e3m3, e3m2, e2m2, e2m1, e1m1 等），完整的低精度类型谱。
    - **端到端性能**：在 vLLM 中集成 Tilus 量化 kernel，对比 vLLM FP16 和 Ladder uint4，在 Gemma-2-9B、QWen2.5-32B、Llama-3.3-70B 上评估 decode（batch 1/16）和 prefill（2048 tokens）延迟。
    - **跨硬件**：A100, L40S, H100 上的端到端性能对比。
    - **Batch size 消融**：decode 阶段 batch 1/4/8/16，prefill 阶段 batch 4096/8192/12288。

- 硬件平台是什么，配置是什么。
  - **主实验平台**：NVIDIA L40S GPU（48 GiB），GPU driver 565.57.01，CUDA Toolkit 12.6.3。
  - **扩展平台**：NVIDIA A100 和 NVIDIA H100 GPU（用于跨架构验证）。
  - **软件版本**：vLLM v0.5.3, Triton v3.1.0, bitblas v0.0.1.dev15 (Ladder), QuantLLM commit 9802c5a, Marlin v0.1.1。

- 开源编译框架是什么。修改了什么。
  - **开源编译框架**：Tilus 是**全新实现的 DSL 和编译器**，非修改已有编译框架。其后端生成代码经过 Hidet IR [14]（一种 CUDA C-like IR），但 Tilus 的布局代数系统、thread-block-level 指令集和低精度 lowering 均为全新设计。
  - **与已有框架的关系**：
    - Tilus 选择了不与 Triton [53] 扩展兼容，因为 Triton 的编程模型本质上抽象掉了张量布局，与 Tilus 的显式布局控制方法不兼容。
    - Tilus 选择了不与 Ladder [58] 扩展兼容，因为 Ladder 依赖 type-level packing，而 Tilus 采用 tile-level reinterpretation，两者根本不同。
    - 后端代码生成使用 Hidet IR 作为 intermediate lowering target，最终通过 nvcc 编译。

- 开源情况。基于开源文档和论文，使用例子解释编译框架如何使用？作用是什么？至少具体到编译框架输入到输出的全过程。
  - **开源**：Tilus 开源在 https://github.com/NVIDIA/tilus。Artifact 在 https://github.com/yaoyaoding/tilus-artifacts，DOI: 10.5281/zenodo.16756859，Apache 2.0 License。提供 Docker 镜像（~21 GiB），包含全部依赖（PyTorch v2.5.1, Triton v3.1.0, BitBLAS, Marlin, vLLM 0.7.3）。
  - **编译框架输入到输出的全过程**（以 FP16 × INT6 矩阵乘法为例）：
    1. **输入**：用户在 Python 中编写 Tilus program（DSL），定义 grid shape、参数、program body。key 特性包括显式指定寄存器张量布局（例如 `column(2,2).spatial(8,4).local(1,2)` 对应于 mma.m16n8k16 tensor core 指令的操作数布局）。
    2. **预处理（权重布局变换）**：在 kernel 启动前，Tilus 执行一个预处理 program 将权重张量从原始格式（如 i6[K,N]）变换为硬件友好的紧凑格式（如 u8[K/BK, N/BN, BK×BN×6/8]）。变换规则：给定每个线程 n bytes 和 T threads，reinterpret 为 dtype u8 + layout local(n₂).spatial(T).local(n₁)，其中 n₁=gcd(n,16), n₂=n/gcd(n₁,16)。
    3. **IR 生成**：Python DSL program 被翻译为 Tilus VM IR（thread-block-level 指令序列）。
    4. **优化 Passes**：冗余消除（dead code elimination）、算术表达式简化。
    5. **Code Emitting (Hidet IR)**：每条 Tilus 指令顺序 emit 为低层 GPU 代码（Hidet IR）。此阶段执行：(a) 指令选择——如布局兼容 `spatial(8,4).repeat(1,4)` 时使用 ldmatrix PTX 指令替代 lds；(b) 自动向量化——使用 cp.async.v4, lds128, ldg128 等向量化指令。
    6. **Memory Planning**：Shared Memory Planner 计算程序所需共享内存大小并映射 shared tensor；Global Memory Planner 管理 workspace 分配。
    7. **低精度 Lowering**：将 IR 中所有低精度操作（如 int6 loading/casting）替换为标准类型操作。在大多数情况下，由于布局形式化和寄存器张量 reinterpretation，只需要向量化的低精度→标准类型 casting（使用 PRMT/LOP3/bitwise 指令）。
    8. **CUDA C 代码生成**：从 Hidet IR 生成 CUDA C 代码。
    9. **编译为二进制**：nvcc 编译 CUDA C → GPU 硬件二进制。
    10. **Runtime 加载与执行**：Runtime System 动态加载编译后的二进制，管理 workspace memory（按需分配的全局内存）、execution context（CUDA stream）、kernel cache（避免重复编译）。一个 program template 通过参数化 tile sizes（约 200 configurations/operator，编译约 1 分钟）支持所有量化数据类型。
