## Arm TrustZone（ARM 可信区）

术语是什么？

Arm TrustZone 是 ARM 架构中的硬件级安全隔离技术，将 SoC 的硬件资源（CPU、内存、外设、中断）划分为两个安全世界：**安全世界（Secure World）** 和 **非安全世界（Normal World）**。安全世界中运行 Trusted Execution Environment (TEE)，包含安全敏感的 Trusted Applications (TAs) 和精简的 TEE OS；非安全世界中运行 Rich Execution Environment (REE)，包含传统的全功能 OS（Linux/Android）和普通应用。TrustZone 通过以下硬件组件强制隔离：(1) CPU 的 NS（Non-Secure）状态位——通过 EL3 安全监控器（Secure Monitor）和 `smc` 指令在安全/非安全状态间切换；(2) TZASC（TrustZone Address Space Controller）——在物理地址级别保护安全内存区域，禁止非安全 CPU 和 DMA 设备访问；(3) TZPC（TrustZone Protection Controller）——保护安全外设的 MMIO 寄存器，禁止非安全 CPU 访问；(4) GIC（Generic Interrupt Controller）安全扩展——将安全设备的中断隔离路由到 TEE OS 而非 REE OS。

从硬件架构角度拆解术语：

TrustZone 在 TZ-LLM 中的运转流程（以 RK3588 上执行一次安全 NPU job 为例）：

1. **初始状态**（NPU 为非安全设备）：NPU MMIO 寄存器可被 REE NPU 驱动访问，NPU 中断路由到 REE OS，TZASC 禁止 NPU DMA 访问安全内存。
2. **TEE 接管 NPU**（smc 触发）：
   - 配置 TZPC：将 NPU MMIO 区域标记为安全设备，此后 REE CPU 的任何 MMIO 访问被硬件拦截
   - 等待进行中的非安全 NPU job 完成（轮询 NPU 状态寄存器）
   - 配置 TZASC：修改对应 TZASC region 的 DMA 权限位，授予 NPU 对 job 执行上下文所在的安全内存区域的 DMA 访问权
   - 配置 GIC：将 NPU 中断重新路由到 TEE OS 的中断向量表
3. **安全 NPU job 执行**：TEE NPU 驱动通过 MMIO 启动 job → NPU 三核从安全内存 DMA 读取参数和输入 → 计算 → DMA 写入安全内存 → 触发安全中断 → TEE OS 中断处理器调用 TEE NPU 驱动的 completion handler
4. **归还 NPU**：逆向操作——撤销 TZASC DMA 权限 → 恢复 GIC 中断路由 → 恢复 TZPC 配置

术语一般如何实现？如何使用？

- **硬件要求**：ARM Cortex-A 系列处理器（Cortex-A53/A55/A72/A76/A78/X1 等）均内置 TrustZone 支持。需要 SoC 设计时在内存映射中包含 TZASC（如 TZC-400、TZC-380）和 TZPC 硬件 IP。
- **TEE OS 选择**：OP-TEE（开源，Linux 基金会项目）、OpenHarmony TEE（华为鸿蒙的 TEE 实现，TZ-LLM 使用）、Qualcomm QTEE（高通闭源）、Trusty TEE（Google Android）。
- **TA 开发**：TA 编译为独立 ELF，由 TEE OS 加载。TA 代码和数据位于 TZASC 保护的安全内存中。CA（Client Application）在 REE 中通过 TEE Client API 与 TA 通信。
- **内存约束**：TZASC 通常支持 8 个可配置的连续物理内存区域。每个区域通过基地址+大小编程。TZ-LLM 受此限制必须使用 CMA 分配物理连续内存，而非 page-granular S2PT。

涉及论文标题：
- TZ-LLM

## TZASC（TrustZone Address Space Controller）

术语是什么？

TZASC（常见型号 TZC-400、TZC-380）是 Arm TrustZone 硬件生态中的**物理地址级内存保护控制器**。它位于 SoC 的互联总线（如 AXI/ACE）上，拦截所有总线事务（CPU 访存和 DMA 访存），根据预设的安全区域配置和事务的安全属性（AxPROT 信号中的安全位）决定放行或拒绝。TZASC 支持配置多个（典型 8 个）连续物理内存区域为安全区域，每个区域可独立设置访问权限。与传统 MMU/S2PT 的虚拟地址级保护不同，TZASC 在物理地址级工作——即使攻击者控制了 REE OS 内核并任意修改页表，也无法绕过 TZASC 读/写安全内存。

从硬件架构角度拆解术语：

TZASC 在 TZ-LLM 中的配置和使用：

- **内存布局**：TZ-LLM 分配两个独立的 TZASC 区域：(1) Region A——存放 LLM 参数（按 first-in-last-out 模式增长/收缩，保持物理连续性）；(2) Region B——存放 KV cache、activations 和其他运行时数据。
- **extend\_protected 操作**：TEE OS 通过编程 TZASC 寄存器（基地址 + 区域大小）将新分配的 CMA 内存块纳入保护范围。区域末地址扩展后，新内存立即可被安全 CPU 访问，但非安全 CPU/DMA 访问被硬件拦截。
- **shrink 操作**：TEE OS 先清除数据（防止信息泄漏），然后编程 TZASC 缩小区域末地址，再通知 REE 释放该内存回 CMA。清除+缩小+释放的顺序确保数据永不暴露给非安全世界。
- **DMA 权限控制**：TZASC 允许为每个区域配置哪些设备可以 DMA 访问。TZ-LLM 为 Region A（LLM 参数）默认禁止所有 DMA；仅在安全 NPU job 执行期间临时授予 NPU DMA 访问权。

术语一般如何实现？如何使用？

- **编程接口**：TZASC 通过 MMIO 寄存器编程（基地址通常在 SoC 手册中定义，如 0x24100000）。典型寄存器包括：区域配置寄存器（REGION\_BASE\_LOW/HIGH、REGION\_TOP\_LOW/HIGH）、访问控制寄存器（REGION\_ATTRIBUTES，控制 secure read/write、non-secure read/write 权限）、DMA 过滤寄存器（REGION\_ID\_ACCESS，按 AXI ID 过滤设备）。
- **安全启动集成**：TZASC 初始配置通常在 ATF（ARM Trusted Firmware）的 BL31 或 TEE OS 启动阶段完成，之后仅安全世界可修改 TZASC 寄存器。
- **限制**：TZASC 仅支持**连续物理内存区域**保护（通常 ≤8 个区域），不支持 page-granular（4KB）保护。这是 TZ-LLM 使用 CMA + first-in-last-out 内存管理模式的根本原因。

涉及论文标题：
- TZ-LLM

## TZPC（TrustZone Protection Controller）

术语是什么？

TZPC（TrustZone Protection Controller）是 Arm TrustZone 硬件生态中的**外设安全属性控制器**。它将 SoC 上的外设（如 NPU、GPU、DMA 控制器、UART、SPI 等）分类为安全设备或非安全设备。TZPC 通过一组 MMIO 寄存器（每个外设对应一个控制位），控制外设 MMIO 接口是否允许非安全 CPU 访问以及外设产生的中断是否路由到安全世界。与 TZASC（保护内存）互补，TZPC 保护的是**外设的控制接口**——防止非安全世界通过配置外设发起恶意 DMA 攻击（如重新编程 DMA 控制器目标地址指向安全内存）。

从硬件架构角度拆解术语：

TZPC 在 TZ-LLM 的 NPU 安全切换中的运转：

1. **REE 模式**（NPU 为非安全）：TZPC DECPROT 寄存器中 NPU 对应的 bit 为 0，允许 REE CPU 通过 MMIO 访问 NPU 寄存器，NPU 中断路由到 REE OS。
2. **切换前**：TEE NPU 驱动通过 smc 请求 REE TZ driver 触发 NPU 安全切换。
3. **TZPC 编程**：TEE OS 写入 TZPC DECPROT SET 寄存器，将 NPU 对应 bit 置 1。此后：
   - REE CPU 对 NPU MMIO 的任何访问被硬件拦截（返回 AXI DECERR/SLVERR），防止 REE 发起新的非安全 NPU job
   - NPU 中断被 GIC 路由到 TEE OS（GIC 根据 TZPC 状态判断中断目标）
4. **归还时**：TEE OS 写入 TZPC DECPROT CLEAR 寄存器，将 NPU 恢复为非安全设备。

术语一般如何实现？如何使用？

- **编程接口**：TZPC 通过 MMIO 寄存器控制。典型寄存器布局：
  - DECPROT\[n\]\_SET：写入 1 将外设 n 设为安全设备
  - DECPROT\[n\]\_CLEAR：写入 1 将外设 n 设为非安全设备
  - DECPROT\[n\]\_STATUS：读取当前安全状态
- **限制**：TZPC 的安全/非安全配置是粗粒度的——整个外设（而非外设内的子功能）被一次性切换。TZ-LLM 的 co-driver 设计利用这一事实：在安全模式下，全部 NPU 资源归 TEE 独占；在非安全模式下，全部归 REE 独占（SPU 的空间共享方案 [sNPU] 需要硬件修改）。

涉及论文标题：
- TZ-LLM

## GIC with TrustZone Security Extension（带 TrustZone 安全扩展的通用中断控制器）

术语是什么？

GIC（Generic Interrupt Controller）是 ARM 架构中的标准中断控制器，负责管理 SoC 上所有外设产生的中断（IRQ/FIQ），将其路由到对应的 CPU 核心和异常级别。GIC 的 TrustZone 安全扩展允许将每个中断源（INTID）配置为**安全中断（Secure interrupt）**或**非安全中断（Non-secure interrupt）**。安全中断只能被安全世界（EL3/TEE OS）处理，非安全世界无法屏蔽、劫持或伪造安全中断。中断路由通过 GIC 的 GICD\_IGROUPR（Group 0 vs Secure Group 1 vs Non-secure Group 1）和 GICD\_ITARGETSR（目标 CPU）寄存器配置。

从硬件架构角度拆解术语：

GIC 安全中断路由在 TZ-LLM NPU 分时复用中的运转：

1. **REE 模式**：NPU 中断在 GICD\_IGROUPR 中配置为 Group 1 Non-secure（Grp1NS），触发时路由到 REE OS 的 IRQ handler → REE NPU 驱动的 completion handler。
2. **切换到安全模式时**：TEE OS 配置 GICD\_IGROUPR 将 NPU 中断改为 Group 1 Secure（Grp1S）或 Group 0 → 触发时路由到 TEE OS 的 FIQ/IRQ handler → TEE NPU 驱动的 completion handler。
3. **安全中断处理**：TEE NPU 驱动在中断上下文中读取 NPU 状态寄存器确认 job 完成 → 清除中断挂起位 → 归还 NPU（TZASC/TZPC 逆向配置）→ 通知 REE 驱动 shadow job 完成。
4. **中断优先级**：ARM GIC 规范中 Group 0（最高优先级）> Group 1 Secure > Group 1 Non-secure（最低优先级），确保安全中断不会被非安全中断抢占或延迟。

术语一般如何实现？如何使用？

- **GIC 版本**：GICv2（Cortex-A53/A7 常用）、GICv3（Cortex-A72/A76 常用，支持更多 CPU 核和 ITS/LPI）、GICv4（支持虚拟化直接中断注入）。TZ-LLM 使用的 RK3588 配备 GICv3 或 GICv2（论文未明确说明版本，但功能上均支持安全中断配置）。
- **编程接口**：GIC 通过 MMIO 寄存器编程（Distributor 基地址 + CPU Interface 基地址）。安全中断配置需在安全世界执行（非安全世界写入 GICD\_IGROUPR 安全区域会被忽略或触发异常）。

涉及论文标题：
- TZ-LLM

## Heterogeneous Memory for Client xLM Inference（客户端 xLM 推理的异构内存）

术语是什么？

Heterogeneous Memory（异构内存）在客户端 xLM 推理场景中指同一台机器上 GPU VRAM（高带宽、低容量）和 CPU sysRAM（低带宽、高容量）组成的双层内存系统，两者通过 PCIe 总线互联。客户端系统的典型特征是 PCIe 带宽远低于 GPU VRAM 带宽（PCIe Gen5 峰值 64 GB/s vs RTX 5090 VRAM ~1.5 TB/s，差距 20×+），且 GPU 显存被多个应用共享（游戏、创作工具等）。Pipelined Sharding 将异构内存视为核心设计约束：Planner 必须在给定的 VRAM budget 下决定哪些数据（权重、KV cache、中间激活）驻留在 VRAM、哪些在 sysRAM，以及何时通过 PCIe 传输。

从硬件架构角度拆解术语：

异构内存在客户端推理中的运转流程（以 nemo8b f16 在 cli3 上 4G VRAM 为例）：

1. **模型加载**：所有权重从磁盘加载到 sysRAM（64GB+ 容量充足）。部分权重（attention 层）pin 到 pinned memory 以支持 DMA 传输。
2. **Prefill 阶段**：prompt tokens 在 CPU 上完成 tokenization。根据当前 token tier 的 Static Plan，attention 权重 stream 到 GPU（PCIe H2D），GPU 执行 FlashAttention 产生 KV cache。KV cache 保留在 GPU VRAM。
3. **Decode 阶段**：每个 decode step，CPU 执行 FFN 层（权重在 sysRAM，利用 CPU 的大容量和 153.6 GBps 内存带宽），GPU 执行 attention 层（利用 32GB VRAM 中的 KV cache + attention 权重 scratch）。中间激活通过 PCIe 在 CPU↔GPU 间传输。
4. **KV Cache 增长**：随 context 从 1K 增长到 64K，KV cache 占用增长。当接近 VRAM budget 上限时，可能触发 plan 切换（如从 Static 切换到 Dynamic），将部分 KV cache 迁移到 sysRAM。

术语一般如何实现？如何使用？

客户端异构内存的核心挑战不是容量（sysRAM 通常 64–256 GB，远超模型大小），而是 PCIe 带宽瓶颈。论文中三台测试机的 PCIe 有效带宽分别为 13 GBps（cli1, Gen4）、50 GBps（cli2/3, Gen5），对应 weight transfer 延迟：nemo8b 全部 15.7GB 权重通过 cli1 PCIe 需 ~1.2 秒，而 cli3 仅需 ~0.3 秒。论文 Fig. 16 展示了 CPU 线程数和 PCIe 代际对 TPS 的交互影响：PCIe Gen4 系统更依赖 CPU 计算（避免 weight transfer），PCIe Gen5 系统可更多使用 GPU。

涉及论文标题：
- Efficient, VRAM-Constrained Cross-Lingual Model Inference on Client Devices

## PCIe Bandwidth Contention in Inference（推理中的 PCIe 带宽竞争）

术语是什么？

PCIe Bandwidth Contention（PCIe 带宽竞争）是指客户端推理场景中，CPU↔GPU 间的 PCIe 总线同时被多个数据流竞争使用：xLM 推理的 weight streaming 和中间激活传输、游戏/创作应用的纹理和几何数据传输、RTX Broadcast 等 AI 特效的视频流等。Pipelined Sharding 在 Profile 阶段显式在 PCIe contention 条件下 benchmark CPU kernel（即同时进行 CPU↔GPU memcpy 时测量 kernel 延迟），以获得 realistic 而非 ideal 的 PCIe 有效带宽。论文报告三台测试机的 PCIe 有效带宽均低于峰值（cli1: 13/16 GBps, cli2/cli3: 50/64 GBps）。

从硬件架构角度拆解术语：

PCIe contention 对推理性能的影响机制：

1. **Weight streaming stall**：当 GPU 正在执行 kernel 时需要下一层的权重，但 PCIe 被其他传输占用 → GPU compute unit stall。
2. **KV cache sync delay**：plan 切换时需同步 CPU/GPU 间 KV cache，若 PCIe 竞争则同步延迟增大 → TTFT/TPS 抖动。
3. **Multi-application interference**：游戏帧渲染期间的 PCIe 传输（纹理、geometry buffer）与 xLM 推理的 weight streaming 互相抢占 → 两者性能均下降（FPS + TPS 双降）。

术语一般如何实现？如何使用？

论文通过 Profile 阶段的 "PCIe contention profiling" 建模竞争影响：在 benchmark 时运行 background PCIe traffic generator（论文未详细说明实现），测量 kernel 在此条件下的 wall-clock 延迟。Planner 使用 contention-profiled timing（而非 ideal timing）估算 plan cost，使 schedule 在真实多应用场景下更鲁棒。论文未量化 contention profiling 的 accuracy 或与真实游戏场景的 fidelity。

涉及论文标题：
- Efficient, VRAM-Constrained Cross-Lingual Model Inference on Client Devices

## DVFS (Dynamic Voltage and Frequency Scaling)

术语是什么？

DVFS（动态电压与频率调节，Dynamic Voltage and Frequency Scaling）是移动 SoC 和现代处理器中的核心硬件级功耗管理技术。其基本原理是：处理器的工作功耗 $P \propto C \cdot V^2 \cdot f$（$C$ 为开关电容，$V$ 为供电电压，$f$ 为时钟频率）。更高的频率要求更高的电压来维持晶体管可靠翻转，而功耗与电压的平方成正比。DVFS 通过在运行时动态调节时钟频率和对应的供电电压，在满足性能需求的前提下最小化功耗。

DVFS 的控制粒度从粗到细分为三级：
1. **SoC 级**：整个 SoC 统一调频（早期方案，效率低）
2. **组件级**：CPU cluster、GPU、Memory controller 各自独立调频（当前移动 SoC 主流方案，如 Pixel 7 Tensor G2 的 CPU 18 级、GPU 12 级、Memory 13 级）
3. **核心级**：每个 CPU 核心独立调频（如 ARM DynamIQ 的 per-core DVFS）

DVFS 的频率选择由 DVFS governor（调度策略，运行在 OS 内核中）决定，而实际的电压/频率切换由硬件 PMIC（Power Management IC）和时钟管理单元（CMU）执行。Governor 写入目标频率到 sysfs 节点 → 内核 cpufreq 框架调用驱动 → 驱动配置 PLL（锁相环）分频比 + PMIC 电压 → 硬件在数十微秒内完成切换。

从硬件架构角度拆解术语：

DVFS 在移动 SoC 中的硬件运转流程（以 Google Tensor G2 为例的一次 LLM 推理 decode step）：

1. **工作负载监控**：CPU 上的 EAS (Energy-Aware Scheduling) governor 通过 PELT (Per-Entity Load Tracking) 跟踪每个 CPU 的 utilization（运行时间/总时间）。GPU 上的 quickstep governor 通过 GPU 硬件性能计数器监控 GPU busy percentage 和 memory bandwidth utilization。Memory governor 通过内存控制器（DMC）的带宽计数器监控 LPDDR5 读写吞吐。

2. **频率决策**：Governor 根据 utilization 和目标值（如 EAS target 80%）计算所需频率。例如当前 CPU util=45%，target=80% → 建议降频（因利用率低，说明当前频率过剩）。但 governor 各自独立决策，互不知晓对方状态。

3. **频率切换硬件路径**：
   - CPU：Governor 写入目标频率到 `/sys/devices/system/cpu/cpuN/cpufreq/scaling_setspeed` → Linux cpufreq driver 计算所需 PLL 分频比 → 配置 ARM CPU 的 PLL → 等待 PLL 锁定（~10-20 μs）→ 切换 CPU core clock source
   - GPU：Governor 写入目标频率到 `/sys/class/kgsl/kgsl-3d0/devfreq/max_freq` → kgsl (Kernel Graphics Support Layer) driver 配置 Mali GPU PLL → GPU clock domain 切换
   - Memory：Governor 写入 `/sys/class/devfreq/` 对应节点 → DMC driver 更新 LPDDR5 频率 → DRAM 自刷新 → 频率切换 → 退出自刷新（~1-5 μs overhead）

4. **DVFS 对 LLM 推理的影响**（CORE 论文的核心发现）：
   - Prefill 阶段（compute-bound）：大矩阵乘（$O(L^2 \cdot D)$ for attention, $O(L \cdot D^2)$ for FFN）需要高 GPU 频率以最大化吞吐——GPU 848 MHz 比 506 MHz 提供近线性加速（~1.7× compute throughput）
   - Decode 阶段（memory-bound）：每步仅 1 token，GPU 执行 memory-bound kernel（$O(L \cdot D)$ attention），高 GPU 频率不能提升吞吐（受制于 LPDDR5 51.2 GB/s 带宽），反而浪费能量——CORE 发现 506 MHz 是最优 decode GPU 频率
   - CPU 在 decode 阶段的 utilization 天然低（等待 GPU + 仅执行轻量 sampling），但过低的 CPU 频率（如 governor 降频至 800 MHz）会减慢 GPU 命令队列填充 → 拖慢 GPU → 形成"向下螺旋"

术语一般如何实现？如何使用？

移动 SoC DVFS 的使用方式（以 CORE 论文的 Pixel 7 + Tensor G2 为例）：

1. **频率列表查询**：
   ```bash
   # CPU 可用频率
   cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_frequencies
   # 输出: 500000 574000 648000 ... 2850000 (18 级)
   
   # GPU 可用频率
   cat /sys/class/kgsl/kgsl-3d0/devfreq/available_frequencies
   # 输出: 151000000 200000000 ... 848000000 (12 级)
   
   # Memory 可用频率
   cat /sys/class/devfreq/17000010.dmc/available_frequencies
   # 输出: 421000000 547000000 ... 3172000000 (13 级)
   ```

2. **当前 Governor 查询**：
   ```bash
   cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
   # 输出: schedutil (或 sched_pelt/performance/powersave)
   ```

3. **CORE 的手动频率钉扎**（绕过 governor）：
   ```bash
   # 钉扎 CPU 最高频率（prefill 阶段）
   echo 2100000 > /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq
   # 钉扎 GPU 频率
   echo 506000000 > /sys/class/kgsl/kgsl-3d0/devfreq/max_freq
   echo 506000000 > /sys/class/kgsl/kgsl-3d0/devfreq/min_freq  # 锁定
   ```

4. **DVFS 切换开销**：频率切换本身需 10-50 μs（PLL 重新锁定时间），对单次 decode step（~10-100 ms）可忽略，但对高频切换场景（如每 token 都切换）可能累积。CORE 仅在 prefill/decode 阶段切换时切换一次（每 request 2 次），开销 <0.01% 总延迟。

5. **关键设计考量**：
   - DVFS 的实质是时间换能量——低频 = 低功耗但长延迟。CORE 的核心贡献是找到 latency-energy Pareto 前沿上的最优点，而非单纯降频。
   - 移动 SoC 的 DVFS 比服务器更关键——电池供电 + 热约束（无主动散热）→ 频率选择直接影响续航和热 throttling。
   - 不同 SoC 的频率粒度和范围差异巨大——CORE 的 profiling 方法对每个模型+平台独立，保证可移植性。

## Qualcomm Hexagon NPU

术语解释
Qualcomm Hexagon NPU 是 Qualcomm Snapdragon SoC 中集成的专用 AI 加速器，采用"向量+矩阵"混合架构，通过 HVX（Hexagon Vector eXtension）向量单元处理通用计算、HMX（Hexagon Matrix eXtension）矩阵单元加速 GEMM/卷积，并配备软件管理的 TCM（Tightly Coupled Memory）片上内存。Hexagon NPU 是移动端 LLM 推理的核心硬件平台，其设计要点包括：VLIW 架构减少控制逻辑开销、SIMD 执行模型（非 GPU 的 SIMT）、以及通过 DMA 引擎实现 DDR↔TCM 异步数据传输。各代架构从 V73（Snapdragon 8 Gen 2）演进至 V79（Snapdragon 8 Elite），算力从 ~12 TFLOPS FP16 持续提升。

术语是什么？
Hexagon NPU 是 Qualcomm 针对移动和边缘 AI 推理设计的专用神经网络处理器。其核心架构特征：
- **异构三指令集**：Scalar（控制流）、HVX（向量 SIMD）、HMX（矩阵乘加）
- **VLIW 执行**：每条指令包可包含多个操作，减少硬件控制开销
- **软件管理内存层次**：L2 Cache (1 MiB) + TCM (8 MiB)，TCM 由软件显式分配和管理
- **DMA 引擎**：支持 1D/2D 异步数据传输（DDR↔L2↔TCM），读取带宽 >60 GB/s
- **精度支持**：INT4/INT8/INT16/FP16

## HMX (Hexagon Matrix eXtension)

术语是什么？
HMX 是 Qualcomm Hexagon NPU 中的专用矩阵乘法加速单元，提供极高的低精度 GEMM 吞吐量（FP16 ~12 TFLOPS，远超 HVX 的 ~33 GFLOPS/thread）。HMX 的基本数据单元是 tile（矩阵块）：FP16 下为 32×32（2 KiB），支持 INT4/INT8/INT16/FP16 精度。HMX 从 TCM 加载 weight tile 和 activation tile，执行矩阵乘法后将结果累积到内部累加器（FP32 精度），最后输出累加器对应的 tile。HMX 还支持 per-channel scale 和 bias（256-byte bias region）。

从硬件架构角度拆解术语：
HMX 的 tile 级 GEMM 执行流程（FP16, M×K×N）：

```
输入: Activation [M, K], Weight [K, N] (已在 TCM 中，HMX tile layout)
输出: Output [M, N]

hmx_gemm_tiled:
  for m_tile in range(0, M, 32):         # 外层级 row tiles
    for n_tile in range(0, N, 32):       # 外层级 col tiles
      acc = zero_tile(32, 32)             # HMX internal FP32 accum
      
      for k_tile in range(0, K, 32):     # 内层级 reduction
        # 同一指令包中 paired load:
        act_tile = mxmem_load(act_addr)   # [32, 32] FP16 from TCM
        wt_tile  = mxmem_load(wt_addr)    # [32, 32] FP16 from TCM
        acc += act_tile @ wt_tile         # FP32 accum
        
      # 可选的 per-channel scale & bias:
      acc = acc * scale[n_tile] + bias[n_tile]  # 256B bias region
      
      # Consume accumulator:
      out_tile = cvt.hf = acc              # FP32 → FP16
      mxmem_store(out_addr, out_tile)     # write [32,32] to TCM
```

FP16 HMX Tile 内存布局（"FP16 Crouton Layout"）：
- 每 tile 为 32×32 矩阵，占 2048 bytes
- 每两行 permuted（交错）：layout 等同于 transposed 2×32 sub-matrix
- 外层级 weight tiles 以 column-major 排列（硬件在 tile 级做 inner product）

术语一般如何实现？如何使用？
- HMX 编程需要 Hexagon SDK 的 LLVM 工具链 + inline assembly。QNN 通过闭源库间接使用 HMX。
- 论文通过逆向工程 QNN 二进制库中的 `mxmem`、`cvt.hf = acc()`、`bias = mxmem2()` 等未公开指令实现自定义 HMX kernel。
- 关键约束：HMX 指令仅能访问 TCM（不能访问 L2 Cache 或 DDR）。HVX scatter/gather 也仅能访问 TCM。因此 TCM 管理是 HMX kernel 设计的核心挑战。
- HMX 的 tile 级 inner product 机制意味着权重外层级必须按 column-major tile 顺序排列，否则 GEMM 结果错误。

## HVX (Hexagon Vector eXtension)

术语是什么？
HVX 是 Qualcomm Hexagon NPU 中的通用向量处理单元，负责执行非矩阵乘法类的 SIMD 计算（如激活函数、LayerNorm、Softmax、反量化等）。HVX 拥有 32 个 1024-bit（128-byte）向量寄存器，每周期可发射 4 个计算操作 + 1 个 load + 1 个 store。HVX 支持 INT8/16/32 和 FP16/32（包括特殊的 qfloat 内部格式），提供 vgather（向量 gather）、vlut16（16-entry 查表）、scatter 等高级 SIMD 指令。单个 HVX thread 的 FP16 GEMM 吞吐量仅 ~33 GFLOPS，远低于 HMX 的 ~12 TFLOPS。

从硬件架构角度拆解术语：
HVX 在 LLM 推理中的典型使用模式：

```
HVX 指令类别及其在 LLM kernel 中的使用:

1. 算术指令:
   - vadd/vsub/vmpy: 逐元素加减乘 (LayerNorm, residual add, RoPE)
   - vmax/vmin: 逐元素最值 (Softmax rowmax, ReLU)
   - vshuff: 跨 lane 数据重排 (HMX tile layout 转换)

2. 查表指令:
   - vlut16: 16-entry LUT，将每字节索引 → 16-bit 值
     (反量化: INT4 index → FP16 weight value)
   - vgather: 从 TCM 不连续地址 gather 元素
     (Softmax LUT: FP16 input → FP16 exp value)

3. 访存指令:
   - vmem: 连续地址 load/store (L2 Cache 或 TCM)
   - vscatter/vgather: 仅 TCM (TCM 的非关联访问特性)

4. 特殊指令:
   - vand/vor: 位掩码操作 (INT4 unpack)
   - vsat: 饱和运算 (量化 clipping)
```

HVX 的关键硬件约束：
- HVX scatter/gather **仅能访问 TCM**（不能访问 L2 Cache），因为 TCM 的非关联访问模式保证了 scatter/gather 的性能确定性。
- HVX FP16 操作产生 **qfloat 内部格式**（非标准 IEEE-754），需额外指令转换回标准格式传输给 HMX。论文的 LUT 反量化方案通过 vlut16 预先输出 qfloat 格式值，避免了转换开销。
- HVX 的 128-byte 向量宽度意味着处理小于 128-byte 的数据粒度（如 32 元素的量化组仅有 16 bytes INT4）会导致寄存器利用率低下。论文通过 super-group coalesce（合并 8 个组 → 256 元素 = 128 bytes）解决此问题。

术语一般如何实现？如何使用？
- HVX 编程使用 Hexagon LLVM C/C++ intrinsic 或 inline assembly。Intrinsic 命名规则：`Q6_<type>_<operation>_<suffix>`。
- 关键实现细节：(1) vlut16 的 LUT table 本身需在寄存器中（而非 TCM），每指令查表 16 个条目；(2) vgather 延迟高达 24-48 个指令包（V75），需谨慎使用——论文仅在 Softmax 中使用 vgather，且限制 LUT 为 32768 条目（64 KiB）。
- 常见优化模式：DMA prefetch 将数据从 DDR 搬到 TCM → HVX 计算（从 TCM load） → HVX store 结果到 TCM → DMA writeback 到 DDR。所有中间数据保持在 TCM 中，最小化 DDR 往返。

- Scaling LLM Test-Time Compute with Mobile NPU on Smartphones

## TCM (Tightly Coupled Memory) on NPU

术语是什么？
TCM（紧耦合内存）是 Hexagon NPU 中 8 MiB 的软件管理片上 scratchpad 内存，与 L2 Cache（1 MiB）分开管理。TCM 不经过硬件 cache 一致性协议——其分配、使用和释放完全由软件控制。TCM 是 HMX 矩阵单元和 HVX scatter/gather 操作**唯一可访问的片上内存**（HMX 不能访问 L2 Cache），因此是 NPU kernel 设计的核心约束和优化目标。DMA 引擎负责在 DDR 和 TCM 之间以异步方式搬运数据（支持 1D/2D 张量传输），读取带宽 >60 GB/s（远超 HVX 的 ~26 GB/s）。

从硬件架构角度拆解术语：
TCM 在 LLM 推理一次 GEMM 中的生命周期管理：

```
TCM 地址空间分区（一次 Dequantization GEMM kernel）:

TCM Total: 8 MiB (8192 KiB)
├── Input Activations (DMA from DDR):   ~32 KiB  (FP16, batch×hidden_dim tile)
├── INT4 Weights (DMA from DDR):        ~512 KiB (per weight tile)
├── Dequantized FP16 Weights (HVX write): ~2 MiB (intermediate buffer)
├── LUT Tables (常驻):                   ~64 KiB  (exp LUT for Softmax)
│   └── Dequantization LUT:             ~128 B   (16-entry × 2B, in HVX reg)
├── Output Activations (HMX write):     ~32 KiB  (FP16 results)
└── Scratch/Other:                      剩余空间

DMA 异步传输模型:
  DMA Channel 0: DDR → TCM (prefetch next weight tile)
  DMA Channel 1: DDR → TCM (prefetch next activation tile)
  (HVX + HMX 在当前 tile 上计算)
  DMA Channel 2: TCM → DDR (writeback completed output tile)

关键管理策略:
- Double Buffering: 两组 weight buffer 交替使用
- Prefetch: 在当前 tile 计算时 DMA 预取下一 tile
- 驻留决策: LUT tables 常驻 TCM（64 KiB, 仅 0.8% 容量）
- Tile 粒度分配: 以 HMX tile (32×32) 为最小分配单元
```

术语一般如何实现？如何使用？
- TCM 通过 Hexagon SDK 的 `ion_alloc` / `rpcmem_alloc` 从 TCM 池中分配。论文中由 htp-ops-lib 管理 TCM 分配策略。
- 关键约束：(1) TCM 总容量仅 8 MiB，大型 weight tile 可能超限——需 tiling 策略；(2) HMX 和 HVX scatter/gather 仅能访问 TCM——若数据在 L2 或 DDR，需先 DMA 搬运到 TCM；(3) TCM 不参与 cache coherence——CPU 和 NPU 间的 TCM 数据同步需显式 flush/invalidate。
- 与 GPU Shared Memory 对比：GPU SM 的 shared memory 由 thread block 内的线程共享，由硬件调度器在 warps 间切换隐藏延迟。TCM 由**单个 NPU thread** 独占且软件显式管理——无硬件调度器、无自动 cache 替换。

涉及论文标题：
- Scaling LLM Test-Time Compute with Mobile NPU on Smartphones

关键硬件架构观察（CORE 论文的发现）：
1. **Unified Memory 的双刃剑**：无需显式的 CPU↔GPU 数据传输（vs NVIDIA 的 PCIe），但 CPU/GPU 竞争同一 LPDDR5 带宽。Decode 阶段 GPU memory-bound kernel 和 CPU sampling 同时访问 LPDDR5 → 带宽竞争。
2. **DVFS 频率粒度的硬件限制**：CPU 18 级、GPU 12 级、Memory 13 级 → 总组合 2808 种。但实际有意义的组合远少于此（许多组合或等价或不可行），CORE 的两阶段搜索利用了这一特性。
3. **Thermal Throttling 的隐性影响**：Tensor G2 的 5nm 工艺 + 无主动散热 → 长时间推理必然触发 thermal throttling（降频）。CORE 论文未讨论 thermal 影响，可能通过"短 prompt + 短 decode"（≤512+256 tokens）规避。
4. **EdgeTPU 的缺席**：尽管 Tensor G2 有专用 AI 加速器（EdgeTPU），CORE 未使用——因 llama.cpp 不支持 EdgeTPU backend，且 INT4 量化 LLM 推理在可编程 GPU 上比在固定功能 TPU 上更灵活。

对于 LLM 推理研究，Tensor G2/Pixel 7 的使用场景：

1. **开发环境搭建**：
   - Root Pixel 7/7 Pro（解锁 bootloader + Magisk root）以获取 sysfs DVFS 控制权限
   - 电池旁路 + Monsoon Power Monitor（细粒度功耗测量）
   - 禁用 thermal daemon（避免 benchmark 期间 throttling）——生产环境不可行
   - 交叉编译 llama.cpp（aarch64-linux-android NDK）或使用 Termux 环境

2. **关键 sysfs 路径**：
   ```bash
   # CPU 频率控制
   /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_frequencies
   /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq
   /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
   
   # GPU 频率控制
   /sys/class/kgsl/kgsl-3d0/devfreq/available_frequencies
   /sys/class/kgsl/kgsl-3d0/devfreq/max_freq
   /sys/class/kgsl/kgsl-3d0/gpuclk  # 当前 GPU 频率
   
   # Memory 频率控制
   /sys/class/devfreq/17000010.dmc/available_frequencies
   /sys/class/devfreq/17000010.dmc/min_freq
   ```

3. **Tensor G2 的 LLM 推理能力**：
   - TinyLlama 1.1B Q4: ~15-20 tokens/s decode on GPU (OpenCL)
   - Llama-2 7B Q4: ~2-4 tokens/s decode (内存带宽瓶颈)
   - 持续推理受 thermal throttling 限制（5-10 分钟后降频）
   - CORE 优化后 TPOT 改善 27.8-39.6%，使 1.1B 模型体验从"可感知延迟"进入"流畅交互"

4. **与其他移动 SoC 的对比**：
   | SoC | CPU | GPU | Memory BW | DVFS 粒度 |
   |-----|-----|-----|-----------|----------|
   | Tensor G2 (5nm) | X1+A78+A55 | Mali-G710 MP7 | 51.2 GB/s | 18+12+13 |
   | A16 Bionic (4nm) | Everest+Sawtooth | Apple 5-core | 51.2 GB/s | per-core DVFS |
   | Snapdragon 8 Gen 2 | X3+A715+A710 | Adreno 740 | 64 GB/s | 20+15+15 |
   | Tensor G4 (4nm) | X4+A720+A520 | Mali-G715 MP7 | 64 GB/s | 类 G2 |

5. **限制**：
   - Android 非 root 无法访问 `/sys/class/kgsl/` 和 `/sys/class/devfreq/`（GPU/Memory DVFS 控制）
   - OpenCL 后端性能弱于 Vulkan/Metal → CORE 的绝对延迟数字偏高
   - 无独立 VRAM → LLM 推理与系统内存（Android OS + Apps）竞争有限的 LPDDR5 带宽
