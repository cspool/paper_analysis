## Monolithic Forwarding

术语是什么？
Monolithic Forwarding（单一化前向）是 PRISM 论文提出的一种针对 cross-encoder reranker 的新推理范式。传统系统将 N 个候选文档分别作为独立 batch 逐一前向计算（每次 `model(query + candidate_i)`），而 Monolithic Forwarding 将所有 N 个候选文档合并为一个统一的 batch 同时前向（一次性 `model([query+candidate_1, ..., query+candidate_N])`），在整个计算过程中保持对所有候选的全局视图（global view）。这种范式转换解锁了两个关键机会：(1) 基于层间相对排名的动态候选剪枝（progressive cluster pruning），(2) 通过大 batch 创建的充足计算窗口完全重叠 I/O 延迟（overlapped layer streaming）。

从系统架构角度拆解：
Monolithic Forwarding 在整个推理系统中的运转流程：

```
传统方式（Isolated Batching）：
  for each candidate d_i:
      scores[i] = model(q + d_i)  # 独立前向，N 次
  top_k = argsort(scores)[:K]

  ┌─────┐  ┌─────┐       ┌─────┐
  │d_1  │  │d_2  │  ...  │d_N  │  ← 独立 batch，各自完整前向
  │28层 │  │28层 │       │28层 │
  │score│  │score│       │score│
  └─────┘  └─────┘       └─────┘
  延迟: N × T_single_pass
  中间张量峰值: batch_size=1 × L × D（每候选独立）

Monolithic Forwarding（PRISM）：
  scores = model_monolithic([q+d_1, ..., q+d_N])  # 一次前向，N 候选合并
  每层可剪枝不需要的候选

  ┌──────────────────────────────┐
  │  d_1, d_2, ..., d_N (合并)    │
  │  Layer 0 → pruning check →   │  ← 部分候选被剪枝
  │  Layer 1 → pruning check →   │
  │  ...                          │
  │  Layer 27 → final top-K      │
  └──────────────────────────────┘
  延迟: 渐进递减（早期剪枝 → 减少后续计算）
  中间张量峰值: chunk_size × L × D（chunked execution 控制）
  权重内存: 2 layers（overlapped layer streaming）
```

关键设计权衡：
- **优势**：全局视图 → 动态剪枝；大计算窗口 → I/O 完全重叠
- **挑战**：中间张量爆炸（N × L × D → chunked execution 解决）；hidden states 累积（dynamic offloading 解决）

术语一般如何实现？如何使用？
- PRISM 实现：基于 HuggingFace Transformers + Accelerate。将 `batch_size` 从 1 扩展到 N，输入 shape 从 `[1, L]` 变为 `[N, L]`
- Chunked Execution 配合：在每层内部将 `[N, L]` 拆分为 chunks of `[C, L]` 顺序执行，保持 I/O 重叠的同时限制内存
- 适用条件：适用于所有候选需同时比较的场景（top-K selection, ranking, reranking），不适用于候选独立处理的场景
- 局限性：当候选数 N 极大（如 >100）时，即使 chunked execution 也会因 hidden states 累积导致内存压力

涉及论文标题：
- On-device Semantic Selection Made Low Latency and Memory Efficient with Monolithic Forwarding

## Overlapped Layer Streaming

术语是什么？
Overlapped Layer Streaming（重叠式逐层流式加载）是 PRISM 系统中用于降低模型权重内存占用的技术。核心思想：将 Transformer 模型权重按层从 SSD 流式加载到内存，始终仅保持**两层**权重在内存中（当前计算层 + 下一预取层），利用当前层的计算时间异步 prefetch 下一层权重，实现 I/O 与计算的完全重叠。与 HF Accelerate 的 disk offloading（加载整个模型→计算→卸载，串行）不同，Overlapped Layer Streaming 通过 monolithic forwarding 创建的大计算窗口（prefill-only, compute-heavy per layer）完全隐藏 I/O 延迟。

从系统架构角度拆解：
Overlapped Layer Streaming 的双进程架构与执行流程：

```
架构组件：
  Computation Process (绕过 GIL):    I/O Process (Libuv 异步 I/O):
  ┌──────────────────────┐           ┌──────────────────────┐
  │ PyTorch Model        │           │ Libuv Event Loop     │
  │ Layer i (buffer_A)   │◄──────────│ fs_read(layer_i+2)   │
  │ CUDA/MPS Stream      │  shared   │ → buffer recycler    │
  │ chunked execution    │  memory   │ SSD bandwidth sat.   │
  └──────────────────────┘           └──────────────────────┘

时间线（以 layer 9→10→11 为例）：

Time  Computation Process          I/O Process               Memory
────────────────────────────────────────────────────────────────────
 t0   Forward Layer 9             Prefetch Layer 10 from    buffer_A: L9
      (chunked execution)          SSD → buffer_B           buffer_B: L10
                                                            其他: free

 t1   Layer 9 done                 Layer 10 ready
      Release buffer_A (L9)        Start prefetch L11       
      Swap: buffer_A ← buffer_B    → buffer_A (recycled)    buffer_A: L10
                                                             buffer_B: L11

 t2   Forward Layer 10             Prefetch Layer 12        buffer_A: L10
      (chunked execution)          → buffer_B (recycled)    buffer_B: L12

 t3   Layer 10 done                ...                      循环往复
      Release buffer_A (L10)
      Swap: buffer_A ← buffer_B
      ...
```

关键前提（为什么可以完全重叠）：
- Reranker 是 prefill-only workload → 每层计算量大（$O(L^2 \cdot D + L \cdot D^2)$ per layer）
- Monolithic batch 进一步增大计算窗口
- SSD 带宽（PCIe 4.0 ~7 GB/s）远低于 GPU 内存带宽 → 每层权重读取时间 << 每层计算时间

术语一般如何实现？如何使用？
- 实现栈：Python multiprocessing（computation + I/O 两进程）+ shared memory buffer（PyTorch `torch.multiprocessing`）+ Libuv 异步 I/O + CUDA MPS（GPU 共享）
- Buffer 管理：两个固定大小的 pre-allocated memory buffer，通过 swap 循环使用，无动态内存分配
- 权重粒度：per-layer weight files（预分割存储），而非整个模型单文件 → 支持细粒度 streaming
- 适用场景：模型权重大于可用内存（如 8B 模型 > VRAM budget），SSD 带宽足够支持实时 streaming
- 局限性：需要 SSD 随机读取性能好（HDD 场景不适用）；pruning 后计算窗口缩小可能导致 I/O 无法完全隐藏（ablation 中增加 81ms）

涉及论文标题：
- On-device Semantic Selection Made Low Latency and Memory Efficient with Monolithic Forwarding

## Chunked Execution

术语是什么？
Chunked Execution（分块执行）是 PRISM 中解决 monolithic forwarding 带来的中间张量内存爆炸问题的技术。将 N 个候选文档的 monolithic batch 拆分为多个较小的 chunks（每个 chunk 含 C 个候选），在每层内**顺序执行**各 chunk 的前向传播，仅保留当前 chunk 的中间张量（Q/K/V/proj、attention scores、FFN activations）在内存中。chunk size C 的下界由 I/O 重叠需求决定（chunk 的计算时间需 ≥ 下一层权重的 SSD 读取时间），上界由可用内存决定。

从系统架构角度拆解：
Chunked Execution 的执行流程与内存管理：

```
配置: N=20 candidates, chunk_size=2, num_layers=28

Layer i 的执行:
  hidden_states_all = [h_1, h_2, ..., h_20]  # 所有候选的 hidden states（在 CPU/GPU）

  FOR chunk_j IN range(0, 20, 2):           # 10 chunks
      # 1. 加载当前 chunk 的 hidden states
      h_chunk = hidden_states_all[chunk_j : chunk_j+2]  # [2, L, D]

      # 2. 执行 layer i 前向（仅当前 chunk）
      h_chunk = SelfAttention(h_chunk)       # Q/K/V: [2, L, D_head]
      h_chunk = FFN(h_chunk)                  # 中间张量仅 [2, L, D_intermediate]
      h_chunk = LayerNorm(h_chunk + residual)

      # 3. 存储结果
      hidden_states_all[chunk_j : chunk_j+2] = h_chunk
      # 释放当前 chunk 的中间张量（Q/K/V/attn/FFN_act）

  # Layer i 完成，仅 hidden_states_all [20, L, D] 保留

内存使用对比:
  Without Chunked Execution:
      中间张量峰值 = N × L × D × (Q+K+V+attn+FFN) ≈ 20 × 500 × 1024 × 6 × 4B ≈ 246 MB/layer
  With Chunked Execution (C=2):
      中间张量峰值 = C × L × D × (Q+K+V+attn+FFN) ≈ 2 × 500 × 1024 × 6 × 4B ≈ 25 MB/layer
  减少: ~10×
```

Dynamic Hidden States Offloading（扩展）：
```
当候选数 N 极大时，hidden_states_all [N, L, D] 本身成为瓶颈:
  - 当前 chunk 计算时
  - 并发 offload 上一 chunk 的 hidden states → SSD/CPU
  - 并发 prefetch 下一 chunk 的 hidden states ← SSD/CPU
  - 最多 3 chunks 的 hidden states 同时在内存
```

术语一般如何实现？如何使用？
- chunk_size 的动态计算：
  ```
  min_chunk_for_gpu = GPU_FLOPS / (L × D × ops_per_element)
  min_chunk_for_io = SSD_BW × layer_compute_time / weight_size_per_layer
  chunk_size = max(min_chunk_for_gpu, min_chunk_for_io)
  chunk_size = min(chunk_size, memory_budget / (L × D × element_size))
  ```
- 与 overlapped layer streaming 的协同：chunk 的累计计算时间必须 ≥ 下一层权重的 SSD 读取时间，以保证 I/O 重叠不破裂
- 与 progressive cluster pruning 的协同：剪枝后候选数减少 → chunk 数自动减少 → 总计算量下降
- 类似技术：PrefillOnly (SOSP '25) 也提出 chunking batches 降低中间张量，但 PRISM 额外增加了 dynamic hidden states offloading

涉及论文标题：
- On-device Semantic Selection Made Low Latency and Memory Efficient with Monolithic Forwarding

## Embedding Table Caching

术语是什么？
Embedding Table Caching（嵌入表缓存）是 PRISM 中针对 embedding layer 内存占用的优化技术。在应用 overlapped layer streaming 后，Transformer 层的权重内存已降至仅两层（~30 MB × 2 for 0.6B model），但 embedding table 仍占据 296 MB（vocab=151,669, dim=1024, FP16），成为新的主要内存瓶颈。Embedding Table Caching 利用 token 使用的极端稀疏性——典型 reranking 任务（20 文档 × 512 tokens）最多使用 10,240 个 unique tokens（vocab 的 6.75%）——通过小型 LRU cache（默认 10% vocab size）仅缓存活跃 token 的 embedding 行，其余按需从 SSD 同步读取。

从系统架构角度拆解：
Embedding Table Caching 的运转流程：

```
初始化:
  cache = LRUCache(max_size = vocab_size × 10% = 151,670 × 0.1 ≈ 15,167 rows)
  # 每个 cache entry: (token_id, embedding_vector [D])，D=1024 for 0.6B

推理时（每个 request）:
  1. Tokenization: input_ids = tokenizer(query + candidates)  # [N, L]

  2. 收集 unique tokens:
     unique_ids = set(input_ids.flatten())  # ≤ 10,240 (6.75% vocab)

  3. Embedding Lookup with Caching:
     embeddings = []
     cache_misses = []

     for token_id in unique_ids:
         if token_id in cache:
             embeddings[token_id] = cache[token_id]  # 命中，零延迟
         else:
             cache_misses.append(token_id)           # 未命中，记录

     # 4. 同步读取 cache misses（libuv 异步 I/O）
     for token_id in cache_misses:
         # 从 SSD 读取 embedding 行
         row = read_from_disk(embedding_file, offset=token_id × D × 2B)
         # 大小: D × 2 bytes (FP16) = 1024 × 2 = 2KB per row

         # 插入 cache（可能触发 LRU eviction）
         if cache.is_full():
             evicted_id = cache.evict_lru()
         cache[token_id] = row
         embeddings[token_id] = row

  5. 构建 embedding 输出:
     output = gather(embeddings, input_ids)  # [N, L, D]
```

内存节省计算：
```
完整 Embedding Table: 151,669 × 1024 × 2B (FP16) = 296 MB
10% LRU Cache:         15,167  × 1024 × 2B           = 30 MB
节省: 266 MB (90%)

对于 Qwen3-Reranker-0.6B:
  After Overlapped Layer Streaming: 2 layers × 30 MB = 60 MB (transformer)
  Embedding (full): 296 MB → 83% of total!
  Embedding (cached): 30 MB → 总内存 = 60 + 30 = 90 MB
```

术语一般如何实现？如何使用？
- Cache 策略：LRU（Least Recently Used），基于 token 使用的 Zipf 分布（高频 token 反复使用 → 高命中率）
- 命中率：论文未明确给出，但从 token 稀疏性（6.75% usage）和自然语言 Zipf 分布推断，10% cache 的命中率应 >95%
- Cache miss 延迟：每个 miss token 需同步读取 2KB（FP16 embedding row），SSD 随机读取延迟 ~100μs → 即使 1000 misses 也仅 ~100ms，且大部分 token 命中 cache
- 使用约束：适用于 token 使用稀疏的场景（reranking 的 short documents），不适用于 token 使用密集的场景（长文档 generation）
- 在 PRISM ablation 中的贡献：消除最后的内存瓶颈，额外延迟仅 4ms

涉及论文标题：
- On-device Semantic Selection Made Low Latency and Memory Efficient with Monolithic Forwarding

## Prefill-Only Workload

术语是什么？
Prefill-Only Workload（仅预填充工作负载）是指仅执行 Transformer 的 prompt prefill 阶段（一次性并行处理所有输入 token 产生 hidden states 和 KV cache），而不执行自回归 decode 阶段（逐 token 生成）的推理工作负载。Cross-encoder reranker 是典型的 prefill-only workload：它接收 query-candidate pair，一次性前向通过所有 Transformer 层，在最后一层输出一个标量 relevance score，无需生成任何 token。这种工作负载的特性是：compute-bound（每层计算量大，$O(L^2 \cdot D + L \cdot D^2)$）而非 memory-bound（无 KV cache 增长，无 token-by-token 迭代）。

从系统架构角度拆解：
Prefill-Only vs Decode-Centric 的系统行为对比：

```
Prefill-Only (Reranker):
  输入: [N, L] tokens（一次）
  计算: N × 每层的 (self-attn [L×L] + FFN)  ← compute-heavy
  内存: 模型权重 + 中间张量（瞬态）           ← 无 KV cache 持续增长
  输出: [N] 个 scores
  特性:
    - 每层计算时间 >> 权重加载时间 → 可重叠 I/O
    - 无 KV cache → 内存压力来自中间张量和模型权重
    - 延迟 ∝ N × L（候选数 × 层数）

Decode-Centric (LLM Generation):
  输入: [1, 1] token（每次 decode step）
  计算: 1 × 每层的 (self-attn [1×L_kv] + FFN) ← memory-bound per step
  内存: 模型权重 + 持续增长的 KV cache（→L_kv 随 context 增长）
  输出: [1, vocab_size] logits → 采样 → 1 new token
  特性:
    - 每步计算量小 → memory-bound（受内存带宽限制）
    - KV cache 持续增长 → 内存管理是核心挑战
    - 延迟 ∝ num_tokens × decode_time_per_token
```

Prefill-Only 对 PRISM 设计的影响：
- **Overlap Window**：prefill-only 的每层计算时间长 → 足以隐藏 SSD 权重加载延迟 → overlapped layer streaming 零延迟开销
- **无 KV Cache**：无需像 vLLM 那样管理 KV cache 的分配/逐出/共享 → 内存优化聚焦于模型权重和中间张量
- **Compute-bound**：在边缘设备上 compute 是瓶颈（非 memory bandwidth）→ monolithic batch 增加的计算量与剪枝节省的计算量之间需权衡

术语一般如何实现？如何使用？
- 识别 prefill-only workload：检查模型的 generate() 调用——如果 max_new_tokens=1 或仅调用 forward() 获取 hidden states/logits，则为 prefill-only
- 优化策略（不同于 decode-centric）：(1) 增大 batch（无 KV cache 累积问题），(2) I/O-compute overlap（计算窗口大），(3) 剪枝/branching（无后续 token 依赖）
- 相关工作：PrefillOnly (SOSP '25) 提出了针对 prefill-only 工作负载的专用推理引擎，PRISM 在此基础上针对 reranker 做了专门的 memory 和 latency 协同优化
- 非 prefill-only 的 cross-encoder 使用：如 LLM-as-reranker（让 LLM 生成 "Yes/No" 判断相关性），此时 decode phase 极小（1-2 tokens）但仍存在，PRISM 的优化同样适用

涉及论文标题：
- On-device Semantic Selection Made Low Latency and Memory Efficient with Monolithic Forwarding

## Federated Learning (FL)

术语是什么？
Federated Learning（联邦学习）是一种分布式机器学习范式，多个参与者（participants/clients）在中央服务器协调下协作训练全局模型，而无需共享原始数据。核心原则：数据不出本地，仅交换模型更新（梯度或参数差）。典型流程：Server 下发全局模型 → 各 participant 用本地数据训练 → 上传模型更新 → Server 聚合（如 FedAvg 加权平均）→ 下一轮。

从系统架构角度拆解：
FL 系统的典型架构与一轮训练流程（parameter-server 架构）：
```
Server                                    Participant i (i=1..N)
  |                                           |
  |--- broadcast w^r ----------------------->|   (下发全局模型)
  |                                           |
  |                                    LocalTrain(w^r, D_i):
  |                                      for batch in D_i:
  |                                        forward → loss → backward
  |                                        w_i = w_i - lr * grad
  |                                      Δw_i = w_i - w^r
  |                                           |
  |<--- upload Δw_i -------------------------|   (上传模型更新)
  |                                           |
  | Aggregate: w^{r+1} = Σ (|D_i|/Σ|D_j|) * (w^r + Δw_i)
  |                                           |
  (下一轮)
```
关键系统设计考量：
- **Participant Selection**：每轮选哪些 participant 参与（如 Oort 基于 utility 选择）
- **通信效率**：gradient compression、quantization、sparsification 减少上传量
- **异构性处理**：participant 计算/通信能力不同（FLUX 通过 $B_i^{tune}$ 约束处理）
- **隐私保护**：Differential Privacy（梯度加噪）、Homomorphic Encryption（加密聚合）
- **Non-IID 数据**：各 participant 数据分布不同，影响收敛——FLUX 的 expert utility 定义考虑了数据分布

术语一般如何实现？如何使用？
- 主流框架：NVIDIA FLARE、Flower（FlowerTune）、FedAdapter、FedML、TensorFlow Federated
- FLUX 使用 parameter-server 架构 + PyTorch，FedAvg 聚合策略
- FLUX 的 FL 特定设计：(1) 仅上传 tuning expert 的更新（非全部参数）；(2) non-tuning experts 本地合并不上传；(3) profiling 与 aggregation 并行（stale profiling）
- 使用场景：隐私敏感数据训练（医疗、金融）、边缘设备协作训练、跨组织数据协作

涉及论文标题：
- Federated Fine-Tuning of Sparsely-Activated Large Language Models on Resource-Constrained Devices

## FedAvg (Federated Averaging)

术语是什么？
FedAvg（Federated Averaging，联邦平均）是联邦学习中最基础的模型聚合算法。Server 收集各 participant 在本地数据上训练的模型更新，按各 participant 的数据量加权平均，生成新的全局模型。公式：$w^{r+1} = \sum_{i \in S_r} \frac{|D_i|}{\sum_{j \in S_r} |D_j|} w_i^r$，其中 $S_r$ 为第 r 轮参与训练的 participant 集合，$|D_i|$ 为 participant i 的本地数据量。

从系统架构角度拆解：
FedAvg 在 FLUX 中的具体应用：
```
Server-side（每轮 aggregation）:
  collected_updates = {}
  for each participant i in selected_set:
      receive Δw_i^{exp}  （仅 tuning experts 的更新）
      collected_updates[i] = (Δw_i^{exp}, |D_i|)

  total_data = Σ |D_i|
  for each expert e in tuning_experts:
      w_e^{r+1} = Σ_i (|D_i|/total_data) * (w_e^r + Δw_{i,e})
      // 加权平均：数据量大的 participant 权重更大

  for each expert e NOT in tuning_experts:
      w_e^{r+1} = w_e^r  // non-tuning experts 不更新
```

FLUX 对 FedAvg 的适配：
- **仅聚合 tuning experts**：non-tuning experts（merged or exploration）不上传也不聚合
- **expert 粒度聚合**：不同 participant 可能 fine-tune 不同 expert 子集——FedAvg 按 expert 独立聚合
- **异步聚合**：stale profiling 利用 aggregation 等待时间，隐藏 profiling 开销

术语一般如何实现？如何使用？
- 标准实现：`global_model = Σ (weight_i * local_model_i)`
- 变体：FedProx（加 proximal term 处理 heterogeneity）、FedNova（归一化更新步数）、SCAFFOLD（control variate 减少 drift）
- FLUX 使用 vanilla FedAvg 进行 expert 参数聚合
- 关键参数：每轮 participant 数量（FLUX 设为 20）、local training iterations（FLUX 设为 1）

涉及论文标题：
- Federated Fine-Tuning of Sparsely-Activated Large Language Models on Resource-Constrained Devices

## Parameter Server Architecture

术语是什么？
Parameter Server（参数服务器）架构是一种分布式机器学习系统架构，由中心化的 parameter server(s) 和分布式的 worker/participant 节点组成。Server 负责存储和维护全局模型参数，workers 负责在本地数据上 compute gradients，server 和 workers 之间通过 push/pull 通信交换参数和梯度。相比 all-reduce 架构，parameter-server 更适合异构环境和跨机构协作（如联邦学习）。

从系统架构角度拆解：
FLUX 的 Parameter Server 实现：
```
Component         Role
──────────────────────────────────────────────────
Parameter Server  - 存储全局 MoE 模型（所有 experts）
                  - 运行 Expert Role Assignment 算法
                  - 求解优化问题（公式4）
                  - 执行 FedAvg aggregation
                  - 分发 tuning/exploration expert 分配

Participant i     - 本地数据存储（不共享）
                  - Quantization-based Profiling
                  - Non-tuning Expert Merging
                  - Local Fine-tuning (tuning + exploration)
                  - 上传 tuning expert updates

通信模式：
Server → Participant: w^r (全局模型) + E_i^{exp}, E_i^{exl} (expert role)
Participant → Server: Δw_i^{exp} (仅 tuning expert 参数更新) + u_i^e (utility values)
```

FLUX 的 parameter server 特定功能：
1. **Expert Role Assignment 求解器**：解决整数规划（公式 4），在 server 端运行（非 participant 端）
2. **Utility 收集与维护**：维护所有 experts 的 utility 表，每轮更新
3. **Dynamic ε 调度**：server 端按轮次调整 exploration-exploitation 比例
4. **Customized MoE 协调**：不同 participant 有不同 expert 配置（每层 expert 数可能不同），server 需协调聚合

术语一般如何实现？如何使用？
- 主流实现：PyTorch Distributed RPC、TensorFlow ParameterServerStrategy、BYPS (ByteDance)、Angel PS
- FLUX 约 3K 行 Python/PyTorch 实现，每个 participant 通过独立 object 管理（participant ID, profiling info 等）
- 联邦学习中的 PS 变体：Hierarchical PS（多级聚合，减少通信）、Decentralized FL（无中心 server）
- FLUX 的 PS 特点：无隐私数据上传、仅交换 expert 参数、server 承担计算任务（角色分配算法）

涉及论文标题：
- Federated Fine-Tuning of Sparsely-Activated Large Language Models on Resource-Constrained Devices

## Expert Offloading

术语是什么？
Expert Offloading（专家卸载）是在 GPU 显存不足以容纳完整 MoE 模型时，将部分 expert 参数存储在 CPU 主存（RAM）中，在需要计算时动态加载到 GPU 的技术。是 MoE 推理/训练中最常用的内存管理方法。典型实现：维护 GPU 上的 expert cache，按需通过 PCIe 将 expert 参数从 CPU 传输到 GPU，替换不活跃的 expert。

从系统架构角度拆解：
Expert Offloading 的系统流程（FMD baseline）：
```
GPU VRAM (有限)                  CPU RAM (充足)
┌──────────────────┐            ┌──────────────────┐
│ Active Experts   │<──PCIe───  │ Expert Pool       │
│ (e_a, e_b, e_c)  │  transfer  │ (all 512 experts) │
│                  │            │                   │
│ Gate Network     │            │ Weights for       │
│ KV Cache         │            │ e_d, e_e, ...     │
│ Activations      │            │                   │
└──────────────────┘            └──────────────────┘

每层 MoE forward:
1. Gate 计算 top-k expert indices
2. 检查 expert 是否在 GPU cache 中
3. Cache miss → PCIe 传输 expert 参数 CPU→GPU（cudaMemcpy）
4. Cache eviction → 换出最少使用的 expert 参数（如需）
5. GPU 执行 expert FFN forward
6. 释放 expert 临时显存（保留在 cache 中供后续使用）
```

FLUX 对比 offloading 的优劣：
- **FMD 的问题**：频繁 CPU↔GPU 数据传输引入大量 PCIe 延迟（Figure 10/11 中 FMD 速度最慢）
- **FLUX 的替代方案**：不 offload，而是合并 non-tuning experts 使模型 fit 进 GPU 显存——消除 PCIe 传输开销
- **速度提升**：FLUX vs FMD 达到 4.75× time-to-accuracy speedup

术语一般如何实现？如何使用？
- 典型系统：MoE-Lightning（预测式 expert prefetch）、Pre-gated MoE（提前预测下一层 expert 激活）、SwapMoE（可调显存 budget）
- 实现方法：CUDA Stream 异步传输 + double buffering（预取下一个 expert 同时执行当前 expert）
- 关键开销：PCIe bandwidth（L20 平台约 16-32 GB/s）成为瓶颈——传输一个 16-expert 层的参数（~1.3GB for LLaMA-MoE）需 ~40-80ms
- 使用场景：单 GPU 推理大 MoE、资源受限训练、边缘设备部署

涉及论文标题：
- Federated Fine-Tuning of Sparsely-Activated Large Language Models on Resource-Constrained Devices

## Non-IID Data in Federated Learning

术语是什么？
Non-IID（Non-Independently and Identically Distributed）数据是联邦学习中的核心挑战：各 participant 的本地数据分布不同（label skew、feature skew、quantity skew），不满足独立同分布假设。这导致本地模型更新方向不一致，降低全局模型收敛速度和最终精度。FLUX 按 FedNLP benchmark 的方式将数据集分割为 Non-IID 子集分配给各 participant。

从系统架构角度拆解：
Non-IID 对 FL 系统的影响与应对：
```
影响:
- Client Drift: 各 participant 的本地最优方向偏离全局最优
- 收敛慢: 需要更多通信轮次
- 最终精度下降: 简单 FedAvg 在 Non-IID 下不如 IID

FLUX 的应对策略:
1. Expert utility 定义考虑本地数据分布: u_i^e = |D_i^e| * sqrt(avg gradient)
   - |D_i^e| 反映 expert 在 participant i 数据上的实际利用率
   - 高 utility expert 被选为 tuning expert → 全局收敛受益
2. Exploration-Exploitation: 非高 utility expert 也有机会被探索
   - 防止过度适应本地 Non-IID 分布
3. Expert merging 保留全局知识: non-tuning experts 不丢弃
   - 保留在 Non-IID 数据上低频但跨 participant 重要的 expert 信息
```

术语一般如何实现？如何使用？
- 常见 Non-IID 类型：Label distribution skew、Feature distribution skew、Quantity skew（不同 participant 数据量差异大）
- 应对方法：FedProx（加 proximal term）、SCAFFOLD（control variate）、FedNova（归一化）、Personalized FL（本地个性化层）
- FLUX 方法属于 Personalized FL 思路——每个 participant 有不同 expert 配置（异构 MoE），expert 选择和合并适应本地数据分布
- 实验设置：FLUX 使用 FedNLP benchmark 的 Non-IID partition，模拟真实数据异构性

涉及论文标题：
- Federated Fine-Tuning of Sparsely-Activated Large Language Models on Resource-Constrained Devices

## Spec（类型化配置对象 / Typed Configuration Object）

术语解释
Spec 是 OPENJARVIS 提出的个人AI系统类型化配置抽象——一个包含五个原语（Intelligence/Engine/Agents/Tools & Memory/Learning）的声明式配置对象，将完整个人AI系统暴露为单一可优化、可共享、可版本化的对象。Spec 使模型替换可恢复（recoverable）、暴露本地-云端精度-效率 Pareto 前沿，并为 LLM-guided spec search 提供优化目标。

术语是什么？
Spec 是一个类型化配置对象（typed configuration object），定义为 S := {Intelligence: (model, params, quant), Engine: (backend, batch, kv_cache), Agents: (loop, prompts, tool_strategy), Tools: (set, descriptions, memory), Learning: (optimizer, reward, gate)}。每个原语字段（slot）独立可替换（swappable），单次编辑可跨多个原语字段，使整个个人AI栈端到端可优化、可度量。在磁盘上，spec 序列化为 TOML 配置文件，指定模型标识符、量化格式、Engine backend、Agent type、system prompt、Tools 启用列表、Memory backend 和 Learning policy。五个原语通过线程安全的 publish-subscribe EventBus 通信，添加新组件只需实现相应接口。Spec 实现了"一次配置，跨硬件移植"——同一 Agent 和 Tool 配置可通过仅修改 [intelligence] 和 [engine] 槽位重定向到不同硬件层级（从 Mac Mini M4 到 DGX Spark）。

从系统架构角度拆解术语：
Spec 在系统架构中的核心作用是**将个人AI栈从单体耦合（monolithic）解耦为可组合的独立自由度**。运转流程：
1. **配置加载**：用户或调度器从 TOML 文件加载 spec → 各原语注册表（registry）解析配置并实例化对应组件。
2. **查询路由**：用户通过 Channel（32+ messaging platforms）发送查询 → 安全层（PII 扫描、prompt injection 检测、SSRF 防护）→ Agent 原语接管。
3. **Agent 推理**：Agent 原语根据 spec 配置的 Agent type（ReAct/CodeAct/single-turn）执行推理循环，决定何时调用 Tools。
4. **Tool 执行**：Tools & Memory 原语处理工具调用（web_search→外部API、code_interpreter→Docker sandbox、memory_search→配置的 memory backend）。
5. **Engine 推理**：需要模型推理时，Engine 原语根据 spec 配置的 backend（Ollama/vLLM/SGLang/llama.cpp）在检测到的硬件上执行。
6. **遥测记录**：instrumented wrapper 自动记录每查询的 accuracy、energy、latency、power、dollar cost。
7. **（可选）学习更新**：若 Learning 原语启用，LLM-guided spec search 读取 traces→diagnose 失败→propose 编辑→gate 验证→更新 spec。

跨硬件移植的关键：同一 Agent/Tool 配置 + 仅修改 [intelligence] 和 [engine] 槽位 = 从 Mac Mini M4（\$999）到 DGX Spark（\$4,699）的无缝迁移。

术语一般如何实现？如何使用？
实现方式（基于 OPENJARVIS 参考实现）：
- 每个原语有类型化接口和注册表（registry）。Intelligence catalog 维护模型元数据（参数量、context length、VRAM 需求、兼容 Engines）并合并运行时后端发现的模型。
- Engine 硬件检测模块识别加速器类型（Apple/AMD/NVIDIA/Intel）并自动推荐最佳 backend。
- Memory 后端可互换：SQLite/FTS5（默认）、FAISS（向量相似度搜索）、ColBERTv2（轻量级 late interaction 检索）、BM25（稀疏检索）、hybrid RRF（倒数排序融合）。
- 使用场景：定义一次 spec → 跨硬件共享 → 在标准化 benchmarks 上评估 → LLM-guided spec search 优化 → 部署到目标硬件。Spec 可版本化、通过 GitHub 共享、作为 TOML 文件分发。

涉及论文标题：
- OpenJarvis

## 五原语架构（Five-Primitive Architecture）

术语解释
五原语架构是 OPENJARVIS 将个人AI系统分解为五个可组合、类型化原语（Intelligence/Engine/Agents/Tools & Memory/Learning）的设计模式。每个原语是独立可配置、可替换、可优化的自由度，通过 spec 组合为完整系统。

术语是什么？
五原语架构定义个人AI系统的五个正交维度：（1）**Intelligence**——语言模型架构和权重，包括模型选择、量化格式、生成参数；（2）**Engine**——推理运行时，包括 backend 选择、batch size、KV-cache、硬件执行路径；（3）**Agents**——推理循环，包括 Agent type（ReAct/CodeAct/single-turn/continuous）、system prompt、few-shot exemplars、tool-use policy；（4）**Tools & Memory**——外部接口（25+ Connectors: Gmail/Calendar/Apple Health/iMessage/Notion/Slack等）、检索（5 个可互换 Memory backend）和持久化用户状态；（5）**Learning**——从 traces 更新 spec 的优化器，包括 LoRA/GRPO 权重更新、DSPy prompt 优化、LLM-guided spec search。五个原语中，前四个（Intelligence/Engine/Agents/Tools & Memory）是可编辑原语（LLM-guided spec search 直接修改），Learning 是元原语（优化所有其他原语）。

从系统架构角度拆解术语：
五原语架构的设计逻辑——**将独立可配置的选择分离到不同原语**：
- Intelligence 和 Engine 分离：模型选择（Qwen3.5-9B vs. Qwen3.5-122B）vs. 运行时选择（vLLM vs. Ollama）。同一模型可通过不同 Engine 在不同硬件上运行。
- Agents 和 Tools 分离：推理循环（ReAct vs. CodeAct）vs. 其调用的接口（filesystem/web search/MCP servers）。同一 Agent logic 可使用不同 Tool set。
- Learning 与其他分离：Learning 是优化器原语——对 Intelligence weights、Agent prompts/logic、Tools & Memory 选择和描述、Engine runtime 配置进行编辑。同一 Intelligence+Agent 配置可仅因 Learning policy 不同而表现不同（如 OpenClaw-RL 仅更新 Intelligence weights vs. OPENJARVIS 的跨原语联合优化）。

运转流程：用户查询 → Channel 输入 → 安全扫描 → Agent 推理循环（根据 spec 中的 Agent type 执行）→ 需要时调用 Tools → 需要模型推理时调用 Engine → Engine 在检测到的硬件上执行 → 结果返回。每条查询的 accuracy/energy/latency/power/cost 由 instrumented wrapper 记录到本地 telemetry store。

术语一般如何实现？如何使用？
实现方式：每个原语通过接口（interface）定义。Engine 原语抽象了 Ollama/vLLM/SGLang/llama.cpp/cloud API backend，通过硬件检测模块自动选择最优 backend。Agents 原语支持离散 Agent（按需调用）和连续 Agent（持久运行、跨会话状态维护）。Tools 原语内置 7 类工具（reasoning/math/code/web_search/file I/O/memory/inference delegation），通过 MCP adapter 接入任意外部 MCP server。Memory 原语支持 5 个后端（SQLite-FTS5/FAISS/ColBERTv2/BM25/hybrid RRF）。Learning 原语支持多种优化策略（SFT/LoRA/GRPO/DSPy/LLM-guided spec search）。使用方式：`jarvis init` 自动检测硬件并生成初始 spec → 用户根据需要修改 spec → `jarvis run` 启动 Agent → 可选启用 Learning 进行持续优化。

涉及论文标题：
- OpenJarvis

## 本地-云端协作搜索模式（Search-Time Cloud, Inference-Time Local）

术语解释
本地-云端协作搜索模式是 OPENJARVIS 的核心架构分工：云端前沿模型在搜索时（search time）诊断失败痕迹并提出跨原语编辑，本地硬件在推理时（inference time）运行优化后的 spec，实现零云端调用的本地推理。这是一种"搜索时借力云端、推理时独立本地"的设计模式。

术语是什么？
该模式将个人AI的生命周期分为两个阶段：（1）**搜索时（search time）**——云端前沿模型（如 Claude Opus 4.6/GPT 5.4/Gemini 3.1 Pro）读取脱敏后的 eligible traces，诊断失败模式（diagnose failure clusters），提出跨 Intelligence/Engine/Agents/Tools & Memory 的协调编辑（propose edits），由 held-out gate 验证编辑有效性并仅接受非退化编辑；（2）**推理时（inference time）**——优化后的 spec 完全在本地硬件上执行模型推理和 Agent 执行，零云端调用、零边际 API 费。能力从云端流向本地通过优化后的 spec（而非持续的云端 API 调用），且未蒸馏的本地 spec 已在 4/8 benchmarks 上匹配或超过云端模型精度。

从系统架构角度拆解术语：
该模式在系统架构中实现了**能力转移（capability transfer）而非能力依赖（capability dependence）**：
1. **搜索阶段**（有界、可选）：用户启用 Learning 原语 → 云端教师接收脱敏 traces（经敏感数据扫描器 redact PII/credentials）→ diagnose→propose→gate→accept 循环 → 更新本地 spec。搜索成本 \$15.6/benchmark（中位数），一次性。
2. **推理阶段**（无界、默认）：本地 spec 运行模型推理 + Agent 执行 → 所有数据（Memory 内容、traces、训练数据）在设备上 → 零网络依赖 → 零边际 API 费。
3. **成本摊销**：100 queries/day × 6 个月 → 教师搜索成本摊销至 <\$0.001/query → 比直接使用 Claude Opus 4.6 便宜 ~10×。
4. **隐私保障**：搜索时仅传输脱敏 traces（经 PII/credential 扫描），用户可以指定哪些 trace 类别 eligible。推理时零数据传输。本地教师回退选项（用更大本地模型替代云端教师）完全消除云端传输。

与传统云端个人AI（OpenClaw/Hermes Agent 默认每查询传输推理数据到云端 API）对比：LLM-guided spec search 将云端暴露限制在搜索阶段——有界、可选、经过脱敏。

术语一般如何实现？如何使用？
实现方式：Learning 原语中的 spec_distillation policy 启用该模式。实现包括：（1）**Scrubbing pipeline**——敏感数据扫描器在传输前 redact PII/credentials/用户配置的敏感模式；（2）**Trace eligibility**——用户指定哪些 Connector/trace 类别可被云端教师访问；（3）**本地教师回退**——strict local-only 用户可用更大本地模型替代云端教师。使用场景：用户执行 `jarvis learn` 触发搜索 → 云端教师分析 traces → 提出编辑 → 本地 gate 验证 → 接受后更新 spec → 后续推理完全本地。

## DVFS Governor

术语是什么？

DVFS Governor（DVFS 调度器/调频策略）是操作系统内核中决定处理器（CPU/GPU/Memory）应运行在何种频率/电压水平的调度策略模块。Governor 持续监控硬件利用率（utilization）、负载等指标，根据预设策略动态调整频率——在性能需求高时升频（保证 QoS），在负载低时降频（节省功耗）。Governor 是 DVFS 机制的"大脑"，而实际的电压/频率切换由硬件 PMIC 和时钟管理单元执行。

Android/Linux 系统中的主要 DVFS Governor 类型：

1. **CPU Governor**：
   - **schedutil / sched_pelt (EAS)**：基于调度器的 utilization tracking（PELT per-entity load tracking），利用内核调度器已有的 per-task load 信息，避免额外采样开销。公式：$f_{target} = f_{max} \times \frac{util}{capacity}$，其中 $util$ 为 PELT 跟踪的 running time 占比。现代 Android（4.0+）默认使用 EAS (Energy-Aware Scheduling)，在选择频率时还考虑 CPU 能耗模型（energy model），倾向于在能耗效率更高的 OPP (Operating Performance Point) 上运行。
   - **performance**：始终锁定最高频率（最大性能，最大功耗）
   - **powersave**：始终锁定最低频率（最省电，最低性能）
   - **ondemand**：采样间隔型（已淘汰），周期性检查 CPU load → 超过 up_threshold 则升频，低于 down_threshold 则降频
   - **interactive**：为交互式 workload 优化的 ondemand 变体（响应更快，但能耗更高），已被 EAS 取代

2. **GPU Governor**：
   - **quickstep**（Pixel 7/Tensor G2 默认）：基于 GPU utilization 的快速响应型 governor。当 GPU busy percentage 超过阈值时快速升频，低于阈值时逐步降频。适合 bursty 的图形 workload，但对 LLM 推理的持续 compute 模式不够优化。
   - **simple_ondemand**：类似 CPU ondemand 的周期性采样型 governor

3. **Memory Governor**：
   - **interactive**（Pixel 7 默认）：基于内存控制器带宽 utilization 的 governor。当 LPDDR 带宽使用率超过阈值时提升内存频率，低于阈值时降低。

从系统架构角度拆解术语：

DVFS Governor 在 Android/Linux 系统架构中的运转流程（以 CORE 论文的一次 LLM 推理为例）：

```
           ▼                 ▼                   ▼
    ┌──────────┐    ┌──────────────┐    ┌──────────────┐
    │ ARM CPU  │    │ Mali GPU     │    │ LPDDR5 Ctrl  │
    │ PLL + PMU│    │ PLL + PMU    │    │ PLL + PMU    │
    └──────────┘    └──────────────┘    └──────────────┘
    
CORE 论文揭示的问题（多 Governor 独立决策的失败模式）：
    
Time  CPU Gov (EAS)          GPU Gov (quickstep)      Mem Gov (interactive)
─────────────────────────────────────────────────────────────────────────
 t0   Prefill starts                                  
      CPU util=85% → freq   GPU busy=95% → freq       Mem BW=80% → freq
      ↑ to 2100 MHz           ↑ to 848 MHz              → default (ok)
 t1   Prefill ends, Decode starts                     
 t2   CPU waits for GPU      GPU waits for CPU cmd    Mem BW=15% → freq
      util=20% → freq ↓       busy=15% → freq ↓        ↓ (but ok)
      to 800 MHz (too low!)   to 300 MHz (too low!)
 t3   CPU slow with 800MHz   GPU slow with 300MHz     
      → GPU queue starves     → CPU waits even longer  
 t4   CPU util drops further GPU busy drops further   "Downward Spiral"
      util=10% → freq ↓↓     busy=8% → freq ↓↓        continues until min
 t5   Both at minimum frequencies — TPOT ↑ 40%
```

关键发现：Governor 各自基于本地利用率独立决策，但利用率低的原因恰恰是另一个 Governor 降低了频率。这形成了正反馈的恶性循环（CORE 论文称为"Antagonistic Interaction"或"Downward Spiral"）。

CORE 的解决方案——绕过 Governor 直接钉扎频率：
- Profiling 阶段搜索最优 (CPU_freq, GPU_freq) 组合
- 推理时通过 sysfs 直接设置 `scaling_max_freq`，绕过 governor 决策
- Prefill 用高频率（compute-bound），Decode 用中等频率（memory-bound）
- 仅在 prefill/decode 阶段切换时切换频率（每 request 2 次）

术语一般如何实现？如何使用？

1. **Governor 选择与配置**：
   ```bash
   # 查看当前 governor
   cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
   
   # 切换 governor
   echo schedutil > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
   
   # EAS governor 参数调优
   echo 80 > /sys/devices/system/cpu/cpufreq/schedutil/up_rate_limit_us
   ```
   
2. **Governor 绕过（CORE 方式）**：
   ```bash
   # 设置 userspace governor（允许手动控制）
   echo userspace > /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
   # 或保留 EAS 但限制最大频率
   echo 2100000 > /sys/devices/system/cpu/cpu0/cpufreq/scaling_max_freq
   echo 2100000 > /sys/devices/system/cpu/cpu0/cpufreq/scaling_min_freq
   ```

3. **CORE Governor 实现**（~2K Python）：
   - Profile 阶段：遍历 (prefill_range, GPU_freq, CPU_freq) 组合 → 记录 latency + Monsoon power
   - Lookup Table：`lut[prefill_bucket][decode] = (gpu_freq, cpu_freq)`
   - Runtime：`echo $gpu_freq > scaling_max_freq` on prefill/decode phase transitions
   - 频率切换开销 < 1 ms（sysfs 写入 + PLL 重新锁定）

4. **关键设计考量**：
   - Governor 的开销：EAS 的 PELT tracking 开销 <0.1% CPU（利用调度器已有数据），但 governor 决策导致的次优频率选择开销可达 23-40% 延迟增加
   - Governor 的假设：默认 governor 假设"高利用率 = 需要高频率"，但 LLM decode 的 memory-bound 特性打破此假设——低利用率不代表不需要合理的频率
   - Cross-resource dependency：CPU/GPU/Memory 在 LLM 推理中高度耦合，独立 governor 无法捕获跨资源依赖

## FastRPC + rpcmem CPU-NPU Shared Memory Communication（CPU-NPU 共享内存通信）

术语是什么？
FastRPC + rpcmem 是 Qualcomm Snapdragon SoC 上 CPU 与 Hexagon NPU 之间的高性能进程间通信（IPC）机制。FastRPC（Fast Remote Procedure Call）是 Hexagon SDK 提供的 RPC 框架，允许 CPU 侧（AArch64）的函数调用透明地转发到 NPU 侧（Hexagon DSP）执行。rpcmem 是 FastRPC 的内存管理组件，封装内核 dmabuf（DMA Buffer）机制，在 CPU 和 NPU 之间创建物理共享内存区域——CPU 和 NPU 通过该区域零拷贝地交换数据（模型权重、中间激活、计算请求/状态）。论文基于此实现了一轮询（polling）通信模式：NPU 侧线程持续轮询共享内存中的 request 标志，CPU 侧通过写入 request + 手动 cache maintenance 提交计算任务，替代默认 RPC 的中断模式从而获得更低延迟。

从系统架构角度拆解术语：
FastRPC + rpcmem 在 CPU-NPU LLM 推理系统中的运转流程：

```
┌─────────────────────────┐           ┌──────────────────────────┐
│  CPU Side (AArch64)      │           │  NPU Side (Hexagon DSP)  │
│                          │           │                          │
│  llama.cpp Process       │           │  htp-ops-lib Skeleton    │
│  ┌────────────────────┐  │           │  ┌────────────────────┐  │
│  │ ggml-htp backend   │  │           │  │ NPU Thread Pool    │  │
│  │                    │  │           │  │                    │  │
│  │ 1. Prepare input:  │  │           │  │ 5. Poll request:   │  │
│  │   - Tokenize       │  │           │  │   while(!shm->     │  │
│  │   - Embedding      │  │           │  │     request_ready) │  │

│  │                    │  │           │  │                    │  │

│  │   cache(shm)       │──┼───────────┼──│   - HVX dequant    │  │

│  │                    │  │           │  │                    │  │
│  │ 3. Submit request: │  │           │  │ 7. Write results:  │  │
│  │   shm->request =   │  │           │  │   DMA writeback    │  │

│  │   while(!shm->     │  │           │  └────────────────────┘  │
│  │     status_ready)  │  │           │                          │
│  │     ;              │  │           │                          │
│  │   // Read output   │  │           │                          │
│  │   // lm_head +     │  │           │                          │
│  │   // sampler       │  │           │                          │
│  └────────────────────┘  │           │                          │
└─────────────────────────┘           └──────────────────────────┘

内存分配与映射流程:
1. CPU: rpcmem_alloc(type=RPCMEM_HEAP_SYSTEM, size, flags) 
   → 分配连续物理内存 → 返回 CPU VA + DMA fd
2. CPU: FastRPC 将 DMA fd 传递给 NPU
3. NPU: rpcmem_to_fd() 从 fd 恢复 NPU 侧 VA 映射
4. 此后 CPU 和 NPU 均可直接读写同一物理内存区域
5. 释放: rpcmem_free() (CPU 侧)

Cache Maintenance (关键！):
  Snapdragon SoC 上 CPU→NPU 仅单向 cache coherence:
  - CPU 写入后 → NPU 可能读到 stale L2 数据
  - 必须手动: rpcmem_flush_cache(shm_ptr, size)
    → Clean CPU L2 → DDR → NPU 方可读取正确数据
  - NPU 写入后 → CPU 同理需 invalidate
```

术语一般如何实现？如何使用？
- 接口来源：`libcdsprpc.so`（Android vendor library）、`libfastrpc.so`（Hexagon SDK）。
- 关键代码路径：(1) `rpcmem_alloc()` / `rpcmem_free()` 分配/释放共享内存；(2) `rpcmem_to_fd()` 获取 DMA fd 用于跨处理器传递；(3) 手动 cache maintenance（flush/invalidate）在每次数据传输后执行。
- 轮询 vs 中断：论文使用轮询（NPU 侧 `while` 循环检查 request flag）替代默认 RPC 的中断模式。优势是更低延迟（无中断上下文切换开销）；代价是 NPU 线程持续占用算力（但论文指出 NPU 在空闲时功耗极低）。
- 关键限制：(1) 32-bit 虚拟地址空间限制 rpcmem 可映射的连续内存大小——论文中 lm_head 因 logits 张量过大而放在 CPU 侧；(2) Cache maintenance 开销不可忽略——每轮 CPU→NPU request 需 flush；(3) rpcmem 是 Qualcomm 专有接口，不可移植到其他平台。

涉及论文标题：
- Scaling LLM Test-Time Compute with Mobile NPU on Smartphones

## llama.cpp，核心设计目标是在消费级硬件（CPU、集成 GPU、移动 SoC、Apple Silicon）上高效运行量化大语言模型。由 Georgi Gerganov 创建，基于其自研的 GGML tensor 库。与 PyTorch + CUDA 的服务器端推理栈不同，llama.cpp 通过以下设计实现边缘端高效推理：

1. **GGUF 量化模型格式**：支持 2-8 bit 多种量化方案（Q2_K、Q3_K、Q4_K_M、Q5_K_M、Q6_K、Q8_0 等），在模型精度和推理速度/内存之间提供灵活的 tradeoff。Q4_K_M 是最常用的方案：attention 和 FFN 权重使用 4-bit 量化 + per-block scaling factors（block size=32），输出层保留 6-bit 以维持精度，模型大小约为 FP16 的 25%。

2. **多后端硬件支持**：
   - **CPU 后端**：基于 GGML 的 C++ tensor 库，利用 OpenMP 多线程并行，支持 x86 AVX2/AVX-512 和 ARM NEON SIMD 指令。CPU 推理适合大 batch、长 context 的 decode（利用 CPU 的大容量 RAM 和 50+ GB/s 内存带宽）
   - **CUDA 后端**：NVIDIA GPU 推理，手写 CUDA kernel（INT4/INT8 matmul、FlashAttention）
   - **Metal 后端**：Apple Silicon GPU 推理（M1/M2/M3/M4），利用 Metal Shading Language
   - **OpenCL 后端**：Android/ARM Mali GPU 推理（CORE 论文的硬件平台），通过 OpenCL kernel 将量化 GEMM 和 attention 部署到移动 GPU
   - **Vulkan 后端**：跨平台 GPU 推理（支持更多移动 GPU）

3. **内存高效设计**：
   - 模型权重直接 mmap 到内存（零拷贝加载），多进程共享同一份权重
   - KV cache 在 CPU 和 GPU 间灵活分布（-ngl 参数控制 GPU 层数）
   - 支持 streaming weight transfer（CPU↔GPU），按需加载

从系统架构角度拆解术语：

llama.cpp 的推理流程与系统架构（以 CORE 论文的 Pixel 7 + Tensor G2 + OpenCL 后端为例）：

```
用户调用: llama-cli -m tinyllama-1.1b-q4_k_m.gguf -p "Hello" -n 100

1. 模型加载阶段:
```

关键系统架构特征：
- **无服务化设计**：llama.cpp 是单进程库/CLI，非 client-server 架构。每个推理请求是独立的 CLI 调用或通过 C API 嵌入。这与 vLLM/TGI 等服务器端框架的 continuous batching 架构根本不同。

   - CPU 执行 tokenization + sampling + KV cache management
   - CORE Python daemon 旁路监控推理阶段并钉扎频率

   - `-t N`：CPU 推理线程数。Pixel 7 的 Tensor G2 有 8 核 → 设置 4-6 避免过热 throttling

   - 集成 Rockchip NPU 数据平面驱动（~1K LoC），将矩阵乘法等 operators 提交到 NPU 执行
   - 优先级抢占式流水线调度：CPU computation operator 已就绪时优先执行，否则执行最早 computation operator 的 restoration operator；allocation/decryption operators 被划分为 micro-operators 并支持抢占
   - 多线程 TA 支持：通过 shadow thread 机制（TA 线程与 CA shadow thread 配对，shadow thread 通过 smc 启动/恢复 TA 线程），调度到 REE 的 4×Cortex-A76 + 4×Cortex-A55 CPU 核心
   - Partial parameter caching：推理结束后按计算图逆拓扑序惰性释放安全内存，保留早期 operators 的明文参数在安全内存中以消除下次推理的初始流水线气泡
   - 仅支持单用户交互式推理（无 continuous batching），与基线 llama.cpp 相同

## CMA for Secure Memory Scaling（用于安全内存动态伸缩的连续内存分配器）

术语是什么？

CMA（Contiguous Memory Allocator）是 Linux 内核的一种连续物理内存分配机制，在 TZ-LLM 中被创新性地用于动态扩展/收缩 TrustZone 安全内存。由于 TZASC 硬件限制（仅保护连续物理内存区域），TEE 不能使用 page-granular buddy allocator 分配安全内存——每次安全内存扩展都必须获得一个大块物理连续区域。CMA 通过预留一个物理内存区域并在分配时迁移其中的可移动页面（page migration），为 TEE 提供动态、按需的连续物理内存。TZ-LLM 设计了 "extend and shrink" 接口：`extend_allocated`（分配但暂不保护）→ `extend_protected`（配置 TZASC 保护）→ `shrink`（递减释放）。关键的 `extend_allocated` 和 `extend_protected` 分离设计允许 REE 文件系统直接 DMA 加载加密参数到已分配但未保护的内存，避免 bounce buffer 开销。

从系统架构角度拆解术语：

CMA 安全内存伸缩在 TZ-LLM 中的运转流程（以 Llama-3-8B 推理的 8GB 参数扩展为例）：

```
LLM TA 请求扩展安全内存
  → TEE OS 接收 extend_allocated(len=next_operator_params_size)
    → TEE OS 通过 smc 委托 REE TZ driver 调用 cma_alloc()
      → Linux CMA: 若 CMA 区域内有可移动页面 → 分配新目标页（非 CMA）→ 复制数据 → 更新页表 → 释放旧页
      → 返回新分配的连续物理内存块地址（必须与前次分配的块物理相邻，TEE OS 验证连续性）
  ← TEE OS 映射新内存到 TA 地址空间
  ← TA 调用 extend_protected(len)
    → TEE OS 编程 TZASC 寄存器：将区域末地址扩展 len（新内存现在受硬件保护）
    → 此时安全/非安全 CPU 和 DMA 设备的访问权由 TZASC 控制
  → TA 在新保护的内存中解密参数（AES-256-CBC）→ 参数可供 computation operator 使用

释放时（推理结束后）：
  TA 按逆拓扑序调用 shrink(len)
    → TEE OS 清除敏感数据（memset 0）
    → TEE OS 编程 TZASC 缩小区域末地址
    → TEE OS 通过 smc 委托 REE TZ driver 调用 cma_release()
```

术语一般如何实现？如何使用？

- **多线程 CMA 分配**：单线程 CMA 分配吞吐 ~1.9 GB/s，4 线程可提升至 ~3.8 GB/s（与 NVMe SSD 顺序读 2 GB/s 相当，因此 I/O 成为瓶颈而非分配）。
- **内存压力场景**：高内存压力下（REE 应用占用大量内存），CMA 区域内的可移动页面多，page migration 开销大（最高 4.2s for 8GB）。低内存压力下分配开销小。TZ-LLM 通过流水线将分配延迟与 I/O 和计算重叠，使其对 TTFT 的影响最小化。
- **与 S2PT 对比**：CMA 分配开销是瞬态的（仅 prefill 阶段），而 S2PT 引入持续性的 stage-2 地址翻译开销（Geekbench 平均降低 2.0%，最高 9.8%）。CMA 更适合移动端 LLM 的"间歇性推理"使用模式。

- TZ-LLM

## Pipelined Parameter Restoration（流水线参数恢复）

术语是什么？

Pipelined Parameter Restoration 是 TZ-LLM 的核心创新之一，通过在 LLM 计算图中注入并发执行的参数恢复操作来隐藏安全内存分配、加密参数 I/O 和解密的延迟。其洞见是 LLM 推理的计算图为 DAG（有向无环图），每个 computation operator（如矩阵乘法、self-attention）仅依赖本层参数，推理框架按拓扑序遍历 operators。因此，当执行 operator i 时，系统可以准确预知 operator i+1 需要哪些参数，并并行启动这些参数的恢复。三类 restoration operators 被插入到计算图每个 computation operator 前：allocation（CMA 分配）、I/O（NVMe SSD 加载加密参数）、decryption（AES 解密明文参数）。

从系统架构角度拆解术语：

Pipelined Restoration 的调度模型（以 512-token prompt 推理为例）：

```
DAG 执行模型（每个 computation operator 前的 restoration pipeline）：
  Operator_i,restore = {alloc_i, io_i, decrypt_i}
  Operator_i,compute  = {cpu_compute_i 或 npu_compute_i}

流水线调度器（scheduler）维护一个优先级队列：
  ReadyCPU = {ready CPU computation operators}
  ReadyRestore = {ready restoration operators, 按所属 computation operator 的拓扑序排列}

调度策略：
  if ReadyCPU non-empty:
    schedule(earliest ReadyCPU)     // 优先执行 computation，防止计算停顿
  else:
    schedule(earliest ReadyRestore) // 执行最早 computation 的恢复，尽早使 computation ready

抢占机制：
  allocation 和 decryption operators 被划分为 micro-operators，每个 micro-operator 完成后检查：
    if any CPU computation operator became ready: preempt current restore → schedule computation

Partial Parameter Caching 扩展：
  推理结束后，从安全内存末端按逆拓扑序释放参数（shrink）。
  保留的早期 operators 参数在下一次推理时直接可用，消除初始流水线气泡。
  缓存比例由 REE 内存压力动态决定，或通过 profiling 找到收益递减的阈值。
```

术语一般如何实现？如何使用？

- **llama.cpp 中的实现**：TZ-LLM 通过 llama.cpp 的内部接口直接提取计算图（ggml\_cgraph），+1.2K LoC 实现流水线恢复调度器。调度器在 ggml 的图执行循环中插入 restoration hooks。
- **调度效果**：与理论下界的差距仅 0.01%∼9.9%（内存压力开启）和 10.4%（无内存压力下，即最坏情况——因 I/O 成为唯一瓶颈路径）。
- **限制**：对非确定性 workload（MoE 中所有 expert 均需 prefetch、early-exit transformer 的所有层均需 prefetch）效率降低，但额外 prefetch 开销可被未来使用这些参数的推理摊薄。

- TZ-LLM

## Partial Parameter Caching（部分参数缓存）

术语是什么？

Partial Parameter Caching 是 TZ-LLM 的流水线恢复优化技术：推理结束后，LLM TA 不立即归还所有安全内存给 REE，而是根据 REE 内存压力**按计算图的逆拓扑序惰性释放**安全内存，将部分早期 operators 的明文参数保留在安全内存中。下一次推理从缓存参数的 computation 阶段直接恢复执行（而非完整冷启动），消除流水线初始气泡（initial pipeline bubble）。该机制基于观察到"最优缓存策略是保留最早使用的参数"——因为早期参数被使用时，后续参数的恢复操作尚不能与任何 computation 重叠，形成空闲气泡。

从系统架构角度拆解术语：

缓存与释放策略：
- **缓存策略**：保留 operator 0, 1, ..., k-1 的参数在安全内存中（k 依据 REE 内存压力动态确定，或通过 profiling 找到收益递减阈值），使下次推理立即从 operator k 开始流水线恢复。
- **释放策略**（逆拓扑序 shrink）：先释放最后使用的参数（如 layer 31 → layer 30 → ...），确保剩余参数在 TZASC 区域中保持物理连续——因为 shrink 总是从 TZASC 区域末端释放内存，逆拓扑序释放 = first-in-last-out（FILO）stack 模式，天然保持连续性。
- **效果量化**：随缓存比例增加，TTFT 近似线性下降直至一个阈值；超过阈值后收益递减（因剩余恢复开销已被计算完全隐藏）。阈值主要由 NPU 计算时间决定（对长 prompt 和 NPU 密集型模型阈值更低）。

术语一般如何实现？如何使用？

- 在 llama.cpp TA 中通过 extend\_allocated + extend\_protected 增加缓存（首次推理），shrink 部分释放。
- 缓存比例需权衡：更多缓存 → 更低 TTFT 但更高 REE 内存压力。TZ-LLM 通过检测 REE 内存压力或 profiling 确定最佳缓存大小。
- 安全考虑：缓存的参数是明文（解密后）在安全内存中，TZASC 保护确保 REE 无法访问。shrink 前必须 memset 清零。

## Iago Attack（Iago 攻击）

术语是什么？

Iago 攻击是针对 TEE 系统的一类攻击，攻击者（控制 REE OS 或恶意 REE 应用）通过**操纵 TEE-REE 接口的返回值或调用参数**，诱导 TEE 侧的 TA 或 TEE OS 做出错误的信任决策或执行非预期的操作，从而泄漏或破坏 TEE 保护的数据。与直接内存访问攻击不同，Iago 攻击不绕过硬件隔离，而是利用 TEE 对 REE 返回值的过度信任。名称源自莎士比亚戏剧《奥赛罗》中的反派 Iago——通过操控信息而非直接暴力达到目的。

从系统架构角度拆解术语：

TZ-LLM 面临的 Iago 攻击面和防御（四个 TEE-REE 接口）：

1. **安全内存伸缩**：CMA 可能返回任意（恶意的、非连续的）内存地址给 TEE。
   - 防御：TEE OS 验证返回地址与上次分配块的物理连续性。
2. **NPU job 调度**：REE NPU 驱动可能调度未授权的安全 job、重放（replay）已完成的 job、或重排序（reorder）job 执行顺序。
   - 防御：TEE 驱动在启动 job 前验证 job 状态（已初始化但未执行）+ 单调递增序列号防重放/重排序。
3. **模型加载（参数 I/O）**：恶意 REE OS 可能返回伪造的加密参数。
   - 防御：TEE TA 使用 checksum 验证加载内容的完整性（在解密后验证）。
4. **CPU 线程调度**：REE 调度器可能违反 TA 线程的预期执行顺序。
   - 防御：同步原语（mutex、condition variable）在 TEE OS 中管理，TA 线程的执行顺序由 TEE 侧的同步原语强制。

术语一般如何实现？如何使用？

- **防御原则（outsource-and-verify）**：将复杂/不可信的操作委托给 REE，但验证其输出。TZ-LLM 的 co-driver NPU 设计也遵循此原则。
- **相关攻击面**：任何 TEE 系统只要存在 REE→TEE 的信息流（内存地址、文件内容、调度决策、时间信息）都需考虑 Iago 攻击面。Intel SGX 的 AEX（Asynchronous Enclave Exit）和 ERESUME 机制也面临类似的接口攻击。

- TZ-LLM

## S2PT Memory Protection（Stage-2 页表内存保护）

术语是什么？

S2PT（Stage-2 Page Tables）是 ARM 虚拟化扩展（ARM VHE/EL2）中的机制，通过第二级地址翻译为虚拟机提供内存隔离。在 TEE 保护场景中，S2PT 可被用于 page-granular（4KB、2MB、1GB）安全内存保护——S2PT 将安全内存页的映射从 Stage-2 页表中删除（unmap），阻止 REE（运行在 VM 中的不可信 OS）访问这些物理页。相比 TZASC（仅保护 ≤8 个连续区域），S2PT 提供 page-granular 保护，理论上支持任意地址的灵活安全内存分配（无需 CMA 分配连续物理页）。

从系统架构角度拆解术语：

TZ-LLM 选择 CMA+TZASC 而非 S2PT 的原因（基于论文的动机分析）：

1. **持续性性能开销**：Stage-2 翻译对每次 TLB miss 引入额外的一级页表走查（two-dimensional page walk），对 REE 应用程序产生持续性的性能开销。4KB 映射下 Geekbench 开销最高 9.8%，平均 2.0%。即使使用 2MB/1GB huge pages，LLM 内存分配后的内存碎片化通常导致大部分映射回退到 4KB 粒度。
2. **DMA 攻击不设防**：S2PT 仅控制 CPU 的虚拟地址访问，不控制 DMA。DMA 设备（如 NPU、恶意 PCIe 设备）仍可访问 S2PT-unmapped 的物理内存。防御 DMA 攻击需额外机制（EL3 monitor 拦截 IOMMU 配置或 MMIO 操作），增加 TCB 和运行时开销。
3. **CMA 的开销是瞬态的**：CMA page migration 开销仅在 prefill 阶段发生，解码阶段和推理空闲期间无开销。而 S2PT 的翻译开销是持续的（只要 S2PT 使能）。因此 CMA+TZASC 更适合 LLM 推理的"间歇性使用"模式。
4. **连续内存 vs 碎片化**：CMA+TZASC 虽需连续物理内存，但通过 first-in-last-out 内存管理模式和 "extend and shrink" 接口可有效维护连续性。S2PT 虽支持非连续页，但引入的持续性开销在移动端不受欢迎。

术语一般如何实现？如何使用？

- **S2PT 的替代场景**：当 TEE 需要保护的对象不是大块 LLM 参数，而是大量离散的小对象（如许多小 TA 的安全内存碎片），或当安全内存需要长时间在线（如一直运行的 background service），S2PT 的 page-granular 灵活性可能优于 CMA+TZASC。TZ-LLM 的 CMA+TZASC 方案针对大块、间歇性 LLM 推理优化。

涉及论文标题：
- TZ-LLM
