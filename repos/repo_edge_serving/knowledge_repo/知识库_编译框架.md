## QNN (Qualcomm AI Engine Direct SDK)

术语是什么？
QNN（Qualcomm AI Engine Direct，前称 Qualcomm Neural Network SDK）是 Qualcomm 提供的闭源深度学习推理框架，是将模型部署到 Hexagon NPU 的主要官方途径。QNN 提供从模型转换（ONNX/TensorFlow → QNN IR）到设备端推理（HTP/NPU backend、CPU backend、GPU backend）的全套工具链。QNN 的核心是 HTP（Hexagon Tensor Processor）backend——将 QNN IR 编译为 Hexagon NPU 上可执行的二进制指令（通过未公开的 HMX/HVX 指令）。QNN 的致命限制：(1) 仅支持 per-tensor/per-channel 粗粒度量化——无法适应现代 LLM 的 per-group 细粒度量化；(2) 编译后计算图为静态固定形状——batch size 和序列长度在编译时确定、运行时不可变；(3) 开发者无法自定义底层 kernel——所有 NPU 算子由 QNN 闭源库提供，HMX 指令未公开。因此 QNN 不适合 test-time scaling（需要动态 batch size）和现代 LLM 部署（需要 per-group 量化）。

从编译框架角度拆解术语：
QNN 的编译与推理全流程：

```
=== 离线阶段: 模型转换与编译 ===

1. 输入: PyTorch/TensorFlow/ONNX 模型

2. QNN Converter (qnn-onnx-converter / qnn-tensorflow-converter):
   模型 → QNN IR (Intermediate Representation)
   IR 包含: 算子图 (op graph) + 张量信息 (shape, dtype, quantization params)
   量化配置: per-tensor 或 per-channel scale/offset

3. QNN Context Binary Generator (qnn-context-binary-generator):
   QNN IR → HTP Context Binary (.bin)
   编译过程:
   a. 图优化: 算子融合 (Conv+BN+ReLU→fused), 常量折叠
   b. 内存规划: 分配 TCM buffer sizes, DMA descriptors
   c. 指令生成: 将每个算子映射到 HTP VM 指令序列
      - GEMM → HMX instructions (mxmem等, 未公开)
      - Activation → HVX instructions
      - 数据搬运 → DMA descriptors
   d. 生成架构特定的 .bin + .so (libQnnHtp.so + skel libraries)

=== 在线阶段: 设备端推理 ===

4. 设备初始化:
   QNN API: qnn_interface_create() → backend_create(HTP) → device_create()

5. Context 加载:
   load_context_from_binary("model.serialized.bin")
   → HTP VM 初始化, TCM 划分, DMA channel 分配
   注意: 此时 shape 已固定! batch_size=1 永远为 1

6. 推理 (固定 batch size):
   for each input:
     qnn_tensor_write(input_data)   # CPU→NPU: l2cursor/lite transport
     qnn_graph_execute()            # NPU 执行编译后的指令序列
     qnn_tensor_read(output_data)   # NPU→CPU

QNN 不支持的功能 (论文的关键动机):
  ✗ Per-group 量化 (仅 per-tensor/per-channel)
  ✗ 动态 batch size (离线编译时固定)
  ✗ 自定义算子 kernel (无法插入 LUT dequant/Softmax)
  ✗ FlashAttention (非标准 QNN 算子)
  ✗ 细粒度内存管理 (TCM 由 QNN runtime 隐藏管理)
```

术语一般如何实现？如何使用？
- SDK 获取：Qualcomm Developer Network → Qualcomm AI Engine Direct SDK（需注册下载）。包含 `qnn-onnx-converter`、`qnn-context-binary-generator`、`libQnnHtp.so`、`libQnnHtpV7xStub.so`/`libQnnHtpV7xSkel.so`。
- 与 Hexagon SDK 的关系：QNN 在 Hexagon SDK 之上构建——QNN 使用 Hexagon LLVM 工具链生成 DSP 代码，但 QNN 闭源了 HMX 指令的使用方式。
- 绕过 QNN（论文方案）：直接使用 Hexagon SDK 的 LLVM 工具链 + inline assembly，通过逆向工程未公开的 HMX 指令（mxmem、cvt.hf=acc()、bias=mxmem2()）实现自定义 kernel 编程。QNN 仅在论文中作为精度 reference（Table 1 显示 QNN 量化精度显著劣于 per-group 方案）。
- 替代框架：ExecuTorch（Meta, 支持 QNN backend）、MNN（阿里, 支持 QNN backend via offline/online mode）、LiteRT（Google, 支持 QNN backend via CompiledModel API）。

## Hexagon SDK

术语是什么？
Hexagon SDK 是 Qualcomm 提供的 Hexagon DSP/NPU 底层开发工具包，包含 LLVM 交叉编译工具链（支持 Hexagon DSP 的 VLIW + HVX + HMX 指令集）、FastRPC 框架（CPU↔DSP 通信）、DSP 计算库（libhexagon）、以及仿真器和调试工具。与 QNN（高层推理框架）不同，Hexagon SDK 提供了更底层的编程能力——开发者可用 C/C++ + inline assembly 直接编写 Hexagon DSP 原生代码，控制 HVX 向量指令、DMA 传输、TCM 分配等硬件细节。论文基于 Hexagon SDK v6.0.0.2 构建了 htp-ops-lib（独立 DSP 共享对象），完全绕过 QNN。

从编译框架角度拆解术语：
Hexagon SDK 的编译与部署流程（以 htp-ops-lib 为例）：

```
=== 编译流程 ===

1. 环境配置:
   source <hexagon_sdk_root>/setup_sdk_env.source
   # 设置 HEXAGON_SDK_ROOT, HEXAGON_TOOLS_VER, 
   # HEXAGON_CPU_ARCH (v73/v75/v79) 等环境变量

2. 双重编译目标:
   (A) AArch64 Stub (CPU 侧):
       build_cmake android
       ├── CMake Toolchain: android.toolchain.cmake (NDK)
       ├── Target: aarch64-linux-android
       ├── Output: libhtp_ops.so
       └── 作用: FastRPC Stub —— CPU 侧调用的接口层
       
   (B) Hexagon Skeleton (NPU 侧):
       build_cmake hexagon DSP_ARCH=v73
       ├── CMake Toolchain: hexagon.toolchain.cmake (SDK)
       ├── Target: hexagon-unknown-elf
       ├── Compiler: hexagon-clang (LLVM-based)
       ├── Flags: -mhvx -mhvx-length=128B -mhmx
       ├── Output: libhtp_ops_skel.so
       └── 作用: FastRPC Skeleton —— NPU 侧实际执行的 kernel

3. LLVM 编译细节 (NPU 侧):
   源文件: src/dsp/ops/flash_attn.c, src/dsp/ops/gemm_deq.c, ...
   
   编译器: hexagon-clang (基于 LLVM, 支持 Hexagon 扩展)
   
   关键编译 flag:
   - -mhvx: 启用 HVX 向量扩展 intrinsic
   - -mhvx-length=128B: 指定 HVX 向量宽度 (V73=128B)
   - -mhmx: 启用 HMX 矩阵扩展 (实验性)
   - -O3: 最高优化级别 (VLIW 打包优化)
   
   Inline Assembly:
   // HMX 指令 (未公开, 逆向工程):
   asm volatile("vmxmem(%0, %1)" :: "r"(act_addr), "r"(tcm_addr));
   asm volatile("cvt.hf = acc()\n\t vmxmem(%0, %1)" :: ...);
   
   // HVX intrinsic:
   HVX_Vector q = Q6_V_vmem_load_A(addr);     // 128B vector load
   HVX_VectorPair p = Q6_V_vlut16(q, lut, ...); // 16-entry LUT lookup
   HVX_Vector r = Q6_V_vgather_A(base, offset); // scatter-gather

=== 部署流程 ===

4. 文件传输 (adb push):
   libhtp_ops.so         → /data/local/tmp/llama.cpp/  (CPU stub)
   libhtp_ops_skel.so    → /data/local/tmp/llama.cpp/  (NPU skeleton)
   libllama.so, libggml.so, libggml-htp.so → same dir

5. 运行环境:
   export LD_LIBRARY_PATH=/data/local/tmp/llama.cpp:/vendor/lib64:/system/lib64
   export DSP_LIBRARY_PATH=/data/local/tmp/llama.cpp
   # DSP_LIBRARY_PATH: FastRPC 从此路径加载 .skel.so

6. FastRPC 会话初始化 (llama.cpp 侧):
   fastrpc_init() → fastrpc_session_create(DSP_DOMAIN)
   → 加载 libhtp_ops_skel.so 到 Hexagon DSP
   → NPU 侧线程启动 → 开始轮询共享内存中的 request

=== 架构版本与 SoC 映射 ===
| DSP_ARCH | SoC 示例 | HMX 支持 | 备注 |
|----------|---------|---------|------|
| v73 | Snapdragon 8 Gen 2 | FP16 HMX | 2 GiB 虚拟地址空间限制 |
| v75 | Snapdragon 8 Gen 3 | FP16 HMX | 主要开发平台 |
| v79 | Snapdragon 8 Elite | FP16 HMX | vgather exp 有浮点 bug, 需 workaround |
```

术语一般如何实现？如何使用？
- SDK 获取：Qualcomm Developer Network → Hexagon SDK（需注册和审批）。论文使用 v6.0.0.2。
- 编程模型：(1) HVX intrinsic（C/C++ API, 声明在 `hvx_hexagon_protos.h`）；(2) HMX inline assembly（未公开指令，通过逆向 QNN 二进制 + Hexagon SDK 5.x 的 `qhl_hmx` 示例发现）；(3) DMA API（`hexagon_dma_*` functions）。
- 关键限制：(1) 闭源 HMX 指令——论文通过逆向工程 `qhl_hmx` 示例 + QNN 头文件中的 `memory_layout.h` 和 `tile_extract.h` 推测指令语义；(2) 编译器成熟度——HMX 支持为实验性，某些优化需手动 inline assembly；(3) 架构差异——v73/v75/v79 间存在微架构差异（如 V79 的 vgather bug），需条件编译。
- 与 CUDA 对比：Hexagon SDK 类似 CUDA Toolkit——提供编译器、工具链、计算库，但成熟度、文档、社区远不及 CUDA。Hexagon 无类似 cuBLAS 的官方开源高性能线性代数库——论文的 htp-ops-lib 填补了这一空缺。
