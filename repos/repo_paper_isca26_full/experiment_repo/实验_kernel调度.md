# 实验_kernel调度

## AXLE: Coordinated Offloading with Asynchronous Back-Streaming in Computational Memory Systems

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 AXLE：面向 CXL-based Computational Memory (CCM) 部分卸载（partial offloading）的异步背流协议与运行时调度系统，核心是把"结果搬运与任务调度"从主机触发改为设备触发并做跨组件流水重叠。CCM 侧新增 DMA executor：监控 µthread 计算结果，连续结果数据达到 DMA slot 大小（默认 32B，可配）时打包成一个 payload，每个 payload 配一条 metadata；待发 payload 总量 ≥ Streaming Factor（SF，32B/64B）时经 CXL.io DMA 反向流式送回主机本地 DMA 区域。主机侧新增：本地轮询 routine（只轮询本地 metadata ring buffer 尾指针，轮询间隔 50ns/500ns/5µs）、ready pool（就绪任务池，直接对接主机调度器）、flow control 消息（CXL.mem store 回传已消费的 payload/metadata head 索引，防固定大小 ring buffer 溢出）。支持 OoO（乱序）流式：metadata 记录对应 payload slot ID，payload ring buffer 按 gap-aware 方式非连续消费，使 CCM 与主机两套并行任务调度器互不感知对方顺序即可工作（对称评估 RR 与 FIFO 两种调度）。内存正确性：内存栅栏保证 {payload 写→payload tail 更新 / metadata 写→metadata tail 更新} 一致性不变量、CCM 本地维护保守 head/tail 索引 + 轻量流控、DMA 区域 cache-bypass 固定。
  - 实验比较 3 个基线 + 1 个变体：Remote Polling（RP，CXL.io 设备中心视图 + 远程 mailbox 轮询）、Bulk Synchronous flow（BS，M2NDP 原生 CXL.mem 同步流）、AXLE_Interrupt（中断通知变体，乐观 50µs 中断处理延迟）；RP 由作者在 M2NDP 上另行实现，BS 为 M2NDP 原生。指标：端到端 runtime（归一化到 RP）、CCM idle time、host idle time、host core stall time；参数敏感性：轮询间隔（p1=50ns/p10=500ns/p100=5µs）、Streaming Factor（SF1=32B 至 SF64、SF_Y%=占总结果 Y%）、OoO 开关、RR/FIFO 调度、DMA slot 容量（12.5%–100%）。
- 后端平台是什么，配置是什么。
  - 主机：CPU 3GHz、32 处理单元、每单元 2 µthreads（模拟超线程）、主存 DDR5-4800 16 通道。CCM 设备：2GHz、16 处理单元、每单元 16 µthreads、CXL 内存 DDR5-4800 16 通道。CXL 协议参数（遵循 CXL 3.0 规范）：CXL.mem 往返 70ns、CXL.io 往返 350ns（比 Intel Xeon 实测 pin-to-pin ~275ns 更保守）；RP 固件频率 2GHz、远程轮询间隔 1µs；AXLE DMA 准备延迟 500ns/请求、DMA slot 容量默认 50000、中断处理延迟 50µs（AXLE_Interrupt）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：M2NDP 开源 cycle-level CCM 模拟器（POSTECH PSAL），组合 Ramulator（CXL 内存设备时序）与 BookSim2（CXL 互连协议）。修改：M2NDP 原生仅支持 BS 同步流，作者在其上 (1) 新实现 RP 模型（邮箱入队/远程轮询/出队/结果 load），(2) 实现 AXLE 的 DMA executor、metadata/payload 双 ring buffer、本地轮询与 ready pool、CXL.mem 流控消息、OoO 流式与栅栏排序，(3) 实现 AXLE_Interrupt 中断变体；另以 RISC-V 指令形式实现 M2NDP benchmark 之外的多个 workload kernel（KNN、SSSP、PageRank、SSB、OPT attention、DLRM）。

  - M2NDP 模拟器开源：https://github.com/PSAL-POSTECH/M2NDP-public（论文参考文献 [13] 给出）。AXLE 的修改代码与新增 workload kernel 是否开源论文未明确说明。
  - 评估原理与全过程：输入 = RISC-V 指令形式的 offload kernel（如 KNN 向量距离计算、PageRank 邻接遍历+顶点更新）+ 由主机与 CCM 调度器预定的固定大小输入向量分块 + 调度策略（RR/FIFO）与 AXLE 参数配置。主机执行应用，对特定远端地址发 CXL.mem store 触发 kernel launch（RP 则经 CXL.io 邮箱 enqueue→轮询→dequeue）；CCM 内每处理单元 16 µthreads 按调度器分派的固定大小输入向量执行 kernel 指令（Ramulator 逐周期模拟 DDR5 时序与 CXL 内存访问），结果写入 CCM 内存 → AXLE 的 DMA executor 打包装 payload+metadata，达到 SF 阈值后经 BookSim2 模拟的 CXL.io 链路 DMA 反流到主机本地 ring buffer → 主机轮询本地 metadata tail 指针，把就绪 metadata 搬入 ready pool，主机调度器按策略选取下游任务、从本地 region 读取 payload 执行 → 主机经 CXL.mem 回送 head 索引流控。输出 = 模拟器逐周期统计的 CCM 执行/数据搬运/主机执行时间 → 端到端 runtime、CCM/host idle time、host core stall time 及其相对 RP/BS 的归一化对比。

## Accelerating MoE with Dynamic In-Switch Computing on Multi-GPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 DySHARP 的 token-centric kernel fusion：把 MoE 层 Dispatch→GEMM-1→GEMM-2→Combine 四算子重组为 token-paced pipeline，用 megakernel + persistent thread blocks（TB）绕过硬件 TB 调度器（借鉴 Rammer rTasks），"向 SM 发射 TB"被模拟为"持久 TB 从任务列表取任务"。SM 划分为 4 组，分别专职 Dispatch / GEMM-1 / GEMM-2 / Combine（GEMM-1/GEMM-2 无就绪 TB 时可共享 SM）。Token tracker 以 token/tile 粒度检测 readiness 边界：TS Table（Tile Status Table，1024 项，DAcc 计数 dymultimem.st 到达以判 Dispatch⇒GEMM-1 就绪、TBCnt1/TBCnt2 计 TB 完成）、TID Table（DRAM）+ OR Table（Output Readiness Table，1024 项，nReady==topk 判 GEMM-2⇒Combine 就绪）。readiness-gated 调度：GEMM-1/GEMM-2 的 TB 行仅当 tracker 标记 ready 且目标 SM 组有空位时发射；Combine 通信 kernel 轮询 OR 表 nReady 后才对 token 发射 dymultimem.ld_reduce。同步 tile 尺寸 128（与 GEMM tile 匹配）。
  - 实验比较 7 个 baseline（DeepEP、NVLS、FasterMoE、Tutel、CCFuser、COMET、DualPipe）+ 3 个消融变体（DySHARP-Basic = 仅 dynamic multimem addressing 无重叠；DySHARP-COMET = DySHARP-Basic + COMET 式重叠；kernel fusion only = 仅 token-centric fusion 无 dynamic multimem addressing）。指标：端到端训练 speedup、MoE 层（Dispatch-Computation-Combine）speedup、流量体积、payload 效率、纯通信性能（vs ideal）、带宽利用率、时间分解；敏感性：GPU 数 4-64、序列长度 1024-16384、token 分布（训练正态 std 0.01-0.05 / 推理 power-law α 0.5-2.5）、tile 尺寸。
- 后端平台是什么，配置是什么。
  - 模拟 NVIDIA GH200 NVL32：32 GPU 经 9 个 NVSwitch 全连接 fat-tree 互连，每 GPU 按 H200 规格配置；NVLink 按 NVLink 4.0 真实器件参数建模：双向带宽 900 GB/s、单跳 250ns、往返 1µs、flit 16B；NVSwitch 每输入端口 16 个 256 深 VC（8 请求 + 8 响应）、端口 reduction buffer 64KB。多节点扩展评估：4/8×DGX-H100 与 2/4×NVL32 + InfiniBand（Quantum Switch），16-way pipeline parallelism；另评估 64-GPU 节点（18 NVSwitch、每 switch 64 端口）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：Accel-Sim（GPU 微架构模拟器，https://github.com/accel-sim/accel-sim）+ BookSim2（cycle-accurate NoC 模拟器，https://github.com/booksim/booksim2）集成做逐周期多 GPU 仿真。修改：在支持基础 Hopper 特性的最新版 Accel-Sim 上扩展高性能 FP8 GEMM kernel 建模、多 GPU 并发执行与 switch-based 网络互联；BookSim2 建模 NVLink 4.0/NVSwitch；实现 dymultimem 指令、token tracker 与 megakernel 调度器。校准：对照 DGX-H100 实测，GEMM 与 DeepEP 通信算子在多种 shape/volume 下平均误差 <6%。

  - DySHARP 自身代码未见公开仓库（论文未给出开源链接，arXiv: 2605.05607；联网搜索未找到官方 repo）。Accel-Sim 与 BookSim2 均开源（链接见上，论文参考文献 [16][18]）。
  - 评估原理与全过程：输入 = MoE 模型配置（DeepSeek-V3 官方 Large-8 + Small/Medium 扩展，topk∈{8,16,32}；GPT-OSS-120B、Qwen3-235B）+ token 分布（训练按正态 std=0.032、推理按 power-law α≈1.5）+ kernel 指令流（Dispatch/GEMM-1/GEMM-2/Combine 及 megakernel 调度版本）。Accel-Sim 逐周期执行 GPU 侧指令流：dymultimem.st / dymultimem.ld_reduce 经 LSU 取 target list 后生成请求包 → BookSim2 模拟 NVLink/NVSwitch 逐周期转发/多播/归约 → 响应写回 GPU 内存；token tracker 表随数据到达/TB 完成事件更新，megakernel 内持久 TB 轮询 readiness 位并按 SM 分组发射任务。输出 = 每层/端到端执行周期数 → speedup（vs DeepEP 端到端最高 2.31×、vs NVLS 5.12×、vs FasterMoE 2.11×、vs Tutel 1.98×、vs CCFuser 1.85×、vs COMET 1.79×、vs DualPipe 1.88×；几何平均 1.93×/3.38×/1.84×/1.72×/1.63×/1.59×/1.66×）、流量体积（vs DeepEP -50%）、纯通信性能（>90% ideal）、带宽利用率与消融时间分解。

## Accelerator Polymorphism: Transcending Domain-Specific Architectures with Robotics（近似层次匹配：queue-centric SIMD 运行时计算与片上/片外数据调度）

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 Morphatron 的 queue-centric SIMD 运行时执行与数据调度机制（论文为硬件架构论文，本层次取其中"动态尺寸数据结构上的运行时计算与数据搬运调度"部分，属近似匹配）。(1) 动态队列的运行时并行计算：FIFO 队列按 interleave 方式划分成 N 个 sub-queue 映射到 N 个执行 stage，每 stage 的 Queue Manager（组合逻辑）独立维护 head/tail/empty，空 sub-queue 由硬件自动 skip，指令（POP_Q/PEEK_Q/PUSH_Q）直接以 sub-queue 为操作数在 scratchpad sub-bank 上执行；(2) in-pipeline 动态内存分配与调度：队列增长时第三流水级的 buddy-tree 分配器按 256 B slice 单周期分配、slice 末字指针链式扩展，队列超出片上容量时按 FIFO 顺序 spill 到 off-chip（保留 head slice 片上），利用队列严格 FIFO 特性做自动 prefetch 与 double-buffering，无需 cache 层次；(3) 数据搬运引擎调度：DMA 在 vector/systolic morpha 由编译器静态编程（prefetch、double-buffering），在 queue-centric 执行时用 Queue Manager 内队列统计动态填充小指令模板编程；(4) 队列即控制流：Q_LOOP_UNTIL_EMPTY 由前端硬件循环（程序计数器仅在所有 sub-queue 空后前进）、Q_CONDITIONAL_PUSH 选择性入队，以"数据可用性"取代 predication 掩码。
  - 实验比较（消融）：vector morpha vs 同硬件上模拟的传统向量处理器（YOLO/EKF/OSQP/CCCD 四 kernel：传统方案地址计算 28%、寄存器文件 load/store 15%、软件循环管理 19% 的平均运行时开销，Morphatron 单次配置开销最多 0.29%、平均 0.01%）；queue 谓词 vs 传统 predication（SLAM 点云过滤，pass rate 0–100% 扫描、1.6× sub-queue 不均衡：30% pass rate 时传统方案 70% 周期被 masked lane 浪费，Morphatron 2.4× 加速）；off-chip queue spill vs 理想 cache+prefetch（数据量 1.5–20× 片上容量、算术强度 5/10/20 FLOP/B 扫描：最坏 1.5× 容量+AI=5 时 12.7% 开销，3× 容量降到 6.6%）。
- 后端平台是什么，配置是什么。
  - Morphatron（自研 cycle-level 模拟器）：7 nm ASAP7、625 MHz、10 W；32×4 Morpha Core 网格、每核 8 执行 stage（ALU + 8 KB sub-bank）、16 MB 片上、32 B 宽 circuit-switched 互连、DRAM 68 GB/s。对照 baseline：ARM A78AE（NEON）、Xeon 6226R（AVX512）、Jetson Orin Nano、RTX 3090（CUDA 12.1）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 自研 cycle-level 模拟器（无名称、未开源）+ Synopsys Design Compiler 综合 + CACTI 能量模型；消融变体为在模拟器内把对应机制替换为传统向量处理器机制（地址计算/寄存器文件/软件循环）或 predication 执行模型后重新测同一 workload。修改点：无开源基座，全部自研。

  - 模拟器与 RTL 是否开源论文未明确说明，联网搜索未找到公开仓库；benchmark RoWild 开源（https://github.com/cmu-roboarch/rowild ）。
  - 评估原理与全过程：输入 = RoWild 应用的 queue 语义指令流（例：`Q_LOOP_UNTIL_EMPTY, Q.ID[#0], 1: ADD, Q.ID[#1].PUSH, Q.ID[#0].POP, 0x01`，及 SLAM 过滤用 Q_CONDITIONAL_PUSH 选择性入队）。每个执行 stage 的 Queue Manager 按 queue ID 查队表取 head/tail 指针，从 scratchpad sub-bank 取操作数直接喂 ALU、结果写 tail 并推进（无寄存器文件、无地址计算指令），空 lane 由硬件 skip；队列扩容触发 buddy-tree 分配 256 B slice（slice 末字链下一 slice），超出片上份额时 FIFO spill 到 off-chip 并自动 prefetch；跨核/片外数据经 DMA 与 BROADCAST/COLUMN_REDUCE collectives 搬运（queue-centric 阶段 DMA 参数由队列统计动态填充）。输出 = 逐周期统计的执行时间与能耗 → 消融加速比（vector morpha 相对传统向量处理器 YOLO 18×、EKF 8.4×、OSQP 1.74×、CCCD 1.27×；queue 谓词 30% pass rate 2.4×；spill 相对理想 cache 最坏 12.7% 开销）与 morpha 级加速贡献（Systolic/Vector 单独 0.7×、+Queue 5.2×、+Graph 3.3×、+Tree 2.2×，均归一化 ARM）。

## Approaching Shannon Bound with Lossless LLM Weight Compression

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 fused tile-aligned rANS 解压 + GEMM 微内核（GPU kernel，CUTLASS plugin）：(1) 双组件融合内核（Algorithm V.1）——warp 0 作生产者：从全局内存按 offset 表取压缩 weight tile、rANS 解码直接写 shared memory tile A(b)；warp 1..W 作消费者：把 A(b) 与激活 tile B(k) 送入 tensor core 做 GemmTile；double-buffered shared memory（A(0)/A(1)）+ cuda::atomic_ref<int, cuda::thread_scope_block> 的 ready 标志同步，每 tile 解压与上一 tile 计算重叠；(2) warp-cooperative rANS 解码（Algorithm V.2）——每 tile 压缩流分 R 个独立 substream、每 warp lane 一条：x ← s mod R → 查 shared memory 解码表 T̃[x]=(σ,f,c) → w ← DecodeSymbol(σ) 写 A[r,c]（r,c 与交错解码序锁步，直接写 GEMM 所需 swizzle 布局）→ s ← f·⌊s/R⌋+(x−c) → s 低于归一化阈值时 coalesced 32-bit load 补流（流跨 lane 交错使补位 load 天然 coalesced）；(3) tile swizzle + 确定性驱逐——大维度 GEMM 按固定 tile-swizzle 遍历序最大化复用并均衡 shared memory 压力，工作集超容量时按该静态序驱逐（recency 由 swizzle 序静态决定，无运行时记账），被逐 tile 的解压形式暂存小 decompression buffer 避免近期重复解压，压缩形式常驻全局内存；(4) 生产者/消费者管线重叠——解码 warp 只用整数/LSU 管线（概率表 load、状态更新、shared memory store），GEMM warp 只用 shared memory load + tensor core MMA，两物理分立管线由 warp scheduler 同周期 co-issue，四阶段 shared memory ring buffer 让解码领先若干 sub-tile。
  - 实验比较：naive 基线（DietGPU ANS decode + CUTLASS GEMM 分离两段）；CUTLASS 原生 GEMM；SOTA 无损压缩 NeuZip、DFloat11（H200 微基准）；KTransformer（OOM 场景 CPU offload 对比）。指标：TFLOP/s vs batch size（1–64、4096 input tokens）、逐步优化分解（tile 对齐 → 双缓冲）、A100/H200 跨架构对比。
- 后端平台是什么，配置是什么。
  - NVIDIA A100（80 GB HBM2e 2 TB/s；tile 32×128）与 NVIDIA H200（shared memory 更大、支持 tile 64×256）。PyTorch 2.5.1、CUDA 12.1。
- 评估性能的软件/脚本是什么。修改了什么。
  - 基于 DietGPU（https://github.com/facebookresearch/dietgpu）的 ANS 内核扩展出 tile 粒度解码，基于 CUTLASS（https://github.com/NVIDIA/cutlass）实现 plugin 式投影算子与 tensor-core GEMM 微内核，并提供 PyTorch 直接调用 wrapper。论文自身 kernel 代码未找到公开仓库（arXiv 2606.15789）。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 评估原理：单层投影 GEMM 微基准（batch 1–64、seq 4096）实测 TFLOP/s。输入 = 压缩 tile bitstreams + offset 表 + per-layer codebook + 激活 tile。全流程：每层开始解码 warp 把 codebook 拷入 shared memory T̃ → 循环 K_tiles 个 K-tile：warp 0 按 offset 从全局内存取压缩 substream，各 lane 独立 rANS 状态机（x←s mod R → 查 T̃ → 写 shared memory swizzle 布局 → s←f·⌊s/R⌋+(x−c) → 阈值重归一化 coalesced 补位）解出权重 tile A(b)，置 ready[b]←1；warp 1..W 等 ready 后从 shared memory 读权重 tile 与激活 B(k)、tensor core MMA 累加 C，消费完置 ready[b]←0 → 块级同步，双缓冲交替 → 输出 C tile → 上报 TFLOP/s。结果：tile 对齐解压（vs 分离两段）3.3–8.2×（Qwen-1.5B 3.66×、Llama-405B 8.20×）；再加双缓冲后总计 4.0–10.1×（Qwen-1.5B 4.41×、DeepSeek-67B 6.71×、Llama-405B 10.06×）；A100 大 batch 达 CUTLASS 的 1.0–1.1× 内、H200 最高 1.2× 超越 CUTLASS；vs NeuZip 最高 ~10×、vs DFloat11 ~6–7×、vs KTransformer prefill 7.7× / decode 18.1×。小 batch 时 tensor 管线先耗尽、内核 decoder-bound（退化为 decode-then-GEMM 行为）；大 batch 时 GEMM 主导、解码被完全隐藏、接近完全重叠。

## BAAP: Coupling Compute-in-SRAM with DRAM Banks for Near-Memory Processing

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现 = 在银行级 PIM 后端（UPMEM 改）新增 AP 运行时算子与"访存-计算重叠"调度：(1) 位并行/位串行 SIMD 算子——ap_and/or/xor（3/3/4 周期）、ap_add/ap_sub（8n+2）、ap_mul（4n²+4n）、ap_redsum（n）、ap_eq（n+4）、ap_merge（谓词合并，4），由 ASU 展开为 CAM 搜索/更新微码序列，在位切片布局的 32x36 子阵列链上对整列元素同时执行；(2) DirectAP 算子——ap_search/ap_searchacc/ap_update/ap_set_tags（1–2 周期）直接暴露 CAM 语义，伪指令 ap_regex 对长度 m 文本穷举匹配长度 k 模式（<m−k 周期、支持通配符）；(3) VPU 重叠调度——AP 计算当前向量时非投机预发射下一向量 load/store 到 DMA 引擎（命中五级流水线访存级，附加一个向量大小缓冲），把位串行长延迟算术与 bank 级 DMA 传输重叠；(4) 运行时布局管理——baap_set_mode(mode, m) 执行 drain-flip-reload 在 scratchpad（字节寻址）/SIMD（位切片）/DirectAP（列连续）三布局间切换（纯 DPU 侧 DMA strided 访问实现，无新增硬件；最坏 2×6 KiB÷72.58 MB/s ≈ 0.171 ms，约 6×10⁴ 周期后摊平）。实验比较：VPU 开/关消融（GPT-2 Large prefill GEMM vs decode GEMV，周期三分类 Overlap/Idle/Compute-only）、UPMEM 标量 DPU、主机侧 AP（PUMICE [52]）、PrIM/Phoenix/基因组负载；指标 = 加速比、带宽饱和。

## BULLETTIME: Time Dilation for High-Fidelity Tracing

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 BULLETTIME：基于 Intel Pin 3.30 的运行时 tracing 框架，核心是 time dilation（时间膨胀）调度——把"tracing 引起的 I/O 延迟跨线程不对称"均衡化，恢复 traced 执行相对 untraced 执行的行为保真度。正确性模型：key state（如内存连续性研究中的空闲物理内存布局 + 应用虚拟-物理映射）与 key operation（修改 key state 的操作）；正确性条件 C1（tracing 框架不得新增修改 key state 的操作）与 C2（key operation 顺序在 traced 与 untraced 执行间一致）。Algorithm 1 按每线程 L 个操作的窗口统计各线程 tracingDelays、取 maxDelay，向较快线程注入 injectedDelay = maxDelay − tracingDelays[thd]，把每窗口"tracing 延迟 : 原始操作"比值拉平（L=1 即 lockstep；L>1 把重排限制在单窗口内）。实现为四组件：(1) BULLETTIME Controller（Pin 内，蓝色）——拦截各线程 trace buffer 填满的 I/O 事件，用 EWMA（窗口 5s、衰减率 0.5）跟踪每线程 progress（指令数，内核态/用户态按各自 IPC 加权）与 tracing delay，计算注入延迟并负责 trace 持久化（独立进程实现，因 Pin 3.30 中 pintool 内 O_DIRECT 无效）；(2) Buffer-Driven Delay Module（Pin 外，橙色）——在下一次 buffer 填满事件时向应用线程注入延迟；(3) Sleep Dilation Kernel Module（Pin 外，橙色）——用 kprobes 插桩内核函数 schedule_timeout 与 hrtimer_nanosleep、放大睡眠时长以放慢系统守护线程（khugepaged 等；仅对 TASK_INTERRUPTIBLE 任务生效），膨胀因子 = 被 trace 应用 CPU 时间 / 等待 trace 落盘时间；(4) 可选 zstd level -7 在线压缩（BT-Comp）以空闲 CPU 换 I/O。
  - 实验比较 6 个配置：Untraced（无 tracing 开销，行为基准）、DynamoRIO drmemtrace（LZ4 压缩）、Empty-Traced（全插桩但不落盘，隔离插桩开销 vs I/O 开销）、Disk-Traced（异步 write() 落盘，主流做法）、BULLETTIME、BT-Comp。指标：按页大小分桶的物理内存覆盖 CDF、Misplaced Memory %（对 Untraced 分布的总变差距离，越低越好）、归一化运行时间、GET/UPDATE 平均延迟、GET:UPDATE 完成数比值；消融：D-I/O → +HP → +AD → +KD → +Comp 逐项叠加。
- 后端平台是什么，配置是什么。
  - Linux 6.13、Intel Core i7-8700 3.2GHz（6 核 12 线程）、SATA 三星 870 EVO SSD（约 0.4–0.6 GB/s 写带宽；Table II 中该配置数据生成率 : I/O 带宽比值 33–63×，处于谱系中间档；参考：CPU DDR4/PCIe4.0 3–6×、DDR5/PCIe4.0 7–18×、DDR5/PCIe5.0 3–7×、GPU GDDR6X/PCIe4.0 143–250×、HBM2e/PCIe5.0 133–200×、HBM3e/InfiniBand 49×）。带宽比值是论文论证的硬件核心变量：trace 数据产生率（与内存指令频率、线程数成正比）远超存储带宽时必然出现 bursty、不对称的 I/O 停顿。

  - 论文实现 = Pin 3.30 pintool（记录所有 load/store 的目标虚拟地址与访问宽度；每 30s 并发快照页表记录虚拟-物理翻译；每线程 2MB trace buffer，I/O 事件只在 buffer 填满时发生）+ 独立 Controller 进程（经 hugetlbfs 共享内存取 trace、命名管道通知 buffer 可用/已落盘、维护 EWMA 元数据、O_DIRECT 落盘、可选 zstd 压缩）+ Linux 内核模块（kprobes 改 schedule_timeout/hrtimer_nanosleep 睡眠参数，sysfs 控制膨胀因子）。对比工具：DynamoRIO drmemtrace（未修改）。工作负载：Llama（llama.cpp 推理，固定起始 seed）、GAP 套件 PageRank、Memcached + YCSB A（MemA：预载 10M 个 1KB 对象 + 100M 请求 50/50 读写）、自建 MemDY（500M 请求、80/10/10 读/写/插入、对象大小 1B–1KB 均匀分布，模仿 Meta ETC）；同步研究为 Memcached 双客户端读-写（同一 key 反复 GET/UPDATE，item 大小 1–512KB 扫描，各自单 worker 服务）。

## Breaking Barriers in Atomic Scaling: A Hardware–Software-Collaborated Framework to Deconstruct RDMA Atomic (Fusa)

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## Bringing Near Data Processing into the Low-Bit Floating-Point Era

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 NDP（PIM）后端的低比特 FP GEMM 指令级调度优化（编译期决定、运行期执行，近似层次匹配——是编译期指令调度而非运行时 kernel 调度器）：(1) 去量化隐藏（dequantization hiding）——把与 QGroup 绑定的高精度 dequant 指令（部分和 × 激活 scale × 权重 scale）重排到 DRAM 行切换/缓冲 refill 造成的 PU 空闲窗口（free slot）内执行；一次 dequant 仅 8 cycle（2·t_CCDL）而行切换空闲 48 cycle（t_RP+t_RCD）；约束为只能前移、不能越过后续 dequant 与 scale refill 读、受 partial-sum 缓冲容量与 slot 空闲容量限制（Alg.1 逆序贪心）。(2) 面向 scale 的 dataflow 调度——loop tiling 与循环置换（Order1/Order2）、value/scale/partial-sum 缓冲分配、DRAM 行列映射按 QConfig 与交织布局联合决定，目标是最小化 row-buffer miss 与 dequant 造成的 DRAM 空闲。(3) 代价模型驱动的编译空间搜索——统计缓冲 miss/dequant/行切换事件并用解析式估算延迟，替代逐策略 cycle 仿真。

## CHIME: A Case for Efficient Long-Context Attention-FC Disaggregated Inference with DIMM-PIM

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现 = DIMM-PIM 后端上的 attention kernel 运行时计算与调度：(1) bubble-free pipelining——借鉴 FlashAttention 的 chunked tile 融合思想把 score/softmax/context 分 chunk 流水：bank PU 每算出一个 token 的 score 输出 O^s 暂存本地 result buffer，rank PU 立即经空闲的外部总线取回，adder 累加后 softmax 单元做 per-chunk softmax；全部 token 处理完后以 streaming chunk-wise 做跨 chunk 归一化得全局正确 S，S 元素写回 DRAM 与后续 context 计算继续流水。内部总线（bank PU↔bank）与外部总线（rank PU↔bank PU/shared buffer）解耦，bank PU 计算与 rank PU 传输并行。bubble-free 条件 = 跨芯片传输时间 T_comm ≤ bank PU 计算时间 T_comp，其中 T_comm = L_t×N_gqa×N_chips/B_rk、T_comp = L_t×E_h×⌈N_gqa/N_cmr⌉/(B_bk×N_bk×N_hc)，推出 head 映射约束 N_hc ≤ E_h×B_rk×⌈N_gqa/N_cmr⌉/(B_bk×N_bk×N_gqa×N_chips)：MHA(N_gqa=1) 取 N_hc=8、GQA-8 取 N_hc=1（表 I/II 配置）。(2) hybrid-grained re-layout——rank PU 上的 re-layout 单元在传输过程中做 in-flight 数据变换：fine-grained 把单元素各位连续排进单 chip 的 burst beat（元素不跨芯片，FP16 的 16 bit 放两个连续 burst beat 存入 Chip 0），coarse-grained 把每个 head 映射到 N_hc 个芯片（N_hc=8 时每个 burst beat 只含单 head 元素、每 head 分布到 8 chips；每 head 1 chip 时 8 个 head 的元素混排一个 burst beat）；offload 时 QKV 先入 rank PU 片上 SRAM 重排再写 DRAM，onload 反向。
  - 实验比较：硬件消融 baseline = bank-level CHIME-PIM 但 head 计算跨芯片映射 + CPU 辅助 re-layout（按 [68] 保守估计为读旧布局+写新布局的访存时间）；指标 = attention 延迟。结果：bubble-free pipelining 使 MHA 延迟 -27.9%、GQA -74.4%；hybrid re-layout 最多 -17%（收益随 token 长度增大占比下降，因计算主导，但 re-layout 开销每层每 token 累积仍需消除）；全部硬件优化后 CHIME 1.42–4.18× 加速；所有 bank-level 实现较 rank-level DIMM-PIM (R-DP) 快 >1.5×。
- 后端平台是什么，配置是什么。
  - CHIME-PIM（DIMM-PIM）：DDR4-3200，每 DIMM 2 Rank（8 chips）× 4 Bank Group × 4 Banks；2TB 容量、等效带宽 13.0TB/s（CHIME bank PU）vs 1.6TB/s（rank-level R-PIM）；DRAM 时序 BL=4:CCD=4:RRD=4/8:RCD=22:RAS=52:RP=22:RC=74:CL=22:WL=16:CDLR=4/12:WR=24:CCDL=8:RTP=12；bank PU 计算访存比 N_cmr=n（对应 GQA-n）。GPU 侧 8× A100（AttAcc roofline 模拟执行 FC）。

  - CHIME-PIM-sim：基于修改版 DRAMSim3（https://github.com/umd-memsys/DRAMSim3）的 trace-driven 逐周期模拟器，新增 PIM 命令（PIM_WR_R/PIM_LD_SB/PIM_WR_SB/PIM_MAC/PIM_RD_RB）、相应时序约束与 FIFO 调度方式。GPU 侧集成 AttAcc（https://github.com/scale-snu/attacc_simulator）的 roofline 模拟。

## COSM: A Cooperative Scheduling Framework for Concurrent PIM and CPU Execution on Mobile Devices

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现 = PIM 后端上 PIM 命令与数据传输的运行时调度：(1) idleness-aware scheduling——IWE 按 Algorithm 1 模拟 FR-FCFS 顺序估计每 bank 最早服务周期：对每 bank 最早请求算 ready cycle（bank 三态：Row-Closed 需 ACT 延迟 tRCD、Opened-to-target-row 按行打开周期、Opened-to-different-row 需 PRE+ACT 延迟 tRP+tRCD），循环内优先当前 rank 的最早就绪请求并 t←t+tBL，否则跨 rank 切换取全局最早，得 window_bank（每 bank 最早服务周期）/window_bus（所有请求最小服务周期）；Command Arbiter 据此推迟过早的 ACT 命令，把 PIM 执行塞进 ACT 与数据访问间的 bank 空闲窗口（窗口须 ≥ tRP+tRCD + 至少一列），把 PIM_RdBuf/WrBuf 塞进 window_bus 之前的 bus 空闲窗口；CPU 请求到达时不立即发 PIM_Pause，而是延迟到"不推迟下一次 CPU 访问的最后周期"再发。(2) overlapped scheduling——把 PIM workload 切成无数据依赖的 tile（如矩阵乘子矩阵，reduction 由 CPU 做），跨 tile 并行发不同阶段命令（收集 tile T_i 结果的同时执行 T_{i+1}），阶段间用 PIM_Barrier 保证依赖。(3) 命令优先级：PRWQ 的 PIM_RdBuf/PIM_WrBuf（独占外部总线，瓶颈）> PIM_LdBuf/PIM_StBuf（清空 buffer 防阻塞后续总线命令）> PEQ 的 PIM_Exec（匹配当前 bank 空闲窗口）；同 bank PRWQ 命令保持到达顺序。实验比较：CPU-first（Chopim 式）调度、4 配置消融（Base=标准读写+三阶段串行 / Overlapped / Overlapped+Decoupled / All=再叠加 IWE）；baseline 硬件与平台见 实验_硬件架构.md 同名条目。结果：idleness-aware 较 CPU-first 平均 PIM 性能 1.21×、多利用 37.0% 可用带宽（剩余 <1% 未用）；Overlapped 使 CPU 性能 +3.7%（高行命中率的 PolyBench 内核因激进重叠引入额外行切换）、Overlapped+Decoupled +11.5%、All 保持 CPU 降速 <5%。
- 后端平台是什么，配置是什么。
  - LPDDR5-6400 PIM：2 Channels × 2 Ranks、16 banks/rank（4 BG × 4 Bank）、bank 级 PIM 单元 16/rank（1GHz、6.4 GB/s、6.4 TFLOPS）、1kB bank buffer；主机 Snapdragon 888 级 CPU（8 核 @2.1GHz、OoO、FR-FCFS 调度）；PIM 命令长 nPTL=128；PEQ/PRWQ 深度各 2/bank。

  - 修改版 Ramulator2 + 自动化脚本：`./build.sh [并行度]` 编译、`cd simulations && ./run_script.sh figure8|figure10 [并行度]` 批量仿真产出 CSV（simulations/scripts_result_processor/），Excel 模板 plot_figure8|10_ae.xlsx 绘图。PIM 侧 LLM trace（DeepSeek-R1-1.5B 等）由 Python 脚本生成，CPU 侧 trace 由 zsim（SPEC CPU2017/PolyBench-ACC）与 Frida 真机插桩（移动应用）采集后反复回放生成背景流量。修改：控制器新增 pim_arbiter_cpu_first_o3_pred.cpp（idleness-aware 调度、PEQ/PRWQ、命令仲裁），LPDDR5-PIM 模型新增可抢占执行与带宽解耦传输命令。

## ConBin: A Performance-Convergence Framework for Wafer-Scale Chip Binning

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似归类，反馈：非 GPU kernel 实现，而是 WSC 空间加速器上计算任务与通信的运行时调度：bin 感知 workload 映射 + 通信序列调度，性能评估软件见 实验_硬件架构.md 同名条目。）实现 = (1) bin 感知 workload 映射：把有向负载图 WG=(W,D)（节点为计算任务如 GEMM/attention 层，边 d_{i→j} 为数据依赖/通信任务）单射映射到修复拓扑 TG=(V,E)，最小化期望最大链路 contention MLCC_exp=max_e LCC_exp(e)，LCC_exp(e)=Σ p_{i→j}（路由过 e 的传输频率权重，式 6），用 SEGA（Geatpy，种群 100、最多 100 代、10 代停滞早停）优化，命中当前 bin 目标 MLCC_exp^target 后自适应升级到高一档 bin（最多 2 次、30 代内未达标回退上一有效目标）；(2) 通信序列调度：把通信时间线切成 CAP（contention 近似稳定区间，三粒度批处理 b1≤b2≤b3 + 历史感知 contention 传播因子 μ∈(0,1)），用多染色体 NSGA-III（种群 120、最多 100 代）最小化各 CAP 期望最大链路/目的端 contention Φ，同样按 bin 目标 Φ^target 自适应升级；(3) pre-binning：按硬件指标 F 把芯片分 B+1 个分位组，每组轻量采样（top 5–15%）跑缩减版映射/调度得到该 bin 的优化目标。实验比较：CB*+NFT（CUPOKer，ISPD 2020 CS-1 WSE 负载分配冠军、非容错）、CB*+SK（Si-Kintsugi，hop 数最小化容错调度）vs CB*+Ours-SW* / Ours-WM / Ours-ALL*；结果：Ours-ALL* 方差降幅最高 79.21%（CB*+Ours-SW* 仅 9.16%）、speedup Ours-WM 至 1.85× / Ours-ALL* 至 2.39×；分 bin 后 Ours-ALL 对 CB*+SK* 获 2.80× premium-bin yield 与 2.64× SECC（8 bins）。

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## DCC: Data-Centric Compilation of Machine Learning Kernels for Processing-In-Memory Architectures

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 DCC 编译器对 PIM 后端上 memory-intensive kernel 的自动"数据分区 × 计算循环划分"联合调度：对每个 kernel 枚举 data-tile（张量维在 PIM group/core 上的分配）与 compute-tile（loop 变量范围映射）tiling drafts，经剪枝（等价映射去重/SIMD 对齐/执行性能等价）+ XGBoost 耦合预测器选出端到端最优 draft，生成 group 级广播/bank 级并行的 DRAM 计算命令调度；同时调度输入/输出数据重排（GPU shared memory staging：串行 Host 读 + 并行 N channel PIM 写，两侧均获 channel 级并行）。评测 7 个 kernel：AttAcc 上 GEMV、RED（reduction）、ATTN（GEMV/ATTN 输入尺寸 128，LLM 最常见每头维度）；HBM-PIM 上 GEMV、RED、VA（向量加）、RELU（ATTN 需 softmax 单元只有 AttAcc 有；AttAcc 无支持 VA/RELU 的 near-bank 计算单元）；精度 FP16（MT-NLG 另测 FP8）。端到端：GPT3-13B、LLaMA2-33B、MT-NLG-310B 推理。
  - 实验比较：(1) GPU-only；(2) AttAcc 默认实现（固定分布：batch/head→16 pCH、第一维→每 pCH 16 bank group、第二维→每 bank group 4 bank）；(3) AttAcc+DCC；(4) HBM-PIM 默认（沿用 AttAcc 数据分布）；(5) HBM-PIM+DCC；§2.2 另比 TVM compute-centric（T）与手工最优（B）。
  - 关键结果：AttAcc 上 DCC 相对 AttAcc 平均提速 1.26× GEMV、1.48× RED、1.23× ATTN（峰值 1.73×/1.66×/1.57×），整体相对 GPU 至多 13.17×（平均 3.92×）；RED batch 1、tensor 4096 达 3.94×；RED 1024 AttAcc 落后 GPU 0.59×、DCC 追平 GPU。HBM-PIM 上 DCC 相对 HBM-PIM 平均提速 1.53×/2.09×/1.64×/1.54×（GEMV/RED/VA/RELU），整体相对 GPU 至多 7.68×（平均 2.21×）；RED 1024/2048 HBM-PIM 落后 GPU 0.48×（固定 tiling 不满足 16-way SIMD 对齐）、DCC 平均提速 2.26× 使 2048 反超 GPU。GEMV batch 1→8：DCC 增益 HBM-PIM 1.33×→1.58×、AttAcc 1.14×→1.31×（head 32、输入 128）。§5.4 时间拆解：DCC 同时优化计算（1.58×）与数据重排（1.65×）；VA/RED/RELU 等重排主导 kernel 提速 1.67×、compute-heavy GEMV/ATTN 1.18×。LLM 推理：AttAcc_Full+DCC 平均 4.52× 对 GPU（LLaMA-2 峰值 7.71×）、1.75× 对 AttAcc_Full；QKV 生成 2.58×、projection 2.91× 对 GPU（AttAcc 固定 tiling 在这两层落后 GPU 1.25×，DCC 使它们移上 PIM）；MT-NLG-310B 大 batch（≤64）/8×A100 下 DCC 较 AttAcc Base/Full 1.59×/1.67×；能耗效率平均 1.24×。在线动态预测：未见过 shape 仅在最初 ~160 查询有编译开销，之后收敛到离线 DCC 水平。

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## DisDP: Disaggregating Compute, Network, and Storage for Model-Sharded Data-Parallel Training

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 DisDP 的 SmartNIC-managed contention-free collectives：把 MSDP 训练中的集合通信（AllGather/ReduceScatter）从 GPU/NCCL 整体卸载到 FPGA SmartNIC 上的 collective processing module，充当 GPU 显存与网络之间的运行时传输调度器。具体包括：(1) 两方软件 API `handle_t push(void* buf, size_t len)` / `handle_t pull(void* buf, size_t len)` / `void wait(handle_t)`：worker 与 PS 双向调用，push 把一整层 partial gradients 从 GPU 显存发出，pull 接收参数到 GPU/CPU 内存；调用返回 handle、异步完成，wait(handle) 阻塞到完成，使 PS 可预取参数。(2) SmartNIC 内独立的 push/pull processing unit，各配独立请求队列与独立流（类比 GPU stream），host CPU 经 MMIO 写入请求（含 handle 指针），处理单元出队后经 GPU 虚拟地址直接对 GPU 显存发 DMA（register_buf 预注册应用缓冲区），DMA 与网络收发按流水线重叠。(3) format conversion unit：按 SwitchML 的格式转换策略把 fp16/bf16 梯度转换为 SmartSwitch 可聚合的整数格式，固化在 SmartNIC 硬件流水线中（论文未展开位宽/缩放细节）。
  - 实验比较：(a) 与 NCCL AllReduce 的 algorithm bandwidth 对比（2/4/8 GPU，并发/不并发 GEMM）：并发 GEMM 下 DisDP 高 2%/35%/44%，无并发 GEMM 下高 8%/20%（4/8 GPU），因 push/pull 相对 AllReduce 流量最多减半且收发在 SmartNIC 执行、与 GEMM 零争用；(b) 消融 DisDP-GpuColl（由 GPU kernel 发起 push/pull 请求并轮询完成，与 GEMM 争 GPU 计算单元，模拟），DisDP 最高 1.58× 吞吐；(c) 端到端迭代分解：DisDP 几乎完全重叠计算与集合（Custom-175B），且集合时间再降 20%。

## Don't Surrender to Low QPS/$: Fast and Cost-Efficient ANNS with TridentANN

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## Dynamic Scheduling for AI Accelerators via TISA

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## ENEC: A Lossless AI Model Compression Method Enabling Fast Inference on Ascend NPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## Enabling Continuous, In-Field Introspection: The Programmable IPU Architecture

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为运行在 IPU（新异构后端：RISC-V 核 + 直方图/hash/循环加速器 + eFPGA 软逻辑）上的 introspection 程序（分析型运行时 kernel 算子）：输入是 HIT 的微架构内部信号（每次执行 32 个命名输入寄存器），程序按数据驱动方式运行（新数据到达即调用 _main，处理期间新数据被丢弃——Little's Law 下无 stall 时丢数据不可避免），把高带宽原始信号流（如 PICS 的 215 bits/cycle、256-cycle 窗口的 3 路活动信号）在片上聚合/过滤/统计后只导出低带宽高层洞察（直方图、PICS、失败模式计数）。kernel 经编译器 intrinsics/函数库使用直方图累加、hash、循环指令，IPU_pro 还打包 Verilog 软逻辑（eFPGA 位流）。四类 introspection kernel：①entangled 预取器状态机（eFPGA 软逻辑，每地址 1 cycle，300 行 Verilog）；②PICS 生成（每 cycle 更新 PSV + 每 400k cycle 归并输出，75 行）；③TensorCore 利用率直方图（单条直方图指令 + 循环指令，256-cycle 窗口，2 行）；④Gaze 逐 miss 根因分类（4 类失败模式直方图，20-cycle 处理窗口，50 行）。
  - 实验比较：①预取器 emulation 对比 entangled 原始实现（ChampSim，135 CVP traces，覆盖/准确/缺失率误差 <5%）；②PICS 对比 TEA 专用硬件（gem5，13 SPEC，平均相对误差 <3%，3 个应用 10-14%，丢 PC 覆盖 ≤0.37% cycles）；③GPU 利用率直方图对比聚合 PMU（AccelSim，21 GEMM，输出带宽 1.7 GB/s @108 SM、10/108 采样 0.16 GB/s）；④逐 miss 根因诊断对比 PMU/PEBS（ChampSim，189 SPEC traces，平均误差 <3.5%、中位 2.46%）。
- 后端平台是什么，配置是什么。
  - IPU 后端：32-bit RV32I 顺序 RISC-V 核，IPU_lite 最高 2 GHz、IPU_pro（soft-logic）1.3 GHz（7nm），32KB scratchpad SRAM，8KB 指令内存（2048 条指令），32 输入 IORegs + TS/TE/ADDR 触发寄存器，4-bit STATUS（PAUSED/ACTIVE-PAUSED/ACTIVE-RUNNING/FINALIZE/ERROR/UNDEFINED）；IPU_pro 另含 590 CLB eFPGA + 470 AIO tiles + 8×64×64-bit BRAM。被监控的 HIT 后端：CPU 前端（entangled，2 信号 64 bits）、CPU 核流水线（PICS，17 信号 215 bits）、GPU SM scoreboard（3 信号 4 bits）、L1D cache/prefetcher（Gaze，6 信号 132 bits）。对照硬件：CPU Zen2 4-core complex（31 mm²、4W）、GPU SM（3.475 mm²、1W）、BOOM（2.2 mm²）。IPU 与 HIT 时钟不同步（HIT 可 3-4 GHz），支持三模式：亚采样（1-in-2 cycles）、快 buffer 异步窗口处理、只限低频相或优化 IPU 速度。

## Harmonia: A Unified Hierarchical Scheduling Framework for Sparse Matrix Multiplication

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为稀疏矩阵乘法（SpMSpM）的分层运行时调度框架，含静态分析层、动态 Profiling 层、动态 Tuning 层三层：(1) 静态层离线按矩阵形状/全局密度/datatype 枚举候选 tile 形状 (T_M,T_K,T_N)，以操作强度 OI=OPs/Bytes 为目标、SRAM 可行性约束过滤，输出基线块形状、遍历顺序（k-outer 保持 C 驻留 / M,N 复用优先）与 SRAM 分区；(2) 动态 Profiling 层对 SRAM 中每个 tile 用精确 nnz 做轻量采样（tile 密度、行/列方差、聚类），细化 tile 形状（低密度扩张、高密度收缩、聚类对齐）并选择 InP/Row/OutP 数据流（InP 适合均匀中稀疏、Row 适合行方差大/聚类 A、OutP 适合均匀 A + 低密度 B）；(3) 动态 Tuning 层消费硬件反馈计数器（SRAM pressure、psum spill、MRN merge-depth、PE stall）在 tile 边界做数据流切换（InP↔Row↔OutP，规则见论文）与微重切块（K 缩小降 merge depth、M/N 限制 buffer/DN 负载），成本模型 Gain>α·Cost 控制是否重构，滞回 T=2~4 周期防振荡，最坏情况回退 1 次重构延迟（50 cycles）。
  - 实验比较 4 种调度 + oracle：Vesper 静态调度（baseline 归一化为 1.0×）、Misam-like 逐 tile 数据流选择（仅局部优化，忽略共享 SRAM 压力）、HYTE-like tile 编排（全局 tile 边界调整但 tile 内数据流固定）、Harmonia、静态最优 oracle（2.03× 上界）。全部在相同 32-row 硬件配置上模拟。指标：16 个 SpMSpM workload 平均 1.75× 加速（orani678 3.46× 接近 oracle）、端到端 4 个 DNN 管道 1.87×、SRAM 流量降 32%（Misam/HYTE 仅 10%，bcsstk10 上 Misam 反而 +39%、orani678 上 HYTE +50%）、off-chip DRAM 流量与片上 stall（HYTE 因固定数据流遇稠密簇 psum 溢出导致 stall 激增）、能耗 -40%、PE 阵列 16×16~64×64 与 SRAM 容量扩展鲁棒性。
- 后端平台是什么，配置是什么。
  - 后端为 Harmonia 稀疏加速器（基于 Trapezoid 行并行模板）：32 PE 行 × 32 FP32 MAC/加法器，0.5 GHz，峰值 1 TFLOPS；1 MB 片上 SRAM + 32 KB 分布式本地 buffer（每行 1KB、64B 宽）；off-chip HBM 2 TB/s；NoC 32-to-32 crossbar；总面积 7.51 mm²（TSMC 28nm 综合）。三种数据流（InP/Row/OutP）共享同一 PE 数据通路，仅 DN（16-to-16 Benes）路由、MRN（radix-16 加法树，merge-before-store 或 column-accumulate 模式）归约与 on-row buffer 策略不同，由 Reconfiguration Engine 在 tile 边界重编程。所有 baseline 调度在同一 32-row 配置上模拟以保证公平。

  - 自研 cycle-accurate 稀疏数据流模拟器（建模 MAC、MRN、DN、本地 buffer、SRAM、HBM，忠实建模 PE stall、psum spill、路由拥塞；动态调谐时注入 pipeline flush + DN/MRN 重编程 + buffer reset 的 20–50 cycle 重构开销）；数据通路 RTL 用 Synopsys Design Compiler（TSMC 28nm）综合评估面积，CACTI 7 建模 SRAM，HBM 能耗用厂商 datasheet。修改了什么：论文自研模拟器；Trapezoid/Vesper/Misam/HYTE baseline 按论文描述在同一硬件配置上重实现（未修改公开代码，均无公开 RTL）。

## HyperDrive: Hierarchical Exploitation of Memory Efficiency for GPU-Based FHE Acceleration

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  实现为面向 NVIDIA Tensor Core（TCU）的 RNS-CKKS FHE GPU kernel 集合，分层内存优化：(1) Inner-NTT 用 FP64 TCU 的 8×4×8 MMA（radix-64）执行——TLMOP（Thread-Level Memory OPtimization）把自动的 SMEM 填充 fragment 替换为细粒度寄存器数据访问：每个 warp 用 4 次 MMA（MMA1/2 把数据矩阵与 twiddle factor matrix TFM 的高/低 16-bit 分量相乘、MMA3/4 完成第二级 radix-8）+ Bit-Merge + ModRed + EWMult 完成一个 64 点 Inner-NTT，全程零 SMEM（仅输入读/最终输出写各一次）；TransOP（Transpose OPtimization）利用 Fragment A/B/D 跨线程数据分布用 MMA 隐式完成 4-step NTT 转置（MMA1/2 数据视为 Fragment B、MMA3/4 视为 Fragment A 并交替选奇/偶列），避免显式 SMEM 转置。(2) Outer-NTT 用 RowMaj（Row-Major NTT）：密文/密钥/明文在 GPU 生命周期内保持预转置布局（编码/解码时对单 limb 数据零成本转换，跨 limb 转置不必要），把 3/4 的 GMEM 访问从列主序 strided 变成行主序全 coalesced；TFOP（Twiddle Factor access OPtimization）：negacyclic 卷积 twiddle 顺序读（INTT 预乘 N^{-1} 省一次模乘）、外层 Hadamard 用预排序 TF-XY、内层 Hadamard/Residual NTT 用 SMEM 中的 TF256（每 block ≤256 元素）、Inner-NTT 的 8×8 TFM 存 SMEM 跨 warp 复用。(3) 操作级 COOP（Memory-Aware Kernel Co-optimization）：RowMaj 消除多 pad 约束后把 (BConv2-NTT1) 与 (NTT2-IP) 融合（Alg. 2/3），高维中间数据驻留片上（BConv 约减沿 α' 维、IP 在寄存器内直接累加），避免 L+α-α' 维物化到 GMEM；IP 的 evk（尺寸为输入 2 倍）在 NTT 执行期间预取到片上隐藏延迟；放弃 lazy reduction 改为每乘即约减，把中间结果位宽减半、寄存器压到 72/线程（35.3% occupancy）。(4) CRPMAC（Ciphertext-Reused PMAC）：BSGS PCMM 中把所有 GS-Rots 推迟到最后、按 GS 方向批处理 PMAC，单个 baby-step 密文与一批明文相乘复用（[22] 按 BS 方向批处理且每轮重复加载同一 BS 密文），并对 EWArith kernel 用向量化访存。(5) Bootstrapping 级操作重排：GS 相位 ModDown 后紧跟 ModUp 时把 EWSub 提前，使 ModDown 的 INTT 与 ModUp 的 INTT 可批处理、合并进 (BConv2-NTT1) kernel（同时融合 EWArith）、改善 (NTT2-IP) 负载均衡（图 13）。

## Intermittence-aware Speculative Page Coloring for Secure NVM

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 近似匹配（论文本体为编译器/运行时协同内存管理，此处覆盖其运行时页管理组件 page manager）：在 MCU 上执行页级调度与安全数据传输——每条 load/store 执行前按编译器 hint（页号 P + 颜色 C）直接索引 Buffer Table（BT，软件页表，条目数 = SPM frame 数）判定 P 是否驻留 frame C；命中则按运行时计算的页内偏移访问；未命中（misspeculation：实际功率周期长于预期、两页争用同一 frame）则把 frame C 中的旧页 AES-XTS 加密写回 NVM、从 NVM 取新页解密载入并更新 BT；Write Tracking Queue（WTQ，1,028B）记录脏页（脏页号 + frame 号）供断电时只持久化脏页。加密用 MSP430FR5994 的 AES 加速器/库实现 AES-XTS（16B 块，SPM 内部缓冲 4 块凑成 64B 页后原子 flush）。崩溃一致性：V_backup 阈值调高保证每次 page manager 调用 failure-atomic；JIT checkpoint 按 WTQ 持久化脏页 + 保存寄存器/heap/stack + 翻转 NVM 完成标志位；恢复时按标志位判定 checkpoint 完整性（0 则 abort）。page manager 代码 491B、WTQ 1,028B。
  - 实验比较：同一真实硬件上比较 MANATEE runtime vs Mapi-Pro [9]（ILP 静态 hot/cold 映射 + 整 SPM checkpoint，4.9×）、NVSRAM [56]（整 SPM checkpoint，4.5–4.6×）、Memory Coloring [63]（无滑动窗口着色 + 永久 spill，1.93×）、Unsecure（无安全基线）；指标：归一化执行开销（MANATEE thermal 1.71×/RFHome 1.71×/solar 1.72×）、页 miss rate（MANATEE ~0.99% vs 无滑动窗口 2.05%，降 ~50%）、性能分解（CRC32 加解密占 ~74%；平均执行 ~58%/页管理 ~25%/加解密 ~16%）、误估敏感性（100% 误估最多 +16% 开销）、wear-leveling 开销（+15%）。

## Lembas: Cost-Efficient Genome Alignment with External Memory and FPGA Acceleration

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是 FPGA 硬件架构，此处从"FPGA kernel 实例化数量与运行时调度/数据移动"角度记录）实现为三个 FPGA kernel 集合 + 软件 orchestrator 的运行时调度：seed 阶段 16 个 columnsort merge-sort kernel（各独占一对 HBM pseudo-channel，单发射 16-to-1 merger，250 MHz/4 GB/s，合计饱和 ~8 GB/s 双工 PCIe），minimizer parse 与 anchor matching 与 columnsort 共享同一 bitfile；chain 阶段 4 个 chaining kernel（各单 PE，分数前向传播流水，II=1）；extend 阶段 16 个 kernel × 16 PE 脉动阵列 + 8×8 tile traceback（每次预取 4 tile 缓解 HBM 延迟）。软件 orchestrator 负责：按阶段把对应 bitfile 编程进全部 FPGA（时分复用）、调度 PCIe 上 NVMe↔FPGA 的数据搬运（minimizer 流/anchors/chains 作为中间数据驻留 NVMe）、列排序转置后 host 侧多 KB 大块 memcpy 重组、以及少量计算。
  - 实验比较的核心是 kernel 配置/数量选择对性能的影响：(1) 排序 kernel 设计空间——16-to-1 单发射 vs 更宽 fan-in（32-to-1 减少 sweep 数但占芯片更多、可放数量更少；更小 fan-in 省空间但 pass 更多）；16 个 kernel 已饱和 U50 PCIe 带宽（即该器件最大性能），32 个无法布局布线；256 MB 列需 6 次 sweep（16B 元素、单发射）。 (2) chaining kernel 数量由 PCIe 带宽而非芯片资源决定（表 IV 资源占用低，仍只放 4 个）。 (3) extend kernel 16×16 PE、8×8 tile 满足历史寄存器时序（更大 tile 不满足时序），480 bit/tile 对齐 512-bit HBM 接口。 (4) 多 FPGA 扩展性：2 FPGA 默认配置性能最优且成本最低；3 FPGA 时 4 个 NVMe 几乎饱和成为瓶颈（12 核 host CPU 未满载）。

## Lit Silicon: A Case Where Thermal Imbalance Couples Concurrent Execution in Multiple GPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是节点级 GPU 功率管理运行时层，不修改 kernel 算子/编译框架/硬件 RTL，此处从"运行时对 GPU kernel 级性能的检测与功率调度"角度记录）实现为约 200 行 PyTorch 的节点级功率管理运行时层，用于检测并缓解多 GPU 节点内的 *Lit Silicon* 效应（热不平衡 + 并发计算通信 C3 耦合导致的节点级性能波动）。包括：(1) 检测——Algorithm 1 LEADVALUEDETECT 基于 Chopper 工具解析 PyTorch trace 得到各 GPU 上每个 kernel 的起始时间戳，对每个 kernel 计算 lead value（本 GPU 起始时间相对最晚 GPU 的差值），按 GPU 聚合（默认 sum=lead 曲线下面积，也可 max/last，窗口平均后输出）以识别 straggler（lead≈0、更热更慢）与 leader（lead>0、更冷更快）；(2) 缓解——Algorithm 2 INCPOWERGPU 按归一化 lead 计算各 GPU 功率上限增量（global scale 用历史最大 lead 衰减调整幅度），Algorithm 3 ADJPOWERNODE 在节点级功率上限与 GPU TDP 约束下均匀回退功率上限；连续采样-调整直到收敛（功率上限分布稳定后可停用或长周期采样）。三种使用场景：GPU-Red（无节点上限，仅降低 leader 功率省电）、GPU-Realloc（节点上限下把 leader 功率重分配给 straggler 提升吞吐）、CPU-Slosh（节点上限下把闲置 CPU 功率预算转移给 GPU）。需要 root/管理员权限设置功率上限（amd-smi），不修改任何 GPU kernel。
  - 实验比较：(1) 三种使用场景在默认配置（Llama 3.1 8B、FSDPv2、bf16、b2s4、功率上限 700W、节点1）下的收敛行为——GPU-Red 平均功率降 4% 吞吐不变；GPU-Realloc 吞吐 +3% 平均功率不变；CPU-Slosh 吞吐 +4%（功率上限 550W 时达 6%）但 GPU 功率 +3%；功率重分配收益递减。(2) 与解析性能/功率模型预测对比（表 III）——功率预测误差 ≤1%（GPU-Red 1.05 vs 1.04、GPU-Realloc 1.00 vs 1.00、CPU-Slosh 0.97 vs 0.97）；吞吐预测约为实测 2 倍但趋势一致（1.06/1.10 vs 1.03/1.04）。(3) 敏感性分析（表 II 旋钮：节点 0/1、模型 Llama 3.1 8B/Mistral 7B v0.1、FSDP v1/v2、精度 bf16/fp8、b1s4/b2s4/b4s4/b1s8/b2s8、迭代 1000、采样周期 4/7/10、warm-up 3/6/12/25/50、窗口大小 1/2/3/5、聚合 max/last/sum、最大调整 5/10/15/30、scale global/local、功率上限 700/650/600/550/500W、功率预算 10/20/30/50W）——各旋钮下收益基本一致，影响最大的是初始功率上限；收敛后的功率上限分布可跨框架/模型/上限复用（图 12）；节点0（更多 straggler）收益略低；500W 功率上限变异性差；warm-up 长度不影响收敛（图 11）。(4) MoE 对比（图 16）——DeepSeek V3 16B（Primus+torchtitan 8 路专家并行，all-to-all 不重叠）lead 值更小但有稀疏大 spike，算法仍收敛到与 dense 训练相同的功率分布与节电。(5) 检测频率与开销——三个月内调两次（3.5%、4% 节电），建议周/月粒度；每样本 dump+处理约 4 秒，约 80 秒（20 样本）达稳定功率分布。

## LoKA: Low-precision Kernel Applications for Recommendation Models At Scale

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现：**LoKA Dispatch** —— 逐算子（per-operator）的低精度 kernel 编排运行时。它把每个 GEMM 当作独立优化问题，从多个低精度库（TorchAO、DeepGEMM、FBGEMM）及其 recipe（tensorwise TW / rowwise RW / blockwise BW 缩放、快速累加 fast accumulation、前向/反向不同数据类型等）的候选实现集合中，选出"满足精度约束下吞吐最高"的 kernel。核心机制：(1) 用 LoKA Probe 的 MERE 分析先过滤候选——期望误差低于保守阈值（典型 MERE < 0.2）且 Probe 测得加速比 > 1.05× 的实现才进入候选集，再从中选实测吞吐最高者；(2) 实现为一个自定义 autograd function（通用适配器），模型初始化时做一次变换 pass，把目标线性层替换为 LoKA-aware 包装层（语义与标准 PyTorch Linear 相同），前向/反向分别路由、可各用最优实现（前向/反向张量 shape/layout/datatype 常不同）；(3) 推理时 kernel 选择完全静态确定，训练时动态切换仅作为对大幅分布漂移（如节假日用户行为突变）的安全阀，避免频繁重编译。
  - 实验比较什么：将 LoKA Dispatch 与"对所有 GEMM 统一应用单一库 recipe"对比（Wukong、compute-only 模式消除通信影响）：TorchAO TW 1.05×、TorchAO RW 1.01×、TorchAO 混合 recipe RW GW HP（前向 rowwise、输入梯度高精度、权重 backward tensorwise）1.08×、DeepGEMM BW 0.85×、FBGEMM RW 0.98×，而 LoKA Dispatch 混合策略 1.12×——超过最佳单一 recipe 1.08×，证明逐算子选择的价值。另对比 27 个生产 LRM GEMM shape（从 (2048,256)@(256,768) 到 (2048,123200)@(123200,1024)）在 H100 上纯计算吞吐 vs 含量化开销的端到端：FP8 相对 BF16 平均仅 1.6×、有效 TFLOPS < 硬件峰值 20%、量化开销占端到端 GEMM 延迟 >30%、含 layout 操纵等内存分配开销时 FP8 可差于 BF16。
- 后端平台是什么，配置是什么。
  - NVIDIA H100、B200、GB200（NVL72）与 AMD MI300X、MI350X 集群（CUDA/ROCm 后端），16–256 GPU；单次 kernel 基准在 H100 上跑 27 个 shape。集成三个开源低精度 kernel 库：TorchAO（pytorch/ao）、DeepGEMM（deepseek-ai/DeepGEMM）、FBGEMM（pytorch/FBGEMM）；评估含 torch.compile 图编译。

## LÆGIS: Pinpointing and Addressing Performance Overheads of GPU-based Confidential Computing

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是硬件架构设计——HBM 内 IV Bank（见实验_硬件架构条目），此处从"CPU 侧加密计算在 UVM driver 空闲窗口的运行时调度/卸载"角度记录）实现为 UVM fault-service 路径上的预加密调度器：在 GPU CC 的 UVM batch 处理期间，把 AES-GCM 加密这一运行时计算从关键路径卸载到 driver 线程的空闲时段执行。关键运行时行为：(i) 识别两类空闲——true idle（两个 fault batch 之间 driver 线程睡眠期，平均占 driver 执行时间 87%）与 false idle（batch 内 fault preparation 阶段 AES 指令未执行的时段）；(ii) 调度器按候选选择策略从 fault buffer 下一批条目 / CPU 驻留页 / 随机页中选页，用 CPU 侧 IV Bank 重建 IV 后乱序预加密；预加密密文直接提交（无 PipeLLM 式预测 IV 的误预测 NOP/丢弃问题）；(iii) 预加密完成的页到达时直接标记 ready、跳过关键路径加密，且批量提交提升 PCIe 突发利用率。变体按"空闲类型 × 候选策略"组合：F-LÆGIS（false idle + fault buffer 候选）、IR-LÆGIS（true idle + 随机候选）、IN-LÆGIS（true idle + fault buffer 候选）、IFN-LÆGIS（false+true idle，先 fault buffer 后顺序页）。每个变体都评估默认（Pt=51%）与 aggressive（Pt=1%）预取版本。
  - 实验比较：各变体 vs Baseline（同步加密关键路径）vs Ideal（加密开销隐藏）：F-LÆGIS 1.51×、pF-LÆGIS 1.37×、IR-LÆGIS 1.38×、pIR-LÆGIS 1.62×、IN-LÆGIS 2.17×、pIN-LÆGIS 2.10×、IFN-LÆGIS 2.22×（最大 3.13×）、pIFN-LÆGIS 2.74×（最大 5.05×）；pIFN-LÆGIS 把 driver active 占比提升到 88.3%（SSSP 99.4%、FLASHATT 96.8%）。另对照 CPU 侧加密能力增强：MT-Baseline（多线程约 7 GB/s，默认预取下平均 -35%，多线程需大数据量且无法解决同步瓶颈）、X-Baseline（CPU 硬件 AES，1.19×/1.58×）、X-IFN-LÆGIS（2.13× 默认 / X-pIFN 3.57×）——证明单靠"利用空闲窗口的机会性预加密"即可接近 Ideal，无需换更快加密硬件。

  - CPU 端：5th Gen Intel Xeon 6530 Gold @2.1GHz（32 核）作为 TDX 信任域宿主（TDX 1.5 + QEMU 7.2.0 TDX patched）。UVM 加密路径为 kernel-space：nvidia-uvm 模块的 Cryptography Services Library（CSL）→ libspdm → Linux Kernel Crypto API（LCA）的 crypto_aead_encrypt，经单 kernel 线程的工作队列串行执行（实测约 1.3 GB/s，即 2.98 µs/4KB 页；TME-MK AES-XTS 硬件仅 40 cycle 开销，瓶颈在软件加密路径）。GPU 端：NVIDIA H100（PCIe 5.0、CUDA 12.4、Driver 550.163.01），CE/GSP/SEC2 集成硬件 AES 引擎。运行时调度行为在 GPGPU-Sim + UVMSmart 中建模（80 SM、64 warps/SM、8 GB HBM2、Bf=128、driver 线程切换 2 µs）。

## MC-ORAM: A Mask-Assisted and Counter-Based Non-Deterministic ORAM inside VM-Based TEEs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是 TEE 内 ORAM 客户端的运行时安全机制（软件运行在 CPU TEE 中，非 GPU kernel/加速器），此处从"CPU 上运行时计算"角度记录）实现为运行在 Intel TDX 虚拟机内的 ORAM 客户端运行时计算集合：每次逻辑访问对路径上每个节点的全部 Z 个 ORAM 块执行掩码写（data⊕node.mask）与 16 位计数器递增；对暂存执行 oblivious 全扫描（readPath 与 eviction 各一次，共 2ZL 次线性暂存槽更新，每次计数器 +1，即使槽未被写入）；并触发掩码刷新运行时流程（Refresh：整节点/暂存重新生成 112 位掩码并清零计数器）。计数器/掩码递增与刷新频率完全由公开 ORAM 参数与访问次数决定、与逻辑访问模式无关，保证确定性 AES-XTS 密文每次访问都变化且不引入新泄漏。
  - 实验比较什么：与采用 64 位交错计数器（每 64 位数据配 64 位计数器，Obelix 风格）的 PathORAM/RingORAM 及其暂存优化版（+，Oblix 思路）baseline 在真实 TDX 硬件上比较平均访问延迟（1M 次访问）：MC-ORAM 最高加速 1.82×（PathORAM）/1.85×（RingORAM），MC-ORAM+ 最高 1.77×/1.60×；带宽仅 baseline 的 1.125×（vs 64 位计数器 2×）；另验证访问模式不变性（四种模式延迟几乎一致）、N/B 全组合、SPEC CPU2017 映射与 DLRM/Qwen-8B 端到端。
- 后端平台是什么，配置是什么。
  - 后端平台：CPU——双路 Intel Xeon 6548Y+、512 GB DDR5，guest 运行在 Intel TDX VM-based TEE（Ubuntu 22.04.5）内；TME 硬件 AES-XTS（按物理地址确定性加密）作为唯一内存加密机制，ORAM 树/暂存/位置图全部驻留 TEE 加密 DRAM；无 GPU/异构/PIM/加速器后端。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：论文自研的 TDX 内 PathORAM/RingORAM 实现（各 <1000 行，其中 <200 行 MC-ORAM 特有：mask/counter/refresh 元数据管理），以开源 PathORAMSimulator 与 oram_simulator 为参考基础；Intel PIN 采集 SPEC CPU2017 数据地址轨迹（每 benchmark 5M 个地址）确定 ORAM 高度；延迟测量为每访问含递归位置图查询+readPath+驱逐、1M 次访问取算术平均。修改了什么：在 baseline ORAM 上加 112+16 位 AES 块布局、共享掩码管理、计数器递增、Refresh 算法与 obliv 暂存全扫描；为公平对比，所有 baseline（PathORAM/RingORAM/+/+）也实现了 64 位交错计数器方案（同 [43] Obelix 风格），纯 masking baseline 单独评估（慢 13.5×）。
  - 开源情况：MC-ORAM 未开源（截至 2026-08 联网搜索未找到公开仓库）；参考实现开源：PathORAMSimulator（https://github.com/renling/PathORAMSimulator，PathORAM 模拟器）与 oram_simulator（https://github.com/wangxiao1254/oram_simulator，含 PathORAM/Circuit ORAM 等多 ORAM 模拟）。
  - 评估原理与 kernel 输入→性能输出全过程：输入 = ORAM 配置（N=2^14/2^23、B=512b/256B/2048B、Z=4、stash 90/10）与 1M 次逻辑访问地址序列（或 SPEC CPU2017 轨迹映射的配置）→ TDX 内 ORAM 客户端逐访问执行：位置图查找（递归 ORAM 查询）→ readPath（L 个节点×Z 块读入暂存，TreeToStash 掩码写+全暂存计数器 +1）→ 目标块处理 → PosM 更新 → eviction（StashToTree 写回，树节点+暂存计数器 +1，含 RingORAM 周期 A=4 与 (Z+S) 块驱逐、reverse-lexicographic 路径调度）→ 计数器溢出触发 Refresh（整节点/暂存新掩码+清零）→ 每步经 TME AES-XTS(addr,·) 加密读写 DRAM，用高精度时钟对每次逻辑访问计时 → 输出平均访问延迟（ms）、加速比（vs 64 位计数器 baseline）、带宽倍率（1.125×）、刷新频率（节点 3.05×10^−5/访问、暂存每 ~585 次）、存储减少（43.75%）。作用：量化"掩码+短计数器+摊销刷新"这一运行时机制相对 64 位计数器的性能收益，证明 1.125× 带宽即可恢复密文非确定性。


## MLX: Multi-Layer Execution for Structured LLM Workload Acceleration on Spatial Architectures

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 属于kernel调度/运行时计算的实现：论文在 GPU 后端实现并评估两类新型结构化稀疏 kernel——**FFT-CMP kernel（chunked FFT 压缩 + 截断 + iFFT，用于注意力/token mixing 与 KV-cache 压缩）** 与 **hierarchical BSMM kernel（B×B tile 内蝴蝶稀疏矩阵乘，用于 QKV/FFN 投影）**。这些 kernel 以 PyTorch 层实现（FFT 用 cuFFT，未与 FlashAttention 融合），运行于 CUDA cores（TensorCore 对蝴蝶稀疏支持有限，会回退到 CUDA core）。实验比较：(a) H100 上压缩后的 Llama2-7B（s=0.5, B=32）相对原模型 eager attention 与 FlashAttention2 的 prefill/decode 加速：prefill 长序列（8K）最多 2.72×（vs eager）/1.64×（vs FA），短序列收益小；decode 结合块 BSMM 1.4-1.9× 端到端。(b) 与 MLX 加速器对比的 GPU kernel 性能剖面：AGX Orin（batch 64）上 FFT-based transformer block 仅 3.77×（N=8K）/2.56×（N=512）相对 dense 加速（FLOP 削减 >10× 理论上）；Jetson Xavier 上八类 Llama2-7B kernel 的 dense TensorCore vs 蝴蝶 CUDA-core 执行；AGX Orin/RTX-3090 的 structured-workload sweep（FFT-CMP→BSMM→SWA，batch 32）与 roofline 利用率（蝴蝶算子 MLX 52-84% vs Orin 12-29% vs RTX 8.2-31%）。动机剖析：蝴蝶 kernel 运算强度低（bandwidth-dominated）却远低于 CUDA 带宽 roofline（图3），源于多级 strided/shuffle 访问破坏局部性、高 cache miss（图2），以及 stage-wise 依赖与 GPU 批量同步、tile 规则执行的错配（执行单元不匹配）。

## MNEMOS A GPU-based TFHE Acceleration Framework with Memory Access Optimization

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 属于kernel调度/运行时计算的实现：在 ZAMA 的 TFHE-rs/Concrete 之上重写 PBS 的 GPU CUDA kernel 集合，全部为新的 GPU kernel 算子：(1) **PBS MAC（External Product）kernel 的 BSK 分块复用**——利用 BSK 与傅里叶系数之间的 Hadamard 积性质，把单个线程块的数据足迹从"整个 BSK"降为"一个 BSK 分块（TBSK）对一个 GLWE 分块（TGLWE）"，使一批中多个 PBS 实例可并发处理同一份 BSK 分块（跨密文密钥复用），并按 GPU 事务粒度设计分块几何：一个分块 = 8 个连续复数 FP64 元素（16B/个）即 128 字节，对齐 128 字节内存事务粒度保证全局内存合并访问（coalesced）；分块大小在"合并带宽 vs 复用度"间权衡（32/64/128B 候选，最终取 8×16B=128B）。(2) **Tensor Core FFT kernel**——FP64 WMMA（A100 原生 8×8×4）加速 FFT：复数乘分解为 4 个实数 MMA（A_rB_r−A_iB_i、A_rB_i+A_iB_r，每个实数乘 2 次 WMMA）；8 点 FFT 为基例，N>8 用四步 FFT radix-8 递归分解，64 点特化算法利用 warp 内 fragment 布局省去一次显式转置与共享内存往返；分层策略：N>64 优先 radix-64、8<N≤64 用 radix-8、<8 用 CUDA Core+warp shuffle；Fourier 矩阵**运行时片上生成**（8 点 DFT 元素来自稀疏集 {0,±1,±sin(π/4)}，在寄存器内算术生成，消除共享内存载入、bank 冲突与布局管理）；宽数据类型（复数 FP64=16B 跨 4 个 bank）专用 **swizzle 模式**（任意 8 个连续线程映射到 32 个互异 bank）消除转置 bank 冲突。(3) **跨迭代 kernel 融合**——FFT 与 IFFT 使用同一系数集（twiddle factors 与 precomputation factors）的共轭版本，构造跨越盲旋转循环迭代边界的融合 kernel，把两套系数从片上内存跨迭代复用，消除主循环内对这些系数的冗余全局内存载入（收益随分解层数 ℓ 线性增长）。
  - 实验比较：PBS 吞吐（BS/s，batch 4096）vs ZAMA baseline（Table III：Para-A~F 在 A100 上平均 1.8×、Para-A~D 平均 2.23×、最高 3.01×（Para-D）；H100 上平均 1.83×、最高 2.86×）；跨平台吞吐对比（Table IV：Para-I/II 下 A100 22007/13744 BS/s、H100 38748/24348 BS/s，vs Concrete CPU 615.0×/676.3×、NuFHE 15.5×/44.3×、cuFHE 4.4×、VeloFHE 3.2×/9.7×、XEHC 8.7×、MATCHA 3.9×，并达 Strix 的 51.9% 与 Morphling 的 26.2%）；应用端到端（Table V：DeepCNN-20/50/100 2.03×/1.97×/2.04×、VGG-9 2.21×、AES 1.53× vs ZAMA GPU，vs 单线程 CPU 平均 142.4×）；消融（图 11：+MAC 单独 1.10×~1.77×，k 大时显著；+FFT 到最终版本）；stall 分解（图 3 vs 图 12：stall_long_scoreboard 从 >50% 降到约 20%，stall_MIO_throttle 主导变为 Stall Math Pipe；图 13：FFT 共享内存 stall_MIO_throttle 延迟降 3.2×/2.9×/1.8× 对应 N̄=256/512/1024）；内存流量（图 14：GMEM→L2 平均降 15.7%、L2→SM 平均降 69.4%）；batch size 敏感性（图 15，Para-B：baseline 在 batch>1024 因工作集超 40MB L2 而性能骤降，MNEMOS 全程稳定）；参数敏感性（图 16：k 增大→MAC 优化贡献增大，ℓ 增大→两者同时受益，N 增大→FFT 优化贡献增大）。

## MTIA 300: Meta's First Training Chip Featuring Built-in NICs and Collective Offloading Engines

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？

## Mapping and Communication Optimizations with Fault Tolerance for Wafer-Scale LLM Inference

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 属于kernel调度/运行时计算：论文（ISCA 2026，HKUST-GZ）提出 BALD（Balanced Allocation with Load and Distance awareness）通信调度算法，为 wafer-scale 层次化 2D mesh 上的 point-to-point、多组 multicast（区域受限 collective 与广播）及 All-Gather / All-to-All 等 collectives 做链路分配（link allocation）与路径调度，属运行时通信调度在不同后端平台（wafer-scale NPU 阵列）上的调度。BALD 三步：(1) Path Profiling——对拓扑 T=(N,E) 用 Dijkstra 全源最短路径（Algorithm 1），记录最短距离映射 S 与唯一路径映射 U（记录等长多路径并把 pair 标记为非唯一），天然处理非对称节点度与异构边权重；(2) Path Scheduling——对每个通信任务 C=P(s,D)（源 s、目标集 D）按优先级 score = α×branch_cost + β×link_load + γ×neighbor_distance 迭代选择分支与邻居分配链路（Algorithm 2），branch_cost 为当前分支最早可调度时间、link_load 为链路当前占用（mesh 上 collective 的主要瓶颈）、neighbor_distance 为到最近目的地的距离（预计算）；(3) Heuristic Backtracking——维护 tabu forbidden/candidate 列表，迭代找出最大负载链路 l*、对其上任务按概率 ρ 重分配（成功回退的任务进 tabu candidates、失败进 tabu forbiddens），最多 I 次迭代（Algorithm 3）。算法基于 BFS/DFS，拓扑无关，只要存活图连通即可容忍任意节点/链路故障；实现为硬件路由器 Look-Up Table（LUT），主机在每次推理任务前加载路由配置、执行中更新，与 TPUv4 的 LUT 机制一致。
  - 实验比较什么：(a) 合成通信研究——5×5 mesh（无故障与 1 条故障链路 (12,13)，链路带宽 256 GB/s，消息 1 KB–16 GB 4× 递增），比较 All-Gather 与 All-to-All 的有效带宽（有效带宽=总数据量/总完成时间）：All-Gather 对比 Hierarchical Ring [34,61]、MultiTree [26]、TACOS [70]（MultiTree/TACOS 抽取调度步骤后用 alpha-beta 模型 [67] 建模总时间以公平比较），BALD 峰值有效带宽 533.3 GB/s 与 TACOS 持平，超过 MultiTree 1.25×、XY baseline 1.5×、Hierarchical Ring 近 2×；All-to-All 峰值 213.3 GB/s，是 XY baseline 收敛有效带宽的 2.4×，链路故障下保持 1.84–2.25× 优势。(b) 故障敏感性——6×6 mesh 上 7 类故障场景（1 节点/1 链路/2 节点/2 链路，覆盖不等价故障类，Fig.9），BALD 相对 XY routing 在 All-Gather 上 1–1.94×、All-to-All 上 1.56–2.55× 加速。(c) 超参数——α=100,β=1,γ=100（首轮偏好最短路径），随后 α=1,β=100,γ=1（均衡各链路负载）。

## O3LS: Optimizing Lattice Surgery via Automatic Layout Searching and Loose Scheduling

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  O3LS 的 Module 3 松散调度（Loose Scheduling）与 Module 4 边感知初始映射（Edge-aware mapping）属于运行时计算/调度实现——在表面码晶格 patch board 这一后端上，对 lattice surgery 操作（Pauli product measurement PPM、patch rotation、patch deformation/movement、ancilla 路由）进行动态调度与映射。松散调度算法（Algorithm 2）：输入 Pauli 算子序列 S={P_1..P_l}、qubit 数 n、board B → 构建 Pauli DAG → while DAG 非空：对 frontier 中可执行算子 P_i 用 Dijkstra 依次求所需 patch 间最短路径（之前路径视为零成本节点），得到最小 bus patch 列表 Lp_i 后执行 P_i（每算子复杂度 O(|B|²)）；对不可执行算子 P_i，遍历当前 board 全部候选 patch 操作 O_B，选奖励函数 r(o_b, P_i) 最高者执行并加入 S'，循环直到 P_i 可执行。奖励函数三部分：①B_o（施加操作后的 board）中使 P_i 可执行（存在有效路径支持）的数据 patch 数；②破坏数据 patch 连通性的操作奖励为 0（连通性为后续 lattice surgery 必需）；③同奖励优先低时间开销。奖励函数保证每步至少增加一个满足执行要求的 patch，总调度复杂度 O(n²)。Module 4 边感知初始映射：分析 PDAG 估计每个 qubit 的旋转需求，旋转需求高的 qubit 优先映射到同时邻接 ancilla 的 X/Z 边缘的 patch，避免 3 时间步的 patch 旋转，复杂度 O(n log n)。实验比较：EA 映射相对 [28] 的 greedy mapping 时间步减少 15.0%、LER 减少 8.4%；松散调度 + Y-synthesis 相对 prior passes 时间步降 37.74%、LER 降 34.34%（ablation）；与高并行执行策略（LAPBC 风格 [4][5][20][25]）集成再降 9.31% 时间步；在紧凑布局中 patch 旋转可占 >50% 时间步（Fig.7 量化），松散调度正是针对这一瓶颈。
- 后端平台是什么，配置是什么。
  后端平台 = 表面码 patch board（二维 tile 网格），patch 抽象自 distance-d 表面码（每 patch 用 d² 个物理数据量子比特编码一个逻辑量子比特；X/Z 边界抽象为 X/Z 边缘，虚线=Z 算子、实线=X 算子）。配置：compact [34]（顺序放置、按需加列）、sparse [25]（每数据 patch 与邻居间隔至少一个空 tile、X/Z 边缘均邻接路由空间）、standard [25]（类 sparse 但放置不同）三种固定布局 + O3LS 自动生成的 squeezed 布局；board 尺寸 N×M∈[5,12] 扫描（Fig.10 heatmap）；d=9 表面码、p=10⁻³ 电路级去极化噪声模型用于 LER 仿真；15-to-1 magic state factory [8] 置于布局外。

## Observability-aided GPU Memory Oversubscription

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - ObservUVM：基于 NVIDIA UVM（Unified Virtual Memory）的软件框架，通过复用现有硬件 access counters，为 CPU 侧 UVM 驱动提供对 HBM-resident 页访问的（采样）可观测性（observability），从而做出更明智的 HBM 换出（eviction）与预取（prefetching）决策，全程无需硬件修改。核心机制：从 HBM-resident 2MB 区域中抽取一个 64KB 页迁移到 DRAM 并 pin 住、映射到 GPU 页表；GPU 对该采样页的 PCIe 访问触发 access counter 通知，驱动据此推断其所属 2MB 区域是否被 GPU 活跃访问。机制（observability/eviction/prefetch 执行）留在驱动内（修改 NVIDIA 开源 UVM 驱动 v525），策略放 userspace（C++11 引擎 + eBPF 通信层）。
  - 实验比较：默认 UVM（LRM 换出 + TBP 预取）vs ObservUVM 的三种 eviction 策略（近似 LRU/LFU/Cyclic Protection）+ Tournament meta-policy（运行时选策略）+ 两种预取策略（FDP 反馈驱动、RGP 区域粒度预取），以及 ACBM（access counter 迁移，计数器原始用途）与 EarlyAdaptor（EA，先前工作）。指标：执行时间（归一化到 UVM）、GPU 页错误数、eviction 次数。14 个应用在 30%-70% 内存超订下平均加速 34%（几何均值，最高 64% SPM）；TM++ 相比 ACBM/EA 平均快约 20%。

## Optimizing 3D Gaussian Splatting with Axis-Shared Rasterization and Order-independent Transmittance

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现：两项 GPU 端 kernel 实现，用于评估专用加速器之外的性能边界：(1) GPU-implemented axis-shared rasterization——在 NVIDIA RTX 3090 上用 CUDA 把轴共享光栅化三阶段（共享项计算→广播→组合）映射：每个 16×16 tile 分配一个 thread block，块内显式共享项计算阶段由线程协同计算 X/Y 轴共享项存入 shared memory，同步后所有线程复用共享项并行执行组合阶段；(2) GPU-implemented MLP-based OIT——用 cuBLAS [37] 以 GEMM 形式实现 MLP 推理（推理前把视角折入 bias），替换 Gsplat [51] 的 Radix sort [31] kernel。
  - 实验比较：(1) axis-shared GPU kernel vs 原始 Gsplat 实现，按等效面积预算归一化比较延迟，几何均值加速 22%（远低于专用加速器的近 60%）；(2) MLP-OIT GPU 实现（cuBLAS）vs Gsplat Radix sort baseline，几何均值延迟为 baseline 的 1.59×（更慢）。结论：光栅化是非 GEMM 负载、Tensor Core 用不上且 GPU 固定 FMA 流水与均衡乘加比不适应其算术结构；MLP 推理算术强度低（1 深度参数仅 6 MAC vs 光栅化每 GS 256×6 MAC，约 30 倍差）、GPU 上 memory-bound，因此两项优化在通用 GPU 收益有限，论证专用可重构 PE 阵列 + interleaved pipeline 的必要性。
- 后端平台是什么，配置是什么。
  - NVIDIA RTX 3090 桌面 GPU（8nm、628mm²、350W、936 GB/s、10496 CUDA cores）；软件栈：Gsplat 渲染库（CUDA kernel 与 Radix sort）、cuBLAS；对照 edge 平台为 Jetson Orin Nano（8nm、200mm²、~15W、68.2 GB/s、1024 CUDA cores）。

## P3-LLM An Integrated NPU-PIM Accelerator for Edge LLM Inference Using Hybrid Numerical Formats

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 P3-LLM 的 decoding 阶段算子映射（operator mapping）与低精度量化计算流（quantized dataflow），即运行时把 GEMM/GEMV 算子按访存强度与精度需求调度到 NPU 或 PIM 两个后端，并对量化算子做 operator fusion 减少运行时 dequantization 开销：(1) 算子映射——host NPU 执行元素级高精度算子（RoPE、Softmax），线性层 GEMM/GEMV 与注意力矩阵乘 offload 到低精度 PCU；Q·K^T 的映射取决于 key cache 是 pre-RoPE 还是 post-RoPE 量化：pre-RoPE（Llama-1/2，序列短）的量化 key 缺位置信息，不能直接与 query 相乘，需在每轮 decode 在线对 key 做 RoPE（RoPE 是元素级操作、开销可忽略）并保持高精度，因此 Q·K^T 计算放在 NPU；post-RoPE（Llama-3/Mistral，长序列下 RoPE 旋转角很小、对 key cache 分布影响可忽略）的量化 key 可直接与 query 相乘，Q·K^T 可 offload 到低精度 PCU；(2) 量化计算流与融合——线性层把 dequant 缩放放到矩阵乘法之后；Q·K^T 把 post-RoPE key cache 的 per-channel smoothing factor (SSF) 融合进 query（乘进 FP8-E4M3 量化前的缩放）；P·V 把 per-value-head 缩放因子 S^V 融合进 attention-score（除以 S^V_max 防 FP8-S0E4M4 越界，S^V_max 乘回 P·V 结果）；8-bit attention-score 量化使整个 self-attention 模块（含 P·V）能留在低精度 PCU 上执行，避免 quantized value cache 搬回 NPU 用 FP16 单元计算。实验比较：kernel 层/数据流效果的量化证据是架构消融（Fig 15，context 4K）：W4A8KV4 相对 HBM-PIM FP16 平均 3.3×；+TEP 额外 1.6×；+8-bit attention-score 使 attention 模块完全 PIM 化额外 1.2×；batch 2-64 大规模解码（Fig 16）显示 batch≥8 时线性层 PIM 变 compute-bound，P3-LLM 把线性层 offload 回 NPU、attention 层（GQA group size 4/3，数据复用低）继续留 PIM，随 batch 增大 attention 主导而重获优势；context length 2K-16K 敏感性（Fig 11）：长 context 下 attention 因 KV-cache footprint 增大而主导，4-bit KV 量化 + attention 上 PIM 缓解之；pre-RoPE 的 Llama-2-7B 因 Q·K^T 留在 NPU 而长 context 提速略低。
  - 后端平台是什么，配置是什么。
  - 异构 NPU+PIM 后端：4 个 NPU core（每 core 128×128 systolic array、128-way vector processing unit、16MB on-chip scratchpad 用 CACTI 建模，基于 [27] 的 NPU 设计）+ 16 个 pseudo HBM channel（每 channel 8 个 PCU，每 2 bank 共享 1 个，256-bit 列访问粒度）；NPU 频率 1 GHz、PCU 500 MHz（tCCD_S=2 DRAM 时钟）；PCU 每 cycle 算 1×4×16 GEMV tile（4 个 8-bit 输入 × 64 个 4-bit 权重 → 16 个 32-bit 输出），TEP 以 tCCD_S 运行使同一权重切片被两个输入复用。评估用论文自研 cycle-level simulator（PIM 部分按 Newton 方法论扩展），PCU RTL 用 SystemVerilog + Synopsys Design Compiler TSMC 28nm 综合并缩放到 HBM-PIM 20nm。

## PIPEWEAVE: Synergizing Analytical and Learning Models for Unified GPU Performance Prediction

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 PIPEWEAVE：一个统一 GPU 性能预测框架（混合解析-学习模型），将 kernel 的运行耗时预测拆成四模块流水线：(1) Kernel Decomposer 把 kernel 拆成基本任务 task（硬件调度范式下 task=CTA/thread block；persistent kernel 范式下 task=resident CTA 从全局 work queue 取的 tile）；(2) Scheduling Simulator 模拟 task 到 SM 的映射，得到 task distribution——支持硬件调度器（GigaThread Engine，推断为 round-robin，逐轮填满 SM 直到资源饱和再按任务完成替换）与软件调度器（persistent kernel 的 tile scheduler，如 FlashInfer FA3 的 MinHeap 调度逻辑）；(3) Feature Analyzer 把 task distribution 聚合成多级特征：Math pipeline（Tensor/FMA/XU）每任务 ops 数 N_ops=α·tile_M·tile_N·tile_K（GEMM α=2，FlashAttention 两次 MMA α=4），理论周期 C_p=N_ops/Th_p，以及 MIO pipeline 的字节需求与 C_mem=B/BW_mem，按 task→SM→GPU 三级聚合（含 Max SM 特征捕捉负载不均）；(4) Performance Estimator 用一个 3 隐层 MLP（256/128/64，ReLU+BN+Dropout 0.1+Sigmoid 输出）以执行效率（理论时间/实测延迟）为训练目标（MAPE loss，AdamW），最终延迟=理论时间/预测效率。此外用 Quantile Regression（P80 分位损失）训练同一特征集的模型预测"潜在性能上限"，用于诊断与优化指导。
  - 实验比较 4 个主 baseline：Roofline、Linear regression（用 Feature Analyzer 的 compute/memory 理论周期特征）、Habitat（黑盒，喂相同 task 定义）、Neusight（SOTA 数据驱动，喂相同 task 定义）；外加 2 个细节建模 baseline：AMALI（指令 trace 解析模型）与 LLMCompass（解析+cycle-accurate systolic array，限于 standalone GEMM）。指标：kernel 级 MAPE、E2E 推理 MAPE、模拟开销 vs 预测误差。效果：kernel 级 seen GPU 平均 MAPE 6.1%（unseen 11.4%），比 Neusight 误差降 6.7×；E2E seen 8.5%/unseen 10.7%，比 Neusight 降 4.4×；相比 AMALI/LLMCompass 预测时间降低 3~7 个数量级且 MAPE 6.4% vs 28.3%/29.7%。"Beyond Simulation" 用 P80 模型诊断 Fused MoE Triton kernel，autotune 三个参数后 A40/L20/A100/H800 分别 1.61×/1.12×/1.06×/1.03× 加速（underperforming points 数与加速比 Pearson 相关 0.86）。
- 后端平台是什么，配置是什么。
  - 评估横跨 4 代 NVIDIA 架构 11 种 GPU：Ampere（A40、A100、RTX A6000）、Ada（RTX 6000 Ada、L20、L40）、Hopper（H20、H800、H100、H200）、Blackwell（RTX PRO 6000 S）；6 个用于训练（seen），5 个仅测试（unseen，评估泛化性）。硬件规格（输入 S）包括：Compute Capability 8.0–12.0、SM 数 78–188、SM 时钟 1410–2520 MHz、Tensor Pipe 吞吐 512–4096 ops/cycle/SM、FMA 64–128、XU 16、Global Mem BW 696–4916 GB/s、L2 BW 2430–10400 GB/s、SMEM BW 128 Byte/cycle、SMEM 100–228 KB、寄存器 256 KB。软件环境：PyTorch 2.8.0、CUDA Toolkit 12.8、FlashInfer 0.4.1、SGLang 0.5.4、vLLM 0.11.0、Triton 3.4.0。E2E 测试模型：Qwen2.5-14B、Qwen3-32B、Llama3.1-70B，TP=1/2/4/8、TP=4&PP=2，数据集 Arxiv Summarization（avg input 2630 tokens）与 Splitwise（avg 982 tokens），batch 变体如 arxiv_8/splitwise_64。
- 评估性能的软件/脚本是什么。修改了什么。

## PRowhammer Propagating Bit-flips from CPU to GPU

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是面向 GPU kernel 运行时执行的攻击（非性能优化，为安全攻击，按最接近的"kernel 算子运行时"归类）：以无特权 CPU 进程在 hDRAM 中对 GPU 共享库（cuBLASLt、GGML）的 .nv_fatbin 压缩 SASS 代码页施加 Rowhammer 位翻转，借助 OS 页去重（.nv_fatbin 以 mmap(MAP_PRIVATE)+PROT_READ|PROT_EXEC 映射、只读页跨进程去重）使受害者 GPU-bound ML 进程被迫映射同一份被破坏的 kernel 代码；kernel 从 hDRAM 传至 GPU（cudaMemcpy/动态链接）后按被篡改 SASS 执行，位翻转传播到 GPU 计算并破坏输出。核心运行时机制：单 bit-flip 把 SASS 指令变为"不同但合法"的指令（表 I 归纳四类：寄存器变化、opcode 变化、offset 变化、指令变化，如 FFMA→FSET.F.FTZ.AND、LDS [R17+0x140]→[R17+0x148]、SHL→LOP3.LUT）；单 bit-flip 在压缩码中可产生平均 2–5 个（最多 25 个）合法改义指令，部分 kernel 崩溃、相当数量（cuBLASLt 3–83、GGML 41–99）不崩溃但输出改变。kernel 定位环节：用单线性层 profiling 模型确定目标模型实际调用的 cuBLASLt kernel（sm_86 共 3508 个 kernel，给定输出维度只调 1–2 个；CIFAR-10/MNIST/FMNIST 输出 10 类共用一个 kernel，ImageNet 输出 1000 类用另一个）。
  - 实验比较：图像分类 16 配置在 RTX 4090 与 RTX A6000 上攻击前后准确率（单 bit-flip 后接近随机猜测，ImageNet 0%，RPL>80%）；LLM 在 RTX A6000/4090/5060 上对 Llama-2-7B/Mistral-7B/Falcon-7B（4-bit 量化、llama.cpp/GGML）的 ggml_mul_mat kernel 单 bit-flip 后 BERTScore 0.58–0.62→0.25–0.30（输出 # 串或跨语言乱码，部分位置产生语法连贯但语义错误的文本）。攻击有效性：DDR3 无噪声成功率 50%/有噪声 30%，DDR4 无噪声 80%/有噪声 73%（噪声=多份 GAP PageRank 在全部核上持续占用内存与 CPU 调度）；首次 flip 需几分钟、首次可利用 flip 一小时内（DDR4 快于 DDR3），memory massaging 微秒级（vmtouch 刷 page cache）。
- 后端平台是什么，配置是什么。
  - NVIDIA 离散 GPU：RTX 4090、RTX A6000、RTX 5060，经 CUDA 软件栈（runtime/driver API、NVIDIA 驱动、GPU-bound 共享库）由 CPU 管理；hDRAM 为平台 A（Intel i7-4790 Haswell、8GB Kingston DDR3 1600MT/s、kernel 5.15.0-131）与平台 B（Intel i7-8700 Coffee Lake、8GB Corsair DDR4 2400MT/s、kernel 6.2.0-060200）；OS Ubuntu 20.04.6、CUDA Toolkit 12.8。SASS 指令集按 GPU 架构不同（表 I 以 RTX 4090 为例，Fig. 6 为 Ampere 架构示例）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：PyTorch（图像分类，经 cuBLASLt 加速 GEMM）；llama.cpp + GGML（LLM，ggml_mul_mat kernel）；cuobjdump（反汇编 .nv_fatbin、验证翻转后 SASS 合法性）+ diff；vmtouch（刷 page cache 便于 memory massaging）；GAP benchmark 的 PageRank（构造系统噪声）。修改了什么：无开源 Serving/推理框架被修改——攻击不改变框架代码，而是用 profiling 管线（kernel_locater_<lib>.sh、choose_target_region.sh、run_flipper_watchdog_<lib>.sh、segregate.sh、extract_useful_flips.sh）在目标库上离线定位可利用 bit，攻击阶段用 Rowhammer 篡改库文件在 hDRAM 中的映射副本。

## PhaseWeave Phase-Aware Execution on Heterogeneous Chiplet Architectures for Datacenters

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似匹配：论文无新 kernel 算子，其核心"运行时调度"是硬件-OS 协同的 phase 级线程迁移，把计算调度到异构 chiplet 后端上。）实现：(1) benefit-aware 迁移算法（Algorithm 1）——每 100µs epoch 末，对每个线程 t、候选 chiplet c' 计算迁移效用 U(t,c')=S(p,c')-S(p,c)-λ·Q(c')-C_switch（S=phase p 在 chiplet c 的离线预期性能如 IPC，Q=Load State 报告的 runqueue 长度，λ 把排队折算延迟惩罚，C_switch=一次 context switch 代价；c'=c 时 U=0），选 c*=argmax U，仅当 U(c*)>θ 且线程在现 chiplet 驻留 ≥T_min 才迁移（T_min 防预测噪声振荡）；(2) OS 集成——chiplet 暴露为 CPU 簇（类似 NUMA 节点、不连续 CPU ID 区间），PhaseWeave 不改 OS 调度器数据结构，经 MSR/MMIO 硬件接口给 placement recommendation，OS 周期性读取并用自己的 affinity 机制迁移线程；(3) Load State 模块 + 软件可写 task-count 寄存器（OS 在 runqueue 变化时更新）。实验比较：PhaseWeave vs PhaseWeave-NoMigrationAlg（无条件迁到预测最优 chiplet）——吞吐 1.26×（仅专精+多核）→ 1.56×（+迁移算法，即迁移算法再贡献 1.24×）；迁移统计：53.2% 的 epoch 迁移≥1 线程，其中 18.5% 因最优核满载而迁往次优核；真实系统迁移开销（平均 23.8µs、中位 9.5µs，phase 时长数百 µs 可忽略）与功耗（同核数下比 baseline 少 7.2% 功耗）。
- 后端平台是什么，配置是什么。
  - 全系统模拟：QEMU+SST Ariel+DRAMSim3 中四类异构 chiplet 后端（Table III，38 核：10 compute@3GHz 6-wide / 9 fast-mem@2.5GHz 4-wide / 9 near-net@2.5GHz 4-wide / 10 low-power@2.0GHz 2-wide）。真实系统：Intel Emerald Rapids（28 核 2-way SMT 3GHz，128GB DDR5 5600MT/s），把核分组为 pool 各模拟一类 chiplet，按 PhaseWeave 参数设置每 pool 频率（cpu-freq-utils）、内存带宽（pqos/CAT）、网络带宽，用改变 OS scheduling affinity 迁移线程；迁移时间=从中断线程到目标核起跑的时间。
- 评估性能的软件/脚本是什么。修改了什么。
  - 全系统模拟中的迁移调度器（Algorithm 1 实现于 SST 环境内）+ 真实系统上用 OS 亲和性（sched_setaffinity 机制）+ perf 采集 PMU 指标评估。修改：SST 内新增 task-count 寄存器、Load State 模块与迁移调度逻辑；OS 侧不改调度器数据结构，仅周期读硬件 recommendation 并设置 affinity。评估指标：SLO（100ms @P99）下吞吐 QPS、端到端延迟、迁移开销、功耗。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源：PhaseWeave 未开源（论文未给链接，联网检索无公开仓库，截至 2026-08）；DCPerf（https://github.com/facebookresearch/DCPerf）与底层模拟器开源。使用例子（一次 phase 迁移的输入到性能输出全过程）：输入 = 预测器输出的 phase p + 各 chiplet runqueue 长度（Load State）+ 离线 phase-特征表 S(p,c) + 阈值 θ/T_min/λ/C_switch → 调度器枚举候选 chiplet 计算 U(t,c')，若 U(c*)>θ 且驻留 ≥T_min，把线程从当前核出队、标准 context switch（页表根更新与 TLB 一致性走既有硬件/OS 机制）入队目标 chiplet runqueue → 线程在目标核跑下一 epoch（预测器并行采样新特征）→ 请求全程按 100µs epoch 反复预测-决策-迁移 → 汇总各负载等级下的 QPS、P99/P50 延迟、功耗与迁移次数统计，从而量化迁移算法带来的 1.26×→1.56× 吞吐提升与 7.2% 真实系统功耗节省。

## SHyLA: 3D-Stacked NVM-DRAM Hybrid LLM-Inference Architecture Exploiting Data and Memory Heterogeneity

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 bandwidth-utilization-centric dataflow（运行时数据布局与 kernel/算子映射策略），在 3D 堆叠混合内存放置约束下最大化 areal bandwidth 利用：(1) memory-plane-aware 数据布局——tile group 内 NVM plane 存 NTile 与 group 内 DTile 的 Weight 切块、DRAM plane 存 IA 行，避免 plane starvation 与 compute-tile-memory-plane 失配；(2) tile 分组——#DTile<#NTile 时每组 1 个 DTile + 若干 NTile（同相对位置配对），group 内专用高速链路、跨组 AXI fabric；(3) FFN 层——Weight 列分布到各 tile 本地 buffer、IA 留全局输入 buffer；(4) ATTN 层——head 级并行跨 chiplet 按 tensor 并行维分头，每 tile 处理一个 GEMV 对（fused ATTN）避免中间 QK^T 结果写 DRAM，KVCache 单 memory plane 放置支持 decode 并行 GEMV（溢出跨两 plane），GQA 按 attention-group/request 级并行、group 内 Q head 复用 KVCache（重载由 tile weight buffer 容量决定）；(5) intra-chiplet 采用 output-stationary+input-stationary 强调 Weight 读复用、最小化 IA 流量，tiling 因子 BI/BK 由片上 buffer 容量决定；(6) 软件栈——CUDA 管理片上缓冲并实现映射，GPGPU-Sim 内存控制器地址映射改连续地址跨 channel 交错。
  - 实验比较 SHyLA vs SHyLA-D（one-to-one NTile-DTile 配对、无 tile 分组与细粒度算子切分）：数据流贡献 1.35× geomean 系统吞吐提升（改进带宽利用、降低 Weight/KVCache 的 NVM 访问开销）；并比较 vs DRAM-only/NVM-only/H800/MI300X 的运行时分解。

## STEP: Adaptive Spatio-Temporal Expert Prefetching for Low-Latency and Memory-Efficient MoE Inference

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 MoE 推理中的运行时专家预取调度（expert prefetch scheduling）：在 CPU-GPU 异构平台上，把 CPU 主存中的专家权重经 PCIe 预取到 GPU 并与专家计算重叠，隐藏专家加载延迟。核心机制：(1) 临时共享专家预取——每个 token 窗口内经投票当选的 top-c 专家在窗口计算开始前整体预取并常驻 GPU，使每步动态加载的 routed 专家从 k 降到 k−c；(2) CUDA 异步流调度——prefetch 被实现为独立 GPU stream 上的异步数据传输 kernel，在专家计算 kernel 之前发起，利用 CUDA 非抢占式 kernel 执行实现传输与计算重叠；(3) CUDA event 同步——在每个解码步序列的最后一个 prefetch kernel 后插入 CUDA event 记录完成时间，供 CPU 高效查询（避免阻塞式同步），保证数据可用性的同时最大化流间重叠；(4) token-aware 自适应窗口——按每层 prefetch 准确率动态调整投票/预取窗口大小（th_s=75%、th_f=40%、τ=3/4），准确率过低（窗口=1）时禁用预取防带宽浪费；(5) EP 扩展——每个 expert-parallel group 独立维护热专家本地缓存并运行自适应预取，NVLink/NVSwitch 高带宽环境下可用 peer GPU HBM 作二级缓存直接 P2P 取专家。
  - 实验比较：以 Cached Expert Ratio（CER = GPU 可用专家槽位数 / 模型专家总数，取 25%/50%/75%）为内存约束控制变量，比较 prefill 阶段 TTFT 与 decode 阶段 TPOT/tok/s（batch=1，输入 512 token 定长 trace），baseline 为 llama.cpp（静态 layer-to-device 映射）、AdapMoE、HybriMoE、DAOP、APTMoE、MoE-Lightning；prefill 平均几何加速 3.12×/1.97×/1.52×/1.07×/1.07×/1.03×，decode 1.54×/2.22×/1.39×/1.15×/1.10×/1.25×；decode 延迟分解（Fig.12）显示 STEP 相对标准 MoE 显著压缩 expert offloading 占比；batch 1–8 与 V100/A100/H20 敏感性分析（Fig.18/19）。

## Taking Analytic Databases to the Bank

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是面向 BLIMP PIM 平台的数据库算子内核（select/semijoin/join/aggregate kernel）与异构调度编排：(1) 内核本身——Algorithm 1 FILTERTOBITVECTOR（select，位图输出）、Algorithm 2 SEMIJOINPROBE（semijoin，位图输出）、join（probe 输出 hash 表 payload）、aggregation kernel；内核以 200MHz RISC-V 指令执行 fetch-read-apply-store 流程，以 1KB row buffer 粒度访存；(2) 调度——host 将列数据按 PIMDT chunk 均匀分发到全部 512 个 BLIMP core（模拟时假设数据同质、计算对称、总时延=最慢 bank），host 负责建 hash 表并 relayout 复制到各 bank；join 的 hash 表大于 32MB bank 容量时按分区多轮 build-probe 循环（每轮 offload 一个分区 hash 表、探测 PIMDT 列、结果 OR 到下一轮）；查询执行器在算子前预处理（切分 PIMDT、建数据结构），kernel+分区+辅助数据经 relayout 载入 bank，执行完后决定部分物化/原位保留或 host 取回；(3) 运行时策略——物化策略（Early/Hybrid/Late Mat.）、算子链（PIM 内 AND 合并双选择位图）、join 顺序（左深树、低选择性优先）。实验比较：各算子内核在 BLIMP-S/BLIMP-V vs host 手调 C++ kernel 的算子级加速比；端到端 SSB 中三种规划（Isolated / CPU-optimal / PIM-optimal）的 relayout、host 编排、hash build、数据加载、post-processing 时间占比。
  - 关键数字：隔离算子外推导致平均 22% 查询时间在 relayout（输出数据送回 host）；Isolated 计划平均比手调基线慢 2.1×、比 PIM-optimal 慢 3.2×；join 在隔离计划中平均差 3.1×；CPU-optimal（DuckDB 生成的 join 顺序）与 PIM-optimal 差异平均 28%、最大 40%（Q3.3）；CPU 推荐顺序 SDC 是 6 种候选序中第 4 差（比最优 CSD 慢 23%）。Q4.3 的 bushy join 树需多次重建 hash 表（重复 relayout+build+broadcast），与最小化 relayout 目标相悖。
- 后端平台是什么，配置是什么。
  - BLIMP-S / BLIMP-V：DDR4 DRAM bank 内 200MHz RISC-V 核，每核本地 32MB bank、1KB row buffer；BLIMP-S 为 RV64GC 标量核（1KB 指令缓冲、1KB scratchpad、5×1KB R/W buffer），BLIMP-V 为 RV64GCV 向量核（32×64b vALU、5×1KB vector register）；512 core bank 级并行、约 12.5TBps bank 内带宽（模拟配置）。Host：2× Intel Xeon Silver 4114（20 物理核/40 线程、AVX512）、27.5MB LLC、384GB DDR4（90GBps 峰值带宽）。BLIMP 与 host 间无 bank 到 bank 直连，跨 bank 数据传输走 host 读-写中转；compute mode 下 host 不能访问该 bank 数据，下游/并行相邻操作需等待。
- 评估性能的软件/脚本是什么。修改了什么。

## TimeGaps Channels: Exploiting CPU Halted Time for Fun and Profit

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是面向 x86 CPU 与 iGPU 的侧信道运行时采集/测量工具集（运行时监控，非 Serving 负载）：(1) C 采集器 gaps_collector_pmc / gaps_collector_5ms——在指定/隔离核上反复执行 rdtscp 检测 TimeGaps，并读 PMC 计数器（CPU_CLK_UNHALTED.THREAD/REF_TSC）区分 halted 与 unhalted jump；(2) user_rdpmc 可加载内核模块——让非特权用户可读 PMC（Section III.B 需 insmod）；(3) OpenCL workload 生成器——在 iGPU 上执行 vector_add、int/float 加法等 kernel，制造可重复的 iGPU 频率切换（提交到单一 command queue 按 batch 同步以最小化 CPU 侧活动）；(4) Python 自动化 attacker.py——驱动浏览器（Selenium/ChromeDriver）采集 TimeGap/loop-counter/频率三通道并评估；(5) shell 脚本 collect_pstate.sh / collect_pstate_opencl.sh / collect_cpu_workload.sh / collect_igpu_workload.sh 编排各实验。实验比较：TimeGaps 序列 vs MSR_PERF_STATUS（MSR 0x198）P-state 切换（时间对齐，仅差时钟采样分辨率）；固定 CPU 频率下 TimeGaps vs gt_cur_freq_mhz iGPU 频率切换（经 i915 驱动，~0.3ms 更新）与 perf_event_open PMU 事件 power/energy-gpu 的 iGPU 功耗；C1/C1E residency（排除 OS idle 干扰）；MSR_PKG_ENERGY_STATUS / MSR_PP0_ENERGY_STATUS 能量 delta 作为 package/core 功率代理（含 TimeGap 区间 package 功率代理平均低 18.2%）。

## Towards Practical Interrupt Side-Channel Attacks on macOS for Apple Silicon

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是面向 macOS/Apple Silicon（M1–M4）的**无定时器中断检测运行时原语 TIDE（Timer-less Interrupt Detection）**及其派生中断侧信道工具集：(1) TIDE 检测原语——利用 Apple Double Map 缓解在 user→kernel 转换时把 AAPCS64 平台寄存器 x18 当作 scratch 用（XNU 异常入口的 MAP_KERNEL 与 BRANCH_TO_KVA_VECTOR 宏覆写 x18），并在 kernel→user 返回前由 macOS 显式清零的行为：攻击者给 x18 赋非零值，循环检查其是否被清零，即可判定本核是否发生中断（无需 cntvct_el0/kperf 等架构定时器，定时器被限制时仍可用）；(2) 中断计时原语——x18 赋非零后在同一个线程内递增计数器直到 x18 被清零，用计数器值表示两次相邻中断的时间间隔；(3) 去噪原语——测量代码前后各一次 x18 写/读（至多 1 写 1 读开销），若 x18 被清零则该次测量受中断污染，丢弃或重做；(4) 用 TIDE 反推苹果私有中断控制器（AIC，M1 Pro 起 AICv2）的 SPI 投递机制（均匀投递到所有 active core、忽略 idle core）；(5) 基于 LSTM（32 units，沿用 Cook et al. [7] 开源实现）的 ML 辅助指纹分类。实验比较：TIDE vs 架构定时器（cntvct_el0，阈值 1μs，检出 >99% 但存在 0.2%–0.5% 误报）与 counting-thread 定时器（对 TIDE 检出的 100,000 个中断仅检出 45.0%–80.5%）；网站指纹 closed-world top-1 93.8%/top-5 98.7%、open-world 91.5%（fixed-frequency 变体 93.1%/91.1%）、视频指纹 78.1%，均优于 Cook et al. 定时器版（94.8%/74.5%，被随机定时器防御打回约 1%/5%）；TIDE 去噪下 SysBumps 攻击成功率 54%→81%（overhead 仅 0.06%）；loop-counting 攻击在 compute-intensive 线程噪声下 94.8%→39.3%，以 active core 数增强训练标签后 92.8%/93.6%；跨核隐蔽信道带宽 111.65 bps、误码率 4.45%；SIKE 密钥提取（CIRCL v1.1）。
- 后端平台是什么，配置是什么。
  - Apple Silicon 真机（非模拟器），6 台机器：MacBook Pro 2021（M1 Pro，2 E+8 P 核，macOS Ventura 13.6）、Mac mini 2023（M2，4 E+4 P，Ventura 13.7）、MacBook Air 2023（M3，4 E+4 P，Sonoma 14.6，cntvct_el0 24 MHz、P 核 4.050 GHz）、MacBook Pro 2023（M3 Max，4 E+10 P，Sonoma 14.7）、Mac mini 2020 云实例（M1，4 E+4 P，Sonoma 14.6）、Mac mini 2024 云实例（M4，6 E+4 P，Sequoia 15.2，cntvct_el0 1 GHz）。威胁模型：无特权原生攻击者（timer-constrained，无 kperf/cntvct_el0），以及浏览器攻击者（loop-counting，ms 级定时器）；不假设攻击者 core 绑定（macOS 用户态无法设置 core affinity）。CoreBinder（kext）与 cntvct_el0 仅用于反推/验证实验，不属于攻击路径。

## XtraMAC: An Efficient MAC Architecture for Mixed-Precision LLM Inference on FPGA

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是 XtraMAC 集成的 tile 并行混合精度 GEMV kernel（FPGA 硬件 kernel，论文 VI 节 case study）：把 XtraMAC 作为级联 MAC 链替换现有 FPGA GEMV 流水线（FlightLLM [42]/FlightVGM [23] 风格）中的标量 MAC，PE 拓扑/tiling/全局数据流保持不变。GEMV workload 按 M 个 tile 划分，每 tile 映射到一个连接独立 HBM channel 的 PE；权重存 HBM、激活片上缓冲复用；HBM 每 channel 512-bit 接口字拆成 per-lane 权重段分发到 PE 内级联的 XtraMAC 实例，per-tile datatype 控制信号（存在内存里、与权重 tile 一起）与操作数同步传播，保证每实例在运行时应用正确的映射规则与累加路径，各 lane 部分和经级联 MAC 链累加后写回。每 channel 级联 XtraMAC 数 N_MAC = BitWidth_channel/(BitWidth_weight×P)：INT4 权重（4-bit）+ P=2 lanes 时单 channel 512/(4×2)=64 个 MAC 输入/cycle；32 个 HBM channel 理论可例化 2048 个，实际采用 1920 个（30 个活跃 channel，留 1 个读激活 + 1 个写回，保证路由时序收敛）。
  - 实验比较：① 资源/频率扩展——post-implementation 测 LUT/FF/DSP 随 XtraMAC 例化数线性增长，≤1024 实例维持 300 MHz，1920 实例因 HBM 接口附近路由拥塞降到 250–270 MHz（Fig.12）；512-XtraMAC 配置下 XtraMAC 占 LUT 98.5%、FF 95.6%、DSP 100%，剩余为 datatype 控制寄存器与片上激活缓冲，HBM 控制器在 Alveo static shell 中不计入用户逻辑（Fig.13），非 MAC 组件与操作数并行注册、不增加流水级；② 与 GPU baseline 对比——NVIDIA H100 PCIe + CUTLASS [29] 官方 GEMV kernel（nvidia-smi 测功耗），1×4096×4096 与 1×4096×12288 GEMV 上 XtraMAC（U55c）时延 0.0246/0.0743 ms vs CUTLASS 0.0294/0.0879 ms（1.2× speedup），功耗 85 W vs 135 W，能量 0.00209/0.00632 J vs 0.00397/0.01187 J（1.9× energy efficiency）；尽管 GPU 峰值带宽 2 TB/s vs FPGA 460 GB/s，FPGA 靠高效混合精度 MAC datapath、无格式转换开销与 ~74% 有效 HBM 利用率跑出接近带宽 roofline 的性能（Table VII）。
- 后端平台是什么，配置是什么。
  - FPGA：AMD Xilinx Alveo U55c（xcu55c-fsvh2892-2L-e，32 个 HBM channel、460 GB/s HBM 带宽），Vivado 2022.2 + Vitis 2022.2 综合/实现，post place-and-route 时序；GEMV kernel 用 1920 个级联 XtraMAC、30 个活跃 HBM channel、每 channel 512-bit 接口、300 MHz（1920 实例时 250–270 MHz）；功耗用 xbutil 稳态流式测量（85 W）。
  - GPU baseline：NVIDIA H100 PCIe（HBM 带宽 2 TB/s），CUTLASS 官方 GEMV kernel，execution time 用官方 kernel 测量，nvidia-smi 监控功耗（135 W）。
- 评估性能的软件/脚本是什么。修改了什么。
  - FPGA 侧：Vivado/Vitis 2022.2 综合+实现（place-and-route 报告资源/频率）、xbutil（稳态流式功耗测量）。修改：在现有 FPGA GEMV 流水线（如 [42][23]）基础上把标量 MAC 替换为 XtraMAC 级联链，PE 拓扑/tiling/全局数据流不变；新增 per-tile datatype 控制信号（与权重 tile 一起存 HBM、随操作数同步传播）；权重 HBM 直读、激活片上缓冲、HBM 512-bit 接口字按 per-lane 拆分、多 PE 跨 HBM channel 并发保持带宽扩展。
  - GPU 侧：CUTLASS [29]（https://github.com/NVIDIA/cutlass）官方 GEMV kernel，未修改，作为官方实现 baseline；计时用官方 kernel 的执行时间，功耗 nvidia-smi。
