## Tensor Partitioning Solver (Offline Profiler + Online Solver)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Tensor Partitioning Solver 是 HeteroInfer 中用于决策 GPU-NPU 并行策略的离线优化组件。其工作流程为：(1) Performance Profiler 在目标 SoC 上对 LLM 涉及的所有 Matmul 算子实测 GPU 和 NPU 的执行延迟、内存带宽和同步开销（< 20 分钟）；(2) Solver 基于 profiling 结果，对每种 (weight_shape, activation_shape) 组合枚举所有可行的分区策略（GPU-only, NPU-only, weight-centric partition at various ratios, activation-centric partition at various standard lengths, hybrid），求解 min-max 优化问题——选择使 max(T_GPU, T_NPU) + T_sync + T_copy 最小的策略。

公式为：
$$T_{\text{total}} = \min \left( \max(T_{\text{GPU}}^{\text{partition1}}, T_{\text{NPU}}^{\text{partition2}}) + T_{\text{sync}} + T_{\text{copy}}, \quad T_{\text{GPU}}^{\text{all}}, \quad T_{\text{NPU}}^{\text{all}} + T_{\text{sync}} + T_{\text{copy}} \right)$$

Profiling 完成后 solver 的求解是离线的——输出的 partition strategy table 在推理时由 control plane decider 查表使用，无需在线优化。

## Chunk-sharing Graph / Chunk-wise Prefill（块共享图 / 分块预填充）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Chunk-wise Prefill 是一种将变长 LLM prompt 分割为多个固定长度 chunk 并按因果依赖关系依次处理的预填充策略。Chunk-sharing Graph 是 llm.npu 在此基础上的优化：将 LLM 算子分为**静态算子**（Linear、LayerNorm——仅依赖 chunk 长度，跨 chunk 共享 NPU 计算图）和**动态算子**（Attention——依赖 chunk 序列位置，需每个 chunk 独立构建），从而大幅减少 NPU 图的内存开销。

核心动机：移动 NPU（如 Qualcomm Hexagon NPU 通过 QNN SDK 编程）仅支持静态形状的推理——在执行前必须完成图构建（model translation → intermediate representation → memory allocation, 300-500ms）和图优化（memory layout, execution order, operator fusion, 数秒至数十秒）。LLM prefill 的 prompt 长度在每次推理中不同，若每次重新构建 NPU 图（Gemma-2B 需要 360ms 构建 + 11.54s 优化），total overhead 远超 CPU 推理时间。Chunk 策略将变长问题转化为复用定长预构建图的问题。

## Out-of-order Subgraph Execution（乱序子图执行, OOE）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Out-of-order Subgraph Execution (OOE) 是 llm.npu 中的 NPU-CPU 异构子图调度算法。在 chunk + 子图两级划分后，LLM 的每个子图 $G_{i,j}$（第 i 个 chunk 的第 j 个子图）可以在不严格遵守 chunk 顺序的情况下被调度——只要其依赖的所有前序子图已完成。这打破了传统 layer-by-layer、chunk-by-chunk 的串行执行约束，允许 CPU/GPU 上的 FP16 算子与 NPU 上的 INT8 算子在时间线上更充分地重叠。

算法的核心是每次选择对"减少 NPU 停顿"贡献最大的就绪子图，而非贪心地选择执行时间最短的子图。贡献值 $C$ 定义：
$$C(g) = \begin{cases} \sum_{i \in S} T_i, & \text{若 } g \text{ 分配到 CPU/GPU} \\ -\sum_{i \in S} T_i, & \text{若 } g \text{ 分配到 NPU} \end{cases}$$

其中 $S$ 是子图 $g$ 完成后新变为就绪状态的子图集合，$T_i$ 是子图 $i$ 的 NPU 执行时间。直观解释：若在 CPU/GPU 上执行子图 g，则执行完后释放出 S 中的子图可以在 NPU 上执行——因此希望 S 中 NPU 工作量越大越好（减少 NPU 空闲）。反之，若在 NPU 上执行 g，执行完后释放的 S 中有 NPU 子图会继续占用 NPU——因此希望释放出的 CPU 工作量尽可能少（避免 NPU 被释放的 CPU 工作阻塞）。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。

```
OOE Scheduler 在 llm.npu 中的工作流程:

# ========== 子图依赖模型 ==========
# 跨 chunk 依赖 (仅 Attention 算子):
#   G[i, attn] ← G[0, attn_prev], G[1, attn_prev], ..., G[i, attn_prev]
#   即第 i 个 chunk 的 Attention 依赖前 i-1 个 chunk 的 Attention 前序子图
#   (需要前序 chunk 的 K, V 值作为输入)

# 块内依赖 (所有算子):
#   G[i, j] ← G[i, j-1]
#   同 chunk 内按 Transformer 层的原始顺序: Q→K→V→Attn→O→FFN...

# ========== OOE 调度算法 ==========
def ooe_scheduler(chunks, subgraphs_per_chunk):
    """
    在线贪心调度 (微秒级每步决策)
    """
    # 初始化
    ready_npu = []  # (chunk_idx, graph_idx, T_npu)  # 就绪且分配到 NPU 的子图
    ready_cpu = []  # (chunk_idx, graph_idx, T_cpu)  # 就绪且分配到 CPU 的子图
    completed = set()  # 已完成的子图
    
    # 所有 chunk 的第一个子图初始化就绪 (分配到 NPU: Linear 投影)
    for i in range(len(chunks)):
        ready_npu.append((i, 0, T_npu[i][0]))
    
    while ready_npu or ready_cpu:
        best_subgraph = None
        best_contribution = -inf
        
        # 评估每个就绪的 CPU 子图
        for g in ready_cpu:
            # S: g 完成后变为就绪的新子图集合
            S = get_newly_ready(g, completed, ready_npu, ready_cpu)
            # C = sum(T_npu of S 中分配到 NPU 的子图)
            contribution = sum(T_npu[s] for s in S if assigned_to_npu(s))
            if contribution > best_contribution:
                best_contribution = contribution
                best_subgraph = g  # CPU 执行
        
        # 评估每个就绪的 NPU 子图
        for g in ready_npu:
            S = get_newly_ready(g, completed, ready_npu, ready_cpu)
            # C = -sum(T_npu of S 中分配到 CPU 的子图)
            contribution = -sum(T_cpu[s] for s in S if assigned_to_cpu(s))
            if contribution > best_contribution:
                best_contribution = contribution
                best_subgraph = g  # NPU 执行
        
        # 提交最佳子图到对应处理器
        if best_subgraph in ready_cpu:
            cpu_execute(best_subgraph)
            ready_cpu.remove(best_subgraph)
        else:
            npu_execute(best_subgraph)
            ready_npu.remove(best_subgraph)
        
        completed.add(best_subgraph)
        
        # 更新就绪队列: 检查是否有新子图因 best_subgraph 完成而就绪
        for new_g in get_dependents(best_subgraph):
            if all_deps_completed(new_g, completed):
                if assigned_to_npu(new_g):
                    ready_npu.append(new_g)
                else:
                    ready_cpu.append(new_g)


# ========== Naive 顺序执行 vs. OOE 时间线对比 ==========
# 场景: 2 个 chunk, 每个 chunk 4 个子图
# NPU 子图 (G[i,1], G[i,3]): 计算密集型, ~2ms each
# CPU 子图 (G[i,2], G[i,4]): FP16 算子, ~0.5ms each

# Naive (chunk-by-chunk):
# NPU: |==G[0,1]==|          |==G[0,3]==|          |==G[1,1]==|          |==G[1,3]==|
# CPU:           |G[0,2]|G[0,4]|          |G[1,2]|G[1,4]|
#      37% bubble rate (NPU idle while waiting for CPU)

# OOE (贡献值引导):
# NPU: |==G[0,1]==|==G[1,1]==|==G[0,3]==|==G[1,3]==|
# CPU:           |G[0,2]|G[1,2]|  |G[0,4]|G[1,4]|  |
#      显著降低 bubble rate (OOE 减少 NPU 停顿 18-44%)
#      G[1,1] 不再等 G[0,2]→G[0,3]→G[0,4] 的 chunk 0 全流程完成;
#      只要 G[0,1] 完成 (G[1,1] 的跨 chunk 依赖满足), G[1,1] 即可在 NPU 执行
```

**OOE 的关键约束与设计选择**：

1. **移动处理器无抢占 (preemption)**：每个处理器（NPU, CPU/GPU）同一时刻仅执行一个子图——约束条件 $\sum_{i,j} P_{i,j,t} = 1$ 确保无资源竞争。

2. **NPU 是关键路径**：OOE 算法的核心观察——prefill 阶段 NPU 执行时间约 2× CPU 执行时间（Qwen1.5-1.8B, prompt_len=256），因此调度目标是最小化 NPU 停顿而非最大化并行度。

3. **微秒级在线调度**：由于 chunk 数量随 prompt 长度变化，无法离线预计算最优调度。OOE 的贡献值计算为 O(N × M)（N=chunk 数, M=子图数），在移动 CPU 上仅需数微秒。

4. **子图执行时间离线 profiling**：所有子图的 NPU/CPU 执行时间在 preparation stage 已测量，在线调度只需查表。

**OOE vs. 其他调度方法的区别**：
| 调度方法 | 粒度 | 优化目标 | 适用场景 |
|----------|------|----------|----------|
| llm.npu OOE | 子图 (subgraph) | 最小化 NPU 停顿 | 移动 NPU-CPU 异构 prefill |
| HeteroInfer | 算子/张量分区 (tensor) | GPU-NPU 并行 min-max 延迟 | 移动 GPU-NPU 异构 prefill+decode |

## LLM Context Switching（LLM 上下文切换）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

LLM Context Switching 是在 LLMaaS 多 app 共享 LLM 场景下，当一个 app 调用 LLM Service 时，将其 persistent LLM context（主要是 KV cache）从非活跃状态恢复到内存中就绪状态的过程。类似于传统移动 OS 中的 app 冷启动延迟优化（将 app 从后台/被杀状态恢复到前台），LLM context switching 的目标是最小化 context 准备延迟，使 app 能快速开始 LLM 推理。

Context Switching 延迟的组成部分（以 Llama2-7B 4K context 为例）：
1. **磁盘 I/O 时间**: 将压缩/未压缩的 KV cache chunk 从 flash storage 加载到 RAM。UFS 4.0 顺序读 ~2 GB/s，2GB KV cache 需要 ~1s。
2. **CPU/GPU 重计算时间**: 若 chunk 被丢弃（而非 swap），需从原始 prompt text 重计算 KV cache。Llama2-7B 4K context 在 MI14 上全量重计算需要 22.92 秒。
3. **解压时间**: 将压缩 chunk (INT4/INT2) 解包还原为 INT8/FP16 以用于 attention 计算。
4. **内存回收时间**: 若设备内存不足，需先 evict 其他 context 的 chunk 以释放空间。

```
  ↓

   - 256 chunks 中 150 在 RAM（就绪）
   - 106 在 disk（需加载）
   - 其中: 20 chunks = INT8, 50 = INT4, 36 = INT2
   - 总需加载内存量: 20*8MB + 50*4MB + 36*2MB = 432 MB

2. 检查可用内存:
   if RAM_free < 432 MB:
       触发 Reclaim primitive → LCTRU queue eviction
       从其他 context 的头部子队列 pop chunks → swap to disk → free RAM

3. Swapping-Recompute Pipeline 规划 (Equation 4):
   minimize max(T_re(x_re), T_IO(432MB - Σratio_w * x_re))
   → 决定: I/O 加载 66 chunks + CPU/GPU 重计算 40 chunks

4. Pipeline 执行 (多线程):
   I/O Thread:    |==Load chk_L0==|==Load chk_L1==|==Load chk_L2==| ...

   Total ≈ 0.27s (vs. 纯 I/O ≈ 0.43s, vs. LMK recompute ≈ 22.92s)

5. 所有 chunk 就绪 → 通知 LLM Inference Engine 可以开始推理

# ========== LLM Inference ==========

7. Decode: 逐 token 生成 (~0.05s/token)

# ========== LLMS Writeback Phase (AoT Swapping) ==========

   将本次推理中新修改的 chunk 写入磁盘（即使无内存压力）

9. 返回生成的 tokens + 更新后的 LLMCtxStub 给 App
```

Context Switching 与传统 App Cold Start 的对比：

传统 App Cold Start 优化（如 MARS [38], SmartSwap [89]）：
- 管理对象：App 的 heap/stack/data pages
- 粒度：OS page（4KB），不可压缩
- 恢复方式：仅 I/O（page swap-in from flash/zram）
- 延迟量级：数百 ms ~ 数秒

LLM Context Switching（LLMS）：
- 管理对象：KV cache chunks（16 tokens, ~8MB INT8）
- 粒度：chunk（可调，16-64 tokens），可近似/压缩
- 恢复方式：I/O（swap-in）+ Compute（recompute from prompt text）pipeline
- 延迟量级：数十 ms ~ 数百 ms（LLMS 优化后）
- 独特特性：
  (a) Context 可压缩（低信息密度 chunk 激进压缩）
  (b) Context 可重计算（KV cache 是 LLM 中间激活，可从 prompt text 恢复）
  (c) Context 访问模式特殊（低频但需持久化，轻量 app 可能拥有重 context）

关键设计选择：Chunk 粒度（16 tokens）
- 太粗（整 context）：I/O bandwidth 利用充分但内存碎片化严重 + swap 冗余大
- 太细（1 token）：内存利用率高但 I/O 带宽浪费（小读取无法利用顺序读带宽）
- 16 tokens：平衡点——chunk 内 token 的 attention 计算具有局部性，同时 memory block 大小（~8MB INT8）适合 NVMe/UFS 的页面级 I/O

## LCTRU Queue（Least Compression-Tolerable and Recently-Used，最小压缩容忍且最近使用队列）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

LCTRU（Least Compression-Tolerable and Recently-Used）是 LLMS 论文提出的 KV cache chunk eviction 策略，用于在设备内存不足时决定哪些 chunk 应该被交换到磁盘。LCTRU 的核心创新是将传统 LRU（Least Recently Used）的单一维度（访问时间）扩展为两个维度：压缩容忍度（chunk 的压缩比，即 weight）和最近使用时间（recency）。LCTRU 优先 evict "heavy" chunk（低压缩率 → 占用更多内存 → 换出后释放更多空间）以及 "cold" chunk（长时间未访问 → 访问时间局部性低）。

从系统架构角度拆解术语，比如术语如何在系统架构中发挥作用，给出术语在系统架构中运转流程的具体例子。通过联网搜索让回答具体和精准。

LCTRU Queue 的结构和运转流程：

```
# ========== LCTRU Queue 数据结构 ==========
# Q_LCTRU = [Q_{ratio_1}, Q_{ratio_2}, ..., Q_{ratio_w}]
# 其中 ratio_1 > ratio_2 > ... > ratio_w（ratio 越大 = 压缩越少 = chunk 越"重"）
#
# 实际配置 (LLMS default: {ratio_w} = {8/8, 4/8, 2/8}):
#   Q_LCTRU = [Q_INT8] → [Q_INT4] → [Q_INT2]
#   头部 → 尾部
#   │          │          │
#   │          │          └─ 最轻 chunk (INT2, 2MB), 最后 evict
#   │          └─ 中等 chunk (INT4, 4MB)
#   └─ 最重 chunk (INT8, 8MB), 最先 evict

# 每个子队列 Q_{ratio} 内部维护 LRU 顺序:
#   头部 = 最近最少使用 (LRU within same ratio)
#   尾部 = 最近最多使用

# ========== LCTRU 更新操作 ==========
on_callLLM(ctx_id, newPrompt):
    # 将 ctx_id 本次访问涉及的所有 chunk 移到各自子队列末尾（最近使用）
    for each accessed_chunk in ctx_id:
        ratio_w = accessed_chunk.ratio
        Q_{ratio_w}.move_to_tail(accessed_chunk)

# ========== LCTRU Eviction 操作 ==========
on_reclaim(required_bytes):
    freed = 0
    # 从头到尾扫描子队列
    for subqueue in Q_LCTRU:  # Q_INT8 → Q_INT4 → Q_INT2
        while subqueue.not_empty() and freed < required_bytes:
            chunk = subqueue.pop_head()  # 获取该子队列中的 LRU chunk
            swap_out_to_disk(chunk)      # 写入磁盘
            freed += chunk.size
            # 示例: 1个 INT8 chunk = 8MB, 1个 INT4 = 4MB, 1个 INT2 = 2MB
    return freed
```

LCTRU 的设计原理推导：

**Principle 1: Heavy chunk first（重 chunk 优先）**
- 给定需要释放的内存大小 $M$，evict 少数重 chunk 比 evict 多数轻 chunk 更优。
- 原因来自 Swapping-Recompute Pipeline 的 Equation 4:
  $$pipelineDelay = \max(T_{re}(\sum x_{re}), T_{IO}(m - \sum ratio_w \cdot x_{re}))$$
  其中 $T_{re}$ 与 chunk 数成正比，与 chunk 大小无关。
- 若 evict 的都是 INT8 chunk（8MB each）→ $x_{re}$ 小 → $T_{re}$ 小 → pipeline delay 低。
- 若 evict 的都是 INT2 chunk（2MB each）→ $x_{re}$ 大 → $T_{re}$ 大 → pipeline delay 高。

**Principle 2: LRU within same ratio（同压缩比内 LRU）**
- 利用 context 访问的时间局部性——最近被访问的 chunk 更可能很快再次被访问。
- 仅在相同压缩比内部使用 LRU 排序——因为压缩比对 eviction 的影响大于时间局部性（Principle 1 优先级更高）。

LCTRU vs. 传统 LMK (Low-Memory Killer) 的对比：
```
传统 LMK:
  Eviction 单位: 整个 app process（包括 app heap + LLM context）
  Eviction 优先级: oom_adj_score（app 类型: 前台/后台/服务）
  Context 感知: 无 → app 内存和 context 内存不加区分
  问题: 轻量 app 可能因持有重 context 而被误杀
         context 构建成本高（~23s 重计算）与传统 app 启动成本（秒级）完全不同

LCTRU:
  Eviction 单位: 单个 KV cache chunk（16 tokens）
  Eviction 优先级: 压缩率 (heavy first) + 最近访问时间 (LRU)
  Context 感知: 是 → 解耦 app 内存与 context 内存管理
  优势: Heavy chunk first 减少 pipeline 重载成本
         LRU 利用时间局部性
         Working set lock 避免 thrashing
```

LLMS 中的实现细节（§4 Implementation）：
- LCTRU 队列在 LLM Service 进程内维护，与 Context Memory Manager 紧密集成。
- 队列大小动态变化——chunk 被换出时从队列中移除，被换入时重新加入。
- 每个子队列使用双向链表 + hash map 实现 O(1) 的 move_to_tail 和 pop_head 操作。
- Chunk 元数据（ratio, last_access_time, disk_location）存储在内存中的 chunk metadata table 中，不在 LCTRU 队列中重复存储。

Working Set Lock 机制：
```
# 防止 eviction 与当前推理冲突
on_callLLM(ctx_id, newPrompt):
    lock(ctx_id)  # 锁定 ctx_id 的所有 chunk
    # ← 此时 Reclaim 不会 evict ctx_id 的 chunk
    perform_llm_inference()
    unlock(ctx_id)
```
这避免了类似于 OS 的 thrashing 现象——同一 context 的 chunk 在 I/O 和推理之间反复换入换出。

Ahead-of-Time (AoT) Swapping（提前换出）：
- 在 callLLM() 返回阶段，LLMS 主动将被修改的 chunk 写入磁盘（即使当前无内存压力）。
- 这是一个 writeback 操作而非 eviction——chunk 仍在内存中，同时有一份磁盘副本。
- 当后续 Reclaim 被触发时，这些 chunk 可以直接从内存释放而无需 I/O——因为磁盘副本已是最新。
- AoT 将 reclaim 延迟隐藏在 callLLM() 的返回路径中（对 caller 不可感知）。

## Low-Memory Killer（LMK，低内存杀手）

Low-Memory Killer (LMK) 是 Android 操作系统内核中的内存管理机制，当系统物理内存不足时自动选择并终止（kill）后台进程以释放内存。LMK 基于进程的 oom_adj_score（Out-Of-Memory Adjustment Score）决定 kill 优先级：分数越高的进程越优先被 kill。oom_adj_score 由 ActivityManagerService 根据进程类型动态分配——前台进程得分最低（最不易被杀），空进程得分最高（最易被杀）。LMK 的触发阈值和 kill 策略由内核驱动（Linux kernel LMK driver）或用户空间的 lmkd daemon 管理。

```
1. 内存压力检测:

   当 MemAvailable 低于阈值时触发 LMK:

     - 重度压力 (e.g., < 400MB): 杀 SERVICE 级别进程
     - 极重压力 (e.g., < 200MB): 杀 PREVIOUS_APP 级别进程

   ├──────────────────────────────┼───────────────┤
   │ FOREGROUND_APP (前台)        │ 0             │ ← 最不易被杀
   │ VISIBLE_APP (可见但非前台)    │ 100           │
   │ PREVIOUS_APP (刚退到后台)     │ 700           │
   │ HOME_APP (桌面)              │ 600           │
   │ SERVICE (活跃服务)           │ 800           │
   │ CACHED_APP (缓存后台 App)    │ 900-906       │
   │ EMPTY_APP (空进程)           │ 1000          │ ← 最易被杀
   └──────────────────────────────┴───────────────┘

3. Kill 过程:
   lmkd 选择 oom_adj_score 最高且 RSS 最大的进程 → send SIGKILL
   → 进程被终止 → 所有内存页（app heap + LLM context）被回收
```

LMK 对 LLM Context 的不适用性（LLMS 论文 §2.3 分析）：

LLMS 论文指出 LMK 不适用于 LLMaaS 场景的三个根本原因：

**(1) LLM Context 构建成本极高**
- App 冷启动: 加载 app binary + inflate UI + restore state → ~1-3s
- LLM Context 构建: 通过 LLM 推理逐 token 生成 KV cache
  - Llama2-7B 4K context 在 MI14 上 recompute 需要 22.92s, 能耗 94.57J
  - 相当于观看 1 分钟 YouTube 视频的能耗
- LMK 不区分这种成本差异——统一以 oom_adj_score 决定 kill 优先级

**(2) LLM Context 访问频率低**
- 例如 Gboard smart reply 仅在 Telegram 聊天时触发 LLM Service
- 一个持有活跃 LLM context 的轻量 app（oom_adj_score 高，易被杀）即使 context 短期内不会被使用也很可能被 LMK 误杀
- App 内存与 LLM context 内存的生命周期不匹配

**(3) LLM Context 可压缩**
- KV cache 可通过量化压缩（INT8 → INT4 → INT2），且不同 chunk 压缩容忍度不同
- App 内存（heap/stack）通常不可压缩（zram 提供有限的透明压缩）
- LMK 将两者混合管理 → 错过针对 context 的压缩优化机会

LLMS 的解决方案：
- **解耦管理**: 将 LLM context 内存与 app 内存分离管理。App 内存仍由 LMK 管理，LLM context 由 LLMS 的 LCTRU + AoT swapping 管理。
- **Chunk 粒度**: 以 16-token chunk 而非整个 context 为单位管理，避免 all-or-nothing kill。
- **Tolerance-aware compression**: 在 evict 之前先压缩，减少 evict 次数。
- **Swapping-recompute pipeline**: 当 chunk 被 evict 后，可通过 I/O + recompute pipeline 快速恢复，而非从零重计算整个 context。

Android LMK 的具体实现演化：
- **Kernel LMK driver** (Android 4.x-9): Linux 内核驱动，基于 `/sys/module/lowmemorykiller/parameters/` 配置。简单但不够灵活——阈值固定，无法感知系统整体内存压力。
- **Userspace lmkd** (Android 10+): 用户空间 daemon，使用 `meminfo` 和 `pressure stall information (PSI)` 监控内存压力，比内核 LMK 更精准。

## DVFS Governor（DVFS 调速器，Android/Linux）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

DVFS Governor 是移动操作系统（Android/Linux）内核中负责动态电压频率调节（DVFS）决策的软件组件。Governor 的核心职责是根据系统运行时观测到的硬件统计信息（如利用率、负载、温度等）动态调整硬件组件（CPU、GPU、Memory）的工作频率和电压，以在性能和能耗之间取得平衡。现代 Android 设备为不同硬件组件配备了独立的 governor：(1) CPU——sched-pixel EAS（基于 Energy-Aware Scheduling 的任务放置 + DVFS 控制），(2) GPU——Quickstep governor（基于 utilization-to-frequency 查表），(3) Memory Interface (MIF)——Interactive governor（基于内存总线利用率）。

Governor 的基本工作原理（以 GPU Quickstep 为例）：GPU 制造商提供 dvfs_table，为每个可用 GPU 频率预定义最小和最大利用率阈值。运行时 governor 持续监控 GPU 利用率——若利用率低于最小阈值则降频（减少功耗），若利用率高于最大阈值则升频（提高性能），若在目标区间内则保持当前频率。Quickstep 的独特之处在于：(1) 升频更快——利用率大幅超出阈值时可跳过中间频率级别直接升至更高频率；(2) 跳过频率级别时的迟滞值减半——减少在新频率级别的停留时间。

**Android 中三种 Governor 的具体实现机制**：

**(1) sched-pixel EAS (CPU Governor)**：
- 基于 Linux 内核的 Energy-Aware Scheduling (EAS) 框架，使用 PELT (Per-Entity Load Tracking) 每 1ms 采样 CPU utilization
- 任务负载估计: 对历史采样应用指数衰减，应用频率不变缩放因子使不同频率下的利用率可比
- 频率选择: 提供 per-cluster load-to-frequency 查表（op-points），选择满足估计负载的最低频率
- 关键局限（对 LLM 推理）: GPU-heavy task 的 CPU load 会持续衰减（CPU 大部分时间在等待 GPU 的 iowait），导致 EAS 选择过低频率

**(2) Quickstep (GPU Governor)**：
- Google 为 Mali GPU 开发，从 Pixel 6 到 Pixel 9 使用
- 基于 dvfs_table，为每个 GPU 频率定义 [min_util, max_util] 阈值
- 升频时可跳过中间频率级别（"quick step"）；跳过级别后迟滞值减半
- 关键局限: decode 阶段 GPU utilization ~50-70%（batch_size=1），始终低于 target range → governor 持续降频

**(3) Interactive (Memory Governor)**：
- 基于 `governor_simpleinteractive.c` (AOSP)，监控 MIF 总线利用率
- 高利用率时立即升至峰值频率，低利用率时按预定义公式逐步降低，20ms 周期重复
- 论文 §5.2 发现 default memory governor 在 CPU/GPU 频率固定时已能实现近最优

## Antagonistic Effect / Downward Spiral（拮抗效应 / 向下螺旋）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Antagonistic Effect（拮抗效应）是 FUSE 论文发现并命名的移动 DVFS governor 间的有害交互现象：当 CPU governor (EAS) 和 GPU governor (Quickstep) 在 LLM 推理过程中并发运行时，两者独立地、互相触发地级联压低对方的频率，形成"向下螺旋"（downward spiral），最终将 CPU 和 GPU 频率均驱动至硬件最低值。

根因：LLM 推理中 CPU 和 GPU 通过 OpenCL command queue 产生利用率耦合——CPU 负责向 GPU 提交 kernel（CPU 频率影响提交延迟 → 影响 GPU 利用率），GPU 负责执行 kernel（GPU 频率影响执行时间 → 影响 CPU iowait 时间 → 影响 CPU 利用率）。两个 governor 各自基于自身硬件的利用率独立调频，互不感知对方的频率对自己的间接影响。

量化证据（论文 Fig. 7）：
- CPU 从 2850→500MHz 时 GPU util 从 70.9%→52.9% (-25%)
- GPU 从 848→151MHz 时 CPU util 从 25.7%→7.9% (-69%)

从系统架构角度拆解，给出拮抗效应实时 trace 示例（论文 Fig. 10）：

t=250ms GPU unpinned (CPU 由 EAS 控制):
  t=288ms: GPU 848→701MHz (Quickstep 降频)
  t=338ms: GPU 510MHz
  t=363ms: CPU 1277→1106MHz (EAS 因 GPU 慢而降频)
  t=399ms: GPU 471MHz (CPU 降频导致 kernel 提交慢)
  t=520ms: CPU 500MHz (最低)
  t=821ms: GPU 151MHz (最低)
  → 571ms 内从高频跌落至双最低, TPOT 退化 ~41%

规避方法：(1) FUSE 的频率固定 (pinning)——通过 offline profiling 确定最优频率组合，运行时 pin 住频率，完全切断 utilization→frequency 的反馈回路；(2) 协同 Governor——理论上可设计跨组件感知的统一 governor，但面临实时耦合模型感知和微秒级决策的挑战；(3) 硬件改进——若 Mali GPU command queue 深度更大（当前仅 2 outstanding entries），CPU 提交延迟敏感性降低，减弱传播强度。

通用性条件：任何存在跨组件利用率耦合的 workload 在独立 governor 下都可能出现类似效应——已在移动游戏 [16, 31] 和边缘计算 [28] 场景中有类似观察。FUSE 是首次在移动 LLM 推理场景中系统性揭示并量化此效应。

## FUSE（Fully Unified Scheduling for Energy，统一能耗感知调度器）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

FUSE 是论文提出的统一能耗感知 DVFS governor，作为 llama.cpp 的扩展（~2K 行 Python），通过 offline profiling-based 频率搜索 + runtime 频率固定来替代 Android 默认的三个独立 governor，消除拮抗效应并优化移动端 LLM 推理的能效。

核心设计：(1) Offline-Online 分离——LLM 模型长期使用同一模型，可接受一次性 offline profiling 开销（17-88 分钟 per model）；(2) GPU 优先两步搜索——GPU 频率是 LLM 推理延迟和能耗的主导因素 → 先搜 GPU 抑制拮抗效应，再搜 CPU 微调；(3) 阶段感知——prefill (compute-bound, GPU 利用率高) 和 decode (memory-bound, GPU 利用率低) 使用不同最优频率组合；(4) Memory governor 不改动（§5.2 发现已近最优）。

支持两种目标：G1（给定能耗预算最小化延迟）和 G2（给定延迟目标最小化能耗）。

从系统架构角度拆解：

**Offline 搜索**:
- Step 1 GPU 搜索 (~2.4 推理/setting): 从最高 GPU 频率递减，停在第一个满足 energy budget (G1) 或超过 minimum-energy point (G2) 的频率
- Step 2 CPU 搜索 (~5.1 推理/setting): 对至多 2 个 GPU 候选频率，从最高 CPU 频率递减搜索 → 选择延迟最低 (G1) 或能耗最低 (G2) 的组合
- 搜索次数: 6 settings × ~45 推理 (vs. 穷举 2808 → 62× reduction)
- 搜索耗时: 17.7 min (TinyLlama) ~ 78.5 min (Llama-2-7B)

**Online 执行**:
- llama.cpp 推理流程中插入 prefill/decode 通知 hook → FUSE 查表 → sysfs pin 频率 → 推理执行 → 阶段切换时重新 pin → 推理结束后恢复默认 governor
- 频率组合在推理全过程中保持恒定，彻底消除 antagonistic effect

## Frequency Pinning（频率固定，via sysfs）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

Frequency Pinning（频率固定）是 FUSE 使用的 DVFS 控制技术：通过将硬件组件的 scaling_min_freq 和 scaling_max_freq 写入相同值，强制该组件以固定频率运行，从而绕过 governor 的动态调频逻辑。在 FUSE 中有两种使用场景：(1) Offline profiling——测量每种频率组合下的延迟和能耗；(2) Online runtime——查表后将 CPU 和 GPU pin 到预先搜索出的最优频率组合。

关键观察：即使 pin 住频率，governor 仍在运行——但由于 min=max，governor 没有调频空间，等效于被禁用。Pin 操作本身开销 ~1-2ms (sysfs write)，可忽略 vs. 秒级推理延迟。

从系统架构角度拆解：

Pin 操作流程（以 Pixel 7 为例）：
  1. echo 2252000 > /sys/devices/system/cpu/cpu*/cpufreq/scaling_min_freq
     echo 2252000 > /sys/devices/system/cpu/cpu*/cpufreq/scaling_max_freq
     → CPU 固定在 2252 MHz, EAS 仍运行但无调频空间
  2. echo 762000000 > /sys/class/kgsl/kgsl-3d0/min_gpuclk
     echo 762000000 > /sys/class/kgsl/kgsl-3d0/max_gpuclk
     → GPU 固定在 762 MHz
  3. Memory 保持默认 governor (论文 §5.2: 已近最优)
  4. 推理完成后恢复: 写回 min/max 默认值 → governor 重获调频空间

## llama.cpp NPU Backend（llama.cpp 的 NPU 后端集成）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

llama.cpp NPU Backend 是论文 "Scaling LLM Test-Time Compute with Mobile NPU on Smartphones" 在 llama.cpp 推理框架上新增的 Hexagon NPU 计算后端（约 7K 行 C/C++ + inline assembly）。与 QNN-based 方案不同，该 backend 完全绕过 Qualcomm 闭源 QNN SDK，直接使用 Hexagon SDK 6.0.0.2 的 LLVM toolchain 编译自定义 NPU kernel（通过 reverse engineering 发现的 FP16 HMX 指令）。这使得系统摆脱了 QNN 的限制——静态计算图（固定 batch size）、仅 per-tensor/per-channel 量化（精度不可接受）、无法自定义底层 kernel。

架构分为两大模块：(1) **NPU operator library**（编译为 Hexagon DSP 独立 shared object）——实现 HMX GEMM、HVX dequantization、FlashAttention、Softmax 等算子；(2) **CPU-side llama.cpp integration**——新增 Hexagon NPU backend 类，使用 rpcmem shared memory 作为底层 buffer 类型，通过 FastRPC 管理 remote NPU session，算子 fallback 机制将未实现算子回退到 CPU。

## rpcmem / FastRPC CPU-NPU Communication（rpcmem 共享内存 / FastRPC CPU-NPU 通信）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

rpcmem 是 Qualcomm Snapdragon SoC 上的一种共享内存机制，基于 kernel dmabuf（DMA buffer），允许 CPU 和 Hexagon DSP（NPU）共享同一段物理内存。libcdsprpc.so（Android vendor library）提供 dmabuf 的分配（rpcmem_alloc）、释放（rpcmem_free）和映射（rpcmem_to_fd）接口。FastRPC 是 Hexagon SDK 提供的远程过程调用设施，允许 CPU 端启动和管理 Hexagon DSP 上的远程 session。论文使用 FastRPC 在初始化阶段启动 NPU remote session，之后通信通过 shared memory polling 实现低延迟 command dispatch（替代默认 RPC 机制的高延迟）。

```
rpcmem + FastRPC CPU-NPU 通信流程:

初始化:
  CPU: FastRPC_create_session() → 启动 Hexagon DSP remote session
       → 加载 NPU operator library (.so) 到 DSP
  CPU: rpcmem_alloc(size) → 分配物理连续内存 → CPU VA + DMA fd
  CPU: FastRPC_map(fd) → 映射到 NPU VA 空间

推理通信 (低延迟 polling 模式):
  ┌─ CPU ───────────────────────────────────────────┐
  │ 1. 填充 activation tensor 到 rpcmem buffer      │
  │ 2. dcache clean (writeback)                     │
  │ 3. 填写 command descriptor:                     │
  │    {op, in_offsets, out_offsets, shapes, quant} │
  │ 4. atomic store READY flag                      │
  └─────────────────────────────────────────────────┘
                       │ rpcmem
  ┌─ NPU (DSP polling loop) ───────────────────────┐
  │ while true:                                     │
  │   5. dcache invalidate (comm buf)               │
  │   6. if READY: parse cmd → execute kernel       │
  │      → dcache clean (results) → set DONE        │
  └─────────────────────────────────────────────────┘
                       │
  ┌─ CPU ───────────────────────────────────────────┐
  │ 7. poll DONE flag                                │
  │ 8. dcache invalidate → read results             │
  └─────────────────────────────────────────────────┘

对比默认 RPC: ~100s μs vs. polling ~10s μs
```
