## NPU 静态计算图（Static Computation Graph）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

NPU 静态计算图是当代移动 NPU（如 Qualcomm Hexagon NPU、Huawei Da Vinci NPU）普遍采用的推理执行模型：模型的计算图（算子拓扑 + 张量形状）必须在推理开始前完全确定并编译为 NPU 可执行的二进制格式。NPU 不支持运行时动态形状（dynamic shape）——任何张量维度的变化都需要重新生成计算图。

静态图的编译过程（graph generation/graph compilation）涉及：算子融合、内存分配规划、tile 尺寸确定（将大张量分解为适配 systolic array 尺寸的 tile）、指令调度等优化步骤。这一过程耗时与张量尺寸成正比——HeteroInfer 论文 Figure 8 显示，单个算子的 NPU 图生成时间随张量形状增长（例如从 seq_len=128 的 ~200ms 增长到 seq_len=1024 的 >800ms）。在整个 LLM（通常每个 decoder block 需要 4 个 NPU 图），运行时图生成开销可能占总推理延迟的 34.6%（seq_len=135 时为 408.4ms）到更大比例（seq_len=1000 时图生成 2050ms）。

这与 GPU 的 kernel 执行模型形成对比：GPU 提供一组 kernel 实现，每个 kernel 可以在运行时适配各种张量形状，无需预编译固定形状的图。

**NPU 静态图的具体实现层次**：
- Qualcomm QNN: 模型（ONNX/PyTorch）→ `qnn-model-converter` → QNN Model (JSON) → `qnn-context-binary-generator` → Context Binary (.bin) → HTP 执行。Context Binary 包含针对特定 SoC (Hexagon arch v69/v73/v75/v79) 和特定张量形状的编译后指令。
- Huawei HiAI / Da Vinci: 模型 → IR → 离线编译（图优化、tiling、内存分配）→ offline model (.om) → 运行时加载执行。
- Apple ANE: 通过 Core ML 编译模型（`.mlmodelc`），ANE 仅执行编译图中支持的算子，不支持的算子回退到 GPU/CPU。

**LLM 推理中对静态图的应对策略**：
1. Padding: 最直接但计算浪费大（HeteroInfer baseline）
2. Chunked-prefill (llm.npu): 固定 chunk 大小拆分序列，每个 chunk 使用预编译图（牺牲短序列性能：seq_len=256 时性能退化至峰值的一半）
3. Activation-centric Partition (HeteroInfer): 仅标准形状在 NPU 执行 + 动态形状卸载到 GPU
4. 动态图编译优化（编译框架方向）：TVM/Ansor/Roller 等通过自动调优加速图编译

## QNN（Qualcomm AI Engine Direct SDK）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

QNN（Qualcomm AI Engine Direct SDK，前身为 Qualcomm Neural Network SDK）是 Qualcomm 提供的统一低级 API，用于将 AI/ML 模型部署到 Qualcomm SoC 的异构加速器上——包括 Kryo CPU、Adreno GPU 和 Hexagon NPU (HTP, Hexagon Tensor Processor)。它是访问 Hexagon NPU 的唯一公开编程接口——开发者无法直接为 NPU 编写 kernel，必须通过 QNN 将模型转换为 NPU 可执行的静态计算图。

QNN 的核心组件和工作流：模型转换（`qnn-model-converter`: ONNX/TensorFlow/PyTorch → QNN Model JSON）、图编译（`qnn-context-binary-generator`: QNN Model → HTP Context Binary `.bin`）、运行时（`libQnnHtp.so` + QNN API 执行 Context Binary）。

在 HeteroInfer 论文中，QNN 被用来集成 NPU 算子——GPU kernel 使用 OpenCL 直接开发，NPU 算子通过 QNN 提供的预编译接口执行。

**QNN 的生态系统集成**：
- ExecuTorch (PyTorch): `executorch/backends/qualcomm/` 提供 QNN backend，将 PyTorch 模型 AOT 编译为 `.pte` 文件（内嵌 HTP context binary）
- ONNX Runtime: `QNN Execution Provider` 将 ONNX 模型委托给 QNN 执行，支持 `htp_performance_mode` 等配置
- MNN (Alibaba): MNN-QNN backend，支持在线和离线两种图构建模式
- Microsoft Olive: 提供 `QNNConversion` / `QNNContextBinaryGenerator` 等 pass

**QNN 的多后端支持**：
- `libQnnHtp.so`: Hexagon Tensor Processor（NPU）— 最高性能
- `libQnnGpu.so`: Adreno GPU — 兼容性更好
- `libQnnCpu.so`: Kryo CPU — 参考/fallback 实现
- `libQnnSystem.so`: 系统级接口

**来自 "Scaling LLM Test-Time Compute with Mobile NPU on Smartphones"（EUROSYS '26）的补充**：

该论文完全绕过 QNN，原因：(1) QNN 仅支持 per-tensor/per-channel 量化——Llama3.2-1B-Instruct 在 QNN per-channel W4A16 下 MATH500 仅 2.1%（vs. AutoAWQ per-group 15.9%），不满足 test-time scaling 最低要求；(2) QNN 静态计算图固定 batch size——无法支持 test-time scaling 的动态 generation budget；(3) QNN 的 HMX 矩阵单元指令未公开——开发者无法自定义高性能 kernel。论文通过 reverse engineering 二进制库中的 HMX 指令 + Hexagon SDK LLVM toolchain 直接编译，实现了无 QNN 依赖的完整 NPU 推理栈。但论文仍将 QNN FP16 数据作为 prefill 性能参考（某些 workload 下论文方法达到 QNN 水平）。
