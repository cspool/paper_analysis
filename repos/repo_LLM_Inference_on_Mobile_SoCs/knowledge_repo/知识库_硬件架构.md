## 移动 SoC 统一内存架构（UMA, Unified Memory Architecture）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

统一内存架构（UMA）是移动 SoC 中 CPU、GPU 和 NPU 共享同一物理内存池的硬件设计，与离散加速器系统（如服务器中 CPU 通过 PCIe 连接独立 GPU 显存）形成根本区别。在 UMA 下，所有处理器使用统一的物理地址空间访问同一块 LPDDR 内存，无需通过 PCIe 总线进行 CPU→GPU 数据拷贝（如 cudaMemcpy）。这消除了数据搬移的延迟和能耗开销，使跨处理器的零拷贝（zero-copy）数据共享成为可能。

在 HeteroInfer 论文的 Snapdragon 8 Gen 3 平台上，UMA 的理论内存带宽为 68 GB/s，但实际可达最大带宽约为 61.9 GB/s（仅在连续大块 memcpy 或 NEON-load intrinsics 场景下达到）。关键发现是：单个处理器（CPU、GPU 或 NPU）在 decoding 负载下仅能达到约 40-45 GB/s 的带宽利用率，而 GPU 和 NPU 并发执行可将聚合带宽提升至约 60 GB/s（达到理论峰值的 ~88%，实际可达最大值的 ~97%）。

## NPU 脉动阵列与 Weight-Stall 计算范式

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

NPU 内部最核心的计算单元是脉动阵列（Systolic Array），一种通过数据流特性最小化权重和激活的冗余加载/存储操作的矩阵计算硬件结构。其基本计算范式为 **weight-stall（权重驻留）** 模式：权重被预加载到每个处理单元（PE, Processing Element）中并保持静止，激活值（输入）以流水线方式依次流过 PE 阵列，每个 PE 执行乘加运算后将部分和传递给相邻 PE。

HeteroInfer 论文揭示的 Snapdragon 8 Gen 3 Hexagon NPU 使用多个 32×32 的 systolic array 作为矩阵计算单元。由于这种 weight-stall 范式和固定硬件尺寸，NPU 表现出三种独特的性能特征（详见 NPU Stage / Order-Sensitive / Shape-Sensitive Performance 术语条目）。

从硬件架构角度拆解术语，比如术语如何在硬件架构中发挥作用，给出术语在硬件架构中运转流程的具体例子。通过联网搜索让回答具体和精准。

```
┌──────────────────────────────────────────────────────────┐
│              32×32 Systolic Array (Weight-Stall)         │
│                                                          │
│   Activation Flow (输入流动方向)                           │
│   a₀, a₁, a₂, ..., a₃₁  ──────────────────────────────→  │
│                                                          │
│   ┌──────┐ ┌──────┐ ┌──────┐       ┌──────┐             │
│   │ PE₀,₀│→│ PE₀,₁│→│ PE₀,₂│→ ... →│PE₀,₃₁│ → psum₀    │
│   │ w₀,₀ │ │ w₀,₁ │ │ w₀,₂ │       │w₀,₃₁ │             │
│   └──┬───┘ └──┬───┘ └──┬───┘       └──┬───┘             │
│      │        │        │              │                  │
│   ┌──┴───┐ ┌──┴───┐ ┌──┴───┐       ┌──┴───┐    Weight  │
│   │ PE₁,₀│→│ PE₁,₁│→│ PE₁,₂│→ ... →│PE₁,₃₁│ → psum₁   │
│   │ w₁,₀ │ │ w₁,₁ │ │ w₁,₂ │       │w₁,₃₁ │    Stall   │
│   └──┬───┘ └──┬───┘ └──┬───┘       └──┬───┘    (权重    │
│      │        │        │              │         保持     │
│     ...      ...      ...            ...       静止)    │
│      │        │        │              │                  │
│   ┌──┴───┐ ┌──┴───┐ ┌──┴───┐       ┌──┴───┐             │
│   │PE₃₁,₀│→│PE₃₁,₁│→│PE₃₁,₂│→ ... →│PE₃₁,₃₁│→ psum₃₁  │
│   │w₃₁,₀ │ │w₃₁,₁ │ │w₃₁,₂ │       │w₃₁,₃₁│            │
│   └──────┘ └──────┘ └──────┘       └──────┘             │
│      ↓        ↓        ↓              ↓                  │
│   Partial Sum Accumulation Chain (部分和累加链)           │
└──────────────────────────────────────────────────────────┘

一个 32×32 Matmul 在 Systolic Array 上的执行过程:
  输入: A[32, K], B[K, 32]  (B 为 weight, A 为 activation)
  
  1. Weight 预加载阶段:
     for i in 0..31, j in 0..31:
       PE[i][j].weight = B[j][i]   // weight 加载到 PE 并驻留
     
  2. 计算阶段 (weight-stall, activation 流动):
     for cycle t in 0..(K+31):       // K 个计算周期 + 流水线填充/排空
       for i in 0..31:
         a_i = A[i][t-i] if 0 <= t-i < K else 0  // 激活沿行流动
         for j in 0..31:
           PE[i][j].psum += a_i * PE[i][j].weight  // 乘加
           if j < 31: pass psum to PE[i][j+1]     // 部分和向右传递
     
  3. 输出阶段:
     for i in 0..31:
       result[i] = PE[i][31].psum   // 从最右 PE 收集结果
```

Weight-Stall 范式的核心优势与限制：
- **优势**：权重加载一次后可复用多次（同一权重行用于所有 activation 列），大幅减少权重内存访问。适合 weight tensor 较小而 activation tensor 较大的场景（大 batch、长序列 prefill）。
- **限制**：当 weight tensor 远大于 activation tensor 时（如 decoding 阶段的 [4096, 14336] × [14336, 1]），仅有一个 activation 列流过阵列，权重需要频繁从内存重新加载到 PE（无法利用复用），NPU 效率急剧下降（NPU-2: order-sensitive performance 的根源）。
- **最坏情况**：如果 weight 矩阵无限大，NPU 无法利用 weight-stall 的优势，性能可能退化至甚至低于 GPU。

- Google TPUv1: 128×128 systolic array, INT8, weight-stationary dataflow
- Qualcomm Hexagon NPU (HTP): 多个 32×32 systolic array, 支持 INT8/INT16/FP16
- Apple Neural Engine (ANE): 多核 NPU，每个核含多个 MAC 单元（非标准 systolic array 但同属 weight-stationary）

**HeteroInfer 中的利用与规避**：
- 利用：通过计算不变量 `[M,N] × [N,K] → [[K,N] × [N,M]]^T` 交换张量顺序，使较小维度作为 weight，利用 weight-stall 减少内存操作。

**HVX (Hexagon Vector eXtension)**：
- 向量处理单元，4-6 个并行单元，每个含 32 个 1024-bit 向量寄存器
- 支持 SIMD 向量指令：vload/vstore、vmpy（乘法）、vadd/vsub、vmax/vmin、vlut16（16-entry 查表）、vgather（gather 64 个 2-byte 元素）

- 内存读取带宽 <30 GB/s（vs. DMA ≥60 GB/s）
- VLIW 架构：4 个 issue slot per scalar core，指令包最大 4 条指令并行

**HMX (Hexagon Matrix eXtension)**：
- 矩阵乘法专用单元，1-2 个单元
- FP16 HMX 基本数据单元：tile = 32×32，占用 2 KiB 空间
- 支持精度：INT4, INT8, INT16, FP16
- 操作流程：从 TCM load activation tile + weight tile → MatMul → accumulate to internal accumulator → output tile to TCM
- 支持 per-channel scale & bias（每个输出 channel 独立缩放+偏置）
- FP16 GEMM 峰值：~12 TFLOPS（1024³ GEMM, 所有数据在 TCM）
- 特殊内存布局（图 4）：每两行 permute，同 transposed 2×32 sub-matrix 布局；tile 外层 column-major 排列
- HMX 指令未公开——论文通过 reverse engineering 二进制库发现并使用

**TCM (Tightly Coupled Memory)**：
- 8 MiB software-managed on-chip memory
- HMX 所有操作和 HVX scatter/gather 仅能访问 TCM
- 数据通过 DMA 从 DDR→TCM（≥60 GB/s）或 12fetch 指令从 DDR→L2 cache
- DMA 支持 1D/2D 异步传输
- LUT-based exp 表占 64 KiB TCM（仅 0.8% 容量）

**CPU-NPU 通信**：
- rpcmem (kernel dmabuf wrapper)：CPU 与 NPU 间共享物理内存
- FastRPC：启动远程 NPU session
- 仅单向 cache coherence（CPU→NPU），需手动 L2 cache invalidate/writeback
- NPU 端 polling-based command dispatch（替代 RPC 默认机制，降低延迟）
- NPU 32-bit 虚拟地址空间限制（部分旧设备 2 GiB 限制）

## Mobile NPU DNN Execution Workflow（移动 NPU 的 DNN 执行流程与 LLM 适配约束）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

移动 NPU（如 Qualcomm Hexagon NPU）执行 DNN 推理的标准流程包括五个阶段：(1) **环境配置**（NPU runtime 初始化）；(2) **图构建**（模型转换 → NPU 中间表示 IR → 内存分配, 300–500ms）；(3) **图优化**（内存布局调整、执行顺序优化、算子融合, 数秒至数十秒——Gemma-2B 在 QNN 上需 11.54s）；(4) **图执行**（INT8 MatMul 在 NPU systolic array 上执行）；(5) **图释放**。其中 (2)+(3) 是一次性开销但极其昂贵，且对于 LLM prefill 中的变长 prompt 问题形成根本性障碍——因为每次不同长度的 prompt 都需要重新走一遍 (2)+(3)，使得 NPU 的总延迟反而高于 CPU。

此外，移动 NPU 的封闭性（如 QNN SDK 为闭源）限制了开发者直接修改编译器行为来适配 LLM 的特殊需求。llm.npu 采用 Chunk-sharing Graph 绕过而非修改图编译流程。

LLM vs. CNN 的区别导致 NPU 图编译瓶颈:
  CNN (如 MobileNet-V2):
    - 输入形状固定: [1, 3, 224, 224] — 永远不变
    - Build + Optimize 一次 → 推理无数次
    → 图编译开销被摊还, NPU 23× 快于 CPU
  
  LLM (如 Gemma-2B):
    - 输入形状可变: [1, N] 其中 N = 64, 256, 1024, 1500... — 每次推理可能不同
    - Build + Optimize 每次推理都要重新走一遍
    → 图编译开销无法摊还, NPU 速度反而低于 CPU

## Qualcomm QNN (Qualcomm AI Engine Direct SDK)

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

QNN (Qualcomm Neural Processing SDK, 也称 Qualcomm AI Engine Direct SDK) 是 Qualcomm 提供的官方 NPU 编程框架，用于将深度学习模型部署到 Snapdragon SoC 的 Hexagon NPU (HTP) 上执行。它是访问 Hexagon NPU 的唯一公开编程接口——开发者无法直接编写 NPU 指令或绕过 QNN 使用 NPU 硬件。

QNN 的工作流程：(1) **模型转换**——将 ONNX/TensorFlow/PyTorch 模型转换为 QNN 的中间表示 (IR)；(2) **图构建**——将 QNN IR 编译为针对特定 SoC 的 Hexagon NPU 计算图（含内存分配、算子映射）；(3) **图优化**——根据 NPU 硬件特性优化内存布局、执行顺序和算子融合；(4) **图执行**——在 Hexagon NPU 上运行优化后的计算图；(5) **图释放**。

QNN 的关键限制（直接驱动 llm.npu 的设计）：(1) 仅支持静态形状（不能在运行时改变张量维度）；(2) 不支持 per-group 量化 MatMul（无法直接执行 K-Quant/AWQ 风格的 LLM 量化推理）；(3) 图构建和图优化的时间开销极大（秒级），不能用于每次推理的在线图生成；(4) SDK 闭源——开发者无法修改编译器行为。

## DVFS（Dynamic Voltage and Frequency Scaling，动态电压频率调节）

术语是什么？回答尽量完整，回答逻辑链中每一步都解释出来。通过联网搜索让回答具体和精准。

DVFS (Dynamic Voltage and Frequency Scaling) 是现代处理器的硬件级功耗管理技术。核心原理：数字电路动态功耗 $P \propto C \cdot V^2 \cdot f$（$C$ 负载电容，$V$ 工作电压，$f$ 时钟频率）——更高频率需更高电压维持信号完整性。DVFS 在运行时动态调整频率和电压：不必要时降频降压以省电，需要性能时升频升压以减少执行时间。总能量 $E = P \cdot t$，DVFS 的优化目标是在 $P$ 和 $t$ 间寻找最优权衡。

DVFS 硬件实现层次：PLL (Phase-Locked Loop) 生成可编程时钟频率；PMIC (Power Management IC) 提供可编程电压轨；DVFS 硬件驱动 (cpufreq/kgsl/devfreq) 接收 governor 的频率请求 → 查 OPP table → 编程 PLL 和 PMIC。OPP (Operating Performance Point) Table 由芯片制造商通过硅特性化预定义。

从硬件架构角度拆解（Google Tensor G2 Pixel 7）：
- CPU: 18 OPPs, 500-2850 MHz (Cortex-X1 perf + Cortex-A55 efficiency cores)
- GPU (Mali-G710): 12 OPPs, 151-848 MHz
- Memory (MIF): 13 OPPs, 421-3172 MHz
- DVFS 切换延迟: PLL 锁定 ~10-50 μs, PMIC 电压斜坡 ~50-200 μs, Governor 决策周期 CPU~1ms / GPU~10-30ms / MIF~20ms
- 三个 DVFS domain 硬件独立但通过 workload 产生利用率耦合

术语一般如何实现？如何使用？

**LLM 推理中的 DVFS 特殊性**（FUSE 论文揭示）：
- Prefill: compute-bound, GPU util ~83% → GPU governor 自然选高频 → DVFS 优化空间有限
- Decode: memory-bound (batch=1), GPU util ~50-70% → governor 倾向降频 → DVFS 决策空间大但 governor 方向错误
- 拮抗效应使 DVFS 在两阶段均远离最优——独立 governor 在跨组件利用率耦合时失效
