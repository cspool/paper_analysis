# 知识库_硬件架构

## In-Switch Computing

术语是什么？
In-Switch Computing（交换机内计算）是一种将轻量级计算原语（多播、归约、转发决策等）卸载到网络交换机/路由器中的数据路径上的技术。数据在流经交换机时，交换机不仅做路由转发，还执行计算操作。在 GPU 互联场景中，NVSwitch 被增强为不仅能转发数据包，还能执行 in-switch multicast（交换机内多播：GPU 仅发送一次数据到交换机，交换机复制并转发到多个目标 GPU）和 in-switch reduction（交换机内归约：多个 GPU 的中间结果在交换机内累加，仅最终结果传回目标 GPU），从而消除多 GPU 间的冗余数据传输。

从硬件架构角度拆解：
In-switch computing 在 MoE 场景的硬件工作流程（以 NVSwitch 为例）：

```
// In-Switch Multicast (Dispatch):
GPU0 --> NVSwitch: 发送单份 token 数据包（含 target list [GPU2, GPU3]）
NVSwitch:
  1. Route Module: 解析 target list，计算输出端口
     OutPort_GPU2 = GPU2 / experts_per_GPU
     OutPort_GPU3 = GPU3 / experts_per_GPU
  2. Crossbar: 复制数据包到 OutPort_GPU2 和 OutPort_GPU3
  3. 每个输出端口裁剪 target list 为该端口相关的 targets
  4. 转发到 GPU2 和 GPU3

// In-Switch Reduction (Combine):
GPU2 --> NVSwitch: 发送 expert 输出（带 reduction 请求）
GPU3 --> NVSwitch: 发送 expert 输出（带同一 reduction 请求）
NVSwitch:
  1. Reduction Logic: 识别属于同一 reduction 的请求
  2. 累加到达的 partial results
  3. 追踪计数: target_count--，直到归零表示所有 partial 到达
  4. 将最终归约结果返回 GPU0
```

传统方案中，Dispatch 时 GPU0 需分别发送 token 到 GPU2 和 GPU3（两份数据过 GPU0-Switch 链路），Combine 时 GPU2 和 GPU3 各自发送中间结果到 GPU0（两份数据过 Switch-GPU0 链路）。In-switch computing 使两方面均仅需一次传输。

术语一般如何实现？如何使用？
- NVIDIA H100 (Hopper) 起在 NVSwitch 中集成 NVLink SHARP (NVLS)，支持 multimem 指令的 in-switch multicast 和 reduction，但仅限静态 collective 操作（AllGather、Reduce-Scatter）。
- 多节点 InfiniBand 网络中，IB SHARP (Scalable Hierarchical Aggregation Protocol) 在 Quantum IB Switch 中实现类似的 in-switch reduction。
- DySHARP 将 in-switch computing 扩展到动态非规整通信模式（MoE Dispatch/Combine），通过 dynamic multimem addressing 实现硬件支持。
- 其他 in-switch computing 工作：CAIS (HPCA'26) 针对静态 collective 的 compute-aware in-switch computing；TRACI (ISCA'25) 针对 DLRM 的 input-dynamic in-switch computing；Flare (SC'21) 针对多租户的 flexible in-switch AllReduce。

## NVLink SHARP (NVLS)

术语是什么？
NVLink SHARP (NVLS) 是 NVIDIA 从 Hopper 架构 (H100) 起引入的硬件 in-switch computing 技术，通过 NVSwitch 内的专用数据路径实现集体通信操作（AllGather、Reduce-Scatter 等）的卸载加速。NVLS 引入 multimem 寻址模型：GPU 通过 `cuMulticastCreate` 创建 multicast group，每个 GPU 在 group 内 bind 本地物理内存，共享单一 multimem 地址。GPU 使用 `multimem.st`（多播存储）和 `multimem.ld_reduce`（归约加载）PTX 指令在此地址空间上操作，NVSwitch 自动完成数据多播/归约。

从硬件架构角度拆解：
NVLS 的 multimem 寻址工作流程：

```
// 初始化 (Host):
cuMulticastCreate(&mc_handle)           // 创建 multicast object
cuMulticastAddDevice(mc_handle, GPU0)   // 添加 GPU 到 group
cuMulticastAddDevice(mc_handle, GPU1)
...
cuMulticastBindMem(mc_handle, GPU0, local_mem_0)  // 各 GPU bind 本地内存
cuMulticastBindMem(mc_handle, GPU1, local_mem_1)
multimem_addr = cuMulticastGetAddress(mc_handle)   // 获取 multimem 地址

// GPU Kernel (使用 multimem 指令):
// AllGather 等效: multimem.st
asm("multimem.st.global [%0], %1" :: "l"(multimem_addr), "r"(data))

// Reduce-Scatter 等效: multimem.ld_reduce
asm("multimem.ld_reduce.global.add [%0], %1" :: "l"(multimem_addr), "r"(result))

// NVSwitch 硬件:
// - multimem.st: Switch 识别 multimem 地址空间，按预配置 target set 多播
// - multimem.ld_reduce: Switch 从所有 group 成员收集数据，归约后返回
```

NVLS 的静态限制：
- Fixed target sets: 所有操作始终与同一组 GPU 通信
- Symmetric addressing: token 在各 GPU 上位于相同内存偏移
- 因此仅支持 AllGather 和 Reduce-Scatter 等静态 collective，无法处理 MoE 的动态非规整通信（varying targets + asymmetric addressing）。

术语一般如何实现？如何使用？
- 硬件需求: Compute Capability 9.0+ (H100/B200)、NVLink4/5 NVSwitch、CUDA 12.1+。
- NCCL 通过 `NCCL_ALGO=NVLS` 使用 NVLS 加速 AllReduce，DGX H100 上可实现约 480 GB/s 带宽（传统 ring 算法约 370 GB/s）。
- NVSHMEM 3.2.5 支持基于 NVLS 的 one-shot/two-shot AllReduce（fp16/bf16/fp32）。
- 静态 collective 模拟 MoE 通信（用 AllGather 模拟 Dispatch, Reduce-Scatter 模拟 Combine）会产生 340% 无用流量，因为所有 GPU 无论是否需要都参与通信。
- DySHARP 通过 dynamic multimem addressing 将 NVLS 扩展到动态通信模式。

## Dynamic Multimem Addressing

术语是什么？
Dynamic Multimem Addressing 是 DySHARP 提出的对 NVLS multimem 寻址框架的动态扩展。它在 NVLS 的基础上新增：(1) 自定义包格式——携带单个 multimem 地址（algebraic index）+ 轻量 target expert list（target extension flits）；(2) ISA 扩展——`dymultimem.st` 和 `dymultimem.ld_reduce` 指令；(3) GPU 微架构——SM LSU 新增 MultimemQ 用于 target 预取，Hub 新增 Hardware Memory Manager 做 algebraic→layout index 映射（AL Table + AL TLB）；(4) Switch 微架构——Route 模块增强 target-aware 转发，Reduction Logic 增强完成追踪。这使得 in-switch computing 可以支持 MoE 的动态非规整通信（varying target sets + asymmetric addressing）。

从硬件架构角度拆解：
Dynamic Multimem Addressing 的完整硬件工作流程：

```
// Source GPU:
1. dymultimem.st 指令进入 SM LSU
2. LSU 通过 MultimemQ 从 shared/global memory 预取 target expert list
   (r3=target_count, r4=target_list_base_addr)
3. LSU 组装请求包:
   - flit0: 48b multimem_addr | 1b stage(Dispatch/Combine) | 15b target_count
   - flit1+: target extension flits (每 flit 8 个 16-bit expert ID)
   - 后续 flit: byte enable + payload
4. 请求包经 on-chip network -> NVLink -> NVSwitch

// Switch:
5. Route Module: 对每个 target i
   OutPort[i] = Target[i] / experts_per_GPU
   按输出端口分组，复制请求包，每个副本仅保留该端口 targets
6. 多播到各 destination GPU
7. (Combine) Reduction Logic:
   记录 target_count，每到达一个 partial response 递减计数
   计数归零 -> 返回归约结果到 source GPU

// Destination GPU:
8. Hub Hardware Memory Manager 接收请求
9. 查 AL TLB (tag = ExpertID | AIdx):
   - Hit: 直接获取 LIdx
   - Miss: 访问 DRAM 中 AL Table[AIdx] 获取 LIdx，填充 AL TLB
10. (Dispatch, 首次访问) AL Table[AIdx] 无效:
    分配新的 layout block (counter++)
    写 AL Table[AIdx] = {Valid=1, LIdx=next_free_block}
11. MV Translation: VAddr = VBase + LIdx * bsize + MAddr % bsize
12. 用 VAddr 做内存访问 (dymultimem.st: write; dymultimem.ld_reduce: read)
13. 标准 Link MMU 做 Virtual -> Physical 翻译
```

关键设计决策：
- 单个 multimem 地址携带 algebraic index（所有 GPU 间相同），而非 destination 物理地址。
- Hardware Memory Manager 在 destination GPU 本地管理 asymmetric memory layout（AL Table 做 algebraic→layout 映射），消除 software overhead。
- 相比显式寻址（包中嵌入所有 destination 地址），dynamic multimem addressing 保持高 payload efficiency（约 80% vs 显式寻址的 69%，8 destination 时）。

术语一般如何实现？如何使用？
- 需要对 GPU (SM LSU + Hub Memory Manager) 和 Switch (Route + Reduction Logic) 的微架构修改。
- CUDA Runtime API 扩展：`cuDyMulticastCreate` 和 `cuDyMulticastBindAddr`。
- AL Table 大小：4 × nToken bytes（1M token 仅 4MB/layer），远小于 GPU DRAM 容量。
- AL TLB 512-entry 为 sweet spot，可实现 near-ideal 命中率。
- MultimemQ 32 entry，匹配 in-flight dymultimem 请求数。
- 所有修改 build upon 现有 datapath，不改变原有功能，支持所有其他 workload。

## Algebraic-Layout (AL) Mapping / AL Table

术语是什么？
Algebraic-Layout (AL) Mapping 是 DySHARP Destination GPU Hub 中 Hardware Memory Manager 的核心寻址机制。它将 token 的 "algebraic index"（algebraic tensor 中 token 的逻辑索引，所有 GPU 间相同）映射到 "layout index"（该 GPU 上实际内存中压缩存储的 layout tensor 索引，各 GPU 间不同/非对称）。AL Table 是存储此映射的 DRAM 表（每 entry 4B: 1b Valid + 31b LIdx），按 algebraic block index (AIdx) 索引。AL TLB (512-entry CAM + SRAM) 加速查表。

从硬件架构角度拆解：
AL Mapping 的生命周期：

```
// Dispatch Phase: 建立映射
当 dymultimem.st 请求到达 destination GPU:
  AIdx = (MAddr - MBase) / bsize          // 从 multimem 地址计算 algebraic block index
  查 AL Table[AIdx]:
    if Valid == 0:                          // 首次访问该 algebraic block
      LIdx = next_free_layout_counter++     // 分配新的 layout block
      AL Table[AIdx] = {Valid=1, LIdx}      // 注册映射
    else:
      LIdx = AL Table[AIdx].LIdx            // 已有映射
  // 用 LIdx 做 MV Translation -> 写数据到 layout tensor

// Combine Phase: 复用映射 (token 顺序不变)
当 dymultimem.ld_reduce 请求到达 destination GPU:
  AIdx = (MAddr - MBase) / bsize
  查 AL Table[AIdx]:
    使用相同的 LIdx                       // Dispatch 时已建立
  // 用 LIdx 做 MV Translation -> 读数据返回

// MV Translation 公式:
VAddr = VBase + LIdx * bsize + (MAddr % bsize)
// MBase, VBase: multimem 和 virtual 地址空间的基地址
// bsize: block size (token vector 大小)
// MV Translation 与 AL Management 解耦，因为 Dispatch/Combine
// 共享 algebraic-layout 映射但操作不同的 virtual 地址空间
```

AL TLB 结构：
- Tag: Expert ID | AIdx（用 CAM 实现快速匹配）
- Data: AL Table entry (Valid + LIdx)
- Hit: 直接获取 LIdx; Miss: 访问 DRAM AL Table + 填充 TLB
- 512-entry, 16-bank dual-port SRAM (1R1W)
- 高命中率因 token 内连续访问的强时间局部性

术语一般如何实现？如何使用？
- 每个 GPU 本地管理自己的 AL Table，无跨 GPU 同步。
- 每个 expert 有独立的 AL sub-table（当多个 expert 驻留同一 GPU 时）。
- AL Table 大小 = 4 × nToken bytes/layer，1M token 仅 4MB。
- AL TLB 用 CAM + SRAM 实现以支持快速并行的 tag matching。
- 这是 dynamic multimem addressing 实现 asymmetric addressing 支持的关键机制。
