## 1 数据流设计：HBM→计算核心的完整访存路径

### 1.1 GPU Memory Hierarchy 数据流路径

**笔记证据**: `knowledge_notes/硬件知识笔记/GPU Memory Hierarchy (HBM vs SRAM).md` (score: 10900)、`knowledge_notes/系统知识笔记/Memory Wall.md` (score: 3878)

```mermaid
flowchart TD
    HBM["HBM (High Bandwidth Memory)<br/>Off-chip DRAM<br/>40-80GB / 1.5-3.35TB/s<br/>Latency: 400-800 cycles"]
    L2["L2 Cache<br/>On-chip, shared across all SMs<br/>40-50MB / 7-12TB/s<br/>Latency: ~200 cycles"]
    L1["L1 Cache / Shared Memory (per SM)<br/>Configurable partition, 128-228KB<br/>Bandwidth: ~19TB/s<br/>Latency: 20-30 cycles"]
    RF["Register File (per SM)<br/>256KB, 65536 x 32-bit registers<br/>Bandwidth: ~40TB/s<br/>Latency: 0 cycles (immediate)"]
    TC["Tensor Core / CUDA Core<br/>Compute Units"]
    DSM["DSM (L1.5 Cache) — H100 only<br/>SM-to-SM Crossbar NoC<br/>0.2-3.6MB / 4-8TB/s"]

    HBM -->|"TMA / cp.async / LDG"| L2
    L2 -->|"Cache Line 128B"| L1
    L1 -->|"ldmatrix / ld.shared"| RF
    RF -->|"operand collector"| TC
    TC -->|"writeback"| RF
    RF -->|"st.shared / TMA store"| L1
    L1 -->|"writeback / evict"| L2
    L2 -->|"writeback"| HBM
    L1 -.->|"SM-to-SM via Crossbar (H100+)"| DSM
    DSM -.->|"dsm_shuffle / dsm_all_exchange"| L1

    style HBM fill:"#ffcccc",stroke:"#cc0000"
    style L2 fill:"#ffe0cc",stroke:"#cc6600"
    style L1 fill:"#ffffcc",stroke:"#cccc00"
    style RF fill:"#ccffcc",stroke:"#00cc00"
    style TC fill:"#ccccff",stroke:"#0000cc"
    style DSM fill:"#e0ccff",stroke:"#6600cc"
```

**注解**：
- **HBM**：以 H100 为例，HBM3 80GB，带宽 3.35 TB/s，是 GPU 的主存储器。存储模型参数、KV Cache、中间激活。多算子并发场景下，不同算子的数据 tile 在 HBM 中交错存放，由 TMA/cp.async 按需搬运到 SMEM。笔记显示 H100 的 FP16 峰值算力（~1000 TFLOPS）增速 3.3× 远超 HBM 带宽增速（1.5×），导致 Memory Wall 问题——多算子并发加剧了这一带宽竞争。
- **L2 Cache**：40-50MB 片上 SRAM，所有 SM 共享。L2 充当 HBM 的"最后一级片上缓存"，hit rate 决定有效带宽。TMA 可绕过 L1 直写 SMEM，但数据仍经过 L2。在多算子并发时，L2 的替换策略（LRU 或类似）会影响不同算子数据 tile 的缓存命中率。
- **L1/SMEM**：per-SM 128-228KB，可配置 split（如 A100 最大 164KB shared memory + 28KB L1）。这是程序员显式管理的最快片上存储，也是多算子 tile 连接的枢纽——WELDER 通过 shared memory tile connection 让前一个算子的输出 tile 直接留在 SMEM 被后一个算子消费，消除 HBM 往返。
- **RF**：256KB/SM，0 延迟访问。每线程最多 255 个 32-bit 寄存器。Warp specialization 中 DMA warp 几乎不消耗寄存器，其寄存器 bank 可被 compute warpgroup 复用。
- **DSM (H100)**：位于 L1.5 层，通过 SM-to-SM Crossbar NoC 将同一 cluster 内最多 16 个 SM 的 SMEM 互联为 3.6MB 池，带宽 4-8TB/s（介于 SMEM 和 L2 之间）。FlashFuser 利用 DSM 将中间 tensor 数据路径从 `SMEM→HBM→HBM→SMEM` 改为 `SMEM→DSM→SMEM`，减少 58% global memory access。

### 1.2 针对多算子并发的访存数据供给流水线

**笔记证据**: `knowledge_notes/kernel知识笔记/Hierarchical Software Pipeline for GPU Kernels.md` (score: 885)、`knowledge_notes/kernel知识笔记/Warp Specialization.md` (score: 2031)、`knowledge_notes/硬件知识笔记/Asynchronous Memory Copy (async-copy).md` (score: 1356)

三级异步数据供给流水线（以 fused dequantization-GEMM 为例，Quantix/ZipGEMM 设计）：

```
时间方向 →
Level 1 (Global→Shared):  [cp.async tile 0][cp.async tile 1][cp.async tile 2]...
Level 2 (Shared→Reg+Dequant):   [dequant s0][dequant s1][dequant s2][dequant s3]...
Level 3 (Tensor Core MMA):          [mma s0][mma s1][mma s2][mma s3]...

三级完全重叠: 当 TC 计算 tile i 的 slice j 时,
  cp.async 正在加载 tile i+2,
  CUDA Core 正在解量化 tile i+1 的 slice j
```

**注解**:
- Level 1（Inter-tile）：利用 cp.async (Ampere) 或 TMA (Hopper) 硬件 DMA，在 shared memory 中维护双缓冲（Smem0/Smem1），`cp.async.wait_group<0>()` + `__syncthreads()` 协调缓冲切换。
- Level 2（Intra-tile）：寄存器级双缓冲（Reg0/Reg1），CUDA Core 执行 dequantization 的同时 Tensor Core 消费上一个 slice 的结果。warp 内 SIMT lockstep 天然同步。
- Level 3（Compute）：Tensor Core 异步 MMA（`wgmma` on Hopper），通过 `warpgroup_wait()` 同步。
- 三级全重叠设计使 ALU 利用率达 66%，Tensor Core 利用率保持 cuBLAS 的 71.6%。禁用 pipeline 后性能降至完整版本的 ~41%。

## 2 控制模块详解：调度、同步与并发机制

### 2.1 控制模块功能表

**笔记证据**: `knowledge_notes/kernel知识笔记/Warp Scheduler (NVIDIA GPU).md` (score: 3340)、`knowledge_notes/硬件知识笔记/GPU Hardware Dispatch Unit (GPU硬件调度单元).md` (score: 1699)、`knowledge_notes/硬件知识笔记/GPU Scoreboard and Throttle Stalls.md` (score: 1003)、`knowledge_notes/硬件知识笔记/Hopper TMA (Tensor Memory Accelerator).md` (score: 8862)、`knowledge_notes/kernel知识笔记/Warp-Group Specialization (Hopper GPU).md` (score: 2669)

| 控制模块 | 硬件位置 | 功能描述 | 并发支持机制 | 多算子支持说明 |
|----------|----------|----------|-------------|---------------|
| **GigaThread Engine / Hardware Dispatch Unit** | GPU 全局 | 接收 CUDA stream 中的 kernel block 队列，执行 left-over scheduling 将 block 分配到 SM | 按 block 资源需求（threads/shmem/regs）与 SM 余量匹配分配 | 不同 kernel 的 block 可同时驻留在不同 SM 上（spatial sharing）；同一 SM 上不同 kernel 的 block colocation 取决于资源可用性 |
| **Thread Block Scheduler (per-GPU)** | GPU 全局 (GSP firmware) | Leftover Policy（仅队头 kernel 的 block 可调度，不可抢占）+ Most-Room Policy（选能容纳最多 block 的 SM） | 无跨 kernel 依赖感知；大 kernel 独占 GPU | 并发主要发生在多个小 kernel（所有 block 能一次全部调度）之间；μShare 通过 blocksize 间接影响调度 |
| **Warp Scheduler (per-SM)** | 每 SM 4 个单元 | 每周期从 resident block 的 ready warps 中选择 warp 发射指令到执行核心 | Warp 间零成本切换（独立 per-warp PC + RF）；greedy-then-oldest 或 loose round-robin 策略 | 同一 SM 上不同 kernel 的 warps 可被同一 scheduler 交错调度——这是 intra-SM 多算子并发的核心机制 |
| **Scoreboard** | 每 SM，与 Warp Scheduler 耦合 | 追踪每条指令的 data dependency（register 是否就绪、memory load 是否完成），阻止操作数未就绪的指令发射 | Scoreboard stall → Warp Scheduler 自动切换到另一 ready warp | 多算子场景中一算子等待 memory 时，另一算子的 warp 获得执行——这是 latency hiding 的硬件基础 |
| **Throttle Control** | 每 SM，与执行单元耦合 | 检测执行单元（FP32/Tensor Core/LD/ST）的结构竞争，当所需单元被占用时阻止指令发射 | Throttle stall → Warp Scheduler 选择需要不同执行单元的 warp | 多算子混合（如 GEMM + dequantization）天然利用不同执行单元（Tensor Core + CUDA Core），减少 throttle stall |
| **TMA (Tensor Memory Accelerator)** | 每 SM，Hopper+ 专用硬件 | 异步 bulk tensor 传输（1D-5D），支持 multicast、descriptor-based addressing、completion barrier | 单线程发起→硬件独立完成；consumer 通过 mbarrier 等待；producer 可继续其他工作 | 将数据搬运从 CUDA Core 卸载到专用 DMA——释放的线程可用于另一算子的计算 |
| **cp.async Engine (LDGSTS)** | 每 SM，Ampere+ 硬件 | 异步 global→shared memory copy（4/8/16B 粒度），16B copy 支持 L1 bypass | `__pipeline_commit` + `__pipeline_wait_prior` 流水线同步 | 与 TMA 类似但粒度更细，适合小 tile 或非规则访问模式的多算子数据传输 |
| **mbarrier (Hopper)** | Shared Memory 内 | 异步 barrier：producer arrive（硬件写入），consumer wait（按需等待），支持 expect_tx 字节级计数 | 与 `__syncthreads()` 不同——不阻塞所有线程，仅阻塞等待方 | Warp-group specialization 的核心同步原语：DMA warp arrive → compute warpgroup wait |
| **MIG (Multi-Instance GPU)** | GPU 全局 (A100/H100) | 将单个 GPU 物理划分为最多 7 个独立实例，各自有专用 SM/内存/带宽隔离 | 硬件级故障隔离和 QoS 保证 | 极端 spatial sharing：不同算子完全隔离到不同实例，零竞争但牺牲灵活性和峰值利用率 |
| **Command Processor** | GPU 前端 (GigaThread Engine 内) | 解码 host 发送的 kernel launch packet，将 kernel 放入执行队列 | 管理 CUDA stream 的顺序语义和跨-stream 依赖 | 笔记未详细说明其内部设计（闭源），但它是多 stream 并发 kernel 发射的入口点 |

### 2.2 Warp Scheduler 调度策略与并发

**笔记证据**: `knowledge_notes/kernel知识笔记/Warp Scheduler (NVIDIA GPU).md` (score: 3340)、`knowledge_notes/硬件知识笔记/Warp _ Warp Scheduler.md` (score: 2796)

Warp Scheduler 的推测调度逻辑（逆向工程推断，NVIDIA 未正式文档化）：

```
// Per-SM, per-cycle warp scheduling (推测模型)
function warp_scheduler_cycle(sm):
    for each of 4 warp_scheduler_units in sm:
        eligible_warps = []
        for warp in scheduler.warp_pool:
            if warp.is_ready():  // scoreboard: 无 data hazard
                if not throttle_check(warp.next_inst):  // structure hazard
                    eligible_warps.append(warp)

        if eligible_warps is empty:
            issue NOP  // idle cycle

        // 调度策略 (greedy-then-oldest，多数文献推测):
        if prev_warp in eligible_warps:
            issue prev_warp  // 优先保持上一周期发射的 warp (指令 cache warm)
        else:
            issue oldest_ready_warp(eligible_warps)  // 次选等待最久的 ready warp
```

**注解**：
- Ampere SM 有 4 个 warp scheduler，每个每两周期发射 1 条 warp 指令。峰值发射率：4 × 0.5 × 1.7GHz ≈ 3.4 warp instructions/clock/SM。
- Warp 切换零成本的核心原因是 SM 为每个 warp 维护独立的 register file 和 program counter——无需 context save/restore。这使得 scheduler 可以在单周期内在不同 warp（甚至不同 kernel 的 warp）间切换。
- Priority Streams 是否影响 warp scheduler 的选择：笔记指出官方文档未说明，推测 warp scheduler **不感知 stream priority**——这可能导致高优先级 warp 被 de-prioritized。这是多算子并发中优先级隔离的一个已知限制。
- 笔记 `Characterizing Concurrency Mechanisms for NVIDIA GPUs` 指出：缺乏 fine-grained preemption 机制、robust task prioritization 和 contention-aware thread block placement 限制了并发效率。

### 2.3 多算子并发的同步机制层次

**笔记证据**: `knowledge_notes/kernel知识笔记/Warp Specialization.md` (score: 2031)、`knowledge_notes/kernel知识笔记/Warp-Group Specialization (Hopper GPU).md` (score: 2669)

同步原语的层次结构（从粗到细）：

| 同步粒度 | 硬件机制 | 适用范围 | 开销 | 并发影响 |
|----------|----------|----------|------|----------|
| GPU 全局 | CUDA Stream 顺序语义 | 跨 kernel 依赖 | ~5μs kernel launch overhead | 限制：不同 stream 的 kernel 可 overlap，但 block-level 调度不感知 stream 依赖 |
| Block 级 | `__syncthreads()` | Block 内所有 warp | ~20-50 cycles | 阻塞整个 block——warp specialization 中需避免（改用 mbarrier） |
| Warpgroup 级 | `warpgroup_sync()` + `warpgroup_wait()` | Hopper warpgroup (4 warps) | ~10 cycles | Warp-group specialization：DMA warpgroup 和 compute warpgroup 独立同步 |
| Warp 级 | `__shfl_sync`, `__ballot_sync` | Warp 内 32 线程 | ~1-5 cycles | SIMT lockstep 天然同步 |
| 异步 | mbarrier (Hopper) | Producer-Consumer 跨 warp/warpgroup | 硬件管理，~0 cycle overhead | TMA completion → mbarrier arrive → consumer wait：零 CPU 参与 |

**注解**：
- Warp specialization 在 Hopper 上的关键突破：将 DMA warp（1 warp = 32 threads，仅 thread 0 调用 TMA）和 Compute Warpgroup（4 warps = 128 threads，执行 WGMMA）分离，通过 mbarrier 异步同步。DMA warp 和 compute warpgroup 通过 warp scheduler 的 time-multiplexing 交替执行：
  - Compute warpgroup 在等 Tensor Core 完成（`warpgroup_wait`）时 → scheduler 切换到 DMA warp
  - DMA warp 在等 consumer 释放 buffer（`wait(cons)`）时 → compute warpgroup 获得执行
- Pipelining depth (PIPE=3) 确保 TMA 延迟被完全隐藏。

## 3 多算子/微算子并发的数据供给关键设计方法

### 3.1 双缓冲与软件流水线

**笔记证据**: `knowledge_notes/kernel知识笔记/Double Buffering for CPU-GPU KV Cache Transfer.md` (score: 3333)、`knowledge_notes/kernel知识笔记/Hierarchical Software Pipeline for GPU Kernels.md` (score: 885)

双缓冲（Double Buffering）是多算子并发数据供给的基础范式：

```
// 通用双缓冲模式（shared memory 级）
Buffer A, Buffer B  // 两个 shared memory buffer

for tile_idx in 0..N-1:
    read_buffer  = (tile_idx % 2 == 0) ? A : B
    write_buffer = (tile_idx % 2 == 0) ? B : A

    // Step 1: 等待 write_buffer 中的前一个 tile 已被消费
    cp.async.wait_group<0>()
    __syncthreads()

    // Step 2: 发起下一个 tile 的异步加载到 write_buffer
    cp.async(write_buffer, global_ptr + (tile_idx+1) * tile_size)

    // Step 3: 计算当前 read_buffer 中的 tile
    compute(read_buffer)

    __pipeline_commit()
```

**注解**：
- 双缓冲将数据搬运与计算串行依赖转化为流水线重叠，理论峰值效率可达 `max(T_compute, T_transfer) / (T_compute + T_transfer)`。
- 多算子场景下，双缓冲扩展到多级 pipeline：inter-tile（smem 双缓冲）+ intra-tile（register 双缓冲），实现 `global→shared`、`shared→register+dequant`、`Tensor Core MMA` 三级全重叠。
- 笔记指出 CPU-GPU KV Cache 传输的双缓冲仅适用于可预测的数据访问模式（如 critical key cache 的 channel 级预取），不可预测的数据依赖（如 Top-K token retrieval）无法使用双缓冲——这是 pipeline 中的串行瓶颈。

### 3.2 Memory Coalescing 与带宽利用

**笔记证据**: `knowledge_notes/硬件知识笔记/GPU Memory Coalescing.md` (score: 3750)

Coalescing 是 GPU 访存系统将 warp 内 32 线程的 global memory 请求合并为最少 128B transaction 的硬件机制：

```
LSU (Load-Store Unit) 的合并逻辑：

Case A: Coalesced → 1 transaction
  thread_i 访问 base + i*4 (连续对齐)
  → 32 × 4B = 128B 在同一个 cache line 内
  → 合并为 1 个 128B transaction → 100% bandwidth 效率

Case B: Uncoalesced → up to 32 transactions
  thread_i 访问 base + random_offset[i] (scatter)
  → 地址分散在多个 128B cache line
  → 每个 cache line 产生独立 transaction
  → bandwidth 利用率可能低至 3-10%
```

Coalescing 效率因子：`γ = A / (M × 128)`，其中 A = 实际有用字节数，M = 所需 128B transaction 数。γ=1 为完美合并，γ<1 为带宽浪费。

**注解**：
- 多算子并发的 coalescing 挑战：不同算子可能有不同的访问模式（如 GEMM 的 dense tile 访问 vs sparse attention 的 gather 访问），混合同一 warp scheduler 时可能导致 L2 cache 污染和带宽碎片化。
- VDHA 利用 hash-based flush（hash 保留 row index 低位 → flush 时 consecutive threads 访问 consecutive addresses）将 γ 从 0.744 提升至 2.607。

### 3.3 异步数据搬运：cp.async 与 TMA

**笔记证据**: `knowledge_notes/硬件知识笔记/Asynchronous Memory Copy (async-copy).md` (score: 1356)、`knowledge_notes/硬件知识笔记/Tensor Memory Accelerator (TMA).md` (score: 8555)、`knowledge_notes/硬件知识笔记/Hopper TMA (Tensor Memory Accelerator).md` (score: 8862)

两代异步数据搬运硬件对比：

| 特性 | cp.async (Ampere A100) | TMA (Hopper H100) |
|------|------------------------|---------------------|
| 编程模型 | warp 内所有线程参与地址计算和发射 | 单线程发起，硬件完成全部传输 |
| 数据路径 | GMEM → L1/L2 → SMEM（16B 粒度） | GMEM → SMEM（bulk tensor，1D-5D） |
| 寄存器中转 | 经过寄存器（增加寄存器压力） | 不经过寄存器（直接 GMEM↔SMEM） |
| 同步机制 | `__pipeline_commit` + `__pipeline_wait_prior` | mbarrier（硬件自动 arrive on completion） |
| Multicast | 不支持 | 单次读取广播到 cluster 内多 SM 的 SMEM |
| 对齐要求 | 4/8/16B | 128B (SMEM destination), 16B (innermost coord) |
| 带宽利用率 | 高（对大块传输） | 更高（2KB 消息可达 74% 峰值 NVLink 带宽） |
| 描述符 | 线性地址 | TensorMap descriptor（host 端通过 cuTensorMapEncodeTiled 创建） |

TMA 在多算子并发中的关键价值：
- **释放线程资源**：传统 cp.async 需要 warp 内所有线程参与地址计算，TMA 仅需 1 个线程——其余 127 线程可用于另一算子的计算。
- **Warp specialization 使能**：DMA warp 专门执行 TMA，compute warpgroup 专门执行 WGMMA——这是 Hopper 上高性能多算子并发的标准范式。
- **Multicast 消除数据重复搬运**：attention 中同一 K/V tile 被多个 Q tile 消费时，TMA 单次读取广播到 cluster 内多 SM。

## 4 负载特定设计方法

### 4.1 MoE：Expert Weight Prefetching 与 Memory Footprint

**笔记证据**: `knowledge_notes/kernel知识笔记/Expert Weight Prefetching with HtoD Overlap.md` (score: 123)

MoE 多算子并发的核心访存挑战：
- **Expert 权重巨大**：MoE 模型（如 Mixtral 8×7B、DeepSeek-V3）的 expert 权重总量远超单 GPU HBM 容量，需 offload 到 CPU memory。
- **HtoD Prefetch Overlap**：利用 GPU 计算当前 expert 的时间窗口，通过 HtoD engine（PCIe Copy Engine）异步将下一个 expert 权重从 CPU 预取到 GPU expert buffer。

```
Expert 顺序执行 + 预取时间线：

Expert 1: |──── Compute E1 ────|
                          ↕ overlap
Expert 2:   |── HtoD Prefetch E2 ──|──── Compute E2 ────|
                                          ↕ overlap
Expert 3:                                 |── HtoD Prefetch E3 ──|...

关键前提: expert batch size > 2^11 tokens/expert
→ GPU 计算时间 ≥ HtoD copy 时间 → 完全隐藏传输延迟
```

- **Double Buffer for Expert Weights**：两个 expert buffer（`S_Expert` 和 `S_Expert2`）交替使用——当前 expert 用 buffer A 计算时，HtoD 预取下一个 expert 到 buffer B。
- **Buffer Size Trade-off**：更大的 expert buffer 可容纳更多预取权重（减少 on-demand wait），但挤压 attention batch size 和 KV-cache buffer。

### 4.2 DiT：Denoising Step Memory Footprint

> **笔记证据较弱**：笔记中 DiT 相关的硬件控制模块/访存架构信息有限。以下为可推断内容。

DiT（Diffusion Transformer）多步 denoising 的访存特征：
- **迭代性**：DiT 需要多次 denoising step（通常 20-50 步），每一步的前向推理产生大量中间激活（与 U-Net 相比，DiT 的 Transformer backbone 产生规则的矩阵乘法模式）。
- **Memory Footprint**：多步 denoising 的中间 latent 和 attention KV 需保留在 HBM 中。笔记 `TetriServe` 提到 denoising step 的 memory footprint 控制和 intermediate latent reuse 优化。
- **Spatial Parallelism 数据交换**：DiT 的 spatial parallelism 在多个 patch 间需要数据交换——笔记 `MixFusion` 提到 patch-level parallel serving 需要高效的 inter-SM 通信。

## 6 实现 (辅助说明)

笔记中显示控制模块与访存架构的实现分布在多个层次：

- **硬件层（闭源）**：Warp Scheduler、Thread Block Scheduler、Dispatch Unit、Scoreboard、TMA 均为 NVIDIA GPU 固件（GSP firmware）的闭源实现，用户不可直接编程。μShare 通过修改 kernel launch 参数间接影响调度行为，是在真实 GPU 上唯一可行的非侵入式方案。
- **CUDA 编程层**：cp.async（`<cuda/pipeline>`）、TMA（`cuda::memcpy_async` / `cp.async.bulk` PTX）、mbarrier（`<cuda/barrier>`）、warp-group specialization（`cooperative_groups::tiled_partition`）通过 CUDA API 暴露。
- **编译框架层**：CUTLASS 3.x（`sm90_mma_tma_gmma_rs_warpspecialized` 模板）、ThunderKittens（LCSF 模板）、Triton（Gluon API for TMA）、TileLang（T.Pipelined 调度原语）将硬件特性封装为高层抽象。

## 8 是什么？(辅助说明)

**笔记证据**: `knowledge_notes/硬件知识笔记/Streaming Multiprocessor (SM).md` (score: 787)、`knowledge_notes/硬件知识笔记/Warp _ Warp Scheduler.md` (score: 2796)

GPU 硬件控制模块和访存架构是支撑多算子并发的物理基础：

- **控制模块**（Warp Scheduler、Thread Block Scheduler、Dispatch Unit、Scoreboard、TMA）构成从 kernel launch → block placement → warp issue → instruction execute 的完整调度链条。多算子并发的本质是：不同算子的 warps 在同一 SM 上通过 warp scheduler 的零成本切换获得交错执行机会，而 TMA/cp.async 等异步硬件将数据搬运从计算中解耦，使计算和数据供给在时间上完全重叠。
- **访存架构**（HBM→L2→L1/SMEM→RF）是一个经典的容量-带宽权衡金字塔。多算子并发的数据供给策略是：将每个算子的 working set 通过 tiling 适配到对应存储层级（SMEM 适合 tile 级复用，RF 适合指令级复用），通过双缓冲/多级 pipeline 隐藏跨层级数据传输延迟。
- **关键瓶颈**：Memory Wall（HBM 带宽增速远低于计算增速）意味着多算子并发的效益上限由数据供给能力决定——fusion 减少 HBM 往返是解决这一瓶颈的核心思路。
