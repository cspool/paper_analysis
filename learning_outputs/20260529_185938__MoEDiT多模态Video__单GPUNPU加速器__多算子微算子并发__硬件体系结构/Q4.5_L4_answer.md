## 一、方法细节：Kernel 调度框架的数据流、架构与运行时调度

### 方法1: Triton — Block-Level Programming + Automatic Tiling + Triton-IR → PTX → SASS

**笔记证据**: `knowledge_notes/编译知识笔记/Triton MPP...md` (score: 2392.9), `paper_secs/.../Tilus.../2-Background.md` (score: 1154.7), `paper_secs/.../KernelEvolve...md` (score: 6413.6)

**核心理念**: Triton 将 GPU 编程从 thread 级提升到 block 级，程序员定义 thread block 行为，Triton compiler 自动处理 tiling、shared memory allocation 和 thread 映射。在 Triton 中，tile 替代标量作为基本数据类型。

**编译流水线 (硬件体系结构侧重)**:

```
Triton DSL (Python)
    │  @triton.jit + block-level program
    ▼
Triton-IR (MLIR-based, triton-gpu dialect)
    │  tile-level optimization, automatic tiling, shared memory allocation
    ▼
MLIR → LLVM-IR → PTX (Parallel Thread Execution, NVIDIA虚拟ISA)
    │  register allocation, instruction scheduling, warp-level mapping
    ▼
PTX → SASS (native GPU microcode, 由 GPU driver JIT 编译)
    │  final instruction encoding, dual-issue scheduling, scoreboarding
    ▼
NVIDIA GPU SM (Streaming Multiprocessor)
    warp scheduler → dispatch unit → CUDA Cores / Tensor Cores / SFUs
```

**注解**:
- **Triton-IR 抽象层次**: 介于高层算子描述和低层 PTX 之间。关键的 triton-gpu dialect 包含 tile-level operations（如 `tt.load`, `tt.dot`, `tt.store`），compiler 自动将 tile 操作展开为 thread-level PTX 指令。
- **Automatic Tiling 原理**: Triton compiler 根据问题 shape 和 GPU 参数（shared memory 大小、warp 数量）自动确定 tile size。用户仅需指定 `BLOCK_SIZE` 等 hint，剩余由 auto-tuner 搜索最优配置。
- **硬件并发抽象**: Triton 将 warp scheduler 抽象为 block-level SPMD——程序员不直接管理 warp/wavefront，但可通过 `tl.dot` (MMA) 利用 Tensor Core。对于 warp-specialization（如 FlashAttention-3 的 producer-consumer warp），Triton 原生不支持，需 hand-coded CUDA。
- **局限**: 笔记显示 Triton 不暴露 GPU memory hierarchy（register file vs shared memory 的显式控制），也不支持非 2 的幂 bit-width 数据类型（需手动 unpack），在低精度 kernel 中 layout conversion 通过 shared memory 完成，导致额外开销。

### 方法2: CUTLASS — Tile Iterator + Warp Tile + MMA Abstraction

**笔记证据**: `experiment_notes/kernel实验笔记/FlashAttention-3...md` (score: 688.1), `paper_secs/.../FlashMoE.../1-Introduction.md` (score: 1133.3), `paper_secs/.../KernelEvolve...md` (score: 6413.6)

**CUTLASS v3 核心抽象与数据**:

CUTLASS 将 GEMM/Conv/Attention 分解为分层 tile：

```
Global Memory (HBM)
    │  TMA (Tensor Memory Accelerator) async copy
    ▼
Shared Memory (SMEM, 228KB/SM on H100)
    │  ldmatrix / cp.async → registers
    ▼
Register File (per-thread, 256 registers/thread max on H100)
    │  WGMMA (Warp Group Matrix Multiply-Accumulate)
    ▼
Tensor Core (MMA unit, FP16: 989 TFLOPs, FP8: 1978 TFLOPs on H100)
```

**Kernel 伪代码 — CUTLASS v3 Persistent Kernel (FlashAttention-3 风格, H100)**:

```
// 输入: Q[batch, heads, seq, dim], K/V 同上, H100 SMs=132
// Grid: 132 threadblocks (persistent, 每 SM 一个)
// 每个 CTA: 3 warpgroups (producer=1 warp, consumer1=2 warps, consumer2=2 warps)

def flash_attn_v3_persistent_kernel(Q_hbm, K_hbm, V_hbm, O_hbm):
    sm_id = blockIdx.x                            // persistent: 1 CTA per SM
    smem_Q = AllocateShared([Br, 128], dtype=bf16) // Q tile buffer
    smem_K = AllocateShared([128, 128], dtype=bf16) // K tile buffer (circular, 2-stage)
    smem_V = AllocateShared([128, 128], dtype=bf16) // V tile buffer (circular)
    
    for tile_i in range(sm_id, total_Q_tiles, gridDim.x):  // grid-stride loop
        // === Producer Warp (1 warp, setmaxnreg=32 registers) ===
        TMA_Load(smem_Q, Q_hbm[tile_i])           // async Q load
        cp_async_commit_group()
        
        O_reg = zeros([Br, 128])                  // FP32 accumulator in registers
        l_reg = zeros([Br])                        // softmax denominator
        m_reg = neg_inf([Br])                      // softmax max
        
        for tile_j in range(0, num_KV_tiles):
            // Producer: async prefetch K_j, V_j
            TMA_Load(smem_K, K_hbm[tile_j])
            TMA_Load(smem_V, V_hbm[tile_j])
            cp_async_commit_group()
            cp_async_wait_group(1)                 // wait for prev stage
            
            // === Consumer Warpgroup (4 warps, setmaxnreg=232) ===
            // Stage 1: QK^T via WGMMA (asynchronously launched)
            S_tile = WGMMA_SS(smem_Q, smem_K)      // SS: both operands from SMEM
            // S_tile shape: [Br, 128], dtype: FP32
            
            // Stage 2: 与 Stage 1 重叠 — softmax(上一迭代的 S)
            if tile_j > 0:
                m_new = rowmax(S_prev)
                l_corr = exp(m_prev - m_new)       // 校正因子
                l_new = l_corr * l_prev + rowsum(exp(S_prev - m_new))
                O_reg = l_corr * O_reg              // 重新缩放旧输出
                
                P_tile = exp(S_prev - m_new)        // softmax probabilities
                O_reg += WGMMA_RS(P_tile, smem_V)   // RS: P from register, V from SMEM
            
            // 旋转: 当前 S 成为下一轮的 S_prev
            S_prev, m_prev, l_prev = S_tile, m_new, l_new
            cp_async_wait_group(0)                 // wait for current stage done
        
        // Epilogue: 最终 rescale + TMA store
        O_reg = diag(1.0 / l_new) * O_reg
        TMA_Store(O_hbm[tile_i], O_reg)
```

**指令 Pipeline 时序图 (单 CTA, 2-stage GEMM-softmax Pipelining)**:

```
Time →   T0-T3        T4-T7        T8-T11       T12-T15      T16-T19
─────────┬────────────┬────────────┬────────────┬────────────┬────────────
Producer │TMA Q load  │TMA K0,V0   │TMA K1,V1   │TMA K2,V2   │TMA K3,V3
(Warp 0) │commit      │commit      │commit      │commit      │commit
─────────┼────────────┼────────────┼────────────┼────────────┼────────────
Consumer │            │WGMMA QK^T0 │WGMMA QK^T1 │WGMMA QK^T2 │WGMMA QK^T3
WarpGrp1 │  idle      │(async)     │(async)     │(async)     │(async)
(4 warps)│            │            │            │            │
─────────┼────────────┼────────────┼────────────┼────────────┼────────────
Consumer │            │softmax(S0) │softmax(S1) │softmax(S2) │softmax(S3)
WarpGrp1 │  idle      │+ WGMMA PV0 │+ WGMMA PV1 │+ WGMMA PV2 │+ WGMMA PV3
(cont.)  │            │            │            │            │
─────────┴────────────┴────────────┴────────────┴────────────┴────────────
Tensor Core 利用率: ~85% (WGMMA 持续发射，softmax 在 warp 级重叠)
HBM 带宽利用率: ~80% (TMA 持续 prefetch，circular buffer 2-stage)
```

**注解**:
- **WGMMA (Warp Group MMA)**: Hopper 架构引入，允许单个 warp group（4 warps）异步发射矩阵乘法。SS 前缀=两个操作数都从 SMEM 读；RS 前缀=第一个操作数从 register 读。WGMMA 发射后不 block，允许与 softmax 等 ALU 操作重叠。
- **setmaxnreg**: Hopper 的寄存器重分配指令。Producer warp 释放寄存器（仅需 32 个，用于 TMA 地址计算），释放的寄存器分配给 consumer warpgroup（232 个），使 WGMMA 有充足寄存器缓冲。
- **TMA (Tensor Memory Accelerator)**: Hopper 的新硬件单元。从 HBM 到 SMEM 的异步 DMA，支持多维 tile 寻址（无需手动计算 offset），可减少 address generation 和 loop overhead。
- **Occupancy**: Persistent kernel（132 CTA = 132 SMs），每 CTA 5 warps。H100 每 SM 最多 64 warps，occupancy = 5/64 ≈ 7.8%，但这是**有意为之**——低 occupancy 换取更多 registers/CTA（232 registers × 128 threads），最大化单 thread 计算密度。笔记显示 FlashAttention-3 在 H100 上达到 840 TFLOPs/s（85% 理论峰值）。

### 方法3: CUDA Graph — Kernel Graph DAG 并发启动与依赖管理

**笔记证据**: `paper_secs/.../Mirage.../span-idpage-2-0span2.2-Kernel-Fusion.md` (score: 3456.3), `paper_secs/.../ACS.../E.-Comparison-with-Persistent-Thread...md` (score: 3106.8), `paper_secs/.../FlashMoE.../1-Introduction.md` (score: 1133.3)

**核心机制**:

CUDA Graph 将一系列 kernel launch 及其依赖关系预录制为 GPU-executable graph，消除 CPU-side kernel launch overhead。

```
传统 Kernel Launch (per-operator):
CPU: launch(K1) → wait → launch(K2) → wait → launch(K3) → ...
GPU:    [K1 exec] → barrier → [K2 exec] → barrier → [K3 exec] → ...

CUDA Graph (kernel graph):
CPU: graph.launch()  ← 单次调用
GPU: [K1] ──→ [K2] ──→ [K3]         ← 静态 DAG, 无 CPU-GPU round-trip
      \                /
       └──→ [K4] ────┘                 ← 支持 fork/join 并发
```

**与 MPK tGraph 的对比 (从硬件体系结构角度)**:

| 维度 | CUDA Graph | MPK tGraph |
|------|-----------|------------|
| 依赖粒度 | Kernel 级 | SM 级 (task) |
| 同步机制 | Stream semantics | Event-driven (device memory semaphore) |
| 并发粒度 | 多 kernel 同发（kernel barrier 间不可重叠） | 跨算子 computation/communication 在 SM 间重叠 |
| 动态性 | 静态捕获，batch size 变化需重建 | JIT task launch 支持动态 work distribution |
| Launch overhead | 降为 ∼5-10μs (vs ∼50μs per-kernel) | 仅 1 次 kernel launch（∼1μs） |
| MoE 支持 | 不兼容 dynamic routing（CUDA Graph 无法表达 conditional dispatch） | 原生支持（hybrid workload balancer + runtime metadata） |

**注解**:
- 笔记显示，Megatron-LM + DeepEP 的 MoE 实现每 forward pass 发射 432 个 kernel，FlashMoE 通过 persistent kernel 降至 1 个。CUDA Graph 可减少但无法消除此 overhead，且不兼容 MoE 的动态路由模式。
- ACS 论文指出 CUDA Graph 对 input-dependent 计算图不适用——构建 graph 的延迟与执行时间相当或更长。

### 方法4: CUDA Stream — 多 Stream 异步并发

**笔记证据**: `paper_secs/.../Demystifying.../2.-CUDA-PROGRAMMING-MODEL.md` (score: 2817.8), `paper_secs/.../HuntKTm.../HuntKTm...md` (score: 2432.5)

**并发模型**:

```
CPU Process
  ├── Stream 0 (default): [K1_GEMM] → [K2_Activation] → [K3_Norm]
  ├── Stream 1:          [K4_Attention_Q] → [K5_Attention_K]
  └── Stream 2:          [K6_D2H_copy] → (overlap with compute)

GPU SM 资源在 stream 间竞争:
  - SM partitioning: Stream 0 占 80 SMs, Stream 1 占 28 SMs
  - 或 spatial sharing: 所有 stream 共享全部 SM, warp scheduler round-robin
  - 或 temporal sharing: MPS (Multi-Process Service) / MIG (Multi-Instance GPU) 时间片
```

**Kernel 伪代码 — 多 Stream MoE Expert FFN 并发**:

```
// 将 MoE 的不同 expert 分配到不同 stream 实现并发
cudaStream_t streams[NUM_EXPERTS];

for expert_id in range(NUM_EXPERTS):
    cudaStreamCreate(&streams[expert_id])

// 异步启动各个 expert FFN
for expert_id, tokens in expert_to_tokens.items():
    // 每个 expert 在独立 stream 中执行
    dim3 grid = calc_grid(tokens.shape, EXPERT_TILE_SIZE)
    cudaLaunchKernel(expert_ffn_kernel, grid, BLOCK_SIZE,
                     0, streams[expert_id],
                     tokens, expert_weights[expert_id], output_buffer)
    // 无需等待其他 expert — 全部异步

// 所有 expert 完成后 barrier
for expert_id in range(NUM_EXPERTS):
    cudaStreamSynchronize(streams[expert_id])
```

**注解**:
- **硬件并发限制**: H100 最多支持 128 个并发 stream，但实际并发 kernel 数受限于 SM 资源（registers、shared memory）。如果每个 kernel 需要的资源超过 SM 剩余容量，后续 kernel 会排队等待。
- **Wave Quantization 效应**（笔记 `knowledge_notes/kernel知识笔记/Wave Quantization...md` score: 2047.6）: 当每个 expert 的 token 数不均时，FFN kernel 的 thread block 数可能远少于 SM 数，导致严重 SM idle。多 stream 并发不能解决此问题——需 persistent kernel + dynamic work stealing。
- **NVIDIA TX2 研究**: 笔记显示 GPU thread block scheduler 在并发 kernel 间采用 round-robin 分配 SM，可能导致 compute-bound 和 memory-bound kernel 的资源竞争。

### 方法5: FlashMoE — Actor-Based Persistent Kernel for MoE

**笔记证据**: `paper_secs/.../FlashMoE.../1-Introduction.md` (score: 1133.3)

**架构数据流 (Actor Model)**:

```
┌───────────────────────────────────────────────────────┐
│               FlashMoE Persistent Kernel              │
│                                                       │
│  ┌─────────────┐   task descriptors    ┌───────────┐ │
│  │ Subscriber  │──────────────────────→│ Scheduler │ │
│  │ (1 warp)    │  decode remote tiles  │ (1 warp)  │ │
│  │             │←──────────────────────│           │ │
│  │ NVSHMEM DMA │  notify task ready    │ dispatch  │ │
│  └─────────────┘                       │ tasks ↓   │ │
│                                        └───────────┘ │
│                                        ┌───────────┐ │
│  GPU 0                                 │Processor 0│ │
│  SM 0                                  │Processor 1│ │
│  SM 1           ┌────shared mem────┐   │Processor 2│ │
│  SM 2           │ Sub↔Sched queue  │   │  ...      │ │
│  ...            └──────────────────┘   │Processor N│ │
│  SM N-1                                └───────────┘ │
│                  (N-1 SMs 执行 FFN/Combine GEMM)      │
└───────────────────────────────────────────────────────┘
         ↑ NVSHMEM one-sided DMA (UVA) ↑
┌───────────────────────────────────────────────────────┐
│               GPU 1: 相同 Actor 架构                    │
└───────────────────────────────────────────────────────┘
```

**Kernel 伪代码 (FlashMoE 分布式 MoE Fused Kernel)**:

```
Input: A ∈ R^{S×H} (input tokens), X ∈ R^{E×H×D} (expert weights)
       N = SM count per GPU

def FlashMoE_FusedKernel(A, X, N):
    T_phi, G_phi = FusedGate(A)                    // gate + top-k + routing table
    
    if blockIdx < N - 1:                           // Processor blocks (N-1 SMs)
        Dispatch(T_phi, A)                         // 打包 tokens 到对称 tensor layout
        processor::start()                          // 进入 work-stealing loop:
        while True:                                 //   dequeue task descriptor
            t = task_queue.dequeue()                //   t = (metadata, op, activation)
            if t is None: break
            F_t(A_tile, B_weight, C, D)            //   C = φ(A ⋆_t B + D)
            notify_trigger_event(t.event)            //   通知 scheduler
    
    else:                                            // OS block (1 SM)
        if warpID == 0:
            scheduler::start()                       // event loop:
            while True:                              //   poll events → dispatch ready tasks
                e = event_queue.poll()               //   → enqueue to processor task queues
                if e.activated:
                    for t in e.task_range:
                        processor[t % (N-1)].enqueue(t)
        elif warpID <= 3:
            subscriber::start(T_phi, G_phi, O, X)   // DMA receive loop:
            while True:                              //   poll NVSHMEM signals
                pkt = NVSHMEM_wait_signal()          //   decode remote tile packets
                task_desc = decode(pkt)              //   → enqueue to scheduler event queue
                scheduler.notify(task_desc)
```

**注解**:
- **Tile 维度选择**: FlashMoE 选择 (128, 64) tile 尺寸。增大 tile width→寄存器压力骤升→spill to local memory；增大 tile height→per-thread 工作量增加；增大 block 线程数→减少并发 CTA→降低 occupancy。笔记显示此平衡点是「经过 careful parameter sweeps」得出的。
- **对称 Tensor Layout**: 通过引入 temporal buffering（overprovision 2×r 倍内存，r=communication rounds），实现 write-write conflict-free 的 one-sided DMA，消除同步开销。内存 overhead ≤ 2%。
- **实验结果**: FlashMoE 达到 93.17% GPU SM 利用率，vs DeepEP 的 13.55%（6.8×），vs Megatron-TE 的 59.11%（4×）。即使 FlashMoE 使用 FP32（baseline 用 FP16），仍获 6× latency speedup。

**tGraph 编译流水线**:

```
PyTorch Model (torch.compile(backend=MPK))
    │
    ▼
Computation Graph (DAG of tensor operators)
    │
    ├── Operator Decomposition: 每个 operator 按输出维度 tiling → 生成 SM 级 tasks
    ├── Dependency Analysis: per-task-pair overlap check → 插入 fine-grained events
    ├── Event Fusion: successor-set + predecessor-set fusion → 消除冗余同步
    ├── tGraph Normalization: fan-in/fan-out ≤ 1 (引入空 dummy tasks)
    ├── tGraph Linearization: BFS, 确保同一 event 的 tasks 连续存储
    └── Task Code Generation: Mirage superoptimizer → 优化 CUDA kernel
    │
    ▼
Mega-Kernel Callable (单个 PyTorch function)
    │
    ▼
GPU In-Kernel Runtime (event-driven, worker/scheduler 分离)
```

**Kernel 伪代码 — MPK Worker Persistent Loop**:

```
// 每个 Worker SM 执行的 persistent loop
def MPK_Worker_Loop(task_array, event_array):
    sm_id = blockIdx.x                              // worker SM index
    task_queue = circular_buffer_init()              // GPU device memory, atomicAdd enqueue
    
    while True:
        t = task_queue.dequeue(sm_id)               // atomicAdd 获取下一个 task 索引
        if t is None: break
        
        // === 执行 task t ===
        config = task_array[t]                      // 352 bytes: event indices, tensor ptrs
        
        // Phase 1: Pre-loading (cross-task pipelining)
        if config.has_prefetch:
            input_tile = TMA_Load_prefetch(config.src_ptr, config.tile_shape)
        
        // Phase 2: 执行计算或通信
        if config.is_compute:
            output = mirage_generated_kernel(input_tile, config.params)
        elif config.is_communicate:
            NVSHMEM_put_signal(output_tile, config.remote_pe, config.remote_addr)
        
        // Phase 3: 通知触发事件
        ev = event_array[config.trigger_event]
        count = atomicAdd(&ev.trigger_count, 1)     // 原子计数
        if count + 1 == ev.required_count:
            ev.activated = true                       // 所有生产者完成→事件激活
            scheduler_notify(ev)                      // 通知 scheduler
```

**注解 (硬件体系结构)**:
- **Decentralized Scheduling**: Scheduler 仅用 local state 调度，无全局协调。Task 和 event 队列为 GPU device memory 中的 circular buffer，enqueue/dequeue 仅用 `atomicAdd`。笔记显示「per-task overhead 极小」。
- **Cross-Task Pipelining**: MPK 将每个 task 拆为 pre-load 和 compute 两阶段。当前 task compute 期间即通过 TMA 预取下一 task 的输入 tile（利用 paged shared-memory abstraction）。Ablation 显示：Qwen3-8B final linear layer on B200 上 1.2-1.3× speedup。
- **Compute-Communication Overlap**: MPK 在 task 对级别分析依赖（非 operator 级别）。例如 MatMul→AllReduce：每个 AllReduce task 仅依赖一个对应 MatMul task 的输出 tile，使 compute 和 communication 在不同 SM 组上并发。Ablation 显示 1.1× speedup。
- **端到端性能**: Qwen3-8B on A100, 单 batch decode, MPK 12.5ms/token vs vLLM 14.5ms。理论下限 ~10ms（模型参数加载时间/1.6TB/s HBM 带宽），MPK 仅比下限高 ~25%。

### 方法7: NPU 生态 — CANN/TBE/TIK + Ascend Da Vinci 架构

┌─────────────────────────────────────────────────────────┐
│                 Ascend NPU (Atlas 800I A2)               │

│  │  AI Core      │  │  AI Vector   │  │  Scalar Unit │  │
│  │  (Cube Unit)  │  │  (Vector)    │  │              │  │

│         │                 │                 │          │

│            ┌──────▼──────┐                              │

│            │  Buffer     │                              │

**注解**:
- **Cube Unit 约束**: 16×16×16 MAC 阵列决定矩阵乘 tile 尺寸必须是 16 的倍数。与 GPU Tensor Core 的 16×16×16 MMA tile 相同形状，但 Cube Unit 不通过 warp 调度——由专用的指令队列 (MTE) 驱动。
- **Cube/Vector 并发**: 三类单元（Scalar/Vector/Cube）有独立指令队列，支持同时取指、并行执行。EPD-Serve 利用此特性实现 operator-level 空间复用——MatMul 在 Cube Unit 执行时，Vector Unit 同时做 AllReduce 或 LayerNorm。
- **CANN 软件栈**: 对标 CUDA——Ascend C (SPMD 编程范式)、Graph Engine (GE)、Ascend Operator Library。开发者通过 PyTorch Ascend Adapter 间接使用，不直接写 Ascend C。
- **笔记未覆盖**: CANN/TBE/TIK 的具体 kernel 编程 API、tile 配置方法、Ascend 的 stream/model 并发细节在 vault 笔记中缺失。以下内容为可推断和 Web 补充。

**可推断**: TBE (Tensor Boost Engine) 提供 DSL 描述算子计算逻辑，TIK (Tensor Iterator Kernel) 提供更低层的 tile 级编程接口。与 Triton 类似，TBE 自动处理 tiling 和 buffer 管理；与 CUTLASS 类似，TIK 允许显式控制数据搬运和计算流水线。

## 四、是什么？ (辅助说明)

### 各框架的核心定位

1. **Triton** (OpenAI → 开源社区): 将 GPU kernel 编程复杂度从 thread 级降低到 block 级。程序员写 block-level Python，编译器自动生成高效 PTX。适用场景：快速原型开发、element-wise/reduction/GEMM kernel、非标准数据类型的探索。不适合需要 warp-specialization 的场景。

2. **CUTLASS** (NVIDIA): 基于 C++ template 的 GPU 线性代数库，提供分层 tile 抽象（tile iterator→warp tile→thread tile→MMA instruction），但需要显式管理数据搬运和同步。适用场景：极致优化的 GEMM/Conv/Attention kernel，特别是需要利用 Hopper TMA/WGMMA/FP8 新特性的场景。

3. **CUDA Graph** (NVIDIA Runtime): 将 kernel launch DAG 预录制以减少 CPU-GPU 同步开销。适用场景：静态计算图 (batch size/shape 固定)、latency-sensitive 推理。不适用：动态 shape/batch、MoE conditional routing。

4. **CANN/TBE/TIK** (华为): Ascend NPU 的异构计算架构。TBE 为算子级 DSL，自动 tiling；TIK 为 tile 级编程接口，类似 CUTLASS。依托 Da Vinci 架构的三类计算单元实现算子并发。

5. **XLA** (Google): 为 TPU 设计的 JIT 编译器。从 JAX/TensorFlow 的 HLO (High-Level Operations) IR 出发，经 target-dependent lowering 生成 TPU/GPU/CPU 指令。TPU 的 128×128/128×256 MXU 约束决定其 tile 尺寸。

6. **TVM/MLIR** (Apache/LLVM): 跨硬件平台的编译框架。TVM 的 AutoScheduler/MetaSchedule 通过 cost model 搜索最优 tile 配置；MLIR 的 multi-dialect 设计允许同一 IR 表达不同硬件的并发特性。

7. **MPK/FlashMoE (Mega-Kernel)**: 将整个模型编译为单个 persistent kernel，消除 kernel launch overhead、pipeline bubble 和 CPU-side scheduling 延迟。代表了从「kernel 级」到「SM 级」的抽象层次下沉。
