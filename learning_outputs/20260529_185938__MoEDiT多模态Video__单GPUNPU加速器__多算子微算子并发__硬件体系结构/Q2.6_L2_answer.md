### 1.2 关键评估指标体系（硬件体系结构侧重）

**笔记证据**: `paper_secs/.../14-PAT...` (score: 700.98), `experiment_notes/.../Shift Parallelism...` (score: 5603.31)

#### 核心延迟指标

| 指标 | 全称 | 定义 | 硬件相关性 | 典型数值范围（笔记证据） |
|------|------|------|-----------|----------------------|
| **TTFT** | Time-To-First-Token | 请求发出到第一个token生成的时间 | 受prefill阶段compute/memory带宽限制，HBM带宽是关键瓶颈 | PAT A100: Qwen3-8B/Llama-3-8B（笔记未给出绝对值，仅相对加速）；Shift Parallelism H200 Llama-70B-FP8: median TTFT=148ms |
| **TPOT** | Time-Per-Output-Token | decode阶段每token平均生成时间 | 受memory bandwidth限制（decode为memory-bound），HBM→SM数据搬运效率决定 | PAT A100: 笔记未给出绝对值；Shift Parallelism H200: median TPOT=51ms |
| **E2E Latency** | End-to-End Latency | 完整请求的端到端延迟 | 受prefill+decode综合影响，调度overhead为加性因子 | PAT A100: vLLM集成下完整请求延迟；MegaScale-Infer: 含prefill的end-to-end throughput |

**注解**: TTFT/TPOT在GPU上受HBM带宽和SM占用率的联合约束。单请求场景下，TTFT主要受prefill阶段的compute-bound特性影响（大batch prefill需要高Tensor Core利用率）；TPOT主要受decode阶段的memory-bound特性影响（每次仅生成1 token，KV-cache加载占主导）。不同硬件平台的HBM带宽差异（H100: 3.35 TB/s vs A100: 2.0 TB/s vs H200: 4.8 TB/s）直接影响TPOT。NPU/TPU的对应指标需要根据其片上存储架构重新定义。

#### 吞吐量指标

| 指标 | 定义 | 硬件相关性 | 典型数值（笔记证据） |
|------|------|-----------|-------------------|
| **Throughput (tokens/s)** | 单位时间处理的token总数 | 反映硬件计算/带宽资源的整体利用效率 | Shift Parallelism H200: peak 69,147 tok/s (throughput-opt) / 51,162 tok/s (latency-opt) |
| **Requests/sec** | 单位时间完成请求数 | 高并发下与batch efficiency正相关 | Dense Training: DS-MoE-6B A100 2.00 req/s, H100 2.30 req/s |
| **TPS (Total tokens/s)** | input+output总token处理速率 | 综合prefill+decode效率 | Dense Training: DS-MoE-6B A100 3992.8 TPS, H100 4603.9 TPS |
| **Per-GPU decode throughput** | 单GPU的decode阶段吞吐 | 直接反映per-GPU硬件效率 | MegaScale-Infer: Mixtral 8x22B不同配置下per-GPU decode throughput |

#### 调度效率指标

| 指标 | 定义 | 测量方法 | 典型数值（笔记证据） |
|------|------|----------|-------------------|
| **Scheduling Overhead (μs/iteration)** | 调度器CPU端决策耗时 | CPU端计时，与GPU执行overlap分析 | PAT §8.7: overhead analysis（pack scheduler overhead, merge overhead）；FastTree: CPU greedy search <1ms（被decoding循环摊销） |
| **Concurrent Operator Utilization** | 微算子并发执行的实际利用率 | 对比sequential vs concurrent execution | 笔记未提供明确的微算子并发利用率数值。Shift Parallelism通过SP/TP切换实现不同并发度的latency-throughput trade-off |
| **Speedup vs Sequential** | 并发调度相比串行执行的加速比 | 固定硬件下的相对加速 | PAT: attention kernel加速（A100上不同batch配置，笔记未给出全局加速比）；Faster MoE: expert skipping up to 1.32× (na=2 vs 6) |

#### 硬件利用率指标（侧重核心）

| 指标 | 定义 | 硬件平台 | 典型数值（笔记证据） |
|------|------|----------|-------------------|
| **SM Occupancy** | GPU SM上活跃warp占最大warp的比例 | NVIDIA GPU (Nsight Compute) | μShare A40: average low-level hardware utilization 15.10% (vs INFless 10.90%/Orion 9.37%)；μShare提升38.53%-61.15% |
| **HBM Bandwidth Utilization** | 实际HBM带宽占用占理论峰值的比例 | GPU HBM / NPU HBM | PAT论文未给出绝对值，但通过kernel latency间接反映；Shift Parallelism H200理论带宽4.8 TB/s |
| **MAC Utilization** | 计算单元实际利用率（NPU脉动阵列/TPU MXU） | NPU/TPU | 笔记未提供NPU MAC利用率的具体数值 |
| **FP8 Tensor Core Utilization** | H100 FP8 Tensor Core利用率 | H100/H200/H800 | FlashAttention-T: 利用repurposed tensor MMA scaling提升Tensor Core利用率；Shift Parallelism: H200 FP8 tensor core峰值1,979 TFLOPS |
| **tokens/J (frames/J)** | 能效——每焦耳能量处理的token（或帧）数 | 全平台 | Hardwired Neuron LPU: HNLPU 5nm 308.39W/chip vs H100 TensorRT-LLM vs Cerebras WSE-3对比；H2-LLM: energy efficiency analysis |

**注解**: 硬件利用率指标是连接Serving调度策略与硬件体系结构的核心桥梁。SM occupancy直接反映调度器能否充分填充GPU计算单元——单请求场景下，batch size=1时的SM occupancy通常极低（<5%），因此调度策略需要通过micro-batching、operator fusion、concurrent kernel execution等手段提升硬件利用率。HBM bandwidth utilization决定了memory-bound decode阶段的天花板——即使调度完美，decode吞吐也无法超过HBM带宽/（单token KV-cache大小×模型参数加载量）。不同硬件平台的利用率测量工具不同：GPU使用Nsight Compute/Systems，NPU使用CANN Profiling工具链，TPU使用XLA profiling/TensorBoard。

### 2.3 MegaScale-Infer 异构集群实验（硬件体系结构亮点）

**笔记证据**: `experiment_notes/.../MegaScale-Infer...` (score: 33.94)

MegaScale-Infer的实验环境是目前笔记中**最具硬件体系结构深度**的跨平台对比：

```
同构集群（Ampere）:
  8节点 × 8×A800 (80GB), 128 CPUs, 2 TB host memory/node
  8×200 Gbps InfiniBand NICs, 节点内 400 GB/s NVLink

异构集群（H20 + L40S）:
  H20: 96 GB HBM, 4096 GB/s bandwidth, 148 TFLOPS, 900 GB/s NVLink, 4×400 Gbps NICs
  L40S: 48 GB, 864 GB/s bandwidth, 362 TFLOPS, PCIe intra-node, 2×400 Gbps NICs

异构设计原理（硬件体系结构视角）:
  - Attention node → H20（高per-cost内存带宽/容量，适合memory-intensive attention计算 + KV-cache存储）
  - Expert node → L40S（高per-cost计算能力362 TFLOPS，适合compute-intensive FFN/expert计算）
  - 通信: M2N通信库 (~4900行C/C++ + ~5000行Python) 替代NCCL进行token dispatch

实验指标（硬件相关）:
  - per-GPU decoding throughput (tokens/s/GPU)
  - time between tokens (TBT)
  - end-to-end throughput (含prefill)
  - per-cost throughput（成本归一化吞吐）
  - per-unit-power throughput（功耗归一化吞吐）
```

**注解**: MegaScale-Infer的异构集群设计体现了硬件体系结构驱动的调度策略——根据不同类型GPU的硬件特性（H20内存带宽高但计算弱，L40S计算强但内存带宽低）将模型的不同模块映射到最匹配的硬件上。这种"硬件感知的模块分解+异构映射"范式是单请求Serving调度从软件层面向硬件层面深入的关键方向。attention与FFN的分离部署也暗合了GPU内部SM资源分配的思路（某些SM专注memory-bound的attention，另一些SM专注compute-bound的FFN）。

## 三、硬件利用率与能效实验（主内容）

### 3.1 GPU SM利用率与多模型Co-location实验

**笔记证据**: `experiment_notes/.../μShare...` (score: 2141.18)

μShare在A40/A800上的实验直接测量了Serving场景下的硬件利用率：

```
实验配置:
  硬件: 8×A40 (84 SMs, 1536 threads/SM, 102,400B shared memory/SM) + A800 (108 SMs)
  负载: 10模型co-located (Llama2-7b/GPT-2/Bert/ResNet50/MobileNet/ViT等)
  每模型4 replica, 共40 replica 分布8 GPU
  Trace: Azure INFless production trace

关键硬件利用率指标:
  μShare: average low-level hardware utilization 15.10%
  INFless (ASPLOS'22): 10.90%
  Orion (EuroSys'24): 9.37%
  提升: 38.53%-61.15%

系统吞吐量:
  μShare: 3046 QPS
  INFless: 1722 QPS
  Orion: 1192 QPS
  提升: 26.90%-54.09%

SLO Violation Rate:
  μShare: 3.35% (v7 k=0.05, λ=-0.2: 0.84%)
  INFless: 2.05%
  Orion: 1.12%
```

**注解**: SM利用率仅15.10%这一数据揭示了一个核心问题——即使在10模型co-located场景下，GPU的硬件计算资源大部分时间仍处于空闲状态。这是因为：(1) kernel launch overhead和CPU-GPU同步导致SM间负载不均；(2) memory-bound kernel（如attention decode）的计算单元利用率天然低；(3) 不同kernel的资源需求profile（FP32/FP64/INT32/LDST/SFU/Tensor/Register/SharedMem）不完全互补。μShare通过half-plus blocksize shaping使不同kernel在同一SM内co-locate，本质上是将Serving调度下沉到SM级别——这是硬件体系结构驱动的调度粒度精细化。

### 3.2 Custom ASIC能效对比

**笔记证据**: `experiment_notes/.../Hardwired_Neuron_LPU.md` (score: 36.59)

## 六、不确定性

1. **NPU/TPU实验数据严重缺失**: 预关键词中列出了昇腾910B/310P、TPU v5e/v5p、AMD MI300X、Groq LPU、Cerebras CS-3等多种加速器，但笔记搜索未找到这些平台上的Serving调度实验笔记。主要原因可能是：(a) 华为昇腾的Serving实验多在中文社区/内部报告，未收录到当前vault；(b) Google TPU的Serving实验通常基于XLA编译框架，调度策略在编译期确定，与GPU运行时调度的实验方法论不同；(c) AMD MI300X的ROCm生态中Serving框架（如vLLM ROCm移植版）的实验笔记尚未被系统收录。

2. **DiT/Video模型Serving实验证据缺失**: 预关键词提及"Diffusion benchmark（DiT推理steps）"和"Video-MME"，但搜索到的笔记均为LLM/MoE Serving实验。DiT模型的denoising step调度和Video模型的帧间调度实验在vault中缺乏覆盖。

3. **能效指标(tokens/J)量化不足**: 仅HNLPU笔记提供了硬件级的功耗和面积数据，GPU平台的tokens/J实验数据在现有笔记中基本缺失。GPU功耗测量（nvidia-smi/nvml）在Serving实验中很少被系统报告。

4. **调度开销绝对值缺失**: 多数笔记报告的调度开销为定性描述（如"overhead <1ms"）或相对值（如"被decoding摊销"），缺乏μs级精度的CPU-side scheduling overhead breakdown（DAG拓扑排序耗时、就绪队列管理耗时、资源查询耗时）。

5. **跨框架对比标准不统一**: vLLM、SGLang、TensorRT-LLM的实验使用不同模型、不同GPU、不同batch配置和不同指标，直接对比存在困难。MegaScale-Infer是为数不多提供与vLLM和TensorRT-LLM直接对比的实验。

6. **笔记未明确说明**: 以下预关键词对应的实验内容在搜索结果中未找到任何匹配笔记——Command queue depth对调度延迟的影响、SRAM bandwidth vs HBM bandwidth利用率的定量差异、PCIe transfer overhead的μs级测量、不同硬件平台的调度最佳并发度实验测定。这些指标需要在未来的实验笔记中补充。
