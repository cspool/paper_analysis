### 方法1: vLLM Scheduler —— Python-frontend + C++/CUDA Backend 架构

**笔记证据**: `knowledge_notes/系统知识笔记/vLLM.md` (score: 472.9), `knowledge_notes/系统知识笔记/vLLM Inference Framework (for MoE).md` (score: 390.5), `knowledge_notes/系统知识笔记/vLLM (LLM Serving Framework).md` (score: 433.2)

**方法细节**（L2调度框架执行模拟）：

vLLM的Scheduler是推理引擎核心，实现在 `vllm/core/scheduler.py`（Python）配合 C++/CUDA backend。以下为完整的调度框架执行模拟：

```
═══════════════════════════════════════════════════════════
        vLLM Scheduler 主循环执行模拟（Step 1-7）
═══════════════════════════════════════════════════════════

T=0ms   [Scheduler._schedule() 被调用]
        ├─ Step 1: 从 waiting_queue 取出新请求
        │   new_reqs = self.waiting.popleft()
        │   对每个 req:
        │       required_blocks = ceil(req.prompt_len / BLOCK_SIZE)
        │       if gpu_free_blocks >= required_blocks:
        │           scheduled_reqs.append(req)
        │
        ├─ Step 2: Preemption 检查（内存不足时触发）
        │   if gpu_free_blocks < needed:
        │       victims = select_victims(running, policy)
        │       # policy ∈ {RECOMPUTE, SWAP}
        │       if policy == RECOMPUTE:
        │           for v in victims:
        │               free_blocks(v.block_table)  # 丢弃KV
        │               v.state = WAITING_FOR_RECOMPUTE
        │       elif policy == SWAP:
        │           for v in victims:
        │               copy_blocks_to_cpu(v.block_table)  # 换出
        │               v.state = SWAPPED

T=1ms   ├─ Step 3: Block Table 管理（核心数据结构）
        │   for req in scheduled_reqs:
        │       num_blocks = ceil(req.max_tokens / 16)
        │       req.block_table = []  # 逻辑→物理映射表
        │       for i in range(num_blocks):
        │           phys_blk = gpu_block_allocator.allocate()
        │           req.block_table.append(phys_blk)
        │       # block_table 结构:
        │       # [phys_blk_0, phys_blk_1, ..., phys_blk_N]
        │       # 每个phys_blk存16 tokens × num_layers × num_heads K/V

T=2ms   ├─ Step 4: Prefix Caching 匹配
        │   # 对prompt按block_size切分并hash
        │   prompt_blocks = chunk_tokens(req.prompt_tokens, 16)
        │   for i, blk in enumerate(prompt_blocks):
        │       blk_hash = compute_hash(blk)  # 内容hash
        │       if blk_hash in prefix_cache:
        │           # 命中 → 复用物理block，跳过prefill计算
        │           req.block_table[i] = prefix_cache[blk_hash]
        │           req.num_cached_tokens += 16
        │       else:
        │           prefix_cache[blk_hash] = req.block_table[i]

T=3ms   ├─ Step 5: Continuous Batching（组装running_batch）
        │   running_batch = []
        │   # Prefill请求 + Decode请求混合
        │   for req in (new_prefill_reqs + running_decode_reqs):
        │       running_batch.append({
        │           'req_id': req.id,
        │           'block_table': req.block_table,
        │           'context_len': req.num_computed_tokens,
        │           'is_prefill': req.is_prefill_stage
        │       })

T=4ms   ├─ Step 6: Model Runner 执行
        │   # 两条硬件执行路径:
        │   if all(r.is_decode for r in running_batch):
        │       # 纯decode batch → CUDA Graph 快速路径
        │       cudaGraphLaunch(decode_graph_exec, compute_stream)
        │       # 单次launch，GPU自主执行所有kernel
        │   else:
        │       # 混合batch → PyTorch eager路径
        │       model_runner.execute_model(running_batch)
        │       # MoE模型内部调用 FusedMoE kernel:
        │       #   router(gate) → top-k select → grouped GEMM → combine

T=5ms   └─ Step 7: 完成检查 + 资源回收
            for req in running_batch:
                if req.generated_token == EOS or req.len >= max_tokens:
                    for blk in req.block_table:
                        gpu_block_allocator.free(blk)
                    running_batch.remove(req)
```

**注解**:
- **变量含义**: `BLOCK_SIZE=16`（每block 16 tokens K/V）、`block_table` 为 `[num_blocks]int32` 映射表（类似OS页表）、`prefix_cache` 为 `{hash → physical_block}` 全局字典、`gpu_block_allocator` 为freelist管理的GPU内存分配器
- **复杂度分析**: Scheduler主循环 O(N+M)（N=waiting请求数，M=running请求数）；Block分配 O(1)（freelist pop）；Prefix caching hash查找 O(L/16)（L=prompt长度，hash+dict lookup）；Model forward O(L·d² + L²·d)（attention项在decode阶段降至O(L·d)）
- **数据依赖**: Step 1（请求选择）→ Step 2（preemption判断，内存约束）→ Step 3（block分配，物理资源约束）→ Step 4（prefix匹配，可并行）→ Step 5（batch组装，无数据依赖）→ Step 6（模型执行，严格依赖前序）
- **并发可行性**: Step 4（prefix caching hash计算）可与Step 3（block分配）并行（分别作用于不同请求子集）；Step 6的CUDA Graph路径独立于CPU scheduler

**硬件体系结构 —— vLLM的GPU硬件特定优化**:

**(a) CUDA Graph 消除 Per-Kernel Launch Overhead**

笔记 `knowledge_notes/kernel知识笔记/Framework Scheduling Overhead.md` (score: 5079.9) 将framework scheduling overhead分解为6个串行CPU步骤：

```
PyTorch Eager Mode 的 Per-Operator Overhead（每个算子重复）:
  Step 1: Operator Dispatch     (~20-30μs)  Python→C++ autograd查找
  Step 2: Output Shape Inference (~10-20μs)  CPU端meta-data计算
  Step 3: Kernel Selection       (~5-50μs)  cuDNN auto-tune
  Step 4: Argument Preparation    (~5-10μs)  grid/block dims, strides
  Step 5: Kernel Launch           (~3-5μs)   cudaLaunchKernel→GPU queue
  Step 6: Memory Allocation       (amortized) PyTorch caching allocator
  ─────────────────────────────────────────
  Total CPU overhead per op:     ~50-115μs
  Typical GPU compute per op:     ~10μs
  → GPU idle ratio:              ~90%+

vLLM CUDA Graph 优化（Decode Phase）:
  预录制整图 → cudaGraphLaunch(exec, stream) 单次提交
  总CPU overhead: <100μs (整iteration)
  → GPU idle ratio: 降至 <5%
```

**(b) FusedMoE Kernel —— Tensor Core 利用最大化**

笔记 `knowledge_notes/kernel知识笔记/FusedMoE (vLLM Fused MoE Kernel).md` (score: 390.2) 描述 FusedMoE 将 MoE 层的 token routing → expert dispatch → grouped GEMM → activation → weighted combine 融合为少量 kernel 调用：

```
// FusedMoE 伪代码（Triton kernel，vLLM实现）
// 输入: hidden_states [num_tokens, hidden_dim]
//       expert_weights [num_experts, hidden_dim, inter_dim*2]
// 输出: output [num_tokens, hidden_dim]

// Step 1: Router (Gate) → 极轻量，O(N·d·E)
gate_logits = hidden_states @ router_weight  # [N, E]
topk_weights, topk_ids = topk(gate_logits, k=2)  # [N, 2]

// Step 2: Expert Dispatch → 重排序tokens
// 通过argsort将同expert的tokens聚集到连续区域
sorted_indices = argsort(topk_ids.flatten())
sorted_tokens = hidden_states[sorted_indices]
expert_offsets = compute_offsets(topk_ids)  # 每expert处理多少token

// Step 3: Grouped GEMM（单次Triton kernel）→ compute-bound
// 利用Triton的block-level parallelism
@triton.jit
def grouped_gemm_kernel(tokens, weights, offsets, output):
    pid = tl.program_id(0)
    expert_id, block_id = decode_pid(pid, offsets)
    # 每thread block处理一个expert的一个tile
    token_tile = load_token_tile(tokens, offsets[expert_id] + block_id)
    weight_tile = load_weight_tile(weights[expert_id], block_id)
    output_tile = tl.dot(token_tile, weight_tile)  # Tensor Core MMA
    store_output_tile(output, output_tile)

// Step 4: Weighted Combine
for k in range(top_k):
    output += topk_weights[:, k:k+1] * expert_outputs[k]
```

**注解**:
- **变量含义**: `num_tokens`=batch中token总数；`hidden_dim`~4096（Mixtral 8x7B）；`inter_dim`~14336；`num_experts`=8；`topk_ids` [N,2] 稀疏路由结果
- **复杂度分析**: Router O(N·d·E) memory-bound（小矩阵）；Grouped GEMM O(N·d·inter_dim/k) compute-bound（大矩阵，Tensor Core高效）
- **硬件收益**: H100上FusedMoE vs naive实现减少 kernel launch overhead（~100次→~5次），减少 HBM round-trip（中间tensor不写回HBM），15-20%吞吐提升

**(c) GPU-side Block Table 消除 CPU↔GPU 同步**

笔记 `knowledge_notes/kernel知识笔记/GPU-side Block Table for PagedAttention (GPU 端 PagedAttention Block Table).md` (score: 23.2) 指出 BrownoutServe 将 block table 从 CPU 移入 GPU 显存：

```
// vLLM原始: CPU-side block table
block_table_cpu[req_id] = [phys_0, phys_1, ...]  // Python分配
cudaMemcpy(block_table_gpu, block_table_cpu, ...) // 每iteration传输
// 问题: cudaMemcpy 延迟 ~5-10μs/iteration

// BrownoutServe: GPU-side block table
// block_table 分配在GPU memory，更新通过GPU kernel:
@triton.jit
def update_block_table(bt_ptr, req_idx, phys_block):
    bt_ptr[req_idx, free_slot] = phys_block
// 消除CPU↔GPU传输，decode iteration overhead 减少 ~50%
```

### 方法2: SGLang Scheduler —— RadixAttention + Token-Level KV-cache Pool

**笔记证据**: `knowledge_notes/系统知识笔记/SGLang（结构化语言模型程序执行框架）.md` (score: 291.2)

**方法细节**（L2调度框架执行模拟）：

SGLang (LMSYS) 的核心调度创新为 **RadixAttention** —— 基于 Radix Tree（压缩前缀树）的 KV Cache 自动前缀复用，区别于 vLLM 的 hash-based prefix caching：

```
═══════════════════════════════════════════════════════════
        SGLang Scheduler + RadixAttention 请求处理时序
═══════════════════════════════════════════════════════════

T=0.0ms  [HTTP Request 到达]
         POST /generate {"prompt": "The theory of relativity explains..."}

T=0.1ms  [RadixAttention 前缀匹配 —— 核心调度创新]
         ┌──────────────────────────────────────────────┐
         │ Radix Tree（压缩前缀树）结构:                  │
         │                                              │
         │  root                                        │
         │   └─ "The theory of " ──── [KV_blk_0]       │ ← 跨请求共享
         │        ├─ "relativity" ─── [KV_blk_1]       │ ← Req_A缓存
         │        │    ├─ " explains" ─ [KV_blk_2]     │ ← Req_A继续
         │        │    └─ " is complex" ─ [KV_blk_3]   │ ← Req_B分支
         │        └─ "evolution" ────── [KV_blk_4]     │ ← Req_C路径
         │                                              │
         │ 新请求 "The theory of relativity explains..."│
         │ 匹配路径: root→"The theory of "→"relativity" │
         │ → 命中 blk_0 + blk_1 (2 blocks缓存命中)      │
         │ → 跳过prefill，直接复用已有KV cache            │
         │ → 仅需prefill未命中部分: "explains..."         │
         └──────────────────────────────────────────────┘

T=0.2ms  [Token-Level KV-Cache 物理分配]
         # 与vLLM block-level(16 tokens/block)不同，
         # SGLang采用token-level粒度:
         for matched_segment in radix_tree.match_prefix(prompt):
             req.token_kv_ptrs.append(matched_segment.kv_ptr)
         for remaining_token in unmatched_tokens:
             new_kv_slot = kv_pool.allocate_token()  # 单token分配
             req.token_kv_ptrs.append(new_kv_slot)

T=0.5ms  [In-Flight Batching 调度]
         # 混合prefill和decode请求
         decode_reqs = [r for r in running if r.is_decode]
         prefill_reqs = schedule_prefills(waiting, available_memory)
         batch = decode_reqs + prefill_reqs

T=0.8ms  [模型执行 —— FlashInfer Backend]
         # FlashInfer是SGLang的底层attention kernel库
         # 支持BSR(Block-Sparse Row)格式的Paged KV-cache
         if prefill_reqs:
             flashinfer.prefill_with_paged_kv_cache(prefill_reqs)
         if decode_reqs:
             flashinfer.decode_with_paged_kv_cache(decode_reqs)

T=1.0ms  [CUDA Graph Decode Launch]
         # Pure decode batch走CUDA Graph快速路径
         # launch overhead <0.5ms（笔记SGLang记录）
         cudaGraphLaunch(decode_graph_exec, compute_stream)

T=1.5ms  [Token 采样 + Radix Tree 更新]
         for req in batch:
             next_token = sample(req.logits)
             # 新token的KV自动插入Radix Tree
             radix_tree.insert(req.full_sequence, next_token_kv_ptr)
             # 后续请求可自动复用
```

**注解**:
- **数据结构**: Radix Tree 节点存储 `{token_seq: bytes, kv_cache_ptr: int64, ref_count: int, children: dict[token_id → node]}`；Token-level KV pool 为 linked-list 结构（笔记PiLLM/5-Implementation）
- **并发粒度**: Radix Tree 的查找/插入为 Python 端单线程操作（~μs级别），与 GPU kernel 执行（~ms级别）相比开销可忽略
- **编译 vs 运行时权衡**: SGLang 使用 `torch.compile` + Triton JIT 生成 GPU kernel（运行时编译），vs TensorRT-LLM 的 AoT 离线编译。JIT更灵活但引入首次编译延迟

**硬件体系结构 —— SGLang的GPU硬件特定优化**:

**(a) FlashInfer BSR (Block-Sparse Row) Attention Kernel**

笔记 `knowledge_notes/kernel知识笔记/Vector Sparsity _ Fine-Grained Block Sparsity.md` (score: 171.4) 描述 FlashInfer 使用 BSR 格式统一表示 Paged KV-cache：

```
// BSR格式: KV-cache pages → BSR non-zero blocks
// page table / radix tree → BSR indices (kv_indptr + kv_indices)
// 支持任意block sizes (Br, Bc) — Br对齐query tile, Bc由KV-cache粒度决定
// Vector sparsity (Bc=1): page-level KV-cache sparsity for token-level scheduling
//
// 关键: gather/scatter将分散的global memory搬运到contiguous shared memory
// → 在dense shared memory数据上使用Tensor Core MMA
// → 避免irregular sparse pattern导致的memory access inefficiency
```

**(b) SM Spatial Sharing (Bullet方案)**

笔记 SGLang 记录 Bullet 在 SGLang v0.4.6 基础上实现 SM 分区并行：
- Prefill worker 和 Decode worker 作为两个独立进程
- 使用 MPS spatial sharing + `libsmctrl` SM masking
- CUDA IPC 共享 GPU memory、ZeroMQ 传递 metadata（CPU端）
- 此方案使 prefill（compute-bound）和 decode（memory-bound）在不同 SM 分区上并行，避免资源竞争

| 平台 | 适配状态 | 说明 |

### 方法3: TensorRT-LLM —— C++ Runtime + Graph Optimization Pipeline

**笔记证据**: `knowledge_notes/编译知识笔记/FasterTransformer.md` (score: 188.2), `knowledge_notes/kernel知识笔记/All-to-All Communication in MoE.md` (score: 16.5)

**方法细节**（L2框架执行模拟）：

TensorRT-LLM (NVIDIA) 是 FasterTransformer 的后继者，采用 **离线图优化 + 运行时 C++ 执行** 架构：

```
═══════════════════════════════════════════════════════════
      TensorRT-LLM 推理编译与运行时执行流程
═══════════════════════════════════════════════════════════

Phase 1: 离线编译（AoT Graph Optimization）

[Step 1] 模型导入与IR构建
  HuggingFace PyTorch checkpoint
    → TensorRT-LLM Python Model Definition API
    → 构建 GraphIR（内部计算图中间表示）
    → 注入并行策略: TP(切Attention/Norm) + EP(分布Expert权重) + PP

[Step 2] Graph Optimization Pass Pipeline
  ├─ Operator Fusion Pass:
  │   ├─ GEMM + GELU/SwiGLU → fused_gemm_activation
  │   ├─ LayerNorm + QKV Projection → fused_ln_qkv
  │   ├─ MoE: Router + Dispatch + GroupedGEMM + Combine → FusedMoE
  │   └─ Residual Add + LayerNorm → fused_residual_layernorm
  ├─ Memory Planning Pass:
  │   ├─ 预分配 KV Cache buffer（PagedAttention兼容格式）
  │   ├─ 中间tensor buffer复用（liveness分析→最小化peak memory）
  │   └─ Workspace预分配（量化scale/zero_point存储）
  ├─ Kernel Auto-Tuning Pass:
  │   ├─ GEMM: cuBLASLt / CUTLASS / custom kernel 在线profile选最优
  │   ├─ Attention: FlashAttention-2 / FlashAttention-3 (Hopper)
  │   └─ MoE: NVLink one-sided alltoall（替代AllGather+ReduceScatter）
  └─ FP8 Precision Pass (H100 SM90):
      ├─ 量化校准: FP16 weights → FP8 E4M3 (per-tensor/channel scale)
      ├─ Transformer Engine集成（动态管理scaling factor）
      └─ FP8 Tensor Core GEMM路径（wgmma指令）

[Step 3] TRT Engine 序列化
  GraphIR + 优化后kernel binary → 单一TRT Engine文件
  → 写入磁盘（跨session复用，无需重新编译）

─────────────────────────────────────────────────────────

Phase 2: 运行时推理（C++ Runtime — GptSession）

[Step 4] Execution Context 初始化
  TRT Engine 加载 → 创建 GptSession
  ├─ 预分配 input/output/kv-cache tensor buffers
  ├─ CUDA Graph 预录制（decode专用，固定batch size + seq len）
  └─ 多个 CUDA stream 预分配（计算stream + 通信stream + copy stream）

[Step 5] In-Flight Batching (IFB) 调度循环
  while not all_requests_done:
      # 动态批次管理
      new_reqs = poll_incoming()
      for req in new_reqs:
          slot = alloc_ifb_slot()  # 分配IFB slot
          req.state = CONTEXT  # Prefill阶段

      # Context Phase (Prefill) & Generation Phase (Decode) 同批混合
      context_slots = [s for s in slots if s.state == CONTEXT]
      gen_slots = [s for s in slots if s.state == GENERATION]

      # 分阶段执行
      if context_slots:
          execute_context_phase(context_slots)  # compute-bound
      if gen_slots:
          if use_cuda_graph:
              cudaGraphLaunch(gen_graph_exec)   # 单次launch
          else:
              execute_generation_phase(gen_slots)  # memory-bound

      # KV Cache更新 + 完成检测
      for slot in slots:
          if slot.gen_token == EOS:
              free_ifb_slot(slot)

[Step 6] MoE Layer 执行细节（基于FasterTransformer MoE实现）
  对每个MoE层:
  1. Router: token → gate_logits → top-k expert indices + weights
  2. Token Dispatch: 按expert_id排序 → 连续内存布局
  3. Expert FFN: CUTLASS Grouped GEMM (FP8/FP16/INT4)
     - 利用CUB radix sort进行token routing排序
     - Grouped GEMM避免per-expert独立kernel launch
  4. Token Combine: 按原始token顺序重排 + 加权求和
  5. NVLink One-Sided AlltoAll: 跨GPU expert并行通信
```

**注解**:
- **数据结构**: `IFB Slot` = `{state: CONTEXT|GENERATION|DONE, kv_cache_blocks[], tokens_generated: int, sampling_params: struct}`；`GptSession` 封装多GPU执行上下文
- **并发粒度**: In-flight batching 在 iteration 级别混合 prefill 和 decode；NVLink one-sided alltoall 通过 GPU 硬件 RDMA 引擎异步执行，与 expert FFN 计算 overlap
- **编译 vs 运行时权衡**: TensorRT-LLM 将重量级优化（算子融合、kernel选择、内存规划）全部前移到离线编译，运行时仅需执行预编译 TRT Engine——CPU overhead 接近零

**硬件体系结构 —— TensorRT-LLM 的 H100 深度整合**:

**(a) FP8 Tensor Core（Transformer Engine）**

笔记 `knowledge_notes/算法知识笔记/FP8 Quantization for MoE Inference.md` (score: 17.8) 记录：
- H100 FP8 Tensor Core 峰值: 1979 TFLOPS（vs FP16: 989 TFLOPS）

**(b) TMA (Tensor Memory Accelerator) 异步数据搬运**

笔记 `paper_secs/secs_multimodal_kernel/FlashAttention-3.../3-FlashAttention-3-Algorithm.md` (score: 15243.6) 详细描述 TMA 在 attention kernel 中的用法：

```
// TMA warp-specialization + pingpong scheduling (FlashAttention-3)
// 两个warpgroup: Producer (DQ) 和 Consumer (DC)

// Producer (DQ): 使用TMA异步预取数据
for each tile:
    tma_load(K_tile, V_tile)  // HBM→SMEM, TMA硬件执行, 不占CUDA core
    // TMA自动处理:
    //   - PagedAttention场景: 通过virtual shape tensor map descriptor
    //   - 非连续memory: SM90_TMA_LOAD_PAGED_OP处理page边界
    //   - hardware barrier: 写入完成后自动signal Consumer

// Consumer (DC): 在TMA搬运期间同时执行计算
for each tile:
    wait(tma_barrier)  // 等待TMA完成当前tile搬运
    WGMMA(Q_tile, K_tile)  // Tensor Core MMA (SMEM数据)
    softmax + rescale
    WGMMA(P_tile, V_tile)
    // 与Producer的下一轮TMA搬运完全重叠
```

**注解**: TMA 使 H100 上的 attention 计算与数据搬运完全 overlap，HBM bandwidth utilization 提升至接近理论峰值

│   - 客户端请求入口                     │

## 二、框架Dispatcher与硬件Command Queue交互深度

### 2.1 GPU 侧（NVIDIA H100/A100）

```
═══════════════════════════════════════════════════════════
      Serving框架 → CUDA Driver → GPU Hardware 全链路
═══════════════════════════════════════════════════════════

[Layer 1: 框架 Scheduler]
vLLM Scheduler (Python) / TensorRT-LLM Runtime (C++)
  ├─ 组装batch、管理block table
  ├─ 调用 model_runner.execute_model() 或 GptSession::execute()
  └─ 最终路径: cudaGraphLaunch() 或 cudaLaunchKernel()

[Layer 2: CUDA Driver/Runtime (Userspace)]
cudaGraphLaunch(cudaGraphExec_t, cudaStream_t)
  → CUDA Driver内部: 参数校验、地址翻译、stream排队
  → Host→Device Command Push (通过MMIO写入GPU Command Buffer)
  → 开销: CUDA Graph: <5μs total; 独立kernel: ~3-5μs per kernel

[Layer 3: GPU Hardware — GigaThread Engine]
  ├─ 接收CUDA stream中的kernel blocks队列
  ├─ 读取每个SM的available resources:
  │   thread_capacity, free_shared_mem, free_registers
  ├─ Left-Over Scheduling (闭源，不可配置):
  │   for each pending block:
  │     for each SM (0..131 for H100):
  │       if SM.free_threads >= block.threads:
  │         dispatch(block, SM)
  │         break
  └─ Block分配粒度: 每个block只能被1个SM执行（不拆分）

[Layer 4: Per-SM Warp Scheduler + Dispatch Unit]
  ├─ Warp Scheduler: 从dispatched blocks选active warps
  │   (round-robin或priority-based, 硬件决策)
  ├─ Dispatch Unit: 发射warp指令到执行单元
  │   (每个cycle可发射1条warp指令 per scheduler)
  └─ 执行单元:
      ├─ Tensor Core (第4代): FP8/FP16/INT8 MMA (wgmma指令)
      ├─ CUDA Core: FP32 FMA + INT32 ALU
      ├─ SFU: sin/cos/exp/sqrt等超越函数
      └─ LD/ST Unit: shared memory + global memory访问
```

**注解**（笔记 `knowledge_notes/硬件知识笔记/GPU Hardware Dispatch Unit (GPU硬件调度单元).md`, score: 13.7）:
- **MAC数量**: H100 per SM含4个第4代Tensor Core，每Tensor Core每时钟1024 FP16 FMA=2048 ops；132 SM×4×2048×1.98GHz≈2000 TFLOPS FP8；989 TFLOPS FP16
- **带宽**: H100 HBM3 3.35 TB/s; L2 Cache 50MB (~12 TB/s); SMEM per SM 256KB (~200 TB/s per SM)
- **闭源限制**: GPU Dispatch Unit细节未公开。left-over scheduling策略不可配置，μShare通过修改kernel blocksize间接影响调度决策（非直接控制）
- **并行度**: 单H100可同时执行的最多blocks取决于SM数(132)×per-SM max blocks(32)=4224 blocks，但受shared memory/register限制

### 2.2 NPU 侧（华为 Ascend 910B）

```
═══════════════════════════════════════════════════════════
      Serving框架 → CANN → Ascend NPU Hardware 全链路
═══════════════════════════════════════════════════════════

[Layer 1: 框架 Scheduler]
vLLM-Ascend / MixServe
  ├─ vLLM Python Scheduler（复用，硬件无关）
  ├─ CANN Adapter: CUDA API → CANN API 映射层
  └─ Ascend Graph 替代 CUDA Graph（静态图编译）

[Layer 2: CANN (Compute Architecture for Neural Networks)]
  ├─ ACL (Ascend Computing Library):
  │   提供GEMM/Conv/Attention等预优化算子
  │   等价于cuBLAS/cuDNN
  ├─ Ascend Graph (图编译):
  │   计算图→Task Descriptor Chain→硬件TS执行
  │   与CUDA Graph的关键差异: 硬件TS直接解析执行,
  │   无需类似GigaThread Engine的软件层干预
  └─ HCCL (Huawei Collective Communication Library):
     替代NCCL, 支持HCCS(片间互联60 GB/s)+RoCE(25 GB/s)

[Layer 3: Ascend NPU Hardware Task Scheduler (TS)]
  ├─ 接收编译好的Task Descriptor Chain
  ├─ 按task dependency顺序发射到AI Core
  ├─ 支持配置优先级 + task queue depth
  │   (vs GPU Dispatch Unit闭源不可配置)
  └─ 笔记未明确说明TS的调度策略细节

[Layer 4: Da Vinci AI Core]
  ├─ Cube Unit (脉动阵列): MatMul主力, 等价GPU Tensor Core
  │   但数据流模式不同 (systolic vs MMA指令)
  ├─ Vector Unit (SIMD): 向量计算, 等价GPU CUDA Core
  ├─ Scalar Unit: 标量/控制流
  └─ L1 Buffer + L0 Buffer:
     (分离设计, 非GPU shared memory统一模型)
```

**注解**（笔记 `knowledge_notes/kernel知识笔记/Fused AR-A2A Communication Algorithm.md`, score: 21.7）:
- **MixServe实测**: Ascend 910B上DeepSeek-R1 TTFT 2.67× vs vLLM TP+PP, 1.70× vs vLLM DP+EP
- **通信架构差异**: HCCS片间60 GB/s vs NVLink 900 GB/s——跨节点通信成为Ascend集群的主要瓶颈（MixServe的Fused AR-A2A算法正是为解决此问题）
- **片上存储差异**: Ascend 910B L1 Buffer与GPU shared memory的容量/bank结构不同，PagedAttention的tile size需针对性调优。vault中未提供精准spec数值
- **Task Descriptor Chain vs CUDA Graph**: Ascend Graph编译后产出task descriptor chain，由硬件TS直接解析——消除了GPU上GigaThread Engine的软件层block调度延迟
