## 一、方法细节：Dispatcher 核心架构与硬件映射

### 方法1: SLO-Aware Dispatcher with Dynamic SM Repartitioning (MuxWise + Bullet)

**笔记证据**: `paper_secs/secs_2026/1-Towards High-Goodput LLM Serving with Prefill-decode Multiplexing/3.4-SLO-aware-Dispatcher.md` (score: 5286.6), `knowledge_notes/系统知识笔记/Dynamic SM Repartitioning（动态SM重分区）.md` (score: 46.3)

**方法细节** — Dispatcher 调度流程伪代码（L2 框架模拟）：

```
// ===== MuxWise SLO-Aware Dispatcher 单次迭代 =====
// 运行平台: 单GPU (A100/H100), SGLang 0.4.10post2 + GreenContext
// 输入: prefill_queue, decode_batch, SLO target (TBT: 50ms/100ms)
// 输出: SM分区配置 + 发射的prefill/decode batch

Function SLO_AWARE_DISPATCH(prefill_queue, decode_batch, SLO_TBT):
    // Step 1: Decode SLO优先 — 计算decode所需最小SM数
    T_d = ContentionTolerantEstimator.estimate_decode(
        decode_batch.size, avg_seq_len, kv_cache_size)
    
    // Step 2: 确定SM分区 (通过GreenContext API)
    // A100: 108 SM → 6种配置 (每16 SM粒度); H100: 132 SM → 7种配置
    SM_decode = ceil((T_d / SLO_TBT) * total_SMs)
    SM_decode = min(SM_decode, total_SMs * 0.8)  // 上界保护
    SM_prefill = total_SMs - SM_decode
    
    // Step 3: 分配SM给两个GreenContext
    libsmctrl_set_stream_mask(stream_decode, build_mask(0, SM_decode))
    libsmctrl_set_stream_mask(stream_prefill, build_mask(SM_decode, SM_prefill))
    // 重分区耗时: ~4.1μs on A100
    
    // Step 4: 计算prefill layer数 (layer-wise multiplexing)
    T_P = ContentionTolerantEstimator.estimate_prefill_layer(
        prefill_batch.tokens, SM_prefill)
    N_PL = ceil((T_d * N_layers) / T_P)  // 此次发射的prefill层数
    
    // Step 5: 发射并行执行
    launch_async(decode_kernel, stream_decode, all_decode_tokens)
    launch_async(prefill_layers[0:N_PL], stream_prefill, prefill_tokens)
    
    // Step 6: Prefill完成→合并到decode batch
    cudaStreamSynchronize(stream_prefill)
    decode_batch.merge(completed_prefill_tokens)  // batch_size 增大
    
    // Step 7 (可选): Prefill Preemption
    if new_prefill.has_tight_TTFT and active_prefill.will_miss_SLO():
        preempt(active_prefill)  // 不递归抢占
        schedule(new_prefill)
```

**SLO-aware Repartition 决策逻辑（Bullet 风格动态SM重分区）**:

```
// 每个prefill layer group或decode step后触发
state = read_shared_metadata_buffer()  // p90_tpot, queue_depth, current_sm_split

if state.p90_tpot > TPOT_SLO * 0.9:
    // decode近SLO边界 → 移SM给decode
    new_sm_decode = state.sm_decode + 16
elif state.prefill_queue_depth > threshold AND state.p90_tpot < TPOT_SLO * 0.7:
    // prefill堆积且decode有余量 → 移SM给prefill
    new_sm_prefill = state.sm_prefill + 16

resource_manager.repartition(new_sm_prefill, new_sm_decode)
// 内部: libsmctrl_set_stream_mask() → 后续kernel自动在新SM子集上执行
```

**注解**:
- **SM分区粒度**: 16 SM/步, A100上6种配置, H100上7种配置。太粗则响应迟钝, 太细则频繁切换开销大
- **GreenContext vs MPS vs MIG**: GreenContext (CUDA 12.4+) 支持进程内SM分区, 比MPS更轻量, 比MIG更灵活（不需要重启GPU）
- **Contention Tolerant Estimator**: 关键组件——建模HBM带宽竞争（prefill和decode共享HBM通道），为decode提供worst-case slowdown因子，确保decode SLO不被prefill干扰
- **硬件依赖**: 依赖NVIDIA SM mask机制（通过libsmctrl/GreenContext API操作硬件寄存器），非开源GPU无法直接移植到NPU。NPU对应机制为task descriptor queue的优先级抢占（笔记未明确说明NPU等价API）
- **Preemption约束**: 不递归抢占——短请求抢占长请求后不可再被抢占（避免级联SLO miss）

### 方法2: Priority-Based Greedy + Preemptive Micro-Operator Scheduling (TZ-LLM)

**笔记证据**: `knowledge_notes/kernel知识笔记/Pipelined Parameter Restoration.md` (score: 141.3), `experiment_notes/系统实验笔记/TZ-LLM_ Protecting On-Device Large Language Models with Arm TrustZone.md` (score: 187.6)

**方法细节** — DAG扩展 + Priority Scheduler 框架模拟：

```
// ===== TZ-LLM Dispatcher: 四种Operator DAG + Priority Greedy =====
// 运行平台: RK3588 (4×A76 + 4×A55 + 3-core NPU ~6 TOPS)
// Operator类型: ALLOC, LOAD, DECRYPT, COMPUTE

// Step 1: 编译期 — DAG构建
扩展Computation Graph:
  for layer_idx in topological_order:
      comp_op = original_graph[layer_idx]  // 原始compute operator
      // 每个compute前插入3类restoration operator
      alloc_op = AllocOp(layer_idx, param_size)    // CMA内存分配
      load_op  = LoadOp(layer_idx, param_size)     // Flash I/O读取
      decr_op  = DecrOp(layer_idx, param_size)     // AES解密
      // 层内依赖: alloc → load → decr → comp
      // 跨层无依赖: comp[layer_i] 可与 {alloc,load,decr}[layer_{i+1}] 重叠

// Step 2: 运行时 — Priority-based Greedy Scheduler
ready_queue = PriorityQueue()  // 按优先级排序

while has_pending_operators():
    ready_queue.update()  // 扫描DAG, 加入依赖已满足的operators
    
    if ready_queue.has(COMPUTE):
        op = ready_queue.pop_highest_priority()  // COMPUTE优先级最高
    else:
        earliest_comp = find_earliest_comp_in_dag()  // 拓扑序最早的compute
        op = get_associated_restoration(earliest_comp)
        // 优先为即将到来的compute准备参数
    
    execute(op)

// Step 3: Preemptive Micro-Operator 机制
// 大alloc/decrypt (>64KB) 被切分为 ~64KB micro-ops
// CPU computation就绪时 → 抢占当前micro-op → 插入compute
// 抢占后恢复: alloc_micro_op.resume_from_checkpoint()

// 执行时序示例 (Llama-3-8B, 512-token prompt):
// Layer0: [Alloc0][Load0][Decrypt0]======[Compute0]==========
// Layer1:          [Alloc1][Load1][Decrypt1]======[Compute1]==
// Layer2:                   [Alloc2][Load2][Decrypt2]=========
//         ← restoration latency被隐藏到computation latency下 →
```

**注解**:
- **Operator类型与硬件映射**: COMPUTE → NPU (3-core, ~6 TOPS) 或 CPU (A76大核); LOAD → Flash I/O (NVMe SSD); DECRYPT → CPU AES (OpenSSL); ALLOC → CPU CMA API
- **抢占粒度**: ~64KB micro-operator — 在RK3588 LPDDR4X (约25 GB/s带宽) 下每次micro-op约 2.5μs。抢占开销为保存/恢复状态寄存器 + TZASC重配置
- **Pipeline效率**: 距critical path lower bound仅 0.01%-9.9% (笔记显示)
- **NPU Co-Driver设计**: REE driver负责scheduling/power/frequency (control plane); TEE data plane driver负责secure job context/MMIO launch/interrupt completion。Shadow job机制使secure job可入统一队列
- **Single-Request适用性**: 该方法天然为单请求设计 — 整个DAG服务于单一LLM推理请求的prefill+decode全流程

### 方法3: ACS — Out-of-Order Kernel Dispatch with Runtime Dependency Resolution

**笔记证据**: `paper_secs/secs_multimodal_kernel/ACS Concurrent Kernel Execution on Irregular, Input-Dependent Computational Graphs/D.-Key-Observations.md` (score: 2441.0)

**方法细节** — Hardware-Assisted 调度窗口 框架模拟:

```
// ===== ACS: Runtime Out-of-Order Kernel Dispatch =====
// 核心思想: 模仿CPU乱序执行 — 在GPU Command Processor中维护调度窗口,
//          运行时检测kernel间数据依赖, 标记就绪kernel并发发射

// === ACS-SW (纯软件实现) ===
// 数据结构
Input_FIFO:     queue<kernel_metadata>    // 应用层调用的kernel队列
SchedulingWindow: fixed[N] slots {         // N=32~64
    kernel_id, state ∈ {READY, PENDING, EXECUTING},
    upstream_list: [kernel_id],            // 依赖的上游kernel
    read_segments:  [(start_addr, size)],  // 读内存段
    write_segments: [(start_addr, size)]   // 写内存段
}

// 多线程调度器
Thread_WindowModule:  // 管理窗口 + 依赖检测
    loop:
        // 1. 从Input FIFO取kernel入窗口
        if SW.has_vacancy() and FIFO.not_empty():
            kernel = FIFO.pop()
            // 依赖检测 (Algorithm 1)
            for each sw_kernel in SW:
                if overlap(kernel.write_segments, sw_kernel.read_segments) OR
                   overlap(kernel.write_segments, sw_kernel.write_segments):
                    kernel.upstream_list.append(sw_kernel.id)
                    kernel.state = PENDING
            SW.insert(kernel)  // 无依赖→READY; 有依赖→PENDING
        
        // 2. 当kernel完成时更新窗口
        on_kernel_complete(kernel_id):
            for each sw_kernel in SW:
                sw_kernel.upstream_list.remove(kernel_id)
                if sw_kernel.upstream_list.empty():
                    sw_kernel.state = READY

Thread_SchedulerModule:  // N_threads, 每个绑定1个CUDA stream
    loop:
        if my_stream.empty():
            ready_kernel = SW.poll_ready()  // 从窗口取READY kernel
            launch(ready_kernel, my_stream)
            cudaStreamSynchronize(my_stream)  // 等待完成→触发窗口更新

// === ACS-HW (硬件加速) ===
// 硬件调度窗口 (GPU Command Processor内)
// 结构: N slots × [(N-1)×8B upstream IDs + 2bit state] SRAM
// N=32 → ~1KB SRAM (全GPU)

Hardware_Scheduling_Window:  // GPU侧
    // 插入: CPU发kernel+upstream list → HW窗口
    // 更新: kernel完成 → HW遍历所有slot, 移除对应upstream ID
    //        → 某slot upstream为空 → 标记READY → 发射到dispatch unit
    // 延迟: N=64时 ~64 cycles (~50-100ns) overhead
    
    // CPU维护scheduled_list (可stale, 最大M条)
    // 插入新kernel前用scheduled_list做初筛依赖 → 减少HW窗口误判
    // upstream_load_module防止scheduled_list遗漏长running kernel
```

**多流 vs DAG vs ACS 对比**:
```
// 传统单流 (顺序执行, GPU利用率低)
Stream0: [K0][K1][K2][K3][K4][K5]  → 无并发

// Multi-Stream + Event (需提前全部依赖分析, 同步开销大)
Stream0: [K0]──────→event→[K3]─────→
Stream1:    [K1]──→event→[K4]──→     ← 5-20μs sync overhead/event
Stream2:       [K2]──────→[K5]→

// ACS (运行时窗口调度, 无CPU同步, 乱序发射)
Scheduling Window (N=4):
  T0: [K0:R][K1:P(K0)][K2:P(K0,K1)][K3:R]  → 发射K0, K3
  T1: [K1:R][K2:P(K1)][K4:P(K3)][K5:R]      → 发射K1, K5
  T2: [K2:R][K4:R][K6:P(K5)][K7:P(K4,K6)]    → 发射K2, K4
```

**注解**:
- **硬件调度窗口 vs CPU调度**: ACS-HW消除CPU-GPU同步（无StreamSync），kernel完成事件在GPU内部处理。对单请求微算子场景，调度窗口大小N=32~64足以覆盖一层MoE或DiT step内的算子数
- **依赖检测开销**: CPU侧scheduled_list fit in cache (~4KB)，依赖检测 compute-bound而非memory-bound。对N=32窗口，segment overlap检测 < 1μs
- **适用场景**: ACS特别适合input-dependent irregular DAG（如动态路由MoE、instance-aware DNN），因为在运行时才知道kernel依赖。对固定DAG（标准Transformer），传统CUDA Graph更高效
- **硬件面积**: 1KB SRAM（N=32调度窗口），可忽略不计
- **与GPU Command Processor交互**: ACS-HW直接修改command processor的调度逻辑——原本按队列顺序发射，现改为从调度窗口中选择READY kernel乱序发射。这是硬件-软件协同设计的关键创新点
- **笔记未明确说明**: NPU/TPU是否有等价的command processor可修改性。NPU的task descriptor queue通常为FIFO，缺乏乱序发射硬件支持

### 方法4: Resource-Aware Multi-Dimensional Task Dispatching (HuntKTm)

**笔记证据**: `knowledge_notes/系统知识笔记/Resource-Aware Task Dispatching (Multi-GPU).md` (score: 556.8)

**方法细节** — 三维资源感知调度算法:

```
// ===== HuntKTm Resource-Aware Dispatcher =====
// 核心: 三维SM资源评估 → 防单一维度瓶颈 → 负载均衡

Function TASK_SCHEDULE(GPU_list G, pending_queue Q, Task T):
    g_best = None, score_best = 0
    
    for each gpu in G:
        // 维度1: Memory — free memory ≥ task需求
        if gpu.free_memory < T.memory_requirement:
            continue
        // 维度2: Hardware Queue — 可用concurrent streams ≥ task需求
        if gpu.available_hw_queues < T.stream_count:
            continue
        
        // 维度3: Compute — 三维SM可用量评估
        // 将threads/registers/shared_memory归一化到[0,1]
        score_threads = (gpu.avail_threads + T.thread_req) / gpu.total_threads
        score_regs    = (gpu.avail_regs    + T.reg_req)    / gpu.total_regs
        score_shmem   = (gpu.avail_shmem   + T.shmem_req)  / gpu.total_shmem
        
        // 最紧张的资源维度决定score (木桶原理)
        bottleneck = min(score_threads, score_regs, score_shmem)
        score = gpu.total_sms - bottleneck  // SM越多 + 资源越宽松 → score越高
        
        if score > score_best:
            g_best = gpu, score_best = score
    
    if g_best != None:
        gpu.reserve(T)  // 预留资源
        return g_best
    else:
        T.suspend_to(pending_queue)  // 挂起等待资源释放
        return None
```

**注解**:
- **三维评估的必要性**: 不同micro-operator有不同资源瓶颈——GEMM受限于registers (large tile), attention受限于shared memory (KV tile), elementwise受限于threads。单维度评估会导致错配
- **Hardware Queue维度**: 每个task可能占用多个CUDA stream（NVIDIA H100: 128 hardware queues; A100: 128）。HuntKTm显式管理stream分配
- **非抢占式**: task一旦分配不迁移 — 避免micro-operator中途迁移的开销（需保存/恢复register + shared memory状态 + 跨GPU拷贝中间结果）
- **Single-Request映射**: 单请求内多个micro-operator可视为多个task，分配到同一GPU的不同stream（空间复用）或不同GPU（如果可用）
- **硬件依赖**: 依赖NVIDIA persistence mode减少GPU初始化开销; 依赖memory pool预分配减少运行时alloc/free

### 方法5: Hybrid Prioritization + Eager Relegation Dispatcher (QoServe)

**笔记证据**: `paper_secs/secs_2026/4-QoServe Breaking the Silos of LLM Inference Serving/span-idpage-3-0span3-QoServe-Design-and-Implementation.md` (score: 3756.4)

**方法细节** — 三队列架构 + 动态优先级插值:

```
// ===== QoServe Dispatcher: 三队列 + Hybrid Prioritization =====
// 队列架构: Prefill Queue → Decode Queue → Relegated Queue

// 优先级公式 (Hybrid = EDF + SRPF插值)
// Interactive请求:
P_i = t_arrival + SLO_TTFT + α × Prefill_rem_tokens
//      ↑ EDF部分   ↑ SLO        ↑ SRPF部分 (remaining work)

// Non-interactive请求:
P_i = t_arrival + SLO_TTLT + α × (Prefill_rem + Decode_rem)

// Dynamic Batch Creation (Algorithm 1)
Function CREATE_BATCH():
    selected = GET_ALL_DECODES()  // 所有decode请求必入batch
    min_slack = GET_MIN_SLACK(selected)  // decode batch的最小slack
    C = GET_PREFILL_BUDGET(num_decodes, context, min_slack)
    // C = 在满足decode TBT约束下最大prefill chunk
    
    job_queue = PRIORITY_QUEUE(COMPARATOR)  // 按P_i排序
    prefill_tokens = 0
    
    while prefill_tokens < C:
        top = job_queue.TOP
        if WILL_VIOLATE(top):  // 已/将违反SLO
            top.relegate()     // → relegated queue
            job_queue.PUSH(top)
            continue
        
        take = min(C - prefill_tokens, top.rem_tokens)
        prefill_tokens += take
        selected.APPEND(top)
        job_queue.POP()
    
    PROCESS_BATCH(selected)  // fused prefill+decode attention

// Relegation策略:
// - 主动relegate已violate或即将violate的请求
// - Multi-tenant: free-tier优先relegate, premium保护
// - 仅5% relegation即可在极端过载下维持SLO
```

**注解**:
- **α参数**: 控制EDF↔SRPF平衡。α=8 ms/token时violation最小; 低负载α=1 ms/token优化tail latency; 高负载α增大以优先短请求
- **Dynamic Chunking的硬件意义**: 增大chunk → 更多prefill tokens与decode融合执行 → HBM bandwidth利用率提升（decode时memory-bound, prefill可填满空闲带宽）
- **选择性Preemption**: 仅prefill阶段可抢占（不抢占decode, 避免TBT violation; 不递归抢占）。KV-cache保留在GPU最短必要时间
- **复杂度**: O(log N_new) — 仅priority queue操作, vs SLOs-Serve的O(N × N_new × M)
- **Single-Request场景**: QoServe主要面向多请求调度, 但其hybrid prioritization + relegation理念可借鉴到单请求内micro-operator调度——对latency-critical算子(如attention)优先, 对batch算子(如FFN)降级

### 方法6: Infera Runtime — Tile-Level DAG Scheduling + Warp-Level Fusion + Daemon Launch

**笔记证据**: `experiment_notes/kernel实验笔记/Automated End-to-End Model Serving with Cooperative Compilation and Scheduling.md` (score: 59.0), `idea_notes/Automated End-to-End Model Serving with Cooperative Compilation and Scheduling.md` (score: 117.3)

**方法细节** — 三阶段Kernel调度Pipeline:

```
// ===== Infera Runtime Dispatcher: SelectKernels → FuseKernels → LaunchKernel =====

// === Phase 3: LaunchKernel (多级异步Pipeline) ===
HKQ (Host Kernel Queue):  // priority queue按launch timestamp排序
    ↓ GDRCopy (gdr_copy_to_mapping, <100ns small / <5μs typical)
DKQ (Device Kernel Queue):  // GPU侧
    ↓ daemon kernel (独占1 SM, CDP fire-and-forget launch, <10μs)
```

**注解**:
- **G(u) asynchrony wavefront metric**: 递归传播children的并发收益到parents — 确保选择能最大化下游并发的data block。terminal G(v) = -1
- **Warp-level fusion**: 在多micro-operator间共享SM资源。BERT warps和ViT warps交错排布在同一SM → 降低scoreboard/throttle stall cycles
- **Daemon Kernel Launch**: 通过CDP (CUDA Dynamic Parallelism) 从GPU内部fire-and-forget发射kernel, <10μs延迟。避免Host→Device kernel launch的PCIe往返（~5-10μs/次）
- **Preemption**: Infera-P ~10μs (暂停HKQ→DKQ保存), Infera-R ~5μs (仅保存不暂停)。比REEF-N快 ~2.5×
- **硬件交互深度**: GDRCopy bypass DMA engines (直接PCIe BAR映射), daemon kernel独占1 SM, shared-memory double-ended queue实现device-side低延迟kernel fetch — 这是最深度的硬件-软件协同dispatcher设计

### 方法7: Arithmetic Intensity-Aware Dispatcher (SADDLE PIM-GPU)

**笔记证据**: `knowledge_notes/kernel知识笔记/Arithmetic Intensity-Aware PIM-GPU Operator Scheduling（算术强度感知的PIM-GPU算子调度）.md` (score: 333.5)

**方法细节** — CI-Based Dynamic Mapping:

```
// ===== SADDLE Dispatcher: CI阈值比较 → Operator-to-Device映射 =====
// 平台: PIM+GPU异构系统 (HBM-PIM PE array + A100 GPU)

// Offline预标定 (一次性)
PIM_peak_compute = 2.4 TFLOPS     // HBM-PIM PE array
PIM_peak_bw      = 144 TB/s       // PIM internal bandwidth
PIM_ridge = PIM_peak_compute / PIM_peak_bw  // ~16.7 FLOP/Byte

GPU_peak_compute = 312 TFLOPS     // A100 Tensor Core FP16
GPU_peak_bw      = 1.5 TB/s       // HBM2e
GPU_ridge = GPU_peak_compute / GPU_peak_bw  // ~208 FLOP/Byte

// Runtime per-iteration调度
Function SCHEDULE_OPERATOR(op_type, eff_batch_size):
    FLOPs = estimate_flops(op_type, eff_batch_size)
    Bytes = estimate_bytes(op_type, eff_batch_size)
    CI = FLOPs / Bytes  // Arithmetic Intensity
    
    if CI < PIM_ridge:
        target = "PIM"   // memory-bound → PIM (高带宽)
    elif CI > GPU_ridge:
        target = "GPU"   // compute-bound → GPU (高算力)
    else:
        target = "GPU"   // intermediate → GPU (避免PIM编程复杂度)
    
    return target

// 动态性示例: DLM FC operator
// eff_bs=12 → CI≈12 → < GPU_ridge but > PIM_ridge → GPU
// eff_bs=4  → CI≈4  → < PIM_ridge → PIM
// 短draft请求先完成后batch缩小 → 同一operator最佳设备随batch变化
```

**注解**:
- **硬件差异化利用**: PIM ridge point (16.7 FLOP/Byte) vs GPU ridge point (208 FLOP/Byte) — 差距13×。PIM适合极度memory-bound算子, GPU适合compute-bound算子
- **运行时效率**: 仅需预标定阈值 + 简单代数运算 (FLOPs和Bytes估算), 无需完整profiling。适合单请求内频繁的per-iteration调度决策
- **Single-Request适用性**: Speculative decoding中每个prediction/verification iteration都需重新决策 — 适合单请求内微算子动态调度
- **笔记未明确说明**: NPU的ridge point (昇腾910B: 256 TFLOPS FP16, HBM2e 1.2 TB/s → ridge ≈ 213 FLOP/Byte)

### 方法8: Micro-Batch CUDA Stream Pipeline Dispatcher (MPipeMoE)

**笔记证据**: `experiment_notes/kernel实验笔记/MPipeMoE_ Memory Efficient MoE for Pre-trained Models with Adaptive Pipeline Parallelism.md` (score: 56.3)

**方法细节** — 多Stream干扰建模 + 自适应调度:

```
// ===== MPipeMoE Dispatcher: 3-Stream Pipeline + Interference Model =====
// 平台: 8×NVIDIA DGX A100 (64 GPU), CUDA 11.1, NCCL

// Stream配置
stream_comp:  // GeMM kernel (expert FFN)
stream_comm:  // NCCL All-to-All (token dispatch + collect)
stream_mem:   // cudaMemcpy D2H/H2D (optional, 某些strategy无此stream)

// === Interference Profiling (离线) ===
// 量化并行执行时的slowdown因子
μ_comm = W_comm × t_alone / (Bytes / t_parallel)  // 通信slowdown (因与计算并行)
σ_comp = 类似定义  // 计算slowdown (实测≈1, 几乎不受影响)
η_mem  = 类似定义  // memory copy slowdown (通信+拷贝并行时显著)

关键发现:
- σ≈1: 计算几乎不被其他stream干扰 → 通信-计算重叠可行
- μ_comm>0.5: 通信受计算干扰但可接受
- η_small: 通信+memory copy并行时带宽竞争严重 → 避免

// === Pipeline执行模型 (5阶段: P0-P4) ===
b = B/n  // micro-batch size
q1 = comp_ops_count, q2 = comm_ops_count, q3 = mem_ops_count

T_fw = max(q1 × FLOPs(b) / (σ × W_comp(b)),
           q2 × Bytes(b) / (μ × W_comm(b)),
           q3 × Bytes(b) / (η × W_mem(b)))

// === Adaptive Strategy Selector ===
// 4种memory reuse策略 (S1-S4), 不同(N,B)组合选最优
S1: forward 3 streams, backward 3 streams
S2: forward 3 streams, backward 3 streams (extra comm)
S3: forward 3 streams, backward 3 streams (extra recompute)
S4: forward 2 streams (no mem), backward 3 streams (extra comm+recompute)

// 选择: min T_total(n, S) over n∈{1,2,4,8,16}, S∈{S1,S2,S3,S4}
// N小(8 GPU): S1/S2更优 (I/O bound场景)
// N大(64 GPU): S4更优 (避免memory bandwidth竞争)
```

**注解**:
- **Pipeline Granularity n**: 影响kernel launch频率和GPU利用率。n=1 (粗粒度): 少launch但气泡大; n=16 (细粒度): 多launch但气泡小、重叠好
- **硬件平台特化**: MPipeMoE的调度决策高度依赖DGX A100的NVLink 3.0 + NVSwitch拓扑。不同硬件需重新profiling μ/σ/η因子
- **Single-Request映射**: micro-batch = 单请求内的token分组, pipeline = micro-operator流水线, 理念直接适用于单请求微算子并发

### 方法9: Shepherd Operator — 调度粒度优化抽象 (Infera)

**笔记证据**: `knowledge_notes/编译知识笔记/Shepherd Operator.md` (score: 658.1), `knowledge_notes/编译知识笔记/Tile-Based Zero-Tuning Compilation.md` (score: 60.0)

**方法细节**:

```
// ===== Shepherd Operator: 小Operator合并 → 降低调度开销 =====
// 问题: elementwise add/activation (执行仅~几μs) 
//       作为独立micro-operator调度 → scheduling/fusion/launch overhead >> 执行时间

// 解决: Compiler在graph partition阶段识别小operator子图 → 合并为Shepherd Operator
Computation Graph Partition:
  ├── Large operators → micro operators (tiled)
  │    e.g., Conv2D → Conv_tile_0, Conv_tile_1, ...
  │    每个tile独立编译为micro-kernel
  └── Small operators → Shepherd Operator (merged)
       e.g., [Add, ReLU, BatchNorm] → Shepherd_0
       Shepherd kernel内部按拓扑顺序调用: k_add → k_relu → k_bn
       对外表现为单一调度单元 (一个micro operator)

// 调度效果: per-micro-operator → per-shepherd-operator
// 调度开销减少 N× (N=合并的小operator数)
```

**注解**:
- **调度粒度权衡**: 过细 (per-μs-operator) → launch overhead主导; 过粗 (per-layer) → 丢失并发机会。Shepherd Operator在两者间取得平衡
- **硬件意义**: 每次CUDA kernel launch约 5-10μs overhead (PCIe command传输 + command processor处理)。合并10个2μs小算子 → 20μs执行+10μs launch → 节省9次launch (~45-90μs)
- **TEU (Task Execution Unit) 兼容**: Shepherd operator在Infera runtime的SelectKernels/FuseKernels/LaunchKernel pipeline中表现为单一调度单元, 减少metadata和fusion开销
- **适用性**: 广泛适用于所有模型中的elementwise/normalization/activation类微算子

## 三、硬件同步原语对 Dispatcher 设计的影响

### 3.1 GPU 同步原语

```
// === GPU同步原语层级 ===
// Level 1: Device级 — 全局同步, 开销最大
cudaDeviceSynchronize()          // ~10-50μs, 等待所有stream完成
cudaStreamSynchronize(stream)    // ~5-10μs, 等待单stream完成

// Level 2: Stream级 — 跨stream异步同步, 中等开销
cudaStreamWaitEvent(stream, event)  // ~1μs, GPU内信号, 无需CPU
cudaEventRecord(event, stream)      // ~0.5μs

// Level 3: Block/Warp级 — SM内同步, 最低开销
__syncthreads()     // block内barrier, ~10-20 cycles (~10ns)
__syncwarp()        // warp内同步 (CC 7.0+)
BAR.SYNC            // SASS级别barrier, Infera用于warp fusion后重组

// Level 4: 数据级 — 无同步, register-level
warp shuffle (__shfl_sync)  // ~1 cycle, lane间数据交换
```

**Dispatcher设计影响**:
- **ACS-SW**: 被迫使用cudaStreamSynchronize (Level 1) → 引入CPU-GPU同步瓶颈。ACS-HW通过硬件调度窗口消除此开销
- **Infera**: FuseKernels后需重组BAR.SYNC (Level 3) — warp fusion改变thread组织, 原kernel的barrier不再有效
- **MuxWise**: 依赖cudaStreamWaitEvent (Level 2) 实现prefill/decode stream间的异步同步 — 避免CPU轮询

### 3.2 NPU 同步原语

**笔记证据**: 笔记未详细描述NPU barrier instruction的具体语义和延迟。TZ-LLM中通过monotonic sequence number + interrupt completion实现NPU job同步。笔记未明确说明NPU是否支持类似GPU warp shuffle的细粒度同步。

### 3.3 同步开销对 Dispatcher 设计的影响总结

| 同步层级 | GPU开销 | Dispatcher策略 | 硬件依赖 |
|----------|---------|----------------|----------|
| Device同步 (cudaDeviceSynchronize) | 10-50μs | 避免 — ACS-HW用硬件窗口替代 | Command Processor |
| Stream同步 (cudaStreamWaitEvent) | ~1μs | 适度使用 — MuxWise prefill/decode同步 | CUDA Event机制 |
| Block同步 (__syncthreads) | ~10ns | 必须 — kernel内部tile边界 | SM warp scheduler |
| Warp同步 (warp shuffle) | ~1 cycle | 首选 — register-level数据交换 | SM warp scheduler |
| NPU interrupt completion | ~μs? (笔记未明确) | TZ-LLM: secure job完成信号 | NPU interrupt controller |

- **评估**: Orange Pi 5 Plus (RK3588); Llama-3-8B, Qwen2.5-7B; TTFT, decoding speed, pipeline critical path overhead

### 6.3 Infera Runtime
- **框架**: ~17K LoC C++ kernel-space module, 从零开发
- **底层**: GDRCopy, CUDA Dynamic Parallelism, SASS-level binary manipulation
- **评估**: A100-PCIE-40GB; BERT + ViT concurrent inference; vs Stream/MPS/Triton/Paella

### 6.4 QoServe Dispatcher
- **框架**: Sarathi-Serve + vLLM扩展
- **底层**: Lightweight Random Forest predictor (CPU侧, <10% error); Vidur simulator profiling harness
- **评估**: 16×A100 cluster; Llama3-8B/70B + Qwen-7B; ShareGPT + Azure Conv/Code traces

## 八、不确定性

1. **NPU Dispatcher具体机制**: 笔记中关于NPU (昇腾/寒武纪) 的task descriptor queue格式、command processor架构、barrier instruction语义等信息缺失。搜索"NPU task descriptor queue"返回0结果。对NPU上微算子dispatcher的设计只能从TZ-LLM的RK3588 NPU co-driver间接推断
2. **TPU Device-Side Scheduling**: 笔记未包含TPU v5e/v5p运行时dispatcher的详细设计。XLA编译期调度与运行时调度的边界在笔记中未明确
3. **Groq LPU / Cerebras CS-3**: 笔记中未检索到关于Groq或Cerebras的dispatcher设计资料
4. **Command Processor修改可行性**: ACS-HW需要修改GPU硬件command processor — 这在商业GPU上不可行（需NVIDIA合作）。实际商用系统的dispatcher仍基于软件（ACS-SW, Infera runtime级别）
5. **Shepherd Operator阈值**: Infera论文未给出小operator合并的具体FLOPs/执行时间阈值，笔记也未说明
6. **Single-Request专有优化**: 大部分方法（MuxWise, QoServe, MPipeMoE）面向多请求batch场景，其微算子并发理念可迁移到单请求，但直接适用性需验证。TZ-LLM和ACS是少数天然面向单请求/input-dependent DAG的方法
