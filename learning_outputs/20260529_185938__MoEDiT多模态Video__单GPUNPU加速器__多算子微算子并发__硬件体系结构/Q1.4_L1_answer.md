## 1. 方法细节：硬件数据流 + 计算/控制模块设计 + 架构（主内容）

### 1.1 MoE：多 Expert FFN 并发 + All-to-All 通信重叠

**笔记证据**: `paper_secs/secs_moe/PROBE.../PROBE-CO-BALANCING...md` (score: 5623.0), `knowledge_notes/系统知识笔记/Expert Parallelism.md` (score: 37.8), `knowledge_notes/kernel知识笔记/Irregular All-to-All...md` (score: 1797.5)

#### 1.1.1 MoE 单层执行的数据依赖 DAG 与并发机会

MoE 层推理的算子级数据依赖 DAG 如下（以 EP 模式下单 GPU 视角）：

```text
输入 tokens X ∈ R^{T×D}
        │
        ▼
   ┌─────────┐
   │  Router  │  ← 每个 token 独立计算 gating score（无 token 间依赖）
   │ (Gate)   │     输出: expert_idx[t] ∈ {1..E}, gate_score[t]
   └────┬─────┘
        │
        ▼
   ┌──────────────┐
   │ All-to-All    │  ← 依赖：必须等所有 token 的 router 决策完成
   │ Dispatch      │     通信模式：每 GPU 向其他 GPU 发送归属的 token 数据
   └──────┬────────┘
          │
    ┌─────▼─────┐
    │ Expert FFN │  ← 各 expert 独立计算（无 expert 间数据依赖！）
    │  (per GPU) │     每个 GPU 上多个 expert 的 FFN 可并发执行
    └─────┬─────┘
          │
          ▼
   ┌──────────────┐
   │ All-to-All    │  ← 依赖：必须等所有 expert 计算完成
   │ Combine       │
   └──────┬────────┘
          │
          ▼
    输出 tokens Y ∈ R^{T×D}
```

**并发可并行性分析**：

| 算子对 | 可并发？ | 数据依赖约束 | 并发条件 |
|--------|---------|-------------|---------|
| Router→All-to-All Dispatch | **串行** | Router 输出（expert_idx）是 All-to-All 的输入路由表 | 不可绕过 |
| Expert_i FFN ‖ Expert_j FFN | **完全并发** | 各 expert FFN 权重独立、输入 token 集不相交 | 需足够的 SM/计算单元 |
| All-to-All Combine ← Expert FFN | **串行** | All-to-All 需等所有 expert 完成（barrier 同步） | 可部分 overlap（见下） |
| Attention Layer ‖ MoE Layer（跨层） | **可流水线** | 仅层间依赖（L_i 的输出是 L_{i+1} 的输入） | 需 micro-batch 切分 |

#### 1.1.2 PROBE 的 Phase-Locked Co-Scheduling：计算-通信正交重叠

**笔记证据**: `paper_secs/secs_moe/PROBE.../PROBE-CO-BALANCING...md` §4.4 (score: 5623.0)

PROBE 提出**双轨执行模型（Dual-Track Execution Model）**，将 expert 预取的通信与主路径计算重叠：

```text
时间轴 ─────────────────────────────────────────────────────►

主轨道 (Main Track, Deterministic):
  Layer L-1:  [─ Attention ─][─ All-to-All Dispatch ─][─ Expert Compute ─][─ A2A Combine ─]
                                     ↑                        ↑
                                     │ 通信密集               │ 计算密集
辅助轨道 (Auxiliary Track):          │                        │
  Layer L (lookahead):    [─ Predict ─][─ Plan ─][─ P2P Expert Transfer ─]
                              ↑                         ↑
                         Gate-Initialized         利用主轨道计算密集期
                        Lookahead Predictor       的 PCIe/NVLink slack
                                                  传输 expert 权重
```

**注解**：
- **变量含义**：主轨道执行确定性 MoE 算子序列；辅助轨道异步执行 lookahead prediction → balance planning → expert prefetch 三阶段流水线
- **硬件并发条件**：需要 GPU 同时支持计算 kernel 和 P2P 通信（NVIDIA Hopper 的 TMA + 独立通信 SM 分区可实现）。主轨道计算密集期（Expert Compute）为辅助轨道提供"执行松弛（execution slack）"——此时 SM 忙于 GEMM，但 NVLink/PCIe 带宽空闲
- **split-phase transmission**：expert 权重传输被切分为与 All-to-All 正交的相位，避免与 All-to-All 争抢通信带宽
- **复杂度**：Lookahead Predictor 开销 <1% 推理延迟（Gate-Initialized 设计复用 frozen router + 轻量 residual MLP）
- **笔记来源**：PROBE 论文 §4.1-4.4，明确描述了 Phase-Locked Co-Scheduling 的 split-phase 机制

#### 1.1.3 Pre-gated MoE：打破 Router→Expert 串行依赖

**笔记证据**: `paper_secs/secs_moe/Pre-gated MoE.../Pre-gated-MoE...md` (score: 4126.5)

标准 MoE 的根本串行瓶颈：**router 决策必须先于 expert 计算**——因为不知道 token 去向哪个 expert，无法提前加载 expert 权重。

Pre-gated MoE 的解决方案：训练一个 **pre-gating function**（轻量预测器），在上一层就能预测当前层的 expert 选择：

```text
标准 MoE（串行）:
  Layer L-1 输出 → Router(L) → 等待 gating 决策 → 加载 Expert 权重 → Expert Compute
                  ↑_______________ 串行依赖 ______________↑

Pre-gated MoE（并发）:
  Layer L-1 输出 ──┬──► Router(L) → (验证用, off critical path)
                    │
                    └──► Pre-gate(L) → 提前加载 Expert 权重 → Expert Compute
                         ↑
                    在 Layer L-1 执行期间完成预测!
```

**注解**：
- **数据依赖突破**：pre-gating function 用 layer L-1 的 hidden state 预测 layer L 的 expert 选择，将原本串行的"router→load→compute"变为并行的"preload while computing L-1"
- **硬件收益**：expert 权重加载（HBM→SMEM/Register）可与上一层的 attention/FFN 计算完全重叠，消除 MoE 推理中 30-50% 的 expert I/O 等待时间
- **精度风险**：pre-gating 精度约 85-90% Top-K 准确率；预测错误时需回退到真实 router 结果（增加少量延迟）
- **笔记说明**：Pre-gated MoE 论文明确分析了 data dependency 瓶颈（"the latency to migrate activated experts from CPU to GPU incurs high performance overhead"）

#### 1.1.4 DeepSeek-V3 DualPipe：跨层计算-通信重叠

**笔记证据**: `paper_secs/secs_moe/DeepSeek-V3.../DeepSeek-V3-Technical-Report.md` (score: 1971.0)

DeepSeek-V3 的 DualPipe 机制实现了一种更细粒度的计算-通信流水线重叠：将每层的 attention/FNN 计算与 expert dispatch/combine 通信在**不同 micro-batch** 上并行执行。

```text
DualPipe 调度示例（2 micro-batch，EP=8）:

Time ──────────────────────────────────────────────►
Micro-batch 0:  [─ Attn ─][─ Dispatch ─][─ Expert ─][─ Combine ─][─ FFN ─]
Micro-batch 1:            [─ Attn ───────][─ Dispatch ─][─ Expert ─][─ Combine ─]
                              ↑               ↑             ↑
                         与 mb0 Dispatch  与 mb0 Expert  与 mb0 FFN
                         的通信重叠      计算重叠        通信重叠
```

**注解**：
- **变量含义**：DualPipe 将 forward pass 的计算和通信分别调度到不同 SM 分区，利用 CUDA graph + NCCL fusion 减少 kernel launch overhead
- **硬件要求**：需要 GPU 支持计算与通信的物理隔离——NVIDIA H800 通过 SM 分区（persistent kernel on 部分 SM + 通信在其余 SM/Copy Engine）实现无竞争重叠
- **Node-Limited Routing**：限制每 token 最多路由到 M 个节点，确保通信量可控，使计算-通信重叠接近 100%
- **笔记说明**：DeepSeek-V3 §3.2.1 描述了 DualPipe 和 node-limited routing 的配合机制

### 1.2 DiT：Diffusion Step 内部的 Attention Head 与 FFN 并发

**笔记证据**: `paper_secs/secs_effAttn/Hardware-Efficient_Attention.../Hardware-Efficient-Attention...md` (score: 7751.1), `knowledge_notes/算法知识笔记/MMDiT...md` (score: 262.0)

#### 1.2.1 DiT Block 内的并发机会

DiT（Diffusion Transformer）的单个 Transformer block 结构：

```text
输入 latent z ∈ R^{N×D}, timestep t
                │
    ┌───────────▼───────────┐
    │  adaLN (adaptive LN)  │  ← 根据 timestep embedding 调制 scale/shift
    │  z_norm = LN(z)       │
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │  Multi-Head Attention  │  ← H 个 attention head 可完全并行！
    │  z_attn = MHA(z_norm)  │     每 head 独立计算 Q/K/V 投影 + attention
    └───────────┬───────────┘
                │
    ┌───────────▼───────────┐
    │  adaLN + FFN          │  ← FFN 内部两个 FC 层串行，但可与下一 token 的 attention 流水线
    │  z_out = FFN(LN(z_attn))│
    └───────────────────────┘
```

**并发分析**：

| 并发粒度 | 可行性 | 硬件映射 |
|---------|--------|---------|
| **Head 级并发**（MHA 内） | ✅ 完全可行 | H 个 head 的 Q/K/V 投影可合并为单次 GEMM（W_QKV ∈ R^{D×3D}），各 head 的 attention score 计算通过 batch-GEMM 在 Tensor Core 上并行 |
| **Attention ‖ FFN**（同 token） | ❌ 串行 | FFN 依赖 attention 输出（残差连接前），有严格数据依赖 |
| **Attention(L_i) ‖ FFN(L_{i-1})**（跨层） | ⚠️ 有条件 | 若使用 micro-batch 流水线，当前 batch 的 L_i attention 可与上一个 batch 的 L_{i-1} FFN 并行 |
| **Denoising Step 间** | ❌ 严格串行 | Step t 的输出是 Step t-1 的输入——扩散模型的马尔可夫链性质决定 |

**注解**：
- **Multi-head 并发的硬件本质**：在 GPU 上，MHA 的多 head 并发并非真正的"并行多算子"，而是通过**增大矩阵维度**实现——将所有 head 的 Q/K/V 投影合并为一个大的 GEMM（batch size = H），利用 Tensor Core 的高吞吐一次性完成。这种"数据并行"式的并发不需要特殊的控制逻辑
- **DiT 的独特瓶颈**：每个 denoising step 都需要完整执行一次 Transformer forward pass（MHA + FFN），step 间**无法流水线化**（笔记未明确说明 step 间是否有可流水线的算子，但从扩散模型的数学性质可推断：z_t = f(z_{t-1}, t) 构成严格的时间序列依赖）
- **MMDiT 的多模态并发**（`knowledge_notes/算法知识笔记/MMDiT...md`）：文本和视频 token 共享 self-attention 但使用**独立 FFN**——这两个 FFN 可在不同 SM 分区上**完全并行**执行，因为它们的输入来自 attention 输出的 split 部分且无数据依赖

#### 1.2.2 Hardware-Efficient Attention 对并发的影响

**笔记证据**: `paper_secs/secs_effAttn/Hardware-Efficient_Attention.../Hardware-Efficient-Attention...md` (score: 7751.1)

GTA（Grouped-Tied Attention）和 GLA（Grouped Latent Attention）通过改变 attention 的算术强度（arithmetic intensity）影响并发效率：
- GTA 通过复用 K/V states 减少 KV cache 加载量，降低 memory bandwidth 压力 → 释放更多 memory bandwidth 给并发算子
- GLA 将 latent attention 设计为"parallel-friendly"——query 长度>1 时（如 speculative decoding），GLA kernel 比 FlashMLA 快 2×

**注解**：attention 的 memory-bandwidth-bound 特性意味着：当有其他算子并发时，attention 的 HBM 带宽需求会与其他算子的带宽需求竞争。减少 attention 的带宽占用（如 GTA 减半 KV cache）可间接提升并发效率

### 1.3 多模态：Vision + Text Encoder 并行编码与跨模态融合并发

**笔记证据**: `knowledge_notes/算法知识笔记/Hyper Attention Transformer Block (HATB...).md` (score: 56.4), `knowledge_notes/算法知识笔记/Three-Stage Cross-Modal Interaction...md` (score: 621.5), `paper_secs/secs_2026/79-Efficient Multimodal Serving.../1-Introduction.md` (score: 4254.8)

#### 1.3.1 Vision Encoder 与 Text Encoder 的并行编码

多模态模型的推理计算图具有天然的**前期并行性**：

```text
输入: Image I + Text Prompt T
         │                    │
    ┌────▼────┐          ┌───▼────┐
    │ Vision   │          │ Text    │
    │ Encoder  │          │ Tokenizer│
    │ (ViT)    │          │ + Embed  │
    └────┬─────┘          └───┬─────┘
         │                    │
    ┌────▼────┐               │
    │ Projector│               │
    │(MLP/Q-Former)            │
    └────┬─────┘               │
         │                    │
         └──────┬─────────────┘
                │
         ┌──────▼──────┐
         │ Concatenate  │  ← 此处为 barrier：必须等两路编码都完成
         │ + LLM Layers │
         └──────────────┘
```

**并发分析**：

| 编码阶段 | 可并发？ | 硬件映射 |
|---------|--------|---------|
| Vision Encoder ‖ Text Tokenizer+Embed | ✅ **完全并发** | Vision encoder（ViT，计算密集）→ GPU Tensor Core；Text tokenizer（查表操作，带宽密集）→ CPU 或 GPU L2 cache |
| Vision Encoder 内部的 patch 编码 | ✅ **数据并行** | 所有 patch 独立进入 ViT，可 batch 为单次 GEMM |
| Projector ← Vision Encoder | ❌ 串行 | Projector 依赖 vision encoder 输出 |
| Concatenate ← Vision+Text encoding | ❌ barrier | 必须等模态编码都完成 |

**注解**：
- **异构计算单元映射**：vision encoder（ViT，GEMM 为主）适合 GPU Tensor Core，text embedding（查表 + positional encoding）适合低延迟的 L1/L2 cache 操作。两者可同时在不同硬件单元上执行
- **Efficient Multimodal Serving**（`paper_secs/secs_2026/79-Efficient Multimodal Serving...`）观察到：传统 serving 系统按 monolithic 方式执行导致 GPU 利用率<10%，因为 vision encoder 和 text processing 的计算特性完全不同（计算密集 vs 访存密集），串行执行时一个单元总是空闲

#### 1.3.2 HATB：Self-Attention 与 Cross-Attention 的并行融合

**笔记证据**: `knowledge_notes/算法知识笔记/Hyper Attention Transformer Block (HATB...).md` (score: 56.4)

mPLUG-Owl3 的 HATB 设计是多模态算子级并发的典型范例——在单个 Transformer block 内将 **self-attention（文本内部）与 cross-attention（文本→视觉）并行执行**：

```text
HATB 计算流程（并行执行路径以 ‖ 标注）:

输入: H_text ∈ R^{L×D}, H_img ∈ R^{V×D}

Step 1: 共享 LayerNorm
  H_text_norm = LN(H_text)
  H_img_norm  = LN(H_img)         ← 复用同一 LN!

Step 2: 并行 Attention（关键！）
  ┌─────────────────────────┐   ┌──────────────────────────┐
  │ Self-Attention (文本)     │   │ Cross-Attention (文本→视觉) │
  │ Q = W_Q(H_text_norm)     │   │ Q = 复用 self-attn 的 Q!  │
  │ K,V = W_KV(H_text_norm)  │ ‖ │ K,V = W_img_KV(H_img_norm)│
  │ A_self = softmax(QK^T/√d)│   │ A_cross = softmax(QK_img^T)│
  │ H_self = A_self @ V      │   │ H_cross = A_cross @ V_img  │
  └──────────┬──────────────┘   └───────────┬──────────────┘
             │                               │
             └──────────┬────────────────────┘
                        │
            Step 3: Adaptive Gating
              g = Sigmoid(W_gate^T @ H_text)       ← 逐 token 门控
              H_fused = g * H_self + (1-g) * H_cross
```

**注解**：
- **并行执行的硬件基础**：self-attention 和 cross-attention 的 Q 投影共享（只需计算一次），K/V 投影虽然不同但形状匹配。在 GPU 上可通过**增大 batch dimension**（将 self-attn 和 cross-attn 的 K/V 投影合并为 batch-GEMM）实现并行
- **与 Flamingo 的对比**：Flamingo 串行地在 self-attention 后插入 cross-attention（先 self → 后 cross），而 HATB 并行执行两者再门控融合，理论上可将 cross-attention 延迟隐藏到 self-attention 的执行时间内
- **稀疏部署**：仅在 4/28 层插入 HATB，避免全层部署的额外参数和计算开销

#### 1.3.3 三阶段跨模态交互与逐阶段并发策略

**笔记证据**: `knowledge_notes/算法知识笔记/Three-Stage Cross-Modal Interaction...md` (score: 621.5)

VisiPruner 发现 MLLM 的跨模态交互遵循三阶段规律，不同阶段有不同的并发机会：

| 阶段 | 层范围 | 特征 | 并发含义 |
|------|--------|------|---------|
| **Shallow**（浅层） | Layer 1-8 | 视觉和文本独立演化，无实质跨模态融合 | 视觉 token 的 self-attention 可跳过（mask 后性能几乎不变）→ 节省的 SM 周期可供其他算子使用 |
| **Middle**（中层） | Layer 9-23 | 稀疏跨模态融合突然发生，仅 ~10/576 个视觉 token 关键 | 可对非关键视觉 token 做 aggressive pruning → 减少后续层的 KV cache 占用 |
| **Deep**（深层） | Layer 24-32 | 视觉信息已集成到文本表示，视觉 token 产生噪声 | **Vision Exit**：深层完全丢弃视觉 token，仅做文本 self-attention → 释放 SM 和 memory bandwidth |

**注解**：三阶段规律意味着：对于深层（约 1/3 的总层数），视觉相关算子可**完全消除**。这减少了 text+visual 并发时的资源竞争——深层只需为文本处理分配计算单元，视觉的 memory bandwidth 占用降为零

### 1.4 Video：Spatial + Temporal Stream 并行处理

**笔记证据**: `paper_secs/secs_video_image/XStreamVGGT.../2-Related-Work.md` (score: 4015.6), `knowledge_notes/算法知识笔记/MMDiT...md` (score: 262.0)

#### 1.4.1 Video 推理的并发 DAG

Video 模型推理涉及三个维度的处理：spatial（每帧内的空间）、temporal（帧间时序）、以及 patch-level（每帧被切为多个 patch）。

```text
输入: Video V ∈ R^{T×H×W×C}（T 帧）

Step 1: Patch 化 + 嵌入（完全并发）
  ┌──────────────────┐   ┌──────────────────┐        ┌──────────────────┐
  │ Frame 0 patches   │   │ Frame 1 patches   │        │ Frame T-1 patches │
  │ PatchEmbed(P_0,j) │ ‖ │ PatchEmbed(P_1,j) │ ‖ ... ‖ │ PatchEmbed(P_T-1,j)│
  └──────┬───────────┘   └──────┬───────────┘        └──────┬───────────┘
         │                      │                             │
         └──────────────────────┼─────────────────────────────┘
                                │
                    ┌───────────▼───────────┐
                    │  Spatial Attention     │  ← 每帧内 patch 间 attention
                    │  (每帧独立，T 路并发!)   │     可 batch 为单次 GEMM
                    └───────────┬───────────┘
                                │
                    ┌───────────▼───────────┐
                    │  Temporal Attention    │  ← 跨帧同位置 patch 间 attention
                    │  (需要所有帧 spatial   │     依赖：必须等所有帧 spatial 完成
                    │   特征完成 → barrier)   │
                    └───────────┬───────────┘
                                │
                    ┌───────────▼───────────┐
                    │  FFN (per token)       │  ← token 独立计算
                    └────────────────────────┘
```

**并发分析**：

| 算子 | 并发粒度 | 可行性 | 硬件瓶颈 |
|------|---------|--------|---------|
| Patch Embed（T×P² 个 patch） | patch 级 | ✅ 完全数据并行 | 无依赖，可最大化 GPU occupancy |
| Spatial Attention（T 帧） | 帧级 | ✅ T 路并发 | 每帧 attention 独立，batch 为 T×H×head 的 GEMM |
| Temporal Attention ← Spatial Attention | — | ❌ 严格 barrier | 时序 attention 需要所有帧的 spatial 特征就绪 |
| Spatial ‖ Temporal（factorized attention） | block 级 | ⚠️ 可流水线 | 对已完成 spatial 的帧启动 temporal，形成 wavefront |
| FFN（per token）‖ Attention（下一 block） | 跨 block | ✅ 可流水线 | 与 MoE 类似，micro-batch 级流水线 |

#### 1.4.2 Video 并发的硬件约束

**注解**：
- **Memory bandwidth 压力**：T 帧 × P² patches 的 KV cache 极大（如 T=16, P=14, D=1024 → KV cache ≈ 16×196×1024×2×2 bytes ≈ 25 MB per layer, FP16），全部保持 on-chip 不现实
- **Spatial-temporal factorization 策略**：将 full 3D attention 分解为先 spatial（per-frame）后 temporal（cross-frame），两阶段独立 batch → 减少单次 GEMM 的 memory footprint
- **MMDiT 中的视频处理**（`knowledge_notes/算法知识笔记/MMDiT...md`）：文本和视频共享 self-attention 但使用**独立 FFN**——视频 FFN 与文本 FFN 完全可并行
- **笔记未明确说明**：Video 模型的 specific micro-operator concurrency design（如是否使用 flash-attention for video、是否支持 frame-dropping 等）——这些在 vault 笔记中未充分覆盖

## 2. 数据依赖 DAG 综合分析：哪些可并发、哪些必须串行

基于上述四种模型负载的分析，从数据依赖 DAG 角度总结算子级并发的可行性边界：

### 2.1 可以并发的算子类

| 并发类型 | 模型 | 具体算子对 | 并发模式 | 数据依赖条件 |
|---------|------|-----------|---------|-------------|
| **无数据依赖并发** | MoE | Expert_i FFN ‖ Expert_j FFN | 空间并行（不同 SM） | 各 expert 输入 token 集互不相交 |
| **无数据依赖并发** | DiT | Head_i Attention ‖ Head_j Attention | 数据并行（batch-GEMM） | 各 head 的 Q/K/V 投影独立 |
| **无数据依赖并发** | 多模态 | Vision Encoder ‖ Text Embedding | 异构并行（不同硬件单元） | 两模态编码独立 |
| **无数据依赖并发** | Video | Frame_i Spatial Attn ‖ Frame_j Spatial Attn | 数据并行 | 各帧 spatial 特征独立 |
| **无数据依赖并发** | MMDiT | Text FFN ‖ Video FFN | 空间并行 | 共享 attention 输出后 split，各自独立 |
| **预测驱动的并发** | MoE | Expert Prefetch ‖ Layer_{L-1} Compute | 时间重叠（prefetching） | 通过 pre-gating/lookahead 提前预测 expert 选择 |
| **流水线并发** | 全部 | Layer_i Compute ‖ Layer_{i-1} Compute（不同 micro-batch） | 流水线并行 | micro-batch 间无依赖 |
| **通信-计算重叠** | MoE | All-to-All ‖ Expert Compute（不同 token 组） | 相位正交重叠 | split-phase 设计避免带宽竞争 |
| **模态内并行融合** | 多模态 | Self-Attention ‖ Cross-Attention（HATB） | 并行执行 + 门控融合 | 共享 Q 投影，K/V 独立 |

### 2.2 必须串行的依赖链

| 串行瓶颈 | 模型 | 依赖链 | 串行化原因 |
|---------|------|--------|-----------|
| **Router→Expert** | MoE | Router 决策 → All-to-All Dispatch → Expert Compute | Routing decision 是 expert 选择的唯一依据 |
| **Step 间时序依赖** | DiT | Denoising Step t → Step t-1 | 扩散过程的马尔可夫性：z_t = f(z_{t-1}, ε_θ(z_{t-1}, t)) |
| **Attention→FFN**（同 token） | 全部 Transformer | MHA(z) → FFN(z_attn) | 残差连接：FFN 的输入依赖 MHA 的输出 |
| **Encoder→Fusion** | 多模态 | Vision/Text Encoder → Cross-Modal Fusion | Fusion 需要两模态的完整编码 |
| **Spatial→Temporal** | Video | Spatial Attention → Temporal Attention | Temporal attention 需要所有帧的 spatial 特征就绪 |
| **All-to-All Combine** | MoE | Expert Compute → A2A Combine | NCCL collective 的 barrier 语义——必须所有 rank 完成 expert 计算 |

## 3. 并发对硬件体系结构的要求

**笔记证据**: `knowledge_notes/硬件知识笔记/On-Chip Ring Network for NMP...md` (score: 615.5), `knowledge_notes/硬件知识笔记/Attention Buffer...md` (score: 577.0), `paper_secs/secs_multimodal_kernel/Task-Based Tensor Computations.../Task-Based-Tensor-Computations...md` (score: 3582.8)

### 3.1 并行计算单元数量需求

| 并发场景 | 所需并行单元 | 具体硬件映射 |
|---------|------------|-------------|
| MoE 多 Expert 并发（k=2） | ≥2 个独立的 GEMM 单元 | GPU：至少 2 个 SM 分区各自运行一个 expert GEMM；Stratum NMP：≥2 个 PU 各执行一个 expert |
| DiT MHA（H=16 heads） | 1 个 Tensor Core（batch-GEMM） | H100 Tensor Core 可在单 cycle 内处理 128×128 MMA，head 维度作为 batch 维 |
| 多模态 Vision+Text 并行 | 异构：Tensor Core（ViT）+ 轻量 CUDA core（embedding） | 需 GPU 支持 concurrent kernel execution（不同 stream） |
| Video T 帧 Spatial Attn | T× 的 batch 能力 | T 较小时（≤16）可 batch，T 较大时需 streaming 或 wavefront 调度 |
| Cypress task-based 并行 | 多 warp 独立调度 | Hopper 架构每个 SM 有 4 个 warp scheduler，需 TMA + Tensor Core 异步流水线 |

### 3.2 片上存储划分

```text
                HBM (high bandwidth memory)
                │  80 GB, 3.35 TB/s (H100)
    ┌───────────┼───────────┐
    │           │           │
    ▼           ▼           ▼
┌───────┐  ┌───────┐  ┌───────┐
│ L2     │  │ L2     │  │ L2     │  ← 50 MB, shared across SMs
│ Cache  │  │ Cache  │  │ Cache  │
└───┬───┘  └───┬───┘  └───┬───┘
    │          │          │
    ▼          ▼          ▼
┌───────┐  ┌───────┐  ┌───────┐
│ SM_0   │  │ SM_1   │  │ SM_N   │
│ SRAM:  │  │ SRAM:  │  │ SRAM:  │  ← 256 KB per SM (H100)
│ 228 KB │  │ 228 KB │  │ 228 KB │     需在并发算子间划分
│ Reg:   │  │ Reg:   │  │ Reg:   │
│ 65536  │  │ 65536  │  │ 65536  │     需为各算子分配 register
└────────┘  └────────┘  └────────┘
```

**并发对片上存储的竞争**：

| 并发场景 | SMEM 划分策略 | Register 分配 |
|---------|-------------|--------------|
| MoE Expert ‖ Expert（同 SM） | 各 expert 的 input tile + weight tile 分占 SMEM | 各 expert 至少需要 128 registers/warp（MMA tile） |
| Attention ‖ FFN（跨 micro-batch） | Attention 的 KV tile 与 FFN 的 activation tile 分区 | 需 warp specialization：部分 warp 做 attn，部分做 FFN |
| Vision ‖ Text Encoder（异构） | Vision 的 patch tile 与 text 不冲突（不同 SM） | 各自独立分配 |
| Video Spatial ‖ Temporal（wavefront） | 已完成 spatial 的帧释放 SMEM 给 temporal | 动态分配，需 software-managed cache |

**HNLPU 的片上 Attention Buffer**（`knowledge_notes/硬件知识笔记/Attention Buffer...md`）提供了一个专门设计的硬件方案：320MB SRAM 专用于 KV Cache，20,000 bank 提供 80 TB/s 带宽。这种**专用片上存储**消除了并发算子间的 memory bandwidth 竞争——attention 的 KV Cache 访问不占用主 memory bus。

### 3.3 控制逻辑的并发调度要求

| 硬件模块 | 功能 | 对算子并发的支持 |
|---------|------|---------------|
| **Warp Scheduler**（GPU SM 内） | 每 cycle 选择 ready warp 发射指令 | 需区分不同算子的 warp group，支持 warp-level 优先级 |
| **Tensor Memory Accelerator (TMA)** | 异步 HBM→SMEM 数据搬运 | 允许数据加载与计算重叠（Cypress 的 warp-specialized kernel 核心依赖） |
| **Copy Engine** | 独立于 SM 的 DMA 引擎 | 支持 P2P expert weight transfer 与 SM 计算并发（PROBE 的 Phase-Locked Co-Scheduling） |
| **MIG (Multi-Instance GPU)** | 物理分区 GPU 为独立实例 | 可将不同算子类型分配到不同 MIG 实例，实现物理隔离的并发 |
| **NMP Ring Router**（Stratum） | 片上环形网络，含 aggregator for in-situ reduction | 支持 all-gather/reduce-scatter 与 expert GEMM 的流水线重叠 |
| **Scoreboard** | 跟踪寄存器写后读依赖 | 多算子并发时需跟踪更多 in-flight 指令的依赖关系 |

### 3.4 访存带宽需求

并发算子对 memory bandwidth 的竞争是最关键的硬件约束：

$$B_{\text{total}} = \sum_{i} B_i^{\text{compute}} + B_{\text{communication}}$$

当 $B_{\text{total}}$ 超过 HBM bandwidth（H100: 3.35 TB/s）时，算子并发反而降低性能（bandwidth contention 导致各算子都 starving）。

| 并发组合 | 带宽需求估算 (H100) | 是否可行 |
|---------|-------------------|---------|
| Vision Encoder (ViT, ~1 TB/s) ‖ Text Embedding (~0.1 TB/s) | ~1.1 TB/s | ✅ 远低于 3.35 TB/s |
| Expert FFN (~2 TB/s) ‖ P2P Expert Transfer (~0.4 TB/s NVLink) | ~2.4 TB/s from HBM + 0.4 TB/s NVLink | ⚠️ 接近 HBM 上限，需 split-phase |
| Spatial Attn (T=16, ~2.5 TB/s) | ~2.5 TB/s | ⚠️ 依赖 KV cache 是否在 L2 |
| Expert FFN ‖ Expert FFN (2 experts) | ~3.5 TB/s | ❌ 超 HBM 带宽，必须串行或降低精度 |

**注解**：带宽竞争是限制细粒度算子并发的根本硬件瓶颈。笔记中的 PROBE 通过 split-phase transmission 解决此问题——将 expert transfer 安排在计算密集期（此时 HBM 带宽被计算占用但 NVLink 空闲）。Stratum 的 NMP 方案通过将 expert 权重放在 DRAM（近存计算）避免 HBM 带宽竞争。

2. **Video spatial-temporal wavefront 调度的具体实现**：笔记中未找到 video transformer 的 wavefront scheduling 伪代码或具体算法。上述 wavefront 分析基于对 spatial-temporal attention factorization 的一般理解推断。

5. **片上存储划分的具体数值**：上述 SMEM/Register 划分策略中的具体数值（如"expert 至少需要 128 registers/warp"）基于 kernel 设计的一般原理推断，笔记中未提供 MoE expert kernel 在 H100 上的精确 register 分配数据。
