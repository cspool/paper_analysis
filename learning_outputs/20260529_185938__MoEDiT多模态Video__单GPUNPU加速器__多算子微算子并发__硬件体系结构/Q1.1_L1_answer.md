## 一、方法细节（数据流/架构）—— 主内容

### 方法1: MoE 模型的单请求推理计算流程

**笔记证据**: `knowledge_notes/算法知识笔记/MoE (Mixture of Experts _ 混合专家模型).md` (score: 主), `knowledge_notes/算法知识笔记/Gate Network _ Expert Router.md` (score: 主), `knowledge_notes/系统知识笔记/Memory-Bandwidth-Bound Decode in MoE.md` (score: 主)

#### 1.1 算法 Pipeline 伪代码

MoE 模型（如 Mixtral-8×7B、DeepSeek-V3）在 decoder-only LLM 的每个 Transformer Block 中将标准 FFN 替换为 MoE 层。以下给出单请求推理中第 l 层的计算流程：

```
Algorithm: MoE Single-Request Inference (第 l 层)

Input:  hidden_state h ∈ R^{d_model}      // 来自 Attention 输出的单个 token
        Expert weights {W_e1, W_e2, ..., W_eE}  // E 个 expert FFN 权重
        Gate weight W_g ∈ R^{d_model × E}       // 门控网络权重

Step 1: Gate Network 前向
    logits = h @ W_g                       // [d_model] @ [d_model, E] → [E]
    probs  = Softmax(logits)               // [E], sum(probs) = 1.0

Step 2: Top-K 选择
    topk_idx, topk_vals = ArgTopK(probs, k)   // k = 1 (DeepSeek-V3) 或 2 (Mixtral)
    norm_probs = topk_vals / sum(topk_vals)   // 重新归一化

Step 3: Expert FFN 计算（稀疏激活）
    output = zeros(d_model)
    for e_idx, e_prob in zip(topk_idx, norm_probs):
        // 每个 expert FFN: h → Linear₁ → Activation → Linear₂
        e_out = ExpertFFN_e(h)              // [d_model] → [d_ff] → [d_model]
        output += e_prob * e_out

Output: MoE_layer_output ∈ R^{d_model}
```

**注解**:
- **变量含义**: `h` 是经过 Attention + LayerNorm 后的中间隐藏状态；`W_g` 是小型可学习矩阵（如 Mixtral: d_model=4096 → E=8）；`ExpertFFN_e` 是独立的全连接网络（如 SwiGLU 结构: d_model → d_ff=14336 → d_model）
- **复杂度分析**: 每个 token 仅计算 k 个 expert（如 top-2），计算量 ≈ k × 2·d_model·d_ff FLOPs，相比 dense FFN 的 E × 2·d_model·d_ff 节省 (E-k)/E 的计算
- **数据依赖**: Gate Network 必须先生成 routing 决策（Step 1→2），然后才能执行 expert FFN（Step 3）——这是严格的串行依赖（serialization bottleneck）
- **并发可行性**: 被选中的 k 个 expert 之间无数据依赖（各自独立处理同一 h），可并行计算（expert parallelism）

#### 1.2 硬件瓶颈分析：Expert 路由与 GPU Memory Hierarchy 的交互

**笔记证据**: `knowledge_notes/系统知识笔记/Memory-Bandwidth-Bound Decode in MoE.md` (score: 主), `knowledge_notes/硬件知识笔记/GPU Memory Hierarchy (HBM vs SRAM).md` (score: 主)

在单请求 decode 阶段（每 iteration 生成 1 token），MoE 推理面临严重的 memory-bandwidth 瓶颈：

```
┌── MoE Decode Memory Bandwidth 时序分析 ────────────────────────┐
│                                                                  │
│  Decode iteration 时间分解（Qwen2-57B, B=16, H200）:             │
│                                                                  │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │  组件                    │ 时间(ms) │ 占比  │ 瓶颈类型    │   │
│  ├──────────────────────────────────────────────────────────┤   │
│  │  Attention (FlashAttn)   │   3.2    │  19%  │ Memory-bound│   │
│  │  Gate Network + Router   │   0.8    │   5%  │ Compute     │   │
│  │  Expert Weight Load(HBM) │   7.1    │  42%  │ ← 核心瓶颈   │   │
│  │  Expert FFN Computation  │   4.5    │  27%  │ Compute     │   │
│  │  Other (norm, residual)  │   2.0    │  12%  │ —           │   │
│  ├──────────────────────────────────────────────────────────┤   │
│  │  Total                   │  16.8    │ 100%  │             │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  Arithmetic Intensity 分析:                                       │
│  - AI = B × k × 2·d_model·d_ff / (active_experts × 2·d_model·d_ff × 2B)│
│  - Qwen2-57B (B=16, k=8, N=64): AI ≈ 16×8/64 = 2 FLOP/byte     │
│  - H200 ridge point: 67 TFLOPS / 3.35 TB/s ≈ 20 FLOP/byte       │
│  - AI (2) ≪ ridge point (20) → deep memory-bound                 │
└──────────────────────────────────────────────────────────────────┘
```

**注解**:
- **HBM→SMEM 数据搬运**: 每个 active expert 的权重（如 d_model=4096, d_ff=14336 → ~112 MB BF16）必须从 HBM 经 L2 cache 搬运至 SMEM，再加载到寄存器供 Tensor Core 计算
- **42% 瓶颈本质**: 单 token 推理中每个 expert FFN 的 arithmetic intensity 极低（~2 FLOP/byte），HBM bandwidth（H200: 3.35 TB/s）成为硬上限，即使 Tensor Core 有 67 TFLOPS 算力也无法充分利用
- **Gate Network 的 memory 开销**: 路由计算本身（d_model × E 线性层）是 compute-bound，但结果影响哪些 expert 权重需要从 HBM（或 CPU memory）加载——错误的路由预测导致 cache miss → PCIe 延迟 ~10ms/expert（PCIe 4.0: ~32 GB/s）
- **数据流路径**: `HBM → L2 Cache (40-50MB, ~12 TB/s) → SMEM (228KB/SM, ~19 TB/s) → Register File → Tensor Core MMA`

### 方法2: DiT 模型的单请求推理计算流程

**笔记证据**: `knowledge_notes/算法知识笔记/Diffusion Transformer (DiT).md` (score: 主), `knowledge_notes/算法知识笔记/Denoising Diffusion Probabilistic Model.md` (score: 主), `paper_secs/secs_2026/20-DSV/2.1-Video-DiT.md` (score: 主)

#### 2.1 算法 Pipeline 伪代码

DiT（Diffusion Transformer）将扩散模型的 U-Net 骨干替换为 ViT Transformer，推理过程是迭代去噪循环：

```
Algorithm: DiT Single-Request Inference (图像生成, T=50 步 DDIM)

Input:  text_prompt, T=50 (去噪步数), latent_shape = [H, W, C]

Step 0: 文本编码（一次性）
    text_emb = TextEncoder(text_prompt)        // [L_txt, d], L_txt < 120

Step 1: 噪声初始化
    z_T ~ N(0, I)                              // [H×W, d], pure noise

Step 2: 去噪循环
    for t = T, T-1, ..., 1:
        // —— Timestep Embedding ——
        t_emb = SinusoidalEmbedding(t)          // [d_t]

        // —— DiT Block 堆叠（L 层） ——
        h = z_t + PatchEmbed(z_t)               // [N_patches, d]
        for block in range(L):
            // adaLN-Zero modulation
            (γ₁,β₁,γ₂,β₂,α₁,α₂) = MLP(t_emb + text_emb)
            
            // Self-Attention（O(N²) 瓶颈）
            h_norm = LayerNorm(h) * (1+γ₁) + β₁
            Q,K,V = Linear_Q(h_norm), Linear_K(h_norm), Linear_V(h_norm)
            // Q,K,V ∈ R^{H_heads × N × d_head}
            A = Softmax(Q @ K^T / √d_head)      // [H_heads, N, N]
            h_attn = α₁ ⊙ (A @ V)
            h = h + h_attn
            
            // Cross-Attention（text conditioning, O(N·L_txt)）
            h_norm2 = LayerNorm(h)
            Q_txt = Linear_Q(h_norm2)            // [N, d]
            K_txt,V_txt = Linear_KV(text_emb)    // [L_txt, d]
            h_cross = Softmax(Q_txt @ K_txt^T / √d) @ V_txt
            h = h + h_cross
            
            // FFN（O(N·d·d_ff)）
            h_norm3 = LayerNorm(h) * (1+γ₂) + β₂
            h = h + α₂ ⊙ FFN(h_norm3)

        // —— 噪声预测 ——
        ε_pred = OutputHead(h)                  // [N, d] → [H,W,C]

        // —— DDIM Step ——
        z_{t-1} = √(α_{t-1}) · (z_t - √(1-α_t)·ε_pred)/√(α_t) + √(1-α_{t-1})·ε_pred

Step 3: VAE Decode
    image = VAE.decode(z_0)

Output: image ∈ R^{H_img × W_img × 3}
```

**注解**:
- **变量维度**: Wan2.1-1.3B 每步 N≈30K tokens; d_model=1536; L=28 layers; self-attention 占单步 52.75T FLOPs（SLA 论文）
- **Self-Attention O(N²)**: 30K tokens → attention matrix [30K, 30K] ≈ 900M entries → 每头 BF16 需 ~1.8GB，无法放入 SMEM（仅 228KB/SM），必须以 tiled 方式流式加载
- **迭代串行依赖**: denoising step t 的输出 z_{t-1} 是 step t-1 的输入——T=50 步严格串行，形成"计算单元利用率断续"的问题：每步内 Attention burst（compute-heavy）→ FFN burst（memory-heavy）交替
- **Dataflow 路径**: `HBM (z_t, weights) → L2 → SMEM(Q,K,V tiles)→ Tensor Core (MMA for Q@K^T)→ SMEM (A) → HBM → SMEM (A@V) → HBM (h)`

#### 2.2 硬件瓶颈分析：迭代去噪对计算单元利用率的影响

```
┌── DiT Denoising 步内时间分解（Wan2.1-1.3B, N=30K, H100） ────────────┐
│                                                                          │
│  Self-Attention (O(N²)):  52.75T FLOPs/step (≈90% 单步 FLOPs)           │
│    ├── Q@K^T MatMul:     ~26.4T FLOPs  [compute-bound, Tensor Core]      │
│    ├── Softmax:           ~0.1T FLOPs   [memory-bound, element-wise]     │
│    └── A@V MatMul:        ~26.4T FLOPs  [compute-bound, Tensor Core]      │
│                                                                          │
│  Cross-Attention (O(N·T)): ~0.5T FLOPs  [memory-bound, N≫T]              │
│  FFN (O(N)):              ~2.0T FLOPs   [memory-bound, low CI]           │
│                                                                          │
│  关键发现（DSV 论文 Fig.2）：200K tokens 时 self-attention 占前向 92%    │
│                                                                          │
│  硬件利用率问题：                                                         │
│  - Attention burst 期间：Tensor Core 利用率 ~70-80%（大 MatMul 尺寸）    │
│  - FFN 期间：Tensor Core 利用率骤降至 ~15-20%（memory-bound GEMV）       │
│  - 步间过渡：Kernel launch overhead + HBM→SMEM 重新加载（~50μs/步）     │
│  - 总体 MFU ≈ 35-45%（远低于 dense LLM 的 50-60%）                       │
└──────────────────────────────────────────────────────────────────────────┘
```

**注解**:
- **计算模式交替**: DiT 推理在 "heavy compute (Attention MatMul)" 和 "light compute (FFN GEMV)" 间交替，导致 GPU 的 Tensor Core 利用率锯齿状波动——这是 DiT 推理 MFU 偏低的根本原因
- **T=50 步串行**: 即使单步可优化，50 步的串行壁垒使得总延迟 = 50 × 单步延迟，DiT 推理比同参数 LLM 慢约 50×
- **与 MoE 的对比**: DiT 的瓶颈是 Attention O(N²) 而非 FFN（与 LLM 相反），因为 N=30K-100K token 远超 LLM 的典型 context length

### 方法3: 多模态模型的单请求推理计算流程

**笔记证据**: `knowledge_notes/算法知识笔记/Multimodal Inference Pipeline Stages (Encode _ Prefill _ Decode).md` (score: 主), `knowledge_notes/算法知识笔记/Cross-Attention (CroAttn) LMM Architecture.md` (score: 主), `knowledge_notes/算法知识笔记/Vision-Language Model (VLM).md` (score: 主)

#### 3.1 算法 Pipeline 伪代码（EPD-Serve 三阶段）

```
Algorithm: Multimodal VLM Single-Request Inference

Input:  Image I ∈ R^{H×W×3}, Text prompt T

// ========== Stage 1: Encode ==========
// 视觉编码器（ViT）将原始图像编码为 visual tokens
V_m = VisionEncoder(I)                         // [N_img, d_vit]
// 例：openPangu-7B-VL: ViT 0.7B, N_img = 576 (24×24 patches)

// ========== Stage 2: Prefill ==========
// 文本 tokenization + embedding
V_t = TokenEmbed + TextEmbed(T)                // [N_txt, d_llm]

// Visual→LLM 投影
V_m_proj = Projector(V_m)                      // [N_img, d_llm]
// Projector: MLP 或 Q-Former 或 Cross-Attention adapter

// 拼接输入序列
input_seq = Concat([V_m_proj, V_t])           // [N_img + N_txt, d_llm]

// LLM 首 token 生成 + KV Cache 构建
O_1, KV_1 = LLM_Forward(input_seq)             // Prefill: 一次处理所有 token
// KV_1 ∈ R^{L_layers × H_heads × (N_img+N_txt) × d_head}

// ========== Stage 3: Decode (自回归) ==========
for i = 1 to max_new_tokens:
    O_{i+1}, KV_{i+1} = LLM_Forward(O_i, KV_i) // Decode: 仅处理新 token
    // KV_{i+1}: 将 O_i 的 K/V 追加到历史 cache
    if O_{i+1} == <eos>: break

Output: generated_text
```

**注解**:
- **三阶段计算异质性**: Encode（ViT forward, compute-heavy, 0.6-6B params）→ Prefill（KV cache 构建, memory+compute 混合, O((N_img+N_txt)²)）→ Decode（逐 token GEMV, memory-bound, O(1) per token）
- **Visual tokens 占比**: images 贡献 98-99% 的输入 tokens（LLaVA-OneVision: ~6272 visual vs 109 text tokens），LLM backbone 占 99.35% 参数
- **CroAttn vs DecOnly 架构对比**: CroAttn（Llama3.2-11B: 4/40 cross-attention layers）prefill 复杂度 O(N_t² + N_t·N_img)；DecOnly（LLaVA-1.5: 全部 self-attention layers）prefill 复杂度 O((N_t+N_img)²) — CroAttn 在大视觉输入下显著更高效
- **Image encoding 瓶颈**: CroAttn 模型中 79% TTFT 来自 vision encoding（Insight 1, ModServe 论文），Image token 比例增加时 LLM prefill 反而减少（Insight 7）

#### 3.2 硬件瓶颈分析：跨模态融合在异构计算单元上的映射

```
┌── 多模态推理硬件映射 ────────────────────────────────────────┐
│                                                                │
│  ┌─ ViT Encoder ────────────────────────────────────────┐     │
│  │  计算模式: Conv2D (patch embedding) + Multi-Head SA   │     │
│  │  最优硬件: Tensor Core (MatMul) + CUDA Core (Conv)    │     │
│  │  瓶颈: 大分辨率图像 → N_img 膨胀 → ViT 延迟线性增长  │     │
│  │  实例: ViT-L/14 (0.3B) 编码 336×336 → 576 tokens/帧  │     │
│  └──────────────────────────────────────────────────────┘     │
│                           ↓ (Visual Features)                  │
│  ┌─ Projector (跨模态映射) ─────────────────────────────┐     │
│  │  计算模式: 轻量 MLP 或 Q-Former Cross-Attention       │     │
│  │  最优硬件: CUDA Core（小 MatMul）                     │     │
│  │  瓶颈: 通常不构成瓶颈（参数 <1% total）               │     │
│  └──────────────────────────────────────────────────────┘     │
│                           ↓ (Projected Tokens)                 │
│  ┌─ LLM Decoder ────────────────────────────────────────┐     │
│  │  Prefill: compute-bound (O((N_img+N_txt)²) Attention) │     │
│  │  Decode:  memory-bound (逐 token GEMV)                │     │
│  │  瓶颈: KV Cache 随 visual tokens 数量线性增长         │     │
│  │  实例: 6272 visual tokens → KV cache ~2GB/request     │     │
│  └──────────────────────────────────────────────────────┘     │
│                                                                │
│  跨模态异构映射挑战:                                            │
│  - ViT 偏好低精度 Tensor Core（INT8/FP8）, LLM 偏好 BF16       │
│  - ViT 的 Conv-heavy 与 LLM 的 MatMul-heavy 交替执行           │
│    → SM 在两种计算模式间切换开销（context switch cost）        │
│  - 视觉 token 的 memory footprint 与文本 token 的 latency       │
│    sensitivity 矛盾 — 无法用同一硬件调度策略优化两者            │
└────────────────────────────────────────────────────────────────┘
```

**注解**:
- **异构计算映射**: ViT encoder 在 NPU（如 Ascend 910B 的 AI Core）上可能更高效（卷积 + 小 attention），而 LLM decoder 更适合 GPU Tensor Core（大 MatMul）；跨模态推理在单 GPU 上被迫串行执行两者
- **Memory 分区**: ViT encoder 需要较大 SMEM 用于 patch embedding 卷积（~128KB），而 LLM prefill 需要最大 SMEM 给 FlashAttention tiles（~164KB）——两者无法同时 resident 在同一 SM
- **KV Cache 压力**: 多模态推理的 KV cache 比纯文本大 10-100×（visual tokens 贡献），HBM 容量和带宽双重受压

#### 4.1 Video DiT 推理 Pipeline 伪代码

Video DiT 的核心特征是将视频作为 3D spacetime volume 处理：

```
Algorithm: Video DiT Single-Request Inference (CogVideoX, flow matching)

Input:  text_prompt, F_frames, latent_shape = [F, H, W, C]

Step 0: 文本编码
    text_emb = TextEncoder(text_prompt)          // [L_txt, d], L_txt < 120

Step 1: VAE 3D Encoding
    video_latent = VAE_3D.encode(video_frames)   // [F, H/8, W/8, C]
    N = F × (H/8) × (W/8)                         // F=49, H/8=12, W/8=12 → N≈7K

Step 2: 噪声初始化 + 去噪循环（T 步）
    z_T ~ N(0, I)                                // [N, d]
    for t = T, T-1, ..., 1:
        // —— Video DiT Block — 
        for block in range(L):
            // Full 3D Self-Attention（所有空间位置 × 所有帧）
            Q,K,V = Proj_QKV(z_t)               // [H_heads, N, d_head], N = F×H×W
            // N 可达 100K+ (16×96×96 = 147K tokens)
            A = Softmax(Q @ K^T / √d_head)       // [H_heads, N, N]
            // A 的规模: H_heads × 147K × 147K = H_heads × 21.6G entries!
            h = A @ V
            
            // Cross-Attention (text conditioning)
            h = h + CrossAttn(h, text_emb)
            // FFN
            h = h + FFN(h)
        
        // Flow matching velocity prediction
        v_pred = OutputHead(h)
        z_{t-1} = z_t - Δt · v_pred

Step 3: VAE 3D Decode
    video = VAE_3D.decode(z_0)

Output: video_frames ∈ R^{F × H_img × W_img × 3}
```

**注解**:
- **Token 数膨胀**: 6 秒视频 @ 8 FPS → F=49, 空间 96×96 → 每帧 9216 tokens, 总 token N ≈ 49×9216 = 451K tokens — 远超图像 DiT 的 30K
- **Full 3D Attention 复杂度**: O(N²) = O((F×H×W)²)，100K tokens → ~10G 个 QK pair per head → BF16 下 ~20GB/head → 完全无法 fit 在任何 on-chip memory
- **计算时间占比**（DSV 论文 Fig. 2）: 200K tokens 时 self-attention 占 forward 92%、backward 93%
- **与 spatial-temporal attention 的 trade-off**: Interleaved spatial-temporal(O(F·N_s²+N_s·F²)) 更高效但质量损失；full 3D attention 质量最好但计算爆炸

#### 4.2 LVLM (Large Video Language Model) 推理 Pipeline

```
Algorithm: LVLM Single-Request Inference (Video Understanding)

Input:  Video, Text query, F_max frames

Step 1: 帧采样
    frames = UniformSample(video, fps=1.0, max_frames=F_max)
    // 30min video @ 1fps = 1800 frames

Step 2: 逐帧视觉编码
    visual_tokens = []
    for frame in frames:
        patches = ViT.encode(frame)             // [N_patches, D_vit]
        // 336×336 → 24×24 patches = 576 tokens/frame
        projected = Projector(patches)           // [N_patches, D_llm]
        visual_tokens.append(projected)
    
    // 总 visual tokens = F × N_patches
    // 1800 frames × 576 = 1,036,800 tokens → 超出现有上下文窗口!

Step 3: Token 拼接 + LLM Decode
    input_seq = Interleave(visual_tokens, text_tokens)
    // 需 token compression/pooling 适配 context window
    output = LLM.generate(input_seq)

Output: text_answer
```

**注解**:
- **长视频 token 爆炸**: 30 分钟视频可 >200K tokens，超过 Qwen2.5-VL-7B 的 128K 上下文窗口，需 sparse frame sampling + token compression
- **时空 attention 的双重压力**: Spatial attention (帧内 O(N_s²)) + Temporal attention (帧间 O(F²)) — Alternating-Attention (VGGT) 将两者分离以降低复杂度
- **Frame-wise causal attention**: StreamVGGT 将 temporal attention 改为仅可访问历史帧（causal mask），使 streaming inference 成为可能，但 KV cache 随帧数线性增长

#### 4.3 硬件瓶颈分析：时空 Attention 对访存带宽的压力

```
┌── Video 推理的 Memory Bandwidth 压力分析 ─────────────────────────┐
│                                                                     │
│  Spatial Attention (per frame, per layer):                          │
│    Q,K,V ∈ R^{N_s × d}, N_s = H×W patches                          │
│    Q@K^T: [N_s, d] @ [d, N_s] → [N_s, N_s]                        │
│    Memory traffic: 3 × N_s × d × 2B (Q,K,V load)                    │
│                  + N_s² × 2B (attention matrix)                     │
│    N_s=9216, d=1536: QKV load ≈ 85MB + attention ≈ 170MB           │
│                                                                     │
│  Temporal Attention (cross-frame, per layer):                        │
│    Q,K,V ∈ R^{F × d}, F = num_frames                                │
│    Q@K^T: [F, d] @ [d, F] → [F, F]  (much smaller than spatial)    │
│    Memory traffic: 3 × F × d × 2B                                   │
│                                                                     │
│  Total memory traffic per layer per frame: ~260MB                   │
│  × 28 layers × 49 frames × 50 denoising steps                      │
│  = 260MB × 28 × 49 × 50 ≈ 17.8 TB HBM traffic per video!           │
│                                                                     │
│  H100 HBM bandwidth: 3.35 TB/s → 理论最小时延: 17.8/3.35 ≈ 5.3s   │
│  （实际受限于 kernel launch overhead、non-coalesced access、        │
│    irregular memory pattern → 实际延迟 ≥ 理论 × 2-3×）               │
│                                                                     │
│  关键发现:                                                          │
│  - Video DiT 的 memory bottleneck 比 LLM decode 严重 ~100×         │
│  - Attention score 的 power-law 分布（DSV Obs.1）意味着            │
│    90% attention 集中于 10% KV pairs → sparse attention 机会        │
│  - 但 critical KV 不呈现 locality 模式（DSV Obs.2, 仅 15.1%        │
│    critical KV 在 5-token 半径内）→ 固定窗口失效                    │
└─────────────────────────────────────────────────────────────────────┘
```

**注解**:
- **Power-law sparsity**: DSV 论文发现 Video DiT 中 95.2% 的 queries 的 attention 被 top-10% KV pairs 主导——sparse attention 理论上有 10× 加速潜力
- **No locality**: 与 LLM 不同（streaming-LLM 的 attention sink + local window），Video DiT 的 critical KV 不集中在邻近 token——48.5% 的 critical KV 在 10-token 半径之外，使 fixed-pattern sparse attention 失效
- **Tiling 约束**: FlashAttention 的 tiling 策略依赖 Q 和 KV 在序列维度的连续性——Video DiT 的 3D token layout 破坏了这种连续性，tile 边界出现大量 cross-frame/cross-row 依赖

### 2.2 硬件平台体系结构差异对推理的影响

**笔记证据**: `knowledge_notes/硬件知识笔记/GPU Memory Hierarchy (HBM vs SRAM).md`, `knowledge_notes/系统知识笔记/Memory Wall.md`, `knowledge_notes/系统知识笔记/Arithmetic Intensity and Roofline Model for LLM Inference.md`

| 硬件特性 | H100 (GPU) | Ascend 910B (NPU) | TPU v5p | 对推理的影响 |
|----------|-----------|-------------------|---------|-------------|
| Peak Compute (BF16) | 989 TFLOPS | ~320 TFLOPS | 459 TFLOPS/chip | MoE Decode 不受益于高算力（memory-bound） |
| HBM Bandwidth | 3.35 TB/s | ~1.6 TB/s | ~2.7 TB/s | 直接决定 decode 阶段延迟 |
| HBM Capacity | 80 GB | 64 GB | 95 GB | 限制可驻留的 expert 数（MoE）和 KV cache（多模态） |
| On-chip SRAM/SM | 228 KB/SM × 132 | ~192 KB/AI Core | ~256 KB/TPU Core | 限制 FlashAttention tile size 和 kernel fusion 范围 |
| L2 Cache | 50 MB | ~32 MB | — | MoE expert weight 缓存效率 |
| 互联带宽 | NVLink 900 GB/s | HCCS 392 GB/s | ICI 4.5 TB/s (Pod) | Expert Parallelism 的 All-to-All 通信效率 |
| Ridge Point (FLOP/byte) | ~295 | ~200 | ~170 | 越低表示越多 workload 处于 compute-bound |

**注解**:
- GPU SIMT（H100）: 适合不规则的 sparse attention 和 expert routing（warp-level divergence 可控），但 HBM 带宽增长慢于 compute
- NPU 脉动阵列（Ascend 910B）: 对规整的 MatMul 高效（MoE expert FFN、Attention Q@K^T），但对 irregular memory access（dynamic expert routing）效率低于 GPU
- TPU systolic array (v5p): 批量 MatMul 效率极高，但 single-request 场景下 batch=1 导致 systolic array 严重 under-utilized
- **笔记未明确说明**: 各平台在 Q1.1 特定四模型推理场景下的端到端对比 benchmark 数据（如 DiT 在 Ascend vs H100 的 step latency）

## 三、实现(aux) —— 辅助说明

**笔记证据**: `knowledge_notes/kernel知识笔记/GroupGEMM (Grouped GEMM for MoE).md`, `knowledge_notes/编译知识笔记/Megablocks.md`, `knowledge_notes/kernel知识笔记/Expert Parallelism (EP _ 专家并行).md`

### 3.1 MoE 推理的关键实现框架

- **GroupGEMM** (CUTLASS): 将所有 expert 的 GEMM 合并为单次 kernel launch。GroupGemm vs DenseGemm 动态切换：m<2048 (decode) 用 GroupGemm，m≥4096 (prefill) 用 DenseGemm
- **Megablocks** (Databricks): block-sparse dropless MoE routing，token permute→block-sparse GEMM→un-permute 流程，避免 expert capacity 导致的 token drop
- **Expert Offloading** (FineMoE, MoE-Infinity): 将 inactive expert 存放 CPU memory，按需经 PCIe 加载到 GPU——key challenge 是 PCIe 带宽（~32 GB/s）远低于 HBM（~3.35 TB/s）

### 3.2 DiT 推理的关键实现框架

- **FlashAttention**: 将 self-attention 的 O(N²) 中间矩阵 tiled 化以避免 HBM round-trip，DiT 可直接复用 LLM 的 FlashAttention kernel
- **SLA (Sparse-Linear Attention)**: 通过 fine-tunable sparse attention 将 Wan2.1-1.3B 的 attention FLOPs 从 52.75T 降至 2.73T (95% 稀疏度)，2.2× 加速
- **MixFusion**: Patch-level parallel serving，利用 operator taxonomy（pixel-wise vs context-dependent）实现 patch 间独立并行

## 四、是什么？(aux) —— 辅助说明

### 4.1 四类模型的推理计算流程本质

- **MoE**: 在标准 Transformer decoder 的 FFN 位置插入稀疏激活的 expert 集合——核心是"用 memory 换 compute"（更多参数 → 更高精度，但仅激活部分 → 控制计算量）
- **DiT**: 利用 Transformer 替代 U-Net 进行迭代式噪声预测——核心是"用 compute 换 quality"（50 步 serial denoising → 高质量生成，但延迟极高）
- **多模态 VLM**: 将视觉信号 tokenize 为"外语"后与文本一起送入 LLM——核心是"将 vision 嵌入 language model 的表示空间"
- **Video (生成/理解)**: 将时间维度作为额外 token 维度处理——核心是"3D spacetime tokenization"，token 数随帧率和时长线性增长

### 4.2 计算图结构与数据依赖关系

```
┌── 四模型推理计算图 DAG ──────────────────────────────────────────┐
│                                                                    │
│  MoE (per layer):                                                  │
│    Attention → LN → Gate(串行依赖) → Expert_i (并行) → Σ(归约)    │
│              ↘___________________↗                                │
│    数据依赖: Gate output 决定 expert 选择 → 严格串行瓶颈           │
│    并发机会: 多个 selected expert FFN 间可并行（无数据依赖）       │
│                                                                    │
│  DiT (per step):                                                   │
│    z_t → [SelfAttn → CrossAttn → FFN] × L → ε_pred → z_{t-1}     │
│          ↑________________________________________↓                │
│    数据依赖: denoising step 间严格时序依赖（串行）                 │
│    并发机会: step 内多个 attention head 可并行；                  │
│            不同 DiT block 间依赖 → 不可并行                        │
│                                                                    │
│  多模态 VLM:                                                       │
│    Image → ViT_Encode(并行) → Project → Concat → Prefill → Decode │
│    Text  → TokenEmbed(并行)  ↗                                    │
│    数据依赖: ViT 和 Text Emb 无依赖（可并行）→Concat 同步点       │
│    并发机会: Encode 阶段 image/text 并行编码                       │
│                                                                    │
│  Video (DiT):                                                      │
│    Frame_1 → SpatialAttn → TemporalAttn(全部帧就绪) → FFN         │
│    Frame_2 → SpatialAttn ↗                                        │
│    ...                                                              │
│    数据依赖: Temporal attention 需所有帧 spatial 编码完成          │
│    并发机会: 各帧 spatial attention 独立（可并行）                 │
└────────────────────────────────────────────────────────────────────┘
```

**注解**:
- MoE Gate → Expert 的串行依赖是**最关键的 algorithm-level serialization bottleneck**——无论硬件有多少并行单元，routing decision 必须先完成
- DiT 的 step-to-step 串行是**扩散模型的核心约束**——consistency models（1-4 步生成）试图打破这一约束
- 多模态的 Encode 阶段具有最佳的并发特性——image/text encoder 完全独立，可映射到不同计算单元

## 六、不确定性

1. **DiT 在 NPU (Ascend 910B) 和 TPU v5p 上的推理延迟数据**: 笔记未明确说明 DiT 在非 NVIDIA 平台上的端到端 benchmark 结果——上述分析基于 GPU memory hierarchy 推断，跨平台结论需实验验证
2. **MoE Gate Network 在单 token (batch=1) 场景下的延迟占比**: FineMoE/LYNX 论文的主要实验基于 B≥16 的 batch 场景，batch=1 时 Gate Network 的相对开销可能更高，笔记未给出具体分解
3. **多模态 VLM 在异构计算单元上的最优映射策略**: EPD-Serve 论文在三阶段分离上有实验数据，但 Encode 阶段在 GPU Tensor Core vs NPU AI Core 上的定量对比缺失
4. **Video DiT 的 sparse attention 在推理中的实际加速比**: DSV 论文主要分析训练场景，推理时 sparse attention 的 overhead（critical KV identification cost）可能抵消部分收益——具体数值笔记未提供
5. **Ascend NPU 的 Da Vinci 架构在 attention 计算上的具体性能特征**: 笔记提及 Ascend 910B 的基本参数（HBM bandwidth 1.6 TB/s），但其 AI Core 在 FlashAttention 类 kernel 上的效率数据缺失
6. **AMD MI300X 和 Cerebras CS-3 在四模型推理场景的性能**: 笔记中关于这些平台的信息限于基本架构描述，无具体 benchmark 数据
