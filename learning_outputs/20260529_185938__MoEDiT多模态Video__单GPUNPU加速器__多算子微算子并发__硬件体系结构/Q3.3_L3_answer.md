## 一、图优化方法细节（主内容 —— 硬件数据流 + 计算/控制模块设计 + 架构）

### 1.1 子图切分与设备放置（Subgraph Partitioning & Device Placement）

#### 方法：NetMoE 动态 Sample Placement（MoE 负载）

**笔记证据**: `paper_secs/secs_moe/NetMoE/2.1-PARALLELISM-IN-DISTRIBUTED-TRAINING.md` (score: 889.4)

NetMoE 将 MoE 训练中的 token-to-expert 映射建模为整数线性规划（ILP）问题。核心思想：不按 token-expert 静态绑定，而是在 expert 已放置到各 GPU 节点上后，将每个 token 动态路由到使通信开销最小的节点上的 expert 副本。

**编译框架执行模拟（L3 粒度）**：

```
// NetMoE 设备放置的 ILP 求解流程
// 输入: 已放置好的 expert→node 映射, 所有 token 的 routing 分布
// 输出: 每个 token i 的样本放置决策 SmpDev(i)

Step 1 — 构建 ILP 变量:
  对每个 token i ∈ [I], 目标节点 n ∈ [N]:
    SmpDev(i) ∈ [I]*_n   // token i 被分配到节点 n 的 expert 集合中

Step 2 — 构建目标函数(最小化通信时间):
  // t_intra: 节点内通信时间 (NVLink)
  // t_inter: 节点间通信时间 (InfiniBand/RoCE)
  minimize: Σ_i [ t_intra(SmpDev(i)) + t_inter(SmpDev(i)) ]

Step 3 — 约束条件:
  (a) 每个 token 恰好被分配到 top-k 个节点之一 (k=2 for Mixtral)
  (b) 节点 n 上 SmpDev(i) 涉及的 expert 必须在 Node(n) 上 (由 device placement 确定)
  (c) 每个 GPU 的 token 数量不超过显存容量

Step 4 — 编译时求解 (offline):
  // 使用 Gurobi/OR-Tools 求解 ILP
  // 对于大规模集群: ILP 分解为 per-layer 子问题，并行求解
  optimal_placement = solve_ilp(variables, objective, constraints)
  // 编译时间 < 1s per layer on CPU (1000 GPU 规模)

Step 5 — 运行时执行:
  for each training iteration:
    router_output = gating_network(hidden_states)  // CPU 上计算 gating
    placement_plan = lookup(optimal_placement, router_output)
    // 异步发射: expert FFN 计算在 GPU 上并发执行
    for gpu in assigned_gpus (parallel CUDA streams):
      launch_expert_ffn(gpu, placement_plan[gpu])
```

**注解**：

- **变量含义**：SmpDev(i) 是 token i 的目标节点分配决策变量；t_intra 衡量同一节点内 GPU 间的 NVLink 通信延迟；t_inter 衡量跨节点 IB/RoCE 通信延迟。
- **复杂度分析**：ILP 求解器复杂度为 O(2^(I×N))（最坏指数），但通过 per-layer 分解 + 贪心预热实现秒级求解。论文实测 1000 GPU 规模下 < 1s。
- **数据依赖**：ILP 求解依赖 expert 的预放置（device placement）结果；运行时 gating 结果决定了实际 expert 选择，placement plan 查询为 O(1)。
- **并发可行性**：编译时 ILP 求解是纯 offline 的；运行时各 GPU 上的 expert FFN 通过独立 CUDA stream 完全并发发射——关键挑战是 all-to-all 通信的异步调度。

#### 方法：FlexMoE 动态设备放置（辅助说明）

**笔记证据**: `paper_secs/secs_moe/SYMI-Efficient-Mixture-of-Experts-Training...md` (score: 876.3) 引用 FlexMoE

FlexMoE 在训练过程中动态调整 expert 的 GPU 放置，根据 expert 负载变化触发 expert 迁移。编译框架层面，IR 中的 device placement annotation 必须是可变的——MLIR 的 `gpu.launch` 的 device 参数或 XLA 的 device assignment 需要在编译时为每个可能的 placement 生成多版本代码，运行时根据动态放置决策选择对应版本。

**注解（辅助说明）**：动态 device placement 的编译挑战在于：(1) 迁移开销——expert 参数（数百 MB）跨 GPU 拷贝的 PCIe/NVLink 延迟；(2) IR 表达——静态 IR 难以表达"运行时可变"的 device 属性。笔记证据仅涉及训练场景，推理场景下的异构切分（CPU gating + GPU/NPU expert FFN）「笔记未明确说明」。

### 1.2 内存规划与重计算（Memory Planning & Rematerialization）

#### 方法：MegaScale-MoE 的 Holistic Scheduling + Selective Activation Rematerialization（SAR）

**笔记证据**: `knowledge_notes/算法知识笔记/Selective Activation Rematerialization in MoE Training.md` (score: 1601.5)；`knowledge_notes/系统知识笔记/Holistic Scheduling for MoE Layer Training（MoE 层训练的全局调度）.md` (score: 212.8)

这是目前从 vault 中获取的最完整的图优化方法。它将 MoE 层的整个前向/反向传播拆分为独立算子，手动编排执行顺序，并在反向传播中将 activation recomputation 与 gradient communication 交织调度。

**编译框架执行模拟（L3 粒度）**：

```
// MegaScale-MoE Holistic Scheduling — 单 MoE Layer 的完整调度时间线
// 假设: 2 CUDA streams — S_compute(主计算), S_comm(通信)
// T 为伪时间步，每个时间步 ~10μs

时间线 (单位: T):

=== 前向传播 (Forward Pass) ===
T0-T3:   [S_compute] RMSNorm(ln2_in) → ln2_out
T4-T8:   [S_comm]    All-Gather(ln2_out) → ln2_out_ag     // 跨 GPU 收集
T9-T12:  [S_compute] Scatter(ln2_out_ag) → ffn_in           // 路由到 expert
T13-T28: [S_compute] GroupedGEMM(ffn_in, {fc1, fc3}) → fc1_out, fc3_out
         [S_compute] SiLU(fc1_out) * fc3_out → fc2_in       // SwiGLU (fused)
T29-T44: [S_compute] GroupedGEMM(fc2_in, fc2) → fc2_out
T45-T48: [S_comm]    Gather(fc2_out) + Reduce-Scatter → ffn_out
T49-T50: [S_compute] ResidualAdd(hidden, ffn_out) → hidden_next

=== 反向传播 (Backward Pass — 含 SAR) ===
// 策略: 仅保留 {hidden, ln1_out, qkv, attn, ln2_out, fc2_out}
// 丢弃 {fc2_in, ffn_in, fc1_out, fc3_out} → 反向时重计算

T51-T54: [S_comm]    All-Gather(Δffn_out)                   // gradient 通信开始
T51-T60: [S_compute] GroupedGEMM_bwd(Δfc2_out, fc2, fc2_out) → Δfc2_in
                     // ↑ 与 gradient all-gather 并发！

T61-T64: [S_compute] Recompute: SiLU(fc1_out, fc3_out) → fc2_in
                     // ↓ fc2_in 被丢弃，重新计算（memory-bound，开销可忽略）
                     // 与 Δfc2_out gradient all-gather 重叠

T65-T72: [S_compute] GroupedGEMM_bwd(Δfc2_in, {fc1,fc3}) → Δfc1, Δfc3
T73-T76: [S_comm]    Reduce-Scatter(Δffn_in)                // gradient 同步
         [S_compute] Recompute: RMSNorm(ln2_in) → ln2_out   // 重计算与通信重叠

T77-T84: [S_compute] Attention backward (FlashAttention bwd)

// 激活内存节省: (2n+2k+3kf+12+5/m)bsh/n → (2kf+4+2/m)bsh/n
// Mixtral-8x7B: 节省 45.5% 激活内存，MFU 差异 < 0.5%
```

**注解**：

- **数据结构**：激活保留/丢弃的决策基于算子类型——GEMM 类（计算密集）输出保留，RMSNorm/通信类（memory-bound）输出丢弃（重计算开销可被通信掩盖）。
- **并发粒度**：inter-operator 级别——前向/反向的独立计算算子和通信算子在两条 CUDA stream 上并发执行，通过 `cudaEventRecord`/`cudaStreamWaitEvent` 同步。
- **编译 vs 运行时权衡**：当前为手动 hand-tailored 调度（论文 §7 指出未来方向是自动搜索）；不依赖 `torch.autograd` 的 monolithic 反向——需编译器级别的 macro-module 抽象来支持自动化。

#### 方法：MoEBlaze 的 Selective SiLU Checkpointing（辅助说明）

**笔记证据**: `paper_secs/secs_moe/MoEBlaze/5-TRAINING-KERNEL-CO-DESIGN...md` (score: 96.0) 通过 SAR 知识笔记引用

MoEBlaze 采用更细粒度的 checkpoint 策略：仅对 SwiGLU 中的 SiLU 激活函数进行选择性重计算。forward 不保存 SiLU(a)，仅保存 a 和 b；backward 时 recompute SiLU(a) = a·σ(a)。在 memory bandwidth bound 条件下（H100），recompute 开销 ≈ 从 HBM 读取 SiLU(a) 的成本。与 kernel fusion 的 epilogue fusion 协同设计，贡献 ~4× activation memory reduction vs MegaBlocks baseline。

### 1.3 布局优化（Layout Optimization）与混合精度

#### 方法：编译时混合精度 + 布局转换的硬件适配

**笔记证据**: `paper_secs/secs_2026/37-RoMeo/3-Algorithm-Rotated-Token-wise-Mixed-Precision-Quantization.md` (score: 4449.6)；`knowledge_notes/编译知识笔记/Vertical Fusion (GPU Operator Fusion).md` (score: 23.0)

**编译框架模拟（L3 粒度）**：

```
// 编译框架中 layout + precision 转换的 Pass Pipeline
// 以 TVM/MLIR 风格的编译 Pass 为例

IR Input: FP32 NCHW computation graph
  ↓
Pass 1 — LayoutInference:
  // 分析每个算子的最优 data layout
  for op in graph.topological_order():
    if op is Conv2D and target is TensorCore:
      op.layout = NHWC  // TensorCore 需要 NHWC 才能利用 TC
    elif op is Attention and target is GPU:
      op.layout = NCHW  // cuDNN attention 偏好 NCHW
    // 插入 layout transform 节点 (编译时优化: 相邻相同 layout 消除)
    if op.layout != prev_op.layout:
      insert_transform(prev_op.output, op.layout)

Pass 2 — PrecisionAssignment:
  // 基于 cost model 分配精度
  for op in graph:
    if op is MatMul and op.M * op.N * op.K > threshold:
      op.precision = BF16  // 大矩阵乘用 BF16 保范围
    elif op is LayerNorm:
      op.precision = FP32  // 归一化层保 FP32 精度
    else:
      op.precision = FP16  // 默认 FP16
    // 插入 cast 节点: FP32 → FP16/BF16 → FP32
    insert_cast_around(op, op.precision)

Pass 3 — MixedPrecisionFusion:
  // 融合相邻的 cast + compute 节点
  // 例: cast(FP32→BF16) + MatMul(BF16) + cast(BF16→FP32) → FusedMatMul
  for pattern in [cast + compute + cast]:
    if target_supports_fused_precision(pattern):
      fuse(pattern)  // 消除显式 cast kernel 的 launch 开销

Pass 4 — MemoryLayoutOptimization:
  // in-place memory reuse for cast tensors
  for tensor in graph.intermediate_tensors():
    if tensor.lifetime is non-overlapping with other_tensor:
      if tensor.layout is compatible(other_tensor.layout):
        alias(tensor, other_tensor)  // 共享内存，消除 alloc/free
```

**注解**：

- **硬件约束**：A100 TensorCore 要求 NHWC 布局 + FP16/BF16 输入才能达到峰值 312 TFLOPS；若输入为 NCHW FP32，需 compile-time 插入 transform + cast，每次转换消耗 ~0.5-2% 总计算时间。
- **SM Register File 压力**：FP32→FP16 转换将 register 使用量减半（32bit→16bit），使 SM 可容纳更多并发 warp，提升 occupancy——但 layout transform 可能引入额外 register spill。编译器的 register allocation 需在精度降低与 layout 转换的 register 开销间权衡。
- **NPU 适配**：「笔记未明确说明」——RoMeo 论文针对 GPU 量化，NPU 的 Da Vinci 架构有固定 Cube Unit（矩阵乘）+ Vector Unit 数据流模式，其 layout 偏好与 GPU TensorCore 不同，需编译框架提供 target-specific layout lowering。

### 1.4 图级并发提取（Concurrency Extraction from SSA Graph）

#### 方法：HuntKTm 的 Stream Scheduler — 自动依赖分析与并发 kernel 分发

**笔记证据**: `paper_secs/secs_multimodal_kernel/HuntKTm/HuntKTm-Hybrid-Scheduling...md` (score: 4288.9)

HuntKTm 的 stream scheduler 是编译器层面的并发提取实现：自动分析 kernel 间的数据依赖（构建 DFG → 分层拓扑排序），将独立 kernel 分配到不同 CUDA stream，插入最小同步点。

**编译框架执行模拟（L3 粒度）**：

```
// HuntKTm Stream Scheduler — 编译时并发提取流程
// 输入: 程序的 Data Flow Graph (DFG)
// 输出: 每个 kernel 的 stream 分配 + 同步点插入

Step 1 — DFG 构建 (编译时静态分析):
  DFG = BuildDataFlowGraph(program)
  // 节点 = kernel / memory copy 操作
  // 边 = 数据依赖 (read-after-write, write-after-read, write-after-write)
  // 例: K_A → K_B (K_B 读取 K_A 的输出 buffer)

Step 2 — 依赖分析 + 拓扑分层:
  // 计算每个 kernel 的 level:
  level[K] = 0 if K has no predecessors
           = 1 + max(level[p] for p in predecessors(K))
  // 同层 kernel 之间无数据依赖 → 可并发执行

Step 3 — Stream 分配 (Load-Balanced):
  available_streams = [S0, S1, ..., S_max]  // 硬件队列数上限 32
  for level in sorted(levels):
    kernels_at_level = sort_by_estimated_runtime(kernels[level])
    for K in kernels_at_level:
      // 选择当前负载最轻的 stream
      S_best = argmin(estimated_queue_length(S_i) for S_i in available_streams)
      assign(K, S_best)
      // 插入同步: 仅对跨 stream 依赖插入 CUDA event
      for pred in predecessors(K):
        if stream(pred) != stream(K):
          insert_event_wait(K, pred)  // cudaStreamWaitEvent

Step 4 — 冗余同步消除:
  // 编译时识别并删除冗余的同步 barrier
  for sync in inserted_syncs:
    if is_transitively_covered(sync, DFG):
      remove(sync)  // 已被其他同步点覆盖，可安全删除

Step 5 — 内存生命周期管理:
  // 分析每个 memory object 的 live range
  for mem_obj in program.memory_objects:
    mem_obj.live_range = [first_access(mem_obj), last_access(mem_obj)]
  // 非重叠 live range 的内存对象可共享物理内存
  for (obj_a, obj_b) in non_overlapping_pairs:
    if size(obj_a) >= size(obj_b):
      alias(obj_b, obj_a)  // 缩减总内存占用
```

**注解**：

- **数据结构**：DFG 以邻接表存储，每条边标注依赖类型（RAW/WAR/WAW）；topological level 通过 BFS 计算，O(|V|+|E|)。
- **并发粒度**：kernel-level（CUDA stream 粒度）+ task-level（MPS 粒度）两层并发。单个 GPU 硬件队列上限 32，HuntKTm 限制为 32 以避免超出并发容量。
- **硬件约束**：并发 kernel 的 SM 分配由 GPU thread block scheduler 的 "most-room" 策略决定（见硬件侧重节）。HuntKTm 不直接控制 SM 分配，而是通过控制同一 stream 内 kernel 的发射时机间接影响 SM 占用。
- **结果**：吞吐提升 33.2% over CASE (SoTA), 13.8% over TaskFlow。

#### 方法：ACS — 运行时 Out-of-Order Kernel 调度（不规则计算图）

**笔记证据**: `paper_secs/secs_multimodal_kernel/ACS/I.-INTRODUCTION.md` (score: 2386.8)

ACS 针对 input-dependent 不规则计算图（如 DeepRL 物理仿真、动态 DNN）设计：在 GPU 运行时维护一个 sliding scheduling window，对窗口内的 kernel 做 out-of-order 依赖检查——已就绪（无未完成依赖）的 kernel 立即发射到可用 CUDA stream 上并发执行。

**注解**：该方法的关键创新在于将 CPU 超标量处理器中的 OoO 调度思想应用到 GPU kernel 调度——不预先构建全图，而是随着 kernel 到达动态决定发射时机，避免了 input-dependent DAG 的重构开销。ACS-SW（纯软件）提供 1.87× 加速，ACS-HW（硬件辅助）提供 2.19× 加速。这本质上是将"编译时并发提取"推迟到"运行时动态并发提取"——对动态图场景比静态编译更有效。

## 二、自动调优方法细节（主内容 —— 硬件在环调优 + 自动搜索）

### 2.1 Tile Size / Thread Block / Unroll Factor 的自动搜索

#### 方法：HyTiS — 离线 Profiling + 自适应搜索空间 Auto-tuning

**笔记证据**: `knowledge_notes/编译知识笔记/GEMM Auto-tuning with Adaptive Search Space.md` (score: 690.5)；`knowledge_notes/编译知识笔记/Offline Profiling for GEMM Micro-kernels.md` (score: 42.8)

HyTiS 是编译框架中"硬件在环"auto-tuning 的代表性方法。它通过一次 offline profiling 构建候选配置空间，将运行时搜索空间从 O(10^4) 降至 O(10^1)。

**编译框架中的 Auto-tuning 流程（L3 粒度）**：

```
// HyTiS Auto-tuning Pipeline
// 阶段 1: Offline Profiling (编译准备阶段，一次完成)
// =============================================

Profiling 输入: P(K_i) = GEMM(bM_i * 4, N_SM * n0/4, K_0=1024)
// 对每个候选 micro-kernel tile 配置 K_i = (bM, bN, bK, layout):
for each K_i in candidate_tiles:
  t(K_i)   = measure_latency(K_i)       // CUDA event 计时
  SMEM(K_i) = query_shared_mem_usage(K_i) // Triton compile-time 查询
  REG(K_i)  = query_register_usage(K_i)

// 构建 Throughput-Oriented (S^TO) 候选集:
//   约束 1 - 资源: SMEM(K_i) <= SMEM_capacity, REG_spill == 0
//   约束 2 - SMEM 利用率: 无更大维度 K' 同时满足资源约束
//   约束 3 - ISA: H100 wgmma 要求 bM % 64 == 0
T(K_i) = (M_i * N_i) / (n0 * t(K_i))  // 吞吐量
S_TO = {K_i | diff(T(K_i), max(T)) < l1}  // l1 阈值动态调整

// 构建 Latency-Oriented (S^LO) 候选集:
t_wave(K_i) = t(K_i) / n0  // 单 wave 延迟
S_LO = {K_i | diff(t_wave(K_i), min(t_wave)) < l2}

// 阶段 2: 运行时 Auto-tuning (每个 GEMM problem shape)
// ====================================================
function autotune(P(M, N, K)):
  if cache.hit(P): return cache.get(P)

  for K1 in S_TO:
    total_tiles = ceil(M/K1.bM) * ceil(N/K1.bN)
    partial_tiles = total_tiles % N_SM  // 尾波 tile 数

    for K2 in S_LO:
      // 两级 tile scheduling 有效性检查:
      if partial_tiles == 0:
        valid = true  // TO-only (刚好填满所有 SM)
      elif partial_tiles <= N_SM:
        valid = true  // two-level: TO 全波 + LO 尾波
      else:
        continue      // 无法有效调度

      for layout in [GM_opt, GN_opt]:
        bench(HyTiS_GEMM, K1, K2, layout, P)  // 实际 GPU 实测

  best_config = argmin(latency)
  cache.store(P, best_config)
  return best_config

// 关键数据:
// H100: 平均搜索空间 14 配置 (max 66)
// vs Inductor-Triton 固定 19 配置
// Profiling 成本: H100 ~19 min, A100 ~36 min (per device, 一次完成)
```

**注解**：

- **硬件建模精度**：Offline profiling 基于"SM 架构独立性"假设——micro-kernel 在单个 SM 上的性能特征在不同 problem shape 下相对稳定，因此 profiling 结果可跨 workload 复用。这一假设对 NVIDIA SM 架构成立，但对 NPU 脉动阵列（固定数据流）不一定成立。
- **Concurrent Kernel 调优**：HyTiS 的 auto-tuning 针对单 kernel 的 tile 配置，不直接调优多 kernel 并发场景。但两级 tile scheduling 的尾波处理（LO 处理 partial tiles）可以释放部分 SM 资源——在并发场景下，这些空闲 SM 可被其他 kernel 利用。「笔记未明确说明」如何 joint tune 多个并发 kernel 的 tile 配置以避免资源竞争。
- **与 Triton Autotuner 的关系**：Triton 的 `@triton.autotune` 是 per-kernel 的配置搜索（tile size, num_warps, num_stages），HyTiS 在此之上增加了 scheduling 层面的决策（TO vs LO 两级），不修改 Triton compiler 本身。

#### 方法：Infera — Tile-Based Zero-Tuning Compilation（零实测编译）

**笔记证据**: `knowledge_notes/编译知识笔记/Tile-Based Zero-Tuning Compilation.md` (score: 297.9)

Infera 反其道而行——完全跳过 GPU profiling，基于静态资源约束推导 tile size：

```
// Infera Zero-Tuning 的 tile size 决策 (top-down):
Register File Level: 32-bit register/thread limit = 64/96/128 → 平衡 ILP vs TLP
Shared Memory Level: usage/block limit = 48/80/112/144 KiB → spatial tile = thread_tile × thread_count
Global Memory Level: spatial tile = block_tile × grid_size (grid_size fixed 64)

// Multi-Version Micro Kernel Generation:
for reg_config in {64, 96, 128}:
  for smem_config in {48, 80, 112, 144}KB:
    for pipeline_stage in {2, 3, 4}:
      if resource_feasible(reg_config, smem_config, pipeline_stage):
        generate_kernel(reg_config, smem_config, pipeline_stage)

// 无需 GPU profiling → 编译并行化 → CPU 核心增加时编译时间按比例缩短
// vs Ansor/MetaSchedule 编译时间低 2-3 个数量级
```

**注解**：Zero-tuning 的关键在于 Roller 的发现——仅考虑 tile size 因素即可生成高性能 kernel。Infera 进一步证明 varying tile size 可平衡 ILP/TLP/intensity trade-off。该方法适合编译时已知硬件资源的场景（如 GPU），对 NPU/加速器的固定数据流架构适配性「笔记未明确说明」。

### 2.2 硬件在环调优（Hardware-in-the-Loop Tuning）

#### 方法：FlowMoE — 贝叶斯优化自动搜索通信参数

**笔记证据**: `knowledge_notes/编译知识笔记/Bayesian Optimization for Auto-Tuning Communication Parameters.md` (score: 667.2)

这是 auto-tuning 在分布式 MoE 训练中的系统级应用——调优的不是 kernel tile size，而是通信 chunk size：

```
// FlowMoE BO Auto-tuning — 搜索最优 all-reduce chunk size S_p
// 目标: 最小化 per-iteration training time
// 使用高斯过程 (GP) 拟合 f(S_p) 的 posterior distribution

Step 1 — 初始采样:
  for S_p in [1MB, 4MB, 16MB, 64MB, 256MB]:
    time[S_p] = measure_avg_iteration(model, S_p, warmup=10, iters=10)

Step 2 — BO 迭代 (通常 3-5 次):
  for iter in 1..5:
    gp.fit(S_p_sampled, time_sampled)
    S_p_next = argmax(ExpectedImprovement(S_p | gp))
    time_next = measure_iteration(S_p_next)
    // 约 8 次采样即可收敛到近优值

Step 3 — 部署:
  S_p_opt = S_p_sampled[argmin(time_sampled)]
  // BERT-Large-MoE: S_p_opt ≈ 2.5MB
  // BO 开销 < 1% per-iteration time
```

**注解**：该方法将传统 ML 编译器中 auto-tuning 的 "tile size search" 扩展到了系统参数搜索——S_p 不是 kernel 参数而是通信参数。当硬件环境变化（GPU 型号、网络带宽、模型配置）时 BO 自动重新搜索，体现了"环境感知的自适应调优"。局限：每次评估需要 10 轮完整迭代，大模型评估开销约 32s——在大规模训练中可接受。

#### 方法：KernelEvolve — 进化搜索 + LLM Agent 自动 Kernel 生成（辅助说明）

**笔记证据**: `paper_secs/secs_multimodal_kernel/KernelEvolve/KernelEvolve-Scaling-Agentic-Kernel-Coding...md` (score: 7565.3)

KernelEvolve 使用进化算法（Evolutionary Search）在 LLM agent 的辅助下自动生成和优化 GPU kernel，代表了 auto-tuning 与 AI agent 结合的前沿方向。搜索空间包括 tile size、thread/warp 配置、pipeline stage、memory hierarchy 使用方式等。

### 2.3 联合调优（Joint Tuning）与并发 Kernel 的硬件建模

#### 方法：DAG-based Critical Path Optimization（MoE-GEN 的离线配置搜索）

**笔记证据**: `knowledge_notes/编译知识笔记/DAG-based Batching Strategy Search (DAG + DP for Critical Path Optimization).md` (score: 43.1)

这是将多个算子/模块的并发执行视为 DAG scheduling 问题，通过搜索 batching 配置最小化 critical path：

```
// MoE-GEN DAG-based 搜索 — Offline Joint Tuning
// 搜索空间: (B, b_a, b_e, ω, S_Expert)
//   B=macro-batch, b_a=attention micro-batch, b_e=expert micro-batch
//   ω=CPU split ratio, S_Expert=expert buffer size

for config in search_space:
  // 1. 构造该配置下的 DAG:
  dag = build_dag(config)
  //    节点: [Copy Attn Weights] → [Pre-Attention GPU] → [Copy KV-Cache]
  //           → [GPU Self-Attn] ─┐
  //           → [CPU Self-Attn] ─┤→ [Post-Attention]
  //                               → [Copy Expert1 Weights] → [Expert1 FFN] → ...

  // 2. DP 求解 Critical Path:
  topo = topological_sort(dag)
  dp[node] = max(dp[p] for p in predecessors(node)) + cost(node)
  T = dp[exit_node]  // 单层总时间

  // 3. 选择 throughput 最大配置:
  throughput = B / T
  if throughput > best:
    best_config = config

// 本质: 将 batching + offloading 参数作为"系统级 hyperparameters" 进行 joint tuning
// 类比 ML 编译器的 kernel schedule search，但搜索的是 batch size 而非 tile size
```

**注解**：DP 求解器 O(|V|+|E|) 复杂度，但外层需要枚举多维配置空间的笛卡尔积——通过 memory constraint 剪枝控制搜索规模。该方法类似 TVM AutoScheduler 的 evolutionary search + cost model，但 cost model 基于 profiling data 而非 learned model。

## 三、硬件侧重：GPU Occupancy / NPU 算力密度 / 加速器数据流

### 3.1 GPU Occupancy 与并发 Kernel 的调度关系

**笔记证据**: `paper_secs/secs_multimodal_kernel/Demystifying/2.-CUDA-PROGRAMMING-MODEL.md` (score: 2968.2)

NVIDIA GPU 的 thread block scheduler 采用 **most-room 策略**（而非广泛认为的 round-robin）：调度器将下一个 thread block 放置到**能容纳该 kernel 最多 block 数的 SM** 上。限制资源可以是 threads、shared memory、registers、max blocks/SM、warps/SM 中的**任一先耗尽者**。并发 kernel 场景下出现两种模式：**concurrent-isolated**（kernel B 的全部 block 放在同一个空闲 SM 上）和 **concurrent-colocated**（kernel B 的 block 与 kernel A 的 block 共享 SM）。

**编译框架的并发度决策含义**：

```
// 编译框架需要建模 GPU occupancy 来决定并发 kernel 数量
// 
// 假设: 每个 SM 可用 registers = 65536, shared memory = 228KB (H100)
// Kernel A: 256 threads/block, 64 registers/thread, 16KB shared memory/block
// Kernel B: 128 threads/block, 32 registers/thread, 8KB shared memory/block

// SM occupancy 计算:
blocks_per_SM_A = min(65536/(256*64), 228KB/16KB, 2048/256, 32)
                 = min(4, 14, 8, 32) = 4 blocks/SM
blocks_per_SM_B = min(65536/(128*32), 228KB/8KB, 2048/128, 32)
                 = min(16, 28, 16, 32) = 16 blocks/SM

// Concurrent-colocated 场景:
// 假设 SM 上已有 3 blocks of A → 剩余:
//   registers: 65536 - 3*256*64 = 16384 → 可容纳 4 blocks of B
//   shared memory: 228 - 3*16 = 180KB → 可容纳 22 blocks of B
//   threads: 2048 - 3*256 = 1280 → 可容纳 10 blocks of B
// → 并发上限: min(4, 22, 10) = 4 blocks of B
```

**注解**：GPU occupancy 调优的核心矛盾——更多并发 kernel 意味着每个 kernel 的 SM 资源减少（warp occupancy 下降），从而可能降低各 kernel 的 IPC。编译框架需要在"并发数量 × 单 kernel 性能"间做 Pareto 最优选择。vault 笔记未给出 multi-kernel joint occupancy modeling 的具体方法；HuntKTm 的 stream scheduler 通过负载均衡间接优化，但未显式建模 register/shared memory 竞争。

### 3.2 NPU 算力密度与 Tile 选择

「笔记未明确说明 NPU（Ascend/CANN）的 auto-tuning 与 tile 选择的具体方法」。从硬件体系结构知识可推断：

- Ascend 910B 的 Da Vinci 架构有固定的 Cube Unit（16×16 FP16 MAC per cycle）+ Vector Unit 双流水线设计
- NPU 的 tile size 选择受 Cube Unit 的固定数据流约束——矩阵乘法 tile 必须是 16 的倍数
- 与 GPU 的灵活 tile size 不同，NPU 编译框架（CANN GE/IRFusion）的 tile 选择空间更受限
- 「可推断」：NPU 的 auto-tuning 搜索空间远小于 GPU（因硬件固定数据流限制），更接近 Infera 的"zero-tuning"范式——静态约束直接推导 tile size

### 3.3 加速器固定数据流与图变换适配

**笔记证据**: `paper_secs/secs_2025/12-ELK/span-idpage-5-0span4.2-Two-Level-Inductive-Operator-Scheduling.md` (score: 380.1)

ELK 编译器为 ICCA（Inter-Core Connected AI Chip）芯片设计的编译框架代表了加速器场景的编译方法：

- **O(KN) 归纳算子调度**：利用 DL 模型的顺序依赖特性，从最后一个算子开始归纳推导每个算子的最优 preload number，而非枚举指数级组合
- **Pareto 最优片上内存分配**：在执行算子与预加载算子之间做两层 tradeoff——每个算子有多个 (execution_time, memory_usage) Pareto 最优方案，编译器在总片上内存约束下联合选择
- **Cost Model**：使用 linear tree model 拟合每个算子的 tile 执行时间（以 tile shape 为输入，profiled execution time 为输出）

**注解**：加速器（如 Graphcore IPU、Groq LPU、Cerebras CS-3）的编译框架与 GPU 编译器的根本区别——加速器的并发由编译器静态决定（spatial mapping），无运行时动态调度。ELK 的 O(KN) 算法在 LLM decoder 场景下 5 分钟内完成编译（32-core CPU），生成的 plan 包含精确到每个 core 的 tile 映射和 inter-core transfer 时序。ELK 在 IPU-POD4 上达到 94.84% roofline 性能、89.52% inter-core interconnect 带宽利用率。

## 四、编译框架的多算子并发编译流程总览（L3 粒度）

```
                       │     输入: DNN 计算图 (ONNX/PyTorch FX)    │
                       └──────────────────┬─────────────────────┘
                                          ↓
┌─────────────────────────────────────────────────────────────────────┐
│  Phase 1 — 图优化 (Graph Optimization)                               │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ Pass 1.1: 子图切分 + Device Placement                         │    │
│  │   • 异构切分: CPU gating ↔ GPU/NPU expert FFN                 │    │
│  │   • MoE: ILP 求解 token→expert→device 映射 (NetMoE/FlexMoE)   │    │
│  │   • 多模态: vision encoder + text encoder 独立 func.func       │    │
│  ├─────────────────────────────────────────────────────────────┤    │
│  │ Pass 1.2: 内存规划 + Rematerialization                       │    │
│  │   • SAR: 保留 GEMM 输出，丢弃 RMSNorm/通信输出                  │    │
│  │   • Live range 分析 → in-place memory reuse                  │    │
│  │   • Memory object 生命周期裁剪 (HuntKTm)                      │    │
│  ├─────────────────────────────────────────────────────────────┤    │
│  │ Pass 1.3: Layout + Precision 优化                             │    │
│  │   • NCHW ↔ NHWC (TensorCore 适配)                             │    │

│  ┌─────────────────────────────────────────────────────────────┐    │

│  │   • 或 Zero-tuning 静态推导 (Infera)                          │    │

└────────────────────────────────┬────────────────────────────────────┘
                                 ↓
┌─────────────────────────────────────────────────────────────────────┐

│  ┌─────────────────────────────────────────────────────────────┐    │
│  │ • CUDA: 多 stream kernel 发射 + event 同步 → 并发执行          │    │
│  │ • NPU (CANN): Cube + Vector 双流水线指令编排                   │    │
│  │ • TPU (XLA): SPMD partition + collective-permute overlap     │    │

│  └─────────────────────────────────────────────────────────────┘    │

```

**注解**：

- Phase 1 的 Pass 顺序有依赖——必须先做 device placement 再提取并发（因为跨 device 的 kernel 不可在同一 CUDA stream 上并发）；内存规划需在并发提取后进行（因为 in-place reuse 需要知道哪些 kernel 的生命周期不重叠）。
- Phase 2 的 auto-tuning 可与 Phase 1 的 graph optimization 交替——例如融合后的 kernel 需要重新 auto-tune tile size（因为融合改变了 memory footprint）。
- 硬件侧重体现在每个 Pass 的约束中：GPU occupancy 约束 concurrent kernel 上限；NPU 固定数据流约束 tile size 搜索空间；加速器片上内存容量约束 preload 数量。

1. **NPU/加速器的编译框架并发支持**：vault 中关于华为 CANN、Apple ANE、Groq Compiler、Cerebras SDK 的具体图优化和 auto-tuning 方法「笔记未明确说明」——当前分析主要基于 GPU 侧笔记证据。
