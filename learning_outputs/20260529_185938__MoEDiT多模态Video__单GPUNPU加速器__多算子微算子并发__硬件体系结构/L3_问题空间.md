## 该层覆盖范围

L3 编译框架层覆盖：
- **IR 表示（Intermediate Representation）**：MoE/DiT/多模态/Video 模型的计算图在编译框架中的中间表示形式——包括 High-level IR（如 HLO/StableHLO/Relay）和 Low-level IR（如 MLIR Linalg/Affine/Triton IR/TVM TensorIR/LLVM IR），以及 IR 如何表达多算子并发语义（parallel regions、async execution、device placement）
- **算子融合（Operator Fusion）**：编译器如何将多个相邻算子融合为单一 kernel 以减少 kernel launch 开销和中间数据搬运——包括水平融合（同一输入上的多分支算子）和垂直融合（生产者-消费者链），以及融合策略对微算子并发的支持
- **图优化（Graph Optimization）**：编译时图级变换——常量折叠、死代码消除、布局优化（NCHW↔NHWC）、代数简化、内存规划（tensor rematerialization/recomputation）、子图切分（subgraph partitioning for device placement），以及面向并发的图切分与调度
- **自动调优（Auto-tuning）**：编译时或运行时自动搜索最优 kernel 实现参数（tile size、thread block、unroll factor、向量化宽度）——包括 AutoTVM/AutoScheduler/Triton Autotuner/XLA HLO cost model 等方法，以及多算子并发场景下的联合调优
- **代码生成（Codegen）**：从 IR 到目标硬件可执行代码的生成——包括 GPU（CUDA/PTX/OpenCL/ROCm）、NPU（CANN/AscendC/ANE）、加速器（TPU XLA/SAX、Groq Compiler、Cerebras SDK）的代码发射，以及并发代码生成（concurrent kernel launch、CUDA Graph、async copy）
- **多算子并发的编译支持**：编译器如何发现、表达和优化算子级/微算子级的并发——包括数据依赖分析与并发性提取、并发 region 的 IR 标注、并发 kernel 的调度与同步插入、硬件资源感知的并发度决策
- **所有问题均从硬件体系结构侧重出发**：IR 设计如何反映硬件能力（如 GPU 的 SIMT 模型 vs NPU 的脉动阵列 vs TPU 的 systolic array）；算子融合如何受 L1/L2 cache、shared memory、HBM 带宽制约；Codegen 如何针对不同硬件的 ISA 生成最优并发代码；自动调优如何建模硬件性能

## Q3.4

**层**: L3
**问题**: 哪些编译框架支持 MoE、DiT、多模态、Video 模型的多算子/微算子并发，各自的架构设计和核心实现是什么？（逐框架论述，覆盖其 IR 设计→融合/优化策略→Codegen→并发支持的完整链路）：
- **XLA（含 StableHLO/OpenXLA）**：HLO IR 如何表示并发——`async` ops、`all-reduce`/`all-to-all` 的异步变体、`custom-call` 的并发语义；XLA 的 fusion pipeline（instruction fusion + multi-output fusion）如何决定算子融合边界；XLA 的 GPU codegen 如何发射 CUDA kernel + 依赖管理；XLA 的并发限制——传统 XLA 以串行执行为主，GSPMD 如何为 MoE 引入 SPMD 并行、异步 all-to-all 的支持状态
- **TVM（含 Relay/TensorIR/Unity）**：Relay IR 的 `parallel` annotation 与算子级并发；TensorIR 的 `block` + `buffer` 抽象如何支持微算子并发调度（如 `parallel` 轴、`vectorize` 轴、`unroll` 的显式标注）；TVM AutoScheduler 的 compute definition → search space → measured tuning 流程；TVM Unity 的 `relax` IR 如何进一步支持 dynamic shape + 并发
- **Triton（OpenAI Triton + Triton IR）**：Triton IR 的 block-level programming model 如何天然支持微算子并发——每个 Triton kernel 的 `program_id` 沿 grid 轴可并行执行多个 program instance；Triton Autotuner 对 tile size/num_warps/num_stages 的配置搜索；Triton 的局限性——单 kernel 内的并发但跨 kernel 的编排需要外部调度器
- **MLIR（含 Torch-MLIR / IREE / CIRCT）**：MLIR 多 dialect 架构如何分层支持并发——`gpu` dialect（`gpu.launch`、`gpu.func`）、`async` dialect（`async.execute`、`async.await`）、`scf` dialect（`scf.parallel`、`scf.forall`）；IREE 的 HAL（Hardware Abstraction Layer）如何将 MLIR 编译到 Vulkan/CUDA/ROCm 并管理并发 command buffer；Torch-MLIR 如何将 PyTorch 的 `torch.cuda.Stream` 映射到 MLIR async
- **PyTorch 2.0 编译栈（TorchDynamo + TorchInductor + Triton backend）**：Dynamo 的 FX graph capture 如何保留并发信息；Inductor 的 loop-level IR 如何做算子融合与 tile 化；Inductor 的 multi-kernel codegen 如何生成多个并发 CUDA kernel
- **其他框架**：CUTLASS 3.x 的 `collective` 抽象与 SM90+ 的协作式并发；MLIR-based CIRCT 面向 FPGA/ASIC 的数据流并发编译；华为 CANN 的图编译（GE/IRFusion）在 Ascend NPU 上的算子融合与并发调度
- 结合硬件侧重：各框架对单 GPU/NPU/加速器的 Codegen 后端成熟度、并发原语支持度、自动调优的硬件建模精度对比

## Q3.6

**层**: L3
**问题**: 面向硬件体系结构的多算子并发编译，Codegen（代码生成）层面的关键方法、设计空间和最佳实践是什么？（逐硬件后端论述代码生成策略如何支持并发）：
- **GPU Codegen（CUDA/PTX）**：并发 kernel 的 PTX 代码生成——CUDA stream 的编译时分配与同步点插入、CUDA Graph 的编译时静态化（将多个 kernel 的 launch 序列编译为单次提交的可执行图以减少 launch overhead）；register allocation 与 occupancy 的编译时平衡——如何在多 kernel 并发的 register file 竞争下做 register spill 决策；shared memory 的动态分配与多 kernel 间的静态划分；async copy（`cp.async`）指令的编译时插入用于计算-数据传输重叠
- **NPU Codegen（AscendC/CANN）**：AscendC 的算子 DSL 编译到 NPU 指令流——Da Vinci 架构的 Cube Unit（矩阵乘）+ Vector Unit（向量计算）的指令流水线编排；多算子并发的指令级并行（ILP）——如何将多个小算子编译为同一指令流中的不同功能单元操作以实现微算子并发；Ascend 的 tiling 策略与 buffer 划分的编译时决策
- **TPU Codegen（XLA/SAX）**：XLA 的 TPU backend codegen——SPMD partition 后的 `collective-permute` 与计算 overlap 的代码生成；TPU 的 VLIW（Very Long Instruction Word）指令编排与多算子并发——如何将多个独立操作打包为同一 VLIW bundle 的显式并发；TPU 的 scratchpad memory（等效 shared memory）的编译时静态分配
- **加速器 Codegen（Groq/Cerebras）**：Groq 的确定性编译——所有并发由编译器静态决定，无运行时调度，codegen 时直接将算子映射到芯片上的特定计算单元（spatial mapping）；Cerebras CS-3 的 dataflow compilation——将计算图编译为晶圆级芯片上的数据流图，微算子并发通过空间映射天然支持
- **Codegen 的设计空间**：动态并发（运行时 kernel launch）vs 静态并发（编译时决定的 schedule）；单 kernel 内微算子并发（通过 warp/wavefront specialization）vs 多 kernel 并发（通过 CUDA stream 或 MPS）；计算-通信 overlap 的 codegen 模式（software pipelining in compilation）；不同硬件后端的 codegen 可移植性（MLIR 的 multi-target codegen 如何抽象并发）
