## 1. GPU Codegen（CUDA/PTX）：并发 Kernel 的代码生成

### 1.1 CUDA Stream 并发与 Kernel Launch 编译时优化

**笔记证据**: `knowledge_notes/系统知识笔记/CUDA Graph.md` (score: 5770.5), `knowledge_notes/硬件知识笔记/Command Processor (GPU CP).md` (score: 407.8)

**方法细节**（L3 编译框架模拟——CUDA Graph 编译时静态化）：

CUDA Graph 是 NVIDIA GPU 上实现并发 kernel 执行的核心编译时机制。其工作流程如下：

```
CUDA Graph 编译时静态化 + 运行时重放 流程:

┌─ 阶段 1: 图构建 (编译时/初始化时) ─────────────────────┐
│                                                          │
│  // 方法 A: Stream Capture (运行时捕捉→编译时固化)       │
│  cudaStreamBeginCapture(stream);                         │
│  kernelA<<<gridA, blockA, smemA, stream>>>(...);        │
│  kernelB<<<gridB, blockB, smemB, stream>>>(...);        │
│  cudaStreamEndCapture(stream, &graph);                  │
│                                                          │
│  // 方法 B: Explicit API (编译时显式构建 DAG)            │
│  cudaGraphAddKernelNode(&nodeA, graph, NULL, 0, &paramsA);│
│  cudaGraphAddKernelNode(&nodeB, graph, NULL, 0, &paramsB);│
│  cudaGraphAddDependencies(graph, &nodeA, &nodeB, 1);    │
│                                                          │
├─ 阶段 2: 图实例化 (编译时优化) ─────────────────────────┤
│  cudaGraphInstantiate(&instance, graph);                 │
│  // GPU 驱动在此时执行:                                  │
│  //   - Register allocation (跨 kernel 静态划分)        │
│  //   - Shared memory 预分配                             │
│  //   - 依赖边 → 硬件同步原语编译                        │
│  //   - 多个 kernel 的 launch 序列编译为 GPU 端单次提交 │
│                                                          │
├─ 阶段 3: 图发射 (运行时，可重复) ───────────────────────┤
│  cudaGraphLaunch(instance, stream);                      │
│  // 仅一次 CPU→GPU MMIO 写入                            │
│  // GPU Command Processor 按 DAG 拓扑自动 dispatch       │
│  // 多个 kernel 在 GPU 上并发执行 (不同 SM 分区)         │
└──────────────────────────────────────────────────────────┘
```

**注解**:
- **Kernel Launch Overhead 消除**: 传统 `cudaLaunchKernel` 每次需 CPU→GPU MMIO 写入（5-20μs/kernel），CUDA Graph 将所有 kernel launch 编译为 GPU 端单次提交。对于 MoE 模型中数百个 expert FFN kernel 的并发场景，graph replay 消除了 O(N) 的 launch overhead
- **编译时资源静态划分**: Graph instantiation 阶段，GPU 驱动对所有 kernel 的 register/smem 需求做全局分析，在多 kernel 间静态划分 SM 资源（register file 和 shared memory），避免运行时资源冲突
- **动态图场景的致命缺陷**: 笔记显示 ACS 论文实验表明 Brax 仿真中用 CUDA Graph 的 DAG 构造时间占程序总执行时间 47%。对于 MoE 的 input-dependent routing（每次 expert 选择不同），每次都需要重建 graph，反而比单 stream 串行更慢
- **适用场景**: 静态推理图（如固定 DiT denoising loop、Video 固定帧数 pipeline）——图只需构建一次即可重复使用

### 1.2 ACS 乱序 Kernel 调度——编译时标注 + 运行时并发

**笔记证据**: `knowledge_notes/kernel知识笔记/Out-of-Order Kernel Scheduling (GPU Runtime).md` (score: 2407.6), `paper_secs/.../ACS.../I.-INTRODUCTION.md` (score: 2060.4)

**方法细节**（L3 编译框架模拟——编译时 RW-segments 标注 + 运行时调度窗口）：

ACS 的核心设计是将编译时内存访问标注与运行时乱序调度结合：

```
ACS 编译时标注 + 运行时调度 完整流程:

┌─ 编译时阶段 (用户/编译器标注) ────────────────────────┐
│                                                          │
│  // 每个 kernel 标注其读写内存段                         │
│  __kernel__ void expert_ffn(float* input, float* weight, │
│                              float* output, int N) {     │
│      __read_segments__  = {{input,  N*sizeof(float)},   │
│                             {weight, W*sizeof(float)}};  │
│      __write_segments__ = {{output, N*sizeof(float)}};   │
│      // ... kernel body ...                              │
│  }                                                       │
│                                                          │
│  // 编译器将这些 metadata 嵌入 kernel launch 包          │
│  // PTX 层面无需修改——metadata 附着在 host 端            │
└──────────────────────────────────────────────────────────┘

┌─ 运行时阶段 (ACS 调度窗口, 大小 N=32) ─────────────────┐
│                                                          │
│  SchedulingWindow SW[32];  // 每个slot:                  │
│    // {kid: u8, upstream: [u8;31], status: READY/PENDING}│
│                                                          │
│  // === Window Module (CPU线程) ===                      │
│  while kernel_stream.not_empty():                        │
│      k = pop(kernel_stream)                              │
│      upstream = []                                       │
│      for each kk in SW:                                  │
│          // O(segments²) 地址范围重叠检测                │
│          for seg_w in k.write_segments:                  │
│              for seg_rw in kk.{read,write}_segments:     │
│                  if overlap(seg_w, seg_rw):              │
│                      upstream.add(kk.kid)                │
│      SW.insert(k, upstream)                              │
│                                                          │
│  on_kernel_complete(kid):                                │
│      for each k in SW:                                   │
│          k.upstream.remove(kid)                          │
│          if k.upstream.empty():                          │
│              k.status = READY  // 所有依赖满足           │
│                                                          │
│  // === Scheduler Module (多CPU线程, 各绑1个CUDA Stream) │
│  while True:                                             │
│      if SW.has_ready():                                  │
│          k = SW.pop_ready()                              │
│          cudaLaunchKernel(k, stream_id)  // 发射到独立流 │
│          // 多个 READY kernel 可在不同 stream 并发       │
│          // GPU 硬件通过 HyperQ 支持多 stream 并发 dispatch│
└──────────────────────────────────────────────────────────┘
```

**注解**:
- **依赖检查复杂度**: O(segments²) 遍历，但 segments 数量极少（通常 1-5 个地址范围/kernel），实际检查时间仅 410ns-1640ns——远小于 kernel launch 的 5-20μs
- **ACS-SW vs ACS-HW**: 软件方案在 CPU 端维护调度窗口，每个 kernel 完成需 CPU-GPU 同步；硬件方案将 1KB 调度窗口 SRAM 集成在 GPU Command Processor 中，kernel 完成后硬件自动更新 upstream list（N-1 cycle），无需 CPU 参与
- **加速效果**: Deep RL Brax Ant 环境下（RTX 3060, 28 SM），GPU occupancy 从 34%（单 stream 串行）提升至接近满载，加速比最高 2.19×（ACS-HW）和 1.87×（ACS-SW）
- **与 MoE 的关联**: MoE 推理中 gating→dispatch→expert_FFN→combine 的 kernel 链天然产生 input-dependent DAG，ACS 的运行时调度窗口可自动发现并发 expert FFN kernel 并行执行

### 1.3 Hopper TMA + Warp Specialization 的编译时代码生成

**笔记证据**: `paper_secs/.../Task-Based-Tensor-Computations-on-Modern-GPUs.md` §2.2 (score: 1736.1), `knowledge_notes/硬件知识笔记/Tensor Memory Accelerator (TMA).md` (score: 12311.5), `knowledge_notes/硬件知识笔记/Asynchronous Memory Copy (async-copy).md` (score: 10327.9)

**方法细节**（L3 编译框架模拟——Hopper GEMM kernel 的编译时 Warp Specialization 代码生成）：

Hopper (H100) 架构要求编译器生成 warp-specialized 代码，将数据搬运 warp (DMA) 与计算 warpgroup 分离，通过 TMA 硬件实现异步数据搬运：

```
Hopper GEMM Kernel 的 Warp Specialization 编译时代码生成:

// 编译器将 kernel 编译为两个独立的执行路径:

┌─ DMA Warp (tid 128-159, 1个warp, 32线程) ───────────────┐
│ // 仅 1 个线程 (tid==128) 发起 TMA 传输                  │
│ // TMA 硬件独立于 CUDA Core 执行数据传输                  │
│ for k in range(0, K/T_K):                                │
│     if k >= PIPE:                                        │
│         wait(cons[k % PIPE])  // 等待 consumer 释放 buffer│
│     if tid() == 128:                                     │
│         TMA_load(                                        │
│             prod[k % PIPE],        // completion barrier  │
│             tile(gA, (blk_x(), k)) → sA[:,:,k%PIPE],     │
│             tile(gB, (k, blk_y())) → sB[:,:,k%PIPE])     │
│     // TMA 在后台执行 burst copy (64-256KB/tile)          │
│     // CUDA Core 线程可立即继续循环 (非阻塞)              │
│                                                          │
│ wait(copyout)  // 等待计算 warpgroup 完成                 │
│ TMA_store(sC → tile(gC, blk_x(), blk_y()))               │
└──────────────────────────────────────────────────────────┘

┌─ Compute Warpgroup (tid 0-127, 4个warp, 128线程) ────────┐
│ // 4 个 warp 协作发射 Tensor Core 指令 (硬件要求)         │
│ for k in range(0, K/T_K):                                │
│     wait(prod[k % PIPE])  // 等待 DMA warp TMA 完成      │
│     warpgroup_sync()      // 128 线程同步                 │
│     wgmma(accum, sA[:,:,k], sB[:,:,k])  // Tensor Core   │
│     warpgroup_wait()      // 等待 Tensor Core 完成        │
│     arrive(cons[k % PIPE])  // 通知 DMA warp buffer 可复用│
│                                                          │
│ copy(accum, sC)  // 将寄存器 accumulator 写入 SMEM        │
│ syncthreads()                                         │
│ arrive(copyout)   // 通知 DMA warp 可写出                 │
└──────────────────────────────────────────────────────────┘

// PIPE=2/3 深度流水线: sA/sB 使用 multi-buffered shared memory
// prod[0..PIPE-1], cons[0..PIPE-1] 为 mbarrier (硬件同步原语)
```

**注解**:
- **TMA 硬件解耦**: TMA 从发出请求到数据到达 SMEM 全由硬件管理，CUDA Core 线程不参与数据搬运。`cp.async`(Ampere) 仍需线程显式发射指令并占用寄存器中转，TMA(Hopper) 彻底消除了这一负担
- **Register File 共享**: DMA warp 仅需极少量寄存器（仅存控制变量），其寄存器可被 compute warpgroup 复用存储更大的 accumulator——提升了单 SM 可并发的计算量
- **Warpgroup 约束**: 每 4 个 warp(128 线程) 构成一个 warpgroup，共用一个 Tensor Core 操作——这是 Hopper 硬件架构的强制性要求，编译器必须将 compute 路径编译为 128 线程协作模式
- **Pipelining 深度**: PIPE 变量控制 shared memory 的 multi-buffering 深度。PIPE=2 时 2 个 buffer 交替使用（一个 DMA 写入、一个 Tensor Core 读取），PIPE=3 可进一步隐藏 TMA 延迟
- **对多算子并发的意义**: Warp specialization 本质上将"数据搬运算子"和"计算算子"编译为同一 kernel 内的微算子并发——DMA warp 和 compute warpgroup 在 SM 内部同时执行，实现了 instruction-level 的计算-通信重叠

### 1.4 Register Allocation 与 Occupancy 的编译时权衡

**笔记证据**: `paper_secs/.../2-Bullet.../2-Background-and-Motivation.md` (score: 1661.2), `paper_secs/.../Demystifying...Concurrent Kernels/2.-CUDA-PROGRAMMING-MODEL.md` (score: 3862.5)

**方法细节**（编译时 Register Spill 决策对并发度的影响）:

```
编译时 Register Allocation 与 Occupancy 的权衡:

GPU SM 资源约束 (以 H100 为例):
  - Register File: 65536 × 32-bit registers / SM
  - Shared Memory: 228 KB / SM (可配置为 L1 cache)
  - Max Threads/SM: 2048
  - Max Thread Blocks/SM: 32

编译时决策:
  每个线程的 register 数 = 编译器分配的寄存器数
  每个 block 的 thread 数 = blockDim.x × blockDim.y × blockDim.z

  Registers_per_Block = Threads_per_Block × Registers_per_Thread
  Max_Blocks_per_SM  = min(32, 65536 / Registers_per_Block)

  Occupancy = (Max_Blocks_per_SM × Threads_per_Block) / 2048

举例 (H100, Threads_per_Block=256):
  Regs=128: 128×256=32768 regs/block → max 2 blocks/SM → Occ=512/2048=25%
  Regs=64:  64×256=16384 regs/block  → max 4 blocks/SM → Occ=1024/2048=50%
  Regs=32:  32×256=8192 regs/block   → max 8 blocks/SM → Occ=2048/2048=100%

多 Kernel 并发场景 (Concurrent Kernel Execution):
  SM 可同时驻留来自不同 kernel 的 thread blocks:
  - 每个 kernel 独立使用自己的 register 分配
  - GPU 硬件 Thread Block Scheduler 使用 "mostroom" 策略
    (将新 block 分配到有最多空闲资源的 SM)
  - 编译时 register spill 决策直接影响多 kernel 并发度:
    过度使用 register → 单 kernel 高 occupancy → 抑制其他 kernel 的 SM 分配
    主动 spill 到 LMEM (local memory = HBM) → 降低单 kernel 性能 → 释放 SM 给并发 kernel
```

**注解**:
- **Mostroom 策略**: 笔记显示 NVIDIA GPU Thread Block Scheduler 使用"mostroom" placement policy——新 thread block 分配到当前拥有最多空闲资源的 SM，这使小 kernel 能"填充"大 kernel 未充分利用的 SM
- **Register Spill 的编译时决策**: 编译器（nvcc/ptxas）在 register pressure 过高时自动 spill 到 local memory（实际是 L1 cache 或 HBM），代价是 5-20× 的延迟增加。在多 kernel 并发场景下，主动降低单 kernel 的 register 使用可换取更多并发 kernel 的 SM 分配
- **MoE 场景**: MoE 推理中的 gating/top-k kernel 寄存器需求很小（<32 regs），而 expert FFN kernel 寄存器需求大（>128 regs）。编译器应为前者分配更少寄存器以最大化并发 expert 执行

## 2. NPU Codegen（AscendC/CANN）：Da Vinci 架构的指令流水线编排

### 2.1 CANN 图编译与算子融合的代码生成

**笔记证据**: `paper_secs/.../46-Fast On-device LLM Inference with NPUs.md` (score: 1393.6), `paper_secs/.../ElasticMoE.../B-Extending-to-the-CUDA-Ecosystem.md` (score: 325.0)

**方法细节**（L3 编译框架模拟——CANN GE/IRFusion 的编译时图优化与 NPU 指令生成）:

笔记显示 CANN (Compute Architecture for Neural Networks) 是华为 Ascend NPU 的编译框架，其 GE (Graph Engine) 负责图编译，IRFusion 负责算子融合。以下基于 llm.npu 论文的 chunk-sharing graph 机制推演 CANN codegen 流程：

```
CANN NPU Codegen 编译流程 (推测性重建):

┌─ 阶段 1: 图构建与子图切分 ─────────────────────────────┐
│                                                          │
│  // 输入: 量化后的 MoE/DiT/LLM 计算图 (W8A8)             │
│  // CANN GE 将图切分为 NPU 子图和 CPU 子图               │
│                                                          │
│  // Chunk-sharing Graph (llm.npu 方法):                  │
│  // - Static operators (Linear, LayerNorm): 可共享子图    │
│  // - Dynamic operators (Attention): 不可共享子图         │
│  // 120/144 子图可共享, 内存减少 75% (7.2GB)             │
│                                                          │
│  Subgraphs = {                                           │
│      G_static: [Linear_W8A8, LayerNorm_INT8, ...],       │
│      G_dynamic_chunk_i: [Attention_KQV_chunk_i, ...]     │
│  }                                                       │
└──────────────────────────────────────────────────────────┘

┌─ 阶段 2: IRFusion 算子融合 ────────────────────────────┐
│                                                          │
│  // Ascend 910B Da Vinci 架构的融合约束:                  │
│  // - Cube Unit: 矩阵乘/卷积 (固定数据流)                │
│  // - Vector Unit: 逐元素运算/激活函数/LayerNorm          │
│  // - 融合规则: 相邻且数据流兼容的算子合并为单指令流     │
│                                                          │
│  Fusion Patterns:                                        │
│    Linear → Reshape → Activation → Reshape               │
│      ↓ IRFusion 融合为                                   │
│    FusedLinearActivation (单 kernel, 无中间 HBM 读写)    │
│                                                          │
│    LayerNorm → Quantize → Dequantize                     │
│      ↓ IRFusion 融合为                                   │
│    FusedNormQuant (避免量化/反量化中间 tensor)           │
└──────────────────────────────────────────────────────────┘

┌─ 阶段 3: AscendC 代码生成 ─────────────────────────────┐
│                                                          │
│  // AscendC DSL → NPU 指令流 (推测性)                    │
│  // Da Vinci 架构: Cube Unit + Vector Unit 可并行执行    │
│                                                          │
│  // 指令流水线编排 (指令级并行 ILP):                     │
│  // T0: Cube Unit 执行 MatMul tile[k]                    │
│  //     Vector Unit 执行 Activation tile[k-1]            │
│  // T1: Cube Unit 执行 MatMul tile[k+1]                  │
│  //     Vector Unit 执行 Activation tile[k]              │
│  // 通过软件流水线实现计算单元并发                        │
│                                                          │
│  // 微算子并发 (ILP):                                    │
│  // 将 QKV projection 编译为:                            │
│  //   Cube Unit 流: Q_proj → K_proj → V_proj             │
│  //   Vector Unit 流: Q_reshape → K_reshape → V_reshape  │
│  // 两条指令流在 NPU 上交替发射，实现计算与数据重排重叠   │
└──────────────────────────────────────────────────────────┘
```

**注解**:
- **Da Vinci 架构约束**: Cube Unit 的固定脉动阵列数据流模式限制了可融合的算子形状——融合后矩阵维度必须对齐 Cube Unit 的硬件 tile 大小（通常 16×16 或 32×32）
- **Shadow Outlier Execution**: llm.npu 论文显示，NPU 整数计算 (W8A8) + CPU 浮点 outlier 补偿的异构执行模式可将模型精度损失控制在可接受范围（<0.3% outlier channels）
- **Out-of-order Subgraph Execution**: NPU/CPU 子图乱序调度消除 37% 的 bubble rate，NPU 执行时间通常是 critical path（Qwen1.5-1.8B 中 NPU 315ms vs CPU ~150ms）
- **笔记局限性**: 笔记中关于 AscendC 的具体指令格式、Cube Unit 的精确微架构参数（MAC 数量、tile buffer 大小）尚未覆盖——以下内容基于 CANN 公开文档和 NPU 论文的推断

### 2.2 NPU 的 Tiling 策略与 Buffer 划分的编译时决策

**方法细节**（推断性重建）:

```
Ascend NPU Tiling 编译时决策:

硬件约束 (Ascend 910B, 推测):
  - Cube Unit 矩阵乘 tile: 16×16 (FP16) 或 32×32 (INT8)
  - Vector Unit 向量宽度: 256-bit (FP16×16 SIMD)
  - L1 Buffer (等效 shared memory): ~192KB per AI Core
  - HBM Bandwidth: ~1.2 TB/s

编译时 Tile Size 选择:
  for M_tile in {16, 32, 64, 128}:    // 输出行 tile
      for K_tile in {16, 32, 64}:     // 内积维度 tile
          for N_tile in {16, 32, 64, 128}:  // 输出列 tile
              // 评估:
              mem_footprint = M_tile*K_tile + K_tile*N_tile + M_tile*N_tile
              if mem_footprint > L1_Buffer_Size: continue
              
              // Cube Unit 利用率 = 实际 MAC 操作数 / 理论峰值 MAC
              cube_util = (M_tile*K_tile*N_tile) / (tile_cycles * MACs_per_cycle)
              
              // Vector Unit 利用率: 逐元素操作并行度
              vec_util = (M_tile*N_tile) / (vec_width * vec_cycles)
              
              score = α*cube_util + β*vec_util + γ*(1 - mem_footprint/L1_Buffer)
              // 选择 score 最大的 tile 配置

多算子并发的 Tiling 决策:
  // 当多个小算子并发时，编译器需联合分配 L1 Buffer:
  // Op_A 分配 M_A×K_A tile → buffer_A KB
  // Op_B 分配 M_B×K_B tile → buffer_B KB
  // 约束: buffer_A + buffer_B + ... ≤ L1_Buffer_Size
  // 编译器需在线性规划求解与启发式搜索间权衡
```

**注解**: NPU 上多算子并发的核心限制是 Cube Unit 和 Vector Unit 共享同一指令发射槽——不同于 GPU 的多 warp 并发和多 SM 并发，NPU 的并发度取决于编译时能否将多个算子编排为 Cube/Vector 交替执行的指令流（类似 VLIW 的显式并行）。笔记未明确说明 Ascend 的并发 kernel 执行能力，此处为基于架构公开信息的推断。

## 3. TPU Codegen（XLA/SAX）：VLIW 指令编排与 SPMD 编译

### 3.1 XLA TPU Backend 的 SPMD Codegen

**笔记证据**: `knowledge_notes/编译知识笔记/GSPMD.md` (score: 41.8), `paper_secs/.../Lancet.../2-BACKGROUND-AND-MOTIVATION.md` (score: 187.1)

**方法细节**（L3 编译框架模拟——GSPMD 的 SPMD partition + collective 插入 + XLA backend codegen）:

```
XLA TPU Backend Codegen 流程:

┌─ 阶段 1: GSPMD Sharding Completion ────────────────────┐
│                                                          │
│  // 用户标注 (<1% tensors):                              │
│  // MoE expert weight: mesh_split(weight, mesh, [E, -1])│
│  // Multi-modal: mesh_split(vision_tokens, mesh, [B, -1])│
│                                                          │
│  // GSPMD 自动推导完整 sharding:                         │
│  // - 前向传播: 根据 op 语义推导 output sharding         │
│  // - 反向传播: 根据 output 约束推导 input sharding      │
│  // - 冲突时: 插入 Reshard (collective communication)    │
│                                                          │
│  // TPU 的关键约束: 所有 tensor shape 必须编译时确定     │
│  // → MoE 中需 padding expert capacity 到固定大小        │
│  // → 每个 expert 的 token buffer 大小编译时静态分配    │
└──────────────────────────────────────────────────────────┘

┌─ 阶段 2: Collective-Permute 与计算 Overlap ───────────┐
│                                                          │
│  // MoE All-to-All 编译为 SPMD collective-permute:       │
│  // TPU 的 ICI (Inter-Chip Interconnect) 支持:           │
│  //   - 2D/3D torus 拓扑上的直接芯片间通信               │
│  //   - collective-permute: 硬件加速的置换通信            │
│  //                                                      │
│  // 编译时 overlap 决策:                                 │
│  // T0: 发射 collective-permute (异步)                   │
│  // T1: 执行 Expert FFN on 已到达的 tokens (计算)        │
│  // T2: 等待 collective-permute 完成 (同步)              │
│  // 编译器插入 async.start → compute → async.done 包围   │
└──────────────────────────────────────────────────────────┘

┌─ 阶段 3: TPU VLIW 指令编排 ───────────────────────────┐
│                                                          │
│  // TPU VLIW 指令格式 (以 TPUv4 为例, 推测):             │
│  // 每个 VLIW bundle 可包含:                             │
│  //   - 1× Scalar op (控制流/地址计算)                   │
│  //   - 1× Vector op (VPU: 向量 ALU 操作)                │
│  //   - 1× Matrix op (MXU: 128×128 systolic array)       │
│  //   - 1× Data movement (DMA: CMEM↔HBM 传输)            │
│  //                                                      │
│  // 编译时显式并行编排:                                  │
│  // VLIW[t]: {                                           │
│  //   scalar:  address_calc_for_next_tile,               │
│  //   vector:  activation_fn(prev_tile_output),          │
│  //   matrix:  matmul(current_tile_A, current_tile_B),   │
│  //   dma:     prefetch(next_tile_A, next_tile_B)        │
│  // }                                                    │
│  // → 4 类操作在同一 cycle 内并发执行                    │
│  // → 编译器负责数据依赖分析和指令调度，无运行时开销     │
└──────────────────────────────────────────────────────────┘

┌─ 阶段 4: Scratchpad Memory 编译时静态分配 ────────────┐
│                                                          │
│  // TPU 使用 scratchpad memory (CMEM) 而非 cache:         │
│  // - 编译时分配所有 tensor 的 CMEM 地址                  │
│  // - 通过 liveness analysis 实现 buffer sharing         │
│  // - 多个并发 VLIW 操作共享 CMEM bandwidth               │
│  //                                                      │
│  // Scratchpad 静态分配的伪代码:                         │
│  for tensor in topological_order(graph):                 │
│      // Liveness analysis                                │
│      live_tensors = {t: t.live_at(tensor.time)}          │
│      // Find reusable buffer                             │
│      for buf in cmem_buffers:                            │
│          if buf.last_user_time < tensor.first_use_time:  │
│              reuse(buf, tensor)                          │
│              break                                       │
│      if not reused:                                      │
│          allocate_new_buffer(tensor.size)                │
│                                                          │
│  // 编译时即可确定: 无运行时 cache miss，延迟完全可预测  │
└──────────────────────────────────────────────────────────┘
```

**注解**:
- **静态调度 vs GPU 动态调度**: TPU 编译器的决定性优势是编译时确定一切（tensor shape、内存分配、VLIW 指令编排），运行时零调度开销——这与 GPU 的动态 thread block 调度形成对比。对于 Groq/Cerebras 等加速器也是一样的设计哲学
- **MoE 的 TPU 约束**: XLA/TPU 要求静态 tensor shape，这导致 MoE 中每个 expert 的 token capacity 必须编译时固定——未填满的 slot 浪费计算，溢出 token 被丢弃（token dropping）。这是与 GPU 上动态 expert 调度相比的劣势
- **Scratchpad vs Cache**: TPU 的 scratchpad memory 由编译器完全管理（类似 GPU shared memory 但跨整个芯片），编译器通过 liveness analysis 做 buffer sharing——这消除了 cache miss 的不确定性，但要求编译器对内存访问模式有完整知识

### 3.2 TPU 的并发模型——编译时决定，运行时无动态并发

**笔记证据**: `paper_secs/.../MegaBlocks.../1-INTRODUCTION.md` (score: 150.8)

TPU 不依赖运行时的多 kernel 并发（不像 GPU 的 CUDA stream/MPS）。编译框架将多算子并发表达为：
1. **VLIW 指令级并行**: 同一 bundle 内的 scalar/vector/matrix/DMA 操作并发执行
2. **SPMD 数据并行**: 通过 GSPMD 将计算分布到多个 TPU chip，每个 chip 执行相同程序但不同数据分片
3. **计算-通信 Overlap**: 编译器插入异步 collective-permute 并调度计算与之重叠

## 4. 加速器 Codegen（Groq/Cerebras）：确定性编译与空间映射

### 4.1 Groq LPU 的确定性编译

**笔记证据**: `paper_secs/.../52-RPU.../X.-RELATED-WORK.md` (score: 122.2), `paper_secs/.../18-Hardwired-Neuron.../1-Introduction.md` (score: 79.6), `paper_secs/.../48-Meta_s-Second-Generation.../Metas-Second-Generation...Meta.md` (score: 76.0)

**方法细节**（L3 编译框架模拟——Groq 确定性编译与空间映射）:

```
Groq Compiler 确定性 Codegen 流程:

┌─ 编译时阶段 (唯一阶段, 无运行时调度) ───────────────────┐
│                                                          │
│  // Groq 的核心理念: 所有并发由编译器静态决定             │
│  // 运行时: 零调度开销, 零同步开销, 零 cache miss         │
│                                                          │
│  Step 1: Operator → 芯片计算单元空间映射                  │
│  // Groq TSP (Tensor Streaming Processor) 架构:           │
│  //   - 片上 SRAM 为主内存 (无 HBM)                      │
│  //   - 数百个功能单元按 1D/2D 数据流排列                │
│  //   - 确定性 interconnect: 每个 cycle 的数据路由预计算  │
│                                                          │
│  for each operator in DAG:                               │
│      // 编译器决定:                                      │
│      //   - 该 operator 映射到哪些物理计算单元            │
│      //   - 输入数据来自哪些上游单元的哪个输出端口        │
│      //   - 输出数据发送到哪些下游单元的哪个输入端口      │
│      //   - 每个 cycle 的精确数据路由路径                │
│      spatial_mapping[op] = {                             │
│          compute_units: [cu_12..cu_47],                  │
│          input_routes:  [(cu_5, port_3), ...],           │
│          output_routes: [(cu_55, port_1), ...],          │
│          schedule: cycle_1042..cycle_2187                │
│      }                                                   │
│                                                          │
│  Step 2: 微算子并发通过空间映射天然支持                   │
│  // 不重叠的算子映射到不同计算单元 → 自动并发            │
│  // 重叠的算子通过时间分片 (time-multiplex) 串行         │
│  // 编译器保证: 无运行时资源冲突, 无 deadlock            │
│                                                          │
│  Step 3: 确定性指令流生成                                │
│  // 每个计算单元接收固定的指令序列 (SIMD 风格)            │
│  // 无分支预测, 无乱序执行, 无 cache hierarchy           │
│  // 指令流在编译时完全展开 (loop unrolling 到具体 cycle) │
└──────────────────────────────────────────────────────────┘

运行时 Groq LPU 执行:
  编译器输出 → 加载到芯片 SRAM 的指令 buffer
  → 芯片逐 cycle 执行预编排指令
  → 延迟完全确定: latency = f(model_graph, spatial_mapping)
  → 笔记显示: 70B 模型需要数百张 Groq 卡 (SRAM 密度限制)
```

**注解**:
- **SRAM 容量瓶颈**: 笔记显示 Groq 和 Cerebras 都放弃 DRAM/HBM 而使用片上 SRAM 作为主内存。SRAM 的低密度导致 70B 模型需要数百张 Groq 卡或 4 张 Cerebras WSE——硬件成本极高
- **确定性延迟优势**: 对于 latency-critical 场景（如实时 Video DiT 推理），Groq 的确定性编译消除了一切运行时抖动——延迟在编译时即可精确预测
- **与 GPU Codegen 的本质区别**: GPU codegen 生成的是"可能并发"的代码（CUDA stream 标注依赖，硬件运行时调度），Groq codegen 生成的是"确定并发"的指令流——所有并发已编译为空间-时间映射，无运行时决策

## 5. Codegen 的设计空间与最佳实践

### 5.1 动态并发 vs 静态并发

**笔记证据**: 综合前述所有笔记

```
Codegen 并发模型设计空间:

               动态并发                         静态并发
              (GPU CUDA)                  (TPU/Groq/Cerebras)
    ┌──────────────────────┐      ┌──────────────────────────┐
    │ 运行时 OS/硬件调度    │      │ 编译时编译器全权调度      │
    │ CUDA Stream/MPS/MIG   │      │ VLIW bundle/确定性指令流  │
    │ Thread Block Scheduler│      │ Spatial mapping           │
    │ 灵活性高, 开销大      │      │ 确定性高, 灵活性低        │
    │ 适合动态/不规则图     │      │ 适合静态/规则图           │
    └──────────────────────┘      └──────────────────────────┘

混合方案:
  ACS: 编译时标注 RW-segments + 运行时调度窗口
  CUDA Graph: 编译时静态化 DAG + 运行时单次 launch
  llm.npu: 编译时子图切分 + 运行时乱序子图调度
```

**最佳实践**:
- MoE 推理: GPU 上使用 CUDA Graph 静态化 expert FFN 链（如 expert 选择固定），TPU 上使用 GSPMD SPMD partition
- DiT 推理: 迭代 denoising loop 天然适合 CUDA Graph（每步结构相同）
- Video 模型: 帧级并行适合 GPU 多 stream 并发或 TPU SPMD
- 多模态: 异构编码器适合编译时 device placement（vision→GPU, text→NPU）

### 5.2 单 Kernel 内微算子并发 vs 多 Kernel 并发

**笔记证据**: `paper_secs/.../Task-Based-Tensor-Computations-on-Modern-GPUs.md` §2.2 (score: 1736.1)

```
单 Kernel 内微算子并发 (Warp Specialization):
  ┌──────────────────────────────────────┐
  │ 同一个 kernel, 同一个 SM:            │
  │   DMA Warp:     TMA_load → sA        │
  │   Compute Warp: wgmma(accum, sA, sB) │
  │   (并发, 同一 SM 内 warp 间并行)     │
  │                                      │
  │  优势: 零 kernel launch overhead      │
  │  劣势: 受单 SM 资源约束              │
  │        (registers/shared memory 共享)│
  │  适用: GEMM/Attention 等规则计算     │
  └──────────────────────────────────────┘

多 Kernel 并发 (CUDA Stream/MPS):
  ┌──────────────────────────────────────┐
  │ 多个独立 kernel, 不同 SM:            │
  │   Stream 0: kernel_expert_0 → SM0-13 │
  │   Stream 1: kernel_expert_1 → SM14-27│
  │   Stream 2: kernel_expert_2 → SM28-41│
  │   (并发, 跨 SM 的 kernel 间并行)     │
  │                                      │
  │  优势: 充分利用全部 SM               │
  │  劣势: kernel launch overhead        │
  │        (通过 CUDA Graph 缓解)        │
  │  适用: MoE 多 expert 并发推理        │
  └──────────────────────────────────────┘

编译时的选择决策:
  if kernel_register_usage < 64 && kernel_smem_usage < 48KB:
      // 小 kernel → 适合多 kernel 并发
      use_multikernel_concurrency()
  elif computation_is_GEMM_like && has_TMA_support:
      // 大 kernel + Hopper → warp specialization 微算子并发
      use_warp_specialization_with_TMA()
  else:
      // 大 kernel + 老架构 → 单 kernel, 最大化 occupancy
      use_single_kernel_max_occupancy()
```

### 5.3 计算-通信 Overlap 的 Codegen 模式

**笔记证据**: `knowledge_notes/kernel知识笔记/Software Pipeline (T.Pipelined).md` (score: 795.9), `knowledge_notes/硬件知识笔记/Tensor Memory Accelerator (TMA).md` (score: 12311.5)

```
编译时 Software Pipelining 的三种模式:

模式 1: cp.async (Ampere A100)
  // PTX 指令: cp.async.commit_group + cp.async.wait_group
  for k in range(0, K/T_K):
      cp.async.commit_group()          // 开始异步组
      cp.async(sA_next, gA + offset)   // 发射异步 copy (非阻塞)
      cp.async(sB_next, gB + offset)
      cp.async.wait_group(N-1)         // 等待前 N-1 组完成
      // ← 此时 gmem→smem copy 与下面的计算重叠 →
      mma(accum, sA, sB)              // Tensor Core 计算
      swap(sA, sA_next); swap(sB, sB_next)

模式 2: TMA (Hopper H100)
  // TMA 硬件完全独立于 CUDA Core
  // DMA warp: 单线程调用 TMA_load (非阻塞)
  // Compute warpgroup: mbarrier 等待 + wgmma
  // PIPE 深度: 通常 2-3 个 buffer
  // 特点: 无寄存器占用，支持多播 (同一数据→多个 SM)

模式 3: TileLang T.Pipelined (编译器自动)
  // TileLang 编译器自动分析循环依赖生成 pipeline schedule
  // Ampere: 自动使用 cp.async + commit_group
  // Hopper: 自动使用 TMA + mbarrier
  // T.Pipelined(Copy(i), GEMM(i)):
  //   → Copy(i+1) || GEMM(i)  交错执行
  //   → 编译器自动插入同步原语

编译时 Pipeline 深度选择:
  pipeline_depth = min(
      max_pipe_from_hardware,  // H100: 由 SMEM 大小决定
      ceil(TMA_latency / GEMM_latency),  // 隐藏 TMA 延迟
      smem_size / (tile_A_size + tile_B_size)  // SMEM 容量限制
  )
```

**注解**: Software pipelining 是实现计算-通信 overlap 的核心编译技术。TileLang 的 T.Pipelined 原语提供了硬件架构自适应的抽象——编译器根据目标 GPU 架构（Ampere→cp.async, Hopper→TMA）自动选择最优路径，这是 MLIR multi-target codegen 的一个良好实践案例。

### 5.4 多硬件后端的 Codegen 可移植性

**笔记证据**: `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md` (score: 371.9), `paper_secs/.../KernelEvolve.../KernelEvolve...Meta.md` (score: 4759.7)

MLIR 的 multi-target codegen 通过分层 dialect 抽象硬件并发能力：

```
MLIR Multi-target Codegen 的并发抽象层次:

高层 (与硬件无关):
  linalg.generic {parallel_iterator_types=[...]}  // 标注可并行维度
  scf.parallel (%i) = (%c0) to (%N) step (%c1)   // 显式并行循环
  scf.forall (%i) in (%N)                         // SPMD 风格并行

中层 (硬件类别相关):
  gpu.launch blocks(%bx,%by,%bz) threads(%tx,%ty,%tz)  // GPU 并发
  gpu.launch_func @kernel blocks in (...) threads in (...) // 已编译 kernel

底层 (硬件特定):
  nvvm (NVIDIA):  nvvm.barrier0, nvvm.shfl.sync      // GPU warp 同步
  rocm (AMD):     rocdl.workgroup.barrier             // AMD wavefront 同步
  spirv (Vulkan): spv.ControlBarrier                  // 跨平台 GPU 同步

异步并发 dialect:
  async.execute [%dep1, %dep2] { ... } → %token      // 异步 region
  async.await %token                                   // 等待异步完成
  // 编译器可决定: 满足依赖的多个 async.execute 并发执行
```

**注解**: MLIR 的 multi-target codegen 策略是**高层标注并发语义→中层映射到硬件并发原语→底层发射硬件特定指令**。这种分层设计的优势是同一套高层 IR 可编译到不同硬件后端，但劣势是难以充分利用各硬件的特殊并发能力（如 Hopper TMA 的 warp specialization 需要在中层插入 `gpu.launch` 不支持的细粒度 warp 控制）。
