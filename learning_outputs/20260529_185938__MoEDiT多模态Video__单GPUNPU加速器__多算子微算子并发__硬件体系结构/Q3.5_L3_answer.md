## 一、单GPU平台实验环境（NVIDIA H100/A100/L40S/RTX 4090）

### 方法1: MoE-CAP —— 编译框架无关的MoE系统基准评测实验

**笔记证据**: `experiment_notes/系统实验笔记/MoE-CAP_ Cost-Accuracy-Performance Benchmarking for Mixture-of-Experts Systems.md` (score: 1119.8)

**实验环境概述**: MoE-CAP 提供了一套与编译框架无关的自动化 MoE 系统评测流水线，覆盖从 consumer GPU 到 data center GPU 的完整硬件谱系，用于评估不同 serving 框架（vLLM、SGLang、MoE-Infinity、K-Transformers）在编译和调度 MoE 模型时的并发效率。

#### 框架运行模拟：MoE-CAP评测流水线全流程

```
=== 实验环境初始化 ===
Step 0: 实验配置声明
  - 硬件: {A100-80G-SXM4 (1×/2×/8×), A100-80G-PCIe (1×/4×/8×),
           H20 (8×), A6000 (4×), A5000, RTX 4090 (450W),
           Apple M3 Max, NVIDIA Orin AGX, Orin NX, DGX-H100 (10200W)}
  - 编译/运行框架: {vLLM, SGLang, MoE-Infinity, K-Transformers,
                    HuggingFace Transformers, Accelerate}
  - 模型: {Qwen3-30B-A3B, Qwen3-235B-A22B, DeepSeek-V2-Lite,
           Qwen1.5-MoE, DeepSeek-R1}
  - 数据集: {GSM8K, HumanEval, MMLU, ...}
  - 请求参数: batch_size ∈ [1, 64], input_tokens=variable, output_tokens=variable

Step 1: 模型加载与编译
  vLLM/SGLang 加载模型权重 → CUDA Graph 编译优化 →
  PagedAttention KV cache 初始化 →
  MoE expert 权重预加载至 GPU HBM

Step 2: CAP Profiler 植入 (编译时instrumentation)
  在每层 MoE layer 的 router 附近插入轻量级 probe:
  ├── 记录 forward pass 中每个 expert 的激活布尔值 𝟙[l,i]
  ├── 记录 router 输出的 top-k expert 索引
  ├── 记录当前 batch size 和解码延迟
  └── 兼容 CUDA Graph 编译 (最大 overhead 仅 2.7%:
      TTFT +8ms, TPOT +4ms)

Step 3: 请求注入与性能采集
  POST /cap-profiler → 推理执行 →
  ├── 计算 S_activated = n_layer × S_attn + Σ_l Σ_i 𝟙[l,i] × S_expert
  ├── 计算 S-MBU = (S_activated + S_KV) / (TPOT × B_peak)
  │   (模型带宽利用率——实际需要的数据量 vs 峰值 HBM 带宽)
  ├── 计算 S-MFU = (T_token × (F_attn + 2N_router + 2k_expert × N_expert)) / F_peak
  │   (模型 FLOPS 利用率——实际执行的 FLOPS vs 峰值 FLOPS)
  └── 采集硬件成本: C_hardware = C_GPU + C_CPU + C_Motherboard + C_DRAM + C_SSD

Step 4: 结果合成
  GET /cap-results → CAP 雷达图:
  ├── Cost 轴: $/token 或 W (能耗)
  ├── Accuracy 轴: Exact Match / F1 / Win Rate
  └── Performance 轴: TPOT / Throughput / S-MBU / S-MFU
```

**注解**:
- **CAP三维度指标**: Cost（硬件+能耗成本/token）、Accuracy（任务准确率）、Performance（延迟/吞吐/利用率）——这一框架将编译和调度决策的经济与物理成本显式量化，而非仅看延迟
- **S-MBU vs S-MFU**: S-MBU 是编译框架融合优化效果的关键指标——融合越好，需要从 HBM 读取的数据越少，S-MBU 越低（或 bandwidth utilization 越高）；S-MFU 衡量计算单元利用率——多算子并发越好，S-MFU 越高
- **批量大小对并发的影响**: 笔记显示 batch size 1→64 时，expert 稀疏性和实际带宽需求发生定量变化——这直接影响编译框架的融合和并发调度决策
- **多节点环境**: 2节点 × 8×H20 GPU、400 GB/s InfiniBand 互联，用于验证分布式编译的 SPMD partition 正确性

### 方法2: FlashAttention-2 / FlashInfer —— Kernel级编译优化实验

**笔记证据**: `experiment_notes/kernel实验笔记/FlashAttention-2 Faster Attention with Better Parallelism and Work Partitioning.md` (score: 651.6); `experiment_notes/kernel实验笔记/FlashInfer Efficient and Customizable Attention Engine for LLM Inference Serving.md` (score: 509.0)

**实验环境概述**: FlashAttention-2 和 FlashInfer 代表了两种不同粒度的"编译"实验——前者通过手写 CUDA kernel + CUTLASS 模板，后者通过 JIT 编译的 attention variant kernel 生成系统，在 A100/H100 上进行 kernel 级 benchmark。

#### 框架运行模拟：FlashAttention-2 Kernel Benchmark 实验

```
=== 硬件配置 ===
GPU: NVIDIA A100 80GB SXM4
  - 108 SMs, 每SM 192KB on-chip SRAM (合计 ~20.7MB L1/SMEM)
  - HBM 带宽: 1.5-2.0 TB/s
  - SRAM 带宽: ~19 TB/s (约 HBM 的 10×)
  - FP16/BF16 Tensor Core (matmul): 312 TFLOPs/s
  - FP32 CUDA Core (non-matmul): 19.5 TFLOPs/s
  - matmul:non-matmul 吞吐比 = 16:1 (关键: non-matmul FLOP 贵 16×!)

GPU: NVIDIA H100 80GB SXM (仅 forward+backward runtime benchmark)
  - 132 SMs, HBM 带宽 ~3.35 TB/s
  - 支持 TMA + WGMMA 异步指令 (但 FlashAttention-2 未使用)
  - FP8 Tensor Core: ~989 TFLOPs/s

=== Benchmark 配置 ===
Seq length: 512 / 1K / 2K / 4K / 8K / 16K
Batch size: 使总 tokens = 16K
Hidden dim: 2048
Head dim: 64 (32 heads) 或 128 (16 heads), causal/non-causal
数据类型: FP16 / BF16

=== 编译/执行管线模拟 ===
Step 1: CUTLASS 3.x 模板编译
  CUDA template → nvcc 编译 → PTX → SASS →
  kernel binary with block sizes B_r=128, B_c=128 (tuned for d=128)

Step 2: Thread Block 调度 (forward, parallelism over sequence length)
  对每个 (batch, head, row_block_i) 组合 launch 1 thread block:
  - 总 thread blocks = batch × heads × T_r = 2×16×64 = 2048
  - 2048 >> 108 SMs → occupancy 接近满载
  - 不同 thread block 处理不同 row block，无需通信

Step 3: Warp 内计算 (4 warps per thread block, split Q row-wise)
  每个 warp 持有 Q 的 32 rows, K/V 由所有 warp 共享:
  ├── S_warp = Q_warp × K_j^T [Tensor Core MMA, FP16→FP32]
  ├── m_new = max(m_old, rowmax(S_warp)) [CUDA Core reduction]
  ├── P_warp = exp(S_warp - m_new) [MUFU.EX2 instruction]
  ├── ℓ_new = exp(m_old-m_new)·ℓ_old + rowsum(P_warp) [CUDA Core]
  └── O_warp = diag(exp(m_old-m_new))·O_old + P_warp × V_j [Tensor Core MMA]
  关键: 无需 warp 间通信 → 每个 warp 独立计算 output slice

Step 4: 性能测量 (CUDA Event Timing)
  - FLOPs (forward) = 4 × seqlen² × head_dim × num_heads
    (causal mask 时 ÷2, 因为约一半 blocks 跳过)
  - FLOPs (backward) = forward FLOPs × 2.5
  - TFLOPs/s = FLOPs / (wall-clock time / 1e12)

Step 5: 结果对比 (A100, d=128, causal=False)
  ├── FlashAttention-2: ~210 TFLOPs/s (~67% of peak 312)
  ├── FlashAttention v1: ~105 TFLOPs/s (~34% of peak)
  └── PyTorch standard attention: ~21 TFLOPs/s (~7% of peak)
```

**注解**:
- **为什么 non-matmul FLOP 贵 16×**: A100 的 FP32 CUDA Core 峰值仅 19.5 TFLOPs/s，而 FP16 Tensor Core 峰值 312 TFLOPs/s——这意味着 softmax、normalization 等非矩阵乘操作成为瓶颈。FlashAttention 通过算法重组（在线 softmax、一次性 rescale）最小化 non-matmul FLOPs
- **Thread block 调度与 SM occupancy**: 2048 个 thread blocks 远超 108 SMs，实现近乎 100% occupancy——这是"多微算子并发"在 GPU 上的实际体现：大量独立 thread block 在不同 SM 上并发执行
- **Warp 内 split-Q 策略**: 相比 FlashAttention v1 的 split-K 方案（需 warp 间通信），split-Q 消除了 shared memory 通信开销，提升 ~2× throughput
- **编译时 tile size 选择**: B_r=128, B_c=128 是针对 head_dim=128 的调优结果——需平衡 SRAM 容量 (192KB/SM) 和 register 压力

### 方法3: PAT —— vLLM + Prefix-Aware Attention Serving 实验

**笔记证据**: `experiment_notes/系统实验笔记/PAT_ Accelerating LLM Decoding via Prefix-Aware Attention with Resource Efficient Multi-Tile Kernel.md` (score: 760.3)

**实验环境概述**: PAT 将编译优化思想（prefix tree 构建 → CTA partition → pack-forward-merge pipeline）应用于 vLLM serving 框架，在 A100/H100 上进行端到端 online serving 评估。

#### 框架运行模拟：PAT 端到端 Serving 实验

```
=== 硬件配置 ===
主测试: NVIDIA A100-SXM4-80GB 单卡
扩展测试: NVIDIA H100-SXM4-80GB (kernel benchmark)
分布式: 4×A100 (Qwen2.5-72B-Instruct, TP=2 PP=2)
软件栈: CUDA 12.4, PyTorch 2.7.0, vLLM v0.9.0

=== 实验工作负载 ===
模型: Llama-3-8B, Qwen3-8B, Qwen2.5-72B-Instruct, Qwen3-30B-A3B (MoE)
请求 Trace:
  - ToolAgent: tool/agent workload，含系统 prompt 共享
  - Conversation: 三层 prefix 结构的多轮对话

=== 编译/调度管线模拟 ===
Step 1: vLLM 启动
  VLLM_ATTENTION_BACKEND=PAT python -m vllm.entrypoints.openai.api_server
  --model Qwen3-8B --gpu-memory-utilization 0.95

Step 2: Pack Scheduler 并发调度 (每次 decode step)
  ├── 读取 vLLM paged KV cache block table
  ├── 构建 prefix tree: internal node = 多 query 共享 prefix 段
  ├── profit model 决策 split/merge 策略 → 生成 CTA partition
  │   (minimize 全局 KV cache 重复加载)
  ├── lazy update: block table 未变化时复用上次调度结果
  └── 与 pre-attention tasks (metadata preparation, QKV projection)
      异步重叠执行 (scheduler latency 比 pre-attention 低 42.3-49.6%)

Step 3: Pack-Forward-Merge Pipeline
  Pack: 将共享 prefix 的 query 分组
  Forward: 各组独立执行 prefix-aware attention
  Merge: 合并 partial results

Step 4: 关键性能指标采集
  ├── mean TTFT (Time To First Token)
  ├── mean TPOT (Time Per Output Token)
  ├── P99 TPOT
  └── SLO attainment rate

=== 实验结果 (Conversation trace, Qwen3-8B, 8 req/s) ===
  PAT vs FlashAttention:  mean TPOT -89.5%, TTFT -99.6%
  PAT vs FlashInfer:     mean TPOT -93.1%, TTFT -99.8%
  Qwen3-30B-A3B (MoE) 单卡 A100: TPOT -5.53~16.9%
  Qwen2.5-72B (4×A100): TPOT -14.3~26.7%
```

**注解**:
- **Pack Scheduler 与编译框架的关系**: PAT 的 pack scheduler 本质上是一个轻量级"编译时"调度器——在每次 decode step 前，将动态的共享 prefix 信息编译为静态的 CTA partition，实现类似 CUDA Graph 的 kernel launch 优化
- **Lazy update 机制**: 通过追踪 block table 变化，复用上次调度结果——这类似于编译框架中的增量编译（incremental compilation）策略
- **异步重叠的意义**: scheduler 在 CPU thread 上异步执行，与 GPU 上的 pre-attention 计算重叠——这是编译框架中"调度-执行 overlap"模式的实例化
- **MoE 场景的局限性**: MoE 模型 (Qwen3-30B-A3B) 上 TPOT 改善仅 5.53-16.9%，远低于 dense 模型的 89-93%——因为 MoE 的 expert routing 引入了 prefix 不可预测性，prefix tree 的有效性降低

### 方法4: Dense Training Sparse Inference —— MoE 编译部署实验

**笔记证据**: `experiment_notes/系统实验笔记/Dense Training, Sparse Inference Rethinking Training of Mixture-of-Experts Language Models.md` (score: 708.4)

#### 框架运行模拟：DS-MoE vLLM 部署 Benchmark

```
=== 硬件配置 ===
GPU: NVIDIA A100-80GB, H100-80GB
GPU memory utilization: 0.9 (vLLM 配置)
软件: vLLM (Kwon et al. 2023), HuggingFace Transformers

=== 实验模型 ===
DS-MoE-6B (6.5B total params, FP16, ~12.6 GiB GPU memory)
对比: Mistral-7B, DeepSeekMoE-16B, Qwen1.5-MoE-A2.7B

=== Benchmark 场景 ===
场景 A (vLLM Serving):
  input_tokens=1000, output_tokens=1000, continuous batching

场景 B (HF Transformers Latency):
  batch=64 sentences, 2000 tokens each, generate 20 tokens

场景 C (HF Transformers Input TPS):
  seq_len=256, max batch size fit in GPU memory

=== 编译/调度管线模拟 (vLLM 场景) ===
Step 1: LLMEngine 加载模型
  ├── Self-attention: dense inference (torch.nn)
  │   原因: attention 层 sparsity < 40%，密集计算更快
  └── MLP: sparse inference (SimpleMoE ParallelLinear)
      top-K expert 选择, Threshold-TopK 策略:
      先统计 batch 内平均激活 expert 数，再统一选 K 个

Step 2: Prefill 阶段
  1000 input tokens → batch forward pass →
  ├── Attention: PagedAttention KV cache 管理
  └── MoE: 每 token 选择 top-K experts，各 expert FFN 并发执行

Step 3: Decode 阶段 (autoregressive, 1000 output tokens)
  每步仅处理新 token + KV cache
  ├── KV cache: block-based 分页，minimize fragmentation
  └── Expert weights: 驻留 HBM，decode 循环中重复读取

Step 4: 关键指标
  ├── Throughput = requests completed / second
  └── TPS = total tokens (input + output) / second

=== 实验结果 ===
A100-80GB: DS-MoE-6B throughput 2.00 req/s, TPS 3992.8
  vs Mistral-7B: 1.86× 加速
  vs Qwen1.5-MoE-A2.7B: 1.50× 加速
H100-80GB: DS-MoE-6B throughput 2.30 req/s, TPS 4603.9
  vs Mistral-7B: 1.64× 加速
  vs Qwen1.5-MoE-A2.7B: 1.27× 加速
```

**注解**:
- **Attention 密集 vs MLP 稀疏的编译决策**: 笔记指出 attention 层 sparsity < 40% 时密集计算更快——这体现了编译框架中基于 profiling 数据的动态 dispatch 策略：不是所有层都适合稀疏化
- **Threshold-TopK 策略**: 在批量推理中，不同 token 可能选择不同 expert 集合——编译框架需决定是否 per-token 动态 launch expert kernel 还是统一 padding 后批量执行。Threshold-TopK 选择后者（统一的 K 个 expert），减少 kernel launch 次数但浪费部分计算
- **H100 上的加速比小于 A100**: H100 上 DS-MoE 相对 Mistral-7B 的加速比 (1.64×) 低于 A100 (1.86×)——因为 H100 更高的 HBM 带宽降低了 MoE 的稀疏计算优势（I/O bottleneck 在 H100 上减轻）

## 二、NPU平台实验环境（华为昇腾 Ascend 910B/910C/310P）

### 方法5: EPD-Serve —— Ascend NPU 多模态三阶段解耦实验

**笔记证据**: `experiment_notes/系统实验笔记/EPD-Serve A Flexible Multimodal EPD Disaggregation Inference Serving System On Ascend.md` (score: 2710.1); `paper_secs/secs_multimodal_kernel/EPD-Serve.../4-Evaluation.md` (score: 1262.7)

#### 框架运行模拟：EPD-Serve 实验环境全流程

```
=== 硬件配置 ===
服务器: 华为 Ascend Atlas 800I A2
  - 每 NPU 64 GB 片上内存 (HBM 等效)
  - 单机多 NPU 环境
  - AI Core (矩阵乘, MatMul) + AI Vector (向量/通信, AllReduce)
    功能单元分离，支持算子级并行

=== 编译/软件栈 ===
Baseline: vLLM v0.11.0 (monolithic: E/P/D 串行)
EPD-Serve 修改:
  ├── E/P/D 拆分为独立实例进程
  ├── Mooncake Store 多模态缓存池 (MM Store)
  ├── 事件驱动 hash 通知 + 异步特征预取
  ├── 分层分组 KV cache 传输 (延迟调度)
  └── 模态感知多路径路由

=== 实验模型与数据集 ===
模型: openPangu-7B-VL (ViT 0.7B + LLM 7B), Qwen3-VL-8B
数据集:
  - VisualWebInstruct: 512样本 (256 text-image + 256 text-only),
    图像 1280×720, 文本平均 63.1 tokens
  - ShareGPT-4o: 512样本, 图像 802×652, 文本平均 9.6 tokens
请求注入: AISBench @ 1-12 req/s
输出长度: 固定 64 tokens

=== SLO 约束 ===
Encode-disaggregated:  TTFT ≤ 2000ms, TPOT ≤ 80ms
Decode-disaggregated:  TTFT ≤ 2000ms, TPOT ≤ 50ms
严格 SLO:             TTFT < 800ms,  TPOT < 30ms

=== 部署拓扑空间 ===
EPD-Serve 支持 7+ 种部署拓扑:
  E-P-D:  三阶段全解耦 (3 NPU)
  EP-D:   Encode+Prefill 共置, Decode 独立 (2 NPU)
  (E-P)-D: E+P 物理共置+逻辑隔离, D 独立 (2 NPU)
  (E-D)-P: E+D 物理共置+逻辑隔离, P 独立 (2 NPU)
  (E-PD):  E 与 P+D 共置单 NPU (1 NPU)
  (E-PD)×2: 双 NPU 副本

=== 关键实验流程模拟 ===
Step 1: 多模态请求路由
  API Server 接收请求 →
  ├── 含图像/音频/视频 → E-P-D 完整管道
  └── 纯文本 → P-D 管道

Step 2: Encode + Prefill (共置 NPU 1, (E-P) 部署)
  ├── ViT 编码图像 I_m → V_m ∈ R^{n×3584}
  ├── 事件驱动异步发送特征 hash 到 Prefill listener
  ├── Prefill 从 MM Store 检索特征 (hash→feature vector)
  └── 拼接 V_m+V_t → LLM Prefill 计算 KVCache

Step 3: P-D 分层分组 KV 传输 (核心编译优化)
  当 Prefill 计算 L+1 层时, L 层 KVCache 异步传输至 Decode:
  ├── 多层 KV 分组打包 → 减少握手次数
  ├── 延迟调度 → 避免通信峰值
  └── 传输 overlap ratio: baseline 15.27% → optimized 98.78%
     (@ seq_len=1024)

Step 4: Decode 阶段 (独立 NPU 2)
  接收分层到达的 KVCache → 自回归生成 →
  独立 NPU 不受 E/P 干扰 → 稳定低 TPOT

Step 5: 算子级并发 (物理共置空间复用)
  NPU 1 上 E 与 P 共享 AI Core / AI Vector:
  ├── MatMul (AI Core, compute-heavy)
  └── AllReduce (AI Vector, communication-heavy)
  → 交替执行实现算子级并行

=== 实验结果 (openPangu-7B-VL @ 10 req/s) ===
                    NPUs  TTFT     TPOT    SLO达   Per-NPU
                                          成率    吞吐
  TP1×2             2     658.27   95.56   2.15%   13.38
  EP-D              2     5523.82  27.31   8.20%   21.54
  (E-P)-D           2     2386.85  28.40   26.17%  77.36
  E-P-D             3     557.89   28.92   94.34%  192.70
  (E-PD)×2          2     548.32   62.22   3.13%   19.70
```

**注解**:
- **Ascend NPU 的双功能单元架构**: AI Core (Cube Unit, 矩阵乘) 和 AI Vector (Vector Unit, 向量/通信) 分离——这是 NPU 与传统 GPU SIMT 模型的关键区别：NPU 编译框架可以在同一指令流中编排不同功能单元的操作，实现微算子并发
- **分层分组 KV 传输的编译意义**: 将逐层传输改为分组传输，本质是编译框架中的"通信聚合"优化——将多次小粒度通信合并为少次大粒度通信，提升带宽利用率 (1024 seq 下 +58%, 2048 seq 下 +10%)
- **物理共置 vs 逻辑隔离**: (E-PD) 在单 NPU 上实现 70% TPOT 降低——通过逻辑隔离避免资源竞争，同时物理共置实现空间复用。这是编译框架中 device placement 决策的实例
- **Per-NPU 吞吐归一化**: 笔记使用 per-NPU 归一化指标确保不同 NPU 数量部署的公平对比

#### 框架运行模拟：ElasticMoE 实验环境

```
=== 硬件配置 ===
超节点: 华为 CloudMatrix384
  - 384× Ascend 910C NPU (每颗 64 GB HBM)
  - 192× Kunpeng 920 CPU

  │   / aclrtMapMem (虚拟内存管理 expert 权重)
  └── disk-copy: 按名称/partition/layer 选择性磁盘加载

=== 实验模型 ===
DeepSeekV2 Lite, Qwen3-30B-A3B, DeepSeek V3

=== 关键实验: Scale-Up 4→6 NPU ===
Step 1: SLO-aware Load Estimator 检测 SLO < 90% → 触发 scale-up
Step 2: HMM 分析旧配置 DP2-TP2-EP4 → 新配置 DP3-TP2-EP6
Step 3: Attention 权重: NPU 0-3 通过 zero-copy 复用;
        NPU 4-5 通过 p2p-copy (HCCL) 从 NPU 0-1 异步传输
Step 4: Expert 权重: 全局 remap expert→NPU 映射,
        p2p-copy 迁移 + vpage-remap 更新映射
Step 5: IMM 从 LRU cache 取 6-NPU 推理实例,
        zero-copy 附加权重和 KV cache
Step 6: 流量切换 (零 downtime): 旧实例处理完 in-flight 请求后终止

=== 实验结果 ===
Scale-up latency: 2.43s (DP3→DP4, DeepSeek V2 Lite)
  ≈ 0.11× 最佳 baseline (Cold Restart 需数十秒)
```

**注解**:
- **CANN 图编译与 GE/IRFusion**: ElasticMoE 基于 CANN 的图编译引擎（Graph Engine, GE）和算子融合（IRFusion）——CANN 编译框架将 PyTorch 算子图编译为 Ascend NPU 可执行的计算图，自动进行算子融合和内存优化

### 方法7: SambaNova SN40L —— Dataflow 编译器实验环境

**笔记证据**: `experiment_notes/硬件实验笔记/SambaNova SN40L_ Scaling the AI Memory Wall with Dataflow and Composition of Experts.md` (score: 954.4); `experiment_notes/系统实验笔记/SambaNova SN40L_ Scaling the AI Memory Wall with Dataflow and Composition of Experts.md` (score: 9028.5)

#### 框架运行模拟：SN40L Dataflow 编译器实验

```
=== 硬件配置 ===
SN40L RDU (Reconfigurable Dataflow Unit):
  - TSMC 5nm 工艺, 2.5D CoWoS chiplet 封装
  - 计算: 638 BF16 TFLOPS, 1040 PCU + 1040 PMU
  - 存储: 520 MiB 片上 SRAM (PMU scratchpad)
           64 GiB co-packaged HBM (~1.8 TB/s)
           最高 1.5 TiB DDR DRAM (~200 GB/s, per socket)
  - 互连: RDN 2D mesh (vector/scalar/control 三种 fabric)
  - 时钟: < 2 GHz, die size < 650 mm²

实验节点:
  - 8-socket SN40L Node (Samba-CoE 实验,
    DDR→HBM 聚合带宽 > 1 TB/s)
  - 16-socket (Llama 3.1 推理)
  - 单 socket (FlashFFTConv benchmark)

对比平台:
  - DGX A100: 8×A100 80GB PCIe, 32 GB/s host-to-GPU
  - DGX H100: 8×H100 80GB, 64 GB/s host-to-GPU

=== 编译器配置 ===
三种 Kernel 执行模式 (编译器融合 × 调度器):
  1. Unfused: 每个 PyTorch operator 独立 kernel 执行,
     中间结果 materialize 到 HBM
  2. Fused + Software Orchestrated: 编译器自动融合 operator
     → 单一 kernel, host 软件调度
  3. Fused + Hardware Orchestrated: 编译器自动融合
     → 单一 kernel, AGCUs 硬件调度 (消除 host 软件开销)

=== 编译管线模拟 ===
Step 1: PyTorch 模型算子图输入
  (如 decoder layer: GEMM→Mul→Transpose→GEMM)

Step 2: 编译器空间融合 (Spatial Fusion)
  ├── Gemm0 → 多个 PCU 配置为 output stationary systolic array
  ├── 中间结果通过 RDN 流式写入 PMU stage buffer I0
  │   (partition 为 I00/I01 匹配带宽)
  ├── Mul → 另一组 PCU 以 pipelined SIMD 模式执行
  ├── Transpose → PMU data alignment unit
  │   diagonally striped write + normal read (零数据搬移!)
  └── Gemm1 → 更多 PCU 以 systolic array 执行

Step 3: AGCUs 硬件调度 (Fused+Hardware Orchestrated 模式)
  - 从 HBM 流式加载权重/激活
  - 硬件级别 kernel launch 编排 (消除 host→device 往返延迟)
  - 对 decode 阶段短 kernel 尤其关键

Step 4: 内存管理 (三级存储)
  - Router: 始终驻留 HBM
  - Expert weights: 存储于 DDR, 按需拷贝到 HBM
  - LRU 淘汰: 跳过 read-only weight 的回写 (静态垃圾回收)

=== 实验结果 (Samba-CoE, 150 experts > 1T params) ===
  BS=1, 20 output tokens:
    延迟对比: SN40L Node vs DGX A100 vs DGX H100
  BS=8, 200 output tokens:
    延迟 + 系统占用对比
  模型切换: SN40L DDR→HBM (>1 TB/s aggregate)
    vs DGX host→GPU (A100: 32 GB/s, H100: 64 GB/s)
  PCU 利用率: ~90%, HBM 带宽利用率: ~85%
```

**注解**:
- **Dataflow 编译 vs 传统编译**: SN40L 的编译器将整个 decoder layer 编译为单个 kernel launch——所有算子通过空间映射到不同 PCU/PMU 组，中间结果通过 RDN 流式传递而不回写 HBM。这消除了传统 GPU 上多次 kernel launch 的 overhead
- **硬件 Orchestrated Kernel Launch (AGCUs)**: 对于 decode 阶段的短 kernel (执行时间可能 < 10μs)，host 软件调度开销（~5-10μs per launch）成为瓶颈。AGCUs 在硬件层面管理 kernel 序列，消除了 host 参与——这是 Groq LPU 确定性调度的类似思想
- **静态垃圾回收**: 编译器通过符号生命周期分析，将非重叠生命周期的符号分配到相同设备虚拟地址——这类似于传统编译器的寄存器分配（graph coloring），但作用于 HBM 地址空间
- **TSMC 5nm + CoWoS**: 先进封装使 64 GiB HBM 与计算 die 紧耦合（~1.8 TB/s），这是 dataflow 架构可行性的物理基础——片上 SRAM (520 MiB) 虽小但带宽极高，配合 HBM 形成有效三级存储

## 五、关键 Profiling 工具与指标说明

### GPU Profiling 工具链

```
NVIDIA Nsight Systems (nsys):
  时间线视图 → kernel 执行序列, CUDA stream 并发度,
               kernel launch overhead, CPU-GPU 同步点
  用途: 分析编译框架生成的多 kernel 并发效率

NVIDIA Nsight Compute (ncu):
  单 kernel 详细分析 → SM occupancy, register usage,
                       shared memory usage, memory bandwidth,
                       instruction mix (Tensor Core/CUDA Core ratio)
  用途: 分析编译框架的 tile size / register allocation 质量

CUPTI (CUDA Profiling Tools Interface):
  编程接口 → 自定义 profiling, 嵌入编译框架
  用途: 编译框架内置性能采集 (如 XLA 的 HLO cost model)

torch.profiler:
  PyTorch 原生 → operator-level timeline,
                 memory consumption timeline
  用途: PyTorch 编译栈 (TorchDynamo + Inductor) 的端到端 profiling
```

### 各平台关键指标公式

| 指标 | 公式 | 含义 | 硬件侧重 |
|------|------|------|----------|
| S-MBU | $(S_{activated} + S_{KV})/(TPOT \cdot B_{peak})$ | 模型带宽利用率——编译融合越好，数据搬运越少 | HBM 带宽约束下的融合质量 |
| S-MFU | $(T_{token} \cdot (F_{attn} + 2N_{router} + 2k_{expert}N_{expert}))/F_{peak}$ | 模型 FLOPS 利用率——计算单元利用效率 | 计算单元（Tensor Core/Cube Unit）利用率 |
| TFLOPs/s | $4 \cdot seqlen^2 \cdot head\_dim \cdot num\_heads / time$ | Attention kernel FLOPS 吞吐 | GPU 计算峰值对标 |
| Bandwidth Utilization | $achieved\_bytes / peak\_bandwidth$ | HBM/SRAM 带宽效率 | 存储层次带宽利用 |
| Overlap Ratio | $(KV\_latency - exposed\_latency) / KV\_latency$ | 通信-计算重叠率 | NPU 算子级并发效率 |
| Occupancy | $active\_warps / max\_warps\_per\_SM$ | SM 占用率 | GPU 并发 kernel 的 SM 资源分配 |

**注解**:
- **S-MBU vs S-MFU 的综合意义**: 两者结合可诊断编译框架的瓶颈类型——高 S-MBU + 低 S-MFU = 编译受限于 HBM 带宽（需加强融合减少数据搬运）；低 S-MBU + 高 S-MFU = 编译受限于计算（可考虑更大 tile size 或更多并发 kernel）；双低 = 编译质量差
- **Overlap Ratio 在 NPU 场景的特殊性**: Ascend NPU 的 AI Core/AI Vector 分离架构使得通信-计算重叠成为可能的优化维度——这是 GPU 上通过 CUDA stream + async copy 实现的类似目标
