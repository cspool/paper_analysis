### 1.1 Triton — MoE Expert FFN 的 Tile-Level 并发实现

**笔记证据**: `experiment_notes/kernel实验笔记/SonicMoE Accelerating MoE with IO and Tile-aware Optimizations.md` (score: 1285.5)、`knowledge_notes/编译知识笔记/CUTLASS.md` (score: 4621.2)

#### 1.1.1 MoE Expert FFN Triton Kernel 伪代码

Triton 通过 block-level programming 将 MoE expert FFN 的 gather + GEMM + SiLU + down-proj 融合为单 kernel。以下是以 H100 为目标的 fused MoE kernel 伪代码：

```python
# ===== Fused MoE Forward Kernel (Triton) =====
# 输入:
#   x: [T, d]      FP16, T=总token数, d=hidden_dim=4096
#   W_gate: [E, d, 4d]  FP8 E4M3, expert gate投影矩阵
#   W_up:   [E, d, 4d]  FP8 E4M3, expert up投影矩阵
#   W_down: [E, 4d, d]  FP8 E4M3, expert down投影矩阵
#   topk_ids: [T, K]    INT32, 每token的top-K expert索引
#   topk_weights: [T, K] FP16, router weights
#   expert_offsets: [E+1] INT32, 每个expert的token偏移量
# 输出:
#   y: [T, d]      FP16

@triton.autotune(
    configs=[
        triton.Config({'BLOCK_M': 128, 'BLOCK_N': 128, 'BLOCK_K': 64,
                        'GROUP_SIZE_M': 8}, num_stages=4, num_warps=8),
        triton.Config({'BLOCK_M': 64,  'BLOCK_N': 256, 'BLOCK_K': 64,
                        'GROUP_SIZE_M': 8}, num_stages=4, num_warps=8),
    ],
    key=['T', 'd', 'E']
)
@triton.jit
def fused_moe_forward_kernel(
    x_ptr,          # [T, d] in HBM
    W_gate_ptr,     # [E, d, 4d] in HBM
    W_up_ptr,       # [E, d, 4d] in HBM
    W_down_ptr,     # [E, 4d, d] in HBM
    y_ptr,          # [T, d] output
    topk_ids_ptr,   # [T, K]
    topk_weights_ptr, # [T, K]
    expert_offsets_ptr, # [E+1]
    T, d, E, K,
    BLOCK_M: tl.constexpr,   # M tile size (tokens per block)
    BLOCK_N: tl.constexpr,   # N tile size (hidden dim)
    BLOCK_K: tl.constexpr,   # K tile size (inner dim)
    GROUP_SIZE_M: tl.constexpr,
):
    # --- PID 到 expert-tile 的映射 ---
    pid = tl.program_id(0)
    num_pid_m = tl.cdiv(T, BLOCK_M)
    num_pid_n = tl.cdiv(4 * d, BLOCK_N)  # 4d intermediate dim

    # L2 cache-friendly block ordering (grouped swizzle)
    group_id = pid // (num_pid_m * num_pid_n // GROUP_SIZE_M)
    first_pid_m = group_id * GROUP_SIZE_M
    group_size_m = min(num_pid_m - first_pid_m, GROUP_SIZE_M)
    pid_m = first_pid_m + (pid % group_size_m)
    pid_n = (pid % (num_pid_m * num_pid_n)) // num_pid_m

    # --- Block pointer 初始化 (TMA-like 语义, 单指针描述多维切片) ---
    # H100 TMA 硬件支持, Triton 通过 tl.make_block_ptr 表达
    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)  # [BLOCK_M]
    offs_n = pid_n * BLOCK_N + tl.arange(0, BLOCK_N)  # [BLOCK_N]
    offs_k = tl.arange(0, BLOCK_K)                     # [BLOCK_K]

    # --- Step 1: Token-to-Expert Gather (fused into SMEM load) ---
    # 使用 atomic_add 累加路由权重
    accumulator = tl.zeros([BLOCK_M, BLOCK_N], dtype=tl.float32)

    for e in range(E):
        # 检查该 expert 是否有 token
        expert_start = tl.load(expert_offsets_ptr + e)
        expert_end   = tl.load(expert_offsets_ptr + e + 1)
        num_tokens_e = expert_end - expert_start
        if num_tokens_e <= 0:
            continue

        # 加载该 expert 中 token 的 router weights
        # 通过 topk_ids 间接索引实现 gather
        token_indices = tl.load(topk_ids_ptr + expert_start +
                                tl.arange(0, BLOCK_M))  # [BLOCK_M]

        # --- Step 2: Gate Projection GEMM (FP8 × FP16 → FP32) ---
        # Tile-level: 沿 K dim 迭代
        gate_acc = tl.zeros([BLOCK_M, BLOCK_N], dtype=tl.float32)
        for k in range(0, d, BLOCK_K):
            # TMA async copy: x[token_indices, k:k+BLOCK_K] → SMEM
            a = tl.load(x_ptr + token_indices[:, None] * d +
                       (k + offs_k)[None, :])  # [BLOCK_M, BLOCK_K]

            # TMA async copy: W_gate[e, k:k+BLOCK_K, pid_n*BLOCK_N:...] → SMEM
            b = tl.load(W_gate_ptr + e * d * 4*d +
                       (k + offs_k)[:, None] * 4*d +
                       offs_n[None, :])  # [BLOCK_K, BLOCK_N]

            # FP8→FP16 dequant + Tensor Core MMA
            # H100: mma.m16n8k32 for FP8 (1979 TFLOPS peak)
            gate_acc = tl.dot(a, b, gate_acc)  # [BLOCK_M, BLOCK_N]

        # SiLU activation (element-wise, CUDA Core)
        gate_silu = gate_acc * tl.sigmoid(gate_acc)

        # --- Step 3: Up Projection GEMM ---
        up_acc = tl.zeros([BLOCK_M, BLOCK_N], dtype=tl.float32)
        for k in range(0, d, BLOCK_K):
            a = tl.load(x_ptr + token_indices[:, None] * d +
                       (k + offs_k)[None, :])
            b = tl.load(W_up_ptr + e * d * 4*d +
                       (k + offs_k)[:, None] * 4*d +
                       offs_n[None, :])
            up_acc = tl.dot(a, b, up_acc)

        # Element-wise: gate ⊙ up
        expert_hidden = gate_silu * up_acc  # [BLOCK_M, BLOCK_N]

        # --- Step 4: Down Projection GEMM ---
        down_acc = tl.zeros([BLOCK_M, d // BLOCK_N], dtype=tl.float32)
        # ... (类似上述 GEMM, 输出 [BLOCK_M, d])

        # --- Step 5: Router-Weighted Accumulation ---
        router_w = tl.load(topk_weights_ptr + expert_start +
                          tl.arange(0, BLOCK_M))  # [BLOCK_M]
        accumulator += router_w[:, None] * down_acc  # [BLOCK_M, d]

    # --- Epilogue: TMA store accumulator → HBM ---
    tl.store(y_ptr + offs_m[:, None] * d + tl.arange(0, d)[None, :],
             accumulator.to(tl.float16))
```

**注解**:
- **Block Pointer 语义**: `tl.make_block_ptr` 将 HBM 中的多维 tensor 切片（如 `x[token_indices, k:k+BLOCK_K]`）映射为单个 SMEM 缓冲区描述符。H100 TMA 硬件在后台执行异步 global→shared memory 拷贝（单线程发起、无寄存器中转），warp 可继续 MMA 计算——这正是 TMA 的核心价值。
- **Atomic Add 用于 routing**: Triton `tl.atomic_add` 映射为 GPU L2 cache 级别的 atomic 操作（H100 支持 SM→L2 atomic），直接在 L2 cache 中完成 token 到 expert 的 weighted accumulation，消除中间 HBM round-trip。原子冲突开销：随着 expert 数增大，多个 thread block 同时写入同一 output 行时 atomic contention 增加。
- **Shared Memory 分配**: `num_stages=4` 将 228KB SMEM 分为 4 个 pipeline stage（每个约 57KB），producer warp 填充 stage i 时 consumer warp 使用 stage i-3 的 MMA 数据。
- **复杂度分析**: 每个 expert 的 FLOPs = 2 · T_e · d · 4d · 3（gate+up+down GEMMs ≈ 6 T_e d²），total FLOPs = Σ_e 6 T_e d² = 6T d²（与 dense FFN 相同）。但 sparse MoE 通过 top-K 限制实际激活 expert 数实现参数容量与计算量解耦。
- **数据依赖**: 各 expert 的 GEMM 完全独立 → expert 间可并发；但 token gather 依赖 topk_ids 的间接寻址 → 需要 SMEM 中 prepend gather phase（cp.async 融合方式）。

#### 1.1.2 Ping-Pong Scheduling 指令流水线时序图

SonicMoE 在 H100 上使用 2 consumer warpgroups 实现 Ping-Pong 调度（笔记显示于 SonicMoE 的 dH kernel）：

```
时间轴 →   T0    T1    T2    T3    T4    T5    T6    T7    T8    T9
         ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
Producer │LD0  │LD1  │LD2  │LD3  │LD0' │LD1' │LD2' │LD3' │LD0  │LD1  │
(WG0)    │TMA  │TMA  │TMA  │TMA  │TMA  │TMA  │TMA  │TMA  │TMA  │TMA  │
         ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
Consumer0│     │MMA0 │MMA0 │MMA0 │EPI0 │     │MMA0'│MMA0'│MMA0'│EPI0'│
(WG1)    │     │iter0│iter1│iter2│SwiGL│     │iter0│iter1│iter2│SwiGL│
         ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
Consumer1│     │     │     │MMA1 │MMA1 │MMA1 │EPI1 │     │MMA1'│MMA1'│
(WG2)    │     │     │     │iter0│iter1│iter2│SwiGL│     │iter0│iter1│
         └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┘

LD: TMA load (HBM→SMEM, 1 thread initiates, non-blocking)
MMA: WGMMA instruction (Tensor Core, 4 warps/warpgroup)
EPI: Epilogue (SwiGLU activation + TMA store, CUDA Core)
```

**注解**:
- **Warpgroup 组织**: 每个 CTA 分配 3 个 warpgroups（1 producer + 2 consumer），共 12 warps（12 × 32 = 384 threads / CTA）。Producer warpgroup（4 warps）专责 TMA 数据搬运；Consumer0/1 各 4 warps，交替执行 MMA 和 epilogue。
- **寄存器分配**: Consumer 的每个 warpgroup 需要 2 组 accumulator register（128×2 = 256 registers），H100 每 SM 255 registers × 4 warps/warpgroup ≈ 1020 registers/warpgroup。两个 consumer warpgroups 共需 ~2040 registers，接近 H100 SM 的 65536 register 总量但分布在不同的 warp scheduler 槽中不冲突。
- **Occupancy 分析**: 12 warps / 64 max warps per SM = 18.75% theoretical occupancy。但 low occupancy 在此场景中是可接受的——因为 TMA 已消除 memory latency stall，Tensor Core 是计算瓶颈，而非 warp 调度。
- **Bank conflict 避免**: SMEM 分配按 128B aligned（H100 SMEM banking: 32 banks × 4B = 128B/cycle），4 pipeline stage 的 buffer 各自 128B 对齐以消除 bank conflict。

### 1.2 CUTLASS v3 — MoE Grouped GEMM + TMA + Persistent Kernel

**笔记证据**: `knowledge_notes/编译知识笔记/CUTLASS.md` (score: 4621.2)、`paper_secs/secs_moe/SonicMoE Accelerating MoE with IO and Tile-aware Optimizations/SonicMoE-Accelerating-MoE-with-IO-and-Tile-aware-Optimizations.md` (score: 3470.3)

#### 1.2.1 CUTLASS v3 Grouped GEMM 实现架构

CUTLASS v3 为 Hopper (SM90) 提供了原生 TMA + WGMMA + persistent kernel 支持。以下是 MoE grouped GEMM 的 kernel 架构：

```
CUTLASS v3 MoE Grouped GEMM Kernel 结构:

┌────────────────────────────────────────────────┐
│ Kernel Configuration (编译期模板参数)           │
│  - ElementA/B/C: cutlass::float_e4m3_t /       │
│                  cutlass::bfloat16_t            │
│  - TileShape: 128×128×64 (M×N×K per CTA)      │
│  - WarpShape: 64×64×64                         │
│  - InstructionShape: 16×8×32 (FP8 MMA)         │
│  - NumStages: 4 (pipeline depth)               │
│  - KernelScheduler: Persistent (SM persistent)  │
└───────────────────┬────────────────────────────┘
                    │
┌───────────────────▼────────────────────────────┐
│ Persistent Kernel 运行时调度 (每个 SM):         │
│                                                 │
│  while (work_tile = fetch_next_tile()) {        │
│    // ① TMA prologue: load first K-tile        │
│    tma_load<A>(gmem_A_tile, smem_A[stage]);     │
│    tma_load<B>(gmem_B_tile, smem_B[stage]);     │
│    mbarrier_arrive(smem_barrier[stage]);         │
│                                                 │
│    // ② Mainloop: iterate over K dim            │
│    for (k = 0; k < K; k += BLOCK_K) {          │
│      // issue next TMA load (async)             │
│      tma_load<A>(next_A, smem_A[next_stage]);   │
│      tma_load<B>(next_B, smem_B[next_stage]);   │
│                                                 │
│      // wait for current stage ready             │
│      mbarrier_wait(smem_barrier[cur_stage]);     │
│                                                 │
│      // WGMMA (async, non-blocking)             │
│      wgmma<FP8, m64nNk32>(                      │
│        smem_A[cur_stage],                         │
│        smem_B[cur_stage],                         │
│        accum_regs);                               │
│                                                 │
│      cur_stage = (cur_stage + 1) % 4;           │
│    }                                            │
│                                                 │
│    // ③ Epilogue: element-wise + store         │
│    wgmma_wait_group(0); // wait all MMA done   │
│    epilogue_fusion<SiLU>(accum_regs,            │
│                          smem_bias);            │
│    tma_store<C>(accum_regs, gmem_C_tile);       │
│  }                                              │
└────────────────────────────────────────────────┘
```

**注解**:
- **Persistent Kernel 设计**: 与传统 "grid-stride loop" 不同，persistent kernel 使用软件 work-queue（atomic counter in global memory）分配 tile 给 SM。每个 SM 的 CTA 持续运行，直到所有 tiles 被处理完毕。消除 kernel re-launch 开销（5-20μs/launch）。
- **TMA (Tensor Memory Accelerator) 硬件**: H100 专用 DMA 引擎，单线程发起 global→shared memory 传输，支持 1D-5D tensor 寻址。数据不经过 register file（直接 GMEM↔SMEM），减少寄存器压力。配合 `mbarrier`（asynchronous shared memory barrier）实现 producer-consumer 同步。
- **WGMMA 指令**: `wgmma.m64nNk32` 将 4 个 warp 编组为 1 个 warpgroup（128 threads），单指令完成 m64×nN×k32 的矩阵乘累加。异步发射（non-blocking）——warp 发射后立即返回可继续执行其他指令。
- **FP8 MMA**: E4M3 权重 × E4M3 激活 → FP32 accumulate。H100 FP8 Tensor Core 峰值 1979 TFLOPS，是 FP16 989.5 TFLOPS 的 2×。
- **Memory Hierarchy 数据流**: HBM(80GB, 3.35TB/s) →[TMA]→ SMEM(228KB/SM, ~19TB/s) →[WGMMA]→ RF(255 regs/thread) →[Epilogue]→ SMEM →[TMA store]→ HBM。

#### 1.2.2 Grouped GEMM Tile 调度策略

针对 MoE 中不同 expert 的 token 数（M 维度）变化极大（1~1000+ tokens/expert），CUTLASS v3 提供多种调度策略：

| 调度策略 | M tile 分配 | 适用场景 | 效率 |
|----------|------------|----------|------|
| **Fixed-Split** | 固定 M tile=128 对所有 experts | 负载均衡 (token evenly distributed) | 含 padding 浪费 |
| **Stream-K** | 沿 K 维度分解 work，动态分配 | 细粒度 M 分布 | 最优负载均衡 |
| **Token Rounding** | M 向上取整到 tile size 倍数 | SonicMoE 方案 | 消除 padding FLOPs + 保持 tile 对齐 |

**笔记证据**: SonicMoE 提出 Token Rounding routing——将 per-expert token 数舍入到 GEMM tile size (M_tile=128) 的倍数，消除 Grouped GEMM 中因 token 分布不均而产生的 padding FLOPs 浪费。

### 1.3 CUDA Graph — MoE 多 Expert Kernel Launch 并发

**笔记证据**: `knowledge_notes/系统知识笔记/CUDA Graph.md` (score: 4701.2)、`idea_notes/Mirage Persistent Kernel.md` (score: 1591.1)

#### 1.3.1 CUDA Graph 构建与 Launch 流程

```cuda
// ===== MoE 单请求 CUDA Graph 构建 =====
cudaStream_t stream;
cudaStreamCreate(&stream);

// --- Phase 1: Graph Capture ---
cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

// Node 1: Router kernel (1 SM grid, 快速完成)
router_kernel<<<1, 256, 0, stream>>>(x, W_gate, topk_ids, topk_weights);

// Node 2-9: Expert FFN kernels (8 experts, 可并发)
// CUDA Graph 自动识别无依赖关系 → 并发调度
for (int e = 0; e < 8; e++) {
    expert_ffn_kernel<<<grid, block, smem, stream>>>(
        x, W_gate[e], W_up[e], W_down[e],
        topk_ids, topk_weights, e, y);
}

// Node 10: Token aggregation kernel (依赖所有 expert FFN)
// 隐式: stream capture 检测到 y 的 RAW 依赖 → 串行化
aggregation_kernel<<<grid, block, 0, stream>>>(y, residual);

cudaStreamEndCapture(stream, &graph);

// --- Phase 2: Graph Instantiation (一次性) ---
cudaGraphInstantiate(&instance, graph, NULL, NULL, 0);

// --- Phase 3: Repeated Launch (每次推理) ---
// 仅一次 CPU→GPU 通信! (vs 11 次独立 launch)
cudaGraphLaunch(instance, stream);
cudaStreamSynchronize(stream);
```

**注解**:
- **Launch Overhead 降低**: 传统逐个 kernel launch 每个 ~5-20μs (H100, PCIe round-trip)。11 个 kernel (1 router + 8 expert FFN + 1 attention + 1 aggregation) 的 launch overhead 约 55-220μs。CUDA Graph replay 仅一次 launch，replay latency 约 2-5μs——overhead 降低 90-98%。
- **Kernel 并发**: CUDA Graph 构建时自动分析依赖 DAG——无依赖的 expert FFN kernel 可被 GPU 硬件调度器并发发射到不同 SM。H100 有 132 SM，8 个 concurrent expert kernel 可在不饱和情况下在 SM 上空间并发。
- **限制**: 动态 MoE routing（每 token 的 expert 选择不同）导致每次推理的 kernel 组合可能不同，需重新构建 graph（开销 40-100ms）。对此，MPK (Mirage Persistent Kernel) 采用 mega-kernel 方案——全模型编译为单个 kernel，避免 graph reconstruction。

#### 1.3.2 Kernel Launch Overhead Benchmark

**笔记证据**: `idea_notes/Mirage Persistent Kernel.md` 记录 MPK baseline (SGLang/vLLM + CUDA Graphs):
- Qwen3-8B decode iteration 含数百个 kernel launch（每个 op 一个 kernel）
- CUDA Graphs 可减少 launch overhead 但不能消除 kernel barrier bubble
- MPK mega-kernel 达到 12.5ms/decode iteration vs baseline 14.5ms (H100)

### 1.4 CANN/TBE/TIK — 昇腾 MoE Kernel 实现与调度

**笔记证据**: `knowledge_notes/硬件知识笔记/Ascend NPU Architecture (AI Core _ AI Vector _ Da Vinci).md` (score: 397.2)、`knowledge_notes/硬件知识笔记/Ascend 910B NPU.md` (score: 455.6)、`knowledge_notes/编译知识笔记/CANN.md` (score: 33.3)

#### 1.4.1 Da Vinci 架构 Kernel 调度模型

Ascend NPU 的三单元异构执行模型（AI Core + AI Vector + Scalar）：

```
CANN/TBE Kernel 编译与执行流程:

[PyTorch/MindSpore 模型定义]
        │
        ▼
[CANN GE (Graph Engine)]
  - IR lowering: 框架 IR → Ascend IR (类似 MLIR)
  - Operator fusion: 将相邻的 MatMul + SiLU + Mul 融合为单个 fused op
  - Tile 配置: 根据输入 shape 选择最优 tile size
        │
        ▼
[TBE (Tensor Boost Engine) / TIK (Tensor Iterator Kernel)]
  - TBE: 基于 Python DSL 编写算子，编译器自动 tiling + 生成 AI Core 指令
  - TIK: 更低级 C++ API，手动控制 AI Core/AI Vector 调度和 buffer 管理
        │
        ▼
[Ascend NPU 硬件执行]
  ┌─────────────────────────────────────────┐
  │ AI Core (Cube Unit)                     │
  │  - 16×16×16 MAC 阵列                    │
  │  - FP16: 每 cycle 4096 MAC operations   │
  │  - MatMul 专用 (类似 GPU Tensor Core)    │
  ├─────────────────────────────────────────┤
  │ AI Vector (Vector Unit)                 │
  │  - 256-bit SIMD 向量运算                 │
  │  - Element-wise ops (SiLU, Mul, Add)    │
  │  - AllReduce/通信算子                    │
  ├─────────────────────────────────────────┤
  │ Scalar Unit                             │
  │  - 程序流程控制 (branch, loop counter)   │
  │  - 标量地址计算                          │
  ├─────────────────────────────────────────┤
  │ MTE (Memory Transfer Engine)            │
  │  - HBM ↔ Unified Buffer 异步搬运         │
  │  - 支持远程 NPU 间 DMA (CoC)             │
  └─────────────────────────────────────────┘
```

**注解**:
- **三单元并发**: AI Core (MatMul) 和 AI Vector (element-wise) 和 Scalar (control) 可同时执行不同指令——EPD-Serve 利用此特性实现 operator-level 空间复用：MatMul 用 AI Core 的同时，AllReduce 用 AI Vector。
- **Cube Unit 约束**: 16×16×16 MAC 阵列决定 tile size 的最优选择为 16 的倍数。与 GPU Tensor Core 的 16×16×16 (FP16 MMA) 对齐，便于跨平台 kernel 移植。
- **Unified Buffer (UB)**: 256KB 片上缓存，类似 GPU shared memory。TBE/TIK 需要显式管理 UB 的 buffer 分配和 DMA 调度。
- **CoC (Communication over Computation)**: ETR 论文提出利用 MTE 的远程 DMA 能力，在 AI Core 执行当前 micro-batch 的 MatMul 时，MTE 同时发起下一 micro-batch 的 token 数据传输（计算与通信流水线重叠）。

### 1.5 XLA/TPU — JAX MoE/DiT Kernel 调度

**笔记证据**: `knowledge_notes/硬件知识笔记/TPU-v4 (Tensor Processing Unit v4).md` (score: 641.7)

#### 1.5.1 TPU v4/v5e/v5p 的 XLA Kernel 生成

TPU 的 kernel 调度完全由 XLA (Accelerated Linear Algebra) 编译器自动管理——用户通过 JAX 编写高级模型代码，XLA 负责 operator fusion、tiling、指令编排和 MXU 调度。

```
JAX 代码 → XLA 编译 → TPU 执行 流程:

# 用户代码 (JAX)
def moe_layer(x, router_weights, expert_weights):
    # Router: top-k gating
    gate_logits = x @ router_weights         # MatMul
    topk_idx, topk_w = lax.top_k(gate_logits, k=2)

    # Expert FFN (通过 vmap/scan 表达)
    def expert_fn(expert_weight, tokens):
        h = jax.nn.silu(tokens @ expert_weight[0])  # gate+up
        return h @ expert_weight[1]                   # down

    out = jax.vmap(expert_fn)(expert_weights, ...)
    return jnp.sum(out * topk_w[..., None], axis=-2)

# ↓ XLA 编译 (自动):
#   1. HLO (High-Level Optimizer) IR 构造
#   2. Operator fusion: gate+up matmul + SiLU + down matmul → single HLO fusion
#   3. Layout assignment: 为每个 tensor 分配最优 TPU memory layout
#   4. TPU backend: 生成 MXU 指令序列 (VLIW bundle)
#   5. Memory allocation: 为 tile buffer 分配 TPU VMEM (类似 SMEM)
#
# ↓ TPU v5e/v5p 硬件执行:
#   - MXU (Matrix Multiply Unit): 128×128 (v5e) / 128×128 (v5p) bfloat16
#   - VPU (Vector Processing Unit): element-wise, activation, normalization
#   - ICI (Inter-Chip Interconnect): 300 GB/s bidirectional, 2D/3D torus
```

**注解**:
- **VLIW 指令编排**: TPU 使用 VLIW (Very Long Instruction Word) 架构，XLA 编译器将 MXU 矩阵运算、VPU 向量运算和数据搬运指令打包为固定宽度的 VLIW bundle。这是与 GPU SIMT 的根本差异——TPU 依赖编译器的静态指令编排，而非 GPU 的 warp scheduler 动态调度。
- **MXU 128×128 tile 约束**: TPU v5e/v5p 的 systolic array 尺寸为 128×128 (bfloat16)，kernel tile size 必须是 128 的倍数才能充分利用 MXU。这比 GPU Tensor Core 的 16×16 tile 粗粒度很多——对于小 batch MoE（单 expert 少量 tokens），MXU 利用率可能极低。
- **GLaM 训练数据**: 1,024 TPU-v4 训练 1.2T 参数模型，计算利用率 50-62%（笔记显示 `knowledge_notes/编译知识笔记/GSPMD 2D Sharding.md`）。

> **S5 节点说明**: 笔记对 TPU v5e/v5p 的 MoE/DiT 具体 kernel benchmark 数据覆盖不足。笔记主要覆盖 TPU v4 (GLaM 训练)，v5 系列的推理场景实验数据在 vault 中缺失。

#### 2.3.1 核心指标定义

| 指标 | 公式 | 含义 |
|------|------|------|
| **MFU** (Model FLOPS Utilization) | actual_FLOPS / peak_hardware_FLOPS | 硬件算力利用效率 |
| **Kernel Occupancy** | active_warps / max_warps_per_SM | SM 上 warp 级并发度 |
| **TFLOPs** | FLOP_count / kernel_time × 10⁻¹² | 实测每秒浮点操作数 |
| **Latency** | kernel_exec_time + launch_overhead | 端到端 kernel 执行延迟 |
| **Memory BW Utilization** | actual_BW / peak_HBM_BW | HBM 带宽利用效率 |
| **Compute-Bound / Memory-Bound** | arithmetic_intensity ≷ FLOPs/BW_ratio | Roofline 分类 |

#### 2.3.2 MoE Roofline Model

**笔记证据**: 笔记显示 MegaScale-Infer 分析了 MoE decoding 的 roofline 瓶颈：

```python
# Roofline Model for MoE Decoding
# Dense FFN: utilization = min(B × F/B, 1)
#   where B = batch_size, F/B = operational_intensity
# MoE FFN:   utilization = min(top_k / num_experts × B × F/B, 1)

# 以 Mixtral 8×22B 在 A100 (312 TFLOPS, 2 TB/s) 为例:
B_dense_bound = 312e12 / 2e12 = 156 tokens  # compute-bound 的最小 batch
# MoE sparsity: top-2/8 = 25%
B_moe_bound = 156 / 0.25 = 624 tokens
# 当 batch=156 → per-expert batch=39 → MFU ≈ 39/156 = 25%
```

**注解**:
- **MoE 的 MFU 挑战**: 稀疏性（top-K/num_experts）将有效 batch per expert 除以稀疏度倍，导致 MoE 推理在相同硬件上更容易陷入 memory-bound。
- **Roofline 转折点**: H100 的 FLOPs/BW = 989.5e12 / 3.35e12 ≈ 295 FLOPs/Byte。算术强度 < 295 → memory-bound（受带宽限制），> 295 → compute-bound（受算力限制）。
- **kernel fusion 的价值**: 将多个算子融合为单一 kernel 可减少 HBM round-trip，使等效算术强度提升（减少分母中的 memory traffic），向右移动 roofline 曲线中的工作点。

## 4 是什么？（辅助说明）

> 各框架/方法的核心定位。

- **Triton**: OpenAI 开发的 GPU kernel 编程框架，提供 block-level 编程抽象和 automatic tiling。通过 MLIR-based Triton-IR 实现跨 NVIDIA/AMD GPU 的代码生成。核心创新是让开发者只需关注 tile-level 算法逻辑，编译器自动处理 shared memory allocation、loop unrolling 和 warp-level scheduling。
- **CUTLASS v3**: NVIDIA 的开源 CUDA C++ 模板库，将 GPU 线程层次映射到矩阵分块层次。v3 支持 Hopper 原生特性（TMA、WGMMA、FP8）和 persistent kernel。Stream-K 论文在 CUTLASS 中实现了新的 grid-level work decomposition，体现其模块化优势。
- **CUDA Graph**: NVIDIA 的 GPU 操作 DAG 定义和 replay 机制，消除重复 kernel launch 开销（5-20μs → 2-5μs per replay），适合静态推理图。限制是动态变化的工作流需重建 graph。
- **CANN/TBE/TIK**: 华为 Ascend NPU 的完整软件栈——CANN 对标 CUDA，TBE (Tensor Boost Engine) 提供 Python DSL，TIK (Tensor Iterator Kernel) 提供 C++ 低级 API。核心差异化是 Da Vinci 架构的 Cube/Vector/Scalar 三单元异构调度。
- **XLA/TPU**: Google 的全自动编译器驱动方案——用户编写 JAX 代码，XLA 负责算子融合、tiling、VLIW 指令打包和 MXU/VPU 调度。完全消除手工 kernel 编写需求，但牺牲了底层控制力。
