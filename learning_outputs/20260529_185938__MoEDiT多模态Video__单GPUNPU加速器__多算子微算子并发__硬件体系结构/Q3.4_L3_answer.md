## 一、XLA / OpenXLA（含 StableHLO / GSPMD）

### 1.1 是什么？

XLA（Accelerated Linear Algebra）是 Google 开发的深度学习编译器，作为 OpenXLA 项目的核心组件。其 IR 层为 HLO（High-Level Operations），经 StableHLO（跨框架 MLIR dialect）进入编译管线。GSPMD（Xu et al., 2021）是其编译器级自动并行化系统：用户仅标注 <1% 的图 tensor 的 sharding hint，编译器自动推导全图分区方案并插入 collective communication。XLA 核心设计为**全图编译**——整模型一次编译为硬件可执行代码。

**笔记证据**: `knowledge_notes/编译知识笔记/GSPMD (General and Scalable Parallelization for ML Computation Graphs).md`

### 1.2 编译框架执行模拟（XLA + GSPMD, MoE Expert Choice on 512 TPUv4）

```
═══════════════════════════════════════════════════════════════════
  XLA + GSPMD 编译流程模拟 — 6 阶段
═══════════════════════════════════════════════════════════════════

[Phase 1] User Annotation (输入 <10 个 key tensors 的 sharding hint)
┌─────────────────────────────────────────────────────────────┐
│ mesh = Mesh(devices.reshape(8, 64), ('expert', 'hidden'))   │
│ sharding_W_expert = NamedSharding(mesh, P('expert', None))  │
│ # W_expert[E=64, M=8192, H=32768] → dim 0 沿 expert 轴切   │
│                                                             │
│ sharding_X = NamedSharding(mesh, P(None, 'hidden'))         │
│ # input[B, S=1024, M=8192] → hidden 维沿 64 devices 切      │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 2] Sharding Completion Pass (优先级队列约束传播, O(N) 图节点)
┌─────────────────────────────────────────────────────────────┐
│ PriorityQueue<HloInstruction*> worklist;                    │
│ while (!worklist.empty()):                                  │
│   inst = worklist.pop()     # elementwise 优先, MatMul 次之 │
│   infer_output_sharding(inst):                               │
│     for each operand: propagate_sharding(op, op_semantics)   │
│     for each user:    propagate_sharding_backwards(user)     │
│   if conflicting_sharding_constraints:                       │
│     insert_reshard(AllReduce/AllGather/ReduceScatter/All2All)│
│                                                             │
│  MoE router: softmax(gate(X)) → expert_probs[B,S,E=64]     │
│    X沿hidden切 → gate权重沿hidden切 → output [B,S,E]       │
│    E维需要沿expert mesh轴分布 → 插入 All-to-All(dispatch)   │
│                                                             │
│  Expert FFN: All-to-All(token→expert device) →              │
│    @expert_FFN(local_tokens; local_expert_weights) →        │
│    All-to-All(expert_output→original_device) ← combine      │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 3] SPMD Program Generation
┌─────────────────────────────────────────────────────────────┐
│ for device_d in 0..511:                                     │
│   local_ops = extract_per_device(complete_sharding_schedule) │
│   for collective in [AlltoAll, AllReduce, ...]:             │
│     insert before/after local_ops based on dependency       │
│                                                             │
│ 所有 512 devices 执行同一 program，各处理不同数据分片:       │
│   Device(0,0): tokens routed to expert 0, FFN(0)            │
│   Device(0,1): tokens routed to expert 1, FFN(1)            │
│   ...                                                       │
│   Device(7,63): tokens routed to expert 63, FFN(63)         │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 4] XLA Fusion Pipeline
┌─────────────────────────────────────────────────────────────┐
│ HLO Graph (per-device)                                      │
│   ↓ Instruction Fusion:                                     │
│       dot(W, X) + bias_add + gelu → single fusion_computation│
│       融合条件: producer-consumer, 无多用户 fork             │
│   ↓ Multi-Output Fusion:                                    │
│       same_input→[gate_proj_W, up_proj_W] → 合并双GEMM kernel│
│       融合条件: 共享输入、输出shape兼容、无跨 fusion 依赖     │
│   ↓ Layout Optimization: NCHW→NHWC, BF16 layout canonicalize │
│   ↓ Memory Planning: buffer liveness → in-place reuse        │
│   ↓ Async Op Scheduling:                                     │
│       async_all-to-all(token) || expert_ffn_compute(tile)    │
│       xla_gpu_enable_latency_hiding_scheduler=true ← env flag│
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 5] GPU/TPU Codegen
┌─────────────────────────────────────────────────────────────┐
│ GPU 路径:                                                    │
│   HLO → LHLO (Late HLO, 显式化 buffer)                      │
│       → Thunk IR (执行单元序列, 类似 command list)           │
│         Thunk_AlltoAll → Thunk_FFN → Thunk_AlltoAll_combine  │
│       → CUDA kernel (via ir_emitter)                         │
│                                                             │
│ TPU 路径:                                                    │
│   HLO → TPU HLO → VLIW instruction bundles                  │
│   collective-permute + compute 重叠（SPMD 原生支持）          │
│   SPMD partition: 每 device 的 local program 独立编译        │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 6] Executable → Runtime (伪时间线)
T=0ms:  Host→Device: load executable on 512 devices
T=1ms:  [Device 0..511]: All-to-All dispatch (async, 通信与计算重叠)
T=2ms:  [Device 0..511]: Expert FFN compute (fused gate/up/down GEMM)
T=3ms:  [Device 0..511]: All-to-All combine (async)
T=4ms:  [Device 0..511]: LayerNorm + residual (elementwise fused)
T=5ms:  Barrier: 所有 device 完成 → 下一 MoE layer
```

### 1.3 注解

- **变量含义**: `device_mesh=[8, 64]` 表示 512-device 8×64 逻辑网格；`P('expert', None)` 表示 dim 0 沿 expert mesh axis 切分，dim 1 不切
- **复杂度分析**: Sharding Completion 单 pass 约束传播 O(N)（N = 图 HLO instructions 数）；2048 TPUv3 编译 <1 min；GLaM 1.2T MoE 用 while_loop 包装避免编译膨胀
- **数据依赖**: SSA 依赖天然定义并发 region——无数据依赖的 HLO instructions 理论上可并发，但 XLA 传统 Thunk executor 串行执行。GSPMD 通过 SPMD 引入 device 级并发（所有 device 同时执行），同一 device 内仍以串行 kernel 为主
- **并发可行性**: `async_all-to-all` 与 compute kernel 的 overlap 依赖 `xla_gpu_enable_latency_hiding_scheduler`（实验性 flag）。**笔记未明确说明 GPU backend 上 async all-to-all 的完整生产就绪状态**
- **硬件侧重**: GSPMD 的 2D sharding 针对 TPU v4 2D torus 拓扑优化——device mesh axis 映射到物理 torus 的 row/column，使 All-to-All 沿最短物理路径

## 二、TVM（Relay → TensorIR → Unity/Relax）

### 2.1 是什么？

Apache TVM（Chen et al., OSDI 2018）为端到端深度学习编译器栈，三层 IR：**Relay IR**（高层计算图，支持 `parallel` annotation）、**TensorIR**（低层张量程序 IR，支持 `block` + `buffer` + `parallel`/`vectorize`/`unroll` 显式标注）、**Relax IR**（TVM Unity 的动态形状 IR）。核心理念是 compute/schedule 分离。

**笔记证据**: `knowledge_notes/编译知识笔记/RAF Compiler (Relay Ahead-of-time Framework for Training).md`

### 2.2 编译框架执行模拟（TVM AutoScheduler, MoE 8 experts on A100）

```
═══════════════════════════════════════════════════════════════════
  TVM 编译流程模拟 — 5 阶段
═══════════════════════════════════════════════════════════════════

[Phase 1] Relay IR — 高层图 + 并发标注
┌─────────────────────────────────────────────────────────────┐
│ fn @moe_layer(%x: Tensor[(B,S,D), float16]) {                │
│   %norm = nn.layer_norm(%x)                                  │
│   %gate_logits = nn.dense(%norm, W_gate)  // gating          │
│   %probs = nn.softmax(%gate_logits)                          │
│   %topk_indices, %topk_weights = top_k(%probs, k=2)         │
│                                                             │
│   // Relay parallel region — 8 experts 可并发                │
│   %expert_outputs = parallel(%norm, %topk_indices) {         │
│     %e0 = @expert_ffn_0(%norm, W_e0)                        │
│     %e1 = @expert_ffn_1(%norm, W_e1)                        │
│     ...  // 编译器通过依赖分析确认 8 个分支无数据依赖        │
│     %e7 = @expert_ffn_7(%norm, W_e7)                        │
│   }                                                          │
│                                                             │
│   %combined = weighted_sum(%expert_outputs, %topk_weights)   │
│   %out = %x + %combined  // residual                        │
│ }                                                            │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 2] TensorIR Lowering — 微算子级并发调度
┌─────────────────────────────────────────────────────────────┐
│ @T.prim_func                                                │
│ def expert_ffn(X: T.Buffer[(B*S, D), "float16"],            │
│                W_gate: T.Buffer[(D, 4*D), "float16"],       │
│                W_up: T.Buffer[(D, 4*D), "float16"],         │
│                W_down: T.Buffer[(4*D, D), "float16"],       │
│                Y: T.Buffer[(B*S, D), "float16"]):           │
│                                                             │
│     # 水平融合: gate_proj + up_proj → 同一 tile 循环        │
│     for by in T.parallel(B*S // block_M):   # parallel 轴   │
│         for bx in T.parallel(4*D // block_N): # parallel 轴 │
│             with T.block("gate_up_gemm"):                    │
│                 vi, vj = T.axis.remap("SS", [by*BM, bx*BN]) │
│                 T.block_attr({"vectorize": 4})               │
│                 for vk in T.serial_range(D // block_K):      │
│                     Y[vi, vj] += X[vi, vk] * W_gate[vk, vj] │
│                     Y[vi, vj+4D] += X[vi, vk] * W_up[vk, vj]│
│                                                             │
│     # 垂直融合: SiLU + elementwise_mul + down_proj           │
│     for by in T.parallel(B*S // block_M):                    │
│         with T.block("silu_mul_down"):                       │
│             ...                                              │
│                                                             │
│ # 调度决策:                                                  │
│ #   T.parallel: 沿 M 和 N 维的 tile 在不同 SM 上并发执行    │
│ #   T.vectorize(4): 128-bit SIMD load/store (4×float32)     │
│ #   期望并发 tile 数 ≈ (B*S/128)×(4D/128)                   │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 3] AutoScheduler — Evolutionary Search + Measured Tuning
┌─────────────────────────────────────────────────────────────┐
│ Compute DAG → Sketch Generation → Evolutionary Search       │
│                                                             │
│ Search Space per block:                                      │
│   tile_structure = product(                                   │
│     [32, 64, 128, 256],    # tile_M 候选                    │
│     [32, 64, 128],         # tile_N 候选                    │
│     [8, 16, 32]            # tile_K 候选                    │
│   )                                                         │
│   loop_attributes ∈ {parallel, vectorize, unroll, bind}     │
│   memory_scope ∈ {global, shared, local}                    │
│   thread_binding ∈ combinations(threadIdx.x/y/z, blockIdx)  │
│                                                             │
│ Evolution (N generations):                                   │
│   1. random_sample(population_size=128) → compile+measure    │
│   2. train XGBoost cost_model on measured data              │
│   3. select top_k elite → crossover + mutation → new batch  │
│   4. measure top candidates on hardware → update model       │
│   5. repeat until convergence                               │
│                                                             │
│ Joint Tuning (多算子并发):                                   │
│   for concurrent_kernels = [k1, k2, ..., k8]:               │
│     cost_model.predict(joint_config) penalizes:              │
│       - SM oversubscription (total blocks > SM×max_blocks)   │
│       - HBM BW oversubscription (> 80% peak)                │
│       - Register pressure (per-SM reg > 65536)               │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 4] Codegen → CUDA Kernel
┌─────────────────────────────────────────────────────────────┐
│ TensorIR → CUDA C++ template:                                │
│   T.parallel(axis=0) → blockIdx.x                           │
│   T.parallel(axis=1) → blockIdx.y                           │
│   T.vectorize(4) → float4 load/store                        │
│   T.bind(threadIdx.x) → thread-level parallel               │
│   shared memory alloc → __shared__ float tile[BLOCK_M][BLOCK_N]│
│   sync insertion → __syncthreads() at block boundary        │
│                                                             │
│ Multi-kernel Stream Assignment:                              │
│   expert_0_ffn → cudaStream_t s[0], SM[0..17]               │
│   expert_1_ffn → cudaStream_t s[1], SM[18..35]              │
│   expert_2_ffn → cudaStream_t s[2], SM[36..53]              │
│   ...  // 8 streams, 每 stream ~16 SM                       │
│   cudaStreamWaitEvent(main, s[i], event_expert_i_done)      │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 5] Runtime 执行 (伪时间线, A100, single inference step)
T_compile: 122s (cold, 8 expert cores + gating kernel)
            5s (warm, cached tuning logs)
T_exec:
  T0:    gating_kernel (softmax+topk)        Stream 0, SM[0..7]
  T0+5μ: expert_kernels × 8                  Streams 1-8, 并发
  T1:    combine_kernel (weighted_sum)        Stream 0, 等待 events
  T2:    layernorm + residual                 Stream 0
```

### 2.3 注解

- **数据结构**: `T.block` 为计算原子单元（指定计算逻辑 + 数据访问 region）；`T.buffer` 为显式内存抽象（带 scope: global/shared/local）；buffer 的 producer-consumer 关系自动建立依赖 DAG
- **并发粒度**: Relay `parallel` annotation 实现**算子级并发**（多 CUDA stream）；TensorIR `T.parallel` 轴实现**微算子级并发**（tile 跨 SM 并行）
- **编译 vs 运行时**: AutoScheduler 搜索在编译时完成（以编译时间为代价），运行时零 profiling 开销。cost model（XGBoost）基于实测数据，比 XLA HLO cost model（纯启发式）精确但需目标硬件 runtime
- **硬件侧重**: cost model 针对 GPU 建模 SM occupancy + shared memory capacity + register file；NPU 需建模 Cube/Vector 单元利用率；TPU 需建模 systolic array bubble。Joint tuning 搜索空间随并发 kernel 数指数增长，实际采用贪心逐个 kernel tune + 联合验证

## 三、Triton（OpenAI Triton Language + Compiler）

### 3.1 是什么？

Triton（Tillet et al., MAPL 2019）核心理念：**block-level programming**——开发者以 Python DSL 写 tile 级运算，编译器自动处理 thread 调度、memory coalescing、shared memory 管理。编译链：**Python → TTIR → TTGIR → LLVM IR → PTX**。已集成于 vLLM、SGLang、PyTorch Inductor backend。

**笔记证据**: `knowledge_notes/编译知识笔记/Triton (GPU Kernel Language and Compiler).md`、`knowledge_notes/编译知识笔记/Triton Language (GPU Kernel Programming).md`

### 3.2 编译框架执行模拟（Triton Autotuner, MoE Expert FFN on H100）

```
═══════════════════════════════════════════════════════════════════
  Triton 编译流程模拟 — 5 阶段
═══════════════════════════════════════════════════════════════════

[Phase 1] Python Kernel Source (block-level, @triton.jit)
┌─────────────────────────────────────────────────────────────┐
│ @triton.autotune(                                           │
│   configs=[                                                 │
│     Config({'BLOCK_M': 64,  'BLOCK_N': 64,  'BLOCK_K': 32},│
│            num_warps=4, num_stages=2),                      │
│     Config({'BLOCK_M': 128, 'BLOCK_N': 64,  'BLOCK_K': 64},│
│            num_warps=8, num_stages=3),                      │
│     Config({'BLOCK_M': 128, 'BLOCK_N': 128, 'BLOCK_K': 32},│
│            num_warps=8, num_stages=4),                      │
│     ... // 20+ candidates                                   │
│   ], key=['M', 'N', 'K'])                                   │
│ @triton.jit                                                 │
│ def grouped_gemm_kernel(                                    │
│     a_ptr, b_ptr, c_ptr,                                    │
│     expert_offsets,        # [E+1], per-expert token offset │
│     M, N, K,                                                │
│     BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr,           │
│     BLOCK_K: tl.constexpr):                                 │
│                                                             │
│   pid_m = tl.program_id(0)  # grid axis 0: 沿 M 维并行      │
│   pid_e = tl.program_id(1)  # grid axis 1: 沿 expert 维并行 │
│                                                             │
│   # 每个 (pid_m, pid_e) 是一个并发 program instance         │
│   # 处理 expert pid_e 的 pid_m-th token tile                │
│   offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)          │
│   offs_n = tl.arange(0, BLOCK_N)                            │
│   offs_k = tl.arange(0, BLOCK_K)                            │
│                                                             │
│   acc = tl.zeros([BLOCK_M, BLOCK_N], dtype=tl.float32)      │
│   for k in range(0, K, BLOCK_K):                            │
│     a = tl.load(a_ptr + expert_offs + offs_m[:, None]*K +   │
│                  offs_k[None, :])  # [BLOCK_M, BLOCK_K]     │
│     b = tl.load(b_ptr + offs_k[:, None]*N +                 │
│                  offs_n[None, :])  # [BLOCK_K, BLOCK_N]     │
│     acc += tl.dot(a, b)            # Tensor Core MMA        │
│   tl.store(c_ptr + offs_m[:, None]*N + offs_n[None, :], acc)│
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 2] TTIR (Triton IR) — block-level IR, 保留并发信息
┌─────────────────────────────────────────────────────────────┐
│ 关键 TTIR 特性:                                              │
│   - program_id(axis): grid 维度的并发轴                      │
│     grid = (num_tiles_M, num_experts) → N instances 可并发   │
│   - num_warps: 编译时决定 per-CTA warp count                 │
│   - num_stages: software pipeline depth (Ping-Pong buffer)   │
│   - tt.load/tt.dot/tt.store: block-level ops                 │
│     tt.dot → 自动映射 Tensor Core (sm80: mma.sync,           │
│              sm90: wgmma.mma_async)                          │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 3] TTGIR (Triton GPU IR) — thread-level lowering
┌─────────────────────────────────────────────────────────────┐
│ TTIR → MLIR Pass Pipeline → TTGIR:                           │
│   a) Layout Conversion: block-level → per-thread register    │
│      tiling (distributed layout: warp×lane mapping)          │
│   b) Loop Unrolling: 根据 BLOCK_K 展平 K-dim inner loop      │
│   c) Memory Coalescing Analysis:                             │
│      重组 thread-to-address mapping → 连续地址 per warp      │
│   d) Shared Memory Allocation:                               │
│      自动分配 staging buffer → __shared__ float A_smem[...]  │
│   e) Sync Insertion:                                         │
│      cp.async.commit_group + cp.async.wait_group (sm80+)     │
│      __syncthreads() at tile boundary                        │
│                                                             │
│ TTGIR = per-"virtual thread" 执行序列 (类似 CUDA thread 视角)│
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 4] LLVM IR → PTX Codegen
┌─────────────────────────────────────────────────────────────┐
│ TTGIR → LLVM IR (MLIR LLVM dialect):                         │
│   NVIDIA:                                                    │
│     tl.dot → mma.sync.aligned.m16n8k32.row.col.f32.f16 (A100)│
│           → wgmma.mma_async.sync.aligned (H100 SM90)         │
│     tl.load → ld.global.nc.v4.f16 (coalesced 128-bit load)   │
│   AMD:                                                       │
│     tl.dot → mfma_f32_16x16x16_f16 (CDNA3)                   │
│     tl.load → global_load_dwordx4                            │
│                                                             │
│ PTX → GPU Driver JIT (cuModuleLoadData) → Executable         │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 5] Autotuner Runtime (按 key 参数做 benchmark)
┌─────────────────────────────────────────────────────────────┐
│ // 伪代码: Triton Autotuner 的 benchmark 流程                │
│ for config in candidate_configs:                             │
│   kernel = compile_with_config(config, BLOCK_M, BLOCK_N, ...)│
│   for _ in range(warmup_iters=25):                           │
│     kernel[grid](args...)                                    │
│   t0 = cudaEventRecord(start)                                │
│   for _ in range(bench_iters=100):                           │
│     kernel[grid](args...)                                    │
│   t1 = cudaEventRecord(stop)                                 │
│   latency = cudaEventElapsedTime(t0, t1) / bench_iters       │
│   cache[signature(M,N,K)] = (config, latency)                │
│                                                             │
│ best_config = argmin(cache, key=latency)                     │
│ return compiled_kernel(best_config)                          │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 注解

- **Triton 并发模型**: `program_id(0)` × `program_id(1)` 定义 2D grid——所有 (pid_m, pid_e) 对是**独立并发单元**（每对映射到一个 CTA），GPU warp scheduler 自动并发调度。这是 Triton 的核心并发优势：单 kernel 内所有 CTA 天然并发
- **跨 kernel 编排缺失**: Triton 无内置多 kernel 编排能力——同时执行 attention_kernel 和 ffn_kernel 需要外部调度器（CUDA Stream/PyTorch scheduler/CUDA Graph）。这是其 vs TVM 的主要差异
- **Autotuner 机制**: `key=['M', 'N', 'K']`——当这些运行时参数值变化时重新 benchmark；否则使用缓存的最优配置。配置空间通常 20-50 candidates，benchmark 总时间 ~10-60s（per kernel shape）
- **tile 约束**: tile 尺寸需 2 的幂且 ≥16（编译器限制）；shared memory 上限 = 硬件 SM capacity（A100: 192KB max, H100: 228KB configurable），超出 → 编译失败
- **硬件侧重**: Triton 的 MMA instruction selection 架构感知——sm80→`mma.sync`, sm90→`wgmma`。但笔记明确指出 TMA 需 `tl._experimental_descriptor_load`（实验性），warp-specialized async pipeline 无法直接在 Triton 表达——这是 vs CUTLASS CuTe 的核心差距
- **bank conflict**: TTGIR lowering 阶段自动做 shared memory padding（加 padding column 使 stride ≠ 32×4B 倍数）

## 四、MLIR（Torch-MLIR / IREE / 多 Dialect 生态）

### 4.1 是什么？

MLIR（Multi-Level Intermediate Representation）是 LLVM 项目的编译器基础设施，核心理念**多 dialect 分层架构**——每个 dialect 定义特定领域 operations/types，编译器通过 progressive lowering 将高层 dialect 逐步转换到低层 dialect。并发相关核心 dialect：**`gpu`**（GPU kernel launch）、**`async`**（异步执行+同步）、**`scf`**（结构化控制流，含 `scf.parallel`/`scf.forall`）、**`affine`**（polyhedral loop analysis）。

**笔记证据**: `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md`、`knowledge_notes/编译知识笔记/Kernel Fusion via MLIR (in Distributed Task-Based Runtimes).md`

### 4.3 注解

- **分层并发**: MLIR 的并发表达分布在多个 dialect——`async.execute`（token-based 异步执行）、`scf.forall`（数据并行）、`gpu.launch`（GPU 执行模型）。progressive lowering 过程中这些并发语义逐步转换为硬件同步原语
- **IREE HAL 并发管理**: HAL 的 command buffer 是对硬件 command queue 的统一抽象——无 barrier 的 dispatches 由 GPU 硬件自动并发（依赖 CUDA concurrent kernel execution 或 Vulkan async compute）。编译时确定 dispatch graph，运行时零调度开销
- **编译 vs 运行时**: 所有 dialect 转换和优化是纯编译时（包括 polyhedral fusion passes）——IREE 的 HAL command buffer 在编译时构建，运行时仅提交
- **硬件侧重**: MLIR 的 `gpu` dialect 是硬件无关的 GPU 抽象——lowering pass 针对 NVIDIA（nvvm）、AMD（rocdl）、Intel（spirv）各自生成 ISA。`async` dialect 的 token 模型在 GPU 上 lowered 为 CUDA event/stream，在 CPU 上 lowered 为 thread pool task graph
- **笔记缺失**: 笔记未提供 Torch-MLIR 对 `torch.cuda.Stream` 映射到 `async` dialect 的详细机制；IREE 在 GPU 上实际的 concurrent dispatch 支持度未量化

## 五、PyTorch 2.0 编译栈（TorchDynamo + TorchInductor + Triton Backend）

### 5.1 是什么？

PyTorch 2.0 编译栈 = TorchDynamo（bytecode-level FX graph capture）+ TorchInductor（loop-level IR + 融合决策 + Triton codegen）+ CUDA Graph（消除 launch overhead）。通过 `torch.compile(model, mode="max-autotune")` 一键启用。

### 5.3 注解

- **并发信息保留**: FX Graph 的 SSA 形式天然编码数据依赖——无依赖的 node 可标记为可并发。max-autotune mode 下 Inductor 自动探索 multi-stream 调度
- **FlexAttention 混合 codegen**: 用户 Python callable (`score_mod`/`mask_mod`) 被 Dynamo 捕获为子图，Inductor lower 为 Triton 代码块后注入到预写手工 attention kernel 模板主循环——这是"编译器生成 + 模板"的混合策略，突破纯编译器方法对 attention variant 优化的限制
- **CUDA Graph**: 将多次 kernel launch + event sync 编译为静态执行图，消除 launch overhead（5-15μs/kernel → ~3μs total per replay）。MagicDec 论文为 draft 和 verify 各预编译独立 CUDA Graph
- **硬件侧重**: Inductor 的 tiling heuristic 基于 SM shared memory capacity 和 register file size 做硬约束——H100 configurable SMEM = 228KB/SM, 65536 registers/SM

## 六、CUTLASS 3.x（NVIDIA CuTe DSL + Collective Abstraction）

### 6.1 是什么？

CUTLASS 3.x 引入 **CuTe DSL**——直接生成 PTX/SASS 的 C++ template-based DSL。核心特性：warp specialization（producer/consumer warp groups）、TMA async load、wgmma、Thread Block Clusters（DSM）、persistent tile scheduler。**与 Triton 根本区别**：CuTe 不走 MLIR 抽象，直接控制异步硬件操作的精确 timing。

**笔记证据**: `knowledge_notes/编译知识笔记/CUTLASS.md`、`knowledge_notes/编译知识笔记/CuTe-DSL (CUTLASS CuTe DSL).md`

### 6.2 编译框架执行模拟（SonicMoE varlen-M Grouped GEMM on H100 SM90）

```
═══════════════════════════════════════════════════════════════════
  CUTLASS CuTe 编译+执行模拟 — 4 阶段
═══════════════════════════════════════════════════════════════════

[Phase 1] CuTe C++ Template 编写 (编译时静态展开)
┌─────────────────────────────────────────────────────────────┐
│ template <typename Config>                                   │
│ __global__ void grouped_gemm_kernel(GemmParams params) {     │
│     // Config 全静态:                                        │
│     //   TileShape: 128×128×64                               │
│     //   WarpGroups: [Producer(2 warps), Consumer(6 warps)]  │
│     //   Pipeline stages: 4 (Ping-Pong double buffer)        │
│                                                             │
│     // CuTe 抽象 → PTX 指令映射 (编译时解析)                  │
│     TiledMMA mma = make_tiled_mma<Config::MMA>();            │
│     // → wgmma.mma_async.sync.aligned (SM90)                │
│     auto tma_load = make_tiled_copy_A<Config::CopyA>();     │
│     // → cp.async.bulk.tensor (TMA, SM90)                   │
│     Pipeline pipe = make_pipeline<Config::Stages>();         │
│     // → mbarrier (SM90 cluster-level sync)                 │
│                                                             │
│     // Warp specialization (编译时分配 role)                  │
│     if (warp_id < 2) {          // Producer warp group      │
│         for (k = 0; k < K_tiles; k++) {                     │
│             copy(tma_load, gmem, smem[stage]); // TMA async │
│             pipe.commit(stage);  // → mbarrier.arrive       │
│             stage = (stage + 1) % 4;                        │
│         }                                                    │
│     } else {                    // Consumer warp group      │
│         for (k = 0; k < K_tiles; k++) {                     │
│             pipe.wait(stage);    // → mbarrier.try_wait     │
│             warpgroup_arrive();  // → wgmma.fence           │
│             mma(acc, smem_A[stage], smem_B[stage]);         │
│             warpgroup_commit();  // → wgmma.commit_group    │
│             stage = (stage + 1) % 4;                        │
│         }                                                    │
│     }                                                        │
│ }                                                            │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 2] 编译链: CuTe C++ → NVCC → PTX → SASS
┌─────────────────────────────────────────────────────────────┐
│ nvcc -arch=sm_90a -std=c++20 -O3 kernel.cu -o kernel.ptx    │
│   ↓ CUTLASS header-only templates 编译期展开                 │
│   ↓ NVCC: C++ → PTX (含 wgmma, cp.async.bulk, mbarrier)     │
│   ↓ ptxas: PTX → SASS (Hopper native instructions)          │
│                                                             │
│ 输出: .cubin (可加载到 GPU driver)                            │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 3] Persistent Tile Scheduler (运行时动态负载均衡)
┌─────────────────────────────────────────────────────────────┐
│ // 不同于固定 output tile → CTA 映射:                        │
│ // Persistent scheduler = 动态 work stealing:                 │
│                                                             │
│ __global__ void persistent_kernel(...) {                     │
│     while (true) {                                           │
│         int tile_idx = atomicAdd(&tile_counter, 1);         │
│         if (tile_idx >= total_tiles) break;                  │
│                                                             │
│         // 根据 tile_idx 计算对应的 (M_group, N_offset)      │
│         int m_start = tile_idx * BLOCK_M;                   │
│         int n_start = compute_n_offset(tile_idx, ...);      │
│                                                             │
│         // 执行该 tile 的 GEMM (warp specialized pipeline)   │
│         execute_gemm_tile(m_start, n_start, BLOCK_M, BLOCK_N);│
│     }                                                        │
│ }                                                            │
│                                                             │
│ // 优势: CTA 数 ≠ tile 数 — 132 CTA (H100 SMs) 处理 1000+   │
│ //       tiles, 快 CTA 多拿 tile → 自动负载均衡              │
└─────────────────────────────────────────────────────────────┘
                         ↓

[Phase 4] 执行伪时间线 (H100, SonicMoE varlen-M Grouped GEMM)
T0:     CTA_0..CTA_131 启动 → masing CTA 取 atomic tile_idx
T0+2μ:  [CTA_0]  Producer(2 warps): TMA load tile_0 (HBM→smem stage0)
        [CTA_0]  Consumer(6 warps): idle (等待 stage0 就绪)
T0+4μ:  [CTA_0]  Producer: TMA load tile_1 → smem stage1
        [CTA_0]  Consumer: wgmma tile_0 → 计算-搬运重叠
T0+6μ:  [CTA_0]  Producer: TMA load tile_2 → smem stage0 (复用)
        [CTA_0]  Consumer: wgmma tile_1
        [CTA_1]  Producer: TMA load tile_3 → smem stage0
        [CTA_1]  Consumer: idle → 即将开始 wgmma
T0+...: 持续 Ping-Pong: 4-stage pipeline 消除 TMA latency bubble
T_final: 所有 tiles 完成 → kernel exit
        快 CTA 处理完 → 取新 tile → 慢 CTA 不会被 straggler 拖累
```

### 6.3 注解

- **tile 约束**: CuTe tile 在编译时固定（template 参数），需手动匹配 SM 资源——SonicMoE 配置 128×128×64, 4 pipeline stages, SMEM ~180KB/CTA (在 H100 228KB 内)
- **CTA 分配**: Persistent scheduler → CTA 和 tile 解耦——CTA 数量 = launch config 固定，tile 数量动态——快 CTA 多取 tile，自动消解 wave quantization 效应（Stream-K 的核心理念）
- **occupancy**: Warp specialization 降低 occupancy（producer warps 不参与 compute 但消费 SM resources），但 TMA 异步特性使计算-搬运完全重叠 → 实测 75-85% HBM BW utilization
- **bank conflict**: `make_layout` 的 swizzle 参数控制 SMEM layout → 避免 warp-level bank conflict。SM90 SMEM = 32 banks × 128bit
- **笔记关键结论**: "CuTe 对比 Triton：Triton 简化开发（Python 语法，auto-tuning），但受限于 MLIR 中间表示的抽象层——无法表达 warp-specialized 异步调度、Ping-Pong pipeline、cluster-level synchronization"

## 七、CANN（华为 Ascend NPU 图编译）

### 7.1 是什么？

CANN（Compute Architecture for Neural Networks）是华为 Ascend NPU 的异构计算架构，类似 NVIDIA CUDA 角色。核心编译组件：**GE（Graph Engine）** 做图编译+IRFusion 算子融合，**runtime** 管理 AI Core/Vector Core 调度和 HCCS 通信。

**笔记证据**: `knowledge_notes/编译知识笔记/CANN (Compute Architecture for Neural Networks).md`

### 7.2 编译框架执行模拟（MoE PanGu-Σ on Ascend 910B）

```
═══════════════════════════════════════════════════════════════════
  CANN 编译流程模拟 — 5 阶段
═══════════════════════════════════════════════════════════════════

  T1:    AI Core[0..15]: Expert 0 FFN (Cube: GEMM + Vector: SiLU)
         AI Core[16..31]: Expert 1 FFN
         // 2 experts 并发 on 32 cores
  T2:    HCCL All-to-All combine (async)
  T3:    AI Core[0..31]: LayerNorm + residual (Vector Unit)
```

### 7.3 注解

- **MAC 数量**: Ascend 910B: 32 AI Cores, 每 Core 1 Cube Unit (4096 MACs) + 1 Vector Unit (1024 FP32 ops/cycle) = ~256 TFLOPS FP16
- **带宽数值**: HBM2e ~1.2 TB/s, HCCS 互联 392 GB/s per link 双向
- **并发特性**: NPU 的并发模型是指令级（Cube∥Vector 同一 cycle 执行不同操作）+ chip 级（多 chip via HCCS）。**编译时静态编排为主**——CANN GE engine 在编译时决定所有算子的执行顺序和功能单元分配——不支持 GPU 式动态 kernel concurrency
- **融合约束**: 脉动阵列的固定数据流 pattern 是融合的核心约束——仅当融合算子链的数据流方向与脉动阵列行/列方向匹配时高效
- **笔记局限性**: CANN 对 DiT/多模态/Video 模型的支持状态笔记未说明；LocMoE 论文使用 CANN 5.1.RC2.1（较旧版本）——新版本能力可能有变化
