## 一、方法细节：指令编排与软件流水线（主内容）

### 方法1：Warp Scheduler 驱动的延迟隐藏 (Latency Hiding via Warp Scheduling)

**笔记证据**: `knowledge_notes/kernel知识笔记/Warp Scheduler (NVIDIA GPU).md` (score: 3339.9)

**方法细节**:

NVIDIA GPU 的 Warp Scheduler 通过零成本 warp 切换实现延迟隐藏。每个 SM 内 4 个 warp scheduler units 独立管理 warp pool 中的 ready warps，当某 warp 因 global memory load 或 execution dependency 产生 stall 时，scheduler 立即切换到另一 ready warp 发射指令。

```
// Per-SM, per-cycle warp scheduling（推测模型）
function warp_scheduler_cycle(sm):
    for each of 4 warp_scheduler_units in sm:
        eligible_warps = []
        for warp in scheduler.warp_pool:
            if warp.is_ready():  // 无 data hazard, 无 memory stall
                eligible_warps.append(warp)

        if eligible_warps is empty:
            issue NOP  // idle cycle
            continue

        // 调度策略（逆向工程推测，未文档化）:
        if policy == "greedy-then-oldest":  // 多数文献认为
            if prev_warp in eligible_warps:
                issue prev_warp       // 优先：保持 I-cache warm
            else:
                issue oldest_ready_warp(eligible_warps)
        elif policy == "loose round-robin":
            next_warp = round_robin_next(scheduler.warp_pool)
            while not next_warp.is_ready():
                next_warp = round_robin_next(scheduler.warp_pool)
            issue next_warp
```

**注解**:
- **零成本 warp 切换**: SM 有独立 per-warp register file 和 program counter，无需 context switch。每个 warp 独占 64-256 寄存器（取决于 setmaxnreg 和 occupancy）。
- **Occupancy 与延迟隐藏的关系**: 更高 occupancy → scheduler 有更多 warp 可选 → 更有效隐藏 memory latency。但 register per warp 减少可能降低 ILP（trade-off）。
- **调度粒度**: 每 warp scheduler 每 2 周期发射 1 条 warp 指令（Ampere）。峰值: 4 × 0.5 × 1.7GHz ≈ 3.4 warp instructions/clock/SM。
- **Stream priority 盲区**: 笔记指出 warp scheduler 可能不感知 CUDA stream priority，两个应用的 warps 在 SM 内被同等对待。

**指令 Pipeline 时序图（Warp 交错隐藏延迟）**:

```
时钟周期:    T0  T1  T2  T3  T4  T5  T6  T7  T8  T9  T10 T11
Warp 0:     [LD][LD][--][--][--][--][MM][MM][--][--][--][--]
Warp 1:     [--][--][LD][LD][--][--][--][--][MM][MM][--][--]
Warp 2:     [MM][MM][--][--][LD][LD][--][--][--][--][MM][MM]
Warp 3:     [--][--][MM][MM][--][--][LD][LD][--][--][--][--]
Scheduler:   W0  W0  W1  W1  W2  W2  W0  W0  W1  W1  W2  W2
             ^--- warp 间交错执行，隐藏 global memory latency ---^
LD = global memory load (长延迟, ~200-800 cycles)
MM = Tensor Core MMA (计算密集)
-- = stall 等待数据就绪（被其他 warp 执行覆盖）
```

**注解**:
- 当 Warp 0 在 T2-T5 等待 global memory load 返回时，scheduler 切换到 Warp 1 和 Warp 2，Warp 0 的 latency 被完全隐藏。
- 这要求 SM 上至少有 4 个 active warp（occupancy ≥ 4 warps/SM），否则部分 stall 周期无法被填充。
- Ampere SM Warp Scheduler 资源参数: 4 warp schedulers / SM，每 scheduler 管理 subset of warps。

### 方法2：Software Pipelining —— Producer-Consumer 流水线

**笔记证据**: `knowledge_notes/kernel知识笔记/Software Pipelining for GPU Attention Kernels.md` (score: 3306.4), `knowledge_notes/kernel知识笔记/Software Pipeline (T.Pipelined).md` (score: 359.6), `paper_secs/secs_effAttn/Hardware-Efficient_Attention...md` (score: 266.9)

**方法细节**:

Software Pipelining 将内存加载 (HBM→SRAM) 与 Tensor Core 计算 (MMA) 组织为流水线阶段，使第 i+1 个 tile 的内存加载与第 i 个 tile 的计算在时间上重叠：

```
// === Ampere (A100) Pipeline: cp.async + double buffering ===
// num_stages=2, 使用 2 组 shared memory buffer (ping-pong)

// Prologue: 预取前 2 个 stage
cp.async(A_tile[0], sA[0])       // async load tile 0 → SMEM buffer 0
cp.async(B_tile[0], sB[0])
cp.async.commit_group()
cp.async(A_tile[1], sA[1])       // async load tile 1 → SMEM buffer 1
cp.async(B_tile[1], sB[1])
cp.async.commit_group()

// Main Loop: steady state 重叠执行
for k in [2, K//block_K):
    cp.async.wait_group<0>()      // 等待 stage (k-2) 的 copy 完成
    __syncthreads()               // 确保所有线程看到完整 tile
    mma(sA[(k-2)%2], sB[(k-2)%2], C_acc)  // compute stage (k-2)
    cp.async(A_tile[k], sA[k%2])  // async load stage k（与 mma 重叠）
    cp.async(B_tile[k], sB[k%2])
    cp.async.commit_group()

// Epilogue: 排空流水线
cp.async.wait_group<0>(); __syncthreads()
mma(sA[(K-2)%2], sB[(K-2)%2], C_acc)
cp.async.wait_group<0>(); __syncthreads()
mma(sA[(K-1)%2], sB[(K-1)%2], C_acc)
```

**注解**:
- **双缓冲**: 2 组 SMEM buffer 交替使用——一组被 cp.async 填充时另一组被 mma 消费，实现 compute 与 data movement 的完全重叠。
- **阶段数选择**: num_stages 越大，延迟隐藏越深，但 SMEM 占用翻倍（每增加 1 stage 需额外 tile_size 的 SMEM）。H100 上 256KB SMEM/SM 可支持 num_stages=2-3（取决于 tile size）。
- **cp.async 特性**: 16 字节粒度，绕过 L1 cache（L1 BYPASS），硬件自动完成而线程继续执行。
- **与 RoMeo 论文对比**: RoMeo 采用 separate-kernels + software pipelining 策略。不同精度组合（INT4-INT4、INT4-INT8 等）使用独立 kernel 以最大化 per-kernel 的 register/occupancy 调优灵活性。

### 方法3：Hopper TMA + Warp Specialization 流水线

**笔记证据**: `knowledge_notes/硬件知识笔记/Tensor Memory Accelerator (TMA).md` (score: 5104.2), `knowledge_notes/硬件知识笔记/Warp Specialization (Warp 专业化).md` (score: 4004.5), `knowledge_notes/硬件知识笔记/Named Barriers (Hopper).md` (score: 895.4)

**方法细节**:

Hopper 架构将 software pipelining 升级为硬件辅助的 warp-specialized pipeline。关键组件：TMA（硬件异步拷贝引擎）+ wgmma.mma_async（异步 Tensor Core 指令）+ Named Barriers（硬件同步原语）+ Warp Specialization（角色分工）。

```
// === Hopper (H100) Pipeline: TMA + Warp Specialization + mbarrier ===
// SM 配置: 256 threads = 8 warps, 自动 warp specialization:
//   Producer warps (1-2 warps): TMA load
//   Consumer warps (6-7 warps, 1 warpgroup): wgmma compute

// Producer Threads (by threadIdx.x, 仅 thread 0 操作 TMA):
for k in range(K // block_K):
    cp.async.bulk.tensor.2d.shared::cluster.global.mbarrier(
        sA[k % PIPE],            // dst: SMEM pipeline slot
        &desc_A,                 // TMA descriptor (2D tensor map)
        [by*block_M, k*block_K], // src coordinates in HBM
        mbar_prod                // completion barrier
    )
    cp.async.bulk.tensor.2d.shared::cluster.global.mbarrier(
        sB[k % PIPE], &desc_B,
        [k*block_K, bx*block_N], mbar_prod
    )
    mbarrier.arrive(mbar_prod)   // 标记数据就绪

// Consumer Warpgroup (128 threads):
for k in range(K // block_K):
    mbarrier.try_wait(mbar_prod)  // 等待 producer 完成（硬件阻塞）
    wgmma.fence()                 // 保证 SMEM 可见性
    wgmma.commit_group()
    wgmma.mma_async(sA[k%PIPE], sB[k%PIPE], C_acc)
    wgmma.wait_group<0>()
    // Producer 已在后台加载下一 tile（完全重叠）
```

**指令 Pipeline 时序图（Hopper WGMMA + TMA 异步流水线）**:

```
时间 →

Producer Warp (TMA):
  T0-T3:  [TMA_load tile_0 → sA[0]]──┐
  T4-T7:  [TMA_load tile_1 → sA[1]]  │ (overlapped)
  T8-T11: [TMA_load tile_2 → sA[0]]  │
                                      │
Consumer Warpgroup (WGMMA):           │
  T0-T2:  [mbarrier.wait prod[0]] ◄──┘
  T3-T6:  [wgmma.mma_async(tile_0, C_acc)]──┐ Tensor Cores 后台执行
  T7-T9:  [mbarrier.wait prod[1]] ◄──────────┘
  T10-T13:[wgmma.mma_async(tile_1, C_acc)]
  T14:    ...

TMA (硬件):                   Tensor Cores (硬件):
  ████████████████████          ░░░░░░░░░░░░░░░░░░░░░
  tile_0 copy ──────────►       tile_0 compute
  tile_1 copy ──────────►       tile_1 compute
  tile_2 copy ──────────►       tile_2 compute
```

**注解**:
- **TMA 硬件独立执行**: TMA 从发出请求到数据到达 SMEM 全由硬件管理，不占用 CUDA Core。Producer warp 只需 1 个线程发出 TMA 指令，其余 31 线程可释放寄存器用于其他用途。
- **无寄存器中转**: 数据直接在 HBM ↔ SMEM 之间移动，不经寄存器文件（vs A100 的 cp.async 需 register staging）。这一特性在 attention kernel 中尤为关键——减少 register pressure 允许更大的 tile size。
- **mbarrier 硬件加速**: TMA completion 自动 arrive(mbar_prod)，consumer 的 wait 是单周期硬件操作。Pipeline 深度 PIPE=2-3，每组 barrier 复用。
- **Multicast 能力**: TMA 可单次操作将相同 tile 广播到 cluster 内多个 SM 的 shared memory，用于 flash attention 中 Q 被多个 KV tile 消费的场景。
- **带宽效率**: Hopper TMA 在仅 2KB 消息大小时就能达到 74% 峰值 NVLink 带宽（vs Copy Engine 需 256MB），这对 attention decode kernel 的小 tile 场景至关重要。

### 方法4：ILP 指令级并行 —— Tensor MMA + Vector ALU 交错调度

**笔记证据**: `knowledge_notes/kernel知识笔记/Tensor-Vector Parallelism Scheduling (ILP_TLP for Softmax).md` (score: 2455.4), `knowledge_notes/硬件知识笔记/CUDA Cores vs Tensor Cores (Compute Unit Heterogeneity on GPU).md` (score: 333.4)

**方法细节**:

FlashAttention-T 提出 Tensor-Vector Parallelism：在 fused attention kernel 中将 softmax 拆分为 tensorized 部分（repurposed MMA on Tensor Core）和 vectorized 部分（CUDA Core），通过 ILP interleaving 使两部分在同一 warp 内并行。

**Ampere ILP Scheduling 伪代码**:

```
// FlashAttention-T: Ampere ILP interleaving
// 在单个 warp 内，通过 PTX inline assembly 手工编排指令交错

void softmax_ilp_warp(reg QK[BLOCK_M], reg PV[BLOCK_M], reg O[BLOCK_M]):
    // Split: horizontal split（同 tile 内按行分割，ratio ≈ 1:1）
    // tensorized 部分：scaling, FMA, rowsum (repurposed MMA)
    // vectorized 部分：max (REDUX), exp (MUFU.EX2)

    // --- ILP interleaved instruction sequence ---
    // iteration i, per warp:

    // Step 1: QK^T MMA (Tensor Core)
    mma.sync(Q_frag, K_frag, S_frag)     // S = QK^T

    // Step 2: ILP-interleaved softmax
    //   tensor MMA:  scaling + FMA + rowsum
    //   vector ALU:   max (REDUX) + exp (MUFU.EX2)
    //   交错编排，使 vector 指令在 tensor MMA 的 issue bubble 中执行

    // Pseudo instruction sequence (手写 PTX):
    mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32  // tensor: scaling
    redux.op.max.f32  R_max, S_row                       // vector: max (并行)
    mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32  // tensor: FMA
    fma.rn.f32         S_sub, -R_max, 1.0               // vector: subtract max
    mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32  // tensor: rowsum
    ex2.approx.f32     P_row, S_sub                      // vector: exp (并行)

    // 效果: t'_softmax < t_vec (baseline 全 vector softmax 时间)
    //       t'_vec = t'_softmax - (t_vec - t'_softmax)

    // Step 3: PV MMA (Tensor Core)
    mma.sync(P_frag, V_frag, O_frag)     // O += PV
```

**注解**:
- **ILP interleaving 原理**: GPU dual-issue 能力允许同时发射一条 Tensor Core 指令和一条 CUDA Core 指令（或相邻周期交错发射）。Tensor MMA 指令有 issue bubble——Tensor Core 后台执行时 CUDA Core 空闲，vector 指令填充这些 bubble。
- **Split 策略**: Horizontal split（同 tile 按行分割 tensorized/vectorized，ratio≈1:1）平衡两种计算资源；Vertical split（跨 tile 分割，ratio 固定 1:1）受 warp register capacity 限制（最多 2 tiles）。
- **Hopper TLP 对比**: Hopper 上使用 Thread-Level Parallelism 替代 ILP——将 repurposed WGMMA row-sum 加入下一 iteration 的 QK^T+PV WGMMA batch，与另一 warpgroup 的 vector S/O rescaling 并行。Vector interval ratio 降至 2.7%（远优于 ILP），因 WGMMA 支持更灵活的 dynamic tensor-vector overlap。
- **CUDA Core vs Tensor Core 吞吐差距**: H100 上 CUDA Core FP32 ≈ 60 TFLOPS，Tensor Core INT8 ≈ 990 TFLOPS（16.5× 差距）。这是 dequantization 成为瓶颈的根本原因——LiquidGEMM 的 LiquidQuant 将 dequant 指令降至 0.875 条/element（vs QServe 的 ≥10 条/element）。

### 方法5：Implicit Fine-Grained Pipeline (ImFP) —— 跨 Warp Group 指令混合

**笔记证据**: `knowledge_notes/kernel知识笔记/Implicit Fine-Grained Pipeline (ImFP).md` (score: 1737.9), `knowledge_notes/硬件知识笔记/CUDA Cores vs Tensor Cores (Compute Unit Heterogeneity on GPU).md` (score: 333.4)

**方法细节**:

LiquidGEMM 提出 ImFP（Implicit Fine-Grained Pipeline），将 traditional explicit coarse pipeline (ExCP) 的 Load→Dequant→MMA 三阶段流水线改为 single-producer multiple-consumer 模型：

```
// ImFP 执行流程（每 thread block = 3 WGs: 1 Load + 2 Compute）
// Load WG (4 warps, 仅操作 TMA):
for each K_tile iteration:
    TMA: GMEM → SMEM[pong]           // async weight load (Dual-MMA packed)
    cp.async.bulk.wait_group
    for each MMA fragment in tile:
        smem_task_queue.push({frag_addr, frag_meta})  // metadata only
    swap(ping, pong)

// Compute WG_0 & WG_1 (各 4 warps, CUDA + Tensor Cores):
while true:
    task = smem_task_queue.try_pop()  // atomic 竞争, 无 barrier
    if !task: break
    LDS.128: RF = SMEM[task.addr]     // 32 UINT4, single instruction
    unpack_4bit(RF)                   // CUDA Core
    dequant_LQQ(RF)                   // IMAD + XOR, CUDA Core (2 条指令)
    WGMMA(C_frag, A_frag, RF)         // INT8 MMA, Tensor Core 异步
    // WG_0 和 WG_1 处理不同 tasks
    // → WG_0 做 dequant 时 WG_1 做 MMA → 跨 WG 重叠
```

**注解**:
- **消除 SMEM↔RF round-trip**: ExCP 需要 Load→Dequant（SMEM→RF→SMEM）→MMA（SMEM→RF），ImFP 中 Compute WG 直接从 SMEM 读取并一站式完成 dequant+MMA，消除中间 SMEM 写回。
- **跨 WG 异构重叠**: WG_0 在 CUDA Core 上做 dequant 时，WG_1 在 Tensor Core 上做 MMA。这种重叠是天然的——不需要软件 barrier，由硬件 atomic 竞争自动调度。
- **Dual-MMA packed layout**: 两个连续 MMA 操作的元素打包存储，LDS.128 单条指令加载 32 个 UINT4 元素，充分利用 shared memory 带宽。
- **dequant 指令最小化**: LiquidQuant (LQQ) 仅需 IMAD + XOR 两条 32-bit 硬件指令处理四个元素，α=0.875 指令/element，远低于 QServe 的 α≥10。确保 CUDA Core 不成为 pipeline 瓶颈。

### 方法6：Multi-stage Register Pipeline（多级寄存器流水线）

**笔记证据**: `knowledge_notes/kernel知识笔记/Multi-stage Register Pipeline (for SpMV on Tensor Cores).md` (score: 3576.4)

**方法细节**:

Drawloom 为解决 SpMV 中 memory-compute 串行化导致的 warp stall，将四大操作步骤重构为 5 阶段流水线：

```
// Pipeline 参数
delaySMEM = 1  // double buffering: 2 组 SMEM buffer 交替
delayREG = 2   // 3 组 REG set 轮流使用

// 5 阶段流水线
// Stage 1: FillSMEM — async-copy 填充 SMEM buffer
// Stage 2: FillREG — SMEM→REG + LDG 加载 vector X
// Stage 3: Comp — TC MMA 计算（使用前一阶段的 REG 数据）
// Stage 4: EmptySMEM — 完成剩余 SMEM→REG 搬移
// Stage 5: EmptyREG — 完成剩余计算

// 关键控制: pipeline_wait_prior(N) 确保 N 阶段前的数据就绪
//           pipeline_commit() 提交当前 async-copy 批次

// delaySMEM=1, delayREG=2 时，最多 3 个 REG set 同时 in-flight:
//   REG set [0]: 正在被 MMA 消费
//   REG set [1]: 正在被 LDG 填充
//   REG set [2]: 正在等待 SMEM 数据就绪
```

**注解**:
- **delaySMEM** 控制 GMEM→SMEM 的 double buffering 阶段数（Ampere 上通过 cp.async 实现）
- **delayREG** 控制 SMEM→REG + computation 的重叠阶段数。多级 REG pipeline 进一步解耦 SMEM→REG 和计算，消除 data dependency stall
- **消融实验**: v4（+Multi-stage Pipeline）相比 v3 平均提速 1.46×（mip1 达 5.68×），warp stall 改善 3.02×-3.13×，memory throughput 提升 2.61×-2.75×
- **适用前提**: 每次 memory access 只触发一个 TC 操作（SpMV 的稀疏特性），因此需要多级 REG pipeline 进一步重叠 short-latency TC computation 与 irregular X vector access

### 关键评估指标

- **Warp occupancy**: SM 上同时 resident 的 warp 数。更高 occupancy → 更多 warp 可隐藏延迟，但每 warp 寄存器减少 → ILP 降低
- **Pipeline stage utilization**: 各流水线阶段的利用率。理想状态 producer load 与 consumer compute 100% 重叠
- **Vector interval ratio**: Tensor Core idle 时间占比（越小越好）。FlashAttention-T Hopper TLP 降至 2.7%
- **指令级效率**: dequant 指令数/element（LiquidQuant α=0.875 vs QServe α≥10）
- **Memory bandwidth 利用率**: TMA 在 2KB 消息达 74% NVLink 峰值带宽

## 三、实现（辅助说明）

**笔记证据**: `knowledge_notes/kernel知识笔记/Actor-Based Warp Specialization for In-Kernel Scheduling.md` (score: 3179.7), `knowledge_notes/kernel知识笔记/Software Pipeline (T.Pipelined).md` (score: 359.6)

### FlashMoE Actor-Based Warp Specialization

FlashMoE 的纯软件 actor 模型（可在 SM70+ GPU 运行，不依赖 Hopper TMA）：

```
// 三种 Actor 角色（同一 kernel 内，无 barrier 同步）
// Processor (N-1 blocks): 执行 GEMM + combine + dispatch
// Subscriber (OS block 内 3 warps): 解码远端 tile packet → task descriptor
// Scheduler (OS block 内 1 warp): work-conserving 调度

// Actor 交互（event-driven, polling-based）:
Subscriber: poll NVSHMEM flag → atomic retrieve → decode →
            write task queue (GMEM) → atomicAdd doorbell (SMEM) →
            notify Scheduler

Scheduler:  sweep all doorbells → WarpInclusiveSum →
            signal idle Processor (GMEM)

Processor:  await_scheduler_signal → warp broadcast task →
            switch(type):
              GEMM0: fGET fused CUTLASS GEMM+GELU
              GEMM1: fGET + NVSHMEM put result → combine (Hadamard)
```

### TileLang T.Pipelined 实现

用户仅需添加 `T.Pipelined(K // block_K, num_stages=N)` annotation，编译器自动：(1) 分析 loop body 中各 buffer 的读/写关系确定 prod/cons 角色；(2) 插入对应架构的异步指令序列（Ampere→cp.async、Hopper→TMA、CDNA→buffer_load_dword）；(3) Live Variable Analysis 确定同步点→插入 barrier；(4) Hopper 架构上自动应用 warp specialization。TileLang 的 FlashAttention 实现（~70 行 Python）达到 FlashAttention-3（手写 CUDA）98% 的性能。

## 四、是什么？（辅助说明）

### 核心概念关系

多算子/微算子并发的指令编排与软件流水线设计的本质是**通过指令级和 warp 级的时间重叠，最大化 GPU 异构计算单元的利用率**。四个概念构成层次化调度体系：

1. **ILP (指令级并行)**: 单 warp 内的指令交错——利用 GPU dual-issue 能力，将 Tensor Core MMA 的 issue bubble 填充 CUDA Core vector 指令
2. **Warp 级调度**: SM 级——Warp Scheduler 通过零成本 warp 切换隐藏 memory latency
3. **Software Pipelining**: Kernel 级——通过 producer-consumer 流水线将 HBM→SMEM 数据搬运与 Tensor Core 计算重叠
4. **指令混合**: 计算单元级——将 GEMM/attention MMA 指令与 element-wise ALU 指令混合调度，提升异构计算单元利用率

### 跨平台差异

| 特性 | NVIDIA GPU (SIMT) | AMD GPU (CDNA) | NPU 昇腾 (达芬奇) | TPU (XLA) |
|------|-------------------|----------------|-------------------|-----------|
