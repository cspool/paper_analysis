## 一、MoE 模型的 Serving 调度策略

### 方法1：标准 EP Barrier 调度（Baseline）

**笔记证据**: `idea_notes/Toward Cost-Efficient Serving of Mixture-of-Experts with Asynchrony.md` (score: 1622.8), `knowledge_notes/kernel知识笔记/All-to-All Communication in MoE Expert Parallelism...md` (score: 2258.7)

**方法细节**（L2 框架运行模拟）：

MoE 单请求推理在标准 Expert Parallelism (EP) 下按 decoding block 的 barrier 同步模式执行。调度流程为四阶段循环：

```
=== MoE EP Barrier 调度流程 (SGLang/vLLM, 单请求, 4 GPU EP) ===

请求 → Tokenizer → [Decoding Block Loop] → Sampler → 输出

每个 Decoding Block 的调度时间线（以 DeepSeek-V2, 1A4E 为例）:

Step 1: Attention 计算 (所有 GPU 并行)
  GPU_0 (持有 KV Cache):  
    QKV_proj → FlashAttention → output_proj → hidden_states [B, S, 7168]
  GPU_1-3 (仅持有 expert 权重): 
    idle / 等待
    
Step 2: Router Gating (GPU_0)
  gate_logits = hidden_states @ W_gate           # [B, S, 256 experts]
  topk_weights, topk_indices = TopK(softmax(gate_logits), k=8)
  # 产生 token-to-expert 映射 (每个 token 选 8/256 experts)
  
Step 3: Dispatch All-to-All ← BARRIER
  # NCCL alltoallv: 每个 GPU 将 token embeddings 发送到持有对应 expert 的 GPU
  # 所有 GPU 必须同时调用，最慢 GPU 决定完成时间
  # DeepSeek-V2-Lite: all-to-all 占 MoE layer forward 延迟的 59.2%
  
Step 4: Expert FFN Compute (所有 GPU 并行)
  各 GPU 对收到的 tokens 执行本地 expert FFN:
    gate_out = SiLU(W_gate @ tokens)            # [local_tokens, intermediate_dim]
    up_out = W_up @ tokens                       # [local_tokens, intermediate_dim]
    expert_out = gate_out * up_out @ W_down      # [local_tokens, 7168]
  # GPU 间负载不均衡: hot expert GPU 处理大量 tokens，cold expert GPU 处理极少 tokens

Step 5: Combine All-to-All ← BARRIER
  # NCCL alltoallv: expert 输出发送回原始 GPU
  # GPU stall 可达总执行时间的 70% (AMoE Fig.4)

Step 6: Token Merge & Residual
  final_output = Σ(topk_weights[e] * expert_out[e]) + attention_residual
  → 进入下一 Decoding Block
```

**注解**:
- **变量含义**: `B`=batch size (单请求=1), `S`=sequence length, `7168`=hidden dim (DeepSeek-V2), `256`=expert 总数, `k=8`=激活 expert 数
- **复杂度分析**: All-to-All 通信量 O(BS·h/d) per layer，barrier 同步使得端到端延迟 = max{各 GPU 的 compute+通信时间}
- **数据依赖**: Dispatch A2A 依赖 Router 的 token-to-expert mapping；Combine A2A 依赖所有 GPU 的 expert FFN 完成；两次 barrier 构成严格串行瓶颈
- **并发可行性**: Attention 和 Expert Compute 在不同 GPU 上有自然并行性，但 barrier 破坏了流水线重叠机会

**硬件视角分析**:
- **SM 占用率**: Cold expert GPU 的 SM 利用率极低——当只有少量 tokens 到达时，GEMM 的 M 维度极小，Tensor Core 利用率 < 10%
- **HBM 带宽压力**: Cold expert 小 batch 场景下，weight loading 主导延迟（HBM bandwidth-bound），而非计算
- **脉动阵列利用率**: NPU 上同样存在 batch size < 128 时吞吐量远低于线性的问题

### 方法2：AEP 异步专家并行调度（AMoE）

**笔记证据**: `knowledge_notes/系统知识笔记/Asynchronous Expert Parallelism (AEP _ 异步专家并行).md` (score: 1116.3), `idea_notes/Toward Cost-Efficient Serving of Mixture-of-Experts with Asynchrony.md` (score: 1622.8)

**方法细节**（L2 框架运行模拟）：

AEP 彻底消除 all-to-all barrier，将每个 GPU 从同步等待中解放。核心机制是 µ-queue（微队列）+ Defragging Scheduler：

```
=== AEP 异步调度流程 (AMoE, 单请求, 4 GPU AEP) ===

初始化:
  每个 GPU 维护 µ-queues: Q[block_id][expert_id] = deque()
  # 每个 (block, expert) pair 一个独立 token 队列

Scheduling Loop (每个 GPU 独立执行, 无全局 barrier):
  
  [Receptor Thread (C++ POSIX)]
    从 Communicator 接收其他 GPU 发来的 tokens
    for each received token:
        layer_id = token.layer_id
        expert_id = token.next_expert_id
        Q[layer_id][expert_id].append(token)    # 按 layer+expert 分流入队
  
  [Defragging Scheduler (主线程)]
    while True:
        best_score = -∞, best_layer = None
        for each (block, expert) pair:
            # LScore: lookahead 加权前方 token 密度 (鼓励 token wave 前向传播)
            # Q[b][e]: 当前队列 token 数
            Score = LScore(b, e) + Q[b][e].size()
            if Score > best_score:
                best_score = Score
                best_layer = (b, e)
        
        if best_layer:
            tokens = Q[b][e].drain_all()       # 取出全部排队 tokens
            Executor.run(best_layer, tokens)    # GEMM/expert FFN 或 attention
    
  [Dispatcher Thread (C++ POSIX)]
    output_tokens = Executor.get_output()
    permute by next_expert_id                  # 按下一层目标 expert 分组
    Communicator.async_send(output_tokens)     # ZeroMQ metadata + NCCL P2P 异步传输
    # CPU 启动 NCCL 后立即返回，不等待 GPU 完成

关键差异 vs Barrier EP:
  - EP:  token batch → barrier A2A → expert compute → barrier A2A → 下一层
  - AEP: token → µ-queue → [GPU 独立选层执行] → 异步转发 → cold tokens 积累无需 stall
```

**注解**:
- **数据结构**: µ-queue 每个 (block, expert) 独立队列；Defragging Scheduler 本质是贪心 max-score 层选择
- **并发粒度**: GPU 间完全异步——hot expert GPU 持续处理积累的 tokens，cold expert GPU 可转而执行 token 充足的其他 layer
- **编译 vs 运行时权衡**: 调度决策完全在运行时基于队列状态动态做出，无需离线 profiling；但 C++ 关键路径（Receptor/Scheduler/Dispatcher）需避免 Python GIL

**硬件视角分析**:
- **SM 占用率提升**: Cold expert 的 tokens 在 µ-queue 中积累到高效 batch size (>128) 才被调度执行 → SM 利用率从 <10% 提升至接近峰值
- **HBM 带宽压力缓解**: 批量执行将 weight loading 开销摊销到更大 batch → 从 memory-bound 转向 compute-bound
- **通信开销消除**: 异步 P2P (ZeroMQ + NCCL P2P) 替代 barrier all-to-all，通信自然与计算重叠

### 方法3：JANUS 解耦 Attention-MoE + AEBS 调度

**笔记证据**: `experiment_notes/系统实验笔记/JANUS_ Disaggregating Attention and Experts for Scalable MoE Inference.md` (score: 1266.9)

**方法细节**（L2 框架运行模拟）：

JANUS 将 Attention 和 MoE 层部署到独立 GPU 子集群，通过 AEBS (Activated-Expert-Balanced Scheduling) GPU kernel 实现同步无关的 expert 调度：

```
=== JANUS 解耦调度流程 (DeepSeek-V2, 1A6E, decode 阶段) ===

配置: n_a=1 attention GPU, n_e=6 MoE GPUs

Step 1: Attention 计算 (GPU A)
  SGLang continuous batching → in-flight decode batch
  MLA (Multi-head Latent Attention) 计算
  Shared Expert (overlap): 在等待 MoE 结果时计算共享 expert FFN

Step 2: 跨子集群数据传输 (每 MoE 层)
  Phase 1 (Intra-node): 同节点多 attention instances 通过 NVLink NCCL 聚合激活
  Phase 2 (Inter-node): NVSHMEM putmem_signal + GPUDirect RDMA 传输到 MoE GPUs
  元数据 (layer index, token count) 打包在 signal value 中

Step 3: AEBS GPU Kernel 调度 (每 MoE GPU 独立执行)
  # GPU kernel, 无 CPU-GPU 同步, 无跨 GPU 协调, 开销 < 90μs
  for each token in current_batch:
      # 收集 top-k 路由结果
      logical_expert_ids = router_output[token]
  
  # 单副本 expert → 固定分配到唯一持有实例
  # 多副本 expert → 贪心分配到当前负载最低的实例
  # 重写路由结果为物理 replica IDs
  
  dispatch_tokens(replica_ids)    # token 发送到持有对应 replica 的 GPU

Step 4: Expert FFN 计算 (GPU E0-E5)
  各 GPU 对接收 tokens 执行本地 expert FFN (cuBLAS GEMM)
  MoE 层延迟 = max(a_max), a_max = 激活 expert 数最多的 GPU

Step 5: 反向两阶段通信
  Phase 1: MoE 侧 intra-node all-reduce
  Phase 2: NVSHMEM putmem_signal 传回 attention GPU

Step 6: SLO-Aware Scaling (15 min 间隔)
  MoE Controller 收集 activation statistics
  构建 Monte Carlo â_max 查找表
  Algorithm 2: 枚举 (n_a, n_e) → 求解稳态 batch size → 检查 TPOT SLO
  → 选择 min(n_a+n_e) 满足 SLO 的配置
```

**注解**:
- **数据结构**: AEBS kernel 在 GPU 上同步无关地运行；每个 MoE instance 维护 expert replica 负载计数器
- **并发粒度**: Attention 与 MoE 在不同 GPU 子集群上并发执行；Shared Expert 与跨子集群通信重叠
- **编译 vs 运行时权衡**: AEBS 是纯运行时 GPU kernel 调度（无编译期干预），Scaling Controller 周期性（15 min）离线调整资源配置

**硬件视角分析**:
- **SM 占用率**: AEBS 将 expert load 均匀分配到所有 MoE GPU → SM 利用率均衡化；相比 SGLang 提升 per-GPU throughput 最高 4.7×
- **HBM 带宽**: 解耦架构使 KV cache 常驻 attention GPU HBM，无需在 expert GPU 间复制 → HBM 压力降低
- **互联带宽**: 900 GB/s NVLink (intra-node) + 400 Gbps InfiniBand (inter-node)；NVSHMEM one-sided put 绕过 CPU 参与

### 方法4：METRO Expert-Level Load Balancing

**笔记证据**: `paper_secs/secs_moe/Efficient MoE Serving in the Memory-Bound Regime Balance Activated Experts, Not Tokens/Efficient-MoE-Serving-in-the-Memory-Bound-Regime-Balance-Activated-Experts-Not-Tokens.md` (score: 13897.1)

**方法细节**（L2 框架运行模拟）：

METRO 的关键发现：在 memory-bound 的 decode 阶段，平衡 "token 数" 反而降低性能——因为它增加了激活 expert 数，加剧 memory 压力。METRO 转而平衡 "激活 expert 数" per GPU：

```
=== METRO 调度策略 ===

核心 Insight:
  传统 EP: 平衡 tokens/GPU → 每个 GPU 处理等量 tokens
  问题: 为平衡 tokens，token 被分散到更多 expert replicas
       → 激活 expert 总数增加
       → 每个 GPU 需加载更多 expert weights
       → memory-bound 阶段 HBM 带宽压力剧增
       → 端到端延迟反而上升 (!)

METRO 方案:
  目标函数: min(max_g 激活 expert 数 per GPU g)
  而非:     min(max_g token 数 per GPU g)
  
  实现:
  1. AllGather 全局 top-k 信息 (替代 all-to-all，开销更小)
  2. 联合优化: 最小化 routing quality loss + 约束激活 expert 分布
  3. GPU 并行求解: 利用 GPU parallel processing power
  4. 输出: token routing 决策 → 最小化每 GPU 激活 expert 数
```

**注解**:
- **关键发现**: memory-bound 阶段 (decode)，激活 expert 数比 token 数对延迟影响更大——因为 expert weight 加载受 HBM 带宽约束
- **适用场景**: single-request decode（自回归逐 token 生成），batch size=1，HBM 带宽成为瓶颈

**硬件视角分析**:
- **HBM 带宽**: 减少激活 expert 数 → 降低 weight loading 的 HBM 带宽需求 → memory-bound → compute-bound 转变
- **与 METRO 互补的调度策略**: 在 compute-bound 阶段 (prefill)，平衡 tokens 更优；在 memory-bound 阶段 (decode)，平衡 experts 更优

## 二、DiT 模型的 Serving 调度策略

### 方法1：DiT Denoising Step 迭代调度

**笔记证据**: `knowledge_notes/算法知识笔记/MMDiT (Multi-Modal Diffusion Transformer)...md` (score: 262.0), `knowledge_notes/系统知识笔记/Inflight Batching...md` (score: 181.4)

**方法细节**（L2 框架运行模拟）：

DiT 推理与 LLM 自回归 decode 有根本不同：DiT 在固定数量的 denoising steps（如 50 steps）中迭代精炼全量 latent tokens，每个 step 内是一次完整的模型 forward pass。调度策略围绕 step-level 编排：

```
=== DiT 单请求推理调度流程 (SD3/Flux, 50 denoising steps) ===

输入: 随机噪声 latent z_T ∈ R^{H×W×C}  (如 128×128×4)
     文本条件 embedding c_text

Step-level 调度循环:
  for t = T, T-1, ..., 1:                    # 50 → 1, 逆扩散过程
  
    ┌─ Step t 内部调度 ─────────────────────────────────┐
    │                                                       │
    │  Sub-step 1: Timestep Embedding                       │
    │    t_emb = SinusoidalEmbedding(t)                     │
    │    c = t_emb + c_text                                 │
    │                                                       │
    │  Sub-step 2: MMDiT Block Forward (重复 N=24-48 层)     │
    │    for each DiT Block:                                │
    │      a) Self-Attention (文本+图像共享 QKV):           │
    │         h_combined = cat(norm(z_img), norm(z_txt))     │
    │         attn_out = FlashAttention(h_combined)         │
    │         attn_img, attn_txt = split(attn_out)          │
    │                                                       │
    │      b) AdaLN Modulation (时间条件注入):               │
    │         scale, shift = MLP(c)                         │
    │         h_img = norm(h_img) * (1+scale) + shift       │
    │                                                       │
    │      c) 独立 FFN (模态特定):                           │
    │         h_img += FFN_img(norm(h_img))                  │
    │         h_txt += FFN_txt(norm(h_txt))                  │
    │                                                       │
    │  Sub-step 3: Final Layer → Noise Prediction           │
    │    ε_θ = output_proj(h_img)                           │
    │                                                       │
    │  Sub-step 4: DDIM/SDE Step (去噪一步)                  │
    │    z_{t-1} = scheduler_step(z_t, ε_θ, t)              │
    │                                                       │
    └───────────────────────────────────────────────────────┘

输出: z_0 → VAE Decoder → 最终图像/视频

Step 间优化:
  - Feature Cache 复用: 文本条件 c_text 在所有 steps 间不变 → 缓存在 GPU memory
  - KV-Cache 不适用: DiT 不是自回归模型，每个 step 的 latent tokens 维度固定
  - Conditioning Cache: CFG 场景下正/负 prompt 条件嵌入可复用
```

**注解**:
- **变量含义**: `H×W×C`=latent 空间分辨率；`N`=DiT block 层数 (24-48)；`t`=扩散时间步
- **复杂度分析**: 每个 step 的 FLOPs ≈ N × (2 × 4HWC × d_model²) attention + FFN；总开销 = 50 steps × per-step FLOPs
- **数据依赖**: step t 严格依赖 step t+1 的输出 z_t；step 内各 sub-step 有严格顺序依赖

### 方法2：CFG (Classifier-Free Guidance) 双流调度

**笔记证据**: `knowledge_notes/算法知识笔记/MMDiT (Multi-Modal Diffusion Transformer)...md` (score: 262.0)（笔记未明确说明 CFG 双流的完整调度实现细节，以下基于 DiT 架构可推断）

**方法细节**（L2 框架运行模拟）：

CFG 在推理时同时执行 conditional 和 unconditional 两条 forward pass，调度策略决定两者的执行顺序和数据复用：

```
=== CFG 双流调度策略 ===

策略 A: 串行双流 (Baseline — 大多数开源实现)
  GPU Timeline:
    T0: conditional forward (c_text = 正 prompt)
        attention/FFN on z_cond
    T1: unconditional forward (c_text = null embedding)  
        attention/FFN on z_uncond
    T2: CFG Merge
        ε_final = ε_uncond + w * (ε_cond - ε_uncond)    # w=7.5 typical
  # 总延迟 = 2× per-step latency
  # SM 占用率: 单流执行，SM 利用率 ~50% (仅一半的矩阵维度)

策略 B: Batch 双流 (DiT serving 优化)
  GPU Timeline:
    T0: batched forward
        z_batch = cat([z_cond, z_uncond], dim=0)         # [2, H, W, C]
        c_batch = [c_text, c_null]
        单次 forward pass 处理两个 latent → 2× batch size
    T1: CFG Merge
  # 总延迟 ≈ 1× per-step latency (batch=2)
  # SM 占用率: 更高 (GEMM M 维度翻倍 → Tensor Core 利用率提升)
  # HBM 带宽: weight 仅需加载一次 → HBM bandwidth 减半

策略 C: 双 GPU 并行 CFG (多 GPU 场景)
  GPU_0: conditional forward (独立 CUDA stream)
  GPU_1: unconditional forward (独立 CUDA stream)
  GPU_0: CFG Merge (接收 GPU_1 结果 via NCCL)
  # 总延迟 ≈ 1× per-step latency + merge overhead
  # 需要模型权重复制或 expert/pipeline 并行
```

**注解**:
- **硬件权衡**: Batch 双流在单 GPU 上最优——减少 weight loading 次数，提高 GEMM 效率
- **SM 占用率**: Batch=2 使 attention 和 FFN 的 M 维度翻倍 → Tensor Core 利用更充分（从 ~50%→~80%+）

**硬件视角分析**（DiT 整体）:
- **SM 占用率**: DiT 是 compute-bound——全量 latent tokens 的 attention/FFN 打满 SM；单个 step 内无需 batching 即接近峰值利用率
- **HBM 带宽**: 文本条件嵌入 (c_text) 可驻留 HBM 并在所有 steps 间复用；图像 latent (z_t) 每 step 更新，需反复读写
- **脉动阵列利用率**: 大分辨率 (1024²) latent 的 GEMM 充分填充脉动阵列；小分辨率 (256²) 可能在 NPU 上利用率不足

## 三、多模态模型的 Serving 调度策略

### 方法1：三阶段跨模态调度（VisiPruner 框架）

**笔记证据**: `knowledge_notes/算法知识笔记/Three-Stage Cross-Modal Interaction in MLLMs...md` (score: 621.3), `knowledge_notes/算法知识笔记/Cross-Modal Information Flow in MLLMs.md` (score: 707.2)

**方法细节**（L2 框架运行模拟）：

多模态 MLLM 的推理调度需协调 vision encoder → text encoder (embedding) → cross-modal fusion → LLM decode 四阶段的执行时机和数据就绪：

```
=== 多模态 MLLM 多阶段调度流程 (LLaVA-v1.5 7B, 单请求) ===

Phase 1: Vision Encoding (CLIP ViT-L, GPU)
  输入: 输入图像 I ∈ R^{336×336×3}
  输出: visual tokens V ∈ R^{576×1024} (576 patches × 1024 dim)
  调度: 单体 forward pass, 不可拆分
  硬件: ViT-L ~300M params, SM 利用率高 (patch 并行天然适合 GPU)
  
Phase 2: Vision Projection (MLP Connector, GPU)
  输入: visual tokens V
  输出: projected tokens P_v ∈ R^{576×4096} (映射到 LLM embedding 空间)
  调度: 轻量 2-layer MLP, 与后续阶段可流水线重叠
  
Phase 3: Multimodal Prefill (LLM Layers, GPU)
  输入: [P_v (576 tokens) ; system_prompt (~50 tokens) ; user_query (~30 tokens)]
        = 总 ~656 tokens
  输出: first text token logits + 全层 KV Cache
  
  # === 关键: 三阶段跨模态调度 (VisiPruner 指导) ===
  Sub-phase 3a: Shallow Layers (1-8) — Task Recognition
    行为: 视觉和文本 token 独立演化，无有意义的跨模态融合
    调度优化: 
      - Cross-attention 可跳过 (Attention Merging → 合并到单个随机 token)
      - 视觉 self-attention 可跳过 (mask 后性能几乎不变)
      - → 节省 ~25% 的浅层计算量
    
  Sub-phase 3b: Middle Layers (9-23) — Sparse Cross-Modal Grounding
    行为: 跨模态融合突然发生，由 ~10/576 关键视觉 token 驱动
    调度优化:
      - Influence-based Token Selection: 仅保留 instruction-relevant 
        的视觉区域 tokens（~10-50 tokens vs 576）
      - Cross-attention 仅对保留 tokens 计算
      - → 节省 ~90% 的跨模态 attention 计算量
    
  Sub-phase 3c: Deep Layers (24-32) — Linguistic Alignment
    行为: 视觉信息已集成到文本表示中 → 纯文本 refinement
    调度优化:
      - Vision Exit: 从 layer 24+ 完全丢弃视觉 tokens
      - 后续 layers 仅做纯文本 self-attention
      - → 节省 ~20% 的深层计算量 + HBM 空间

Phase 4: Autoregressive Decode
  输入: 上一步生成的 token + KV Cache (仅文本部分)
  输出: 逐 token 生成回答
  调度: 标准自回归 decode；KV Cache 仅含文本 tokens (视觉 tokens 已 exit)
```

**注解**:
- **数据就绪管理**: Vision encoding 必须在 prefill 前完成；Prefill 完成后方可开始 decode
- **Stage 间流水线**: Phase 1-2 (vision processing) 可与 Phase 3a (shallow prefill) 通过 CUDA stream 部分重叠
- **Vision Exit 的条件**: 需中层 (layers 9-23) 已充分完成跨模态融合；实验验证 layer 26+ discard 视觉 tokens 对 GQA 几乎无影响 (61.95→61.91)

### 方法2：Modal Cache 跨请求复用调度（EEVEE）

**笔记证据**: `knowledge_notes/系统知识笔记/Modal Cache（模态缓存）.md` (score: 382.2)

**方法细节**（L2 框架运行模拟）：

EEVEE 提出的 Modal Cache 机制将 vision encoder 的输出跨请求缓存复用，消除重复的 visual encoding：

```
=== EEVEE Modal Cache 调度流程 ===

请求到达:
  1. Controller 计算输入图像的内容 hash (64-bit)
  2. Hash 查找 GPU shared memory 中的 Modal Cache
     命中 → 跳过视觉编码 → 直接从 cache 加载 visual tokens/KV
     未命中 → 执行视觉编码 → 结果写入 cache
  
Cache 结构:
  - Encoder-Decoder 模型: 缓存 cross-attention 的 visual KV pairs
  - Decoder-Only 模型: 缓存 visual prefix 在 self-attention 中的 KV pairs
  
Cache 压缩:
  按 token-wise attention score 排序 → 剪除低分 visual tokens
  576 tokens → ~170 tokens (30% retention)
  Critical Modal Cache (压缩版) 优先放置 GPU memory
  Full Modal Cache 保留在 host memory 备用
  
Cache 逐出:
  GPU memory quota 超限 → Global LRU → stale tensors spill 到 host memory
  后台释放与 CUDA kernel launch 重叠
```

**注解**:
- **跨请求优化**: 同一图像被多次引用时，后续请求完全跳过视觉编码阶段
- **Pipeline Overlap**: 新请求的 encoder computation 与之前请求的 modal cache loading 重叠执行

**硬件视角分析**（多模态整体）:
- **SM 占用率**: Vision encoding (ViT) 和 LLM prefill 交替使用 GPU——编码阶段 SM 被 ViT 的 patch 并行打满；prefill 阶段 LLM 的 attention 主导
- **HBM 带宽**: 视觉 encoder 输出的 576 visual tokens (576×4096×FP16 ≈ 4.7MB) 需从 HBM 写入 KV Cache；Vision Exit 策略可节省深层 HBM 空间
- **多模态 NPU 适配**: 华为昇腾上 ViT 和 LLM 可能在不同计算核心上执行（ViT→Cube 单元，LLM Attention→Vector 单元），调度需考虑异构计算单元的负载分配

## 四、Video 模型的 Serving 调度策略

### 方法1：Streaming Video 逐帧因果调度（LiveStar）

**笔记证据**: `knowledge_notes/系统知识笔记/Online Video-LLM (Streaming Video Understanding).md` (score: 192.5), `knowledge_notes/系统知识笔记/Streaming KV Cache (Dual-Level).md` (score: 556.9)

**方法细节**（L2 框架运行模拟）：

Video 模型（尤其是 Streaming Video LLM）需要在 strict causal constraint（不能预看未来帧）下逐帧处理视频流，并在合适的时机做出响应-沉默决策：

```
=== LiveStar Streaming SVeD 调度流程 ===

系统架构:
  Video Frame Stream → Vision Encoder (InternViT) → Streaming SVeD Loop
  → Response/Silence Decision → (if response) Decode → Time-Stamped Captions

SVeD (Streaming Verification and Decoding) Loop:
  for each incoming frame Frm^{t_j}:
    
    Step 1: Vision Encoding (逐帧)
      frame_tokens = InternViT(Frm^{t_j})    # 16 tokens/frame
      
    Step 2: Cache Lookup (Inter-dialogue Streaming Cache)
      # 加载历史帧的 K/V, 无需重算所有帧
      hist_K, hist_V = inter_dialogue_cache.load(up_to=t_j-1)
      
    Step 3: Verification Forward Pass
      new_K, new_V = compute_KV(frame_tokens)
      K = concat(hist_K, new_K)
      V = concat(hist_V, new_V)
      PPL = attention_and_ppl(Q, K, V, Dec_tokens)
      # PPL: 当前上下文下生成已有描述的 perplexity
      
    Step 4: Gate Decision (响应-沉默决策)
      if PPL > alpha * PPL_ref:            # 语义发生变化
          → [Response Mode]
          new_tokens = generate(K, V)      # 生成新描述
          output = tokenizer.decode(new_tokens)
          intra_cache.update(Dec_tokens)   # 更新 clip 内 cache
          inter_cache.append(Dec_tokens)   # 追加到跨 clip cache
      else:
          → [Silence Mode]
          # SVeD Swap: Cache 中 Dec 从响应位置移到末尾
          swap_last_two_in_cache(inter_cache)
          # 维持状态，无输出
          
    Step 5: Memory Management (每 W 帧)
      if cache_size > threshold:
          # Peak-End 压缩: 保留高 PPL (峰值) + 最新 (末尾) 帧
          pruned_indices = peak_end_select(cache, PPL_scores)
          inter_cache = inter_cache[pruned_indices]
          
性能数据 (5 min video):
  双级 Cache (Both):  FPS 3.82
  仅 Intra-dialogue:  FPS 2.92
  无 Cache:           FPS 2.50
  加速比: 1.53×
```

**注解**:
- **关键数据结构**: Intra-dialogue KV Cache (clip 内) + Inter-dialogue Streaming Cache (跨 clip)；Peak-End 压缩基于 PPL score
- **因果约束**: 严格不能访问未来帧——调度器必须按时间戳顺序处理帧
- **响应-沉默权衡**: PPL 门控阈值 alpha 控制灵敏度——过高则漏响应，过低则频繁伪响应

### 方法2：长视频分块调度与上下文窗口滑动

**笔记证据**: `knowledge_notes/系统知识笔记/Online Video-LLM (Streaming Video Understanding).md` (score: 192.5)（笔记未明确说明分块调度的完整实现，以下基于 Video-LLM 通用模式可推断）

**方法细节**（L2 框架运行模拟）：

```
=== 长视频分块调度策略 ===

策略 A: Sliding Window (固定窗口滑动)
  窗口大小 W=64 frames, stride S=32 frames
  for chunk_idx in range(0, total_frames, S):
      chunk_frames = video[chunk_idx : chunk_idx + W]
      # 每 chunk 内做 spatial-temporal encoding
      chunk_tokens = VisionEncoder(chunk_frames)
      # 与前一 chunk 有 S frames 重叠以保持时序连续性
      # 保留 chunk 的 attention KV cache (仅最近 K chunks)
      
策略 B: Hierarchical Chunk (分层分块)
  Level 1: Short-term chunks (8 frames/chunk) → local spatial-temporal attention
  Level 2: Medium-term segments (8 chunks → 64 frames) → segment-level attention
  Level 3: Long-term context (选择关键 segments via similarity search)
  
  调度时间线:
    T0: 并行处理 Level 1 的 N 个 chunks (可在多 SM 分区上并发)
    T1: Level 2 的 segment attention (依赖 Level 1 所有 chunks 完成)
    T2: Level 3 的 long-term context retrieval + final decode

策略 C: Context Window Sliding (LLM 上下文窗口管理)
  对于无限长视频，LLM context window 有限 (如 128K tokens)
  调度器维护 sliding context:
    当前窗口: [system_prompt | recent N frames' tokens | frame queries]
    当新帧达到窗口限制:
      → 按重要性评分 (attention score / PPL) 驱逐最旧/最不重要帧
      → 保留 attention sink tokens (从不驱逐)
      → 类似 StreamingVLM 的 Asymmetric Token Retention
```

**注解**:
- **窗口大小选择**: W 受 GPU memory (KV cache) 约束；S 决定 stride 间重叠度和计算开销
- **分层调度的优势**: 粗粒度 segment-level 搜索定位候选区域，细粒度 frame-level 处理执行精确分析

**硬件视角分析**（Video 整体）:
- **SM 占用率**: 逐帧编码 (每帧仅 16 tokens) 的 ViT forward 是 light-weight——SM 利用率低；batch 多帧可提升利用率但增加延迟
- **HBM 带宽压力**: 长视频 (30 min+) 的 KV Cache 可能 > GPU HBM 容量 → 需要 eviction/swapping 策略；Streaming KV Cache 的双级设计缓解了反复 re-encoding 的带宽消耗
- **脉动阵列利用率**: 单帧 spatial encoding (16 tokens/frame) 的 GEMM 维度极小 → NPU 脉动阵列利用率低；temporal attention 的序列长度较大可部分补偿

## 五、跨模型硬件体系结构对比

### 5.1 调度粒度与硬件并行能力匹配

| 模型类型 | 调度粒度 | GPU SM 匹配度 | NPU 脉动阵列匹配度 | HBM 带宽压力 | 最优硬件平台特征 |
|----------|----------|---------------|---------------------|-------------|------------------|
| **MoE** | Expert-level (粗粒度) / Token-level (AEP 细粒度) | 中-高 (GEMM batch size 依赖) | 中 (A2A 通信开销大) | 高 (expert weights 反复加载) | 高 NVLink 带宽 + 大 HBM 容量 |
| **DiT** | Step-level (粗粒度) | 高 (全量 latent tokens 填充 SM) | 高 (大 GEMM 打满脉动阵列) | 中 (compute-bound) | 高 Tensor Core 密度 |
| **多模态** | Stage-level (粗粒度，ViT vs LLM 交替) | 中 (阶段切换有 idle) | 中-低 (异构单元负载不均) | 高 (visual tokens KV Cache) | 大 HBM + 多计算单元异构调度 |
| **Video** | Frame-level (细粒度，逐帧) | 低 (单帧编码 SM 利用率低) | 低 (逐帧 GEMM 太小) | 极高 (长视频 KV Cache 膨胀) | 大内存容量 + 高效 eviction/swap |

### 5.2 调度策略对硬件利用率的影响汇总

| 调度策略 | SM 占用率影响 | HBM 带宽影响 | 通信开销影响 |
|----------|--------------|-------------|-------------|
| EP Barrier (Baseline) | ↓↓↓ Cold expert GPU idle | ↓↓↓ Small batch weight loading dominant | ↑↑↑ Barrier A2A 占 59% |
| AEP 异步调度 | ↑↑↑ Cold tokens 积累后批量执行 | ↑↑↑ 批量执行摊销 weight loading | ↓↓↓ Async P2P 替代 barrier |
| AEBS GPU Kernel | ↑↑ Expert load 均衡 → SM 均匀利用 | → 解耦架构 KV cache 常驻 | ↓↓ NVSHMEM one-sided |
| METRO Expert-Balanced | ↑↑ 减少激活 expert 数 | ↑↑ Memory→Compute 转变 | ↓ AllGather vs All-to-All |
| CFG Batch 双流 | ↑↑ GEMM M 维度翻倍 | ↑ Weight 加载减半 | N/A (单 GPU) |
| Vision Exit (多模态) | ↑ Deep layers 计算量降低 | ↑ 视觉 KV Cache 释放 | N/A |
| Streaming KV Cache | → 逐帧编码固有低利用率 | ↓↓ 避免重编码历史帧 | N/A |
