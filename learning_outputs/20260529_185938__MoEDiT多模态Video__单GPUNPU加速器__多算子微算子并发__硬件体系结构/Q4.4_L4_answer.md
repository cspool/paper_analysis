## 方法细节（Kernel 调度粒度）

### 方法1: FlashAttention 的 IO-Aware Tile Size 优化（GPU — Tensor Core/MMA tile 匹配）

**笔记证据**: `knowledge_notes/kernel知识笔记/Tiling in GPU Attention Kernel.md` (score: 6335.8)、`knowledge_notes/硬件知识笔记/GPU Memory Hierarchy (HBM vs SRAM).md` (score: 3119.0)、`knowledge_notes/kernel知识笔记/FlashAttention（IO-Aware精确注意力融合Kernel）.md` (score: 611.0)

#### Kernel 伪代码：FlashAttention Forward Tile 切分与 SRAM 管理

```cuda
// ============================================
// FlashAttention Forward: IO-Aware Tiled Attention
// Q, K, V: [N, d]  fp16/fp32
// O: [N, d]       output
// ============================================

// GPU 硬件参数 (NVIDIA A100/H100)
#define SMEM_PER_SM     192*1024   // 192 KB shared memory per SM (H100 up to 228KB)
#define MAX_REGISTERS   65536      // per SM
#define MAX_THREADS     2048       // per SM (H100)
#define MAX_WARPS       64         // per SM

// Tile 参数 (根据 SMEM 容量推导)
// B_r: Q/O tile size along N (rows per Q block)
// B_c: K/V tile size along N (rows per K/V block)
// M = SMEM capacity (192KB for A100)
__device__ void flash_attention_forward(
    float* Q, float* K, float* V, float* O,
    int N, int d, int B_r, int B_c
) {
    // === Step 0: 分配 Shared Memory ===
    // 每 block pair (i,j) 的 SRAM 分配 (A100, B_c=384, B_r=64, d=64, fp16):
    //   K_j tile: B_c × d × 2B  = 384 × 64 × 2 = 49 KB
    //   V_j tile: B_c × d × 2B  = 384 × 64 × 2 = 49 KB
    //   Q_i tile: B_r × d × 2B  = 64 × 64 × 2  =  8 KB
    //   S_ij/P_ij: B_r × B_c × 2B = 64 × 384 × 2 = 49 KB
    //   Total: 49+49+8+49 = 155 KB ≤ 192KB ✓
    //
    // 注: 若 B_c 增大到 512 → Total ≈ 49+49+8+64 = 170KB，仍可放入但降低 occupancy
    //        若 B_c 减小到 256 → Total ≈ 32+32+8+32 = 104KB，提升 occupancy 但增加 HBM pass 数
    
    __shared__ float K_tile[B_c][d];    // [B_c, d] = 384×64 = 24,576 elements
    __shared__ float V_tile[B_c][d];    // [B_c, d]
    __shared__ float Q_tile[B_r][d];    // [B_r, d] = 64×64 = 4,096 elements
    
    // === Step 1: Outer Loop — 遍历 K/V blocks ===
    int T_c = ceil(N / B_c);            // N=1024 → T_c=3 KV blocks
    for (int j = 0; j < T_c; j++) {
        // Load K_j, V_j from HBM to Shared Memory
        // Coalesced access: 相邻线程读取连续地址 → 128B transaction alignment
        cooperative_load(K_tile, K + j*B_c*d, B_c*d);   // 从 HBM 加载
        cooperative_load(V_tile, V + j*B_c*d, B_c*d);   // 从 HBM 加载
        __syncthreads();  // 确保 K_j, V_j 全写入 SMEM
        
        // === Step 2: Inner Loop — 遍历 Q/O blocks ===
        int T_r = ceil(N / B_r);        // N=1024 → T_r=16 Q blocks
        for (int i = 0; i < T_r; i++) {
            cooperative_load(Q_tile, Q + i*B_r*d, B_r*d);
            __syncthreads();
            
            // === Step 3: Tensor Core MMA — On-chip Compute ===
            // S = Q × K^T: [B_r,d] × [d,B_c] → [B_r,B_c]
            // 使用 mma.sync.aligned.m16n8k16 (FP16 Tensor Core)
            // MMA fragment: 16×16×16 → 每个 warp 产出一个 16×16 fragment
            #pragma unroll
            for (int k = 0; k < d; k += 16) {
                // a_frag: 16×16 from Q_tile
                // b_frag: 16×16 from K_tile^T
                // c_frag: accumulate
                asm volatile(
                    "mma.sync.aligned.m16n8k16.row.col.f32.f16.f16.f32"
                    : "+f"(c_frag[i][j])
                    : "r"(a_frag[i]), "r"(b_frag[j])
                );
            }
            
            // === Step 4: Online Softmax (SRAM only) ===
            // m_new = max(m_old, row_max(S_ij))
            // P_ij = exp(S_ij - m_new)
            // l_new = exp(m_old - m_new) * l_old + row_sum(P_ij)
            // O_i = diag(exp(m_old - m_new)) * O_i + P_ij @ V_j
            // 全程在 registers + shared memory 中完成，不写 HBM
            
            online_softmax_rescale(S_ij, O_i, m_i, l_i);
            __syncthreads();
        }
    }
}

// === Tile Size 推导公式 ===
// B_c = ceil(M / (4 * d))          M=SMEM size, d=head dim
// B_r = min(B_c, d)
// A100, d=64, M=192KB → B_c = ceil(192*1024/(4*64*2)) = ceil(49152/512) = 384
//                      B_r = min(384, 64) = 64
// H100, d=128, M=228KB → B_c = ceil(228*1024/(4*128*2)) ≈ 228
//                        B_r = min(228, 128) = 128
```

#### 指令 Pipeline 时序图

```
T0    T1    T2    T3    T4    T5    T6    T7    T8    T9    T10   T11
|-----|-----|-----|-----|-----|-----|-----|-----|-----|-----|-----|-----|
[Load K_0]   [Load V_0]   [sync]  [Q_0@K_0 MMA]  [softmax]  [P@V MMA]
           [Load K_1]   [Load V_1]   [sync]  [Q_0@K_1 MMA]  [softmax]  [P@V MMA]
                      [Load K_2]   [Load V_2]   [sync]  [Q_0@K_2 MMA]...
  ←────────────────── Global Memory Load ──────────────────→
                          ←─── Tensor Core MMA (compute) ───→
                                         ←─── Shared Memory R/W ───→

图例:
- Load K_j, V_j: HBM → Shared Memory (async copy / TMA on Hopper)
- Q_i@K_j MMA: Tensor Core warp-level matrix multiply (warpgroup::mma)
- softmax: register-level row reduction + exp + rescale
- P@V MMA: second Tensor Core MMA for output accumulation

异步重叠 (Hopper TMA):
T0    T1    T2    T3    T4    T5
|-----|-----|-----|-----|-----|
[TMA Load K_0,V_0] [Compute S_ij] [TMA Load K_1,V_1] [Compute S_ij+1]...
                    ↑ Producer warp       ↑ Consumer warp
                    ↑ Warp-specialized pipeline (FA3)
```

#### 注解

**Tile Size 与 SM 资源匹配**:
- **Shared Memory 约束**: 192KB/SM (A100)、228KB/SM (H100) 是可配置 SMEM/L1 的统一 SRAM。tile 总 size 必须 ≤ SMEM/SM。H100 支持 `cudaFuncSetAttribute` 配置 SMEM 上限到 228KB
- **Register 约束**: 每 SM 65536×32-bit regs = 256KB。每 thread 最多 255 regs (A100)、每 warp 32 threads → 若每 thread 使用 128 regs，则每 SM 最多 65536/128/32 = 16 warps → occupancy=25%
- **Occupancy 影响**: 更大 tile → 更大 SMEM/thread → 更少 resident warps → 更低 occupancy → 延迟隐藏能力下降。FlashAttention 中 B_c 从 64→256 增大会降低 occupancy，但 HBM passes 减少带来的收益更大（笔记 Figure 2 middle 消融实验验证）
- **Bank Conflict 避免**: K_tile 和 V_tile 行对齐到 128B（32 floats），`cooperative_load` 保证连续访问。shared memory 32 banks × 4B/bank，128B 对齐后无 bank conflict

**Tensor Core MMA Tile 约束**:
- FP16 MMA: `mma.sync.m16n8k16` → M=16, N=8, K=16，每 warp 每步计算 16×8 output subtile
- B_r=64, B_c=384 → B_r 必须能被 16 整除（64=4×16 ✓），B_c 必须能被 8 整除（384=48×8 ✓）
- MMA tile shape 优化：若 B_c 不能被 8 整除 → 最后一个 fragment 需要 padding → 浪费计算；若 B_r 不能被 16 整除 → 部分 warp 空闲 → 降低利用率

**HBM 访问量分析**（笔记数据，N=1024, d=64, B_r=64, B_c=384）:
- Q 加载: N×d = 128KB (16次，每次 8KB)
- K 加载: T_c × B_c × d = 3 × 384 × 64 × 2B = 144KB
- V 加载: 同 K = 144KB
- O 写入: 128KB
- **Total forward HBM ≈ 552KB** vs 标准 attention ≈ 8.5MB → **~15× reduction**

### 方法2: FlashMoE 的 Persistent Kernel Tile-Level 并发（MoE GEMM tile + 多算子/微算子并发）

**笔记证据**: `paper_secs/secs_multimodal_kernel/FlashMoE.../1-Introduction.md` (score: 2752.3)、`knowledge_notes/kernel知识笔记/PIT (Permutation Invariant Transformation) for MoE.md` (score: 47.2)

#### Kernel 伪代码：Persistent Kernel 中 Multi-Tile 并发管理

```cuda
// ============================================
// FlashMoE: Single Persistent Kernel = Gate + Dispatch + Expert FFN + Combine
// 完全融合在一个 persistent kernel 中
// ============================================

// 硬件平台: NVIDIA H100 (132 SMs, 228KB SMEM/SM)
// Grid: N thread blocks, 其中 N-1 个 processor blocks + 1 OS block
// 每个 block: 128 threads (4 warps), 控制 register 使用避免 spill

// === Tile 维度选择 ===
// FlashMoE 经过参数 sweep 选择 tile = (128, 64)
// 即: M=128 (token batch in tile), K=64 (hidden dim in tile)
// 理由:
//   - 增大 tile width (K 维度) → 显著增加 register 压力 → register spill to local memory
//   - 增大 tile height (M 维度) 不增加 threads → 每 thread 工作量增大 → 延迟增加
//   - 增大 threads/block → 减少 concurrent blocks → 降低 SM occupancy
//   - threads/block > 128 → __syncthreads() barrier overhead 增加

#define TILE_M     128    // token batch (rows of input matrix)
#define TILE_K     64     // hidden dimension (columns)
#define TILE_FFN   2048   // FFN intermediate dim (expert weight col dim)
#define MAX_TASKS   256   // 最大 pending tasks in scheduler queue

// === Actor 模型: 3 种 warp-specialized 角色 ===
// 1. Processor (N-1 blocks × 4 warps): 执行 GEMM (CUTLASS) + element-wise
// 2. Scheduler (1 warp in OS block): 多线程 work-conserving 任务调度
// 3. Subscriber (3 warps in OS block): 解码远程 tile packets → 任务入队

__global__ void flash_moe_persistent_kernel(
    float* input_tokens,       // [S, H]  S=seq_len, H=hidden_dim
    float* expert_weights,     // [E, H, D]  experts, intermediate dim
    float* output_tokens,      // [S, H]
    int S, int H, int E, int D, int tile_M, int tile_K
) {
    // === 初始化: 确定 actor 角色 ===
    int block_id = blockIdx.x;
    int warp_id  = threadIdx.x / 32;
    
    if (block_id < gridDim.x - 1) {
        // ====== Processor Actor ======
        // 使用 CUTLASS 底层 GEMM 基础设施
        // CUTLASS tile configuration: 
        //   ThreadBlockShape: 128×128×32
        //   WarpShape: 64×64×32
        //   MMA: 16×8×16 (FP16 Tensor Core)
        
        __shared__ float A_tile[tile_M][tile_K];    // input tile
        __shared__ float B_tile[tile_K][tile_FFN];  // expert weight tile
        __shared__ float C_tile[tile_M][tile_FFN];   // intermediate result
        float accum_reg[8][8];  // register accumulator (MMA fragment)
        
        while (true) {
            // === 从 Scheduler 获取 task ===
            TaskDescriptor task = fetch_task_from_scheduler();  // 通过 global memory
            if (task.type == TASK_TERMINATE) break;
            
            // === Task 1: Gate + Routing (element-wise) ===
            if (task.op == OP_GATE) {
                // Gate 计算: Softmax(W_g · x)  → 选择 top-k experts
                // Tile: 128 tokens × 64 hidden
                float gate_scores[tile_M][E];
                // ... 线性变换 + softmax + top-k selection
                // 结果写入 symmetric tensor layout L (for inter-GPU dispatch)
            }
            
            // === Task 2: Expert FFN (GEMM-based) ===
            if (task.op == OP_GEMM0) {
                // A_tile: [128, 64] input activation tile
                // B_tile: [64, 2048] expert weight W1 tile
                // C_tile: [128, 2048] output
                
                // CUTLASS warp-level MMA:
                // warpgroup::mma(A_tile, B_tile, C_tile)
                // 利用 Tensor Core mma.m16n8k16 × 多次迭代
                for (int k_tile = 0; k_tile < H/16; k_tile++) {
                    load_to_reg(A_reg, A_tile + k_tile*16);
                    load_to_reg(B_reg, B_tile + k_tile*16);
                    mma_sync(C_reg, A_reg, B_reg, C_reg);  // 累加
                }
                // Activation: GELU(C_tile) → 在寄存器中完成
                // 避免单独 kernel launch → 消除 kernel launch overhead
                apply_gelu_in_registers(C_reg);
            }
            
            // === Task 3: GEMM1 (FFN second linear) ===
            if (task.op == OP_GEMM1) {
                // C_tile: [128, 2048] (post-GELU)
                // W2_tile: [2048, 64]
                // Output: [128, 64]
                // 同理 CUTLASS warp-level MMA
            }
            
            // === Task 4: Expert Combine (Hadamard product + reduction) ===
            if (task.op == OP_COMBINE) {
                // weighted_sum = Σ g_i * expert_output_i
                // 在寄存器中完成 element-wise 加权累加
            }
            
            // === Inter-GPU Communication (via NVSHMEM DMA) ===
            if (task.op == OP_SEND_TILE) {
                // payload-efficient: 不发送 padding tokens
                // 直接 DMA 写入 remote GPU symmetric tensor buffer
                nvshmem_put_nbi(remote_buffer, local_tile, tile_size, remote_pe);
            }
        }
        
        // ====== Scheduler Actor (OS block, warp 0) ======
        // work-conserving: 只要有 processor idle + task ready → 立即调度
        // task queue: 在 global memory 中, 支持 multi-threaded enqueue/dequeue
        // 调度策略:
        //   1. 优先调度同一 expert 的连续 tile (提升 cache 局部性)
        //   2. GEMM0→GEMM1 的 data dependency 通过 notification signal 传递
        //   3. 跨 GPU tile 通过 subscriber 解码后入队
        
        // ====== Subscriber Actor (OS block, warps 1-3) ======
        // 监控 remote GPU incoming DMA buffer
        // 解码 tile packets → 创建 task descriptors → notify scheduler
    }
}
```

```
- ░░ = idle/waiting
- GEMM0 = first linear (W1), GEMM1 = second linear (W2)
- E0-T0 = Expert 0 Tile 0, 被 scheduler 动态分配到空闲 processor
- SEND/GET = inter-GPU tile transfer via NVSHMEM one-sided DMA
- 注: FlashMoE tile(128,64) 确保 128 threads/block → 充足的 occupancy
       不增大 thread count 以免 __syncthreads() 开销增加
```

#### 注解

**Persistent Kernel Multi-Tile 管理策略**:
- **Tile-level parallelism**: 输入 token 矩阵沿 sequence 维度切分为 tile(128,64)，每个 tile 由 processor block 独立处理
- **OS Block 资源占用**: 1/132 blocks (H100) → ~0.75% SM 资源用于调度管理，其余用于计算
- **Single kernel launch vs 550 kernel launches**: FlashMoE 1 次 launch 替代 Megatron-LM+DeepEP 的 432-550 次 launch → 消除 host-device 同步点、kernel 启动间隙 → SM 利用率从 14% 提升到 93.17%（笔记 Table 1, Figure 4a, 9）
- **Task queue in global memory**: 调度开销 ≥ SMEM-based inter-actor communication (OS block 内部 subscriber↔scheduler 通过 SMEM)

**MoE Tile 特殊考虑**:
- Expert 分散访存: 不同 expert 的输入 token 经过 routing 后可能分散在不同 GPU → tile 需要通过 DMA/RDMA 传输
- PIT (笔记 `knowledge_notes/kernel知识笔记/PIT (Permutation Invariant Transformation) for MoE.md`): 将稀疏 micro-tile 重组为 dense tile → 高 GPU GEMM 利用率 → 置换不变性保证计算等价
- Expert capacity padding: FlashMoE 使用 in-place padding（不发送空 token），减少通信开销

### 方法3: CUTLASS Kernel Tile 配置与 MMA Tile 利用率优化

**笔记证据**: `knowledge_notes/kernel知识笔记/Hardware-Aligned Tile Search (WELDER).md` (score: 2522.1)、`paper_secs/secs_multimodal_kernel/ThunderKittens.../span-idpage-14-0spanB-EXTENDED-RESULTS.md` (score: 1713.1)

#### Kernel 伪代码：CUTLASS-Style Grouped GEMM Tile 配置

```cuda
// ============================================
// CUTLASS v3 Grouped GEMM for MoE Expert FFN
// Tile配置驱动的warp-level MMA调度
// ============================================

// === CUTLASS Tile 配置层次 ===
// Level 1: ThreadBlock Tile (shared memory resident)
//   ThreadBlockShape: 128×128×32  (M×N×K)
// Level 2: Warp Tile (register resident)  
//   WarpShape: 64×64×32
// Level 3: MMA Instruction Tile (1 cycle)
//   InstructionShape: 16×8×16 (FP16)、16×8×32 (INT8)、16×16×32 (FP8 on Hopper)

template <
    typename ElementA,       // input activation, fp16
    typename ElementB,       // expert weight, fp16  
    typename ElementC,       // output, fp32
    int TileM, int TileN, int TileK,  // ThreadBlock tile shape
    int WarpM, int WarpN, int WarpK,  // Warp tile shape
    int Stages                           // Software pipeline stages (3 for H100)
>
struct MoEExpertGEMM {
    // === Shared Memory 分区 (H100: 228KB/SM, 可配置) ===
    // 双缓冲 (double-buffered) shared memory for software pipeline:
    //   A_smem: Stages × TileM × TileK × sizeof(fp16)
    //           = 3 × 128 × 32 × 2 = 24,576 B ≈ 24 KB
    //   B_smem: Stages × TileK × TileN × sizeof(fp16)
    //           = 3 × 32 × 128 × 2 = 24,576 B ≈ 24 KB
    // Total SMEM ≈ 48 KB → 剩余 228-48=180 KB 用于 occupancy
    
    // === Register 分配 (每 warp) ===
    // 每 warp 计算 64×64 output subtile → 4×4 MMA iterations
    // A_frag: 64×32 fp16 = 2048 elements × 2B / 32 threads = 128B/thread = 32 regs
    // B_frag: 32×64 fp16 = 2048 elements × 2B / 32 threads = 32 regs  
    // C_accum: 64×64 fp32 = 4096 elements × 4B / 32 threads = 128 regs
    // Total ≈ 192 regs/thread → 255 max, OK for H100
    
    __device__ void operator()(
        float* C, const float* A, const float* B, int M, int N, int K
    ) {
        // === 确定 MMA tile 对齐 ===
        // FP16 MMA: M 必须被 16 整除, N 必须被 8 整除, K 必须被 16 整除
        // 若实际维度不对齐 → padding to next multiple → 计算后 crop
        
        // === TMA (Tensor Memory Accelerator) — H100 only ===
        // 异步 HBM→SMEM 数据搬运，不占用 register/shared memory 带宽
        #if __CUDA_ARCH__ >= 900  // SM90 (Hopper)
            // TMA descriptor for A matrix tile
            // TMA load: 1D array, coordinate-based addressing
            // 每个 thread block 1 个 TMA unit → producer warp 负责
            if (warp_id == PRODUCER_WARP) {
                for (int stage = 0; stage < Stages; stage++) {
                    // expect TMA completion before loading next tile
                    cp_async_bulk_tensor::expect_read(barrier);
                    // 异步加载 A tile to SMEM
                    cp_async_bulk_tensor::load_global_to_shared(
                        A_smem[stage], A_ptr, tile_coord, barrier
                    );
                    // 异步加载 B tile to SMEM
                    cp_async_bulk_tensor::load_global_to_shared(
                        B_smem[stage], B_ptr, tile_coord, barrier
                    );
                }
            }
        #else
            // 传统 async copy (cp.async) for A100/4090
            // 128B transaction width for coalesced access
            cp_async::load_global_to_shared(A_smem[stage], A_ptr, tile_size);
            cp_async::commit();
        #endif
        
        // === Warp-level MMA (consumer warps) ===
        // 每个 warp 计算自己的 output subtile
        // CUTLASS warp tile iterator 自动处理分块
        #pragma unroll
        for (int k_block = 0; k_block < K; k_block += TileK) {
            // SMEM → Register (copy fragment)
            load_A_fragment(A_reg, A_smem[current_stage]);
            load_B_fragment(B_reg, B_smem[current_stage]);
            
            // Tensor Core MMA: A_frag[16,16] × B_frag[16,8] → C_accum[16,8]
            // 对于 WarpM=64, WarpN=64:
            //   warp_tile_iters_M = 64/16 = 4
            //   warp_tile_iters_N = 64/8  = 8
            //   Total MMA instructions per warp per k_block = 4×8 = 32
            #pragma unroll
            for (int m = 0; m < WarpM/16; m++) {
                #pragma unroll
                for (int n = 0; n < WarpN/8; n++) {
                    mma_sync(C_accum[m][n], A_reg[m], B_reg[n], C_accum[m][n]);
                }
            }
        }
        
        // === Epilogue: Activation + Store ===
        // 融合 GELU activation → 在寄存器中完成，避免额外 kernel
        #pragma unroll
        for (int m = 0; m < WarpM/16; m++) {
            #pragma unroll
            for (int n = 0; n < WarpN/8; n++) {
                // GELU: x * Φ(x) 其中 Φ 是 standard Gaussian CDF
                // 近似: 0.5x * (1 + tanh(√(2/π) * (x + 0.044715 * x^3)))
                apply_gelu_fused_in_reg(C_accum[m][n]);
            }
        }
        // Store to global memory (coalesced, 128B-aligned)
        store_coalesced(C_ptr, C_accum);
    }
};

// === Tile Shape 对 MMA 利用率的影响分析 ===
// 场景 1: 完美对齐 (TileM=128, TileN=128, TileK=32)
//   128/16=8 M-iterations × 128/8=16 N-iterations = 128 MMA/warp
//   → 100% Tensor Core 利用率（无 padding waste）
//
// 场景 2: 非对齐 (TileM=130, TileN=128, TileK=32)  
//   130→padded to 144 (=9×16) → 144/16=9 M-iterations
//   实际有效计算: 130×128, Padding: 14×128
//   → 利用率 = 130/144 = 90.3%（10% waste）
//
// 场景 3: 小 tile (TileM=64, TileN=64, TileK=16)
//   64/16=4 × 64/8=8 = 32 MMA/warp
//   → 低 MMA 指令密度 → warp scheduler 有更多 stall slots → 低 SM 利用率
//   但高 occupancy（更多 resident warps 延迟隐藏）
```

#### 注解

**CUTLASS Tile 配置层次约束**:
- **ThreadBlock Shape 约束**: TileM 必须是 WarpM 的整数倍，TileN 必须是 WarpN 的整数倍。CUTLASS v3 推荐 128×128×32 为 MoE expert FFN 的默认配置
- **MMA Fragment 对齐**: FP16 `mma.m16n8k16` → M 维被 16 整除、N 维被 8 整除、K 维被 16 整除。不满足时需 padding → 计算浪费。FP8 (Hopper) `mma.m16n8k32` → K 维对齐放宽到 32
- **Bank Conflict 避免**: CUTLASS 自动 padded shared memory layout (swizzle mode) → 确保同一 warp 内所有 lane 访问不同 bank。例如 A[128,32] 经 swizzle 后每行跨 32 banks 均匀分布
- **WELDER Hardware-Aligned Tile Search**: 笔记显示三个惩罚——coalesced access penalty (非连续 128B transaction)、parallelism penalty (tile 数 < 128)、capacity penalty (footprint > capacity) ——确保搜索到的 tile 配置不仅在 traffic cost 上最优，而且在硬件执行效率上最优

**ThunderKittens 的简化 Tile 抽象**（笔记 `paper_secs/secs_multimodal_kernel/ThunderKittens...`）:
- 默认 16×16 tile for Tensor Core，支持 padded tiles 处理非对齐维度
- LCSF 模板 (Load-Compute-Store-Finish): producer warp 通过 TMA 异步加载 → consumer warpgroups 执行 MMA → store warp 写回
- Pipeline stages: 对于 128×256 (2 compute warpgroups) 或 192×192 (3 compute warpgroups) output tile，自动生成 4-stage software pipeline
- 跨平台: NVIDIA H100 (CUDA)、NVIDIA 4090 (Ada Lovelace)、Apple M2 (Metal) 共用同一抽象

```
// ============================================
// Infera Compiler: Tile-Based Zero-Tuning Compilation
// 编译时静态分析 → 多配置 micro-kernel 生成 → 无需 GPU profiling
// ============================================

编译流程:
  DNN Operator (e.g., MoE Expert FFN, DiT Attention)
        │
        ▼
  [1] Operator Tiling: 将 operator 切为 tile/micro-operators
        │  tile shape 枚举 (从最小合法 shape 开始扩展)
        │  对每个 axis: expand_toward_hardware_alignment
        │
        ▼
  [2] Multi-Version Generation: 对每个 micro-operator 生成多份 kernel
        │  配置维度:
        │    - Register cap: 64 / 96 / 128 registers per thread
        │    - SMEM cap: 48 / 80 / 112 / 144 KiB
        │    - Pipeline stages: 2 / 3 / 4
        │    - Spatial tile: (M=128,N=64) vs (M=64,N=128) vs (M=256,N=32)...
        │    - Reduction tile: K=16 vs K=32 vs K=64
        │
        ▼
  [3] Static Analysis (Zero-Tuning, 无需 GPU profiling):
        │  - Resource constraint check: reg ≤ reg_cap, SMEM ≤ SMEM_cap
        │  - Instruction scheduling: ILP 分析 → 独立指令数 → dual-issue opportunity
        │  - Arithmetic intensity: FLOPs/Byte → compute-bound vs memory-bound
        │  - Warp specialization: producer/consumer split on H100
        │
        ▼
  [4] Kernel Selection at Runtime:
        根据输入 shape 和硬件平台选择最佳 kernel variant
        若输入变化 (如 MoE token count、DiT latent size) → 选择对应 variant

// === 多版本 kernel 示例 ===
// 同一 DiT Attention 算子，根据 sequence length 选择不同 tile 配置：

kernel_variants = {
    // Variant A: 短序列 (N ≤ 512), 大 tile, 高 arithmetic intensity
    "short_seq": {
        B_r: 128, B_c: 256,       // large tiles, fewer HBM rounds
        reg_cap: 128,              // high register usage
        smem_cap: 144,             // 144 KiB SMEM
        pipeline_stages: 2,
        target: "compute-bound"    // compute dominates
    },
    // Variant B: 长序列 (N > 512), 小 tile, 高 occupancy
    "long_seq": {
        B_r: 64, B_c: 128,        // small tiles, more resident blocks
        reg_cap: 64,               // low register usage → high occupancy
        smem_cap: 80,              // 80 KiB SMEM
        pipeline_stages: 4,
        target: "memory-bound"     // memory bandwidth is bottleneck
    },
    // Variant C: FP8 Hopper variant
    "fp8_h100": {
        B_r: 128, B_c: 256,
        mma: "m16n8k32",          // FP8 uses larger K dimension in MMA
        use_tma: true,             // TMA for async data movement
        pipeline_stages: 4,        // deeper pipeline for FP8
    }
};
```

#### Dynamic dEngine Selection in ChituDiffusion (DiT)

```
// ============================================
// ChituDiffusion 运行时 Tile/DEngine 动态选择
// 笔记: paper_secs/secs_2026/29-Difflow...
// ============================================

运行时决策流程:
  Request arrives (e.g., DiT image gen, ragged input shape)
        │
        ▼
  [1] Data Property Inference
      - 用 fingerprint hash 检测输入 redundancy
      - 评估 property condition expression
        │
        ▼
  [2] dEngine Selection (Algorithm 1 in paper)
      - 枚举匹配 property condition 的 dEngine
      - 每个 dEngine = 预编译的 tile 配置 + kernel variant
      - 选择 max batch size within hardware constraints
        │
        ▼
  [3] Tile-Level Execution
      - Ragged operation regularization: 不规则 operation → 等价 regular operator
      - Round-robin tile → thread block mapping (for ragged batching)
        │
        ▼
  [4] Performance Model 辅助选择
      - OLS regression on input size → estimated execution time
      - compute-intensive ops: linear/quadratic scaling with input
      - selects dEngine with minimal estimated latency
```

#### 注解

**编译时 vs 运行时 Tile 选择权衡**:
- **Zero-Tuning (Infera)**: 编译时全静态分析 → 无需 GPU profiling → 比 Ansor/MetaSchedule 快 2-3 个数量级。适合已知硬件配置的场景
- **dEngine Selection (ChituDiffusion)**: 编译时生成多个 dEngine → 运行时根据 data property 动态选择。适合 diffusion 模型的不同 denoising step、不同 batch size、不同 LoRA/ControlNet 配置
- **Triton Autotuning**: 笔记未详细说明，但一般流程是: 定义 tile size 为 tunable parameter → 编译时网格搜索 → 缓存最优配置。对 MoE 的 token 分配可变性支持有限

**动态 Tile 切分的可行性分析**（笔记证据综述）:
- **MoE expert 输入 token 数变化**: FlashMoE 使用固定 tile(128,64)，scheduler 动态分配 task → 自适应不同 expert 的 token 数；PIT 方法在运行时重组微 tile
- **DiT 不同 diffusion step 的 latent size**: ChituDiffusion 通过对不同输入 property 预编译多个 dEngine 来支持；编译时已知所有可能 shape → 运行时快速 match
- **笔记未明确说明**: runtime real-time tile shape adjustment（如在 kernel 中动态改变 shared memory tile 维度）的可行性。笔记更多指向编译时多版本 + 运行时选择的策略

### Web 推断补充：NPU 和 TPU 的 Tile 约束

**升腾 910B (Da Vinci 架构)** (Web 推断):
- Cube Unit (矩阵乘): 16×16×16 FP16 MAC per cycle，类似 Tensor Core 的 MMA fragment 概念。tile 的 M、N 维度应被 16 整除
- Vector Unit (向量计算): 256-bit SIMD width → FP16 下 16 elements/cycle。tile 的 element-wise activation/normalization 应匹配 16-element 向量宽度
- L0 Buffer (A/B): 各 64KB → tile footprint 主导的约束类似 GPU SMEM。推测 tile size ≤ ceil(Cube_L0 / element_size / data_width)

**TPU v5e/v5p** (Web 推断):
- MXU 128×128 (BF16/INT8)，v5p 支持 128×256。这是 systolic array 的硬件固定尺寸
- Tile 必须适配 MXU 维度：矩阵乘的 M 和 N 维度应被 128 整除或使用 padding；若 tile < 128，MXU 部分 PEs 空闲 → 硬件利用率下降
- VPU memory: 每 TPU chip 16-32 GB HBM，但 on-chip memory 受限于 MXU 输入 buffer → tile 选择需在 systolic array 输入带宽和 HBM 带宽间权衡
