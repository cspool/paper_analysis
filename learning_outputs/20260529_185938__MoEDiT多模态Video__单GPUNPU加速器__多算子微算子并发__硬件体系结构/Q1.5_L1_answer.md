## 一、方法细节 — 多算子并发的五大关键挑战与硬件约束

### 挑战 1: 数据依赖导致的串行化瓶颈

#### 1.1 MoE: Routing Decision → Expert 计算的严格串行依赖

**笔记证据**: `paper_secs/secs_moe/Pre-gated MoE...` (score: 4862.4), `knowledge_notes/系统知识笔记/Expert Parallelism.md` (score: 2809.6)

MoE 层的执行存在不可并行的数据依赖链：**Router 必须先生成 gating decision，expert 计算才能开始，expert 输出必须聚合后才能继续下一层**。

```
算法: MoE Layer Data Dependency DAG
输入: X ∈ R^{B×S×D} (batch × seq × hidden)
      Router W_g ∈ R^{D×E}
      Expert FFN_1,...,FFN_E

// Stage 1: Gating — 必须串行执行，因为所有 expert 依赖其输出
1: G = X · W_g                          // [B,S,E] Router 计算
2: S, I = TopK(G, K)                    // [B,S,K] scores + indices
   // ★ 串行瓶颈: Expert 计算依赖 I 的内容
   // ★ I 的值在运行时才能确定，无法静态调度

// Stage 2: Token Dispatch — 依赖 Stage 1 的 I
3: for token t ∈ {1..B×S}:              // 遍历所有 token (串行逻辑)
       e = I[t]                          // 读取路由目标
       X_e[e].append(token_emb[t])       // 按 expert 分组
   // ★ 串行瓶颈: dispatch 是 gather 操作，依赖 routing indices

// Stage 3: Expert FFN — 可并行 (不同 expert 间无依赖)
4: for expert e ∈ {1..E}:               // ★ 可并行!
       Y_e[e] = FFN_e(X_e[e])            // 独立计算，无数据依赖

// Stage 4: Token Combine — 依赖所有 expert 完成
5: for token t ∈ {1..B×S}:              // 按 token 聚合 (串行逻辑)
       Y[t] = S[t] · Y_e[I[t]]           // weighted combine

返回: Y ∈ R^{B×S×D}
```

**注解**:
- **变量含义**: `B`=batch size, `S`=seq length, `D`=hidden dim, `E`=num experts, `K`=top-k 激活数
- **数据依赖**: Stage 1→2 (Router 输出→Dispatch)、Stage 3→4 (Expert 输出→Combine) 是严格串行依赖；Stage 3 内部 expert 间无数据依赖，可全并行
- **硬件瓶颈**: Routing decision 的 "运行时确定" 特性意味着 GPU 的 warp scheduler 无法预先知道计算分布，所有 expert 的权重必须驻留在显存中或提前预取（如 Pre-gated MoE 的 pre-gating 方案）；All-to-All 通信在 expert 并行场景下引入额外的同步 barrier
- **并发可行性**: Expert FFN 之间完全可并行，但受制于 routing 的串行前驱和 combine 的串行后继

#### 1.2 DiT: Denoising Step 间的严格时序依赖

**笔记证据**: `paper_secs/secs_2026/21-TetriServe.../Mosharaf-Chowdhury.md` (score: 3291.2)

DiT 推理的核心约束：**每个 denoising step 的输出是下一个 step 的输入，step 间无法并行**。

```
算法: DiT Iterative Denoising — 严格时序依赖
输入: z_T ∈ R^{H×W×C} (初始噪声 latent)
      t = T, T-1, ..., 1 (timesteps)

1: for step s = T down to 1:            // ★ 严格串行: 无法并行
       // Step 内部计算流 (可部分并行):
2:     t_emb = TimestepEmbedding(s)       // 时间嵌入
3:     // Attention Block — multi-head 可并行
       for head h ∈ {1..H}:
4:         Q_h, K_h, V_h = z_s · W_{qkv,h} // ★ Head 间无依赖，可并行
5:     Attn = Concat(head_1..head_H) · W_o // ★ 依赖所有 head 完成
6:     z_s' = LayerNorm(z_s + Attn)        // 残差 + 归一化

7:     // FFN Block
8:     z_s'' = z_s' + FFN(z_s')            // 逐 token 独立，可并行

9:     // Diffusion-specific: 噪声预测 + 去噪更新
10:    ε_θ = OutputHead(z_s'')             // 噪声预测
11:    z_{s-1} = SchedulerStep(z_s, ε_θ, s) // DDIM/DDPM 更新
       // ★ z_{s-1} 成为下一步的输入 — 严格时序依赖

返回: z_0 (去噪后的图像 latent)
```

**注解**:
- **串行化瓶颈**: T 个 denoising step（典型 T=20-50）形成严格的时序链；每个 step 内 attention head 和 FFN token 维度可并行，但 step 间有 barrier
- **硬件影响**: DiT 是 compute-bound（多 step 操作全量 latent token），单 step 内部大量 GEMM→Tensor Core 利用率高；但 step 间 barrier 导致 GPU SM 在 step 切换时空转，尤其 step 尾部的 element-wise 操作（LayerNorm、SiLU）只能使用 SIMT Core，Tensor Core 空闲
- **优化方向**: Consistency Models / step distillation 减少 step 数；step 内 attention+FFN 间 pipeline 化（下一 step 的 embedding 可与当前 step 的 output head 重叠）
- **笔记未明确说明**: 不同 denoising step 间是否存在类似 LLM 的 "speculative decoding" 推测机制

#### 1.3 多模态: Cross-Attention 依赖双模态编码完成

**笔记证据**: `paper_secs/secs_video_image/FOCUS.../FOCUS-...md` (score: 1389.0)

多模态模型的跨模态融合存在清晰的 **两阶段数据依赖**:

```
算法: Multimodal Cross-Attention Dependency
输入: Image I ∈ R^{H×W×3}, Text T ∈ R^L (token ids)

// Phase 1: 双模态编码 — ★ 可完全并行
1: V_feat = VisionEncoder(I)            // [N_patch, D_v] 视觉编码
2: T_feat = TextEncoder(T)              // [L, D_t] 文本编码
   // Vision 和 Text 编码间无数据依赖，可并行执行

// Phase 2: 跨模态融合 — ★ 依赖 Phase 1 两者完成
3: // Cross-Attention: Text→Vision (或 Vision→Text)
   Q = V_feat · W_Q                      // Query from vision
4: K = T_feat · W_K, V = T_feat · W_V    // Key/Value from text
5: Cross_Attn = Softmax(QK^T/√d)·V       // ★ 依赖 V_feat 和 T_feat 均已就绪
   // ★ 串行瓶颈: cross-attention 必须等两个 encoder 都完成

6: Fused = FusionLayer(Cross_Attn)       // 融合层
7: Output = LLM_Decoder(Fused)           // 语言模型解码
```

**注解**:
- **并发机会**: Vision Encoder 和 Text Encoder 之间无数据依赖，可在不同计算单元上并行编码（如 GPU Tensor Core 跑 Vision ViT + SIMT Core 跑 Text Tokenization）
- **串行瓶颈**: Cross-Attention 是硬 barrier——两模态编码未完成前无法开始；且 Cross-Attention 的 QKV 投影是 GEMM 操作，占用 Tensor Core，与 encoder 的 GEMM 竞争同一硬件资源
- **硬件影响**: 若 GPU 仅有单一 Tensor Core 阵列，双模态编码只能时分复用；若有独立 NPU（如 Apple ANE）+ GPU 异构，可实现真正的并行编码
- **笔记未明确说明**: 是否存在 "partial cross-attention"（模态编码进行到一定阶段即开始融合）

#### 1.4 Video: Temporal Attention 依赖多帧特征就绪

**笔记证据**: `paper_secs/secs_video_image/VideoRoPE.../4-Temporal-Index-Scaling...md` (score: 6581.1)

Video 模型的 spatio-temporal attention 引入跨帧数据依赖:

```
算法: Video Spatio-Temporal Attention Dependency
输入: V ∈ R^{T×H×W×C} (T 帧视频)

// Phase 1: Spatial Encoding — 帧间独立，★ 可并行
1: for frame f ∈ {1..T}:                 // ★ 所有帧可并行编码
       S_feat[f] = SpatialEncoder(V[f])  // 独立 spatial attention

// Phase 2: Temporal Attention — ★ 依赖所有帧的 spatial 特征
2: // 将所有帧特征沿 temporal 维度拼接
   S_all = Concat(S_feat[1], ..., S_feat[T])  // [T·N_patch, D]
3: Q_t = S_all · W_Q_t                   // temporal query
4: K_t = S_all · W_K_t, V_t = S_all · W_V_t
5: Temp_Attn = Softmax(Q_t·K_t^T/√d)·V_t  // ★ 跨帧 attention
   // ★ 串行瓶颈: 必须等所有帧完成 spatial encoding

// Phase 3: Joint Spatio-Temporal — 交错依赖
6: for layer l ∈ {1..L}:
       S_feat = SpatialAttention(S_feat)  // 帧内
       S_feat = TemporalAttention(S_feat) // 帧间 — 依赖层内 spatial 结果
```

**注解**:
- **并发粒度**: Spatial encoding 阶段 T 帧完全独立可并行，硬件利用率最高；Temporal attention 阶段是硬 barrier，所有帧必须在此汇聚
- **内存压力**: 多帧特征同时驻留显存——T=16 帧④ 16× per-frame memory；若每帧特征 256MB (ViT-L)，则需 4GB 中间张量，挤占 expert 权重和 KV cache 的显存空间
- **硬件影响**: Temporal attention 的 QK^T 矩阵维度为 (T·N)^2，远大于 per-frame spatial attention 的 N^2，对 HBM 带宽压力更大；Video model 推理是 memory-bandwidth-bound

#### 2.2 Kitsune 细粒度 Dataflow: Tile 级空间并发

**笔记证据**: `knowledge_notes/kernel知识笔记/Synchronous Dataflow Execution on GPUs.md` (score: 2058.2)

Kitsune 实现了 **tile 级空间并发**——不同算子的 CTA 同时驻留在不同 SM 上，通过 L2-resident ring buffer queue 传递 tile 级中间数据:

```
// Kitsune Spatial Pipeline 伪代码
// MLP: Linear1 → ReLU → Linear2 的空间并发执行

// Host 端配置
cudaPipeline pipeline;
pipeline.addKernel(kernel_Linear1, CTA_count=64, type=TENSOR);  // Tensor Core CTA
pipeline.addKernel(kernel_ReLU,   CTA_count=44, type=SIMT);     // SIMT Core CTA
pipeline.addKernel(kernel_Linear2, CTA_count=44, type=TENSOR);  // Tensor Core CTA
pipeline.addQueue(queue0, producer=Linear1, consumer=ReLU);     // L2-resident queue
pipeline.addQueue(queue1, producer=ReLU, consumer=Linear2);
pipeline.launch();

// GPU 端执行 (空间并发):
// SM_0: Linear1_CTA_0 (TensorCore: GEMM tiles) + ReLU_CTA_0 (SIMT)
// SM_1: Linear1_CTA_1 + ReLU_CTA_1
// SM_2: Linear1_CTA_2 + ReLU_CTA_2
// ...
// SM_N: ReLU_CTA_k + Linear2_CTA_m
//
// 数据流:
//   Linear1 写 tile → queue0 (L2 cache) → ReLU 消费 tile
//   ReLU 写 result → queue1 (L2 cache) → Linear2 消费 tile
//   全程无 global barrier, 无 DRAM round-trip
```

**注解**:
- **Tile 粒度**: 128-256KB payload 时 aggregate bandwidth 达 2 TB/s (A100 108 SMs)
- **同步开销**: <63% @ ≥64KB payload; 小 payload (1KB) 时同步开销 12× bandwidth 下降
- **硬件约束**: 需要双 arbiter grid scheduler（SIMT + Tensor）实现异质 CTA 的 SM co-location；当前 GPU 无此硬件支持
- **与 BSP 的关键区别**: (a) 无 global barrier between operators; (b) 中间数据通过 L2 queue 传递 (非 DRAM round-trip); (c) Tensor Core + SIMT Core 同时活跃

#### 2.3 Iris 粗/细粒度模式分类

**笔记证据**: `paper_secs/secs_multimodal_kernel/Iris...` (score: 5903.6)

Iris 将 compute-communication overlap 分为两大类:
- **Unfused 模式** (粗粒度): 计算和通信在独立 kernel 中执行 — 实现简单但存在 pipeline bubble (kernel launch overhead + 同步延迟)
- **Fused 模式** (细粒度): 计算和通信融合在单 kernel 内 — 消除 bubble 但需精细的 tile 级资源管理

**粒度选择对硬件的影响**:
- 粗粒度 → 对 GPU grid scheduler 无特殊要求，但 SM 利用率低 (许多 SM 在等待通信时空闲)
- 细粒度 → 需要硬件支持 inter-CTA 通信（如 Kitsune 的双 arbiter scheduler）或 device-side enqueue（如 AMD ROCm）

### 挑战 3: 并发算子间的负载均衡

**笔记证据**: `paper_secs/secs_moe/MoE-GPS...` (score: 10821.0), `paper_secs/secs_moe/PROBE...` (score: 12085.9), `knowledge_notes/系统知识笔记/Expert Parallelism.md` (score: 2809.6)

#### 3.1 MoE Expert 计算量不均

PROBE 定义了 **Imbalance Ratio (IR)** 量化 expert 负载不均:

$$\mathcal{IR} = \frac{\max_{r \in \{0,\dots,ep-1\}} \mathcal{L}_r}{\frac{1}{ep} \sum_{r=0}^{ep-1} \mathcal{L}_r}$$

其中 $\mathcal{L}_r = \sum_{e \in \mathcal{E}_r} n_e$ 为 rank r 上的 token 负载。

**实验观测** (笔记显示):
- Prefill 阶段: IR 峰值 > **2.6**（大批次 ≈32K tokens 时），语义局部性导致 expert 激活集中
- Decoding 阶段: IR 波动于 **1.43–2.28**，约 **50% 的全局计算能力在同步 barrier 处空闲**
- 模型稀疏度越高（如 Top-4 vs Top-8），imbalance 越严重

#### 3.2 "Double Penalty" 效应

**笔记证据**: `paper_secs/secs_moe/PROBE...` (score: 12085.9)

```
┌──────────────────────────────────────────────────────────────────┐
│          Double Penalty: 计算偏斜 + 网络拥塞耦合                   │
│                                                                   │
│ 热门 Expert GPU:                                                  │
│   ┌─────────────────────────────────────────────────────┐        │
│   │ All-to-All Recv (高) → Expert Compute (高) → Send (高) │       │
│   │     ↑ 网络拥塞          ↑ 计算 straggler     ↑ 发送拥塞  │       │
│   └─────────────────────────────────────────────────────┘        │
│                                                                   │
│ 冷门 Expert GPU:                                                  │
│   ┌─────────────────────────────────────────────────────┐        │
│   │ All-to-All Recv (低) → Expert Compute (低) → Send (低) │       │
│   │     → 大量空闲, 等待 barrier                          │        │
│   └─────────────────────────────────────────────────────┘        │
│                                                                   │
│ 瓶颈: straggler GPU 的计算延迟 + 网络拥塞 顺序叠加               │
│       而非并行掩盖, 形成 "double penalty"                        │
└──────────────────────────────────────────────────────────────────┘
```

**注解**:
- **硬件根因**: All-to-All collective 是 barrier 同步操作——最慢的 rank 决定全局延迟
- **数据证实**: 真实负载下有效 All-to-All Dispatch 带宽相比手动均衡 baseline 显著下降 (笔记第 4 图)
- **CUDA Graph 冲突**: 动态负载均衡需要可变控制流，与 CUDA Graph 的静态图捕获矛盾；PROBE 将 solver 实现在 GPU 上以避免 host-device 同步

#### 3.3 多模态编码器计算量差异

Vision Encoder（如 ViT-L, ~300M params, ~10^12 FLOPs/image）与 Text Encoder（如 T5-small, ~60M params, ~10^10 FLOPs/text）的计算量可差 **1-2 个数量级**。并行编码时，text encoder 早早完成后等待 vision encoder，造成计算单元利用率不均。

**笔记未明确说明**: 多模态模型中 vision/text encoder 的负载均衡具体数值

#### 4.2 并发带宽竞争模型

当 N 个细粒度并发算子同时访问 HBM 时:

$$B_{effective\_per\_op} \approx \frac{B_{HBM}}{N_{concurrent\_memory\_ops}}$$

**关键场景**:
- MoE expert 并发: E 个 expert FFN 同时需要加载各自权重（每个 expert ~数 GB）→ HBM 带宽被均分
- Video 时空并发: spatial attention 读帧数据 + temporal attention 读跨帧特征 → 双倍带宽需求
- Multi-modal 编码并发: Vision Encoder 加载 ViT 权重 + Text Encoder 加载 LLM embedding → 竞争同一 HBM 通道

**APTMoE 的发现** (score: 2247.3): 在带宽受限的 GPU 节点上（弱互联），MoE 的 data-to-computation ratio 升高导致 **memory-blocking** 问题——即使计算单元有余力，HBM 带宽成为瓶颈。

**MoE-Lens 公式** (score: 6243.2): CPU 总内存带宽需求为 KV cache 访问带宽 + 权重传输带宽之和:

$$B_{Mem} = B_{KV} + B_{IO} = \frac{M}{M_{weight}} B_{IO}$$

注解: 当多个算子并发执行时，上述公式中的 $B_{IO}$ 需乘以并发算子数，峰值带宽需求可能超过 HBM 物理带宽。

### 挑战 5: 同步开销和控制流开销

**笔记证据**: `paper_secs/secs_moe/Toward Cost-Efficient...` (score: 971.6), `paper_secs/secs_multimodal_kernel/ACS...` (score: 568.0), `paper_secs/secs_moe/MegaScale-MoE.../4.2-Intra-operator-Overlap.md` (score: 721.3)

#### 5.1 Barrier 同步: BSP 的固有代价

传统 MoE Expert Parallelism 采用 barrier-style 同步：每个 MoE 层的 All-to-All 要求所有 GPU 在该 barrier 处对齐。AEP/AMoE 论文指出：**load skew 导致 suboptimal device utilization 和 excessive synchronization overheads**。

```
传统 BSP MoE 同步时间线:
GPU0: [Router][All-to-All Dispatch][══════Expert FFN══════][All-to-All Combine][...]
GPU1: [Router][All-to-All Dispatch][══Expert FFN══][空闲等待barrier][All-to-All Combine][...]
GPU2: [Router][All-to-All Dispatch][════════Expert FFN════════][All-to-All Combine][...]
                                   ↑                        ↑
                              Straggler决定            所有GPU等待
                              全局延迟                  barrier释放

AEP 异步 MoE 同步时间线:
GPU0: [Router][µ-queue][Expert FFN][µ-queue][Router_next][...]
GPU1: [Router][µ-queue][Expert FFN(快)][µ-queue][Router_next(提前开始)][...]
GPU2: [Router][µ-queue][Expert FFN(慢)][µ-queue][Router_next(稍后开始)][...]
                         ↑
                  无全局 barrier, token 在 µ-queue 中动态批处理
```

**注解**:
- **AEP 核心思想**: 将 layer 执行与 barrier-style 同步解耦——每层维护 µ-queue，token 到达即处理，不等待 straggler
- **硬件收益**: AMoE 提升吞吐达 **2.7×**；几乎线性扩展到多节点，而 baseline 在 GPU 翻倍时吞吐零增长
- **代价**: 异步执行引入 token 乱序到达，需要额外的 reorder buffer（类似 CPU 乱序执行中的 ROB）

#### 5.2 Kernel Launch Overhead

**笔记证据**: `paper_secs/secs_multimodal_kernel/ACS...` (score: 568.0)

ACS 论文指出细粒度多 kernel 并发面临的困境:
- **CPU-GPU 通信延迟**: 每个 kernel launch 需 CPU→GPU round-trip
- **Grid Scheduler 串行化**: 当前 GPU grid scheduler 要求前一 kernel 所有 CTA dispatch 完成后才能开始下一 kernel dispatch
- **CUDA Graph 缓解**: 预录制 kernel 序列消除 launch overhead，但与动态并发冲突

#### 5.3 Intra-operator Overlap 的 Tile 级同步

**笔记证据**: `paper_secs/secs_moe/MegaScale-MoE.../4.2-Intra-operator-Overlap.md` (score: 721.3)

MegaScale-MoE 的 tile 级计算-通信重叠方案:
- 在 device memory 中实现 barrier，支持 tile 级细粒度通知
- 分配少量 SM 专门处理通信，其余 SM 处理计算
- Swizzling 技术重排 tile 顺序以对齐通信到达与计算节奏

**关键约束**:
- "For A2A+GEMM... allocate a small number of SMs for communication" —— 通信 SM 本身不贡献计算吞吐
- "imperfect tail computation, increasing overall computation latency" —— tile 分解引入的尾部效应
- 动态 routing（MoE）下每个 computation tile 依赖的 source rank 不同，signal control 复杂

## 四、是什么？ (辅助说明)

多算子并发面临的算法挑战本质上是 **计算图 DAG 的拓扑约束与硬件并行能力的张力**。五个核心挑战构成一个层次化的约束体系:

1. **最底层: 数据依赖** —— 计算图固有的拓扑序决定了哪些算子可并发、哪些必须串行
2. **粒度层: 并发粒度** —— 粗粒度简单但硬件利用粗糙，细粒度高效但同步开销大
3. **均衡层: 负载均衡** —— 即使拓扑允许并发，计算量不均也会导致部分单元空转
4. **资源层: 带宽竞争** —— 并发算子争抢有限片上带宽，可能使并发得不偿失
5. **控制层: 同步开销** —— 管理并发的控制逻辑本身消耗硬件资源和时间

这五层约束在不同模型负载上表现各异：MoE 主要受负载均衡和同步开销困扰，DiT 主要受时序依赖约束，多模态和 Video 主要受跨模态/跨帧数据依赖限制。

## 六、方法对比表

| 挑战维度 | MoE 表现 | DiT 表现 | 多模态表现 | Video 表现 | 硬件约束 |
|----------|----------|----------|------------|------------|----------|
| **数据依赖串行化** | Router→Expert→Combine 三阶段严格依赖 | T 步 denoising step 间严格时序依赖 | Cross-Attention 依赖双模态编码完成 | Temporal Attention 依赖所有帧 spatial 特征就绪 | 依赖链长度决定 SM idle time |
| **最优并发粒度** | Expert 级 (粗) + intra-expert tile 级 (细) | Step 内 multi-head + token 级 (中) | Encoder 级 (粗, 两 encoder 并行) | Frame 级 (粗) + per-frame patch 级 (细) | 粗粒度 → SM 利用不均; 细粒度 → 原子操作开销 |
| **负载均衡** | 严重 (IR>2.6 prefill, 1.43-2.28 decode) | 中等 (不同分辨率 step 计算量固定) | 严重 (Vision vs Text encoder 量级差) | 中等 (帧数固定后可均衡) | Straggler 决定 barrier 释放时间 |

| **控制流开销** | 高 (动态 routing 无法静态调度) | 低 (固定 step 数, 计算图确定) | 中 (可静态调度编码器) | 中 (帧数固定) | CUDA Graph 兼容性 vs 动态调度 |
