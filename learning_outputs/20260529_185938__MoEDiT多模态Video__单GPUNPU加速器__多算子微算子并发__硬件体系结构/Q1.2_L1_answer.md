## 一、方法细节（主内容 —— 硬件体系结构侧重）

### 方法1: MoE 稀疏 Gating 容量感知推理 (Capacity-Aware Token Drop)

**笔记证据**: `paper_secs/secs_moe/Capacity-Aware Inference Mitigating the Straggler Effect in Mixture of Experts/CAPACITY-AWARE-INFERENCE-MITIGATING-THE-STRAGGLER-EFFECT-IN-MIXTURE-OF-EXPERTS.md` (score: 9475.4)

#### 是什么？

MoE 的 sparse gating 机制在 expert parallelism 下产生 **Straggler 效应**：token-to-expert 分配不均衡导致某些 expert 过载、其他 expert 空闲等待，过载 expert 的计算时间决定全局延迟。Capacity-Aware Token Drop 通过强制 expert capacity 上限，丢弃过载 expert 上的多余 token，从而均衡负载、消除 straggler。

#### 方法细节（算法伪代码）

```
# Capacity-Aware Token Drop for MoE Inference
# 输入: hidden_states ∈ R^{B×S×D}  (B=batch, S=seq_len, D=hidden_dim)
#       W_gate ∈ R^{D×E}           (E 个 expert 的 gating 权重)
#       capacity_factor C ∈ [1.0, 2.0]
#       num_experts E, top_k K

# Step 1: Gating 计算
router_logits = hidden_states @ W_gate          # [B, S, E]
router_probs  = softmax(router_logits, dim=-1)  # [B, S, E]
topk_weights, topk_indices = topk(router_probs, K, dim=-1)  # [B, S, K]

# Step 2: Expert capacity 计算
tokens_per_expert = capacity_factor * ceil(B*S / E)  # 每个 expert 的 token 上限

# Step 3: Capacity-Aware Token Drop (核心)
for expert_id in 0..E-1:
    # 收集分配给该 expert 的所有 tokens
    expert_mask = (topk_indices == expert_id)      # [B, S, K]
    expert_tokens = hidden_states[expert_mask]     # [N_e, D]

    if N_e > tokens_per_expert:
        # 按 router_probs 降序排序，仅保留 top-C 的 tokens
        sorted_idx = argsort(gate_score[expert_mask], descending=True)
        keep_idx = sorted_idx[:tokens_per_expert]
        drop_idx = sorted_idx[tokens_per_expert:]

        # 丢弃的 token 不参与 expert FFN 计算
        expert_tokens = expert_tokens[keep_idx]  # [C, D]

    # Step 4: Expert FFN 计算
    expert_output = expert_ffn[expert_id](expert_tokens)  # [C, D]

# Step 5: Expanded Drop (可选增强)
# 在 top-K 基础上扩展候选集为 top-(K+K')，增加 token 被至少一个 expert 接受的概率
# 然后再施加 capacity 约束
```

**注解**：
- **变量含义**：`capacity_factor` 控制每个 expert 可处理的最大 token 数，C=1.0 表示精确均分，C=2.0 表示允许 2× over-subscription。`tokens_per_expert` 是硬件友好的上限值。
- **复杂度分析**：原始 MoE 的 expert 计算复杂度为 O(B×S×K×D_ffn)，Capacity-Aware Token Drop 将最坏情况的 expert 计算从 O(max_e N_e × D_ffn) 限制到 O(C×B×S/E × D_ffn)，消除了尾部延迟。
- **数据依赖**：gating 决策必须先于 expert FFN 计算（串行瓶颈），但 expert 间完全独立可并行。
- **硬件适配性**：均衡后的 expert 负载使得 GPU SM 分配更均匀，减少 warp divergence。在 H100 上，30% 推理加速仅带来 0.9% 精度损失（笔记来源：OLMoE 实验）。

#### 硬件体系结构分析

| 硬件层面 | 影响 |
|----------|------|
| **Memory Hierarchy** | Expert 权重在 HBM→L2→SM 的加载时间与 token 数成正比；容量限制减少了最大 expert 的权重加载压力，缓解 HBM bandwidth 瓶颈 |
| **Compute Unit Utilization** | 消除了 "快 expert 等慢 expert" 的同步等待，SM 利用率从 40-60% 提升至 70-85%（笔记：Expanded Drop 在 Mixtral-8×7B 上实现 1.85× 加速） |
| **Tensor Core** | Expert FFN 中的 GEMM 操作在均衡后可以更充分地利用 Tensor Core 的 MMA 指令，避免因 token 过少造成的 CTA 填充不足 |

### 方法2: 后训练量化 (PTQ) —— INT8/FP8/INT4/NF4

**笔记证据**: `knowledge_notes/算法知识笔记/Post-Training Quantization (PTQ).md` (score: 1171.5)；`paper_secs/secs_model_quant/DMQ.../span-idpage-0-0spanDMQ...md` (score: 3729.4)；`paper_secs/secs_model_quant/Q-VDiT.../Q-VDiT-Towards-Accurate-Quantization...md` (score: 5777.5)

#### 是什么？

PTQ 将预训练模型的高精度参数（FP32/FP16）转换为低比特表示（INT8/INT4/FP8），通过整数算术替代浮点运算实现存储压缩和计算加速。对于 **DiT/扩散模型**，DMQ 针对扩散过程的离群值分布和迭代去噪特性设计了专用量化策略。对于 **Video DiT**，Q-VDiT 引入了 Token-aware 量化和时序蒸馏。

#### 方法细节（算法伪代码 —— 通用 PTQ + DMQ 扩散专用）

```
# ===== 通用 PTQ 量化流程 =====
# 输入: 预训练 FP16 模型 M_fp，校准数据集 D_calib
# 输出: INT4/INT8 量化模型 M_q

# Stage 1: 校准（统计各层数值分布）
for each layer L in M_fp.layers:
    w = L.weight                           # [d_out, d_in]，FP16
    for batch in D_calib:
        a = forward_until(L, batch)        # 激活值，FP16

    # 确定量化参数 (scale s, zero-point z)
    if is_symmetric_distribution(w):       # 权重量化 → 对称量化
        s_w = max(|w|) / (2^{N-1} - 1)    # N-bit 量化
        z_w = 0
    else:                                   # 激活量化 → 非对称
        l, u = MSE_minimizing_clip_bounds(a, K=100)  # 最小化 MSE 的 clip 范围
        s_a = (u - l) / (2^N - 1)
        z_a = round(-l / s_a)

    quantizer[L] = (s_w, z_w, s_a, z_a)

# Stage 2: 量化推理
def quantized_linear(x_int, W_int, s_w, s_x, s_y):
    # x_int: [B, S, d_in] @ W_int^T: [d_out, d_in] -> y_int: [B, S, d_out]
    y_int = INT_MATMUL(x_int, W_int.T)     # Tensor Core INT8/INT4 MMA
    y_fp  = y_int * (s_w * s_x / s_y)      # rescale
    return y_fp

# ===== DMQ: 扩散模型专用优化 =====
# 核心1: Learned Equivalent Scaling (LES)
for each channel c in weight:
    # 学习 channel-wise scaling factor α_c
    # 使得量化误差在 weight 和 activation 之间最优分配
    # W'_c = W_c / α_c,  X'_c = X_c * α_c
    # 目标: min_{α} ||W_c X_c - Q(W_c/α_c) Q(X_c*α_c)||²
    α_c = optimize_scaling_factor(W_c, X_c)

# 核心2: Adaptive Timestep Weighting
# 扩散早期步骤的量化误差累积效应更大
for t in denoising_steps:
    w_t = exp(-β * t / T)  # 早期步权重更高
    loss += w_t * reconstruction_loss(o_fp[t], o_q[t])
```

**注解**：
- **量化位宽与硬件映射**：INT8 GEMM 在 NVIDIA Tensor Core 上可达 FP16 的 2× 吞吐（H100: INT8=3958 TOPS vs FP16=1979 TFLOPS）。INT4 进一步可达 INT8 的 2× 吞吐，但精度损失需通过 PTQ 方法（如 GPTQ/AWQ）补偿。
- **DMQ 的 PTS (Power-of-Two Scaling)**：利用 2 的幂次缩放使得 rescale 操作退化为移位，硬件上无需乘法器，节省 ALU 资源。
- **Q-VDiT 的 TQE**：在 token 维度和 feature 维度使用 rank=1 低秩矩阵补偿量化误差，参数开销仅 d_in + d_out + t，推理时通过融合 kernel 执行，额外延迟 <5%。

#### 硬件体系结构分析

| 量化格式 | Tensor Core 加速比 (vs FP16) | 内存带宽节省 | 适用硬件 |
|----------|------------------------------|-------------|----------|
| INT8 | 2× (H100 Tensor Core INT8) | 2× (vs FP16) | NVIDIA GPU, 昇腾 NPU |
| FP8 (E4M3/E5M2) | 2× (H100 FP8 Tensor Core) | 2× | H100/H200, MI300X |
| INT4 | 4× (但需软件支持) | 4× | GPU + 定制 kernel, NPU |
| NF4 | ~4× (非均匀量化) | 4× | 需要解量化开销，适合 memory-bound 场景 |

**硬件关键**：量化对 Tensor Core 利用率提升的前提是 GEMM 维度对齐（如 INT8 需要 K 维度为 16 的倍数，以匹配 Tensor Core 的 16×16 MMA 指令）。NPU（如昇腾 910B）的 cube 单元原生支持 INT8，量化后可在 cube 单元上直接执行整数矩阵乘，与 FP16 使用相同的 cube 硬件但获得 2× 吞吐。

### 方法3: 知识蒸馏 —— MoE → Student MoE / Dense

**笔记证据**: `knowledge_notes/算法知识笔记/Knowledge Distillation for MoE Inference (MoE推理中的知识蒸馏 _ Mixture-of-Students).md` (score: 8563.9)

#### 是什么？

将大 teacher MoE（如 8×7B 参数 Mixtral）蒸馏为更小的 student MoE（如 4×3B）或 dense 模型，减少推理时需加载的 expert 参数总量和计算量。Mixture-of-Students (MoS) 架构用多个 students 联合学习 teacher 的分布，各 student 通过 gating 分工。

#### 方法细节（算法伪代码）

```
# MoE Knowledge Distillation (Mixture-of-Students)
# Teacher: MoE with E_t experts, d_model = D_t
# Student: MoE with E_s experts, d_model = D_s (E_s << E_t, D_s < D_t)

# Stage 1: Teacher logits collection
teacher_logits_cache = {}
for batch in distillation_dataset (e.g., C4/Wikipedia):
    # Teacher 前向 (top-K=2 gating)
    h = embed(batch)                             # [B, S, D_t]
    for layer in teacher_moe.layers:
        gate = softmax(h @ W_gate)               # [B, S, E_t]
        topk_w, topk_idx = topk(gate, K=2)
        h = sum(topk_w[e] * expert_ffn[e](h) for e in topk_idx)
    teacher_logits_cache[batch] = output_logits  # [B, S, V]

# Stage 2: Student training with distillation
for batch in distillation_dataset:
    # Student 前向 (top-K=2, E_s experts)
    h_s = embed_s(batch)                         # [B, S, D_s]
    for layer in student_moe.layers:
        gate_s = softmax(h_s @ W_gate_s)         # [B, S, E_s]
        topk_w_s, topk_idx_s = topk(gate_s, K=2)
        h_s = sum(topk_w_s[e] * expert_ffn_s[e](h_s) for e in topk_idx_s)

    student_logits = lm_head(h_s)                # [B, S, V]

    # 联合损失
    loss_ce  = CrossEntropy(student_logits, labels)           # 硬标签
    loss_kd  = KL_div(softmax(student_logits/T),
                      softmax(teacher_logits_cache[batch]/T)) # 软标签蒸馏
    loss = (1-λ) * loss_ce + λ * T² * loss_kd    # T=温度, λ=蒸馏权重

# Stage 3: 部署推理
# Student 推理仅需加载 E_s 个 expert（vs teacher E_t 个）
# 显存占用从 O(E_t × D_t × d_ffn) 降至 O(E_s × D_s × d_ffn)
```

**注解**：
- **MoS 关键改进**：多个 students 通过 gating 分工，比单一 student 更能保留 teacher 的 expert 多样性，精度损失更小。
- **硬件收益**：蒸馏后 expert 数从 128→32（如 DeepSpeed-MoE 方案），HBM 占用减少约 4×，使得模型可放入单卡 HBM（80GB），避免 CPU offloading 的 PCIe 带宽瓶颈（~64 GB/s vs HBM ~3.35 TB/s）。
- **memory bandwidth 影响**：减少的参数量直接降低了 expert 权重从 HBM→L2→SM 的加载时间，将原本 memory-bound 的 MoE 推理转变为 compute-bound。

#### 硬件体系结构分析

| 指标 | Teacher MoE (Mixtral 8×7B) | Student MoE (4×3B, 蒸馏后) | 改善 |
|------|---------------------------|---------------------------|------|
| 总参数量 | ~46.7B (8 experts) | ~12B (4 experts) | ~4× |
| 每 token 激活参数 | ~12.9B (2 experts) | ~6B (2 experts) | ~2× |
| HBM 占用 (FP16) | ~93 GB | ~24 GB | ~4× |
| 单卡可行性 | 需 A100-80GB×2 或 offload | 单卡 A100-40GB | 降级部署成本 |
| Memory bandwidth 需求 | ~3.35 TB/s (A100) | ~1.5 TB/s | 降低 55% |

### 方法4: 推测解码 (Speculative Decoding) —— 通用及 MoE 专用

**笔记证据**: `knowledge_notes/算法知识笔记/Speculative Decoding.md` (score: 4483.2)；`knowledge_notes/算法知识笔记/Speculative Decoding in MoE Offloading（MoE Offloading 中的投机解码）.md` (score: 3614.1)；`paper_secs/secs_moe/MoESD Unveil Speculative Decoding's Potential for Accelerating Sparse MoE/MoESD-Unveil-Speculative-Decodings-Potential-for-Accelerating-Sparse-MoE.md` (~score: 6500)

#### 是什么？

推测解码使用轻量 draft model 自回归生成 γ 个候选 token，target model 一次并行前向验证所有候选，通过 rejection sampling 保证输出分布与 target model 原生解码一致（lossless）。对于 MoE 模型，IFMoE 的 self-draft 变体使用同一模型但减少激活 expert 数（6→2）作为 draft，无需额外模型。

#### 方法细节（算法伪代码 + MoE 专用优化）

```
# ===== 标准 Speculative Decoding =====
# Input: prefix p, draft model M_q, target model M_p, draft_len γ
# Output: generated token sequence

while not EOS:
    # Phase 1: Draft (auto-regressive, 小模型/少expert)
    draft_tokens = []  # 存储 γ 个候选 token
    for i in 1..γ:
        q_i = sample(M_q(p + draft_tokens))     # 自回归，每次前向 ~2ms
        draft_tokens.append(q_i)

    # Phase 2: Verify (parallel, 大模型/全expert)
    # 一次前向并行处理 prefix + γ 个 draft token
    logits_{1..γ+1} = M_p(p + draft_tokens)     # 单次前向 ~20ms

    # Phase 3: Rejection Sampling
    n_accepted = 0
    for i in 1..γ:
        p_i = softmax(logits_i)                 # target 的概率分布
        q_i = softmax(M_q_logits_i)              # draft 的概率分布
        if random() < min(1, p_i(draft_tokens[i]) / q_i(draft_tokens[i])):
            output.append(draft_tokens[i])       # 接受
            n_accepted += 1
        else:
            # 拒绝：从 (p_i - q_i) 归一化后采样
            resampled = sample(normalize(max(p_i - q_i, 0)))
            output.append(resampled)
            break                               # 截断，剩余 draft token 丢弃
    if n_accepted == γ:
        # 全部接受，额外从 logits_{γ+1} 采样一个 bonus token
        output.append(sample(softmax(logits_{γ+1})))

# ===== MoE Self-Draft (IFMoE) =====
# Draft: 激活 2/6 experts
# Target: 激活 6/6 experts
# 不做 rejection sampling，接受所有 draft token
# 通过 KV-cache revision (用全量 experts 重算 KV) 补偿信息损失

# ===== MoE Offloading 中的 SD (SpecMoEOff) =====
# Draft model on GPU, Target MoE experts on CPU
# Draft 阶段快速生成候选 token
# Verify 阶段: CPU 端加载 target MoE expert 权重并验证
# 关键优化：Computation Reordering
# 在 verify 前按 expert_id 对 draft tokens 重新分组
# 使同 expert 的 tokens 连续计算 → 提高 CPU cache 命中率
```

**注解**：
- **加速比公式**（笔记来源: knowledge_notes/Speculative Decoding for Long Context）：SD 的理论加速比为 `Speedup = (γ × α + 1) / (γ × c + 1)`，其中 α 为 acceptance rate，c = latency(M_q)/latency(M_p)。当 α > c 时有正加速。典型值：γ=5, α=0.8, c=0.1 → speedup ≈ 3.3×。
- **MoE 的优势**：MoESD 论文发现中等 batch size 下 MoE 从 SD 获益超过 dense 模型，因为 MoE 的验证阶段受益于 expert 稀疏性（更少的每 token 计算），而 draft 阶段相对更轻量。
- **target efficiency 度量**：MoESD 提出新度量，表征 draft 质量 × 验证效率的乘积效应，帮助识别是 draft 质量瓶颈还是验证吞吐瓶颈。

#### 硬件体系结构分析

| 硬件维度 | SD 的影响 |
|----------|----------|
| **Tensor Core 利用率** | 验证阶段 batch = γ+1 的并行前向可充分利用 Tensor Core，batch size 增大使得 GEMM 更接近 roofline |
| **Memory Bandwidth** | Draft model 参数少、memory footprint 小（~1/100），可在 L2 cache 中常驻，减少 HBM 访问 |
| **NPU 适配** | 昇腾 NPU 的 cube 单元在小 batch 时利用率低，SD 的验证阶段将多个 token 打包为 "伪 batch" 并行处理，提升 cube 利用率 |
| **PIM (Processing-in-Memory)** | Adaptive Draft Sequence Length 论文探索了在 PIM 系统上动态调整 draft 长度以匹配 PIM 的带宽和计算特性 |

### 方法5: KV-Cache 压缩 —— eviction/sliding window/选择性裁剪

**笔记证据**: `paper_secs/secs_effAttn/Rethinking_Key-Value_Cache_Compression_Techniques_for_Large_Language_Model_Serving/RETHINKING-KEY-VALUE-CACHE-COMPRESSION-TECHNIQUES-FOR-LARGE-LANGUAGE-MODEL-SERVING.md` (score: 4857.4)；`paper_secs/secs_effAttn/Cross-Self_KV_Cache_Pruning_for_Efficient_Vision-Language_Inference/span-idpage-0-1spanCross-Self-KV-Cache-Pruning-for-Efficient-Vision-Language-Inference.md` (score: 4837.8)

#### 是什么？

KV-cache 压缩通过 eviction（淘汰不重要的历史 KV）、sliding window（仅保留最近 W 个 token 的 KV）、或选择性裁剪来减少 LLM 解码阶段的显存占用和 memory bandwidth 消耗。对于多模态模型，Cross-Self KV Cache Pruning 进一步区分 cross-attention（视觉-文本）和 self-attention 的 KV 缓存，进行模态感知的剪枝。

#### 方法细节（算法伪代码）

```
# ===== KV-Cache 压缩通用框架 =====
# 输入: 当前 token 的 Q ∈ R^{1×d}，已缓存的 K_cache ∈ R^{L×d}, V_cache ∈ R^{L×d}
# 参数: 最大缓存长度 L_max, sliding_window W

# 1. Sliding Window Attention
def sliding_window_kv(K_cache, V_cache, W):
    # 仅保留最近 W 个 token 的 KV
    K_win = K_cache[-W:, :]                     # [W, d]
    V_win = V_cache[-W:, :]                     # [W, d]
    return K_win, V_win

# 2. Eviction Policy (H2O / Heavy-Hitter Oracle)
def heavy_hitter_eviction(K_cache, V_cache, Q, budget):
    # 计算每个历史 token 的 attention score 累积作为重要性
    scores = softmax(Q @ K_cache.T / sqrt(d))    # [1, L]
    importance = cumulative_attention(scores)     # 累积注意力分数

    # 保留 top-budget 重要的 KV + 最近 W 个 token
    top_idx = topk(importance, budget - W)
    recent_idx = [L-W, ..., L-1]
    keep_idx = top_idx ∪ recent_idx

    K_compact = K_cache[keep_idx, :]             # [budget, d]
    V_compact = V_cache[keep_idx, :]
    return K_compact, V_compact

# 3. 多模态 KV Cache Pruning (Cross-Self)
# 区分两种 KV cache:
#   - Cross-KV: 视觉 token 的 KV (编码器输出侧)
#   - Self-KV:  文本 token 的 KV (解码器自注意力侧)
def multimodal_kv_prune(cross_kv, self_kv, budget_cross, budget_self):
    # 对 cross-KV 使用 modality-specific pruning
    # 视觉 token 通常有大量空间冗余
    cross_scores = compute_visual_importance(cross_kv)  # 基于注意力图
    cross_pruned = cross_kv[topk(cross_scores, budget_cross)]

    # 对 self-KV 使用标准 eviction
    self_scores = compute_attention_importance(self_kv)
    self_pruned = self_kv[topk(self_scores, budget_self)]

    return cross_pruned, self_pruned
```

**注解**：
- **memory bandwidth 收益**：KV-cache 压缩将解码阶段的 memory footprint 从 O(L×d×layers) 降至 O(budget×d×layers)。对于长序列推理（L=128K, d=128, layers=80, FP16），原始 KV-cache 需 128K×128×80×2B ≈ 2.6 GB/layer，压缩到 budget=4096 后降至约 83 MB/layer，HBM→SM 的访存量减少约 32×。
- **Rethinking KV-Cache 的关键发现**（笔记来源）：(1) 当前实现未针对生产级 serving 优化压缩后的 memory layout，压缩带来的 memory 减少未必转化为延迟减少；(2) 压缩 KV 可能导致更长输出（模型倾向于生成更多 token），反而增加端到端延迟。
- **多模态特化**（笔记来源：Cross-Self KV Cache Pruning）：视觉 token 通常占 KV cache 的 80-90%，模态感知的剪枝策略可比统一剪枝多节省 30-50% 的 KV 存储。

#### 硬件体系结构分析

KV-cache 压缩的硬件影响主要体现在 **memory hierarchy**：

| 缓存层级 | 原始 KV-cache | 压缩后 | 影响 |
|----------|-------------|--------|------|
| HBM 占用 | >100 GB (128K seq) | <10 GB | 可能使模型从多卡部署降为单卡 |
| L2 Cache 命中率 | 低（KV 溢出 L2） | 高（压缩 KV 可部分常驻 L2） | 减少 HBM→L2 传输延迟 |
| SM 寄存器压力 | 高（长序列 softmax 需多轮 tile） | 低 | 提高 occupancy |

### 方法6: 扩散模型步蒸馏 (Step Distillation / Consistency Models)

**笔记证据**: `paper_secs/secs_model_quant/D2-DPM Dual Denoising for Quantized Diffusion Probabilistic Models/Dsup2sup-DPM-Dual-Denoising-for-Quantized-Diffusion-Probabilistic-Models.md` (score: 8899.0)；`paper_secs/secs_2026/96-LATENT WAVELET DIFFUSION FORULTRA-HIGH-RESOLUTION IMAGE SYNTHESIS/96-LATENT WAVELET DIFFUSION FORULTRA-HIGH-RESOLUTION IMAGE SYNTHESIS.md` (score: 2734.3)

#### 是什么？

扩散模型推理需要 T 步迭代去噪（通常 T=50-1000），每步都需完整 DiT 前向。Consistency Models (CM) 和步蒸馏将多步去噪压缩到 1-4 步，在保持生成质量的同时实现数量级加速。其核心思想是学习直接从噪声映射到干净数据的 consistency function：`f(x_t, t) → x_0`。

#### 方法细节（算法伪代码）

```
# ===== Consistency Models 推理 =====
# 原始扩散: x_T → x_{T-1} → ... → x_0 (T步, 例如 T=50)
# CM 推理:   x_T → x_0 (1-4步)

# 训练目标 (Consistency Distillation)
def consistency_loss(model_cm, pretrained_diffusion):
    # 采样相邻时间步
    t = random_uniform(1, T)
    x_t   = add_noise(x_0, t)                   # [B, C, H, W] 或 [B, S, D]
    x_{t-1} = pretrained_diffusion.denoise_step(x_t, t)  # 教师的一步去噪

    # CM 在相邻时间步的输出应一致
    f_t   = model_cm(x_t, t)                     # [B, C, H, W]
    f_{t-1} = model_cm(x_{t-1}, t-1)
    loss = MSE(f_t, f_{t-1})                     # 一致性损失

# 推理: 从噪声一步/少步生成
def cm_inference(noise, model_cm, n_steps=2):
    x = noise
    for t in reversed(linspace(0, T, n_steps)):
        x = model_cm(x, t)                       # 每步直接预测 x_0
    return x

# ===== 与量化结合 (D²-DPM) =====
# 双去噪: 同时使用量化模型和 FP 模型的输出进行蒸馏
def d2_dpm_step(x_t, t, quant_model, fp_model):
    # quant_model: INT4/INT8 量化的扩散模型 (加速)
    # fp_model: 原始 FP16 模型 (高质量参考)
    x_q = quant_model.denoise(x_t, t)            # 量化去噪
    x_fp = fp_model.denoise(x_t, t)              # FP 去噪（仅在部分步使用）
    # 融合两个输出去除量化噪声
    return (1-β) * x_q + β * x_fp               # β ∈ [0, 1] 混合系数
```

**注解**：
- **加速幅度**：原始扩散 50 步 → 4 步 CM 约 12.5× 理论加速，实际 wall-clock 加速约 8-10×（考虑 CM 每步计算量略大）。
- **硬件收益**：步数减少直接降低 DiT 前向次数，每次前向都需要 HBM→L2→Tensor Core 的完整数据流，减少步数等比例降低 HBM 带宽需求。
- **D²-DPM 的硬件考虑**（笔记来源）：量化去噪 + FP 去噪的融合策略使得大部分去噪步骤在 INT8 Tensor Core 上执行（高吞吐），仅关键步骤回退到 FP16 保证质量。

#### 硬件体系结构分析

| 配置 | 去噪步数 | HBM 访问量 (相对值) | Tensor Core 利用率 |
|------|---------|---------------------|-------------------|
| 原始 DDIM | 50 | 1.0× (基准) | ~50% (小 batch) |
| 步蒸馏 (4-step) | 4 | 0.08× | ~60% (每步计算量略大) |
| 量化 + 步蒸馏 | 4 (INT8) | 0.04× | ~80% (INT8 Tensor Core) |

### 方法7: 多模态 Token 剪枝 / 模态稀疏化

**笔记证据**: `paper_secs/secs_effAttn/Cross-Self_KV_Cache_Pruning_for_Efficient_Vision-Language_Inference/span-idpage-0-1spanCross-Self-KV-Cache-Pruning-for-Efficient-Vision-Language-Inference.md` (score: 4837.8)；`paper_secs/secs_video_image/VisiPruner__Decoding_Discontinuous_Cross-Modal_Dynamics_for_Efficient_Multimodal_LLMs/VisiPruner-Decoding-Discontinuous-Cross-Modal-Dynamics-for-Efficient-Multimodal-LLMs.md` (score: 3026.3)

#### 是什么？

多模态模型（如 LLaVA、Qwen-VL）中视觉 token 常占输入 token 的 70-95%，但其中大量 token 对最终答案贡献微小。VisiPruner 通过分析跨模态注意力动态的 "不连续性"，识别并剪枝冗余视觉 token，减少高达 99% 的视觉注意力计算和 53.9% 的 FLOPs。

#### 方法细节（算法伪代码）

```
# ===== VisiPruner: 跨模态视觉 Token 剪枝 =====
# 输入: visual_tokens ∈ R^{N_v × D}, text_tokens ∈ R^{N_t × D}
#       attention_maps 来自 VLM 的 early layers

# Step 1: 分析跨模态注意力不连续性
for layer in VLM.layers[:K]:                    # 仅在 early layers
    attn_vis2text = layer.cross_attn(           # 视觉→文本注意力
        Q=text_tokens, K=visual_tokens
    )                                            # [N_t, N_v]

    # 计算每个视觉 token 的跨模态重要性
    vis_importance = attn_vis2text.sum(dim=0)    # [N_v]
    vis_importance = vis_importance / vis_importance.max()

# Step 2: 不连续性检测
# 跨模态注意力在 token 维度上呈现 "阶跃" 模式：
# 部分 token 获得极高注意力（~连续的重要区域），其余接近 0
importance_sorted = sort(vis_importance, descending=True)
gradient = diff(importance_sorted)               # 差分检测突变点
split_point = argmax(abs(gradient))              # 不连续边界

# Step 3: Token 剪枝
keep_mask = vis_importance > threshold
pruned_vis_tokens = visual_tokens[keep_mask]     # [N_v', D], N_v' << N_v

# 剪枝后的 visual tokens 进入后续 layers
# 仅需 KV-cache 存储保留的 visual token 的 KV
```

**注解**：
- **VisiPruner 发现**（笔记来源）：跨模态注意力的不连续性在 VLM 的 early layers (layer 2-4) 已显现，可用 early-layer 注意力图作为剪枝依据，无需所有 layers 计算。
- **硬件收益**：视觉 token 数从 576 (CLIP ViT-L/14) 降至约 50-100，self-attention 复杂度从 O(N²) 降至 O((N/10)²)，GPU memory bandwidth 压力降低约 10×。
- **训练无关**：VisiPruner 是 training-free 方法，可在推理时直接应用，无需重新训练或微调。

### 方法8: Video 帧跳过 / 选择性帧推理

**笔记证据**: `paper_secs/secs_2026/55-V-Rex Real-Time Streaming Video LLM Acceleration via Dynamic KV Cache Retrieval/VII.-RELATED-WORK--DISCUSSION.md` (score: 1634.4)；`paper_secs/secs_video_image/VideoNSA__Native_Sparse_Attention_Scales_Video_Understanding/VIDEONSA-NATIVE-SPARSE-ATTENTION-SCALES-VIDEO-UNDERSTANDING.md` (score: 614.9)

#### 是什么？

视频理解模型需要处理大量帧（通常 8-256 帧），每帧产生 N_patch 个视觉 token，总 token 数 = frames × patches_per_frame，极易超出 KV-cache 容量。帧跳过和选择性帧推理通过识别关键帧、跳过冗余帧来减少处理的帧数。

#### 方法细节（算法伪代码）

```
# ===== 视频帧选择性推理 =====
# 输入: video_frames ∈ R^{T × H × W × C} (T=帧数)
#       frame_encoder (ViT/DiT), LLM_decoder

# Step 1: 帧重要性评估 (Keyframe Detection)
def select_keyframes(frames, budget):
    # 方法 A: 帧间差异检测
    importance = []
    for t in 1..T:
        diff = MSE(frames[t], frames[t-1])       # 帧间变化
        importance.append(diff)

    # 方法 B: Learnable Frame Selector (VideoLLM-Online)
    # 使用轻量 selector 网络评估每帧的信息量
    # selector: 3D Conv → MLP → sigmoid
    scores = frame_selector(frames)              # [T]

    # 选择 top-budget 帧
    key_indices = topk(importance ∪ scores, budget)
    return frames[key_indices]                   # [budget, H, W, C]

# Step 2: 选择性编码
selected_frames = select_keyframes(frames, budget=min(T, K_max))
visual_tokens = frame_encoder(selected_frames)   # [budget×P, D]

# Step 3: 关键帧的 KV-cache 保留，非关键帧的 KV 压缩
# ReTaKe 方法: PivotKV — 关键帧保留完整 KV，非关键帧仅保留高注意力 token 的 KV
for t, frame_tokens in enumerate(visual_tokens_by_frame):
    if t in keyframe_indices:
        kv_cache.append(frame_tokens)            # 完整保留
    else:
        # 仅保留高注意力 token 的 KV
        attn_scores = compute_self_attn(frame_tokens)
        top_tokens = frame_tokens[topk(attn_scores, budget_per_frame)]
        kv_cache.append(top_tokens)              # 稀疏保留
```

**注解**：
- **VideoNSA**（笔记来源）将 Native Sparse Attention (NSA) 适配到视频理解，通过端到端训练使模型学会在长视频中关注关键帧，原生支持 token 稀疏化，无需额外的 selector 网络。
- **硬件考虑**：帧跳过直接减少了 frame_encoder 的前向次数，每次 ViT/DiT 编码需要完整的 HBM→Tensor Core 数据流。从 256 帧降至 32 帧将编码器计算量减少 8×。

#### 硬件体系结构分析

视频推理的核心硬件瓶颈是 **memory bandwidth**（而非 compute）：

| 视频配置 | Token 总数 | KV-cache 大小 (FP16) | HBM 带宽需求 |
|----------|-----------|---------------------|-------------|
| 256 frames × 256 patches | 65,536 | ~1.3 GB/layer | ~2.6 TB/s (memory-bound) |
| 32 frames × 256 patches (帧跳过 8×) | 8,192 | ~0.16 GB/layer | ~0.33 TB/s (compute-bound 转换) |
| 32 frames × 64 patches (帧跳过 + 空间裁剪) | 2,048 | ~0.04 GB/layer | ~0.08 TB/s |

帧跳过将推理从 **memory-bound 区域推向 compute-bound 区域**，使 Tensor Core 利用率从 ~30% 提升至 ~70%。
