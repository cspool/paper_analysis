### 1. MoE 模型的编译 IR 表示

#### 1.1 High-level IR：XLA HLO 中 all-to-all + expert FFN 子图

**笔记证据**: `knowledge_notes/kernel知识笔记/Irregular All-to-All (All-to-Allv) for MoE Partitioning.md` (score: 1797); `paper_secs/secs_moe/X-MoE.../3.3-Expensive-All-to-All...md` (score: 9305)

MoE 的编译 IR 核心挑战是将 **expert dispatch/combine** 的通信语义与 expert FFN 的计算语义在 IR 中统一表达。

**编译流程模拟 — MoE 层的 IR lowering 链**：

```
Step 1: 前端框架（PyTorch/JAX）→ 计算图
  MoE Layer Forward:
    gate_logits = Linear(hidden)              // [B×S, E]
    topk_indices, topk_weights = TopK(gate_logits, k=2)
    dispatched = Dispatch(tokens, topk_indices)  // [G×C, D] per GPU
    expert_out = ExpertFFN(dispatched)           // 各 expert 独立计算
    combined = Combine(expert_out, topk_indices, topk_weights)

Step 2: XLA HLO 中的表达
  // all-to-all 将 token 按 expert 分配路由到各 GPU
  %dispatched = all-to-all(%tokens, replica_groups={{0,1,...,G-1}})
      维度: 输入 [B×S/G×E, D] → 输出 [B×S/G×E, D]（语义重排）
      底层: NCCL alltoall (intra-node NVLink 900GB/s / inter-node IB 400GB/s)

  // Expert FFN 子图（可被 XLA fusion pipeline 融合内部算子）
  %expert_out = fusion(
      dot(%dispatched, %w1),     // gate_proj
      dot(%dispatched, %w2),     // up_proj  
      multiply(%gate, %up),      // SiLU activation
      dot(%result, %w3)          // down_proj
  )  // XLA multi-output fusion: 3个dot共享输入→融合为单kernel

  // 逆 all-to-all: 将 expert 输出按 token 原始位置归约
  %combined = all-to-all(%expert_out, replica_groups=...)

Step 3: XLA GPU Codegen
  HLO → LHLO (buffer assignment) → LMHLO (MLIR HLO dialect) →
  gpu.launch (CUDA kernel) + Thunk-based runtime (XLA:GPU)

  // 硬件约束下的融合边界:
  // - shared memory ≤ 228KB/SM (H100) → 3个dot weight tile 共享 SRAM 受限
  // - register file 65536 regs/SM (H100) → 255 regs/thread max
  // → XLA fusion pass 根据 cost model 决定是否融合 3 个 dot
```

**注解**：
- **all-to-all 的硬件映射**：笔记显示 X-MoE 在 HPC 平台上发现 intra-node（Infinity Fabric 200 GB/s）与 inter-node（Slingshot 25 GB/s）带宽不对称达 8:1。XLA HLO 的 `all-to-all` 操作在 codegen 阶段需感知此拓扑——intra-node 传输使用 NVLink peer-to-peer，inter-node 降级为 IB send/recv——但笔记未明确说明 XLA 是否自动做此拓扑感知优化。
- **并发机会**：expert FFN 内部的 3 个 dot（gate_proj, up_proj, down_proj）在传统 XLA 中以融合单 kernel 串行执行。多 expert（8 个 expert）之间数据独立，若 IR 能标注每个 expert 为独立 `async.execute` region，可在多 CUDA stream 上并发——但笔记显示 standard XLA 以串行为主，async all-to-all 支持有限。
- **Irregular all-to-all 的 IR 含义**：笔记显示 Lancet 使用双趟 all-to-all（先交换 size 再交换数据），降低通信量（不传输 padding tokens）。在 IR 层面这意味着 all-to-all 的 send/recv sizes 是动态的（不固定 C），IR 需支持 variable-length communication——这对传统 HLO 的固定 shape 假设构成挑战。

#### 1.2 Low-level IR：MLIR 中 MoE expert 并行 region

**笔记证据**: `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md` (score: 578); `knowledge_notes/编译知识笔记/Event-Based Intermediate Representation.md` (score: 3521)

```
编译流程模拟 — MLIR 多 dialect MoE lowering:

=== Level 1: StableHLO (High-level) ===
func @moe_layer(%tokens: tensor<GxCxDxf32>) {
  %gate = stablehlo.dot(%tokens, %gate_w)
  %topk = stablehlo.custom_call @topk(%gate)
  // all-to-all 是 StableHLO 一等公民 op
  %dispatched = stablehlo.all_to_all(%tokens) {replica_groups = dense<...>}
  %expert_out = stablehlo.custom_call @expert_ffn(%dispatched)
  %combined = stablehlo.all_to_all(%expert_out) {replica_groups = dense<...>}
}

=== Level 2: Mixed dialect lowering ===
// all-to-all → 分解为 memref copy within gpu.launch
gpu.launch blocks(%grid) threads(%block) {
  gpu.memcpy %dst, %src : memref<CxD>  // NCCL send/recv
}

// Expert FFN → scf.forall 标注 expert 并发!
scf.forall (%e) in (0 to 8) {
  // 每个 expert 迭代独立 → 编译器可并发发射
  %w = memref.load %expert_weights[%e]
  linalg.matmul ins(%expert_in, %w) outs(%buf)
}
// scf.forall 的硬件映射: 
//   → GPU lowering: 每 iteration 映射为一个 thread block 或独立 kernel
//   → CPU lowering: 每 iteration 映射为 parallel task

=== Level 3: Async dialect (显式并发) ===
%tok_e0 = async.execute { call @expert_0(%in0) }  // async region 0
%tok_e1 = async.execute { call @expert_1(%in1) }  // async region 1 (并发于 0)
// ... E 个 async.execute 可全部并发
async.await %tok_e0, %tok_e1, ...  // gather barrier

=== Level 4: GPU lowering → CUDA streams ===
// async.execute → 独立 CUDA Stream
// async.await → cudaEventRecord/cudaStreamWaitEvent
// gpu.launch → CUDA kernel launch on assigned stream
```

**注解**：
- **`scf.forall` vs `async.execute` 的选择**：`scf.forall` 适合规则并行（各 expert 计算量相近），编译器可做 loop fusion/tiling；`async.execute` 适合不规则并行（各 expert 延迟不同），支持更灵活的设备放置和通信 overlap。
- **硬件约束**：单 GPU 上并发 CUDA stream 数受限于 GPU 的 Hyper-Q 能力（通常 32 个硬件工作队列）。8 个 expert 全部并发映射到 8 条 stream 在硬件层面可行，但超过 32 个 expert 时需 compile-time stream assignment 策略。
- **Event IR 对比**：Cypress 的 Event-Based IR 更进一步——每个异步操作显式生成 event 值，支持 `[(N, WARP)]` 级别的并行完成追踪，可直接 lowering 到 `__syncwarp`/`mbarrier`/`warpgroup sync` 等硬件同步原语。笔记显示该 IR 是纯编译时 construct，无运行时开销。

### 2. DiT（Diffusion Transformer）模型的编译 IR 表示

#### 2.1 High-level IR：StableHLO `while` op + Difflow 符号化 DFG

**笔记证据**: `paper_secs/secs_2026/29-Difflow.../4-Compile-Time-Optimizations.md` (score: 1488); `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md` (score: 578)

DiT 模型的 IR 核心是 **denoising loop** 的表达。StableHLO 用 `while` op 包裹单步 noise prediction + scheduler step；Difflow 通过展开 loop 为 Data Flow Graph（DFG）后进行符号化优化。

**编译流程模拟 — DiT denoising loop 的 IR 变换**：

```
Step 1: 模型定义 → StableHLO while op

  %result = stablehlo.while(%iter_arg = %latent_noise, %t = %num_steps) {
    // cond region: t > 0 继续迭代
    ^cond(%latent, %t):
      stablehlo.return (stablehlo.compare GT %t, %c0)
    // body region: 单步 denoising
    ^body(%latent, %t):
      %t_emb = stablehlo.custom_call @timestep_embed(%t)
      %noise_pred = stablehlo.call @dit_backbone(%latent, %t_emb)
      %next_latent = stablehlo.custom_call @scheduler_step(%latent, %noise_pred)
      stablehlo.return %next_latent, (stablehlo.subtract %t, %c1)
  }

  // 并发语义分析:
  // while body 内部: DiT backbone (MHA + FFN) 的各层间有数据依赖
  // while 跨迭代: %latent_t → %latent_{t+1} 是 SSA loop carried value
  //   → 严格串行依赖: 下一迭代必须等待本次的 latent 输出
  // step-internal 并发: attention 各 head 的 QKV projection 可并行

Step 2: Difflow 符号化 DFG 方法

  // Difflow 的关键洞察: 展开 denoising loop 到收敛
  // (非嵌套、非重叠的 loop，通常 ≤5 步收敛)
  
  ① Loop Unrolling (to stabilization):
     unroll while body × 3-5 iterations
     → flat DFG with symbolic redundancy variables

  ② Symbolic Property Assignment:
     对 DFG 每个输入赋值符号变量:
       α: prompt_text = redundant? (跨请求同一 prompt)
       β: timestep_embedding = redundant? (相邻步可能复用)
       γ: control_image = redundant? (ControlNet 输入)
       T/F: 已知固定属性值

  ③ Property Propagation (Table 1 rules):
     // 示例: BatchMatmul [NHW] 的冗余传播规则
     output_redundancy = [a1 ∧ b1, a2, b3]
     // → 当两个输入的 batch 维都冗余时，输出的 batch 维也冗余

  ④ dGraph Identification:
     按输出属性表达式相同性对连续算子分组:
       dGraph_A: {t_emb → AdaLN → QKV_proj} → 当 β=T 时跨步复用
       dGraph_B: {attention → FFN}           → 每步重算
       dGraph_C: {scheduler_step}             → 每步重算

  ⑤ dEngine Compilation:
     每个 dGraph 按枚举的属性组合编译为多个 dEngine:
       dEngine_A1: β=T → 缓存 timestep embedding，跳过重算
       dEngine_A2: β=F → 标准重算
     → 运行时根据实际属性选择 dEngine

Step 3: MLIR lowering of while body
  // while body 内的 DiT backbone 通过 MLIR 编译:
  ① affine-loop-fusion: 融合 denoising step 内的独立循环
  ② affine-scalar-replacement: 消除临时 intermediate 分配
  ③ affine-parallelize: affine.for → affine.par (标注并行)
  ④ lower-affine → scf + arith
  ⑤ gpu-kernel-outlining + gpu-map-parallel-loops → GPU kernel
  ⑥ convert-to-nvvm → PTX → cubin
```

**注解**：
- **`while` op 的硬件语义**：StableHLO 的 `while` op 在 GPU backend 上被编译为 host-side loop——每次迭代从 host 发射 DiT backbone 的 kernel 序列。这意味着迭代间的 kernel launch 由 host CPU 控制，GPU 端严格串行。Difflow 的方法在编译时将 while body 展开，在展开后的 DFG 中发现跨迭代的数据复用（如相同的 timestep embedding），将"每次重算"转为"一次计算+缓存复用"。
- **符号属性传播的硬件含义**：属性 `redundant=T` 意味着该 tensor 的 HBM 读取可以被消除——直接在 L2 cache 或 shared memory 中复用。H100 的 HBM 带宽 3.35 TB/s，消除一个 1GB 的冗余读取节省 ~0.3ms latency。对 50 步 denoising，若 30% 的数据可复用，总延迟降低 ~4.5ms。
- **dGraph 分解的并发含义**：dGraph 本质上是 IR 层面的并发发现单元——不同 dGraph 的数据依赖由 DFG 的边显式表达，编译器据此决定哪些 dGraph 可并发执行（如 dGraph_A 的 timestep embedding 可与上一 denoising step 的 dGraph_C scheduler_step 在 pipeline 中 overlap）。
- **笔记未明确说明**：StableHLO while op 在 GPU backend 上是否支持 body 内部的异步 kernel launch；Difflow 的单 GPU 验证仅在 A100/H100 上进行；DiT 跨 timestep KV cache 复用等高级优化在 vault 中无直接笔记。

#### 2.2 Low-level IR：Triton IR 中 DiT attention 的 block-level 表达

**笔记证据**: `knowledge_notes/编译知识笔记/Triton (GPU Kernel Language and Compiler).md` (score: 1762); `knowledge_notes/编译知识笔记/Triton Language (GPU Kernel Programming).md` (score: 213)

```
编译流程模拟 — Triton IR 中 DiT Multi-Head Attention 的 lowering:

Python (@triton.jit attention_kernel)
    ↓ Triton Frontend (Python AST → Triton IR)
TTIR (Triton Intermediate Representation)
  - tt.func: kernel 函数签名（含 block-level shape 参数如 BLOCK_M, BLOCK_N）
  - tt.program_id(0): batch index → 并发轴 1
  - tt.program_id(1): head index  → 并发轴 2
  - tt.load: HBM → SRAM tile load
  - tt.dot: Tensor Core GEMM（block-level MMA）
  - tt.store: SRAM → HBM tile write
    ↓ MLIR Optimizations (layout, loop unroll)
TTGIR (Triton GPU IR)
  - block → warp → thread 分解
  - shared memory allocation 显式化
  - cp.async insertion (load pipeline)
    ↓ GPU lowering
LLVM IR → PTX → cuModule → GPU execution

// Autotuner 配置空间（笔记 Monarch kernel 示例）:
configs = [
  {'t_n': 32, 't_r': 32, 't_p': 32}, num_warps=4,
  {'t_n': 64, 't_r': 64, 't_p': 64}, num_warps=8,
  {'t_n': 128, 't_r': 128, 't_p': 64}, num_warps=8,
  ...
]  // 20+ candidate configs
// key=['n', 'r', 'b_1']: 当这些参数变化时重新 tune
```

**注解**：
- **`program_id` 的并发映射**：Triton IR 的 `program_id(axis)` 是 block-level 并发的显式 IR 标注。`program_id(0)` 和 `program_id(1)` 分别沿 grid 的两个轴独立——在 H100 上，若 grid=(B, H)，每个 (batch, head) 组合映射为一个 thread block，SM 级并行调度。这与 GPU 的 SIMT 硬件模型直接对齐。
- **Autotuner 的硬件建模**：Triton autotuner 通过实测进行配置搜索（非 cost model 预测）。`num_warps` 直接影响 SM occupancy——4 warps 允许 16 个 block/SM（H100），8 warps 降至 8 个 block/SM。`num_stages` 控制 software pipeline 深度，影响 global↔shared memory 带宽利用率。
- **单 kernel 内 vs 跨 kernel 并发**：笔记明确指出 Triton 的局限性——单 kernel 内微算子并发（通过 tile-level 并行），但跨 kernel 编排需要外部调度器（如 CUDA Graph 或 host-side scheduler）。

### 3. 多模态模型的编译 IR 表示

#### 3.1 MLIR 中异构编码器的并行表达

**笔记证据**: `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md` (score: 578); `knowledge_notes/系统知识笔记/Module Multiplexing（模块多路复用）.md` (score: 279)

多模态模型（LLaVA/BLIP-2/ImageBind）的核心 IR 特征是**异构编码器的多分支并行**——vision encoder 和 text encoder 在融合前无数据依赖。

**编译流程模拟 — MLIR 中多模态模型 IR 的并行编译**：

```
Step 1: 多模态模型 → MLIR 顶层 IR（两个独立 func.func）

module {
  // 分支 A: Vision Encoder (ViT)
  func.func @vision_encoder(%image: tensor<Bx3x224x224xf32>)
      -> tensor<BxNxDxf32> {
    %patches = stablehlo.convolution(%image, %patch_emb)  // patch embedding
    %feat = call @vit_transformer(%patches) {depth=12, heads=12}
    return %feat
  }

  // 分支 B: Text Encoder (BERT/LLM)
  func.func @text_encoder(%tokens: tensor<BxLxi32>)
      -> tensor<BxLxDxf32> {
    %emb = stablehlo.gather(%emb_table, %tokens)           // token embedding
    %feat = call @bert_transformer(%emb) {depth=12, heads=12}
    return %feat
  }
  // 关键: vision_encoder 和 text_encoder 无相互调用 → 
  // 编译器的 call graph 分析发现两个 func 无依赖 → 可并行
}

Step 2: MLIR Pass Pipeline 中的并行调度

  // Async 包裹两个编码器为独立 region
  %vis_token = async.execute { call @vision_encoder(%image) }
  %txt_token = async.execute { call @text_encoder(%tokens) }
  // 两个 async.execute 可并发发射到不同 GPU stream

  // 融合层 barrier
  async.await %vis_token, %txt_token
  // 等待两个编码器完成 → cross-modal attention 获取两者输出

Step 3: 融合层 — Cross-Modal Attention 的 SSA 数据流

  func.func @cross_modal_fusion(%v: tensor<...>, %t: tensor<...>) {
    // SSA use-def 链显式编码跨模态数据流:
    //   vision tokens (v) → K,V projection → cross-attention
    //   text tokens (t)   → Q projection   → cross-attention
    //   cross-attention   → gated add      → text tokens (updated)
    %q = linalg.matmul ins(%t, %w_q)
    %k = linalg.matmul ins(%v, %w_k)
    %v_proj = linalg.matmul ins(%v, %w_v)
    %attn = stablehlo.custom_call @cross_attention(%q, %k, %v_proj)
    return %attn
  }

Step 4: EEVEE 模块化 IR（补充视角）

  // EEVEE 的 Module Multiplexing: 每个 modality-specific module
  // 在 IR 中表示为独立可调度单元，各自有独立的:
  //   - batch size
  //   - GPU SM allocation (via MPS)
  //   - CUDA stream
  // 这本质上是空间多路复用（spatial multiplexing）在 IR 层面的表达
```

**注解**：
- **异构编码器的 IR 分离价值**：vision encoder（ViT, 卷积-heavy）和 text encoder（BERT, attention-heavy）的计算特征根本不同——前者适合大 tile size + 低 occupancy，后者适合小 tile size + 高 occupancy。IR 中的独立 `func.func` 允许编译器为两者分别做 target-specific 优化（tile size、fusion strategy、register allocation）。
- **跨模态 SSA 边的同步语义**：`cross_attention(%q, %k, %v_proj)` 的 operands `%k` 和 `%v_proj`（来自 vision encoder）与 `%q`（来自 text encoder）必须在 cross-attention 执行前都就绪。编译器从 SSA use-def 链自动推导此同步需求，插入 `async.await`（或等价的 CUDA event 同步）。
- **硬件约束**：笔记显示 EEVEE 通过 NVIDIA MPS 在同一 GPU 上为 vision 和 text encoder 分配不同 SM partition。但笔记未明确说明 MLIR 的 `async.execute` 是否支持 SM 显式分配（这需要额外的 SM allocation hint 在 IR 中表达）。

#### 3.2 多模态 IR 中跨模态融合的表达

**笔记证据**: `knowledge_notes/编译知识笔记/MLIR (Multi-Level Intermediate Representation).md` (score: 578)

多模态融合层（cross-attention）在 IR 中建立了跨模态数据流。MLIR 的 Linalg dialect 通过 `linalg.matmul` 表达跨模态 QKV 计算，SSA 的 use-def 边从 vision 域跨越到 text 域：

```
// 跨模态数据流的 SSA 表达:
// vision 域 → K,V → cross-attention → text 域更新
%K_vis = linalg.matmul ins(%v_feat, %w_k)  // vision 域
%V_vis = linalg.matmul ins(%v_feat, %w_v)  // vision 域
%Q_txt = linalg.matmul ins(%t_feat, %w_q)  // text 域
// 跨域 SSA 边: vision 域的 value 流入 text 域的计算
%cross = linalg.matmul ins(%Q_txt, %K_vis) // cross-modal!
%out   = linalg.matmul ins(%cross, %V_vis) // cross-modal!
```

**注解**：跨模态 SSA 边是编译器的天然同步标记——`%cross` 依赖 `%Q_txt`（text encoder 输出）和 `%K_vis`（vision encoder 输出），编译器据此推导出融合层必须在两个编码器都完成后才能执行，无需用户显式标注同步点。

### 4. Video 模型的编译 IR 表示

#### 4.1 帧级并行的 IR 表达

**笔记证据**: `paper_secs/secs_2026/29-Difflow.../4-Compile-Time-Optimizations.md` (score: 1488, 涵盖 video temporal/spatial attention); `knowledge_notes/编译知识笔记/Multi-Version Micro Kernel Generation.md` (score: 379)

Video 模型的 IR 核心是**时空计算的表达**——帧级并行在不破坏时序依赖的前提下在 IR 中标注。笔记未直接覆盖 `pmap`/`shard_map` 的详细知识笔记，但 Difflow 论文提供了 video generation model 的实际编译流程。

**编译流程模拟 — Video 模型的 IR 表达**：

```
Step 1: Video 模型 → DFG/Difflow 编译

  Video DiT / UNet 的时空算子:
    - spatial_conv:  每帧独立的 2D 卷积 → 帧间无依赖
    - temporal_attn: 跨帧 attention (Q,K,V over T 维) → 帧间全依赖
    - spatial_attn:  每帧独立的 2D attention → 帧间无依赖
    - 3D conv:       kernel 跨帧 (如 3×3×3 over T,H,W) → 局部帧间依赖

Step 2: Difflow DFG 中的帧级分析

  ① Symbolic shape propagation:
     frames 维度表示为符号变量 f
     ragged case: f ∈ {14, 28, 57} (不同请求生成不同帧数)
  
  ② dGraph decomposition for video:
     dGraph_spatial:  所有 spatial-only 算子 (每帧独立)
     dGraph_temporal: temporal attention 算子 (跨帧依赖)
     dGraph_3Dconv:   3D convolution (局部跨帧，如 3×3×3 kernel)
  
  ③ Ragged operation regularization:
     ragged 帧数 → 合并到 batch 维:
       原 [f, C, H, W] → reshape → [(f·H), W, C] → 标准 Matmul
       或 tile each frame independently → round-robin 分配到 GPU blocks

Step 3: 帧级并发的 IR 标注（推断模式）

  // 每帧独立的 spatial 算子 → 标注为并行
  // 伪 IR: scf.forall (%frame) in (0 to num_frames) {
  //   spatial_conv_2d(latent[%frame])
  //   spatial_attn(latent[%frame])
  // }  // frame iterations 无数据依赖 → 可并发映射到不同 SM

  // temporal attention → 需跨帧通信
  // 伪 IR: %all_frames = all-gather(%local_frames, dim='frame')
  //        %t_attn = temporal_attn(%all_frames)
  // SSA 链接: %local_frames (帧 i 的 local) → 
  //            %all_frames (跨帧收集) → 
  //            %t_attn (继续计算)
  // 这种 SSA 链显式编码了 temporal attention 的跨帧依赖
```

**注解**：
- **帧级并发的硬件约束**：temporal attention 的 all-gather 操作在 HBM 上的通信量 = O(T × H × W × C)。对于 T=14 帧、1024×1024 分辨率、C=64 通道的 SVD 模型，单层 temporal attention 需传输约 14×1024×1024×64×2 bytes ≈ 1.8 GB（FP16）。H100 的 HBM 带宽 3.35 TB/s 下传输 ~0.5ms——这是帧级并发的主要瓶颈。
- **Difflow 的 ragged 处理与硬件**：笔记显示 Difflow 将 ragged 帧数请求通过 `fuse batch dim + ragged dim → regular Matmul` 的方式处理——这种方式利用 GPU 的硬件 batch Matmul kernel（如 cuBLAS），无需手写 ragged kernel。
- **笔记未明确说明**：`pmap`/`shard_map` 在单 GPU 上的确切性能和实现细节；video 模型 temporal attention 的 communication-computation overlap 自动生成能力。

## 四、是什么？（辅助说明）

### 4.1 IR 层次定义

| IR 层级 | 代表 | 硬件无关性 | 并发信息保留 |
|---------|------|-----------|-------------|
| High-level IR | StableHLO, Relay | 高（无硬件假设） | SPMD annotation, all-to-all op |
| Mid-level IR | MLIR Linalg/SCF/GPU, DFG (Difflow) | 中（memory hierarchy 抽象） | scf.forall, async.execute, dGraph |
| Low-level IR | Triton IR, LLVM IR, PTX | 低（指令集映射） | program_id, gpu.launch, stream |

### 4.2 四类模型 IR 设计核心差异

| 模型 | IR 核心特征 | 关键并发 IR 原语 | 硬件映射关键 |
|------|-----------|-----------------|-------------|
| **MoE** | all-to-all + expert FFN 子图 | `scf.forall`, `async.execute`, `all-to-all` | NVLink/NVSwitch 拓扑感知 |
| **DiT** | `while` op 或展开 DFG | `affine.par`, `program_id`, dGraph | SM block 级并行, denoising loop 展开 |
| **多模态** | 独立 `func.func` + cross-attention | `async.execute` + `async.await` | 多 CUDA stream, MPS 空间分区 |
| **Video** | 时空算子 IR + frame parallelism | `scf.forall`(frame axis), ragged dEngine | SM 帧级并行, temporal attn 跨帧通信 |
