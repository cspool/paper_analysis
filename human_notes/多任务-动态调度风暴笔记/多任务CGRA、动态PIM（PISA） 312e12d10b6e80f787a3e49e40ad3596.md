### BCE in 动态块稀疏

BCE加速器，BCE是动态块稀疏Attn中的主要耗时算子，计算密度不高而是访存密集算子，严重依赖Host处理。（因此PIM执行访存密集型，XPU执行计算密集型）

BCE——Top-K——SparseAttn中Attn计算的输入块是动态地址，动态数据依赖难以高效处理。

> **[图片提取文字 (image.png)]:**
> block sparse attention, as seen in state-of-the-art methods like Quest [56], LServe [65], and Arkvale [6], has emerged as one of the most promising solutions. This technique is predicated on the insight that, for any given query, only a small subset of the context is semantically relevant and contributes significantly to the attention output. Consequently, it dynamically selects these relevant tokens at block granularity for subsequent attention computation. While this technique significantly prunes unnecessary computation, it inadvertently creates an increasingly dominant bottleneck: Block Criticality Estimation (BCE). The block-wise attention compute is now at constant cost, but the BCE stage must still scan the metadata for every block in the full context. As context lengths scale to one million tokens, this BCE phase, which still scales quadratically with sequence length, can consume as much as 86.7% of the end-to-end latency. Meanwhile, this algorithm exposes a new architectural challenge in how to execute this dynamic, data-dependent workflow (BCE  $\rightarrow$  Top-K  $\rightarrow$  Sparse Attention) efficiently.

### PISA设计（围绕PIM Node的系统/应用）

异构Node系统，支持动态类型算子，Node包含PIM（PISA Acc）和XPU。

PIM控制器

控制器目标：通用可编程要求细粒度，但细粒度指令动态生成和传输的延迟高。

动态块稀疏算法有复杂的控制决策（标量算法），控制器需要**引入可编程通用Core**来完成。

但通用Core生成指令的时间远远快于PIM的执行时间，Core等待PIM完成（同步）会浪费Core去处理其他任务的性能，因此Core生成PIM指令和PIM执行需要异步。

Core能访问Mem die的HBM内存，HBM作为PIM-CCU和RV-Core组成pipeline的中介Mem。

PIM-CCU独占Logic die上的Buffer（SRAM），设置Buffer来加快CCU访存。

动态稀疏Attn的pipeline是BCE（PIM-CCU）-TopK（PIM-RV）-SpAttn（PIM-CCU），设置Sync指令保持PIM和Core异步执行时的数据依赖。

异构系统执行

Host端：

编译：Attn kernel编译成RV-Core的微程序（PIM指令和RV指令），打包控制逻辑。

初始化：推理前，host通过DMA，将RV微程序传到PIM控制器的SPM。

decoding推理执行：host将query vec和KV Cache地址等参数，写入PIM控制器的MemMap Regs，然后启动。

完成后：PIM控制器发送中断给Host。

PIM Node端：

host启动后，PIM自动执行，RV-Core执行微程序。

BCE：Core将KV Cache地址等信息填充PIM.BCE指令，每个指令是一个block并派发给一个PIM-CCU，block分数结果保存（ST）到HBM的指定区域。

Top-K：Core从HBM读取每个block的分数搭配SPM，作Top-K选择，输出最相关的Block信息。

Block SpAttn：Core读取最相关的Block信息，填充PIM.GEMM和PIM.SFMX指令参数，发给Cmd FIFO，等待派发和PIM-CCU执行。

> **[图片提取文字 (image.png)]:**
> In contrast, the fuse execution mode enables shared resource utilization across the temporal dimension. In the intra-task temporal fuse execution mode illustrated in Fig. 2(b), both Task 1 and Task 2 are unrolled twice to fill temporal idle tiles across different clock cycles like DySER [20] does. Although the II=4, the total iterations reduce to 1000/2=500. Consequently, both tasks require only  $500\times4=2000$  cycles in total. Nevertheless, spatial partitioning in Fig. 2(a) remains the dominant approach for multitasking on CGRAs, as many computations such as recursive filter and Fibonacci sequences cannot be unrolled due to mandatory data dependencies between loop iterations.
> 
> Considering that embedded scenarios often involve multiple mutually independent tasks requiring acceleration (e.g., a cleaning robot simultaneously accelerating loops in SLAM and navigation), this work proposes the inter-task temporal fuse execution mode in Fig. 2(c). Operations A and B of task 1 can share the same tiles with operations E and F of task 2 in adjacent clock cycles. For all iterations after the first, tiles achieve 100% utilization in temporal dimension, thereby achieving higher throughput (II=2). Here, Task 1 and Task 2 also only require total 1000×2=2000 cycles to finish. Critically, the absence of inter-task dependencies allows more flexible scheduling when filling temporal idle tiles, enhancing adaptability compared to intra-task fusion.

> We extend a widely cited Python-based cycle-accurate simulator [49] to model the behavior of PartitionBase, FuseBase, and FexMo. The simulator takes three inputs including the target multi-task cases, target CGRA of different sizes, and multi-tasks' cache miss rates. Its outputs consist of application throughput, average CGRA tile utilization across spatial and temporal dimensions, and the number of clock-gated cycles for each CGRA tile under the FexMo's centralized control scheme.
> 
> To ensure a realistic simulation of cache miss behavior, we input different multi-task cases into the Gem5 [2] simulator and use the L1 data cache miss rate as the cache miss rate for these multi-task scenarios. Note that the size of the L1 data cache is set to match the scratchpad data memory size of the CGRA architecture, maintaining comparability between the two systems.
> 
> We leverage an open-source parameterized toolchain [50] to generate Verilog implementations for three CGRA configurations: 4×4, 5×5, and 6×6 array sizes with scratchpad data memory of 16 KB, 20 KB, and 24 KB, respectively. Concurrently, we implement FexMo's centralized control and checkpoint mechanisms in Verilog, consolidating both components into a unified design file. Finally, we synthesize, place, and route the integrated design using the open-source ASAP7 PDK [17] through Synopsys Design Compiler and Cadence Innovus.
