# 背景

标量计算性能落后于向量计算的性能，标量计算成为瓶颈；

Flynn瓶颈：**按序发射的流水线**每周期最多通过1个指令，单指令流处理器仅设置单条pipeline而性能受限；

> **[图片提取文字 (image.png)]:**
> 这篇论文于1982年发表。那时的超级计算机<sup>\*</sup>已经可以很好地 处理**单指令流多数据流**(SIMD, single instruction, multiple data)的运算了,但是**单指令流单数据流<sup>†</sup> (SISD, single** instruction, single data) 性能却迟迟没有进步。对于那些标 量运算和向量运算性能不平衡的处理器,我们只能称之为"一 代"向量处理器,比如CDC CYBER 200系列的向量计算机<sup>\*</sup>。 若是想投入商用,必须得升级一下它的底层的处理器STAR-100, 使它也能高性能地处理标量运算, 只有这样, 它才能升 级为"二代"向量处理器<sup>+</sup>。
> 
> 标量计算和向量计算需要达到一个平衡,这在1981年就已经被J. Worlton提出了。用Amanda定律上来看待这个问题的话,那就是:向量计算已经利用并行性加速了很多了,目前处理器大部分的运行都耗在了标量计算上,因此计算机的总体性能将受制于标量计算的性能。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image.png)

> **[图片提取文字 (image.png)]:**
> 制约标量计算性能的一个重要因素就是 **Flynn瓶颈**(Flynn bottleneck)——任何一种按序发射的策略中,指令通过流水线的速度具有一个上限,那就是每个时钟周期<sup>†</sup>最多通过一条指令。
> 
> 这篇论文提出的**访存/执行解耦体系结构**(Decoupled Access/Execute Computer Architectures),能够显著改善 标量计算\*的性能。它使用了两个分开的指令流,通过一个硬 件实现的队列进行通信,合作完成一个标量计算。使用两个指 令流就可以无视 Flynn 瓶颈,因为指令流的带宽变成了原来的 两倍。指令的译码/发射逻辑非常简单,并不比当前最先进的 CRAY-1 处理器核 CYBER 205 处理器更复杂。而且,指令流之 间可以利用相关的硬件进行**滑行**(slip),从而进行动态调
> 
> 度,减小了对指令**重排列**(schedule)的需求。

# 处理器结构

> **[图片提取文字 (image.png)]:**
> 所谓解耦的体系结构,就是把整个体系结构划分为两个主要的功能单元:**访问处理器** (access processor, A-processor) 和**执行处理器** (execution processor, X-processor) 。在下文中我用A处理器和X处理器来称呼他们。
> 
> 每个处理器分别拥有自己的指令流,下称A指令流和X指令流。
> 
> 每个处理器还分别拥有自己的寄存器堆:
> 
>  $A_0, A_1, \ldots, A_{n-1}$  和  $X_0, X_1, \ldots, X_{m-1}$  。其中,n和m可以不相等,A和X的字长也可以不同。
> 
> A处理器和X处理器有相似的流图结构,但是功能有所不同。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%202.png)

> **[图片提取文字 (image.png)]:**
> ![](_page_0_Figure_0.jpeg)
> 
> Fig. 1. Block diagram of a decoupled architecture.
![image.png](Cohort%20Software-Oriented%20Acceleration%20for%20Heteroge/image%2087.png)

A处理器计算内存地址、访问内存（MMU映射、Cache访问），X处理器执行内存无关的计算；

A从内存加载的数和X存储内存的数分别通过队列**XLQ**和**XSQ**传递，存储地址在**SAQ**中；

A和X的寄存器数据传递通过复制单元完成，分别需要A和X的相关指令；

> **[图片提取文字 (image.png)]:**
> ## A处理器负责计算内存地址和读写内存:
> 
> - 对于load指令,A处理器从内存中载入数据。这个数据可能继续用于A处理器,也可能把它传送给X处理器。我们维护一个**先进先出**(FIFO)的队列,称为**执行载入队列**(X Load Queue, XLQ)。A处理器可以把从内存中取出的数据放入XLQ的队尾,然后X处理器从XLQ的队头中取出操作数进行计算。类似的,如果X处理器计算出的结果需要传送给A处理器,则需要用到另一个队列,**执行存储队列**(X-Store Queue, XSQ)。
> - 对于store指令,可能是将A处理器中的一个数据存入内 存,也可能是将X处理器的计算结果存入内存。第二种情况 就要用到XSQ。X处理器将计算结果存入XSQ队尾,然后A 处理器从XSQ队头取出待存数据,存入指定内存地址。在X 处理器的数据到达XSQ之前,A处理器可能已经计算好了内 存地址,这时它就会把计算好的内存地址存放在一个**存储地** 址队列(Store Address Queue, SAQ)中。当XSQ的数据 可用后,SAQ的地址自动和它进行配对,然后写入内存。 这种自动配对是简单的,因为数据一旦进入XSQ,它的唯一 去向就是内存,因此只要XSQ和SAQ的队头同时拥有有效。 数据,那么它们就可以配对成功,完成一次 store 操作。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%203.png)

> **[图片提取文字 (image.png)]:**
> X处理器则是负责那些与内存读写无关的运算。
> 
> 如果我们需要数据在A处理器和X处理器之间传递,那么可以 使用一个**复制单元**(copy unit)。比如说现在需要把数据  $A_i$ 传送给  $X_i$  ,那么两个处理器都会被放入一条指令。A处理器 的指令将读取  $A_i$  并放在复制单元 $^{\dagger}$ 的一个队列中,X处理器则 读出这一数据并放在  $X_i$  中。如果要把数据  $X_i$  传给  $A_i$  那也 是类似的。当队列满时,所有放置数据的请求将被阻塞;当队 列空时,所有取出数据的请求将被阻塞。

**跳转指令的实现**

> 
> $$q = 0.0$$
> Do 1 = 1, 400
> $$x(k) = q + y(k)*(r*z(k+10) + t*z(k+11))$$
> (a)
> 
> ```
> A_4 \leftarrow -400
>                                      • negative loop count
>         A_2 \leftarrow 0
>                                      • initialize index (k)
>         A_3 \leftarrow 1
>

>

>

> 
>         X_{\delta} \leftarrow t
>                                             into registers
> loop: X_3 \leftarrow z + 10, A_2 \bullet load z(k + 10)
>         X_7 \leftarrow z + 11, A_2 \qquad \bullet \text{ load } z(k+11)
>         X_4 \leftarrow X_2 * f X_3
>                                     • r*z(k + 10) - floating multiply
>         X_3 \leftarrow X_5 * f X_7 • t * z(k+11)
>         X_7 \leftarrow y, A_2
>                        • load y(k)
>         X_6 \leftarrow X_3 + fX_4 • r*z(k+10) + t*z(k+11)
>                          • increment loop count
>         A_4 \leftarrow A_4 + 1

>

> 
> 因为正常的体系结构只有一个处理器核一个指令流,所以当 x(k)的值计算出来并且写入对应内存位置<sup>\*</sup>后,就可以结束一轮的循环。

> ## 解耦体系结构下,程序会被编译成这样:
> 
> ```
> Execute
>                 Access
>           A_4 \leftarrow -400
>           A_2 \leftarrow 0
>           A_3 \leftarrow 1
>                                                     X_2 \leftarrow XLQ
>           XLQ \leftarrow r
>                                                     X_5 \leftarrow XLQ
>           XLQ \leftarrow t
> loopa: XLQ \leftarrow z + 10, A_2 loopx: X_4 \leftarrow X_2 * f XLQ
>           XLQ \leftarrow z + 11, A_2
>                                          X_3 \leftarrow X_5 * f X L Q
>                                                     X_6 \leftarrow X_3 + fX_4
>           XLQ \leftarrow y, A_2
>                                                     XSQ \leftarrow XLQ*fX_6
>           A_4 \leftarrow A_4 + 1
>                                                     BFQ loopx • remove outcome from XBQ
>           X, A_2 \leftarrow XSQ
>           A_0 \leftarrow A_4
>           A_2 \leftarrow A_2 + A_3
>           JAM loopa • place outcome in XBQ
> ```
> 
> 我们可以看到,左侧的指令在A处理器上执行,循环体内的主要的行为是计算y(k)和z(k)的地址、从y(k)和z(k)中取数据放到XLQ队尾、计算x(k)的地址、把XSQ队头的数据写入x(k)。
> 
> 右侧的指令在X处理器上执行,循环体内的行为就是从XLQ队头读入y(k)和z(k)的值,以此计算x(k),将计算的结果写入BFQ队尾。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%206.png)

访存、计算解耦的处理器**控制流唯一**，即A或X计算跳转逻辑而**另一个跟随**，**访存和计算逻辑分散但控制流一致或同步**；

> **[图片提取文字 (image.png)]:**
> 巧妙的是,尽管A处理器和X处理器在合作完成一段代码,但 是对于跳转指令<sup>†</sup>,并没有要求两个处理器在同一时刻执行。 在这个例子中,A处理器的跳转条件是  $A_0 < 0$  。只要A处理 器满足这个条件,就可以进行跳转,而不用关心X处理器到底 执行到哪一步了。当A处理器决定了是否跳转,会把这个决定 放在执行分支队列(X-Branch Queue, XBQ)中。X处理器执 行指令BFQ (branch from queue) , 从XBQ中获知A处理 器的决定,并且做出与A处理器相同的决定(跳转或不跳 转),从而达到同步的效果。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%207.png)

> **[图片提取文字 (image.png)]:**
> 因此,在解耦体系解耦中,判断是否跳转只会由其中一个处理 器决定,而另外一个处理器只需执行一条 BFQ 指令,读取 ABQ或者XBQ,然后做出同样的跳转决定。通常,我们希望 尽可能在A外理器上决定跳转是否执行。这样A外理器就可以 不用等待X处理器的结果,从而可以直接执行后续指令。而 目,X外理器更愿意执行BFQ指令,因为执行BFQ指令本质上 是执行了一条直接跳转指令(或者 nop 指令<sup>†</sup>),不需要进入 执行阶段就可以确定跳转的目标地址,消除了条件分支指令\* 带来的取指的延迟,使后续指令可以尽早取指。事实上,很多 条件跳转指令是都是由循环遍历数组\*带来的,此时,数组的 下标既用于寻址(这部分是A处理器的工作),又用于判断转 移条件,因此把判断是否转移的工作放在A处理器上也是很自 然的事情。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%208.png)

**数据冒险**

分离结构中，**store指令在获得操作数前就能发射**，无法阻塞后续存在数据冒险的**load指令**，因此但指令流的计分板SB机制无法处理**RAW冒险，**需要阻塞存在RAW的load之指令发射，或采用数据转发解决冒险；

store指令的源操作数**可能是A寄存器，可能是XSQ**，先发射的store指令可能等待XSQ，后发射的store指令直接能拿到A寄存器的数据，存在**WAW冒险**，需要阻塞存在WAW的后续store指令的发射或执行；

> **[图片提取文字 (image.png)]:**
> 我们之前已经看到了,在解耦体系结构中,一条 store 指令,它的目标地址可以在待存数据可用之前就早早地计算出来,此时这个地址会放在 SAQ中。当待存数据可用后,会进入XSQ,然后与 SAQ的地址配对并送入内存。因此,store 指令可以不用等待操作数可用就直接**发射**(issue),减少了流水线的阻塞,改进了性能。而我们熟悉的单指令流的**计分板**(scoreboard)算法,必须在 store 指令的操作数可用后才能发射,在此之前会一直阻塞。
> 
> 但是,这样就出现了一个问题,load指令可能需要从一个地址取数,而在此之前有一个尚未完成的store指令,它将要这个地址存数。这样就造成了一个**写后读**(read after write, RAW)冲突。
> 
> 解决这个问题的方法是,我们可以将每一条新发射的 load 指令的内存地址与 SAQ 中的所有地址进行比对。如果找到相同的内存地址,就把这条 load 指令(以及之后所有的 load 指令)阻塞,直到 SAQ 中所有地址相同的 store 操作全部完成。这种方式对 SAQ 的大小提出了要求,太小的 SAQ 无法容纳所有的 store 地址,从而遗漏一些冲突,太大的 SAQ 会减小比对的速度,增加硬件开销。一般来说,建议 SAQ 存放 8-16 个地址。或者用一种更复杂的改进方式,使用类似旁路的技术把store 指令的待存数据直接送给 load 指令<sup>†</sup>。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%209.png)

> **[图片提取文字 (image.png)]:**
> 还有另一个问题,如果两个store指令的待存数据一个来自于 A处理器,另一个来自于XSQ,并且它们将要送到同一个目的 地址,这就会造成**写后写** (write after write, WAW) 冲突。 解决这种冲突的方法是,强迫所有的 store 指令按序离开 A 处 理器。比如,先发射的 store 指令还在等待 XSQ 中的数据,而 后发射的store指令已经可以直接使用A处理器中的操作数 了,这时就要把后发射的这条指令缓存起来,直到先发射的那 条指令取得XSQ的地址。这种策略可以用SAQ机制实现。另 一种方式是将 store 和 load 指令同等对待(像之前处理 RAW 冲突一样),将每一条新发射的 store 指令的内存地址与 SAQ 中的所有地址进行比对。如果找到相同的内存地址,就把这条 store 指令阻塞,这种方式的好处是,如果没有地址冲突,后 发射的 store 指令<sup>\*</sup>就可以不用等待先发射的 store 指令。

XLQ和XSQ队列的实现

> **[图片提取文字 (image.png)]:**
> 在我们的解耦体系结构中,程序员可以像看待寄存器一样看待 队列。
> 
> 我们为队头和队尾分配了寄存器编号 $^{+}$ ,程序员可以像访问寄存器一样访问队列中的操作数,不再需要为它设计特别的指令或者寻址模式。在X处理器指令集 $^{+}$ 中,当 $X_{n-1}$ 作为源操作数 $^{+}$ 时,代表XLQ的队头;作为目的操作数时,表示XSQ的队尾。比如,在一个8寄存器的X处理器中,指令XSQ  $\leftarrow$  XLQ +  $X_{2}$  被表示成 $X_{7}$   $\leftarrow$   $X_{7}$  +  $X_{2}$  。
> 
> A处理器的情况略有不同。当我们想把数据从一个内存地址 $^{\dagger}$ 加载到XLQ队尾时,会使用这条指令: $XLQ \leftarrow address$ 。它的操作码直接暗示了load操作的目的地是XLQ,因此也不需要指定目的寄存器了。类似的,store操作对应的指令 $address \leftarrow XSQ$ 也不需要指定寄存器。
> 
> 有一种更加普遍的策略可以让处理器可以访问队头的前两个元素,以此来处理双操作数的指令(如 add 和 mul),此时,编号为  $X_{n-1}$  和  $X_{n-2}$  的两个寄存器就指代 XLQ 的前两个元素。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%2011.png)

> **[图片提取文字 (image.png)]:**
> 这种策略可以再变化一下,现在它只为队列分配一个寄存器编号,允许形如  $X_1 \leftarrow X_{n-1} + X_{n-1}$  的指令来访问 XLQ 队头的前两个值。对于不满足交换律 的操作,例如减法,也可以实现约定一个出队顺序。这种策略节约了一个寄存器编号,但是增加了控制逻辑的复杂性(比如,当队列为空或者队列只有1个操作数时,要阻塞指令发射)。
> 
> 用寄存器来指示队头和队尾在硬件实现上是不难的,可以用环 来实现,就像**重排序缓存**\* (re-order buffer) 一样。其中, 队头计数器 (head counter) 和队尾计数器 (tail counter) 指向队列中头部和尾部的元素。检测队列是否为空或者是否为 满也很容易。典型的流水线处理器<sup>+</sup>中(如CRAY-1)为每个寄 存器附加了一个触发器<sup>\*</sup>(flip-flop),当触发器置位时,表 示寄存器正在讲行写入,之后将要对它进行读写的任何指令都 禁止发射,直到它完成写入,相应的触发器复位。在解耦体系 结构中,队头和队尾也分别附加了触发器。如果XLQ为空,相 应的触发器就要置位,任何需要从XLQ中读操作数的指令都禁 止发射。如果XSQ为满,相应的触发器也要置位,任何需要 将结果写入XSQ的指令都禁止发射。因为在实现中,XLQ和 XSQ都是用寄存器编号  $X_{n-1}$  表示的,所以寄存器  $X_{n-1}$  会 对应到两个触发器,分别记录XLQ和XSQ的状态。

队列实现延迟**不会增加指令执行延迟**

> **[图片提取文字 (image.png)]:**
> 下面我们稍微讨论一下队列机制的耗时。
> 
> 在CRAY-1处理器中,一旦指令被锁存在**指令发射寄存器** (current instruction parcel register, CIP) 中,它的操作数对应的寄存器编号就会被一起锁存。实际上,CIP分布在处理器的各个位置,大概和tomasulo算法<sup>†</sup>中的**保留站<sup>†</sup>** (reserve station) 差不多,在每个功能单元的入口处都有一些CIP。当一条CIP中的指令被发射时,它会从相应的寄存器中读取操作数。发射完毕后,CIP的这个位置继续装载下一条指令。
> 
> XLQ也可以用同样的方法来实现。只不过操作数所在的位置不再由指令给出,而是由队头计数器给出。指令发射时,CIP会从读取XLQ的队头读取操作数,然后队头计数器的值自增。因为在指令发射之前,队头计数器就可以开始计算自增,所以自增花费的时间不会比从XLQ载入数据要长。从内存中读取数据放在XLQ队尾,也是类似的情况。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%2013.png)

> **[图片提取文字 (image.png)]:**
> 为了能让浮点单元<sup>\*</sup>既能从XLQ读数,又能从X寄存器读数,这里我们需要用到**多路选择器** (multiplexer)。多路选择器本身是会增加执行时间的,处理器中本身就有很多多路选择器,所以这个多路选择器不会增加耗时。
> 
> 总结一下,队列机制<sup>\*</sup>和普通的寄存器堆相比,因为队列的地址也是用寄存器编号来表示,所以分析操作数地址的耗时不会增加;从队列中读操作数和从寄存器堆中读操作数的耗时相近;多路选择器也不会增加耗时。

**中断interrupt来自外部（IO、timer、syscall），暂停A和X处理器**的指令发射，完成当前指令后保存指令计数器、寄存器和队列状态后中断；

**异常trap来自内部（内存缺页、计算溢出）**，内存缺页的处理只涉及A处理器，因此性能开销更低；

> **[图片提取文字 (image.png)]:**
> 我们认为,**中断**(interrupt)通常由外部引发,如一次I/O服务请求。而**异常**(trap)则是处理器内部引发,如浮点溢出。精确中断<sup>†</sup>要求当处理器遭遇中断或异常时,之前的指令正常执行,后续的指令不改变程序可见状态。
> 
> 我们的解耦处理器在处理中断时,首先暂停指令发射。然后令 在产生中断的指令之前的指令正常完成执行,然后用硬件的方 式来保存X处理器和A处理器的程序计数器<sup>\*</sup>(program counter, PC) , 用硬件或软件的方式(或二者兼用)保存寄 存器<sup>†</sup>和队列的状态。队列的数据比常规处理器中的寄存器数 据要多,不过解耦体系结构的通用寄存器要少一些,所以解耦
> 
> 体系结构并不一定需要更多的空间来保存状态。

> CRAY-1以及我们讨论的解耦处理器并不提供精确异常。事实 上,大部分异常都来自于虚拟内存\*技术中的缺页错误。而在 解耦体系结构中,缺页错误可以按照类似中断的方式处理。对 于A处理器,只需要照常完成异常之前的指令,然后等待换页 完成后新的数据到来,这和在X处理器中发生中断的情况没有 什么区别,而X指令本身也不会访问内存,只要静候数据从A 处理器放入 XLQ 即可。因此,解耦体系结构可以在更少的性能 损失下支持虚拟内存技术。

**interleave**方法编译成**单指令流**，处理器以**Flip**方法取指、译码后执行**双指令流**

> **[图片提取文字 (image.png)]:**
> 我们之前一直讨论的是双指令流。但是双指令流有一些缺点。第一,它会加重程序员或者编译器<sup>†</sup>编写者的负担,第二,它需要双份的指令缓存和译码/发射单元<sup>†</sup>,加大了硬件开销。
> 
> 我们使用**交织**(interleave)的方式让编译器生成单指令流,但处理器仍然能够按照双指令流的方式去处理这些指令。假设 $a_1, a_2, \ldots, a_n$  是**A程序**(A-program)的指令序列, $x_1, x_2, \ldots, x_m$  是**X程序**(X-program)的指令序列,交织就是让这两个指令序列合并成一个,并且满足:
> 
> - (1) 如果在A指令序列中  $a_i$  先于  $a_j$  ,那么在交织的指令序列中也要满足。
> - (2) 如果在X指令序列中  $x_i$  先于  $x_j$  ,那么在交织的指令序列中也要满足。
> - (3) 如果  $a_k$  和  $x_l$  式两个指令序列对应的一组跳转,那么在交织的指令流中,只需要放置一个单独的跳转指令,并且使得这条指令的位置满足(1)和(2)的要求。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%2017.png)

> **[图片提取文字 (image.png)]:**
> 在交织的情况下,每一条指令(跳转指令除外)都保留了一位 数据来表示它本身属于的指令流(A或者X)。当取指和译码<sup>\*</sup> 完成后,这一位数据就指示它前往相应的处理器。如果我们用 一个队列来存放近期准备发射的指令,那么两个处理器就可以 各自检查队列,跳过那些不属于自己的指令,找到属于自己的 指令然后执行,达到一种指令调度的效果,我们可以形象地称 之为**滑行**(flip)。
> 
> 这种机制的好处是,体系结构只需要一个程序计数器,而且不再需要 BFQ指令(因为不再需要成对出现的跳转指令)。 BFQ 指令被消除后,X处理器的执行时间就会缩减,总体性能也会上升。因为我们仍然有能力在一个周期内同时发射一条 A 指令和 X 指令,所以也无需担心 Flynn 瓶颈。

死锁：**proper的interleave**能保证一定程度的**指令“序”**，能**预防死锁**；

> **[图片提取文字 (image.png)]:**
> 在我们的解耦体系结构中,如果一条指令从空队列中取数,或者向满队列中存数,就会引起阻塞。当两个指令流同时因上述原因阻塞,就会发生**死锁**<sup>†</sup> (deadlock)。
> 
> ![](_page_0_Figure_1.jpeg)
> 
> Fig. 5. A deadlock situation in a decoupled architecture.
> 
> 上图中就是死锁的一个例子。 BFQ L1 等待 JAM L2 的执行结果,  $X_3 \leftarrow XLQ$  等待  $XLQ \leftarrow A_3, disp$  的执行结果。因此两边的指令都被阻塞,不能继续执行,产生了死锁。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%2021.png)

> **[图片提取文字 (image.png)]:**
> 但是我们可以证明,在我们的解耦体系结构中,不会产生死 锁。原文中给出了死锁不会发生的充分条件:如果A指令流和 X指令流可以形成交织,那么它们就不会死锁。在第四节中, 我们已经描述了编译器将如何产生交织的代码,因此程序必然 不会产生死锁。
![image.png](%E8%AE%BF%E5%AD%98-%E8%AE%A1%E7%AE%97%E8%A7%A3%E8%80%A6%E7%9A%84%E5%A4%84%E7%90%86%E5%99%A8%E6%9E%B6%E6%9E%84/image%2022.png)

> **[图片提取文字 (image.png)]:**
> An interleaving of instructions (Section 4) is defined to be proper if the instruction causing SEND i immediately precedes the instruction causing RE-CEIVE i for all data or control transfers i. The interleaving shown in Figure 4 is proper.
> 
> THEOREM. If the A and X processor instruction streams can be properly interleaved, then deadlock cannot occur.
> 
> PROOF. Deadlock occurs when both instruction streams are blocked due to queues being empty or full. To be more specific, a SEND instruction can be blocked if its queue is full, or a RECEIVE instruction can be blocked if its queue is empty. One such deadlock situation is shown below.
> 
> blocked 
> $$\rightarrow$$
>  RECEIVE  $i$  RECEIVE  $j$   $\leftarrow$  blocked  $\vdots$   $\vdots$  SEND  $j$  SEND  $i$ 
> 
> Here, both streams are blocked with empty queues waiting to RECEIVE, while the matching SENDs occur later in the streams. Figure 5 is an example of the preceding situation. We see, however, that a proper interleaving of the two streams is impossible: if SEND i is placed ahead of RECEIVE i, as it must be, then because RECEIVE j precedes SEND i in the X-stream, it must also precede SEND j in any interleaving.

> **[图片提取文字 (image.png)]:**
> | blocked | $\rightarrow$ | $\frac{\text{A-stream}}{\text{RECEIVE}}$ i | $\frac{\text{X-stream}}{\text{SEND } j}$     | <b>←</b> | blocked |
> |---------|---------------|--------------------------------------------|----------------------------------------------|----------|---------|
> |         |               | •                                          | •                                            |          |         |
> |         |               | RECEIVE j                                  | SEND i                                       |          |         |
> | blocked | $\rightarrow$ | $\frac{\text{A-stream}}{\text{SEND } j}$   | $\frac{X\text{-stream}}{\text{RECEIVE}}$ $i$ | <b>←</b> | blocked |
> |         |               | :                                          | •                                            |          |         |
> |         |               | $\stackrel{\cdot}{\text{SEND}}\ i$         | $\stackrel{\cdot}{\text{RECEIVE}} j$         |          |         |
> | blocked | $\rightarrow$ | $\frac{\text{A-stream}}{\text{SEND } i}$   | $\frac{\text{X-stream}}{\text{SEND } j}$     | <b>←</b> | blocked |
> |         |               | •                                          | •                                            |          |         |
> |         |               | RECEIVE j                                  | RECEIVE i                                    |          |         |
> 
> For each of these three other cases, it can be seen that a proper interleaving is impossible. We have just examined all four of the possible deadlock situations and have shown that a proper interleaving is impossible in each case. Using the contrapositive completes the proof.

> Code compiled as in Section 4 automatically has this property, since it is compiled so that the static code sections are properly interleaved before being separated.
