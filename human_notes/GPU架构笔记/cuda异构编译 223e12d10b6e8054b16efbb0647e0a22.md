## **编译与汇编**

cuda源代码：

```cpp
#include <cuda.h>
#include <stdio.h>
__global__ void printHello()
{
    int index = threadIdx.x + blockIdx.x * blockDim.x; // 计算全局索引
    printf("hello world from GPU by thread:%d\n", index);
}
int main()
{
    dim3 grid_dim = {1, 1, 1};             // 设置线程网格
    dim3 block_dim = {4, 1, 1};            // 设置对应线程块大小
    printHello<<<grid_dim, block_dim>>>(); // 执行kernel
    cudaDeviceSynchronize(); // 如果没有这一行，无法执行打印过程
    return 0;
}
```

**至于这里为什么是sm_52，虽然服务器上的gpu是h800?**

```cpp
答：因为当使用nvcc编译cuda程序时，如果没有显式地指定-gencode或-arch参数，nvcc为了兼容性会默认使用较旧的架构，需要通过nvcc -arch=sm_90 my_program.cu -o my_program等命令格式显式指定架构。
这里还有一个虚拟架构（virtual architectures）和真实架构（real architectures）的概念区别需要理解一下。
虚拟架构：虚拟架构（如 compute_50、compute_90）定义了 PTX 代码的功能集（例如支持的指令集、计算能力），用于控制 CUDA 代码的前端编译（生成 PTX 中间代码）。
真实架构：真实架构（如 sm_50、sm_90）直接对应硬件（如 Maxwell、Hopper），用于将 PTX 代码编译为实际的 GPU 二进制代码（SASS）。
-arch用于指定虚拟架构，-code用于指定真实架构，一般用-gencode结合起来做多架构的组合操作
```

然后我们先介绍一下cuda工具链中的**fatbinary**

**Fatbinary 的核心功能**

跨架构兼容： 将不同计算能力（如 sm_52、sm_75）的 CUBIN 文件还有PTX中间代码合并成一个 .fatbin 文件。(fat: 合并后的文件大小会变大所以fat)

运行时选择： 当程序运行时，CUDA 驱动会根据当前 GPU 的架构从fatbinary中选择最匹配的版本，优先使用现成的cubin(如果架构完全匹配的话)，若无匹配cubin，则即时编译(JIT)PTX代码。

fatbinary对test.sm_52.cubin的操作有：

**嵌入 CUBIN 数据**

test.sm_52.cubin 的二进制内容被转换为十六进制数组（fatbinData），直接嵌入到 fatbinary 的代码段中。

这些数据就是 sm_52.cubin 的二进制表示。

**标记架构信息**

在 fatbinary 的元数据中，会记录 test.sm_52.cubin 的目标架构（如 sm_52），例如：

#define __CUDAFATBINSECTION ".nvFatBinSegment"

驱动通过该信息识别适用的 GPU 架构。

**生成 Fatbinary 容器**

通过 __fatBinC_Wrapper_t 结构体将 fatbinData 封装为标准的 Fatbinary 格式：

*值得注意的是：流程图右侧的关于device代码的编译流程，可能跟随着你指定的多个虚拟架构的版本重复多次，然后一同打包到fatbinary里面去。*

**关于cudafe++工具的介绍：**

cudafe1 是 NVIDIA CUDA 编译器工具链 (nvcc) 在编译过程中生成的关键中间文件（通常为 *.cudafe1.cpp 或 *.cudafe1.stub.c），它本质上是 CUDA 主机端（Host）代码的预处理和封装版本。 cudafe1 在编译流程中的作用：

```cpp
输入：用户编写的 .cu 文件（含 __global__ 和 Host 代码）。
处理：
cudafe++ 分离 Host/Device 代码，生成test.cudafe1.cpp：主机端桩代码。
cuda语法转化，将cuda特有语法（如 <<<grid, block>>> 核函数调用）转换为标准 C++ 代码（例如展开为 cudaLaunchKernel 等运行时 API 调用）
模板实例化处理，对涉及 GPU 代码的 C++ 模板进行特殊处理，确保它们在设备和主机端正确实例化。
```

**编译**：

主机编译器（如 g++）编译 test.cudafe1.cpp。

nvcc 后端处理 GPU 代码生成可执行文件。

将得到的test.cudafe1.cpp文件再经由C++ Compiler compile成.o/.obj文件(包含了host代码+fatbinary).

## **链接**

现在让我们聚焦链接过程，同样的，cuda程序的链接过程也分为主机代码链接和设备代码链接两部分。跟之前的编译和汇编的思想类似。

**nvlink环节**

nvlink 是 NVIDIA 提供的链接器 ，它主要处理 CUDA 的设备端代码。它将输入的文件（之前编译生成的以 .o 或 .obj 为后缀的目标文件 ）进行处理，生成一个.cubin文件（例如图中的a_dlink.cubin ,我在本地目录中生成的为a_dlink.sm_52.cubin ）

**fatbinary环节**

fatbinary工具会进一步处理.cubin文件，生成一个.fatbin.c文件具体的fatbin思路都是一样的，借助内联汇编把 CUDA 设备代码的二进制数据嵌入到宿主代码中，并且通过定义结构体和变量，使得宿主代码能够访问这些设备代码。

**与宿主代码整合然后是Host Linker环节**

![](https://pic2.zhimg.com/v2-fcc8f829f22a76368cf123eb38d3aee5_1440w.jpg)

官网的这张图更能体现这个异构链接的过程，Host Linker（宿主链接器 ld或者lld）会将设备端相关的目标文件与宿主端的其他目标文件（如果有）链接在一起，生成最终可执行的文件（executable ）或者库（library），这个可执行文件就可以在支持 CUDA 的系统上运行，实现 CUDA 程序的功能。 整个链接过程确保了设备端代码和宿主端代码能够正确协同工作，使 CUDA 程序能在 GPU 上高效执行计算任务。
