## sCROOGe Circuit-level Design and Optimization Framework for RISC-V Out-of-Order GPUs

- baseline方法是什么？
  - Baseline 是顺序执行的 in-order GPU（如 Vortex 六段流水与商用 GPU）：靠 TLP 上下文切换隐藏延迟，每 sub-core 每 cycle 最多调度一条 warp 指令，ILP 未利用；当 workload TLP 不足（众多通用负载如此）且增加并发 warp 会加剧 cache 争用时，流水线频繁 stall、资源利用率低。prior OoO 方案（LOOG 后端 OC 阶段 CUs+寄存器重命名、GhOST/SIMIL 前端 Issue 阶段依赖检查+队列等）在概念上重排指令以挖掘 ILP，但全部在软件仿真器（Accel-Sim、PTXPlus、SASS 等）+ 解析模型（GPUWattch/McPAT、AccelWattch）中评估，不建模电路级效应（关键路径/频率退化、pipeline timing 变异性、OoO 结构随 warp/thread 扩展时互连的非线性膨胀），IPC 被系统性高估（LOOG/GhOST/SIMIL 仿真报 23%/6.9%/31% IPC 增益，RTL 实测仅 4.18%/0.86%），面积/功耗被低估（GhOST 仿真 0.01%/0.67% vs RTL 6.5%/6.7%）。
  - baseline 全栈执行例子：OpenCL kernel 经 POCL/LLVM 编译为 RISC-V 二进制 → Vortex 调度器选 warp、Fetch 取指、Decode 译码、Issue 按 scoreboard 依赖 in-order 逐指令发射（每 warp 每 cycle 一条）→ 遇长延迟（访存未命中、寄存器依赖未就绪）时该 warp 停驻，靠切换其他 warp 的 TLP 隐藏 → TLP 不足时 stall → Execute/Commit 写回 RF。性能用 Accel-Sim 估 cycle（对 V100 实测 MAPE 11.55%、Deepbench 超 30%、GRU RNN 达 73%），功耗/面积用 GPUWattch/AccelWattch 估（基于过期 McPAT 外推）。算法/系统框架/编译框架/kernel 调度层：论文未明确说明（无新算法模型、无服务框架、无编译器改造——软件栈沿用 Vortex 的 POCL+LLVM）；硬件架构层：in-order 六段流水 + scoreboard + IBuffer，每 cycle 每 warp 单指令 issue。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法：sCROOGe 首次在可综合 RTL（Vortex 内）同时实现 frontend 与 backend 两种 OoO 重排，并用 ASIC 综合/PnR 给出精确 PPA，替代仿真-only 评估。(1) Backend 方案（OC 阶段）：CUs 作 Reservation Stations + RAT 寄存器重命名消除 WAR/WAW + RRS 轻量放行 CU，乱序派遣 ready 指令进 Execute，写回经 broadcast+RRS 中间缓冲——对应 baseline 顺序 issue 被长依赖链串行阻塞、TLP 不足即 stall 的缺陷（sched stall -61%，通用负载最高 27.3% 加速、ML 最高 53%）；RRS 对应 LOOG 仿真版 CU 长期占用导致面积评估失真的缺陷（RRS entry 面积仅为 CU 的 4% 左右）。(2) Frontend 方案（Issue 阶段）：IsB+InFL+Dependence Checker+Issue Arbiter，让独立指令跳过依赖未决的旧指令（2% 增益）并移除 scoreboard——对应 baseline scoreboard 串行依赖阻塞与"per-warp oldest 指令把流水线卡在未决依赖上、新独立指令空等"的缺陷。(3) 电路级优化直接针对仿真未建模的开销：UUID 生成单元（递增编号+循环复用+MSB 越界检测）替代全相联 reorder buffer 的昂贵面积；OC broadcast pipelining（中间结果寄存器把互连从 3×N×R×T×datasize 降到 4×N×T×datasize）针对互连随 OoO 结构扩展的非线性膨胀；LSQ 内存重排经 RTL 实测（加速上限 <1.1%、面积/功耗 +8.7%/9.3%）后排除——对应仿真未量化"高复杂度低成本"权衡的缺陷。结果：iso-area 对比中 OoO SM 相对增加 warp 的 in-order SM 平均 IPC +14.4%，ADP/EDP 最优改善 12.4%/27.9%，frontend/backend 面积开销峰值仅 7.5%/28.6%，且 PnR 与 2nm 扩展验证趋势稳定。
  - 论文方法全栈执行例子：同一 OpenCL kernel → POCL/LLVM 编译 → sCROOGe 流水线：backend 方案下指令经 Issue 进入 OC——分配 CU + 分配 RRS entry（RRS ID 写入 RAT 的 rd 字段），源操作数按 RAT 查表从 RF 直读或等待结果 broadcast，每个 cycle 一个 ready CU 经 Dispatch arbiter 乱序派遣进 Execute（可越过仍在收集操作数/被依赖阻塞的更早指令），Execute 计算、Commit 后结果经 broadcast 路由回 OC 存入 RRS 中间缓冲，eop 信号触发 RAT 更新与 RF 写，随后 RRS 释放——依赖链内指令乱序完成，stall 大幅减少（总 stall -14.8%）；frontend 方案则在 IsB 内由 Dependence Checker 标记独立指令、Issue Arbiter 优先发射，InFL 跟踪写回。性能用 Verilator cycle-accurate RTL 仿真输出 per-kernel cycles/IPC（Fig.13/14/17），功耗/面积经 DC 综合 22nm（GF Memory Compiler SRAM 宏）+ PrimeTime VCD + Innovus PnR（400 MHz）+ N2 2nm（1.2 GHz）输出（Fig.19-24）。算法/系统框架/编译框架/kernel 调度层：论文未明确说明；硬件架构层：六段流水 + 两套可配置 OoO 扩展（UUID/IsB/InFL/DC/Arbiter 或 CU/RAT/RRS/broadcast）。
