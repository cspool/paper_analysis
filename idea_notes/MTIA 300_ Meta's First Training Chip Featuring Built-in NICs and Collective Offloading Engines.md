## MTIA 300: Meta's First Training Chip Featuring Built-in NICs and Collective Offloading Engines

- baseline方法是什么？
  - Baseline：通用 GPU（NVIDIA H100/H200）上的 DLRM 训练，及 Meta 前代推理芯片 MTIA-2i 的思路。DLRM 训练与 GenAI 不同：FLOPS 需求中等（单样本 ~3G FLOPs）但 HBM 容量/带宽与网络带宽需求大、collective 通信频繁——数据并行 AllReduce 同步梯度 + 模型并行 AllToAllv 交换特征 + 分布式 Shampoo 优化器 AllGather，导致加速器利用率低。GPU 基线痛点：(1) 通信路径低效——NIC 外置、数据经 PCIe 到 GPU（PCIe 开销 + 主机 CPU 参与 work submission/CQ 处理，1.2 TB/s IO 若由 host 管理会耗尽 host 核）；(2) collective 用 compute 引擎（SM）执行——归约占用流式多处理器、面积效率低（MTIA 300 的 ME 用 1/3 面积达到同等归约带宽），且高带宽 collective 流量与计算争用 GPU 内部资源（H100 计算+collective 并发时 SM 争用、明显退化）；(3) 网络拓扑限制——H100 8 加速器 scale-up 域（450 GB/s）、scale-out 50 GB/s，网络 bytes-to-FLOPS 比低。
  - Baseline 全栈执行例子（一次 H100 上的 DLRM 训练迭代，40 加速器、local batch 6144）：算法层：DLRM 前向——dense 特征过 MLP、sparse 特征查 embedding 表（TBE，99% 参数在稀疏侧）、dense interaction 层，反向算梯度；系统框架层：PyTorch + TorchInductor 编译，梯度经 NCCL 发起 AllReduce（入站 1.6 GB），sparse 侧 35 次 AllToAllv（1 KB-1 GB）；编译框架层：TorchDynamo/AOTAutograd 生成图、NCCL 作为独立通信后端（compute 与 collective 分图、主机驱动通信）；kernel调度层：collective 归约在 GPU SM 上执行（占 SM 与 GEMM 争用），数据经 PCIe 到外置 NIC 往返主机；硬件架构层：梯度经 HBM→L2→SM 归约→PCIe→NIC→网络，SM 争用导致计算/通信并发双退化。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：MTIA 300 三大硬件创新 + 软件栈协同，全栈解决"DLRM 通信密集导致低利用率"：
    1. **内置 NIC chiplet（对应解决 PCIe 开销与 host 瓶颈）**——12×800 Gbps RDMA NIC 封装进 2 个网络 chiplet（die-to-die + 112G SerDes），消除 PCIe 数据通路与 host 数据面参与；express doorbells（WR 即 doorbell 写、省 800 ns HBM ring-buffer 读）、去 QP caching（省面积）、简化包流水线（去掉不需要的 virtual switching/TC offload）、AXI steering tag（流量分流到独立 cache partition）。
    2. **collective offloading（16 ME，对应解决 SM 做归约的面积/性能浪费）**——专用 Message Engine 执行 SEND/RECV/WRITE/WAIT/SET/REDUCE 等 WQE，同吞吐仅 1/3 面积，把归约从 PE/SM 卸载；CPU-M 共享大 CQ 免多队列轮询、NIC interface 单 FIFO 分发到 12 NIC doorbell。
    3. **近内存计算（NMC，对应解决 collective 与计算争用互连/内存系统）**——ME 置于 HBM/cache/I/O 旁，NMC 128 B/cycle 归约、最高 2.8 TB/s（>2× IO），ME 在网格边缘避免跨网格 NoC 拥塞；NMC 就近 cache/HBM 执行 AllReduce/ReduceScatter 关键操作、不占 PE 网格。
    软件侧：HCCL 把 collective 与 compute 编进单一大图（semaphore 依赖、降低启动开销）、RDMA verbs 控制路径、ME 并行子图，实现计算通信重叠（重叠微基准双 ~100% 效率 vs H100 退化）；1:1 host:accelerator 支撑 CPU offload（Shampoo 特征分解，1:8 损失 7.8%）；关闭 FP8 量化通信 +4.4%；大 local batch 10240 +2%。
  - 论文方法全栈执行例子（同一次 DLRM 训练迭代，40 加速器，MTIA 300）：算法层：同 DLRM 前向/反向，关闭 FP8 量化通信（-4.4% 开销）、Shampoo 特征分解 offload 到 host CPU（1:1 host:加速器）；系统框架层：TorchRec + TorchInductor 单图编译（compute+collective 合一），工作包经 CPU-C 派发；编译框架层：TorchDynamo 捕获 + AOTAutograd 反向 + TorchInductor 融合/Triton 生成 kernel + ILP 图调度降峰值内存 + rematerialization；HCCL 把 AllReduce ring 翻译为 WQE（ReduceScatter+AllGather 两阶段、wqe_sync/fence 依赖，每 ME 并发多 subgraph）；kernel调度层：compute 子图到 72 PE（DPE GEMM、SFU SIMD/radix-sort、FI 索引 DMA），collective 子图到 16 ME（共享大 CQ、NIC interface 单 FIFO 分发 12 NIC express doorbell）；硬件架构层：梯度经 NoC（L-routing 均匀分布）→ 网络 chiplet RoCE NIC（112G SerDes）→ scale-up 800 GB/s 网络（16 节点域），NMC 在 HBM 旁 128 B/cycle 归约（Reduce/AllReduce/ReduceScatter），ME 在网格边缘不干扰 PE 计算；结果：通信性能超 H100 3.9×（40 卡、1.6 GB AllReduce/2.1 GB AllGather/35 次 AllToAllv），计算+通信并发双 ~100% 效率（H100 退化），Perf/TCO 1.42×（Table IV），LLM 推理（DeepSeek-R1、InferenceMax、8 卡）高并发下优于 H200；设计原则延续到 MTIA 400/450/500（GenAI 优化）。
