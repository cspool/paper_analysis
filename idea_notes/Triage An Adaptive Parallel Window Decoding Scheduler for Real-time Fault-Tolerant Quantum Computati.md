## Triage An Adaptive Parallel Window Decoding Scheduler for Real-time Fault-Tolerant Quantum Computation

- baseline方法是什么？
  - baseline 是 FTQC 经典控制层中两类现有解码协议：(1) 串行 sliding window [41]——把 syndrome 时间流切成固定大小窗口顺序解码，实时性要求 τdec<τgen，否则指数级 syndrome 积压；由 τdec∝N 得 N<τround/k，任何解码器硬件都存在可支撑 code distance 上界，不可扩展。(2) 并行窗口解码：time-parallel window [24]（时间维把 syndrome 流按奇偶窗口 checkerboard 并行，但逻辑层按整个 patch 粒度、不拆分 multi-qubit 操作）、spatial parallel decoding [27]（空间维按逻辑区域切分，但通常静态分配给专用解码器）；SWIPER [26]（投机窗口解码，SOTA，用投机机制消除窗口边界开销）。资源模型上 naive 方案要么 one-to-one（每逻辑比特一个专用解码器，代价高、利用率低、大规模不可行）、要么 one-for-all（恒定解码器数服务全机，每解码器延迟需求 O(1/N_lq) 不可满足）。baseline 的核心痛点是：缺乏把有限解码器池动态分配给持续 syndrome 流的资源感知调度框架——时/空窗口技术已知，但资源感知的时-空并行统一调度框架未被证明；T 门（非 Clifford）强制 Pauli frame 同步点前若因果锥未解码完就 stall，直接抬高 LER。
  - baseline 全栈执行例子（以 time-parallel window 处理一个含 T 门的 lattice surgery 程序为例）：算法层——surface code 每 d 轮提取一轮 syndrome，Pauli frame 经典跟踪 Clifford 误差；遇 T 门 teleportation 末端的 classically-controlled S-gate 必须在物理纠正 E_acc 后才能执行（同步点）。系统框架层——time-parallel 调度器把时间流切成块，偶数/奇数窗口并行，但每个多量子比特 lattice surgery 操作被当作一个整块，合并后的大 volume 交给单解码器串行处理；在 M 个解码器池下每个决策点只是"下一个整块给谁"，无法把合并区域切成可并行的小窗口，导致多量子比特操作成为并行度上限（高饱和层 floor）。编译框架层——Litinski 风格编译器生成 LLI 流（multi-patch measurement / patch rotation / idle）与 Timeline 注释，但调度器不感知 deadline/因果锥。kernel 调度层——论文未明确说明（FTQC 解码任务运行在经典 CPU/FPGA 的 MWPM/Union-Find 解码器上，无 GPU kernel 概念）。硬件架构层——pymatching/Sparse Blossom 等 MWPM 解码器在经典硬件执行，单解码器延迟按解码 volume 幂律增长（超线性复杂度），窗口缓冲越大延迟越高；swiper 的投机在资源稀缺时造成资源争用（speculative 开销），同步失败 → 插入 idle 层 → 总层数与 LER 上升。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 Triage 把解码器池调度形式化为带约束的动态实时调度问题，提出双模调度架构：以 slice（d×d patch × d rounds 的空间-时间基本单元）建无向约束图 G=(V,E)（边=互斥，最多 6 邻居：2 时间 + 4 空间），slice 状态机 UNGENERATED→PENDING→OCCUPIED→ASSIGNED→COMPLETED，每个 slice 带 deadline（到最近关键同步点的层数）与按需 BFS 计算的 causal cone（LRU 缓存）。①稳态模式：统一加权启发式 P(V)=w_u·(1/Deadline)+w_c·(1/(Degree+1))（w_u=w_c=0.5），每事件选 ≤M_available 个无冲突 slice 派发，保证平均吞吐；②紧急模式：Triage Trigger 在 deadline≤τ_emergency(4) 时触发，用 Algorithm 1"预测因果锥着色"——把 causal cone 的 PENDING slice 入优先级队列，离散事件模拟推时钟、每步按 degree 升序（MDF）贪心选独立集生成完整计划，O(n log n)；ScopeCap<100 防巨型因果锥的规划延迟尖峰（回退稳态），增量重规划（30% 扩幅 + ≥2 层间隔）防 thrashing，机会回填用 M−M_peak 预算跑非关键任务回收吞吐。对应解决 baseline 缺陷：slice 粒度把多量子比特 lattice surgery 的大 volume 切成可并行小窗口（解决 time-parallel 的 floor 与超线性复杂度惩罚）；紧急模式用最大并行度在 T 门同步点前预解码因果锥（解决同步失败 → idle stall → LER 上升）；ScopeCap+回填在慢/稀缺解码器区（τdec>τgen）仍维持性能（SWIPER 在该区因投机开销失效）；平均 LER 比时间并行 baseline 降 52.6%。
  - 全栈执行例子（Triage 处理同一含 T 门的 lattice surgery 程序）：算法层——同 surface code + Pauli frame，但同步失败判定改为"因果锥是否解码完"：每关键操作前检查，未解码完则插入 idle layer（所有 t≥ℓ 层右移）并保留 deadline 语义，idle 超 10 倍原层数判 backlog 失败终止。系统框架层——slice 约束图 + Timeline（每 unit 含 layer、坐标、6-bit 邻居 mask、deadline、causal cone 引用）驱动在线调度：稳态按 P(V) 加权启发式派发；T 门 deadline 临近 → Trigger 触发紧急模式，BFS 从关键 slice 反推 causal cone（只扩同层空间邻居 + t−1 时间前驱，COMPLETED 剪枝），Algorithm 1 预测着色生成 (t_sim, s) 计划表并缓存，在线只做轻量派发；空闲解码器机会回填非关键任务。编译框架层——Litinski 风格编译器生成 LLI 与 Timeline 注释，Triage 利用 deadline/causal cone 字段做资源感知调度（未改编译器本身）。kernel 调度层——论文未明确说明（解码任务在 pymatching 上执行，Triage 只做派发不改造解码 kernel）。硬件架构层——pymatching 延迟幂律模型（α=1.17）决定 slice 解码时长，随机抖动用校准 log-normal（σ_base=0.3447/α_d=0.0041/α_p=15.03）建模；蒙特卡洛 LER 用 Stim（d=9, p=3×10^-3, ≥10^5 runs）聚合；d=21 时每层约 21μs（超导）或 2.1-21ms（离子阱/中性原子）——减少 idle 层直接折算为墙钟时间节省。
