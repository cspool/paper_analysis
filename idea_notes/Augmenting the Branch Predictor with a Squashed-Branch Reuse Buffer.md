## Augmenting the Branch Predictor with a Squashed-Branch Reuse Buffer

- baseline方法是什么？
  - Baseline 是标准 64KB TAGE-SC-L 分支预测器 + immediate squash 的超标量处理器（12 级 fetch-to-execute、8-wide、ROB 512）：误预测立即 squash 其后全部指令，重取指时所有分支重新预测，CIDI（control-independent data-independent）分支可能再次误预测。已有 fetch 阶段 squashed-branch reuse 方案（SYRANT 的 ABL/SBL、Akkary 的 branch recycling、Galliher 的 Reuse Queue）全部依赖"按 PC/顺序比对两条路径"做对齐：SYRANT 为防嵌套分支迭代错位设置两条约束（重收敛搜索止于 resolved path 上第二个误预测分支实例、SBL 只搜到第二个实例），代价是 loop branch 误预测（under-iteration/over-iteration）后丧失复用机会，且 SBL 只保留最近一次 squash、首次 divergence 即终止复用、置信机制只有全局计数器简述；branch recycling 用 PC 关联查找 + 最近命中建立对齐，作者自认会错位并靠 gshare 置信度补偿；Galliher 的迭代计数器法只能处理一层循环且需要不定长比较窗口。baseline 痛点：缺乏"动态分支实例"的精确标识，squashed path 与 resolved path 之间任意插删分支/迭代后无法可靠对齐，导致要么放弃复用机会（SYRANT 约束）要么错误覆盖预测（错位）。
  - baseline 全栈执行例子（一次 br1 误预测后重取指）：算法层：无（纯 CPU 微架构优化，SPEC 2006/2017 int 与 GAPBS 程序本身，无算法改动）；系统框架层：无（无 serving/OS 参与，标准二进制直接执行）；编译框架层：LLVM -O3 标准编译，无循环信息传递（SYRANT/branch recycling 亦无编译器支持）；kernel 调度层：无（非 GPU/加速器负载，指令在超标量流水线内取指/派发/发射）；硬件架构层：fetch 预测 br2/br3 → br1 误预测 broadcast squash（R10K branch mask）→ 从 C 块重取指，br2/br3 被再次预测；SYRANT 靠 ABL/SBL 顺序比对检测重收敛后才用 SBL outcome 覆盖预测器，遇到 loop branch 误预测或首次 divergence 即失效。执行结果：CIDI 分支（如 br3）被 TAGE-SC-L 重复误预测，MPKI 居高、IPC 受损。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = 不变签名（invariant signatures）+ SBRB 覆盖预测 + 延迟 squash，全部改动在 fetch 单元。(1) 不变签名——对应"无动态实例标识导致对齐失败"缺陷：动态分支实例由层级循环迭代标识符 {header block, iteration count} 栈唯一确定，该标识符在 squashed/resolved 两条路径上不变（无论两路径间插删多少分支/迭代），按 key=fold32(PC)^sig 查 SBRB 即精确对齐，无需顺序比对、无 SYRANT 两条约束、容忍任意 control-flow divergence；(2) LFSR 紧凑实现——对应"标识符存储/哈希昂贵"缺陷：32-bit Galois LFSR 带数据输入，进循环 sig=LFSR_step(sig^fold32(PC))、续循环 sig=LFSR_step(sig^0)（旋转即迭代计数）、退出弹栈恢复，SS+LIT+SBRB+置信总开销 11KB；与 SBRB-literal-stack（SHA-256+CRC32 完整标识符哈希）性能几乎无差，证明 LFSR 代理有效；(3) SBRB 覆盖预测器——对应"MSSR/RI 只在 rename 阶段复用结果、不减 misprediction"缺陷与 SYRANT 对齐约束缺陷：fetch 阶段命中 SBRB 且置信高即用 squashed outcome 取代预测器输出，直接消除误预测；(4) BTB per-branch 3-bit 置信计数器——对应 SYRANT"单一全局置信计数器"缺陷：仅当 squashed outcome 可用且与默认预测不同才训练（对则 +1 错则 -1），SPEC 复杂 CIDD/CIDI 关系下防 slowdown（全局计数器 GAPBS 可行、SPEC 不行）；(5) 延迟 squash——对应"immediate squash 下 squashed-path 分支来不及执行完"缺陷：fetch~dispatch 立即清、rename 后指令继续执行至 resolved-path bundle 到 rename，阴影内完成分支 25%→45%，delayed squash 本身对 baseline 还 +1.55%（更多 CI load 提前发起 cache miss）；(6) 软硬协同落地——LLVM pass 生成 loop descriptor 入二进制 LIS 段、O/S 调度时装入 LIT、SS 随 64 个分支 checkpoint 与退休 SS 恢复。SBRB（fetch 消误预测）与 MSSR/RI（rename 减 penalty）目标互补，可组合。
  - 论文方法全栈执行例子（同一 br1 误预测后重取指）：算法层：无新算法；系统框架层：O/S 调度进程时从 PCB 把 LIS 顶部 loop descriptor 装入 CPU LIT-H/LIT-E（SMT 均分、线程暂停则扩分区）；编译框架层：LLVM 自研 pass 生成 loop descriptor 并按 header PC profile 频率排序注入 LIS 段；kernel 调度层：无；硬件架构层：取指时 LIT hit 驱动 SS 维护 sig → br1 误预测 → deferred squash（rename 后 squashed-path 分支继续执行完并写 SBRB）→ 从 checkpoint 恢复 SS → 重取指到 br3 时 key 命中 SBRB 且置信计数 >3 → 用 squashed outcome 覆盖 TAGE-SC-L，br3 不再误预测。结果：SPEC geomean +2.08%（最高 14.1% astar_rivers）、GAPBS +7.25%（最高 21.2% bfs-twitter）、全部 +4.43%、无负收益、11KB 存储；vs SYRANT 全部 geomean 1.77%；vs 192KB TAGE-SC-L 仅个别 benchmark 有效且预测延迟不可接受；immediate squash 下收益降至 2.22%。
