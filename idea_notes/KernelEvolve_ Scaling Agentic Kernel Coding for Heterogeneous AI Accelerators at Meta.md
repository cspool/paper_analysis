## KernelEvolve: Scaling Agentic Kernel Coding for Heterogeneous AI Accelerators at Meta

- baseline方法是什么？
  - Baseline 是生产现状的"手工 kernel 开发 + 异构部署"：(1) 对每个算子-平台组合由专家手写 kernel（每平台每实现 2-8 周），成熟算子用 vendor library（cuBLAS/cuDNN/FBGEMM/DeepGEMM），Triton 仅少量专家编写；(2) 编译端 baseline 是 torch.compile 与 PyTorch 原生算子；(3) 异构部署上，MTIA 缺原生算子时模型被迫 disaggregated serving（预处理上 CPU tier、NN 上加速器）。现有 AI coding 原型（KernelBench/AutoTriton/KernelLLM/TritonRL/GEAK/Kevin/TritorX/AlphaEvolve）的缺陷：窄优化范围（单子问题）、合成负载、单平台（多为 NVIDIA）、静态 prompt 的多 operator 框架（Debug/Improve 固定 prompt 无法随运行时上下文适配）、无大规模推理时搜索、无 checkpoint。
  - 全栈执行例子（conv1d 处理 production batch (2048,96,96,200) FP16，MTIA 部署）：算法层——标准 NCHW 卷积算子；系统框架层——因 MTIA 缺预处理算子，模型走 Serving Paradigm 2：Client→CPU tier→MTIA tier 三段，P99 从 61ms 增至 97ms，纯网络开销 δ=α-β-γ≈10-20ms 无任何计算收益；编译框架层——torch.compile 编译出 5 个 kernel（nchwToNhwcKernel×2 布局转换、sm90_xmma_fprop_implicit_gemm、nhwcToNchwKernel、triton_poi_fused_convolution_0），conv2d workaround 也需 4 个 kernel（unsqueeze/squeeze+channels_last 转换），中间张量反复往返 HBM；kernel调度层——kernel 不跨平台共享，MTIA 上 clamp.out/gather.out/sort.values_stable/all.all_out/_unique2/unique_consecutive 等算子缺失时 PyTorch 回退 CPU 执行（跨节点网络+序列化+级联失败）；硬件架构层——kernel 未利用 MTIA 的 SFU/LUT、跨 PE 通信、dual-core 异步流水。结果：开发周级、单体部署不可行、预处理算子成为二进制部署约束。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - KernelEvolve 把 kernel 优化形式化为图搜索 (F, π_sel, O, τ)，逐条对应 baseline 缺陷：(1) 单一 universal operator + 检索增强动态 prompt 合成（context memory sub-agent 分析运行时产物 + deep search sub-agent 按瓶颈检索知识库）对应解决"静态 prompt 多 operator 框架"——不再预设 Debug/Improve 视角，让 LLM 同时推理正确性/性能/架构权衡；(2) 持久分层知识库（constraints/guidance/hardware，≥100 文档）与 MTIA knowledge injection 对应解决"私有架构 MTIA 不在 LLM 训练语料"——教 LLM 用 libdevice API 映射 SFU LUT、cb_multiplier/use_dual_core 编译选项、cross-PE broadcast/reduction、pe_runtime_barrier、tl.copy 等；(3) metadata/object store 分离 + SQL CTE 图查询对应解决"无 checkpoint/无复用"——分布式并发探索、跨 session 从历史高分 kernel 起步、崩溃恢复；(4) 多粒度 profiling（TritonBench/Torch Profiler/NCU/Proton/MTIA Insight）+ Triton MPP 统一 + 确定性 evaluation code generator 对应解决"profiling 碎片化/结果不可机读"；(5) FaaS 远程评估解耦 CPU 生成与加速器评估对应解决"本地加速器稀缺导致生成-评估串行"；(6) 推理时大规模搜索（greedy/MCTS/进化，每 kernel 数百上千步）+ shape-aware dispatch（离线生成验证每平台专属变体，在线选最优、回退 vendor library）对应解决"窄优化范围/单平台"。
  - 全栈执行例子（同一 conv1d production batch）：算法层——相同卷积语义，kernel 采用 GEMM 式重排（权重打包 [Cout,Cin_g,Ksz]→[Cin_g*Ksz,Cout]，M=B×Lout、N=Cout/group、K=Cin_g×Ksz）；系统框架层——预处理与 NN 算子均在 MTIA 原生执行，消除 disaggregated 网络开销，恢复 Serving Paradigm 1 单体部署（P99 61ms）；编译框架层——Triton kernel 经多目标 MLIR lowering 在 NVIDIA/AMD/MTIA 生成 PTX/AMDGCN/RISC-V，emit_cxx/replay_cpp 支持 C++ 级调试；kernel调度层——生成 kernel 仅 2 个（pack_conv1d_weight_kernel + conv1d_gemm_kernel），消除布局转换与中间 HBM 往返（conv1d 5 kernel→2 kernel，H100 2.30×/1.62×，MTIA v3 6.54×/4.71×）；MapId 融合 bucketize/clamp/gather/where 为单 kernel 消除 CPU 回退（MTIA v2i 最高 4.07×）；MBDT 融合 bucketization 全流程（v2i 最高 9.25×）；硬件架构层——NVIDIA 用 Tensor Core tile 化+3D grid 分组并行+double-buffer+差异化 cache modifier（.ca/.cg）、AMD 用 Infinity Cache 感知 tiling、MTIA 用 SFU/LUT+跨 PE 通信+dual-core（RMSNorm 2D backward 17×）。结果：480 配置 100% 正确、KernelBench 250 题 100% pass、生产 1.25-17× speedup、开发时间从周级降到小时级、私有加速器 kernel 覆盖从部署 blocker 变为 enabler。
