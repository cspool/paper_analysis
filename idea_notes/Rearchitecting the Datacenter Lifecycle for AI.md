## Rearchitecting the Datacenter Lifecycle for AI

- baseline方法是什么？
  - Baseline 是面向通用 CPU 负载的传统数据中心生命周期管理（表 II）：①build——层级式电源分配（ATS→多台冗余 UPS→PDU→机架，每级功率上限，域内按 ⌊X/Y⌋ 部署 server，留下 stranded power 功率碎片）、air 冷却（chiller/CRAC+热/冷通道，PUE 1.1–1.3）、multi-tier Ethernet（leaf-spine、适度 oversubscription）；②IT provisioning——固定 4–6 年 server 生命周期、2–3 年一代的 CPU 发布节奏、逐代平滑替换；③operation——服务绑定固定硬件代际，新服务迁移到最新 server，legacy 应用留在旧机。三阶段被割裂（siloed）优化：build 选便宜保守的基础设施，refresh 按时钟而非效率信号决策，operation 均匀部署无代际感知。论文用 TCO 量化 baseline 的痛点：GPU 成本与功耗暴涨（P100 $9K→H100 $30K/GPU、DGX H100 整机 >$350K、10.2kW TDP vs 64 核 Emerald Rapids 385W）、GPU 每年出新代远超 CPU 2–3 年节奏、模型每年指数/线性膨胀（GNMT 200M→GPT-3 175B→Llama4 2T），固定 5 年刷新导致过早退役浪费 CapEx 或过晚退役牺牲效率，FLOPS 增长不线性转化为实际 LLM 性能（图 8：Llama3-70B 在旧 GPU 上 TTFT/TBT 退化远超 FLOPS 差距；图 9：Qwen3 sparse 模型在旧 GPU 上更耐退化；图 10：Mamba 架构在 V100 上只慢 3.6× vs Llama3 慢 7.7×）。
  - Baseline 全栈执行例子（模型推理算法-系统框架-编译框架-kernel调度-硬件架构；本文为数据中心运营/TCO 框架，编译框架与 kernel 层论文未明确说明）：一个 Llama3-70B 推理请求 → vLLM 把请求调度到 8×H100（TP8）执行 GEMM/attention kernel（系统框架层；kernel 层）→ 无论请求特性如何，集群按固定 5 年生命周期以最新 GPU 代际供给（IT provisioning 层）→ 新请求全部迁往新 server、旧 server 到点退役，功率按层级域限额部署、air 冷却按峰值热负荷保守供给、Ethernet 均匀组网（build 层）。结果：H100 集群 70B 模型 goodput 高但 A100 旧机闲置/退役过早，TCO 主要被 GPU CapEx 与能源 OpEx 吃掉（图 3：10MW 数据中心 GPU server 占 IT CapEx 大头、能源其次），且 2027 年前后一次 B200 级代际升级要么全量换新（巨额 CapEx）要么固守旧硬件（效率/容量损失）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：跨 build/IT provisioning/operation 三阶段的 TCO 驱动联合优化框架（AI Lifecycle Compass，开源），核心是把割裂的逐阶段策略改成统一 TCO 目标下的联合搜索：①build——用框架比较 flat vs hierarchical 电源（flat per-DC 供电最小化 stranded 但需更多冗余；图 6a flat 降 TCO 4.2%）、air/hybrid/liquid 冷却（75/25 hybrid 降 9%）、Ethernet/InfiniBand/NVLink/hierarchical 组网（NVLink intra-server+InfiniBand intra-rack+Ethernet inter-rack 的 hierarchical 降 6%）；②IT provisioning——把"固定 5 年刷新"换成 roofline 模型+SLO goodput 驱动、蒙特卡洛枚举（每代生命周期 0–10 年、可跳过、可多代共置）的刷新策略：新一代效率跃升时（V100→A100）提前退役换新，效率边际时（B100/B200）跳过并延长 H100/H200 寿命（图 13 最优时间线），模型增长加速则加速刷新；③operation——把均匀部署换成平滑模型迁移、量化、KV-cache 管理、prefill/decode disaggregation、heterogeneity-aware 调度（compute-bound prefill 放新 GPU、memory-bound decode 放旧 GPU）、infrastructure-aware 调度（利用功率/冷却余量）等 8 类软件优化（表 VIII），单策略降 TCO 12–39%、组合超 60%。三阶段联动：build 期投更大 powersharing 域→IT provisioning 刷新更灵活→operation 效率更高；跨阶段联合最高降 TCO 40%（图 15b：单阶段 20–30%、build+refresh 超 35%、全联合超 40%），且在需求冲击（-31%）、模型收缩（-43%）、硬件能力跳变（-38%）、价格冲击（-36%）四类结构性突变与 ±35–55% 趋势偏差（表 X）下仍稳健。
  - 论文方法全栈执行例子（编译框架与 kernel 层论文未明确说明）：同样是 Llama3-70B 推理请求 → vLLM 调度到 GPU 执行（系统框架+kernel 层不变）→ operation 层先做异构感知调度：请求 prefill 阶段路由到新代 H100/H200、decode 阶段可 disaggregate 到 A100（旧 GPU 承担 memory-bound 阶段，延长其有用寿命）→ IT provisioning 层按 roofline 模型+SLO（TTFT≤400ms、TBT≤100ms）评估：70B 在 A100 上 goodput/Watt 比 H100 低约 3×10^10 但不至于退役，1B/3B/8B 小模型 A100 甚至 per-dollar 优于 H100（8–23%），因此决策跳过 B100/B200、延长 H100/H200 到 6 年以上、把小模型负载保留在旧 GPU（图 13 平滑混合机队）→ build 层为支撑该混合机队部署 flat 电源（减少 fragmentation）+75/25 hybrid 冷却（高密度 rack 液冷）+hierarchical 组网（TP8 intra-server 走 NVLink、跨 rack 走 InfiniBand/Ethernet）→ 全生命周期蒙特卡洛（10,000 trials、8 个相关随机变量）验证该组合的 TCO 分布与 95% 置信区间 → 输出年度采购/退役计划。效果：把"固定刷新时钟+均匀部署"的割裂式管理，变成"roofline 性能模型+SLO goodput+蒙特卡洛 TCO 搜索+三阶段约束联动"的联合优化，避免过早退役的 CapEx 浪费与过晚退役的效率损失，最高 40% TCO 降低；硬件-软件-基础设施的协同设计建议（如未来加速器把高功耗 SM 用于 prefill、PIM 单元用于 decode）为下一轮 AI 数据中心架构提供方向。
