## Scalable Synthesis of Distributed LLM Workloads Through Symbolic Tensor Graphs

- baseline方法是什么？
  - Baseline 是三类获取分布式 LLM workload 的方式：(1) 真实系统执行 trace（ET）：在真实集群（数百~数千 GPU）上跑 PyTorch/JAX/NeMo 训练或推理，用 PyTorch profiler/Kineto/CUPTI/Chakra 采集带时序的执行图。全栈执行例子：用户写 PyTorch 分布式训练脚本 → 在 128×H100 集群启动 → kernel 执行并记录时间线 → 产出 Chakra ET（节点带 tensor 尺寸/时间/内存）→ 喂给 ASTRA-Sim 做性能分析。痛点：成本极高且仅超大规模云厂商可访问；隐私/安全限制无法共享；trace 与平台绑定（改拓扑/软件栈/并行策略需重采集）；与模型绑定（MoE/SSM 等新架构几个月内使旧 trace 过时）；单 epoch 每 GPU 就有数万算子（GPT-3 175B@32GPU 每 epoch 156,317 计算+30,978 通信），扩展分析困难。(2) ML 框架图捕获（如 PyTorch FX 编译期图）：仍需真实集群、并行度受集群规模限制、只支持框架已实现的模型与并行策略（FSDP 概念可行但 PyTorch 未支持时无法评估）。(3) 手工/模板化合成建模（Calculon、MADMAX、SimAI、vTrain）：用定制模板或解析一阶方程描述 workload，模板针对特定目标算子过度优化、扩展需深入改代码并重 profiling，解析本质难以捕捉 compute-communication 依赖等真实行为，无法系统建模 MoE 动态通信与 SSM。baseline 的模型推理算法-系统框架-编译框架-kernel调度-硬件架构全栈执行例子：算法层（Python 定义 transformer block）→ 系统框架层（PyTorch DDP/FSDP 运行时，后向 AllReduce 梯度同步 / FSDP 参数 AllGather）→ 编译框架层（eager/FX 直接执行，无并行化注解，无法系统 DSE）→ kernel 调度层（cuBLAS GeMM、FlashAttention、NCCL 集合通信在 GPU 上实际执行）→ 硬件架构层（H100 SXM5 + NVLink/Infiniband 真实机时消耗）；改任何一层配置都必须重跑真实集群重采集，假设配置（未存在框架/硬件）不可探索。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 STAGE：用符号张量图（STG）IR 把 workload 建模为独立一等公民工件，解耦"workload 生成"与"仿真/性能建模"（Design Principle 1）以及"workload 语义"与"系统实现"（Design Principle 2）。核心设计：(a) 符号张量表示——tensor 形状含符号维（B/S/H）与分布符号（dp/tp/sp/fsdp/ep 等）及 PartialSum 标记，算子用 einsum 表达（保留/归约/共享维度统一抽象），三种分布语义 Duplicated/Partition/PartialSum 可组合；(b) 模块模板 STG IR（MHA/GQA/MLA/FFN/MoE/SSM），按层组装整模型，用户只需模型名+并行度两个输入；(c) Collective Communication Matcher——producer/consumer 分布经 Pull（No-Comm/Gather/Reduce）+虚拟头节点+Push（Broadcast/Scatter）自动匹配出 AllReduce/AllGather/ReduceScatter/AllToAll 及其任意组合（含此前被忽略的模式）；(d) 图级分布（PP 切图插 send/recv）；(e) 符号→数值实例化，可选择性注入 PyTorch/Kineto 真实值。对应解决 baseline 缺陷：高成本/不可访问→CPU 上秒级~分钟级合成任意规模（128K GPU）trace（32K GPU 540B 模型 28 分钟），只需改参数不需集群；平台绑定→同一 workload 无改接入 AstraSim/SimAI/ScaleSim/Genie（<100 LoC 翻译层），系统抽象为可配置多维拓扑；模型绑定→符号表示覆盖 dense/MoE/SSM/混合架构并可扩展，任意并行组合（含框架中不存在的假设配置如 Fully-Sharded Tensor Parallel FSTP）可建模；模板过度优化→自动分布与通信匹配替代手工模板。
  - 论文方法的模型推理算法-系统框架-编译框架-kernel调度-硬件架构全栈执行例子：算法层（STG 模板描述 MHA/FFN/MoE 符号算子，如 einsum[bm,mn->bn]）→ 系统框架层（Workload Distributor 应用 DP/TP/SP/PP/EP/FSDP，通信匹配器按 producer-consumer 插入集合通信节点，如 x[B/dp,S,H@1/tp] 经 ReduceScatter 变 [B/dp,S,H/tp]）→ 编译框架层（Graph Instantiation 把符号维替换为具体 batch/seq/hidden 数值并传播，输出带依赖、tensor 尺寸、通信量的 Chakra DAG）→ kernel 调度层（下游 ASTRA-Sim 对 GeMM/Attn/ElementWise 算子用 benchmark lookup+校准 roofline 估时、对 NCCL 集合通信模拟调度，支持 compute-comm 重叠或按真实 trace 禁重叠）→ 硬件架构层（ASTRA-Sim 模拟 8×8 2D torus/NVLink+IB/DGX 分层拓扑与 HBM 容量/Infiniband 带宽；SimAI 模拟 NCCL/NVLink、ScaleSim 模拟 TPU 阵列、Genie 模拟 RDMA 网络）。一个 tensor 的路径：STG 张量 x[B/dp,H] 与 w[H,4H] 经 einsum → 按 tp 分片后匹配 AllReduce 汇聚 partial sum → 实例化为具体字节数 → ASTRA-Sim 模拟其在 H100+NVLink 拓扑上的延迟 → 输出 runtime/峰值显存/通信量供并行策略与硬件 DSE。
