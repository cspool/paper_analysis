## LIBRA: A High-Accuracy, Cost-Aware, and Coordinated Multi-GPU Page Prefetcher

- baseline方法是什么？
  - baseline 分两类。反应式：GRIT（SOTA）按页动态在 on-touch、access-counter-based（NVIDIA 默认阈值 256 次远程访问）、page duplication 三策略中选一，在首次远程访问后才触发迁移，所有迁移都在 critical path（GRIT 花 36% 总执行时间在页面迁移上）。预测式：NVIDIA TBNP 系（TBNP-O/F/AT/EA、Forest），空间局部性预取——UVM 内存先分 2MB 大页再切 64KB 逻辑块构成二叉树，far-fault 迁移 64KB 叶子块，子树 >50% 叶子已迁移即预取剩余叶子；Forest 进一步按访问序列自适应块/树深度。空间局部性预取器在多 GPU 下失效：(1) 精度低——工作负载跨 GPU 分区、每 GPU 只访问数据子集，空间局部性弱，且多 GPU 并发访问同页造成争用，Forest accuracy 仅 42%；(2) 无成本收益权衡——53% TBNP-EA / 51% Forest 的迁移反而增加总远程访问，仅 7%/10% 迁移有益；(3) 无协调导致 ping-pong——多 GPU 在短时间窗内反复来回迁移同一页，增加互连流量与争用。
  - 全栈执行例子（沿 MT 一次远程访问的数据路径）：请求 → L1/L2/L3 TLB miss（40-cycle L3、GMMU 100-cycle/级遍历）→ far-fault 中断 CPU UVM driver → GRIT 立即把页迁到请求 GPU（on-touch）或 TBNP 系同时按二叉树预取相邻 64KB 叶子块 → 迁移在 critical path 上执行（源 GPU TLB/cache 失效、SM 流水线 flush、NVLink 数据传输，一次迁移开销≈200 次远程访问）→ 请求 GPU 本地访问；另一 GPU 随后访问同页时 on-touch 再次迁移 → 来回 ping-pong；预取出的相邻页多为本 GPU 不再访问的页（低 accuracy），浪费互连带宽。编译框架、kernel 调度、芯片设计层次：论文未明确说明。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文用 stride-based 预测 + 成本收益 + 跨 GPU 协调替代空间局部性预取，对应三个设计：(1) 高精度硬件 MMP（Triggered Table + MMAT）：每 SM 4 way、每 way 4 个最高频 stride，L3 TLB miss 按 VPN 差阈值 512 归类学习，far-fault 时按式(1) stride_likelihood 做动态深度预测（每 +25% 概率多预取 1 页，如图 8 中 stride +2 概率 0.52 → 预取 0xa2+2、0xa2+4），匹配 GPU 每 SM 独立的多 way/多 stride 访问模式（Takeaway 2）——直接解决低 accuracy/coverage（81.8%/83.9% vs Forest 42.9%/48.9%，且预取页数更少 19967 vs 26617）；(2) 成本收益分析：复用 NVIDIA per-page 硬件访问计数机制估计被预取页的未来访问数，式(2) lat_remote*(acc_highest - acc_source) > page_migration_overhead 才迁移、否则只建 PTE 不迁移——解决"迁移成本被忽视"（LIBRA >69% 迁移有益 vs Forest 12%，迁移+远程访问时间合计比 GRIT 减 59%）；(3) PPC 协调器（CPU UVM runtime 软件模块）：汇总所有 GPU 的预取请求，hash 表记录 recent-migration/recent-use 位与 8 个跨 GPU 访问计数、周期右移衰减历史、回收冷条目，把页迁到估计访问数最高的 GPU 并抑制短窗内重复迁移——解决"无协调导致的 ping-pong 与错误目标 GPU"（消融：coordination 额外减 13% 迁移、35% 不必要迁移、45% 低效迁移、+6% 性能）。
  - 全栈执行例子（沿同一 MT 远程访问数据路径）：请求 → L1/L2/L3 TLB miss → L3 miss 转发 MMAT（每 SM 按 VPN 差归类到 way、更新 stride 计数器）→ far-fault → Triggered Table 判重（已处理则跳过）→ MMAT 动态深度预测（按式(1) 对 4 个最高频 stride 各生成 1–多页）→ 带估计访问数的预取请求经中断送 CPU 侧 PPC → PPC hash 表更新该 GPU 访问计数、查 recent-migration 位、按式(2) 判断：估计收益 > 迁移开销则 uvm_api_migrate(.) 迁到 acc 最高 GPU 并给请求 GPU 预取 PTE，否则仅 uvm_va_block_map(.) 建 PTE 不迁移 → GMMU 按协调结果解析 far-fault 并迁移全部/部分/零个请求页；GPU 侧 UVM support 周期性经 access-counter 中断把实际本地访问数回填 MMAT monitored VPN，形成预测-执行-反馈闭环。CPU-GPU 首次迁移仍用 first-touch（CPU 延迟高，符合默认 UVM 策略）。编译框架、kernel 调度、芯片设计层次：论文未明确说明。
