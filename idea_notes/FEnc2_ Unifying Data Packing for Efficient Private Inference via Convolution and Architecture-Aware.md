## FEnc2: Unifying Data Packing for Efficient Private Inference via Convolution and Architecture-Aware Fragment Encoding

- baseline方法是什么？
  - Baseline 为既有 HE-CNN 密文打包/编码方案族：CHET（row-major/Toeplitz 单通道卷积）、HELayers（block tiling + 多图打包，可做 spatial blocking）、CryptoNets（pixel-wise，每像素一密文）、Gazelle/Fast-HEAR/Multiplexed/Orion/Hyena+（interleaving + BSGS 多通道打包）、Fhelipe（层后合并稀疏槽但忽略下一层计算模式）。SOTA 为 Orion：多通道打包 + BSGS，初始密文稠密但 channel/feature 缩减层后密度不可保持。Baseline 三大缺陷：①静态/启发式、逐层无关的手工布局，无原则性指导；②跨层碎片化——1×1 缩减层后槽利用率从 50% 掉到 25% 甚至更低，稀疏密文导致密文数翻倍、SIMD 效率差、内存膨胀；③旋转优化不完整——各方案只减内旋转或只减外旋转，罕有跨层联合优化；且仅依赖单通道编码时大 feature map（224×224）单通道即饱和密文容量，Orion 多通道优化失效退化为 CHET。
  - baseline 全栈执行例子（Orion，LeNet 单图推理，32×32 输入）：模型推理算法层 = 输入 feature map 按 row-major 打包进密文槽，多通道卷积用 BSGS 拆嵌套循环做内（spatial，K²−1 次/密文）与外（channel，α−1 次/密文）旋转对齐做 MAC；系统框架层 = 客户端本地 CKKS 编码加密后把密文发给服务端，Orion 框架在 GPU/CPU 上执行 HE 电路；编译框架层 = 论文未明确说明（打包布局为手工静态设计，无自动生成器）；kernel调度层 = GPU HE 库执行 NTT/INTT、keyswitch（旋转主导，4.8ms vs PMult 0.15ms）、CMult/PMult kernel，旋转贡献端到端延迟约 70%；硬件架构层 = NTT/keyswitch 单元被海量旋转调用打满，内存带宽被 twiddle factor 与密文系数搬运占用。结果：单图 CIFAR-10 推理 >300s（Intel Xeon），ImageNet 上 MobileNet/ResNet 延迟被旋转+稀疏密文膨胀主导，1×1 缩减后槽利用率 12.5%-31.25%，密文数与内存翻倍，batch 稍大即 GPU OOM（MobileNet batch 4-8 即失败）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = FEnc²，统一自动化 fragment 编码框架，两个组件逐一对应缺陷：①Conv-aware Encoding（对应"静态启发式 + 旋转优化不完整"）——把 4D 张量按 S×S 块分解、块间独立密文，同时解耦 spatial 与 channel 依赖；最优 S* 由解析旋转代价模型（Theorem 1：S* = ceil((K²·N_in/(α·N_out))^(1/4))）自动导出、无需运行期 profiling，内旋转复杂度从 O(K²)（Hyena+ 甚至 O(K⁴)）降到 O(K)；且 S=1,BS=1 与 S=M 分别包含 Orion 与 CryptoNets 作为非最优特例，证明通用性。②Arch-aware Ct Compression/AAC（对应"跨层碎片化"）——通道缩减层后用 mask-rotate-add（Δ₁·Δ₂=Δ 共享尺度、单次 rescale、零额外乘法深度）把稀疏密文压实到 100% 槽利用率，阻断碎片向后续层传播，密文数减少 78%-94%。缺陷→设计映射：手工逐层无关布局 → 凸模型自动选块 + 层间 block size 调整（rot-mask-add 重打包，开销仅 0.42%-3.7%）；只优化单侧旋转 → 内/外旋转联合平衡；缩减层槽浪费 → AAC 恢复密度（50%→100%）。
  - 论文方法全栈执行例子（FEnc²，同一 LeNet 单图/大 batch）：模型推理算法层 = 输入 X∈R^{BS×C×H×W} 按 Algorithm 1 分块打包（S=S*），每密文存同块内坐标跨 block 的元素，卷积时内旋转降为 (⌈K/S⌉²−1) 或 4(S−1)/S²、外旋转由 αS²/BS 控制，stride≥2 直接丢弃密文实现（免后处理）；系统框架层 = 客户端只发非敏感元数据（H,W,C,BS,模型 id）+ 密文，服务端按 FEnc² 自动生成的索引-槽映射执行 HE-CNN，全程无明文交互、无运行期适配，与任何 CPU/GPU/FPGA/ASIC HE 加速器兼容；编译框架层 = 论文未明确说明（FEnc² 为应用层布局生成器，不修改编译框架；层间 block 变化用 rot-mask-add 适配）；kernel调度层 = GPU 上旋转/keyswitch/NTT 调用量下降 67%-94%（HELayers 为基准），kernel 调用 48,015→5,775（LeNet batch 32），密文数与同态乘法降 89%-94%，slot 利用率达 100%；硬件架构层 = 旋转需求骤降直接降低对 NTT/iNTT 执行单元的需求（面积/功耗可缩减、twiddle/密文访存带宽压力缓解），与 NTT/keyswitch 加速器正交互补。效果：LeNet 相对 Orion 最高 228.83×（GPU）/226.06×（CPU），MobileNet 4.55×（GPU）/9.43×（CPU），内存减少最高 98.49%/75.6%，最大 batch 从 4-8 提升到 16-512。
