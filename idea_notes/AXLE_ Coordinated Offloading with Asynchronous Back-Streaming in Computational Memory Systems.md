## AXLE: Coordinated Offloading with Asynchronous Back-Streaming in Computational Memory Systems

- baseline方法是什么？
  - Baseline 一：Remote Polling（RP，设备中心视图，代表工作 [37][19] 及多数 prior work）——把 CCM 当加速器，卸载经 CXL.io 远程 mailbox（MMIO 寄存器）完成：主机先经 CXL.mem 写 kernel descriptor，再经 CXL.io 入队命令 → 反复轮询远程 mailbox 查完成状态（真实硬件轮询间隔可达 100µs + 每次 CXL.io 往返）→ 固件写完成描述符、主机确认 → CXL.io 出队 → 最后经 CXL.mem 同步 load 结果。异步执行但不支持细粒度卸载：µs 级 kernel 的纯执行只需 16.7% 周期，其余全是轮询与协议开销。
  - Baseline 二：Bulk Synchronous flow（BS，内存中心视图，M2NDP [12]，本文 SOTA 基线）——把 CCM 当内存：自定义 packet filter 识别发往特定地址范围的 CXL.mem store 即 kernel launch，同步 store 响应即 kernel 完成，靠 memory barrier 阻塞后续访存。协议开销低、支持细粒度卸载，但主机在 CCM 执行 + 结果 load 期间全程 stall（图分析里 host idle 达 ~98%、CCM idle ~50%），端到端 pipeline 完全串行化。
  - baseline 全栈执行例子（PageRank 迭代）：算法层：邻接遍历+顶点更新卸载到 CCM、PageRank 值计算留主机，每迭代数据搬运量从 {#edge×#vertex} 降到 {#vertex}，但结果 load 仍是主机发起的 CXL.mem 同步加载（无量化/稀疏等算法优化）；系统框架层：无 serving/软件框架，应用直接驱动卸载协议（RP：CXL.io 邮箱多步交互；BS：单条 CXL.mem store + barrier）；编译框架层：论文未明确说明（kernel 以 RISC-V 指令形式手写，无编译器参与）；kernel 调度层：CCM 内 µthread 调度器按固定大小输入向量分派（RR），主机侧串行等待（RP 轮询/BS 阻塞），跨迭代依赖（新 frontier 依赖上轮结果）使主机并发也无法填补空闲；硬件架构层：CXL Type 3 设备 + PNM，无设备发起的数据搬运硬件——主机空闲 = T_CCM + T_data，CCM 空闲 = T_data + T_host，形成"两个空闲时间"。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = 异步背流（asynchronous back-streaming）协议 + AXLE 系统：把"结果何时搬、怎么搬"的控制权从主机转移到 CCM 设备。(1) 设备发起反向数据流：CCM 侧 DMA executor（CXL Type 3 上的 bus master DMA 引擎）在待发结果达到 Streaming Factor 时经 CXL.io posted write 把部分结果提前反流到主机本地内存——对应 BS"主机同步 load 结果、搬数据期间主机/CCM 交替空闲"的缺陷（T_C/T_D/T_H 三方重叠）；同时保留 CXL.mem store 启动 kernel 与 CXL.mem 流控消息——对应 RP"细粒度卸载协议开销高"的缺陷（低开销 + 异步兼得，Table II 第三行）。(2) 本地轻量轮询：轮询点移到主机本地，只轮询单地址 metadata 尾指针，µs 级间隔即可支撑细粒度任务——对应 RP 跨链路远程轮询与"高效通知"挑战（中断需 50µs 级、远程轮询需 pin 核，均不可用）。(3) metadata/payload 双 ring buffer + ready pool：轮询 routine 只搬 metadata 入 ready pool，主机调度器按自身策略从本地 region 消费 payload——主机任务可随时切换不空转，对应"数据快速暴露 + 与既有并行调度器接口"挑战。(4) OoO 流式 + gap-aware payload ring：metadata 携带 payload slot ID，CCM 与主机两套调度器互不感知对方顺序即可并行工作，无需同步任务执行顺序——对应"接口不同调度器而不强加排序"挑战。(5) 内存正确性零开销：栅栏保证 payload 先于 tail 更新、CCM 本地维护保守 head/tail + CXL.mem 流控防覆盖/溢出、DMA 区域 cache-bypass 防 staleness——对应 reordering/visibility/partial-write/cache-staleness 四类正确性问题。
  - 论文方法全栈执行例子（同一 PageRank 迭代）：算法层：卸载划分与 baseline 相同（无新算法，聚焦"如何卸载"）；系统框架层：三层软件栈——主机内核态驱动管理并预 pin DMA 区域（scatter-gather 描述符影子化给设备、cache-bypass）、主机用户态保证协议行为（如流控消息）、设备固件 DMA executor 处理卸载请求/监控结果/触发反流，硬件与 CXL 协议无需任何改动；编译框架层：论文未明确说明；kernel 调度层：CCM µthread 产出结果 → DMA executor 打 payload+metadata → 达 SF 即 CXL.io DMA 反流 → 主机轮询本地 metadata tail → 搬入 ready pool → 主机调度器（RR/FIFO，OoO 支持）选取就绪下游任务读本地 payload 执行 → CXL.mem 回传 head 索引流控（陈旧流控消息仍安全，CCM 无需等待即可继续流式）；主机/CCM/链路三方连续重叠运行；硬件架构层：CXL Type 3 + bus-master DMA 引擎 + 主机本地双 ring buffer（cache-bypass）。结果：端到端 runtime 较 RP 最高 -50.14%、较 BS 最高 -48.88%（PageRank、50ns 轮询；9 负载平均 -30.21%/-26.22%）；CCM idle 平均 -13.99×（相对 RP）/ -14.53×（相对 BS）、host idle 平均 -3.93×/-3.85×；host core stall 最高 -6×；OoO 关闭在 RR 调度下 runtime +1.38~1.74×；DMA slot 容量降至 12.5% 多数负载性能几乎不变（LLM 稀疏数据依赖 + OoO + 极小缓冲会死锁，需充足缓冲或顺序流式）。
