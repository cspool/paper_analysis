## MERIDIAN: In-Memory Acceleration for RAG with Document Attention Decomposition

- baseline方法是什么？
  - Baseline 是 KV 预计算 RAG 推理的**集中式执行范式**（TurboRAG [44]、BlockAttention [46]，以及 PIM 系的 CENT [14]、PAPI [16]、HeterRAG [40]）：文档 KV 离线预计算并存于 host DRAM（500K 文档约 ~14 TB，远超 H100 的 80 GB 容量），推理时把整份检索文档 KV 经 PCIe/CXL 搬到计算设备（GPU 或 PIM 加速器）与 query 实时生成的 KV 拼接后集中做注意力。痛点一（Bottleneck 1，Off-Device Communication）：host-device 互连带宽与设备内存带宽严重失衡——PCIe Gen5 ×16 约 128 GB/s vs H100 HBM 约 2 TB/s（>15× 差距），多设备场景共享 PCIe fabric 不随设备数扩展；文档 KV 传输平均占推理时间 48.60%、最坏 86.45%，1→4 H100 时升至 72.72%。痛点二（Bottleneck 2，Compute Inefficiency）：RAG 的 query 平均仅 ~16 token（表 I），预计算后 prefill 只剩 skinny GEMM（低算术强度、权重复用少），decode 被 memory-bound GEMV 主导，小 batch 下 FFN 也退化为 skinny GEMM；roofline 显示 attention 与 FFN 全程 memory-bound（图 3），H100 类加速器算力被严重闲置。
  - Baseline 全栈执行例子（一次 2Wiki 请求，doc 856.76 token、query 17.6 token、H100 集中式）：算法层：Qwen2-7B 前向，query+文档拼接后逐层 QKV 投影，文档侧 KV 复用预计算缓存、query 侧 KV 实时算；系统框架层：TurboRAG/BlockAttention 从 CPU 内存把该文档 ~857 token×2×d_model×2 bytes 的 KV 包经 PCIe DMA 搬到 H100 HBM，与 query KV 拼接；编译框架层：论文未明确说明（TurboRAG 对 KV 缓存命中做 chunked 组织，BlockAttention 做块级缓存）；kernel调度层：prefill 时 query 的 17 个 token 做 17×d_model 的 skinny GEMM（低占用），decode 每步 query KV 与 857 文档 KV 的 GEMV 注意力 + FFN GEMV，GPU 算力低利用率、内存带宽吃满；硬件架构层：H100 上文档 KV 常驻 host DRAM 反复跨 PCIe 搬运，通信占端到端延迟最高 93.40%，prefill/decode 被 memory-bound 拖慢。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法：MERIDIAN —— **去中心化 RAG 推理 + PIM 加速器协同设计**。(1) **Document attention decomposition（文档注意力分解）**：把注意力拆成 DocumentAttention 与 QueryResponseAttention 两个独立分支，文档侧 K/V 按 head 分片静止在 PIM 设备内存，各设备只对本地 shard 算注意力并产出紧凑局部摘要 (o_d, m_d, l_d)，经数值稳定的 online-softmax 聚合（m=max(m_d,m_c) 后 l=e^{m_d-m}l_d+e^{m_c-m}l_c、o=(e^{m_d-m}o_d+e^{m_c-m}o_c)/l）合并，数值语义与标准 softmax 完全一致。→ 对应解决痛点一：传输量从"整份文档 KV"（#Doc tokens×2×d_model×2B）降到"query+response 向量"（(#Q+#Resp)×2×d_model×2B），文档平均比 query+response 长 ~380×，通信降低两个数量级以上，且随设备数 N 分片后每设备只传 d_model/N 切片、总流量恒定；实测 MERIDIAN 通信占比 ≤6.34%。(2) **资源感知 PIM 计算基板**：LPDDR5X 受限功率/带宽下，skinny GEMM 用"只复制 buffer（占 GEMV 单元 ~14% 面积）而非复制完整数据通路（PAPI 式）"实现权重复用；非线性（GeLU/Swish）用与 GEMV 算术单元复用的 LUT 分段线性逼近（y=ax+b，breakpoint 查表+单次乘加）在内存侧就地执行，softmax 用专用精度硬件；PU（bank 旁，16 FP16 比较/乘法/加法器+4KB buffer，All-Bank-Mode）+ NMU（reduction+softmax）+ 8 个 BOOMv2 RISC-V 核分层完成 bank 内/内 channel/跨设备计算。→ 对应解决痛点二：skinny GEMM/GEMV/非线性全部在内存侧执行，无需外部引擎，缩短数据通路、消除集中式 attention 的全局聚合通信。(3) **协调感知混合调度器**：初始化静态映射（tensor/pipeline/hybrid 并行），运行时动态触发 + Interleaved Cluster Execution（在空闲 cluster 上启动后续 batch 消除 DAC/CEC 时序失衡）+ 动态负载迁移（CEC 参数静态复制到 DAC，空闲时协助上下文计算）。→ 对应解决去中心化引入的跨设备依赖 stall，保持高并行效率。
  - 论文方法全栈执行例子（同一次 2Wiki 请求，32 PIM 设备=16 DAC+16 CEC，Qwen-TB，d_model=3584）：算法层：document attention decomposition 把注意力拆为文档/上下文两分支，文档 KV 按 head 分片到 DAC 各设备、query 侧 KV 在 CEC；系统框架层：host 收 query + 文档 ID，经元数据索引定位 DAC 中预计算 KV，CXL 3.0 switch 提供 host-device 与 device-to-device 直连，host 统一调度器按 hybrid 并行静态映射层/head、运行时动态下发；编译框架层：PIM-SYCL/CUDA 式异构编程模型把高层 API（GEMV/GeLU、设备初始化、并行策略）编译为 PIM 指令（PIM_MAC/PIM_CMP/PIM_EW_MULT/PIM_EW_ADD + PIM_ACT/PIM_WR_PB/PIM_RD_PB，标准 load/store 经 CXL.mem）派发到设备控制器，控制器广播到 channel/PU；kernel调度层：ICE 让 DAC/CEC 交替处理 batch 消除失衡，DAC 空闲时用复制的 CEC 参数协助上下文计算；prefill 的 17 个 query token 做 17×3584 的 bank 内 skinny GEMM（buffer 复制共享算术单元实现权重复用），decode 每步 query 向量（~7KB FP16）经 CXL 发到各 DAC 设备、设备本地算 q·K_d^T（1×857 GEMV）+ online softmax，只回传 o_d/m_d/l_d 紧凑摘要；硬件架构层：PU 在 All-Bank-Mode 下 16-lane（1 GHz，32 TFLOPS/设备）执行 GEMV/分段线性，NMU 做 channel 内 reduction 与专用精度 softmax，BOOMv2 核跨设备聚合，CXL switch 共享 128 GB/s 链路带宽建模 contention；结果：文档 KV 静止在内存、仅交换紧凑统计量，通信占比 ≤6.34%，平均吞吐 5.36×/6.64×/3.98×/3.32×/3.91×、延迟 4.30×/5.34×/3.31×/2.73×/2.79×（vs TurboRAG/BlockAttention/CENT/PAPI/HeterRAG），能量效率 7.48×/9.24×/4.48×/4.54×，准确率差 <0.4pp。
