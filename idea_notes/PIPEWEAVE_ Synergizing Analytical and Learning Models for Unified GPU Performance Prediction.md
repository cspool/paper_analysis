## PIPEWEAVE: Synergizing Analytical and Learning Models for Unified GPU Performance Prediction

- baseline方法是什么？
  GPU 性能建模三范式各有痛点：(1) cycle-accurate 模拟器（Accel-Sim、MGPUSim、AMALI、LLMCompass）：逐指令/逐周期模拟微架构，保真度高但速度慢、跨架构不可移植；(2) 解析模型（Roofline、GPUMeCH、GCOM、Linear）：靠吞吐公式快速估算，但精度受限、依赖硬件专属 microbenchmark，跨新架构不通用；(3) 数据驱动（Habitat、Neusight）：学 tile 级延迟，速度快但把 tile 当原子、假设 SM 行为均匀、静态 wave 假设，无法刻画 fused kernel 耦合（如 FlashAttention）与跨 SM 负载不均。
  全栈执行例子（以 Qwen2.5-14B 在 A100 上 BF16 推理为例，baseline=Neusight 类 tile 级黑盒/灰盒）：算法pipeline——模型推理中 GEMM/Attention/RMSNorm/SiLU&Mul 等算子被当成计算图上的独立 operator，kernel 边界按算子边界切分；系统框架——vLLM/SGLang 按算子逐个 launch kernel；编译框架——论文未明确说明（无编译期介入）；kernel调度——把每个 tile 当作等延迟的原子单元，用静态 wave 模型估算 SM 占用与 tail 效应，FlashAttention 这类 fused kernel 被拆回 GEMM+Softmax 算子近似，未显式建模 Tensor/FMA/内存 pipeline 各自的负载与争用，也未建模硬件 round-robin 或 persistent tile 调度导致的跨 SM 负载不均；硬件架构——将 SM 视为单一聚合吞吐的黑盒（一次一个 tile 级"compute roof"），不区分 Tensor/FMA/XU/内存 pipeline 的并发与饱和，时钟级细节缺失导致新架构（H800 vs H20 计算/访存比差异大）上误差可达 75%+。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  论文方法为 PIPEWEAVE 灰盒框架：用知识驱动解析模型（Kernel Decomposer→Scheduling Simulator→Feature Analyzer）把 kernel 显式分解为 SM 上异构指令 pipeline（Tensor/FMA/XU/MIO）的 demand 与理论周期特征，再用轻量 MLP 学习跨 pipeline 交互与资源争用等难以解析刻画的高阶效应；另用 P80 分位回归模型预测"潜在性能上限"来诊断实现低效并指导 kernel 优化。
  全栈执行例子（同一 Qwen2.5-14B BF16 推理在 A100）：算法pipeline——Kernel Decomposer 直接从 FlashInfer/vLLM/SGLang 源码（cuBLAS 用反推的 surrogate 映射）把 kernel 拆成 task（CTA 或 persistent tile），attention 按 causal masking 差异给每个 task 真实维度，fused kernel（FA2/FA3）不再按算子切；系统框架——不修改 vLLM/SGLang，Workload Generator 按其 kernel 调用逻辑生成串行 kernel 序列，逐个用 PIPEWEAVE 预测后求和得 E2E 延迟，分布式下通信 kernel 用 Random Forest 预建库建模；编译框架——论文未明确说明（不介入编译期）；kernel调度——Scheduling Simulator 显式模拟硬件 GigaThread 的 round-robin CTA 调度与 persistent kernel 的软件 tile 调度（FA3 MinHeap 逻辑），得到真实 task distribution，捕捉跨 SM 负载不均与 tail 效应（对应 Neusight 的静态 wave 假设缺陷）；硬件架构——Feature Analyzer 把 Roofline 的单一 roof 扩展为每类 instruction pipeline 独立的 multi-dimensional roof：每 task 按 tile 几何算 Tensor ops（α·tile_M·tile_N·tile_K）与 FMA/XU ops、按字节算 MIO 需求，除以各自吞吐得理论周期，再按 task→SM→GPU 三级聚合（含 Max SM 特征），MLP 以这些 pipeline 级特征学习不同 GPU 上 pipeline 并发/争用的非线性和与硬件专属低效（如 H20 极易饱和 vs H800 难达峰值），从而 seen/unseen GPU 上 kernel MAPE 降到 6.1%/11.4%、E2E 8.5%/10.7%，并借 P80 上限模型把 A40 上 Fused MoE Triton kernel 诊断出 921 个 underperforming points 并 autotune 提速 1.61×。
