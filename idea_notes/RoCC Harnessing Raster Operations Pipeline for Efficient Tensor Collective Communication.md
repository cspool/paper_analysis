## RoCC Harnessing Raster Operations Pipeline for Efficient Tensor Collective Communication

- baseline方法是什么？
  - Baseline 分两类：① 软件重叠（software-based overlapping，如 kernel fusion、SM 分区 [6][32][45][61]）：GEMM 与 CC 都在 SM 上执行，把一部分 SM 分给 CC（如 oracle 方案 20% SM 专用于 CC），或 kernel 融合按阶段交错 GEMM 与 CC。痛点：SM 资源争用（80% SM 时 GEMM 慢 20%，性能随 SM 数指数下降）、需要定制 tiled GEMM kernel 与 fuse/sync 编程、只能在 coarse-grained 粒度重叠（一次融合/一个 kernel 边界），难以完全隐藏通信延迟；CC 是网络/内存 bound（AllReduce 操作强度 ≈0.1 FLOPs/Byte），在 SM 上执行浪费大量计算资源且经受 SM 到内存的长延迟（实测 CC 占 tensor 并行执行时间 40%-70%）。② 硬件加速方案（T3 [44] DMA+HBM-PIM、in-network aggregator [26]、专用 CC 加速器 [47][48]）：为 CC 新增独立加速器，需要完整数据通路（多步 CC 操作 + 独立发起内存/网络请求的能力），最轻量设计也要几十个浮点单元和数 MB 内部 buffer（[48]），面积成本高且需与 GPU 接口。
  - Baseline 全栈执行例子（算法pipeline-系统框架-编译框架-kernel调度-硬件架构；本文为 GPU 硬件架构论文，算法pipeline 与编译框架层论文未明确说明）：一个 LLM（如 GPT-2/Whisper）FFN 层在 4 GPU 上做 RowLinear 张量并行训练，一次权重行切分 + AllReduce 归约：① 算法pipeline 层：模型结构是标准 transformer FFN（隐藏层/FFN 尺寸如表 II），行线性并行把权重按输入行切分、各 rank 算部分输出——算法本身不变；② 系统框架层：PyTorch distributed 经 NCCL 库调用——NCCL 把 CC 拆成独立的 CC kernel，与计算 kernel 顺序/分批执行，fuse 方案（如 FlashOverlap/Comet 风格）把 CC kernel 与 GEMM kernel 融合但只能按 kernel 粒度重叠；③ 编译框架层：论文未明确说明（无编译框架修改，kernel 由 CUDA 直接编写）；④ kernel 调度层：GEMM kernel 用全部或部分 SM 执行，CC kernel（ring AllReduce 的 reduce-scatter + AllGather 多阶段）在部分 SM 上执行（软件重叠）或顺序等待（无重叠），SM 在 GEMM 与 CC 间时间/空间共享，CC 阶段 SM 大量时钟花在访存与等待网络（NVLink 300GBps）上；⑤ 硬件架构层：SM 发 atomic/load 请求经 NoC 到远端 L2/DRAM 完成归约与数据搬移（SM 距内存远、NoC 往返开销大），或者（T3 式）DMA 引擎搬数据 + HBM-PIM 做归约但 PIM 与普通内存请求在双模 HBM 上争用。结果：GEMM 与 CC 顺序执行时 CC 占 40%-70% 时间，软件重叠也因 SM 争用只能部分隐藏。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 RoCC：不加新加速器，而是扩展 GPU 已有的 ROP（光栅化管线）单元做 CC 引擎。ROP 是唯一同时满足 4 个条件的引擎：能做归约（原子 ALU）、能独立于 SM 发起内存请求、LLM 计算期间高度空闲（实测 Qwen2-7B 训练 11476 个 kernel 仅 141 个发 atomic、GEMM 内 atomic 占比 ≈0.0183%）、位于 L2/内存旁（减少 NoC/缓存争用）。四件设计对应四类缺陷：① 对应"无接口触发 CC"——每条 CC 操作只加 1 个 intrinsic（rocc_allreduce 等）+ 1 条 ISA 指令（ROP_AR/ROP_AG/ROP_A2A），经既有 atomic 数据通路下发；② 对应"ROP 语义与 collective 不匹配"——collective primitive decomposition：CC → 5 primitive（send/recvReduceSend/recvReduceCopySend/recvCopySend/recv，NCCL ring 算法）→ 5 μOp（ReadDoorbell/Write/DepBarrier/Add/RingDoorbell），两个查找表译码器只占 225 bit（投影 1KB），命令缓冲 66B；③ 对应"ROP 无法路由多步 CC"——doorbell 门铃消息：SM→ROP 与 ROP→ROP 都靠 doorbell 包（含 Offset/PayloadAddr/SrcRank/Stage），doorbell manager（7 状态状态机）+ 32 条目 buffer，ROP 按 descriptor 的 stage 自动识别下一 rank、跨 GPU 接力，无需 SM/CPU 参与调度；④ 对应"ROP 只能访问本 MPU 的 L2 slice"——按 cache line 单元分配 tile，每个 ROP 只处理其 MPU 内 L2 slice 的 cache line，并用 symmetric tensor allocation（SymMalloc）把 CC tile 映射到各 GPU 相同物理地址，跨 GPU 寻址免翻译。对比 baseline 缺陷的收益：SM 全部留给 GEMM（无软件重叠的 SM 争用）、无新加速器面积（只加译码/路由小逻辑 ≈2.4% L2 slice，T3/专用加速器需数 MB buffer）、ROP 近内存减少 NoC/L1 miss 延迟（CC-only AllReduce 快 35%）、warp 级细粒度重叠（重叠率 83.4%，超过 kernel 粒度）。
  - 论文方法全栈执行例子（算法pipeline、编译框架层论文未明确说明）：同一 GPT-2 FFN RowLinear 训练（或 MoE AllToAll、ColumnLinear AllGather）：① 算法pipeline 层：模型不变，tensor 并行语义不变；② 系统框架层：DL 框架（PyTorch 式）启动 kernel 前用驱动 API 创建 RoCC descriptor（SrcBase/DstBase/DataSize/LocalRank/TensorDim/TileShape/CollType/DataType）存到各 MPU 片上 buffer，用 SymMalloc 分配对称物理地址；③ 编译框架层：论文未明确说明（intrinsic 由 CUDA 前端直接使用，无编译器改动）；④ kernel 调度层：单个 fused kernel——GEMM 用全部 SM 执行，每个 warp 完成自己的 tile 计算、store C[..] 后立即调 rocc_allreduce(&C[..], &D[...]) 触发 CC 再算下一 tile（warp 级细粒度交错）；ROP 侧每 cycle 从 doorbell buffer 取最多 4 个 doorbell 分发到 4 个执行单元，按 stage 译码执行 μOp；⑤ 硬件架构层：SM 发带 doorbell flag 的 ROP 指令包 → 目标 MPU doorbell manager 识别（与普通 atomic 分离）→ collective decoder+primitive decoder 查表 → collective command buffer → ROP ALU 执行（Add 归约、Write 经 ROP cache/L2 写回、RingDoorbell 把归约结果作 payload 经 GPU-GPU 300GBps full-mesh 发往下一 rank 的 ROP，Stage 递增，4-GPU ring 7 阶段/8-GPU 15 阶段直到终态）→ 结果写本地对称地址；同时 SM 继续算下一 tile，GEMM 与 CC 完全并行（平均 51% 加速 vs 顺序 baseline、23% vs oracle 软件重叠、T3 23% vs RoCC 48%，仅 2.4% L2 slice 面积，H100/B200 上再 +3%/+2%）。
