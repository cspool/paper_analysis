## ParetoES Hardware-Accelerated Sparse Embedding Similarity via Pareto-Optimal Pruning

- baseline方法是什么？
  - Baseline 是"全计算"（full-computation）范式的 Top-K SpMV 稀疏 embedding 检索系统：(i) CPU/GPU 基线——Faiss v1.7.2（IndexIVFFlat 倒排索引 + 可调 nprobe 的选择性计算，但基于 K-means 的 L2 距离聚类在稀疏高维空间聚类质量差、需扫约 1.83× 更多簇才达 Recall@100=80%；且 SIMD/warp 并行被不规则访存与负载不均拖累）、sparse_dot_topn（精确全计算基线，不做近似）、MKL+Sort；(ii) FPGA 基线——FPGA32 [47]（BS-CSR 块流式）、AccelES [60]（Ultra-CSR 编码 + INT6 低比特量化 + ReSparse 剪枝 + HBM 流式），两者都是稀疏无关（sparse-agnostic）但对全部数据库向量做穷尽比较以保证 Recall>99%，固定延迟、无法运行时用 Recall 换吞吐，存在大量冗余访存与计算（非 Pareto 最优）。共同缺陷：未认识到"处理 20% 候选向量即可达 ~80% Recall"的 Pareto 规律，算法上固守全计算范式，架构上也缺乏高效执行剪枝搜索的支持（表 I 显示无系统同时具备 sparse-agnostic + selective computation）。
  - Baseline 全栈执行例子（一次 query，AccelES 风格）：算法层：查询向量 v 与全库稀疏矩阵 A 做 Top-K SpMV y=A·v，所有 m 行非零都被读取与计算（INT6 量化 + 剪枝后仍遍历全部剩余非零）；系统框架层：host CPU 把 query 量化后发给 FPGA，整库扫描、nprobe 固定为 nlist；编译框架层：Vitis HLS 把 C 内核综合为固定全遍历数据流，无运行时配置接口（改 Recall 目标需重新综合）；kernel调度层：HBM 流式拉取全部非零、单/少核执行、无核间动态负载均衡（power-law 热点导致 straggler）；硬件架构层：HBM 流式读全库非零 → 全局点积累加 → 单体 Bitonic-512 排序（11,520 比较器、45 级流水，资源爆炸）→ 输出 Top-K；芯片设计层：论文未明确说明（FPGA + HBM2 栈，非新芯片结构）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：ParetoES 用"选择性计算"（selective computation）范式 + 算法-架构-系统垂直协同设计，把 Recall 目标从 >99% 的穷尽计算放松到 80–100%（生产 RAG/推荐系统在 80–90% Recall 下几乎无损），只评估最有价值的候选向量，沿 Pareto 前沿做 Recall-吞吐权衡。三大设计直接对应解决 baseline 缺陷：
    1. 算法侧（解决"K-means 稀疏聚类质量差→扫过多簇"与"带宽/算力冗余"）：Spherical K-means++ Refine（归一化 + 余弦方向敏感聚类 + K-means++ 初始化 + merge(θ=0.9)/split(θ=0.6) 动态精化）使 Recall@100=80% 下扫描向量数更少（Fig.9 各数据集均优于 K-means/Spectral/Hierarchical）；INT6 量化（动态缩放、不裁剪保角度）+ 增强 ReSparse 剪枝（仅非零均值阈值，解决极端稀疏下全局均值被零拉低导致几乎不剪的问题）把非零再降 18.09%（平均）相对 AccelES，与 Ultra-CSR 结合带宽效率提升 6×。
    2. 架构侧（解决"全遍历 + 全局排序资源爆炸 + 不规则访存"）：ACPE 把选择性簇探测做成硬件原语——Bitonic-16 质心筛选选 Top-nprobe 簇，仅流式读选中簇子矩阵（Recall 0.8/0.9/1.0 时消除 68%/44%/4% 访存与计算）；DMSU 用 32 个核内 Bitonic-16 替代单体 Bitonic-512（比较器 11,520→2,560、10-cycle 确定性延迟）支持核内局部 Top-16 排序；质心-向量 HBM 共置 + Mem Map scheduler + 15 路 URAM query 复制把全局不规则随机访存重塑为有界流式，32 个隔离 compute-memory 对持续占满全部 HBM 通道；sub_nprobe 软件接口把 nprobe 参数从 bitstream 解耦，运行时动态调 Recall 目标无需重综合。
    3. 系统侧（解决"power-law 热点负载不均 → 4.6× 核间失衡"）：H2Balance 三级层次均衡（100-query 热点 profiling → top-32 热点簇静态锚定到专用核 → 其余簇贪心调和到最轻负载核），CV 从 34.25% 降到 0.01%（静态）/5.16%（新查询），吞吐 +37.52%，对分布漂移（+0.2 bias）仍保持 CV 36.27%→12.25%。
  - 论文方法全栈执行例子（一次 query）：算法层：离线 Spherical K-means++ Refine 聚类 + 混合精度（聚类全精度浮点、检索 INT6）+ ReSparse 剪枝 + Ultra-CSR 编码；在线 query INT6 量化 → 与质心内积选 Top-nprobe 簇（仅覆盖 ~20% 候选即达 ~80% Recall）；系统框架层：host CPU 算 sub_nprobe=⌈nprobe/32⌉ 静态下发，改 Recall 只改参数不改 bitstream；编译框架层：Vitis HLS 2023.2 把 ACPE 数据流综合到 Alveo U280（225MHz），nprobe 不入 bitstream；kernel调度层：32 ACPE 核各自独立流水（x-decoder popcount → 15 URAM 复制取 query → 6-bit 内积 → Aggregator → 4×Top-4 updater → Bitonic-16 sort → Mem Map 取下一簇），H2Balance 静态锚定+贪心映射簇→核；硬件架构层：选中簇非零经 512-bit HBM 通道以 30 非零/packet 流式进入，Top-16 核内排序，32 核 Top-16 经 PCIe 回传 host 聚合为全局 Top-512（2KB、微秒级）；芯片设计层：论文未明确说明（HBM2 双栈 32 PC 为平台配置，非新芯片结构）。
