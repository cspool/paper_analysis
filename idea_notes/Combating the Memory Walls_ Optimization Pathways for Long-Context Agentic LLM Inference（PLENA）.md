## Combating the Memory Walls: Optimization Pathways for Long-Context Agentic LLM Inference（PLENA）

- baseline方法是什么？
  - Baseline 是方形 systolic array 的 GEMM 加速器（TPU v3 式 128×128 方阵，以及 64×64 的 MicroscopiQ/OliVe/FIGNA）与商用平台（A100/H100/TPU v6e）跑长上下文 agentic LLM 推理：(1) agentic 负载（CUA/WUA/CLI agent）比 chatbot 平均多 100× token（极端 1000×），带来两个内存墙——带宽墙（KV/权重读 + KV 写回）与容量墙（KV cache 随上下文线性增长，LLAMA-3-70B 128k 上下文 FP16 KV cache 单 batch ≈39 GB，常超过权重体积，限制 batch）；(2) 内存受限迫使 batch（GEMM 的 M 维）远小于隐藏维 K，产生 fat GEMM（M≪K≈N），方形阵列 M=N=128 的对称假设失效，乘法器利用率骤降；(3) 长 decode 中 attention FLOPs 反超 FFN（LLAMA-3-70B 约 19k 生成 token 处交叉），但方阵对 FlashAttention 的 per-head 小 GEMM（head_dim=128、GQA 一个 K 头配多 Q 头）利用率低；(4) 无原生 FlashAttention 的 systolic 加速器只能把 QK^T 中间结果写回 off-chip 再读回做 softmax 与 PV，额外内存流量加剧带宽墙；(5) PTQ 方法（GPTQ/QuaRot）为整数格式设计，直接套用到 MX 格式会失效（MXFP4 直接跑 4/4/4 掉到 256.22 PPL）。
  - baseline 全栈执行例子（OSWorld-L 请求 90k prefill / 8k output，A100 4×SXM、batch 被容量压到 4）：token 流 → vLLM 0.10 V1 / PyTorch 调度（prefill 大 GEMM、decode 逐 token GEMV）→ CUDA kernel：QK^T GEMM 用 Tensor Core（方形 tile 下 M=batch≪K 利用率低）→ softmax 与 PV 中间结果回写 HBM 再读回 → FFN 两层 GEMM（同样 fat）→ KV cache 以 FP16 追加（写带宽）并随上下文增长占满 80 GB HBM。算法层：FP16/INT4 常规量化（GPTQ/QuaRot 面向整数格式）；系统框架层：GPU 上 vLLM 0.10 V1 调度、TPU 用 TPU 运行时（v2-alpha-tpuv6e）；编译框架层：CUDA/XLA 编译（论文未明确说明）；kernel 调度层：Tensor Core GEMM / FlashAttention CUDA kernel；硬件架构层：方形 systolic array / Tensor Core + HBM。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = 三条优化路径 + 完整软硬件栈。Pathway 1 flattened systolic array：sub-arr 串排 + 输出驻留数据流 + 全流水 + M_SUM 加法树，BLEN 可配成≈batch（FFN fat GEMM 满利用），FlashAttention 时切分为多个小 flattened core 做 per-head GEMM、MLEN//HLEN 头并行——对应"方阵 M=N 假设 vs fat GEMM / per-head GEMM"缺陷（A.A FLOPs/mm² 12.81 vs FIGNA 6.71 / MicroscopiQ 1.08，Table XI）。Pathway 2 非对称量化：W/A/KV 独立精度（W 用 MXINT4、KV 低精度、激活高精度 FP 驻留 Vector SRAM），块级裁剪 + 输出范数引导裁剪搜索（GPTQ 式 Hessian 外循环 + 输出范数内循环）+ 选择性旋转解决 MX 上 PTQ 失效——对应带宽墙（4/4/4 下 OSWorld-L 峰值带宽 8192→2048 GB/s）与容量墙（KV 足迹 239.26→59.81 GB、权重 129.46→32.36 GB，同 HBM 下 batch 可放 4→16）。Pathway 3 原生 FlashAttention：Matrix SRAM transpose-on-read（QK^T 免显式转置，行分布多 sub-bank 零冲突）、指令级 H_LOAD 预取与计算重叠、vector/scalar 单元 online softmax、ISA tile-by-tile 融合调度——对应"中间结果回写 off-chip 与缺少融合原语"缺陷（大中间激活留在片上）。外加软硬件栈：自定义 47 条 ISA、PyTorch→ISA 编译器（config→汇编模板）、Rust transactional emulator（+Ramulator/DRAMSys，比 RTL 快 200×、延迟误差 4.17%）、BoTorch 多目标 BO 的 DSE（accuracy-latency-area 三目标）自动搜出 (BLEN,MLEN,VLEN,W/A/KV) 最优配置。
  - 论文方法全栈执行例子（同一 OSWorld-L 请求）：token 流 → PLENA 编译器按模型 config 映射为 ISA 模板（FFN：M 指令 GEMM (BLEN,MLEN)×(MLEN,BLEN) 输出驻留 + M_SUM 加法树归约；attention：QK^T 用 Matrix SRAM 转置读、vector 指令 max/sum/exp/div 做 online softmax、PV GEMM，K/V append 前 vector 指令做 Hadamard 旋转 + MX 量化写 HBM）→ 32-bit 指令 PCIe 下发 → 矩阵单元在 flattened 阵列上满利用执行 fat GEMM（PE 吃 MX 输入、INT 累加、写回前转 FP）→ H_LOAD_M/H_LOAD_V 预取引擎后台从 HBM 流式取 MX 数据（块与 scale 分离对齐存储）隐藏延迟 → 权重 MXINT4、KV MXINT4（带选择性旋转）、激活高精度 FP 的非对称数据通路 → Ramulator/DRAMSys 模型给出内存时序。结果：LLAMA-3.3-70B OSWorld-L 下 TPS 2.21× A100、Tok/J 4.04×；整体最高 2.23× A100（114k/5k）、4.70× TPU v6e 吞吐、4.04× 能效；4/4/4 量化下游任务损失小（HumanEval 89.6→84.1、GSM8K 97.85 持平、BFCL-W 27→24）。算法层：MX 非对称量化 + 块级裁剪/选择性旋转；系统框架层：自研编译栈（无 GPU serving 框架）；编译框架层：自研轻量编译器 + BoTorch DSE；kernel 调度层：ISA tile 级持久调度（M/V/S/H/C 指令，无 OS kernel 概念）；硬件架构层：flattened systolic array + 非对称数据通路 + 双 SRAM 预取 + 7 nm RTL（DC 综合 1 GHz）。
