## LoKA: Low-precision Kernel Applications for Recommendation Models At Scale

- baseline方法是什么？
  - Baseline 是把 LLM 上成熟的 FP8 低精度训练直接套用到大型推荐模型（LRM）：用 TorchAO（PyTorch 主流低精度库）对 Wukong 模型所有线性层（输入/输出特征 ≥128）做 tensorwise FP8 scaling 的 DLP（Direct Low Precision）训练/推理，以及生产现状（95% 模型 TF32 训练、99% FP16 推理、FP8 仅 1% PTQ 推理）。痛点：① 数值敏感——LRM 质量约束极紧（0.02% relative log loss 即显著退化），直接 FP8 训练在 64 H100 上实测 1.3× 变慢 + 2.5% relative log loss 退化；② 库基准失真——FBGEMM/TorchAO/DeepGEMM 用标准正态随机张量验证精度，而真实 LRM 激活分布重尾、相关、非平稳（离群激活），用学习分布测试时各库 MERE 几何均值增高达 15%，随机基准漏掉真实量化误差；③ 小 GEMM + 归一化结构——LRM 由大量小 GEMM 紧跟归一化层组成，量化/反量化与去归一化开销占端到端 GEMM 延迟 >30%、有效 TFLOPS < 峰值 20%，甚至比 BF16 更慢；④ 训练环境通信密集——混合并行（嵌入表 AlltoAll sharding + 稠密 FSDP），低精度收益被通信稀释。
  - Baseline 全栈执行例子（Wukong 一个线性层 FP8 训练迭代）：输入 x 与权重 W → **算法层**：TorchAO 按 tensorwise scale 把 x、W 量化到 FP8 → FP8 GEMM（FP32 快速累加）→ 反量化到 BF16/FP32 → 紧跟 LayerNorm（须在更高精度反量化后计算方差/均值，再重新量化，量化+归一化+反量化往返开销常抵消低精度收益）→ Swish 激活（x·σ(x)，指数运算放大离群值，量化损失剧增）→ **系统框架层**：嵌入表经 AlltoAll 在 GPU 间 sharded 通信（未量化），稠密层 FSDP AllGather/ReduceScatter，通信占迭代时间大比例；**编译框架层**：PyTorch eager + torch.compile，低精度 kernel 经库暴露；**kernel调度层**：每个线性层固定走 TorchAO 单一 recipe（tensorwise），27 个不同 shape 一律同策略，shape 不适配时量化开销吞掉 FP8 收益；**硬件架构层**：H100/B200 的 FP8 张量核（峰值 FLOPs 远高于 TF32）被"小 GEMM 量化开销 + 精度不安全被迫回退高精度"浪费，B200 FP8=TF32 的 4.1× 无法兑现。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法：LoKA 系统-模型协同设计，三个组件逐条对应解决：
    1. **LoKA Probe（分布感知 profiling）**（对应解决"库基准失真/数值敏感"）：在线学习每层激活（多元高斯，Welford 批量协方差，O(N²)）与权重（矩阵正态，Kronecker-factor EMA，O(M²+N²)）的二阶统计，离线从学习分布采样合成输入/权重做统计显著的 MERE + 吞吐评估——量化出真实分布下的逐层误差（随机测试漏掉的 15% 误差增幅、FBGEMM faulty test code 的 47× MERE 差异均由此发现），并识别三类隐患：bias 项发散、归一化开销与 mean-cancellation、sigmoid 激活不稳定。它让"哪里低精度安全"从拍脑袋变为统计可判（不安全层回退，MERE<0.2 才入选）。
    2. **LoKA Mods（精度感知模型-硬件协同设计）**（对应解决"小 GEMM+归一化开销 / sigmoid 不稳定 / bias 发散"）：No Bias 移除发散 bias（借鉴 DeepSeek/PaLM/Falcon，兼减 FSDP padding 通信）；BlockNorm 把归一化改为固定块（256 元素）的 Grouped-RMS 归一化，融合进 GEMM epilogue 在片上完成（避免 HBM 往返、全局同步与均值相消误差，等价无参数 Grouped RMSNorm，训练/推理同块大小）；Hard Swish 替换指数型 Swish（分段线性、可与 BlockNorm 同 kernel 融合）。三 mod 单独均不能稳，合并后 FP8 全轨迹 loss 与高精度基线持平。
    3. **LoKA Dispatch（逐算子 kernel 编排）**（对应解决"单一 recipe 不适配 / 通信密集下收益被稀释"）：把每个 GEMM 作为独立优化问题，在 TorchAO/DeepGEMM/FBGEMM 各 recipe 中按 Probe 的 (MERE, speedup) 过滤（<0.2、>1.05×）后选吞吐最高者，自定义 autograd + 初始化变换 pass 包装线性层、前向/反向独立路由；推理静态选 kernel，训练仅在分布大漂移时动态切换。逐算子混合策略 1.12× 超过最佳统一 recipe 1.08×。
  - 论文方法全栈执行例子（同一次 Wukong 线性层 FP8 训练迭代，LoKA 启用）：x、W → **算法层**：Probe 从流式统计（μ,Σ / M,U,V）采样合成分布做离线 MERE 评估 → Dispatch 按评估选该 shape 的最优 (库, recipe)（如该 (2048,123200)@(123200,1024) GEMM 选 DeepGEMM blockwise，另一 (2048,256)@(256,768) 选 TorchAO rowwise）→ FP8 量化 + GEMM 后，**epilogue 内融合 BlockNorm（块 256 RMS）+ Hard Swish + 反量化**，输出直接写 HBM，无 bias 项 → **系统框架层**：嵌入表 AlltoAll 与稠密 FSDP 通信模式不变（量化通信统一 BF16 保证公平），低精度只作用于稠密计算，通信占比高时收益略降但 256 GPU 仍 +10% 吞吐；**编译框架层**：PyTorch + torch.compile，包装层保持标准 Linear 语义、新 kernel 经库 API 接入；**kernel调度层**：每 GEMM 独立映射到最快且满足 MERE<0.2 的 kernel，前向/反向可不同实现；**硬件架构层**：H100/B200/GB200/MI300X/MI350X 的 FP8 张量核被按算子充分利用（B200 内存更大→更大 batch→低精度收益比 H100 更高），开发后未见的 GB200/MI350X 上无修改直接得到相当加速比。端到端：训练最高 1.19×、推理 1.4×，生产 5–20% 训练 / 10–17% 推理加速，全轨迹零质量损失。
