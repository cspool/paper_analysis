## Helium: Quantifying Microarchitectural Side-Channel Leakage with Probabilistic Guarantees

- baseline方法是什么？
  - baseline 为两类零泄漏防御：(1) constant-time (CT) 编程——避免把秘密传给不安全指令的操作数（历史上不安全操作数仅限内存地址、分支操作数与少数可变时算术指令如除法；如今数据相关优化（zero-skip、silent store、value prediction、data memory-dependent prefetching 等）威胁使所有指令操作数都不安全，CT 编程变得不可能）；(2) 硬件侧 ISA 扩展（Arm DIT、Intel DOIT、RISC-V Zkt/Zkvt）——粗粒度关闭数据相关优化，DOIT 当前开销可接受但 Intel 警告未来处理器上性能影响可能"显著更高"；(3) 软件侧细粒度方法，以最近工作 cio（ASPLOS'24，二进制码变换编译 pass）为代表——把秘密相关不安全操作数变换为永不在不安全值集合中取值（如 32-bit 减法：两操作数零扩展、第 33 位置 1、相减后取低 32 位），使所有指令始终呈现同一 µobs，零泄漏但开销高达 2.31×–15.71×（Chacha20-Poly1305 mul64 2.31×、Ed25519 mul64 8.79×、Argon2id mul64 15.71×）。泄漏量化的 baseline 是平均类信息论指标（Shannon 熵、互信息、最大泄漏）：互信息与最大泄漏都只给"所有观测上的平均泄漏"，掩盖低概率高泄漏事件（如 32-bit 均匀秘密下 x=0 触发 y₁ 泄漏全部 32 bit，互信息仅 7.786×10⁻⁹、最大泄漏恒为 1 且与输入分布无关），无法提供安全实践者需要的概率界；且这些方法用 cache/控制流等通道特设的 bespoke 模型，难以适配新通道。
  - baseline 全栈执行例子（cio 缓解 Chacha20-Poly1305 mul64 的一次执行）：算法层——Libsodium 二进制中每条 64-bit MUL，cio 编译 pass 把 (a×b) 变换为等价无泄漏序列（零扩展→第 33 位置 1→乘法→取低 64 位），使乘法结果与操作数中 0/1 的存在无关、硬件 zero-skip 快速路径永不触发；系统框架层——论文未明确说明（无 Serving/OS 层，直接执行二进制）；编译框架层——cio 为对已编译 Libsodium 二进制做指令级重写的二进制码变换 pass（每指令平均多 3–4 条指令，总程序开销 2.31×）；kernel调度层——变换后指令流在 CPU 上顺序执行，硬件乘法器对每对操作数都走慢速路径（zero-skip 快速路径永不命中）；硬件架构层——CPU 实现 zero-skip（MUL 操作数含 0/1 走快速 µobs，否则慢速 µobs），cio 保证操作数永不含不安全值，故 µobs 恒定、时序不随秘密变化，零泄漏但每乘法付出固定性能惩罚。痛点：防御者被迫在"绝对零泄漏+高开销"与"平均泄漏指标无法给出概率保证"之间二选一。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = Helium 三部分框架：(1) 采用 pointwise maximal leakage（PML，逐观测泄漏 ℓ(y)=log max_{x} P_{X|Y=y}(x)/P_X(x)）+ tail-bound 保证 P_Y[ℓ(Y)≤ε]≥1−δ——把"泄漏"从单个平均值变成带概率的分布，对应解决"平均指标掩盖低概率高泄漏事件"（优化 2 中 y₁ 泄漏 32 bit、y₂ 泄漏 3.36×10⁻¹⁰，PML 都能刻画而互信息=7.8×10⁻⁹ 无法）与"无法给出概率界"（tail-bound 直接给 ε,δ，可解释的"泄漏≤ε 的概率≥1−δ"）；(2) µobs functions——把硬件数据相关优化建模为"不安全操作数→可观测执行 µobs"的抽象约束公式集（zero-skip/digit-serial/bit-serial），比硬件模式（DIT/DOIT 只标不安全指令/操作数对）多一层"把操作数划分为 µobs 等价类"的信息，通用、可组合、适配任意新通道，对应解决"bespoke 通道模型不可泛化"；(3) Tracer（TracerSym 符号执行+模型计数精确 / TracerSim Monte Carlo+保守统计界可扩展）——自动计算程序级 µtrace 概率分布，对应解决"零泄漏缓解一刀切高开销"：Helium 输出 (ε,δ) 让程序员判断"是否愿意为省 2.31×（mul64）/3.37×（cs32）开销承担 P[ℓ≤0.0004]≥0.9997 的泄漏"，或只缓解泄漏重的函数（Ed25519 中只保护 sc25519_reduce/ge25519_scalarmult_base，避免 8.79× 全量开销）。关键洞见：改进性能的数据相关优化不必然降低安全性（SVG 卷积下 digit-serial 性能更好且 PML=0，而 Poly1305 下 digit-serial 泄漏高，P[ℓ≤0.97]≥0.51）——必须程序×微架构成对评估，这正是 baseline 平均指标与通道特设模型做不到的。
  - 全栈执行例子（Helium 评估 Chacha20-Poly1305 mul64，从算法到硬件）：算法层——PML 定义逐观测泄漏并构造 tail-bound（ε=可容忍划分中概率最低 µtrace（ε-µtrace）的 PML，1−δ=可容忍 µtrace 概率和）；系统框架层——论文未明确说明（Tracer 直接分析预编译 Libsodium 1.0.18-RELEASE 二进制，无 OS/Serving 运行时）；编译框架层——TracerSym 构建在 Angr 符号执行引擎上（对二进制插桩 µobs 约束并做模型计数，等价于符号化二进制分析），TracerSim 用 Intel Pin 动态插桩；kernel调度层——Pin 逐 trial 执行二进制并记录每条动态 MUL 的操作数值（Pin 插桩工具拦截 transponder 指令，µobs 由操作数经 µobs function 计算，Chacha20-Poly1305 mul64 共 72 条动态插桩指令、每 trial 0.4s），10,000 trials 估计 µtrace 频率；硬件架构层——µobs functions 抽象建模 CPU 的 zero-skip 等数据相关优化（f^{µobs}_{MUL}：操作数含 0/1→快速 µobs，否则慢速 µobs），µtrace 即秘密 key 在建模微架构上逐 MUL 的 µobs 序列；观测端——TracerSim 两轮采样（N₁=10,000 定 ε、N₂=10,000 定 δ），mul64 仅见单一 µtrace ⇒ Rule of Three 保守估计未观测 µtrace 概率 <3/N=0.0003 ⇒ 保证 P[ℓ≤0.0004]≥0.9997（Clopper-Pearson 95% 置信）。输出 = (ε=0.0004 bits, δ=0.0003) 的 tail-bound：程序以 ≥0.9997 概率每观测泄漏 ≤0.0004 bits，程序员据此可安全省去 cio 的 2.31× 开销；同理 cs32 得 P[ℓ≤0.0062]≥0.9947（省 3.37×）、cs64 得 P[ℓ≤2.1461]≥0.9552（建议保留缓解），Ed25519/Argon2id 泄漏重则仍须缓解。
