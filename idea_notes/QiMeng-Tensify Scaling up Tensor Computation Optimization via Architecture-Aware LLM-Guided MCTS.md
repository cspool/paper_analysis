## QiMeng-Tensify Scaling up Tensor Computation Optimization via Architecture-Aware LLM-Guided MCTS

- baseline方法是什么？
  两类主流 baseline：(1) 手工专家优化——PyTorch eager、TensorRT/TensorRT-LLM、Triton、FlashAttention 系列，依赖专家逐算子手写 CUDA/Triton kernel，labor-intensive、难以跟上模型迭代（动态控制流、上百上千算子）。(2) 探索式自动调优编译框架——TVM/Ansor/TensorIR（MetaSchedule）、Welder、Mirage、Reasoning Compiler：定义基于调度规则的变换空间再搜索最优实现，但规则应用策略被硬编码（Table I：TVM 对"有数据复用且可融合"的子图静态选择 Tiling+Fusion）、或受模板限制（Mirage 依赖 CUTLASS 模板库/手工 CUDA/Triton 模板、block 级融合空间 <1024，无法 thread 级融合两个非 elementwise 算子），因此对 LLM 的大规模计算图（如 Falcon-7B 的 GatedMLP，含 3 个 GEMM + SiLU + mul 及动态控制流）无法覆盖。全栈执行例子（GatedMLP 子图）：算法pipeline——GatedMLP 计算 O = SiLU(X·W1) ⊗ (X·W2)，由 X 派生两条 GEMM 路径后 elementwise 合并（模型 Falcon-7B 的 GatedMLP block）；系统框架——PyTorch/推理框架按算子图逐节点下发执行；编译框架——TVM MetaSchedule 把图切为两个子图（融合 matmul+SiLU+mul，空间 >1e10 但错过全融合机会），或 Mirage 用模板在 block 级融合全部算子（空间 <1024，参数受限）；kernel调度——生成 2 个（或 1 个）CUDA kernel，中间结果经 O1/O2/O3 中间 buffer 多次全局内存往返，SiLU 子算子各为独立 kernel 增加 launch 开销；硬件架构——A100/H100 CUDA core（FP32）或 TensorCore（FP16）执行，寄存器/共享内存/L2 未按架构特点利用。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  两个核心设计直接对应两个痛点：(1) 针对"变换空间受限"——把张量计算图优化形式化为无约束 MDP（状态 S(G,n) 图+逆拓扑序调度节点、动作 A(r,p) 规则+参数、转移 T 按 pattern/condition 改写、MDP 目标搜索 policy space π 而非单条手写规则序列），用 7 条参数化调度规则（MultiLevelTiling/AutoInline/ParallelizeVectorizeUnroll/CrossThreadReduction/ComputeAtLocation/AutoBind/InlineConstantScalar）做任意顺序组合的图变换，把空间量级扩大几个数量级；(2) 针对"搜索算法低效"——architecture-aware LLM-guided MCTS：LLM（gpt-5-preview）根据含硬件感知 learned principles 的自适应 prompt 生成 7 规则先验概率分布，注入 Selection（Gumbel-augmented 分数 a*=argmax[g(s,a)+π(s,a)+σ·Q(s,a)]，g 保探索）与 Expansion，Simulation 用 XGBoost cost model + 邻域局部搜索做细粒度参数规格并真机测量回传奖励，Backpropagation 移动平均更新 Q；离线 Prior Adaptation 从 7 个代表子图 12,500 次测量蒸馏自然语言启发式（A100 偏 memory-centric 规则 AutoInline/ComputeAtLocation 降寄存器压力/L2 局部性，H100 偏 compute-centric 规则 MultiLevelTiling/ParallelizeVectorizeUnroll/CrossThreadReduction 利用更大寄存器文件与更高 TensorCore 吞吐）。全栈执行例子（GatedMLP，对应 baseline 同路径）：算法pipeline——同一 GatedMLP 定义 O = SiLU(X·W1) ⊗ (X·W2)；系统框架——论文未明确说明（端到端 LLM 评估在 Chameleon-7B/LLaMA3-8B/GPT-3-7B-LoRA/nGPT-1B 上以 PyTorch 为宿主测推理延迟，batch 1/8、seq 4096）；编译框架——TensorIR 初始 IR → MDP 状态化 → LLM-guided MCTS：LLM 识别 SiLU 可融合（SiLU(x)=x/(1+e^-x)）→ AutoInline 融合 SiLU 子算子为单 block；识别 GEMM1/GEMM2 共享 X → MultiLevelTiling+ComputeAtLocation 在共享 (i0,j0,k0) tiling loop 下融合双 GEMM；compute_at(SiLU, GEMM1)；最终把 MUL 提升进 GEMM2 reduction loop → 全融合单 kernel（S0→S5）；kernel调度——输出单个全融合 CUDA kernel，无中间 buffer、无 kernel launch 开销、多级 tiling 重叠 global-to-shared 异步拷贝，SiLU/mul 融入 GEMM2 reduction 循环避免冗余内存写；硬件架构——真机执行反馈（SM Efficiency、Shared Utilization、Achieved Occupancy、Instructions per Warp、Tensor Precision FU Utilization、Warp Execution Efficiency 等指标）回传 MCTS，离线 prompt 自进化把规则选择对齐目标架构（A100 记忆优先/H100 计算优先），GatedMLP 最终 kernel 比 TVM MetaSchedule 快 2.80×、比 Mirage 快 1.47×。
