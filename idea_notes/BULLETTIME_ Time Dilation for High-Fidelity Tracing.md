## BULLETTIME: Time Dilation for High-Fidelity Tracing

- baseline方法是什么？
  - Baseline 是"直接落盘型"tracing 框架：细粒度访存 trace 产生率远超存储带宽（单线程每 20 条指令 1 次访存即超过论文 SATA SSD 带宽，真实 benchmark 每 3 条指令 1 次访存，且数据率随线程数线性增长），框架被迫频繁同步 flush，I/O 延迟 bursty 且跨线程不对称（只插桩内存指令时，访存密集线程被拖慢、计算密集线程几乎不受影响），造成应用线程之间、应用与系统守护线程（khugepaged 等，不受 tracing 拖慢）之间的操作重排。重排引发两类行为污染：(1) 内存连续性研究——tracing 框架自身分配/释放内存（内核 page cache 反复分配 4KB 页碎片化物理内存）直接改变虚拟-物理映射；延迟使 khugepaged 更早、更频繁地折叠大页，页大小分布从 Untraced 的 128–512KB 集中变成 4KB 与 >1MB 的双峰；(2) 同步研究——只 trace 内存操作使 memops() 相对 computeops() 不成比例变慢，改变锁竞争结果（Table I 中 interesting() 可能从 50% 概率变为永不执行）。具体 baseline 实现：Disk-Traced（异步 write() 落盘，主流做法）与 DynamoRIO drmemtrace（LZ4 压缩）；Empty-Traced（只插桩不落盘）用于隔离插桩开销与 I/O 开销。低开销硬件方案（Intel PT、Arm CoreSight、HMTT）以牺牲 trace 完整性换低开销，不适用于需要完整 trace 的研究。
  - baseline 全栈执行例子（Memcached 内存连续性研究）：应用线程执行指令 → Pin 对每条访存生成 trace 记录 → 2MB 线程 buffer 满触发 flush → 异步 write() 经内核 page cache 落 SATA SSD（带宽 0.4–0.6 GB/s vs 数据产生率 20–25 GB/s）→ 该线程被 I/O 停顿拖慢而其他线程继续 → 线程间操作重排 + 总运行时间变长 → khugepaged 更频繁把普通页折叠为 2MB 大页 → 最终页大小分布偏离 Untraced（Disk-Traced Misplaced Memory 平均 35.49%、MemA 43.12%、MemDY 61.29%；DynamoRIO MemA 94.62%，几乎全部 ≤16KB 页）。算法层：无模型推理（Llama/PageRank/Memcached 为被测负载）；系统框架层：Pin 3.30 / DynamoRIO 二进制插桩框架；编译框架层：论文未明确说明（无编译器改造）；kernel 调度层：trace buffer flush 与异步 write() 即运行时 I/O 路径，无延迟均衡机制；硬件架构层：商用 x86 实机（i7-8700 + SATA SSD），无模拟器。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = key state/key operation 正确性模型 + time dilation 运行时（Algorithm 1 + Pin 内 Controller + Pin 外 Buffer-Driven Delay Module 与 Sleep Dilation Kernel Module + 可选 zstd 压缩）。(1) 满足 C1（框架不得修改 key state）：trace I/O 走 O_DIRECT 绕过 page cache（消除 4KB 页碎片）、内部 buffer 用 hugetlbfs 2MB 大页并远离应用分配、插桩锁仅在首次遇到代码块时短暂获取且不触碰应用 key state（如 Memcached hash 表）——对应"框架自身分配破坏连续性/注入同步操作"缺陷。(2) 满足 C2（key operation 顺序保持）：time dilation 把各线程"tracing 延迟 : 执行进度"比值按最慢线程拉平——应用线程经 Buffer-Driven Delay Module 在 buffer 填满事件注入延迟（EWMA 窗口 5s、衰减 0.5 跟踪 progress=按 IPC 加权的指令数，无需逐操作跟踪）；内核守护线程经 Sleep Dilation Kernel Module（kprobes 插桩 schedule_timeout/hrtimer_nanosleep，仅 TASK_INTERRUPTIBLE）延长睡眠、按最慢线程减速因子放慢 khugepaged——对应"延迟不对称导致操作重排、守护线程超比例运行"缺陷。(3) 窗口化（L>1）把重排限制在单窗口内，用可控近似换取远低于 lockstep 的开销。(4) zstd -7 在线压缩以空闲 CPU 换 I/O，抵消延迟注入拉长的运行时间——对应"行为保真 vs 运行时间"的代价缺陷。
  - 论文方法全栈执行例子（同一 Memcached 连续性研究）：应用线程执行指令 → Pin 记录访存 trace 进 2MB hugetlbfs 线程 buffer → buffer 满触发 I/O 事件 → Controller 进程经共享内存 + 命名管道接管落盘（O_DIRECT 直写 SATA SSD，不污染 page cache），同时 EWMA 更新每线程 progress/delay → 计算各线程 progress-to-delay 比值并识别最慢线程 → 对较快线程在下次 buffer 填满时注入延迟使比值匹配 → Controller 定期经内核模块放大 khugepaged 等守护线程的 sleep 时长，使其节奏与最慢应用线程一致 → 结束时页大小 CDF 与 Untraced 对齐。结果：Misplaced Memory 平均 8.89%（BT-Comp 6.25%），比 Disk-Traced 准 4×、比 DynamoRIO 准 6.4×；Memcached 读-写同步研究 GET:UPDATE 完成数比值对所有 item 尺寸保持在 Untraced 的 10% 内（Disk-Traced 最高偏离 25×，摘要称 20×），GET/UPDATE 延迟差最接近 Untraced；运行时间代价平均 +35%（最高约 58–60%），BT-Comp 压缩后运行时间改善 >2× 且精度无损。算法层：无模型推理；系统框架层：Pin 3.30 + 独立 Controller 进程 + Linux 内核模块（kprobes）；编译框架层：论文未明确说明；kernel 调度层：EWMA 驱动的线程延迟注入与内核睡眠膨胀即运行时调度核心；硬件架构层：商用 x86 实机评估，无 RTL/模拟器。
