## From Lab to Fleet: Building and Deploying a Practical Rowhammer Defense in Cloud SoCs

- baseline方法是什么？
  - Baseline 是学术界两类 Rowhammer 防御（论文表 I 归纳 14 个方案 + 论文在 RHSim 中实现对比的 7 个：BlockHammer、DREAM-R、Graphene、Hydra、PARA/PRA、PRAC、RRS）：(1) 跟踪类（tracking）——用计数器识别"hot"行，如 Graphene 用 Misra-Gries 完整实现（每个 bank 数百项计数器表 + 支持查最低计数值的 CAM，整个 DDR4 bank 需 2,511 bits/bank，DDR5 因阈值更低更多），ABACuS 用全 rank 单计数器表（计数器到阈值时须跨所有 bank 刷 victim 行、stall 整个 rank 数微秒），BlockHammer 用 hash 计数表 + 对可能 aggressor 行 stall CPU 指令（违反 liveness），Hydra/RRS 把计数状态放 DRAM 或用 row swap（RRS 平均开销 <1% 但有 2.9µs 异常值），START-M/AQUA/CoMeT 用 LLC 或缓存状态也有 eviction 性能尖峰；(2) 采样类（sampling，PARA/PRA/DREAM-R）——每次 row activation 以概率 p 抛硬币采样并按 aggressor 处理，无状态、低成本、无 stall、可灵活适应低阈值，但无法区分受攻击与否，带宽/延迟开销恒定（DREAM-R 用 DRFM 特性降低但仍恒定）。baseline 共同痛点：跟踪类硬件成本不可承受（大 CAM/大 SRAM 违背低硬件成本需求#4）、不灵活（状态量随 rank 数/阈值线性增长，违背灵活性#5）、有性能异常值（违背一致性#2）、stall 破坏系统活性（违背 liveness#3）；采样类恒定高开销（违背需求#1 最小开销），且都缺乏可分析、可配置的安全保证（违背需求#6）。
  - baseline 全栈执行例子（Graphene 式跟踪防御处理一次 row activation）：模型推理算法层 = 论文未明确说明（本域为内存系统安全，非模型推理——输入是云负载 Redis/Memcached/MySQL/Cassandra/SPEC2017/PARSEC 的 DRAM 行激活流）；系统框架层 = 论文未明确说明（负载跑在 Azure Cobalt 200 类似 Arm 云 SoC 全系统上，QEMU+Asim+RHSim 三层仿真框架）；编译框架层 = 论文未明确说明；kernel调度层 = 论文未明确说明（DRAM 行激活由内存控制器接收，无 GPU kernel 概念）；硬件架构层 = 每次 ACT 到达内存控制器 → 在 bank 的大 CAM 计数器表中查行地址 → 命中计数+1，未命中与 spillover 比较替换 → 达到 Rowhammer 阈值时发 DRFM 刷 victim 行。代价：每 bank 数百项 CAM 无法在 DDR5 频率下构建/运行（全 Misra-Gries 会把内存控制器面积放大 ~40×、防御逻辑占 die 面积 96%），且 rank/阈值变化需要过配置。采样类（PARA）同一路径：每次 ACT 抛硬币（p≪1）→ 采样命中即发 DRFM → 无状态但每 32ms refresh window 对 commodity workload 也持续发 DRFM、恒定消耗 DRAM 带宽。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = Sigries，混合方案：light mode 用欠配置的 Misra-Gries（每 sub-bank 仅几十项计数器表）+ heavy mode 用行采样，落点在 Azure Cobalt 200 SoC 内存控制器（首次详细披露的生产级实现）。三个新颖洞察直接对应 baseline 缺陷：(Insight #1) 欠配置的 Misra-Gries 只要 spillover counter 低于阈值仍能阻止所有 Rowhammer 攻击——对应跟踪类"必须巨大 CAM"的痛点：常见情况（无攻击/低强度攻击）下小表足够，无需全尺寸 CAM；(Insight #2) 计数器表不必跟踪整个 bank，可跟踪 sub-bank——k 个 c 项小表比单个 k×c 大表更可实现，进一步压硬件成本（对应需求#4 低成本，SRAM < 内存控制器 10% 面积，而完整 Misra-Gries 是 40×）；(Insight #3) spillover counter 接近阈值作为"可能受攻击"的早期预警，触发该 sub-bank 切换到更重的防御（gatekeeper）——只切被攻击的 sub-bank，其余保持 light mode，把采样类的恒定开销变成"仅攻击时按 sub-bank 局部支付"（对应需求#1 最小开销与 #3 liveness）。另外：随机化 mode transition 时长 + 每 refresh window 粒度 + heavy mode 用 shadow counting 决定回切，使安全保证可量化（worst-case 暴露时间 < 1 小时/年，可配置，对应需求#6 可配置安全）；欠配置表 + 阈值配置化适应不同 rank/DIMM/阈值（对应需求#5 灵活性）；无 stall 无异常值（对应需求#2）。
  - 论文方法全栈执行例子（memcached 负载 + 一次 row activation，通过 Sigries）：模型推理算法层 = 论文未明确说明（输入为云负载的 DRAM 行激活流）；系统框架层 = 论文未明确说明（QEMU 内部 emulator 跑 workload → Asim 内部 cycle-level SoC 模拟器出带时间戳的 memory request trace → RHSim）；编译框架层 = 论文未明确说明；kernel调度层 = 论文未明确说明（内存控制器收到 row activation）；硬件架构层 = 每次 ACT 到达内存控制器 → 按 bank/行地址定位 sub-bank → 在 set-associative SRAM 计数器表中查找：命中则 counter+1，未命中则与 spillover counter 比较（表项计数 ≥ spillover 不变量）替换行地址 → 计数到阈值发 DDR5 DRFM 刷 victim 行、counter 复位、置 lock bit（防止被替换）→ spillover 达阈值-1 时该 sub-bank 切 heavy mode：每次 activation 以 p 采样发 DRFM，用 shadow counting 监控 spillover 饱和率，heavy mode countdown 到期且饱和率低于阈值才切回 light（cutover 一定发生在 refresh window 边界，暴露限于一个 tREFW）→ 期间遵守 DDR5 7.8µs DRFM 速率限制（per-bank DRFM 地址表）。结果：commodity workload 下从不切 heavy mode、零 DRFM 带宽开销、无 stall；decahammer/omni-deca 被 light mode 遏制，megahammer/omni-mega 只让被攻击 sub-bank 切 heavy mode（omni-mega 最坏 6.8% 带宽开销），实现"common case 零开销、攻击时按 sub-bank 局部防御、安全保证可量化可配置"的工业级折中。
