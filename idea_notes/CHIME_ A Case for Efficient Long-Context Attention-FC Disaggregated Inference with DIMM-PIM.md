## CHIME: A Case for Efficient Long-Context Attention-FC Disaggregated Inference with DIMM-PIM

- baseline方法是什么？
  - Baseline 是既有 AFD（Attention-FC Disaggregated）系统与常规 GPU 推理：把 memory-bound 的 decoding Attention 与 KV cache 卸载到加速器（HBM-PIM [NeuPIMs/AttAcc]、GDDR-PIM [CENT/PAPI]、CPU 主机内存 [NEO]），compute-bound 的 FC 留在 GPU，以 sub-batch 调度让两设备的 Attention 与 FC 并行。它们的缺陷：违背论文用 DRM 归纳的 "Liebig's Law"（系统吞吐由加速器带宽/容量较弱一维决定）——HBM-PIM 带宽充足但容量不足（GPT-175B 部署后仅约 310GB 存 KV cache，batch 上限卡死 GPU 利用率，吞吐受 T_cap_hp 限制）；CPU 卸载容量充足但带宽不足（吞吐受 T_bw_cpu 限制）；只扩一维导致另一维成为瓶颈、资源浪费（如给 DGX-A100 的 HBM 装 1×→16× 带宽的 PIM，GPT-175B+OpenR1 吞吐提升 <1%）；且调度缺乏跨设备延迟建模——HBM-PIM 侧延迟恒小于 GPU 侧造成空泡，CPU 侧受干扰不可预测。
  - baseline 全栈执行例子（HBM-PIM AFD 上的一个 decode 请求）：模型推理算法层 = 标准 MHA/GQA attention（Q×K^T→softmax→S×V，逐 head 独立）；系统框架层 = NeuPIMs/AttAcc 式 sub-batch 调度，HBM-PIM 仅存 KV cache，容量 ~310GB 使最大 batch B_hp 限制了 GPU 的 FC 吞吐；编译框架层 = 论文未明确说明；kernel 调度层 = AttAcc 的 HBM3-PIM bank GEMV + buffer softmax 指令流水；硬件架构层 = HBM-PIM bank PU + buffer chip，260.8TB/s 带宽远超需求但容量不足 → 系统吞吐被 T_cap_hp 钳制。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = CHIME：先提出 DRM（Disaggregated Roofline Model），统一建模 GPU 的 FC 吞吐曲线（Line-FC）与加速器的 attention 吞吐曲线（Line-ATTN）及容量线（Line-Cap），得三大推论与 Liebig's Law，据此选择把 PIM 集成进 DIMM（bank-level PU）做加速器：2TB 容量打破 HBM-PIM 容量瓶颈、13.0TB/s 等效带宽打破 CPU 带宽瓶颈、标准 DIMM 接口可插拔扩展（可经 CXL 扩展）、每 GB 成本约为 HBM2e 的 1/6。硬件层 CHIME-PIM 用 bubble-free pipelining（内外部内存总线解耦 + FlashAttention 式 chunked tile 流水 + 满足 N_hc 约束的 head 映射：MHA N_hc=8、GQA-8 N_hc=1）消除分布式 DRAM 芯片间的数据同步开销；用 hybrid-grained re-layout（fine-grained 位级保证元素不跨芯片 + coarse-grained head 级映射）在 rank PU 上 in-flight 完成布局变换，消除布局同步开销。系统层 CHIME-sys 用 rankset-granular 通信计算重叠（rankset=每通道一 rank 的最小独立通信/计算单位，DGX-A100 上 4 ranksets，通信时保留其余 rankset 计算）隐藏 PCIe 通信；用 alignment-predicting scheduling（RFR 预测 GPU 延迟 + 线性模型预测 PIM 延迟 + chunked prefill 微调）对齐两设备执行延迟、消除进度同步空泡。
  - 论文方法全栈执行例子（同一 decode 请求在 CHIME 上）：模型推理算法层 = 同一 MHA/GQA 精确 attention，但改为 FlashAttention 式 chunked tile 计算（per-chunk softmax + streaming 跨 chunk 归一化）；系统框架层 = alignment-predicting 调度组成两个延迟对齐的 sub-batch，2TB KV cache 使平均 batch size 达 GPU/HBM-PIM 的 6.6×，GPU 利用率大幅提升；编译框架层 = 论文未明确说明；kernel 调度层 = PIM 命令流（PIM_WR_R/PIM_LD_SB/PIM_WR_SB/PIM_MAC/PIM_RD_RB）驱动的 score/softmax/context chunk 流水 + 传输中 re-layout + rankset 粒度通信计算重叠；硬件架构层 = 分布式 bank PU（DRAM 工艺）+ buffer chip rank PU（逻辑工艺，softmax/adder/re-layout 单元），标准 DDR 接口不改内存控制器 → 端到端吞吐较 HBM-PIM 最高 5.15×、能量 -40%。
