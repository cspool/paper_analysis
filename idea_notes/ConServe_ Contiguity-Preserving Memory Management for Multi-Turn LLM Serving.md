## ConServe: Contiguity-Preserving Memory Management for Multi-Turn LLM Serving

- baseline方法是什么？
  - Baseline 是 PagedAttention 类 serving 系统与 CUDA VMM 单请求系统的多轮适配：(1) vLLM：初始化把显存切成固定 KV block（16 tokens/block）组成共享池，序列按需取 block、经运行时软件 block table 把逻辑块号翻译为块虚拟地址，硬件页表再翻译到物理帧——双层翻译 + 散页布局；(2) vAttention-Turn：每 turn 一个 request，每 turn 内部 VA 连续，但同一 conversation 的历史跨多个不相邻虚拟区；(3) vAttention-Conv：整个 conversation 一个长期 request，预留 max-context 长度连续 slice，绝大多数空间闲置。共同痛点：多轮复用历史 KV 时，prefill/decode 的访存跳越多个不相邻虚拟页 → TLB 工作集与 page-walk cache 复用距离超容量 → 更多页走查与翻译 stall；block table 查表增加指令与寄存器压力；max-context 预留使并发 conversation 的活跃 KV 区在 VA 上相距很远，NVIDIA TLB 的 16 sub-entries/entry 利用率低（如 4K-token Llama-3-8B 每层约 8 个 2 MB 页，只填满一个 32 MB 覆盖 TLB entry 的 8/16 sub-entries，50% 利用率）。
  - baseline 全栈执行例子（vLLM 多轮 prefill 复用历史 KV，A100）：模型推理算法层 = 同一 attention 计算，KV 放置与寻址不同（论文不改模型算法）；系统框架层 = 连续 batching 调度 + 软件 block table 查表（每次 access 查块指针、算块内偏移、跨块再取下一块）；编译框架层 = 论文未明确说明；kernel 调度层 = FlashInfer-paged 对散页 KV 的 gather 访存（更多更小事务）；硬件架构层 = A100 TLB/页走查（散页扩大 TLB 工作集，长 scoreboard stall 84.64%、eligible warps/cycle 0.718、SM/L2/DRAM 吞吐 −22.4%/−16.7%/−21.1% vs 连续布局，prefill 慢 12–24%，多轮累积至 1.75×）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = ConServe conversation 级连续 VA slice 分配器：(1) 每 conversation 一个连续 VA slice、layer-major 分段、base+offset 纯算术寻址（VA(t,l)=base+seg_off[l]+t×B_layer），消除软件 block table——对应 vLLM 双层翻译与散页 gather 的缺陷；(2) slice 大小按"live tokens + Q×k"弹性增长（Q 取 ShareGPT 每轮 token 的 r=80% 分位数、k=8，η>0.90 触发，R_next=max(⌈γR⌉, target 对齐值)，γ=1.5），不按 max-context 预留——对应 vAttention-Conv 最坏情况预留导致 VA 上活跃区相距远、TLB sub-entry 利用率低的缺陷（batch 内活跃 KV 页保持紧凑，attention 只暴露 B×1 个区域而非 B×k 或 B 个巨大段）；(3) copy-free 弹性 resize：layer ℓ 完成后即在新 slice 该层段 cuMemMap 同一物理页（数据不搬）、与剩余层计算重叠、迭代边界切换 base、旧 slice 隔离 + 批量延迟 unmap/TLB invalidation + dual-index free-list 合并碎片——对应 resize 的 stop-the-world 与 VA 碎片缺陷（94.7% resize 全隐藏、99% 暴露 ≤1.5 ms；不与计算重叠时每次尖峰 4–18 ms）；(4) 跨 turn 连续——对应 vAttention-Turn 历史跨多虚拟区、翻译工作集随 B×k 放大的缺陷。
  - 论文方法全栈执行例子（同一 conversation 新 turn，ConServe/A100）：模型推理算法层 = 论文未明确说明（不改模型算法，仅 KV 虚拟布局）；系统框架层 = 调度器组 micro-batch → runtime 从 48-bit VA arena 为 conversation 取连续 slice（best-fit），kernel 经 descriptor 得 base 后 base+offset 直接寻址，token 边界按需 cuMemCreate(2 MB)/cuMemMap/cuMemSetAccess 与上一迭代重叠，η>0.90 时层间重叠 copy-free remap、迭代边界切换 base，旧 slice PENDING_UNMAP 批量延迟回收；编译框架层 = 论文未明确说明；kernel 调度层 = variable-length attention kernel 连续流式读 KV（对齐合并事务、少数 TLB 项与 page-walk cache 行）；硬件架构层 = A100 TLB 16 sub-entries 高利用率（活跃 KV 页紧凑）、翻译 stall 下降，SM/L2/DRAM 吞吐回升。结果：TTFT −64.1%~−74.4% (vLLM) / −31.4%~−43.4% (vAttention-Turn) / −8.3%~−19.1% (vAttention-Conv)；decode 吞吐 +19.4%~25.6% / +6.1%~9.5% / +4.2%~6.1%；离线端到端吞吐 +17.7%~35.1% / +8.6%~15.6% / +7.2%~12.1%；SLO attainment +11%~19% / +7%~9% / +3.2%~4.9%（增益随模型 KV footprint 与 batch 增大）。
