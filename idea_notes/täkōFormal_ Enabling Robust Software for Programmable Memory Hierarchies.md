## täkōFormal: Enabling Robust Software for Programmable Memory Hierarchies

- baseline方法是什么？
  - Baseline 是 täkō 可编程内存层级（PMH）本身（原 täkō 论文 [55]）：用户为虚拟地址范围注册 OnMiss/OnEvict/OnWB 回调，由 cache miss/eviction/writeback 触发，在 tile 的 engine 上以独立线程语义运行（与 core 程序线程并行），支持无主存背衬的 phantom addresses 与 FlushRange 同步原语。其痛点：① 硬件-软件接口被彻底改变——cache 的 prefetching 与替换策略这些以往隐藏的硬件细节直接决定程序结果（如 phantom 地址在两次访问间被 evict 会让之前的写被完全丢弃，图 2），程序行为反直觉、难写难懂；② 无形式化接口——回调可与 core 线程任意交错引发 race，程序员必须理解缓存/替换/prefetch 细节才能理解程序行为，且 täkō 只有 closed-source 模拟器、无实现，其他研究者无法验证实现正确性；③ 传统 MCM（SC、TSO、release consistency、C11）没有 phantom 地址与 cache 事件回调的概念，无法刻画 täkō 语义。IMO/EcMon 等 cache-event trap 方案有 function call 语义（打断 core 线程执行 handler），而 täkō 回调是 thread 语义（专用 engine 并行执行），冲突访问会成 race，更需要形式化。
  - baseline 全栈执行例子：core 线程写 phantom 地址 [x]（指令 [x]←1）→ cache miss → engine 运行 OnMiss 回调（从引擎局部状态计算 [x] 内容并填 cache）→ 之后若 cache 因替换策略/预取在 (i1) 与 (i2) 之间 evict [x]，[x] 再次 miss 触发第二次 OnMiss → 因 phantom 地址无主存背衬，(i1) 写入的值被完全丢弃，(i2) r1←[x] 读到 OnMiss 生成的值而非 (i1) 写的值；OnWB 回调还可并发写普通地址 [y]，与 core 线程读 [y] 竞争（无 FlushRange 时 racy）。算法层/系统框架层/编译框架层：论文未明确说明（täkōFormal 不涉及这些层）；kernel 调度层：论文未明确说明；硬件架构层：tiled chip（core+L1/私有 L2/共享 L3 分片/engine），cache 事件触发回调、phantom 地址、FlushRange，prefetching/替换策略任意。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法：täkōFormal 为 täkō 建立 ISA 级 MCM 并机器检查证明其 soundness。(1) ISA 级 MCM（图 6）——新增事件（Rcb/Wcb/RMWcb/Ms/Me/Es/Ee/Fl）与关系（cbo 单地址回调全序、viscb phantom 可见性、vf/ef/eb 扩展 hb），以及前缀封闭公理：VfWf/EbWf 强制 phantom 读/写前必有 OnMiss、Fl 前必有 eviction；CboVal+EvDirty/WbDirty 强制回调值对应与 OnEvict/OnWB dirty bit 对应；OEInt/OMInt/MeInt/EeInt 强制 OnMiss 与 eviction 交替；Vis/VisCb+扩展 hb 强制回调引发的普通地址写可见性并禁止 r1=2,r2=0 类结果；race 定义刻画回调与 core 线程冲突。对应解决"无形式化接口、行为反直觉"——程序员只需检查执行图满足公理即可判断程序结果/race，无需理解微架构细节。(2) 参数化 Dafny operational model——分层状态机（Core+L1/Engine+L1/L2/L3 slice/Memory/Network）+ inclusive cache + 分层 directory MSI（HieraGen proxy L2）+ environmental transitions 过近似 prefetching/替换策略/回调任意触发 + 参数化 cache 容量/core 数/NoC/映射。对应解决"架构师要改设计"——prefetching/替换/NoC 参数可变而不破坏与 MCM 的一致性。(3) 端到端机器检查 soundness 证明——ISM 构建部分执行图 + 归纳（inductive invariant，119 clauses/61K LoC）+ refinement（abs 抽象证明 operational trace 映射到 ISM 迁移）；前缀封闭性保证每个公理可用归纳证明。对应解决"无实现可验证、传统 MCM 无法刻画 täkō"——对任意程序证明实现模型所有执行都被 MCM 允许，其他人可据此验证 täkō 实现。(4) Alloy 编码全部公理与 litmus tests（test_paper_ex/test_mp/test_mp_rmw/test_mp_rmwcb/test_icb_sb/test_wbrace/test_wbflush/test_phir/test_phinr/test_hatsr/test_hatsnr），案例研究 HATS 图遍历（hatsR racy → hatsNR 在 OnEvict 只记录合法边后 race-free）展示用 MCM 写正确且高性能 täkō 程序的流程。
  - 论文方法全栈执行例子：同一 phantom 地址程序——core 执行 [x]←1 与 r1←[x]：程序员把执行建模为执行图：Wcb([x],1)（(i1)）、Rcb([x])（(i2)），任何 Rcb 前必须有 Me（VfWf），两次 Me 间必须有 E（OEInt），OnMiss 生成值由 viscb/CboVal 约束，写与 eviction 的 dirty bit 对应由 EvDirty/WbDirty 约束；若 (i2) 读到 OnMiss 生成的 2 而中间无 eviction，执行图违反上述公理从而被 MCM 禁止（对应"值被丢弃"的基线反直觉结果被形式化排除）；OnWB 写普通地址 [y] 时，vf/eb 与 cbo 扩展的 hb + Vis 公理保证 (i5) 写 [y] 在 (i4) 读 [y] 前完成（r1=2,r2=0 被禁）。验证：litmus test 编码进 Alloy（run_alloy_tests.sh 输出 allowed/forbidden/racy 结果），实现侧由 Dafny operational model（Core 发 GetS→Network 无序投递→L3 回 Data→engine 经 FIFO 收 OnMiss 请求运行回调，环境迁移可任意插入 eviction/prefetch 序列）经 ISM+归纳+refinement 机器检查证明与 MCM 一致（run_dafny_verification.sh 输出证明通过）。算法层/系统框架层/编译框架层：论文未明确说明；kernel 调度层：论文未明确说明；硬件架构层：täkō 分层状态机（含 MSI 一致性、Network、engine 回调调度）+ ISA 级 MCM 公理层，公理约束硬件任意执行的合法性。
