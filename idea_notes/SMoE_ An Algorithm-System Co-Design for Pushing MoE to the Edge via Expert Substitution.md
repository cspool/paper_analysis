## SMoE: An Algorithm-System Co-Design for Pushing MoE to the Edge via Expert Substitution

- baseline方法是什么？
  - baseline 为边缘 GPU 显存受限下部署 fine-grained MoE LLM 的两类 online expert offloading 方法：①预取类（MoE-infinity、HybriMoE、ProMoE）：把 CPU 内存中的激活专家经 PCIe 预取/加载到 GPU 或直接在 CPU 计算，用加载与计算的重叠隐藏传输延迟；②剪枝类（expert pruning/skipping）：直接丢弃部分专家以减少加载量；另有 llama.cpp（纯 CPU 推理）与 DeepSpeed（layer-wise 整层加载、静态缓存）。这些方法对激活专家一视同仁地调度，未利用 gate score 反映的专家重要性差异。全栈执行例子（预取类，一个 token 一层）：router 选出 top-k 激活专家 → GPU 已驻留者直接计算，其余全部进入 CPU→GPU PCIe 加载队列或 CPU 计算 → 每个非驻留专家都产生一次 PCIe 传输（PCIe 比 GPU 计算慢 10–100×；Qwen/A6000 下 low-score 专家加载占 TPOT 42%、top-score 加载 29%、GPU 计算 29%）或 CPU 计算（比 GPU 慢约 1 个数量级）→ 计算与加载流水线重叠但受 PCIe 带宽限制，无法全部隐藏 → 逐 token 重复，TPOT 被非驻留专家主导；剪枝类则因缺失专家计算而精度下降。编译框架、kernel 调度、硬件架构、芯片设计层次：论文未明确说明。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文提出第三类方法 expert substitution（SMoE 调度器）。关键观察（Motivation，Fig.5）：fine-grained MoE（DeepSeekMoE/Qwen2-57B-A14B/XVERSE-MoE）中激活专家 gate score 高度不均匀——只有少数 top-score 专家显著影响输出，其余 low-score 专家分数与未激活专家相当（routing noise + load balancing 使 tail expert 行为趋同、信号冗余）。据此将 low-score 激活专家替换为 GPU 中已缓存、score 落在 [(1−α)S_{k+1}, S_{k+1}] 的近似未激活专家，直接消除这些专家的 PCIe 加载与 CPU 计算（解决 baseline 缺陷：表 I 中 low-score 加载恰是 TPOT 最大瓶颈）。配套设计一一对应 baseline 缺陷：score-aware eviction 保留高分专家、扩大替换候选池 E_s（对应预取类缓存策略对替换无感知）；只预取 top-score 专家、命中率 82%（95% 概率 active），把预取量从 3 降到 1、大幅降低 PCIe 带宽压力（对应预取类盲目预取全部缺失专家造成的带宽瓶颈）；CPU-assisted 双指针调度（Algorithm 2）兜底处理既不能替换也不能预取的专家（对应预取失败/预测错误场景）。全栈执行例子（一个 token 一层，对比 baseline）：gate 输出 score → expert-cache router 按 α 阈值分 top/low-score（score > (1+α)S_{k+1} 为 top）→ low-score 被 GPU 驻留近似专家替换（GPU 命中率 2/5→4/5，预取量 3→1）→ 剩余未命中专家按 CPU-assisted 调度分派 PCIe 加载或 CPU 计算（双指针平衡 T_load/T_CPU）→ GPU 直接计算替换后专家集合 + 预取下一层 top-score 专家（与当前层计算重叠）→ TPOT 相对最优 baseline 降 24%（batch=1）/35%（batch=3）、S3 达 48%、GPU 命中率 >60%，α≤0.35 时精度无损（部分数据集因抑制 low-score 专家的 noisy activation 反而提升，表 VI 手动降分验证）。编译框架、kernel 调度、硬件架构、芯片设计层次：论文未明确说明。
