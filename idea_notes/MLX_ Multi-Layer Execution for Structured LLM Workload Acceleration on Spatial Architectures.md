## MLX: Multi-Layer Execution for Structured LLM Workload Acceleration on Spatial Architectures

- baseline方法是什么？
  - Baseline 是 GPU（NVIDIA H100/AGX Orin/Jetson Xavier/RTX-3090）上的稠密 Transformer 推理与两类先验结构化稀疏方法：(1) 稠密 Transformer：自注意力 O(N²D) 计算 + O(N²) 数据流量，线性投影 O(ND²) 计算 + O(D²) 参数存储，quadratic attention 与内存搬运主导端到端延迟与能量；(2) 先验 butterfly 稀疏（Monarch/butterfly factorization）：把稠密权重近似为全局 log2 n 个块对角矩阵因子的乘积（BSMM，O(n²log n)），但大 d 时全局分解收敛难、近似误差大；(3) 先验 FFT-based 注意力（FNet 式 2D-FFT token mixing，O(ND log N)）：去除内容相关的 pairwise token 交互，精度受损，且不兼容 prefill/decode 的 cache 增量更新。核心痛点（论文 profiling 揭示）：FFT 注意力理论上削减 >10× 算术量，但 GPU 上端到端加速远小（AGX Orin batch 64 仅 3.77×@8K / 2.56×@512）；roofline 分析显示蝴蝶 kernel 运算强度低（bandwidth-bound）却仍远低于 CUDA 带宽 roofline——多级 strided/shuffle 数据重排破坏局部性（高 cache miss）+ stage-wise 依赖与 GPU 批量同步、tile 规则执行错配（执行单元不匹配），蝴蝶 kernel 只能跑 CUDA core 而非 TensorCore。
  - Baseline 全栈执行例子（一次 Llama2-7B prefill，N=8K，H100，全局 butterfly / FNet 式方法）：算法层：权重全局蝴蝶分解（Monarch 式，O(D log D) 参数）替换 QKV/FFN 投影，注意力替换为 2D-FFT token mixing；系统框架层：PyTorch 前向（未与 FlashAttention 融合），KV cache 无法增量压缩；编译框架层：论文未明确说明（cuFFT/PyTorch 算子层）；kernel调度层：蝴蝶/FFT kernel 回退到 CUDA cores 执行，多级 strided/shuffle 访问导致高 cache miss、带宽利用率低，attention 与投影分阶段同步执行、中间结果进出全局内存；硬件架构层：TensorCore 闲置（蝴蝶稀疏不支持），CUDA core 带宽受限，FLOP 削减（>10×）只转化为 2.56-3.77× 实际加速。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：MLX = 算法-架构协同设计，两大算法创新 + 一套空间执行抽象。(1) **语义感知傅里叶压缩（FFT-CMP）**：利用 LLM 层沿序列维的语义频率局部性（浅层高频、深层低频），按每层 chunk 长度 L 分块 FFT、截断保留前 sL 个低频系数、iFFT 缩短 token 序列（prefill O(N²D)→O(s²N²D)），decode 用 append-only chunk-granular 压缩 KV cache——对应解决 FNet 式全局 2D-FFT 的精度损失（保留信息丰富的低频分量）与 KV-cache 不兼容问题。(2) **分层蝴蝶分解（hierarchical BSMM）**：只在 B×B 局部 tile 内应用蝴蝶因子，复杂度 O(D²/B·log B) 而非 O(D log D)——对应解决全局蝴蝶分解在大 d 时收敛难、误差大的问题，B 提供可调精度-效率旋钮。(3) **Multi-Layer Execution（MLX）硬件抽象**：把 FFT/BSMM/block MM/SWA 等结构化算子统一形式化为 Closed Dependency Components（CDC）+ 前向分层依赖（式3），用 **tagged-block 指令**（每层一个可复用短指令块+loop trip count）在 **skip-hop 网格**（hop-encoded 有界跳转路由）上**折叠**深层算子为紧凑阵列上的跨层流水，**解耦 compute/transfer/memory 流水** + tag 级粗粒度仲裁重叠各层——对应解决 GPU 上蝴蝶算子的"stage-wise 依赖 vs 批量同步"错配、数据重排破坏局部性、执行单元不匹配与 kernel launch 开销：跨层依赖不再往返全局内存，stride 交换映射为 1-2 跳片上路由，深层次逻辑深度与物理阵列大小解耦。
  - 论文方法全栈执行例子（同一次 Llama2-7B prefill，N=8K，D=4096，MLX 12nm 芯片）：算法层：QKV/FFN 投影权重按 B=32 tile 分层蝴蝶分解（tile 内 stride±2/±4/±8 蝴蝶因子），Q/K/V 按每层 L 分块做 s=0.5 语义 FFT 压缩（8K→4K token）；系统框架层：RISC-V host controller 发紧凑命令，编译工具链（LLVM-based C compiler + 轻量 "spatial assembler"）把 dataflow 式汇编编成二进制 header 配置 MLX；编译框架层：编译器把每个算子编译成 tagged block（LD 头/COMP 中/XFER 尾的固定布局 + loop trip count），CDC 到 PE 静态放置、跨层路由类由 (Δx,Δy) 参数化，层内静态确定、跨层 tag 级弹性调度；kernel调度层：4×4 网格 PE 以 active-window 内多折叠层重叠执行——一层 LD 从 SIMD-striped scratchpad 取数（列向 lane 对齐序列轴 N 做 BSMM、行向流式隐藏轴 D 做 FFT）、一层 COMP 在 FU 上 FMA、一层 XFER 经 skip-hop 网格按残差 hop 数把部分和路由给 stride 匹配的消费 PE，tag 仲裁（小 tag 优先+round-robin）协调；硬件架构层：蝴蝶层在网格上折叠成连续跨层流水（无全局内存往返），stride=4/8 转 1-2 跳垂直 hop，FP16 最小稳定精度 + 超越函数单元（1/4 SIMD 宽）支持 RMSNorm/位置编码；结果：蝴蝶 kernel 3.1× 加速/3.2× 能量节省（vs Xavier dense TensorCore kernel），端到端 3.2× 加速/3.1× 能量（vs sparsified CUDA），相对先验稀疏加速器最多 5.8×，PE 利用率约 90%，4×4→8×8 网格近线性扩展。
