## NeRArch-Sim: A Unified Simulator for Benchmarking and DSE of Neural Rendering Accelerators

- baseline方法是什么？
  - Baseline 是"一对一专用化"（one-off specialization）的神经渲染加速器研发范式：每个加速器（MLP-based：ICARUS、MetaVRain；grid-based：NeuRex、CICERO、SRender；primitive-based：GSCore、GS Processor）针对单一渲染算法 pipeline 和单一硬件目标手工定制，各自采用不同的场景表示、内存层级、光线采样策略，并在不同的数据集/分辨率/工艺/频率下单独评估（Tab. III），因此既无法公平对比也无法互相移植；其 DSE 方法也过于专化（覆盖各自场景的特定设计目标）且多为专有，难以适配新 pipeline 或新硬件预算。通用 NN 加速器模拟器（论文引 [41][46]，如 Timeloop/Accelergy 类）不支持神经渲染必需的图形学专用算子（ray marching、spatial sampling、hybrid neural-graphics 算子），且其算子与 dataflow 调度面向规则的张量负载。
  - 全栈执行例子（以 grid-based 的 NeuRex 为例）：算法层——Instant-NGP 式 hash grid + MLP、ray marching 体积渲染；系统框架层——Nerfstudio 等框架直接运行原算法，只能给出算法级输出，无法提供硬件可执行视图；编译框架层——论文未明确说明（无自动化 kernel 生成/软硬件映射工具）；kernel 调度层——GPU 上手工编写 hash 查找与 MLP 计算 kernel，按固定张量形状调度，无跨加速器可比口径；硬件架构层——专用 hash-encoding 单元 + 固定 systolic array 的单一 RTL 实现，面积/功耗由该论文自己的流程给出；芯片设计层——论文未明确说明。想换 pipeline（如 3DGS）或换硬件预算（面积/频率）就得全部重做，跨加速器比较只能拼凑各论文各自报告的 FPS/面积/功耗。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：NeRArch-Sim 统一模拟器，核心是"统一分类学驱动的模块化"：(1) 把神经渲染 pipeline 系统分解为四个模块化阶段（Field Sampler→Encoding→Field Computation→Blending），形成有向无环算子图（DAG），据此把软件工作流与硬件同时模块化；(2) 模块化软件工作流：用运行时钩子插桩 Nerfstudio 等框架自动提取算子图（不改原算法），模块化算子库暴露统一接口、按参数区分 pipeline 变体；(3) 模块化硬件加速器：按四阶段分类的 20+ 可复用 SystemC 模块库，HLS 综合 + 全 ASIC post-layout 两级 PPA 表征，SRAM + Ramulator 2.0 DRAM 显式建模；(4) 模块化数据流调度器：三层分解（mapping→operator-level→system-level），mapped IR / operator-scheduled IR 作为层间接口，端到端 PPA 秒级出结果，支持快速 DSE。这直接解决 baseline 的三个缺陷：公平可扩展基准（同一模拟器、统一 taxonomy 下复现 11 个加速器，误差 ≤9.4%）、灵活 DSE（改硬件 JSON 秒级探索 buffer/PE/并行因子，引导新设计最高 1.3× 效率提升）、可移植性（新 pipeline 如 4DGS/Lumina 以 <300 行 C++、2-3 天接入）。
  - 全栈执行例子（同一 NeuRex 在 NeRArch-Sim 中）：算法层——用 `neurex_pipeline(dim)` 经统一接口搭建：UniformSampler + HashEncoding(num_levels=16) + MLP(num_layers=4)，公共属性与扩展参数分离，改精度等参数无需重新插桩；系统框架层——Nerfstudio 插桩版 `ns-eval --enable-trace` 渲染一张图输出 execution_dag.pkl 算子图（函数标识、张量形状/值、调用关系、I/O 数据量）；编译框架层——论文未明确说明传统编译框架（HLS 综合可视为硬件侧"编译"，算子图→映射即软硬件绑定）；kernel 调度层——mapping engine 按分类学把 HashEncoding 算子绑定到 hash 硬件单元、MLP 算子绑定到 systolic array（多候选取最高吞吐、多实例均衡），operator-level scheduler 在模块内排 start_cycle/duration，system-level scheduler 全局编排执行计划；硬件架构层——SystemC 模块经 Catapult HLS→逻辑综合→功耗分析得到该配置面积/功耗，结合 SRAM + Ramulator 2.0 DRAM 时序算出端到端 FPS 与每 SRAM 访存流量；芯片设计层——论文未明确说明（RAM 建模经 Ramulator 时序）。随后只改 icarus/neurex 等 *_config.json（buffer 深度、PE 数、并行因子、SRAM 组/端口）即可秒级重算 PPA 完成 DSE，从而把 baseline 中"一个设计点对应一次完整手工硬件开发"变成"同一框架内参数化探索"。具体证据：GSCore DSE 案例中 SA 搜索五参数 (Culling Conversion Units, Quick Sorting Units, Bitonic Sorting Units, Volume Rendering Cores/VRCs, Buffer sizes)，最优配置 (16,8,4,32,4) 相对原 (4,8,4,64,8) 取得 1.3× energy-delay product 与 1.6× 面积下降（相对穷举 2.8× 加速）；端到端复现 6 个基线加速器（ICARUS/NeuRex/CICERO/GSCore/GBU/Uni-Render）在 Lego 场景面积误差 6.5%、FPS 误差 3.4%、PSNR 误差 2.6%，17 个硬件模块面积/功率误差 4.72%~9.33% 且延迟与全 ASIC flow 完全一致——同一模拟器既当"公平基准尺"又当"DSE 引擎"，正是 baseline 每篇论文各自报数、无法横向比较的直接解药。
