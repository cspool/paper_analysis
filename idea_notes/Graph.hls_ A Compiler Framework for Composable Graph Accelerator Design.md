## Graph.hls: A Compiler Framework for Composable Graph Accelerator Design

- baseline方法是什么？
  - baseline 为现有手工 HLS 图加速框架：ReGraph [9]（HBM 平台 U55C 代表，big-little 异构 pipeline）与 ThunderGP [8]（DRAM 平台 U200 代表，单一统一分区 + 精细顶点缓存）。两者都是把算法、硬件与验证纠缠在单一刚性代码库中：ReGraph 参数散落在 5 个 makefile、21 个头文件、14 个源文件，每个优化（位宽、分区、pipeline 结构）深嵌实现，跨框架无法组合；验证依赖慢速硬件仿真。
  - baseline 全栈执行例子（SSSP 的 32→16-bit 距离位宽优化 on ReGraph）：模型推理算法层 = 静态图上的迭代 SSSP（每次迭代松弛当前 frontier 的所有边，16-bit 距离上限 65535）；系统框架层 = 论文未明确说明（静态图处理，无 serving/调度框架，主机负责加载图与迭代控制）；编译框架层 = ReGraph 手工 HLS C++（无编译器，直接编辑 5 makefiles/21 headers/14 sources）：位宽改动级联 200+ 行跨 10+ 文件——顶点/边属性与消息类型 typedef、HBM packing 位区间重算（src[i]>>4→>>5、URAM 字 a.range 重算）、gather dataflow 每周期处理顶点数调整（邻居 buffer、归约树、scatter 接口）、算法常量 MAX_I 2147483647→32767（初始化/终止/松弛条件）、host 侧分配/填充/解包校验逻辑；kernel调度层 = 手工 HLS pipeline kernel，C-Sim 顺序执行模型无法模拟并发 pipeline（无法建模有限流深度/死锁），只能靠硬件仿真 Co-Sim ~50 分钟/次迭代，定位一个 bug 需多轮"注释掉某个 stage → 重跑仿真 → 二分定位"，共数小时；硬件架构层 = ReGraph 固定 2-class big-little 分区（所有 little pipeline 共享 65,536 目的节点分区，所有 big pipeline 共享 524,288 节点分区），ThunderGP 为单一分区+顶点缓存，GraphLily 为 overlay 重构式处理——三者架构假设互不兼容，想组合 ReGraph 的分区与另一框架的优化必须整体架构重写（>1000 行）；结果：稀疏图上 big pipeline 全部处理同一受限目的集而利用率低，大稠密图上 65,536 节点分区不够且半条 little pipeline 空闲。验证方面：16-bit 转换在小均匀图 graph500-scale19（500K 顶点，直径<1000）上测试通过，但在 LiveJournal（4.8M 顶点，长链使直径>65535）上距离溢出回绕（65540 回绕成 4），错误沿图传播且部分可达顶点因前驱距离等于 MAX 而被当不可达——数据依赖 bug 只能在特定拓扑上触发，C-Sim 又跑不了并发 pipeline，开发者只能靠多次 Co-Sim 盲找。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = Graph.hls：把图加速器设计空间按修改成本组织为三层抽象（L1 图处理常量 / L2 图微架构配置 / L3 图数据流策略），配 GH-Architect 自动生成引擎（DSL→IR→L3 启发式→L1/L2 双向依赖传播→完整 Vitis 工程）与 GH-Scope IR 级验证引擎。对应解决：(1) 对应优化不可组合（Pitfall I）——把位宽（L2）、分区比（L1）、pipeline 分组（L3）提升为一等配置参数，GH-Architect 用 Algorithm 1 的确定性双向约束交集自动解析跨层依赖（forward pass 定硬件可行性、backward pass 定算法正确性，如 PageRank 16-bit 定点把 ~10⁻³ 的贡献舍入为 0 致假收敛、故固定 32-bit），用户声明配置即自动生成全局一致的硬件，位宽修改从 200+ 行跨 10+ 文件降为单行；L3 把 ReGraph 固定 2-class 分区泛化为任意 N-class 分区（每类独立目的集 + 可配置 pipeline 数 + N 个独立 merger），跨框架策略可经配置组合；(2) 对应验证慢（Pitfall II）——GH-Scope 在保留图语义的 IR 级模拟（非 C 数组/for 循环的 C 级模拟），直接指出冲突的源/目的顶点，运行时检测 overflow（16-bit 回绕这类数据依赖 bug 即时报告）与无限循环，并把用户实现与预验证 golden reference 自动对比（cross-SLR 连接、SLR 利用率、FIFO 深度等），平均 301.6× 于 Vitis C-Sim、最高 455,000× 于硬件仿真，把数小时调试循环压到亚秒。
  - 全栈执行例子（PageRank on Alveo U55C、rmat-21-32，L1+L2+L3 全 DSE）：模型推理算法层 = DSL 表达 PageRank（iteration_input 生成边流 → map 读 e.src.rank → reduce(commutative-associative lambda) 聚合 → return as result_node_prop），DSL 为 GAS 超集、map/reduce/filter 组合可表达 Belief Propagation 等不规则数据流（GAS 无法表达）；系统框架层 = 论文未明确说明（静态图处理，主机迭代调用统一 kernel 直到收敛阈值 ε 满足，无 serving 框架）；编译框架层 = GH-Architect：DSL → IR 空间数据流 DAG → L3 启发式按度分布（平均度 ~30、~5% 顶点吸引 60%+ 边）在 3 SLR 的 14 个 pipeline slot 上分组 11 little + 3 big → L1/L2 双向依赖传播（forward：32-bit 下 72-bit URAM 行存 2 值 → 每管道 64 URAM、14×64=896/960（93%）→ L1 max partition 65536；backward：16-bit 定点 delta 2⁻⁸ 舍入致假收敛 → L2 固定 32-bit）→ 生成完整 Vitis 工程（HLS C++ kernel + host + Makefile + system.cfg SLR/HBM 绑定）约 100ms；kernel调度层 = GH-Scope IR 解释器快速验证（R24+PR 8.29s vs C-Sim 1779s，215×），运行时 overflow/无限循环检测 + 与 golden reference 对比，在综合前捕获错误；硬件架构层 = 生成的异构 big-little pipeline（L3 可配置分组、N-class 广义分区替代固定 2-class），Vitis 综合 4–6 小时出 bitstream，FPGA 运行 1–10 分钟/图；L1 分区比 + L2 8-bit 位宽（带宽与片上缓存翻倍）+ L3 异构分组三层互补、super-additive，SSSP 上达 4.48× 平均加速（vs Naive 0.71×、L1-only 1.99×、L1+L2 2.95×、L1+L3 2.52×），PR/CC/SSSP vs ReGraph 平均 2.6×、五算法 vs ThunderGP 平均 1.2× 且覆盖其 OOM 的大图。
