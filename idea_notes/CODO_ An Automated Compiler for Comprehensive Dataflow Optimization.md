## CODO: An Automated Compiler for Comprehensive Dataflow Optimization

- baseline方法是什么？
  - Baseline 是 SOTA FPGA 数据流编译器 + 商用 HLS 工具的数据流原语：(1) ping-pong 派——ScaleHLS（PyTorch→MLIR，仅部分消解 multi-consumer 粗粒度违例）、POM（DSL，靠开发者手动管理数据依赖防违例）、HIDA（DSL，只消粗粒度违例、自动并行化但数据按块处理）：块级双缓冲使消费者须等整块数据写满才开始，长间隔、低重叠、内存翻倍，且对全模型施加同质优化策略；(2) FIFO 派——Allo（可组合 DSL 直接生成 FIFO 空间加速器，但不处理违例→流水线停顿甚至死锁，且无自动调度）、StreamHLS（重排循环+插控制逻辑做单任务部分消解，FIFO 写被推迟到近 8/9 迭代之后→大量流水气泡；MINLP 调度指数爆炸 35s–20min）、StreamTensor（迭代张量类型系统，类型不匹配即回退保守 ping-pong，无法利用高性能 FIFO）；(3) 商用 Vitis HLS dataflow pragma 只报告粗粒度违例、不自动改写代码，必须手工重构。
  - baseline 全栈执行例子（ResNet-18 3*32*32 推理，目标 Alveo U280）：算法层：标准 CNN 前向（Conv/BN/ReLU/残差加/池化，ScaleHLS 直接吃 PyTorch 模型）；系统框架层：论文未明确说明（无 serving 框架，编译产物以 HLS kernel + host code 部署）；编译框架层：ScaleHLS 把模型解析进 MLIR 后对残差多消费者违例仅部分消解→多处 dataflow 断裂为串行，层间默认 ping-pong 双缓冲按块传输；POM/HIDA 同样 ping-pong 按块执行；kernel 调度层：Allo 依赖用户手写调度（pipeline 放最外层导致内层全展开，3×3×3 卷积窗口从双口 BRAM 顺序读产生 14-cycle 延迟、无 array partitioning）；StreamHLS MINLP 求调度随模型规模指数膨胀；硬件架构层：综合结果 ScaleHLS BRAM 208.7% 溢出无法上板（ping-pong 双份缓冲），Allo 设计存在 Padding→Conv2D 访问顺序 (3,34,34) vs (34,34,3) 不一致与访问计数不一致（Padding 写完最后数据后 Conv2D 仍等待→i+2 迭代死锁），StreamHLS 对 ResNet 级模型无法生成有效设计。结果：ScaleHLS latency 104.88M cycles（5.3×）、POM 20.33M（27.4×）、Allo 8.29M（66.9×）、HIDA（3*224*224）74.85M（29.7×）。
  - 全栈痛点归纳：correctness（违例→串行化/死锁）、communication（缓冲选择与写时机→延迟写入）、parallelism（调度→不均衡/资源爆炸）三因素深度耦合，prior work 解耦处理导致互相冲突。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = CODO：在 MLIR 上联合 co-optimize correctness/communication/parallelism 的端到端编译器。(1) 对应"粗粒度违例只能手工/部分消解"：pattern-aware 变换按三类访问模式自动改写——single-producer-multi-consumer 插复制节点（残差 bypass）、multi-producer-single-consumer node fusion（初始化+padding）、multi-producer-multi-consumer buffer 复制，全图满足 single-producer-single-consumer；(2) 对应"细粒度违例死锁/回退 ping-pong"：reduction rewriting 把归约维度移入最内层+临时数组聚合，统一读写计数并保证尽早写（vs StreamHLS 8/9 迭代后才写）；permutation map generation 以 bottleneck 循环为参考做深度映射+深度对齐+循环置换，统一访问顺序（vs StreamTensor 类型不匹配即回退）；(3) 对应"缓冲选择与写时机缺陷"：FIFO-first 缓冲确定 + violation-free reuse buffer（按归约维度自动生成 line/window buffer，协同 array partitioning 消除双口 BRAM 顺序读延迟）；(4) 对应"调度指数爆炸/不均衡/资源爆炸"：profiling-based 性能模型 + 三阶段 resource-aware bottleneck-centric DSE（PA 按延迟比例分配并行度→UP 上扩瓶颈→DP 下缩放过度优化循环），优先 tile 与 FIFO 无关维度剪枝设计空间，inter-task 把瓶颈策略传播给 FIFO 对端并重跑正确性 pass、冲突处降级 ping-pong（vs StreamHLS MINLP 35s–20min，CODO 0.1s–0.5s）；(5) 对应"无片上部署验证"：自动生成 host code + 多 HBM channel burst 传输，端到端上板可部署。
  - 论文方法全栈执行例子（同一 ResNet-18 3*32*32，Alveo U280）：算法层：同一 PyTorch 模型（无算法改动）；系统框架层：论文未明确说明（无 serving 框架；codo-transmit 生成 OpenCL host code 与 HBM burst 访问、权重分布多 channel）；编译框架层：Torch-MLIR→linalg 融合/bufferization→affine dialect，残差多消费者被复制节点消除，Padding→Conv2D 顺序违例被 permutation map 对齐、计数违例被 reduction rewriting 消除，层间缓冲 FIFO-first（FIFO 占比 100%），卷积输入 line/window buffer 复用，DSE PA→UP→DP 加 inter-task 策略传播，输出 HLS C++ kernel；kernel 调度层：编译期静态调度——与 FIFO 无关维度优先 tile、安全循环 unroll/pipeline + array partitioning，平衡各层延迟（Fig. 11 并行度↑ speedup 近线性）；硬件架构层：Vitis HLS 2023.2 综合→Vivado→xclbin 上 U280（300MHz），FIFO 只存 in-flight 数据→BRAM 13.6% vs ScaleHLS 208.7%。结果：latency 1.69M cycles（326.6× vs ScaleHLS 5.3×/POM 27.4×/Allo 66.9×），编译 1.2 s；上板 overall speedup 69.2×（3*32*32）、100.6×（3*224*224），能耗 0.8 J vs baseline 63.8 J；GPT-2 Medium 3.54× DFX、2.03× Allo、1.23× StreamTensor（后者跑在更强的 U55C 上）。
