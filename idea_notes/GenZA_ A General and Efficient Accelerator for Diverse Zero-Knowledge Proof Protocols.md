## GenZA: A General and Efficient Accelerator for Diverse Zero-Knowledge Proof Protocols

- baseline方法是什么？
  - Baseline 分三类：(1) 单协议 kernel 专用 ASIC——PipeZK（Groth16 的固定功能 NTT/MSM 深流水线单元，其余计算丢给 host CPU，非端到端）、SZKP（端到端 Groth16 prover，结构化 NTT/MSM 模块 + MSM 稀疏优化）、zkSpeed（完整 HyperPlonk prover，专用 sumcheck/MSM 单元，超大片上 SRAM 与大量 MSM PEs）、NoCap（hash-centric Spartan/Orion，64-bit Goldilocks 向量单元）；(2) 单协议统一架构——LegoZK（Groth16：分层片上互连组合有限域算术单元成可重构流水线，简单 bit splitting 支持多 bitwidth，NTT 管线长度受限 L=8 需 3D 分解三次 off-chip 往返）、UniZK（Plonky2：统一 systolic array + 专用 transpose buffer + 向量模式，NTT 拼接 L=6 管线但 transpose buffer 面积贵、2D 阵列在 Poseidon full round 损失 25% 利用率）；(3) 可重构乘法器——ReZK/Chen et al.（仅 256/384-bit 两档，ReZK 用 KO-2/KO-3 单层空间分解不可扩展到 64–768-bit，Chen et al. 简单 padding 到最大 bitwidth 浪费资源）。这些 baseline 的共性痛点：kernel 专用单元在跑其他协议时闲置（MSM 单元跑 Plonky2 时闲置、sumcheck 单元跑 Groth16 时闲置）、每个协议只支持单一固定 bitwidth（pad 到最大宽度浪费）、MSM window size 硬编码固定（zkSpeed c=9 对大小不同 MSM 均次优）、长 NTT 管线受片上 SRAM 限制（需多次 off-chip 往返或昂贵 transpose buffer）、sumcheck 无视稀疏性把系数都当稠密场元素处理（zkSpeed 固定功能 sumcheck 单元、NoCap 在 64-bit 下延迟绑定收益天然小）。
  - baseline 全栈执行例子（Groth16 一次证明，走 PipeZK/ReZK 式流程）：模型推理算法层 = R1CS 电路 → witness 生成 → NTT 域变换 → MSM（Pippenger 固定 window c）→ KZG 承诺，所有场元素 pad 到最大 768-bit；系统框架层 = libsnark/Jsnark 把电路编译成 witness 与约束，host CPU 负责非 NTT/MSM 部分；编译框架层 = 论文未明确说明（固定功能单元无 kernel 模板参数，NTT 3D 分解、window size 由架构写死）；kernel调度层 = NTT 用专用流水线（PipeZK）或 L=8 短管线多趟 off-chip（LegoZK），MSM 用固定 c=9 窗口、bucket 映射无并行优化，sumcheck（若有）用稠密单元逐元素处理；硬件架构层 = kernel 专用深流水线单元 + 全局共享 buffer，每单元只有跑自己 kernel 时才有利用率，多 bitwidth 靠 pad 到最大宽度，芯片上同一时刻大量单元闲置。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - GenZA = 统一同构 PE 阵列 + 多 bitwidth 可重构算术 + 每类 kernel 的定制映射策略 + 静态调度器，逐条对应 baseline 缺陷：(1) 同构 16×8 PE 阵列 + 静态调度器按协议/电路把任意 kernel 映射到同一硬件，替代 kernel 专用单元 → 解决"专用单元闲置"：同一批 PEs 跑 Groth16 时做 MSM/NTT、跑 Plonky2 时做 Poseidon/Merkle/多项式，跑 HyperPlonk 时做 sumcheck/MSM，跨协议复用；(2) KO 分解 + hybrid spatial-temporal 映射（KO-2→2 lanes、KO-3→4 lanes，2-cycle 且两计算交错 100% 利用率）+ Montgomery（通用域）/Goldilocks 简化（特殊域）→ 解决"单 bitwidth 与 pad 浪费"：64/128/256/384/768-bit 原生支持，无 pad，吞吐/面积对比专用 768-bit 全流水乘法器仅 0.53×（为灵活性付的代价），对比 LegoZK 的简单 bit splitting 利用率更高；(3) 动态 MSM window sizing（离线成本模型按 bitwidth/N/片上 SRAM/带宽选 c，如 MNT4-753 从 2^14 的 c=11 到 2^23 的 c=16）+ window-major 映射（每轮从所有 window 各取子集 buckets，提高 bucket reduction 阶段并行度、免去 LegoZK 树式归约的额外 buckets）→ 解决"固定 window 次优"（对照 zkSpeed c=9，最高 2.90× 加速）；(4) NTT 折叠流水线 + scratchpad 空间借贷（L=13 长 MDC 管线映射到 2×8 PEs，SRAM 饥饿的首段向邻近空余 PE 借 FIFO 空间，无需大容量 FIFO 或专用 transpose buffer）→ 解决"长管线受 SRAM 限制需多趟 off-chip"（2^23 NTT 流量 7.4→3.0 GB、PE 利用率 16%→38%）；64-bit NTT 则整条 MDC 管线合并进单 PE（32 lanes 足够两条 L=13 管线）消除 NoC 压力；(5) sumcheck 延迟绑定（稀疏系数与稠密挑战分开存、逐轮 on-the-fly 绑定）+ eq-poly 空间压缩（O(N) 物化→O(√N) 工作存储）→ 解决"sumcheck 无视稀疏性"（2^23 流量 2.9→0.7 GB）；(6) inter-kernel fusion（相同 tiling 的 producer/consumer 合并消除中间数据落片外）+ 空间分区流水线（调度器按 roofline 估计把计算图切成子图、调 PE 比例匹配吞吐，cut 点含数据转置/全局归约/Fiat-Shamir 串行点）→ 解决"kernel 顺序执行利用率低"（Plonky2 流量 1220→128.3 GB，9.5×）。结果：Groth16/HyperPlonk/Plonky2 分别比最佳 baseline 性能/面积高 1.98×/2.51×/1.64×，比 80 线程 CPU 快 156–644×。
  - 论文方法全栈执行例子（沿 Groth16 一次 2^23 电路证明的数据路径，穿过全部层次）：模型推理算法层 = R1CS witness 生成 → PIOP 用 NTT 域变换 → KZG PCS 用 MSM，但稀疏 selector/witness 保持 0/1 稀疏、按 MNT4-753 768-bit 或 BLS12-381 384-bit 场运算；系统框架层 = libsnark 式电路经静态调度器翻译成计算图（手动，可交给标准 ZKP 编译器），调度器选 NTT L=13、MSM c=16、融合 cut 点，输出静态执行调度；编译框架层 = 映射策略实现为手写 kernel 模板集（类比 cuDNN 手调 kernel），每模板含自动配置参数（kernel 类型、bitwidth、场模、lane 映射、pipeline 深度），运行时每 PE 收模式配置；kernel调度层 = NTT 蝴蝶经折叠 MDC 流水线（跨 PE 借贷 FIFO，仅 2 hops 距离）→ MSM 经 decoder&dispatcher 分点到 window-major 的 PEs，PE 内 14 次模乘时间复用做 PADD、bucket 积累/归约 → sumcheck/多项式经 fusion 与 pipelining 前递数据；硬件架构层 = 数据流经 2D mesh NoC（32×64-bit @ 2GHz）→ PE：KO Pre/Post 阶段把 768-bit 拆到 32 条 64-bit lane 的乘法器/模加器，Montgomery 模乘多周期完成，128 kB scratchpad 存中间态，HBM2e 1 TB/s 供片外流量 → 输出：AES 2^14 电路 2.1 ms（对比 PipeZK 97 ms），整芯片 58.5 mm²/64.1 W @ 1 GHz。
