## HBM-CASO: A Coordinated Approach to HBM System-Level and On-Die ECC

- baseline方法是什么？
  - baseline 有两类：(1) 现代 HBM（HBM3/HBM3E/HBM4）ODECC 中心的默认保护模式（Baseline(8b)/Baseline(16b)）：处理器侧 memory controller 只保留轻量 CRC-8/CRC-16（仅检错、无纠错能力），通过 4-bit 窄 parity 通道保护信道传输；数据到达 HBM 后由片内 ODECC 用 RS(19,17)* local 码字（8-bit 或 16-bit symbol）生成 parity 负责存储保护，并支持片内 error scrubbing。该模式的问题是：ODECC 固定（RS(18,16) 级别），无法针对不同部署场景定制更强 ECC；系统侧仅 CRC 保护薄弱——写传输中任何 CRC 未检出的错误都会让 ODECC 基于已损坏数据生成错误 parity。(2) 两类既有改进：DUO [18] 用 advanced SysECC（如 RS(72,64)）直接取代 ODECC——受限于 4-bit parity 通道与 8-bit parity 空间，需额外带宽传 parity（性能显著下降），且浪费已有 ODECC 并损害内置 scrubbing；XED [52] 部分转移 SysECC（4-bit SysECC + 4-bit 剩余空间由 ODECC 补）——ODECC 为 8-bit 空间设计的资源未充分利用，更关键的是 HBM 无资源解码 advanced SysECC，导致写验证问题（写传输错误无法检测、生成的 ODECC 不可信）。ECC 理论对比：同样冗余下大码字更优——四个 RS(18,16) 只纠正"每个 16B 块恰好一个错误"的完美分布（2^16 syndrome 空间约 7% 可纠正），而一个 RS(72,64) 任意 4 个错误都能纠正（2^64 syndrome 空间仅 0.02% 可纠正、纠错置信度更高），大码字即"advanced ECC"。
  - baseline 全栈执行例子（GPU 上一笔 64B 写请求走 Baseline(8b) 的数据路径）：算法层 = 无 ECC 算法参与，workload（如 GEMM 或 GNN kernel）经 NVBit 插桩产生 32B/64B 访存请求；系统框架层 = memory controller（FR-FCFS 调度、RoBaRaCoCh 映射）对写请求做 CRC-8 检错，把数据+4-bit CRC 经窄 parity 通道发往 HBM，CRC 失败则重传；编译框架层 = 论文未明确说明（ECC 为硬件固定功能，无编译器）；kernel 调度层 = 论文未明确说明（非 kernel 算子论文，访存请求由硬件调度）；硬件架构层 = HBM 片内 ODECC 用 RS(19,17)* 对每 128-bit 数据块生成 local parity（每 64B 共 4B parity + 4B metadata/CRC，38 TSV I/O × 8-bit burst 经两个 pseudo-channel 传输），写时 CRC 校验通过后生成 parity 存入阵列；读时 ODECC 解码纠正片内错误，传输到控制器由 CRC 检错。痛点：若系统想用更强 SysECC，8B parity 空间被 ODECC 独占无空间可用（挑战➊）；改用 SysECC 后无 CRC 带宽、HBM 又解码不了 advanced SysECC，写数据无法验证（挑战➋）；压缩后的 ODECC 读解码与 scrubbing 不可行（挑战➌）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - HBM-CASO 新增一个可选的保护模式（mode register 控制，静态全局或按块动态启用），三个技术一一对应三个挑战：(1) Codeword Merge 对应挑战➊（parity storage）：用轻量 Merging Unit 利用 RS 码线性性质把两个 local RS(18,16) 码字合并为 regional RS(34,32)（p_regional_0 = p_local_0 + C * p_local_1，GF(2^8) 常数乘），4B local parity 压缩成 2B regional parity，释放 2B 空间；同时把原 4-bit CRC 通道改为传输 advanced SysECC（G-mode 用 RS(68,64) 4B parity），总保护能力从"8B ODECC"变为"2B regional ODECC + 4B global SysECC + 可选 CRC metadata"，比 baseline 强得多（任意两字节错误可在同一 32B 块内纠正，见 R-mode vs Baseline(8b)）；Merging Unit 仅 +61 cells/+17μm²（1.51% 逻辑开销），因为最重的 plocal 生成由现有 ODECC 完成。(2) Delayed Write Verification 对应挑战➋（write verification）：放弃逐写 CRC 校验（写不在关键路径、控制器保存原始数据副本），改为两个跨 pseudo-channel 的 Accumulation Unit 对每 64B 写的 2B regional + 2B CRC parity 做 bitwise XOR 累加进 64-bit 寄存器，控制器并行同样累加，批末（32~64 transfers）附带比较，不匹配则整批重传；冲突率 2^-64 强于 baseline 的 16-bit CRC，重传代价因 DRAM 错误率极低（<10^-8）可忽略。(3) Decoupled Read Protection 对应挑战➌（read decoding）：读时 HBM 内只用检测（复用 Merging Unit 重生成 parity 与存储 parity 比较，无需完整 RS 解码器），检测到错误发 alarm 给处理器，控制器再通过加长 burst 取回全部 parity（regional+CRC）做 tiered error correction（≤2 错误硬件快速处理，≥3 错误用 brute-force 枚举 956,870 组合 + CRC 校验或卸载到软件），同时保留片内 scrubbing 兼容性。三种 SysECC 强度模式 L/R/G-mode 分别用 local/regional/global 码字，按系统能力选择（GPU 32B 粒度限 L/R-mode，CPU 64B 粒度用 G-mode），并可扩展到 Hamming、residue、算法导向 ECC 等其他线性码（SEC(71,64)→SEC(136,128)、residue 码 p_c=(p_a+C·p_b) mod m）。结果：G-mode 2SBF/3SBF/4SBF DCE 100%/100%/98.95%（baseline 76.57%/41.02%/13.03%），全部场景零 SDC、传输 UE% 归零，性能 <0.5% 开销（DUO 最高 12%、Domain-ECC >25%）、功耗 ~0.2%（DUO 最高 15%）、OD 面积仅 +17μm²。
  - 论文方法全栈执行例子（G-mode 下 GPU 一笔 64B 写 + 一次读的数据路径，穿过支持的层次）：算法层 = 无 ECC 算法参与，但保护覆盖范围从"每 128-bit 块"扩展到"512-bit global codeword"，即 4 个 local 码字合并为一个 global（H 矩阵结构从对角矩阵扩展为 hybrid global+regional 结构，可纠正 i∈[0,35]&j,k,l∈[36,71] 等非均匀分布错误）；系统框架层 = memory controller 承担三类新职责：为每 64B 写生成 global SysECC parity（RS(68,64)）并通过原 4-bit 通道送出、并行 XOR 累加进 64-bit 寄存器（批末比较、失败整批重传、写缓冲扩展到 batch 大小）、读时若无 alarm 则用 global parity 做附加验证、有 alarm 则发起特殊访问加长 burst 取回全部 parity 并执行 tiered correction；编译框架层 = 论文未明确说明（ECC 是硬件固定功能流水线，非编译框架）；kernel 调度层 = 论文未明确说明（访存请求由 FR-FCFS 硬件调度，写按 32~64 传输批量以减读写 turnaround，批末校验传输安排在写-读 turnaround 时隙）；硬件架构层 = HBM 片内新增 Merging Unit（把每 64B 写的 4B local parity 合成 2B regional parity）与两个 Accumulation Unit（XOR 累加 2B regional+2B CRC parity 成 64-bit 结果），读时 ODECC/CRC 单元只做检测（复用编码逻辑）、命中错误发 alarm；控制器侧新增 global encoder/decoder（G-mode 5910μm²、0.47ns 检测、4.56ns 纠正）与 RMW 适配（32B 粒度时）；数据路径：写→控制器生成 global parity + XOR 累加→HBM ODECC 生成 regional parity + XOR 累加→批末比较验证；读→HBM 检测（regional 码字）→无错则控制器用 global parity 复核（覆盖传输错误）→有错则取回 parity 分层纠正。全链路净效果：以近 baseline 的面积/性能/功耗代价把单次可纠正错误范围从 4×RS(18,16) 提升到 G-mode 的 512-bit 全局覆盖，并让系统级强 ECC 首次能在现代 HBM 上落地。
