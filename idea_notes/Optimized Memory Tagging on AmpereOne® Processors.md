## Optimized Memory Tagging on AmpereOne® Processors

- baseline方法是什么？
  - Baseline 分两类：(1) 其它 MTE/内存安全硬件实现——移动处理器（Google Pixel 8、Apple A19/A19 Pro）的 MTE 面向手持设备：无 ECC 内存、单租户可控、无数据中心 SYNC 性能与多租户隔离要求；历史 ISA 扩展（Intel MPX、SPARC ADI）因性能/内存开销与 ABI 代码重写而限制生产部署；SPARC ADI 与 RISC-V Rocket SoC（lowRISC）虽已用 ECC 位存 tag，但未解决 SYNC 模式性能与 tag 保序问题。(2) tag 存储的两种 baseline 组织方式——(a) sequestered（启动时静态划出专用 tag 内存）：每 16B granule 需 4bit，须为平台全部物理内存预留（无法预知哪些区域会被 tag），即保留总物理内存的 3.03%（4/(16×8+4)），直接削减软件可见容量 → 降低 CSP 可配置 VM 密度、抬升 TCO；(b) tag 与数据分离存储：每次 tagged 读/写除数据外还要单独的 tag 内存事务（Fig 4：分离方案 Read Data+Tag 需 2 个 coherent 事务 vs 共置 1 个；Write Data+Tag 分离需 2 个或 1+1(RMW)），额外带宽 + 更高读延迟，且 SYNC 下 store 的 tag 校验串行加长 commit 路径。
  - baseline 全栈执行例子（CSP 512GB 平台、多租户开 MTE）：算法/应用层：C/C++ 应用 malloc 返回带 4bit address tag 的指针（虚拟地址 bits 56:59）；系统框架层：glibc malloc 在分配时把 allocation tag 写入 sequestered tag 区；硬件架构层：应用 load 经 MMU 翻译 → 数据读 + tag 区单独读（2 个内存事务、2 个 mesh 传输）→ SYNC 下 store 在 commit 前串行等待 tag 校验 → 带宽/延迟下降影响同平台所有租户；平台层：3.03% 物理内存被划走（512GB 中约 15.5GB）→ VM 密度下降、TCO 上升；无 ECC 的移动 SoC 无此容量税但无多租户/可靠性要求。编译框架层、kernel调度层、Serving 层：论文未明确说明（无编译/kernel 算子/Serving 软件栈内容，依赖现有 glibc/kernel/应用）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法：AmpereOne SoC 的全栈"tag 与数据共置（co-located bundle）"MTE 实现，直接消除 baseline 三类开销（tag 存储开销、tag 取回开销、tag 检查开销）：
    (1) 共置存储解容量税——tag 存 DDR5 ECC 位（每 16B granule 4bit）与数据内联，软件可见容量零影响；为保住数据中心级 RAS 设计新 ECC scheme：SECDED-128+4+9（128B 数据+4B tag+9B ECC、4 codewords/64B cacheline，加倍数据粒度腾出闲置 ECC 位存 tag、可靠性不削弱）与 SymbolECC-64-14+2（Reed-Solomon 借 2 parity bit，100% 检测/100% 有界纠正/99.98% 无界纠正），对应解决 baseline 的容量税与"ECC 与 tag 争位"的可靠性冲突；
    (2) 共置取回解带宽/延迟税——mesh 用保留 implementation-specific metadata 位与数据同传 tag，L1/L2 加宽缓存 tag 与数据共驻，MCU 读 DRAM 时 ECC 位 tag 与数据同返 → 读写数据时 tag 同时到达、无额外内存事务（Fig 4 共置列全为 1 事务），对应解决 baseline tag 分离取回的多事务带宽/延迟；
    (3) 微架构优化解 SYNC 检查税——tag 校验与地址翻译/权限检查并行于 cache-lookup 点（无额外 pipeline stage/stall）；tagged store 在地址翻译时即 early line fetch（line+tag 一起取回、乱序重叠使校验远早于 commit 完成）、store buffer 记录 address tag 并按 tag 匹配规则允许 store-to-load forwarding（跨 tag-store 指令禁止）→ 多数 store 无额外延迟，对应解决 baseline/首代实现中 store 校验串行阻塞 commit 的问题；
    (4) 面向多租户——以 SYNC 模式为主，且因物理页可能被多个页表映射、SoC 不能只靠页表 tag 属性判断，须保守全量保存 tag；MTE 全局使能而未用 tag 的租户仅 1–6% always-on 开销（B/A），租户开 tag checking 后 C/B 中个位数百分比。
  - 论文方法全栈执行例子（同一 CSP 512GB 多租户场景）：平台/芯片层：512GB 软件可见容量不变（tag 藏 ECC 位）→ VM 密度/TCO 不受影响，MCU 以 SECDED-128+4+9 或 SymbolECC-64-14+2 同时提供 tag 存储与 RAS（Tag+数据经 mesh metadata 位同传、缓存共驻）；系统框架层：租户 A 的 glibc malloc 开 tag（GLIBC_TUNABLES=glibc.mem.tagging=3，SYNC 模式），libc_mtag_tag_region() 写 allocation tag 到 ECC 位并返回带 address tag 指针；硬件架构层：应用 load 经地址翻译（tag 校验与翻译/权限检查并行于 cache-lookup 点）→ MCU 读 DRAM 时 tag 与数据同返、经 mesh 同传、L1/L2 与数据共驻 → 匹配通过/不匹配 SYNC 异常且访问不完成；store 在地址翻译时 early fetch line+tag、校验早于 commit 完成、store-to-load forwarding 按 address tag 匹配允许 → 大多数 store 无额外延迟；租户 B（未用 tag）的 full-cacheline store 转 RMW 保 tag（这是 B/A 1–6% always-on 开销来源）；kernel/内存管理：glibc 关 brk(2) 改用 mmap(2)（PROT_MTE 页属性与 tag 存储初始化需要），allocator 路径指令增加 + eager tag initialization + 高频小对象碎片化分配放大开销（SPEC 192-copy C/B geomean 0.924，502.gcc 0.698/523.xalanc 0.855）；jemalloc 对照实验证实开销源于内存管理而非 tag checking 本身 → 论文指出 MTE-aware allocator（如 Apple xzone malloc：小块 free 即重赋 tag、大块惰性重赋）为后续软件优化方向。编译框架层、kernel调度层、Serving 层：论文未明确说明（无编译/kernel 算子/Serving 软件栈内容）。
