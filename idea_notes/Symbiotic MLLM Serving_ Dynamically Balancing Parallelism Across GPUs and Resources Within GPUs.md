## Symbiotic MLLM Serving: Dynamically Balancing Parallelism Across GPUs and Resources Within GPUs

- baseline方法是什么？
  - Baseline 是两类部署 MLLM 的主流方式：(1) 把 vision encoder 直接挂在 LLM GPU 上与 decoder 共存（vLLM/SGLang 式 text-only 栈扩展），encoder 进入 prefill 关键路径、与 prefill/decode 竞争 SM 与 HBM，导致 TTFT/TPOT 恶化、SLO 违例增多；(2) 把 encoder 放到固定专用 GPU 池（EPD-Serve 式 encoder-prefill-decode 分池），小请求/纯文本请求浪费池容量。两者共同点是 ahead-of-time 静态决策：并行度方案（DP/TP/PP/EP 度）在部署时固定、GPU 分配（哪些 GPU、SM 配额）也钉死。baseline 全栈执行例子（SGLang 处理一个 1k×1k 图像请求，encoder+prefill 在同一 GPU）：算法pipeline 层——ViT encoder 对 n_raw 视觉 token 做自注意力（序列长平方级计算）、Merger 把 n_raw 压到 n_final；系统框架层——SGLang 调度器把 encoder 与 LLM prefill/decode 按固定流/固定 SM 排到同一 GPU 或固定池；编译框架层——论文未明确说明（依赖 vLLM/SGLang 既有 kernel 选择，无 encoder 专用编译）；kernel调度层——encoder 的 compute-bound kernel 与 prefill/decode 的 memory-bound kernel 混在同一 SM 池上按硬件调度器抢占，encoder 进入 prefill 关键路径；硬件架构层——A100 上 encoder 阶段 SM 高利用（1024² 下 78.0%）但 HBM 低（25.3%），prefill/decode 阶段 HBM 高（67.6–70.2%）但 SM 中等，两个阶段的时间错配与静态资源分配互相造成 SM/HBM 空洞，LLM 明明算力充足仍 SLO 违例；静态并行度下（如固定 TP=8），低分辨率请求被过度并行化（通信开销主导、1 GPU 最优）、高分辨率请求被欠并行化（4-TP 才够），任何单一静态方案都同时过供给与欠供给。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 RESONATOR：把 encoder 从干扰源变成 LLM 的合作者，解耦后再通过两级运行时控制重耦合——(1) **Intra-GPU Sharing Engine** 对应解决"共存干扰与资源空洞"：不再用固定 SM 配额或单一全局流，而是按场景自适应——complementary 场景（memory-bound decode chunk）显式 SM 分区给 decode 保留最小 SM 切片（SM_dec=⌈SM_total·SM_dec_min(c)⌉）以隔离延迟抖动、把其余 SM 全给 encoder（空间共享）；contending 场景（compute-bound prefill chunk）不做静态分区，用 per-kernel stream binding 把 compute-bound kernel 送 wide stream（全部 SM）、memory-bound/低占用 kernel 送 narrow stream（窄 SM 子集）（时间-空间共享），让 encoder 与 prefill 的 kernel 级 SM/HBM 空洞互相填充；(2) **Inter-GPU Parallelism Engine** 对应解决"静态并行度过/欠供给"：PRISM 把请求排队建模为 MCKP/DP 调度（最大化 ∑1/T(R_i,k)，受 GPU 预算约束），结合 Performance Atlas（encoder 多项式模型 + LLM 随机森林 + 合法 TP 集）按当前请求分辨率、batch 组成与 GPU 预算逐 batch 选 DP/TP 计划；logical sharding（每 GPU 预载完整 encoder 权重 + cuBLAS/CUTLASS strided GEMM 的 ld 参数逻辑分片）让 TP 切换从 weight 重分布降为控制面元数据更新，近零开销实现 JIT 动态并行（Alg.2）。论文方法全栈执行例子（同一 1k×1k 请求 + 一批混合分辨率请求在 8×A100）：算法pipeline 层——encoder 序列长 L_seq 仍是 ViT 平方级计算，但 Atlas 以 L_seq 为唯一复杂度参数预测各 TP/SM 下延迟；系统框架层——SGLang-0.4.7 上 PRISM 调度器在 batch 形成时给高分辨率请求配 TP、低分辨率配 DP（回溯 dp[m][N] 得最优 batch），控制面只更新 ld 参数即完成逻辑分片切换，无权重搬移；编译框架层——论文未明确说明（无编译器改动，kernel 代码与数据路径不变，只改 launch 流与 SM 配额）；kernel调度层——decode-heavy 时 encoder kernel 与 decode kernel 按 SM 切片分区（complementary 路径兼容 CUDA Graph 重放），prefill-heavy 时逐 kernel 查 profile 表 P 选 wide/narrow stream（contending 路径用 eager 执行）；硬件架构层——A100 上 encoder 的 compute-bound kernel 填 prefill/decode 留下的 SM 空洞、prefill/decode 的 memory-bound kernel 填 encoder 的 HBM 空闲，TP 通信等待间隙的 SM 被回收给 co-located decode，logical shard 的 strided GEMM 与 contiguous 中位差仅 0.7%；结果：相同 GPU 预算下 mean TTFT 最高 5.1×、TPOT 3.0×、E2E 4.9×、吞吐 3.4×，相对 EPD-Serve 少用 33% GPU 仍全面领先，共存下 TPOT P99 SLO 违例率 20%→5%。
