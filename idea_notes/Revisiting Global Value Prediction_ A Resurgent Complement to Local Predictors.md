## Revisiting Global Value Prediction: A Resurgent Complement to Local Predictors

- baseline方法是什么？
  - Baseline 由两部分构成：① 全局值预测 gDiff（ISCA 2003，Zhou et al. [37]）——PC 索引预测表，每项存 n 个 global stride（diff）+ distance index；Global Value Queue（GVQ）记录近期 dispatch 指令的投机结果。预测时：指令 dispatch → PC 索引取 n 个候选 diff 与 distance index → 按 distance 定位 GVQ 中该距离的 base value（前序动态指令输出）→ 预测值 = base + diff。更新采用投机更新：指令投机结果就绪后计算与 GVQ 中前序全局值的 global delta 序列，与 n 个 diff 比较，匹配者位置成为新 distance index。为缓解 value delay（base 值因流水线延迟不可用），Zhou 等提出用局部 VP 结果构造 GVQ 并用投机结果更新队列与预测器。② 局部值预测 SOTA EVES [33]（EVTAGE 上下文预测器取 PC+branch history，ES 计算预测器只取 PC，EVTAGE 权威更高）——利用 per-static-instruction 局部值历史，成熟但覆盖增长受限，尤其处理不了 H2P（Hard-to-Predict）指令。Baseline 痛点：a) gDiff 精度不足 99%（误预测触发 pipeline squash 惩罚，代价超过收益）；b) 投机更新污染——误预测分支/值的未提交结果留在 GVQ 并更新预测器，错误历史持续影响后续预测（无 squash 策略）；c) 依赖局部预测器构建全局历史（低置信时局部预测器不输出、全局历史不完整），且对局部值局部性强的指令全局预测冗余；d) 存储巨大——order-32 gDiff 每项 32 个 diff，4K 项表达 1.03MB，远超几十 KB 的实际硬件预算。
  - Baseline 全栈执行例子（算法pipeline-系统框架-编译框架-kernel调度-硬件架构；本文为微架构论文，算法、系统框架、编译、kernel 层论文未明确说明）：xalancbmk（SPEC CPU 2017）链表遍历场景，I6（ldr x0,[x1,#16]）是 H2P 指令：① 硬件架构层——I6 被 dispatch 进 OoO 核：gDiff 以 I6 的 PC 索引预测表取出 n 个 diff 和 distance index，但 I6 所需 distance 处的 base 值（I1 的输出，ldr x1,[x22,#8]）在深流水线早期不可用（value delay），只能等局部 EVES 的投机结果或 OoO 引擎结果填充 GVQ；I6 执行完成 → 投机更新用未提交结果更新 GVQ 与预测表 → 若期间分支 I2（cbz x1）被误预测，无效路径的投机值残留在 GVQ 且污染预测器（no-squash），后续 I6 预测被陈旧错误值带偏，精度下降 → 误预测触发 pipeline squash 丢弃后续指令并重执行，ILP 收益被抹掉；且 32 diff/项 × 4K 项 = 1.03MB 存储远超预算。局部 EVES 对 I6 这类局部 stride 剧烈波动的 H2P 指令无能为力（局部值序列非周期、局部 stride 序列强波动），覆盖上不去。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 EgDiff——重设计的全局 load 值预测器，四重改动逐一对应 baseline 缺陷：① 对应精度缺陷（a）：aggressive confidence——tag-based 索引（与索引不同哈希的 PC tag，减少 aliasing 误触发）+ usefulness bits（正确预测递增、10-bit TICK 周期衰减、u=0 才允许替换）+ last misprediction 控制（误预测后 1024 条指令窗口全局抑制输出，防级联错误）+ FPC（3-bit 概率计数器，概率向量 {1,1/4,1/4,1/8,1/8,1/8,1/8} 高位减缓置信累积、误预测清零重建），把精度推到 99% 以上；② 对应污染缺陷（b）：非投机更新——GVQ 分投机段（32 项，与 LQ 同步，用于预测）与非投机段（32 项，存提交值），预测器只用 commit 阶段架构正确值更新，squash 只回滚投机段，杜绝错误值污染（对比 gDiff no-squash）；③ 对应 value delay/历史不完整缺陷（c）：deferred prediction——预测时 base 值不可用则暂缓，把 distance/diff 写入投机 GVQ 条目并绑定 base 条目的 Wake 字段，base 值就绪反向触发生成预测，前端不 stall；不再依赖局部预测器构建全局历史（去掉 EVES 辅助仅从 3.24% 微降到 3.11%，覆盖 26.15%→22.45%，说明可独立工作）；④ 对应存储缺陷（d）：distance polling——每项只留 1 个 diff + 5-bit distance，轮询算法（Algorithm 1）在误预测时 distance-1 探测更近位置精化相关性，把 1.03MB 压到 44KB（-95.8%），且更新只算 distance/distance-1 两个 diff（gDiff 要算 n 个）。额外：预测值存 GVQ 验证，减少 PRF 端口压力；唤醒复用 load 完成端口。结果：EgDiff 4.37% IPC speedup（覆盖率 25.87%、>99% 精度）；与 EVES hybrid（EVES 预测写 PRF+GVQ 作 base，两者都有效时 EVES 优先）19KB 混合 6.16% 超过 32KB EVES 4.81%，无限混合 7.02%（EgDiff-only 覆盖 9.4% 是局部预测器完全看不见的全局模式），证明全局与局部预测部分正交互补。
  - 论文方法全栈执行例子（算法pipeline-系统框架-编译框架-kernel调度-硬件架构；本文为微架构论文，算法、系统框架、编译、kernel 层论文未明确说明）：同样的 xalancbmk 链表遍历 I6（H2P）场景：① 硬件架构层——I6 dispatch：PC 哈希索引 44KB 预测表 → tag 匹配且 FPC 饱和(7) → 取 64-bit diff 与 5-bit distance → 从投机 GVQ 读 distance 处 base 值；此刻 I1 结果未就绪 → deferred 模式：把 distance/diff 写入 I6 的投机 GVQ 条目（VP=0），并把 I6 条目索引写入 base 指令（I1 对应条目）的 Wake 字段 → I1 完成执行、LQ 更新并把投机结果写入 GVQ（speculative 段与 LQ 同步）→ 查 Wake 字段找到 I6 条目、确认 distance 仍匹配 → 用新 base 值+diff 计算预测值写入 PRF（用 dispatch 时记录的 PRF 名）并广播 wakeup 唤醒依赖指令（复用 load 完成端口，冲突时延迟 1 cycle，>99% 周期至多 1 次唤醒）→ I6 执行完成，LQ 结果与 GVQ 预测值比对，匹配则跳过 PRF 回写（省端口），不匹配（极少，>99% 精度）置 misp、21 cycle pipeline squash、回滚投机 GVQ → commit 时 I6 实际值 FIFO 传播到非投机段，按 Algorithm 1 更新：δa=v_actual−NVQ[d].value 与 δp 比较，匹配则 FPC/u 递增，不匹配则 distance-1 换更近位置重算 diff 并重置计数器——预测表与 GVQ 始终只被已提交值训练，无污染；局部 EVES 照常对普通局部指令预测，两者 hybrid 并行工作（EVES 优先），EgDiff 覆盖 EVES 看不到的 9.4% 全局 stride 模式，最终 19KB hybrid 达 6.16% IPC 提升（无限混合 7.02%）。
