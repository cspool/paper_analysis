## TTP A Hardware-Efficient Design for Precise Prefetching in Ray Tracing

- baseline方法是什么？
  - Baseline 为三类：(1) 无预取的默认 RT unit（Vulkan-sim baseline）——BVH DFS 遍历，RT unit 中线程 80%+ 时间等待内存读取（memory-latency-bound），DRAM 带宽多数场景未用满（说明有预取空间），cache miss 中长 pop streak（向上/同层遍历）占大头，但没有任何机制提前取数；(2) Treelet prefetcher（MICRO 2023）——需要预先用 treelet 遍历算法重排 BVH 树、在每个 BVH 节点加 treelet 归属信息，treelet 根节点被读时整体预取整个 treelet；缺点是直接替换 DFS、访问节点更多、预取过量浪费带宽（DRAM 流量 1.38x、spnza 场景带宽 58%→80%）且需改软件遍历算法与树组织；(3) Park et al.（2013）——只在叶子节点做交点测试的 8 cycles 内触发预取，触发窗口太短、无法隐藏 100-300 cycles 的 cache miss 延迟，且只在叶子访问后触发。
  - baseline 全栈执行例子（一个 closest-hit 主光线 trace ray 指令在 baseline GPU 上执行 BVH 遍历）：① 算法pipeline层——BVH（Embree 构建、AABB 层次、叶子每节点 1 primitive）DFS 遍历找最近命中：弹栈→读节点→ray-box 测试→子节点命中则压栈（6-ary），无预取；② 系统框架层——Vulkan ray tracing 管线（raygen 生成主光线→RT unit trace ray→closest-hit/any-hit/miss shader），LumiBench 16 场景经 RayTracingInVulkan 驱动；③ 编译框架层——论文未明确说明（无编译器改动，RayTracer 为既有 Vulkan 应用直接编译运行）；④ kernel 调度层——warp（32 线程）在 RT unit 中被调度，per-thread 遍历栈 push/pop，同 warp 重复请求 coalescing 后经内存访问队列送 L1；向下遍历（连续 push）时下一节点地址依赖交点测试结果、无法提前得知；向上遍历（连续 pop）时下一节点地址已在栈中但 baseline 不利用，线程仍等 100-300 cycles 的 miss 返回；⑤ 硬件架构层——8 SM、每 SM 1 个 RT unit、RT warp buffer 4、L1D 32KB（20 cyc）/L2 512KB（160 cyc），射线状态（origin/direction 192 bit/线程）与遍历栈在 warp buffer 中，读节点数据是主要停顿来源。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = TTP，一个完全建立在 RT unit 既有遍历栈之上的硬件预取器，核心洞察是"向上遍历的下一节点地址已经在栈里，预取零推测"。DFS 下用 2-bit FSM 监控 pop streak：连续第 1/2/3 个 pop 分别发 1/2/16 个预取（直接取栈顶 k 个地址），push 重置；BFS 下每次 pop 从 FIFO 队头预取 N 个（N=4）。对应解决：(1) vs 无预取 baseline——把向上遍历（占 RT read miss 大头）的 miss 延迟用栈内现成地址提前隐藏，且不做地址预测、不预取向下路径，避免错误路径带宽浪费，L1/L2 MPKI 降 28.28%/40.01%、accuracy 98.92%，DRAM 总流量不变（只加速时间、不增加传输）；(2) vs Treelet——TTP 不需要修改遍历算法、不需要重排 BVH 树、不需要在树节点加额外信息，软件完全透明，且按需少量预取（最多 16）而非整 treelet 过量预取，DRAM 流量 1.38x→不变，各分辨率全场景胜出（128x128：1.48x vs 1.00x）；(3) vs Park et al.——TTP 覆盖所有向上遍历而非只在叶子交点测试的短窗口触发，隐藏更长延迟；(4) 硬件开销——每线程仅 2-bit FSM + 指针 + 比较器，FreePDK45 综合每状态机 8.7 cells/SM（128 状态机共 1117 cells），相对单线程 192-bit 射线属性可忽略；(5) 额外收益——TTP 使 BFS 变得可行（BFS 可预测性被充分挖掘，L2 miss 降 92.04%），平均 1.61x 反超 DFS，为按负载选择遍历算法提供了新优化机会。
  - 论文方法全栈执行例子（同一 trace ray 在加 TTP 的 RT unit 上）：① 算法pipeline层——DFS/BFS BVH 遍历算法不变（TTP 不改软件、不改树格式，对 shader 透明）；② 系统框架层——Vulkan RT 管线与 LumiBench 场景不变，TTP 纯硬件实现、无 API/驱动改动；③ 编译框架层——论文未明确说明（无编译器/运行时改动）；④ kernel 调度层——warp 内某线程 pop 节点时触发其 TTP FSM 迁移（S1/S2/S3），预取指针从栈顶 T 向下取 1/2/16 个地址，demand read 空闲时按 32B sector 拆块逐周期发出预取请求（可选 prefetch 优先仲裁），prefetch 提前填充 L1/L2，等该节点被真实 pop 读取时命中；⑤ 硬件架构层——RT unit warp buffer 每线程新增 2-bit FSM + 预取指针 + 比较器（T−k 停止），预取请求与 demand 共享内存访问队列（demand 优先），隐藏 100-300 cycles miss 延迟；结果：8-SM 配置平均 1.48x（峰值 1.89x）、功率 1.35x、能量 -8.70%、带宽开销 18.22% 而 DRAM 总量不变；30-SM/64KB L1/3MB L2 配置平均 1.50x（峰值 1.93x）、256x256 分辨率 1.44x、AO/SH shader 1.22x/1.18x，稳健性全配置保持。
