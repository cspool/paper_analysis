## BoostX™-NTI Fast, Scalable and Flexible Storage Architecture with NVMe-TCP Initiator Acceleration

- baseline方法是什么？
  - Baseline 一（软件方案）：Linux kernel NVMe/TCP initiator [1] 与 SPDK NVMe/TCP initiator [37]——主机 CPU 跑完整 NVMe/TCP initiator 栈（NVMe 命令↔PDU 转换）+ 内核/用户态 TCP 栈（polling、zero-copy、kernel bypass 优化），主机下发的 NVMe 命令经块层→nvme-tcp 驱动组 PDU→socket→TCP/IP 逐包处理→NIC 发出，响应反向同路。痛点：CPU 效率极低——SPDK 侧 200 Gbps 需 24 核（FIO 4KiB 随机、32 线程、QD256 实测），800 Gbps 网络预计需 96 核，CPU 增速赶不上网络速率；CPU 时间被 NVMe/TCP 与 TCP 栈的逐包处理、内存拷贝、存储/网络层交互吃满；且不支持内核应用（用户态块接口）。
  - Baseline 二（sidecore 方案）：BlueField-3 SNAP [9]——PCIe 卡仿真成标准 NVMe 设备，主机下发的 NVMe 命令被板载 16 个 ARM sidecore 上的存储仿真栈取走，经 interposition 层转成块请求，再由 sidecore 上完整 nvme-tcp + TCP 软件栈发网。痛点：sidecore 算力/访存有限——16 核全打满仅达 200 Gbps line-rate 的 9.6%（FIO 4KiB、32 线程、QD128）；若换服务器级 CPU（读方向需 24 核 Xeon Gold 6348N）则 ~200W 功耗 + 多 DIMM/VRM/重散热不可接受。
  - Baseline 三（部分硬件加速）：SNAP+XLIO [20]——只让 TX 方向 PDU payload 绕开板载内存直送 NIC + 用户态 TCP 栈，RX 仍走 sidecore 软件。痛点：仅 34.3% line-rate，ARM 核减到 8/4 个时掉到 13.9%/6.1%；ANO [90] 只加速 RX 直写、丢包/乱序即回退软件并要求内核补丁（vendor lock-in）。结论：只要 I/O 路径残留 sidecore 软件，性能就被卡死；NVMe/RDMA（RoCEv2）虽性能高但需 RNIC + 无损网络调优 + 厂商锁定。
  - baseline 全栈执行例子（一次 4KiB 随机读）：主机应用 read → 块层/SPDK 把 NVMe Read（含 PRP 地址）交给 initiator 栈 → 组 NVMe/TCP capsule PDU 头 → 写 TCP socket → 内核 TCP 栈分段/封装/逐包中断或轮询 → NIC 发包 → 目标回 read data PDU → 主机 TCP 栈收包先 stage 进每连接大 TCP receive buffer（全程经主存）→ initiator 栈顺序扫描 TCP payload 解析 PDU 边界、拆出 PDU 头与数据 → 数据 memcpy 到 NVMe data buffer → 组装 completion 返回应用。算法层：无 ML 算法（负载为存储 I/O；MLPerf Storage 是模拟 H100/A100 数据消费率的存储基准，不做模型推理）；系统框架层：Linux 块层 + nvme-tcp 内核驱动 或 SPDK 用户态栈（sidecore 方案为 SNAP 存储仿真 + interposition + nvme-tcp/TCP 软件栈，XLIO 再加 TX 旁路）；编译框架层：论文未明确说明（无编译器改造）；kernel 调度层：内核/用户态 TCP 栈逐包软中断/轮询 + 队列调度（无 GPU/加速器 kernel）；硬件架构层：通用 NIC 只做收发（ConnectX-6 Ex），所有协议处理在主机/板载 CPU 上。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = 把 NVMe/TCP initiator 的整条 I/O 数据路径做成 FPGA 硬件（NHI + NVMe/TCP Engine + TOE），以 Virtual buffer 消除片外内存瓶颈，以 Dynamic handover/Fault handler/热管理保证可部署性。(1) 全栈硬件卸载——对应"软件栈 CPU 低效"缺陷：I/O 命令处理、PDU 生成/解析、数据搬运、TCP 处理全部在 Versal FPGA 逻辑内完成，主机 CPU 只发 NVMe 命令收 completion（核心效率最高 16.7×，128KiB read）；sidecore 只做 admin 队列等控制面，带宽增长不加重其负担。(2) I/O 处理全硬件——对应"sidecore 算力瓶颈"缺陷：Command Scheduler/PDU Header Generator/PDU Stitcher/PDU Parser/Decapsulator 覆盖命令与完成处理；PRP 抽取入表解决 NVMe（PRP 指向主机地址）与 NVMe/TCP（目标看不到发起端地址空间）的协议鸿沟，读数据跨多个 PDU 返回时由硬件追踪末数据生成 completion；50M IOPS 能力对标 1.6 Tbps。(3) Virtual buffer——对应"片外内存带宽瓶颈"缺陷：TX 侧每 NVMe/TCP 队列只维护 virtual offset 元数据，TOE 按 TCP 字节序取数据时查 PDU metadata table 定位重叠 PDU、经 PRP table 按需 DMA 主机数据现场拼接（重传/乱序/PDU 跨包由元数据解决，零中间拷贝）；RX 侧 PDU splitter 边收边切、数据按 PRP 直写主机内存——全程数 KB 级片上 SRAM、数据永不穿越片外内存。(4) 灵活命令调度——对应"固定 1:1 队列映射"缺陷：NVMe 队列与 NVMe/TCP 队列解耦，round-robin 并行化（目标端 per-queue 吞吐受限场景）与 1:1 隔离（AI 负载 per-thread 队列防串扰）双策略。(5) 可部署性——对应"FHHL 150W / RNIC + 无损网络"缺陷：HHHL 75W + System Monitor 90% 阈值节流（温度回落后自动恢复）；PRP list 宿主驻留（片上只存头指针 + 预取）、完成的 PDU 元数据实时失效省片上资源；标准 NVMe 接口 + 严格协议合规（UNH-IOL 全部强制 NVMe 测试通过、NVMe Integrator's List 在列）、免内核驱动，兼容 Linux/Windows/VMware ESXi/QEMU-KVM 与 kernel/SPDK/Purestorage/Netapp target；Dynamic handover 双向、按队列粒度 HW↔SW 切换（MMIO 寄存器交接最小上下文，出错队列单独复位重传、其他队列不断流），Fault handler 硬件自愈可恢复错误——在商品以太网 + 未修改主机软件栈下落地，保留 TCP 的低 TCO 同时拿到 RDMA 级性能。
  - 论文方法全栈执行例子（同一 4KiB 随机读）：主机向 NHI 暴露的标准 NVMe 设备提交 Read（PRP 指向 data buffer）→ NHI 硬件轮询 doorbell、DMA 取命令 → Command Scheduler 解耦映射 NVMe 队列→NVMe/TCP 队列 → PDU Header Generator 生成 PDU 头、抽取 PRP 条目入 PRP table → PDU Stitcher 记录 {qid, virtual offset, header} 元数据并通知 TOE → TOE 按 TCP 拥塞/重传状态发起发送读请求 → Table handler 拦截、按 virtual offset 匹配重叠 PDU → PDU payload receiver 按 PRP 经 DMA 从主机 data buffer 取数（写路径）→ 100GbE 发出 → 目标回 data PDU → TOE 收包 → PDU splitter 顺序扫描 TCP payload 切出 PDU 头与数据 → PDU header handler 判 opcode、查 PRP table 得主机地址 → DMA 直写主机 data buffer → PDU Decapsulator 追踪最后一个 data PDU 生成 completion → NHI 写 CQ。全程数据不落片外内存、sidecore 零参与。算法层：无算法改动（协议转换与数据搬运硬件化；MLPerf Storage 等为 I/O 负载）；系统框架层：主机栈完全未改（标准 nvme 驱动 + SPDK/vHost/内核 nvme-tcp target 任选），控制面软件在板载 sidecore（Mango SDK + OPI 桥，SPDK RPC 配置）；编译框架层：论文未明确说明（RTL + HLS 混合实现，无编译器改造）；kernel 调度层：命令/队列调度与 PDU 数据搬运全部在 FPGA 硬件流水（Command Scheduler + Virtual buffer 元数据表），无软件 kernel；硬件架构层：Versal FPGA 三 IP + sidecore 控制面 + Fault handler + 热管理，57.8% LUT/61.7% BRAM 实现 200 Gbps 全双工 line-rate。结果：4KiB 50:50 达 line-rate（vs Sidecore 9.17×、Sidecore+XLIO 2.81×）；128KiB 50:50 双向合计 356 Gbps（6.59×/1.56×）；核心效率 4KiB 最高 3.01×、128KiB 最高 16.7×；vs NVMe/RDMA 吞吐最高 1.24×、核心效率最高 2.00×；MLPerf Storage 最高 2×（平均 1.34×、达本地 SSD 91.6%）；vHost 1 核吞吐 2.64×；pgbench TPS 最高 +30.3%、延迟最高 -23.1%。
