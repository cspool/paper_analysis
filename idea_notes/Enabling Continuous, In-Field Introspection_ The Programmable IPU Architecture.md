## Enabling Continuous, In-Field Introspection: The Programmable IPU Architecture

- baseline方法是什么？
  - Baseline 为现有硬件 introspection 工具的三角困局：①Fixed-Function PMU（性能计数单元）——固定功能硬件计数器，只能数设计者预先设想的固定事件（如"数 L2 miss"），零开销但不可编程、无法适配部署后新问题、隐藏片上事件细节；②High-Overhead Trace（JTAG 等）——cycle-by-cycle 全量 trace，保真但产生 TB/s 级数据洪流，淹没片上 buffer、饱和 I/O、显著拖慢应用，只适合 lab 事后调试，无法实时观察长期生产负载；③Specialized Hardware（如 TEA for PICS）——专用固定功能分析块（如 per-instruction cycle stacks），对窄任务有效但不具扩展性，无法为每个潜在用例流片数十种不同监控硬件。核心 gap：没有任何方案同时具备可编程性（如 CPU）、实时信号访问（如 trace）、低开销（如 PMU）；且现有方案均无法做：有状态仿真（PMU 无状态）、有状态片内数据聚合（trace 数据爆炸）、line-rate 低延迟状态跟踪。
  - baseline 全栈执行例子（开发者想对线上工作负载做 per-instruction 性能归因）：算法层 = 用 Linux perf_event / CUPTI 采样 + 事后离线分析推断瓶颈（无片上分析能力）；系统框架层 = 主机侧采样工具（perf stat/perf record）读 PMU 计数器或记录 sample；编译框架层 = 论文未明确说明（仅编译期静态 PGO，无动态反馈）；kernel调度层 = 无（采样由 PMU 硬件/OS 处理，无法对单个 PC 的事件做状态跟踪）；硬件架构层 = 固定 PMU 只能数预设事件（L2 miss 等），无法回答"这个 PC 的 miss 是哪种 root cause"；或上 TEA 专用块（BOOM RTL 修改，固定 9 事件）只服务窄用例，新问题就得重新流片；JTAG trace 数据量爆炸无法在线。结果：开发者对真实负载的微架构行为基本盲视，只能靠模拟/代理/离线分析。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = IPU（Introspection Processing Unit），一个混合微架构：紧凑可编程 RISC-V 核 + 精心挑选的微架构加速扩展（直方图加速器、hash、循环指令）+ 可选微型 eFPGA 软逻辑（IPU_pro），整体 <1% 面积、<25mW。三个核心属性逐一对应 baseline 缺陷：①Low-Level Signal Access（对应"PMU 只暴露预设事件"）——每个 IPU 经 P&R 贴近其 HIT，高带宽只读订阅 32 个精选微架构内部信号（比 PMU 深得多），信号选择按 HIT 类型而非下游分析决定（datapath 值/控制信号/状态指示三轴覆盖），N 个 PMU 事件得 N 个固定答案，N 个 IPU 信号得组合爆炸的分析程序空间；②On-Chip Data Processing（对应"trace 数据洪流"）——introspection 程序在片上本地执行聚合/过滤/统计（computational introspection），只导出高层洞察（1024-bin 直方图、PICS、失败模式计数），把瓶颈从数据传输移到本地计算，数据输出带宽降到 KB/s 级；③Low-Latency State Tracking（对应"PMU 无状态 / trace 无法实时"）——紧耦合集成使 IPU 能 line-rate 跟踪系统状态并跑有状态仿真（如预取器 A/B 测试）。安全模型（证书代码签名 + closed/restrictive/permissive 三策略 + IPU 不能向 HIT 注入信号）使 app-store 式部署成为可能。核心设计洞察：纯处理器核不足以线速处理数据 → 混合 core-accelerator 架构（直方图加速器处理统计类、eFPGA 处理状态机遍历类任务），两个变体（IPU_lite/IPU_pro）覆盖分析-vs-数据率设计空间；触发逻辑（TS/TE/ADDR）与 API（IPU_CONFIG_IMAGE/START/STOP/PAUSE/RESUME/FINALIZE）仿 CUPTI/perf_event 提供细粒度控制。
  - 论文方法全栈执行例子（同一 per-instruction 性能归因任务，PICS generation）：算法层 = 软件定义 PICS：IPU 每 cycle 用 17 个核流水线信号更新每个 PC 动态实例的 PSV（bit-mask），每 400k cycle 归并输出 cycle 栈（不再需要 TEA 专用硬件）；系统框架层 = IPU 作为 PCIe 设备出现，主机 API 加载签名二进制并配置触发区（IPU_CONFIG_IMAGE("PICS-generation")、IPU_CONFIG_START(ROI_BEGIN)、IPU_CONFIG_STOP(ROI_END)），开发者从 app-store 下载 PICS 二进制，输出写文件/磁盘（表 II 格式）；编译框架层 = introspection 程序用标准 RISC-V 工具链 C 编写，直方图/hash/循环暴露为编译器 intrinsics 与函数库，IPU_pro 附带 Verilog 软逻辑；kernel调度层 = IPU 顺序核数据驱动执行：fetch-PC/事件到达 → _main 更新 PSV（load-modify-store，如 itlbm_m: hash r1,x12; ld r2,r1,0; addi r2,r2,0x40; sw r2,r1,0）→ 活动期间新数据丢弃（400,000-cycle 采样窗口控制近似误差）→ 归并后经逻辑 FIFO 发主机；硬件架构层 = IPU_lite flatten 进核流水线 HIT（0.019 mm²、15.0mW、0.06% 面积开销），订阅 215-bit 信号接口，触发逻辑用 TS/TE/ADDR 限定 ROI。结果：与 TEA 硬件 PICS 相同的 per-instruction 瓶颈分解（平均误差 <3%、PC 排名正确），但把性能归因从 pre-silicon 固定设计选择变成 post-silicon 可编程软件任务（对 BOOM 无需 RTL 改动）；同一 IPU 硬件再验证 GPU 利用率监控（AccelSim）与逐 miss 根因诊断（Gaze）两类任务，证明架构通用性。
