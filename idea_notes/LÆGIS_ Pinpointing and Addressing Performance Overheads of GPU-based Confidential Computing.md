## LÆGIS: Pinpointing and Addressing Performance Overheads of GPU-based Confidential Computing

- baseline方法是什么？
  - Baseline 是现有 GPU-based CC（CPU TDX TEE + CC-capable GPU，如 H100）下的 UVM 页迁移流程：GPU 访存缺页 → GMMU 聚合 fault 到 buffer（默认 Bf=256）→ 中断 CPU → nvidia-uvm driver 取批、预处理（fault preparation）、服务批次，对每个 4 KB 页做 AES-GCM 加密后经 PCIe DMA 到 GPU，GPU CE 解密后以明文写入 HBM（HBM 假设可信）。加密模型为"同步计数式"：IV 由访问顺序隐式推导（IV_t ← increment(IV_{t-1})），CPU 与 GPU 靠对称访问保持同步（兼防重放攻击），因此加密只能在数据被访问时同步执行、落在关键路径上且无法与计算重叠。加密走 kernel-space 路径：nvidia-uvm 的 CSL → libspdm → Linux Kernel Crypto API（crypto_aead_encrypt），单 kernel 线程工作队列串行、未并行化，实测仅 1.3 GB/s（对比非 UVM 用户态 OpenSSL 路径约 3.03 GB/s）。三大痛点：①每页加密前需 CPU-GPU 紧同步协商 IV，同步本身在关键路径；②driver 线程等待下一批 fault 期间大量空闲（true idle 平均占 87%），CPU 算力浪费；③即便 CPU 忙，LCA 软件加密吞吐仅 1.3 GB/s。Aggressive 预取（Pt=1%）虽减少 batch 交互，却把负担转移到加密（加密占 batch 处理 CPU 时间可超 70%）。
  - Baseline 全栈执行例子（一次 GEMM UVM 页迁移）：算法层：无 ML 算法，数据页（4 KB 粒度）按 UVM 在 CPU-GPU 间迁移；系统框架层：CUDA cudaMallocManaged 分配 → GPU 缺页 → GMMU 聚合 fault buffer → nvidia-uvm driver（/dev/nvidia-uvm）中断式 batch 处理，TBNp 树状邻域预取按 2 MB VABlock 叶粒度迁移（Pt 阈值控制激进程度）；编译框架层：论文未明确说明（不涉及）；kernel调度层：CPU driver 单线程经 LCA 对每页 AES-GCM 加密（IV 同步递增），CE copy 命令入 push buffer，PCIe DMA + GPU 异步解密流水；硬件架构层：CPU TME-MK（AES-XTS，仅 40 cycle 开销）+ GPU CE/GSP/SEC2 硬件 AES 引擎，HBM 明文存储；结果：加密+同步位于关键路径，batch 间 driver 空闲 87%，CPU 加密吞吐 1.3 GB/s 成为瓶颈（加密可占 batch 处理 CPU 时间 70%+）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法：LÆGIS —— 在"GPU HBM 可信"假设下，用 HBM 内显式 IV Bank 把 IV 管理从 CPU-GPU 同步中解耦，再借此在 driver 空闲窗口做乱序机会性预加密。三个关键设计对应解决三个痛点：
    1. **HBM 内显式 IV Bank（解耦同步）**：每 GPU HBM stack 预留 8 MB（512K 行 × 128-bit）存 per-VABlock 的 IV Bank Entry（19-bit ID + 77-bit RV + V/D/O/R 控制位 + 9-bit CTR），IV 经 PDE0 中复用的 19 个未用位 ID 索引重建，加密公式 AES(K_h2d, RV||ID||blkidx||0^15)；CPU 侧 IV Bank 存于 TDX 保护内存或 HBM。加密不再依赖访问顺序同步，CPU/GPU 可独立乱序加密/解密，也无需完整性树（对比 Intel SGX 25% 元数据开销，此处仅 8 MB）→ 对应解决痛点①（消除同步关键路径开销）并恢复乱序加密灵活性。
    2. **预加密调度器（利用空闲）**：识别 true idle（批次间，平均 87%）与 false idle（fault preparation 期），用 AES 辅助线程在空闲窗口预加密候选页（fault buffer 下一批 / 顺序 CPU 驻留页 / 随机页），预加密密文直接提交（无需预测 IV，因 IV 可随机访问），页到达时跳过关键路径加密并批量写 bounce buffer 提升 PCIe 利用率 → 对应解决痛点②（driver 空闲浪费）与③（用空闲带宽摊薄低吞吐限制）。
    3. **片上 IV cache（16 项、256B SRAM）+ GPU 流水 AES 引擎**：IV 访问 20-cycle、per-page 粒度局部性高、开销可忽略；硬件开销仅 L2 的 0.02%，无新增密码引擎 → 保证解耦不引入新瓶颈。
    对比 PipeLLM（预测式加密，仍用同步 IV、误预测产生 NOP/丢弃及时间信道）：LÆGIS 的 IV 可随机访问，预加密密文总能提交，无误预测开销。
  - 论文方法全栈执行例子（同一次 GEMM UVM 页迁移，pIFN-LÆGIS）：算法层：页数据（4 KB base / 2 MB VABlock）迁移时加密；系统框架层：cudaMallocManaged 初始化时 driver 与 GPU 微控制器为每页分配 ID、CPU IV Bank 填 IBE（D/V 位置位），所有 UVM 页入候选集 S_a → GPU 缺页 → GMMU 聚合 fault buffer → driver batch 处理；编译框架层：论文未明确说明（不涉及）；kernel调度层：batch i 服务期间，预加密调度器在 false idle（fault prep）预加密 fault buffer 下一批候选页、在 true idle 顺序预加密 S_a 中 CPU 驻留页，加密时从 CPU IV Bank 按 ID 重建 IV（AES(K_h2d,RV||ID||blkidx||0^15)），完成后标记 ready 并从 S_a 移除；F_A 页到达时免加密直接提交，DMA 附带 128-bit MAC||ID → PCIe 大突发传输（64 GB/s 利用率提升）；硬件架构层：GPU 收到后 CE 用 ID 从 HBM IV Bank 取 IBE（经片上 IV cache 命中）→ GPU 流水 AES 生成 OTP 解密 → 明文写 HBM，首次到达页在 GPU 侧初始化 IBE；结果：CPU 加密移出关键路径、driver active 占比升至 88.3%，pIFN-LÆGIS 平均 2.74×（最大 5.05×）speedup over Baseline，与 pIdeal 差距 40.34%；结合 CPU 硬件 AES（X-pIFN）平均 3.57×、差距收窄到 22.31%。
