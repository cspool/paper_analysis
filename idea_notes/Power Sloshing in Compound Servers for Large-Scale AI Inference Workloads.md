## Power Sloshing in Compound Servers for Large-Scale AI Inference Workloads

- baseline方法是什么？
  - Baseline 是"静态独立功率上限 + 被动 DVFS"：compound AI inference server 的 CPU 与各 GPU 被分配固定 TDP（如 8 GPU×1kW + CPU 300W，文中 TDP 指软件可配置功率上限），服务器级电源控制仅由 vendor 内置 DVFS 在功耗逼近 TDP 上限时才调制 GPU 频率（最低可降到 55% f_GM），CPU 频率恒为最大值 f_CM；模型加载后即使无查询 GPU 也保持 f_GM，空闲期功率白白浪费。fleet 层面 60% 服务利用率不足其功率上限的 80%，而另一些组件被功率节流（Fig.3-6：同服务器 GPU 间功率高度不平衡，60% 服务器有 20-40% TDP 闲置可收割）。手动逐模型微调（§IV，频率扫描找满足 SLO 的最小功率点）可省 30-31% 功率，但每个模型/每次更新都要人工调参，大规模 fleet 不可扩展。要求：自动化、零应用修改、无应用级指标、仅用通用硬件计数器。
  - Baseline 全栈执行例子（一次 Model C1 推理请求，0.5×TDP_M 功率过订场景）：算法pipeline——请求经推荐类模型（DLRM 式，CPU 预处理/特征提取 + GPU embedding/MLP）前向，模型无改动；系统框架层——serving 框架分发请求，GPU 满载以 f_GM 运行、CPU 固定 f_CM，两者均无功率感知；编译框架层：论文未明确说明（无编译框架修改）；kernel调度层——无电源管理调度，仅 GPU driver 内置 DVFS 在功耗逼近 TDP 时被动降 GPU 频率（Fig.9c 最低 55% f_GM），降频后 GPU 利用率上升、请求排队、P99 延迟尖峰、SLO 在更低负载即违反（Fig.9b）；硬件架构层——GPU/CPU 恒以最大频率运行，GPU 被功率节流时其余组件（CPU/内存）功率仍上涨，总功率触顶、性能损失或功率浪费同时存在；芯片设计层：论文未明确说明（商用 Grace Hopper，无芯片结构改动）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = module-level power sloshing（Algorithm 1）：把服务器视作功率受限模块（cap P_M），闭环控制器以 GPU 利用率 u_G（应用无关信号，f_G·u_G≈Q_w 负载代理）为核心信号，动态在 CPU 与各 GPU 间重分配功率预算——u_G<u_min 时逐步降 GPU 频率收获闲置功率，u_G>u_max 时单步拉满 f_GM 保护突发；功率受限模式按功率模型 P_G(f_G,u_G) 估算 GPU 稳态功率、反推 CPU cap P_C=P_M-ΣP_Gi 施加 CPU power cap；非受限模式用线性映射 f_C=F(f_G) 协调 CPU DVFS。目标区间按模型历史利用率百分位选取（SLO-Optimized=P75 / Power-Optimized=P90），100ms 控制周期 + 非对称调整（快升慢降）保证响应与稳定。逐点对应解决 baseline 缺陷：(1) 静态独立上限→动态整体预算重分配，把松弛组件的闲置功率转给受限组件（Fig.13 把 CPU 预算转给 GPU），Performance/Watt 最高 1.83×，紧功率封顶下收益最大；(2) 盲目全速/空闲浪费→利用率驱动的降频收获功率，1 小时动态 trace 下 SLO-Optimized 省 11%、Power-Optimized 省 24%（贴近 Theoretical 的 30% 下界），且非线性的频率-功率关系（半载仅需 0.37×P_MQ）被主动降频利用；(3) 人工逐模型调参不可扩展→仅用通用硬件计数器 + 阈值策略的自动化方案（TABLE I：无 per-model setup、新模型即时适配、per-GPU 独立、部署开销最小、不依赖应用级指标）；(4) 突发负载 SLO 风险→快升慢降 + 超上限立即回满频率，SLO-Optimized 的 SLO 违反比例（5%）几乎与 Baseline（4%）持平。
  - 论文方法全栈执行例子（同一 Model C1 请求，固定模块功率 P_M）：算法pipeline——模型前向不变（DLRM 式推荐），无算法改动；系统框架层——serving 框架正常分发请求，host 上电源管理控制器每 100ms 采样 u_G（NVML），u_G 低于目标区间（如 SLO-Optimized 的 40-50%）则 GPU 频率降一档，功率受限模式下经 SetCpuPowerLimit 把 CPU 上限设为 P_M-ΣP_Gi(f_G,u_G)，把省下的预算转给受限 GPU；编译框架层：论文未明确说明（无编译框架修改）；kernel调度层——控制器作为运行时调度层：u_G>u_max 单步 f_GM、u_G<u_min 逐档下调，每 GPU 独立控制（8-GPU colocate 场景把松弛 GPU 的功率转给受限 GPU，per-GPU ~100µs/100ms 开销，tensor-parallel 场景建议组内统一频率防 straggler）；硬件架构层——GPU DVFS 硬件 100µs-数 ms 内完成频率迁移，GPU 稳态功率按 P_G(f_G,u_G) 变化，CPU 经 power-cap/frequency 接口执行，模块总功率始终 ≤P_M，非受限时 f_C=F(f_G) 协调 CPU 降频；芯片设计层：论文未明确说明（商用 Grace Hopper，无芯片结构改动；仅在 §VII 提出硬件级电源管理、更细粒度功率接口、负载均衡与电源管理协同的下一代平台指南）。
