## Accelerating MoE with Dynamic In-Switch Computing on Multi-GPUs

- baseline方法是什么？
  - Baseline 是 MoE 专家并行（EP）训练中的现有通信方案：1) DeepEP（SOTA 通信库）：Dispatch/Combine 用软件优化的通信算子，无 in-switch computing——同一 token 发往多个 GPU 时在源 GPU-交换机链路上重复传输、多个 GPU 的可聚合输出分别单独回传（冗余 ≈ 总流量 50%，通信占 MoE 层执行时间 70.4%）；2) NVLS（NVLink SHARP）：in-switch computing 但只能加速静态集合通信（AllGather/Reduce-Scatter，固定 target set + 对称地址），把 MoE 动态通信强行映射为静态集合通信产生 340% 无用流量；3) FasterMoE/Tutel（粗粒度计算-通信重叠）、CCFuser/COMET（细粒度 Dispatch-GEMM、GEMM-Combine 重叠）、DualPipe（跨层 pipeline）——只重叠隐藏通信，不消除冗余传输本身。
  - baseline 全栈执行例子（一个 token 的 MoE 层前向）：算法层：gate 网络选 topk=8 个专家；系统框架层：EP 把专家分布到 32 GPU，DeepEP 的 Dispatch 把 token 打包发往各专家所在 GPU（同一 token 在 GPU0-交换机链路被复制多次）、Combine 拉回各专家输出在软件侧加权求和；编译框架层：论文未明确说明（手工 CUDA kernel + 通信库）；kernel 调度层：Dispatch、GEMM-1、GEMM-2、Combine 按算子粒度隔离执行，COMET 等最多做算子间重叠；硬件架构层：NVLink 4.0 + NVSwitch 只做转发（NVLS 的多播/归约仅限静态集合通信）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = DySHARP：dynamic multimem addressing（通信原语）+ token-centric kernel fusion（通信感知调度）。(1) dynamic multimem addressing——对应 NVLS "静态"缺陷：请求包携带单个 multimem address（algebraic index，代数张量内索引跨 GPU 一致）+ 轻量 target expert list（flit0：48-bit 地址 + 1-bit stage + 15-bit target count），源 GPU LSU 取 target list、交换机按 target 复制裁剪转发/归约计数完成返回、目的 GPU Hub 硬件 memory manager 用 AL Table/AL TLB 把 algebraic index 映射为各 GPU 本地 layout index（VAddr = VBase + LIdx×bsize + MAddr%bsize）——交换机多播消除 Dispatch 冗余、交换机归约消除 Combine 冗余，且避免 explicit addressing 的 header 膨胀（payload 效率 80% vs 69%）与软件远端内存状态管理开销（>5% 性能损失 + 10-20% GPU 算力）；加权归约通过在 GEMM-2 epilogue 先乘 gate 权重、交换机做无权重归约实现。(2) token-centric kernel fusion——对应"流量削减不对称无法变 speedup"缺陷：token tracker（TS/TID/OR 三表）在 token/tile 粒度检测 readiness 边界，megakernel + persistent TB 把 SM 分 4 组，使 Dispatch（GPU→交换机，多播后变轻）与 Combine（交换机→GPU，归约后变轻）并发执行，互补的流量方向合并、双向带宽利用率提升。单独 dynamic multimem addressing（DySHARP-Basic/COMET）削减近 50% 流量但不加速，单独 kernel fusion 不超过 COMET，二者结合才把流量削减转化为 1.79× speedup。
  - 论文方法全栈执行例子（同一 token）：算法层：gate 网络不变（加权求和在 GEMM-2 epilogue 完成，语义等价）；系统框架层：CUDA Runtime 扩展 cuDyMulticastCreate/cuDyMulticastBindAddr 注册 multimem 区域，megakernel 内算子以任务形式调度；编译框架层：论文未明确说明（megakernel 手工实现，无编译器改造）；kernel 调度层：dymultimem.st 把 token 单次发往交换机、交换机多播到 topk 个专家 GPU，GEMM-1 按 tile（tsize=128）就绪即发、GEMM-2 紧随、Combine 的 dymultimem.ld_reduce 在 nReady==topk 时发射并在交换机内归约，Dispatch 与 Combine 并发双向流动；硬件架构层：NVSwitch 增强 Route/Reduction Logic（<0.01mm²、+1 cycle）、GPU Hub AL TLB/AL Table 与 SM MultimemQ（合计 0.198mm² ≈ H100 die 的 0.024%）。结果：vs DeepEP 端到端最高 2.31×（几何平均 1.93×）、vs COMET 最高 1.79×、vs NVLS 最高 5.12×；流量 vs DeepEP -50%、纯通信性能 >90% ideal；4-64 GPU 扩展与推理 power-law 分布下优势保持；多节点 IB 扩展（dymultimem 跨 NVSwitch 与 Quantum IB Switch 全局路由）同样有效。
