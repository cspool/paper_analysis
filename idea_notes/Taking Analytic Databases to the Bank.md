## Taking Analytic Databases to the Bank

- baseline方法是什么？
  - Baseline 是 CPU 为中心的 OLAP DBMS 与一般 PIM 算子研究两类：(1) 端到端基线——DuckDB（state-of-the-art 分析型 DBMS，论文 ref [63]）与手调多线程 AVX512 C++ 单块（monolithic/fused）query kernel（代表 host 最大性能，论文基准）；(2) CPU 侧 OLAP 执行栈与规划启发式——列存（column-store）、select 输出 index array 或 bitvector、hash join（build-probe 两阶段）、物化策略（early/late materialization）、查询优化启发式（低选择性优先 + 最小化 hash 表以适配 CPU cache + left-deep join 树，ref [61][19][12]）；(3) 既有 PIM/DB 研究——只评估单个算子（select/join/partition/hash）隔离性能或小范围端到端（UPMEM、AxDIMM 等），忽略算子链之间的数据格式不兼容、relayout 开销、bank 内存限制与 CPU 中心假设失效。
  - Baseline 全栈执行例子（SSB Q3.1 三 join 在 CPU/DuckDB 上）：① 算法pipeline 层——列式扫描 LINEORDER 各列，select 输出 index array，hash join 先 build（把 build 侧值与 payload 插入 hash 表）后 probe（探测侧逐值 hash 查找），物化中间结果，三个 join 按 CPU 启发式排成 SDC 序（hash 表 6MB/400KB/11KB 尽量塞进 LLC/cache）；② 系统框架层——DuckDB 解析→优化器（低选择性优先、最小 hash 表）→执行器逐算子流水；③ 编译框架层——论文未明确说明（DuckDB 的 JIT/向量化执行，无自定义编译器）；④ kernel 调度层——host 多线程 AVX512 C++ kernel：扫描/过滤/哈希/探测全部在 CPU 上，40 线程并行，数据从 DRAM 经 90GBps 外部带宽搬入 cache/寄存器，hash 表随机访问依赖 L2/L3 命中；⑤ 硬件架构层——2× Xeon Silver 4114 + 384GB DDR4，PIM 内存仅当普通内存用，全部计算走 von-Neumann 数据搬运。结果：DuckDB 比手调 C++ 慢 2.3×，CPU 最优 join 序 SDC 在 BLIMP 上是第 4 差（比最优慢 23%），PIM 上端到端差距可达 40%。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文提出 BLIMP（bank 内 RISC-V 核 PIM）上的全栈协同设计，把计算下沉到内存 bank，四项设计对应解决 baseline 缺陷：(1) PIMDT 存储格式——指定列以 PIM 友好布局常驻（整字单 bank 可访问、支持查询时按元素边界 chunk 适配 32MB bank），消除查询时 relayout，直接解决"host 侧 relayout 29GBps/90GBps 瓶颈 + 隔离算子研究反复 relayout 送数据回 CPU"的缺陷（隔离计划平均 22% 时间在 relayout，PIM-optimal 比隔离快 3.2×）；(2) BLIMP 优化哈希表——row buffer 对齐 + 2 的幂桶数 + 冲突 slot/桶链空间局部性 + 轻量乘法哈希 O(1) 换算 row 地址，解决"CPU 哈希表在 PIM 上 row buffer 抖动/指针追逐/无法利用有限 bank 内存（传统 hash join 需更多空间换低时延，不适用于预分配 scratch 受限的 PIM）"的缺陷；(3) PIM 特定算子实现——select 位图输出（BLIMP-V 12.9×）、hash join 由 host 建表 + relayout 广播 + BLIMP 探测（3.0×，大表按分区多轮 build-probe）、聚合（非分组 33.7×），利用 12.5TBps bank 内带宽 + 512 核并行，解决"CPU 受 90GBps 外部带宽限制"的缺陷；(4) PIM 感知查询规划——晚物化（bitvector 链式传递、PIM 内 AND 合并双选择，物化时机按整体选择性在 Hybrid/Late 间选）、低选择性优先 join 顺序（PIM 中 hash 表 >几 KB 后大小不再影响性能，选择性成为唯一主驱动，CPU 的"最小 hash 表"启发式失效）、避免 bushy join 多次重建 hash 表，解决"CPU 启发式在 BLIMP 上比最优差 40%（Q3.3）"与"隔离算子外推不体现算子链/物化/编排交互"的缺陷。
  - 论文方法全栈执行例子（SSB Q3.1 三 join C/S/D 在 BLIMP 上）：① 算法pipeline 层——PIMDT 布局的 LINEORDER 外键列（lo_orderdate/lo_partkey/lo_suppkey/lo_custkey）与过滤列（lo_quantity/lo_discount）常驻 bank；PIM 感知优化器按低选择性优先排成 CSD 序（20%/20%/86%）；每个 join 由 host 预处理（建 row-buffer 对齐哈希表、把 PIMDT 切 chunk 适配 32MB bank）；② 系统框架层——解析不修改，查询执行器识别 PIMDT 列上的算子：支持则走 PIM 算子工作流（预处理→relayout 载入→执行→部分物化/原位保留），不支持则回退 host；③ 编译框架层——论文未明确说明（BLIMP kernel 为 RISC-V/RISC-V-V 汇编/微 kernel，经同组 dovedevic/blimp 框架的 /compilation 交叉编译与 /relayout 例程）；④ kernel 调度层——kernel+分区+hash 表经 relayout 载入 512 个 bank，BLIMP 核 compute mode 下以 1KB row buffer 粒度执行 SEMIJOINPROBE（BLIMP-V 向量化 hash、串行探测，位图结果留在 bank 内链给下一算子），最后一算子完成后 host 才取回输出（按选择性选 Hybrid/Late 物化）；⑤ 硬件架构层——计算在 DDR4 bank 内就地执行，bank 内 12.5TBps 带宽替代 90GBps 外部带宽，跨 bank 数据经 host 读-写中转，仅 kernel 与 relayout 后数据走外部总线。结果：PIM-optimal 比 CPU-optimal 快平均 28%（Q3.3 达 40%），比隔离计划快 3.2×，BLIMP-S/BLIMP-V 端到端相对手调 C++ 基线 1.4×/2.3×、相对 DuckDB 3.1×/5.8×。
