## Bumper: Hinting Instruction Usefulness for Robust Unified Caches

- baseline方法是什么？
  - Baseline 是工业级 cycle-accurate 模拟器（ARM ISA）建模的现代高端移动 CPU 前端+cache 体系：BPU（64KB TAGE-SC+iTAGE、1K-entry L1-BTB、16K-entry L2-BTB、RAS）与 IFU 经 32-entry FTQ 解耦，FDIP 沿 Prefetch Head 用剩余 L1I 带宽向 L1I 发指令预取；统一 L2C 为 6MB 12-way、替换策略 DRRIP（RRPV 0=最可能复用，3=最不可能，按行类型优化插入/提升）；L1I 192KB 6-way pLRU、与 L2C 非一致无写回。Baseline 缺陷：移动应用 code footprint（0.5–2.3MB）超出 BTB 容量，BPU MPKI 平均 8.0 且主要由 BTB 容量 miss 引起，前端重定向（re-steer）导致 >50% 插入 L2C 的代码行来自错误执行路径；平均 20.3% 的 6MB L2C 容量被 useless 代码行占据（Definition 1：被淘汰前行内无任何指令提交），且 useless 行生命周期与 useful 行相当，长期挤占数据/MMU/useful 代码行的复用机会；移动应用平均 41% 周期 front-end bound。
  - baseline 全栈执行例子（一次错误路径指令预取污染 L2C）：BPU 因 L2-BTB miss 给出错误目标 → FTQ 追加错误基本块 → FDIP 沿 Prefetch Head 用空闲 L1I 带宽预取错误路径代码行 → L2C miss → 按 DRRIP 默认插入策略以正常优先级安装，与正确路径代码/数据行公平竞争 → 该行随前端重定向在 L1I 中被冲刷、行内无任何指令提交，但仍以正常生命周期驻留 L2C 直至自然淘汰。模型层：无（无 ML 模型，负载为匿名真实移动应用）；系统框架层：论文未明确说明（纯微架构方案，无软件框架修改）；编译框架层：论文未明确说明；kernel 调度层：论文未明确说明（CPU 前端/cache 运行时管理，无 GPU kernel）；硬件架构层：BPU/FTQ/FDIP/L1I/统一 L2C（DRRIP 替换策略）微架构。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - Bumper 用提交（commit）信息区分 useful/useless 代码行并驱动 L2C 替换策略，四个设计点逐一对应 baseline 缺陷：(1) 所有代码行以最低优先级 RRPV=3 插入、仅被识别为 useful 的行提升到 RRPV=0——对应 useless 行长期占容量且淘汰不快的缺陷，同时避免"全部低优先级插入"误伤 useful 行（naive 全低优先级插入使 IPC 降 13.9%）；(2) 以"行内首条提交指令"为 usefulness 代理而非每条提交指令都发信号——L1I tag 加 1-bit send_hint、L2C→L1I 填充响应加 1-bit l2_vulnerable_fill 标志，保证仅 L2C 中处于 RRPV=3 的行才可能发 hint、且每行 L1I 生命周期内至多一次提升信号——对应"L1I hit 不是 usefulness 可靠代理（47% useless 行经历过 L1I hit）"与"逐指令发 hint 带宽/能耗过高"的缺陷；(3) 退休点无 PA、L2C 为 PIPT 的硬件约束下，退休时复用恢复路径已有 VA 回传 IFU，HL1Q 机会式访问 ITLB 完成 VA→PA 翻译，经 L1I tag 检查/清除 send_hint 位后由 HL2Q 与 LSU/数据预取请求仲裁、以 PA 提升 L2C 行——对应"从 Retire 直接发 hint 到 L2C 不可行"的缺陷；(4) L2C 管理规则中 IFU hit 仅当 RRPV<3 才提升，RRPV=3 的行保持 3 等待 commit hint——对应 DRRIP 无法区分"新插入待提升/无用/老化"三类 RRPV=3 行的缺陷。总存储 422B，随 L1I 而非 L2C 规模扩展。
  - 论文方法全栈执行例子（一条正确路径指令行从 fetch 到提升）：BPU 预测基本块 → FTQ → IFU 向 L2C 发需求请求 miss → 以 RRPV=3 安装、填充响应置 l2_vulnerable_fill=1 → L1I 填充该行并置 send_hint=1、该位随行内首条指令/uop 沿流水线（ROB 1-bit 标志）传播 → 该指令退休（retire）→ VA 回 IFU → HL1Q 机会访问 ITLB 得 PA → 访问 L1I tag：send_hint=1 则清除并向 L2C 发 Hint Request（HL2Q 仲裁）→ L2C hit → RRPV 提升到 0，获得最长生命周期直至老化再次降到 3（再次被使用需重新发 hint）；错误路径行：行内无指令提交 → 无 hint → 保持 RRPV=3 → 快速淘汰，腾出容量给数据/MMU/useful 代码行。结果：平均加速 6.5%、较 Emissary +7.5%、FTQ-Size-OPT +5.4%（UDP 本身仅 1.2%）、Bumper+FTQ-Size-OPT 再 +0.8%、Bumper+DJOLT 达 9.7%；useless 行生命周期 -57.9%、useful 代码行 +52.5%、其他行 +21.5%；useless 占用 20.3%→9.5%。模型层：无（无 ML 模型）；系统框架层：论文未明确说明；编译框架层：论文未明确说明；kernel 调度层：论文未明确说明（CPU 前端硬件机制，无 GPU kernel）；硬件架构层：L1I tag/ROB 位扩展、HL1Q/HL2Q、ITLB 机会访问、L2C DRRIP 插入/提升规则修改。
