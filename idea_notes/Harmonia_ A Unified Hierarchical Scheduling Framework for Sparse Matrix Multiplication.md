## Harmonia: A Unified Hierarchical Scheduling Framework for Sparse Matrix Multiplication

- baseline方法是什么？
  - Baseline 是稀疏矩阵乘法加速器上的三类孤立调度 + 固定数据流硬件：(1) 固定数据流加速器（SIGMA、HighLight）——PE 微架构绑定假设的稀疏模式，模式/密度偏离设计假设时利用率骤降（SIGMA 的 Flex-DPE 阵列在高稀疏下 <10% 利用率）；(2) 灵活/可重构加速器（Flexagon、Trapezoid、VersaAccel）——支持多数据流模板但灵活性仅停留在硬件结构层，缺系统机制在运行时选择数据流（Flexagon 75% 面积是非计算结构；Trapezoid 只重构 DN/MRN 两个部件，不能按运行时稀疏变化自适应）；(3) 单层调度器——Misam 只做 tile 内数据流选择（忽略 tile 间依赖与共享 SRAM 压力）、HYTE 只做全局 tile 编排（假定固定 tile 内数据流）、Vesper 用静态解析模型跨层建模但假设均匀稀疏（tile 级稀疏变化导致 SRAM 流量高估 3.7×/3.1×，错误选择 OutP）。
  - 全栈执行例子（baseline：Vesper 静态调度 + Trapezoid 硬件）：算法层——稀疏矩阵乘法 C=A×B 用 CSR/CSC 表示，按全局平均密度离线选一个数据流；系统框架层——论文未明确说明（无 Serving/运行时系统）；编译框架层——论文未明确说明（无编译器，静态分析离线完成）；kernel调度层——Vesper 离线按全局平均稀疏度估计 OI，固定选 OutP 数据流与 64×64 方块，tile 内数据流不可变，tile 形状不可变；硬件架构层——Trapezoid 32-row PE 阵列用 DN/MRN 执行固定数据流，无运行时反馈；芯片设计层——论文未明确说明。遇到 bcsstk10 的局部稠密 tile 时 OutP psum 溢出本地 buffer 频繁 spill 到 SRAM，而静态模型仍认为 OutP 最优（实际 OutP 延迟为 Row 的 1.6×，InP 的 SRAM 流量才是最小）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法为三层静态-动态协同调度框架 Harmonia：(a) 静态分析层——用粗粒度描述符（矩阵形状、全局密度、datatype）枚举候选 tile 形状，以 OI=OPs/Bytes 为目标、受 SRAM 可行性约束 (2) 过滤，输出基线块形状/遍历顺序/SRAM 分区，提供 1.0× 安全性能下限并缩减在线搜索空间；(b) 动态 Profiling 层——块进 SRAM 后用 tile 精确 nnz 与行/列密度、聚类采样，细化 tile 形状（低密度扩张、高密度收缩、聚类对齐边界）并按 tile 特性选择 InP/Row/OutP；(c) 动态 Tuning 层——硬件反馈计数器（SRAM pressure、psum spill、MRN merge-depth、PE stall）经成本模型 Gain>α·Cost 触发数据流切换与块内微重切块，滞回（T=2~4 周期）防振荡、最坏情况回退 1 次重构延迟（50 cycles）。硬件仅加反馈计数器（<0.5% PE 阵列面积）、重构引擎、tiling 控制器（合计 3.3% 面积），PE 数据通路与 MRN/DN 逻辑不变。直接对应解决：静态层解决 HYTE 无全局规划的盲目性（提供安全起点与 OI 最大化），动态 Profiling 解决 Vesper 均匀稀疏假设的失准（按 tile 实测细化），动态 Tuning 解决 Misam 只局部优化、无法感知硬件信号（SRAM 压力/spill/merge depth 反馈闭环），硬件侧低成本反馈解决 Flexagon/Trapezoid 只有结构灵活性无系统自适应的缺陷。
  - 全栈执行例子（Harmonia 处理 bcsstk10 同一矩阵）：算法层——稀疏矩阵乘法仍用 CSR/CSC/bitmask 表示，但 tile 形状与数据流随局部稀疏度动态变化；系统框架层——Harmonia 本身即运行时调度系统，SW-HW 调度接口把 microarchitectural 信号翻译成 tile 级调度动作，无 Serving 框架；编译框架层——论文未明确说明（静态分析离线完成，非编译器）；kernel调度层——静态层选 (64,128,64) 基线块，动态层按 tile 实际密度细化：低密度 tile 扩张形状提升复用、高密度 tile 收缩防 psum spill，按行密度方差/聚类选数据流；硬件架构层——Trapezoid 数据通路不变，DN/MRN 在 tile 边界重编程（20–50 cycles），反馈计数器观察执行；遇到 OutP psum 溢出时 Tuning 层在 tile 边界切到 Row（或稠密时 InP），消除 SRAM spill 与 stall；芯片设计层——论文未明确说明。结果：bcsstk10 上消除 3.7×/3.1× SRAM 流量高估，16 个 workload 平均 1.75× 加速（orani678 3.46×）、端到端 DNN 1.87×、SRAM 流量降 32%、能耗 -40%，动态开关总 stall <1%，性能接近 2.03× 静态最优 oracle 上界。
