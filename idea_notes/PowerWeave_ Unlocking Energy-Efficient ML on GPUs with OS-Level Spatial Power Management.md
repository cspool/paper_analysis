## PowerWeave: Unlocking Energy-Efficient ML on GPUs with OS-Level Spatial Power Management

- baseline方法是什么？
  - Baseline 是设备级（device-wide）DVFS 电源管理，代表为 LithOS（SOSP'25 SOTA，SOSP'25 论文 [12]）与 default GPU DVFS policy。现代 GPU（B200）只暴露一个整卡全局频率旋钮：默认全速运行、功率逼近 TDP 时固件被动降频/热节流。LithOS 做 TPC 粒度空间多租户，但 DVFS 仍只选一个覆盖所有 collocated 工作负载需求的整卡频率；更早的工作（GEEPAFS [63]、μ-Serve [46]、POLCA [43]、DynamoLLM [51]、throttLL'eM [24]）同样只在设备粒度控制频率。核心缺陷（论文 Motivation）：①单模型内部异构——LLM 的 prefill 是 compute-bound、对频率敏感，decode 是 memory-bound、对频率几乎不敏感，整卡频率被迫跟踪最苛刻的 prefill，decode 被过度供给浪费功率；②多模型/多租户异构——不同模型最优频率不同（Motivation 中 Qwen3-14B 最低能耗在 ~1000MHz、Qwen3-8B 与 Llama-3.1-8B 在 ~750MHz），一个全局频率必然向最苛刻租户看齐；③热节流相互干扰——高负载应用把整卡功率顶到 TDP、固件全局降频，低负载同卡应用无辜被拖累（Fig. 4 频率振荡）；④动态负载变化——请求率（RPS）波动、SLO slack 变化时设备级 DVFS 无法按域差异化响应。
  - Baseline 全栈执行例子（B200 上 disaggregated prefill，prefill/decode 各占半卡 TPC）：算法pipeline——Llama-3.1-8B 请求先跑 prefill（密集 GEMM，TTFT SLO 0.5–2s）再逐 token decode（memory-bound，TPOT SLO 30–100ms），模型本身无改动；系统框架层——vLLM 0.10.2 serving，请求按 Azure trace 到达，LMCache/NIXL 管 KV cache 与传输，LithOS TPC 调度器把 prefill/decode 分区到不同 TPC；编译框架层：论文未明确说明（无编译框架修改）；kernel调度层——无电源感知调度，LithOS 按所有 collocated 阶段需求选一个全局频率，decode 内核继承 prefill 需要的高频率（decode 内核在高频下几乎不加速却按 f 立方耗更多动态功耗）；硬件架构层——整卡单一 DVFS 域，固件在功率触顶时全局降频（默认策略下 Qwen3-32B-FP8 有 52.9% 实验时长被节流），decode 低负载阶段拖累 prefill 的 TTFT；芯片设计——B200 双 die，仍只有设备级频率域（论文未明确说明细粒度域）。结果：LithOS 平均节能仅 13%，Qwen3-32B-FP8 场景几乎无收益。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = PowerWeave，首个基于 OS 级电源管理控制平面的空间 DVFS：把频率控制解耦到 GPU 的空间域（per-TPC 直至 per-SM 级独立频率域），四组件协同：(1) Online Kernel Profiler——透明拦截 kernel launch（CUDA driver API 拦截 + CUDA event 异步计时），按 kernel identity（函数句柄+grid/block+shared mem+stream）在线学习每 kernel 的频率-延迟曲线，新配置用 wave 比例预测 l=waves×(l_old/waves_old)；(2) Frequency-Latency Scaling——一阶 Taylor 近似合成 per-application 缩放函数 f(k)=f_max/S, S=1+k/Σ(s·w)（w=运行时权重在线更新、s=频率敏感度因子固定）；(3) DVFS Controller——按 Governor 给的 performance slack 为每域选频率；(4) Governor——用户态库（import 进 vLLM/SGLang），监控每域 RPS、尾延迟与 SLO，算 slack s₂=((1−s₁)×l₁)/SLO，SLO 违反时拉满受影响域频率快速纠正。硬件侧论文给出可行性证据：DLDO 稳压器 + 2048-bit 电压域跨界同步 + PLL 时钟生成，per-SM 148 域面积开销 <0.5% die、功耗相对 TDP 可忽略。
  - 逐点对应解决 baseline 缺陷：prefill/decode 异构 → 同一模型内部按阶段解耦，prefill 域高频率满足 TTFT、decode 域低频率利用 TPOT slack（Qwen3-32B-FP8 因 TTFT slack 极小而 decode 被强制过供给，相对 LithOS 达 8× 节能）；多租户异构 → 每租户独立频率域，高需求租户不抬高其他租户频率（多租户平均 28% vs LithOS 10%，最差 6%）；热节流干扰 → 局部化节流：高负载域自己降频、低负载域维持高频率，全部工作负载热节流被消除（Qwen3-32B-FP8 节流时间 52.9%→2%，Qwen3-14B 与多租户完全消除）；动态负载 → Governor 连续监控窗口跟踪 RPS 波动/尾延迟，slack 在线重算 + 5% profiling 阈值触发重训，零 SLO 违反；agentic 流水线 → 慢 stage 域保持高频率、快 stage 域降频，吞吐不降前提下平均节能 19%、TPJ +20%。
  - 论文方法全栈执行例子（同一 B200 disaggregated prefill，Llama-3.1-8B + Azure trace）：算法pipeline——请求前向不变（无算法改动），但 PowerWeave 用 kernel 级画像区分 compute-bound prefill 内核与 memory-bound decode 内核；系统框架层——vLLM 0.10.2 照常 serving，Governor 被 import 进框架、每监控窗口经几行代码读取每域 RPS 与尾延迟，Interposer 在框架与 driver 之间透明拦截每次 kernel launch（CUDA event 对异步计时，不阻塞关键路径）；编译框架层：论文未明确说明（无编译框架修改）；kernel调度层——Online Kernel Profiler 先全速建 baseline 再扫 1965–915MHz 共 12 个频率点（分布到约 150 个请求，单请求不感知全成本），生成每 kernel 频率-延迟曲线与新配置预测，Frequency-Latency Scaling 按实时 prefill/decode 比例更新权重 w，DVFS Controller 为 prefill 域与 decode 域分别选频率（TTFT 趋近 SLO 时只升 prefill 域、TPOT 有 slack 时 decode 域保持低频）；硬件架构层——空间频率域（仿真中用多 GPU+TPC 分配等价一个整卡模拟，能量按未分配 TPC 份额扣除 idle ≈140W），频率经 NVML 写入，prefill GEMM 高频率执行、decode 内核低频率执行，各自域内无跨域节流；芯片设计——论文通过面积模型论证 per-SM/per-GPC 频率域硬件代价（<0.5% die 面积、DLDO 78µW/域、boundary 5.65W 上界），并讨论与 GPU 固件的前瞻性频率请求队列接口。结果：平均节能 28%（最高 38%、Qwen3-32B-FP8 相对 LithOS 8×），热节流消除、零 SLO 违反；agentic 场景平均 19% 节能且吞吐/TPJ 提升。
