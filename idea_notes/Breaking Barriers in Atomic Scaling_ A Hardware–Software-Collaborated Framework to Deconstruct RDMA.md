## Breaking Barriers in Atomic Scaling: A Hardware–Software-Collaborated Framework to Deconstruct RDMA Atomic (Fusa)

- baseline方法是什么？
  - Baseline 是 RNIC-Only（HCA Atomic 模型）：所有 RDMA CAS/FAA 由服务端 RNIC 内部锁定表执行——地址哈希映射到 512 槽之一，同槽请求在多个 PU 间串行，PU 用 PCIe Read（取旧值）+ PCIe Write（回写）完成 RMW。另有两条被论文证否的备选：(1) Global Atomic（PCIe Atomic 旁路锁定表，原子性交给 PCIe 子系统）——受 Atomic Completer Engine 容量限制，吞吐只有锁定表的 34.0%，且不支持 masked CAS 等增强原子；(2) HERD RPC 全量卸载到服务端 CPU——two-sided SEND/RECV 开销大，均匀负载下比 RNIC-Only 慢 4.7×。痛点：倾斜负载下热地址集中于少数槽，串行化使原子吞吐最高下降 94.5%；无方案能同时兼顾"低争用时的硬件快路径"与"高争用时的软件灵活执行"。
  - baseline 全栈执行例子（一个 RDMA CAS）：客户端应用调 ibv_post_send → 用户态驱动直发 one-sided CAS 到 RNIC → RNIC 按地址哈希定槽、槽锁仲裁（同槽串行）→ PU 发 PCIe Read 取旧值 → PCIe Write 回写新值 → 生成 CQE 通知客户端；热点 key 都落在同一槽时其余请求排队等待。算法层：无 ML 算法（负载为 KV/事务系统的同步原语访问流）；系统框架层：libibverbs 用户态驱动直通 RNIC；编译框架层：论文未明确说明（无编译器改造）；kernel 调度层：锁定表槽级硬件调度（无软件调度）；硬件架构层：RNIC 内部锁定表/多 PU/PCIe RMW（论文不改硬件，仅测试台测量）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = Fusa 硬件-软件协同框架，三层设计一一对应痛点：(1) 细粒度争用感知分发（group 级调度）——把每个槽按地址额外 g 位细分为 group（默认 8,192 组），每组 64-bit 计数 + 1-bit 分发位，以 watermark（全组平均请求数）判定争用、按 CPU 容量 C 选择性卸载最热组的请求到 CPU、其余留在 RNIC → 对应"RNIC-Only 倾斜负载槽争用（全串行）"与"HERD 均匀负载 RPC 开销（全卸载）"两个极端，同时保留硬件快路径与软件灵活执行；(2) 正确性融合分发（consensus 切换）——客户端 lazy 多 QP epoch 同步 + 服务端新旧策略 XOR 一致位、reject 重传，48 µs 完成切换，TLA+ 模型验证 >400 亿状态 → 对应"动态切换策略时新旧策略混用导致 RNIC 与 CPU 并发写同一地址"的一致性风险；(3) 透明 RPC——分发逻辑放驱动层（LD_PRELOAD 覆盖 libibverbs），coroutine-friendly RPC（WRITE+RECV + CQE 异步）→ 对应"RPC 方案需改应用、轮询式 RPC 阻塞协程切换"的落地障碍。
  - 论文方法全栈执行例子（同一 RDMA CAS）：应用调 ibv_post_send → Fusa-Driver 拦截（qp_id、group_id = address % 8192、计数/epoch 更新、读 strategy bit）→ bit=0 走 RNIC：inflight++、槽哈希 + PCIe RMW、CQE 递减 inflight；bit=1 走 CPU：Fusa-RPC 转 WRITE+RECV 写 server 请求缓冲、server 线程出队并执行原子、SEND CQE 返回 → 每 1 s Fusa-Agent 汇报统计、Fusa-Server 重算策略并广播、客户端共识切换（Wait_sync + reject/重传 + inflight 归零等待）。算法层：无 ML 算法（无模型推理）；系统框架层：修改 Mellanox 用户态驱动（mlx5_create_qp/mlx5_post_send + LD_PRELOAD），应用零修改；编译框架层：论文未明确说明（无编译器改造）；kernel 调度层：group 级运行时调度 + WR_ID/inflight 在途跟踪 + Fusa-RPC 异步传输；硬件架构层：不改硬件，仅在 PCIe Atomic 启用时把 Completer Engine 当第三后端做混合卸载（兼容 Global Atomic）。结果：YCSB 微基准吞吐最高 4.6×（各更新比平均 2.8×，U10R90 43.9 vs 14.8 Mops/s；θ=0.99 下 4.8×；≥4 server 线程 4.8–7.0×）；RACE 上 14.7×、P99 -97.8%；DrTM 上 7.1×、P99 -89.0%；换策略共识 48 µs、驱动开销 +18 ns（123→141 ns）。
