## HartBreaker: Deterministic Fuzzing of Multi-Hart RISC-V CPUs with Non-Deterministic Programs

- baseline方法是什么？
  - baseline 为两类既有多核测试手段：(1) litmus tests（litmus-tests-riscv、CHERI-Litmus、cva6-litmus，PULP 组 1314 个 bare-metal 测试）——小并发程序，聚焦单一内存一致性场景，Table II 显示其指令多样性极低（无 exception、FPU、特权切换、IPI、部分类别仅极小子集），无法触发需要特定微架构条件的复杂重排序（实测这些测试在五个 CPU 上零 bug）；(2) 单核 CPU 硬件 fuzzers（Cascade、DifuzzRTL、ProcessorFuzz、RISCVuzz、TestRIG、INSTILLER 等）——随机生成高指令多样性的确定性程序，依赖差分测试（Spike/Sail ISS 或 reference hart）验证，要求程序执行确定（一个起点一个终点、无死代码）；RISCV-DV 是唯一支持自动生成多 hart 程序的工具，但无法验证非确定性执行。形式化方法（PipeCheck、RTLCheck、TriCheck）穷举微架构状态但需手工抽象硬件模型、难扩展到带推测执行/缓存的复杂 CPU。
  - baseline 全栈执行例子（Cascade 单核 fuzzer 的一个测试程序）：算法层——随机生成确定性的单 hart 汇编程序（每指令恰好一个后继状态，路径预先已知），覆盖 ALU/branch/fence/exception/privilege switch 但无共享内存并发与 IPI；系统框架层——无 Serving 框架（bare-metal 程序，无操作系统/运行时）；编译框架层——论文未明确说明（程序生成是随机汇编器，非编译框架）；kernel调度层——程序在单 hart 上顺序执行，无跨核调度；硬件架构层——同一二进制在 DUT RTL（Verilator 仿真）与 Spike ISS 上分别执行，逐指令比较提交状态；一旦引入第二个 hart 的共享内存读写或 IPI，store/load 重排序、中断到达时刻使 ISS 与 RTL 提交状态必然发散（ISS 无法预测非确定性交错的合法结果），差分测试即失效；litmus 路径则因固定微架构状态与低指令多样性，无法覆盖 CoRR 这类需要"三个并发 load + 延迟地址计算 + 一致性 probe 时序"的 bug 场景（B1/N1 需数小时 core-time 才触发，且依赖 store buffer/load 重放路径等结构）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 = HARTBREAKER，用三类 *determinism anchors* 在保持程序级确定性的前提下放开指令级非确定性，并把非确定性数据流验证转化为等价 litmus test 交给 MCM solver。逐条对应 baseline 缺陷：(1) cf-anchors（control-flow anchors）对应"fuzzer 无法处理中断/IPI 控制流非确定性"——接收 hart 进入 confined landing zone 后发信号，发送 hart 才发 IPI，接收方任意周期 trap，landing zone 内循环重建相同数据、退出时架构状态与中断到达时刻无关，从而把 IPI 注入变成可验证的确定性程序结构（bug 使架构不变性破坏→控制流跳飞→hang/timeout 检测）；(2) df-anchors（data-flow anchors）对应"非确定性数据值使差分验证失效"——load 结果寄存器与 mepc 被标记隔离并重置（xor/sub 清零保持句法依赖），非确定性数据不污染控制流，但内存操作依赖关系保留以触发重排序；(3) sync anchors + trace→litmus 翻译 + Dartagnan 后端对应"litmus 多样性不足 + MCM 求解 NP-complete 无法规模化"——把任意测试程序按图 7 依赖构造法翻译成等价 litmus test（df-anchor 保证 store 值确定、静态依赖已知、trace 给出 load 返回值），用 state-of-art MCM solver（自研仅 ~10 内存操作，Dartagnan ~100）按分区验证，窗口 10–100 内存操作即可触发全部已发现 bug；(4) 与 RISCV-DV 对比证明多样性不损失——三 hart BOOM v3 上 15,872 coverage points，HARTBREAKER 达到与 RISCV-DV 相近覆盖率且附带 IPI/内存模型校验/确定性中断注入能力，关闭验证时显著更快。
  - 全栈执行例子（一次触发 B1 的多 hart 测试程序，穿过全部层次）：算法层——生成器随机产生三 hart 汇编：hart 1 含"store(x)→[复杂地址计算延迟]→load(x)#0→...→load(x)#1→...→load(x)#2"的序列（df-anchor 用 xor/sub 清零保持依赖），hart 0 并发 store(x)，hart 2 做独立访存制造噪声，cf-anchor 把一个 IPI 注入进 hart 1 的 landing zone；系统框架层——无 Serving/OS，bare-metal ELF 由 HARTBREAKER 工具链（hartattack/）生成；编译框架层——论文未明确说明（程序生成为随机汇编生成器，非编译框架）；kernel调度层——三 hart 各自执行指令流，共享内存无同步，store buffer/load 重放/LSU 一致性 probe 由微架构时序决定交错（图 16：load#1 地址计算被多周期指令延迟→load#2 先成功→hart 0 的 store 触发 coherency probe 无效化 cache line 但 load#2 无重放路径→load#2 提交陈旧值）；硬件架构层——二进制先在 Spike ISS 跑取确定 store 值，再在 Verilator 仿真的 BOOM v4 上跑，从 commit log 收集三个 load 的返回值（x1=0,x2=1,x3=0），翻译成等价 litmus test（表 V），Dartagnan 判定该结果违反 CoRR/load value axiom（RVWMO 下不存在合法执行）⇒ 报告 bug B1；同样流程在 NaxRiscv 发现 N1（同 hart store 后异宽 load 使 store-to-load forwarding 失效、store queue 释放时序 + 跨核 probe 造成 stale 提交）、N2（CLINT 只接受全字 store）、Toooba T1（mret 未立即处理 pending IPI）、XiangShan X1（MIP 乱序读错过新中断）。结果：5 个此前未知并发 bug，N1/N2/X1 已获开发者确认修复，B1/T1 已上报，Rocket 因 in-order 微架构无 bug。
