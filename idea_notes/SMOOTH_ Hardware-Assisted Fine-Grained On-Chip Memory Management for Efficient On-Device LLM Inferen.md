## SMOOTH: Hardware-Assisted Fine-Grained On-Chip Memory Management for Efficient On-Device LLM Inference

- baseline方法是什么？
  - baseline 是"静态编译器驱动的粗粒度 scratchpad（SPM）管理"：XLA/TVM 式 DL 编译器在编译期做 memory tiling、operator fusion（QKV 投影融合、FlashAttention、FFN 融合）与 lifetime-based 分配，把每个 tensor/tile 连续地映射到片上 SRAM 的固定地址区（tile 常达几十到几百 KB）；预加载只在"带宽空闲 + 有足够时间取完整连续 tile + 存在足够大连续空闲区"三个条件同时满足时触发；评估中的具体 baseline 实现为 Compiler-Ideal（理想化版本：best-fit 分配 + 完美 lifetime 知识 + 每算子穷举 tile size 取最优，但保持连续分配约束）、Capuchin（硬件 64B cache 动态预取，无编译器 lifetime 信息）、Gemmini（pipelined 分配 + 字节级 tile 预加载）。
  - baseline 全栈执行例子（以移动 NPU 上 8MB SRAM、batch=1 的 decode 期一个 token 为例）：算法pipeline 层——w4a8/int8 量化的 transformer 逐层执行 QKV/FlashAttention/FFN（论文未明确说明 serving 调度层，单请求 on-device）→ 编译框架层——XLA/TVM 后端按全图 liveness 把每层权重 tensor 切成 N×K tile、按 lifetime 分配连续 SRAM 地址并固定 tile size（如 LLaMA2 4096 维权重以固定块连续铺放）→ kernel 调度层——GEMV kernel 在 32×32 Matrix Engine 上以 tile 为单位取数运算，softmax/GELU 在 Vector Engine 上执行 → 硬件架构层：SPM 是连续寻址 scratchpad；decode 期 GEMV 低运算强度（Low-OI）瞬间把 32GB/s 带宽占满，compute 阶段（softmax 等 High-OI）带宽空闲但编译器看不到运行期进度、无法预取；融合算子（如 QKV 融合）强制 Q/K/V 同时存活，tile 大小跨层不一致（projection/FFN/attention head 各异）在连续地址空间留下锯齿状空洞，2MB/8MB SRAM 下 best-fit 也无法填洞，导致碎片化 SRAM 利用率下降、偶发 off-chip spill、compute stall 增多（Compiler-Ideal 较字节级 Optimal 策略在 4K 序列时 stall 多 32.7%）；序列长度与统一内存带宽（CPU/GPU/NPU 争用）运行期波动又使静态 tile size 失效，延迟最多恶化 2.9×。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 SMOOTH：硬件辅助的细粒度运行时 SPM 管理。编译器仍做静态 lifetime 分析，但只输出每 tile 的剩余使用次数 use_cnt；硬件 Dynamic Memory Controller（DMC）接管动态分配与回收：① block-based 分配把 SPM 虚拟化为固定大小块（1KB 级，与处理单元对齐），logical 张量不再要求物理连续，碎片空洞可被小块填上；② direct-mapped block table + bitmap 空闲表做虚拟→物理地址翻译，address_check 模块对连续映射区旁路翻译（dual-mode 快路径）保持传统 SPM 的零开销访问；③ buffer 跟踪 ISA 执行进度，末次访问发出 end_cmd，DMC 递减 use_cnt 提前回收已消费块，并用硬件动态测量的 idle 带宽按 N_preload=⌊U×BW/Block_size⌋ 立刻预取后续层权重——把编译器看不见的短时带宽窗口利用起来。对应解决：缺陷①（静态 tile size 与运行期不匹配）→ 运行时硬件动态管理，无需重编译即可适应变长序列与波动带宽；缺陷②（连续分配的碎片化）→ block 级虚拟化让非连续空闲空间可被利用，外部碎片消除；缺陷③（静态 lifetime 与实际执行偏差、无法利用短带宽窗口）→ use_cnt+end_cmd 的硬件驱动 early reclamation 提供细粒度、及时的内存复用与预取（SMOOTH-ER 较 SMOOTH-Base 平均再降 TTLT 24.0%）。结果：TTFT 最高降 59.2%，TTLT 最高降 73.0%，能量平均降最高 51.2%，硬件开销可忽略（面积 <0.1%、功耗 pW 级）。
  - 论文方法全栈执行例子（同 8MB SRAM、batch=1 decode 期一个 token）：算法pipeline 层——同为 w4a8/int8 量化 transformer，模型不变、无精度损失（论文未明确说明 serving 调度层，单请求 on-device）→ 编译框架层——编译器静态 liveness 分析为每 tile 标注 use_cnt（如 W1 权重 tile use_cnt=2、V cache 块用完即释放），不再做连续物理分配，tile size 选择被放宽 → kernel 调度层——GEMV kernel 在 Matrix Engine 上执行时，buffer 按 ISA 进度感知当前块访问，末次访问发 end_cmd=1（如 Q 投影中块 0x2400-0x27FF 的末元素 d）→ 硬件架构层——DMC 收到 end_cmd 递减 use_cnt，为 0 的块（如已消费的 V_3、S_3 块）在 idle 周期被 find_zero/bitmap 标记释放并立即预取下一 tile（W1_1 等），非连续空闲块可拼装预取（如 V-cache 单块一到就预取）；访问时若地址在已翻译连续区（p_blk=0x2400, cont=4）内则直接物理访问、跨块边界且非连续才重新查 block table；prefetch 寄存器记录已预取到哪一块，未取完则回主存取数。→ 输出：token 间带宽峰值被摊平、compute-I/O 重叠最大化，TTLT/TTFT 显著下降（长序列、低带宽下收益更大：32K 序列较 Gemmini 平均 +66.8% 改善，16GB/s 带宽下 ITL 收益最大），能量随访存减少而降低。面积/功耗经 Yosys+ASAP7 7nm 综合验证开销可忽略。
