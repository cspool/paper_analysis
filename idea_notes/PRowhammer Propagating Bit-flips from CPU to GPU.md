## PRowhammer Propagating Bit-flips from CPU to GPU

- baseline方法是什么？
  针对 ML 推理的精度降级攻击有两类 baseline：(1) 权重型攻击（Bit-Flip Attack、DeepHammer、TBFA、Terminal Brain Damage 等）——对模型权重做定向 bit-flip，需 white-box 掌握模型架构与权重、先识别脆弱权重，且 Rowhammer 约束下要求"多个受控 bit-flip"，在只有 API 查询的黑盒云推理（MLaaS）场景不可行；(2) 库代码攻击（Li et al., USENIX Security 24，"Yes, One-Bit-Flip matters!"）——利用 OS 页去重对 hDRAM 中 CPU 共享库代码做 Rowhammer 单 bit-flip 破坏 CPU 指令，但明确把"闭源 GPU 库"列为开放问题；GPUHammer 则直接攻击 GPU 自有显存 dDRAM（GDDR6），不涉及 hDRAM，与 PRowhammer 正交。
  全栈执行例子（baseline=Li et al. 的 CPU 库代码攻击，目标为 GPU 加速的 ResNet-50 ImageNet 推理）：算法pipeline——攻击者须有模型权重/架构知识才能选脆弱层与权重位（本场景 black-box 下不可用）；系统框架——PyTorch 前向逐算子调用 CPU 共享库（MKL/OpenBLAS）与 GPU 库 cuBLASLt，库经 mmap 映射进 hDRAM；编译框架——论文未明确说明；kernel调度——攻击只能破坏 CPU 端指令（如矩阵乘的 AVX 指令），GPU kernel 由 cuBLASLt 的压缩 .nv_fatbin 承载、在闭源压缩格式下无从定位可翻转 bit，GPU 端计算不受影响；硬件架构——Rowhammer 位翻转只发生在 hDRAM（CPU DRAM），GPU 计算与 dDRAM 隔离，GPU 侧无攻击面。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  PRowhammer：把攻击面从"模型权重/CPU 库"转到"hDRAM 中的 GPU 共享库压缩代码"，用 CPU 侧 Rowhammer 单 bit-flip 经 OS 页去重传播到 GPU kernel 执行，形成新的"CPU 漏洞→GPU 计算"传播类攻击。逐项对应 baseline 缺陷：white-box 依赖→黑盒（只需 API 查询，用单线性层 profiling 模型定位 kernel，输入维度 2–10000 扫描）；闭源 GPU 库不可攻→不需要反编译/逆向压缩算法，用"bit-flip 模拟 + n=2 递归分段剪枝到 1KB + 随机抽 10000 bit"直接在压缩码上找可利用位（≤90 分钟）；压缩码单 flip 多改义易崩溃→统计显示平均 2–5 个（最多 25 个）合法改义指令、相当部分不崩溃只改输出；大库规模（cuBLASLt 压缩 255MB、逐 bit 需 11805 天）→剪枝策略规避；GPU 无攻击面→利用 CPU-GPU 架构耦合（GPU 数据/代码必经 hDRAM）把 CPU 漏洞传播为 GPU 漏洞，无需触碰 dDRAM/GPU 硬件。
  全栈执行例子（PRowhammer 攻击 ResNet-50 ImageNet 推理，单 bit-flip）：算法pipeline——profiling 模型（单线性层、输出 1000 类）定位 ImageNet 调用的 cuBLASLt kernel，剪枝策略找到 93 个可利用翻转（如偏移 0xc56745c 的 bit 8），相同翻转位跨模型（ResNet/VGG）转移有效；系统框架——不修改 PyTorch，攻击发生在库加载层：攻击者 mmap 同一 .nv_fatbin 页（PROT_READ|PROT_EXEC、MAP_PRIVATE），Rowhammer 篡改后 OS 页去重强制 victim 使用被破坏库；编译框架——论文未明确说明（利用 NVCC --compress-mode 产生的压缩 .nv_fatbin 结构而非修改编译器）；kernel调度——被改 SASS 指令（FFMA→FSET.F.FTZ.AND、LDS offset+8、SHL→LOP3.LUT 等）在 GPU SM/Tensor Core 上执行，破坏最终线性层 GEMM 输出 → 分类概率乱序 → 准确率 0%（RPL 100%）；硬件架构——攻击仅作用于 hDRAM（DDR3/DDR4，DDR5 亦适用），利用"bit-flip→合法指令"的概率特性绕过 GPU 指令路径无完整性校验的缺陷，GPU 与 dDRAM 均无需改动；防御需在 CPU→GPU 传输链路做完整性校验（压缩/解压管线加 ECC/CRC、kernel dispatch 前哈希验证）。
