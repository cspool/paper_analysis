## A Silicon-Proven Unified Low-Latency CXL Controller and Port-Based Routing Switch for Memory-Centric Fabrics

- baseline方法是什么？
  - Baseline 是 PCIe 衍生 CXL 控制器 + HBR 交换机 / 无交换机多主机方案。控制器三层（物理/链路/事务）各自独立流水线并在层边界握手同步；PCS 用 half-full 弹性缓冲驻留数据；链路层等待整帧校验后重放；事务层按 CXL.io/CXL.cache/CXL.mem 分设独立队列。HBR 按主机层级路由：每主机仅管自己 Root Complex 下的 VCS，不支持交换机级联与跨主机内存共享；多主机只能靠 MHD（各 head 独立地址空间、无跨头一致性、按头分带宽，端口数受 die 面积限制约 4）或软件一致性（显式 cache flush、单主节点串行写）。商用单跳扩展器 RTT 265–442ns，过交换机路径因叠加 ≥2 个控制器流水线+固件路由而翻倍，故超大规模数据中心回避交换机，退化为 1:1 直连或 MHD。
  - baseline 全栈执行例子：TPC-C NewOrder 事务（命中率 6%）→ 主机访存经 PCIe 派生控制器（SerDes/PCS half-full 弹性缓冲 → 链路层整帧校验与重放 → 事务层三协议独立队列调度，层层握手）→ HBR 交换机固件路由（每跳叠加多控制器流水线）→ SHD/MHD 设备；写请求须由单一主节点串行处理以维持一致性（4N4S_isolated 仅 2.9× 扩展；MHD_private 4 节点相对单节点 -35%）。模型：无（无 ML 模型）；数据/bench：TPC-C（10K/20K/40K 仓库）、YCSB A–D（YCSB-B 为主）、TPC-H、AuctionMark、Twitter/Wikipedia/Epinions。算法-编译-kernel 层：论文未明确说明（负载为数据库事务与微服务访问流，无模型推理、无编译框架、无 GPU kernel）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法一：统一低延迟 CXL 控制器——三层整合进单一时钟域流水线、共享缓冲与统一时序，消除层边界 staging/握手（对应 baseline 深流水线+边界同步缺陷）；nominal-empty 弹性缓冲把"空"视为合法状态、实时时钟对齐（对应 half-full 固定驻留，-15~20ns）；高信噪比下 FEC 旁路（对应 FEC 解码延迟）；256B flit + 部分数据单元提前校验 early-release（对应整帧等待，-5~10ns）；统一流控调度引擎协调三协议、按流量模式自适应（对应按协议分队列争用，+1.3× 吞吐；跨层整合后 RTT<50ns、链路带宽 +25%）。方法二：全硬件自动化转换/路由——每端口固定周期流水线完成 HBR↔PBR 双向翻译、SPID/DPID 分配、DRT/RGT 查表与拥塞感知仲裁，零固件抖动（对应固件路由的调度 jitter 与中断变异性）；非阻塞 NoC 并行转发、每跳恒定延迟（对应交换机多控制器串行穿越）；PBR + 多交换机级联支持 64 节点扩展、VCS 多根 + DP 绑定实现硬件级多主机内存池化与一致性（对应 HBR 层级绑定与 MHD 带宽/一致性受限）。
  - 论文方法全栈执行例子：同一 TPC-C NewOrder 请求 → 各节点统一控制器单级流水（nominal-empty 弹性缓冲 → 256B flit 提前校验 → 统一事务调度）→ 入口端口硬件分类器判定 HBR 域并单级翻译为 PBR（SPID/DPID 分配、头部重建）→ DRT 查出口 + RGT 拥塞选路 → 仲裁 → NoC 并行转发 → 出口逆向翻译回 HBR；多主机并发写由 CXL.cache 硬件一致性直接支持（修改版 PostgreSQL 跨节点并发写与缓存复用，无 cache flush、无单写主节点）。结果：4N4S_SWopt 64B RTT 较 SWbasic -53%、平均延迟 -42%、p99 -58%、吞吐最高 4.8×（vs 1N1S_local）、64 节点近线性扩展、YCSB-A 下带宽利用率 >95%、跨 NUMA 延迟均一且吞吐 4×。模型：无（无 ML 模型）；数据/bench 同 baseline。算法-编译-kernel 层：论文未明确说明（负载为数据库事务与微服务访问流，无模型推理、无编译框架、无 GPU kernel）。
