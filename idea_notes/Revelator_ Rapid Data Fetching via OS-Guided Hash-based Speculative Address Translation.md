## Revelator: Rapid Data Fetching via OS-Guided Hash-based Speculative Address Translation

- baseline方法是什么？
  - Baseline 是常规地址翻译（address translation）+ 基于连续物理内存（contiguity）的投机地址翻译方案。常规流程：处理器访存 → TLB 查找（L1/L2 TLB），命中则直接得 PA；L2 TLB miss 则发起 4 级 page table walk（每级都可能访问 DRAM，40–100 cycles），PTW 完成后才能用 PA 发数据取数——翻译与取数严格串行，地址翻译可占执行时间 40–45%（无大页）。投机地址翻译先行者：①SpecTLB [88]（structured contiguity）——OS 保留 2MB 候选大页区域但不立即提升为大页，从保留区域内分配 4KB 页，硬件用额外 TLB 记录"已保留未提升"的大页区域，在区域内假设固定 VA→PA offset 投机预测 PA；②SpOT [21]（arbitrary contiguity，SOTA）——OS 侧 CA-paging 把同一 VMA 的页尽量放在连续物理段、记录该 VMA 的 VA→PA offset 并指导后续缺页按此 offset 放置；硬件侧用一个小预测表（按 load/store PC 索引）缓存 contiguity descriptor（虚拟范围 base/bounds、权限、投机 VA→PA offset），TLB miss 时按 PC 取 descriptor、检查 VA 落在范围内后以 PA=VA+offset 投机取数。两类的共同缺陷：①依赖大页或 VA-to-PA 连续可用——内存碎片高（数据中心常态）或多应用竞争时（allocation interference）无法保证；论文量化 SpOT 在低碎片下覆盖 >85%/准确率≈100%，medium 碎片覆盖骤降到 40% 以下，high 碎片覆盖 <10%（Fig.2），后台内存 hogging 20% 就把最大连续段砍掉 50–80%、16 应用交错分配把 offset-based 分配成功率从 100% 打到 11%（Fig.3）；②投机元数据存在昂贵硬件里（SpecTLB 的额外 TLB、SpOT 的 contiguity descriptor 缓存），面积/功耗开销未必值回收益。
  - Baseline 全栈执行例子（算法pipeline-系统框架-编译框架-kernel调度-硬件架构；本文为 OS/MMU 协同论文，算法、编译框架、kernel 层论文未明确说明）：一个 DLRM sparse-length-sum 或 GraphBIG BC 的访存请求（translation-intensive，PTWPKI 10–45）→ 系统框架层：应用经 Linux 虚拟内存管理分配 VMA、按需缺页，buddy allocator 全相联地把虚拟页映射到任意空闲物理帧（映射完全由碎片与分配历史决定）→ 硬件架构层：取指/访存单元把 VA 送 TLB 层级（L1 D-TLB 64 项 → L2 TLB 2048 项），L2 TLB miss → MMU 发起 4 级 PTW，每级查 page structure cache 或 DRAM（40–100 cycles）→ PTW 完成后得到 PA → 才发数据取数请求进 cache/DRAM → 返回数据。SpOT 变体：OS CA-paging 尽力把 VMA 页放连续段并记录 offset → TLB miss 时硬件按 PC 查 contiguity descriptor 表 → 命中则 PA=VA+offset 投机取数、与 PTW 重叠 → 但在碎片/干扰下命中率暴跌，投机失败还得等 PTW，浪费带宽并污染缓存；SpecTLB 变体：只在保留大页区域内投机，一个"hole"（区域内被占页）就断送整个区域。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 Revelator：把"连续放置"换成"per-page 哈希放置"这一与碎片无关的不变量。OS 侧 tiered hash-based allocation：分配时对 VPN 用同一哈希函数 CityHash(VPN, PID, seed_i) 依次尝试最多 N 个候选 PPN（每 tier 一个独立 seed，成功概率 p(1-p)^(i-1)，全部失败概率 (1-p)^N 随 N 指数下降），N 次全失败才回退常规分配器——成功与否只取决于内存利用率 u、与碎片结构和分配干扰无关（对应解决缺陷①的碎片/干扰敏感）；末级 PT 帧同样哈希分配（单次尝试 H_1(VPN>>9)，因每 PT frame 覆盖 512 个 VPN），使 VA→PTE 也可预测。硬件侧：L2 TLB miss 后，MMU 内轻量投机引擎（~2 cycle 哈希电路，只含哈希函数电路 + 每 hash 计数器和，无大型元数据表——对应解决缺陷②的硬件开销）按 tier 顺序重算 N 个候选 PPN 拼成候选 PA，在 PTW 期间投机取数；同时按 VPN>>9 预测末级 PTE 帧并并行投机取 PTE，实现两级并发（数据取数与整个 PTW 重叠 + 末级 PTE 取数与 PTW 前几级重叠）。投机 degree filter 用 utilization monitor（各 tier 实际分配成功率）与 bandwidth monitor 动态决定发几个候选请求，避免浪费带宽/污染缓存。与 baseline 对比：Revelator 不依赖 2MB 页也不依赖连续，high 碎片下仍保持高准确（单核较 SpOT 高 15.3%，较 THP 高 25%）；虚拟化下同时预测 gPA/hPA（Diagonal+Horizontal 组合，较 NP+THP 高 13.6%）；多核随核数扩展（16 核较 THP 1.40×/1.50×，投机准确率稳定 87–88%）；NUMA 下 policy-first node-scoped hashing 保留 OS 节点选择 + Bloom-filter hint 处理 spillover（较 SpOT 最高 1.20×）；真实 Linux 6.10.8 原型 3 个哈希即可哈希分配 70–85% 页、minor fault 开销 0.078%；RTL 综合（Chisel+Yosys+Nangate 45nm）投机引擎仅 0.0149 mm²/14.723 mW = Cascade Lake core 的 0.02% 面积/0.03% 功耗。
  - 论文方法全栈执行例子（算法pipeline、编译框架、kernel 层论文未明确说明）：同样的 DLRM/GraphBIG 访存请求 → 系统框架层：OS 按 Revelator 策略分配——buddy allocator 扩展为 tiered hash-based（对 VPN 算 CityHash(VPN,PID,seed_1..3) 找第一个空闲候选帧，都占则回退；PT frame 分配按 H_1(VPN>>9) 单次尝试），硬件侧按同一函数重算 → 硬件架构层：L1/L2 TLB miss → 投机引擎 2 cycle 内用相同 CityHash 电路 + tier seed 重算候选 PPN、拼 page offset 得候选 PA，同时哈希 VPN>>9 得候选末级 PTE 地址 → degree filter 按带宽/利用率决定发出 1–3 个投机取数请求 → 这些请求与 4 级 PTW 并行进入内存层级，投机数据装入私有 L2（正确性：PTW 解析后按 bounded address log 使错误投机失效，Meltdown/Spectre 不可用）→ 若候选命中 OS 实际放置的帧，数据在 PTW 完成前到达 → 翻译与取数重叠，地址翻译延迟被隐藏/减少（medium 碎片下数据取数延迟较 THP 平均降 31%）。Revelator+THP 变体：2MB 连续可用时先用哈希 2MB 分配/THP 回退保留大页收益，碎片化时回退 4KB 哈希投机，全碎片谱系性能稳健。NUMA 变体：先按 OS 策略选节点 n*、只在 n* 范围内做哈希放置，硬件按每节点计数器选 dominant node 投机，p_dominant<0.8 时用 OS Bloom-filter hint 表对远端节点额外发一次投机取数（隐藏 85–95% PTW 延迟）。
