## MNEMOS A GPU-based TFHE Acceleration Framework with Memory Access Optimization

- baseline方法是什么？
  - baseline 方法：ZAMA 的 TFHE-rs/Concrete-Python/Concrete-ML 官方 GPU（CUDA）实现。算法层：TFHE PBS 四阶段流水——Modulus Switching → Blind Rotation（n 次迭代，每次 Rotation → Decompose → FFT → MAC(External Product) → IFFT+累加）→ Sample Extraction → Key Switching；多项式乘用 negacyclic 卷积（Tangent FFT，N/2 点复数 FFT）加速。系统框架层：Concrete 编译器把 Python 程序编译为 PBS 任务并按内部启发式在 CPU/GPU 间分配；Concrete-ML 的 CUDA backend 执行加密 CNN（DeepCNN/VGG-9）推理。编译框架层：Concrete 编译器生成参数集（Para-A~D）与 PBS 任务划分，FFT 前的 Rotation 到 FFT 融合为单 kernel、其余操作放入第二个 kernel。kernel调度层（核心缺陷所在）：PBS 的 MAC kernel 中，每个线程块独立从全局内存经 L2 取整个 BSK（(k+1)ℓ×(k+1)×N×n 元素）与 GLWE 相乘；一批内多个 PBS 密文共享参数，但只获得 L2 级复用——大 BSK 成为多 SM 同时访问的"hot data"，L2 带宽/延迟成为系统瓶颈；剖析显示 stall_long_scoreboard >50%（加 stall_MIO_throttle 超 60%，PBS 严重 memory-bound）；FFT 运行在 CUDA Core（非 Tensor Core），Fourier 矩阵从共享内存读取并受 bank 冲突困扰；无跨迭代数据复用。硬件架构层：A100 80GB PCIe（108 SM、40MB L2、每 SM 192KB 合并 L1/SPM、FP64 Tensor Core WMMA 8×8×4）与 H100。
  - baseline 全栈执行例子（一次批量 PBS，batch 4096，Para-B：N=512,k=4,ℓ=2,n=679）：算法层：每个 LWE 密文 c=(a_1,…,a_n,b) 经 Modulus Switching 按模 2N 舍入；系统框架层：Concrete 后端按启发式把部分 PBS 分配到 CPU、部分到 GPU（论文为公平比较改为全 GPU）；编译框架层：Concrete 编译器把 Rotation→FFT 融合为 kernel 1，其余（MAC/IFFT/SE/KS）为 kernel 2；kernel调度层：kernel 1 对每个密文逐迭代做 Rotation、Decompose（基 β=16 切片成 2 组）、Tangent FFT（CUDA Core，256 点复数 FFT，Fourier 矩阵从共享内存读）；kernel 2 中每个线程块从 L2/全局内存独立取 BSK 做 MAC（Hadamard 乘）——batch 中所有密文重复取同一份 BSK，仅靠 40MB L2 缓存热数据（batch>1024 时工作集超 L2，出现 cache thrashing 与带宽饱和），IFFT 后累加、Sample Extraction、Key Switching 输出 LWE；硬件架构层：数据从 GMEM→L2→L1/SM 逐级搬运，L2→SM 流量远超 GMEM→L2（BSK 反复从 L2 重取、未驻留 SM），stall_long_scoreboard 主导执行时间。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法（MNEMOS）针对 baseline 的两大痛点——"BSK 只到 L2 级复用、SM 级数据局部性缺失"与"Tensor Core 闲置、FFT 未利用其算力"：
    1. **BSK 分块跨密文复用（对应解决 L2 带宽瓶颈）**：利用 BSK×傅里叶系数是逐元素 Hadamard 积的性质，把朴素"整 BSK 缓存进共享内存"（不可行：A100 上可能超 192KB 上限且蚕食 L1 容量）改为分块——单个线程块只处理一块 TBSK 对一块 TGLWE，同一 BSK 分块被一批中多个 PBS 实例并发复用（SM 级数据局部性）；分块几何取 8 个连续复数 FP64（128B）对齐内存事务粒度，保证合并访问且无需重排 FFT 输出布局。
    2. **Tensor Core FFT kernel（对应解决 Tensor Core 闲置）**：FP64 WMMA（8×8×4）加速 FFT——复数乘分解为 4 个实数 MMA；8 点 FFT 基例 + 四步 FFT radix-8/64 分层分解；64 点特化用 warp fragment 布局省一次显式转置；Fourier 矩阵运行时在寄存器内算术生成（{0,±1,±sin(π/4)}）替代共享内存载入；16B 宽数据类型专用 swizzle 消除转置 bank 冲突。
    3. **跨迭代 kernel 融合（对应解决 FFT/IFFT 冗余全局载入）**：FFT/IFFT 用同一系数集的共轭版本，融合 kernel 跨越盲旋转迭代边界，把 twiddle/precomputation 系数在片上跨迭代复用（收益随 ℓ 线性增长）。
    4. **精度分析**：噪声公式 n·2^ω·ℓ·2^(2β)·N²·(k+1) 下，4-bit 明文需 ≥30 小数位（常 >35）→ 确定 FP64 为 TFHE FFT 精度底线（FP32/FP16 不足），解释为何 CKKS 的低精度 Tensor Core NTT 映射不能直接照搬，并给出未来 ℓ↑/β↓ 低位宽分解方向。
  - 论文方法全栈执行例子（同一批量 PBS，Para-B，batch 4096）：算法层：Modulus Switching → 盲旋转循环中每迭代 Rotation → Decompose（基 β 位切片成 ℓ=2 组）→ Tangent FFT（256 点复数 FFT，negacyclic 卷积）→ MAC → IFFT+累加 → SE → KS，语义与 baseline 相同（正确性等价）；系统框架层：全部 PBS 独占 offload 到 GPU（修改 Concrete 任务划分）；编译框架层：论文未明确说明（沿用 Concrete 编译产物，仅改 CUDA kernel 与后端 offload 策略；baseline 的 Rotation→FFT 双 kernel 融合被 MNEMOS 的跨迭代融合取代）；kernel调度层：FFT 在 Tensor Core 上执行（FP64 WMMA 8×8×4，四步 FFT 分层、Fourier 矩阵寄存器内生成、64 点 fragment 免转置、宽类型 swizzle），MAC kernel 中一个线程块读同一块 TBSK（128B 合并访问）与同一分块位置的一批 TGLWE 复用 Hadamard 乘（BSK 读体积从 (k+1)×GLWE 降为可忽略），跨迭代融合 kernel 在片上复用 IFFT 输出与共轭系数；硬件架构层：GMEM→L2 流量平均降 15.7%、L2→SM 平均降 69.4%，stall_long_scoreboard 从 >50% 降至约 20%（memory-bound 转为 compute-bound，Stall Math Pipe 占主导），PBS 吞吐 Para-B A100 2.26×/H100 2.02×，Para-D 最高 3.01×（A100）/2.86×（H100），应用端到端 DeepCNN ~2×、VGG-9 2.21×、AES 1.53×，batch 从 256 到 16384 全程稳定（baseline 在 >1024 后骤降）。
