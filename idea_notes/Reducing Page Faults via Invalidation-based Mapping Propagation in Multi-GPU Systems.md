## Reducing Page Faults via Invalidation-based Mapping Propagation in Multi-GPU Systems

- baseline方法是什么？
  - Baseline 是 multi-GPU UVM（Unified Virtual Memory）+ access counter-based page migration（NVIDIA Volta 起采用，阈值如 Ampere 的 256 次访问）。五步迁移处理机制（host UVM driver）：① host 为新页分配 destination GPU 上的物理页；② 广播 invalidation 请求到所有 GPU，各 GPU 经 GMMU page table walk 清除 PTE 并做 TLB shootdown，保证翻译一致性；③ 通知 copy engine 从 source GPU 拷贝数据；④ host 把新映射只发送给 destination GPU 更新其本地页表；⑤ 释放旧物理页。每步串行执行。痛点：迁移把旧映射从所有 GPU 的页表和 TLB 中清掉，但新映射只装到 destination GPU——其他 GPU（即使以前访问过该页）再次访问时其 PTE 已无效，触发 re-fault，再走一遍 host 集中式 page table walk。实测 re-faults 占全部 page faults 的 73.59%（14 个 workload 平均），而 78.32% 的翻译延迟来自 GPU 之外的 host 侧处理（interconnect + IOMMU PTW），mapping step 又占迁移处理延迟的 26.02%。
  - Baseline 全栈执行例子（算法pipeline-系统框架-编译框架-kernel调度-硬件架构；本文为 GPU 虚拟内存/硬件架构论文，算法、编译框架层论文未明确说明）：一次典型 shared-page 访问流（如 BFS 的邻接表被 4 个 GPU 分块访问）：① kernel 调度层——OpenCL workload（SHOC BFS、AMD APP SDK MM/FW、POLYBENCH MVT 等）在 4-GPU MGPUSim 平台、分布式 CTA 调度下把 CTA 分到各 GPU 的 CU；② GPU 0 的 CU 发对页 P 的访存 → 硬件架构层：L1 TLB/cache miss → L2 TLB miss → GMMU（PWQ 排队 → 8 个 PTW 每级 100 cycle page table walk，查 PWC）→ 本地页表无映射 → page fault → ATS 请求经 32GB/s CPU-GPU 互连到 host IOMMU（16 个共享 PTW）集中式 walk → 返回远程映射（GPU 1 上的物理地址）→ GPU 0 以远程映射经 600GB/s GPU-GPU 互连访问 GPU 1 内存，直到 access counter 达 256；③ 触发迁移：host 分配 GPU 0 上的新页 → 广播 invalidation（4 个 GPU 都清 PTE + TLB shootdown）→ copy engine 拷页 → 只更新 GPU 0 的页表 → 释放旧页；④ 之后 GPU 1/2/3 再次访问页 P 时 PTE 已无效 → re-fault → 再走一次 host ATS 往返（interconnect 延迟 + IOMMU 排队 + 集中式 walk），线程被长时间阻塞；naive 的"迁移后把新映射广播给所有 GPU"方案需要每 GPU 额外做 page table walk（与在途翻译争用 PWQ），software-driven 更新在 4 GPU 时 L2 TLB miss 延迟比 hardware-based 高最多 2.37×、性能低 1.38×，均不划算。

- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 ShadowUpdate：把"新映射传播"免费并入已有的 invalidation 阶段——invalidation 本来就为维护翻译一致性而通过 GMMU 遍历每个 GPU 的页表，因此把迁移页的新物理地址 piggyback 到 invalidation 广播消息里，让每个 GPU 在 invalidation 的 page table walk 中顺带写上新 PTE，消除 re-fault 且不产生任何额外 page table walk；同时把 destination GPU 的 mapping 更新步骤提前与 invalidation 合并（mapping 26.02% 与 invalidation 30.35% 两阶段 overlap），迁移处理延迟降 22.79%。正确性由轻量硬件 IfMT（L2 TLB 后）保证：UMPT（256 项全相联，VA+新PA+P 位，8 并行比较器最坏 32 cycle）+ Cuckoo filter（64×4×11-bit，xxHash，平均 FPR 0.94%，无假阴性，1 cycle 筛选）在拷贝期间把对迁移页的翻译请求挂起（P 位），拷贝完成后 copy engine 广播 completion 信号清除 fingerprint、驱逐 UMPT 条目、把存储的新 PA 直接返回 L2 TLB MSHR（不重放 walk），保证不会在拷贝完成前用新映射访问到错误位置。对应解决：① 消除 73.59% 的 re-fault（page fault 总数降 73.83%），把翻译尽量留在 GPU 内完成（L2 TLB miss 延迟降 41.92%）；② 相对 naive 广播不引入额外 page table walk（PWQ queuing 延迟降到 baseline 的 0.76× vs naive 的 1.25×）；③ 无需 software-driven 更新（全硬件路径，host 干预最小）；④ 面积开销极小（Cuckoo filter 0.0243mm²+1.5852mW @45nm、UMPT 0.8171mm²+81.35mW @22nm，折算 28nm 仅占 AMD Fiji 的 0.0016%/0.2221%）。
  - 论文方法全栈执行例子（算法pipeline、编译框架层论文未明确说明）：同样的 BFS shared-page 访问流：① kernel 调度层——不变（同一 OpenCL workload、分布式 CTA 调度），LLM 场景额外构造输出 tiled GEMM kernel（按 M/N 分块、遍历 K，仿 cuBLAS 结构）配合按输出维切分的 column-wise tensor parallelism 模拟多 GPU 执行（QKV/FFN 平均 1.37×/1.42×）；② 硬件架构层——GPU 0 对页 P 的远程访问计数达 256 → host 分配 GPU 0 新页 → 广播 invalidation 消息（携带新 PA）→ 4 个 GPU 的 GMMU 在 invalidation page table walk 中同时写新 PTE 并做 TLB shootdown，同时 IfMT 把 (VA→新PA) 插入 UMPT、fingerprint 写入 Cuckoo filter → GPU 1/2/3 在拷贝期间访问页 P：L1/L2 TLB miss → Cuckoo filter 命中 → UMPT 确认置 P 位挂起翻译（不发 ATS，不再产生 re-fault）→ copy engine 经 600GB/s 拷页完成 → completion 广播 → 各 GPU 清 fingerprint、驱逐 UMPT 条目、把新 PA 返回 L2 TLB MSHR 放行翻译 → 后续访问全部本地命中新映射，全程无需 host IOMMU 参与；③ 结果：14 workload 平均 1.40×（naive 仅 1.26×，说明 re-fault 消除 + 映射传播零额外开销两部分收益缺一不可），GPU 数扩到 32 时 1.57×，与 IDYLL（减 GMMU 争用）互补组合 1.36×，2MB large page 下 1.38×。
