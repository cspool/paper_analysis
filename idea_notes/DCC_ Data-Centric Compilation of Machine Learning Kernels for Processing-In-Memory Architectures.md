## DCC: Data-Centric Compilation of Machine Learning Kernels for Processing-In-Memory Architectures

- baseline方法是什么？
  - Baseline 一（编译流程，主要对标）：compute-centric 的 PIM 编译流程，以 TVM 式方案（论文 §2.2 的 T，公平复刻 ATiM [42] 的三步串行流程）为代表：先用 TVM 的 cost model 找到并固定一组计算 schedule 模板（只最小化计算时间），再为每个模板生成 UPMEM 专用的数据重排，最后只在固定模板集内搜索最佳配置——数据重排与计算优化被当作两个独立问题顺序求解。ATiM 本身只支持 UPMEM PIM（DDR4、CPU 集成、无浮点/弱乘法），CPU-PIM 协同通常打不过 GPU-only。其余 PIM 编译工作（SimplePIM/PIM-DL/CINM/PIMFlow）只支持单 kernel 或单后端、基本忽略重排成本。
  - Baseline 二（PIM 侧执行）：AttAcc [28] 默认实现的手工固定数据分布——把不同 batch/attention head 分布到 16 个 pCH、第一张量维分布到每 pCH 16 bank group、第二维分布到每 bank group 4 bank，对所有 token 数/batch 使用同一固定 tiling。
  - baseline 全栈执行例子（LLM 解码一个请求）：GPU 内存中张量按 Host 布局存储（连续元素跨 bank 分布以利用 bank 级并行）→ TVM/ATiM 式编译先固定使计算时间最小的 loop schedule → 再按该 schedule 生成输入重排（经 Host 内存总线搬数：顺序读 Host 只能单 channel 写 PIM，或多 channel 并行写 PIM 需非连续 Host 读引发 channel 冲突）→ PIM core 计算 → 输出重排回 Host 布局；AttAcc 固定 tiling 下 attention 层在 PIM 跑但 tiling 不随 token 数自适应，QKV 生成与 projection 层仍留在 GPU（固定分布在这两层落后 GPU 1.25×）。算法层：无新算法（GEMV/RED/ATTN/VA/RELU 标准 kernel）；系统框架层：PyTorch + AttAcc 运行时（论文未说明更多）；编译框架层：TVM 式 compute-centric 调度（先固定模板再事后生成重排）；kernel 调度层：AttAcc 手工固定数据分布；硬件架构层：AttAcc（每 bank GEMV + 每 channel softmax/accumulator）/ HBM-PIM（每两 bank 16-way FP16 FPU）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 方法 = data-first 的联合 co-optimization 编译流程：①先枚举数据分区（所有候选 data-tile：张量维在 PIM group/core 上的分配，DFS+memoization 穷举）再映射计算循环（compute-tile），生成全部 tiling drafts——对应"先固定计算模板再被动生成重排、搜索空间受限"的缺陷（compute-centric 方案漏掉"稍低效计算换取便宜重排"的配置，动机实验：TVM 式方案数据重排占 kernel 时间 64.68%、比手工最优差 1.28×，DCC 1.27× 反超并逼近手工最优）；②draft 剪枝三规则（等价映射去重/SIMD 宽度对齐/执行性能等价）把搜索空间平均减 9.01×——对应穷举空间爆炸；③PIM-specific 代码优化：数据重排经 GPU shared memory staging（B=on-chip/N 分块，串行 Host 读 + 并行 N channel PIM 写）同时获得 Host 读与 PIM 写两侧 channel 级并行——对应"单 channel 写或非连续 Host 读"的重排瓶颈；计算命令 group 级广播优先（组内数据 padding 对齐地址偏移，一条命令驱动全组，缓解内存控制器命令瓶颈）、bank 级并行兜底——对应控制命令瓶颈；④耦合 XGBoost 预测器同时估计重排+计算端到端时间选最优 draft（静态尺寸离线查表、动态尺寸在线生成+预测并记录 lookup table）——对应"只看计算时间、重排成本事后才知道"的缺陷；⑤多层抽象（System/Group/Core）+ data-centric IR 解耦后端语义，同一编译器覆盖 HBM-PIM 与 AttAcc 两类 GPU-PIM 后端——对应 ATiM 只支持 UPMEM CPU-PIM 的缺陷。
  - 论文方法全栈执行例子（同一 LLM 解码请求）：请求到达 → DCC 异步推断各 PIM kernel 张量尺寸、查 lookup table 取最优 draft（未见尺寸则在线生成+预测并记录，~160 查询后收敛）→ 输入重排：GPU 侧分块串行读 Host 内存到 shared memory、按 N channel 并行写 PIM bank（两侧 channel 级并行）→ 计算：group 级广播 DRAM 计算命令（padding 保证组内相同地址偏移）驱动各 bank 的 GEMV/FPU 计算 → 输出重排合并部分结果并转回 Host 布局 → forward() 返回 torch.Tensor 给 GPU 上的后续层（compute-intensive 的 Feed-forward 主体仍在 GPU）。结果：QKV 生成与 projection 从 GPU 移到 PIM（2.58×/2.91× 对 GPU）；LLM 端到端 AttAcc_Full+DCC 平均 4.52× 对 GPU（峰值 7.71×）；kernel 级对 GPU 至多 13.17×（AttAcc）/7.68×（HBM-PIM）。算法层：无新算法（GEMV/RED/ATTN/VA/RELU 不变）；系统框架层：PyTorch + DCC.Layer 替换模型层、DCC.Kernel.preLoad 预载权重、DCC.setModel 收集模型元数据；编译框架层：DCC 五组件 data-first 联合 co-optimization（本论文核心）；kernel 调度层：data-tile/compute-tile tiling drafts + group/bank 分级命令调度；硬件架构层：论文未提出新硬件（复用 AttAcc/HBM-PIM，修改模拟器评测）。
