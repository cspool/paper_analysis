## SPEC CPU: The Next Generation

- baseline方法是什么？
  - baseline 是经典的 SPECrate 同质多拷贝容量方法（自 1992 年 CINT92/CFP92 起）：M 个 copy 同时运行同一个 benchmark（同质负载），每个 copy 跑完全相同的工作，测系统吞吐（weak scaling / Gustafson's Law）；配套的 SPECspeed 运行风格测单任务完成时间（strong scaling / Amdahl's Law）。这仍是 CPU2017 与 CPU2026 中 SPECrate 的默认运行方式。
  - baseline 全栈执行例子（一台 48 核服务器跑 SPECrate intrate）：runcpu 以 --copies=48 同时启动 48 个进程，全部执行同一个 benchmark（如 727.cppcheck_r）的 ref 输入——每个进程从磁盘读同一份输入、执行近乎相同的指令序列，同时并发竞争共享 L3、DRAM 带宽、ITLB 与预取器；因为所有 copy 程序相同，争用模式恒定且同时开始大致同时结束，输出只是"该 benchmark 的 48 路同质吞吐"。问题：现代云/数据中心/AI agentic 多租户服务器实际运行的是异构多程序负载（VM 同时跑数据库、编译、LLM 推理、Web 服务），同质方法无法暴露跨程序 cache/TLB/带宽争用、OS 调度动态与异构资源争用；而研究界自制多程序负载时各用各的自定义 benchmark 混合 + ad-hoc 调度策略，sample imbalance（各程序独立时长不同）与 schedule imbalance（并发争用）混杂，结果无法跨研究对比。算法pipeline（LLM 推理算法）/系统框架（LLM serving）/编译框架/kernel调度（GPU kernel）/硬件架构（RTL）层次：论文未明确说明（本文是基准套件方法论论文，分析工具为 PMC/Top-down、BBV recurrence 图与 perf 时间图，平台为真实 CPU）。
- 论文方法是什么？如何对应解决Baseline的缺陷？
  - 论文方法 RRR（Rolling Round-Robin Rate）+ 套件整体重构。RRR 直接对应解决"同质方法不反映异构负载 + 多程序生成无标准化"的缺陷：每个核（copy）持有一条包含全部 N 个 benchmark 的队列，起点按核号 mod N 错开、按 --rrrrate_inc 步长轮转，把 N 个 benchmark 全部顺序跑完（可重复 --iterations 轮）。机制上保证每个 benchmark 在每个核上各跑一遍、指令总量在所有核上完全相等——从机制上消除 sample imbalance（对应 FIESTA [165] 指出的问题），只保留 schedule imbalance（并发争用造成的非对称干扰），而这正是异构多核研究想要研究的内容。因为 benchmark 经过可移植性硬化（§V：去随机化、去环境查询、去系统调用干扰、≥95% 用户态执行），RRR 负载的干扰完全来自用户态 CPU 执行，可与 OS 调度策略、资源划分方案、微架构创新做公平直接对比，替代"手工 kernel 隔离代替完整应用"的旧做法。套件其他设计：52 个 benchmark（CPU2017 为 43），新增前端受限的大代码足迹整数负载（对应现代软件大代码足迹/复杂控制流）、首次加入多线程整数 benchmark（task-parallel 的 821.gcc/823.llvm 模拟 make -j N 行为）、每 benchmark 多 workload 抗针对性优化（1/N 规则）、BBV/PMC 特征化辅助选型与剪枝。
  - 论文方法全栈执行例子（同 48 核服务器）：runcpu 以 `--rrrrate --copies=48` 启动 48 个 copy，每个 copy 依自己的错开队列顺序执行全部 14 个 intrate benchmark（copy0 从 714.cpython_r 开始、copy1 从 727.cppcheck_r 开始……依次错位），48 个异构程序并发运行，各自产生不同的取指/访存/分支/压缩/搜索模式，在共享 L3/DRAM/预取器/ITLB/分支预测器上制造真实的多程序争用（如 cpython 的高 IPC 前端压力与 sqlite 的内存延迟敏感并存）→ 每个 benchmark 在 48 个核上各完成一遍，每 benchmark 取 48 个 per-copy 时间的中位数再取均值 + CV → 输出 14 个 benchmark 的异构调度时间表（无官方 SPECratio/geomean，RRR 处于 exhibition 状态，指标未定稿），配 scripts.misc/rate_timeplot.py 生成 refrate vs rrrrate 时间图（Figure 2）→ 研究者按自选指标（累计 IPC、平均吞吐、调和平均、公平性指数）分析。算法pipeline（LLM 推理算法）/系统框架（LLM serving）/编译框架/kernel调度（GPU kernel）/硬件架构（RTL）层次：论文未明确说明（本文产出的是 benchmark 套件与运行方法论，硬件平台为 AMD EPYC 9755 等真实 CPU，无模拟器/RTL 修改；对编译器的支持体现在新增"vendor 编译器 vs 社区 GCC/LLVM 编译器"两类结果报告类别）。
