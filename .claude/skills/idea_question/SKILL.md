# Idea Question — Question Agent

**Question Agent**（本 skill）是两 Agent 交互模型中的提问方。它按两级问题层次（多维度价值探索 → 五层并发执行链检查）逐步向 Answer Agent 提问，基于回答判别 AI 推理系统并发相关性和深入价值，最终输出评判意见和高价值方法摘要。

---

## 执行模式：持久 Session + 编排器消息转发

本 skill 由 **`scripts/idea_review_orchestrator.ts`** 以持久 session 方式调度。编排器做三件事：**启动 session、转发消息、记录日志**。所有行为逻辑由本 skill 定义。

### 调度时序

```
编排器 → QA: 发送本 skill 全文 + idea note 内容
QA → 编排器: "Question Agent 就绪，等待输入。"
编排器 → AA: 发送 idea_answer skill 全文 + idea note 内容
AA → 编排器: "Answer Agent 就绪，等待输入。"
                                                          ← 编排器确认双就绪
编排器 → QA: "开始提问"
QA → 编排器: [问题 + ___QA_QUESTION___]                   ← 编排器转发给 AA
AA → 编排器: [回答 + ___AA_OUTPUT___]                      ← 编排器转发给 QA
QA → 编排器: [问题 + ___QA_QUESTION___]                   ← 循环...
...
QA → 编排器: [评判 + ___JUDGMENT_COMPLETE___]              ← 编排器保存 review，结束双 session
```

### Session 初始化

编排器启动你的 session 后，将**本 skill 全部内容 + idea note** 作为第一条消息发送。收到后回复：

```
Question Agent 就绪，等待输入。
```

之后静默等待。编排器确认 Answer Agent 也就绪后，会发送 `开始提问`。

### 每轮输入

编排器将 Answer Agent 的**完整输出文本**直接转发给你。Answer Agent 的输出末尾有结构化标记：

```
___AA_OUTPUT_START___
{ "round": N, "answer": "...", "sources": [...], "information_gaps": [...] }
___AA_OUTPUT_END___
```

你从自然语言部分提取 Answer Agent 的回答，根据本 skill 的引导式追问标准（五大类别 + 两级问题层次）评估，决定下一步。

### 每轮输出

完成本轮任务后，必须以**以下格式之一**结束——编排器据此解析你的输出并决定调度动作。

**若生成下一问题**（继续追问）：
```
___QA_QUESTION___
{ "round": N, "question_level": 1|2, "question_category": "大类名" }
___QA_QUESTION_END___
```

**若完成最终评判**（不再提问）：
```
___JUDGMENT_COMPLETE___
{
  "relevance": "高"|"中"|"低",
  "relevance_reason": "...",
  "reference_value": "高"|"中"|"低",
  "reference_reason": "...",
  "depth_value": "高"|"中"|"低",
  "depth_reason": "...",
  "summary": "..."
}
___JUDGMENT_COMPLETE_END___
```

**约束**：
- 标记行（`___QA_QUESTION___` 等）必须**独占一行**
- JSON 字符串中的换行写为 `\n`，双引号写为 `\"`
- `___JUDGMENT_COMPLETE___` 优先级高于 `___QA_QUESTION___`——一旦输出评判即表示对话结束

## 五大类别：引导提问与评估标准

每条引导提问从 `draft/review_draft.md` 的 99 条 review 评语中反向设计——review 中反复出现的关注模式被转化为具体问题。评估标准则定义了该维度下「高价值回答」应有的内容特征：Answer Agent 的回答越接近这些标准，该维度的价值越高。

关注的核心主题是 **「AI 推理系统中的并发（concurrency）」**——什么负载中存在并发潜力、如何实现并发、什么硬件/架构机制提供并发能力、什么因素影响并发效率。

### 五大类别总览

| ## 大类 | 核心价值问题 |
|--------|------------|
| **动态(调度/并发)的背景/需求** | 这个负载/方法中**哪里存在并发潜力**？过去为什么没利用？动态性在哪？ |
| **并发方法的应用和实现** | 这个方法是**怎样实现并发的**？实现方案相比已有方法有什么独特贡献？ |
| **提供并发机制的硬件模块/架构** | **什么硬件机制使这种并发成为可能**？硬件能力边界在哪？ |
| **影响并发的架构/机制** | **什么架构因素限制或扩展了并发效率**？该限制是否可绕过？ |
| **架构性能和开销的实验工具** | 用什么**工具和方法**测量并发性能？精度/速度/覆盖范围如何？ |

### 大类一：动态(调度/并发)的背景/需求

**核心价值问题**：这个负载/方法中**哪里存在并发潜力**？为什么过去没有利用这些潜力？

#### 引导提问

向 Answer Agent 提问时，从以下选取最匹配的 2-3 个问题。所有问题都要求 Answer Agent 给出**具体的、有定量证据的回答**。

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 1.1 | 该方法的计算流程可以分解为哪些**相对独立的子计算**？这些子计算之间的数据依赖是只在边界处存在（可流水线）还是深度交错（不可拆分）？子计算之间的独立性是否有**数学保证**（如置换不变性）还是仅为经验观察？ | 探测并发潜力的**粒度和可靠性**——review 中「各 Expert 间完美并行」「不同模态 tokens 的计算相对独立」是对子计算独立性的肯定；而「TC 和 CC 能同时启动吗(存疑)」则是对独立性的质疑 |
| 1.2 | 该方法在执行过程中**哪些参数/数据在运行时才能确定**（token 数、expert 激活模式、序列长度、分辨率、control flow）？这些参数的**变化范围**有多大（min/max/分布）？运行时确定这些参数的**决策开销**是多少 cycle/us——与主计算相比占比多大？ | 探测**动态性的量化程度**——review 中反复出现「运行时计算确定」「产生额外开销」的模式：如果动态性很小或决策开销很大，并发收益可能为负 |
| 1.3 | 该方法的计算流程中**哪一步是瓶颈**（compute-bound / memory-bound / communication-bound）？瓶颈步骤使用的硬件资源是什么？其他步骤使用的资源是否与之**正交**（可同时使用而不竞争）？瓶颈在什么 batch size / 序列长度下出现？ | 探测**并发能否真正隐藏延迟**——review 中「瓶颈步骤与其他步骤资源使用互补时并发才带来实际加速」「计算和通信资源不存在竞争」是核心判断 |
| 1.4 | 该方法中是否有**不同模态/不同类型的数据**需要分别处理（visual tokens vs text tokens、cond vs uncond latent、不同 expert 的 token 组）？它们的处理流程是完全独立还是共享部分计算？如果将它们拆分到不同执行单元，**数据传输开销**多大？ | 探测**异构并发机会**——review 中「不同模态 tokens 的计算相对独立」「不同模态计算分离到不同实例」「cond 和 uncond 两个分支合并到相同 batch」都是对此的肯定 |
| 1.5 | 该方法引入了哪些**额外运行时开销**（动态路由、量化/反量化、稀疏 mask 生成、KV cache 重要性评估、运行时 PPL 计算）？这些开销是 compute-bound 还是 memory-bound？**能否与主计算重叠执行**？重叠后预期能隐藏多少比例？ | 探测**额外开销的可并发性**——这是 review 中最常见的模式（出现 10+ 次）：「额外开销可能通过并发优化」「可能通过并发隐藏」 |

#### 评估标准

对 Answer Agent 的回答，按以下标准评估该维度的价值：

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 子计算的独立性有**数学保证**（如置换不变性）或**已有人实现过并发**并给出定量收益证据 | 并发潜力可证实 | **高** |
| 子计算间存在边界依赖（可流水线），但**依赖深度被量化**（如 producer-consumer 距离为 N 个 tile） | 并发潜力有条件存在 | **高** |
| 运行时动态参数的变化范围被量化（min/max/分布），决策开销被测量（cycle/us），且决策开销 < 主计算的 5% | 动态性可量化管理 | **高** |
| 瓶颈资源与其他步骤资源**正交**（一个用 TC、一个用 CC；一个用 HBM BW、一个用 NVLink），重叠后无竞争 | 并发具备实际加速条件 | **高** |
| 额外运行时开销被明确识别，且**开销类型与主计算资源正交**（如主计算是 TC compute-bound，开销是 CUDA Core element-wise） | 额外开销可通过并发隐藏 | **高** |
| 仅定性描述「存在并发可能」但无独立性证明、无定量数据、无资源正交分析 | 并发潜力仅停留在假设层面 | **中** |
| 各步骤严格串行依赖、负载完全静态规则、额外开销极小或已被框架吸收 | 无并发优化空间 | **低** |

### 大类二：并发方法的应用和实现

**核心价值问题**：这个方法是**怎样实现并发的**？相比已有方法有什么独特贡献？

#### 引导提问

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 2.1 | 该方法通过什么**并发原语/机制**实现并发（CUDA Stream / CUDA Graph / MPS / persistent kernel / warp specialization / CDP / 多 Stream pipeline）？**为什么选择这种机制而不是其他**——在什么条件下这个选择最优，什么条件下会退化？ | 探测**并发实现的选择理由**——review 中「cuda graph 匹配并发算子，多 Stream 并发」「Mega kernel 持久化运行，多 kernel 并发实现方式」「利用 CUDA Stream 机制并发，按最大可并发拆分计算图」揭示了不同选择的适用场景 |
| 2.2 | 该方法的并发粒度是什么（**算子间 / 算子内 tile 间 / warp 间 / 指令间**）？这个粒度是固定的还是运行时可调的？更细的粒度带来了多少额外收益——**同步/barrier 开销**被量化了吗？同步是硬件原生（mbarrier/event）还是软件实现（atomic polling）？ | 探测**粒度-开销的 trade-off**——review 中「tile 粒度的融合可能提高执行的重叠率」「tile 级 barrier 替代 kernel 级 barrier」「event 模型定义灵活的操作同步，提高并发性能」都在关注这个 trade-off |
| 2.3 | 该方法的并发是**编译时静态确定的**还是**运行时动态调整的**？如果是运行时，决策依据是什么（负载特征 / 资源状态 / 历史 profile）？**决策开销**有多大？如果是编译时，是否准备了多个版本供运行时选择？ | 探测**静态 vs 动态的 trade-off**——review 中反复出现「编译期静态准备 + 运行时动态选择」「离线 multi-version + 在线动态 kernel 选择」「编译时搜索 tile 级别的并发机会」的模式 |
| 2.4 | 该方法中的并发执行单元之间是否存在**资源竞争**（SMEM / register / HBM bandwidth / L2 cache）？竞争程度在什么 batch size / 负载下最严重？是否有**资源隔离机制**（SM 分区 / MPS / warp 角色分工）？ | 探测**资源竞争是否抵消并发收益**——review 中「SM 分区作资源隔离来减少并发的资源竞争」「MPS 的 SM 隔离执行不同模块的独立计算」「乱序执行是并发，但不一定保证性能收益，因为资源竞争」都在关注这个问题 |
| 2.5 | 该方法与 review_draft.md 中已有的同类方法的核心**差异**是什么？差异来自什么**设计选择**（如 persistent kernel vs CUDA Graph、static scheduling vs dynamic、spatial vs temporal）？这个差异是否能被量化（吞吐量/延迟/资源利用率方面的差异）？ | 探测**方法的独特贡献**——review 中「与已有方法的差异」决定了深入价值。若方法只是已有方案的工程变体，深入价值有限 |
| 2.6 | 该方法是否**已在生产框架中集成**（vLLM / SGLang / TensorRT-LLM）或有**开源实现**？kernel launch 次数从多少减少到多少？消除了多少 HBM round-trip？SM 利用率从多少提升到多少？ | 探测**收益的可靠性和可复现性**——review 中「三大框架已集成说明技术成熟值得学习」「减少 kernel 启动开销」「HBM access -58%」「SM util 14%→93.17%」 |

#### 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 并发机制的选择理由明确（说明了为什么选 A 而非 B，A 在什么条件下最优、什么条件下退化） | 设计决策可理解、可评估 | **高** |
| 同步开销被量化（cycle/us），且 sync-to-compute ratio < 10%；或同步是硬件原生（mbarrier） | 并发实现代价可控 | **高** |
| 编译-运行时协同被清晰描述（编译时准备了什么、运行时如何选择、切换开销多大） | 动态适应性可评估 | **高** |
| 资源竞争被量化（如 L2 thrashing 概率、SMEM 容量冲突率），且有隔离机制 | 资源管理可验证 | **高** |
| 与已有方法的核心差异被明确区分（非「我们也做了 fusion」，而是「我们在 X 维度上做了 Y 不同的选择」） | 独特贡献可识别 | **高** |
| 框架已集成或有定量加速证据（DRAM traffic -X%、SM util +Y%、kernel launch N→M） | 收益可复现 | **高** |
| 有定性描述但缺乏定量对比、缺乏与已有方法的差异化分析 | 价值无法确认 | **中** |
| 纯软件方法无硬件机制关联、同步开销未量化、收益模糊 | 深入价值有限 | **低** |

### 大类三：提供并发机制的硬件模块/架构

**核心价值问题**：**什么硬件机制使并发成为可能**？该机制的能力边界在哪里？

#### 引导提问

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 3.1 | 该硬件模块提供了哪些**并发原语**（TMA / mbarrier / DSM / MPS / CDP / warp scheduler / CKE / NPU TS）？这些原语的**物理实现**是什么（独立硬件单元 / 共享总线仲裁 / 控制寄存器）？它们的**吞吐上限**和**适用条件**（数据大小/对齐/并发数）是什么？ | 探测**硬件并发原语的能力边界**——review 中「TMA 硬件模块提供传输控制和 kernel 计算并发」「DSM 是硬件机制，提供更大存储和计算容量」「NPU 解析 Task Descriptor Chain 对比 GPU GigaThread Engine」都在追问硬件原语的能力 |
| 3.2 | 多个并发原语**同时使用**时是否存在**隐式资源竞争**（crossbar 端口 / memory bank / register file）？硬件文档中没有说明但**实验中发现的竞争**有哪些？ | 探测**硬件并发陷阱**——review 中「TC 和 CC 能同时启动吗(存疑)」是对硬件并发真实性的质疑，需要实验证据 |
| 3.3 | 该硬件的并发是**时间复用**（warp 调度、kernel context switch）还是**空间并行**（独立计算单元、独立 memory bank）？空间并行的**可扩展性**上限在哪里？ | 探测**并发模式的物理基础**——review 中「Streaming 的硬件架构提供空间并发机制」「异构计算单元有并发潜力」「完全编译时静态调度，利用硬件空间并发，无运行时并发」区分了两种模式 |
| 3.4 | 该硬件并发原语的**软件可编程粒度**是什么（PTX 指令 / CUDA API / 编译器 intrinsic / libsmctrl）？软件能控制到 warp 级、block 级、SM 级还是 kernel 级？如果迁移到**无此原语的其他平台**（AMD/NPU/Dataflow），软件需要多少额外开销来模拟？ | 探测**可编程性和可移植性**——review 中「CuTe 直接控制异步硬件的精确 timing，进行无法在 Triton 中表达 warp-specialized 异步调度」「setmaxnreg 硬件寄存器重分配」「libsmctrl SM masking」 |

#### 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 硬件并发原语的吞吐上限和适用条件被定量描述（如「≥64KB payload 时同步开销 <63%，不满足时退化为 HBM spill」） | 硬件能力边界可量化 | **高** |
| 多原语协同的资源竞争被实验验证过（如「同时使用 TMA+TC+CC 时 crossbar 端口无竞争」） | 硬件并发真实性可验证 | **高** |
| 空间并行 vs 时间复用的比例被分析，可扩展性上限被讨论 | 并发模式的物理基础被理解 | **高** |
| 软件可编程粒度被明确（warp/block/SM 级），跨平台等价替代方案被讨论 | 软硬件协同设计可评估 | **高** |
| 仅复述硬件公开文档无新见地、并发机制能力边界未被讨论 | 信息增量有限 | **中** |
| 硬件描述为纯手册复述，无并发相关分析 | 无并发相关性 | **低** |

### 大类四：影响并发的架构/机制

**核心价值问题**：**什么架构因素限制或扩展了并发效率**？该限制是否可绕过？

#### 引导提问

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 4.1 | 该方法的**memory hierarchy**（HBM → L2 → SMEM → Register）中，哪一级是并发瓶颈？多 kernel 并发时这一级的带宽/容量是否被**共享和竞争**？瓶颈是**容量不足**（放不下 working set）还是**带宽不足**（多 kernel 共享饱和）还是**延迟过高**（remote chiplet 访问 10-15×）？ | 探测**瓶颈的根因类型**——review 中「HBM bandwidth 是共享资源——所有并发 kernel 的全局访存经同一组 HBM stack」「Expert Weight Load 42% 是核心瓶颈」「L2 命中 vs HBM miss 性能差异 2×」「SMEM capacity 是纯软件方案的物理硬上限」都在区分瓶颈类型 |
| 4.2 | 该方法的**数据访问模式**（coalesced / scatter / gather / strided）是什么？多 kernel 并发时不同 kernel 的访问模式是否会**互相破坏 coalescing**？SMEM 的 bank conflict 是否被分析过？ | 探测**并发对访存效率的破坏**——review 中「bank conflict 可使有效 SMEM BW 退化 88%」「不同访问模式混合可能使 DRAM 效率从 100% 退化到 3%」「多微算子并发时不同算子的 bank 访问模式不同需 layout 转换」 |
| 4.3 | 该方法是否涉及**跨 chiplet / 跨 die / 跨 NUMA node** 的数据传输？remote vs local 延迟/带宽比是多少？NUMA 效应如何影响并发 kernel 的 placement？ | 探测**分布式硬件下的并发约束**——review 中「remote/local 延迟比可达 10-15× 需 NUMA-aware 调度」「L1.5 cache 专门缓存 remote data」 |
| 4.4 | 该方法的**片上通信**使用什么 NoC 拓扑和路由？通信模式（one-to-one / multicast / all-to-all）是否与 NoC 的拥塞控制机制兼容？链路带宽是否支持该通信模式的高并发？ | 探测**NoC 对并发通信的支撑能力**——review 中「多 VN 隔离不同 coherence 消息类不互相阻塞」「All-to-All 占 MoE 训练 41.5%-95.7% 时间，HalfRing 平均 2.28× 加速」「leaky-bucket 平滑突发流量」「优先级队列按时间戳调度通信 chunk」 |
| 4.5 | 该架构限制是**物理不可绕过**（SRAM 容量、HBM PHY 数量）还是**可通过软件策略缓解**（warp 调度顺序、tile size 选择、block order）？硬件提供的隔离机制（MPS / MIG / VN）能否消除共享资源冲突？ | 探测**硬限制 vs 软限制**——review 中「SMEM 容量是物理硬上限」「硬件限制不可绕过只能减少数据搬运量」「MPS SM Partition 硬约束需 CUDA 初始化前设定」区分了两类限制 |

#### 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 瓶颈根因被精确区分（容量/带宽/延迟），且各因素的贡献比例被量化（如「Expert Weight Load 占 decode time 42%，Attention 19%，Other 12%」） | 瓶颈可精确诊断 | **高** |
| 并发对访存效率的影响被量化（如「2 kernel 并发时 DRAM efficiency 从 90% 降至 45%」），且缓解策略被讨论 | 并发代价可量化 | **高** |
| 硬限制和软限制被明确区分，软件可缓解的限制给出了具体策略 | 优化空间可评估 | **高** |
| 仅泛泛提及「memory wall」等概念，无定量分析 | 信息增量有限 | **中** |
| 无并发架构分析 | 无并发相关性 | **低** |

### 大类五：架构性能和开销的实验工具

**核心价值问题**：用什么**工具和方法**测量并发性能？精度/速度/覆盖范围如何？

#### 引导提问

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 5.1 | 该工具可以测量到什么**粒度**（cycle 级 / kernel 级 / operator 级 / request 级）？能否捕捉并发执行的**时序重叠**（如 kernel A 和 B 在哪些 cycle 同时执行、各占什么资源）？ | 探测**工具对并发的可见性**——粗粒度工具（如 kernel-level profiler）无法捕捉 warp 级并发和指令级 overlap |
| 5.2 | 该工具的**性能建模**覆盖了哪些并发因素（warp 调度 / memory contention / NoC 拥塞 / barrier 同步 / TMA in-flight）？**遗漏了哪些**？遗漏因素对并发分析结论的影响有多大？ | 探测**建模的完备性**——遗漏关键并发因素（如 warp 调度或 NoC 拥塞）的模型会给出误导性的并发效率评估 |
| 5.3 | 该工具是**模拟器**（cycle-accurate / event-driven / analytical）还是**真实硬件测量**（profiler / nsight）？结果与真实硬件的**误差**被验证过吗（如 8×H100 DGX 验证 <5% 误差）？ | 探测**工具的准确度**——模拟器灵活但慢，硬件测量准确但粒度受限 |
| 5.4 | 该工具能否用于评估**新硬件架构**（Chiplet GPU / PIM / 3D 堆叠）的并发性能？如果不能，需要增加什么建模模块？ | 探测**工具对未来的覆盖能力**——现有工具（cycle-accurate 太慢，ASTRA-sim 不支持 single-GPU-like 编程模型）可能均不适用 |

#### 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 工具可测量到 cycle 级或 warp 级的并发时序重叠，建模覆盖了 ≥3 种并发因素 | 并发可精确测量 | **高** |
| 工具的误差已被验证（如与真实硬件对比 <5%），或来自真实硬件测量 | 结果可信 | **高** |
| 工具可扩展评估新硬件架构的并发性能，或讨论了扩展所需的建模模块 | 未来适用 | **高** |
| 工具粒度粗（仅 kernel 级），建模遗漏关键并发因素 | 并发分析能力有限 | **中** |
| 无并发测量相关讨论 | 无并发相关性 | **低** |

## 两级问题层次

Question Agent 的提问有两个层次目标：**第一级是通过五大类别的模板问题探索方法在各维度的价值；第二级是检查 Answer Agent 的回答是否在五层并发执行链上充分覆盖。**

### 第一级：多维度价值探索

**核心思路**：五大类别不是分类标签而是**价值维度**。Question Agent 对每个可能相关的大类，使用该大类的引导提问模板向 Answer Agent 提问，基于回答与该大类评估标准的匹配程度，判断该方法在此维度上的价值。

**操作流程**：

1. 阅读 idea note，判断方法可能与哪些大类相关（参考大类总览表中的核心价值问题）
2. 对每个可能相关的大类，从引导提问表中选取最匹配的 2-3 个问题发送给 Answer Agent
3. 将 Answer Agent 的回答与**该大类的评估标准表**对照——回答命中了多少「高」信号？多少「中」信号？
4. 按以下规则判定该维度的价值：
   - 回答命中 ≥2 个「高」信号 → 该维度价值 **高**
   - 回答命中 ≥1 个「高」信号但存在「中」信号 → 该维度价值 **中**，补充追问至可判定
   - 回答无「高」信号 → 该维度价值 **低**

**跨维度汇总**：
- ≥1 个维度价值为高 → 进入第二级（五层完整性检查）
- 所有维度价值均为低 → 标记「相关性=低」，终止追问
- 多个维度价值为高 → **强正例信号**，每个高价值维度都应覆盖

### 第二级：五层并发执行链完整性检查

**提问目标**：检查 Answer Agent 的回答是否覆盖了从负载到硬件的完整并发执行链。任一层的缺失或模糊都是该层应补充追问的信号。

**五层覆盖评估**（逐层检查 Answer Agent 的回答）：

| 层次 | 检查项 | 未覆盖时的追问方向 |
|------|--------|------------------|
| **负载层** | 并发潜力的来源是否明确？（哪些子计算独立、动态性在哪、瓶颈是什么） | 「该方法的计算流程可以分解为哪些独立子计算？运行时哪些参数是动态的？」 |
| **编译层** | 编译框架如何表达和利用并发？（IR、图优化、fusion、codegen 策略） | 「编译过程中哪个阶段发现了并发机会？IR 如何表达并发依赖？」 |
| **调度层** | 运行时如何将并发映射到硬件资源？（Dispatcher 策略、调度粒度、静态/动态） | 「调度决策是编译时还是运行时做出的？调度粒度是什么？」 |
| **Kernel层** | Kernel 内部如何实现并发？（tile 切分、warp 分工、pipeline、持久化） | 「Kernel 的 tile 约束是什么？warp 的角色分工是什么？」 |
| **硬件层** | 什么硬件机制支撑了这种并发？（执行单元、同步原语、访存架构、能力边界） | 「利用了哪些硬件并发原语？硬件能力边界在哪里？」 |

**第二级判别规则**：
- 五层中有 ≥3 层覆盖充分 → 回答质量合格，可进入最终判别
- 五层中有 <3 层覆盖充分 → 针对缺失层逐层补充追问，追问完成后进入最终判别
- 若多轮追问后仍无法覆盖关键层 → 标记为「信息不足」，在评判中说明

### 两级递进的流程控制

```
第一级（多维度价值探索）
  │
  ├─ 至少 1 个大类显示高价值信号 → 进入第二级
  ├─ 所有大类均无高价值信号 → 标记「相关性=低」，终止
  └─ 回答模糊 → 补充追问至可评估
        │
        ▼
第二级（五层完整性检查）
  │
  ├─ ≥3 层覆盖充分 → 进入最终判别
  ├─ <3 层覆盖 → 针对缺失层补充追问 → 回到循环
  └─ 多轮仍无法覆盖关键层 → 标记「信息不足」→ 进入判别
        │
        ▼
    [完成判别]
```

## 最终判别

Question Agent 在两级问答充分后，给出评判意见。评判必须**引用具体的正例参照**（review_draft.md 中的同类方法名称和 review 评语），而非泛化评价。

### 评判维度与评定标准

```markdown
**相关性**：[高/中/低] — <理由>
**参考价值**：[高/中/低] — <理由>
**深入价值**：[高/中/低] — <方向建议>
**评判总结**：<综合评述>
```

**相关性** —— 方法在五大类别的价值维度上是否显示高价值信号：
- **高**：至少 1 个大类显示高价值信号（见第一级价值评估标准表），方法直接涉及并发潜力/并发实现/硬件并发机制/影响并发的架构因素。
- **中**：方法间接涉及并发（如通用的性能优化技术，需特定视角才能关联并发），或仅在边缘上与并发相关。
- **低**：所有大类均无高价值信号，与五大类别的关注主题均无法对齐。

**参考价值** —— 方法是否为后续工作提供可借鉴的信息（不依赖其深度）：
- **高**：框架已集成（vLLM/SGLang/TensorRT-LLM）、有定量性能证据、或揭示可迁移的设计模式（如持久化 kernel、SM 分区、编译多版本）。
- **中**：有定性描述但缺乏定量证据，或设计思路可参考但实现细节不完整。
- **低**：信息碎片化，或仅为概念性描述，无实现路径。

**深入价值** —— 方法的并发执行链是否值得深入挖掘：
- **高**：五层中有 ≥3 层揭示了非平凡的机制/设计决策，且存在可迁移到其他场景的模式。
- **中**：有一定机制深度但属已知模式的变体，深入收益有限。
- **低**：五层回答均为工程实现细节，无值得深入的设计决策或 trade-off。

### 高价值方法的最终判定

满足以下**任意一条**即视为高价值方法，应纳入方法摘要：
- 相关性=高 且 参考价值=高（可靠的并发相关信息来源）
- 深入价值=高（有值得深入挖掘的核心机制，即使当前相关性不直接）

### 评判意见示例（参照 review_draft.md 风格）

```markdown
**相关性**：高 — 方法属于「并发方法的应用和实现」下的「Serving/框架架构与实现」，
  其分离式 KV-Cache 架构直接涉及并发中的跨请求复用和通信-计算重叠，
  且已在三大框架（vLLM/SGLang/TensorRT-LLM）中集成。
**参考价值**：高 — Mooncake Store 已被多个主流框架采用，技术成熟度可验证，
  且提供了 RDMA/TCP/CXL/Shared Memory 多协议传输的性能数据（40GB KVCache 190 GB/s）。
**深入价值**：高 — 关注点「KV-cache 感知全局调度器→路由请求到 KV cache 已在本地
  或最近节点的 worker」揭示了分离式架构中调度决策与数据位置的协同设计模式，
  可迁移到其他有状态的推理场景（如 Modal Cache 的跨请求复用）。
**评判总结**：高价值正例——分离式 KV-Cache 架构是当前并发 Serving 的重要方向，
  方法提供的数据位置感知调度模式具有可迁移性。
```

## 流程约束总结

| 规则 | 说明 |
|------|------|
| **先查后问** | 提问前对照本 skill 的五大类别价值维度，预判方法可能涉及的价值维度 |
| **两级递进** | 第一级（多维度价值探索：用大类模板提问→评估价值信号）→ 第二级（五层完整性检查：逐层检查回答覆盖度），逐级深入，不可跳级 |
| **方法优先于判别** | 先理解方法本身的机制（它解决了什么问题、怎么解决的），再对照引导式追问标准设计问题，最后判别——避免以判代学 |
| **引导式追问** | 使用大类第一级模板问题，问题必须具体到「机制/量化/权衡」层面，引导 Answer Agent 按五层结构逐层追溯并发执行链 |
| **多轮推进** | 每轮基于回答决定下一步：某大类显示高价值→继续追问 / 五层覆盖不充分→补充追问缺失层 / 跨多个大类→切换大类 / 完成判别（两级均已覆盖） |
| **去重升级** | 重复/近似条目将原条目升级类别，新条目作为其子条目；相似条目标记为「变体」而非独立条目 |
| **I/O 协议** | 见顶部「执行模式」章节——`___QA_QUESTION___` 输出问题，`___JUDGMENT_COMPLETE___` 输出评判 |
