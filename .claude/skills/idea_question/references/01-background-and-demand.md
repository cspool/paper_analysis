# 动态(调度/并发)的背景/需求

**核心价值问题**：这个负载/方法中**哪里存在并发潜力**？为什么过去没有利用这些潜力？

## 引导提问

向 Answer Agent 提问时，从以下选取最匹配的 2-3 个问题。所有问题都要求 Answer Agent 给出**具体的、有定量证据的回答**。

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 1.1 | 该方法的计算流程可以分解为哪些**相对独立的子计算**？这些子计算之间的数据依赖是只在边界处存在（可流水线）还是深度交错（不可拆分）？子计算之间的独立性是否有**数学保证**（如置换不变性）还是仅为经验观察？ | 探测并发潜力的**粒度和可靠性**——review 中「各 Expert 间完美并行」「不同模态 tokens 的计算相对独立」是对子计算独立性的肯定；而「TC 和 CC 能同时启动吗(存疑)」则是对独立性的质疑 |
| 1.2 | 该方法在执行过程中**哪些参数/数据在运行时才能确定**（token 数、expert 激活模式、序列长度、分辨率、control flow）？这些参数的**变化范围**有多大（min/max/分布）？运行时确定这些参数的**决策开销**是多少 cycle/us——与主计算相比占比多大？ | 探测**动态性的量化程度**——review 中反复出现「运行时计算确定」「产生额外开销」的模式：如果动态性很小或决策开销很大，并发收益可能为负 |
| 1.3 | 该方法的计算流程中**哪一步是瓶颈**（compute-bound / memory-bound / communication-bound）？瓶颈步骤使用的硬件资源是什么？其他步骤使用的资源是否与之**正交**（可同时使用而不竞争）？瓶颈在什么 batch size / 序列长度下出现？ | 探测**并发能否真正隐藏延迟**——review 中「瓶颈步骤与其他步骤资源使用互补时并发才带来实际加速」「计算和通信资源不存在竞争」是核心判断 |
| 1.4 | 该方法中是否有**不同模态/不同类型的数据**需要分别处理（visual tokens vs text tokens、cond vs uncond latent、不同 expert 的 token 组）？它们的处理流程是完全独立还是共享部分计算？如果将它们拆分到不同执行单元，**数据传输开销**多大？ | 探测**异构并发机会**——review 中「不同模态 tokens 的计算相对独立」「不同模态计算分离到不同实例」「cond 和 uncond 两个分支合并到相同 batch」都是对此的肯定 |
| 1.5 | 该方法引入了哪些**额外运行时开销**（动态路由、量化/反量化、稀疏 mask 生成、KV cache 重要性评估、运行时 PPL 计算）？这些开销是 compute-bound 还是 memory-bound？**能否与主计算重叠执行**？重叠后预期能隐藏多少比例？ | 探测**额外开销的可并发性**——这是 review 中最常见的模式（出现 10+ 次）：「额外开销可能通过并发优化」「可能通过并发隐藏」 |

## 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 子计算的独立性有**数学保证**（如置换不变性）或**已有人实现过并发**并给出定量收益证据 | 并发潜力可证实 | **高** |
| 子计算间存在边界依赖（可流水线），但**依赖深度被量化**（如 producer-consumer 距离为 N 个 tile） | 并发潜力有条件存在 | **高** |
| 运行时动态参数的变化范围被量化（min/max/分布），决策开销被测量（cycle/us），且决策开销 < 主计算的 5% | 动态性可量化管理 | **高** |
| 瓶颈资源与其他步骤资源**正交**（一个用 TC、一个用 CC；一个用 HBM BW、一个用 NVLink），重叠后无竞争 | 并发具备实际加速条件 | **高** |
| 额外运行时开销被明确识别，且**开销类型与主计算资源正交**（如主计算是 TC compute-bound，开销是 CUDA Core element-wise） | 额外开销可通过并发隐藏 | **高** |
| 仅定性描述「存在并发可能」但无独立性证明、无定量数据、无资源正交分析 | 并发潜力仅停留在假设层面 | **中** |
| 各步骤严格串行依赖、负载完全静态规则、额外开销极小或已被框架吸收 | 无并发优化空间 | **低** |
