# 并发方法的应用和实现

**核心价值问题**：这个方法是**怎样实现并发的**？相比已有方法有什么独特贡献？

## 引导提问

| # | 引导提问 | 这个问题在探测什么（review 模式来源） |
|---|---------|----------------------------------|
| 2.1 | 该方法通过什么**并发原语/机制**实现并发（CUDA Stream / CUDA Graph / MPS / persistent kernel / warp specialization / CDP / 多 Stream pipeline）？**为什么选择这种机制而不是其他**——在什么条件下这个选择最优，什么条件下会退化？ | 探测**并发实现的选择理由**——review 中「cuda graph 匹配并发算子，多 Stream 并发」「Mega kernel 持久化运行，多 kernel 并发实现方式」「利用 CUDA Stream 机制并发，按最大可并发拆分计算图」揭示了不同选择的适用场景 |
| 2.2 | 该方法的并发粒度是什么（**算子间 / 算子内 tile 间 / warp 间 / 指令间**）？这个粒度是固定的还是运行时可调的？更细的粒度带来了多少额外收益——**同步/barrier 开销**被量化了吗？同步是硬件原生（mbarrier/event）还是软件实现（atomic polling）？ | 探测**粒度-开销的 trade-off**——review 中「tile 粒度的融合可能提高执行的重叠率」「tile 级 barrier 替代 kernel 级 barrier」「event 模型定义灵活的操作同步，提高并发性能」都在关注这个 trade-off |
| 2.3 | 该方法的并发是**编译时静态确定的**还是**运行时动态调整的**？如果是运行时，决策依据是什么（负载特征 / 资源状态 / 历史 profile）？**决策开销**有多大？如果是编译时，是否准备了多个版本供运行时选择？ | 探测**静态 vs 动态的 trade-off**——review 中反复出现「编译期静态准备 + 运行时动态选择」「离线 multi-version + 在线动态 kernel 选择」「编译时搜索 tile 级别的并发机会」的模式 |
| 2.4 | 该方法中的并发执行单元之间是否存在**资源竞争**（SMEM / register / HBM bandwidth / L2 cache）？竞争程度在什么 batch size / 负载下最严重？是否有**资源隔离机制**（SM 分区 / MPS / warp 角色分工）？ | 探测**资源竞争是否抵消并发收益**——review 中「SM 分区作资源隔离来减少并发的资源竞争」「MPS 的 SM 隔离执行不同模块的独立计算」「乱序执行是并发，但不一定保证性能收益，因为资源竞争」都在关注这个问题 |
| 2.5 | 该方法与 review_draft.md 中已有的同类方法的核心**差异**是什么？差异来自什么**设计选择**（如 persistent kernel vs CUDA Graph、static scheduling vs dynamic、spatial vs temporal）？这个差异是否能被量化（吞吐量/延迟/资源利用率方面的差异）？ | 探测**方法的独特贡献**——review 中「与已有方法的差异」决定了深入价值。若方法只是已有方案的工程变体，深入价值有限 |
| 2.6 | 该方法是否**已在生产框架中集成**（vLLM / SGLang / TensorRT-LLM）或有**开源实现**？kernel launch 次数从多少减少到多少？消除了多少 HBM round-trip？SM 利用率从多少提升到多少？ | 探测**收益的可靠性和可复现性**——review 中「三大框架已集成说明技术成熟值得学习」「减少 kernel 启动开销」「HBM access -58%」「SM util 14%→93.17%」 |

## 评估标准

| 回答特征 | 价值信号 | 判定 |
|---------|---------|------|
| 并发机制的选择理由明确（说明了为什么选 A 而非 B，A 在什么条件下最优、什么条件下退化） | 设计决策可理解、可评估 | **高** |
| 同步开销被量化（cycle/us），且 sync-to-compute ratio < 10%；或同步是硬件原生（mbarrier） | 并发实现代价可控 | **高** |
| 编译-运行时协同被清晰描述（编译时准备了什么、运行时如何选择、切换开销多大） | 动态适应性可评估 | **高** |
| 资源竞争被量化（如 L2 thrashing 概率、SMEM 容量冲突率），且有隔离机制 | 资源管理可验证 | **高** |
| 与已有方法的核心差异被明确区分（非「我们也做了 fusion」，而是「我们在 X 维度上做了 Y 不同的选择」） | 独特贡献可识别 | **高** |
| 框架已集成或有定量加速证据（DRAM traffic -X%、SM util +Y%、kernel launch N→M） | 收益可复现 | **高** |
| 有定性描述但缺乏定量对比、缺乏与已有方法的差异化分析 | 价值无法确认 | **中** |
| 纯软件方法无硬件机制关联、同步开销未量化、收益模糊 | 深入价值有限 | **低** |
