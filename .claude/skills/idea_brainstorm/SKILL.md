# Idea Brainstorm — Brainstorm Agent

**Brainstorm Agent** 用于处理那些与「AI 推理系统并发」**表面关联性低**的方法或论文。它不是做确定性判别（那是 Question Agent 的职责），而是通过结构化的联想框架，探索「这个方法/场景是否可能迁移到并发领域」的可能性。

---

## 核心思想：从「学习过程」到「联想框架」

Question Agent（`idea_question` skill）中的五大类别 + 三级问题层次 + 引导式追问标准，来源于对 `draft/review_draft.md` 中 120+ 条人工评阅的系统性归纳。这个归纳过程本身具有方法论价值——它可以被复用为一个**联想框架**，用于在看似无关的领域中寻找连接点。

### 归纳过程回顾

从 `review_draft.md` 中提炼出五大类别的过程：

1. **聚类**：120+ 条高价值正例按「它们在问什么」自然聚类为 5 个大问题
2. **提取共性**：每个大类下识别出反复出现的子问题模式（二级类别）
3. **抓住核心机制**：用户用 `****` 标注的部分揭示了方法「为什么有效」的根因——这些根因往往是可跨域迁移的设计模式
4. **形成追问模板**：将判别经验固化为引导式问题，使后续评估不再依赖直觉

### 联想框架的核心操作

当面对一个与并发**表面无关**的方法时，不直接问「它和并发有什么关系」，而是依次通过以下 5 个透镜审视：

| 透镜 | 问题 | 目的 |
|------|------|------|
| **透镜 1：负载特征** | 这个方法处理的负载有什么特征（动态性、不规则性、数据规模、实时性要求）？这些特征在并发推理负载中是否也存在？ | 发现负载层面的相似性 |
| **透镜 2：实现机制** | 这个方法的核心实现机制是什么（调度策略、资源管理、数据流组织、编译优化）？这些机制如果应用到并发推理中，能解决什么问题？ | 发现机制层面的可迁移性 |
| **透镜 3：硬件-软件协同** | 这个方法是否利用了特定的硬件机制或揭示了硬件限制？如果是，类似的硬件-软件协同模式在 GPU/NPU 并发场景中是否也存在？ | 发现架构层面的对应关系 |
| **透镜 4：瓶颈与trade-off** | 这个方法解决了什么瓶颈？在解决过程中引入了什么 trade-off？这个 trade-off 在并发推理中是否也是核心矛盾？ | 发现设计决策层面的共性 |
| **透镜 5：实验方法** | 这个方法用什么工具/方法测量性能？这些测量方法是否可用于评估并发推理系统的效果？ | 发现工具层面的复用可能 |

## 执行模式

本 skill 可被 `idea_review_orchestrator.ts` 调度（作为 QA session 的替代 skill），或以独立 session 运行。输出格式与 Question Agent 对齐：

### 输出格式

**若有联想发现**：
```
___BRAINSTORM_FINDING___
{
  "method_name": "<方法名>",
  "relevance_to_concurrency": "高"|"中"|"低",
  "lens_match": ["透镜1:负载特征", "透镜2:实现机制", ...],
  "migration_idea": "<具体的跨域迁移思路——这个方法/机制如何应用到并发推理>",
  "analogous_concurrent_methods": ["review_draft.md中的类似并发方法"],
  "confidence": "高"|"中"|"低",
  "requires_validation": true|false
}
___BRAINSTORM_FINDING_END___
```

**若未发现联想**：
```
___BRAINSTORM_NEGATIVE___
{
  "method_name": "<方法名>",
  "lenses_checked": ["透镜1", "透镜2", ...],
  "reason": "<为什么未发现——方法论局限/确实无关/信息不足>"
}
___BRAINSTORM_NEGATIVE_END___
```

**最终总结**：
```
___BRAINSTORM_COMPLETE___
{
  "findings_count": N,
  "high_relevance_count": N,
  "summary": "<综合评述——最有价值的联想方向>"
}
___BRAINSTORM_COMPLETE_END___
```

## 联想操作流程

### 第一步：理解方法本身

读取 idea note 或论文，理解：
- 这个方法解决了什么问题
- 核心机制是什么（等价于 `****` 关注点）
- 在什么约束下做出了什么设计选择

### 第二步：五透镜审视

对每个透镜，不是简单匹配关键词，而是按照以下引导问题进行**结构化联想**：

**透镜 1：负载特征联想**
```
- 该方法的负载有什么动态性？（数据量变化、到达时间分布、依赖关系动态）
- 并发推理中哪些负载有类似的动态性？（MoE 的 expert 激活可变、MLLM 的 visual token 数量可变、Video 的帧率可变）
- 该方法处理这种动态性的策略是什么？该策略是否可迁移？
```

**透镜 2：实现机制联想**
```
- 该方法的核心机制可以抽象为什么模式？（调度/缓存/融合/分解/流水线/预测/复用）
- review_draft.md 五大类别中是否有使用类似抽象模式的方法？
- 如果有——具体差异在哪里？如果没有——这是否意味着新的方法类别？
```

**透镜 3：硬件-软件协同联想**
```
- 该方法是否利用了特定硬件特性？这个硬件特性的本质是什么（空间并行/时间复用/异步/同步）？
- GPU/NPU 中是否有等价的硬件特性？
- 如果无等价特性——软件层面能否近似模拟？
```

**透镜 4：瓶颈与 trade-off 联想**
```
- 该方法的瓶颈是什么（compute/memory/communication/latency/overhead）？
- 解决这个瓶颈的 trade-off 是什么（精度-速度/灵活性-效率/通用性-专用性）？
- 并发推理中是否面临同类型瓶颈和 trade-off？
```

**透镜 5：实验方法联想**
```
- 该方法用什么评测指标和工具？
- 这些指标/工具是否能揭示并发推理中目前未被测量的维度？
```

### 第三步：形成联想假设

对每个有匹配的透镜，形成具体的**迁移假设**：
- 「<方法名> 中的 <机制> 可能可以用于解决并发推理中的 <问题>，因为两者都面临 <共性>」

### 第四步：评估假设可信度

- **高**：机制层面的共性明确，迁移路径清晰，定量证据充分
- **中**：概念层面的类比成立，但具体迁移路径需要进一步验证
- **低**：仅在隐喻层面有相似性，缺乏可操作的迁移路径

## 与 Question Agent 的分工

| 维度 | Question Agent | Brainstorm Agent |
|------|---------------|-----------------|
| **输入** | 与并发直接相关的方法 | 与并发表面无关的方法 |
| **目标** | 确定性判别（相关/不相关，高/低价值） | 可能性探索（有无联想，迁移是否可行） |
| **输出** | 评判意见（相关性/参考价值/深入价值） | 联想假设 + 可信度评估 |
| **方法** | 五大类别匹配 → 三级追问 → 判别 | 五透镜审视 → 类比推理 → 假设生成 |
| **典型场景** | review_draft.md 覆盖的方法类型 | 跨领域论文、新硬件架构、非 AI 系统方法 |

---

## 流程约束

| 规则 | 说明 |
|------|------|
| **先理解后联想** | 先完整理解方法本身，再套用透镜——避免强行类比 |
| **五透镜不必全部通过** | 有 1-2 个透镜的强联想即可产出有价值的假设 |
| **无联想也是有效输出** | 五透镜均无匹配 → 输出 `___BRAINSTORM_NEGATIVE___`，说明原因 |
| **假设不等于结论** | 联想假设标记 `requires_validation: true`，需要后续验证 |
| **类比需具体** | 避免「两者都涉及调度所以相关」——必须指出具体机制/模式层面的共性 |
