# Experiment Flow 的本地代理基线、开源源码改造与模拟器修订设计

状态：已实现为 Direction Experiment Loop format v3、实验载体政策
`LOCAL_PROXY_V2`；承接
`02_direction_lab_and_evidence_judge_loop_design.md`，记录首次运行暴露出的基线复现
问题。实现入口为 `scripts/direction_experiment_loop.ts`，主政策快照为
`scripts/direction_experiment_loop/contracts/experiment_policy.md`，对应 Skill 为
`.codex/skills/direction-evidence-judge/` 与 `.codex/skills/direction-lab-goal/`。

## 1. 本次修订解决的问题

第一版设计允许 Lab Goal 动态寻找环境和实现，但没有充分区分以下两件事：

```text
复现论文完整软件、硬件和绝对性能趋势

与

构造能够公平检验当前 Direction 因果变化的实验载体
```

当冻结 Direction 把前者设成进入 A/B 消融的硬门槛，而论文实现、最终策略或指定
硬件不可获得时，Flow 会在完成大量环境和基线工作后返回 `BLOCKED`，却始终没有
执行真正决定 Direction 的对照实验。

以缓存状态感知 DAG Slack Direction 为例，真正需要判断的是同一执行系统中的
`P3-P2`：

```text
P2：缓存无关的 DAG 剩余 Slack 排序
P3：仅把参考 cache 分支替换为实际 cache 状态对应分支
```

论文 EEVEE 的绝对 SM 利用率、完整 vLLM 修改和特定 A100/RTX 3090 环境可以界定
外部有效性，但不应在没有充分理由时阻止上述局部因果比较。

## 2. 修订后的核心原则

Experiment Flow 优先复现当前 Direction 的**因果接口和公平比较边界**，不默认要求
复现论文完整系统。

```text
冻结 Direction
  ↓
识别唯一主要变化及其所需接口
  ↓
选择能够表达这些接口的最小可信实验载体与最窄证据级别
  ↓
在同一载体内执行配对 baseline/variant 消融
  ↓
按载体能力限定结论
```

论文系统仍是重要参考，但其作用改为：

- 提供 baseline 方法、机制动机、配置范围和已报告趋势；
- 帮助选择开源实现、真实硬件接口、模拟器和测量方法；
- 说明本地代理结果能否向原论文环境外推；
- 不把未公开源码、不可得最终策略或不同 GPU 自动变成实验停止条件。

硬件、软件、模型规模、数据量、请求规模和 trace 时长均可平替或弱化。若某一维度
承载 Direction 必需的机制，则代理或模拟器必须保留该机制，而不要求复刻论文的
完整环境。弱化时必须保留：

- 当前优化所作用的因果接口；
- 机制发生所需的触发条件；
- baseline/variant 之间唯一主要变化；
- 仍然必要的正确性、输出等价或质量约束。

同载体一致是指弱化配置冻结后，baseline 与 variant 在组内一致，而不是要求二者
与论文环境一致。弱化只会缩小结论适用范围，不会自动使实验无效。

## 3. 实验载体的选择顺序

### 3.1 机制验证优先：弱化代理

当本轮只需判断机制是否成立时，Lab Goal 应使用能够触发因果路径的最小可信代理，
而不是立即建立完整规模环境。允许的弱化包括：

- 使用保留相关 operator、controller、queue 或 cache 路径的更小模型；
- 使用仍覆盖触发条件的数据子集；
- 减少请求数、并发范围或测量时长；
- 缩短 trace，但保留足够的预热、事件数量和机制触发次数；
- 平替硬件、runtime、framework，或移除与因果比较无关的软件模块。

每次弱化必须记录弱化项、保留的因果不变量、实际触发次数和结论边界。若弱化消除
了关键竞争、cache 状态、队列事件、kernel 路径、拓扑或质量依赖，则该代理无效。

### 3.2 本地性能证据：单卡真实执行

只要 Direction 的主要机制能在单卡上表达，就优先使用当前可用 GPU 做真实实验。
单卡可以减少多卡通信、拓扑、同步和资源分配带来的混杂，也能缩短源码修改、运行
和诊断循环。

单卡真实执行可以覆盖但不限于：

- controller 与请求优先队列；
- 动态或静态 batching；
- cache 命中、驻留、淘汰和 host spill；
- 单卡内 CUDA stream、MPS、共享内存和 CUDA IPC；
- kernel、内存、队列和运行时开销；
- 模型输出等价性、端到端延迟和单卡吞吐。

若原 Direction 同时包含可单卡检验的核心机制和多卡外推主张，先完成单卡机制
验证，再把多卡部分作为独立证据边界处理。不得因为先做单卡而静默宣称已经验证
多卡通信或扩展性。

### 3.3 涉及系统修改：优先选择最容易修改的开源实现

当 Direction 需要修改 serving runtime、controller、scheduler、cache manager、
compiler 或 simulator 时，Lab Goal 应先寻找能够覆盖关键因果接口且修改成本最低的
开源版本，而不是默认从头重建论文完整系统。

候选实现按以下标准选择：

1. 能在当前单卡环境安装并运行，或只需有界依赖修复；
2. 关键模块有源码，能够定位并修改当前 Direction 的接口；
3. baseline 可以独立运行并通过正确性检查；
4. baseline 与 variant 可由同一代码路径或 feature flag 切换；
5. 能记录当前 Direction 所需的队列、cache、阶段、资源和性能事件；
6. 修改面较小，构建和单轮实验成本适合迭代；
7. 许可证和依赖允许当前科研用途及本地修改。

开源实现不要求与论文系统同名。若一个更容易修改的公开 serving/runtime 已经暴露
同样的因果接口，它可以成为本地代理载体，但必须明确记录与论文系统的差异。

### 3.4 源码安装和修改合同

涉及系统源码修改时，Lab Goal 应：

- 使用源码安装或 editable install，而不是只修改不可追溯的已安装 wheel；
- 保存仓库地址、commit、submodule、依赖锁定和构建命令；
- 保存未修改 baseline、当前 patch 和必要的本地适配层；
- 尽量让 baseline/variant 共用一个 build，并通过显式开关切换；
- 记录因当前 GPU、驱动、CUDA 或 Python 版本产生的兼容性修改；
- 先通过输出、接口和资源不变量检查，再冻结确认性实验配置；
- 不根据确认性结果继续修改 baseline 或成功条件而不重新建立实验绑定。

Lab Goal 可以自行局部构建缺失的软件组件，例如最小 controller、队列适配器、
cache 状态接口、trace collector 或 A/B harness。局部构建的目标是补齐当前
Direction 所需接口，不是复制论文全部服务功能。

### 3.5 无法原生表达的硬件机制：合适的模拟器

若关键机制依赖当前硬件无法表达的对象，例如特定互连、多 GPU 拓扑、芯片资源、
分布式通信或尚不可获得的架构，则 Lab Goal 可以选择合适模拟器。

模拟器必须满足：

- 直接表达当前 Direction 需要改变的对象和事件；
- baseline 与 variant 使用同一模拟器版本、模型、拓扑、负载和配置；
- 核心时延或资源参数具有来源、真实测量校准或显式假设；
- 能输出足以检查排序、资源竞争、通信和性能结果的事件；
- 明确记录未模拟的硬件与软件行为。

模拟器用于支持机制、相对趋势和边界判断，不得把模拟值写成真实 GPU 的绝对性能。
若同一 Direction 同时产生真实单卡结果和模拟结果，必须分别形成配对组，不能跨
载体直接比较数值或混合统计。

## 4. 本地代理执行基线

本地代理执行基线是能够承载当前 Direction 因果比较的、已声明边界的真实或模拟
系统。它不声称等同于论文系统。

代理基线的有效性由以下条件决定：

- 当前主要变化真正位于该载体可观察、可修改的接口上；
- 弱化配置冻结后，baseline 与 variant 在组内使用同一执行图、资源上限、模型、
  精度、输入和测量口径；这些配置不要求与论文环境相同；
- 实验需要的队列竞争、cache 分支、阶段依赖或其他触发条件真实存在；
- baseline/variant 的输出或质量满足冻结的一致性约束；
- 关键事件和配置可追溯，失败尝试没有被隐藏；
- 载体差异被写入适用边界，而不是静默外推。

以下内容不再默认作为代理基线的硬 Gate：

- 与论文相同的 GPU 型号；
- 与论文相同的完整 runtime；
- 未公开的最终调度策略或私有 patch；
- 论文绝对延迟、吞吐或 SM 利用率数值；
- 与论文全部趋势逐项一致；
- 与论文相同的模型规模、完整数据量、请求规模或 trace 时长。

这些差异只有在会破坏当前因果接口或使 P2/P3 不可比时，才阻止实验继续。

## 5. P2/P3 配对消融合同

针对缓存状态感知 DAG Slack Direction，真正决定支持与否的比较必须是同一代理
载体内的 `P3-P2`。

弱化代理选定后，“同一”只约束该 baseline/variant 组内，不要求与论文设置相同。
两组至少冻结：

- 同一源码仓库、commit、build 和本地 patch；
- 同一真实 GPU，或同一模拟器和拓扑；
- 同一模型权重、精度、执行图和输出配置；
- 同一请求、到达时间、cache 初始状态、负载和随机种子；
- 同一 batch、MPS/资源份额、cache 容量、淘汰、spill 和 IPC 路径；
- 同一离线模块时延表、deadline 和稳定破同值规则；
- 同一预热、测量窗口、指标、统计和正确性规则。

唯一主要变化是：

```text
P2 使用冻结的统一参考 cache 分支计算剩余路径
P3 使用排序前已经确定的实际 cache 状态分支计算剩余路径
```

论文 P0 与本地代理 P0 的趋势差异应作为适用边界和诊断证据保存，但不替代
`P3-P2`，也不自动取消该配对实验。

## 6. Lab Goal 的修订职责

Direction Lab Goal 在选择和构建实验载体时，应按以下顺序推进：

```text
读取冻结 Direction 与证据
  ↓
提取当前主要变化必须具备的最小因果接口
  ↓
确定本轮要验证机制、本地性能还是不可原生表达的硬件机制
  ↓
机制验证先构建更小模型／数据子集／较少请求／缩短 trace 的弱化代理
  ↓
需要本地实际性能时检查单卡真实环境
  ↓
涉及系统修改时，查询并选择最容易修改的开源实现
  ↓
源码安装＋最小局部修改＋正确性检查
  ↓
仍有硬件机制缺口时，为该缺口选择模拟器
  ↓
冻结载体和配置
  ↓
执行同载体 baseline/variant 配对消融
```

开源实现搜索可以使用：

- Direction 与 Anchor 声明的源码和 evidence；
- `experiment_notes/` 中记录的仓库、环境和实现；
- `human_notes/` 中记录的可修改入口和失败经验；
- 当前授权允许的公开仓库与项目文档。

搜索应是有界的。找到一个满足接口并能形成可执行尝试的版本后即可进入安装和
验证，不要求穷尽所有框架。

Lab 的 `result.md` 需要额外明确：

- 为什么选择当前开源实现或模拟器；
- 它覆盖了哪些冻结因果接口；
- 源码版本和 patch 在哪里；
- 哪些论文机制未实现；
- 弱化了哪些环境或规模变量，保留了哪些因果不变量；
- 本轮结论属于弱化代理机制证据、真实单卡性能证据、模拟硬件机制证据还是仅实现
  可行性证据；
- 下一 Judge 能否直接进入 P2/P3 或对应 baseline/variant 比较。

## 7. Evidence Judge 的修订判断

### 7.1 `RUN_LAB`

满足以下任一情况且存在有界、有判别力的尝试时，应优先选择 `RUN_LAB`：

- 当前单卡可以表达主要机制，但尚未完成局部实现；
- 更小模型、数据子集、较少请求或缩短 trace 可以形成有判别力的机制代理；
- 存在可源码安装和修改的开源载体；
- 当前代理系统已经通过正确性检查，可以进入 P2/P3；
- 真实硬件缺少一个局部机制，但有合适模拟器可以表达；
- 当前结果只暴露实现或测量缺口，下一修复能改变最终判断。

Judge 不应仅因 GPU 型号、软件栈、模型/数据/请求规模、trace 时长或论文绝对趋势
不同而停止，只需确认这些差异是否破坏因果接口、触发条件或组内公平比较。

### 7.2 `REVISE_DIRECTION`

以下情况应选择 `REVISE_DIRECTION`：

- 冻结 Direction 把不可获得的论文完整系统错误地设成必要 baseline；
- 当前成功条件要求复现与主要因果主张无关的论文绝对数值；
- 必须改变因果 lever、必要 baseline 合同、guard 或成功条件才能执行主要比较；
- 当前主要机制或适用边界需要实质重写后才能公平验证。

旧绑定结束后，由 Learning Flow 或显式修订过程生成新的 Direction revision。不得在
原运行中直接修改冻结输入。

### 7.3 `BLOCKED`

只有在下列路径均不能推进，并且存在明确外部条件时，才选择 `BLOCKED`：

1. 弱化代理不能保留或触发关键机制；
2. 当前单卡不能表达关键机制；
3. 有界搜索未找到可安装、可修改的开源载体；
4. 最小局部构建仍无法建立关键接口；
5. 没有适合该机制的模拟器，或模拟器也依赖不可得资源；
6. 继续确实需要用户授权、账号、数据、专有代码或指定硬件。

`BLOCKED.reason` 应写清：

- 缺少的具体外部条件；
- 已尝试的单卡、开源实现、局部构建和模拟器路径；
- 为什么它们无法表达当前因果接口；
- 外部条件满足后下一步能执行什么。

“与论文环境不同”本身不是充分的阻塞理由。

### 7.4 `SUPPORT` 与 `REJECT`

- `SUPPORT` 必须来自对冻结主张足够的有效组内配对，并按弱化代理、真实单卡或
  模拟器的证据级别限定结论；弱化代理本身只能支持机制成立，不能支持未测的完整
  规模性能。Judge 必须通过 `evidenceScope` 把该级别写入机器协议与最终 handoff。
- `REJECT` 必须来自有效实现和公平比较命中冻结失败条件；环境失败、源码安装失败、
  论文复现不足或模拟器不支持都不能单独作为科学否证。

## 8. 证据层级和报告边界

实验报告至少区分：

| 证据层级 | 可以支持什么 | 不能直接支持什么 |
|---|---|---|
| `WEAKENED_PROXY_MECHANISM` | 更小模型、数据子集、请求规模、短 trace 或简化系统中机制是否发生及相对效应 | 原规模、生产负载或论文环境中的实际性能 |
| `LOCAL_SINGLE_GPU_PERFORMANCE` | 当前 GPU、软件、模型和负载下的实际正确性与性能效果 | 未测多卡拓扑及其他硬件的扩展性 |
| `SIMULATED_HARDWARE_MECHANISM` | 被模拟机制的相对趋势、因果解释和边界 | 真实 GPU 的绝对延迟、吞吐和利用率 |
| 本地代理实现检查 | 因果接口可实现、开关可隔离、输出可比 | Direction 的性能收益 |
| `PAPER_EXTERNAL_VALIDITY` | 增强与原系统比较的外部有效性 | 作为机制验证或本地性能实验的默认前置门槛 |

如果真实单卡与模拟结果都存在，应分别形成结论，再由 Judge 判断它们是否共同支持
同一个受限主张。不得把不同载体的请求级样本合并为一个统计检验。

## 9. 对现有冻结运行的迁移原则

已经以旧规则冻结的运行保持不可变：

- 保留原 Direction、Judge 决策、Lab 代码、配置、日志和测量；
- 若主要问题是“论文完整系统硬门槛不合理”，以 `REVISE_DIRECTION` 结束旧绑定；
- 新 Direction revision 明确本地代理基线、载体选择顺序和结论边界；
- 新运行复用旧 workspace 中已验证的模型、数据、代码、正确性 gate 和测量经验；
- 旧 P0 结果作为代理载体校准与外部有效性证据，不写成论文复现成功；
- 新 Lab Goal 优先实现并比较真正的 P2/P3，而不是重新进行无界的完整 EEVEE 重建。

## 10. 建议替换的 Measurement Plan 原则

旧规则：

```text
必须忠实复现论文 P0 及其硬件利用率、延迟和容量趋势；
趋势无法复现则停止后续因果比较。
```

修订为：

```text
先建立一个能够表达冻结模块 DAG、cache 分支、队列排序和资源不变量的本地代理
执行基线。机制验证允许使用更小模型、数据子集、较少请求、缩短 trace 和简化的
硬件/软件；需要本地实际性能时使用单卡真实实现；涉及系统修改时优先选择最容易
源码安装和修改的开源实现，并只局部构建缺失接口；当前硬件无法表达但对 Direction
必要的机制使用合适模拟器。论文环境和趋势仅用于增强外部有效性，不作为进入主要
消融的硬门槛。

P2 与 P3 必须在完全相同的代理载体、源码版本、配置、资源、输入和测量协议下做
配对比较，唯一主要变化是实际 cache 分支是否进入剩余路径排序。真实单卡和模拟器
结果分别报告。只有载体不能表达关键因果接口，或同载体比较无效时，才停止该轮
因果判断。
```

## 11. 与 02 的关系

本文不改变 02 的双角色状态机：

```text
Evidence Judge ↔ Direction Lab Goal
```

本文修订的是两个角色理解 baseline、环境忠实度和外部阻塞的方法：

- Lab Goal 从“尽量复现论文完整系统”改为“选择最小可信载体并完成当前因果比较”；
