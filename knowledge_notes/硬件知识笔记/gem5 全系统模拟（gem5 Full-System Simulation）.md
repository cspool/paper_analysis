## gem5 全系统模拟（gem5 Full-System Simulation）

- gem5 是模块化全系统架构模拟器（密歇根 M5 与威斯康星 GEMS 合并，BSD-3-Clause，C++ 实现，SCons 构建，官网 https://www.gem5.org，源码 https://github.com/gem5/gem5，支持 x86/Arm/RISC-V 与 SE/FS 两种模式）：SE（Syscall Emulation）只模拟用户态指令；FS（Full-System）引导操作系统、模拟完整系统栈。ICP 论文在 gem5 的 FS 模式下评估，模拟 Arm Cortex X2 风格乱序核 + 三级缓存层级 + LPDDR5 5500 内存的单核系统（配置遵循 Triangel [7] 原实现）。gem5 中预取器通过 Python 配置脚本挂接在缓存模块上，支持多预取器组合与自定义逻辑。

- gem5 FS 在 ICP 评估中的运转流程：Python 配置脚本声明系统（Table II：5-wide fetch/decode、10-wide issue/commit、120 项 IQ、85/90 项 LQ/SQ、288 项 ROB、L-TAGE 分支预测器；64KB 4-way L1I/L1D（16 MSHR）、512KB 8-way 包含式 L2（32 MSHR）、2MB/core 16-way L3（36 MSHR，CHAR 替换，mostly exclusive）；LPDDR5 5500 1x16 BG BL32）→ FS 模式引导并执行 SPEC CPU 2006 / GAP 基准的 SimPoint checkpoint 区间（warmup 200M 指令 + 统计 20M 指令）→ 逐周期推进核/缓存/内存时序模型 → 统计 IPC、DRAM 流量、元数据复用率等 → 各 checkpoint 按权重加权聚合。ICP 在 gem5 中的修改面（论文描述）：L1 集成 ICP 各表与 Lightweight Calculator、MSHR target 扩展 10-bit 压缩 PC、ROB 扩展源寄存器字段、commit 异步 FIFO、以及 baseline 侧 IPCP stream/stride/spatial + Alecto 部署于 L1D。注意与知识库已有条目"gem5 Garnet / HeteroGarnet"（面向 NoC 模拟的扩展）区分：本条目覆盖 gem5 通用 CPU/缓存/内存层次时序模拟的用法。

- 实现方式：scons 构建（如 scons build/ARM/gem5.opt -j N）→ 用 Python 配置脚本描述系统拓扑与参数 → 运行 checkpoint/可执行文件 → 解析 stats.txt 输出；预取器作为缓存模块内的 C++ 实现 + Python SimObject 绑定。开源情况：gem5 本身完全开源；ICP 论文未提供其预取器实现/artifact 链接，联网未发现官方开源仓库，无法确认开源状态；对比对象 Triangel 的 gem5 实现公开（GitHub SamAinsworth/gem5-triangel）。使用场景：CPU 微架构与缓存预取研究的事实标准模拟平台（DPC/CRC 锦标赛基于其衍生 ChampSim 或 gem5 直接评估），ICP 用它做全系统 FS 评估以贴近商用 CPU 的真实预取环境。

TDMSim 补充视角（ISCA'26，GPU 内存层级/2D-material DRAM cache 全系统模拟）：TDMSim 用 gem5 构建完整 CPU-GPU 异构系统评估 2D-material DRAM cache——以 AMD MI300X 为模拟架构，KVM 模式运行 CPU 加速、挂接详细 GPU 模型并经 PCIe 互连，系统启动 OS 并运行 12 个真实 GPU workload（Pannotia/Rodinia/AMDSDK/Llama/MLPerf，各运行至完成）；因全量仿真运行时间 prohibitive，采用单 XCD 配置（40 CU、1GHz、L1 32KiB/55cyc、L2 4MiB/100cyc、LLC 32MiB/200cyc、treePLRU、2 HBM3 stack 660GB/s、FR-FCFS），HBM stack 数与 cache 容量按比例缩放。修改面：在 gem5 MI300X 模型中扩展 DRAM cache 组件，准确表征 2D-material cache 行为（含周期 refresh 操作与 LH-cache 组织——tag 访问先 activation+read 载整行入 row buffer、命中保留 row buffer）；gem5 统计访问与刷新事件，组合 TDMSim 提供的访问延迟/动态能量/静态能量参数推导系统级性能与 cache 能耗（对比 9 种 LLC 配置的 speedup、access interference rate 与总能量）。

- TDMSim: Enabling High-Density and Energy-Efficient GPU DRAM Caches with 2D-Materials for Data-Intensive Applications
- RUNLTS Branch Prediction with Register-Value Correlations and Hierarchical Table Orchestration（RUNLTS 用法：gem5 20.0+ 做 execution-driven 全系统模拟，SPEC CPU 2017 用 gcc 13.1.0 -O3 -march=armv8-a 编译、SimPoint 100M 指令区间、full-system 模式，评估 16/8/4-wide 三种核宽；与 trace-driven CBP simulator 对照验证 Log-RBias/Seq-RBias 在 wrong-path 执行下的行为——gem5 精确建模 flush 时 Log-RBias 的 digest table checkpoint 恢复（每 checkpoint ~1 Kbit、需持续监听 completion 通知）与 Seq-RBias 的 ring buffer 指针回滚（保留 wrong-path 写入内容）；gem5 活动计数喂给 McPAT 输出整核 EPI 与面积（Table III：16-wide 下 RUNLTS-Log ΔMPKI -0.324、ΔIPC +1.55%；Seq-RBias 在 4/8/16-wide 降低整核 EPI 0.19%/0.74%/1.08%、面积开销 +0.35%/0.14%/0.04%）。RUNLTS 的 gem5 实现随 ISCA 2026 artifact（Zenodo 10.5281/zenodo.19453058）作为 reference 代码发布，但 SPEC CPU 2017 输入不可再分发、gem5 全量复现不在 artifact 范围内）
- Random-Access Hardware Sequence Compression（RST 用法：gem5 对接 Ramulator 做硬件压缩内存全系统仿真——以 DyLeCT [ISCA'24] 为基线（ASIC Deflate + expand-on-access 策略），把 Deflate 换成 RST：读压缩页先只取+解压请求的 64B 块、回复 cache 后再扩展整页（Deflate 必须先取整页），排队延迟高时跳过页级 fetch/expansion（Deflate 无法跳过），写压缩页用页内现有字典局部重压缩被写块（不更新字典）；8B 位置元数据与 CTE 共存（每页翻译项 16B）。Table 4 配置：4 核 2.8GHz 4-wide OoO、ROB 224、1024 TLB 项、L1D/L1I 32KB、L2 256KB、L3 2MB/核（8MB 总）、1 通道 25.6GB/s、8 ranks、FR-FCFS、tCL/tRCD/tRP=13.75ns；5s atomic warmup（>200 亿指令）+ 1ms detailed warmup + 4ms 详细仿真；12 个 DyLeCT workloads + readStride-1K 微基准（1KB stride、低局部性压力测试）。结果：平均性能 +15%（几何平均 14%，Fig.22）、压缩数据访问延迟 ~110ns vs baseline 260ns~1µs（Fig.23）、readStride-1K 5.1×（不计入平均）。注意 gem5 全系统仿真的 fast-forward checkpoint 需多 TB 存储、未随 Zenodo artifact 分发（§A.7）；硬件侧另用 Verilator 做 RTL 验证与性能提取）
