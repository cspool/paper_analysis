# <span id="page-9-0"></span>6.3 A-star Processing Unit (APU)

The APU subsystem optimizes key computational tasks in the A-star planning algorithm through specialized hardware for cost computation, heap management, and memory access. As illustrated in Fig. [10b](#page-8-1), its architecture comprises three main components: the Cost Compute Unit for cell cost evaluation, the Heap Unit for priority queue management, and a scratchpad memory for storing neighboring cell data during node expansion. These components collaboratively accelerate A-star operations, reducing delays from repetitive arithmetic and memory access. Iteratively, the heap extracts the lowest-cost cell, the cost compute unit computes neighbor costs, and updates are made to both the heap and scratchpad for the next iteration.

Cost compute unit. The cost compute unit is responsible for calculating the , ℎ, and values for the neighboring cells of the current node. It includes dedicated arithmetic units that can handle multiple operations in parallel, significantly speeding up the computation process. The cost compute unit takes the current cell's coordinates, cost information, and heuristic input, computes the new values for each neighbor, and outputs the results for insertion into the scratchpad memory.

Heap unit. The heap unit manages the priority queue (min heap) of open cells based on their values. Optimized for efficient operations such as insertion, deletion, and reordering, the heap unit dynamically updates the heap as new cells are added or when existing cells have their costs recalculated. A specialized four-level control circuit ensures that the heap remains balanced, enabling the extraction of the lowest-cost cell (highest priority) with minimal overhead for real-time path exploration. The heap unit is designed with a

single interface point at the first-level controller, eliminating the need for manual control of the deeper hardware circuits.

Scratchpad memory. The scratchpad memory within the APU serves as fast short-term storage, supporting the iterative nature of the A-star path planning algorithm. Acting as a temporary buffer, it holds critical data during node expansions, including metadata related to neighboring cells (or search subspace) and the computed cost values for expanded nodes. A dual-port memory design allows simultaneous read and write operations, enabling the APU to quickly retrieve and update cost values during each iteration.

At the subsystem level, the global scratchpad memory provides a larger, shared space for managing data that persists across multiple iterations (or processes) of the A-star planning and facilitates communication between the APUs and the host CPU. Unlike APU's local scratchpad, the global scratchpad serves as a long-term memory that stores more comprehensive information about the entire environmental space, including metadata on planning and search progress and the history of visited nodes.

APU data and control flows. The APU accelerates path planning by efficiently orchestrating data and control flows through its core components: cost compute unit, heap unit, and scratchpad memory. The process begins with loading search parameters, such as start and target coordinates, into the APU's local scratchpad and configuration registers via the global scratchpad. These parameters serve as fixed references guiding the iterative execution of the A-star search path planning procedure.

The control flow initiates with the heap unit constructing the multi-level priority queue by inserting the starting node (S in Fig. [11\)](#page-9-1) along with its initial (total cost) value. The heap unit autonomously extracts the lowest-cost node from the heap to be expanded, which is S in the first iteration. Once a node is selected, its neighboring cells are identified, and their corresponding data (coordinates and current costs) are fetched from the scratchpad memory. The cost compute unit then performs parallel calculations of , ℎ, and values for each neighbor using dedicated arithmetic units. This parallel processing of multiple neighbors significantly accelerates the expansion step.

An efficient dataflow design is critical for rapid neighbor extraction. The identification of neighboring cells relies on how the scratchpad stores data, ensuring that the spatial locality of cells in the search space is reflected in their storage layout. Specifically, when the current cell's index is provided, the scratchpad uses hardware-implemented hash function as an indexing mechanism to generate the addresses of neighboring cells. The hash function computes the scratchpad memory addresses corresponding to the neighboring cell based on the spatial coordinates of the current cell, allowing the APU to quickly fetch the relevant data for each neighbor without needing to search through the entire scratchpad. This locality-based addressing mechanism accelerates the

node expansion process by ensuring that neighboring cells can be accessed with minimal delay.

After the cost compute unit computes the costs, the control flow directs the insertion of the new values into the heap unit and updates the local scratchpad with the neighbor information. The heap unit then reorders the priority queue based on these new costs, ensuring that the lowest-cost node is always selected for the next iteration. The dual-port design of the scratchpad memory allows simultaneous read and write operations, thus reducing memory access latency. This iterative cycle of node extraction, neighbor expansion, and heap updating continues until the target node F is reached.

The APU's architecture is scalable and generalizable, capable of supporting any -dimensional path planning tasks. The modular design of the cost compute unit and heap unit allows the system to handle more complex environments, from 2D grids to -dimensional spaces. The parallelism within the cost compute unit and efficient heap management in the heap unit ensure that the APU can adapt to varied complexity levels in path planning tasks. The local and global scratchpad memories further enhance its scalability, enabling efficient data management across large search spaces.

## <span id="page-10-1"></span>6.4 Heterogeneous Subsystem Interface

The proposed design features a heterogeneous architecture where the A-star subsystem and LLM subsystem interface through shared global DRAM, as illustrated in Fig. [10a](#page-8-1). Data transitions between the two subsystems are structured based on their respective roles: the LLM subsystem writes highlevel plans to memory, which the A-star subsystem retrieves and executes for low-level planning. The A-star subsystem reads this data, configures its search parameters through Start and Target Configuration Registers, and upon execution, returns feedback (such as search outcomes or error conditions) to DRAM for further processing by the LLM subsystem. This bidirectional data flow enables adaptive planning, allowing the LLM subsystem to refine its planned actions and strategies based on the low-level execution results from the A-star subsystem.

Synchronization between two subsystems is managed by the host, which coordinates data transfers and ensures consistency through memory flushes, barriers, and interrupts. The programming model for the APU subsystem involves the GPU command buffer [\[19\]](#page-13-18) configuring the APU and scheduling the low-level path planning and execution module on the APU subsystem. This architectural design facilitates efficient communication between the subsystems while supporting the varied requirements of parent and child agents. In child agents, the interface is streamlined: the global DRAM primarily serves to fetch task-specific configurations (start/target) for the APU from external sources or parent agents. Since child agents rely on parent agents' high-level LLM planning results within the cluster, the DRAM facilitates direct lowlevel planning execution without high-level LLM inference.
