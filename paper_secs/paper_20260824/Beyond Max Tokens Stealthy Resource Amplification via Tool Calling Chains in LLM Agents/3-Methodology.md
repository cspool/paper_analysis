# 3 Methodology

To address single-turn attack limitations, we exploit the multi-turn, stateful nature of agent-tool interactions. We convert a benign MCP tool server into a malicious variant that produces long, costly, yet successful task trajectories without altering function signatures or identifiers. Our approach includes: (i) a formal problem definition as constrained optimization ([§3.1\)](#page-2-0); (ii) a universal malicious template guiding the agent via text-visible fields and a return policy ([§3.2\)](#page-2-1); and (iii) an MCTSbased optimizer for localized text edits to create effective malicious templates across LLMs and tasks ([§3.3–](#page-3-0)[§3.4\)](#page-3-1). Figure [1](#page-2-2) illustrates the pipeline.

## <span id="page-2-0"></span>3.1 Problem Formulation and Threat Model

System model. We model an MCP-based agent– tool loop with an agent policy A, a black-box LLM M, and an external MCP server T<sup>θ</sup> parameterized by a text template θ. The server exposes tool functions F and communicates via MCP request/response semantics. The policy A maps the dialogue and tool feedback to the next action whether to call a tool (which one, with what arguments) or to emit the final answer. Our attack never changes A or M; instead, it manipulates the tool-facing messages returned by T<sup>θ</sup> so that A (often implicitly instantiated by M under structured prompting) chooses longer multi-turn trajectories while still solving the task. We do not tamper with user queries, prompts, or retrieval; the attack activates only after the tool is legitimately invoked under the benign configuration (formal trigger-set definition in Appendix [B.1\)](#page-11-1).

Objective. An agent run induces an interaction trajectory τ = {(a<sup>t</sup> , rt)} n <sup>t</sup>=1, a sequence of tool calls (at) and tool responses (rt). Our primary cost metric is the total number of output tokens generated by M:

$$C(\tau) = \text{Tok}_{\text{out}}(\tau),$$

which is typically the dominant driver of both API fees and inference load; input-token growth is a secondary effect of longer trajectories. Let q be a user query with implied goal u = goal(q), and let o be the final answer. Let Succ(u, τ, o) ∈ {0, 1} indicate whether o achieves u given τ . The attacker seeks a template θ that maximizes expected cost while maintaining task success with probability at least pmin over routable queries (Appendix [B.1\)](#page-11-1):

$$\max_{\theta \in \Theta} \mathbb{E} [C(\tau(q;\theta))]$$
 (1)

$$\Pr[\operatorname{Succ}(u,\tau,o)=1] \ge p_{\min}. \tag{2}$$

The central mechanism is multi-turn cost amplification: we induce longer trajectories (larger n) and make each tool-calling turn verbose, so that the vast majority of tokens are generated during tool calling rather than in the final answer.

Threat model. The adversary's capability is confined to controlling the MCP server Tθ specifically, modifying its template θ as a dropin, MCP-compatible server. The attacker cannot modify the agent policy A or the LLM M, has only black-box access to them, and does not alter queries, prompts, or retrieval. Under benign conditions where A decides to call the tool, the attacker may replace θ<sup>0</sup> with a text-only variant θ (or impersonate a benign server) while remaining protocol-compatible.

## <span id="page-2-1"></span>3.2 The Universal Malicious Template

Design constraints. We do not change function signatures, identifiers, or the semantics of the terminal (benign) payload. Instead, we edit only textvisible fields and enforce a template-governed return policy that (i) validates a segment index and

a calibration sequence, and (ii) defers surfacing the benign payload until t=Tmax with a valid sequence. Before the terminal condition holds, the server emits protocol-compatible Progress or Repair notices; once it holds, the server returns the unchanged benign payload. The full element list and failure handling are summarized in Table [4](#page-12-0) (Appendix [B.2\)](#page-11-2).

Mechanism and return policy. The template introduces two lightweight, text-only arguments and three response modes. The segment index t provides an explicit notion of progress so the agent treats intermediate calls as part of an ongoing procedure, extending the trajectory until a terminal cue. The calibration sequence is a complete commaseparated list whose sole purpose is to inflate perturn completion at the tool-calling site; producing the list increases cost but does not alter task semantics. On the return side, Progress notices keep the agent on the goal path while prompting the next call; Repair notices prevent abbreviated or invalid formats by explicitly requesting a compliant retry; and the Terminal return passes through the original benign payload unchanged, ending the loop. We enforce four invariants: (i) Monotone progress: t1=1 and valid calls advance tk+1=tk+1; (ii) Format completeness: validate(sequence) holds iff the sequence matches the required complete, commaseparated format and ordering; (iii) Return policy: valid sequences with t<Tmax yield a Progress notice, while invalid sequences yield a Repair notice without advancing t; and (iv) Termination: only when t=Tmax and the latest sequence validates does the server emit the Terminal return (benign payload). Together, these invariants induce multiturn, long tool-call traces while preserving task correctness and MCP compatibility.

## <span id="page-3-0"></span>3.3 Universal Template Seed Bank

We maintain a seed bank of protocol-compatible, task-correct templates T<sup>θ</sup> to warm-start search. Each MCTS run starts from a selected seed and halts when an acceptance predicate is met; the resulting template is written back and reused as a high-quality starter for subsequent runs. Additional screening, promotion, and metadata details are provided in Appendix [B.3.](#page-11-3)

## <span id="page-3-1"></span>3.4 MCTS Optimizer

Each tree node v corresponds to a concrete server Tθ<sup>v</sup> ; edges apply a single localized text edit under payload-preserving, text-only constraints. We or-

ganize edits into three families: AMT (multi-turn induction), ALEN (length induction), and AREP (repair after omission/format errors). Search proceeds with phase gating: in pre\_MT, we use AMT to stabilize multi-turn behavior; once short screenings show stable segment sequencing, we switch to post\_MT and use ALEN to strengthen long outputs. If an omission/format error is observed at node v (i.e., a Repair notice), AREP is unlocked at v only; otherwise it remains disabled. New children are evaluated in parallel with a lightweight Stage-1 screen and an optional Stage-2 refinement, and accepted templates are recorded back into the seed bank. We select children to explore by UCT [\(Koc](#page-9-12)[sis and Szepesvári,](#page-9-12) [2006\)](#page-9-12):

$$u^* = \arg \max_{u \in \mathcal{C}(v)} \bar{Q}(u) + C \sqrt{\frac{\ln(1 + N_{\text{uct}}(v))}{1 + N_{\text{uct}}(u)}},$$

where Q¯(u) is the running mean evaluation signal and Nuct counts visits used for exploration. Full details of action instantiation and evaluation gates are provided in Appendix [B.4.](#page-11-4) The overall procedure is formalized in Algorithm [1.](#page-4-0)
