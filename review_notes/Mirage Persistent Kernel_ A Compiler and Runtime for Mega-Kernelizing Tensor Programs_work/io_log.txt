## 问题 1：MPK 并发机制链条中各环使用的并发原语

### 各环节并发原语映射

| 环节 | 使用的并发原语/机制 | 说明 |
|------|---------------------|------|
| **tGraph（SM 级任务图）** | 纯软件抽象（device memory 紧凑数据结构） | tGraph 本身不是 CUDA 原生原语，而是编译期构建、存储在 GPU device memory 中的有向无环图数据结构 |
| **Persistent Kernel** | **CUDA Persistent Kernel**（单次 `__global__` launch，持久执行） | 整个模型编译为单个 mega-kernel，一次 launch 后持续运行直至所有 decode iteration 完成。这是整个系统的底座——用**一次 kernel launch** 替代 baseline 的数百至数千次 launch |
| **SM 物理分区（128 workers + 4 scheduler-SMs）** | **Warp Specialization**（调度器以 warp 粒度组织） + **持久化线程块** | 每个 SM 物理分区固定一个 worker（block），4 个 scheduler-SM 各运行 4 个 scheduler warp（共 16 warp-scheduler）。分区在 kernel-launch 时固定，运行时无动态角色切换 |
| **Cross-task software pipelining** | **TMA**（Tensor Memory Accelerator）异步数据搬运 + **Paged Shared Memory** | pre-loading 阶段使用 TMA 执行 HBM→shared memory 的异步拷贝；compute 阶段使用 Tensor Cores/CUDA Cores。两者在不同硬件单元上并发执行 |
| **Fine-grained event 同步** | **软件实现**（atomic polling + circular buffer），**非** mbarrier | 详见下文 |
| **Inter-GPU 通信** | **NVSHMEM**（`nvshmem_signal_wait_until`） | 用于 in-kernel inter-GPU AllReduce 等集合通信 |
| **Intra-SM 代码生成** | Mirage superoptimizer 生成的优化 CUDA（含 intra-SM software pipelining: TMA + Tensor Cores + CUDA Cores） | 每个 task 的 CUDA device function 由 Mirage 自动搜索最优 thread block graph |

### Event 同步：软件实现，非 mbarrier

MPK 的 event 同步是**纯软件实现**，具体机制：

- **存储位置**：所有 events 和 tasks 以连续数组存储在 **GPU device memory**（非 shared memory，因为需要跨 SM 可见）
- **Event 数据结构**（紧凑格式）：每个 event 存储 `required_trigger_count` + `[first_task, last_task]` 索引范围。其中 `required_trigger_count` 表示该 event 被激活前需要接收的 trigger 次数（等于依赖该 event 的 task 的前驱 task 数量），`[first_task, last_task]` 编码该 event 激活后需要 dispatch 的所有 task 在 task 数组中的连续范围
- **Task 数据结构**：每个 task 描述符 352 bytes，包含 `dependent_event_index`（该 task 依赖哪个 event）、`trigger_event_index`（该 task 完成后通知哪个 event）、input/output tensor 指针和配置参数
- **同步原语**：使用 **atomicAdd** 在 device memory 上实现 trigger 计数和 event 队列的 enqueue/dequeue。Worker 完成 task 后对 `trigger_event` 的计数器执行 atomicAdd；当计数器达到 `required_trigger_count` 时，event 被标记为激活并 atomicAdd 入 scheduler 的 event 队列（circular buffer）
- Worker-scheduler 同步使用 **device memory semaphores**（通过原子操作实现的轻量信号量）
- **Task 描述符 prefetching**：worker 在执行前将 352-byte task 描述符从 device memory prefetch 到 shared memory 以隐藏访问延迟

**与 mbarrier 的区别**：mbarrier 是 CUDA 硬件同步原语（SM 内 thread block 级同步，在 shared memory 上操作），而 MPK 需要**跨 SM 同步**（不同 SM 上的 worker 之间协调），mbarrier 不支持跨 SM 使用。因此 MPK 选择了基于 device memory 原子操作的软件 event 系统。

### Worker-Scheduler 通信机制

```
Scheduler warp (运行在 scheduler SM 上):
  1. poll event queue (device memory circular buffer)
  2. dequeue 下一个激活的 event e
  3. 读取 e.[first_task, last_task] → dispatch 该范围内所有 tasks
     对每个待 dispatch task t:
       atomicAdd 到对应 worker 的 task queue (device memory circular buffer)
  
Worker (每个 worker SM 一个):
  1. loop: atomicAdd dequeue task queue → 取出 task 描述符
  2. prefetch task 描述符 (352 bytes) 到 shared memory
  3. 执行 task: pre-loading phase (TMA) → compute phase (Tensor Cores/CUDA Cores)
  4. 完成: atomicAdd 到 task 的 trigger_event 的计数器
     - 若计数器达到 required_count → event 激活 → atomicAdd 到 scheduler event queue
  5. goto 1
```

关键通信路径：(1) Scheduler→Worker: device memory task queue + atomicAdd；(2) Worker→Scheduler: device memory event counter + atomicAdd → 激活后入 scheduler event queue。整个过程**无 CPU 参与、无 kernel relaunch**。

## 问题 2：并发粒度

### Task 的计算粒度

一个 tGraph task 对应的是**一个 operator 的单个输出 tile 的计算**（约等于一个 SM 的工作量）。具体来说：

- 每个 operator（如 MatMul）按**输出张量维度 tiling** 分解为多个 SM 级 tasks
- 每个 task 计算输出张量的一个**不相交子集**（tile），所有 tasks 的 tile 合起来覆盖整个输出张量
- 输出 tile 选择策略：**最小化 device memory→shared memory 的数据加载量**（tile 大小由编译器根据 SM 的 shared memory 容量和 register 预算自动确定）
- 对于 H100（132 SMs），典型 MatMul 分解为约 **132 tasks**，即每个 SM 约 1 个 task。但同时 task 数也取决于 MatMul 的具体维度（受 shared memory page 大小 32KB 约束）

**Task 粒度是固定的还是可调的？**

- **编译期固定**：task 数量在编译时由 operator decomposition 步骤确定，基于 GPU 类型（SM 数量）和 batch size。编译器为每个 batch size（2 的幂次，up to max_batch）生成**专用的 tGraph**
- **运行期不可调**：单个 tGraph 内 task 数量和粒度固定
- **但有两种 task 执行模式**：
  - **JIT（Just-In-Time）模式**：用于 data-dependent 执行时间的 operator（如 attention，执行时间随 sequence length 变化）。Scheduler 在 event 激活后才 assign task → 实现动态负载均衡
  - **AOT（Ahead-Of-Time）模式**：用于确定性的 operator（如 MatMul after barrier）。Tasks 预分配到特定 workers → 消除 dispatch 开销

### Task launch 开销

论文和实验笔记**未明确给出 task launch 开销的精确微秒/周期数**，但可以从设计细节推断：

- **JIT 模式**：需要 **worker↔scheduler 两次同步**（scheduler assign task → worker 确认），开销较高，但换来负载均衡
- **AOT 模式**：仅需 **一次同步**（worker 检查 event 是否激活 + AOT queue entry），开销极低。AOT 预分配消除了 dispatch 开销
- 对比 baseline：每个 kernel launch 的开销约为 5-10μs（CUDA kernel launch overhead），而 MPK 内 task 间切换的原子操作开销在数十到数百纳秒级别
- **Task 执行时间 vs dispatch 开销**：以 Qwen3-8B decode 为例，per-token latency ~12.5ms。整个 iteration 涉及约 132×N_operators 个 tasks，每个 task 的平均执行时间在微秒量级（粗略估计 10-50μs），dispatch 开销（<1μs）占比很小。**信息缺口**：论文未提供具体的 task launch delay profile 数据。

## 问题 3：并发潜力的来源

### 算子对依赖关系分类（以 Qwen3-8B Decode Iteration 为例）

#### 真正存在数据依赖（必须串行/可流水线但不可完全并行）

| 算子对 | 依赖类型 | 说明 |
|--------|----------|------|
| **Q_proj → Attention** | 真数据依赖 | Attention 的 Q 输入来自 Q_proj 的输出。但这是 **task 级部分依赖**——Attention 的某个 task 只需 Q_proj 的对应 tile 就绪，无需等完整 Q 矩阵 |
| **K_proj → Attention** | 真数据依赖 | 同上，K 输入。Q_proj、K_proj、V_proj **三者之间无相互依赖**（独立并行） |
| **V_proj → Attention** | 真数据依赖 | 同上 |
| **Attention → O_proj** | 真数据依赖 | O_proj 的输入是 Attention 输出 |
| **Gate_proj → SiLU** | 真数据依赖 | SiLU 激活函数需要 Gate 投影结果。**但 Up_proj 与 Gate_proj/SiLU 无直接依赖**（MPK 可并行执行 Up_proj 和 Gate_proj→SiLU） |
| **SiLU(Gate) × Up → Down_proj** | 真数据依赖 | Down_proj 需要 element-wise 乘积结果 |
| **O_proj output → Residual Add** | 真数据依赖 | Residual connection 需要 O_proj 输出和原始输入 |
| **RMSNorm → 下一层 Q/K/V_proj** | 真数据依赖 | 下一层的输入来自上一层的 RMSNorm 输出 |

#### Kernel Barrier 强加的人为串行（MPK 可解锁的并行/流水线）

| 算子对（baseline 串行） | 为什么是人为串行 | MPK 如何并行化 |
|--------------------------|-------------------|----------------|
| **Q_proj、K_proj、V_proj 三者互相串行** | Kernel barrier 阻止三个独立 MatMul 在不同 SM 上同时执行 | MPK 将三者分解为独立 task group，不同 SM 同时执行 Q/K/V 的 task → **SM 级并行** |
| **MatMul → AllReduce（TP 场景）** | Baseline 必须等整个 MatMul kernel 完成后才能启动 AllReduce kernel | MPK 在 **per-task-pair 级别**分析依赖：每个 AllReduce task 仅依赖一个对应 MatMul task 的输出 tile → MatMul task 完成的 SM 立即启动对应 AllReduce task，与其他仍在执行 MatMul 的 SM **并发** |
| **最后一层 Down_proj → 下一 iteration 的 Q_proj** | 跨 iteration 的 kernel barrier | MPK 通过 cross-task pipelining：当前 iteration 的 Down_proj compute 阶段期间，TMA 已开始 pre-load 下一 iteration Q_proj 的权重 → **跨 iteration 流水线** |
| **RMSNorm（element-wise 轻量级） → 下一层 MatMul** | Kernel barrier 将轻量 element-wise op 与后续 heavy MatMul 串行 | MPK 可在 RMSNorm task 所属 SM 完成计算后立即启动下游 MatMul task，而其他 SM 仍可并行执行不同的 MatMul task |
| **Attention → O_proj + Gate/Up_proj 并行性未被利用** | Attention 和 MLP 输入路径在 Attention 层后分叉，但 kernel barrier 将它们全部串行 | MPK 通过 event 系统：Attention 完成后同时触发 O_proj 和 MLP 路径的 events → 两条路径的 tasks **并行 dispatch** |

### 跨 Task Pipelining 的瓶颈分析

#### Bottleneck 性质

MPK 的跨 task pipelining 同时涉及两种瓶颈：
- **Memory-bound**（pre-loading 阶段）：TMA 执行 HBM→shared memory 的数据搬运，瓶颈在 HBM 带宽（H100: 1.6 TB/s）
- **Compute-bound**（compute 阶段）：Tensor Cores 执行 MMA 计算，瓶颈在 Tensor Core 吞吐（H100: 989 TFLOPS FP16）

pipelining 的设计关键在于**两个阶段使用不同的硬件单元**（TMA vs Tensor Cores），因此可以真正并发执行而无资源竞争。

#### Pre-loading 阶段使用的指令

- **TMA（Tensor Memory Accelerator）**：专用于 HBM→shared memory 的异步批量数据传输。TMA 是独立的硬件单元，不占用 CUDA Core 或 Tensor Core 的周期
- **非** CUDA Core 的普通 load 指令（如 `LDG`）。使用 TMA 的原因是：(a) 异步执行不占用计算资源；(b) 硬件自动处理地址计算和 alignment；(c) 支持多维 tile 描述符

#### 资源竞争分析

| 资源 | Pre-loading（TMA） | Compute（Tensor Cores） | 是否竞争？ |
|------|---------------------|-------------------------|-----------|
| **HBM 带宽** | 使用（读取权重/输入 tile） | 输出写回时少量使用 | **轻微竞争**：pre-loading 以 HBM read 为主，compute 以 on-chip 计算为主，HBM write 占比小 |
| **Shared Memory** | 写入 destination pages | 读取 source pages | **存在竞争**：通过 **Paged Shared Memory Abstraction** 管理——task 需 acquire/release 32KB pages。Pipelining 条件：(1) 当前 task 已发出所有 data-transfer 指令；(2) 有足够的空闲 shared memory pages。若 pages 不足，pipelining 暂停 |
| **Tensor Cores** | 不使用 | 独占使用 | **无竞争** |

## 问题 1：MPK 并发机制链条中各环使用的并发原语

### 各环节并发原语映射

| 环节 | 使用的并发原语/机制 | 说明 |
|------|---------------------|------|
| **tGraph（SM 级任务图）** | 纯软件抽象（device memory 紧凑数据结构） | tGraph 本身不是 CUDA 原生原语，而是编译期构建、存储在 GPU device memory 中的有向无环图数据结构 |
| **Persistent Kernel** | **CUDA Persistent Kernel**（单次 `__global__` launch，持久执行） | 整个模型编译为单个 mega-kernel，一次 launch 后持续运行直至所有 decode iteration 完成。这是整个系统的底座——用**一次 kernel launch** 替代 baseline 的数百至数千次 launch |
| **SM 物理分区（128 workers + 4 scheduler-SMs）** | **Warp Specialization**（调度器以 warp 粒度组织） + **持久化线程块** | 每个 SM 物理分区固定一个 worker（block），4 个 scheduler-SM 各运行 4 个 scheduler warp（共 16 warp-scheduler）。分区在 kernel-launch 时固定，运行时无动态角色切换 |
| **Cross-task software pipelining** | **TMA**（Tensor Memory Accelerator）异步数据搬运 + **Paged Shared Memory** | pre-loading 阶段使用 TMA 执行 HBM→shared memory 的异步拷贝；compute 阶段使用 Tensor Cores/CUDA Cores。两者在不同硬件单元上并发执行 |
| **Fine-grained event 同步** | **软件实现**（atomic polling + circular buffer），**非** mbarrier | 详见下文 |
| **Inter-GPU 通信** | **NVSHMEM**（`nvshmem_signal_wait_until`） | 用于 in-kernel inter-GPU AllReduce 等集合通信 |
| **Intra-SM 代码生成** | Mirage superoptimizer 生成的优化 CUDA（含 intra-SM software pipelining: TMA + Tensor Cores + CUDA Cores） | 每个 task 的 CUDA device function 由 Mirage 自动搜索最优 thread block graph |

### Event 同步：软件实现，非 mbarrier

MPK 的 event 同步是**纯软件实现**，具体机制：

- **存储位置**：所有 events 和 tasks 以连续数组存储在 **GPU device memory**（非 shared memory，因为需要跨 SM 可见）
- **Event 数据结构**（紧凑格式）：每个 event 存储 `required_trigger_count` + `[first_task, last_task]` 索引范围。其中 `required_trigger_count` 表示该 event 被激活前需要接收的 trigger 次数（等于依赖该 event 的 task 的前驱 task 数量），`[first_task, last_task]` 编码该 event 激活后需要 dispatch 的所有 task 在 task 数组中的连续范围
- **Task 数据结构**：每个 task 描述符 352 bytes，包含 `dependent_event_index`（该 task 依赖哪个 event）、`trigger_event_index`（该 task 完成后通知哪个 event）、input/output tensor 指针和配置参数
- **同步原语**：使用 **atomicAdd** 在 device memory 上实现 trigger 计数和 event 队列的 enqueue/dequeue。Worker 完成 task 后对 `trigger_event` 的计数器执行 atomicAdd；当计数器达到 `required_trigger_count` 时，event 被标记为激活并 atomicAdd 入 scheduler 的 event 队列（circular buffer）
- Worker-scheduler 同步使用 **device memory semaphores**（通过原子操作实现的轻量信号量）
- **Task 描述符 prefetching**：worker 在执行前将 352-byte task 描述符从 device memory prefetch 到 shared memory 以隐藏访问延迟

**与 mbarrier 的区别**：mbarrier 是 CUDA 硬件同步原语（SM 内 thread block 级同步，在 shared memory 上操作），而 MPK 需要**跨 SM 同步**（不同 SM 上的 worker 之间协调），mbarrier 不支持跨 SM 使用。因此 MPK 选择了基于 device memory 原子操作的软件 event 系统。

### Worker-Scheduler 通信机制

```
Scheduler warp (运行在 scheduler SM 上):
  1. poll event queue (device memory circular buffer)
  2. dequeue 下一个激活的 event e
  3. 读取 e.[first_task, last_task] → dispatch 该范围内所有 tasks
     对每个待 dispatch task t:
       atomicAdd 到对应 worker 的 task queue (device memory circular buffer)
  
Worker (每个 worker SM 一个):
  1. loop: atomicAdd dequeue task queue → 取出 task 描述符
  2. prefetch task 描述符 (352 bytes) 到 shared memory
  3. 执行 task: pre-loading phase (TMA) → compute phase (Tensor Cores/CUDA Cores)
  4. 完成: atomicAdd 到 task 的 trigger_event 的计数器
     - 若计数器达到 required_count → event 激活 → atomicAdd 到 scheduler event queue
  5. goto 1
```

关键通信路径：(1) Scheduler→Worker: device memory task queue + atomicAdd；(2) Worker→Scheduler: device memory event counter + atomicAdd → 激活后入 scheduler event queue。整个过程**无 CPU 参与、无 kernel relaunch**。

## 问题 2：并发粒度

### Task 的计算粒度

一个 tGraph task 对应的是**一个 operator 的单个输出 tile 的计算**（约等于一个 SM 的工作量）。具体来说：

- 每个 operator（如 MatMul）按**输出张量维度 tiling** 分解为多个 SM 级 tasks
- 每个 task 计算输出张量的一个**不相交子集**（tile），所有 tasks 的 tile 合起来覆盖整个输出张量
- 输出 tile 选择策略：**最小化 device memory→shared memory 的数据加载量**（tile 大小由编译器根据 SM 的 shared memory 容量和 register 预算自动确定）
- 对于 H100（132 SMs），典型 MatMul 分解为约 **132 tasks**，即每个 SM 约 1 个 task。但同时 task 数也取决于 MatMul 的具体维度（受 shared memory page 大小 32KB 约束）

**Task 粒度是固定的还是可调的？**

- **编译期固定**：task 数量在编译时由 operator decomposition 步骤确定，基于 GPU 类型（SM 数量）和 batch size。编译器为每个 batch size（2 的幂次，up to max_batch）生成**专用的 tGraph**
- **运行期不可调**：单个 tGraph 内 task 数量和粒度固定
- **但有两种 task 执行模式**：
  - **JIT（Just-In-Time）模式**：用于 data-dependent 执行时间的 operator（如 attention，执行时间随 sequence length 变化）。Scheduler 在 event 激活后才 assign task → 实现动态负载均衡
  - **AOT（Ahead-Of-Time）模式**：用于确定性的 operator（如 MatMul after barrier）。Tasks 预分配到特定 workers → 消除 dispatch 开销

### Task launch 开销

论文和实验笔记**未明确给出 task launch 开销的精确微秒/周期数**，但可以从设计细节推断：

- **JIT 模式**：需要 **worker↔scheduler 两次同步**（scheduler assign task → worker 确认），开销较高，但换来负载均衡
- **AOT 模式**：仅需 **一次同步**（worker 检查 event 是否激活 + AOT queue entry），开销极低。AOT 预分配消除了 dispatch 开销
- 对比 baseline：每个 kernel launch 的开销约为 5-10μs（CUDA kernel launch overhead），而 MPK 内 task 间切换的原子操作开销在数十到数百纳秒级别
- **Task 执行时间 vs dispatch 开销**：以 Qwen3-8B decode 为例，per-token latency ~12.5ms。整个 iteration 涉及约 132×N_operators 个 tasks，每个 task 的平均执行时间在微秒量级（粗略估计 10-50μs），dispatch 开销（<1μs）占比很小。**信息缺口**：论文未提供具体的 task launch delay profile 数据。

## 问题 3：并发潜力的来源

### 算子对依赖关系分类（以 Qwen3-8B Decode Iteration 为例）

#### 真正存在数据依赖（必须串行/可流水线但不可完全并行）

| 算子对 | 依赖类型 | 说明 |
|--------|----------|------|
| **Q_proj → Attention** | 真数据依赖 | Attention 的 Q 输入来自 Q_proj 的输出。但这是 **task 级部分依赖**——Attention 的某个 task 只需 Q_proj 的对应 tile 就绪，无需等完整 Q 矩阵 |
| **K_proj → Attention** | 真数据依赖 | 同上，K 输入。Q_proj、K_proj、V_proj **三者之间无相互依赖**（独立并行） |
| **V_proj → Attention** | 真数据依赖 | 同上 |
| **Attention → O_proj** | 真数据依赖 | O_proj 的输入是 Attention 输出 |
| **Gate_proj → SiLU** | 真数据依赖 | SiLU 激活函数需要 Gate 投影结果。**但 Up_proj 与 Gate_proj/SiLU 无直接依赖**（MPK 可并行执行 Up_proj 和 Gate_proj→SiLU） |
| **SiLU(Gate) × Up → Down_proj** | 真数据依赖 | Down_proj 需要 element-wise 乘积结果 |
| **O_proj output → Residual Add** | 真数据依赖 | Residual connection 需要 O_proj 输出和原始输入 |
| **RMSNorm → 下一层 Q/K/V_proj** | 真数据依赖 | 下一层的输入来自上一层的 RMSNorm 输出 |

#### Kernel Barrier 强加的人为串行（MPK 可解锁的并行/流水线）

| 算子对（baseline 串行） | 为什么是人为串行 | MPK 如何并行化 |
|--------------------------|-------------------|----------------|
| **Q_proj、K_proj、V_proj 三者互相串行** | Kernel barrier 阻止三个独立 MatMul 在不同 SM 上同时执行 | MPK 将三者分解为独立 task group，不同 SM 同时执行 Q/K/V 的 task → **SM 级并行** |
| **MatMul → AllReduce（TP 场景）** | Baseline 必须等整个 MatMul kernel 完成后才能启动 AllReduce kernel | MPK 在 **per-task-pair 级别**分析依赖：每个 AllReduce task 仅依赖一个对应 MatMul task 的输出 tile → MatMul task 完成的 SM 立即启动对应 AllReduce task，与其他仍在执行 MatMul 的 SM **并发** |
| **最后一层 Down_proj → 下一 iteration 的 Q_proj** | 跨 iteration 的 kernel barrier | MPK 通过 cross-task pipelining：当前 iteration 的 Down_proj compute 阶段期间，TMA 已开始 pre-load 下一 iteration Q_proj 的权重 → **跨 iteration 流水线** |
| **RMSNorm（element-wise 轻量级） → 下一层 MatMul** | Kernel barrier 将轻量 element-wise op 与后续 heavy MatMul 串行 | MPK 可在 RMSNorm task 所属 SM 完成计算后立即启动下游 MatMul task，而其他 SM 仍可并行执行不同的 MatMul task |
| **Attention → O_proj + Gate/Up_proj 并行性未被利用** | Attention 和 MLP 输入路径在 Attention 层后分叉，但 kernel barrier 将它们全部串行 | MPK 通过 event 系统：Attention 完成后同时触发 O_proj 和 MLP 路径的 events → 两条路径的 tasks **并行 dispatch** |

### 跨 Task Pipelining 的瓶颈分析

#### Bottleneck 性质

MPK 的跨 task pipelining 同时涉及两种瓶颈：
- **Memory-bound**（pre-loading 阶段）：TMA 执行 HBM→shared memory 的数据搬运，瓶颈在 HBM 带宽（H100: 1.6 TB/s）
- **Compute-bound**（compute 阶段）：Tensor Cores 执行 MMA 计算，瓶颈在 Tensor Core 吞吐（H100: 989 TFLOPS FP16）

pipelining 的设计关键在于**两个阶段使用不同的硬件单元**（TMA vs Tensor Cores），因此可以真正并发执行而无资源竞争。

#### Pre-loading 阶段使用的指令

- **TMA（Tensor Memory Accelerator）**：专用于 HBM→shared memory 的异步批量数据传输。TMA 是独立的硬件单元，不占用 CUDA Core 或 Tensor Core 的周期
- **非** CUDA Core 的普通 load 指令（如 `LDG`）。使用 TMA 的原因是：(a) 异步执行不占用计算资源；(b) 硬件自动处理地址计算和 alignment；(c) 支持多维 tile 描述符

#### 资源竞争分析

| 资源 | Pre-loading（TMA） | Compute（Tensor Cores） | 是否竞争？ |
|------|---------------------|-------------------------|-----------|
| **HBM 带宽** | 使用（读取权重/输入 tile） | 输出写回时少量使用 | **轻微竞争**：pre-loading 以 HBM read 为主，compute 以 on-chip 计算为主，HBM write 占比小 |
| **Shared Memory** | 写入 destination pages | 读取 source pages | **存在竞争**：通过 **Paged Shared Memory Abstraction** 管理——task 需 acquire/release 32KB pages。Pipelining 条件：(1) 当前 task 已发出所有 data-transfer 指令；(2) 有足够的空闲 shared memory pages。若 pages 不足，pipelining 暂停 |
| **Tensor Cores** | 不使用 | 独占使用 | **无竞争** |
| **CUDA Cores** | 不使用（TMA 自治） | element-wise ops 使用 | **无竞争** |

## 问题 4：MPK tGraph 与同类图分解方法的对比

### 4.1 MPK vs MegaScale-MoE：同步开销的核心差异

**MegaScale-MoE 的 tile 级 barrier**：
- MegaScale-MoE 使用 **device memory barrier**（硬件支持，本质是 GPU 的 global memory fence/atomic 操作）。tile 级 barrier 将通信-计算 barrier 融合，使得单个 tile 完成后即可触发对应的 AllReduce tile，不等整个 operator 完成
- 但 MegaScale-MoE 的 barrier 机制仍然建立在 **kernel 边界** 之上——每个 tile 的工作仍然是一个独立的 kernel（或 CUDA Graph 中的一个 node）。Barrier 的作用是允许不同 kernel 的 tile 之间进行细粒度同步，但 kernel launch 本身的 overhead 仍然存在

**MPK 的软件 event（atomicAdd + circular buffer）**：
- 完全消除 kernel 边界：所有 task 在同一个 persistent kernel 内执行
- 同步通过 device memory 上的 atomicAdd 实现（跨 SM 可见）
- Event 的 trigger 和 dispatch 均在 GPU 内部完成，无 CPU 参与

**核心差异对比**：

| 维度 | MegaScale-MoE | MPK |
|------|---------------|-----|
| 同步基座 | 仍需 kernel 边界（tile 内是 kernel） | 无 kernel 边界（所有 task 同在一个 persistent kernel） |
| 同步机制 | Device memory barrier + 硬件 fence | 纯软件 atomicAdd + circular buffer |
| 同步粒度 | Tile 级（tile = kernel 的工作单元） | Task 级（task = 一个 output tile，在 persistent kernel 内） |
| Launch overhead | 有（每个 tile 仍需 kernel launch/CUDA Graph node） | 无（仅一次 launch） |
| 跨算子流水线 | 有限（kernel 边界阻碍跨算子 pre-loading） | 完全（cross-task pipelining 跨算子 TMA pre-loading） |

**哪种更优？**：
- **MegaScale-MoE 的硬件 barrier 在以下条件下更优**：当 workload 以通信为主要瓶颈且通信 pattern 规则时（如 MoE all-to-all），硬件 fence 的延迟比软件 atomic polling 更低（硬件 fence 约几十个周期，atomicAdd + polling 约数百周期）
- **MPK 的软件 event 在以下条件下更优**：当需要跨算子细粒度流水线且 operator 种类多（非仅 MoE）时，软件 event 的灵活性更高——可以任意定义依赖图拓扑，不受硬件 barrier 只能同步固定 pattern 的限制；且消除 kernel launch overhead 对 latency-critical decode 场景至关重要

### 4.2 MPK vs Welder：是否达到了类似的跨算子 SM 级流水线？

**Welder 的能力边界**：
- Welder 的 tile-graph 将 DNN 计算从 operator 级 dataflow graph 降低为 tile 级，自动发现 89 种 fusion pattern（含两个以上 reduction operator 的融合，这是传统 TVM/Ansor 无法做到的）
- Welder 的 tile-graph 中，tile 之间通过 shared memory 直接连接——上游 tile 产出结果留在 shared memory，下游 tile 直接消费，消除中间的 global memory 往返
- **但 Welder 的 tile-graph 最终仍然编译为单个 kernel**（每个融合后的 subgraph 是一个 kernel），并未将所有 operators 融合为一个 persistent kernel。Welder 的融合止于 **kernel 内 tile 级流水线**（intra-kernel），而非 MPK 的 **跨 kernel 边界的 SM 级流水线**

**关键区别**：

| 维度 | Welder | MPK |
|------|--------|-----|
| 融合范围 | 单 kernel 内的 operator 子图 | 整个模型的所有 operators（跨所有 layers） |
| 执行模型 | 多个 fused kernel（每个 fused subgraph 一个 kernel launch） | 单个 persistent kernel |
| 流水线跨 kernel？ | 否（kernel barrier 中断流水线） | 是（cross-task pipelining 跨越所有 operators） |
| 运行时调度 | 编译期静态确定（无运行时 adaptive dispatch） | JIT+AOT hybrid：运行时 adaptive workload balancing |
| 代码生成 | 基于 Triton | 基于 Mirage superoptimizer（生成 CUDA device functions） |

**MPK 的独特贡献**：
1. **端到端 persistent kernel**：Welder 做不到——Welder 仍然在 kernel 边界处有 barrier，无法跨 kernel 进行 TMA pre-loading
2. **运行时 event-driven execution**：Welder 的 tile-graph 是静态编译产物，运行时固定；MPK 的 event 系统支持 JIT dispatch（data-dependent 的动态调度）
3. **SM 分区 + decentralized scheduling**：Welder 没有类似的 in-kernel runtime 设计

### 4.3 MPK 为何不进一步分解到 micro-op 级别？

MPK 将 task 粒度停在「一个 output tile per task」而不是继续分解到 micro-op（如 Infera 的 micro-op tile），有以下几个设计约束：

1. **Shared Memory 容量约束（首要约束）**：每个 task 需要 shared memory 来存储输入/输出 tiles。H100 每个 SM 的 shared memory 约 228KB，32KB page × 7 pages。MatMul 的一个 output tile（如 128×128 FP16 = 32KB）已经占满一个 page。如果再分解到 micro-op（如 32×32 tile），每个 micro-op task 太小，shared memory 利用率下降（page 内部碎片化），且 tile 过小导致 Tensor Core 利用率降低（MMA tile 最小维度受限于 MMA 指令尺寸，如 H100 的 WGMMA 需要 M≥64）

2. **Event 同步开销的 scaling 问题**：Task 数量每翻倍一次，event 数量至少线性增长（每个新 task 可能需要额外的 event 来追踪依赖）。MPK 的 event 同步本身有开销（atomicAdd + polling），task 粒度过细 → task 数量暴增 → event 同步开销占比上升 → 侵蚀加速收益。论文选择约 132 tasks/MatMul（匹配 SM 数量）是一个平衡点：task 数与物理 SM 数匹配，每个 SM 一个 task queue，调度效率最高

3. **Register 压力**：每个 task 的 CUDA device function（由 Mirage superoptimizer 生成）需要充足的 register 来实现 intra-SM software pipelining。Task 过小意味着每个 task 的工作量不足以充分利用 register file（H100 每个 SM 65536 registers），导致 register 利用率低

4. **Task 描述符存储开销**：每个 task 描述符 352 bytes 存储在 device memory。如果 task 数量从 ~132/operator 增加到 ~1000/operator，task 描述符存储从 ~46KB 增加到 ~352KB per operator，对 device memory 带宽和 capacity 造成压力

5. **与 Infera 的差异化设计目标**：Infera 的 micro-op 切分是为了解决通信调度问题（将 All-to-All/AllReduce 分解为 micro-ops 以便 priority scheduling），其 micro-op 本身不做计算，只是通信调度单元。MPK 的 task 则是完整的计算+通信单元，设计目标不同

## 问题 5：Persistent Kernel 设计决策的深入分析

### 5.1 Persistent Kernel 最优/退化条件

**最优条件**：
- **Latency-critical decode**（batch size 小，per-iteration latency 敏感）：kernel launch overhead（~5-10μs × 数百次/iteration）占 iteration latency 显著比例（Qwen3-8B decode iteration ~12.5ms，数百次 launch 约 0.5-2ms overhead）。Persistent kernel 单次 launch 消除此 overhead
- **Operator 粒度细碎**（如 Transformer decoder 的许多 element-wise ops + small MatMuls）：大量小 kernel launch 的累积 overhead 远大于 mega-kernel 内部 task dispatch 开销
- **需要跨算子流水线**：cross-task pipelining 只能在统一的 persistent kernel 内实现，跨 kernel 的 TMA pre-loading 无法工作（kernel barrier 阻止）
- **GPU 代际越新越优**：H100/B200 有 TMA 和更大的 shared memory（更深的 pipelining），使 persistent kernel 的收益更大。A100 也有 TMA（自 H100 引入，实际上 A100 没有 TMA），但 A100 使用 cp.async 替代

**退化条件**：
- **Batch size 极大**（>64）：每个 task 的计算量随 batch size 增大而增大（如 attention 的计算量与 batch_size × seq_len² 成正比），task 执行时间增长 → SM 间负载不均加剧 → JIT dispatch 的收益下降（因为 task 执行时间长，动态调度的相对收益变小）。同时 tGraph 的线性化调度在极大 batch 下可能不如原生 kernel-per-operator + CUDA Graphs（后者可以利用 CUDA 的 MPS 和 multi-stream 并发）
- **Batch size 极小**（=1, prefill）：prefill 阶段单个 batch 的 MatMul 维度可能不足以让所有 SM 都获得有意义的 task。如果 K 维太小（如 prompt_len=64），每个 MatMul task 的 K 维 tile 可能只有 64，远小于 Tensor Core 的最优 K 维（通常 128-256），SM 利用率低下。Persistent kernel 的调度 overhead（event polling + task dispatch）在小 workload 下占比变大
- **模型极浅**（如 2-3 层）：task 总数少（如 2 层 × ~30 operators/layer × ~4 tasks/operator ≈ 240 tasks），不足以让 128 workers 充分负载。大量 SM 在等待 event 激活时 idle polling
- **模型极深**（如 >100 层）：tGraph 规模大（task 总数 >10K），event 数量多 → event 同步开销累积（每个 event 需要 atomic polling）。同时 task 描述符存储（352 bytes × 10K = 3.5MB device memory）和 event 元数据占用增加。但理论上这是 MPK 的主场（operator 多 → fusion 收益大）

### 5.2 多租户 Serving 下的 SM 占用代价

**MPK 论文未评估此代价**（这是一个明确的信息缺口）。从设计原理分析：

- **代价**：Persistent kernel 一旦 launch，**所有 SM 被持续占用**直至整个 mega-kernel 完成（可能持续数十秒到数分钟，取决于 decode length）。在此期间，其他 CUDA Stream 的 kernel 无法抢占这些 SM——NVIDIA GPU 的 SM 是以 thread block 为粒度分配的，而 persistent kernel 的 thread blocks 占满所有 SM，其他 kernel 只能等待
- **多租户场景下的问题**：
  - 如果多个模型共享一块 GPU（如 MPS 模式），MPK 的 persistent kernel 会**独占 GPU**，无法与另一个模型的推理并发
  - 如果有高优先级请求需要抢占当前推理，persistent kernel 无法被中断（CUDA 不支持 kernel preemption on SM level）
  - 与 continuous batching 的兼容性：MPK 将 continuous batching 逻辑嵌入 mega-kernel 内的 start event task 中执行，这意味着 batch 变化需要在 mega-kernel 内部处理。如果需要在 mega-kernel 运行期间添加/移除请求，MPK 通过 in-kernel page allocation + request admission task 处理——这实际上是一种**内部化的多租户支持**，而非外部 OS/GPU-level 的多租户

- **可接受性判断**：对于**单模型高吞吐 serving**（如一个模型独占 GPU），这个代价可接受——这正是 MPK 的目标场景。对于**多模型共享 GPU** 的 cloud serving，这个代价不可接受——需要 GPU-level 的 spatial partitioning（如 MIG）或 temporal multiplexing（persistent kernel 天然不支持）

### 5.3 Batch Size 版本管理

根据实验笔记：MPK 编译器为每个 batch size（2 的幂次，up to max_batch）生成专用 tGraph。

**需要预编译的版本数**：如果 max_batch=16，则需要 batch_size ∈ {1, 2, 4, 8, 16} 共 **5 个 tGraph 版本**。如果 max_batch=128，则需要 8 个版本

**每个版本的 binary size + metadata**：
- 每个 task 描述符：352 bytes
- 每个 event：约 16 bytes（required_trigger_count + first/last indices）
- 典型 Qwen3-8B tGraph：约 132 tasks × ~28 operators（per layer）× 32 layers ≈ 118K tasks（这似乎太多了）。让我修正——实际上每层约 7 个 MatMul + 若干 element-wise ops，分解为约 132 tasks/MatMul × 7 ≈ 924 tasks/layer。32 layers ≈ 30K tasks。30K × 352 bytes ≈ 10.5 MB 用于 task 描述符。再加 event metadata，估计总 metadata 约 12-15 MB per tGraph
- **CUDA code binary**：Mirage superoptimizer 生成的 task CUDA device functions 是跨 tGraph 版本**共享的**——不同 batch size 的 MatMul task 使用相同的 CUDA device function（只是 input tensor 维度不同），所以 binary 不会随版本数线性增长。估算总 binary size 约 5-10 MB
- 5 个版本 × 12 MB metadata + 10 MB shared binary ≈ **70 MB total**（数量级估计，论文未给出精确数字）

**版本切换延迟**：MPK 在 mega-kernel launch 时选择对应 batch size 的 tGraph。这发生在 **host 端**（PyTorch 层），切换开销忽略不计（仅一个函数指针选择）。但如果 batch size 变化需要 CPU 侧察觉并 relaunch mega-kernel，则涉及一次 mega-kernel 退出 + 重新 launch 的开销（~10-50μs）。论文通过在 mega-kernel 内部处理 continuous batching（in-kernel request admission）来减少 relaunch 频率

**信息缺口**：论文未提供具体的 per-tGraph memory footprint 和版本数量上限的定量数据

### 5.4 为何不选 CUDA Graph + multi-Stream？

**CUDA Graphs 在 MPK 场景下的不可逾越限制**：

1. **静态性**：CUDA Graphs 是 static capture——所有 kernel launch 参数、tensor addresses、control flow 在 capture 时固定。Continuous batching 导致 batch size 动态变化 → tensor shapes 变化 → CUDA Graph 需要 re-instantiation。这是**根本性限制**
2. **跨 kernel 流水线不可能**：即使使用 multi-Stream + CUDA Graphs，每个 kernel 仍然受 kernel barrier 约束（同一 stream 上的连续 kernel 之间）。跨 stream 的依赖需要 host 端 event 同步 → CPU 参与 → 仍无法实现 GPU 内部自决策的 fine-grained pipelining
3. **无法实现 in-kernel scheduling**：CUDA Graphs 的调度决策由 CUDA runtime（host 端）做出，无法在 GPU 内部根据 data-dependent 条件动态调整（如 JIT task dispatch for attention）
4. **Nimble 的 multi-Stream 方案**：Nimble 通过多 Stream 实现 prefill/decode 并发，但仍然是 kernel-per-operator 模型——它优化的是**不同请求**之间的并发（prefill 和 decode 在不同 Stream 上并行），而非**同一请求内**的跨算子流水线
5. **CDP (CUDA Dynamic Parallelism) 的局限**：CDP 允许 GPU kernel 内 launch 子 kernel，理论上有动态能力，但：(a) 子 kernel launch overhead 极高（数十微秒），比 host 端 launch 还慢；(b) 子 kernel 继承父 kernel 的资源限制；(c) 不支持跨 SM 的 shared memory 共享。因此 CDP 不适合 fine-grained task dispatch

**MPK 的 Persistent Kernel 本质上是手工实现了 CUDA Graphs 想做但做不到的事**：GPU 内部自主的、动态的、细粒度的 task 图调度——无需 host 参与，无需 kernel relaunch。

## 问题 6：Paged Shared Memory 的深入分析

### 6.1 Page 分配/回收策略

MPK 的 Paged SMEM 采用**编译期静态分配 + 运行期 acquire/release**：

- **编译期**：在 tGraph 生成阶段，MPK 编译器分析每个 task 的 SMEM 需求（输入 tiles、输出 tiles、中间 buffer），使用类似**寄存器分配的 interval graph coloring** 方法来分配 shared memory pages。具体地：将每个 task 的生命周期（从被 dispatch 到完成）映射为一个 interval，两个 intervals 重叠的 tasks 不能使用相同的 page → 转化为图着色问题 → 编译期求解最小 page 数
- **运行期**：task 在执行前通过 **acquire(page_id)** 获取 page，完成后通过 **release(page_id)** 归还。Page 的 ownership 由 task queue 和 event system 隐式管理——当一个 task 的所有前驱 event 都激活时，它需要的 pages 保证可用（由编译期的 interval 分析保证）
- **关键设计**：page 分配是**编译期求解**的（不是运行时动态分配），因为 SMEM page 的分配需要在编译期验证安全性（确保无 deadlock 和无 data race）。运行时仅执行 acquire/release 的轻量级状态切换（本质上是一个 flag set/clear 操作）

**与 interval graph coloring 的关系**：MPK 论文在描述 runtime optimizations 时提到使用类似寄存器分配的方法来管理 SMEM pages。这与传统编译器中寄存器分配的 live range analysis + graph coloring 是同构的问题——tasks 是 live ranges，pages 是 registers

### 6.2 Pipelining Stall 分析

**论文未提供 stall 频率和持续时长的定量 profiling 数据**（这是一个信息缺口）。从设计原理推断：

- **Stall 发生条件**：当前 task 的 compute 阶段未完成（未释放 pages）+ 需要 pre-load 下一个 task → 但空闲 pages 不足（7 pages/SM on H100，部分被当前 task 占用）
- **典型场景**：如果当前 MatMul task 占用 4 pages（2 input + 1 weight + 1 output），剩余 3 pages 可用于 pre-loading。如果下一个 task 也需要 4 pages，则 pre-loading 只能加载部分数据（如先 pre-load 1-2 pages 的 weight/input），无法完全隐藏 memory latency
- **影响**：pipelining depth 受 SMEM page 数量限制。H100 的 7 pages/SM → 理论最大可同时容纳 2 个 task 的 pages（每个 task ~3-4 pages），即 pipelining depth≈2。如果 SMEM 容量更大（如未来 GPU），pipelining depth 可加深
- **对加速比的侵蚀**：B200 上 cross-task pipelining 仅带来 1.2-1.3x 加速（Qwen3-8B final linear layer），说明 pipelining 的收益受限于 SMEM 容量和 task 的 compute/memory 比例。如果 compute 阶段足够长（覆盖 pre-loading 的 memory latency），stall 的影响较小

### 6.3 Paged SMEM vs ThunderKittens vs 传统方案

| 维度 | ThunderKittens (compile-time swizzle) | 传统双缓冲 | MPK Paged SMEM |
|------|--------------------------------------|-----------|----------------|
| **管理粒度** | 固定 swizzle pattern（编译期确定 layout 避免 bank conflict） | 两个固定大小的 buffer（ping-pong） | 32KB fixed-size pages，task 级 acquire/release |
| **跨 task 复用** | 否（单 kernel 内使用，kernel 结束后 SMEM 清空） | 否（仅在同一 kernel 的连续 iterations 间轮换） | **是**（跨 task 的 SMEM 复用——前一个 task 的 output page 可直接作为下一个 task 的 input page） |
| **分配策略** | 编译期固定 layout | 编译期固定 buffer 大小 | 编译期 interval graph coloring + 运行期轻量级 acquire/release |
| **灵活性** | 低（每个 kernel 专用 layout） | 低（仅支持单 producer-consumer pipeline） | **高**（支持多 task 间的任意 page 共享图，由 tGraph 拓扑决定） |
| **可迁移性** | 不绑定特定架构 | 通用 | 可用于其他 persistent kernel 方案（核心 idea 是通用的），但需要 tGraph 级别的依赖分析来保证安全性 |

**Paged SMEM 的可迁移性**：核心 idea（SMEM 分页 + 编译期 interval analysis + 运行期 acquire/release）是**通用的**，可以迁移到其他 persistent kernel 方案。但它与 MPK 的 tGraph 强绑定在于：
- 需要**编译期知道完整的 task 依赖图**（tGraph）来进行 interval graph coloring
- 需要**运行期的 event 系统**来保证 page 在正确的时间可用
- 如果没有 MPK 的编译框架（operator decomposition → dependency analysis → event fusion → tGraph normalization），单独使用 Paged SMEM 需要手动管理这些依赖

### 6.4 32KB Page 内部 Layout 与 Bank Conflict

**论文未详细描述 page 内部 layout 的 bank conflict 避免策略**（这是一个信息缺口）。从设计原理和 Mirage superoptimizer 的能力推断：

- **Bank conflict 由 Mirage superoptimizer 在 task 代码生成阶段处理**：每个 task 的 CUDA device function 由 Mirage 自动搜索最优 thread block graph，搜索空间中包含 shared memory layout 的 swizzle 模式（XOR-based swizzle 是最常见的 bank-conflict-free 方案）
- **不同 access pattern 的兼容方式**：
  - **MatMul tasks**：Mirage 为 MMA 操作自动选择避免 bank conflict 的 swizzle layout（如 128×128 tile 使用 32-bank × 4-byte XOR swizzle）。这类似于 ThunderKittens 的 compile-time swizzle selection
  - **Element-wise ops**（如 SiLU、RMSNorm）：这些 ops 的 SMEM access pattern 是 strided（每线程处理多个元素），bank conflict 风险较低。32KB page 可以按自然 layout（row-major）存储，无需 swizzle
  - **Attention tasks**：FlashAttention-style kernel 有自己的 SMEM layout 需求（Q/K/V tiles 需要特定 layout 以支持 online softmax）。Mirage 生成 attention task 时会为 attention-specific patterns 优化 SMEM layout
- **关键设计**：每个 task 的 SMEM access pattern 由 Mirage superoptimizer 在**每个 task 的 CUDA device function 内部**独立优化。Paged SMEM 提供的是**空间隔离**（不同 task 不互相干扰），而不规定 page 内部的数据 layout。Page 内部的 layout 完全由 task 的代码决定

## 问题 4：MPK tGraph 与同类图分解方法的对比

### 4.1 MPK vs MegaScale-MoE：同步开销的核心差异

**MegaScale-MoE 的 tile 级 barrier**：
- MegaScale-MoE 使用 **device memory barrier**（硬件支持，本质是 GPU 的 global memory fence/atomic 操作）。tile 级 barrier 将通信-计算 barrier 融合，使得单个 tile 完成后即可触发对应的 AllReduce tile，不等整个 operator 完成
- 但 MegaScale-MoE 的 barrier 机制仍然建立在 **kernel 边界** 之上——每个 tile 的工作仍然是一个独立的 kernel（或 CUDA Graph 中的一个 node）。Barrier 的作用是允许不同 kernel 的 tile 之间进行细粒度同步，但 kernel launch 本身的 overhead 仍然存在

**MPK 的软件 event（atomicAdd + circular buffer）**：
- 完全消除 kernel 边界：所有 task 在同一个 persistent kernel 内执行
- 同步通过 device memory 上的 atomicAdd 实现（跨 SM 可见）
- Event 的 trigger 和 dispatch 均在 GPU 内部完成，无 CPU 参与

**核心差异对比**：

| 维度 | MegaScale-MoE | MPK |
|------|---------------|-----|
| 同步基座 | 仍需 kernel 边界（tile 内是 kernel） | 无 kernel 边界（所有 task 同在一个 persistent kernel） |
| 同步机制 | Device memory barrier + 硬件 fence | 纯软件 atomicAdd + circular buffer |
| 同步粒度 | Tile 级（tile = kernel 的工作单元） | Task 级（task = 一个 output tile，在 persistent kernel 内） |
| Launch overhead | 有（每个 tile 仍需 kernel launch/CUDA Graph node） | 无（仅一次 launch） |
| 跨算子流水线 | 有限（kernel 边界阻碍跨算子 pre-loading） | 完全（cross-task pipelining 跨算子 TMA pre-loading） |

**哪种更优？**：
- **MegaScale-MoE 的硬件 barrier 在以下条件下更优**：当 workload 以通信为主要瓶颈且通信 pattern 规则时（如 MoE all-to-all），硬件 fence 的延迟比软件 atomic polling 更低（硬件 fence 约几十个周期，atomicAdd + polling 约数百周期）
- **MPK 的软件 event 在以下条件下更优**：当需要跨算子细粒度流水线且 operator 种类多（非仅 MoE）时，软件 event 的灵活性更高——可以任意定义依赖图拓扑，不受硬件 barrier 只能同步固定 pattern 的限制；且消除 kernel launch overhead 对 latency-critical decode 场景至关重要

### 4.2 MPK vs Welder：是否达到了类似的跨算子 SM 级流水线？

**Welder 的能力边界**：
- Welder 的 tile-graph 将 DNN 计算从 operator 级 dataflow graph 降低为 tile 级，自动发现 89 种 fusion pattern（含两个以上 reduction operator 的融合，这是传统 TVM/Ansor 无法做到的）
- Welder 的 tile-graph 中，tile 之间通过 shared memory 直接连接——上游 tile 产出结果留在 shared memory，下游 tile 直接消费，消除中间的 global memory 往返
- **但 Welder 的 tile-graph 最终仍然编译为单个 kernel**（每个融合后的 subgraph 是一个 kernel），并未将所有 operators 融合为一个 persistent kernel。Welder 的融合止于 **kernel 内 tile 级流水线**（intra-kernel），而非 MPK 的 **跨 kernel 边界的 SM 级流水线**

**关键区别**：

| 维度 | Welder | MPK |
|------|--------|-----|
| 融合范围 | 单 kernel 内的 operator 子图 | 整个模型的所有 operators（跨所有 layers） |
| 执行模型 | 多个 fused kernel（每个 fused subgraph 一个 kernel launch） | 单个 persistent kernel |
| 流水线跨 kernel？ | 否（kernel barrier 中断流水线） | 是（cross-task pipelining 跨越所有 operators） |
| 运行时调度 | 编译期静态确定（无运行时 adaptive dispatch） | JIT+AOT hybrid：运行时 adaptive workload balancing |
| 代码生成 | 基于 Triton | 基于 Mirage superoptimizer（生成 CUDA device functions） |

**MPK 的独特贡献**：
1. **端到端 persistent kernel**：Welder 做不到——Welder 仍然在 kernel 边界处有 barrier，无法跨 kernel 进行 TMA pre-loading
2. **运行时 event-driven execution**：Welder 的 tile-graph 是静态编译产物，运行时固定；MPK 的 event 系统支持 JIT dispatch（data-dependent 的动态调度）
3. **SM 分区 + decentralized scheduling**：Welder 没有类似的 in-kernel runtime 设计

### 4.3 MPK 为何不进一步分解到 micro-op 级别？

MPK 将 task 粒度停在「一个 output tile per task」而不是继续分解到 micro-op（如 Infera 的 micro-op tile），有以下几个设计约束：

1. **Shared Memory 容量约束（首要约束）**：每个 task 需要 shared memory 来存储输入/输出 tiles。H100 每个 SM 的 shared memory 约 228KB，32KB page × 7 pages。MatMul 的一个 output tile（如 128×128 FP16 = 32KB）已经占满一个 page。如果再分解到 micro-op（如 32×32 tile），每个 micro-op task 太小，shared memory 利用率下降（page 内部碎片化），且 tile 过小导致 Tensor Core 利用率降低（MMA tile 最小维度受限于 MMA 指令尺寸，如 H100 的 WGMMA 需要 M≥64）

2. **Event 同步开销的 scaling 问题**：Task 数量每翻倍一次，event 数量至少线性增长（每个新 task 可能需要额外的 event 来追踪依赖）。MPK 的 event 同步本身有开销（atomicAdd + polling），task 粒度过细 → task 数量暴增 → event 同步开销占比上升 → 侵蚀加速收益。论文选择约 132 tasks/MatMul（匹配 SM 数量）是一个平衡点：task 数与物理 SM 数匹配，每个 SM 一个 task queue，调度效率最高

3. **Register 压力**：每个 task 的 CUDA device function（由 Mirage superoptimizer 生成）需要充足的 register 来实现 intra-SM software pipelining。Task 过小意味着每个 task 的工作量不足以充分利用 register file（H100 每个 SM 65536 registers），导致 register 利用率低

4. **Task 描述符存储开销**：每个 task 描述符 352 bytes 存储在 device memory。如果 task 数量从 ~132/operator 增加到 ~1000/operator，task 描述符存储从 ~46KB 增加到 ~352KB per operator，对 device memory 带宽和 capacity 造成压力

5. **与 Infera 的差异化设计目标**：Infera 的 micro-op 切分是为了解决通信调度问题（将 All-to-All/AllReduce 分解为 micro-ops 以便 priority scheduling），其 micro-op 本身不做计算，只是通信调度单元。MPK 的 task 则是完整的计算+通信单元，设计目标不同

## 问题 5：Persistent Kernel 设计决策的深入分析

### 5.1 Persistent Kernel 最优/退化条件

**最优条件**：
- **Latency-critical decode**（batch size 小，per-iteration latency 敏感）：kernel launch overhead（~5-10μs × 数百次/iteration）占 iteration latency 显著比例（Qwen3-8B decode iteration ~12.5ms，数百次 launch 约 0.5-2ms overhead）。Persistent kernel 单次 launch 消除此 overhead
- **Operator 粒度细碎**（如 Transformer decoder 的许多 element-wise ops + small MatMuls）：大量小 kernel launch 的累积 overhead 远大于 mega-kernel 内部 task dispatch 开销
- **需要跨算子流水线**：cross-task pipelining 只能在统一的 persistent kernel 内实现，跨 kernel 的 TMA pre-loading 无法工作（kernel barrier 阻止）
- **GPU 代际越新越优**：H100/B200 有 TMA 和更大的 shared memory（更深的 pipelining），使 persistent kernel 的收益更大。A100 也有 TMA（自 H100 引入，实际上 A100 没有 TMA），但 A100 使用 cp.async 替代

**退化条件**：
- **Batch size 极大**（>64）：每个 task 的计算量随 batch size 增大而增大（如 attention 的计算量与 batch_size × seq_len² 成正比），task 执行时间增长 → SM 间负载不均加剧 → JIT dispatch 的收益下降（因为 task 执行时间长，动态调度的相对收益变小）。同时 tGraph 的线性化调度在极大 batch 下可能不如原生 kernel-per-operator + CUDA Graphs（后者可以利用 CUDA 的 MPS 和 multi-stream 并发）
- **Batch size 极小**（=1, prefill）：prefill 阶段单个 batch 的 MatMul 维度可能不足以让所有 SM 都获得有意义的 task。如果 K 维太小（如 prompt_len=64），每个 MatMul task 的 K 维 tile 可能只有 64，远小于 Tensor Core 的最优 K 维（通常 128-256），SM 利用率低下。Persistent kernel 的调度 overhead（event polling + task dispatch）在小 workload 下占比变大
- **模型极浅**（如 2-3 层）：task 总数少（如 2 层 × ~30 operators/layer × ~4 tasks/operator ≈ 240 tasks），不足以让 128 workers 充分负载。大量 SM 在等待 event 激活时 idle polling
- **模型极深**（如 >100 层）：tGraph 规模大（task 总数 >10K），event 数量多 → event 同步开销累积（每个 event 需要 atomic polling）。同时 task 描述符存储（352 bytes × 10K = 3.5MB device memory）和 event 元数据占用增加。但理论上这是 MPK 的主场（operator 多 → fusion 收益大）

### 5.2 多租户 Serving 下的 SM 占用代价

**MPK 论文未评估此代价**（这是一个明确的信息缺口）。从设计原理分析：

- **代价**：Persistent kernel 一旦 launch，**所有 SM 被持续占用**直至整个 mega-kernel 完成（可能持续数十秒到数分钟，取决于 decode length）。在此期间，其他 CUDA Stream 的 kernel 无法抢占这些 SM——NVIDIA GPU 的 SM 是以 thread block 为粒度分配的，而 persistent kernel 的 thread blocks 占满所有 SM，其他 kernel 只能等待
- **多租户场景下的问题**：
  - 如果多个模型共享一块 GPU（如 MPS 模式），MPK 的 persistent kernel 会**独占 GPU**，无法与另一个模型的推理并发
  - 如果有高优先级请求需要抢占当前推理，persistent kernel 无法被中断（CUDA 不支持 kernel preemption on SM level）
  - 与 continuous batching 的兼容性：MPK 将 continuous batching 逻辑嵌入 mega-kernel 内的 start event task 中执行，这意味着 batch 变化需要在 mega-kernel 内部处理。如果需要在 mega-kernel 运行期间添加/移除请求，MPK 通过 in-kernel page allocation + request admission task 处理——这实际上是一种**内部化的多租户支持**，而非外部 OS/GPU-level 的多租户

- **可接受性判断**：对于**单模型高吞吐 serving**（如一个模型独占 GPU），这个代价可接受——这正是 MPK 的目标场景。对于**多模型共享 GPU** 的 cloud serving，这个代价不可接受——需要 GPU-level 的 spatial partitioning（如 MIG）或 temporal multiplexing（persistent kernel 天然不支持）

### 5.3 Batch Size 版本管理

根据实验笔记：MPK 编译器为每个 batch size（2 的幂次，up to max_batch）生成专用 tGraph。

**需要预编译的版本数**：如果 max_batch=16，则需要 batch_size ∈ {1, 2, 4, 8, 16} 共 **5 个 tGraph 版本**。如果 max_batch=128，则需要 8 个版本

**每个版本的 binary size + metadata**：
- 每个 task 描述符：352 bytes
- 每个 event：约 16 bytes（required_trigger_count + first/last indices）
- 典型 Qwen3-8B tGraph：约 132 tasks × ~28 operators（per layer）× 32 layers ≈ 118K tasks（这似乎太多了）。让我修正——实际上每层约 7 个 MatMul + 若干 element-wise ops，分解为约 132 tasks/MatMul × 7 ≈ 924 tasks/layer。32 layers ≈ 30K tasks。30K × 352 bytes ≈ 10.5 MB 用于 task 描述符。再加 event metadata，估计总 metadata 约 12-15 MB per tGraph
- **CUDA code binary**：Mirage superoptimizer 生成的 task CUDA device functions 是跨 tGraph 版本**共享的**——不同 batch size 的 MatMul task 使用相同的 CUDA device function（只是 input tensor 维度不同），所以 binary 不会随版本数线性增长。估算总 binary size 约 5-10 MB
- 5 个版本 × 12 MB metadata + 10 MB shared binary ≈ **70 MB total**（数量级估计，论文未给出精确数字）

**版本切换延迟**：MPK 在 mega-kernel launch 时选择对应 batch size 的 tGraph。这发生在 **host 端**（PyTorch 层），切换开销忽略不计（仅一个函数指针选择）。但如果 batch size 变化需要 CPU 侧察觉并 relaunch mega-kernel，则涉及一次 mega-kernel 退出 + 重新 launch 的开销（~10-50μs）。论文通过在 mega-kernel 内部处理 continuous batching（in-kernel request admission）来减少 relaunch 频率

**信息缺口**：论文未提供具体的 per-tGraph memory footprint 和版本数量上限的定量数据

### 5.4 为何不选 CUDA Graph + multi-Stream？

**CUDA Graphs 在 MPK 场景下的不可逾越限制**：

1. **静态性**：CUDA Graphs 是 static capture——所有 kernel launch 参数、tensor addresses、control flow 在 capture 时固定。Continuous batching 导致 batch size 动态变化 → tensor shapes 变化 → CUDA Graph 需要 re-instantiation。这是**根本性限制**
2. **跨 kernel 流水线不可能**：即使使用 multi-Stream + CUDA Graphs，每个 kernel 仍然受 kernel barrier 约束（同一 stream 上的连续 kernel 之间）。跨 stream 的依赖需要 host 端 event 同步 → CPU 参与 → 仍无法实现 GPU 内部自决策的 fine-grained pipelining
3. **无法实现 in-kernel scheduling**：CUDA Graphs 的调度决策由 CUDA runtime（host 端）做出，无法在 GPU 内部根据 data-dependent 条件动态调整（如 JIT task dispatch for attention）
4. **Nimble 的 multi-Stream 方案**：Nimble 通过多 Stream 实现 prefill/decode 并发，但仍然是 kernel-per-operator 模型——它优化的是**不同请求**之间的并发（prefill 和 decode 在不同 Stream 上并行），而非**同一请求内**的跨算子流水线
5. **CDP (CUDA Dynamic Parallelism) 的局限**：CDP 允许 GPU kernel 内 launch 子 kernel，理论上有动态能力，但：(a) 子 kernel launch overhead 极高（数十微秒），比 host 端 launch 还慢；(b) 子 kernel 继承父 kernel 的资源限制；(c) 不支持跨 SM 的 shared memory 共享。因此 CDP 不适合 fine-grained task dispatch

**MPK 的 Persistent Kernel 本质上是手工实现了 CUDA Graphs 想做但做不到的事**：GPU 内部自主的、动态的、细粒度的 task 图调度——无需 host 参与，无需 kernel relaunch。

## 问题 6：Paged Shared Memory 的深入分析

### 6.1 Page 分配/回收策略

MPK 的 Paged SMEM 采用**编译期静态分配 + 运行期 acquire/release**：

- **编译期**：在 tGraph 生成阶段，MPK 编译器分析每个 task 的 SMEM 需求（输入 tiles、输出 tiles、中间 buffer），使用类似**寄存器分配的 interval graph coloring** 方法来分配 shared memory pages。具体地：将每个 task 的生命周期（从被 dispatch 到完成）映射为一个 interval，两个 intervals 重叠的 tasks 不能使用相同的 page → 转化为图着色问题 → 编译期求解最小 page 数
- **运行期**：task 在执行前通过 **acquire(page_id)** 获取 page，完成后通过 **release(page_id)** 归还。Page 的 ownership 由 task queue 和 event system 隐式管理——当一个 task 的所有前驱 event 都激活时，它需要的 pages 保证可用（由编译期的 interval 分析保证）
- **关键设计**：page 分配是**编译期求解**的（不是运行时动态分配），因为 SMEM page 的分配需要在编译期验证安全性（确保无 deadlock 和无 data race）。运行时仅执行 acquire/release 的轻量级状态切换（本质上是一个 flag set/clear 操作）

**与 interval graph coloring 的关系**：MPK 论文在描述 runtime optimizations 时提到使用类似寄存器分配的方法来管理 SMEM pages。这与传统编译器中寄存器分配的 live range analysis + graph coloring 是同构的问题——tasks 是 live ranges，pages 是 registers

### 6.2 Pipelining Stall 分析

**论文未提供 stall 频率和持续时长的定量 profiling 数据**（这是一个信息缺口）。从设计原理推断：

- **Stall 发生条件**：当前 task 的 compute 阶段未完成（未释放 pages）+ 需要 pre-load 下一个 task → 但空闲 pages 不足（7 pages/SM on H100，部分被当前 task 占用）
- **典型场景**：如果当前 MatMul task 占用 4 pages（2 input + 1 weight + 1 output），剩余 3 pages 可用于 pre-loading。如果下一个 task 也需要 4 pages，则 pre-loading 只能加载部分数据（如先 pre-load 1-2 pages 的 weight/input），无法完全隐藏 memory latency
- **影响**：pipelining depth 受 SMEM page 数量限制。H100 的 7 pages/SM → 理论最大可同时容纳 2 个 task 的 pages（每个 task ~3-4 pages），即 pipelining depth≈2。如果 SMEM 容量更大（如未来 GPU），pipelining depth 可加深
- **对加速比的侵蚀**：B200 上 cross-task pipelining 仅带来 1.2-1.3x 加速（Qwen3-8B final linear layer），说明 pipelining 的收益受限于 SMEM 容量和 task 的 compute/memory 比例。如果 compute 阶段足够长（覆盖 pre-loading 的 memory latency），stall 的影响较小

### 6.3 Paged SMEM vs ThunderKittens vs 传统方案

| 维度 | ThunderKittens (compile-time swizzle) | 传统双缓冲 | MPK Paged SMEM |
|------|--------------------------------------|-----------|----------------|
| **管理粒度** | 固定 swizzle pattern（编译期确定 layout 避免 bank conflict） | 两个固定大小的 buffer（ping-pong） | 32KB fixed-size pages，task 级 acquire/release |
| **跨 task 复用** | 否（单 kernel 内使用，kernel 结束后 SMEM 清空） | 否（仅在同一 kernel 的连续 iterations 间轮换） | **是**（跨 task 的 SMEM 复用——前一个 task 的 output page 可直接作为下一个 task 的 input page） |
| **分配策略** | 编译期固定 layout | 编译期固定 buffer 大小 | 编译期 interval graph coloring + 运行期轻量级 acquire/release |
| **灵活性** | 低（每个 kernel 专用 layout） | 低（仅支持单 producer-consumer pipeline） | **高**（支持多 task 间的任意 page 共享图，由 tGraph 拓扑决定） |
| **可迁移性** | 不绑定特定架构 | 通用 | 可用于其他 persistent kernel 方案（核心 idea 是通用的），但需要 tGraph 级别的依赖分析来保证安全性 |

**Paged SMEM 的可迁移性**：核心 idea（SMEM 分页 + 编译期 interval analysis + 运行期 acquire/release）是**通用的**，可以迁移到其他 persistent kernel 方案。但它与 MPK 的 tGraph 强绑定在于：
- 需要**编译期知道完整的 task 依赖图**（tGraph）来进行 interval graph coloring
- 需要**运行期的 event 系统**来保证 page 在正确的时间可用
- 如果没有 MPK 的编译框架（operator decomposition → dependency analysis → event fusion → tGraph normalization），单独使用 Paged SMEM 需要手动管理这些依赖

### 6.4 32KB Page 内部 Layout 与 Bank Conflict

**论文未详细描述 page 内部 layout 的 bank conflict 避免策略**（这是一个信息缺口）。从设计原理和 Mirage superoptimizer 的能力推断：

- **Bank conflict 由 Mirage superoptimizer 在 task 代码生成阶段处理**：每个 task 的 CUDA device function 由 Mirage 自动搜索最优 thread block graph，搜索空间中包含 shared memory layout 的 swizzle 模式（XOR-based swizzle 是最常见的 bank-conflict-free 方案）
- **不同 access pattern 的兼容方式**：
  - **MatMul tasks**：Mirage 为 MMA 操作自动选择避免 bank conflict 的 swizzle layout（如 128×128 tile 使用 32-bank × 4-byte XOR swizzle）。这类似于 ThunderKittens 的 compile-time swizzle selection
  - **Element-wise ops**（如 SiLU、RMSNorm）：这些 ops 的 SMEM access pattern 是 strided（每线程处理多个元素），bank conflict 风险较低。32KB page 可以按自然 layout（row-major）存储，无需 swizzle
  - **Attention tasks**：FlashAttention-style kernel 有自己的 SMEM layout 需求（Q/K/V tiles 需要特定 layout 以支持 online softmax）。Mirage 生成 attention task 时会为 attention-specific patterns 优化 SMEM layout
- **关键设计**：每个 task 的 SMEM access pattern 由 Mirage superoptimizer 在**每个 task 的 CUDA device function 内部**独立优化。Paged SMEM 提供的是**空间隔离**（不同 task 不互相干扰），而不规定 page 内部的数据 layout。Page 内部的 layout 完全由 task 的代码决定
