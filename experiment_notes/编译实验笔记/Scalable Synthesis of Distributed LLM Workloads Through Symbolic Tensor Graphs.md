## Scalable Synthesis of Distributed LLM Workloads Through Symbolic Tensor Graphs

- 属于编译框架的实现是什么？实验比较什么？
  - STAGE（Symbolic Tensor grAph GEnerator，Georgia Tech + NVIDIA，ISCA'26）是一个分布式 LLM/MoE workload 合成框架：把"符号张量图（STG）IR + 并行化配置"编译成高保真、可喂给下游模拟器的 Chakra 执行图（Execution Graph，DAG，节点=计算/通信算子，边=数据/控制依赖，节点带 tensor 尺寸/类型/通信量属性），从而在不需要真实集群和 PyTorch/JAX 全栈部署的情况下做部署前系统优化（并行策略选择）与硬件 DSE。编译流水线四步：①STG IR 模块模板（MHA、GQA、MLA、Up-down FFN、Gate-up-down FFN、RMSNorm、Elem-wise Norm、MoE、MoE+Shared Experts、SSM 等，origin 对应 Transformer/LLaMA/DeepSeek-V2/Mamba/GPT/BERT/Gshard/Switch Transformer/DeepSeek-MoE）→②按层数（num_stacks）重复连接组装整模型 STG→③Workload Distributor：(a) 张量级分布——按 dp/tp/sp/fsdp/ep/hp 等把算子分片，先传播计算图推断各 tensor 形状、逐算子应用分布再重传播，暴露 producer/consumer 之间的 tensor 分布 mismatch（如 [a,c@1/tp] vs [a,c] 需 AllReduce），由 Collective Communication Matcher 按 Pull（Duplicated=No-Comm / Partition=Gather / PartialSum=Reduce）+ Push（Duplicated=Broadcast / Partition=Scatter / PartialSum 一般不用）虚拟头节点机制匹配出 AllReduce/AllGather/ReduceScatter/AllToAll 及其组合（如 [B/dp,S,H@1/tp]→[B/tp,S,H/dp] 匹配 ReduceScatter+AllToAll）；(b) 图级分布——把计算图按层切成 PP 子图列表，在跨图边上按 rank 插入 send/recv 对→④Graph Instantiation（符号→数值）：把 batch/seq/hidden/并行度等符号维替换为具体数值并自动传播，可选择性注入 PyTorch/Kineto 采集的真实值做混合扩展→输出默认 MLCommons Chakra schema（v0.0.4，可扩展 JSON 等其他 backend）。
  - 实验比较：(1) 与真实 ET 保真度验证（128×H100 SXM5 HGX 集群，NeMo 24.07+CUDA 12.5+PyTorch 2.5.0+CUPTI 采集）：峰值显存误差 1.3%~7.4%（扣除 CUDA init 后约覆盖实测 97%）、算子计算时间误差 0.3%~15.0%（平均 4.25%，混合 benchmark lookup table + 校准 roofline 估时）、通信量误差 0.000%~2.980%（NCCL 的 AllToAll 分解为 Send/Recv 后对比）、端到端 runtime 平均误差 3.53%（ASTRA-Sim 模拟通信+调度）。(2) 与 SOTA 建模框架对比：优于 Calculon（4 个 dense Megatron 模型 3.65% 误差）和 MADMAX（LLaMA-70B 15.34% 误差），且二者未验证 MoE。(3) DSE 案例：并行策略 DSE（64 H100 8×8 NVLink+IB，PaLM-540B batch=64 / LLaMA3.2-1B batch=2048 / LLaMA-70B batch=1024 @1024 GPU 80/40/24GB HBM 约束；结论：无单一最优策略、高 DP 常最快但受内存约束、FSDP 通信可与计算重叠、activation recompute 权衡）、workload 可扩展性（512~16K GPU DGX 节点、弱扩展 DP / 强扩展 TP w/ SP 到 1024 GPU）、系统可扩展性（Infiniband 3000 vs 80 GB/s，带宽 sweet spot）、架构导向 HBM/互连带宽预算分配（固定总预算扫 HBM 占比，最优 HBM 占比>50%）、DeepSeek-R1 推理（prefill/decode 分离，EP 配置 36/72/144 GPU 集群，Table VIII，prefill 偏好低 EP、decode 偏好高 EP 大集群）。(4) 模拟器可移植性：同一 workload 经轻量翻译层接入 AstraSim（Chakra 原生）、SimAI（NVIDIA NCCL/NVLink 语义，73 LoC）、ScaleSim（TPU 计算阵列，34 LoC）、Genie（RDMA 物理网络仿真，40~46 LoC），LLaMA3.1-70B DP2-TP4 32 micro-batch 的 runtime 3,909.5/3,791.5/1,843.8/1,452.9/33,128.5/11,441.7 ms。
  - STAGE 自身性能：32K GPU 生成 540B dense 模型约 28 分钟、Mixtral-8x7B（含 EP）约 50 分钟、128K 设备数小时内且内存<400 MB；对比采集 LLaMA-3.1-70B 128 micro-batch @32 H100 真实 trace 需约 47 GPU-分钟，STAGE 仅 37 CPU-秒。
- 硬件平台是什么，配置是什么。
  - 验证平台：128 个 NVIDIA H100 SXM5（16 服务器×8 GPU，NVLink 组网），每服务器双 Intel Sapphire Rapids CPU（32 核，2.8 GHz）+ DDR5 DRAM；软件栈 NVIDIA NeMo 24.07、CUDA 12.5、PyTorch 2.5.0，CUPTI 采集 kernel/算子级时间线与显存；另用 1×8-H200-HGX 至 8×8-H200-HGX 配置做内存验证（FSDP=8/TP=8/PP=8/TP=32/TP=16/TP4-EP8-PP4/EP8-PP4/EP8/EP8-TP2-DP2）。DSE 目标系统：8×8 2D torus 或 NVLink+IB 的 64 H100、1024 GPU H100（80/40/24 GB HBM）、DGX 节点（8 H100 NVLink，16 节点 pod 本地环 + 全局环）512~16K GPU、144 GPU DeepSeek-R1 集群、Infiniband 100/400 Gbps 等。STAGE 生成性能测试机：Linux 服务器，4×Intel Xeon E7-8880 v4（2.2 GHz）+ 354 GiB DDR3-1333。
- 开源编译框架是什么。修改了什么。
  - STAGE 是论文提出的新开源框架（https://github.com/astra-sim/stage，MIT license，astra-sim 组织，论文 arXiv:2511.10480）。它不改现有编译框架，而是作为 workload 生成器与下游模拟器对接：扩展了 ASTRA-Sim 的 workload feeder（磁盘化 trace 处理与缓存，支撑 512~16K GPU 不爆内存），为 ASTRA-Sim 扩展了 tensor 元数据驱动的内存读写事件与生命周期跟踪以算峰值显存；通过轻量翻译层（<100 LoC）接入 SimAI/ScaleSim/Genie 而不改 workload 语义；默认输出 MLCommons Chakra schema（v0.0.4，含 JSON backend 示例 symbolic_tensor_graph/chakra/backends）。
  - 使用示例（GitHub README）：`git clone git@github.com:astra-sim/stage.git`；`conda install numpy sympy python-graphviz protobuf pandas -c conda-forge`（或 pip install -r requirements.txt，可用 Docker）；运行 `python main.py --output_dir generated/ --output_name workload.%d.et --comm_group_file comm_group.json --dp 8 --tp 4 --pp 4 --sp 1 --weight_sharded 0 --chakra_schema_version v0.0.4`。输入=并行度（--dp/--tp/--pp/--sp/--ep，设备数=DP×TP×PP×SP）+ 模型形状（--dmodel 8192、--dff 28672、--batch、--seq、--head、--kvhead、--dvocal 32000、--num_stacks 80、--experts、--kexperts）+ 选项（--weight_sharded 0/1=FSDP、--activation_recompute、--tpsp、--micro_batch、--mixed_precision、--model_type llama/gpt/moe/debug、--chakra_schema_version v0.0.4/json）。输出=每 rank 一个 .et 文件 + comm_group.json（通信组，描述并行策略）。
  - 作用：把"模型规格 + 并行化策略"编译为带显式依赖、张量尺寸、通信量的执行图，替代真实集群 trace 采集，供 ASTRA-Sim 等模拟器评估 runtime/显存/通信/重叠并做并行策略与硬件 DSE；MoE 专家激活用逐层激活直方图建模（默认均匀分布，可覆盖）、element-wise kernel 默认假设可融合（提供 hook 自定义）、数据默认驻留设备（可逐 tensor 指定 offload）、假设理想内存分配/释放。
