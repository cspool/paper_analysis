## CODO: An Automated Compiler for Comprehensive Dataflow Optimization

- 属于编译框架的实现是什么？实验比较什么？
  - 实现为 CODO：基于 MLIR 的端到端 FPGA 数据流加速器自动生成编译器，输入 C/C++ kernel 或 PyTorch 模型，输出 host code + HLS C++ kernel。前端双通道：(1) Polygeist [28] 把 C/C++ 翻译为 affine dialect；(2) Torch-MLIR [3] 把 PyTorch 模型先降到 linalg（做元素级算子融合与 tensor bufferization）再降到 affine dialect，affine dialect 为后续所有优化的主表示（面向常量循环界的 affine 程序，覆盖卷积、注意力、ReLU/GeLU、矩阵乘、点积等）。核心优化（均为模块化 MLIR pass，每步变换后跑内建 verification + canonicalize/cse）：① 粗粒度 violation 消除——pattern-aware 代码变换（Algorithm 1）：遍历所有 buffer 收集访问节点、analyze_access_pattern 识别违例、按三类访问模式分派变换：single-producer-multi-consumer（残差 bypass 模式，如 ResNet-18/GPT-2）插入中间节点 Node1' 读 a 并写复制缓冲 b/b'；multi-producer-single-consumer（初始化+padding 配对）用 node fusion 融合共享外层迭代域且无 loop-carried 依赖的写循环，内层结构不同则插控制逻辑，先前写的结果暂存并并入最后一次写；multi-producer-multi-consumer 复制 buffer 使每个 buffer 单写单读。② 细粒度 violation 消除——reduction operation rewriting（针对全连接/最大池化/归一化等归约：识别归约维度移入最内层、把写移出归约区、临时数组聚合中间结果，使生产者写数与消费者读数一致，并保证尽早 FIFO 写、just-in-time 传输）+ permutation map generation（选计算强度/迭代数最大的 bottleneck 循环为 reference loop，Step1 建立连接数组维度↔循环深度映射，Step2 对 reference loop 做 tiling size=1 的循环切分对齐深度，Step3 构造深度-深度映射，Step4 按映射置换 target loop 嵌套顺序，统一 producer/consumer 访问顺序）。③ 通信缓冲确定——FIFO-first：无违例处优先 FIFO（延迟低、只存 in-flight 数据省资源），无法消除的细粒度违例处回退 ping-pong。④ violation-free reuse buffer 生成——检测乘加等计算模式识别卷积/矩阵乘等计算密集 kernel，把出现在数组索引中的循环维度分类为 FIFO 维度、其余为归约维度，按归约循环迭代域自动构造 line buffer（lb[n][ci][kh][w]，深度=kh、保留 kh-1 行历史）与 window buffer（wb[n][ci][kh][kw]，新列进入时横向移位更新），同时重写循环保证 FIFO 访问循环维度与数组索引精确对齐；并给出并行化合法性指引：最外层循环不可并行（会展开全部三个内部区域、引入复杂依赖）、中间 FIFO 索引相关循环并行需配套措施、最内层与 FIFO 无关循环可安全并行——用于剪枝后续 DSE 设计空间。⑤ 片外传输管理——codo-transmit 命令自动生成 host code 与 burst 访问操作，把模型权重等参数分布到多个 HBM channel 并行访问独立内存区域，提升 HBM 带宽利用率。⑥ 自动调度——resource-aware bottleneck-centric DSE 三阶段：PA 用 profiling-based 性能模型（基本操作延迟/资源离线 profiling 为模型参数）按循环 trip count 与并行策略估计各循环 latency，按延迟比例分配并行度（最小 1）、保持比例整体放大到用户上限或资源极限，优先 tile 与 FIFO 无关的循环维度，自动插入 pipelining/unrolling/array partitioning pragma；UP 遍历 bottleneck 循环，延迟仍 ≥ 最低延迟 n 倍者把并行度提到 max(⌈n⌉×初始度, 最大度) 并迭代；DP 把比最长循环快 n 倍的过度优化循环并行度除以 n 回收资源（可配置开关），平衡阈值 n=2.0 经验值；inter-task optimization 把 bottleneck 循环的 tiling/unrolling/partitioning 策略传播给 FIFO 对端 producer/consumer 循环，冲突不可解时把该缓冲降级为 ping-pong、保住其余 FIFO 段。优化后的 IR 经扩展 HLS dialect（基于 HIDA [44] 版本扩展，表达 dataflow pragma 与 array partitioning 指令）与专用 FIFO/ping-pong 数据类型/操作，降级为 host code + HLS C++ kernel，并复用 StreamHLS [8] 的自动 testbench 生成管线做功能等价验证。
  - 实验比较：对比 6 个编译器 ScaleHLS [43]、POM [46]、Allo [10]、HIDA [44]、StreamHLS [8]、StreamTensor [42] 与加速器 DFX [17]。(1) Table II kernel 级应用（PolyBench + 常用模型：Atax、Gesummv、Gemm、Mvt、3mm、Residual MLP、Autoencoder、Residual Block、DWSConv. Block、3-Layer Conv. Block、Feed Forward、Multi-Head Attention），统一 DSP 预算 900（约单个 super logic region 的 1/3），latency speedup = Vitis HLS 优化基线周期数/框架优化代码周期数：CODO 几何平均 292.1× vs StreamHLS 200.9×、HIDA 91.8×、Allo 64.7×；DSE 时间 CODO 0.1s–0.5s vs StreamHLS 35s–20min（MINLP 随复杂度指数增长）、HIDA 0.4s–5min32s。(2) Table III/IV DNN：ResNet-18/VGG-16/MobileNet（输入 3*32*32，对比 ScaleHLS/POM/Allo）与 ResNet-18/VGG-16/MobileNet/ZFNet/YOLO（3*224*224，YOLO 3*1280*384，对比 HIDA）：CODO 平均 speedup 33.8×/13.6×/3.7×/7.1× vs ScaleHLS/POM/Allo/HIDA，编译时间 1.0–6.1 s（HIDA 83.1–199.9 s）；BRAM 显著低于 ScaleHLS/HIDA（FIFO vs ping-pong），如 ResNet-18 3*224*224：CODO 4.76M cycles/466.5×/BRAM 13.6% vs HIDA 74.85M/29.7×/46.1%。(3) Table V 上板：只有 CODO 与 HIDA 能对全部模型（除 YOLO——Vitis HLS 资源估计不准无法实现）生成可执行加速器，ScaleHLS 内存超限、Allo 细粒度违例死锁、StreamHLS 无法生成有效设计；CODO overall speedup 9.6×–127.5×、能耗效率平均 77.1× vs baseline、9.2× vs HIDA。(4) GPT-2 Medium：CODO（U280/8GB/300MHz/W4A8）3.54×/2.03× vs 手工优化 DFX（U280/200MHz/FP16）/Allo（U280/250MHz/W4A8），1.23× vs StreamTensor（U55C/16GB/250MHz/W4A8 自动 DSE），[128:128] TTFT 110.40 ms、decoding 231.48 token/s。(5) Fig. 10 消融 Opt1–Opt5（Table VII 配置：细粒度孤立 → 粗粒度+ping-pong → +高效通信 → +细粒度 FIFO → +自动调度）：Opt1 几乎无收益（粗粒度违例使 dataflow 失效退化为串行），Opt2 2.5×–9.7×，Opt3 对高复用模型（ResNet-18/YOLO）line/window buffer 显著提效，Opt4 最高 105.8×，Opt5 靠资源感知并行+inter-task 优化最高（GPT-2 极不均衡数据流只有 Opt5 能解）；Table VIII FIFO 占比 Gesummv/Residual Block/MobileNet/ResNet-18 100%、Multi-Head Attention 84%、GPT-2 89%；Fig. 11 并行度-资源 trade-off（speedup 随并行度近线性、DSP 利用率同步上升）；Fig. 12 上板执行时间分解（HBM 带宽利用充分、数据搬运占比低，GPT-2 长序列计算主导）。
- 硬件平台是什么，配置是什么。
  - 综合：Xilinx Vitis HLS 2023.2 + Vivado 2023.2（论文明确要求 2023.2，更低版本结果不一致），Ubuntu 20.04.6 LTS，全部实验目标频率 300 MHz；latency/资源取自 HLS 综合报告。上板：AMD Alveo U280 FPGA（9024 DSP slice、2.6M FF、1.3M LUT、4032 BRAM18K、8GB HBM），OpenCL host 程序 + xclbin（./host.exe kernel.hw.xclbin）。对照：StreamTensor 用 Alveo U55C（16GB HBM、250 MHz）。
- 开源编译框架是什么。修改了什么。
  - 基座 MLIR [25]；前端复用 Polygeist [28] 与 Torch-MLIR [3]；README 声明部分代码修改/扩展/借自 HIDA、Allo、StreamHLS。CODO 新增：专用 FIFO/ping-pong 数据通信类型与操作、基于 HIDA 版本扩展的 HLS dialect（dataflow pragma、array partitioning 语义）、全部优化 pass（pattern-aware 粗粒度消除、读写协调细粒度消除、缓冲确定、reuse buffer 生成、片外传输管理、三阶段 DSE、inter-task 优化）、codo-opt（单命令全流程，可调最大并行度/tiling factor/平衡阈值 n）、codo-transmit（host code 与 burst 访问生成，可指定 HBM channel 数）；验证复用 StreamHLS 的 testbench 自动生成管线；每 pass 后经 MLIR verification（dominance/SSA/类型）+ canonicalize/cse。
- 开源情况。基于开源文档和论文，使用例子解释编译框架如何使用？作用是什么？至少具体到编译框架输入到输出的全过程。
  - 完全开源（GPL-3.0）：GitHub https://github.com/sjtu-zhao-lab/codo-artifact（论文给定，已联网确认存在，ISCA 2026 Best Paper Award Finalist；含 Docker/experiments/include/lib/samples/third-party/tools、CMakeLists.txt、compail.sh、run_ae.sh）；Zenodo 存档 https://doi.org/10.5281/zenodo.19425920；Docker Hub 镜像 docker pull xzz11/codo_ae_image:v1（启动时挂载本机 Vitis HLS/Vivado 目录）。复现流程：bash ./compail.sh（约 2 分钟）→ ./run_ae.sh 全自动；或分项 cd experiments/ && bash run_all.sh && bash merge_results.sh（结果 all_result.csv）；table-2：run_codo.sh + run_syn.sh + batch_extract_rpt_metrics.py（约 2 小时）；table-3_and_table-4：run_ae.sh + run_hls.sh + batch_extract_rpt_metrics.py（约 512 分钟）；fig-11：run_hls.sh + extract_rpt_metrics.py（约 5 小时）。上板（Table V/VI、Fig. 9）：AE 未执行全部上板实验（所有 bitstream 需两周以上 + 配置好的 U280 环境），提供 GPT-2 的 host/kernel 源码、P&R 报告与预编译 xclbin，可直接 ./host.exe kernel.hw.xclbin。
  - 编译框架输入到输出全过程：输入 = C/C++ kernel（Polygeist→affine dialect）或 PyTorch 模型（Torch-MLIR→linalg 元素级融合/bufferization→affine dialect）→ 粗粒度 pattern-aware 变换（bypass 复制节点 / node fusion / buffer 复制）满足全图 single-producer-single-consumer → 细粒度 reduction rewriting（统一读写计数、尽早 FIFO 写）+ permutation map（统一访问顺序）→ 缓冲确定 FIFO-first / 违例处 ping-pong → reuse buffer 生成（line/window buffer + 循环重构，重跑正确性 pass 防新违例）→ codo-transmit 生成 HBM burst 访问与 host code → 自动调度 PA→UP→DP + inter-task 策略传播/冲突降级 → HLS dialect 降级输出 host code + HLS C++ kernel → Vitis HLS 2023.2 综合（latency/资源报告）或 Vivado 出 xclbin 上板。具体例：ResNet-18 残差连接的 bypass 违例由复制节点消除、Padding→Conv2D 的 (3,34,34)/(34,34,3) 访问顺序违例由 permutation map 对齐、Padding 尾迭代写读计数不一致死锁由 reduction rewriting 消除，全部通过后 FIFO 流式执行，ResNet-18(3*32*32) 综合 latency 1.69M cycles、326.6× speedup（ScaleHLS 104.88M/5.3×、POM 20.33M/27.4×、Allo 8.29M/66.9×），编译仅 1.2 s。
