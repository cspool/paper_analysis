## Graph.hls: A Compiler Framework for Composable Graph Accelerator Design

- 属于编译框架的实现是什么？实验比较什么？
  - 实现为面向 FPGA 图处理加速器的领域专用编译框架（10k+ 行 Rust），核心是把图加速器设计从"跨文件手工 HLS 集成"变成"声明式配置 + 自动生成 + IR 级快速验证"。三大组件：(1) Graph.hls Frontend DSL——流式函数原语（iteration_input / map / filter / reduce / return ... as ...，配 lambda、上下文访问器 self.<prop> / e.src / e.dst / e.<prop>），是 GAS（Gather-Apply-Scatter）模型的超集（GAS 可映射为 map/reduce/filter 特例），可表达 Belief Propagation 这类 GAS 无法表达的不规则数据流（filter 排除目标邻居边后再 reduce）；(2) 层次化设计抽象——按修改成本把图加速器参数分为 L1 图处理常量（顶点属性初值、收敛阈值 ε、活跃顶点过滤阈值，单行修改）、L2 图微架构配置（顶点属性位宽、并行 PE 数、内存总线宽度、片上 buffer 大小，多文件传播）、L3 图数据流策略（pipeline 分组策略、vertex-centric/edge-centric 执行模型、SLR/HBM 通道分配，需整体重设计）；(3) 两个引擎——GH-Architect（自动化硬件生成：DSL→Graph.hls-IR 空间数据流 DAG（5 类节点：iteration_input/map/filter/reduce/return）→ 常数折叠/死代码消除 → L3 启发式选择（基于度分布/平均度估计负载均衡）→ L1/L2 确定性双向依赖传播（Algorithm 1，Analyzer 过滤+选择，如 Parallel Lane Count 过滤不整占内存总线宽度的 lane、按 URAM/HBM 容量选最大吞吐）→ 输出完整可编译 Vitis 工程）与 GH-Scope（IR 级验证：类型检查、循环依赖静态检查（提前发现 pipeline 反馈环）、IR 解释器模拟（保留图语义、运行时 overflow 检测与无限循环检测）、与预验证 golden reference 自动对比架构指标（cross-SLR 连接数、分区大小、SLR 利用率、LUT/FF 占用、FIFO 深度））。
  - 实验比较：(1) Figure 6——vs ReGraph [9] on U55C（HBM 平台，PR/CC/SSSP 全覆盖 14 图，L2/L3 固定为 ReGraph 配置、仅 L1 探索），平均 2.6× speedup；(2) Figure 7——vs ThunderGP [8] on U200（DRAM 平台，PR/Weighted SSSP/CC/ArticleRank/WCC 五算法，同样参数匹配），平均 1.2× speedup，且 ThunderGP 在 5 个大图上 OOM 而 Graph.hls 可运行；(3) Figure 8——SSSP 上 ablation（L1 分区比 / L2 位宽 / L3 pipeline 分组），Naive 0.71×、L1-only 1.99×、L1+L2 2.95×、L1+L3 2.52×、L1+L2+L3 4.48×（super-additive）；(4) Figure 9——GH-Scope IR 模拟器 vs Vitis C-Sim，PR/CC/SSSP 全图平均 301.6× 加速（如 R24+PR：C-Sim 1779s → GH-Scope 8.29s，215×）；(5) Table V——32K 节点/512K 边合成图三种错误场景调试时间：算法失败（6 iter.）HLS 仿真 ~6h → GH-Scope ~0.04s（~455,000×）、流类型不匹配 73m40s → ~0.02s（~186,000×）、参数不匹配 13m13s → ~0.02s（~33,000×）。
- 硬件平台是什么，配置是什么。
  - 目标 FPGA 平台两块：Alveo U55C（HBM 型）——1,304K LUTs、960 URAMs、3 SLRs、460 GB/s、32 HBM 通道、32 端口、115W；Alveo U200（DDR 型）——1,182K LUTs、960 URAMs、3 SLRs、77 GB/s、4 通道、215W。宿主服务器 CPU 为 AMD EPYC 7C13。开发工具链 Xilinx Vitis 2024.1（含 XRT），综合 ~4–6 小时/设计点，FPGA 运行 ~1–10 分钟/图。GH-Scope 模拟与代码生成只需任意 x86-64 Linux（≥16GB RAM，无需 FPGA），Rust toolchain（edition 2024，rustc 1.85+，实测 1.94.1）。编译器 build <5 分钟。
  - 数据集 14 个（Table IV）：graph500-scale23 (4.6M/258.5M, |D|=56)、rmat-19/21/24-32/16 (R-MAT 合成)、amazon-2008、ca-hollywood-2009、dbpedia-link、soc-flickr-und、soc-LiveJournal1、orkut、web-baidu-baike、web-Google、web-hudong、wiki-topcats，来源 SNAP (snap.stanford.edu/data) 与 Network Data Repository (networkrepository.com)。
  - 算法 6 个：PageRank (PR)、SSSP、Weighted SSSP、Closeness Centrality (CC)、ArticleRank (AR)、Weakly Connected Component (WCC)。baseline 按各自支持子集比：ReGraph 支持 PR/CC/SSSP（U55C），ThunderGP 支持 PR/Weighted SSSP/CC/AR/WCC（U200）。
- 开源编译框架是什么。修改了什么。
  - 不是对既有开源编译框架（LLVM/MLIR 等）的修改，而是全新自研领域专用编译框架（Rust，~10k LOC，依赖 chumsky 解析、thiserror、serde、rand、rstest）。它对既有工具链的"消费"是：生成目标为 Xilinx Vitis HLS C++ 工程（交给 Vitis 2024.1 综合），baseline ReGraph / ThunderGP 为独立开源工程（artifact 提供其 benchmark 输出转换脚本）。自研/新增部分：DSL 前端、Graph.hls-IR（空间数据流 DAG）、L1–L3 参数域与依赖 DAG、GH-Architect 生成引擎（依赖传播 + Analyzer + 资源感知代码生成）、GH-Scope IR 模拟/验证引擎。
- 开源情况。基于开源文档和论文，使用例子解释编译框架如何使用？作用是什么？至少具体到编译框架输入到输出的全过程。
  - 开源：https://github.com/pku-lemonade/Graph.hls（MIT 协议，公开仓库），归档 https://doi.org/10.5281/zenodo.19451706。安装：`git clone` 后 `cargo build --release`、`cargo test`。CLI：`--emit-hls <dsl> [dest]`（由 DSL 生成 Vitis HLS 工程）、`--simulate-json <dsl> <graph.json> [max_iters]`（GH-Scope IR 模拟）、`--generate <app> <nodes> <edges> [seed]`（生成随机测试图）、`--convert-graph`、auto-emission 与 grouping-prediction 命令。复现脚本：ae_emit_fig7/8/9.sh、ae_build.sh、ae_run.sh --figure 7/8/9、ae_plot.py --fig7/8/9、ae_fig10.sh（模拟）、ae_tab3.sh（调试时间）。
  - 输入到输出全过程（以 PageRank on Alveo U55C、rmat-21-32 为例）：①用户用 DSL 写算法——Iteration block 内 iteration_input 生成边流 → map(lambda: e.src.rank 等上下文访问器提取属性) → reduce(key, val, commutative-associative lambda) 聚合 → return ... as result_node_prop 终止指定输出目标，外加 Node/Edge 属性 schema 声明与可选 HierarchicalParam/HlsConfig 块（L2/L3 参数可省，缺省由 GH-Architect 推断）；②GH-Architect 解析 DSL → Graph.hls-IR 空间数据流 DAG（每节点对应一段硬件流）；③常数折叠 + 死代码消除；④L3 启发式——U55C 3 个 SLR 容纳 14 个 pipeline slot，据 rmat-21-32 的幂律度分布（平均度 ~30，~5% 顶点吸引 60%+ 边）分组为 11 条 little（稠密分区）+ 3 条 big（稀疏尾部）pipeline；⑤L1/L2 双向依赖传播（Algorithm 1，确定性约束交集至固定点）——forward pass 定硬件可行性：32-bit 下每条 72-bit URAM 行存 2 值，65536 目的节点 /2/8 PEs = 4096 行 = 每 PE 8 URAM，8×8=64 URAM/管道，14×64=896/960（93%）→ L1 max partition size 定为 65536；backward pass 定算法正确性：PageRank 贡献 ~rank/out_deg（out_deg=1000 时 ~10⁻³），16-bit 定点最小 delta 2⁻⁸≈0.004 把贡献舍入为 0 导致假收敛，32-bit delta 2⁻¹⁶≈1.5×10⁻⁵ 足够 → 固定 L2 bitwidth=32；⑥代码生成——发出完整 Vitis 工程（全部 kernel 的 HLS C++、host 代码、Makefile、system.cfg SLR/HBM 绑定），约 100ms；⑦(可选) Vitis 综合 4–6 小时出 bitstream；⑧FPGA 执行 1–10 分钟/图，或 GH-Scope 亚秒~秒级 IR 模拟（R24+PR 8.29s）并对比 golden reference。作用：把"200+ 行跨 10+ 文件的手工位宽重构"降为单行配置自动传播，使来自不同框架（ReGraph/ThunderGP/GraphLily）的优化可经配置组合；切换算法（如 SSSP 整数距离）时 backward pass 自动把位宽放宽到 8-bit（|72/8|=8 值/行），每管道 URAM 降到 16、buffer 深度 4×，全程无需手改代码。
