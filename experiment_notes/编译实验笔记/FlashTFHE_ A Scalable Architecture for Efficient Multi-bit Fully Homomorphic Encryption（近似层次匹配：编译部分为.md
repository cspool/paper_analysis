## FlashTFHE: A Scalable Architecture for Efficient Multi-bit Fully Homomorphic Encryption（近似层次匹配：编译部分为加速器配套编译器，与开源 Concrete 工具链集成，非独立编译框架评估）

- 属于编译框架的实现是什么？实验比较什么？
  - 实现为 FlashTFHE 加速器的配套编译流程（Section V），直接集成于开源 Zama Concrete 工具链，继承其参数选择、量化流程与软件生态。它消费 MLIR 中间表示（Concrete 的 FHELinAlg dialect，带精确类型与参数集），把 batched 操作（matmul、multi-LUT 等）展开为 per-ciphertext primitives，做依赖分析以暴露程序级优化，并输出匹配 FlashTFHE temporal-reuse 执行模型的指令流。核心优化：(1) KS-dedup——把 key-switching 提到 blind rotation 之前（key-switching-first PBS 顺序），当多个 LUT 作用在同一 ciphertext（fanout 结构）时复用 key-switching 结果广播到多个 BRU，最多减少 47.12% key-switching 操作；(2) ACC-dedup——多-bit 程序常对多个 tensor element 应用同一 accumulator，共享 GLWE accumulator 使 GLWE 存储需求减少 91.54%、显著缩小程序体积与 DRAM 容量需求；(3) adaptive batching——编译器按程序实际 ciphertext-level parallelism 动态调整 batch size，并行丰富时 batch 增至 48，并行稀缺时收缩 batch（配合 LPU 的 compile-time lane masking）消除空闲轮次，把回收的 key-switching 带宽重分配给 external product 流水线。
  - 实验比较什么：编译优化本身无独立编译 benchmark，其效果通过消融实验（Fig.20，在同等吞吐与带宽的空间 baseline 上逐步叠加 temporal 设计/异构 FFT/adaptive batching/两级去重，量化 delay、EDP、EDAP 改善）、KS-dedup/ACC-dedup 的统计（key-switching 减少 47.12%、GLWE 存储减少 91.54%）、以及端到端 workload 加速（CNN-20 相对 Morphling 0.34s→0.0139s、CNN-50 1.72s→0.0925s；KNN adaptive batching 延迟 -41.7%）体现。
- 硬件平台是什么，配置是什么。
  - 编译目标是 FlashTFHE 加速器（见硬件架构条目：4 core、BRU+LPU、1GHz/16nm）；编译产物的运行与对比平台为 CPU（AMD EPYC 7R13）与 GPU（双 NVIDIA RTX A5000）。工作负载生成环境：Concrete-ML v1.6.1（commit 8681124）做 PTQ 与模型编译、Concrete Compiler v2.7.0（commit b7793aeb）与 Concrete Optimizer（commit 1da7347）做参数优化与 IR 生成，LLVM 17（commit f5aec278e8df）；Profiling 用 MLIR 与 Concrete Compiler 生成的 IR。
- 开源编译框架是什么。修改了什么。
  - 开源编译框架 = Concrete Compiler（https://github.com/zama-ai/concrete，MLIR 之上的 TFHE 编译器，含 FHELinAlg dialect 与 Concrete Optimizer 参数搜索）、Concrete-ML（https://github.com/zama-ai/concrete-ml，PyTorch/ML 模型到 FHE 的编译器前端）、TFHE-rs（https://github.com/zama-ai/tfhe-rs，Rust TFHE 实现，CPU 测量基线）、MLIR/LLVM 17。修改/新增：FlashTFHE 编译器在 FHELinAlg dialect 之上新增 batch 展开与依赖分析 pass、KS-dedup 与 ACC-dedup 去重 pass、adaptive batching 与 lane masking 决策，以及面向 temporal-reuse 执行模型的指令调度；论文未明确说明是否改动了 Concrete Compiler 本体（其说明为"integrates directly with the Concrete toolchain, inheriting its parameter selection, quantization flow"）。
- 开源情况。基于开源文档和论文，使用例子解释编译框架如何使用？作用是什么？至少具体到编译框架输入到输出的全过程。
  - 开源情况：FlashTFHE 编译器自身未开源（论文无链接，联网未找到仓库）；其依赖的 Concrete/Concrete-ML/MLIR/LLVM/TFHE-rs 全部开源（zama-ai 组织）。以下用法基于论文描述与 Concrete 工具链文档重建。
  - 输入到输出全过程（以 quantized GPT-2 decoder layer，7-bit 量化/6-bit rounding 为例）：输入 = 训练好的 PyTorch GPT-2 模型 → Concrete-ML 做 post-training quantization 并编译为 FHE 兼容图（编译期间用 Concrete Optimizer 搜索满足 128-bit 安全与 p_err≤2^-14 的参数集，产出 Table II 的 n/l_b/N/k 与量化尺度）→ Concrete Compiler 把图 lower 到 MLIR FHELinAlg dialect（每条 TFHE 操作带类型与参数集）→ FlashTFHE 编译器消费该 dialect：把 matmul/multi-LUT 等 batch 操作展开为 per-ciphertext primitives（add、scalar mul、PBS/LUT），做依赖分析（识别可并行 ciphertext 与 fanout），执行 KS-dedup（同一 ciphertext 的多个 LUT 复用一次 key-switching 结果）与 ACC-dedup（跨 tensor element 共享 accumulator）、adaptive batching（按并行度定 batch size、lane masking），最后把指令流调度到 4 core 的 BRU/LPU 与 DRAM BSK/KSK chunk 加载序列（匹配 Fig.11 的 temporal-reuse 伪代码）→ 输出 = 加速器指令流 + 每 batch 的 key-switching/LWE-native/PBS 调度。作用：把高层 ML 模型自动映射为可在 FlashTFHE 上高效执行的指令流，用去重与自适应 batching 提升硬件利用率（大部分 workload 平均 106–6448 个并行 ciphertext、利用率近 100%；KNN 类低并行度 workload 借 adaptive batching 从 32.7% 提到 56.2%）。
