## PIPEWEAVE: Synergizing Analytical and Learning Models for Unified GPU Performance Prediction

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 PIPEWEAVE：一个统一 GPU 性能预测框架（混合解析-学习模型），将 kernel 的运行耗时预测拆成四模块流水线：(1) Kernel Decomposer 把 kernel 拆成基本任务 task（硬件调度范式下 task=CTA/thread block；persistent kernel 范式下 task=resident CTA 从全局 work queue 取的 tile）；(2) Scheduling Simulator 模拟 task 到 SM 的映射，得到 task distribution——支持硬件调度器（GigaThread Engine，推断为 round-robin，逐轮填满 SM 直到资源饱和再按任务完成替换）与软件调度器（persistent kernel 的 tile scheduler，如 FlashInfer FA3 的 MinHeap 调度逻辑）；(3) Feature Analyzer 把 task distribution 聚合成多级特征：Math pipeline（Tensor/FMA/XU）每任务 ops 数 N_ops=α·tile_M·tile_N·tile_K（GEMM α=2，FlashAttention 两次 MMA α=4），理论周期 C_p=N_ops/Th_p，以及 MIO pipeline 的字节需求与 C_mem=B/BW_mem，按 task→SM→GPU 三级聚合（含 Max SM 特征捕捉负载不均）；(4) Performance Estimator 用一个 3 隐层 MLP（256/128/64，ReLU+BN+Dropout 0.1+Sigmoid 输出）以执行效率（理论时间/实测延迟）为训练目标（MAPE loss，AdamW），最终延迟=理论时间/预测效率。此外用 Quantile Regression（P80 分位损失）训练同一特征集的模型预测"潜在性能上限"，用于诊断与优化指导。
  - 实验比较 4 个主 baseline：Roofline、Linear regression（用 Feature Analyzer 的 compute/memory 理论周期特征）、Habitat（黑盒，喂相同 task 定义）、Neusight（SOTA 数据驱动，喂相同 task 定义）；外加 2 个细节建模 baseline：AMALI（指令 trace 解析模型）与 LLMCompass（解析+cycle-accurate systolic array，限于 standalone GEMM）。指标：kernel 级 MAPE、E2E 推理 MAPE、模拟开销 vs 预测误差。效果：kernel 级 seen GPU 平均 MAPE 6.1%（unseen 11.4%），比 Neusight 误差降 6.7×；E2E seen 8.5%/unseen 10.7%，比 Neusight 降 4.4×；相比 AMALI/LLMCompass 预测时间降低 3~7 个数量级且 MAPE 6.4% vs 28.3%/29.7%。"Beyond Simulation" 用 P80 模型诊断 Fused MoE Triton kernel，autotune 三个参数后 A40/L20/A100/H800 分别 1.61×/1.12×/1.06×/1.03× 加速（underperforming points 数与加速比 Pearson 相关 0.86）。
- 后端平台是什么，配置是什么。
  - 评估横跨 4 代 NVIDIA 架构 11 种 GPU：Ampere（A40、A100、RTX A6000）、Ada（RTX 6000 Ada、L20、L40）、Hopper（H20、H800、H100、H200）、Blackwell（RTX PRO 6000 S）；6 个用于训练（seen），5 个仅测试（unseen，评估泛化性）。硬件规格（输入 S）包括：Compute Capability 8.0–12.0、SM 数 78–188、SM 时钟 1410–2520 MHz、Tensor Pipe 吞吐 512–4096 ops/cycle/SM、FMA 64–128、XU 16、Global Mem BW 696–4916 GB/s、L2 BW 2430–10400 GB/s、SMEM BW 128 Byte/cycle、SMEM 100–228 KB、寄存器 256 KB。软件环境：PyTorch 2.8.0、CUDA Toolkit 12.8、FlashInfer 0.4.1、SGLang 0.5.4、vLLM 0.11.0、Triton 3.4.0。E2E 测试模型：Qwen2.5-14B、Qwen3-32B、Llama3.1-70B，TP=1/2/4/8、TP=4&PP=2，数据集 Arxiv Summarization（avg input 2630 tokens）与 Splitwise（avg 982 tokens），batch 变体如 arxiv_8/splitwise_64。
- 评估性能的软件/脚本是什么。修改了什么。
  - 数据集构建：用 PyTorch Profiler 在物理 GPU 上实测 kernel 延迟（5 次 warmup+10 次取平均）作为 ground-truth，覆盖 6 类 kernel：Attention（FA2/FA3，FlashInfer，104,958 样本）、cuBLAS GEMM（613,263）、RMSNorm（65,036）、SiLU&Mul（104,834）、Scaled MM（vLLM FP8，25,228）、Fused MoE（SGLang Triton，33,264，仅作优化 case study）。解析组件用 NVIDIA Nsight Compute (NCU) 在 A100/H100 上验证 op count（最大误差 total 0.5%/per-SM 6.3%）。E2E 用 Workload Generator 依据 SGLang/vLLM 的 kernel 调用逻辑生成 kernel 序列，假定串行无重叠，逐个用 PIPEWEAVE 预测后求和；分布式通信 kernel（All-Reduce、Send/Recv）用 Random Forest 回归预建性能库建模。对 cuBLAS 闭源 kernel 用 PyTorch Profiler 反推 task 切分逻辑（surrogate 映射函数），unseen GPU 上借用架构最相近 GPU 的切分逻辑。
  - 修改了什么：无既有开源 Serving 框架被修改；PIPEWEAVE 是独立框架，Kernel Decomposer 对开源库（FlashInfer、SGLang、vLLM）直接读源码提取并行化/thread block 映射逻辑，Scheduling Simulator 复刻 RR 策略与 FA3 MinHeap tile 调度（约 40 行），各 kernel 的 Decomposer 仅 10–50 行。
  - 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源：https://github.com/zksainx/pipeweave （Apache-2.0），即本文 ISCA 2026 artifact。依赖仅 `pip install torch numpy pandas scikit-learn joblib`。目录结构：analytical_model/（各算子与架构的 roofline 计算器 pipes.py，含 SM80/SM90/FP8 GEMM、FA2/FA3、RMSNorm、SiLU×Mul、Triton MoE）、hardware/（GPU 规格 JSON）、config/（模型配置）、dataset/（profiled 算子 CSV）、mlp_models/ 与 mlp_models_quantile/（训练好的 MLP checkpoint）、workload/（JSON 规格+trace CSV）、e2e/（预测与对比输出）。根脚本：aggregator.py（E2E 预测主入口）、mlp_model.py（MLP 架构）、workload_generator.py、train_mlp.py、train_mlp_quantile.py（P80 分位）、train_collective_rf.py（通信 kernel）、compare_pred_real.py、compare_vllm_pred_real.py、tp1.sh–tp8.sh、vllm_tp4_pp2.sh。
  - 使用例子（评估原理与 kernel 输入→性能输出全过程）：① 训练：用 PyTorch Profiler 对某 kernel（如 cuBLAS GEMM BF16）在不同 (M,N,K) 与多 GPU 上实测延迟，连同硬件规格写入 dataset/ 与 hardware/，跑 `python3 train_mlp.py` 按 kernel 类型训练各 MLP（输入为解析特征向量：Math 的 GPU/SM 级 Total/Max ops 与理论周期 + MIO 的 Global/L2/SMEM 字节需求与理论周期，输出为 0–1 执行效率）；② 预测单算子：对给定输入，Kernel Decomposer 先解析出 task 集合（开源源码直接推导，cuBLAS 用反推的 surrogate 映射），Scheduling Simulator 按 RR 或软件 tile 调度把 task 分到各 SM 得到 task distribution，Feature Analyzer 用 hardware/ 里的 GPU 规格把分布算成特征向量，MLP 前向得到效率，最终延迟=解析理论时间/效率；③ E2E：`python3 workload_generator.py` 按模型配置与 batch 生成 kernel 调用序列（JSON），`python3 aggregator.py --workload workload/Qwen2.5-14B_arxiv_8_fa3_tp1_pp1.json --hardware H100 --model_dir mlp_models --dataset_dir dataset --hardware_dir hardware --output e2e/pipeweave_pred/result.json` 逐个 kernel 预测并求和输出 E2E 延迟，`compare_pred_real.py`/`compare_vllm_pred_real.py` 与 Roofline/Habitat/Neusight/vLLM 实测对比出 MAPE CSV；④ 优化指导：`train_mlp_quantile.py` 训练 P80 模型预测性能上限，对 Fused MoE Triton kernel 算 perf_gap=ŷ_p80−y_actual，gap>0.1 记为 underperforming point，再 brute-force autotune BLOCK_SIZE/num_stages/num_warps 三参数验证提速。
