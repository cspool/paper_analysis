## MTIA 300: Meta's First Training Chip Featuring Built-in NICs and Collective Offloading Engines

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 属于kernel调度/运行时计算的实现（MTIA 300 自研后端上的 kernel 与运行时评估，ISCA 2026）：(1) **table-batched embedding (TBE) kernel**——DLRM 稀疏部分核心算子（表批式 embedding，AutoShard [36] 式），MTIA 300 通过高内存/cache 带宽 + 专用功能单元（dedicated embedding caches、硬件索引 DMA scatter/gather、radix-sort 加速 embedding 反向的稀疏索引排序）加速；评估各种 shape 与生产输入分布：前向 2.0×/1.6×、反向 2.1×/1.6×（几何均值 vs H100/H200）；注意 embedding 性能不随 HBM 带宽线性扩展（skewed 输入使算子 cache-bound/instruction-bound 而非带宽-bound，故未达 2.5×）。(2) **BF16 加法内存带宽 kernel**——5.57 TB/s（91% 峰值）vs H100 2.26 TB/s（94%）、H200 4.40 TB/s（92%）；细粒度 kernel 每 kernel 延迟更高（Section VI）。(3) **BF16-GEMM kernel**——小内存-bound GEMM 靠高带宽占优，大矩阵受峰值 FLOPS 限制（算术强度 >400 bytes/FLOPS 时 59% roofline 效率 vs H100 63%/H200 54%，GEMM 库仍需优化）。(4) **collective 运行时（HCCL）**——AllGather/AllReduce/AllToAll 在 16-128 加速器、多种消息大小的归一化延迟，整体通信性能超 H100 3.9×（大消息/多卡靠 2.2× scale-up 带宽 + 16 节点域）；小消息 NCCL 更强（未优化，占比小）。(5) **计算-通信重叠微基准**——1000 次 TF32 4K×4K×4K GEMM 与代表消息大小 collective 并发（16 加速器），MTIA 300 双 ~100% 效率、H100 因 SM 争用明显退化。(6) **生产 DLRM 训练**——150B 参数（99% 稀疏）、40 加速器、local batch 6144、分布式 Shampoo 优化器：AllReduce 入站 1.6 GB、AllGather 2.1 GB、35 次 AllToAllv（1 KB-1 GB 可变消息）——大消息 AllToAll/AllReduce 上 MTIA 300 显著领先 H100。
  - 后端平台：MTIA 300 自研芯片（72 PE 网格 + 16 ME + NMC），对比 NVIDIA H100/H200。kernel 在 PE 内执行——DPE（GEMM）、SFU SIMD（量化/非线性/min/max/clamp/stochastic rounding/radix sort）、RE（跨 PE 归约网络）、MLU（layout 变换）、Fabric Interface（字节对齐切片 DMA + 索引 DMA）；collective 在 16 ME 的 NMC（128 B/cycle 归约、2.8 TB/s）执行。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：PyTorch 栈（TorchRec 实现的 DLRM 模型 + TorchInductor 全图编译）+ 自研 HCCL 集体通信库（经 PyTorch Distributed 与 torchcomms 接口暴露，RDMA verbs 控制路径）+ 微基准（embedding 形状/分布扫描、BF16 加法、BF16-GEMM vs roofline、collective 延迟扫描、重叠测试 1000 GEMM + collectives）。对比侧：H100/H200 上同一 TorchRec+TorchInductor 模型、NCCL。修改了什么（MTIA 300 侧三项 co-design）：(1) 把 Shampoo 优化器的矩阵特征分解从加速器 offload 到 host CPU（1:1 host:加速器比支撑；H100 用 cuSOLVER 片上算，1:8 比例下会损失 7.8%）；(2) 关闭 row-wise FP8 量化通信（H100 优化模型默认开启以减数据量；MTIA 300 上该过程走低效 RISC-V，关闭后利用高网络带宽 +4.4%）；(3) 增大 local batch size 至 10240（24 加速器，利用大 HBM 降低 trainer 数、提升 kernel 粒度、减少通信开销，Perf/TCO +2% vs 6144 baseline）。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源情况：HCCL 与 MTIA 300 kernel/微基准未开源（Meta 专有；HCCL 配套论文 arXiv:2608.00358 亦无代码）；软件侧组件开源：PyTorch + TorchInductor（https://github.com/pytorch/pytorch）、TorchRec（https://github.com/pytorch/torchrec）、FSDP2/DTensor、vLLM（https://github.com/vllm-project/vllm）、InferenceMax 开源 benchmark（[5] https://newsletter.semianalysis.com/p/inferencemax-open-source-inference）、torchcomms（https://pytorch.org/blog/torchcomms/）、DeepSeek-R1（https://arxiv.org/abs/2501.12948）、分布式 Shampoo（https://arxiv.org/abs/2309.06497）。复现 MTIA 300 侧需内部硬件；H100/H200 对照可用开源组件重建。
  - 评估原理与 kernel 输入→性能输出全过程（以一次 DLRM 训练迭代的 AllReduce 为例，40 加速器）：输入 = TorchRec DLRM 模型（150B 参数）、local batch 6144、AllReduce 入站 1.6 GB 梯度张量 + 35 次 AllToAllv（稀疏特征、消息 1 KB-1 GB）。执行：TorchRec 构建模型 → TorchDynamo 抓前向 + AOTAutograd 生成反向 → TorchInductor 编译为单一大图（compute+collective 合一、semaphore 管依赖）→ 工作包经 CPU-C 派发：compute 子图到 72 PE（DPE GEMM、SFU SIMD/radix-sort embedding 反向、MLU layout、FI 索引 DMA scatter/gather）、communication 子图到 16 ME → HCCL 按 outstanding work/拓扑/消息大小先验选算法（ring/recursive doubling/ordered tree）并翻译为 WQE（SEND/RECV/WRITE/WAIT/SET/REDUCE + wqe_sync/fence/rx_sync/sync 流控）→ ME NIC interface 单 FIFO 分发 12 NIC express doorbell → RoCE 网络传输 → NMC 在 HBM 旁 128 B/cycle 归约（ReduceScatter 累加、AllGather 转储）→ 完成回调 CPU-C 解阻塞。输出：collective 归一化延迟（相对 H100 加速比，整体 3.9×）、通信时间占比、端到端迭代时间与 Perf/TCO（1.42× vs H100；Table IV）。
