## Accelerating MoE with Dynamic In-Switch Computing on Multi-GPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 DySHARP 的 token-centric kernel fusion：把 MoE 层 Dispatch→GEMM-1→GEMM-2→Combine 四算子重组为 token-paced pipeline，用 megakernel + persistent thread blocks（TB）绕过硬件 TB 调度器（借鉴 Rammer rTasks），"向 SM 发射 TB"被模拟为"持久 TB 从任务列表取任务"。SM 划分为 4 组，分别专职 Dispatch / GEMM-1 / GEMM-2 / Combine（GEMM-1/GEMM-2 无就绪 TB 时可共享 SM）。Token tracker 以 token/tile 粒度检测 readiness 边界：TS Table（Tile Status Table，1024 项，DAcc 计数 dymultimem.st 到达以判 Dispatch⇒GEMM-1 就绪、TBCnt1/TBCnt2 计 TB 完成）、TID Table（DRAM）+ OR Table（Output Readiness Table，1024 项，nReady==topk 判 GEMM-2⇒Combine 就绪）。readiness-gated 调度：GEMM-1/GEMM-2 的 TB 行仅当 tracker 标记 ready 且目标 SM 组有空位时发射；Combine 通信 kernel 轮询 OR 表 nReady 后才对 token 发射 dymultimem.ld_reduce。同步 tile 尺寸 128（与 GEMM tile 匹配）。
  - 实验比较 7 个 baseline（DeepEP、NVLS、FasterMoE、Tutel、CCFuser、COMET、DualPipe）+ 3 个消融变体（DySHARP-Basic = 仅 dynamic multimem addressing 无重叠；DySHARP-COMET = DySHARP-Basic + COMET 式重叠；kernel fusion only = 仅 token-centric fusion 无 dynamic multimem addressing）。指标：端到端训练 speedup、MoE 层（Dispatch-Computation-Combine）speedup、流量体积、payload 效率、纯通信性能（vs ideal）、带宽利用率、时间分解；敏感性：GPU 数 4-64、序列长度 1024-16384、token 分布（训练正态 std 0.01-0.05 / 推理 power-law α 0.5-2.5）、tile 尺寸。
- 后端平台是什么，配置是什么。
  - 模拟 NVIDIA GH200 NVL32：32 GPU 经 9 个 NVSwitch 全连接 fat-tree 互连，每 GPU 按 H200 规格配置；NVLink 按 NVLink 4.0 真实器件参数建模：双向带宽 900 GB/s、单跳 250ns、往返 1µs、flit 16B；NVSwitch 每输入端口 16 个 256 深 VC（8 请求 + 8 响应）、端口 reduction buffer 64KB。多节点扩展评估：4/8×DGX-H100 与 2/4×NVL32 + InfiniBand（Quantum Switch），16-way pipeline parallelism；另评估 64-GPU 节点（18 NVSwitch、每 switch 64 端口）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：Accel-Sim（GPU 微架构模拟器，https://github.com/accel-sim/accel-sim）+ BookSim2（cycle-accurate NoC 模拟器，https://github.com/booksim/booksim2）集成做逐周期多 GPU 仿真。修改：在支持基础 Hopper 特性的最新版 Accel-Sim 上扩展高性能 FP8 GEMM kernel 建模、多 GPU 并发执行与 switch-based 网络互联；BookSim2 建模 NVLink 4.0/NVSwitch；实现 dymultimem 指令、token tracker 与 megakernel 调度器。校准：对照 DGX-H100 实测，GEMM 与 DeepEP 通信算子在多种 shape/volume 下平均误差 <6%。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - DySHARP 自身代码未见公开仓库（论文未给出开源链接，arXiv: 2605.05607；联网搜索未找到官方 repo）。Accel-Sim 与 BookSim2 均开源（链接见上，论文参考文献 [16][18]）。
  - 评估原理与全过程：输入 = MoE 模型配置（DeepSeek-V3 官方 Large-8 + Small/Medium 扩展，topk∈{8,16,32}；GPT-OSS-120B、Qwen3-235B）+ token 分布（训练按正态 std=0.032、推理按 power-law α≈1.5）+ kernel 指令流（Dispatch/GEMM-1/GEMM-2/Combine 及 megakernel 调度版本）。Accel-Sim 逐周期执行 GPU 侧指令流：dymultimem.st / dymultimem.ld_reduce 经 LSU 取 target list 后生成请求包 → BookSim2 模拟 NVLink/NVSwitch 逐周期转发/多播/归约 → 响应写回 GPU 内存；token tracker 表随数据到达/TB 完成事件更新，megakernel 内持久 TB 轮询 readiness 位并按 SM 分组发射任务。输出 = 每层/端到端执行周期数 → speedup（vs DeepEP 端到端最高 2.31×、vs NVLS 5.12×、vs FasterMoE 2.11×、vs Tutel 1.98×、vs CCFuser 1.85×、vs COMET 1.79×、vs DualPipe 1.88×；几何平均 1.93×/3.38×/1.84×/1.72×/1.63×/1.59×/1.66×）、流量体积（vs DeepEP -50%）、纯通信性能（>90% ideal）、带宽利用率与消融时间分解。
