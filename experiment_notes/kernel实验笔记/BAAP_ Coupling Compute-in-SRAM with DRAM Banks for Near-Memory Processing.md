## BAAP: Coupling Compute-in-SRAM with DRAM Banks for Near-Memory Processing

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现 = 在银行级 PIM 后端（UPMEM 改）新增 AP 运行时算子与"访存-计算重叠"调度：(1) 位并行/位串行 SIMD 算子——ap_and/or/xor（3/3/4 周期）、ap_add/ap_sub（8n+2）、ap_mul（4n²+4n）、ap_redsum（n）、ap_eq（n+4）、ap_merge（谓词合并，4），由 ASU 展开为 CAM 搜索/更新微码序列，在位切片布局的 32x36 子阵列链上对整列元素同时执行；(2) DirectAP 算子——ap_search/ap_searchacc/ap_update/ap_set_tags（1–2 周期）直接暴露 CAM 语义，伪指令 ap_regex 对长度 m 文本穷举匹配长度 k 模式（<m−k 周期、支持通配符）；(3) VPU 重叠调度——AP 计算当前向量时非投机预发射下一向量 load/store 到 DMA 引擎（命中五级流水线访存级，附加一个向量大小缓冲），把位串行长延迟算术与 bank 级 DMA 传输重叠；(4) 运行时布局管理——baap_set_mode(mode, m) 执行 drain-flip-reload 在 scratchpad（字节寻址）/SIMD（位切片）/DirectAP（列连续）三布局间切换（纯 DPU 侧 DMA strided 访问实现，无新增硬件；最坏 2×6 KiB÷72.58 MB/s ≈ 0.171 ms，约 6×10⁴ 周期后摊平）。实验比较：VPU 开/关消融（GPT-2 Large prefill GEMM vs decode GEMV，周期三分类 Overlap/Idle/Compute-only）、UPMEM 标量 DPU、主机侧 AP（PUMICE [52]）、PrIM/Phoenix/基因组负载；指标 = 加速比、带宽饱和。
- 后端平台是什么，配置是什么。
  - 银行级 PIM：DDR4-2400 8 GB DIMM（128 DPU，每 bank 1 GB/s、聚合 128 GB/s）；每 DPU = 500 MHz in-order CPU + 64 KB WRAM（25–88% 重配置为 AP，VL=96/224/320/384）+ 64 MB DRAM bank；AP 逻辑 350 MHz。主机侧 AP 基线：2.72 GHz、VL=49,152、4× 4H HBM（128 伪通道、256 GB/s）；主机 CPU：Xeon W-1390P（3.5 GHz、AVX-512）。系统建模 gem5 + uPIMulator。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：uPIMulator（https://github.com/VIA-Research/uPIMulator）跑 UPMEM 基线与设计空间探索；gem5（https://github.com/gem5/gem5）按表 IV 指令周期数评估 BAAP AP 前端。benchmark：PrIM（https://github.com/CMU-SAFARI/prim-benchmarks，16 个内核、取每 benchmark 在 UPMEM 上最佳变体、12/16 可可靠运行）；Phoenix MapReduce（https://github.com/kozyraki/phoenix，linear_regression/histogram/kmeans/reverse_index/wrdcnt/strmatch）；GPT-2 Large（prefill/decode 两阶段）；SPAdes（https://github.com/ablab/spades）作基因组多核 CPU 参考实现。修改：论文在 gem5 内实现 BAAP ISA 的周期模型、VPU 预取与布局切换逻辑；uPIMulator 用于 UPMEM 基线评估（未说明修改其内部）。BAAP 自身模拟代码论文未提供开源链接（无法确认）。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 评估原理：uPIMulator 把 UPMEM kernel 编译为 ISA 后逐周期模拟流水线/MRAM/WRAM/DMA；gem5 对 BAAP 指令按表 IV 的 AP 周期数执行、内存后端按 UPMEM 实测时序。全过程（GPT-2 Large decode GEMV，VL=96）：权重驻留 DRAM bank → 发 DMA 载入当前 token 的激活向量 → ap_mul 展开 4n²+4n 次 CAM 搜索/更新做位串行乘 → VPU 预发射下一 token 向量 load 与 DMA 重叠 → 执行周期按"AP 忙且 bank 忙（Overlap）/等内存（Idle）/仅计算（Compute-only）"三分类 → 输出周期。结果：prefill（GEMM、计算受限）关 VPU 仅损失 5.9–7.9%；decode（GEMV、访存受限）关 VPU 损失 39.0%（VL=96）→ 20.9%（VL=384），VPU 把约 1/4 decode 执行时间从内存停顿转为有效计算。PrIM：SEL/SCAN/REDSUM 靠流式比较/归约饱和带宽，GEMV/TS/MLP 靠位串行乘并行化 + VPU 重叠，VA 加速有限（UPMEM 已单周期加法）；Phoenix：内存密集的 reverse_index 对主机侧 AP 超 10×、strmatch 对 OoO CPU 近 3 个数量级，计算密集的 linear_regression/histogram/kmeans 因 350 MHz 低频率而下降；基因组 k-mer 计数对 UPMEM 2–38×（k>21 回退主机），de Bruijn 图遍历 1.1–2.8×。
