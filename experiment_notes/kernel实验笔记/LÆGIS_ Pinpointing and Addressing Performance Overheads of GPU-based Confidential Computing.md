## LÆGIS: Pinpointing and Addressing Performance Overheads of GPU-based Confidential Computing

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是硬件架构设计——HBM 内 IV Bank（见实验_硬件架构条目），此处从"CPU 侧加密计算在 UVM driver 空闲窗口的运行时调度/卸载"角度记录）实现为 UVM fault-service 路径上的预加密调度器：在 GPU CC 的 UVM batch 处理期间，把 AES-GCM 加密这一运行时计算从关键路径卸载到 driver 线程的空闲时段执行。关键运行时行为：(i) 识别两类空闲——true idle（两个 fault batch 之间 driver 线程睡眠期，平均占 driver 执行时间 87%）与 false idle（batch 内 fault preparation 阶段 AES 指令未执行的时段）；(ii) 调度器按候选选择策略从 fault buffer 下一批条目 / CPU 驻留页 / 随机页中选页，用 CPU 侧 IV Bank 重建 IV 后乱序预加密；预加密密文直接提交（无 PipeLLM 式预测 IV 的误预测 NOP/丢弃问题）；(iii) 预加密完成的页到达时直接标记 ready、跳过关键路径加密，且批量提交提升 PCIe 突发利用率。变体按"空闲类型 × 候选策略"组合：F-LÆGIS（false idle + fault buffer 候选）、IR-LÆGIS（true idle + 随机候选）、IN-LÆGIS（true idle + fault buffer 候选）、IFN-LÆGIS（false+true idle，先 fault buffer 后顺序页）。每个变体都评估默认（Pt=51%）与 aggressive（Pt=1%）预取版本。
  - 实验比较：各变体 vs Baseline（同步加密关键路径）vs Ideal（加密开销隐藏）：F-LÆGIS 1.51×、pF-LÆGIS 1.37×、IR-LÆGIS 1.38×、pIR-LÆGIS 1.62×、IN-LÆGIS 2.17×、pIN-LÆGIS 2.10×、IFN-LÆGIS 2.22×（最大 3.13×）、pIFN-LÆGIS 2.74×（最大 5.05×）；pIFN-LÆGIS 把 driver active 占比提升到 88.3%（SSSP 99.4%、FLASHATT 96.8%）。另对照 CPU 侧加密能力增强：MT-Baseline（多线程约 7 GB/s，默认预取下平均 -35%，多线程需大数据量且无法解决同步瓶颈）、X-Baseline（CPU 硬件 AES，1.19×/1.58×）、X-IFN-LÆGIS（2.13× 默认 / X-pIFN 3.57×）——证明单靠"利用空闲窗口的机会性预加密"即可接近 Ideal，无需换更快加密硬件。
- 后端平台是什么，配置是什么。
  - CPU 端：5th Gen Intel Xeon 6530 Gold @2.1GHz（32 核）作为 TDX 信任域宿主（TDX 1.5 + QEMU 7.2.0 TDX patched）。UVM 加密路径为 kernel-space：nvidia-uvm 模块的 Cryptography Services Library（CSL）→ libspdm → Linux Kernel Crypto API（LCA）的 crypto_aead_encrypt，经单 kernel 线程的工作队列串行执行（实测约 1.3 GB/s，即 2.98 µs/4KB 页；TME-MK AES-XTS 硬件仅 40 cycle 开销，瓶颈在软件加密路径）。GPU 端：NVIDIA H100（PCIe 5.0、CUDA 12.4、Driver 550.163.01），CE/GSP/SEC2 集成硬件 AES 引擎。运行时调度行为在 GPGPU-Sim + UVMSmart 中建模（80 SM、64 warps/SM、8 GB HBM2、Bf=128、driver 线程切换 2 µs）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：GPGPU-Sim v4.2（commit 84c6cf4）+ UVMSmart UVM 支持（共享 GMMU、batch 处理）作为仿真评估平台；真实硬件 profile 采集用 instrumented NVIDIA Open GPU Kernel Modules（nvidia-550.163.01 树，HOWTO.txt 指南）、bpftrace（追踪 CSL 与 libspdm/kernel AEAD 交互确认 LCA 加密路径）、OpenSSL v3.0.2（用户态 AES 对照吞吐，Fig.15）。修改了什么：论文在 nvidia-uvm 驱动故障服务链上识别加密路径并采集 profile（fault prep 时间、idle 窗口、加密吞吐，随 Pt/Bf 变化）；在 GPGPU-Sim 中新增预加密调度器模型（idle 窗口选页 + 乱序加密提交）、CPU 加密吞吐注入、GPU 流水 AES 引擎与 IV Bank/IV cache 建模；实现 F/IR/IN/IFN 四种候选策略与默认/aggressive 预取组合。
  - 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源情况：https://github.com/insight-cal-uva/laegis-isca26-artifact —— nvidia-550.163.01（instrumented driver，按 HOWTO.txt 复现 Fig.3/4/Listing 1/Fig.15）、gpgpu-sim-uvm（复现 Fig.8/12/13/14/16）、benchmark（应用）。LÆGIS 预加密调度器实现细节公开 artifact 未包含，需联系作者；NVIDIA Open GPU Kernel Modules（https://github.com/NVIDIA/open-gpu-kernel-modules，kernel-open/nvidia-uvm 与 libspdm_aead.c）为上游参考。
  - 评估原理与 kernel 输入→性能输出全过程：输入 = UVM 应用 kernel（如 GEMM/2DCONV/SSSP，经 cudaMallocManaged 分配）+ 加密方案配置（Baseline/F/IR/IN/IFN × Pt 51%/1%）+ 物理 profile。原理：仿真器按 cycle 推进——GPU 访存缺页 → GMMU 聚合 fault buffer → CPU driver ISR 取批 → fault preparation（profile 时间）→ driver 线程服务批次：Baseline 对每页 4 KB 同步 AES-GCM（LCA 1.3 GB/s）+ IV 同步 → PCIe DMA → GPU CE 解密；LÆGIS 运行时调度器在 true/false idle 用 AES 辅助线程预加密候选页（IV 从 CPU IV Bank 按 ID 重建），预加密页到达直接 ready 并批量写 bounce buffer → DMA 时附带 128-bit（MAC||ID）→ GPU 用 ID 从 HBM IV Bank 取 IBE 解密 → 统计各组件周期（kernel 执行、batch 处理、PCIe 传输、CPU 加密、GPU 解密、IV 访问）→ 输出 speedup、driver active/idle 占比、加密吞吐敏感性（Fig.15 AES 实现对比）。作用：量化"加密计算卸载到空闲窗口"这一运行时调度对 CC UVM 关键路径的收益，证明无需更快的加密硬件、单靠机会性预加密即可逼近 Ideal（差距 5.8%）。
