## DCC: Data-Centric Compilation of Machine Learning Kernels for Processing-In-Memory Architectures

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现为 DCC 编译器对 PIM 后端上 memory-intensive kernel 的自动"数据分区 × 计算循环划分"联合调度：对每个 kernel 枚举 data-tile（张量维在 PIM group/core 上的分配）与 compute-tile（loop 变量范围映射）tiling drafts，经剪枝（等价映射去重/SIMD 对齐/执行性能等价）+ XGBoost 耦合预测器选出端到端最优 draft，生成 group 级广播/bank 级并行的 DRAM 计算命令调度；同时调度输入/输出数据重排（GPU shared memory staging：串行 Host 读 + 并行 N channel PIM 写，两侧均获 channel 级并行）。评测 7 个 kernel：AttAcc 上 GEMV、RED（reduction）、ATTN（GEMV/ATTN 输入尺寸 128，LLM 最常见每头维度）；HBM-PIM 上 GEMV、RED、VA（向量加）、RELU（ATTN 需 softmax 单元只有 AttAcc 有；AttAcc 无支持 VA/RELU 的 near-bank 计算单元）；精度 FP16（MT-NLG 另测 FP8）。端到端：GPT3-13B、LLaMA2-33B、MT-NLG-310B 推理。
  - 实验比较：(1) GPU-only；(2) AttAcc 默认实现（固定分布：batch/head→16 pCH、第一维→每 pCH 16 bank group、第二维→每 bank group 4 bank）；(3) AttAcc+DCC；(4) HBM-PIM 默认（沿用 AttAcc 数据分布）；(5) HBM-PIM+DCC；§2.2 另比 TVM compute-centric（T）与手工最优（B）。
  - 关键结果：AttAcc 上 DCC 相对 AttAcc 平均提速 1.26× GEMV、1.48× RED、1.23× ATTN（峰值 1.73×/1.66×/1.57×），整体相对 GPU 至多 13.17×（平均 3.92×）；RED batch 1、tensor 4096 达 3.94×；RED 1024 AttAcc 落后 GPU 0.59×、DCC 追平 GPU。HBM-PIM 上 DCC 相对 HBM-PIM 平均提速 1.53×/2.09×/1.64×/1.54×（GEMV/RED/VA/RELU），整体相对 GPU 至多 7.68×（平均 2.21×）；RED 1024/2048 HBM-PIM 落后 GPU 0.48×（固定 tiling 不满足 16-way SIMD 对齐）、DCC 平均提速 2.26× 使 2048 反超 GPU。GEMV batch 1→8：DCC 增益 HBM-PIM 1.33×→1.58×、AttAcc 1.14×→1.31×（head 32、输入 128）。§5.4 时间拆解：DCC 同时优化计算（1.58×）与数据重排（1.65×）；VA/RED/RELU 等重排主导 kernel 提速 1.67×、compute-heavy GEMV/ATTN 1.18×。LLM 推理：AttAcc_Full+DCC 平均 4.52× 对 GPU（LLaMA-2 峰值 7.71×）、1.75× 对 AttAcc_Full；QKV 生成 2.58×、projection 2.91× 对 GPU（AttAcc 固定 tiling 在这两层落后 GPU 1.25×，DCC 使它们移上 PIM）；MT-NLG-310B 大 batch（≤64）/8×A100 下 DCC 较 AttAcc Base/Full 1.59×/1.67×；能耗效率平均 1.24×。在线动态预测：未见过 shape 仅在最初 ~160 查询有编译开销，之后收敛到离线 DCC 水平。
- 后端平台是什么，配置是什么。
  - 两个 PIM 后端：AttAcc [28]（ASPLOS'24 开源 GPU-PIM 异构注意力加速框架：每 bank GEMV 单元 + 每 channel softmax/accumulator，支持完整 attention 在 PIM 侧执行）与 Samsung HBM-PIM [25]（每两 bank 一个 16-way FP16 FPU + 两个 16×256-bit GRF）。平台：NVIDIA A100 Host + 5 HBM 设备；HBM3 5.2Gbps/pin @333MHz，16 pCH/设备、64 bank/pCH；时序 tCK=0.79、tRCD=19、tRP=19、tCL=19、tCCD=4、BL=2。大规模：8×A100 每 GPU 5 HBM。
- 评估性能的软件/脚本是什么。修改了什么。
  - 修改的开源 AttAcc 模拟器 [28]（基于 Ramulator 2.0 [81]），扩展支持 AttAcc 与 HBM-PIM 两种后端及其 DRAM 计算命令；数据搬移成本用 Ramulator 2.0 仿真的 DRAM LD/ST 命令统计。软件栈：DCC Python 前端（@DCC_kernel、DCC.Layer、DCC.Kernel.preLoad/update/forward）与 PyTorch 集成；benchmark 脚本 src/test_configs.py（custom_kernel_sizes/custom_inference_sizes）+ run_experiments.sh，输出 CSV 与 PDF 图。能耗建模：Synopsys Design Compiler + ASAP7 7nm PDK 综合算术单元、FinCACTI 建 SRAM buffer、HBM 芯片显微照片估算 DRAM die 内数据路径能耗（沿用 AttAcc 方法）。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - DCC 开源（MIT）：https://github.com/SPIN-Research-Group/DCC；Zenodo https://doi.org/10.5281/zenodo.19442321。评估原理为 trace-driven 时序仿真：kernel 输入（tensor 尺寸/形状）→ DCC 生成+剪枝 tiling drafts → XGBoost 选最优 draft → 生成数据重排 LD/ST + group/bank 级计算命令 trace → 注入修改版 Ramulator 2.0，按 HBM3 时序参数（tCK/tRCD/tRP/tCL/tCCD/BL 等）逐命令推进 DRAM 状态机仿真 → 输出端到端执行时间（可拆分计算时间与数据重排时间）→ 对 GPU baseline 归一化为 speedup；LLM 场景按查询 token 尺寸在线生成 draft，该生成时间计入测量。复现：`bash setup.sh` 建 conda 环境 dcc → `bash run_experiments.sh` 跑三组实验（Fig.8 kernel AttAcc、Fig.9 kernel HBM-PIM、Fig.11 LLM 推理），结果写 results/*.csv、图写 figures/*.pdf；完整约 7–10 天、trace 约 90GB；失败实验重跑 run_experiments.sh。自定义配置：custom_kernel_sizes("GEMV", batch, input, output, nhead) 或 custom_inference_sizes(batch, input, output)（注意绘图脚本不支持自定义配置，需同步修改绘图脚本）。
