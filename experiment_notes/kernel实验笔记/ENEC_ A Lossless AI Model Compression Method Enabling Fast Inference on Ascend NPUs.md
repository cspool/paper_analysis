## ENEC: A Lossless AI Model Compression Method Enabling Fast Inference on Ascend NPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是面向 Ascend NPU AIV 向量单元、用 AscendC 编写的一对无损压缩/解压 kernel 算子（csrc/ 目录，编译为 .so NPU 算子），属于 NPU 后端的运行时压缩计算 kernel。压缩 kernel 在 AIV 上执行：指数分离→频率统计→向量化无分支整数变换→分组位宽阈值+bit mask→分层对半位打包（32KB buffer 累积后输出）；解压 kernel 执行：bit mask 转 0/1→IDD-Scan 前缀和→逆 gather→逆变换→重组还原。调度/执行模型：数据按固定长度块（默认 16,384 元素）以循环方式分发给 48 个 AIV（线程数=AI core 数），每 AI core 是单一重线程，靠任务队列 EnQue/DeQue 的流水数据流重叠数据搬运与计算；压缩 kernel 只跑 AIV（压缩是向量逐元素操作，不能直接用 AIC Cube 矩阵单元），与 AIC 的模型算子构成协作推理流水线（AIV 逐层解压与 AIC 当前层 forward 重叠）。实验比较：用 msprof 测 kernel 级压缩/解压吞吐 vs ZipNN/nvCOMP/DietGPU/HANS（Figure 9）；消融 V0/V1/V2/V3 各 kernel 版本吞吐（Figure 13：V1 相对 V0 压缩/解压 +30%，V2 近翻倍，V3 解压较 V2 +100%）；不同块大小（Figure 11：16K 最优、32K 超 UB）；不同输入文件大小 1–512MB（Figure 12）；ENEC-GPU-V0/V1 跨平台对照（Table VII）。
- 后端平台是什么，配置是什么。
  - Ascend 910B2 NPU：24 AI Cube + 48 AI Vector 单元；每 AI core 集成 1 个 AIC + 2 个 AIV；AIV 数据路径 HBM→L2→Unified Buffer（UB，约 192KB），数据搬运由 Memory Transfer Engine（MTE）完成；AIC 用多级片上 buffer（L1/L0A/L0B/L0C/BT/FP）。Host：Kunpeng-920 CPU，Ubuntu 22.04.5 LTS，NPU 驱动 25.0.rc1.1，CANN 8.2.RC1.alpha002 + kernels 同版本。
  - 关键架构约束（kernel 设计的动机，Figure 4）：Ascend SIMD 无条件分支、无 scatter/gather 指令、变长内存处理低效、无轻量线程间同步（每 AI core 单一重线程）、AscendC 操作数 32 字节对齐（half 每行 M=16 元素恰好 32 字节，同一 32 字节段内相邻元素禁止直接 SIMD 运算 → IDD-Scan 的由来）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件/脚本：msprof（AscendC/CANN profiling 工具，测 kernel 级执行时间）→ 吞吐=原始数据大小/kernel 时间（不含 PCIe）；compressor_test.sh 自动化参数搜索+压缩/解压 profiling+全局分析+端到端推理；build_csrc.sh 编译 csrc/ NPU kernel 为 .so；data_prepare.sh 从 HF 下载并切分模型权重；python/ 目录含数据处理、参数搜索、profiling 收集脚本。环境：Python 3.9、torch 2.5.1、torch_npu 2.5.1.post3、numpy/pandas/scipy、ATB 8.0.0。
  - 修改了什么：自研 csrc/ NPU 压缩/解压 kernel（未修改 CANN/msprof）；扩展了 LC framework（github.com/burtscher/LC-framework）的 HCLOG 组件（支持不同子块数量）用于最优压缩组件搜索。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源：https://github.com/hpdps-group/ENEC（主仓库）+ https://github.com/jinwuyang/ENEC_ISCA_AE（ISCA 2026 AE，BSD-3）。工作流（Appendix D/E）：安装 CANN toolkit+kernels 8.2.RC1.alpha002（.run 文件 + source set_env.sh）→ conda python 3.9 装 torch/torch_npu → git clone + bash build_csrc.sh（约 1 小时）→ bash data_prepare.sh（默认只下 Qwen3-32B，约 1 小时，可注释恢复其他模型）→ bash compressor_test.sh（约 2 小时）→ 输出 param_search_enec/（hyperparams_results.csv、param_combinations_stats.txt）、results_enec/（summary_enec.csv 对应 Table II/Figure 9）、Latency_Qwen3-32B_BF16.csv（对应 Figure 10）。参考期望值：Llama-3.1-8B CR 1.36/376.8/219.4 GB/s，Qwen3-32B CR 1.35/366.3/217.1，deepseek-7b CR 1.37/391.2/223.1；Qwen3-32B batch=1：baseline TTFT 2.36064s/TPOT 1.1951s → ENEC TTFT 0.556342s（4.24×）/TPOT 0.361142s（3.31×）。
  - 评估原理与 kernel 输入到性能输出全过程：数据准备把 HF 模型权重存为二进制文件并按层切分 → 参数搜索阶段对每个张量跑 V-E 三阶段搜索得到 (b,n,m,L) 写入 hyperparams_results.csv → 压缩测试：原始二进制权重按块（16,384 元素）循环分发给 48 个 AIV 线程 → 每线程 AIV kernel 执行 Split→变换 y=(2^n-x+b)%2^n→分组位宽阈值+bit mask→分层对半打包（32KB buffer 累积满 16 位即输出低 16 位+bit mask 并右移）→ 输出压缩流；msprof 记录 kernel 执行时间 → 吞吐=原始大小/kernel 时间（压缩 366 GB/s 级）→ 解压测试同法：读 bit mask→转 0/1 整数→IDD-Scan 前缀和（8×16 half 局部张量转置+列扫描+行扫描得偏移）→按偏移逆 gather 取低位→逆变换还原指数→Combine 重组 BF16 → msprof 测解压吞吐（217 GB/s 级）→ summary_enec.csv 汇总 CR/压缩/解压吞吐 → 端到端：解压算子集成进 HuggingFace Transformers 推理，逐层解压并与当前层 forward 重叠，测 TTFT/TPOT。示例：Qwen3-32B BF16，权重 62.5GB 压缩到 46.3GB（CR 1.35），解压吞吐 217 GB/s 覆盖层传输需求，TTFT 4.24× 提速。
