## XtraMAC: An Efficient MAC Architecture for Mixed-Precision LLM Inference on FPGA

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现是 XtraMAC 集成的 tile 并行混合精度 GEMV kernel（FPGA 硬件 kernel，论文 VI 节 case study）：把 XtraMAC 作为级联 MAC 链替换现有 FPGA GEMV 流水线（FlightLLM [42]/FlightVGM [23] 风格）中的标量 MAC，PE 拓扑/tiling/全局数据流保持不变。GEMV workload 按 M 个 tile 划分，每 tile 映射到一个连接独立 HBM channel 的 PE；权重存 HBM、激活片上缓冲复用；HBM 每 channel 512-bit 接口字拆成 per-lane 权重段分发到 PE 内级联的 XtraMAC 实例，per-tile datatype 控制信号（存在内存里、与权重 tile 一起）与操作数同步传播，保证每实例在运行时应用正确的映射规则与累加路径，各 lane 部分和经级联 MAC 链累加后写回。每 channel 级联 XtraMAC 数 N_MAC = BitWidth_channel/(BitWidth_weight×P)：INT4 权重（4-bit）+ P=2 lanes 时单 channel 512/(4×2)=64 个 MAC 输入/cycle；32 个 HBM channel 理论可例化 2048 个，实际采用 1920 个（30 个活跃 channel，留 1 个读激活 + 1 个写回，保证路由时序收敛）。
  - 实验比较：① 资源/频率扩展——post-implementation 测 LUT/FF/DSP 随 XtraMAC 例化数线性增长，≤1024 实例维持 300 MHz，1920 实例因 HBM 接口附近路由拥塞降到 250–270 MHz（Fig.12）；512-XtraMAC 配置下 XtraMAC 占 LUT 98.5%、FF 95.6%、DSP 100%，剩余为 datatype 控制寄存器与片上激活缓冲，HBM 控制器在 Alveo static shell 中不计入用户逻辑（Fig.13），非 MAC 组件与操作数并行注册、不增加流水级；② 与 GPU baseline 对比——NVIDIA H100 PCIe + CUTLASS [29] 官方 GEMV kernel（nvidia-smi 测功耗），1×4096×4096 与 1×4096×12288 GEMV 上 XtraMAC（U55c）时延 0.0246/0.0743 ms vs CUTLASS 0.0294/0.0879 ms（1.2× speedup），功耗 85 W vs 135 W，能量 0.00209/0.00632 J vs 0.00397/0.01187 J（1.9× energy efficiency）；尽管 GPU 峰值带宽 2 TB/s vs FPGA 460 GB/s，FPGA 靠高效混合精度 MAC datapath、无格式转换开销与 ~74% 有效 HBM 利用率跑出接近带宽 roofline 的性能（Table VII）。
- 后端平台是什么，配置是什么。
  - FPGA：AMD Xilinx Alveo U55c（xcu55c-fsvh2892-2L-e，32 个 HBM channel、460 GB/s HBM 带宽），Vivado 2022.2 + Vitis 2022.2 综合/实现，post place-and-route 时序；GEMV kernel 用 1920 个级联 XtraMAC、30 个活跃 HBM channel、每 channel 512-bit 接口、300 MHz（1920 实例时 250–270 MHz）；功耗用 xbutil 稳态流式测量（85 W）。
  - GPU baseline：NVIDIA H100 PCIe（HBM 带宽 2 TB/s），CUTLASS 官方 GEMV kernel，execution time 用官方 kernel 测量，nvidia-smi 监控功耗（135 W）。
- 评估性能的软件/脚本是什么。修改了什么。
  - FPGA 侧：Vivado/Vitis 2022.2 综合+实现（place-and-route 报告资源/频率）、xbutil（稳态流式功耗测量）。修改：在现有 FPGA GEMV 流水线（如 [42][23]）基础上把标量 MAC 替换为 XtraMAC 级联链，PE 拓扑/tiling/全局数据流不变；新增 per-tile datatype 控制信号（与权重 tile 一起存 HBM、随操作数同步传播）；权重 HBM 直读、激活片上缓冲、HBM 512-bit 接口字按 per-lane 拆分、多 PE 跨 HBM channel 并发保持带宽扩展。
  - GPU 侧：CUTLASS [29]（https://github.com/NVIDIA/cutlass）官方 GEMV kernel，未修改，作为官方实现 baseline；计时用官方 kernel 的执行时间，功耗 nvidia-smi。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源情况：XtraMAC 的 MAC RTL 全开源（https://github.com/Xtra-Computing/XtraMAC，Apache-2.0），但论文未单独开源完整 GEMV kernel 集成工程（1920 XtraMAC 的 tile 级组装），需按论文 Fig.11 自行集成；CUTLASS 开源（https://github.com/NVIDIA/cutlass）；AMD Alveo U55c 卡资料 https://www.amd.com/en/products/accelerators/alveo/u55c/a-u55c-p00g-pq-g.html。联网搜索 2026-08 确认 GEMV 集成工程未单独发布。
  - 使用例子（GEMV kernel 输入到性能输出的全过程）：① 输入——1×4096×4096 或 1×4096×12288 的 INT4 权重矩阵（存 HBM，按 tile 与 per-tile datatype 控制信号打包）、单行激活向量（片上缓冲）、30 个 HBM channel 的 512-bit 接口、1920 个级联 XtraMAC（P=2 lanes，N_MAC=512/(4×2)=64 per channel ×30 channel）；② FPGA 执行——HBM 每 cycle 读出 512-bit 权重字 → 拆成 per-lane 权重段 → 分发给对应 PE 的 XtraMAC 实例，同 tile 的 datatype 控制信号同步选择 INT4×BF16→BF16 的映射规则与累加路径，激活从片上缓冲复用，级联 MAC 链逐 lane 累加部分和 → 写回 GEMV 输出；③ 性能测量——Vivado post-P&R 报告资源/频率（Fig.12/13），xbutil 稳态流式测功耗 85 W，计时得 0.0246 ms（1×4096×4096）；④ 输出——Table VII 的 time/power/energy/speedup（0.0246 ms/85 W/0.00209 J/1.2×），对比 CUTLASS H100（0.0294 ms/135 W/0.00397 J）。作用原理：GEMV 是带宽受限 workload，kernel 吞吐上限 ≈ HBM 带宽/权重字节数；XtraMAC 的 2× lane 打包让每个 DSP48E2 每 cycle 处理 2 个 INT4 权重（512-bit 接口在 4-bit 权重 + P=2 下恰好每 cycle 喂满 64 个 MAC），相同带宽下用更少 DSP/逻辑达到更高有效计算密度且无格式转换开销，使 FPGA 在 460 GB/s 下维持 ~74% 有效 HBM 利用率并反超 2 TB/s 的 H100。
