## Lit Silicon: A Case Where Thermal Imbalance Couples Concurrent Execution in Multiple GPUs

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - （近似分层：本论文核心是节点级 GPU 功率管理运行时层，不修改 kernel 算子/编译框架/硬件 RTL，此处从"运行时对 GPU kernel 级性能的检测与功率调度"角度记录）实现为约 200 行 PyTorch 的节点级功率管理运行时层，用于检测并缓解多 GPU 节点内的 *Lit Silicon* 效应（热不平衡 + 并发计算通信 C3 耦合导致的节点级性能波动）。包括：(1) 检测——Algorithm 1 LEADVALUEDETECT 基于 Chopper 工具解析 PyTorch trace 得到各 GPU 上每个 kernel 的起始时间戳，对每个 kernel 计算 lead value（本 GPU 起始时间相对最晚 GPU 的差值），按 GPU 聚合（默认 sum=lead 曲线下面积，也可 max/last，窗口平均后输出）以识别 straggler（lead≈0、更热更慢）与 leader（lead>0、更冷更快）；(2) 缓解——Algorithm 2 INCPOWERGPU 按归一化 lead 计算各 GPU 功率上限增量（global scale 用历史最大 lead 衰减调整幅度），Algorithm 3 ADJPOWERNODE 在节点级功率上限与 GPU TDP 约束下均匀回退功率上限；连续采样-调整直到收敛（功率上限分布稳定后可停用或长周期采样）。三种使用场景：GPU-Red（无节点上限，仅降低 leader 功率省电）、GPU-Realloc（节点上限下把 leader 功率重分配给 straggler 提升吞吐）、CPU-Slosh（节点上限下把闲置 CPU 功率预算转移给 GPU）。需要 root/管理员权限设置功率上限（amd-smi），不修改任何 GPU kernel。
  - 实验比较：(1) 三种使用场景在默认配置（Llama 3.1 8B、FSDPv2、bf16、b2s4、功率上限 700W、节点1）下的收敛行为——GPU-Red 平均功率降 4% 吞吐不变；GPU-Realloc 吞吐 +3% 平均功率不变；CPU-Slosh 吞吐 +4%（功率上限 550W 时达 6%）但 GPU 功率 +3%；功率重分配收益递减。(2) 与解析性能/功率模型预测对比（表 III）——功率预测误差 ≤1%（GPU-Red 1.05 vs 1.04、GPU-Realloc 1.00 vs 1.00、CPU-Slosh 0.97 vs 0.97）；吞吐预测约为实测 2 倍但趋势一致（1.06/1.10 vs 1.03/1.04）。(3) 敏感性分析（表 II 旋钮：节点 0/1、模型 Llama 3.1 8B/Mistral 7B v0.1、FSDP v1/v2、精度 bf16/fp8、b1s4/b2s4/b4s4/b1s8/b2s8、迭代 1000、采样周期 4/7/10、warm-up 3/6/12/25/50、窗口大小 1/2/3/5、聚合 max/last/sum、最大调整 5/10/15/30、scale global/local、功率上限 700/650/600/550/500W、功率预算 10/20/30/50W）——各旋钮下收益基本一致，影响最大的是初始功率上限；收敛后的功率上限分布可跨框架/模型/上限复用（图 12）；节点0（更多 straggler）收益略低；500W 功率上限变异性差；warm-up 长度不影响收敛（图 11）。(4) MoE 对比（图 16）——DeepSeek V3 16B（Primus+torchtitan 8 路专家并行，all-to-all 不重叠）lead 值更小但有稀疏大 spike，算法仍收敛到与 dense 训练相同的功率分布与节电。(5) 检测频率与开销——三个月内调两次（3.5%、4% 节电），建议周/月粒度；每样本 dump+处理约 4 秒，约 80 秒（20 样本）达稳定功率分布。
- 后端平台是什么，配置是什么。
  - 2 个 AMD GPU 节点，每节点 8× AMD Instinct MI300X（TDP 上限默认 700W，评估 700/650/600/550/500W）+ 2× AMD EPYC 9684X CPU（训练时仅约 13.5% CPU 核心被利用）。温度/频率/功率经 amd-smi（ROCm rocm-systems 项目，github.com/ROCm/rocm-systems）测量，功率上限亦经 amd-smi 设置（root 权限）。PyTorch FSDP/FSDP2 分布式训练框架，bf16 与 fp8（Transformer Engine kernel，E4M3 前向/E5M2 反向+动态缩放，fp8 时用 FSDPv1 兼容）两种精度。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：Chopper（论文作者自研 GPU 特性分析工具，arXiv:2512.08242，可公开获取）解析 PyTorch profile trace 得到 kernel 起止时间与 C3 重叠率；amd-smi 采样温度/频率/功率；自带 benchmark 脚本（stress test）做离线校准。修改了什么：论文新增约 200 行 PyTorch 的检测+缓解层（Algorithm 1/2/3），不改 GPU kernel、不改 PyTorch/FSDP/Transformer Engine 本身。

  - 开源情况：代码开源 https://github.com/UnaryLab/lit_silicon_tuning_amd （ISCA 2026 artifact，约 380 commits，`lit_silicon` 分支；目录含 benchmark/docs/examples/primus（Singularity/Apptainer 容器定义 primus.def）/runner/tests/tools/third_party（chopper 子模块）/power.proto+power_server.py（protobuf 功率服务接口）/requirements*.txt（PyTorch、torchft 容错分布式、JAX））。使用：git clone --recursive → Python 3.12 venv（uv）→ uv pip install third_party/chopper → 申请 HF 访问 Llama 3.1 8B 并 export HF_TOKEN → ./submit_all.sh <account> 提交全部作业（build.sh 构建容器、chopper.sh、plot.sh 出图），生成的图对应论文 Fig.9（red_realloc_slosh_lead_and_throughput.png、red_realloc_slosh_freq_pow.png）与 Fig.16（deepseek_llama_straggler_per_gpu.png、deepseek_llama_lead_and_throughput.png、deepseek_llama_avg_pow_freq.png）。源码级功率上限设置逻辑（amd-smi 调用）未在 README 中详述，需读 runner/tools/power_server.py 确认。
  - 评估原理与 kernel 输入→性能输出全过程：输入 = 8 GPU 上同构的 FSDP LLM 训练迭代（每 GPU 相同 kernel 序列：forward/backward 各层的 GEMM/flash attention/RMSNorm + 通信 AllGather/ReduceScatter 与计算重叠）→ PyTorch profiler 生成每 GPU kernel 时间戳 → Chopper 聚合为每 kernel 每 GPU 的起始时间与重叠率（C3 重叠 = 计算/通信 kernel 并发时间占比）→ Algorithm 1 计算各 GPU 每 kernel 的 lead value（起始时间与最晚 GPU 之差，默认 sum 聚合 + 窗口 3 平均）→ 判断 straggler（最小 lead）与 leader → Algorithm 2 按归一化 lead 生成各 GPU 功率上限增量 I[g] = norm_lead × (max_lead/global_max) × max_inc（max_inc 默认 15W，global scale 随收敛衰减）→ Algorithm 3 检查节点功率上限与 TDP：GPU-Red 下把 leader 上限均匀下调（例：straggler 保持 TDP，7 个 leader 各 -15W）；GPU-Realloc 下 straggler +15W 后全部 8 GPU 均匀 -15W/8；CPU-Slosh 下若每 GPU CPU 预算 ≥2W 则用 CPU 侧额外 16W 兜底、不降 leader → amd-smi 设置各 GPU 功率上限 → 采样频率/功率（rolling 5th-95th 分位）→ 输出收敛后的功率上限分布、平均功率（GPU-Red 归一化 -4%）、吞吐（sum of kernel duration，GPU-Realloc/CPU-Slosh +3%~+6%）、lead 值（趋于 0）。作用：把节点级热不平衡导致的 straggling 通过功率重分配在运行时消除，无需改 kernel 与硬件，作为 GPU 级与集群级功率管理之间新增的节点级功率管理层部署。
