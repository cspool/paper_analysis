## MLX: Multi-Layer Execution for Structured LLM Workload Acceleration on Spatial Architectures

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 属于kernel调度/运行时计算的实现：论文在 GPU 后端实现并评估两类新型结构化稀疏 kernel——**FFT-CMP kernel（chunked FFT 压缩 + 截断 + iFFT，用于注意力/token mixing 与 KV-cache 压缩）** 与 **hierarchical BSMM kernel（B×B tile 内蝴蝶稀疏矩阵乘，用于 QKV/FFN 投影）**。这些 kernel 以 PyTorch 层实现（FFT 用 cuFFT，未与 FlashAttention 融合），运行于 CUDA cores（TensorCore 对蝴蝶稀疏支持有限，会回退到 CUDA core）。实验比较：(a) H100 上压缩后的 Llama2-7B（s=0.5, B=32）相对原模型 eager attention 与 FlashAttention2 的 prefill/decode 加速：prefill 长序列（8K）最多 2.72×（vs eager）/1.64×（vs FA），短序列收益小；decode 结合块 BSMM 1.4-1.9× 端到端。(b) 与 MLX 加速器对比的 GPU kernel 性能剖面：AGX Orin（batch 64）上 FFT-based transformer block 仅 3.77×（N=8K）/2.56×（N=512）相对 dense 加速（FLOP 削减 >10× 理论上）；Jetson Xavier 上八类 Llama2-7B kernel 的 dense TensorCore vs 蝴蝶 CUDA-core 执行；AGX Orin/RTX-3090 的 structured-workload sweep（FFT-CMP→BSMM→SWA，batch 32）与 roofline 利用率（蝴蝶算子 MLX 52-84% vs Orin 12-29% vs RTX 8.2-31%）。动机剖析：蝴蝶 kernel 运算强度低（bandwidth-dominated）却远低于 CUDA 带宽 roofline（图3），源于多级 strided/shuffle 访问破坏局部性、高 cache miss（图2），以及 stage-wise 依赖与 GPU 批量同步、tile 规则执行的错配（执行单元不匹配）。
- 后端平台是什么，配置是什么。
  - NVIDIA H100（prefill N=512/8K，FP16，cuFFT 优化 roofline 分析）；NVIDIA AGX Orin（batch 64、batch 32 两组）；NVIDIA Jetson Xavier（12nm、1.7 TFLOP/s CUDA 峰值/6 TFLOP/s TCU 峰值、15W、16 GB）；NVIDIA RTX-3090。FFT kernel 走 cuFFT；BSMM/FFT-CMP 为 PyTorch 层组合 kernel（torch.fft + 分块矩阵乘）。
- 评估性能的软件/脚本是什么。修改了什么。
  - 评估软件：PyTorch（模型推理 + kernel 组装）+ cuFFT（FFT 变换）+ FlashAttention2（FA baseline）+ 自定义 profiling/roofline 工具（图2/图3 的 CUDA 利用率、cache miss、OI 测量；roofline 用 P_achieve/min(P_peak, OI·BW)）。修改内容：在 Llama2-7B 的 QKV 投影/注意力/FFN 中替换 kernel——(1) QKV/FFN 投影改为 hierarchical BSMM（权重按 B=32 tile 分块、tile 内蝴蝶分解）；(2) 注意力改为 FFT-CMP（Q/K/V 按 L 分块 FFT、截断 sL、iFFT 后算注意力）；(3) decode 侧做 chunk-granular 压缩 KV cache（新 token 累积 L 才 FFT 一次并 append 新块）；(4) 用 LoRA 微调压缩层恢复精度。FFT-CMP 保持在 PyTorch 层（不融合 FA），故 H100 收益有限。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源情况：论文（ISCA 2026，ICT CAS）未开源 kernel 实现/评估脚本（联网搜索未找到仓库）；FFT-CMP/BSMM 以 PyTorch 层实现，可基于 torch.fft 与矩阵分块重建。
  - 评估原理与 kernel 输入→性能输出全过程（以 H100 prefill N=8K 为例）：输入 = Llama2-7B 权重（QKV 投影 W 已按 B=32 分块蝴蝶分解、FFT-CMP 层已 LoRA 微调）+ 8K token 输入序列。执行：QKV 投影用 hierarchical BSMM kernel（CUDA core，块间 coarse blocked-GEMM 数据流、块内 tile 级蝴蝶 stride±2/±4/±8 数据流）→ Q/K/V 每层按 L=2048 分 4 个 chunk 做 cuFFT 2048 点变换、保留前 sL 个低频系数、iFFT 回 1024 token 缩短表示（注意力矩阵 8K×8K→4K×4K，4× 缩减）→ 注意力在缩短序列上执行（未融合 FA）→ decode 时每次新 token 累积到 L 触发一次 FFT 压缩并 append 压缩块到 KV cache（减少 KV 流量）。输出：profiling 工具测量各 kernel 的 cache miss（图2）、运算强度 OI（有效 FLOPs/DRAM 字节）、CUDA core 利用率与端到端/分阶段延迟，换算为相对原模型的 speedup（prefill 2.72× vs eager / 1.64× vs FA，decode 1.4-1.9×），并解释为何 FLOP 削减（>10×）只转化为有限加速（bandwidth-bound + 多级数据重排 + 执行单元不匹配）——这直接引出 MLX 空间架构设计。
