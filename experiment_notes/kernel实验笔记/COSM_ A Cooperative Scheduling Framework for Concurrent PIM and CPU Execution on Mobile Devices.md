## COSM: A Cooperative Scheduling Framework for Concurrent PIM and CPU Execution on Mobile Devices

- 属于kernel调度/运行时计算的实现是什么？实验比较什么？
  - 实现 = PIM 后端上 PIM 命令与数据传输的运行时调度：(1) idleness-aware scheduling——IWE 按 Algorithm 1 模拟 FR-FCFS 顺序估计每 bank 最早服务周期：对每 bank 最早请求算 ready cycle（bank 三态：Row-Closed 需 ACT 延迟 tRCD、Opened-to-target-row 按行打开周期、Opened-to-different-row 需 PRE+ACT 延迟 tRP+tRCD），循环内优先当前 rank 的最早就绪请求并 t←t+tBL，否则跨 rank 切换取全局最早，得 window_bank（每 bank 最早服务周期）/window_bus（所有请求最小服务周期）；Command Arbiter 据此推迟过早的 ACT 命令，把 PIM 执行塞进 ACT 与数据访问间的 bank 空闲窗口（窗口须 ≥ tRP+tRCD + 至少一列），把 PIM_RdBuf/WrBuf 塞进 window_bus 之前的 bus 空闲窗口；CPU 请求到达时不立即发 PIM_Pause，而是延迟到"不推迟下一次 CPU 访问的最后周期"再发。(2) overlapped scheduling——把 PIM workload 切成无数据依赖的 tile（如矩阵乘子矩阵，reduction 由 CPU 做），跨 tile 并行发不同阶段命令（收集 tile T_i 结果的同时执行 T_{i+1}），阶段间用 PIM_Barrier 保证依赖。(3) 命令优先级：PRWQ 的 PIM_RdBuf/PIM_WrBuf（独占外部总线，瓶颈）> PIM_LdBuf/PIM_StBuf（清空 buffer 防阻塞后续总线命令）> PEQ 的 PIM_Exec（匹配当前 bank 空闲窗口）；同 bank PRWQ 命令保持到达顺序。实验比较：CPU-first（Chopim 式）调度、4 配置消融（Base=标准读写+三阶段串行 / Overlapped / Overlapped+Decoupled / All=再叠加 IWE）；baseline 硬件与平台见 实验_硬件架构.md 同名条目。结果：idleness-aware 较 CPU-first 平均 PIM 性能 1.21×、多利用 37.0% 可用带宽（剩余 <1% 未用）；Overlapped 使 CPU 性能 +3.7%（高行命中率的 PolyBench 内核因激进重叠引入额外行切换）、Overlapped+Decoupled +11.5%、All 保持 CPU 降速 <5%。
- 后端平台是什么，配置是什么。
  - LPDDR5-6400 PIM：2 Channels × 2 Ranks、16 banks/rank（4 BG × 4 Bank）、bank 级 PIM 单元 16/rank（1GHz、6.4 GB/s、6.4 TFLOPS）、1kB bank buffer；主机 Snapdragon 888 级 CPU（8 核 @2.1GHz、OoO、FR-FCFS 调度）；PIM 命令长 nPTL=128；PEQ/PRWQ 深度各 2/bank。
- 评估性能的软件/脚本是什么。修改了什么。
  - 修改版 Ramulator2 + 自动化脚本：`./build.sh [并行度]` 编译、`cd simulations && ./run_script.sh figure8|figure10 [并行度]` 批量仿真产出 CSV（simulations/scripts_result_processor/），Excel 模板 plot_figure8|10_ae.xlsx 绘图。PIM 侧 LLM trace（DeepSeek-R1-1.5B 等）由 Python 脚本生成，CPU 侧 trace 由 zsim（SPEC CPU2017/PolyBench-ACC）与 Frida 真机插桩（移动应用）采集后反复回放生成背景流量。修改：控制器新增 pim_arbiter_cpu_first_o3_pred.cpp（idleness-aware 调度、PEQ/PRWQ、命令仲裁），LPDDR5-PIM 模型新增可抢占执行与带宽解耦传输命令。
- 开源情况。基于开源文档和论文，使用例子解释评估软件/脚本如何使用？至少具体到评估软件的评估原理和kernel输入到性能输出的全过程。
  - 开源情况：Zenodo artifact（https://doi.org/10.5281/zenodo.19660293）含全部源码、trace 与脚本；基座 Ramulator2 开源（https://github.com/CMU-SAFARI/ramulator2）。使用例子：装 GCC 12+/CMake 3.30+/Python 3.12+ → `./build.sh 16` → `./run_script.sh figure8 16`（figure10 同理）→ 把 summary_figure8.csv 贴入 Excel 模板出图，复现 Fig. 8（并发性能）与 Fig. 10（传输消融）。
  - 评估原理与全过程（一次并发执行）：CPU trace 回放进 O3CPU 前端形成 FR-FCFS 请求队列 → IWE 按 Algorithm 1 从请求队列预测 window_bank/window_bus → PIM scheduler 按"总线命令 > buffer 命令 > 执行命令"优先级从 PRWQ/PEQ 选 PIM 候选 → Command Arbiter 三源仲裁（CPU/refresh 优先、必要时延迟发 PIM_Pause、空闲窗口内发 PIM 命令）→ 命令注入 LPDDR5-PIM 模型按表 1 时序逐 cycle 推演 → 输出 PIM 吞吐（tokens/sec）与 CPU 归一化性能。kernel 输入 = attention 层 GEMV/MAC/softmax 的 PIM 命令流（PIM_Exec(L/S) + 传输命令对）；性能输出 = 吞吐（COSM 较 All-Bank 6.0×、较 Chopim 2.8×，CPU 降速 <2.0%）。
