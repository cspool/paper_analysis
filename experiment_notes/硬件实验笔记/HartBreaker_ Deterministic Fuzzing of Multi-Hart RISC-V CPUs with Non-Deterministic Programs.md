## HartBreaker: Deterministic Fuzzing of Multi-Hart RISC-V CPUs with Non-Deterministic Programs

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现为 HARTBREAKER，一个多 hart RISC-V CPU 硬件模糊测试（fuzzing）框架：随机生成**非确定性**多线程测试程序（bare-metal 汇编），在 RTL 仿真上执行，并验证多核 CPU 的共享内存一致性（RVWMO）与核间中断（IPI）等通信通道实现是否正确。核心机制是三类 *determinism anchors*：(1) control-flow anchors（cf-anchors）——接收 hart 进入 confined landing zone 并向发送 hart 发信号，发送 hart 发出 IPI 后接收方在任意（非确定性）周期 trap，landing zone 内随机计算在任意迭代次数下重建相同数据，退出时架构状态与中断到达时刻无关（图 5）；(2) data-flow anchors（df-anchors）——把非确定性值（load 目的寄存器、收到中断后的 mepc CSR）标记隔离并重置为确定值（xor/sub 清零），防止污染控制流，同时保持指令间句法依赖以触发重排序（图 7）；(3) synchronization anchors——跨核同步（barrier）+ 段间 fence，把测试程序划分为分区、限制可重排序窗口，使 MCM 验证可扩展。验证端：把执行 trace 与程序静态依赖转换为**等价 litmus test**（图 7 的依赖构造法），交给 MCM solver（Dartagnan，初版自研 solver 仅支持 ~10 条内存操作，Dartagnan 提升到 ~100 条）检查观察到的 load 返回值是否在 RVWMO 下存在合法执行；控制流 bug 表现为程序级确定性失效（hang/timeout）。
  - 实验比较四类指标：(1) 多 hart 特性覆盖——10000 个生成测试程序，100% 含中断（平均 12.1 个 IPI/测试，每测试平均 1600 条指令），PPO 规则全部覆盖（图 8，排除 rule 8 LR/SC 因 spurious SC failure 无法区分合法/活性 bug），共享内存操作距离分布（图 9）；(2) fuzzing 吞吐——开启/关闭验证的开销（图 10）、各 CPU 跨程序大小的端到端吞吐（图 11）、XiangShan 仿真时间（图 12）、流水线各阶段（generation/ISS/RTL sim/MCM verification）时间占比（图 13）；(3) coverage——vs RISCV-DV 在三 hart BOOM v3 上的 mux select coverage（15,872 个 coverage points，图 14，各 858 core-hours）；(4) bug discovery——5 个新并发 bug（表 IV）。
- 硬件平台是什么，配置是什么。
  - 评估机：2× AMD EPYC 7H12 @2.6GHz，256 逻辑核，1TB DRAM。测试目标（DUT）为 5 个开源多 hart RISC-V 设计：Rocket（简单 in-order，三 hart）、BOOM v3/v4（OoO superscalar）、Toooba（Bluespec）、NaxRiscv（SpinalHDL/Scala）、XiangShan（Chisel，大型高性能 OoO）。artifact 最低要求 8 核/16GB RAM/50GB 磁盘，完整复现推荐 256 核/64GiB/1TB。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - Verilator（https://github.com/verilator/verilator）做 RTL 仿真（按设计需求适配版本）；Spike（https://github.com/riscv-software-src/riscv-isa-sim）作 golden ISS；MCM 后端 Dartagnan（https://github.com/MPI-SWS/dartagnan，ref [37] Porthos/Dartagnan）与 herd7（litmus 工具族，ref [14]/[21]，README 注明未接入 Docker pipeline）；RISCV-DV（https://github.com/chipsalliance/riscv-dv，UVM + 商业模拟器跑对比实验）。DUT 仓库：Rocket/BOOM 经 Chipyard（github.com/chipsalliance/chipyard）、Toooba（github.com/bluespec/Toooba）、NaxRiscv（github.com/SpinalHDL/NaxRiscv）、XiangShan（github.com/OpenXiangShan/XiangShan）。
- 模拟器模拟什么的性能，修改了什么。
  - 模拟/验证的是多 hart RISC-V CPU 在并发共享内存与 IPI 压力下的功能正确性（RVWMO 内存一致性、中断时序），指标为：指令吞吐（inst/s）、各流水级耗时占比、PPO 规则覆盖、共享内存操作距离、coverage points（mux select）、bug 触发 TTE（Time-to-Exposure，20 次 fuzzing run 统计）。HARTBREAKER 不修改 DUT 的 RTL，而是在测试生成器与验证后端上实现 cf/df/sync anchors 与 trace→litmus 翻译；为 coverage 对比在 Boom v3 中插桩覆盖率（coverage_comparaison/ 目录）。NaxRiscv 仿真经 Scala/JNI 绑定 Verilator 二进制，启动需重建缓存 artifacts 故启动慢（图 11 中吞吐突升的原因）。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 完全开源：GitHub https://github.com/comsec-group/hartbreaker（推荐，含 bugfix），Zenodo artifact https://doi.org/10.5281/zenodo.19417381。结构：hartattack/（fuzzing 框架：程序生成、仿真、验证）、simulators/（各设计预编译二进制 + cfg.json，需 build 脚本生成）、artifact_reproduction/（复现图 8–14 的 per-figure bash 脚本，每个脚本在对应 Docker 容器内运行并产出 figures/*.pdf）、coverage_comparaison/（BoomV3 覆盖率插桩）、docker/（Dockerfile）、scripts/。安装：build_docker.sh base → build_docker.sh run（+ covcollect 复现图 14、+ naxriscv）；模拟器预编译二进制在 simulators/，可重编译（数小时）：build_chipyard.sh / build_toooba.sh / build_xs.sh。成本由环境变量调：HARTATTACK_CORES（默认 15）、HARTATTACK_NUM_PROGRAMS（默认 500/10000）、HARTATTACK_NUM_ELFS（默认 10000）。复现：./artifact_reproduction/collect_data.sh（图 10–13 共享数据）→ figure_8.sh … figure_14.sh（图 8/9/14 自采数据，图 14 支持 --quick，需 ~14GB RISCV-DV corpus 从 Zenodo 下载）；run_all.sh 一键全跑。
  - 模拟原理与输入→输出全过程：输入 = (a) 随机种子与参数（每测试指令数、内存操作/中断密度、hart 数 3）+ (b) DUT 的 Verilator 仿真二进制与 Spike golden 配置。流水线四步（图 13 分解）：① 生成——随机生成带 cf/df/sync anchors 的多 hart 汇编测试程序（df-anchor 保证 store 值确定，可在生成时静态推导依赖）；② ISS——程序先在 Spike 上跑，得到生成时未知的值（如 store 将提交的值），并作为控制流确定性基线；③ RTL 仿真——同一二进制在 Verilator 编译的 DUT 上执行，从 commit log 收集所有并发 load 的返回值与内存操作 trace；④ MCM 验证——把 trace 按图 7 方法翻译成等价 litmus test（利用 1. df-anchor 使 store 值确定可获、2. 静态句法依赖已知、3. trace 给出 load 返回值三条性质），构造 exists 断言，交 Dartagnan 检查该结果在 RVWMO 下是否合法；不存在合法执行 ⇒ 内存一致性 bug。控制流 bug 则因 anchors 保证程序级确定性而表现为执行超时。输出 = 合法/非法判定、bug 触发测试程序、吞吐/覆盖率/TTE 统计与图 8–14 复现数据。作用：在 pre-silicon 阶段系统性验证多核 CPU 的共享内存与 IPI 通信通道，发现 5 个此前未知并发 bug（NaxRiscv N1/N2、Toooba T1、BOOM v4 B1、XiangShan X1——含 CoRR 违例的非法 load-load 重排序、CLINT 仅接受全字 store、mret 未立即处理 pending 中断、MIP 乱序读），B1/N1 需要复杂结构/计算依赖与特定微架构条件，现有工具无法触发。
