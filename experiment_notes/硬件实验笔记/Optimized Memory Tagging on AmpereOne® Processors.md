## Optimized Memory Tagging on AmpereOne® Processors

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现：Ampere Computing AmpereOne® SoC（96–192 核自研 Arm v8.6+ 核，2024 年发布，首个支持 ARM MTE 的数据中心 SoC）的全系统 MTE（Memory Tagging Extension）硬件实现，覆盖 MCU/DRAM、coherent mesh、Core PE 三个子系统，核心设计是 tag 与数据全栈共置（co-located bundle）：
    (1) MCU/DRAM——把 MTE allocation tag（每 16B granule 4 bit）存在 DDR5 ECC 位中、与数据内联，软件可见内存容量零开销；为此设计 4 种 ECC scheme（A. SECDED-64+8 无 MTE，72 bit codeword=64B 数据+8B ECC，8 codewords/64B cacheline；B. SECDED-128+4+9 支持 MTE，128B 数据+4B tag+9B ECC，4 codewords/64B cacheline，靠加倍数据粒度腾出闲置 ECC 位存 tag 且不削弱可靠性；C. SymbolECC-64+16 无 MTE，Reed-Solomon 每 codeword 纠正 1 个 symbol；D. SymbolECC-64-14+2 支持 MTE，从 ECC parity 借 2 bit，100% 故障检测、100% 有界故障纠正、99.98% 无界故障纠正），MTE 部署用 B/D；MCU/DRAM 内不做任何 tag 检查，tag 位与数据位同步传输、无 MCU 内延迟影响；
    (2) Coherent mesh——用保留的 implementation-specific metadata 位随数据同传 tag，mesh 内所有 cache line 存储扩展含 tag 位且被 ECC 覆盖，mesh 不做 tag 检查；
    (3) Core PE——L1/L2 缓存加宽、tag 与数据共驻，tag 校验在 cache-lookup 点与地址翻译/访问权限检查（如 page fault 检测）并行执行，不引入额外 pipeline stage/stall；load 相对未 tag 执行开销可忽略；store 需先取回并校验目标 cache line 的 memory tag 才能 commit（core 内 MTE 主导成本），用 early line fetch 缓解——tagged store 在地址翻译时即发起 cache-line（含 tag）取回，可与其它工作乱序重叠、使 tag 校验远早于 commit 完成；store-to-load forwarding 规则：store buffer 记录 allocation tag（address tag），load 仅在其 address tag 与旧 store 匹配时才可 forwarding（此时 store 的 tag 校验结果可能未定，但 address tag 匹配则二者同验同错、保正确性），禁止跨 tag-store 指令（写 memory tag 的指令）forwarding。支持 SYNC（不匹配即异常且访问不完成，与 page/permission fault 类似）与 ASYNC（访问完成、置系统寄存器位供软件事后检查）两种 tag-checking 模式，以 SYNC 为主（多租户生产隔离必需）。
  - 实验比较：三个系统配置——A. MTE Disabled（硅片级关闭）；B. MTE Enabled, No Tag Checking（硅片开、用户态 glibc 不开 tag）；C. MTE Enabled, With Tag Checking（GLIBC_TUNABLES=glibc.mem.tagging=3 开 SYNC tag checking）。比较两个比率：B/A（硬件使能 MTE 的 always-on 开销，多租户 CSP 的关键决策）与 C/B（应用开启 tag checking 的软件开销）。每个 benchmark 跑 5 次，用 ministat（Student's t-test）在 99% 置信度下统计，无显著差异记为 "on par"。结果：datacenter workloads 上 B/A 开销 1–6%（memcached +7.6%，tag checking 关闭时 tagload 变成 prefetch、L2 miss 等待时间显著下降带来收益）；C/B 为中个位数百分比（nginx 1.022 小加速，tag checking 使 store 的 cache line 更早被取回产生 prefetch 效应）；SPEC CPU 2017 192-copy refrate 上 C/B geomean 0.924（7.6% 降），主要由 502.gcc_r（0.698）与 523.xalancbmk_r（0.855）驱动，归因软件因素（指令数增加、eager tag init、高频小对象碎片化分配），并用 jemalloc 替换实验（Fig 10，523.xalanc 1.363 uplift）证明 MTE 降速源于内存管理而非 tag checking 本身。
