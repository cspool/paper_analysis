## Bumper: Hinting Instruction Usefulness for Robust Unified Caches

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现为 Bumper 微架构方案（无 RTL，模拟器建模）：以"行内是否包含已提交（commit）指令"为 usefulness 代理，动态区分统一 L2C 中的 useful/useless 代码行并驱动替换策略。所有代码行以最低优先级插入 L2C（DRRIP 的 RRPV=3），仅被识别为 useful 的行提升到 RRPV=0。硬件改动：(a) L1I 每个 tag 增加 1-bit send_hint，仅当 L2C→L1I 填充响应中的新增 1-bit l2_vulnerable_fill 标志指示该行在 L2C 处于 RRPV=3 时置位；(b) ROB 每 uop 增加 1-bit send_hint 位，随该行首条指令/首条 uop 沿流水线传播到退休（retire）阶段；(c) 退休时把 VA（复用恢复路径已有 VA）送回 IFU，经 8-entry Hint Lookup Queue HL1Q 在 FTQ 请求未占满 ITLB 带宽时机会式完成 VA→PA 翻译，再访问 L1I tag 检查并清除 send_hint 位（该行 L1I 生命周期内至多一次提升信号），随后经 8-entry HL2Q 与 LSU/数据预取请求仲裁，以 PA 访问 L2C 触发提升。L2C 管理规则（Table I，适用于任何 RRPV 类策略）：IFU 请求 miss→以 RRPV=3 插入；IFU 请求 hit→仅当 RRPV<3 才提升到 0（RRPV=3 的 hit 保持 3，等待 commit hint，避免再度提升 useless 行）；Hint 请求 hit→提升到 RRPV=0；Hint 请求 miss→无动作；其他请求→沿用 baseline 策略。存储开销合计 422B（Table II：L1I send_hint 位 256B、ROB 位 80B、HL1Q 43B、HL2Q 43B，l2_vulnerable_fill 不计），随 L1I 而非 L2C 规模扩展。
  - 实验比较：baseline（DRRIP+FDIP 的高端移动 CPU 模型）vs Emissary（code-aware L2C pinning，最优配置 max 25% ways 可 pin、概率 1/16）、UDP（TAGE confidence 过滤 FDIP 预取）与 FTQ-Size-OPT（每应用离线最优 FTQ 大小，作 UDP 动态 FTQ 尺寸的上界参照）、DJOLT（IPC1 冠军 L1I 预取器）；组合 Bumper+FTQ-Size-OPT、Bumper+DJOLT。消融：Bumper-L1I-Hit-Always（L1I hit 即发 hint、无 l2_vulnerable_fill 过滤）、Bumper-L1I-Hit（L1I hit + l2_vulnerable_fill）、Bumper-Always（用 commit 信息但无 l2_vulnerable_fill）。敏感性：L2C 1–16MB、L2-BTB 16K–64K entries。指标：IPC/加速比、L2C 行分类（useful/useless/other）占用率与生命周期（百万周期）、BPU MPKI、L1I/L2C 请求数分解（fetch/prefetch/hint）、SPEC 2017 与 Geekbench 上无副作用的验证、能量开销（定性）。
- 硬件平台是什么，配置是什么。
  - 模拟对象：工业级 cycle-accurate 模拟器（ARM ISA）建模的现代高端移动 CPU（Table III）：核心 620-entry ROB、32-entry FTQ、FDIP、16-wide fetch、10-wide retire；BPU = 64KB TAGE-SC + iTAGE、1K-entry L1-BTB、16K-entry L2-BTB、RAS；ITLB/DTLB/L2TLB = 256/224/4096 entries；L1I 192KB 6-way pLRU（与 L2C 非一致、无写回）；L1D 128KB 4-way pLRU；L2C 6MB 12-way DRRIP（按行类型优化插入/提升）；内存 DDR5-8800；非包含非独占 cache 层次；多个带自适应节流的协调数据预取器、5 级 radix tree 页表、MMU cache、硬件页表 walker；不建模 SLC。

  - 模拟高端移动 CPU 前端（BPU/FTQ/FDIP/IFU）与 cache 层次的逐周期行为，输出 IPC、MPKI、L2C 行分类与生命周期。修改点（论文在模拟器内实现）：L1I tag 增加 send_hint 位与填充响应 l2_vulnerable_fill 标志、ROB 增加 1-bit hint 标志、HL1Q/HL2Q 队列与 ITLB 机会式 Hint Request 翻译、L2C DRRIP 插入/提升规则修改（Table I）；对比方案 Emissary/UDP/FTQ-Size-OPT/DJOLT 亦在同一模拟器中建模。

  - 模拟原理与全过程：输入 = 12 个匿名真实移动应用（Table IV：搜索引擎客户端/社交视频/聊天/在线购物/内容创作/新闻/消息社交/手游 RPG/角色扮演/策略/竞速/MOBA；code footprint 0.5–2.3MB、data 2.0–15.0MB；建模团队选取性能关键场景，每场景 ≥100M 指令、充分 warmup）+ SPEC 2017 与 Geekbench。逐周期过程：BPU 预测基本块追加 FTQ → Fetch Head 弹 cacheline 地址发需求请求、FDIP 用剩余 L1I 带宽沿 Prefetch Head 发预取 → L2C miss 以 RRPV=3 安装、填充响应带 l2_vulnerable_fill → L1I 置 send_hint 位并随首条指令传至 ROB → 指令退休时 VA 回 IFU → HL1Q 机会访问 ITLB 翻译 → L1I tag 命中则清 send_hint 位 → HL2Q 仲裁后以 PA 访问 L2C 提升 RRPV=0。输出：平均加速 6.5%（较 Emissary +7.5%、FTQ-Size-OPT +5.4%、UDP 本身仅 1.2%、Bumper+FTQ-Size-OPT 再 +0.8%）；生命周期（useless 代码行 -57.9%、useful 代码行 +52.5%、其他行 +21.5%）；L2C 占用（useless 20.3%→9.5%、useful 12.9%→15.4%）；带宽（L2C IFU 请求 -1.8%、FDIP 预取流量 -5.7%、L1I 请求 +0.4% 平均/max 2.3%）；敏感性（L2C 1–2MB 加速 2.9–3.6%、4–8MB 5.1–6.8%；L2-BTB 16K→64K 下 Bumper 持续有效但与 baseline 差距收窄）；SPEC 2017/Geekbench 无性能损失；能量开销可忽略（422B 存储 + 可忽略的 L1I/L2C 流量增量）。
