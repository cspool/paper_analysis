## Reducing Page Faults via Invalidation-based Mapping Propagation in Multi-GPU Systems

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现是 ShadowUpdate——对 UVM 页迁移处理机制（migration handling mechanism）的硬件重设计，目标是消除 multi-GPU 系统中 access counter-based migration 下的 re-fault（页迁移后非目的 GPU 因映射被 invalidation 清除但未更新而再次触发页错误）。核心硬件新增是 IfMT（Inflight Migration Tracker），放在 L2 TLB 之后、GMMU 之前，由两部分组成：① UMPT（Updated Migration Page Table）——256 项全相联表，每项存 36-bit 虚拟页号 + 40-bit 物理页号 + 1-bit pending(P) 位，8 个并行比较器，最坏 32 cycle 查找；② Cuckoo filter——64 buckets × 4 slots × 11-bit fingerprint（xxHash 对 VA 哈希），两个候选 bucket 并行 1 cycle 检查，平均假阳性率 0.94%，用于快速筛选（无假阴性）避免每次 L2 TLB miss 都查 UMPT。机制原理：把"新物理地址"piggyback 到原本就广播到所有 GPU 的 invalidation 信号上，使每个 GPU 的 GMMU 在 invalidation 阶段（本来就为维护翻译一致性而遍历页表）同时完成 PTE 更新，从而既消除 re-fault 又不引入额外 page table walk；同时把 destination GPU 的 mapping 更新步骤提前并入 invalidation 阶段（两者分别占迁移处理延迟的 26.02% 与 30.35%，overlap 后整体迁移处理延迟降 22.79%）。正确性由 IfMT 保证：拷贝期间新映射已写入各 GPU 页表但被 IfMT 拦截，翻译请求挂起，拷贝完成后 copy engine 广播 completion 信号，各 GPU 清 Cuckoo filter fingerprint、驱逐 UMPT 条目，若 P 位置位则把存储的新 PA 直接返回 L2 TLB MSHR 完成翻译，不重放 page table walk。
  - 实验比较什么（baseline = 论文采用的 hardware-based mapping update 版 UVM，access counter-based migration，阈值 256）：① 整体性能：14 个 workload 平均 1.40×；② page fault 数：平均降 73.83%（re-fault 消除）；③ L2 TLB miss 延迟：平均降 41.92%；④ 迁移处理延迟：降 22.79%（invalidation 成本仅 +3.23pp，因 payload 增大与 IfMT 管理信号）；⑤ vs naive mapping propagation（拷贝后广播新映射但需额外 page table walk）：naive 1.26×、ShadowUpdate 1.40×，且 naive 使 GMMU PWQ queuing 延迟增至 baseline 的 1.25× 而 ShadowUpdate 降至 0.76×；⑥ vs SOTA：Trans-FW 1.22×、IDYLL 1.16×，两者组合（ShadowUpdate+IDYLL）相对 IDYLL 1.36×、相对 ShadowUpdate 1.18×；⑦ 敏感性：PTW 数（8/16/32 → 1.40/1.42/1.46×）、L2 TLB entries（256–4096）、UMPT entries（64→0.87×、128→1.19×、256 后饱和）、UMPT associativity（全相联 vs 16-way 0.63×）、GPU 数（8→32，1.57×@32）、memory footprint（×1/16 的 1.23× 到 ×16 的 1.36×）、2MB large pages（1.38×）、其他 CTA 调度（CTA Clustering 1.24×、LADM 1.26×）；⑧ LLM：Llama3-8B/Llama2-7B/Mistral-7B-v0.3/Deepseek-llm-7b-chat/Qwen-14B 的 QKV projection 平均 1.37×、FFN 平均 1.42×；⑨ 面积/功耗：Cuckoo filter 0.0243mm² + 1.5852mW（Synopsys Design Compiler + FreePDK 45nm），UMPT 0.8171mm² + 81.35mW（CACTI 7.0 @22nm），相对 AMD Fiji GCN3（596mm²@28nm）折算仅占 0.0016% 与 0.2221% 面积。
  - 硬件/模拟配置（Table I）：4-GPU 平台，每 GPU 16 SA × 4 CU = 64 CU；L1 TLB 32 项 32-way 1-cycle、L2 TLB 512 项 16-way 10-cycle；共享 GMMU：PWQ 64 项、8 个 PTW（host MMU 16 个共享 PTW）、PWC 128 项、每级 page table walk 100 cycle；L2 2MB 16-way writeback；DRAM 4GB 1TB/s 100-cycle；CPU-GPU 互连 32GB/s、GPU-GPU 互连 600GB/s；access counter 阈值 256；分布式 CTA 调度。

- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - MGPUSim（cycle-accurate multi-GPU 模拟器，ISCA '19 [67]，Sun et al.，已针对工业 GPU 验证 [4] AMD GCN 架构）：官方仓库 https://github.com/sarchlab/mgpusim （web search 确认，Go 编写，基于 Akita discrete-event 框架，支持 AMD GCN3，unified memory / page migration 模型、RDMA 引擎、分布式 CTA 调度；样例：samples/fir 下 `go build && ./fir -timing --report-all`，输出 metrics.csv 或 akita_sim_*.sqlite3）。
  - 面积/功耗评估工具：Synopsys Design Compiler + FreePDK 45nm [66]（Cuckoo filter）、CACTI 7.0 @22nm [10]（UMPT）。

- 模拟器模拟什么的性能，修改了什么。
  - MGPUSim 模拟什么：4-GPU UVM 系统端到端性能——CU 访存请求经 L1 TLB/L1 cache → L2 TLB → GMMU（PWQ 排队 → PTW 多级 page table walk → PWC 命中检查 → L2/GPU 内存取 PTE）；本地无映射则发 ATS 请求经 CPU-GPU interconnect 到 host IOMMU（16 PTW）完成集中式 page table walk 并返回远程映射；access counter 达阈值后触发页迁移（host 分配新页、广播 invalidation、TLB shootdown、copy engine 传输、更新 destination 页表、释放旧页）。输出每 workload 的执行时间、page fault 数、L2 TLB miss 延迟、迁移处理延迟、GMMU PWQ 排队延迟等统计。
  - 修改了什么：① 在 MGPUSim 中实现 access counter-based page migration（Volta/Ampere 策略，阈值 256）；② 实现 ShadowUpdate：在 invalidation 广播消息中携带新物理地址（piggyback），各 GPU GMMU 在 invalidation 的 page table walk 中同时写新 PTE；③ 新增 IfMT 硬件模型（UMPT 256 项全相联 + Cuckoo filter 64×4×11-bit，xxHash）；④ 迁移完成时广播 completion 信号清除 IfMT 条目并把 pending 翻译从 UMPT 直接返回 L2 TLB；⑤ 论文基线采用 hardware-based mapping update（对比 software-driven 广播：L2 TLB miss 延迟最多高 2.37×、性能低 1.38×，故选硬件方式作 baseline）；⑥ 大规模扩展（8–32 GPU）与 2MB large page、其他 CTA 调度策略（CTA Clustering、LADM）的模拟配置。

- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：MGPUSim 开源（https://github.com/sarchlab/mgpusim，Go + Akita，AMD GCN3，README 提供 build/run 示例）；ShadowUpdate 本身的实现论文未明确说明是否开源，未能确认公开仓库（无法确认）。workload 来自开源 benchmark 套件：AMD APP SDK [5]（MM/FW/BS）、DNN-MARK [19]（C2D/IM/LeNet）、HETERO [68]（FIR/AES/KM）、PANNOTIA [15]（MIS）、POLYBENCH [80]（MM3/MVT）、SHOC [18]（SpMV/BFS），由 MGPUSim 提供的 multi-GPU 版本、OpenCL 编译并移植到仿真环境。
  - 使用例子（MGPUSim，基于官方文档/论文）：① 安装 Go；② `git clone https://github.com/sarchlab/mgpusim && cd mgpusim/samples/<workload>`；③ `go build` 生成可执行文件；④ 运行 `./<workload> -timing --report-all`（-timing 打开时序仿真）；⑤ 从输出（metrics.csv / akita_sim_*.sqlite3）读取 kernel 执行时间、per-GPU 统计、cache hit/miss、RDMA 传输、DRAM controller 事务等；⑥ 对 baseline 与 ShadowUpdate 两套配置分别跑 14 个 workload，归一化得 Figure 13–27。配置参数（SA/CU 数、TLB/缓存容量、PTW/PWQ/PWC、互连带宽、阈值）在模拟配置文件中按 Table I 设置。
  - 模拟器输入到性能输出全过程（MGPUSim 原理）：输入 = OpenCL 编译的 workload 二进制（如 BFS、SpMV、GEMM）+ GPU 平台配置（Table I：每 GPU 16 SA×4 CU、L1/L2 TLB、GMMU 8 PTW/PWQ 64/PWC 128、L2 2MB、DRAM 4GB 1TB/s 100-cycle、600GB/s GPU-GPU、32GB/s CPU-GPU、阈值 256）→ Akita discrete-event 引擎逐事件推进：CU 发射访存 → L1 TLB/cache 命中则直接返回（1 cycle），miss 进 L2 TLB（512 项 10 cycle）→ miss 后请求进 GMMU PWQ（64 项，与其它翻译请求争用）→ PTW 逐级遍历页表（每级 100 cycle，查 PWC 128 项）→ 本地有映射：返回 CU 走数据 cache 查询；本地无映射（page fault）：经 CPU-GPU interconnect（32GB/s）发 ATS 请求到 host IOMMU（16 共享 PTW）完成集中式 page table walk（含 interconnect 往返与 host 排队）→ 返回远程映射，GPU 更新本地页表并重放请求 → 远程访问持续直到 access counter 达 256 → 触发迁移处理（五步串行；ShadowUpdate 下改两步合并：invalidation+映射更新并行，IfMT 挂起翻译，拷贝 600GB/s，completion 广播释放）→ 输出每 workload 的 execution time、page fault 数（cold vs re-fault 分类）、L2 TLB miss latency、迁移处理延迟、GMMU PWQ queuing latency 等，归一化到 baseline 得 Figure 13/14/15/16 及敏感性图。作用：在周期级精度评估"页迁移机制重设计 + 轻量硬件 IfMT"对 multi-GPU UVM 系统吞吐、翻译延迟与迁移开销的净收益，并指导 UMPT/Cuckoo filter 容量与相联度设计（256 项全相联最优）。
