## Revelator: Rapid Data Fetching via OS-Guided Hash-based Speculative Address Translation

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现是 Revelator——一种 hardware-OS 协同的投机地址翻译方案，用哈希建立可预测的 VA-to-PA 映射来隐藏地址翻译延迟。OS 侧：在 Linux buddy allocator 中加入 tiered hash-based 物理页分配策略（对每个 VPN 用同一哈希函数 CityHash(VPN, PID, seed_i) 依次尝试最多 N 个候选 PPN，命中空闲帧即分配，N 次都失败才回退常规分配器）；同时把同样的哈希分配应用于末级页表帧（PT frame 用单次尝试 H_1(VPN>>9)，因每个 PT frame 覆盖 512 个 VPN）。硬件侧：L2 TLB miss 后，MMU 内的轻量投机引擎用与 OS 相同的哈希电路和 tier seed 重新计算 N 个候选 PPN，拼上 page offset 生成候选 PA，在 PTW 完成前投机取数；对末级 PTE 也按 VPN>>9 哈希预测并投机取 PTE 帧，从而同时隐藏数据取数和加速 PTW。投机引擎带 speculation degree filter（memory utilization monitor 按各 tier 分配成功率阈值丢弃低效 tier + bandwidth monitor 按内存带宽压力动态决定发几个候选请求）。还支持：Revelator+THP（2MB 可用时先用哈希 2MB 分配，否则回退传统 THP，再回退 4KB 哈希，最后回退 buddy allocator）、虚拟化 Diagonal/Horizontal 投机（hypervisor 用 gVA 或 gPA 做哈希输入预测 hPA）、NUMA（policy-first node-scoped hashing：先按 OS NUMA 策略选节点 n*，只在 n* 地址范围内做哈希放置；硬件侧 dominant-driven speculation 用每节点计数器 C_n 估计 p_n，p_dominant≥0.8 时只在 dominant node 投机，否则配合 OS 维护的 Bloom-filter hint 表做 hint walk 对非 dominant 节点额外发一次投机取数）。正确性保障：投机取数仅装入私有 L2，PTW 解析后按 bounded address log 使错误投机失效并清除微架构痕迹。
  - 实验比较什么：与 8 个 SOTA 地址翻译方案 + 64K-entry L2 TLB 对比：THP（baseline）、ReserveTHP [105]（保留 2MB 区域按利用率提升）、SpecTLB [88]（基于保留大页的投机）、POM-TLB [107]（16MB 软件管理 L3 TLB）、L2 TLB-64K、ASAP [108]（页表数据连续布局做页表预取）、DMT [16]（虚拟地址直映射末级 PT 项）、ECH [19]（elastic cuckoo 页表并行 PTW）、Mosaic Pages [106]（Iceberg hashing 增 TLB reach）、SpOT [21]（基于任意大小连续映射的 SOTA 投机地址翻译）、Revelator、Revelator+THP。对比维度：① 单核性能（low/medium/high 三档内存碎片下 vs THP 与 SpOT，11 个 translation-intensive workload）；② 翻译延迟与数据取数延迟分解（Fig.14）；③ 哈希 tier 数与内存利用率敏感性（0-80% 利用率、1-5 tier）；④ 虚拟化（vs Nested Paging+THP 与 DMT，Horizontal/Diagonal/Full 三配置）；⑤ 多核扩展（4/8/16 核，30 个 Google 服务器 trace 混合，1.40×/1.50× vs THP，87-88% 投机准确率稳定）；⑥ NUMA（8 节点/64 核，spillover 0-50%，vs SpOT 最高 1.20×，隐藏 85-95% PTW 延迟）；⑦ 能耗（McPAT，Revelator+THP 较 THP 降 5.5%）；⑧ 真实 Linux 6.10.8 原型（tiered 分配成功率 70-85% 页、minor fault 开销仅 0.078% 总执行时间）；⑨ RTL 综合面积/功耗（0.02% 面积、0.03% 功耗 vs Intel Cascade Lake core）。
  - 模拟基线配置（Table 2）：8-way OoO core、ROB 300、x86-64 2.9GHz；L1 I-TLB 128 项 8-way 1-cycle；L1 D-TLB(4KB) 64 项 4-way、L1 D-TLB(2MB) 32 项 4-way 各 1-cycle；L2 TLB 2048 项 16-way 12-cycle；3 个 page structure cache 4/8/32 项 2-cycle；L1 64KB 8-way 4-cycle pLRU；L2 1MB 16-way 12-cycle pLRU；L3 2MB/core 16-way 35-cycle SRRIP；DRAM 128GB DDR4-2400 4 channel、2 ranks/channel、16 banks/rank、tCL=tRCD=tRP=14.17ns。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - Virtuoso（ASPLOS 2025 验证过的 imitation-based OS simulation 方法论，https://github.com/CMU-SAFARI/Virtuoso，MIT 协议，Revelator 的 artifact 在 revelator-artifact-release 分支），底层搭建在 Sniper（event-driven 多核模拟器，https://github.com/snipersim/snipersim）之上，DRAM 时序经 IPC bridge 对接 Ramulator2。论文修改 Virtuoso 建模 OS 层 tiered hash-based 分配、修改 Sniper 建模硬件投机引擎。哈希用 CityHash（https://github.com/google/cityhash），OS/硬件共用，2-cycle 哈希延迟。能耗用 McPAT（https://github.com/HewlettPackard/mcpat）。RTL 综合：投机引擎用 Chisel [140] 实现，Yosys（https://github.com/YosysHQ）综合，Nangate 45nm open standard-cell 库 [142]（OpenROAD-flow-scripts）。
- 模拟器模拟什么的性能，修改了什么。
  - Virtuoso 模拟什么：地址翻译的端到端开销——TLB 层级（L1/L2 TLB）、多级 page table walk、物理内存分配、page fault 处理，用 MimicOS（轻量 userspace kernel）只模仿必要内核功能（物理内存分配、页错误处理）而非跑完整 Linux，避免全系统 OS 模拟开销，同时暴露高层编程接口给新的 OS 内存管理例程；Sniper 提供 event-driven CPU 周期级模拟。输出每 workload 的执行时间、L2 TLB MPKI、投机覆盖率/准确率、地址翻译延迟、数据取数延迟、能耗等。
  - 修改了什么：① Virtuoso/MimicOS 侧实现 Revelator 的 tiered hash-based 分配器（Linux 6.10.8 buddy allocator 集成，O(1) 每分配，含 2MB 哈希分配/THP 回退/4KB 哈希分配/buddy 回退四级逻辑、NUMA policy-first node-scoped hashing、PT-frame 哈希分配、Bloom-filter hint 表）；② Sniper 侧实现投机引擎：哈希电路（CityHash，2-cycle）、候选 PA 生成（tier 顺序）、speculation degree filter（utilization monitor + bandwidth monitor）、per-NUMA-node 计数器 C_n、hint walk、投机 fetch 的 bounded address log 与 PTW 解析后的 invalidation；③ 按三档碎片（high/medium/low = 可用 2MB 页占总 2MB 页 10%/50%/90%，对应 22 节点集群约一个月、一小时、刚重启的上限测量）与 20% 基础内存利用率初始化实验。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：Virtuoso 开源（github.com/CMU-SAFARI/Virtuoso，MIT，README 明确 Revelation 在 revelator-artifact-release 分支，实现+共享基建在 main）；Sniper 开源（github.com/snipersim/snipersim）；CityHash 开源（github.com/google/cityhash）；McPAT 开源（github.com/HewlettPackard/mcpat）；Linux 6.10.8 开源；Chisel/Yosys/Nangate 45nm 库开源。Revelator 本身可经 Virtuoso 的 revelator-artifact-release 分支获取。
  - 使用例子（Virtuoso，基于官方文档）：① `git clone --recursive https://github.com/CMU-SAFARI/Virtuoso.git`；② `cd simulator/sniper/ && sh install_dependencies.sh && make distclean && make -j`；③ `sh download_traces.sh` 下载 trace 套件（GraphBIG/XSBench/GUPS/DLRM/GenomicsBench 与 Google traces）；④ `sh run_example.sh` 跑 baseline（4-level radix + ReserveTHP on sample trace）；⑤ 实验配置用顶层 `.cfg` 文件（address_translation_schemes/ 下，以 #include 组合 core model、MMU、page table、DRAM timing、allocator、spec engine、prefetcher、CXL 模块），实验集中定义在 clist.yaml（trace 套件、配置、指令数、参数扫描）；⑥ `experiments/create_experiments.py --yaml clist.yaml --suite <suite>` 生成 jobfile，`safe_submit.py` 提交（SLURM 可选），`get_experiments_status.py` 监控，`create_rerun_experiments.py` 重跑失败项。Revelator 场景：在配置中选 allocator=Revelator（tiered hash-based，N=3 默认）+ spec engine=Revelator（degree filter on），与 allocator=ReserveTHP/SpOT/ASAP 等组合跑同一 trace，300M 指令，归一化得 Fig.13-18。
  - 模拟器输入到性能输出全过程（Virtuoso+Sniper 原理）：输入 = trace（每 workload 300M 指令的访存流）+ 系统配置（Table 2 的 core/TLB/cache/DRAM 参数 + allocator/spec engine 模块选择 + 碎片与利用率参数）→ MimicOS 在 Sniper 上模拟内核内存管理（物理页分配走 tiered hash-based 例程、页错误处理），Sniper event-driven 逐事件推进（取指/执行、L1/L2 TLB 查询、miss 后发起 PTW——每级查 page structure cache/DRAM；Revelator 下投机引擎并行做 2-cycle 哈希算出候选 PA 并发出投机取数请求，投机数据装入私有 L2）→ 输出每 workload 的 cycle 数（→ speedup）、地址翻译延迟、数据取数延迟、L2 TLB MPKI、投机覆盖/准确率（87-88%）、被浪费的投机带宽；DRAM 时序由 Ramulator2 建模；能耗由 McPAT 从架构统计估算。作用：在周期级精度评估"OS 哈希分配 + 硬件哈希投机"这一跨 OS/硬件改动对翻译密集型系统整体性能的收益，以及投机 degree filter 对带宽/缓存污染的权衡，并验证其对碎片、利用率、核数、NUMA、虚拟化的鲁棒性。RTL 侧（面积/功耗）：Chisel 投机引擎 → Yosys + Nangate 45nm 综合 → 0.0149 mm²、14.723 mW 静态功耗 = Cascade Lake core 的 0.02% 面积 / 0.03% 功耗。
