## BoostX™-NTI Fast, Scalable and Flexible Storage Architecture with NVMe-TCP Initiator Acceleration

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现为 MangoBoost NTI（BoostX-NTI / StorageBoost NTI）：第一款全硬件加速的 NVMe/TCP 发起端（initiator）DPU 卡——单槽 HHHL 板卡、Xilinx Versal FPGA、75W 功耗包络、双 100GbE（全双工 200 Gbps）。FPGA 内三大 RTL/HLS IP：(1) NVMe Host Interface（NHI）——向主机暴露标准 NVMe PCIe 设备、硬件轮询 SQ doorbell、DMA 取 NVMe 命令/写完成队列；(2) NVMe/TCP Engine（核心）——Command Scheduler、PDU Header Generator、PDU Stitcher（Table handler + PDU payload receiver）、PDU Parser（PDU splitter + PDU header handler）、PDU Header Decapsulator、PRP table、PDU metadata table，完成 NVMe 命令/完成与 NVMe/TCP PDU 之间的协议转换并编排数据搬运；(3) TCP Offload Engine（TOE，基于同组 F4T ISCA'23 框架 [47]）。板载 sidecore（ARM）只做控制面（NVMe/NVMe-TCP admin queue、IP 配置、错误恢复），I/O 数据路径 100% 在 FPGA 硬件、数据只经片上 SRAM 不落板载 DDR。配套机制：Virtual buffer（元数据驱动的 TX/RX 缓冲替代——每连接仅数 KB 片上 SRAM 记录 {qid, virtual offset, PDU header} 元数据 + PRP 表，TOE 按 TCP 字节序读"概念性发送缓冲"时由 Table handler 拦截、查表、按需 DMA 从主机 NVMe data buffer 取 payload 现场拼接；RX 侧 PDU splitter 边收边切头/切数据、按 PRP 直写主机内存）；Dynamic handover（双向、按单队列粒度的 HW↔SW 切换，经 MMIO 寄存器交接最小上下文，出错队列单独复位重传、其他队列不断流）；Fault handler IP（置于 NVMe/TCP Engine 内部及与 NHI/TOE 的边界，监控错误寄存器、硬件自愈可恢复错误或上报软件）；热管理（AMD CIPS IP 的 System Monitor 测温，达阈值 90% 时主动节流 + 经 NVMe admin completion 向主机报警）。
  - 实验比较 4 类方案：(a) 软件基线——Linux kernel NVMe/TCP initiator（Linux-SW）与 SPDK NVMe/TCP initiator；(b) sidecore 基线——NVIDIA BlueField-3 SNAP（16 ARM 核全卸载）；(c) sidecore+加速——SNAP+XLIO（TX 零拷贝旁路）；(d) 高性能传输对照——kernel NVMe/RDMA initiator（RoCEv2）。指标：FIO 4KiB/128KiB 吞吐（line-rate 百分比）、50:50 混合负载、host 核心效率（每核吞吐）、MLPerf™ Storage 得分（ResNet50/CosmoFlow/UNET-3D，A100/H100 模型）、vHost 云环境聚合带宽扩展（1/4/8/16 核）、PostgreSQL pgbench TPS 与延迟（64–500 clients）、Multipath/ANA 故障切换、热管理、1-to-N 多目标压力测试、Versal 资源占用（LUT/FF/BRAM/URAM）。
- 硬件平台是什么，配置是什么。
  - NTI 卡：单槽 HHHL、Xilinx Versal FPGA、75W。资源占用（Table II，Versal 总量 900K LUT/1.8M FF/1341 BRAM/677 URAM）：Total LUT 520K(57.8%)、FF 954K(53.0%)、BRAM 828(61.7%)、URAM 208(30.7%)；分项：NHI 36K LUT/103K FF/76 BRAM/0 URAM，NVMe/TCP Engine 195K LUT/446K FF/464 BRAM/74 URAM，TOE 225K LUT/332K FF/264 BRAM/132 URAM，Peripheral 63K LUT/73K FF。硬件 I/O 处理能力最高 5000 万 IOPS（足够 4KB 小块 I/O 饱和 1.6 Tbps 链路）。
  - 发起端服务器：Supermicro SYS-421GE-TNRT3、双 Intel Xeon Gold 6438N（64 核）、512GB DDR4；目标端：Supermicro ASG-1115S-NE316R、AMD EPYC 9454P（48 核）、384GB DDR5、16× Samsung PM1743 SSD；双机 Ubuntu 22.04.5 LTS、kernel 5.15.0-119-generic。网络：NTI 卡或 Mellanox ConnectX-6 Ex NIC，经 Dell PowerSwitch Z9432F-ON（32×400GbE）互连；Multipath/ANA 实验用 2×100GbE 双链路。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - 论文不使用模拟器：全部评估在真实 FPGA DPU 原型卡 + 真实服务器集群上完成，无 RTL 级仿真/模拟环节（与多数架构论文不同）；资源占用来自 Vivado 对 Versal 的实际综合实现报告，性能均为端到端实机测量。无模拟器链接。
- 模拟器模拟什么的性能，修改了什么。
  - 不适用（无模拟器）。TOE 复用同组 F4T 框架 [47]（ISCA'23）、NHI 复用 FVM [69]（OSDI'20）的设计，但 NTI 版本的 RTL/仿真环境论文未提供，修改点无法逐条确认。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - NTI 的 FPGA RTL/位流与 SDK 私有组件不开源（MangoBoost 商业产品，论文未给开源链接）。开源部分是配套软件栈：Mango SDK 文档（https://sdk.mangoboost.io/docs/guide/docs_storageboost_nti/guide/ ，FPGA vendor id 0x1f52、最多 18 个 NVMe 子系统、经 mango-ctl soc push/pull 配置）、OPI 生态开源桥 opi-mangoboost-bridge（Apache-2.0，OPI 标准命令翻译为 Mango SDK/SPDK RPC，https://explore.market.dev/ecosystems/grpc/projects/opi-mangoboost-bridge ）、nvme-cli 的 MangoBoost vendor 插件 PR（https://github.com/linux-nvme/nvme-cli/pull/2798 ）。评估工具全部公开：FIO（https://git.kernel.dk/cgit/fio ）、SPDK（https://spdk.io ）、MLPerf Storage（https://mlcommons.org/benchmarks/storage/ ）、pgbench（https://www.postgresql.org/docs/current/pgbench.html ）+ PostgreSQL on xfs。
  - 实机评估原理与全过程（替代模拟器流程）：输入 = FIO job（4KiB 随机读/写、32 线程、128–256 queue depth；128KiB 顺序；50:50 混合）或 pgbench/MLPerf Storage 负载 + 主机未修改的 NVMe 驱动栈。执行路径：主机向 NHI 暴露的标准 NVMe 设备提交命令 → NHI 硬件轮询 doorbell 并 DMA 取命令 → Command Scheduler 按策略映射 NVMe 队列到 NVMe/TCP 队列（并行性 round-robin / 隔离 1:1 优先）→ PDU Header Generator 生成 PDU 头并抽取 PRP 入表 → PDU Stitcher 的 TX virtual buffer 以元数据拦截 TOE 发送读请求、经 PRP table 按需 DMA 主机数据拼接 PDU → TOE 完成 TCP/IP 封装经 100GbE 发出 → 目标（SPDK/kernel target，16× PM1743）回包 → TOE → PDU splitter 顺序扫描 TCP payload 切分 PDU 头/数据 → PDU header handler 按 opcode 分发、查 PRP 表得目的地址 → DMA 直写主机 NVMe data buffer → PDU Decapsulator 提取 completion 经 NHI 写 CQ。输出 = 吞吐/IOPS/延迟与每核吞吐：NTI 4KiB 50:50 达 line-rate（vs Sidecore 9.17×、vs Sidecore+XLIO 2.81×），128KiB 50:50 双向合计 356 Gbps（vs 6.59×/1.56×）；核心效率 vs kernel initiator 4KiB 3.01×/1.98×/2.11×/1.66×（read/write/70:30/50:50）、128KiB 16.7×/4.38×/8.76×/5.35×；vs NVMe/RDMA 吞吐最高 1.24×（4KiB）、核心效率 4KiB 2.00×/1.96×/1.65×/1.24×、128KiB 1.28×/1.16×/1.32×/0.82×；MLPerf Storage 平均 1.34×、最高 2×（UNET-3D/H100）、达本地 SSD 91.6%；vHost 1/4/8/16 核吞吐 2.64×/2.41×/1.71×/1.10×；pgbench TPS +17.0%/+23.5%/+19.6%（64/128/256 clients）、最高 +30.3%（500 clients）、延迟 -14.5%～-23.1%；active/active 故障后经存活路径重传恢复 200 Gbps、ANA 状态切换微秒级完成；1-to-N 多目标压力下持续饱和线速。
