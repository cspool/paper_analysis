## sCROOGe Circuit-level Design and Optimization Framework for RISC-V Out-of-Order GPUs

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现为在开源 RISC-V Vortex GPGPU 框架内，首次以可综合 SystemVerilog RTL 同时实现 frontend 与 backend 两种 Out-of-Order (OoO) 指令重排执行方案（此前方案均仅在软件仿真器中评估）：(1) Frontend 方案（类 GhOST/SIMIL，在 Issue 阶段重排）——Issue Buffer (IsB，可配 4-12 entry) 缓存译码后指令；In-Flight buffer (InFL) 记录已越过 IsB、尚未写回的指令目标寄存器（warp ID + 分配位）；Dependence Checker 通过比较 IsB 指令的 3 个 rs 与 InFL/IsB 的 rd 检测 RAW、rd 间比较检测 WAW、IsB 内 rd vs rs 检测 WAR，生成依赖位向量；Issue Arbiter 从 "independent instructions" 池选指令（无独立指令时退化为按 UUID 的 per-warp 最老指令）。省略了 GhOST 的 IBuffer 与同步控制 flag；调度优化后直接只向 arbiter 供给独立指令，从而移除 "per-warp oldest" buffer、scoreboard 的 SRAM 阵列及其逻辑。(2) Backend 方案（类 LOOG，在 Operand Collect/OC 阶段重排）——Collector Units (CUs，可配 4-14) 作 Reservation Stations 保存指令元数据与操作数；Register Alias Table (RAT) 通过寄存器重命名（寄存器名→RRS ID）消除 WAR/WAW 并跟踪 RAW；Register Renaming Stack (RRS，轻量标识符存储) 使 CU 在 Dispatch 后即可释放（一个 CU 面积约 21.382µm² 即总面积的 2.28%，一个 RRS entry 仅 0.873µm² 即 0.09%）；Dispatch arbiter 每 cycle 从 ready CU 池选一个进 Execute；写回经 broadcast + RRS 中间缓冲，eop 信号触发 RAT 更新与 RF 写。删除了 baseline 的 Scoreboard 阶段。配套设计优化：(i) UUID 生成单元——每 warp 递增的指令编号嵌入指令直到 Commit，循环复用 UUID + MSB 过渡（11→00、00→01）越界检测，避免全相联 reorder buffer；(ii) OC 阶段 broadcast pipelining——在广播 RRS 与接收方之间插入中间结果寄存器，把 3×N×R×T×datasize 的互连降到 4×N×T×datasize（N=CU 数、R=RRS entry 数、T=threads/warp），12 个以上 CU 时用双缓冲分接两组 CU；(iii) frontend 独立指令调度（前述）；(iv) LSQ 内存指令重排——实现后测出最大加速上限 <1.1%（LSQ_size×T² 比较器、单 cycle 派遣惩罚），面积/功耗开销 8.7%/9.3%，故从最终实现中排除。
  - 实验比较：22 个 Vortex 框架自带 benchmark（Fig. 10）上的 baseline（in-order Vortex 流水）vs frontend OoO vs backend OoO，并做 {warps=4..64, threads=4..32} × {IsB=4/8/12, CU=4/8/10/12/14, RRS} 的设计空间扫描；ML workload（llama2-Gemm 即 llama2-48M 的 FP32 FMADD 张量运算、CNN-Layer 即 AlexNet 卷积层、SqueezeLayer 即 SqueezeNet Fire 模块 1×1 卷积、llama-260k 即 260k 参数 llama 端到端推理，后两者来自 Tango Suite 与 ggml-org tiny-llamas）加速比。指标：IPC/speedup（backend 通用负载最高 27.3%、ML 最高 53%，frontend 平均 6.7%）、stall 分解（新增 sched/exu/OC/dpnd 硬件计数器，frontend/backend 总 stall -11.8%/-14.8%，sched stall -51%/-61%）、面积/功耗开销（frontend 峰值 7.5%/8.2%，backend 28.6%/32.1%）、ADP/EDP（最优 12.4%/27.9%）、iso-area 对比（backend OoO 相对增加并发 warp 数的同面积 in-order baseline 平均 IPC +14.4%）、memory hierarchy 敏感性（L1/L2 容量、icache、bank 数）、多 SM weak scaling（1/2/4 SM）、ILP 分析（平均 ILP 2.02-2.92）、memory reordering 加速上限、以及 vs Accel-Sim 的仿真精度校准（Rodinia-3.1 与 Deepbench 在 NVIDIA Tesla V100 上实测，Accel-Sim MAPE 11.55%、Deepbench 超 30%、GRU RNN 达 73%）。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - 模拟器：Vortex GPGPU（开源 RISC-V GPGPU 框架，https://github.com/vortexgpgpu/vortex，基准 commit abdea91）——sCROOGe 直接在其 RTL 中扩展实现；RTL cycle-accurate 性能仿真用 Verilator（https://www.veripool.org/verilator/）；DRAM 建模集成 Ramulator（https://github.com/CMU-SAFARI/ramulator）；软件栈沿用 Vortex 的 POCL（OpenCL 前端编译）+ LLVM（生成应用二进制）。ASIC 流程：Synopsys Design Compiler v2022.12（综合，GF 22nm FDSOI，TT corner/0.9V/25°C）、Synopsys PrimeTime + VCD 切换活动（功耗，含 UPF）、GF Memory Compiler（SRAM 宏）、Cadence Innovus v23.11（全 PnR，400 MHz 保守时钟），并扩展至 IMEC N2 2nm GAA nanosheet pathfinding PDK（1.2 GHz）。
  - 论文同时用 Accel-Sim（https://github.com/accel-sim/accel-sim）作为仿真精度对照（V100 实测 vs 仿真的 cycle 误差）。
- 模拟器模拟什么的性能，修改了什么。
  - Verilator 对 Vortex+sCROOGe RTL 做 cycle-accurate 仿真，输出 per-kernel 总指令数与 cycles（性能评估指标），速度数百 MHz，比 Accel-Sim（数 KHz）快 5 个数量级；修改内容即论文主体：在 Vortex 六段流水（Schedule→Fetch→Decode→Issue→Execute→Commit）中加入上述 frontend（IsB/InFL/Dependence Checker/Issue Arbiter/UUID）与 backend（CU/RAT/RRS/broadcast/UUID）OoO 组件、删改 Scoreboard/IBuffer/仲裁逻辑，并新增 stall 性能计数器。综合/门级层面：DC 综合后门级仿真 + PrimeTime 分析 VCD 得到面积/功耗/频率；Cadence Innovus 做 PnR 交叉验证；N2 PDK 验证 2nm 节点趋势。
  - DRAM 部分由 Ramulator 模拟访存时序（Vortex 与 sCROOGe 集成 Ramulator 建模 DRAM 行为）。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：是（artifact 公开）。Zenodo https://doi.org/10.5281/zenodo.19453033 提供 Docker 容器镜像（>32GB RAM、>120GB 磁盘，内含全部 SystemVerilog OoO 实现源码、22 个 benchmark 源码与数据集、预计算动态指令 trace 与中间 .csv 文件、/home/reference 参考图）；Vortex 本体 https://github.com/vortexgpgpu/vortex（commit abdea91）。ASIC 工具（DC/Innovus/PDK/Memory Compiler）因 NDA/许可无法分发，只提供面积/功耗 .csv。性能实验全量重跑最长约 270h（单进程，Fig.14 约 100h）。
  - 使用例子（模拟器输入到性能输出的全过程）：① 安装 Docker Engine（https://docs.docker.com/engine/install/ubuntu/）→ 运行 download.sh 拉取容器镜像 → 进入容器；② 执行 /vortex/ci/blackbox.sh，以 bash 脚本选项传入所需执行方案（OoO scheme：frontend/backend/无 RRS 的 backend 变体等，详见 /vortex/README.md，另可指定专用硬件计数器与 build flags）——脚本在 /vortex 内用 POCL 把 OpenCL kernel 编译为 LLVM 应用二进制（无预编译二进制）；③ 应用二进制经 Vortex 软件栈（含 Ramulator DRAM 模型）驱动 RTL，由 Verilator 逐周期仿真（cycle-accurate、同步频率、建模流水线各阶段时序），输出 per-kernel 总指令数与 cycles（覆盖 Fig.1、6、9-24 对应实验）；④ 生成的中间 .csv 覆盖容器内预计算文件，绘图脚本生成验证图。ASIC 部分：SystemVerilog → DC 综合 22nm（SRAM 用 Memory Compiler 宏）→ 门级仿真验证功能 + PrimeTime 分析 VCD 切换活动估功耗 → Innovus PnR（400 MHz）交叉验证 → 与 N2 2nm 结果一并输出面积/功耗/频率表（Fig.19-24、Table III/IV）。模拟原理：RTL 层面逐周期推进流水线状态机与互连，反映真实门级结构（如 OC 广播互连、RAT/CU/RRS 容量限制、写回 eop 时序），相比高抽象软件仿真器能捕获频率退化与 pipeline timing 变异性，输出 IPC、stall 分解、面积/功耗/EDP/ADP 等 PPA 指标。
