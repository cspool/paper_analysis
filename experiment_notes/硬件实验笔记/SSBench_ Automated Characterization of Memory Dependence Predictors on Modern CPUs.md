## SSBench: Automated Characterization of Memory Dependence Predictors on Modern CPUs

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现：SSBench——首个跨平台自动识别与表征现代 CPU 上 Memory Dependence Predictor（MDP，存储器依赖预测器）硬件结构的自动化框架。MDP 是乱序 CPU 中预测 store-load 数据依赖、决定 load 是否可绕过（Speculative Store Bypass）执行的微架构部件，设计未公开文档化。SSBench 由三层组成：① workflow-based MDP taxonomy（维度1 表项选择：L=仅 load IP、SL=store+load IP、HSL=含历史信息；维度2 状态机：S=有状态、nS=无状态，共 6 类，覆盖 20 个已知设计 [2][9][12][18][27][30][32][39][41][42][46][47][49][57]-[62][74]）；② 自动识别算法——利用 MDP 定时侧信道（Bypass S / Block B / Rollback R 三种执行时延）加 DBSCAN 聚类（minPts=100, ε=2）判定 MDP 存在性与设计类型；③ 自动表征算法——counter-based model solver（单计数器状态机 7 参数：upd_{0t}, upd_{1f}, upd_{0f}, upd_{1t}, bnd, ovf, unf, ths，Algorithm 1 自动搜索边界条件 x1..x6 构造不等式组 EQ1..EQ7 求解，可扩展到双计数器）与 store-load bounce 法（在指令页上用分支跳转构造不同 IP 的 store-load pair，自动反推 hash 函数、表大小、相联度、index/tag 位与替换策略，Algorithm 2）。实现语言：Python 测试套件（scikit-learn 做 DBSCAN、pulp 做方程求解、numpy 做矩阵运算）+ C/汇编微基准原语（JIT 用 mmap/mprotect 生成指令页）。
  - 实验比较：① 跨平台部署 30 台真实 CPU（10 Intel、4 AMD、5 Arm、8 Apple 大小核、3 RISC-V），输出每颗 CPU 的 MDP 设计类型（L-S/SL-S/L-nS）、状态机参数、hash 函数、表组织（size/way/tag/index/替换策略），识别出 3 种设计类别共 14 种 MDP 配置；② 与人工逆向（prior work：Intel [51][35]、AMD [37]、Arm/Apple [36]）比较揭示新发现（Table VIII）：Intel 12 代起表项 256→512、index 位 8→9；AMD 首次识别出多路相联 MDP 与不同替换策略（Zen3/4/5 为 LRU/FIFC/NLRU）、用物理 IP 索引 + 12-bit stride hash、状态机 ths>0（需 3 次误预测激活）；Cortex-A76 首次发现状态机（初始化 14、dependence 不更新、independence 递减）；Apple MDP 首次发现为 SL-S 设计（3-bit 计数器，dependence 加 1、independence 减 1，hash 后的虚拟 IP 作 tag）；③ 安全测试（Table III）：进程/特权隔离、chaining（状态传播）、无延迟 store、单 load、speculative 更新五类性质；④ 运行时（Table IV）：单 CPU 全程 <2 小时（i13ra 2531.59s，hash 测试占 95.5%），hash 测试时间随搜索地址空间线性增长、org 测试随表大小/相联度增长。
- 硬件平台是什么，配置是什么。
  - 真实 CPU（Table II）：Intel 10 颗——i7-6700K (Skylake)、i7-7700K (Kaby Lake)、i5-8400/i7-9700 (Coffee Lake)、i7-10700 (Comet Lake)、i7-11700 (Rocket Lake)、i9-12900K (Alder Lake)、i9-13900K/i9-14900K (Raptor Lake)、Xeon Gold 6438Y+ (Sapphire Rapids)；AMD 4 颗——EPYC 7543 (Zen 3)、Ryzen 7950X (Zen 4)、Ryzen 9950X (Zen 5)；Arm 5 颗——Cortex-A53/A55/A510/A72/A73/A76（含 Raspberry Pi 4B 的 A72）；Apple 8 颗——M1/M2/M3/M4 的 performance (P) 与 efficiency (E) 核；RISC-V 3 颗——OpenC910 core、Spacemit X60、SonicBOOM（后两者用 RTL 模拟器）。时序原语按平台：Intel rdtscp、AMD rdpru、Arm PMCCNTR（内核 PMU 模块）、Apple S3_2_c15_c0_0（内核修改）、RISC-V rdcycle；核绑定 Linux taskset / macOS pthread_set_qos_class_self_np。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - RISC-V 侧用 RTL 模拟器验证：SonicBOOM（https://github.com/riscv-boom/riscv-boom，UC Berkeley 乱序 RISC-V 核，在 gem5 中运行，gem5: https://www.gem5.org/）、OpenC910（https://github.com/T-head-Semi/openc910，平头哥玄铁 C910 开源 RTL 核）；论文只说明 "we use the RTL simulators [25], [78]"（gem5/SonicBOOM），未明确说明对模拟器做了什么修改（未开源模拟器改动）。
  - 主要"测量载体"是真实硬件本身的定时侧信道：SSBench 不用传统性能模拟器，直接在真实 CPU 上运行微基准测周期（Fig.6 的 store-load pair，用乘法链延迟 store 地址生成放大时序差）。RTL 模拟器仅作已知 MDP 设计的 ground-truth 验证（验证 SSBench 识别/表征算法能否正确恢复）。
- 模拟器模拟什么的性能，修改了什么。
  - 论文未明确说明对 gem5/SonicBOOM/OpenC910 模拟器的修改内容；用途是作为已知 MDP 设计的 ground-truth 平台，验证 SSBench 对"非真实 CPU 型号"（如 SL/HSL、双计数器状态机等设计）的识别与表征能力。真实 CPU 侧的"性能探测"即定时侧信道：执行受控 store-load pair，测量 S（bypass）/B（block）/R（rollback）三种时延分布，经 DBSCAN 聚类与统计推断恢复 MDP 内部状态与组织。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：SSBench 开源（https://github.com/CPU-Security/SSBench，Apache-2.0，Python 为主，web search 于 2026-08 确认）。仓库结构：main.py（入口）、lib/（Python 测试套件 exist.py/hash.py/org.py/sm.py + utils/ 求解器）、src/（C/汇编微基准）、data/（结果）、tools/arm-pmu-enable（Arm PMU 内核模块）。使用：① Intel/AMD：安装 Miniconda，./build.sh 后 conda activate ssbench-env；② Arm：先 sudo make && sudo insmod pmu_enable.ko 加载 PMU 模块；③ Apple：需 PacmanPatcher 内核 patch 启用 PMU。运行 `python3 main.py -c <core-id>`（自动检测架构）或 `-a <arch>`（intel/amd/arm/apple/neoverse），无 root 加 `-u`（物理地址映射可能不准，影响 hash 推断）。
  - 输入到输出全过程（真实 CPU 定时侧信道原理）：输入 = core-id/架构 + JIT 生成的 store-load pair 微基准 → 依次执行测试套件：exist.py 固定 store/load IP 执行 100 N_P（独立 pair）+ 100 D_P（依赖 pair）取 200 时延样本，DBSCAN 聚类出 S/B/R，按 max(T0)≤min(T2) 且 min(T1)≥max(T2\T1) 判定 MDP 存在；sm.py 用 Algorithm 1 自动搜索计数器越界边界 x1..x6，构造不等式组 EQ1..EQ7 用 pulp 解出状态机参数（如 Apple M4 P 核 store_sm=[0,-1,7,1,7,1,0,0]，store_seq="4a"）；hash.py 用 store-load bounce 收集同 hash 碰撞地址集 X，构造差分矩阵 R（地址 XOR 位矩阵），求 nullspace 得 hash 函数矩阵（如 Apple hash_func=[[2],[3],[4],[5],[6],[13],[7,14],[8,15],...]），解不出则回退物理地址 hash；org.py 构造最小 eviction set（2 的幂倍增避免全局禁用 MDP + 线性搜索），按 Algorithm 2 判定 index/tag 位、表大小/相联度，用"最小 eviction set + 4 项"测 Π 置换模式匹配 Table I（FIFO/LRU/Tree-PLRU/NLRU 的 (0,1,2,3) 等模式）判定替换策略 → 输出 data/characterization.json（结构化字典：exist、type_time_dict（S/B/R 时延区间与 b1-b3 边界）、state machine（store_sm/load_sm 整数数组）、hash（矩阵 + hash_va + expected_sm_val）、org（eviction_set_size、size/set/set_index、replacement_policy 与 confidence）、time（各阶段耗时），如 Apple M4 P 核 size=69、set=1、lru）。作用：自动化恢复未文档化的 MDP 微架构参数，支撑 MDP 安全研究（MDP-Gates/MDP-CF/MDP-CC 三个攻击）。
