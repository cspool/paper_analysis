## HBM-CASO: A Coordinated Approach to HBM System-Level and On-Die ECC

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现 = HBM-CASO 是现代 HBM（HBM3/HBM3E/HBM4）上新增的一种保护模式（可写入 DRAM mode register，全局静态启用或按块动态启用），在保留 baseline ODECC 正常工作的前提下重组片上 ECC 资源以容纳更强的系统级 ECC（SysECC），包含三个硬件技术：(1) Codeword Merge（Merging Unit，Figure 3(b)）：基于 RS 码线性性质（regional H 矩阵行是 local H 矩阵行的线性组合，p_regional_0 = p_local_0 + C * p_local_1，C 由 H 矩阵决定），把两个 local RS(18,16) 码字合并成一个 regional RS(34,32) 码字——原 4B local ODECC parity 被压缩为 2B regional parity，省出 2B 空间；同时把原 4-bit CRC 通道改用来传输 advanced SysECC（如 global RS(68,64) 的 4B parity），填满 8B parity 空间。Merging Unit 乘法在 GF(2^8) 上用 bitwise 逻辑实现，非常轻量（较 baseline ODECC 仅 1.51% 逻辑开销），且不跨 pseudo-channel（p_local_0/p_local_1 来自同一 32B 区域）。CRC parity 可选存/不存于 metadata 空间：存时写操作中 CRC 单元反向工作（生成 parity 填充 4B metadata），读操作中做错误检查；(2) Delayed Write Verification（Accumulation Units）：由于 HBM 无资源解码 advanced SysECC，写操作不再逐条 CRC 校验，而是两个独立 Accumulation Unit（均匀分布在两个 pseudo-channel）对每 64B 写生成的 2B regional + 2B CRC parity 做 bitwise XOR，累加进 64-bit 寄存器；内存控制器并行做同样累加，最后一条写后把控制器侧 64-bit XOR 结果随最后一条写传输并与 HBM 内结果比较，不匹配则重传整批写（需把写 buffer 扩展到 batch 大小）。批大小典型 32~64 次传输（burst 256~512），64-bit XOR 仅占一次 burst，且可在写-读 turnaround 期间传输；未检出冲突率仅 2^-64，强于 baseline 每 32B 用 16-bit CRC；(3) Decoupled Read Protection：把 ECC 解码分离成 error detection 与 correction 两阶段，读数据（regional codeword）在 HBM 内只用检测（复用 Merging Unit 重新生成 parity 与存储 parity 比较，同 [79] 思想），检测到错误则发 alarm 信号（或 "catchword" 特殊数据模式）给处理器；控制器收 alarm 后发起特殊访问、通过加长 burst 取回全部 parity（regional + CRC，类似 DUO [18]），在控制器侧做 tiered error correction（见 V-C）。三种模式 L/R/G-mode 分别用 local RS(18,16)、regional RS(34,32)、global RS(68,64) 作为 SysECC；也支持 16-bit symbol 的 RS(18,16)（Baseline(16b)），通过 p_regional_0 = p_local_0L + α^8 * p_local_0H 把 16-bit parity 折叠成 8-bit。
  - 实验比较：HBM-CASO R-mode（片上 RS(36,34)*，系统 RS(34,32)）与 G-mode（片上 RS(36,34)*，系统 RS(68,64)）对比两个 baseline（Baseline(8b)：片上 RS(19,17)*+CRC-8，系统 CRC-8；Baseline(16b)：片上 RS(19,17)*+CRC-8，系统 CRC-16）及四个代表性方案：DUO [18]（系统 RS(72,64) 直接取代 ODECC）、Config-ECC [10]（两层 ECC：片上 CRC-24 + 系统 RS(72,70)）、COMET [3]（片上 SECDED(76,68)* + 系统 SECDED(104,96)）、Domain-ECC [78]（系统 RS(544,512)，针对 AI 负载）。比较维度：(1) 可靠性——15 种代表性错误模式（SBF/BBF/WBF/SAF 四类故障组合）下每模式 10^9 次 Monte Carlo 注入，解码结果分为 DCE/DUE/SDC（Table III）；传输错误检测未检出率 UE%（Table IV）；六年前瞻生命周期模拟（10^12 cacheline，FaultSim 操作模型，3 小时注入间隔、12 小时 scrubbing，permanent-only p=10^-4 与 mixed p=10^-5/t=10^-5 两种配置，Figure 7）。关键结果：R/G-mode 在 2SBF 达 100% DCE（baseline 仅 76.57%/56.27%），4SBF 下 G-mode 仍 98.95% DCE，R/G-mode 全部场景无可观察 SDC，G-mode 传输 UE% 全为 0；Year 6 G-mode DUE 1.6×10^-3、SDC 1×10^-10（mixed 下 5×10^-12）。(2) 硬件开销——Synopsys Design Compiler 45nm 综合（Table V）：OD 侧仅 +61 cells/+17μm²（较 baseline 4027 cells/1113μm²），MC 侧 R-mode 2100μm²/0.21ns 检测/2.52ns 纠正，G-mode 5910μm²/0.47ns/4.56ns；DUO 需 9637μm²/4.77ns，Domain-ECC 169Kμm²/19.84ns。(3) 性能——Ramulator2（Table II HBM3 参数，tCL 增加 0.25ns/0.51ns 建模 R/G-mode）：R-mode、G-mode 接近 baseline（<0.5% 开销，Figure 8(a)），DUO 最高 12%、Domain-ECC 超 25%；错误率 10^-4 时 R/G-mode 约 2%/5% 开销（Figure 8(b)）；batch size 16~256 扫描最坏 ~3%（Figure 9）；32B 粒度下 G-mode 的 RMW 开销在写比 20%、BW 90% 时约 1%（Figure 10）。(4) 功耗——DRAMSim3 评估（Figure 11）：R-mode <0.1%、G-mode ~0.2%，Domain-ECC 5~8%、DUO 最高 15%。

- 模拟器模拟什么的性能，修改了什么。
  - Ramulator2 模拟 HBM3 内存系统的端到端性能：CPU/GPU 侧内存请求经 memory controller（FR-FCFS 调度、64 项读缓冲/64 项写缓冲、RoBaRaCoCh 地址映射）→ HBM3 时序（16 channels、16 banks、row 1024B、BL=16、峰值带宽 819.2 GB/s，tRC-tRCD-tRP-tRAS: 45-18-16-29，tCL-tFAW-tBURST: 16-16-1.25，tCCDS-tCCDL-tRRD: 1.25-2.5-2），输出各方案下 workload 的执行时间/归一化性能。修改内容：(1) 按 Table II 配置 HBM3 模型（时序取自 [1] folded banks HBM 设计）；(2) 为 R-mode/G-mode 把额外访问延迟建模进 tCL（+0.25ns/+0.51ns，来自 45nm 综合结果）；(3) G-mode 在 32B 细粒度访问下实现 read-modify-write（RMW）适配（G-mode 推荐 64B 粒度）；(4) 延迟写验证的批重传逻辑（batch size 16~256 扫描）与错误率注入（BER 10^-8/10^-6/10^-4）。DRAMSim3 用各 scheme 一致的时间参数评估功耗（IDD4R=839mA、IDD7=958mA、Iact=36mA），输出归一化功耗开销。ECC 编码器/解码器（local/regional/global RS、CRC-8/16、SECDED 等所有对比 scheme）用 Synopsys Design Compiler 45nm 综合出面积与延迟；片上检测延迟被 full correction path 管线覆盖（subsumed），MC 侧仅在检测到错误后才触发完整纠正。

  - 模拟器输入→输出全过程（以 G-mode 性能评估一次 64B 写批次为例）：输入 = (a) GPU memory trace：由 NVBit 在 GPU 上对 workload（Rodinia StreamCluster/NW、GNN GAT Cora/GCN Cora、HPC LAMMPS LJ/PENNANT、GEMM Softmax/Base、DLRM High Batch/High Dimension，Table II）动态二进制插桩采集的访存请求序列（32B/64B 访问）→ (b) Ramulator2 配置：HBM3 时序 + FR-FCFS + 64 读/64 写缓冲 + RoBaRaCoCh + G-mode 的 tCL+0.51ns 与 RMW 逻辑 → (c) scheme 参数（系统 RS(68,64)、片上 RS(36,34)*、batch size、错误率）。模拟推进：请求进入 memory controller → FR-FCFS 调度，写请求批量化（32~64 transfers）→ 每 64B 写由控制器侧生成 global parity 并 XOR 累加进 64-bit 寄存器 → HBM 侧 ODECC 生成 regional parity 同步累加 → 批内最后一条写附带控制器侧 64-bit XOR 结果（写-读 turnaround 期间传输）→ 若与 HBM 内累加不符则整批重传（延长执行时间）→ 读请求在 32B 粒度下触发 RMW（读-改-写合并以匹配 64B ECC 编码粒度）。输出 = 各 workload 的归一化执行时间/吞吐（相对 baseline）、错误率扫描下性能曲线、batch size 16~256 的性能矩阵、写比扫描（Stream/Random 微基准）的 RMW 开销。原理：Ramulator2 以 HBM3 时序精确建模访存生命周期（激活-读/写-预充电、bank 冲突、总线仲裁、读写 turnaround），把 ECC 方案的延迟/带宽/重传/合并开销映射为时序与总线占用，从而量化相对 baseline 的性能代价——结论是 R/G-mode 延迟写验证与合并逻辑几乎不占关键路径，只有错误率 >10^-4 或 32B 细粒度高写比时才出现明显开销。
