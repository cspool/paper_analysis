## SMOOTH: Hardware-Assisted Fine-Grained On-Chip Memory Management for Efficient On-Device LLM Inference

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现：SMOOTH（SMOothing I/O Traffic with Hardware support），一套硬件辅助的片上 SRAM/scratchpad（SPM）细粒度内存管理框架，针对移动 NPU 上 LLM 自回归解码的突发性（bursty）访存与碎片化问题。核心是 Verilog 实现的硬件 Dynamic Memory Controller（DMC），含五个轻量模块：find_zero（查找最长空闲连续块区）、alloc（预取并分配块）、free（回收过期块）、block_table_lookup（块表地址翻译）、address_check（连续区直通检查）。三大设计点：① 细粒度 block-based 分配——以与硬件处理单元对齐的固定大小块（默认 1 KB，可按模型维度设置）管理 SPM，把逻辑张量组织与物理 SRAM 布局解耦，消除外部碎片；② 低开销地址翻译——direct-mapped block table（每项存 p_blk 物理块地址、cont 连续块数、use_cnt 编译器标注的剩余使用次数）+ bitmap 空闲表，address_check 模块对连续映射区旁路块表直通访问（dual-mode hybrid：碎片时走 block-virtualized 细粒度模式，连续时走 zero-overhead 快路径）；③ 硬件驱动 early reclamation——buffer 跟踪 ISA 执行进度，对某块的末次访问发出 end_cmd 信号，DMC 递减对应 use_cnt，为 0 即提前回收，并按 N_preload = ⌊(U×BW)/Block_size⌋（U 为空闲 compute cycle，BW 为硬件动态测量的可用带宽）利用空闲带宽做细粒度预取。编译器只做静态 lifetime 分析标注 use_cnt，动态分配/回收交给 DMC。
  - 实验比较：5 种片上内存管理策略——Compiler-Ideal（理想化编译器策略：best-fit 分配 + 全图 liveness 分析 + 对每层每算子穷举 512B–4MB tile size 选最小延迟，模拟 XLA 式行为）、Capuchin（硬件管理 64-byte cache，按运行期访问模式以 cache-line 粒度动态预取）、Gemmini（全栈 DNN 加速框架，pipelined 分配，重叠 input/output tile 做字节级预加载）、SMOOTH-Base（仅 block 分配、无 early reclamation）、SMOOTH-ER（block 分配 + early reclamation，即完整 SMOOTH）。指标：TTFT、TTLT、ITL、SRAM occupancy、hit tile 比例、N-th token 生成能量、硬件面积/功耗/时序。结果：TTFT 较 Compiler-Ideal 平均降 41.4%、最高 59.2%；TTLT 较 Compiler-Ideal 平均 43.2%/最高 60.0%，较 Gemmini 平均 49.1%/最高 73.0%；较 SMOOTH-Base 平均 +24.0%；能量较 Compiler-Ideal/Gemmini/Capuchin 平均降 44.0%/51.2%/39.9%（Gemmini 1K→32K 从 28.1%→70.7%）；控制逻辑面积开销仅 compute 0.0023% + SRAM 侧 0.095%（相对估算 NPU 面积），模块功耗亚纳瓦级、32K 序列总开销峰值 15nJ。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - LLMCompass（cycle-accurate LLM 推理模拟器，https://github.com/PrincetonUniversity/LLMCompass，ISCA'24），其底层为 ScaleSim（systolic array 模拟器，https://github.com/scale-sim/scale-sim，pip 包 scalesim==2.0.2）。
- 模拟器模拟什么的性能，修改了什么。
  - 模拟 mobile NPU（按 Qualcomm Hexagon V73 HMX/HVX + LPDDR5 配置，Table III：940 MHz、1 core、32×32 Matrix Engine、32-lane Vector Engine（32 ALUs/lane）、2/8/32 MB SRAM、16/32/64/128 GB/s DRAM 带宽，batch=1）上 transformer 模型 prompt + generation 阶段的 cycle 级延迟与能量。修改：在 LLMCompass 中集成 end-to-end SRAM 管理器，支持基于地址的 block 分配（block table + bitmap）、end_cmd 早期回收、idle 带宽检测与细粒度预取；编译器侧做静态 lifetime 分析为 tile 标注 use_cnt。额外在真实移动平台（Samsung Galaxy S25+/S24 Ultra、Google Edge TPU、NVIDIA Jetson AGX Orin 的 Constrained-SoC 配置：EMC 512MHz≈32GB/s、GPU 714MHz≈5.5TFLOPS）用 Geekbench 6 与 QNN/edgetpu_compiler/NVCC 做动机 profiling（非 SMOOTH 本体）。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：SMOOTH 开源（https://github.com/skkim-caslab/SMOOTH，tag [ISCA 26]，DOI https://doi.org/10.5281/zenodo.20020344）。AE 环境：Docker（Ubuntu 22.04，推荐）或 Conda（Python 3.9 + scalesim==2.0.2（严格版本约束）+ PyTorch 2.0.0 + matplotlib/pandas/seaborn）+ 宿主 Yosys/OpenSTA 综合；ASAP7 7nm PDK 仓库自带。模拟器用结构化元数据（层数/维度/head/量化位宽）而非真实权重，无需外部数据集，磁盘约 10GB、48 核 CPU 约 20 小时，Docker 内自动设 $SMOOTH_HOME。
  - 使用例子（SMOOTH AE 复现流程）：① `cd $SMOOTH_HOME/src/policies && bash run_all_policies.sh`（默认 15 核，可改 NUM_CORES）——对 Compiler-Ideal/Capuchin/Gemmini/SMOOTH-Base/SMOOTH-ER 各跑 LLMCompass 仿真，产出各模型、各序列长度（seq_1…seq_32K、默认 8MB SRAM）的延迟/能量日志；② `cd $SMOOTH_HOME/src/ae/figure14 && python plot_ttft.py ../../../data/seq_1/8MB` 归一化 TTFT（Fig.14）；`cd $SMOOTH_HOME/src/ae/figure16 && python plot_latency.py ../../../data/seq_32K/8MB` 得 TTLT（Fig.16）；③ `cd $SMOOTH_HOME/src/ae/figure20 && python plot_energy.py` 得 N-th token 能量（Fig.20）；④ `cd $SMOOTH_HOME/src/verilog && bash run_all.sh` 用 Yosys+ASAP7 综合 5 个模块；⑤ `cd $SMOOTH_HOME/src/ae/table1 && python get_area.py`、`cd $SMOOTH_HOME/src/ae/table2 && python get_power.py` 产出 Table 1/2 面积与功耗/时延。
  - 模拟原理（LLMCompass，基于论文+官方文档）：LLMCompass 以 transformer 结构元数据（层数、d_model、head、量化 w4a8/int8）为输入，调用 ScaleSim 对每个算子做 systolic array 的 cycle 级时序仿真（ScaleSim 按数据流/访存模式与阵列几何计算每算子 cycle），并内置自动 mapper 生成性能最优的 mapping/schedule；SMOOTH 把内存管理建模进该时序——DMC 按 bitmap 找空闲块、block table 翻译虚拟地址到物理 SRAM 地址、buffer 在块末次访问发 end_cmd、use_cnt 归零提前回收、idle 周期按 N_preload 预取后续权重/KV。输入到输出全过程：模型元数据 + 硬件配置（Table III）+ 内存策略 → 逐层仿真 QKV/FlashAttention/FFN 融合 kernel 的 compute 与 off-chip 访存（区分 prompt 期 GEMM 高 OI 与 decode 期 GEMV 低 OI 的交替）→ 输出每层 cycle/能量、TTFT/TTLT/ITL、SRAM occupancy、hit tile 比例 → 归一化绘图。面积/功耗：Verilog RTL 经 Yosys 用 ASAP7 7nm 标准单元综合，OpenSTA 静态时序分析，输出各模块面积（合计 memory 侧 13,050 μm²）与时延（find_zero 364.4ps、alloc 1508.2ps、addr_check 83.7ps、bt_lookup 615.2ps、free 654.6ps）和功耗（pW 级）。
