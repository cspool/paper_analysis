## LÆGIS: Pinpointing and Addressing Performance Overheads of GPU-based Confidential Computing

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现为 LÆGIS：面向 GPU-based Confidential Computing（CC）下 UVM 页迁移加密的硬件-软件协同架构。核心硬件改动：(i) HBM 内显式 IV Bank——在每个 GPU HBM stack 中预留逻辑区（每 stack 512K 行、每行 128-bit、共 8 MB = 4 个 big page），按 VABlock（2 MB）粒度存 IV Bank Entry（IBE）；IBE 由 19-bit ID + 77-bit 随机值 RV + V/D/O/R 控制位 + 9-bit CTR 组成。IV 不再随访问顺序同步递增，而是通过查找 IBE 重建，把加密与 CPU-GPU 同步解耦，支持乱序/提前加密，且无需完整性树（HBM 假设可信）；(ii) 片上 IV cache（16 项、全相联、20-cycle 命中延迟、LRU，256B SRAM = L2 的 0.02%）；(iii) GPU 侧 CE/GMMU 路径上的流水 AES 引擎（用 AES(K_h2d, RV||ID||blkidx||0^15) 构造 128-bit 输入生成 OTP 做加密/解密）；(iv) CPU 侧预加密调度器——利用 driver 线程的 false idle（fault preparation 期间）与 true idle（批次间空闲）机会预加密页面。ID 复用页目录 PDE0 中 19 个未用位存于页表；IV Bank 通过固件管理的物理地址映射散列到各 HBM 通道/bank（8 通道 × 16 bank 交错，1 KB row 存 64 个 IV、64 行/bank 落在单 sub-array），支持 4 KB/64 KB/2 MB 页粒度与 VABlock-LRU 换出（换出时 RV 递增并刷新整块）。
  - 实验比较：Baseline（现有 GPU CC 硬件：加密同步且位于关键路径、4 KB 粒度、TBNp 默认预取 Pt=51%）vs Ideal（加密开销完全隐藏、仅留系统级 batch 开销）vs 四个 LÆGIS 变体 F-LÆGIS（false idle 预加密）、IR-LÆGIS（true idle 随机选页）、IN-LÆGIS（true idle 按 fault buffer 选页）、IFN-LÆGIS（完整版：false+true idle，先 fault buffer 候选再顺序预加密 CPU 驻留页），以及 aggressive prefetching（Pt=1%）变体 pBaseline/pIdeal/pF-/pIR-/pIN-/pIFN-LÆGIS；另评估 CPU 侧加密能力增强：X-Baseline/X-IFN-LÆGIS（CPU 侧硬件 AES，复用 TME-MK AES-XTS 引擎重配置为 AES-GCM，40-cycle fill、16 B/cycle）、MT-Baseline（CPU 多线程加密约 7 GB/s）。结果：IFN-LÆGIS 平均 2.22×（最大 3.13×）、pIFN-LÆGIS 平均 2.74×（最大 5.05×）、X-pIFN-LÆGIS 平均 3.57×（最大 6.82×，2DCONV）；Ideal 相对 Baseline 2.36×、pIdeal 相对 pBaseline 4.60×（揭示加密是首要瓶颈）；IFN-LÆGIS 与 Ideal 差距仅 5.8%。性能分解（kernel/batch 处理/PCIe 传输/CPU 加密/GPU 解密/IV 访问六分量）显示 LÆGIS 消除 CPU 加密开销、以更大突发提升 PCIe 利用率，同时 GPU 解密延迟与 fault preparation 仍占主要时间（提示 fault prep 缩短会削弱预加密收益的权衡）；IV 访问因 per-page 粒度局部性高开销可忽略。driver active 占比：IFN 53.2%、pIFN 88.3%（SSSP 99.4%、FLASHATT 96.8%）。
- 硬件平台是什么，配置是什么。
  - 纯模拟评估（GPGPU-Sim），物理 CC 平台仅用于 profile 采集。GPU 配置（Table II-A）：80 SMs、64 warps/SM、共享 GMMU、私有 TLB、crossbar 网络；L2 1 MB（64 KB/bank）、128B line（32B sector）、120-cycle 延迟；8 GB HBM2（1 stack）；页大小 4 KB base / 2 MB big；PCIe 64 GB/s per direction；Pt=51%（默认）/1%（aggressive）；Bf=128；driver 线程切换 2 µs；IV cache 16 项全相联 20-cycle LRU；fault preparation 时间与 idle 时间按物理 profile 逐 base page 与 Pt 注入。HBM2 内存节点（Table II-B）：8 GB 4-Hi stack、8 channel、16 pseudo channel、1 KB page、FR-FCFS、16 banks、4 bank groups/channel、128-bit 接口（BL4/channel）、8 channel @1GHz 共 256 GB/s、CL:RCD:RAS:WR:RP=14:14:33:16:14、静态映射 RR.RRRRRRRR.RRRRRRRB.BBCCBDDD.CCCSSSSS。真实 CC 硬件（Table II-C，仅 profile）：CPU 5th Gen Intel Xeon 6530 Gold @2.1GHz（32 核）；Supermicro SYS-421GE-TNRT3；Linux 6.2.0-mvp10v1+8-generic + OpenSSL v3.0.2；QEMU 7.2.0（TDX patched）+ TDX 1.5（tag 2023ww15）；NVIDIA H100、PCIe 5.0、CUDA 12.4、Driver 550.163.01。
- 模型是什么。数据集和bench分别是什么。
  - 无 ML 模型训练/推理环节；负载为 UVM 页迁移敏感的应用：16 个应用来自 UVMBench [129]、Rodinia [130]、Parboil（Auto-tuning a High-Level Language [131]）等广泛使用的 UVM 基准套件，另加一个 CNN workload 与独立 FlashAttention kernel（FlashAttention-2 [132]）。文中点名：GEMM、2DCONV、3DCONV、NW（Needleman-Wunsch）、SSSP、SYRK、FLASHATT、CNN。这些负载产生大量页故障且计算/访存模式多样，在先前 UVM 研究中被广泛采用。输出指标为相对 Baseline 的归一化 speedup（含几何平均）。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源：https://github.com/insight-cal-uva/laegis-isca26-artifact （顶层 MIT，子目录各自许可）。仓库含三部分：nvidia-550.163.01（instrumented NVIDIA kernel driver 树，含 HOWTO.txt，复现 Fig.3/4/Listing 1/Fig.15 的 UVM profile）、gpgpu-sim-uvm（修改版 GPGPU-Sim + UVM 支持，复现 Fig.8/12/13/14/16）、benchmark（论文主结果应用）。注意：LÆGIS 实现细节（Fig.12/13/14/16 对应代码）被有意从公开 artifact 移除，需联系作者 yangyang@virginia.edu。GPGPU-Sim 上游：https://github.com/gpgpu-sim/gpgpu-sim_distro；UVMSmart [20] 提供虚拟内存模型（共享 GMMU + batch 处理）。
  - 模拟器：GPGPU-Sim v4.2（基于 commit-id 84c6cf4），扩展 UVMSmart 虚拟内存支持。修改内容：加入 UVM batch handling 模型（fault batching、可调预取阈值、tree-based 预取）；显式建模 fault preparation 时间、driver 线程 idle 窗口、页加密性能（用真实硬件在不同预取/batching 阈值下采集的 profile 注入）；CPU 侧加密用实测 kernel-space UVM 加密吞吐（约 1.3 GB/s）建模，GPU 侧用 CE/GMMU 路径上的流水 AES 引擎建模；IV Bank 建模为 HBM-resident 元数据 + 固件管理地址映射 + 片上 IV cache（hit/miss 跟踪 + 简单写回策略）；实现用 idle 窗口选择候选页的预加密调度器。
  - 模拟原理与输入→输出全过程：输入 = UVM 应用 kernel（GPU 指令）+ GPU/HBM2 配置 + 物理 profile（fault prep 时间、idle 时间、加密吞吐，随 Pt/Bf 变化）+ 加密方案参数（Baseline/F/IR/IN/IFN × Pt=51%/1%）。原理：cycle 级推进——GPU SM 执行 kernel 访存 → 未命中 PTE 触发 replayable fault → GMMU 聚合进 fault buffer（Bf 个一批）→ 中断 CPU driver → ISR 取 fault 信息并预处理（fault preparation，时间为 profile 注入）→ driver 线程按 batch 服务：Baseline 在关键路径上对每个 4 KB 页做同步 AES-GCM 加密（CPU 侧 1.3 GB/s 吞吐 + IV 同步开销）→ 经 PCIe（64 GB/s）DMA 到 GPU → GPU CE 用硬件 AES 解密写回 HBM；LÆGIS 则在 idle 窗口（false：fault prep 期间；true：批次之间）由预加密线程对候选页（fault buffer 下一批 / 顺序 CPU 驻留页 / 随机页）提前加密，加密时从 CPU IV Bank 按 ID 取 IBE 重建 IV，预加密页到达时标记 ready 跳过关键路径加密、批量写 bounce buffer 提升 PCIe 突发 → 统计各阶段周期（kernel 执行、batch 处理、PCIe 传输、CPU 加密、GPU 解密、IV 访问）→ 输出相对 Baseline 的 speedup 与性能分解。作用：在无真实 CC 硅片的情况下 cycle 精确量化同步加密的关键路径开销，验证 HBM IV Bank + 乱序预加密消除该开销的收益，并支撑与 Ideal、多线程（MT）与硬件加速（X）方案的对比结论。
