## Patterns behind Chaos: Forecasting Data Movement for Efficient Large-Scale MoE LLM Inference

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现（Case Study 1，wafer-scale GPU 架构）：基于对 4 个 SOTA MoE 模型的数据移动 profiling 洞察（Insight 3 专家放置感知任务分配 + Insight 1/2 时序可预测性），做轻量架构修改：(1) 两级层次化 Command Processor——wafer 级 Global CP + 每 die 的 Local CP，Global CP 维护全局 Expert Distribution Table（每专家初始 die ID + n-bit 分布状态码，指示专家在哪些 die 上）与 cross-token heatmap（跨 token 专家激活历史，50MB 存 Global CP DRAM、0.5MB on-chip cache 一次缓冲一层）；(2) 扩展 D2D controller 增加 Address Translation Unit（ATU，4.25KB 68-bit）和 Prediction Unit（PDU，Prediction Table 128B 16-bit，字段 cp_en 是否应本地缓存 + is_local 是否已缓存），实现 hardware-managed HBM：自动把预测的远程热门专家复制到本地 HBM，后续访问由 ATU 把远程地址翻译成本地地址直接读本地 LLC/HBM。Global CP 在每次 kernel 启动时运行任务分配算法（Algorithm 1）把 MoE kernel 按专家请求拆成 per-die 子 kernel，并运行数据驱动预测器（从 heatmap 当前选择行取 top-n 专家预测下一 token 热门专家，生成 cp_en 指导）。single-GPU-like 编程模型（整 wafer 当单一 GPU，软件无感知，类似 HDPAT/Hecton）。
  - 实验比较：Base（EP-like 数据放置，专家均匀分到各 die，但 wafer 当单一 GPU、不感知 die 位置和专家选择偏斜）、EP（每个专家计算分配到其所在 die，消除 D2D，如 MoEntwine）、以及三个变体 Allo Only（仅任务分配）、Pred Only（仅数据驱动预测器）、Allo+Pred（两者结合）。指标：MoE decode 阶段吞吐（归一化到 baseline）、hop count 减少比（跨 die 通信 Manhattan 距离和）、DRAM 访问 breakdown（本地读/远程读/本地写）、与 host CPU 分配的开销对比、面积功耗。
  - 结果：Allo+Pred 平均 6.6x 吞吐提升（Deepseek 7.0x、Kimi 8.2x、Llama 7.3x、Qwen 4.1x）；Dojo 拓扑 6.0x、TSMC 7.5x；batch 16384 时比 EP 快 1.44x；hop 数减少 213x（Pred Only 4.5x、Allo Only 142x）；面积功耗开销 <0.04%（总 6.13 mm² / 8588.61 mW，25-die wafer，支持 100 层 512 专家/层）。
- 硬件平台是什么，配置是什么。
  - 无真实 wafer GPU，使用自研 Python 事件驱动多 chiplet GPU 模拟器。模拟两种拓扑：Tesla Dojo 5x5 2D mesh 和 TSMC SoW 8x3 2D mesh（System-on-Wafer，最多 24 compute die + 96 HBM die）。每 die H100-like：1000 TFLOPS FP16、80GB HBM、3.35TB/s 本地 HBM 带宽、1.7TB/s D2D 相邻带宽、989 TFLOPS（Table I 中 "Cmpt Power per Die (FP16)"）；Dojo-Enhanced 配置每 die B300-like：4500 TFLOPS、180GB、8TB/s DRAM、2TB/s D2D。公共参数：LLC hit 100ns、LLC miss penalty 110ns、LLC write 30ns、LLC 64MB；D2D latency 200ns；XY routing；每个 remote request command+address 16B；本地 HBM 访问 300ns；预留 10% DRAM 给系统管理。用真实 8xH100 DGX 测量校准模拟器，误差 <5%。

  - 自研多 chiplet GPU 模拟器（论文说明现有工具不满足：Gem5、gpgpusim、mgpusim 精确建模单 GPU 但对 20+ die、batch>15000 太慢；ASTRA-sim 支持多 GPU 但缺微架构细节且不支持 single-GPU-like 编程模型）。开源：https://github.com/zhongkaiyu/waferscale_gpu_moe_sim（DOI 10.5281/zenodo.19617713，Apache-2.0，CPU 可运行，Python ≥3.10 + numpy/pandas/matplotlib，≥64GB RAM，约 80GB/模型、300GB 全部 4 模型磁盘，单模型模拟 8-12 小时、全模型 18-36 小时，确定性可复现）。
- 模拟器模拟什么的性能，修改了什么。
  - 模拟所有 die 的 LLC、HBM、计算单元、D2D 链路，中央资源管理器捕捉跨 die 的竞争与拥塞，支持 single-GPU-like 编程模型。输出 MoE decode 层吞吐（MoE 层 throughput）、hop count（跨 die 通信距离和）、DRAM 访问 breakdown。修改/新增模块：Global CP（Expert Distribution Table 4.5KB 72-bit + cross-token heatmap，A76 core 估计）、Local CP（A72）、D2D controller 中 ATU + PDU、hardware-managed HBM 的远程/本地数据读取流程（非复制远程读：D2D 路由→PDU 查 Prediction Table 决定复制→数据给 SM→需复制则写 LLC+本地 HBM、ATU 更新地址、is_local=1；复制后本地读：ATU 翻译地址→重定向 LLC→返回 SM）。kernel 启动流程：Global CP 跑任务分配算法拆 sub-kernel + 预测器生成复制指导→发 Local CP→Local CP 分配 SM 并配置 PDU 表→计算后收集专家复制统计回 Global CP 更新分布表。面积功耗评估用 Yosys（寄存器综合）+ CACTI（SRAM 建模），缩放到 5nm 匹配 H100 制程。
  - 模拟器输入到性能输出全过程：输入 = 每 token 每层每专家的专家选择 trace（expert_reqs_dict：每个专家的请求数）、专家到 die 的动态分布（expert_die_map，来自 Expert Distribution Table）、die 拓扑与带宽/延迟参数；任务分配算法按请求数升序排序专家（先小专家）、对每个专家生成候选 die 列表（存专家权的 die + 相邻 die）、按 cost model（DRAM 访问 + 计算 + D2D 通信）以 50 请求/块为单位选最优 die 分配并更新负载、块合并成最终分配计划；预测器从 heatmap 找当前选择对应行取 top-n 预测下一 token 专家；D2D controller 据此在本地 HBM 复制/读取专家权重；模拟器统计各 die 计算负载、跨 die 流量（hop count）、DRAM 本地/远程读写次数，输出 MoE decode 吞吐与 hop 减少比，从而量化 6.6x 吞吐提升与 213x hop 减少。
