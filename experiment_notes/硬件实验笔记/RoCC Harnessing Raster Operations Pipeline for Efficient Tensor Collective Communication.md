## RoCC Harnessing Raster Operations Pipeline for Efficient Tensor Collective Communication

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现是 RoCC——把 GPU 中高度空闲的 ROP（Raster Operations Pipeline，光栅化管线）单元改造成集体通信（CC）引擎，实现 LLM 训练中 GEMM 计算与 CC（AllReduce/AllGather/AllToAll）的细粒度重叠。硬件改动：① 先反向工程 V100/A100 的 ROP 微架构（SASS 微基准 + SR_CLOCKLO 时钟计数）：ROP 原子操作与 SM 异步执行（指令发出即返回）、ROP 数据通路延迟 V100 28 cycle / A100 22 cycle、单流水级延迟 V100 3 cycle / A100 1 cycle、ROP 内 4 路 32-bit 标量并行；② 每条 CC 操作新增一条 ISA 指令（ROP_AR/ROP_AG/ROP_A2A），经既有 atomic 指令数据通路下发，带 warp ID 与输出 tile 地址，配合每 CC 一个 intrinsic（如 rocc_allreduce(src,dst,size,dataType,opType)）与 RoCC descriptor（SrcBase/DstBase/DataSize/LocalRank/TensorDim/TileShape/CollType/DataType，存于每 MPU 片上专用 buffer）；③ collective primitive decomposition：CC → 5 种 primitive（send、recvReduceSend、recvReduceCopySend、recvCopySend、recv，遵循 NCCL ring 算法）→ 5 种 ROP μOp（ReadDoorbell、Write、DepBarrier、Add、RingDoorbell），由 collective decoder 与 primitive decoder 两个查找表译码（3 操作×15 阶段×3-bit + 5 primitive×6 μOp×3-bit = 225 bit，投影共 1KB 查找表），decoded μOp 进 4 条目 collective command buffer（每执行单元一条，66B，每 cycle 发 4 个 μOp）；④ doorbell 消息机制：doorbell manager（7 状态状态机，2 个 1-bit 比较器 + 2 个 32-bit 寄存器 + 4-bit 计数器 + 4-bit 比较器）+ 32 条目 doorbell buffer（每条目含 Offset/PayloadAddr/SrcRank/Stage，3-bit 状态共 96 bit），SM 经 doorbell 触发 ROP、ROP 间经 doorbell 包（携带 tile 数据 payload）跨 GPU 接力，doorbell region 每 MPU 预留 4KB（32 条目×128B）；⑤ symmetric tensor allocation（SymMalloc 自定义分配器）：把 CC tile 映射到各 GPU 相同物理地址，避免跨 rank 地址翻译，找不到对称帧时回退虚拟地址方案。硬件开销：doorbell buffer 0.75KB + collective command buffer 66B + descriptor buffer 77B + 1KB 查找表 ≈ L2 slice 面积的 2.4%（CACTI v7.0）。
  - 实验比较什么：① 总体性能——baseline（GEMM 与 CC 在 SM 上顺序执行）vs RoCC-Serial（drop-in rocc_* API，CC 单独 kernel 触发）vs RoCC-Overlap（warp 级 intrinsic 细粒度重叠，本文方案）：4 GPU 下 9%/48%，8 GPU 下 27%/54%，平均 18%/51%；② 重叠率：平均 83.4%（未重叠部分来自首段 GEMM 与末段 CC）；③ 争用分析：并发 CC 使 GEMM 仅慢 6.25%；④ CC-only 延迟（RoCC-Serial vs SM baseline，按消息大小）：大消息下 AllReduce 35%、AllGather 11%、AllToAll 25% 加速；⑤ 与 SOTA 硬件方案 T3（DMA + 双模 HBM-PIM）比较：T3 23% vs RoCC 48%（RowLinear 差距最大，因双模 PIM 在 GEMM 访存与 PIM 归约间争用）；⑥ 与 oracle 软件重叠（20% SM 专用于 CC）比较：RoCC 平均高 23%；⑦ 敏感性：ROP 数减半/减四分之一 → -3.7%/-5.4%；互连延迟 2×慢/2×快 → -6.5%/+2.5%；SM 侧 ROP 部署（ARM Mali/TU102 式）→ 31%；ROP cache 2×/4× → +4.8%/+5.5%；⑧ 端到端模型加速（Astra-Sim + Chakra trace）44%；⑨ 大规模 32/64/128/256 GPU → 20%/21%/13%/13%（GPT-3，8 GPU tensor 并行组 + 数据并行）；⑩ 多样化架构：H100（24 ROP、132 SM、50MB L2、3.35TBps、900GBps NVLink）与 B200（2 chiplet、48 ROP、148 SM、126MB L2、8TBps、1.8TBps NVLink）比 V100 额外 +3%/+2%。真实机 profiling：4× V100 NVLink 上训练 Qwen2-7B（FlashAttention + HuggingFace），11476 个 kernel 中仅 141 个发过 atomic 指令、其中仅 28 个是 GEMM，GEMM 内 atomic 平均占比 ≈0.0183%，证明 ROP 空闲；libsmctrl 测 SM 分区对 GEMM 的影响（80% SM 时 GEMM 慢 20%）。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - MGPUSim（主评估，周期级多 GPU 模拟器，ISCA 2019，https://github.com/sarchlab/mgpusim，Go + Akita 离散事件框架，MIT）：论文以 NVIDIA V100 为 baseline 配置、H100/B200 作敏感性配置，并扩展 MGPUSim 支持 SM-initiated kernel 与 NCCL 式 ring collective（实现 AllReduce/AllGather/AllToAll）。baseline 模拟参数：80 SMs/GPU、L1D 128KB 4-way 16 MSHR、L1I 32KB、L2 6MB 16-way 64 MSHR、XBar NoC 32B flit、64 MPU（LLC slice，参照 [22][59][63][64]）、每 MPU 1 个 ROP（1KB ROP cache、28-cycle 数据通路、4 个 3-cycle ALU）、4 并发 doorbell、GPU-GPU 300GBps full-mesh、CPU-GPU PCIe Gen4 x16 ≈150 cycle、DRAM ≈900GBps（tRC=24,tRCD=7,tRP=7,tCL=7,tWL=2,tRAS=17,tRRDl=3,tRRDs=2,tFAW=20,tRTP=3,tCCDl=1,tCCDs=1）。
  - Astra-Sim（端到端与大规模扩展，网络中心分布式 DL 训练模拟器，ISPASS 2020，https://github.com/astra-sim/astra-sim，官方站点 https://astra-sim.github.io/）：用开源 Symbolic Tensor Graph（STG）生成器（https://github.com/astra-sim/symbolic-tensor-graph，Georgia Tech synergyLab）生成 Chakra 执行 trace，改写执行图以支持 RoCC 细粒度重叠；Chakra（https://github.com/mlcommons/chakra，MLCommons 标准执行 trace 格式）。
  - 面积评估：CACTI v7.0（https://github.com/HewlettPackard/cacti）。
  - 反向工程工具：TuringAS（SASS 汇编器，源自优化 batched Winograd 卷积工作）、NVIDIA V100/A100 实测（driver 570.133.20、CUDA 12.1）、libsmctrl（SM 分区）、PyTorch distributed API + NCCL。
- 模拟器模拟什么的性能，修改了什么。
  - MGPUSim 模拟什么：多 GPU 平台上 SM-initiated GEMM kernel 与 NCCL 式 ring collective 的周期级执行——SM 计算、L1/L2 cache、NoC crossbar、MPU（含 L2 slice + ROP）、DRAM controller、GPU-GPU 全连接互连与 CPU-GPU PCIe，输出 GEMM/CC 阶段执行时间、重叠比例、GEMM 与 CC 争用下的性能、CC-only 延迟、端到端每模型加速比。
  - 修改了什么：① 在 MGPUSim 中建模 RoCC 的 ROP 扩展——新增 ROP_AR/ROP_AG/ROP_A2A 指令译码与触发路径（doorbell flag 识别）、RoCC descriptor buffer、doorbell manager（识别/分配 doorbell region、跨 GPU 门铃包收发、Stage 递增与终态判定）、32 条目 doorbell buffer、collective/primitive 双译码器查找表、4 条目 collective command buffer、按 cache line 粒度把 tensor tile 分配到各 ROP 所在 L2 slice 的机制、symmetric tensor allocation（SymMalloc）的物理地址映射；② 实现 SM-initiated kernel 支持（GEMM 由 SM 发起）与三种 ring collective（AllReduce/AllGather/AllToAll）的 NCCL 式多阶段分解；③ 以 V100/H100/B200 三套架构参数化配置（H100：24 ROP/132 SM/50MB L2/3.35TBps/900GBps；B200：2 chiplet/48 ROP/148 SM/126MB L2/8TBps/1.8TBps）；④ 用 GEMM 参数取自 LLM FFN 层（Table II）与 Column-Linear/RowLinear/Expert-Parallelism AllToAll 三套并行模式构造 workload；⑤ Astra-Sim 侧改写 Chakra 执行图，把 GEMM 节点与 CC 节点按 RoCC 语义细粒度重叠。
- 开源情况。基于开源文档和论文，使用例子解释模拟器如何使用？作用是什么？至少具体到模拟器模拟性能的原理和模拟器输入到性能输出的全过程。
  - 开源情况：MGPUSim 开源（https://github.com/sarchlab/mgpusim，Go + Akita，AMD GCN3 默认建模、v5 起移除 NVIDIA 支持，README 提供 build/run 示例，`samples/fir`：`go build && ./fir -timing --report-all`，输出 metrics.csv/SQLite）；Astra-Sim 开源（https://github.com/astra-sim/astra-sim，`git clone --recurse-submodules` + `./build/astra_analytical/build.sh -c` 构建 analytical backend，输入 Chakra trace，输出 per-collective/系统级执行时间）；CACTI 开源（github.com/HewlettPackard/cacti）；Chakra trace 生成器 STG 开源。RoCC 本身论文未给出开源链接，web search 未能找到公开仓库（论文刚被 ISCA 2026 接收，artifact 可能未发布），无法确认是否开源。
  - 使用例子（MGPUSim，基于官方文档）：① 安装 Go，`git clone https://github.com/sarchlab/mgpusim && cd mgpusim/samples/<workload>`；② `go build` 编译模拟器可执行文件；③ `./<workload> -timing --report-all` 以时序模式运行（--report-all 输出全部统计）；④ 从 metrics.csv（或 akita_sim_*.sqlite3）读取 kernel 执行时间、cache/DRAM/互连统计。Astra-Sim 使用：`git clone --recurse-submodules git@github.com:astra-sim/astra-sim.git && ./build/astra_analytical/build.sh -c`，用 `--workload=<chakra trace>` 运行，网络后端可选 Analytical/Garnet(gem5)/NS3。
  - 模拟器输入到性能输出全过程（MGPUSim 周期级原理）：输入 = GEMM kernel + CC 配置（tensor 大小、tile 形状、并行模式 CL/RL/A2A、模型参数）+ 平台配置（Table III 的 SM/L1/L2/NoC/MPU/ROP/DRAM/互连参数、V100 或 H100/B200 架构、ROP 28-cycle 数据通路与 4 路 3-cycle ALU、4 并发 doorbell）→ Akita 离散事件引擎逐事件推进：SM 执行 tiled GEMM，某 warp 完成一个 tile 时执行 rocc_allreduce intrinsic → 经 atomic 数据通路带 doorbell flag 发往对应 MPU 的 ROP → doorbell manager 识别并写入 doorbell buffer → collective decoder 按 CollType+Stage 查表出 primitive、primitive decoder 译成 μOp 序列进 collective command buffer → 命令生成器每 cycle 发 4 个 μOp 到 4 个 ROP ALU：ReadDoorbell 取上一 rank 数据/本地 GEMM 结果、DepBarrier 校验 warp-tile 完成、Add 做归约、Write 写本地、RingDoorbell 构造门铃包（payload=归约结果）发往下一 rank（按 ring 顺序、对称物理地址免翻译）→ 跨 GPU 门铃经 GPU-GPU 互连（300GBps，full-mesh）传递，重复至终态 → 输出 GEMM/CC 执行时间、重叠比例（83.4%）、CC-only 延迟、争用下 GEMM 性能与各模型/并行模式加速比，归一化到 baseline 得 Figure 20-32。Astra-Sim 侧：输入 Chakra trace（STG 生成的 LLM FFN/注意力执行图）+ 重写后的 RoCC 重叠执行图 + 网络/计算配置 → 网络级模拟输出端到端模型训练时间 → 44%（小规模）/13-21%（32-256 GPU）加速比。作用：在周期级精度验证"复用 ROP 做 CC + 门铃消息 + primitive 分解"对 LLM 训练 compute-CC 重叠的收益与面积代价（2.4% L2 slice），并验证对 ROP 数量、互连延迟、ROP cache、部署位置（L2 侧 vs SM 侧）与新一代 AI GPU（H100/B200）的鲁棒性。
