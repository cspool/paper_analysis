## From Lab to Fleet: Building and Deploying a Practical Rowhammer Defense in Cloud SoCs

- 属于硬件架构的实现是什么？实验比较什么？
  - 实现 = Sigries，微软部署于 Azure Cobalt 200 SoC（Arm 云原生 SoC）内存控制器中的生产级 Rowhammer 防御硬件 IP（ISCA 2026 Industry Track，微软内部设计）。混合两类方案：light mode 用欠配置（under-provisioned）的 Misra-Gries 流式算法跟踪"hot"行（每个 DRAM bank 分为多个 sub-bank，每个 sub-bank 一个几十项以内的小计数器表，内存控制器 SRAM 以 set-associative 方式组织，每个 set 存一个 sub-bank 的计数器表，条目含 row address、counter、lock bit）；heavy mode 用行采样（row-sampling，每次 row activation 以概率 p 采样并按 aggressor 行处理，概率参数来自作者先前工作 [72]）。计数器值达 Rowhammer 阈值时发 DDR5 Directed Refresh Management (DRFM) 命令刷新 victim 行。核心机制：spillover counter 接近阈值时该 sub-bank 从 light 切到 heavy mode（Insight #3 的 gatekeeper 机制），切换按 sub-bank 独立进行；heavy mode 下用 shadow counting 跟踪 spillover 是否持续饱和，配合 heavy mode countdown 决定何时切回 light。实现要点还包括：per-bank DRFM 地址表遵守 DDR5 的 7.8µs DRFM 速率限制；clear bit 懒清零计数器省功耗；SRAM 状态用 parity+列交织（column multiplexing）保护并按表 IV 做保守修复；Dafny 形式化验证算法（发现 3 个 bug：clear bit 未清除、lock bit 置 0 而非 1、空条目查找未检查 lock 位）。
  - 实验比较什么 = 四个关键问题：(Q1) 无攻击时是否从不切到 heavy mode（heavy mode 有持续 DRAM 带宽开销）；(Q2) 攻击时哪些 sub-bank 切换 heavy mode；(Q3) Sigries 与 7 个 prior defenses 的性能比较，指标为两类：(a) DRFM 造成的 DRAM 带宽开销、(b) workload 的 stall（DRAM access delay 异常值）；(Q4) 面积/功耗开销。结果：所有 commodity workload 下 Sigries 从不离开 light mode、零 DRAM 带宽开销（因为无行在 32ms refresh window 内超过几百次 activation）；decahammer（10 面）和 omni-deca 被 light mode 完全遏制，megahammer（k 面）和 omni-mega 只让被攻击的 sub-bank 进入 heavy mode（omni-mega 最坏 6.8% 带宽开销）；仅 Graphene 和 PRAC 与 Sigries 性能相当（三者对 commodity workload 均无 DRFM、无 stall）；DREAM-R/PARA/PRA 常发 DRFM 消耗带宽，BlockHammer/Hydra/RRS 有 stall 异常值（BlockHammer 最坏 1.97ms 访问延迟）。面积：计数器 SRAM 占内存控制器面积 <10%。
- 模拟器名，模拟器链接（web search），或论文修改的模拟器。
  - 论文使用三层内部仿真框架（论文图 6）：(1) 内部 emulator（基于 QEMU [5]）运行 workload 生成指令 trace；(2) 内部 cycle-level SoC 架构模拟器（基于 Microsoft Asim [15]），建模乱序执行、分支预测器、TLB、cache 层次，输出到达每个内存控制器的 memory request trace（带时间戳）；(3) 内部 timing-accurate 内存控制器与 Rowhammer 模拟器 RHSim。三者均为微软内部工具，未开源、无公开链接；论文引用的公开对照模拟器为 Ramulator 2.0（https://github.com/CMU-SAFARI/ramulator），仅用于核对 prior defenses 的配置参数。论文 PDF 公开于 https://stefan.t8k2.com/publications/isca/2026/sigries.pdf。
- 模拟器模拟什么的性能，修改了什么。
  - RHSim 模拟内存控制器的请求调度、后台刷新 (REF)、刷新管理 (RFM)、定向刷新管理 (DRFM)。与 Ramulator/DRAMSim/DRAMSim3 等不同，RHSim 不建模 read/write/precharge DDR 命令，只模拟输入 trace 中的 row activation，且仅受行周期 tRC 约束；read/write 延迟通过全系统 SoC 模拟器给出的时间戳体现（作为每行 activation 的 earliest time）。此设计使 RHSim 远快于 prior 模拟器，并刻意移除任何会降低 activation 速率的因素，为 Rowhammer 防御制造最坏条件。修改了什么：在 RHSim 中实现 Sigries 及 7 个 prior defenses（BlockHammer、DREAM-R、Graphene、Hydra、PARA/PRA、PRAC、RRS），各 defense 按原文配置，有开源实现（如 Ramulator 2.0）的核对过配置。评估配置：除 Rowhammer 阈值外全部采用 production 值（阈值用比生产更保守的低值）；硬件平台 = Azure Cobalt 200 SoC 全系统（完整 core、mesh 互连、DDR5 配置）。

  - 开源情况：Sigries 硬件实现与三个模拟器均为微软内部，未开源（生产安全硬件，Rowhammer 阈值/面积等数据因机密隐去，图 9 等轴无数值）；论文仅公开 PDF。公开可获取的是被引用/对照的 Ramulator 2.0（https://github.com/CMU-SAFARI/ramulator）。联网确认：Sigries 无公开代码/模拟器仓库，无法确认更具体链接。
  - 输入→输出全过程（以 memcached 上的一次评估为例）：输入 = workload（Redis/Memcached/MySQL/Cassandra、SPEC2017 的 mcf 与 XZ、PARSEC 的 blackscholes/bodytrack/canneal/dedup/facesim/ferret/fluidanimate/freqmine/streamcluster/swaptions/x264、synthetic memstress；Rowhammer 攻击 = decahammer 10 面、megahammer k 面（k 保密）、omni-deca/omni-mega 全 bank 并行）的磁盘镜像在 QEMU 内部 emulator 中运行 → 生成指令 trace → Asim 内部 SoC cycle-level 模拟器按乱序 core/mesh/cache 推进，输出每个内存控制器的 row activation trace（带 earliest-time 时间戳）→ RHSim 以 tRC 约束重放 activation，逐 sub-bank 执行 Misra-Gries 计数器更新（命中条目计数、spillover counter 比较与行地址替换、DRFM 发布/计数器复位/lock 置位、clear bit 懒清零），spillover 达到阈值-1 时该 sub-bank 切 heavy mode（行采样 + shadow counting + heavy mode countdown），并模拟 DDR5 的 REF/RFM/DRFM 及 7.8µs DRFM 速率限制。输出 = 每 workload 的 DRFM 带宽开销百分比（无攻击时 0%）、max/p90/p50 DRAM access delay（stall）、每个 refresh window（32ms）内切换 heavy mode 的 sub-bank 数、保持 light mode 所需的最小计数器表尺寸（图 9）、面积开销（<10% 内存控制器面积）。作用：验证 Sigries 在无攻击时零开销、攻击时只惩罚被攻击 sub-bank、无性能异常值，满足"最小开销/无异常值/活性/低成本/灵活性/可配置安全"六大设计需求。
