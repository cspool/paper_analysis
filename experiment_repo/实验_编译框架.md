
## Streaming Tensor Programs (STeP)

- 属于编译框架的实现是什么？实验比较什么？
  - **实现**：STeP 是一种面向空间数据流加速器（SDA）的异步数据流编程抽象，可作为编译器 IR。其编译框架包括：
    1. **Symbolic Python Frontend**：提供类似 PyTorch 的 Python 编程接口，使用 SymPy 实现符号表达式系统，自动计算 off-chip memory traffic、on-chip memory requirement 和 operational intensity 等性能关键指标。支持 stream shape 验证（producer-consumer shape alignment）和符号变量替换（用于分析不同 input shape/control-flow 下的指标）。
    2. **Stream-centric IR**：以 stream 为核心表示，stream 具有编译时确定的 rank 和 data type。每个 stream 支持三种维度类型：static-regular、dynamic-regular、ragged。Stream 通过 stop tokens（$S_N$, $D$）嵌入逻辑 tensor 结构。
    3. **五类 STeP 算子**：(a) Off-chip memory operators（LinearOffChipLoad/Store, RandomOffChipLoad/Store）表达片下-片上数据传输；(b) On-chip memory operators（Bufferize, Streamify）显式管理片上 scratchpad；(c) Dynamic routing and merging operators（Partition, Reassemble, EagerMerge）支持 data-dependent control flow；(d) Higher-order operators（Map, Accum, Scan, FlatMap）应用硬件支持的计算函数；(e) Shape operators（Flatten, Reshape, Promote, Expand, Zip）仅修改 stop tokens 不改数据。
    4. **Rust Simulator Backend**：基于 Dataflow Abstract Machine (DAM) simulation framework [55]，集成 Ramulator 2.0 HBM 节点模拟片外内存时序，使用 Roofline 模型计算 higher-order operator 延迟：$\max(\frac{size\_of\_inputs}{on\_chip\_mem\_BW}, \frac{total\_FLOPs}{compute\_BW}, \frac{size\_of\_outputs}{on\_chip\_mem\_BW})$。
    5. **编译路径设想**（Section 6.1）：PyTorch → torch.compile → FX Graph → STeP subgraphs（通过遍历 FX graph node 并 lowering，优化 schedule 通过 index variables 指定）。
    - **实验比较**：
      - **Dynamic Tiling vs Static Tiling**：在 MoE layer (Qwen3-30B-A3B, Mixtral-8x7B) 上比较 cycle count 和 on-chip memory，static tiling 扫描 tile sizes（2-1024），dynamic tiling 自适应 batch dimension。
      - **Configuration Time-multiplexing vs 每 expert 独立配置**：sweep 共享同一 configure region 的 expert 数量，比较 compute utilization 和 resource usage。
      - **Dynamic Parallelization vs Static Coarse-grained/Interleaved Parallelization**：在 attention layer 上比较，KV cache length 分布来自 AzureLLMInferenceDataset。
      - **End-to-end Model**：Qwen3-30B-A3B 和 Mixtral-8x7B 完整模型，比较 optimized vs baseline 的 speedup 和 resource savings。
      - **Simulator Validation vs HDL**：SwiGLU layer 在 STeP cycle-approximate simulator 与 Bluespec SystemVerilog cycle-accurate HDL simulator 之间比较，Pearson correlation = 0.99。

- 硬件平台是什么，配置是什么。
  - **目标硬件**：Spatial Dataflow Accelerators (SDAs)，参考架构为 reconfigurable dataflow accelerators（如 SambaNova SN40L [33], Plasticine [35], Onyx [20]）。compute units 操作于 16×16 BFloat16 tiles。
  - **模拟器配置**：on-chip memory bandwidth = 64 bytes/cycle，off-chip memory bandwidth = 1024 bytes/cycle（匹配 SambaNova SN40L RDU 配置）。
  - **HDL 验证环境**：Bluespec SystemVerilog HDL model，cycle-accurate BlueSim simulator。HBM2 subsystem（8 stacks）通过 Ramulator 2.0 library calls 集成。on-chip memory bandwidth = 256 bytes/cycle。
  - **硬件环境**：模拟器运行于 x86-64 机器（推荐 ≥32GB RAM），Docker 容器内执行。完整实验约需 24.5 小时（Google Cloud C4-standard-8: 8 Intel Emerald Rapids vCPUs, 30GB memory）。

- 开源编译框架是什么。修改了什么。
  - **开源编译框架**：STeP **全新实现**（非修改已有编译器），包括 symbolic Python frontend 和 Rust simulator backend。
  - **开源仓库**：
    - https://github.com/stanford-ppl/step_artifact（Python frontend + Rust simulator + 实验脚本）
    - https://github.com/stanford-ppl/step-artifact-hdl（Bluespec SystemVerilog HDL 验证）
  - **License**：MIT License
  - **DOI**：https://doi.org/10.6084/m9.figshare.31095274
  - **依赖**：Docker, Git, Python 3, Bash。Docker 镜像包含所有依赖（Python, Rust, Bluespec, protobuf 等）。
  - **核心组件**：
    - **Symbolic Frontend**：Python 实现，使用 SymPy 进行符号表达式计算。提供 off-chip traffic、on-chip memory requirement 方程。支持 hierarchical tiling（将 STeP-level logical tiles 分解为硬件对齐的 16×16 physical tiles）。
    - **Rust Simulator**：基于 DAM framework [55] 实现。HBM node 模拟 Ramulator 2.0 时序。Operator initiation intervals 和 latencies 可配置以适配不同 SDA 硬件。

- 开源情况。基于开源文档和论文，使用例子解释编译框架如何使用？作用是什么？至少具体到编译框架输入到输出的全过程。
  - **使用流程**：
    1. **输入**：程序员使用 STeP symbolic Python frontend 编写程序，类似写 PyTorch 但使用 STeP operator 替代 PyTorch operator，并显式指定 schedule（parallelization, tiling, memory placement）。
    2. **Symbolic Frontend 处理**：Python frontend 验证 stream shape 对齐，使用 SymPy 计算符号化的 off-chip traffic 和 on-chip memory requirement 表达式。
    3. **Simulator 执行**：Rust simulator 读取 STeP graph，依据 DAM framework 进行 cycle-approximate 模拟。HBM node 基于 Ramulator 2.0 模拟片外内存时序，higher-order operators 通过 Roofline 模型计算延迟。
    4. **输出**：cycles, off-chip memory traffic, on-chip memory requirements, allocated compute resources, compute resource utilization, off-chip memory bandwidth utilization。
  - **具体例子**（简化 MoE 的 STeP graph 编译流程，Figure 7 + Listing 1）：
    ```
    # STeP symbolic Python frontend 代码示例（简化 MoE layer）
    # Step 1: 加载输入
    inp = LinearOffChipLoad(ref=..., base_addr=..., ...)  # [D_i, 1] shaped stream of [1,64] tiles
    # Step 2: Route - Partition 根据 selector 将 tokens 路由到不同 expert
    routed = Partition(inp, selector, num_consumers=2)      # [D_i, 1] per branch
    # Step 3: Pack to Tile - Flatten + Reshape + Accum 将 [1,64] tiles 打包为 [4,64]
    # Step 4: Broadcast - Reshape + Expand 展开以匹配 weight tile column dimension
    # Step 5: Load weight - LinearOffChipLoad-Ref 根据动态 reference stream 加载 weight
    # Step 6: Compute - Map (matmul) 执行矩阵乘法
    # Step 7: Merge - Accum + FlatMap + Reassemble 合并各分支输出
    ```
  - **DSE 工作流**：Frontend 提供符号化指标（快速比较设计点）→ Simulator 提供具体数值（精确 timing）→ 二者结合实现高效的 design space exploration。例如 dynamic tiling 实验中，static tiling 需 sweep tile sizes，而 STeP 的 frontend 可直接给出符号化的 memory-traffic trade-off。
